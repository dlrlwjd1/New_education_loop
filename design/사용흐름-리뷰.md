## 1. [화면 누락] AI 학습실 진입에 "학습 대상 선택" 화면이 없음

**근거 (수정 전)**

```
$ grep -rn 'href="#study"' *.dc.html | grep AI\ 학습실
```
12개 화면(`Main`, `Study`, `Roadmap`, `Review`, `Library`, `StudyHistory`, `BriefingHistory`, `ReviewQueue`, `RoadmapOverview`, `RoadmapEdit`, `Settings`, `Study` 자기 자신)의 사이드바 "AI 학습실"이 예외 없이 `#study`(`Study.dc.html`)로 직접 연결되어 있었다. 그런데 `Study.dc.html:74`는 이미 8턴이 오간 "완료" 배지가 붙은 특정 대화(TCP 3-way handshake)를 고정으로 보여주는 화면이다 — 선택 화면이 아니라 **결과 화면**이다.

동시에 자료실의 "학습 시작"(`Library.dc.html` 자료 3곳), 학습 기록의 "이어하기"(`StudyHistory.dc.html`), 브리핑의 "이어서 학습"(`Main.dc.html`)처럼 **서로 다른 의도의 진입점**이 전부 같은 이 화면 하나로 모였다.

**명세서와의 어긋남**

`웹전환_기능명세_및_개발가이드.md` F03(학습 시작 — 주제·자료·자동 제안) 1~3단계:

> 1. 사용자가 `주제 공부`, `로드맵 이어하기`, `자료로 공부`, `무엇을 할지 찾기` 중 하나를 선택한다.
> 2. 주제 공부에서는 주제명을 입력하고, 자료 기반 학습에서는 실제 로드맵·Phase·자료를 선택한다.
> 3. 입력이 없으면 오늘 복습 대상, 진행 중 로드맵, 로드맵 후보 2~3개 순으로 제안한다.

이 선택 단계 자체가 화면으로 존재하지 않았다.

**조치**

`StudyLaunch.dc.html`(제목: "무엇을 공부할까요?")을 새로 만들었다. F03 1~3단계를 그대로 화면 구성에 담았다:

- 주제 직접 입력 — 검색창 + "시작하기"
- 로드맵 이어하기 — 진행 중인 로드맵 카드(진행률·다음 Phase 포함)
- 자료에서 골라보기 — 자료실로 연결
- 오늘의 추천(자동 제안) — **오늘 복습 대상 → 진행 중 로드맵 → 로드맵 후보** 순서로 F03 3단계 규칙을 그대로 반영

**재배선 원칙과 예외**

대상이 정해지지 않은 진입(사이드바 "AI 학습실")만 `#study-launch`로 바꾸고, **이미 특정 대상이 정해진 진입은 그대로 `#study`로 남겼다** — 강제로 선택 화면을 한 번 더 거치게 하면 오히려 불필요한 단계가 되기 때문이다.

| 진입점 | 대상이 정해졌는가 | 연결 |
|---|---|---|
| 사이드바 "AI 학습실" (전 화면 공통) | 아니오 | `#study-launch` (변경) |
| 브리핑 "이어서 학습" (네트워크 서비스 카드) | 예 (그 로드맵) | `#study` (유지) |
| 로드맵 개요 "이어서 공부" | 예 (선택된 로드맵) | `#study` (유지) |
| 로드맵 만들기 완료 "학습 경로 만들기" | 예 (방금 만든 로드맵) | `#study` (유지) |
| 자료실 "학습 시작" | 예 (그 자료) | `#study` (유지) |
| 학습 기록 "이어하기" | 예 (그 세션) | `#study` (유지) |

**검증**: 아래 `grep`으로 12개 화면의 사이드바 링크가 모두 바뀌었는지, `Study.dc.html` 자기 자신도 포함해 확인했다.

```
$ grep -n 'AI 학습실' *.dc.html | grep 'href="#study"'
(결과 없음 — 전부 #study-launch로 교체됨)
```

**조치 (수정 후)**

```html
<!-- DB·DNS 복습 화살표 -->
<a class="row-arrow" href="#review-queue" aria-label="...">...</a>

<!-- DB 로드맵 "이어서 학습" -->
```

DB 항목 자체의 대화는 여전히 없지만, 클릭했을 때 최소한 그 항목이 실제로 보이는 목록/선택 화면에 도착한다 — "존재하지 않는 척 안내만 하기"에서 "실제로 갈 수 있는 가장 가까운 화면으로 보내기"로 바꿨다.

## 판단이 필요했던 애매한 점 — 정리 결과

### A. "AI 학습실" 메뉴가 화면 두 개(`StudyLaunch`/`Study`)를 가리키는데 라벨은 하나 → **그대로 둔다**

**추가로 확인한 근거**: 사이트에 이미 똑같은 패턴이 있다. `Roadmap.dc.html:63`과 `RoadmapEdit.dc.html:60`도 "로드맵" 메뉴를 `aria-current="page"`로 표시하면서 `href`는 자기 자신이 아니라 허브 화면인 `#roadmap-overview`를 가리킨다:
```html
<!-- Roadmap.dc.html:63 (로드맵 만들기 화면 안에서) -->
<a class="nav-link" href="#roadmap-overview" data-view="roadmap-overview" aria-current="page">로드맵</a>
```
즉 "로드맵 만들기 → 로드맵 수정 → 로드맵 개요"를 묶어 "로드맵" 섹션 하나로 보고, 그 섹션 안 어디에 있든 메뉴를 현재로 표시하되 클릭하면 섹션의 허브 화면으로 보내는 게 이 사이트가 이미 두 번 쓰고 있던 규칙이었다. `Study`/`StudyLaunch`를 "AI 학습실" 섹션 하나로 보고 같은 규칙을 적용하면 A는 새로운 문제가 아니라 **기존 규칙과 일치하는 사례**다. 코드를 바꾸지 않고 이 판단 근거만 남긴다.

### B. "대상이 정해지면 Launcher를 건너뛴다"는 규칙이 화면에는 안 드러남 → **그대로 둔다**

이 규칙은 진입 경로에 따라 다음 화면이 달라지는 정상적인 제품 동작이지, 사용자가 그 이유를 화면에서 설명받아야 하는 종류의 정보가 아니다. 이미 대상이 정해진 진입(자료 클릭, 로드맵 이어하기)에서 확인 화면을 또 거치게 하면 그게 오히려 불필요한 단계가 된다. 실제 서비스에서 흔한 "빠른 경로 vs 탐색 경로"의 차이이므로 별도 안내 없이 둔다.

### C. `StudyLaunch.dc.html` 안의 DB 설계 카드가 여전히 데모 버튼 → **그대로 둔다**

6~7번, 10번 항목과 같은 이유다 — 이 시안 전체에 실제로 완성된 대화가 TCP 3-way handshake 하나뿐이라는 제약의 연장선이지, `StudyLaunch`만의 새로운 문제가 아니다. `data-demo` 안내 문구가 이미 붙어 있어(`StudyLaunch.dc.html:81`) 방치된 죽은 버튼도 아니다.

### D. 로드맵 개요의 카드가 클릭 가능한 것처럼 보이지만 실제로는 아무 것도 없음 → **해결**

**근거 (수정 전)** — `RoadmapOverview.dc.html:15`:
```css
.roadmap-mini{padding:16px 15px;border-radius:12px;cursor:pointer}
.roadmap-mini.active{background:#eaf2df}
```
`cursor:pointer`로 "골라서 상세를 바꿔 보는" 탭처럼 보이게 해놓았는데, 실제 마크업(`RoadmapOverview.dc.html:77-78`)은 `<div>`일 뿐이고 `href`도 `button`도 `data-demo`도 전혀 없었다. 다른 화면의 같은 클래스(`Main.dc.html`, `Roadmap.dc.html`, `Review.dc.html`, `StudyLaunch.dc.html`의 `.roadmap-mini`)에는 애초에 `cursor:pointer`가 없다 — 이 화면에서만 실수로 클릭 가능한 것처럼 스타일링되어 있었다.

**조치 (수정 후)**
```css
.roadmap-mini{padding:16px 15px;border-radius:12px}
```
`cursor:pointer`만 제거했다. `.active` 배경색은 "지금 오른쪽 상세 패널에 표시 중인 로드맵"이라는 정적인 표시로는 정직하므로 남겨뒀다 — 실제로 선택을 바꾸는 기능(카드 클릭 → 상세 패널 전환)까지 만들려면 `Study.dc.html`의 "로드맵 모드" 토글처럼 `DCLogic` 컴포넌트와 다른 로드맵의 Phase 데이터가 더 필요해서, 이번에는 "클릭 가능해 보이지 않게" 정도로만 정리했다.

## 검증

수정 후 25개 아트보드 파일 전체(화면 13개 + 설명 박스 11개 + FlowMap)에 대해 세 가지를 스크립트로 재검증했다.

```
ALL TAG-BALANCE OK        # HTML 태그 짝 안 맞는 곳 없음
ALL ICONS RESOLVED         # <use href="#i-..."> 가 가리키는 아이콘 심볼이 전부 정의돼 있음
ALL NAV LINKS VALID        # href="#xxx" 형태의 모든 화면 이동 링크가 실제 존재하는 13개 화면 중 하나를 가리킴
```

세 번째 검증이 이번 작업의 핵심이다 — 존재하지 않는 화면을 가리키는 링크(예전의 `#roadmap-edit` 부재)나, 존재하는데 안 쓰인 링크(예전의 `수정`, `취소`, `기록 보기` 등)가 더는 없다는 뜻이다. 캔버스 링크도 이 수정 사항을 반영해 버전 14로 재게시했다.

## 이번에도 문제 삼지 않은 것 (근거)

- **자료실·학습 기록·브리핑 기록의 "상세보기"/"이력 보기"**: 실제로 갈 수 있는 더 나은 화면이 없다(그 화면 자체가 이미 목록/열람 화면이라 더 보낼 곳이 없음). `data-demo` 안내가 이미 붙어 있어 방치된 죽은 버튼이 아니다. `화면-현황.md`의 "남은 과제"에 이미 기록됨.

- **복습 계열(`ReviewQueue → Review`) 흐름 자체**: 목록에서 항목을 고른 뒤에만 대화로 들어가는 구조가 F06과 일치해 문제 없음.
