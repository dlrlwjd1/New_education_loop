## 중단 규칙

### 3회 규칙 — 가장 중요하다

**같은 문제로 2~3번 교정에 실패하면 프롬프트를 더 고치지 않는다.**

서로 독립적인 여러 출처가 같은 숫자에 도달했다. 대응은 셋 중 하나다.

1. `/clear` 후 **배운 것을 반영한 새 프롬프트**로 다시 시작
2. 세션을 버리고 **다른 에이전트/모델**에 재배정
3. 직접 한다 — 맡길 작업이 아니었다는 신호일 수 있다

**왜 되나**: 실패한 시도가 컨텍스트에 쌓이면 그 실패 방향이 계속 참조된다. 새 세션은 그 오염이 없다.

### 되감기는 git이 한다

- 되돌릴 때는 **git을 쓴다.** 에이전트의 되돌리기 기능이 아니다
- 체크포인트/rewind 기능은 **git 대체가 아니다** — Bash 명령이나 외부 프로세스가 만든 변경은 스냅샷에 안 잡힌다
- 성공한 작업마다 커밋한다. 새 기능은 **깨끗한 상태에서 시작**한다
- 되감기가 있으므로 **위험한 시도를 일부러 해 보는** 운용도 가능하다. 안전망이 있을 때만

### 에러가 계속되면 원인 목록부터

바로 고치게 시키지 말고 **가능한 원인 목록을 먼저 만들게** 한다. 그다음 각 가설을 **실제로 코드를 실행해 확인**시킨다.

가설을 실행으로 확인하지 않으면 그럴듯한 가짜 설명이 걸러지지 않는다. **인시던트 중 "그건 불가능하다"는 단언은 특히 의심한다.**

## 흔한 실패 패턴

### 1. Kitchen sink 세션

한 세션에 무관한 작업을 계속 쌓는다. 컨텍스트가 오염되고 초기 제약이 잊힌다.

→ **무관한 작업 사이에는 `/clear`한다.** 세션은 싸다.

### 2. 반복 교정 (3회 규칙 위반)

"아니 그게 아니라"를 다섯 번 반복한다.

→ 위 3회 규칙.

### 3. 과잉 규칙 파일

CLAUDE.md에 규칙을 계속 쌓는다. **비대해지면 실제 지시가 묻혀서 통째로 무시된다.**

→ 200줄 안쪽. 가끔 필요한 것은 스킬로. 자세한 것은 [Phase 2](02%20Phase%202%20-%20컨텍스트를%20운용한다.md).

⚠️ **최신 모델일수록 세세한 금지 규칙이 해가 된다.** "절대 여러 문단 docstring 쓰지 마라" 같은 것보다 "주변 코드 스타일에 맞춰라"가 낫다.

### 4. Trust-then-verify 갭

"됐다"는 말을 믿고 넘어간 뒤 나중에 발견한다.

→ [Phase 5](05%20Phase%205%20-%20검증%20게이트를%20건다.md)의 증거 요구. 주장이 아니라 테스트 출력·실행 결과·스크린샷.

### 5. 무한 탐색

에이전트가 코드베이스를 계속 읽기만 하고 진전이 없다.

→ 범위를 좁혀 준다. 파일을 명시하거나, 조사를 서브에이전트로 격리해 요약만 받는다.

### 6. 컨텍스트 오염을 모르고 계속 밀기

창이 안 찼는데 품질이 떨어진다. **사용률 70~80%에서 저하가 관찰된다.**

증상 — 이미 요약한 파일을 다시 열기 · 초기 제약 망각 · 같은 도구 반복 호출.

→ [Phase 2](02%20Phase%202%20-%20컨텍스트를%20운용한다.md)의 40~60% 압축 규율.

### 7. 슬롯머신 효과 ⚠️

**재생성이 쉬워서 강박적으로 다시 돌리게 된다.** 생성 속도가 이해 속도를 추월하면 번아웃이 온다.

이건 기술 문제가 아니라 작업 방식 문제다. 커뮤니티에서 "에이전틱 코딩이 나를 태우고 있다"는 논의가 반복된다.

→ 대응
- **읽지 않은 코드를 머지하지 않는다.** 이해 속도가 상한이다
- 재생성 횟수에 스스로 상한을 둔다 (3회 규칙이 여기도 적용된다)
- [Phase 7](07%20Phase%207%20-%20병렬로%20굴린다.md)의 동시 실행 상한을 **리뷰 능력 기준**으로 정하는 이유가 이것이다
- 병렬 개수를 늘리는 것이 항상 처리량을 늘리지 않는다 — 조정 비용이 비선형으로 증가한다

## 무엇을 맡기지 않는가

| 맡긴다 | 맡기지 않는다 |
|---|---|
| 버그 수정 | 복잡한 리팩터링 |
| UI 조정 | 보안 민감 작업 |
| 테스트 보강 | 프로덕션 크리티컬 이슈 |
| 문서 갱신 | 모호한 과제 (먼저 명확히 한다) |
| 대량 반복 변경 | **내가 배우는 것이 목적인 과제** |

마지막 항목이 학습 저장소를 운영하는 입장에서 특히 중요하다. **배우려고 하는 일을 에이전트에 맡기면 배움이 사라진다.** [Phase 11](11%20Phase%2011%20-%20캡스톤%20운용%20표준.md)의 운용 규범에 이 항목을 반드시 넣는다.

## 흔한 설정 실수

- **지속 규칙을 매 프롬프트에 반복해 넣는다** → 규칙 파일이나 스킬로 옮긴다
- **빌드/테스트 실행법을 안 알려 준다** → 에이전트가 자기 작업 결과를 못 본다. 가장 큰 낭비
- **계획을 생략한다** → 파일 3개 이상 얽히면 반드시 계획부터
- **권한을 대충 넓게 연다** → [Phase 6](06%20Phase%206%20-%20권한과%20샌드박스.md)의 클래스 설계
- **한 프롬프트에 다섯 가지를 넣는다** → 한 번에 하나씩

## 사장된 관행

시간이 지나 더 이상 권장되지 않는 것들이다. 오래된 글을 읽을 때 참고한다.

|---|---|
| 마법의 프롬프트 찾기 | 컨텍스트·설정 엔지니어링 |
| 매 행동을 수동 승인 | **클래스별 위임 설계** (승인 피로로 무력화됨) |
| 구현 미러링 유닛 테스트 | 계약·속성 테스트 |
| 선행 정보 덤프 | progressive disclosure |
| 도구 전용 규칙 파일을 각자 유지 | 공통 규격 + 얇은 종속 계층 |
| 리뷰를 없앤 완전 자율 | 품질 지표 악화로 반박됨 |
