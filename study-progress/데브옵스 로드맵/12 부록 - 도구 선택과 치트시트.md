# 부록 — 도구 선택과 치트시트

로드맵을 진행하다 「어느 쪽을 쓸까」에서 멈출 때 보는 문서다. 각 항목은 판단 기준과, 근거가 되는 강의를 함께 적었다.

## CI 서버 — Jenkins vs GitHub Actions

| 기준 | Jenkins | GitHub Actions |
|---|---|---|
| 운영 부담 | 서버·플러그인·보안을 직접 관리 | 없음 (SaaS) |
| 초기 비용 | 서버 비용 | 무료 한도 있음 |
| 유연성 | 플러그인으로 거의 무엇이든 | 액션 생태계 안에서 |
| 사내망 접근 | 쉬움 (같은 네트워크에 둘 수 있다) | 셀프호스트 러너 필요 |
| 학습 곡선 | 높음 | 낮음 |
| 저장소와의 거리 | 별도 시스템 | 저장소 안 |

- **소규모 팀·GitHub 사용·사내망 접근 불필요** → GitHub Actions. Phase 7의 실습이 이쪽 기준이다.
- **사내 시스템 배포·복잡한 승인 흐름·기존 Jenkins 자산** → Jenkins.

## 배포 방식 — push vs GitOps(pull)

| 기준 | CI가 밀어 넣기 (Phase 7) | GitOps (Phase 8) |
|---|---|---|
| 클러스터 자격 증명 | CI가 들고 있어야 함 | 클러스터가 Git만 읽음 |
| 현재 상태 확인 | 파이프라인 로그를 봐야 함 | Git이 곧 선언된 상태 |
| 드리프트 | 감지 안 됨 | 계속 맞춰 줌 |
| 도입 비용 | 낮음 | 도구 하나 추가 운영 |

- **처음 만들 때** → push 방식으로 시작한다. 동작하는 파이프라인이 먼저다.
- **클러스터가 여럿이거나, CI에 클러스터 권한을 주기 어려울 때** → GitOps.
- 근거 강의: [GitOps](../../courses/mooc/DevOps%20and%20SRE/IBM%20DevOps%20and%20Software%20Engineering/12%20Continuous%20Integration%20and%20Delivery/Module%204%20-%20Explore%20DevOps%20Pipeline%20Tools%20and%20Best%20Practices/04%20Introduction%20to%20GitOps.md) · [ArgoCD](../../courses/mooc/DevOps%20and%20SRE/IBM%20DevOps%20and%20Software%20Engineering/12%20Continuous%20Integration%20and%20Delivery/Module%204%20-%20Explore%20DevOps%20Pipeline%20Tools%20and%20Best%20Practices/05%20GitOps%20with%20ArgoCD.md)

## 파이프라인 실행 위치 — 클러스터 밖 vs 안

- **밖 (Jenkins, GitHub Actions)**: 클러스터가 죽어도 파이프라인은 산다. 설정이 단순하다.
- **안 (Tekton, OpenShift Pipelines)**: 파이프라인도 쿠버네티스 리소스라 같은 방식으로 관리·확장된다. 클러스터 운영 능력이 전제된다.
- 근거 강의: [Tekton 입문](../../courses/mooc/DevOps%20and%20SRE/IBM%20DevOps%20and%20Software%20Engineering/12%20Continuous%20Integration%20and%20Delivery/Module%203%20-%20Continuous%20Delivery/07%20Introduction%20to%20Tekton%20and%20Pipelines.md)

## IaC — Terraform vs CloudFormation vs Ansible

| 도구 | 잘하는 일 | 안 맞는 일 |
|---|---|---|
| Terraform | 클라우드 리소스 생성·변경·삭제. 멀티 클라우드 | 서버 안의 설정, 절차적 작업 |
| CloudFormation | AWS 전용. 상태를 AWS가 관리 | AWS 밖 |
| Ansible | 서버 안의 패키지·설정·서비스. 절차적 작업 | 대규모 리소스 생성·상태 추적 |

- **경험 법칙**: 만드는 것 = Terraform / 안을 채우는 것 = Ansible. 쿠버네티스를 쓰면 후자가 컨테이너 이미지로 옮겨 가 Ansible 몫이 줄어든다.
- 근거 강의: [Terraform vs Ansible](../../courses/mooc/DevOps%20and%20SRE/Master%20DevOps%20-%20CI-CD,%20Automation%20and%20Monitoring/Course%203%20-%20Infrastructure%20as%20Code%20and%20Monitoring/Module%201%20-%20Provisioning%20using%20Terraform/10%20Terraform%20vs%20Ansible%20-%20Differences%20and%20Similarities.md) · [사용 사례 비교](../../courses/mooc/DevOps%20and%20SRE/Master%20DevOps%20-%20CI-CD,%20Automation%20and%20Monitoring/Course%203%20-%20Infrastructure%20as%20Code%20and%20Monitoring/Module%201%20-%20Provisioning%20using%20Terraform/11%20Terraform%20vs%20Ansible%20-%20Configuration%20Approach%20and%20Use%20Cases.md) · [구성 관리 도구 비교](../../courses/mooc/DevOps%20and%20SRE/Master%20DevOps%20-%20CI-CD,%20Automation%20and%20Monitoring/Course%202%20-%20Continuous%20Integration%20and%20Continuous%20Deployment/Module%203%20-%20Configuration%20Management%20with%20Ansible/05%20Comparative%20Analysis%20of%20Configuration%20Management%20Tools%20-%20Ansible%20vs%20Others.md)

## 배포 전략 — 롤링 vs 블루-그린 vs 카나리

| 전략 | 필요한 것 | 언제 |
|---|---|---|
| 롤링 업데이트 | 프로브 설정만 | 기본값. 대부분 이걸로 충분하다 |
| 블루-그린 | 두 배의 자원, 트래픽 스위치 | 즉시 전환·즉시 롤백이 필요할 때 |
| 카나리 | 트래픽 분할 수단, 판정할 지표 | 변경 위험이 크고 사용자 영향을 미리 재고 싶을 때 |

- **카나리는 관측성이 전제다.** 지표가 없으면 「조금만 보내기」의 의미가 없다. → **개발운영 로드맵**
- 근거 강의: [배포 전략](../../courses/mooc/DevOps%20and%20SRE/Foundations%20of%20Site%20Reliability%20Engineering%20Training/Module%204%20-%20Reliability%20Engineering%20%26%20Deployments/03%20Deployment%20Strategies%20in%20Reliability%20Engineering.md) · [블루-그린·카나리 데모](../../courses/mooc/DevOps%20and%20SRE/Foundations%20of%20Site%20Reliability%20Engineering%20Training/Module%204%20-%20Reliability%20Engineering%20%26%20Deployments/04%20Demo%20-%20Implementing%20SRE%20with%20Blue-Green%20and%20Canary%20Deployment.md)

## 상태가 있는 것을 어디에 둘까

1. **관리형 서비스** (RDS, Cloud SQL 등) — 가능하면 이것. 백업·업그레이드·고가용성을 위임한다.
2. **StatefulSet + PVC** — 클러스터 안에 둬야 할 때. 운영 부담이 실제로 발생한다.
3. **Deployment + PVC** — 하지 않는다. 파드 이름과 볼륨의 대응이 보장되지 않는다.

## 외부 노출 — NodePort vs LoadBalancer vs Ingress

- **NodePort**: 로컬·개발용. 포트 번호가 지저분하고 노드 IP에 의존한다.
- **LoadBalancer**: 서비스마다 클라우드 LB가 하나씩 생긴다. 서비스가 늘면 비용이 곱해진다.
- **Ingress**: LB 하나 뒤에서 경로·호스트로 분기. **실서비스의 기본 선택.** HTTPS 인증서도 여기서 처리한다.
- 근거 강의: [Service 네 종류 비교](../../courses/mooc/DevOps%20and%20SRE/Master%20DevOps%20-%20CI-CD,%20Automation%20and%20Monitoring/Course%204%20-%20Containerization%20and%20Orchestration/Module%204%20-%20Kubernetes%20Networking%20and%20Storage/15%20Services%20-%20Demonstration%20-%20ClusterIP,%20NodePort,%20LoadBalancer,%20and%20External%20Name%20for%20External%20Resource%20Mapping.md) · [LB와 Ingress](../../courses/udemy/Microservices%20with%20Node%20JS%20and%20React/Section%204%20-%20Orchestrating%20Collections%20of%20Services%20with%20Kubernetes/28%20Load%20Balancers%20and%20Ingress.md)
