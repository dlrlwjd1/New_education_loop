# 부록 — 기획·데브옵스와의 연결

명세는 홀로 서지 않는다. **앞에는 「무엇을 왜 만드는가」가 있고, 뒤에는 「어떻게 배포하고 지키는가」가 있다.** 이 저장소의 다른 로드맵들이 그 앞뒤를 담당한다.

## 12-A. 전체 흐름에서 SDD의 자리

```
[무엇을 왜 만드나]            [어떻게 만드나]           [어떻게 내보내나]      [어떻게 지키나]
   PM 로드맵           →     스펙 주도 개발 로드맵    →   데브옵스 로드맵    →   개발운영 로드맵
   문제 정의·PRD             명세 → 구현 → 검증          CI/CD·쿠버네티스        SLO·관측성·장애 대응
   사용자 스토리                                          테스트/보안 게이트
```

| 경계 | 넘어가는 것 | 관련 문서 |
|---|---|---|
| 기획 → SDD | PRD·사용자 스토리 → **기능 명세** | 12-B |
| SDD → 데브옵스 | 명세의 Testing 항목 → **CI 게이트** | 12-C |
| 데브옵스 → 운영 | 배포된 기능 → **SLI/SLO** | 12-D |

## 12-B. 앞쪽 — PRD·사용자 스토리와 기능 명세는 무엇이 다른가

| | PRD / 사용자 스토리 | 기능 명세 (SDD) |
|---|---|---|
| 독자 | 사람 (이해관계자·팀) | **에이전트** (그리고 리뷰어) |
| 답하는 질문 | 왜 만드나, 누구를 위해, 성공은 무엇인가 | 무엇이 만들어져야 하나, 어디를 건드리나 |
| 성공 기준 | 사용자·사업 지표 | 「됐다/안 됐다」 판정 조건 |
| 수명 | 기능이 살아 있는 동안 | 구현이 끝나면 아카이브 |
| 구현 지시 | 없음 (있으면 안 된다) | 있음 (파일·패턴·접점) |

**둘 다 필요하다.** PRD 없이 명세만 쓰면 「잘 만들었는데 아무도 안 쓰는 기능」이 나오고, 명세 없이 PRD만 넘기면 에이전트가 범위를 스스로 정한다.

관련 로드맵: [PM 로드맵](../PM%20로드맵/README.md)

- [Phase 3 - 솔루션 발견과 검증](../PM%20로드맵/03%20Phase%203%20-%20솔루션%20발견과%20검증.md) — 무엇을 만들지 정하는 단계. **명세를 쓰기 전에 끝나 있어야 한다**
- [Phase 4 - 실행 애자일과 스프린트](../PM%20로드맵/04%20Phase%204%20-%20실행%20애자일과%20스프린트.md) — 사용자 스토리와 백로그. 스토리 하나가 명세 하나에 대응하는 경우가 많다

> **연결 지점**: 사용자 스토리의 「인수 조건(acceptance criteria)」이 명세의 「Testing / Validation」 칸으로 그대로 내려온다. [Phase 3](03%20Phase%203%20-%20%EA%B8%B0%EB%8A%A5%20%EB%AA%85%EC%84%B8%20%EC%9E%91%EC%84%B1.md)의 3-E(Given/When/Then)가 그 다리다.

## 12-C. 뒤쪽 — 명세의 검증 항목이 CI 게이트가 된다

[Phase 5](05%20Phase%205%20-%20%EA%B2%80%EC%A6%9D%20%EB%A6%AC%EB%B7%B0%20%ED%85%8C%EC%8A%A4%ED%8A%B8%20%EA%B0%90%EC%82%AC.md)에서 만든 검증 3층은 사람이 손으로 돌리는 것부터 시작한다. 그것을 파이프라인에 고정하는 것이 데브옵스 쪽 일이다.

| SDD 쪽 (이 로드맵) | 데브옵스 쪽 |
|---|---|
| 명세의 Testing 항목 | PR 테스트 게이트 |
| 감사 서브에이전트 | 정적 분석(SAST)·의존성 스캔 |
| 사람 리뷰 체크리스트 | 브랜치 보호 규칙 |
| 에이전트가 추가한 라이브러리 확인 | 의존성 취약점 게이트 |

관련 로드맵: [데브옵스 로드맵](../데브옵스%20로드맵/README.md)

- [Phase 10 - 테스트와 보안 게이트](../데브옵스%20로드맵/10%20Phase%2010%20-%20%ED%85%8C%EC%8A%A4%ED%8A%B8%EC%99%80%20%EB%B3%B4%EC%95%88%20%EA%B2%8C%EC%9D%B4%ED%8A%B8.md) — **게이트 설계표**가 있다. 이 로드맵 [Phase 5](05%20Phase%205%20-%20%EA%B2%80%EC%A6%9D%20%EB%A6%AC%EB%B7%B0%20%ED%85%8C%EC%8A%A4%ED%8A%B8%20%EA%B0%90%EC%82%AC.md)의 3층 구조와 대응시켜 읽는다

- [Phase 3 - 빌드 자동화와 CI](../데브옵스%20로드맵/03%20Phase%203%20-%20%EB%B9%8C%EB%93%9C%20%EC%9E%90%EB%8F%99%ED%99%94%EC%99%80%20CI.md) — 테스트를 자동으로 돌리는 단계

또한 [Phase 6](06%20Phase%206%20-%20%EC%9E%AC%EA%B3%84%ED%9A%8D%EA%B3%BC%20MVP.md)의 6-E(마이그레이션·배포)가 데브옵스 로드맵과 직접 겹친다.

## 12-D. 그 뒤 — 만든 기능이 실제로 괜찮은지

명세의 「Testing」은 **기능이 동작하는가**를 본다. 운영은 **사용자에게 실제로 괜찮은가**를 본다. 다른 질문이다.

관련 로드맵: **개발운영 로드맵**

- **Phase 1 - SRE 기초와 SLO·에러 예산** — 명세의 완료 기준과 SLO는 층이 다르다
- **Phase 9 - 장애 대응·사후 분석·토일** — 사후 분석의 후속 조치가 다음 명세의 입력이 된다

## 12-F. 이 저장소가 그 자체로 예시다

이 로드맵의 [Phase 9](09%20Phase%209%20-%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B5%90%EC%B2%B4%EC%99%80%20%ED%91%9C%EC%A4%80.md) 과제 3번에서 언급한 대로, 이 저장소 자체가 도구 중립 컨텍스트 구조의 예다.

- **`AGENTS.md`** — **규칙의 단일 원본.** 프로젝트 구조·명명 규칙·워크플로가 모두 여기 있다
- **`CLAUDE.md`** — `AGENTS.md`를 참조만 한다. 도구별 파일에 규칙을 중복 작성하지 않는다는 원칙
- `.claude/skills/study/SKILL.md` — 반복 작업(강의 Q&A 학습 + 진행 기록)을 스킬로 굳힌 예. [Phase 7](07%20Phase%207%20-%20%EC%9B%8C%ED%81%AC%ED%94%8C%EB%A1%9C%20%EC%9E%90%EB%8F%99%ED%99%94.md)의 7-G 「자동화 후보」 중 「반복하는 작업」에 해당한다

자기 프로젝트의 컨텍스트 구조를 잡을 때 이 두 파일의 관계를 그대로 베낄 수 있다.
