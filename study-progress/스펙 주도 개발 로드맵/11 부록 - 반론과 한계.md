# 부록 — 반론과 한계

**SDD가 항상 답은 아니다.** 이 부록은 로드맵의 전제를 공격하는 자료를 모았다. Phase 3에서 명세를 쓰다 「이거 시간 낭비 아닌가」 싶을 때 읽는다.

## 11-A. 「명세 대신 프로토타입을 만들어라」

메인: Matt Pocock Skills

이 로드맵과 정면으로 충돌하는 주장이다. **읽을 가치가 가장 크다.**

- [ ] [2026-07-23 Dont waste time on specs - prototype instead.md](../../courses/youtube/Matt%20Pocock%20Skills/2026-07-23%20Dont%20waste%20time%20on%20specs%20-%20prototype%20instead.md) — **핵심 주장**: 아직 제품의 모양을 모르는 상태에서 상세 명세를 쓰면 **확인되지 않은 설계 결정을 텍스트에 고정**하게 된다. 명세는 「이미 아는 요구사항을 전달하는」 데는 좋지만 「어떤 디자인이 나은가」처럼 **답을 모르는 질문에는 대역폭이 낮다.** AI로 프로토타입 제작 비용이 낮아졌으므로, 폐기 가능한 고충실도 프로토타입으로 질문에 먼저 답하고 그 결과를 명세의 근거로 쓴다

### 이 로드맵은 이 반론을 어떻게 흡수하는가

**충돌이 아니라 순서 문제다.** 실제로 [Phase 3](03%20Phase%203%20-%20%EA%B8%B0%EB%8A%A5%20%EB%AA%85%EC%84%B8%20%EC%9E%91%EC%84%B1.md)의 3-B가 이 순서를 그대로 쓴다 — DevStash도 UI 프로토타입을 먼저 만들고 그 결과로 명세를 썼다.

| 상황 | 무엇을 먼저 |
|---|---|
| 만들 것이 명확하다 (요구사항이 이미 있다) | **명세** |
| 「어떤 게 나은지」 모른다 (디자인·UX·아키텍처 선택) | **프로토타입** → 결과를 명세에 반영 |
| 외부 API·낯선 라이브러리를 써야 한다 | **리서치** → 명세 ([부록 10](10%20%EB%B6%80%EB%A1%9D%20-%20%EB%AA%85%EC%84%B8%20%ED%85%9C%ED%94%8C%EB%A6%BF%EA%B3%BC%20%EC%8B%A4%EB%AC%BC%20%EC%98%88%EC%8B%9C.md)의 리서치 문서) |
| 이미 있는 것을 고친다 | **명세** (범위 통제가 핵심이라서) |

> **판단 기준 한 줄**: 명세에 쓰려는 문장 중 「이게 맞는지 확신이 없다」가 절반을 넘으면, 그건 명세가 아니라 프로토타입으로 답할 질문이다.

## 11-F. 언제 SDD를 쓰지 않나

위 자료들을 종합한 판단표다.

| 상황 | 권장 | 이유 |
|---|---|---|
| 한 파일 안의 작은 수정 | **명세 없이** | 명세 쓰는 시간이 고치는 시간보다 길다 |
| 무엇을 만들지 아직 모름 | 프로토타입 먼저 | 11-A |
| 버려질 실험 코드 | 명세 없이 | 11-C |
| 낯선 외부 시스템 연동 | 리서치 먼저 | [부록 10](10%20%EB%B6%80%EB%A1%9D%20-%20%EB%AA%85%EC%84%B8%20%ED%85%9C%ED%94%8C%EB%A6%BF%EA%B3%BC%20%EC%8B%A4%EB%AC%BC%20%EC%98%88%EC%8B%9C.md) |
| 여러 화면·파일에 걸치는 기능 | **명세** | 범위 통제가 목적 |
| 남이(또는 미래의 내가) 리뷰해야 함 | **명세** | 대조 기준이 필요 |
| 보안·결제·권한 영역 | **명세 + 감사** | 빠뜨리면 비용이 크다 |
| 이미 있는 코드를 고침 | **명세** | 「개선」 이탈을 막아야 한다 |
| 같은 작업을 반복함 | 명세보다 **스킬** | [Phase 7](07%20Phase%207%20-%20%EC%9B%8C%ED%81%AC%ED%94%8C%EB%A1%9C%20%EC%9E%90%EB%8F%99%ED%99%94.md) |

> **가장 큰 함정은 「명세를 쓰는 것」이 목적이 되는 것이다.** 명세의 목적은 ① 에이전트의 범위를 좁히고 ② 결과를 대조할 기준을 남기는 것 두 가지다. 이 둘이 필요 없는 작업에는 쓰지 않는다.

## 11-G. 그래도 남는 것

반론을 다 받아들여도 무너지지 않는 부분이다.

- **컨텍스트 문서**([Phase 2](02%20Phase%202%20-%20%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%EC%99%80%20%ED%97%8C%EB%B2%95.md))는 프로토타입을 만들 때도 필요하다. 반론자들도 여기는 공격하지 않는다.
- **코드베이스 가독성**([Phase 8](08%20Phase%208%20-%20%EB%A0%88%EA%B1%B0%EC%8B%9C%20%EC%BD%94%EB%93%9C%EB%B2%A0%EC%9D%B4%EC%8A%A4%EC%97%90%20%EB%8F%84%EC%9E%85%ED%95%98%EA%B8%B0.md))은 어떤 방식으로 일하든 이득이다.
- **검증 3층 구조**([Phase 5](05%20Phase%205%20-%20%EA%B2%80%EC%A6%9D%20%EB%A6%AC%EB%B7%B0%20%ED%85%8C%EC%8A%A4%ED%8A%B8%20%EA%B0%90%EC%82%AC.md))는 명세가 없어도 필요하다.
- **스킬**([Phase 7](07%20Phase%207%20-%20%EC%9B%8C%ED%81%AC%ED%94%8C%EB%A1%9C%20%EC%9E%90%EB%8F%99%ED%99%94.md))은 프로토타입 워크플로에도 그대로 쓰인다.

명세 자체가 논쟁 대상이지, 로드맵의 나머지는 대체로 합의돼 있다.
