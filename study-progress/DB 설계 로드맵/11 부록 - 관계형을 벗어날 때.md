# 부록 — 관계형을 벗어날 때

이 로드맵의 본편은 관계형 설계다. 이 부록은 **"관계형이 답이 아닌 경우를 알아보는 것"** 이 목적이다. 순서대로 다 볼 필요는 없고, 실제로 그런 데이터를 만났을 때 해당 절만 본다.

> ⚠️ **정규화를 배우기 전에 이 부록을 보지 않는다.** "스키마 없이도 되네"가 먼저 남으면 [Phase 4](04%20Phase%204%20-%20정규화와%20함수%20종속.md)를 배울 이유가 사라진다. [Phase 6](06%20Phase%206%20-%20물리%20모델과%20무결성.md) 이후에 온다.

## 판단 정리 — 관계형을 벗어나야 하는 신호

| 신호 | 후보 |
|---|---|
| 한 "레코드"의 필드가 케이스마다 다르고, 그 다름 자체가 정상이다 | 문서형 (MongoDB) |
| 조회가 전부 단일 키 기준이고 범위 스캔도 키 순서로 끝난다 | 키-값 (Redis, Deno KV) |
| 전문 검색·유사도·형태소 분석이 주 기능이다 | 검색 엔진 (Elasticsearch) |
| 관계를 여러 다리 건너 따라가는 질의가 주력이다 | 그래프 (Neo4j) |
| 시간축 집계가 전부고 갱신이 없다 | 시계열 DB → **디지털 트윈 Phase 4** |
| **위 어디에도 확실히 해당하지 않는다** | **관계형.** 확신이 없으면 관계형이 정답이다 |

**JSON 컬럼이라는 중간 지대도 있다.** MySQL 8은 JSON 타입과 그 위의 인덱스를 지원하므로, 스키마가 유동적인 일부 필드만 JSON으로 두고 나머지는 정규화하는 선택이 가능하다. 다만 **JSON 컬럼 안의 값에는 외래키를 걸 수 없다** — 무결성을 포기하는 것이므로 그 경계를 명시적으로 정한다.
