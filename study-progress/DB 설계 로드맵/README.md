# DB 설계 로드맵 — 요구사항에서 스키마 한 벌까지 직접 만든다

**DB 운영 안정화 로드맵**이 **이미 있는 DB가 멈추지 않게 지키는 법**이라면, 이 로드맵은 **처음부터 스키마를 만드는 법**이다. 저장소에 설계·모델링 강의가 150강 넘게 쌓여 있는데 어느 로드맵도 소유하지 않고 떠 있던 것을 한데 모았다.

실습 대상은 남의 예제 도메인이 아니라 **지금 이 저장소 자체**다. 카테고리→코스→모듈→강의의 계층, 강의↔로드맵 Phase의 다대다, 소유/참조라는 두 종류의 관계, 학습일 이력 — 설계 교재가 챕터마다 예제로 드는 까다로운 케이스가 이미 다 들어 있다. 도메인을 완전히 알고 있으니 요구사항 단계에서 헤매지 않고, 만든 스키마가 맞는지 직접 판정할 수 있다.

- 작성일: 2026-09-08
- 웹 리서치 기준일: 2026-09-08
- 대상: SQL을 읽고 쓸 줄 알고 프로그래밍 경험이 있으나, ERD를 처음부터 그려 스키마를 설계해 본 적은 없음
- 원칙: 저장소 자료 우선. 공백 3개는 공식 문서와 산출물 과제로 메운다 — **추가 강좌 구매 없이 완주할 수 있다**
- 실습 DBMS: **MySQL 8** (InnoDB) — **DB 운영 안정화 로드맵**과 실습 환경을 공유한다
- 도착점: **learning-hub 저장소를 요구사항 정리 → ERD → 3NF 검증 → MySQL DDL → 무결성 제약까지 한 벌로 설계해 실제 MySQL에 올리고, 지금 Markdown 체크박스를 눈으로 훑어 답하던 질문 20개를 SQL로 답한다.**

## 순서를 이렇게 잡은 이유

**개념 → 논리 → 물리라는 교과서 순서를 그대로 따른다.** 이 주제만큼은 순서를 흔들 이유가 없다. 물리 모델을 먼저 만지면 "테이블을 어떻게 쪼갤까"가 아니라 "컬럼을 어디에 붙일까"가 되어 버리고, 그러면 정규화를 배울 기회 자체가 사라진다.

**대신 그릴 대상을 익숙한 것으로 바꿔 지루함을 없앴다.** Phase 1에서 이 저장소의 업무 규칙을 뽑는 순간부터 "로드맵 Phase가 같은 강의를 두 번 체크하는 걸 어떻게 표현하지?" 같은 실제 문제가 나온다. 남의 도서관 예제로는 3주 뒤에나 만날 문제다.

**Phase 5(다대다·이력)를 정규화 직후에 따로 뺀 이유**는 이 저장소의 난점이 거기 몰려 있기 때문이다. 강의 하나가 여러 로드맵에 속하고, 어떤 로드맵은 소유하고 어떤 로드맵은 참조만 하며, 같은 강의를 두 로드맵에서 각각 다른 날 체크한다. 이걸 N:M 하나로 풀면 반드시 틀린다. 교과서 순서대로라면 Phase 3에 묻힐 주제인데, 여기서는 한 Phase를 통째로 줄 값어치가 있다.

**Phase 8(분석계)을 뒤에 둔 것**은 정규화를 몸에 붙이기 전에 팩트·디멘션을 배우면 "중복을 허용해도 된다"만 남기 때문이다. 왜 되돌리는지를 알려면 왜 쪼갰는지를 먼저 알아야 한다.

## 추천 진행 방식

- **주 5시간 기준 약 16주** 코스다.
- 강의 하나를 볼 때마다 `study` 스킬로 Q&A 학습을 하면 정리본이 자동 생성된다. 각 Phase 문서의 체크박스가 진행 기록 원본이다.
- **Phase 1 시작 전에 MySQL 8 컨테이너 하나와 ERD 도구를 준비한다.** ERD 도구는 Phase 7에서 MySQL Workbench를 정식으로 배우지만, Phase 2에서는 종이나 아무 도구로나 그려도 된다. 도구를 고르느라 시작을 미루지 않는다.
- **Phase 2부터 산출물 파일을 한 폴더에 모아 둔다.** Phase 9에서 그 폴더가 그대로 최종 산출물이 된다. 매 Phase마다 새로 시작하지 않는다.
- **설계는 되돌아가는 작업이다.** Phase 4에서 정규화하다 보면 Phase 2의 ERD가 틀렸다는 걸 알게 된다. 그때 ERD를 고치는 것이 정상이고, 그 수정 이력 자체가 Phase 9 데이터 사전의 재료다.

## 이 로드맵에 없는 것

- **인덱스 튜닝·실행계획·락** — **DB 운영 안정화 로드맵**이 Phase 2~5로 다룬다. 여기서는 "설계 시점에 인덱스를 어디 걸지"만 판단한다.
- **SQL 문법 학습** — 이 로드맵은 SQL을 읽을 줄 안다고 가정한다. 조인·집계가 흔들리면 **DB 운영 안정화 10 부록**으로 간다.
- **데이터 파이프라인·ETL 구축** — dbt·Airflow는 Phase 5에서 SCD2 부분만 빌려 쓴다. 파이프라인 자체는 **디지털 트윈 로드맵 Phase 4**가 소유한다.
- **암호화 구현·접근 제어** — [10 부록](10%20부록%20-%20개인정보와%20데이터%20거버넌스.md)에서 "무엇을 저장하지 않을 것인가"라는 설계 판단만 다룬다. 구현은 **보안 로드맵 Phase 7**이다.
- **객체지향 도메인 모델링·UML** — [Software Design and Architecture](../../courses/mooc/Computer%20Science%20Fundamentals/Software%20Design%20and%20Architecture/README.md) Course 1이 다룬다. Phase 2에서 참고 링크로만 건다.

## 주의 사항

- **각 Phase 문서의 체크리스트가 이 로드맵이 다루는 코스들의 진행 기록 원본이다.** 별도의 코스 단위 진행 기록 파일은 두지 않는다. 이 로드맵을 만들면서 `study-progress/Database Design - A Modern Approach.md`는 삭제하고 28항목을 Phase 1~4·6·9로 옮겼다.
- **다른 로드맵과 겹치는 강의가 있다.** SCD2 5강은 **디지털 트윈 로드맵 Phase 4**가, Data Modeling and Architecture Module 1의 4강은 **디지털 트윈 로드맵 Phase 1**이, 정규화·파티셔닝 일부는 **DB 운영 안정화 로드맵**이 이미 소유한다. **한쪽에서 이미 봤다면 다른 쪽에도 학습일을 옮겨 적는다.** 소유 관계는 [00 강의 자료 인덱스](00%20강의%20자료%20인덱스.md)의 표에 정리했다.
- **공백은 3개뿐이지만 전부 Phase 7·8에 몰려 있다.** 스키마 마이그레이션 도구·데이터 계약·OBT 논쟁은 저장소에도 MOOC·Udemy에도 마땅한 강좌가 없어 공식 문서와 산출물 과제로 채웠다. [13 부록](13%20부록%20-%20추천%20강의%20종합.md) 참조.
- **운영 DB에 실습하지 않는다.** 로컬 MySQL 컨테이너에서만 한다. 이 로드맵은 `DROP TABLE`을 자주 하게 된다.
