# Evals and Error Analysis

## 개요

Agentic 워크플로우를 잘 구축하는 사람과 그렇지 않은 사람을 가르는 중요한 차이는 **체계적인 평가 프로세스(evaluation process)** 를 운영할 수 있는지입니다.

핵심 메시지:
- Agentic 워크플로우는 사전에 모든 실패 가능성을 예측하기 어려움
- 먼저 시스템을 만들고 출력물을 직접 살펴보며 문제를 발견
- 발견한 문제를 eval로 측정하고, 개선 후 지표가 좋아지는지 추적
- Evals와 Error Analysis는 Agentic 워크플로우 개선의 핵심 기술

## 왜 Evals가 중요한가

Agentic 워크플로우는 여러 단계와 툴 호출로 구성되기 때문에 어디서 어떤 문제가 생길지 미리 알기 어렵습니다.

예:
- 고객 응답이 너무 장황함
- 답변이 정책과 맞지 않음
- 불필요하게 경쟁사를 언급함
- 중간 단계에서 잘못된 데이터베이스 쿼리를 호출함
- 최종 출력은 그럴듯하지만 근거가 약함

따라서 권장되는 접근은 다음과 같습니다.

1. 먼저 Agentic 워크플로우 구현
2. 여러 출력물을 직접 검토
3. 만족스럽지 않은 패턴을 발견
4. 해당 문제를 측정하는 eval 추가
5. 시스템을 개선하고 eval 결과가 좋아지는지 확인

## 예시: 경쟁사 언급 문제

고객 주문 문의 응답 에이전트가 다음과 같이 답한다고 가정합니다.

예:
- "저희와 쇼핑해 주셔서 감사합니다. 저희는 경쟁사 ComproCo보다 훨씬 낫습니다."
- "물론입니다. RivalCo와 달리 저희는 반품을 쉽게 처리합니다."

많은 비즈니스에서는 고객 응답에서 경쟁사를 언급하는 것을 원하지 않습니다.

이 문제의 특징:
- 사전에 예상하기 어려울 수 있음
- 출력물을 직접 읽어보면서 발견될 가능성이 높음
- 발견 후에는 비교적 명확한 평가 지표로 만들 수 있음

## 객관적 평가 지표

경쟁사 언급 여부는 객관적 기준으로 평가할 수 있습니다.

예:
- 경쟁사 목록: `ComproCo`, `RivalCo`, `The Other Co`
- 에이전트 출력에서 해당 이름이 등장하는지 코드로 검색
- 전체 응답 중 경쟁사를 잘못 언급한 비율 계산

### 장점

- 기준이 명확함
- 코드로 자동 측정 가능
- 개선 전후를 숫자로 비교하기 쉬움

### 객관적 eval 예시

| 평가 항목 | 측정 방식 |
|----------|----------|
| 경쟁사 언급 여부 | 경쟁사 이름이 출력에 포함되는지 검색 |
| 필수 필드 누락 | 특정 JSON 필드 또는 텍스트 필드 존재 여부 확인 |
| 형식 준수 | 출력이 Markdown, JSON 등 요구 형식을 따르는지 검사 |
| 금지어 사용 | 금지된 표현이 포함되었는지 검색 |

## 주관적 평가와 LLM-as-Judge

LLM 출력은 자유 텍스트이기 때문에 코드만으로 평가하기 어려운 기준도 많습니다.

예:
- 에세이 품질
- 응답의 친절함
- 설명의 논리성
- 리서치 보고서의 깊이
- 고객 답변의 적절성

이런 경우 **LLM-as-Judge** 방식을 사용할 수 있습니다.

### 예시

Research Agent가 생성한 에세이를 다른 LLM에 입력하고 다음과 같이 평가하게 할 수 있습니다.

> 다음 에세이의 품질을 1점에서 5점 사이로 평가하세요. 1점은 최악, 5점은 최고입니다.

여러 주제에 대해 보고서를 생성한 뒤, Judge LLM이 점수를 매기고 개선 과정에서 점수가 올라가는지 확인합니다.

### 주의점

LLM은 단순한 1~5점 척도 평가를 항상 잘 수행하지는 않습니다.

- 점수 기준이 모호할 수 있음
- 점수가 일관되지 않을 수 있음
- 작은 품질 차이를 안정적으로 반영하지 못할 수 있음

이 방식은 초기 평가 방법으로는 쓸 수 있지만, 이후 모듈에서는 더 정확한 LLM-as-Judge 평가 기법을 다룹니다.

## End-to-End Eval과 Component-Level Eval

Agentic AI eval에는 크게 두 가지 유형이 있습니다.

| 유형 | 설명 | 예시 |
|------|------|------|
| End-to-End Eval | 전체 에이전트의 최종 출력 품질 평가 | 고객에게 보낼 최종 답변이 적절한가 |
| Component-Level Eval | 워크플로우의 특정 단계 출력 평가 | 주문 정보 추출 단계가 정확한가 |

### End-to-End Eval

전체 시스템이 최종적으로 원하는 결과를 내는지 평가합니다.

장점:
- 실제 사용자 경험과 가까움
- 전체 워크플로우 성능을 확인 가능

한계:
- 문제가 발생했을 때 어느 단계가 원인인지 알기 어려울 수 있음

### Component-Level Eval

Agentic 워크플로우의 개별 단계를 따로 평가합니다.

예:
- 이메일에서 주문 번호를 정확히 추출했는가
- 데이터베이스 쿼리가 올바른가
- 검색어 생성 단계가 적절한가
- 초안 검토 단계가 실제 문제를 잘 찾아냈는가

장점:
- 어느 단계가 병목인지 파악하기 쉬움
- 특정 컴포넌트를 집중적으로 개선 가능

## Error Analysis

Error Analysis는 Agentic 워크플로우의 중간 출력과 최종 출력을 직접 검토해 문제가 발생한 위치와 원인을 찾는 과정입니다.

### Trace 검토

Agentic 워크플로우의 중간 출력은 종종 **trace**라고 부릅니다.

Trace에 포함될 수 있는 것:
- LLM이 생성한 검색어
- 호출한 툴과 인자
- 데이터베이스 쿼리
- 검색 결과 요약
- 초안
- 검토 결과
- 최종 응답

중간 trace를 읽어보면 최종 출력만 볼 때는 알기 어려운 실패 원인을 발견할 수 있습니다.

예:
- 검색어가 부정확해서 리서치 품질이 낮아짐
- 데이터베이스 조회는 맞았지만 응답 작성 단계에서 잘못 요약함
- 초안은 괜찮았지만 수정 단계에서 중요한 내용을 삭제함

## 개선 루프

Evals와 Error Analysis는 반복 개선 루프를 만듭니다.

1. 출력과 trace 검토
2. 문제 패턴 발견
3. 해당 문제를 측정하는 eval 설계
4. 워크플로우, 프롬프트, 툴 호출, 단계 분해 개선
5. eval 결과 확인
6. 새 문제를 찾고 반복

이 과정을 통해 Agentic 워크플로우를 원하는 성능 수준까지 점진적으로 개선할 수 있습니다.

## 요약

- Agentic 워크플로우의 성능을 높이려면 disciplined evaluation process가 필요함
- 실패 가능성을 모두 미리 예측하기 어렵기 때문에 출력물을 직접 보고 문제를 찾아야 함
- 객관적 기준은 코드 기반 eval로 측정 가능
- 주관적 기준은 LLM-as-Judge로 평가할 수 있지만 설계에 주의가 필요함
- End-to-End Eval과 Component-Level Eval은 서로 다른 개선 목적에 유용함
- Trace를 읽고 실패 원인을 찾는 Error Analysis가 매우 중요함
