# Component-level evaluations

## 개요
- end-to-end eval만 쓰면 특정 컴포넌트를 튜닝할 때마다 **전체 워크플로를 다시 돌려야 해 비싸고**, 다른 컴포넌트의 무작위성(noise)에 작은 개선이 묻힌다.
- 대안: **개선 대상 컴포넌트 하나만 측정하는 eval**(component-level eval)을 만든다.

## 내용

### 왜 컴포넌트 단위 평가인가
- end-to-end eval의 문제:
  - **비용** — 웹 검색만 바꿔도 전체 워크플로를 매번 재실행해야 함.
  - **노이즈** — 복잡한 워크플로에서 다른 단계의 랜덤성 때문에 웹 검색의 미세 개선이 잘 안 보임.
- component-level eval의 장점:
  - 특정 오류에 대한 **더 명확한 신호** — 그 컴포넌트가 실제로 좋아지는지 알 수 있음.
  - 전체 시스템의 복잡성/노이즈를 피함.
  - **팀 분업**에 유리 — 팀마다 자기 컴포넌트의 명확한 지표만 최적화하면 되므로 더 작고 집중된 문제를 빠르게 해결.

### 예시: 웹 검색 컴포넌트 평가
1. 몇 개 쿼리에 대해 전문가가 **gold standard 웹 리소스**(가장 권위 있는, 반드시 찾아야 할 페이지들)를 지정.
2. 웹 검색 출력이 gold standard와 얼마나 겹치는지 코드로 측정.
3. 정보 검색(information retrieval)의 표준 지표인 **F1 score** 등으로 겹침 정도를 수치화.
   > F1이 뭔지 몰라도 됨 — "반환된 페이지 목록이 전문가 지정 정답 목록과 얼마나 겹치는가"를 재는 표준 지표.

이 지표로 다음을 빠르게 비교 가능:
- 검색 엔진 교체 (Google / Bing / DuckDuckGo / Tavily / You.com 등)
- 반환 결과 개수 조정
- 검색 대상 날짜 범위 조정

## 마무리 원칙
- 컴포넌트를 하나씩 튜닝할 때는 **그 컴포넌트만 평가**하면 훨씬 효율적 — 매번 end-to-end를 돌릴 필요 없음.
- 단, 튜닝을 끝내고 "완료" 선언 전에는 **반드시 end-to-end eval을 돌려** 전체 성능이 실제로 올랐는지 확인.

## 요약
- component-level eval = 개선 대상 컴포넌트 하나만 측정 → 명확한 신호 + 효율.
- 예: 웹 검색은 gold standard 리소스 대비 F1 등으로 평가.
- 컴포넌트 튜닝 후 최종 확인은 end-to-end eval로.
