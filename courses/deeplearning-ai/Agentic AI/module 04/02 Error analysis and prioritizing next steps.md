# Error analysis and prioritizing next steps

## 개요
- 에이전틱 워크플로는 **여러 컴포넌트**로 이루어져 있어, 어떤 컴포넌트를 개선하느냐에 따라 효율 차이가 크다.
- **감(gut)으로** 개선 대상을 고르면 몇 달을 써도 성과가 없을 수 있다.
- **오류 분석(error analysis)** = 각 단계의 중간 출력을 살펴 어느 컴포넌트가 가장 문제인지 체계적으로 찾는 것. 팀의 개선 속도를 좌우하는 핵심 역량.

## 내용

### 문제: 어느 컴포넌트를 고칠 것인가
리서치 에이전트가 "핵심 논점 누락" 문제를 보일 때, 원인이 될 수 있는 단계는 여럿이다.
- 검색어 생성 LLM이 엉뚱한 검색어를 만듦
- 웹 검색 엔진 자체 품질이 낮음
- 검색 결과 중 다운로드할 상위 몇 개를 잘못 고름
- 페이지를 넣은 뒤 LLM이 문서의 일부 논점을 무시함

### 트레이스(trace)와 스팬(span)
- **trace**: 한 번의 에이전트 실행에서 나온 **모든 중간 단계 출력의 집합**.
- **span**: **단일 단계**의 출력. (컴퓨터 관찰가능성(observability) 분야 용어)
- 트레이스를 읽으면 어느 컴포넌트의 품질이 전문가 대비 떨어지는지 감을 잡을 수 있다.

### 체계적 오류 분석 방법
1. **실패한 케이스에 집중** — 출력이 만족스러운 예시는 제쳐두고, 불만족스러운 예시만 모은다. (그래서 "error" analysis)
2. **스프레드시트로 오류 집계** — 각 단계 출력이 "전문가 대비 현저히 나쁜지"를 명시적으로 센다.
3. 컴포넌트별 오류 빈도를 계산해 어디가 가장 문제인지 파악.

## 예시: 리서치 에이전트 오류 분석

블랙홀 과학 기사 요청 시:
1. **검색어**: `black hole theories Einstein`, `Event Horizon Telescope Radio` → 전문가가 보기에 합리적. (문제 아님)
2. **검색 결과 URL**: "초등학생이 30년 된 블랙홀 미스터리를 풀었다 - Astro Kid News" 같은 비전문 블로그/대중지가 너무 많음. (문제!)
3. **상위 5개 소스 선택**: Astro Kid News, SpaceBot 2000 등. → 단, **입력 자체가 부실한 기사뿐이었다면** 이 단계를 탓할 수 없다(주어진 선택지 안에서 최선을 다한 것).

### 오류 집계 스프레드시트 (개념)
| 프롬프트 | 검색어 | 검색 결과 | ... |
|---|---|---|---|
| 블랙홀 최신 동향 | OK | 블로그 too many, 과학 논문 부족 | |
| 시애틀 임대 vs 매매 | OK | 유명 블로그 누락 | |
| 과일 수확 로봇 | 너무 일반적 | 결과도 부실 | |
| **불만족 비율** | **5%** | **45%** | |

- → 검색 결과가 45%로 압도적 문제. **웹 검색 엔진 교체/파라미터 튜닝**에 집중해야 한다는 결론.

## 우선순위 결정 원칙
개선 대상 = **오류가 잦은 컴포넌트** × **개선 아이디어가 있는 컴포넌트**
- 문제가 많지만 개선 아이디어가 없으면 → 우선순위 낮춤.
- 오류가 많고 개선 방법도 있으면 → 우선순위 높임.

## 요약
- 워크플로를 만든 뒤 **트레이스(중간 출력)를 들여다보는 습관**을 들여라.
- 스프레드시트로 **어느 컴포넌트가 얼마나 자주 오류를 내는지** 통계화하라.
- 복잡한 시스템에서는 잘못된 대상에 몇 달을 낭비하기 쉽다. 오류 분석은 **노력을 어디에 집중할지** 정해 개발 효율을 크게 높인다.
