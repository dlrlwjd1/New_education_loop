# How to address problems you identify

## 개요
- 개선할 컴포넌트를 정했다면, **실제로 그 컴포넌트를 좋게 만드는 방법**은 컴포넌트 종류에 따라 다르다.
- 크게 **비(非)LLM 컴포넌트**와 **LLM 컴포넌트**로 나눠 개선 기법을 정리한다.
- 더불어, 어떤 LLM이 어떤 작업에 강한지 **직관(intuition)을 기르는 법**을 다룬다.

## 비-LLM 컴포넌트 개선

예: 웹 검색, RAG 텍스트 검색, 코드 실행, 별도 학습된 ML 모델(음성 인식, 사람 탐지 등)

- **파라미터/하이퍼파라미터 튜닝**
  - 웹 검색: 결과 개수, 검색 날짜 범위
  - RAG 검색: 유사도 임계값(similarity threshold), 청크 크기(chunk size)
  - 사람 탐지: 탐지 임계값 → false positive/negative 트레이드오프 조정
  - *(세부 하이퍼파라미터를 다 몰라도 됨 — 요점은 "튜닝 가능한 값이 있다"는 것)*
- **컴포넌트 자체 교체** — 다른 RAG 검색 엔진/제공자로 바꿔 더 나은지 시도.
- → 종류가 다양해 개선 기법도 컴포넌트마다 제각각.

## LLM 컴포넌트 개선 (우선순위 순)

1. **프롬프트 개선**
   - 더 명시적인 지시 추가
   - **few-shot 프롬프팅** — 입력/원하는 출력의 구체적 예시를 1개 이상 넣어 성능 향상
2. **다른 LLM 시도** — AI Suite 등으로 여러 모델을 쉽게 바꿔보고, eval로 최적 모델 선택
3. **작업 분해(decompose)** — 한 단계가 너무 복잡하면 여러 단계로 쪼개기 (예: 생성 → 리플렉션, 또는 2~3번 연속 호출)
4. **파인튜닝(fine-tuning)** — *최후의 수단.* 복잡하고 개발 시간/비용이 큼.
   - 다른 방법을 다 써도 90~95%에서 마지막 몇 %를 짜내야 하는 **성숙한 애플리케이션**에서만 고려.

## 모델 직관 기르기

### 예시: PII 삭제(redaction)
- 고객 통화 요약에서 개인식별정보(PII: 이름, 주민번호, 주소 등)를 제거하는 작업.
- **작은 모델**(예: open-weight Llama 3.1 8B): 단순 사실 질문엔 괜찮지만 **지시 따르기(instruction following)에 약함**.
  - 지시를 어기고 리스트→삭제문→또 리스트를 출력, 이름을 놓치고, 주소도 일부만 삭제.
- **더 지능적인 프런티어 모델**: PII를 모두 정확히 나열·삭제.
- → 모델마다 강점이 다르다. 코딩에 강한 모델, 지시 따르기에 강한 모델, 특정 지식에 강한 모델이 따로 있다.

### 직관을 기르는 방법
- **새 모델이 나오면 자주 써보기** (proprietary + open-weight 모두).
- **개인용 eval 세트**를 두고 여러 모델에 같은 질문을 던져 성능을 보정(calibrate).
- **남의 프롬프트를 많이 읽기** — 인터넷 공개 프롬프트, 존경하는 사람의 오픈소스 패키지 속 프롬프트, 지인/프런티어 회사 동료와 프롬프트 공유.
- 워크플로에서 **여러 모델을 실제로 돌려보기** — 트레이스나 eval로 성능뿐 아니라 **가격/속도 트레이드오프**까지 직관화.
- Andrew Ng이 AI Suite를 자주 쓰는 이유: **모델을 빠르게 교체·비교**할 수 있어서.

## 요약
- 비-LLM 컴포넌트: 하이퍼파라미터 튜닝 or 교체.
- LLM 컴포넌트: 프롬프트 개선 → 모델 교체 → 작업 분해 → (최후) 파인튜닝.
- 모델을 자주 써보고 남의 프롬프트를 읽으며 **어떤 모델이 어떤 작업에 강한지 직관**을 길러라.
