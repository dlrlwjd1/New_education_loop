# Latency, cost optimization

## 개요
- 우선순위: **출력 품질을 높이는 것이 가장 어렵고 중요**하다. 지연 시간(latency)과 비용(cost)은 **품질이 잘 나온 뒤에** 최적화하라.
- 비용/지연을 무시하라는 게 아니라, 걱정 순위에서 **뒤에 둔다**는 뜻.
- Andrew Ng 경험담: 사용자가 몰려 비용이 문제가 된 적이 있는데, 이는 "행복한 고민(good problem to have)". 사용자가 많아졌을 때 사용자당 비용을 낮추면 된다.

## 지연 시간(latency) 최적화

### 1) 각 단계 시간 측정(benchmark)
리서치 에이전트 예시:
| 단계 | 평균 소요 |
|---|---|
| 검색어 생성(LLM) | 7초 |
| 웹 검색 | 5초 |
| (중간 단계) | 3초 |
| (중간 단계) | 11초 |
| 최종 에세이 작성(LLM) | 18초 |

- 타임라인을 보면 **어느 컴포넌트에 개선 여지가 큰지** 파악 가능.

### 2) 개선 기법
- **병렬화(parallelism)** — 예: web fetch 등 독립적인 작업을 병렬로 실행.
- **더 작은/빠른 모델** — 오래 걸리는 LLM 단계(18초 등)에 조금 덜 똑똑해도 충분한 소형 모델을 시도.
- **더 빠른 LLM 제공자** — 전용 하드웨어로 토큰을 훨씬 빨리 서빙하는 업체가 있으니 비교.

## 비용(cost) 최적화

### 단계별 비용 측정
- LLM 제공자: 보통 **입력/출력 토큰 길이당** 과금.
- API 제공자: **API 호출당** 과금.
- 연산 단계: 서버 용량 지불 방식에 따라 비용 상이.

비용 집계 예시:
| 단계 | 비용 |
|---|---|
| LLM 토큰(검색어) | 0.04센트 |
| 웹 검색 API | 1.6센트 |
| PDF→text | ... |
| 최종 생성 토큰 | ... |

- → 더 싼 컴포넌트/모델로 바꿀 여지가 큰 곳을 찾는다.

## 요약
- 품질 먼저, 비용·지연은 나중. (프로덕션에 올리고 잘 돌아갈 때 최적화)
- **각 단계의 시간과 비용을 측정**하면 어디를 최적화할지 근거가 생긴다.
- 벤치마킹은 명료함을 준다 — 어떤 컴포넌트는 비용/지연 기여가 작아 **신경 쓸 필요 없다는 것**도 알려준다.
