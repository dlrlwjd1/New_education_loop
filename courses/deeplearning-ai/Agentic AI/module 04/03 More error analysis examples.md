# More error analysis examples

## 개요
- 오류 분석은 **여러 예시를 직접 보며 직관을 훈련**해야 익숙해진다.
- 이번 영상은 두 가지 추가 사례로 연습한다: **송장 처리**, **고객 이메일 응답**.
- 공통 원칙: 실패한 예시(10~100개)에 집중해, 여러 컴포넌트 중 **어디서 오류가 났는지 스프레드시트로 집계**한다.

## 예시 1: 송장(invoice) 처리 — 마감일 오류의 원인

워크플로: PDF → text 변환 → LLM이 4개 필드 추출 → DB 기록

마감일 오류의 원인 후보:
- **PDF→text 변환**이 날짜를 잘못 뽑았나? (사람도 못 알아볼 정도로)
- 아니면 텍스트는 멀쩡한데 **LLM이 엉뚱한 날짜**(발행일 vs 마감일)를 뽑았나?

집계 결과 예시:
| | PDF→text 오류 | LLM 추출 오류 |
|---|---|---|
| 오류 비율 | 낮음 | **높음** |

- → **LLM 데이터 추출 컴포넌트**에 집중해야 한다는 결론.
- 오류 분석이 없었다면 몇 주~몇 달 동안 PDF→text만 튜닝하다 정작 최종 성능은 안 오르는 낭비를 할 수 있다.
- 참고: 각 컴포넌트 오류 비율의 **합이 100%가 아닐 수 있다** — 오류들이 상호 배타적이지 않기 때문(한 예시에 여러 원인).

## 예시 2: 고객 이메일 응답

워크플로: 고객 이메일 → LLM이 DB 쿼리 작성 → 주문 정보 조회 → 답장 초안(사람 검토)

불만족 출력의 원인 후보:
- **LLM이 잘못된 DB 쿼리** 작성 (엉뚱한 테이블/데이터 요청) → 정보 조회 실패
- **DB 데이터 자체가 손상/오류** → 쿼리는 맞아도 정보가 틀림
- 정보는 맞는데 **LLM이 쓴 이메일이 부적절**

집계 결과 예시:
| 컴포넌트 | 오류 비중 |
|---|---|
| DB 쿼리 작성 (LLM) | **75%** |
| DB 데이터 오류 | 소량 |
| 이메일 작성 (LLM) | ~30% |

- → 최우선: **LLM의 쿼리 작성 방식 개선**, 차선: 이메일 작성 프롬프트 개선.
- "잘하는 것도 많지만, **틀리는 것 중 75%가 DB 쿼리 문제**"라는 정보가 노력의 방향을 정해준다.

## 요약
- 실패 예시에 집중해 **컴포넌트별 오류 빈도를 집계**하면, 개선 대상이 명확해진다.
- 오류 비율 합은 100%가 아닐 수 있다(원인 비배타적).
- 오류 분석으로 집중할 컴포넌트를 정한 뒤에는, end-to-end eval을 **보완**하기 위해 **개별 컴포넌트 단위 평가(component-level eval)** 가 유용하다.
