# Reflection

## 개요

Reflection은 LLM이 자신의 출력물을 다시 검토하고 개선하도록 만드는 디자인 패턴입니다.

사람이 초안을 작성한 뒤 다시 읽고 수정하듯이, LLM도 1차 결과물을 생성한 뒤 이를 다시 입력으로 받아 더 나은 2차 결과물을 만들 수 있습니다.

핵심 아이디어:
- 먼저 LLM이 초안 또는 1차 결과물을 생성
- 같은 LLM 또는 다른 LLM이 결과물을 검토
- 문제점과 개선 방향을 반영해 더 나은 버전을 생성

## 이메일 작성 예시

사람이 급하게 이메일을 쓰면 첫 번째 초안에 문제가 있을 수 있습니다.

예:
- "다음 달"이라는 표현이 구체적이지 않음
- 오타가 있음
- 이름 서명을 빠뜨림

사람은 초안을 다시 읽고 다음처럼 개선할 수 있습니다.

개선 방향:
- 가능한 날짜를 구체적으로 명시
- 오타 수정
- 이름 추가

LLM도 같은 방식으로 동작할 수 있습니다.

### Reflection 워크플로우

1. LLM에게 이메일 초안 작성 요청
2. 생성된 `email v1`을 다시 LLM에 입력
3. 다른 프롬프트로 검토와 개선 요청
4. 개선된 `email v2` 생성

이 방식은 개발자가 두 번의 LLM 호출을 순서대로 하드코딩한 간단한 Agentic 워크플로우입니다.

## 코드 작성 예시

Reflection은 이메일뿐 아니라 코드 생성에도 사용할 수 있습니다.

### 기본 워크플로우

1. LLM에게 특정 작업을 수행하는 코드 작성 요청
2. LLM이 `code v1` 생성
3. 같은 LLM 또는 다른 LLM에게 버그 검토 요청
4. 검토 결과를 바탕으로 개선된 `code v2` 생성

### 모델 선택

서로 다른 LLM은 서로 다른 강점을 가질 수 있습니다.

예:
- 일반 모델: 첫 번째 코드 초안 생성
- Reasoning model 또는 thinking model: 버그 탐지와 검토

Reasoning model은 코드의 논리적 오류나 버그를 찾는 데 강할 수 있으므로, 초안 생성 모델과 reflection 모델을 다르게 선택할 수 있습니다.

## 외부 피드백을 활용한 Reflection

Reflection은 LLM 내부의 자기 검토만으로도 가능하지만, 외부 정보를 추가로 제공하면 훨씬 강력해집니다.

### 코드 실행 예시

1. LLM이 `code v1` 생성
2. 실제로 코드를 실행
3. 실행 결과 또는 에러 로그 확인
4. 코드, 출력, 에러 메시지를 LLM에 다시 입력
5. LLM이 피드백을 바탕으로 `code v2` 생성

예:
- 코드 실행 결과 syntax error 발생
- 에러 메시지를 LLM에 전달
- LLM이 에러 원인을 파악하고 수정된 코드 생성

외부 피드백은 LLM이 무엇이 잘못되었는지 더 구체적으로 이해하게 해주므로, 단순히 "다시 검토해줘"라고 요청하는 것보다 더 좋은 결과를 만들 가능성이 높습니다.

## Reflection의 한계

Reflection은 마법 같은 해결책은 아닙니다.

- LLM이 항상 정답을 내게 만들지는 않음
- 100% 정확도를 보장하지 않음
- 추가 LLM 호출이 필요하므로 속도가 느려질 수 있음
- 비용도 증가할 수 있음

하지만 많은 경우 시스템 성능을 어느 정도 끌어올리는 데 도움이 됩니다.

## 설계 시 고려할 점

Reflection을 설계할 때 특히 중요한 질문:

> Reflection 단계에 새로운 외부 정보를 제공할 수 있는가?

가능한 외부 정보:
- 코드 실행 결과
- 에러 메시지
- 단위 테스트 결과
- 데이터베이스 쿼리 실행 결과
- 사용자 피드백
- 평가 결과

새로운 정보가 있을수록 LLM은 더 깊이 있게 반성하고 개선할 수 있습니다.

## 요약

- Reflection은 LLM이 1차 출력물을 검토하고 개선하는 디자인 패턴
- 이메일, 코드, 문서 작성 등 다양한 출력물에 적용 가능
- 같은 LLM을 다시 호출할 수도 있고, 다른 모델을 reflection 단계에 사용할 수도 있음
- 코드 실행 결과나 에러 로그 같은 외부 피드백을 넣으면 훨씬 강력해짐
- 성능 개선 효과가 있지만 추가 시간과 비용이 들기 때문에 평가가 필요함
