# Evals for Reflection Workflows

## 개요

Reflection은 시스템 성능을 개선할 수 있지만, 추가 단계가 필요하므로 실행 시간이 늘어납니다. 따라서 실제로 성능이 얼마나 개선되는지 eval로 확인한 뒤 유지할지 결정하는 것이 좋습니다.

핵심 질문:
- Reflection을 추가했을 때 성능이 실제로 좋아지는가?
- 좋아진다면 어느 정도 좋아지는가?
- 추가 비용과 지연 시간을 감수할 만큼 가치가 있는가?

## 예시: 데이터베이스 쿼리 개선

Retail store에서 다음과 같은 질문에 답해야 한다고 가정합니다.

예:
> 어떤 색상의 상품이 총매출이 가장 높은가?

이런 질문에 답하려면 LLM이 데이터베이스 쿼리(SQL 등)를 생성해 필요한 데이터를 가져올 수 있습니다.

### Reflection 없는 워크플로우

1. 사용자 질문 입력
2. LLM이 데이터베이스 쿼리 생성
3. 쿼리를 실행해 데이터 조회
4. 조회 결과를 바탕으로 답변 생성

### Reflection 있는 워크플로우

1. 사용자 질문 입력
2. LLM이 1차 데이터베이스 쿼리 생성
3. 같은 LLM 또는 다른 LLM이 쿼리를 검토
4. 더 정확하거나 효율적인 쿼리로 수정
5. 수정된 쿼리를 실행해 데이터 조회
6. 조회 결과를 바탕으로 답변 생성

핵심 평가 질문:
> 두 번째 LLM의 reflection이 최종 답변 정확도를 실제로 높이는가?

## 객관적 Eval: Ground Truth 기반 평가

정답이 명확한 작업에서는 객관적 eval을 만들 수 있습니다.

### 평가 데이터셋 구성

질문과 정답을 함께 준비합니다.

예:
- 2025년 5월에 몇 개의 아이템이 판매되었는가?
- 재고에서 가장 비싼 상품은 무엇인가?
- 매장에는 몇 가지 스타일이 있는가?

각 질문에 대해 ground truth answer를 기록합니다.

### 평가 방식

1. 같은 질문 세트를 reflection 없이 실행
2. 같은 질문 세트를 reflection 있게 실행
3. 각 결과가 ground truth와 일치하는지 코드로 확인
4. 정답률을 비교

예시 결과:

| 방식 | 정답률 |
|------|--------|
| Reflection 없음 | 87% |
| Reflection 있음 | 95% |

이런 결과라면 reflection이 데이터베이스 쿼리 품질과 최종 답변 정확도를 의미 있게 개선한다고 볼 수 있습니다.

## Prompt 개선과 Eval

Reflection 워크플로우를 만들면 개발자는 종종 프롬프트를 여러 방식으로 바꿔봅니다.

변경 예:
- 초기 쿼리 생성 프롬프트 수정
- Reflection 프롬프트 수정
- 쿼리를 더 빠르게 실행하라는 지시 추가
- 쿼리를 더 명확하게 작성하라는 지시 추가

Eval이 있으면 여러 프롬프트 후보를 빠르게 비교할 수 있습니다.

프롬프트 튜닝 루프:
1. 프롬프트 후보 작성
2. 동일한 eval 데이터셋으로 실행
3. 정답률 또는 점수 비교
4. 가장 좋은 프롬프트 선택
5. 필요하면 반복

Eval은 감으로 프롬프트를 고르는 대신, 체계적으로 선택할 수 있게 해줍니다.

## 주관적 Eval이 필요한 경우

모든 작업에 명확한 정답이 있는 것은 아닙니다.

예:
- 어떤 그래프가 더 이해하기 쉬운가?
- 어떤 시각화가 더 보기 좋은가?
- 어떤 에세이가 더 깊이 있는가?
- 어떤 응답이 고객에게 더 적절한가?

이런 기준은 객관적인 right/wrong으로 평가하기 어렵습니다.

## LLM-as-Judge의 한계

주관적 평가에서는 LLM-as-Judge를 사용할 수 있습니다.

단순한 접근:
1. Reflection 없는 결과와 Reflection 있는 결과를 모두 LLM에 입력
2. 어느 쪽이 더 나은지 판단하게 함

하지만 두 입력을 직접 비교하게 하는 방식에는 문제가 있습니다.

한계:
- 평가 결과가 항상 좋지 않을 수 있음
- 프롬프트 문구에 민감함
- 인간 전문가의 판단과 순위가 잘 맞지 않을 수 있음
- Position bias가 발생할 수 있음

### Position Bias

많은 LLM은 두 선택지를 비교할 때 첫 번째 옵션을 더 자주 고르는 경향이 있습니다.

문제:
- A를 먼저 보여주면 A가 좋다고 판단
- B를 먼저 보여주면 B가 좋다고 판단
- 실제 품질보다 제시 순서가 평가에 영향을 줌

따라서 단순 pairwise comparison은 신뢰하기 어렵습니다.

## Rubric 기반 평가

두 결과를 직접 비교하게 하는 대신, 하나의 결과를 명확한 rubric에 따라 평가하게 하면 더 일관된 결과를 얻을 수 있습니다.

### 그래프 평가 예시

LLM에게 단일 이미지를 주고 다음 기준을 평가하게 합니다.

Rubric 예:
- 그래프에 명확한 제목이 있는가?
- 축 레이블이 있는가?
- 차트 타입이 데이터에 적절한가?
- 중요한 값이나 범례가 읽기 쉬운가?
- 시각적으로 혼란스럽지 않은가?

### Binary Criteria

LLM에게 1~5점 점수를 직접 주게 하는 것보다, 여러 개의 0/1 기준으로 평가하게 하는 편이 더 안정적일 수 있습니다.

예:

| 기준 | 점수 |
|------|------|
| 제목이 명확한가 | 0 또는 1 |
| 축 레이블이 있는가 | 0 또는 1 |
| 차트 타입이 적절한가 | 0 또는 1 |
| 범례가 읽기 쉬운가 | 0 또는 1 |
| 전체적으로 해석 가능한가 | 0 또는 1 |

5개의 binary criteria를 합산하면 0~5점 점수를 만들 수 있습니다. 10개의 기준을 쓰면 0~10점 점수를 만들 수 있습니다.

이 방식은 LLM이 추상적인 1~5점 척도를 직접 매기는 것보다 더 일관된 평가를 만들 가능성이 높습니다.

## Reflection 시각화 평가 예시

커피머신 판매 데이터에 대한 다양한 시각화 요청을 10~15개 정도 준비합니다.

평가 과정:
1. 각 요청에 대해 reflection 없이 그래프 생성
2. 각 요청에 대해 reflection 있게 그래프 생성
3. 각 그래프를 rubric 기반 LLM-as-Judge로 평가
4. Reflection 있는 결과의 평균 점수가 더 높은지 확인
5. 프롬프트를 바꿀 때마다 같은 eval을 재실행

이렇게 하면 주관적인 시각화 품질도 어느 정도 체계적으로 비교할 수 있습니다.

## 객관적 Eval과 주관적 Eval 비교

| 평가 유형 | 적합한 경우 | 방법 | 특징 |
|----------|------------|------|------|
| 객관적 eval | 정답이 명확한 작업 | 코드 기반 채점 | 관리가 쉽고 신뢰도가 높음 |
| 주관적 eval | 품질, 명확성, 적절성 평가 | LLM-as-Judge + rubric | 더 많은 튜닝이 필요함 |

정답이 있는 작업에서는 ground truth 데이터셋과 코드 기반 평가가 가장 관리하기 쉽습니다.

반면 주관적 작업에서는 LLM-as-Judge를 쓸 수 있지만, 좋은 rubric을 설계해야 평가가 더 안정적입니다.

## 요약

- Reflection은 성능을 높일 수 있지만 추가 지연이 있으므로 eval로 효과를 확인해야 함
- 데이터베이스 쿼리처럼 정답이 있는 작업은 ground truth 기반 객관 eval이 적합함
- Eval을 만들면 초기 생성 프롬프트와 reflection 프롬프트를 체계적으로 비교할 수 있음
- 주관적 작업에서는 LLM-as-Judge를 사용할 수 있지만 pairwise comparison은 position bias에 취약함
- Rubric 기반 binary criteria 평가는 더 일관된 결과를 줄 수 있음
- 좋은 eval은 Reflection뿐 아니라 다양한 Agentic 워크플로우 개선에 필수적임
