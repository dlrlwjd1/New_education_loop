# Logging, Monitoring, and Observability

## 개요
- 어떤 지표를 수집할지 정했다면, 이를 **수집하는 시스템**을 구축해야 한다. LLM 애플리케이션용 **관측성 플랫폼**을 쓰면 설계·구현 시간을 아끼고 모니터링·개선 실험에 집중할 수 있다.
- 예시로 오픈소스 플랫폼 **Phoenix**(Arize 제작)를 소개한다: **트레이스(traces)**, RAGAS 통합 평가, 실험/A-B 테스트, 집계 통계 리포트.
- 좋은 관측성 파이프라인은 **개선의 플라이휠(flywheel)** 을 만든다 — 특히 과거 프롬프트로 **커스텀 데이터셋**을 만들어 변경 영향을 검증.

## 내용

### 관측성 플랫폼
- LLM 앱용 플랫폼은 시스템·구성 요소 지표 수집, 트래픽 로깅, 새 설정 실험 같은 공통 평가 작업을 수행한다. 직접 구축하는 대신 플랫폼을 쓰면 성능 모니터링·개선에 시간을 쓸 수 있다.

### Phoenix의 주요 도구
- **트레이스(traces)** (가장 많이 쓰임): 프롬프트가 파이프라인 전체를 지나며 각 구성 요소에서 어떻게 변형되는지 추적. 초기 텍스트 프롬프트 → 리트리버로 보낸 쿼리 → 반환된 청크 → 리랭커 처리 → 코어 LLM에 보낸 최종 프롬프트 → 생성된 응답, 그리고 **각 단계의 지연**까지 기록. 저품질 응답의 원인 단계를 추적할 수 있다.
- **RAGAS 통합 평가**: 리트리버의 검색 관련성, LLM의 정확한 출처 인용 여부 같은 평가 단계를 쉽게 추가.
- **실험(experiments)**: 기본 평가 파이프라인을 세우면 자신의 프롬프트를 반복 시도해 처리 과정을 보거나, 변경을 **A/B 테스트**. 새 시스템 프롬프트가 실제로 품질을 높이는지, 리랭커 추가로 얼마나 개선되는지 판단.
- **집계 통계(aggregate)**: 트레이스가 저수준 정보라면, 고수준 추세를 위해 **일일 리포트**(리트리버 정확도부터 환각률까지) 제공.

### 플랫폼의 공백 — 고전 모니터링 도구
- Phoenix 등 LLM 관측성 플랫폼이 대부분의 평가를 커버하지만 공백이 있다. 예: **벡터 DB의 연산·메모리 사용** 모니터링엔 부적합.
- 이런 경우 **Datadog, Grafana** 같은 고전적 모니터링·관측성 도구를 사용.

### 개선의 플라이휠(flywheel)
- 좋은 관측성 파이프라인은 개선의 선순환을 만든다: **실제 프로덕션 트래픽** 처리 방식을 보고 → 버그·개선 영역 식별 → 변경 영향 확인 → 각 구성 요소를 사용자 실제 사용에 맞게 튜닝.
- 핵심 도구: **과거에 처리한 프롬프트로 커스텀 데이터셋 생성**. 저장 후 재실행하면 시스템 변경이 **실제 받은 프롬프트**에 미치는 영향을 볼 수 있다.

## 예시

### Phoenix 도구 요약
| 도구 | 용도 |
|------|------|
| 트레이스 | 프롬프트의 파이프라인 여정·단계별 지연 추적 |
| RAGAS 통합 | 검색 관련성·인용 정확성 평가 |
| 실험/A-B | 시스템 프롬프트·리랭커 변경 효과 검증 |
| 집계 리포트 | 정확도·환각률 등 일일 추세 |

### 관측성 도구 분담
| 대상 | 도구 |
|------|------|
| LLM 파이프라인 평가·트레이스 | Phoenix 등 LLM 관측성 플랫폼 |
| 벡터 DB 연산·메모리 | Datadog, Grafana 등 고전 도구 |

## 요약
- 정한 지표는 **관측성 플랫폼**으로 수집한다 — 예시 **Phoenix** 는 **트레이스**(프롬프트 여정 추적), **RAGAS 평가**, **A/B 실험**, **집계 리포트**를 제공한다.
- 플랫폼이 못 잡는 벡터 DB 연산·메모리는 **Datadog·Grafana** 같은 고전 도구로 보완한다.
- 관측성은 **개선의 플라이휠**을 돌린다 — 특히 **과거 프롬프트로 만든 커스텀 데이터셋**으로 변경 영향을 실제 트래픽에 검증한다.
- 다음 강의에서 그 커스텀 데이터셋을 만드는 법을 다룬다.
