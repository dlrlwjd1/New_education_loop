# Latency vs Response Quality

## 개요
- 프로덕션 RAG의 또 다른 균형은 **지연(latency) vs 응답 품질**이다. 리트리버·리랭킹·에이전틱 구성 요소를 더할수록 품질은 오르지만 지연도 늘어난다.
- 지연의 대부분은 **트랜스포머 실행** — 즉 **LLM 호출**에서 온다. 벡터 DB 등 검색은 빠르고 잘 확장된다.
- 절감 순서: 먼저 **코어 LLM**(작은 모델·라우터·캐싱), 다음 다른 트랜스포머 구성 요소, 그다음 리트리버(바이너리 양자화·샤딩).

## 내용

### 맥락에 따라 다른 중요도
- 지연의 중요도는 용도에 따라 다르다. 전자상거래 추천은 **저지연**을 위해 완벽하지 않은 추천을 감수하고, 희귀병 진단 보조 RAG는 오래 걸려도 **품질**을 우선한다.

### 지연의 주범 = LLM 호출
- 거의 모든 지연이 트랜스포머 실행 결과다. 가장 큰 주범은 **LLM 호출**. 검색은 지연을 조금 더하고(특히 일부 트랜스포머 기반 리랭킹), 현대 벡터 DB는 매우 빠르고 잘 확장된다.

### 코어 LLM 지연 줄이기
1. **더 작은 LLM**: 같은 하드웨어·메모리에서 작은/양자화 모델은 항상 더 빠르다.
2. **라우터 LLM**: 프롬프트를 보고 작은 모델과 큰 모델 중 적합한 것을 선택. 복잡한 추론은 큰 모델로, 단순 쿼리는 작고 빠른 모델로 → 단순 프롬프트의 지연은 낮게 유지하고 필요한 복잡 프롬프트만 지연 증가.
3. **캐싱(caching)**: 유사 프롬프트가 자주 오는 시스템에 유용. 자주 제출되는 프롬프트+응답을 캐시에 유지 → 새 프롬프트와 캐시의 **유사도**를 빠르게 계산해 충분히 가까우면 **캐시된 응답을 즉시 반환**(느린 생성 생략).
   - 개인화가 필요하면: 캐시된 응답 + 사용자 프롬프트를 **작고 빠른 LLM** 에 넣어 약간 조정해 관련성을 높인다.

### 다른 트랜스포머 구성 요소
- 코어 LLM 최적화 후, 쿼리 재작성기·리랭커·라우터 LLM 등을 본다. 각각 중요하지만 지연을 더한다.
- 조언: 각 구성 요소가 **더하는 지연**과 **주는 품질 향상**을 함께 측정하라. 예: 쿼리 재작성기의 이점이 크지 않으면 제거를 택할 수 있다.

### 리트리버 지연 줄이기
- **바이너리 양자화(binary quantized) 임베딩**: 벡터 거리 계산을 단순화해 검색 가속.
- **샤딩(sharding)**: 큰 DB를 별도 인스턴스로 분할하면(특히 아주 커지면) 검색 지연 감소. 어떤 DB에서든 흔한 방식이며 대부분의 벡터 DB가 도구를 제공.

### 실무 순서
- 시스템이 **얼마의 지연을 감내할 수 있는지** 먼저 이해.
- 지연을 줄여야 하면: ① 코어 LLM → ② 다른 트랜스포머/LLM 기능 → ③ 파이프라인의 다른 구성 요소 순.
- 관측성 시스템으로 변경 영향을 보며 필요한 수준까지 반복적으로 줄인다.

## 예시

### 지연 절감 우선순위
| 순서 | 대상 | 방법 |
|------|------|------|
| 1 | 코어 LLM | 작은/양자화 모델, 라우터, 캐싱 |
| 2 | 트랜스포머 구성 요소 | 재작성기·리랭커·라우터 지연 vs 품질 측정 |
| 3 | 리트리버 | 바이너리 양자화, 샤딩 |

### 용도별 우선순위
| 용도 | 우선 |
|------|------|
| 전자상거래 추천 | 저지연 |
| 희귀병 진단 보조 | 응답 품질 |

## 요약
- **지연 vs 품질** 트레이드오프에서, 지연의 대부분은 **LLM 호출**(트랜스포머)에서 오고 검색은 상대적으로 빠르다.
- 코어 LLM 절감: **작은/양자화 모델, 라우터 LLM(작은/큰 모델 선택), 캐싱**(+작은 LLM으로 개인화 조정).
- 이후 **다른 트랜스포머 구성 요소**(지연 vs 품질 측정 후 불필요하면 제거), 그리고 리트리버(**바이너리 양자화·샤딩**)로 절감.
- 먼저 감내 가능한 지연을 파악하고, **코어 LLM → 다른 트랜스포머 → 기타 구성 요소** 순으로 관측하며 줄인다. 다음은 **보안**이다.
