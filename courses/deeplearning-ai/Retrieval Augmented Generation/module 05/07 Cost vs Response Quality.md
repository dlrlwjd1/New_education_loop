# Cost vs Response Quality

## 개요
- 시스템을 수백~수백만 요청으로 확장하면 **비용**이 중요해진다. 전형적 RAG의 두 최대 비용은 **벡터 데이터베이스**와 **LLM** 이다.
- **LLM 비용 절감**: 더 작은/양자화된 모델, 입출력 **토큰 수 제한**, 규모에선 **전용 하드웨어** 호스팅.
- **벡터 DB 비용 절감**: RAM/디스크/클라우드 스토리지 **계층** 활용 — 비싼 빠른 메모리(RAM)에는 성능에 실제 도움 되는 것(HNSW 인덱스)만, **멀티테넌시(multi-tenancy)** 로 효율적 이동.
- 핵심: 비용의 출처를 이해하고 **성능으로 정당화되는지** 확인하라.

## 내용

### LLM 비용 절감
1. **더 작은 모델 실험**: 코어 생성 LLM이든 에이전틱의 라우터 LLM이든, 더 작고 싼 모델로도 유사 품질 달성 가능. "작다"는 처음부터 파라미터가 적거나, **8비트 등으로 양자화**된 경우. 제한된 작업만 한다면 작은 모델이 의외로 잘하며, **작은 모델 파인튜닝**이 저비용 고성능을 낼 수 있다.
2. **입출력 토큰 수 제한**: RAG 프롬프트는 긴 청크를 많이 검색하면 급격히 커진다. **top-k 줄이기**(문서 적게 검색). LLM은 장황할 수 있고 **생성 토큰마다 과금**되므로, 시스템 프롬프트로 간결한 응답을 유도하거나 **토큰 한도**를 설정.
   - 관측성 파이프라인으로 이런 변경의 영향을 평가해 비용 절감 vs 품질 저하가 가치 있는지 판단.
3. **전용 하드웨어 호스팅**: Together AI·AWS·Google의 인퍼런스 엔드포인트는 프로토타입에 편리. 규모(수천~수백만 요청)에서는 같은 회사에서 **전용 하드웨어를 빌려** 모델을 돌리면 절약 가능. GPU를 **시간당 과금**하며, 규모에서는 토큰당 과금보다 훨씬 저렴할 수 있고 신뢰성(전용이라)도 향상.

### 벡터 DB 비용 절감 — 메모리 계층
- 대부분의 DB는 세 종류 메모리 제공:
  - **RAM**: 가장 빠르지만 가장 비쌈.
  - **디스크(disk)**: 중간.
  - **클라우드 객체 스토리지**: 가장 느리지만 가장 쌈.
  - (GB당 RAM ≫ 디스크 ≫ 클라우드 스토리지)
- 원칙: **성능에 실제 도움 될 때만** 비싼 빠른 스토리지에 둔다.
  - **HNSW 인덱스**는 빠른 벡터 검색을 위해 **RAM**에.
  - **문서 본문**은 RAM에 둘 필요 없음 → 자주 접근하는 문서는 디스크, 드문 것은 클라우드 스토리지.
- 많은 벡터 DB가 이 트레이드오프를 모니터링하고 필요에 따라 데이터를 **동적으로 이동**시키는 기능을 제공.

### 멀티테넌시(multi-tenancy)
- 벡터 DB 문서를 **소속 사용자/조직별로 분리**. 예: 100만 문서를 1,000명이 소유, 각 사용자는 자기 문서만 접근 → 사용자별 **개별 HNSW 인덱스**.
- 이렇게 하면 필요할 때만 특정 테넌트 데이터를 빠른 비싼 메모리에 로드하기 쉽다. 예: 고객이 로그인할 때 비로소 그 벡터를 RAM에 로드, 또는 유럽 야간엔 유럽 테넌트 데이터를 느린 스토리지에. 데이터를 테넌트별로 조직하면 이런 이동을 효율적으로 수행.

### 핵심 원칙
- 엔지니어는 **비용의 출처를 이해**하고 **성능으로 정당화**되는지 확인해야 한다.
- LLM은 **더 작은 모델 + 짧은 프롬프트**, 벡터 DB는 **비싼 스토리지에 적게 저장 + RAM/디스크/스토리지 간 이동**이 주된 절감 수단. 변경의 성능 영향을 실험·모니터링해 가치를 판단하라.

## 예시

### 절감 전략 요약
| 대상 | 전략 |
|------|------|
| LLM | 작은/양자화 모델, top-k↓, 토큰 한도, 전용 하드웨어(시간당) |
| 벡터 DB | 메모리 계층(HNSW→RAM, 본문→디스크/스토리지), 멀티테넌시 |

### 메모리 계층
| 메모리 | 속도 | 비용 | 용도 |
|--------|------|------|------|
| RAM | 빠름 | 비쌈 | HNSW 인덱스 |
| 디스크 | 중간 | 중간 | 자주 접근 문서 |
| 클라우드 스토리지 | 느림 | 쌈 | 드문 문서 |

## 요약
- RAG의 두 최대 비용은 **벡터 DB와 LLM** 이며, 확장 시 비용 관리가 중요해진다.
- **LLM**: 더 작은/양자화 모델, **top-k·토큰 수 제한**, 규모에선 **전용 하드웨어(시간당)** 로 절감.
- **벡터 DB**: **RAM/디스크/클라우드 스토리지 계층**을 써 빠른 메모리엔 **HNSW 인덱스**만 두고, **멀티테넌시**로 데이터를 효율적으로 이동.
- 원칙은 비용의 출처를 이해하고 **성능으로 정당화**되는지 실험·모니터링으로 판단하는 것. 다음은 **지연 vs 품질** 트레이드오프다.
