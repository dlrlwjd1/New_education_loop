# Customized Evaluation

## 개요
- **커스텀 데이터셋(custom dataset)** = 시스템이 과거 처리한 프롬프트와, 그 프롬프트가 시스템을 지나며 남긴 정보의 모음. 이를 통해 과거 성능을 이해하고, 재설계가 **실제 프롬프트**에 미칠 영향을 실험할 수 있다.
- 무엇을 저장할지의 답은 **무엇을 평가하고 싶은가**다. 최소한 입력 프롬프트·최종 응답, 구성 요소 평가를 원하면 각 구성 요소의 입출력까지 저장한다.
- 저장한 데이터로 **개별 문제 추적**과 **고수준 추세 시각화**(주제 클러스터링 등)를 하며, 이는 시스템을 실제 사용자 요청에 맞게 개선하는 핵심 도구다.

## 내용

### 커스텀 데이터셋이란 / 무엇을 저장할까
- 과거 프롬프트 + 선택한 여정 정보의 모음. 초기 프롬프트·최종 응답만 저장할 수도, 벡터 DB가 검색한 문서, 리랭커 전후 순위, 쿼리 재작성기 출력 등 방대한 정보를 저장할 수도 있다.
- 결정 기준: **무엇을 평가하고 싶은가**.
  - **입력 프롬프트 + 최종 응답**: 필수. 시스템 성능 감을 주고, 프롬프트 수정에 따른 응답 변화 추적 → **엔드투엔드 평가**만 가능.
  - **구성 요소별 입출력**: 리트리버·리랭커·쿼리 재작성기 성능을 알려면 각 구성 요소의 입출력 저장 필요. RAG 호출 로그 테이블은 수십 개 컬럼(고객 ID, 리랭커가 처리한 청크, 에이전틱 워크플로의 각 라우터 LLM 출력 등)이 될 수 있다.

### 다차원 분석
- 다양한 데이터를 저장하면 각 구성 요소를 개별 분석하고 여러 차원에서 성능을 볼 수 있다.
- 예(고객 서비스 챗봇): **질문 주제별 필터링** → "환불" 질문은 고품질, "제품 지연" 질문은 저품질임을 발견 → 로그 분석으로 지연 관련 프롬프트에 리트리버가 관련 문서를 못 찾음을 파악 → 지식 베이스에 관련 정보 추가 필요.

### 실제 사례 (강사 경험)
- 텍스트·이미지·코드 기반 차트(Mermaid.js)를 생성하는 특화 RAG에서, 일부 다이어그램 품질이 낮다는 불만.
- 로그를 거슬러 분석 → 사용자가 "다이어그램 그려줘"라고 하면 **라우터 LLM이 오해해 텍스트→이미지 모델로 보냄**(이 모델은 사람·사물은 잘 그리지만 차트는 못 그림).
- 원인 파악 후 **라우터 LLM의 시스템 프롬프트를 수정**해 그런 프롬프트가 이미지가 아니라 **코드 기반 차트**를 만들게 함. 견고한 모니터링·로깅 덕에 신고 → 원인 추적 → 프로덕션 수정이 수월했다.

### 시각화와 클러스터링
- 개별 저품질 프롬프트 추적뿐 아니라, 많은 데이터를 로깅하면 **시각화**로 고수준 추세(전체·구성 요소)를 파악할 수 있다.
- 예: 모든 입력 프롬프트를 **클러스터링**해 고수준 주제(제품 출시, 문제 해결 등)를 식별 → 특정 유형 프롬프트에만 평가 파이프라인을 돌려 그 유형에서 성능이 저조한지 확인.

## 예시

### 저장 데이터 수준
| 저장 범위 | 가능한 평가 |
|-----------|-------------|
| 프롬프트 + 최종 응답 | 엔드투엔드 |
| + 구성 요소 입출력 | 리트리버·리랭커·재작성기 개별 평가 |
| + 고객 ID·청크·라우터 출력 | 다차원 분석·주제별 필터 |

### 문제 추적 흐름 (예)
```
불만 접수 → 로그 역추적 → 원인 구성 요소 특정(라우터 오분류)
→ 시스템 프롬프트 수정 → 프로덕션 반영 → 개선 확인
```

## 요약
- **커스텀 데이터셋**은 과거 프롬프트와 여정 정보의 모음으로, 실제 트래픽에 대한 시스템 변경 영향을 검증하는 핵심 도구다.
- 저장 범위는 **평가 목표**에 따라 정한다 — 엔드투엔드면 프롬프트·응답만, 구성 요소 평가면 각 단계의 입출력까지.
- 저장 데이터로 **주제별 필터링·개별 문제 추적**(예: 라우터 오분류 발견·수정)과 **클러스터링 시각화**로 고수준 추세를 파악할 수 있다.
- 커스텀 데이터셋을 평가에 통합하는 것이 실제 사용자 요청에 맞게 시스템을 개선하는 최선의 방법이다.
