# Choosing Your LLM

## 개요
- RAG의 주요 결정 중 하나는 **어떤 LLM을 쓸까**이며, 이는 앱의 속도·품질·예산에 큰 영향을 준다.
- **정량화 가능한 요소**(모델 크기·비용·컨텍스트 윈도·속도·지식 컷오프)로 후보를 좁히고, 정량화가 어려운 **품질**은 **벤치마크**(자동 / 인간 평가 / LLM 심사)로 비교한다.
- 모델은 매우 빠르게 발전해 벤치마크가 **포화(saturate)** 되므로, LLM 선택은 **중요하지만 일시적**인 결정이다 — 더 나은 모델로 교체를 계획하라.

## 내용

### 정량화 가능한 요소
- **모델 크기(model size)**: 파라미터 수(억 단위). 소형 1~10B, 대형 100~500B+. 대형이 대개(항상은 아님) 더 유능하나 **항상 더 비싸다**.
- **비용(cost)**: 보통 **100만 토큰당 고정 가격**(입력/출력 가격이 다를 수 있음). 새롭고 크고 유능할수록 비쌈.
- **컨텍스트 윈도(context window)**: 프롬프트+컴플리션 합쳐 처리 가능한 최대 토큰. 크면 유연하나 여전히 토큰당 과금.
- **속도**: **첫 토큰까지 시간(time to first token)** 과 초당 토큰(tokens/sec). 실시간 상호작용이 중요하면 다른 면을 양보하고 저지연 모델을 택할 수 있다.
- **훈련/지식 컷오프(cutoff date)**: 훈련 데이터의 마지막 시점. RAG에서도 **최신 컷오프가 대체로 선호**됨(특히 최신 사건 응답 시).

### 품질과 벤치마크(benchmark)
- 정량 지표는 후보를 좁혀줄 뿐, 실제로 가장 중요한 것은 **품질**(복잡한 수학 추론부터 읽기 좋은 글까지)로 정량화가 어렵다. 이를 위해 다양한 벤치마크가 있다. 3가지 유형:

1. **자동 벤치마크(automated)**: 코드로 채점 가능한 과제(객관식, 수학·코딩 챌린지). 예: **MMLU**(Massive Multitask Language Understanding) — STEM·인문·법률 등 57개 과목 객관식.
2. **인간 평가(human scoring)**: 익명의 두 LLM이 같은 프롬프트에 답하고 사람이 선호를 고름 → 체스의 **ELO** 알고리즘으로 순위. 예: **LLM Arena**(가장 널리 인용). 자동 벤치마크가 못 잡는 미묘한 품질을 포착.
3. **LLM 심사(LLM-as-a-judge)**: 한 LLM이 참조 정답을 갖고 다른 LLM의 응답을 채점 → **승률(win rate)**. 저렴·유연하지만, 심사 LLM이 **자기 계열 모델을 선호**하는 편향(예: GPT는 GPT를, Gemini는 Gemini를)이 있어 **보정(calibration)** 이 필요.

### 좋은 벤치마크의 조건
- **관련성**: 프로젝트에 맞아야 함(코드 안 만들면 코드 벤치마크는 무의미).
- **난이도**: 고성능·저성능 모델을 구분할 만큼 어려워야 함(모두 잘하면 무용).
- **재현성(reproducible)**: 실행 간 점수가 크게 변하지 않고, 제공사 수치가 검증 가능해야 함.
- **실제 성능과 정렬**: 벤치마크 고득점이 실제 성능으로 이어져야 함 → 개발자 포럼 등을 참고. 안 맞는 이유 중 하나가 **데이터 오염(data contamination)** — 벤치마크 데이터가 훈련 데이터에 포함되어 문제·정답을 이미 본 경우 과대 성능.

### 벤치마크 포화(saturation)와 빠른 발전
- 전형적 패턴: 처음엔 평균 점수가 낮다가 몇 년 만에 인간 전문가급이 흔해짐 → 벤치마크가 **포화**(대부분 모델이 최고점 근처라 변별력 상실) → 더 어려운 새 벤치마크 도입 → 그것도 곧 포화.
- 핵심 시사점: **오늘 나온 모델은 몇 년 전보다 크게 우수**하며, 오늘 고른 모델도 더 유능한 모델이 나오면 **교체가 필요**하다.

## 예시

### 벤치마크 3유형
| 유형 | 방식 | 예 |
|------|------|-----|
| 자동 | 코드로 채점(객관식·수학·코딩) | MMLU |
| 인간 평가 | 선호 비교 → ELO 순위 | LLM Arena |
| LLM 심사 | LLM이 참조 정답으로 채점 → 승률 | (자기 계열 편향 주의) |

### LLM 선택 정량 요소
| 요소 | 고려점 |
|------|--------|
| 크기(파라미터) | 대개 클수록 유능, 항상 더 비쌈 |
| 비용 | 100만 토큰당 가격(입력/출력 별도 가능) |
| 컨텍스트 윈도 | 크면 유연, 토큰당 과금 |
| 속도 | 첫 토큰 시간, tokens/sec |
| 지식 컷오프 | 최신일수록 선호 |

## 요약
- LLM 선택은 앱의 속도·품질·예산을 좌우하며, **크기·비용·컨텍스트 윈도·속도·컷오프** 로 후보를 좁힌다.
- 품질은 **자동 벤치마크(MMLU 등)·인간 평가(LLM Arena)·LLM 심사** 로 비교하되, **관련성·난이도·재현성·실제 정렬**을 갖춘 벤치마크를 골라야 하고 **데이터 오염**을 주의한다.
- 벤치마크는 빠르게 **포화**되고 모델은 급속히 발전하므로, LLM 선택은 **일시적 결정**이며 더 나은 모델로 교체를 계획해야 한다.
