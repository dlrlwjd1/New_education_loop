# Transformer Architecture

## 개요
- LLM은 2017년 논문 **"Attention is All You Need"** 에서 제안된 **트랜스포머(transformer)** 아키텍처에 기반한다. 트랜스포머는 **인코더(encoder)** 와 **디코더(decoder)** 로 구성되며, 대부분의 LLM은 텍스트 생성용 **디코더만** 쓰고 인코더는 임베딩 모델에 쓰인다.
- 프롬프트는 토큰화 → 초기 임베딩+위치 벡터 → **어텐션(attention) + 피드포워드(feedforward)** 층을 **여러 번 반복**하며 의미가 정제되고, 마지막에 다음 토큰 **확률 분포**에서 하나를 골라 생성한다.
- 이 구조가 RAG가 통하는 이유(어텐션의 깊은 이해), LLM의 **무작위성**, 그리고 **높은 연산 비용**을 설명한다.

## 내용

### 인코더 vs 디코더
- 트랜스포머는 원래 **기계 번역**을 위해 제안됨. **인코더**는 원문(예: 독일어 문단)을 처리해 깊은 의미를 이해하고, **디코더**는 그 이해로 새 텍스트(영어)를 생성.
- 대부분의 LLM은 텍스트 생성만 하므로 **디코더만** 포함. **인코더**는 풍부한 시맨틱 표현을 만드는 게 목표라 **임베딩 모델**에 쓰인다.

### 프롬프트의 여정 (디코더)
1. **토큰화(tokenize)**: 프롬프트를 토큰으로 분할.
2. **초기 임베딩(first guess)**: 각 토큰에 의미의 첫 추측인 조밀 벡터 부여. 이 값은 **정적(static)** — 같은 토큰엔 항상 같은 첫 추측.
3. **위치 벡터(positional vector)**: 프롬프트 내 위치를 담는 벡터 부여.
4. **어텐션(attention) 메커니즘**: 각 토큰이 다른 모든 토큰의 의미·위치를 보고, **어느 토큰에 가장 주목할지** 결정. 즉 "어떤 토큰이 내 의미에 가장 큰 영향을 주는가".
   - 예: "the brown dog sat next to the red fox"에서 "dog"는 brown(70%)·sat(20%)에 주로 주목.
   - **어텐션 헤드(attention head)**: 주목을 배정하는 장치. 대부분의 모델은 서로 다른 관계에 특화된 **여러 헤드**를 갖는다(객체-설명 관계 헤드, 공간 관계 헤드 등). 실제 관계는 사람이 정한 게 아니라 훈련으로 학습된 복잡·추상적 관계. 소형은 8~16개, 대형은 100개 이상.
5. **피드포워드(feedforward)**: LLM에서 **파라미터가 가장 많은** 부분. 원 임베딩·위치·어텐션을 바탕으로 각 토큰의 **갱신된(second guess) 벡터** 부여 — 이제 다른 토큰들의 맥락이 반영됨.
6. **반복**: second guess 벡터를 다시 어텐션+피드포워드에 넣어 third guess로 정제. 보통 이 층을 **8~64번** 통과하며 이해를 점진적으로 다듬는다.

### 토큰 생성
- 정제된 임베딩으로 "학습 데이터상 다음에 올 토큰"의 **확률 분포**를 어휘 전체에 대해 계산(대부분은 사실상 0). → 분포에서 확률 가중으로 **하나 선택**(확률 높은 토큰이 자주, 이론상 어떤 토큰도 미세한 확률).
- 선택된 토큰을 프롬프트 끝에 붙임 → 토큰 1개 생성. 다음 토큰은 **원 토큰 + 새 토큰**을 모두 고려해 전 과정을 반복(초기 무작위 선택이 이후에 영향). 토큰 한도 도달 또는 **종료 토큰(end-of-completion)** 생성까지 반복 → 디토큰화해 사용자에게 반환.

### 트랜스포머가 RAG 설계에 주는 시사점
1. **RAG가 통하는 이유**: 어텐션 처리와 피드포워드의 세계 지식 덕에, LLM은 프롬프트에 추가된 정보의 **의미·관련성을 깊이 이해**한다.
2. **LLM은 본질적으로 무작위**: 의미 있는 정보를 넣어도 그에 근거하지 않을 수 있다 → **무작위성 제어**와 검색 정보에 **근거(ground)** 시키는 것이 여전히 중요.
3. **연산 비용이 크다**: 토큰 하나 생성에 큰 처리가 들고, **프롬프트·컴플리션이 길수록 비용 증가**(각 토큰이 다른 모든 토큰을 봐야 함). RAG 비용의 대부분이 이 트랜스포머 실행에서 온다.

## 예시

### 트랜스포머 처리 파이프라인
| 단계 | 내용 |
|------|------|
| 토큰화 | 프롬프트 → 토큰 |
| 초기 임베딩 | 토큰별 첫 추측 벡터(정적) |
| 위치 벡터 | 위치 정보 |
| 어텐션 | 토큰 간 주목도(여러 헤드) |
| 피드포워드 | 맥락 반영한 갱신 벡터 |
| 반복(8~64층) | 의미 점진 정제 |
| 생성 | 다음 토큰 확률 분포에서 선택 |

## 요약
- LLM은 트랜스포머의 **디코더**로, 프롬프트를 토큰화·임베딩한 뒤 **어텐션(토큰 간 주목, 여러 헤드) + 피드포워드**를 **여러 층 반복**해 의미를 정제하고 다음 토큰을 확률적으로 생성한다.
- **인코더**는 임베딩 모델에, **디코더**는 생성용 LLM에 쓰인다.
- 이 구조는 ① 어텐션 덕에 **RAG가 통하고**, ② LLM이 여전히 **무작위**적이며(근거화 필요), ③ **연산 비용이 크다**(길수록↑)는 점을 설명한다.
- 다음 강의부터 RAG 안에서 LLM 동작을 다듬는 법을 다룬다.
