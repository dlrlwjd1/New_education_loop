# Evaluating Your LLM's Performance

## 개요
- 온도 조정·시스템 프롬프트 수정·모델 교체 등의 영향을 판단하려면 **LLM 성능 지표**가 필요하다.
- LLM은 복잡한 시스템 안에서 작동하므로, **리트리버의 역할(관련 정보 찾기)과 LLM의 역할(그 정보로 좋은 응답 구성)** 을 구분해 LLM 역할에 초점 맞춘 지표를 써야 한다.
- LLM 행동은 주관적이라 대부분 지표가 **다른 LLM으로 평가(LLM-as-a-judge)** 한다. 대표 도구는 **RAGAS** 라이브러리(response relevancy, faithfulness 등)이며, 시스템 전체 지표(👍/👎 A/B 테스트)도 활용한다.

## 내용

### LLM의 역할을 분리하라
- 리트리버 = 지식 베이스에서 관련 정보 찾기, LLM = 그 정보로 고품질 응답 구성. 문제의 원인이 리트리버면 시스템 프롬프트를 고쳐봐야 소용없다.
- 리트리버가 잘 작동한다고 가정하면(대부분 관련 정보 + 일부 무관), LLM의 임무는: 질문에 답하기, **관련 정보를 응답에 반영**, 적절히 **인용**, **무관 정보에 산만해지지 않기**.
- 이런 LLM 행동은 대부분 **주관적** — "질문에 잘 답했는가", "무관 정보를 무시했는가"를 정량화하기 어렵다. 그래서 대부분의 LLM 지표는 **다른 LLM으로 응답 품질을 평가**해, 확장 가능한 방식으로 유연성·주관성을 반영한다.

### RAGAS 라이브러리의 지표
- **응답 관련성(response relevancy)**: 응답이 사용자 프롬프트에 실제로 관련 있는지(사실 정확성과 무관).
  - 방법: 응답을 새 LLM에 주어 그 응답을 낳았을 법한 **여러 샘플 프롬프트**를 생성 → 원래 프롬프트와 각 샘플 프롬프트를 임베딩 → **코사인 유사도** 계산 → 평균. 응답에서 원래 프롬프트로 **거꾸로 추론 가능한지**를 본다.
- **충실도(faithfulness)**: LLM이 검색 정보를 실제로 사용했는지.
  - 방법: LLM으로 응답의 **모든 사실 주장**을 식별 → 추가 LLM 호출로 각 주장이 **검색된 정보로 뒷받침되는지** 판단 → 뒷받침되는 주장의 **비율**이 충실도.
- 그 외 지표도 유사한 방식으로 **무관 정보에 대한 민감도**나 **정확한 출처 인용 능력** 등을 평가.
- 공통 패턴: 평가 과정에 **LLM 호출**과, 경우에 따라 **정답(ground truth) 예시**에 의존 → RAG에서 LLM의 역할이 복잡해 단순 자동 지표로 평가하기 어렵다는 방증.

### 시스템 전체 지표 활용
- 사용자가 응답에 **👍/👎** 를 남길 수 있다면, 시스템 프롬프트 변경을 **A/B 테스트** 해 전체 사용자 만족도에 미친 영향을 본다.
- 시스템 전체 성능을 측정하되 **LLM 설정 변경만 격리**해, 성능 변화를 LLM 변경에 귀속시킨다.

## 예시

### RAGAS 주요 지표
| 지표 | 측정 대상 | 방법 |
|------|-----------|------|
| response relevancy | 응답이 프롬프트에 관련 있나 | 응답→가상 프롬프트 생성→코사인 유사도 평균 |
| faithfulness | 검색 정보를 실제 사용했나 | 주장 추출 → 뒷받침 비율 |
| (기타) | 무관 정보 민감도·인용 정확성 | LLM 기반 평가 |

## 요약
- LLM 성능 평가는 **리트리버 역할과 분리**해, 응답 구성·근거 반영·인용·무관 정보 무시 같은 **LLM 역할**에 초점을 맞춘다.
- 이 행동들은 주관적이라 대부분 지표가 **LLM-as-a-judge** 로 평가하며, **RAGAS** 의 **response relevancy**(관련성)와 **faithfulness**(검색 정보 사용 비율)가 대표적이다.
- 시스템 전체 지표(👍/👎 A/B 테스트)로 LLM 설정 변경을 격리해 영향을 귀속시킬 수 있다.
- LLM 응답은 주관적이므로 **LLM 심사 평가 + 인간 피드백**을 조합해 평가하라. 다음은 **에이전틱 RAG**다.
