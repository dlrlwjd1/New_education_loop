# Lifecycle of a generative AI project

## 개요
- 생성형 AI 소프트웨어 애플리케이션 개발은 빠른 프로토타입, 내부 평가, 개선, 배포, 모니터링을 반복하는 과정이다.
- 프롬프트 작성과 마찬가지로 생성형 AI 프로젝트도 매우 실험적(empirical)이고 반복적(iterative)이다.
- 성능 개선에는 프롬프트 수정뿐 아니라 RAG, 파인튜닝(fine tuning), 사전학습(pretraining) 같은 기술도 활용될 수 있다.

## 내용

### 생성형 AI 프로젝트의 기본 라이프사이클
생성형 AI 소프트웨어 애플리케이션을 만드는 과정은 보통 다음 흐름을 따른다.

1. 프로젝트 범위 정하기(scoping)
2. 빠른 프로토타입 구현
3. 내부 평가(internal evaluation)
4. 발견된 문제를 바탕으로 개선
5. 외부 배포
6. 실제 사용을 모니터링하며 계속 개선

생성형 AI를 사용하면 초기 프로토타입을 매우 빠르게 만들 수 있다. 어떤 애플리케이션은 1~2일 만에 초기 버전을 만들 수 있다. 처음부터 완벽하지는 않지만, 빠르게 만들어야 실제 예시로 테스트하고 개선할 수 있다.

### 평판 모니터링 시스템 예시
식당 평판 모니터링 시스템을 만든다고 가정해보자. 먼저 시스템이 식당 리뷰를 읽고 긍정 또는 부정 감성을 판단하도록 범위를 정한다.

초기 프로토타입을 만든 뒤 내부 팀이 여러 리뷰를 넣어 테스트한다. 이 과정에서 시스템이 잘못 판단하는 예시가 발견될 수 있다.

예를 들어 "My pasta was cold"라는 리뷰를 긍정으로 분류했다면 문제가 있다. 차가운 파스타가 어떤 경우에는 맛있을 수도 있지만, 일반적인 식당 리뷰 맥락에서는 부정적인 평가일 가능성이 높다.

이런 문제를 발견하면 프롬프트나 시스템을 개선하고 다시 평가한다.

### 배포 후 모니터링과 개선
내부 평가를 충분히 거쳐 시스템이 어느 정도 잘 동작한다고 판단되면 외부에 배포한다. 하지만 실제 사용자는 개발자가 예상하지 못한 입력을 넣을 수 있다.

예를 들어 "My miso ramen tasted like tonkotsu ramen"이라는 리뷰가 들어올 수 있다. 라멘이나 일본 음식에 익숙하지 않으면 이것이 좋은 의미인지 나쁜 의미인지 판단하기 어렵다. 미소 라멘을 주문했는데 돈코츠 라멘 맛이 났다면 부정적인 의미일 수 있다.

이런 실제 오류를 발견하면 다음 중 하나를 선택할 수 있다.

- 내부 평가로 돌아가 특정 음식 유형에서 성능이 낮은지 체계적으로 확인한다.
- 프롬프트나 시스템을 개선한다.
- 오류가 허용 가능한 수준인지 판단한다.

### 실험적이고 반복적인 개발
생성형 AI 프로젝트는 매우 실험적인 과정이다. 무언가를 시도하고, 결과를 보고, 실수를 찾고, 다시 고치는 방식으로 진행된다.

프롬프팅 자체도 마찬가지다. 아이디어를 프롬프트로 작성해보고, LLM 응답을 확인한 뒤, 프롬프트를 수정해 다시 시도한다. 생성형 AI 소프트웨어 개발은 이 반복 과정을 시스템 전체 수준으로 확장한 것이다.

### 성능 개선 기술
프롬프트 수정 외에도 생성형 AI 시스템 성능을 개선하는 여러 기술이 있다.

- **RAG(retrieval augmented generation)**: LLM이 외부 데이터 소스에 접근할 수 있게 하는 기술
- **파인튜닝(fine tuning)**: LLM을 특정 작업에 맞게 조정하는 기술
- **사전학습(pretraining)**: LLM을 처음부터 학습시키는 과정

강의에서는 이 용어들을 이후에 더 자세히 다룬다고 설명한다. 중요한 점은 프롬프트만이 성능 개선 수단은 아니라는 것이다.

### 음식 주문 챗봇 예시
두 번째 예시는 음식 주문을 받는 고객 서비스 챗봇이다.

먼저 음식 주문 챗봇을 만들기로 범위를 정하고, 빠르게 초기 챗봇을 구현한다. 내부 팀이 여러 주문을 넣어 테스트하면서 시스템이 제대로 응답하는지 확인한다.

잘 동작하는 예시:
- 고객: "치즈버거에 피클이 들어가나요?"
- 챗봇: 피클 여부를 확인하거나 추가 여부를 묻는다.

문제가 있는 예시:
- 실제로 버거에 버섯을 넣을 수 있는데 챗봇이 "버섯은 없습니다"라고 답한다.

이런 오류를 발견해 고친 뒤, 충분히 안전하다고 판단되면 실제 고객에게 배포한다. 배포 후에도 LLM 응답을 모니터링하며 잘못된 응답을 계속 개선한다.

사용자는 개발자가 예상하지 못한 질문을 할 수 있다. 예를 들어 "버거 칼로리가 얼마인가요?"라고 물을 수 있다. 초기 시스템은 답을 모를 수 있지만, RAG 같은 기술을 사용해 영양 정보 데이터에 접근하게 만들면 올바른 답을 제공할 수 있다.

## 예시

### 프로젝트 라이프사이클
| 단계 | 설명 |
|------|------|
| 범위 정하기 | 소프트웨어가 무엇을 해야 하는지 결정 |
| 프로토타입 구현 | 빠르게 초기 버전 생성 |
| 내부 평가 | 내부 팀이 다양한 입력으로 테스트 |
| 개선 | 발견된 오류를 바탕으로 프롬프트나 시스템 수정 |
| 배포 | 실제 사용자에게 공개 |
| 모니터링 | 실제 사용 중 오류를 발견하고 계속 개선 |

### 성능 개선 기술
| 기술 | 역할 |
|------|------|
| 프롬프트 개선 | 지시와 맥락을 더 명확히 제공 |
| RAG | 외부 데이터 소스를 검색해 LLM에 제공 |
| 파인튜닝 | 특정 작업에 맞게 모델 조정 |
| 사전학습 | 모델을 처음부터 학습 |

## 요약
- 생성형 AI 프로젝트는 빠르게 만들고, 평가하고, 개선하고, 배포 후 모니터링하는 반복적 과정이다.
- 초기 프로토타입은 완벽하지 않아도 되며, 실제 예시에서 오류를 발견하는 것이 개선의 출발점이다.
- 외부 사용자는 예상하지 못한 입력을 만들기 때문에 배포 후 모니터링이 중요하다.
- 프롬프트 개선 외에도 RAG, 파인튜닝, 사전학습 같은 기술이 시스템 성능 향상에 사용될 수 있다.
