# 07 When to Change Dev/Test Sets and Metrics

## 개요
- 지표(metric)나 dev/test 세트가 **실제 원하는 것과 어긋나면** 바꿔야 한다. (과녁을 옮긴다)

---

## 내용

### 경우 1: 지표가 잘못된 우열을 매김
- 예: 알고리즘 A(오류 3%) > B(오류 5%)로 보이지만, **A가 음란물(porn)을 통과**시킴 → 실제로는 B가 훨씬 낫다.
- 지표가 A를 선호 = **지표가 선호도를 잘못 순위 매김** → 지표를 바꿔야 할 신호.
- 해결: 오류에 **가중치 w⁽ⁱ⁾** 부여.
  ```
  Error = (1 / Σwᵢ) · Σ wᵢ · 1{ŷ⁽ⁱ⁾ ≠ y⁽ⁱ⁾}
  wᵢ = 1 (비음란물), 10 or 100 (음란물)
  ```
  → 음란물 오분류에 큰 벌점.

### 경우 2: dev/test 분포가 실사용과 다름
- dev/test는 고화질 인터넷 이미지인데, 실제 사용자는 **흐릿하고 프레임 안 맞는 폰 사진**을 올림.
- dev에서 A가 나아 보여도 실사용에선 B가 나음 → **dev/test 세트를 실사용 데이터로 바꿔야** 함.

### 직교화(orthogonalization) 관점 ⭐
ML 문제를 **두 단계로 분리**:
1. **과녁 놓기** — 원하는 것을 포착하는 **지표를 정의**.
2. **과녁 맞추기** — 그 지표에서 잘하도록 (비용 함수 J 최적화 등).
- 지표 정의가 먼저, 성능 개선은 별개의 단계.

### 실무 조언
- 완벽한 지표·dev를 못 정해도 **일단 빠르게 세워** 반복 속도를 확보하라.
- 나중에 부적절하다고 판단되면 그때 바꿔도 됨. 지표·dev 없이 오래 가는 것이 더 나쁨.

---

## 요약
- 지표가 잘못된 우열을 매기거나 dev/test가 실사용과 다르면 → 지표/세트를 바꿔라.
- 지표 정의(과녁 놓기)와 성능 개선(과녁 맞추기)은 분리된 단계.
- 완벽하지 않아도 빠르게 세워 반복 속도 확보.
