# 02 Cleaning Up Incorrectly Labeled Data

## 개요
- 데이터의 **레이블 y가 잘못된(incorrectly labeled)** 경우 고칠 가치가 있는지 판단하는 법.
- (구분: mislabeled = 알고리즘이 틀림, incorrectly labeled = 데이터의 정답 라벨 자체가 틀림)

---

## 내용

### 훈련 세트의 잘못된 레이블
- 딥러닝은 **무작위(random) 오류에 강건** → 데이터가 크고 오류 비율이 높지 않으면 그냥 둬도 대체로 OK.
- ⚠️ 단, **체계적(systematic) 오류에는 약함** — 예: 흰 개를 항상 고양이로 레이블하면 분류기도 그렇게 배움.

### dev/test 세트의 잘못된 레이블
- 오류 분석 표에 **"incorrect label" 열을 추가**해 그 비중을 센다.
- 고칠 가치 판단 — 세 숫자 비교:
  | | 예1 | 예2 |
  |---|---|---|
  | 전체 dev 오류 | 10% | 2% |
  | 잘못된 레이블 기여 | 0.6% | 0.6% |
  | 그 외 원인 | 9.4% | 1.4% |
  | 잘못된 레이블 비중 | 6% | **30%** |
  | 판단 | 우선순위 낮음 | **고칠 가치 큼** |
- dev의 목적(A/B 분류기 선택)을 방해할 정도(예: 2.1% vs 1.9%를 신뢰 못 함)면 고쳐라.

### 레이블 수정 가이드라인
1. **dev와 test에 같은 절차 적용** (같은 분포 유지).
2. 틀린 것뿐 아니라 **맞힌 것도 검토** (안 그러면 편향된 오류 추정). 단 정확도 높으면 맞힌 게 많아 어려움 → 항상 하진 않음.
3. **훈련 세트는 안 고쳐도 됨** — 딥러닝이 강건하고, train이 dev/test와 분포가 조금 달라도 대체로 괜찮음(후속 영상).

### 조언
- 딥러닝도 실무에선 **수동 오류 분석·인간 통찰**이 많이 들어간다.
- 예제를 직접 들여다보는 걸 꺼리지 말 것 — 수십 분~수 시간의 카운팅이 우선순위 결정에 큰 도움.

---

## 요약
- 훈련: 무작위 오류엔 강건(놔둬도 됨), 체계적 오류엔 취약.
- dev/test: 오류 분석에 incorrect-label 열 추가, 그 비중이 크면 수정. dev/test 동시에, 맞힌 것도 검토.
