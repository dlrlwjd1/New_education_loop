# 01 Train / Dev / Test Sets

## 개요
- 응용 머신러닝은 **반복적(iterative) 과정** — Idea → Code → Experiment 순환을 빠르게 도는 것이 관건.
- 데이터를 **훈련(train) / 개발(dev) / 테스트(test) 세트**로 잘 나누면 이 순환이 빨라진다.

---

## 내용

### 세 세트의 역할
| 세트 | 역할 |
|---|---|
| **Train** | 모델 학습 |
| **Dev (=holdout cross-validation)** | 여러 모델 중 어느 것이 나은지 평가·선택 |
| **Test** | 최종 모델의 성능을 **편향 없이(unbiased)** 추정 |

### 분할 비율 — 데이터 크기에 따라 다름
- **과거(소규모)**: 70/30 (train/test) 또는 60/20/20 — 총 100~10,000개 수준이면 합리적.
- **빅데이터 시대**: dev/test 비율이 훨씬 작아짐.
  - 예: 100만 개 → 98/1/1 (dev·test 각 1만 개면 충분).
  - 더 크면 99.5/0.25/0.25 등.
- 이유: dev는 "여러 알고리즘 중 뭐가 나은지"만 판단하면 되고, test는 최종 성능 추정만 하면 되므로 **큰 비율이 필요 없다**.

### 규칙 1: dev와 test는 같은 분포에서 ⭐
- 예: 고양이 사진 앱 — train은 인터넷 크롤링(고화질), dev/test는 사용자 업로드(흐릿한 폰 사진)일 수 있음.
- **dev와 test는 반드시 같은 분포**에서 오게 하라 (dev로 성능을 튜닝하므로).
- train은 데이터 갈증 때문에 크롤링 등으로 크게 확보하다 보면 **분포가 달라질 수 있는데**, 위 규칙만 지키면 진전이 빠르다.

### test 세트가 없어도 될 때
- test의 목적은 편향 없는 최종 추정. 그게 필요 없으면 **test 세트 생략 가능**.
- train + dev만 있는 경우, 많은 사람이 dev를 "test set"이라 부르지만, 실제론 holdout cross-validation으로 쓰는 것(엄밀히는 test에 과적합). 용어 주의.

---

## 요약
- train/dev/test로 나누면 반복이 빠르고 편향·분산 측정이 쉬워진다.
- 빅데이터에선 dev/test 비율을 1% 이하로 줄여도 됨.
- **dev와 test는 같은 분포**에서. test는 불필요하면 생략 가능.
