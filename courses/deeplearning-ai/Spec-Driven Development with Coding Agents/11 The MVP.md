# The MVP

## 개요
- 두 기능을 SDD로 구현한 뒤, 경영진의 **MVP(최소 기능 제품, Minimum Viable Product)** 요청에 응해 나머지 로드맵을 한 번에 구현해 본다.

## 내용

### 큰 덩어리 구현의 조건
- 표준 기능 명세 프롬프트의 변형으로 **로드맵의 나머지 전체**를 구현하게 하고 기존 기능 명세에 대한 가이드를 줌.
- 이렇게 큰 덩어리는 **헌법·명세 품질에 확신이 있을 때만** 실행 — 맥락이 좋을수록 의도와 정렬된 결과에 자신을 가질 수 있고, **리뷰·검증을 감당**할 수 있어야 함.
- MVP를 **헌법·완성된 기능 명세의 극한 테스트**로 봄 — 원한 것과 다르면 에이전트를 벗어나게 한 원인을 제거하는 **재계획**이 필요하다는 신호.

### 진행
- 에이전트의 좋은 질문·권고에 답하고 **Submit** → MVP 명세를 디스크에 기록.
- 명세 검토 — 에이전트가 공백을 메우며 세운 **잘못된 가정**을 자주 발견. 계획·요구사항·검증을 훑고 **작은 단계·잦은 커밋**으로 저장.
- 계획 완료 → 에이전트가 **대규모 구현** 수행 → 스크립트로 앱 실행. 각 섹션이 DB에서 쿼리한 **샘플 데이터**로 풍부해짐.

### MVP 검증
- 보통은 코드 결과를 검증하지만 MVP이므로 **에이전트에 명세 검증**을 요청 → 유용하게도 **계획의 구멍(holes)** 을 드러냄. 이 평가를 이해관계자와 공유해 MVP 리뷰 → 브랜치 머지 또는 아카이브.

## 요약
- MVP는 **헌법·기능 명세의 극한 테스트**이며, 품질에 확신이 있을 때만 큰 덩어리를 구현한다.
- 에이전트의 **명세 검증**이 계획의 구멍을 드러내 이해관계자 리뷰에 활용된다.
- SDD 워크플로가 헌법+두 기능만으로 유용한 데모를 만듦. 다음은 **브라운필드(기존 코드베이스)** 에 SDD를 도입하는 법.
