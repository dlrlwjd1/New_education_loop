# The Second Feature Phase — 대화정리

## 개요

06~09에서 배운 사이클을 두 번째 기능(agents and ailments)으로 한 바퀴 더 도는 강의다. 새 절차를 배우는 편이 아니라 **두 번째부터 실제로 부딪히는 것들**을 다룬다.

```text
첫 바퀴:  06 명세 → 07 구현 → 08 검증 → 09 재계획   (강의 4개)
두 번째:  10 The Second Feature Phase              (강의 1개에 압축)
```

새로 나오는 것은 셋뿐이다.

- **AI 피로(AI fatigue)** — 이 코스가 자기가 만든 문제를 정면으로 인정하는 대목
- **컨텍스트 클리어의 두 번째 이유** — 명세를 시험대에 올리는 행위
- **서브에이전트 심층 리뷰** — 독립적인 두 번째 눈

나머지는 전부 06~09의 반복이고, **09에서 고친 것들이 실제로 굴러가는 장면**이 나온다.

## 내용

### 1. AI 피로(AI fatigue)

> 에이전트가 많은 코드·변경을 생성 → 휴먼 인 더 루프 검증이 지침

논리 사슬이 이렇다.

```text
에이전트가 코드를 엄청 빨리 만든다
        ↓
우리 지침은 "사람이 검증한다" (08·09에서 계속 강조)
        ↓
사람이 그 많은 걸 다 봐야 한다
        ↓
지친다  ← AI 피로
```

휴먼 인 더 루프를 계속 밀어붙인 대가를 여기서 인정하고 다룬다.

#### 08의 인지 부채와 다르다

| | 인지 부채 (08) | AI 피로 (10) |
|---|---|---|
| **정체** | 이해 못 한 코드의 **누적** | 검증자의 **소진** |
| **방향** | 쌓인다 ▲ | 닳는다 ▼ |
| **한 줄** | "이거 뭐 하는 코드지?" | "또 봐야 돼?" |
| **원인** | 에이전트 속도 (같음) | 에이전트 속도 (같음) |

원인은 같은데 **증상이 다른 두 병**이다.

#### 그리고 둘은 연쇄한다

대화 중 나온 정리. 인지 부채는 "검증 안 하고 승인해서" 생기는 게 아니라 **코드가 이해 속도보다 빨리 생산되어** 생긴다. 승인을 꼼꼼히 해도 격차는 벌어진다.

```text
코드 생산 속도 ▲▲▲▲▲▲▲▲  (에이전트)
사람 이해 속도 ▲▲          (그대로)
               └──┬──┘
              이 격차가 쌓임 = 인지 부채
```

다만 "검증 없이 승인"은 **AI 피로가 인지 부채를 만드는 경로**다.

```text
AI 피로 (닳는다)
    ↓  지쳐서 리뷰를 대충 하게 됨
검증 없이 승인
    ↓
인지 부채 (쌓인다)
```

10이 AI 피로를 중요하게 다루는 이유가 이것 — 피로를 방치하면 08에서 경계하던 인지 부채로 그대로 굴러떨어진다.

### 2. 깨끗한 구획(clean division)

> 이를 줄이려면 **기능 단계마다 깨끗한 구분(clean division)**

기능과 기능 사이에 확실한 선을 긋는다. 그래야 하나 끝내고 쉴 수 있고, 다음을 백지에서 시작한다.

**시작 전 체크리스트 4개**

```text
□ 미완 작업 없나?
□ 지난 브랜치를 main에 머지했나?
□ 다음 로드맵 항목이 맞나?
□ 에이전트 컨텍스트를 비웠나?
```

### 3. 컨텍스트를 비우는 두 가지 이유

강의가 둘 다 명시한다.

**① 제한된 컨텍스트 예산을 다음 작업에 집중** — 쉬운 쪽. 지난 기능 얘기가 차 있으면 새 작업에 쓸 공간이 줄어든다.

**② 명세가 기억 스냅샷이 아닌 의도를 담게** — 이쪽이 미묘하다.

안 비웠을 때 벌어지는 일:

```text
컨텍스트에 "아까 PicoCSS 쓰기로 했잖아"가 남아 있음
        ↓
명세에 안 적혀 있어도 에이전트가 알아서 함
        ↓
결과물이 잘 나옴 → "명세 잘 썼네" 착각
        ↓
실제로 일한 건 명세가 아니라 대화 기록
        ↓
새 세션 / 팀원이 그 명세를 읽으면 → 동작 안 함
```

06이 **"명세에 없으면 안 만들어진다"** 였다면, 여기는 그 반대 위험이다. **컨텍스트에 있으면 명세에 없어도 만들어져서, 명세의 결함이 감춰진다.**

그래서 컨텍스트 클리어는 **명세를 시험대에 올리는 행위**다. 백지 상태의 에이전트가 명세만 읽고 제대로 만들면 그 명세는 진짜다.

### 4. 09에서 고친 것들이 여기서 굴러간다

> 에이전트 질문에 답: **기능들 한 단계 유지=Yes**, 마이그레이션=plain SQL, 검증=1·2·3

| 09에서 고친 것 | 10에서 나타나는 모습 |
|---|---|
| ① 헌법 (테스트 정책) | 테스트를 **디버거로 실행**하며 흐름 탐색 |
| ③ 로드맵 (2·3·4·5 통합) | "기능들 한 단계 유지 = **Yes**" |
| ④ 워크플로 (체인지로그 스킬) | 검증 후 **체인지로그 스킬로 문서화** |

09에 쓴 시간이 10에서 계속 이자를 낳는다. **"빨리 가려면 천천히 가라"가 증명되는 장면.**

#### 추론 과정 관찰

> 에이전트 **추론 과정 관찰**이 유용(verbose 모드면 중간 아이디어까지)

결과물만 보면 왜 그렇게 만들었는지 모른다. 추론을 보면 **잘못된 방향으로 가는 걸 도착 전에 잡는다.** 30분 뒤 뒤엎는 것보다 싸다.

그래서 PicoCSS로 방향을 살짝 튼다. 그리고 **요구사항 수정 시 다른 파일도 반영하게 지시** — 또 드리프트 방지다.

### 5. 구현 — 크면 잘라서

> 기능이 너무 크면 **계획 일부만 먼저 구현**해 변경 크기를 관리

계획 전체를 한 번에 구현하라는 법이 없다.

```text
계획: 태스크 1~12
        ↓
한 번에 12개 → 리뷰할 게 산더미 (AI 피로)
1~5만 먼저 → 리뷰 → 6~12
```

07의 "위험 영역은 태스크 그룹 단위로", 08의 "관리 가능한 크기로"와 같은 계열이다.

### 6. 심층 검토 — "내 이름으로 커밋할 수 있는가"

> 진행을 봤어도 부족 → **속도를 늦추고** 심층 리뷰

09의 "run slow to run fast"가 검토 단계에서 재등장. 중간 진행을 봤다고 리뷰를 건너뛰면 안 된다.

> AI 피로를 줄이려 **고수준 요구사항**에 집중, 변수명 트집 금지

08의 저수준 필터 그대로인데 **동기가 하나 추가됐다.**

```text
08: 저수준을 보지 마라  ← 명세에 안 적었으니 트집 잡으면 앞뒤가 안 맞아서
10: 저수준을 보지 마라  ← 그거 보다가 지쳐서 (AI 피로)
```

#### 실전 판별 질문

08의 고수준/저수준 구분은 개념적이라 애매할 때가 있는데, 이건 바로 쓸 수 있다.

```text
리뷰 중 뭔가 거슬린다
        ↓
"이 상태로 내 이름 달고 커밋할 수 있나?"
        ├ 응, 좀 아쉽지만 가능    → 넘어간다
        └ 아니, 이건 좀...        → 고친다
```

**감정("맘에 안 든다")을 판단("책임질 수 있나")으로 바꿔주는 질문**이다.

### 7. 명세 진화 — 이 강의에서 가장 중요한 태도

> props에 인라인 타입 사용 → **독립 TypeScript 타입**으로 바꾸도록 전역 수정 지시

```typescript
// 에이전트가 만든 것 — props 자리에 타입을 그대로 박음
function Card({ title, count }: { title: string; count: number }) { }

// 요청한 것 — 타입을 따로 빼서 재사용·참조 가능하게
type CardProps = { title: string; count: number };
function Card({ title, count }: CardProps) { }
```

> 이런 누락은 **실패가 아니라 명세를 진화시키는 과정** — 포착하면 향후 결과가 좋아짐

태도가 완전히 갈리는 지점이다.

| 이렇게 보면 | 기능 3·4·5에서 |
|---|---|
| "에이전트가 또 틀렸네" | **매번 똑같이 발생**하고 매번 고침 |
| "명세에 이게 빠졌네" | 한 번 적으면 **다시 안 나타남** |

#### 어디에 적는가

"모든 컴포넌트 props는 독립 타입으로 추출한다"는 이 기능만의 얘기가 아니라 프로젝트 전체 규칙이다. 그래서 기능 명세가 아니라 **헌법(기술 스택/코딩 규칙)** 에 들어간다.

이것이 **09의 재계획 ①번("첫 구현에서 빠진 규칙 발견 → 헌법 갱신")의 두 번째 사례**다.

#### 덤 — 태도가 피로에도 영향을 준다

```text
"에이전트가 또 틀렸네" → 짜증 → 리뷰가 감정노동이 됨 → AI 피로 가속
"명세가 자라는 중"     → 담담 → 한 번 적고 끝
```

### 8. 서브에이전트 심층 리뷰

> "속았는지" 검증하려 에이전트에 **여러 서브에이전트(sub-agents)** 를 띄워 이 변경으로 프로젝트 전체 심층 리뷰 지시

"속았는지(fooled)"라는 표현이 날카롭다. 에이전트는 잘 됐다 하고, 앱도 돌고, 테스트도 통과하는데 — **그게 진짜라는 보장이 없다.**

#### 강의가 든 이유 둘

> **생각할 공간 확보** + **메인 에이전트 컨텍스트 보존(오염 방지)**

"오염"의 실체는 **탐색 과정에서 읽은 것들이 메인에 쌓이는 것**이다.

```text
메인이 직접 리뷰:
  컨텍스트 = [명세] + [내가 짠 코드] + [읽은 파일 40개 전부] + [분석 과정]
                                        └────── 쓰레기 ──────┘
  → 정작 수정하려는데 공간이 없음

서브에이전트에 위임:
  서브 컨텍스트 = 파일 40개 전부 (여기서 다 쓰고 버려짐)
  메인 컨텍스트 = [명세] + [내 코드] + [이슈·권고 목록]  ← 결론만
```

**탐색은 밖에서 하고 결론만 들여온다.**

> **두 번째 점검에서 중요한 이슈를 자주 발견** — 도구함에 넣어둘 것

강의가 이례적으로 강하게 권한다. "가끔 쓸모 있다"가 아니라 **"자주 걸린다, 상비하라"** 다.

#### 이후 흐름

```text
서브에이전트가 이슈·권고 반환
        ↓
수정 + 테스트로 좋은 상태 만들기
        ↓
커밋 → 체인지로그 스킬로 문서화 → 커밋 → 머지
```

### 9. 빠른 재계획

> 로드맵을 보며 다음 기능이 여전히 맞는지 확인

09가 **풀 재계획**(헌법+제품계획+로드맵+워크플로)이었다면 여기는 **빠른(quick) 재계획**이다. 매번 넷을 다 뒤집을 필요는 없다. 이번엔 로드맵만.

> 기능 간 **깨끗한 단절**이 AI 피로를 관리(**커피 브레이크 가능**)

1번의 AI 피로로 돌아와 강의가 닫힌다. "커피 브레이크 가능"이 깨끗한 구획의 실질적 정의다.

```text
깨끗하게 끊겼다 = 여기서 자리를 떠도 괜찮다
                = 머릿속에 들고 있어야 할 게 없다
                = 돌아왔을 때 컨텍스트 재구축이 필요 없다
```

미완 작업이 남고 머지도 안 했고 컨텍스트도 안 비웠으면 커피 마시는 동안에도 머리가 계속 돈다. 그게 쌓여 AI 피로가 된다.

## 예시

### 전체 흐름

```text
┌─ 시작 전: 깨끗한 구획 4체크 ────────────┐
│  미완 작업 / 머지 / 로드맵 / 컨텍스트    │
└──────────────────┬──────────────────────┘
                   ↓
             기능 명세 (09 결과 반영)
                   ↓  ← 추론 과정 관찰
                 구현
                   ↓  ← 크면 계획 일부만
             심층 검토
                   ↓  ← "내 이름으로 커밋 가능?"
                   ↓  ← 누락 = 명세 진화
        검증 + 서브에이전트 리뷰
                   ↓  ← 독립적인 두 번째 눈
          커밋 → 체인지로그 → 머지
                   ↓
             빠른 재계획
                   ↓
            ☕ 커피 브레이크
```

### 서브에이전트는 09 Q7 논리의 두 번째 해법

09 검증에서 정리한 명제가 있었다.

> 채점하는 주체는 자기 기준의 결함을 못 잡는다

같은 문제에 09와 10이 서로 다른 답을 낸다.

```text
09의 답:  사람이 디버거로 직접 본다   → 독립적인 눈 = 사람
10의 답:  다른 에이전트를 붙인다      → 독립적인 눈 = 서브에이전트
```

서브에이전트가 유효한 이유는 **그 코드를 안 짰기 때문**이다. 짠 쪽은 자기 논리 안에 갇힌다. (단, 자기 리뷰 편향은 강의에 명시된 이유가 아니라 09 논리와 이어지는 확장이다.)

### 이해도 점검 — "미리 해두는 게 효율적"이라는 함정

대화에서 다룬 시나리오다.

> "기능 2 거의 다 끝났어. 리뷰 두어 개 남았는데 그건 내일 보고, 지금 시간 남으니까 **기능 3 명세부터 뽑아둘게.**"

효율적으로 들리지만 체크리스트 **4개가 전부 걸린다.**

```text
□ 미완 작업 없나?          ✗ 리뷰 두어 개 남음
□ 지난 브랜치 머지했나?     ✗ 기능 2가 아직 브랜치에
□ 다음 로드맵 항목이 맞나?  ✗ 재계획을 안 거침
□ 에이전트 컨텍스트 비웠나? ✗ 기능 2 위에 그대로
```

특히 뒤의 둘이 무섭다.

- **머지 안 됨** — 기능 3 명세가 **확정 안 된 코드를 전제로** 깔린다. 내일 리뷰에서 기능 2를 뜯어고치면 기능 3 명세도 틀어진다.
- **재계획 생략** — 기능 2에서 배운 것(인라인 타입 같은)이 헌법에 안 들어간 채 기능 3 명세를 쓰면, **기능 3에서 똑같은 문제가 또 난다.** 7번의 "실패로 보는 사람"이 되는 길이다.

결론은 **"시간 남으니 미리"가 아니라 남은 리뷰 → 머지 → 재계획 → 컨텍스트 클리어 → 그다음 기능 3.** 커피 한 잔 마시고 시작하는 게 더 빠르다.

### 헷갈리기 쉬운 용어 — 오염 vs 안 비움

둘 다 컨텍스트 얘기지만 결과가 다르다.

| | 맥락 | 결과 |
|---|---|---|
| **오염(pollution)** | 서브에이전트 (8번) | 쓰레기가 쌓여 **공간이 없어짐** |
| **안 비움** | 깨끗한 구획 (3번) | 명세가 **기억 스냅샷이 됨** |

## 요약

- 10은 새 절차를 배우는 편이 아니라 **06~09 사이클을 한 바퀴 더 도는** 편이다. 새로 나오는 건 AI 피로 · 컨텍스트 클리어의 두 번째 이유 · 서브에이전트 리뷰 셋뿐이다.
- **AI 피로**는 검증자의 소진(닳음)이고 **인지 부채**는 이해 못 한 코드의 누적(쌓임)이다. 원인은 같고 증상이 다르며, **피로가 부채를 유발하는 연쇄**로 이어진다.
- **깨끗한 구획 4체크**: 미완 작업 / 머지 / 로드맵 / 컨텍스트. 실질적 기준은 **"여기서 커피 마시러 가도 되는가"** 다.
- **컨텍스트 클리어**는 예산 절약이자, **명세가 대화 기록에 기대고 있지 않은지 시험하는 행위**다. 안 비우면 명세의 결함이 조용히 감춰진다.
- 리뷰는 고수준에 집중하고, 판별은 **"내 이름으로 커밋할 수 있는가"** 로 한다.
- 에이전트의 누락은 **실패가 아니라 명세 진화**다. 전체 규칙이면 헌법에 올린다 — 09 재계획 ①번의 실제 사례.
- **서브에이전트 심층 리뷰**는 탐색을 밖에서 하고 결론만 들여와 메인 컨텍스트를 지킨다. 09의 "채점 기준은 채점으로 못 잡는다"에 대한 **두 번째 해법**이며, 강의는 상비를 권한다.
- 반복 가능한 SDD 프로세스가 자리잡음 → 다음은 **MVP**를 만들 수 있는지 검증.
