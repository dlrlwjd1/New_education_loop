# Agent Replaceability — 대화정리

## 개요
- 이 강의는 코스의 **마지막 기술 강의**이며, 레슨 15가 요약하는 네 기둥 중 "**스킬·표준을 통한 워크플로 자동화**"의 **표준** 쪽을 채운다. (스킬 쪽은 레슨 13.)
- 핵심 명제: SDD는 작업을 **어떻게(how)** 에서 **무엇을·왜(what·why)** 로 옮기므로, 모델·에이전트가 빠르게 발전해도 워크플로를 **한 선택에 묶지 않는다**.
- 14와 15는 한 세션에서 묶어 공부했다. 함께 볼 문서: `15 Conclusion — 대화정리.md`

## 내용

### 1. how → what·why 이동이 왜 에이전트 교체 가능성이 되나

명세가 **고수준(high-level)** 이라 특정 에이전트·IDE에 종속되지 않는다.

조금 더 풀면 두 층의 언어가 다르다.

| | 성질 |
|---|---|
| **how** | **도구별 문법**이다. 어떤 명령을 어떤 순서로, 어떤 API로 — 에이전트마다 다르다 |
| **what · why** | **도구와 무관한 언어**다. "피드백 폼이 필요하고 이유는 이것"은 어느 에이전트가 읽어도 같은 뜻이다 |

그래서 명세를 다른 에이전트로 옮겨도 살아남는다.

### 2. 표준 네 개 — ACP만 성격이 다르다

강의가 드는 표준은 넷이다.

| 표준 | 역할 |
|---|---|
| **MCP** | 외부 도구 연결 |
| **AGENTS.md** | 규칙(rules) |
| **Agent Skills** | 부가 맥락과 함께 반복 워크플로 포착 |
| **ACP** (Agent Client Protocol) | 에이전트를 **클라이언트(에디터)** 에 연결 |

**대화에서 확인한 구분: 앞의 세 개는 에이전트가 *소비하는* 것이고, ACP는 에이전트가 *구현하는* 것이다.**

| | 방향 |
|---|---|
| MCP | 에이전트 → 바깥의 도구·DB·API |
| AGENTS.md | 에이전트 → 규칙 파일을 읽음 |
| Agent Skills | 에이전트 → 워크플로 파일을 읽음 |
| **ACP** | **에이전트 ↔ 클라이언트(에디터)** |

앞 셋은 에이전트에게 **무엇을 알고 무엇을 할 수 있는지**를 주는 표준이다. 즉 에이전트의 *내용물*이다. ACP는 에이전트가 **어디에 꽂히는지**를 정한다. 에이전트 자체를 부품으로 만드는 표준이고, 그래서 강의가 ACP만 따로 절을 떼어 설명한다.

실무에서 갈리는 지점: MCP·스킬은 **에이전트를 바꾸면 따라 옮겨야** 하지만, ACP는 **에디터를 그대로 두고 에이전트를 갈아끼우게** 해준다.

### 3. 에이전트 교체 실증 — 왜 스킬이었고 플러그인은 아니었나

기능 명세 스킬을 **Codex**(OpenAI 에이전트, 데스크톱·에디터·터미널 구동)로 복사 → **다른 경로에 저장되지만 마이그레이션 후 정상 작동**. 같은 프로젝트에서 에이전트를 오가며 SDD 워크플로를 유지한다.

이 실증이 스킬로 이루어진 이유는 레슨 13의 두 사실을 붙이면 나온다.

- **스킬 = 오픈 표준** → 크로스 에이전트 이동 가능
- **플러그인 = 크로스 에이전트 표준이 아직 아님** → Claude Code 확장

Codex는 OpenAI의 에이전트이므로 Claude Code의 플러그인 포맷을 읽을 이유가 없다. 반면 표준은 파일의 **내용**을 보장하므로, 경로만 맞춰주면 다른 에이전트가 그대로 읽는다. "다른 경로에 저장되지만 작동한다"가 정확히 그 뜻이다.

**정리: 플러그인은 배포에 강하고 이식성이 약하다. 스킬은 그 반대다.** 팀에 뿌릴 땐 플러그인, 에이전트를 갈아끼울 땐 스킬이다.

### 4. ACP를 LSP 구조로 설계한 이득 — 조합 폭발 제거

ACP로 서로 다른 에디터·에이전트 조합이 가능하다. **양쪽이 ACP를 지원하면 완벽한 매치**다. 그리고 **ACP 레지스트리**가 에이전트-클라이언트의 발견·설치·연결을 자동화한다(전체 라이프사이클 커버).

강의는 ACP 아키텍처가 **LSP가 쓰는 방식과 일치하도록** 설계되었다고 짚는다. 그 의미는 다음과 같다.

*(배경 지식 — 강의 밖)* LSP 이전에는 **에디터 N개 × 언어 M개 = N×M**개의 통합을 각각 만들어야 했다. LSP가 사이에 프로토콜을 끼워 **N + M**으로 줄였다. 에디터는 LSP만 지원하면 모든 언어를 얻고, 언어는 LSP 서버 하나만 만들면 모든 에디터에 들어간다.

ACP는 같은 구조를 **에디터 × 에이전트**에 적용해 조합 폭발을 없앤다.

강의의 예시가 이것을 보여준다 — JetBrains IDE의 AI Chat → 레지스트리에서 호환 에이전트 목록 → **OpenCode**(인기 오픈소스 에이전트) 설치 클릭 → **설치 + IDE 통합이 자동화**. JetBrains가 OpenCode 전용 통합을 만든 것이 아니라, 양쪽이 같은 프로토콜을 말하기 때문이다.

LSP 구조를 따른 덕에 단순 채팅에 그치지 않고 **Next Edit Suggestion·플랜 모드**까지 표준 안에서 다뤄지며, 나아가 **커스텀 에이전트**를 만들어 로컬 설치도 가능하다.

### 5. 에이전트 선택 — 강의는 답을 주지 않는다

업계가 빠르게 변하고 **벤치마크 리더보드**가 등장했지만 자주 바뀐다. 그래서 **자신에게 중요한 기준**으로 최신 정보를 반영해 직접 결정하라고 한다.

## 예시

레슨 13과 14를 이어붙인 이식성 지도:

| 계층 | 표준인가 | 다른 에이전트로 이동 |
|---|---|---|
| 명세(헌법·기능 명세) | 고수준 마크다운 | 가능 — 도구 무관한 언어 |
| Agent Skills | **오픈 표준** | **가능 (Codex 실증)** |
| AGENTS.md | 표준 | 가능 |
| MCP | 표준 | 가능 |
| ACP | 표준 | 에디터를 고정하고 에이전트를 교체 |
| **플러그인** | **아직 크로스 에이전트 표준 아님** | **불가 — Claude Code 확장** |

## 요약

- SDD 명세는 **고수준**이라 특정 에이전트·IDE에 종속되지 않는다. how는 도구별 문법이고, what·why는 도구 무관한 언어다.
- **MCP·AGENTS.md·Skills·ACP** 네 표준이 교체·조합을 가능하게 한다. 앞 셋은 에이전트가 **소비**하는 표준이고, **ACP는 에이전트가 구현**하는 표준이다.
- 기능 명세 스킬을 **Codex로 옮겨도 작동**한다. 스킬이 오픈 표준이기 때문이고, **플러그인으로는 불가능**했을 실증이다.
- ACP를 **LSP 구조**로 설계해 에디터 × 에이전트의 **조합 폭발(N×M → N+M)** 을 없앴다. 레지스트리가 발견·설치·연결까지 자동화한다.
- 에이전트 선택 기준은 강의가 정해주지 않는다 — 리더보드가 자주 바뀌므로 **자기 기준**으로 최신 정보를 보고 결정한다.
- 워크플로·도구를 에이전트 독립적으로 구축했으며, 표준이 늘수록 이 유연성은 커진다.
