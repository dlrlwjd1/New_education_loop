# Feature Validation

## 개요
- 기능이 준비돼도 **바로 머지하지 않는다** — 에이전트와 협업해 작업을 **검증(validation)** 한다.
- 프로그래머는 오래전부터 **코드 리뷰(code review)** 도구를 잘 써 왔다.

## 내용

### 리뷰 방법
- **커밋 뷰**로 변경을 훑되, CSS 클래스 같은 세부보다 **기능이 동작하고 명세를 반영하는지** 같은 고수준 관심사에 집중.
- 예: `Home.tsx`가 너무 미니멀 → 헤더·메인·푸터 랜드마크가 있는 **레이아웃 컴포넌트**를 서브컴포넌트로, CSS 파일도 요청. 이 코드 실수는 **계획의 실수에서 흘러나온 것** → 에이전트에게 수정을 맡겨 **명세와 구현을 함께** 교정.

### 휴먼 인 더 루프 & 인지 부채
- 에이전트 생성 → 사람 검증의 과정이 **휴먼 인 더 루프**.
- 에이전트가 빨라서 **인지 부채(cognitive debt)**(코드가 무엇을 하고 어떻게 진화했는지 추적하는 정신적 부담)가 화두 → 프로세스를 빠르고 통제 가능하게 하려면 **변경을 관리 가능한 크기**로.
- 에이전트는 변경을 만들면서 **깨진 것이 없는지도 검증**.

### 드리프트(drift) 주의
- 서브컴포넌트 3개가 한 파일에 들어감 → 규칙 위반. IDE **move 도구**로 각 파일로 분리하고 싶지만, 직접 하면 **명세·README 등 다른 산출물이 어긋나는 드리프트** 발생 → **에이전트에게 관련 언급 수정**을 맡겨 나중 시간 낭비 방지.

### 테스트와 버전 관리
- 테스트가 도움 되지만 에이전트가 테스트 패키지를 설치하지 않음 → 모든 기능에 필요하므로 **다음 레슨**에서 다룸.
- 이 브랜치에서 **헌법의 일부(로드맵 단계 체크오프)** 도 함께 갱신됨. 명세 버전 관리·어떤 명세가 어떤 코드를 만들었는지 연결하는 것은 **커뮤니티에서 진화 중인 주제**. 로드맵 변경이 작으면 같은 브랜치, 헌법 변경이 복잡하면 **별도 브랜치**가 나음.
- 작업을 완료로 표시하고 **머지**.

## 요약
- 검증은 **커밋 뷰**로 고수준 관심사(동작·명세 반영)를 리뷰하며, 문제는 **명세·구현을 함께** 고친다.
- 변경은 **관리 가능한 크기**로 유지해 인지 부채를 줄이고, 수동 편집은 **드리프트**를 유발하니 에이전트에 맡긴다.
- 첫 기능을 SDD로 개발·검증·머지 완료. 다음은 프로젝트 범위 재검토(**재계획**).
