# Introduction — 대화정리

## 개요

- 학습일: 2026-07-28
- 원본 강의: `01 Introduction.md`
- 1강의 핵심 세 축(**SDD의 3대 이점 / 명세 작성 방식 / 워크플로 구조**)을 Q&A로 확인한 기록이다.
- 대화에서 실제로 파고든 질문은 세 가지였다.
  1. 게으른 프롬프팅(lazy prompting)과 명세 작성은 어떤 기준으로 나뉘는가
  2. 명세를 에이전트와 함께 쓰면 결국 다시 에이전트의 변덕에 맡기는 것 아닌가
  3. 기능을 브랜치에 격리하면 줄어드는 "컨텍스트 전환"은 누구의 것인가

## 내용

### 1. 게으른 프롬프팅 vs 명세 — 기준은 ROI 계산

처음 떠올린 기준은 **"상용에 나가는 소스는 명세, 간단한 건 게으른 프롬프팅"** 이었다.
방향은 맞지만, 강의가 제시한 기준은 코드의 성격이 아니라 **투입 대비 산출(ROI)** 이다.

> 에이전트가 20~30분(전통적 개발로는 수 시간) 코드를 짤 작업이라면,
> 3~4분 앉아 명확한 지시를 쓰는 편이 낫다.

```text
명세 작성 시간(3~4분)  vs  에이전트가 만들어낼 코드의 양(20~30분 = 사람 기준 수 시간)
```

- 5줄 고치는 일에 명세 4분을 쓰는 건 손해다.
- 에이전트가 30분간 파일 수십 개를 만들 작업에 프롬프트 한 줄만 주는 건, 레버리지가 가장 큰 지점을 버리는 것이다.
- 앞서 본 **작은 명세 → 큰 코드**의 증폭(downstream amplification)이 여기서도 그대로 작동한다.

또 하나의 기준은 **내가 그 결정에 의견이 있느냐**다.
강의가 말한 이유는 "상용이라서 엄격하게"가 아니라,
뛰어난 개발자에게는 **고유한 맥락과 의견(unique context, opinions)** 이 있어
LLM이 무작위로 고르는 것보다 낫기 때문이다.

- ORM을 무엇으로 할지 선호가 있으면 → 명세에 쓴다.
- 아무 의견이 없으면 → 에이전트가 골라도 된다.
- "상용 소스"는 결국 **의견과 제약이 많이 쌓인 코드**라서 결과적으로 기준이 맞아떨어진다.
  다만 개인 토이 프로젝트라도 고집이 있으면 명세를 쓰고, 상용 코드라도 로그 문구 오타 수정은 게으른 프롬프팅이 정답이다.

#### 게으른 프롬프팅이란 (용어 보충)

강의 노트에는 강사가 lazy prompting을 지지한다는 언급만 있고 정의는 없다.
아래는 강의 밖 배경 설명이다.

프롬프트에 맥락을 미리 채워넣지 않고 **일단 최소한만 던져보는 것**을 말한다.
"게으르다"는 건 부주의가 아니라 **의도적인 절약**이다.
모델이 맞히면 시간을 아끼고, 틀리면 그때 맥락을 추가하면 되므로 총 시간이 짧다.

유효한 조건은 명세를 쓸지 말지 판단하는 축과 동일하다.

- 결과를 즉시 확인할 수 있다 (틀리면 바로 안다)
- 재시도 비용이 싸다
- 틀렸을 때 피해가 없다

```text
재시도 비용 낮음 ──────────────────→ 재시도 비용 높음
게으른 프롬프팅                        Spec-Driven Development
```

강사의 입장은 모순이 아니라 **하나의 기준을 양쪽 끝에 적용한 것**이다.

### 2. 에이전트와 명세를 쓰는데 왜 "변덕"이 아닌가

강의는 명세가 없으면 중요한 결정이 **코딩 에이전트의 변덕(whim)** 에 맡겨진다고 경고하면서도,
명세 작성법으로 **에이전트와의 대화**를 제시한다.

해소의 열쇠는 **역할 분담**이다. 에이전트는 제안하고, 결정은 사람이 한다.

| 단계 | 에이전트 | 사람 |
| --- | --- | --- |
| 선택지 나열 | O | |
| 트레이드오프 설명 | O | |
| **결정** | | O |
| 결정을 마크다운으로 받아쓰기 | O | |

에이전트는 **선택지 제시자**이자 **서기(scribe)** 역할이다.

- "에이전트의 변덕"이 위험한 건, 에이전트가 **아무도 결정하지 않은 것을 기본값으로 채워버릴 때**다.
- 대화형 명세 작성에서는 그 빈칸이 사람 앞에 명시적으로 올라온다.
- 결정이 마크다운에 박제되면 다음 세션에서 다시 마음대로 고를 여지가 사라진다 → **컨텍스트 감쇠 제거**와 연결.

### 3. 브랜치 격리로 줄어드는 컨텍스트 전환은 "에이전트"의 것

강의는 기능을 자체 브랜치에 격리하는 이유로 **기능 간 깨끗한 상태 유지**와 **컨텍스트 전환 감소**를 든다.
여기서 1차 수혜자는 **에이전트**다. 에이전트가 **무상태(stateless)** 라는 점과 직결된다.

- 브랜치 하나에 기능 하나만 담기면, 세션 동안 에이전트의 컨텍스트에 **그 기능에 필요한 것만** 들어간다.
- 기능 A의 미완성 코드와 기능 B의 논의가 섞이면, 에이전트는 매번 "지금 뭘 하는 중이었지"를 재구성하다가 엉뚱한 파일을 건드린다.

운용 흐름은 다음과 같다.

```text
기능별 브랜치 격리 → 계획(plan) → 구현(implement) → 검증(verify) → 머지 → 컨텍스트 비우기
```

머지 후 컨텍스트를 비워도 손해가 아니다.
잃어버리면 안 되는 결정은 이미 **헌법(constitution)과 명세(spec)** 에 적혀 있기 때문이다.
세션을 버려도 중요한 것은 남는다 — 이것이 컨텍스트 감쇠 제거의 실제 운용 방식이다.

부수적으로 사람의 컨텍스트 전환도 줄어들지만, 강의 맥락의 1차 대상은 에이전트다.

### 4. 헌법(constitution)과 기능 명세(spec)의 경계

이해도 점검 문제를 풀며 드러난 구분이다.
"기능마다 에러 처리 방식이 제각각"인 상황의 원인은 **규칙을 안 적은 것**이 맞지만,
그 규칙을 **기능 명세에 적으면 문제가 그대로 남는다.**
기능이 20개면 명세도 20개고, 매번 같은 규칙을 옮겨 적다 보면 결국 또 어긋난다.

1강이 헌법을 정의한 문장이 답이다.

> **프로젝트 수준의 헌법(constitution)** 을 만들어 **불변 표준(immutable standards)** 을 정의.

| | 헌법(constitution) | 기능 명세(spec) |
| --- | --- | --- |
| 범위 | 프로젝트 전체 | 기능 하나 |
| 수명 | 불변 | 기능과 함께 끝남 |
| 예 | 에러 처리 규약, 로깅 형식, 네이밍, 테스트 정책 | "엑셀 다운로드 버튼 추가" |

판별 기준은 하나다.

- **기능이 바뀌어도 안 바뀌는 것 → 헌법**
- **이 기능에만 해당하는 것 → 명세**

헌법은 매 세션 부팅 때 주입되므로, 브랜치를 갈아타고 컨텍스트를 비워도 살아남는다.
**컨텍스트 감쇠 제거**가 실제로 작동하는 지점이 여기다.

### 5. 진단과 실행의 재시도 비용은 다르다

게으른 프롬프팅의 판단 기준을 적용할 때 흔히 헷갈리는 지점.

```text
원인 진단           → 게으른 프롬프팅 OK (틀려도 피해 없음)
프로덕션 수정 적용   → 재시도 비용이 급격히 비싸짐
```

기준은 "이 프롬프트가 싼가"가 아니라 **"이 프롬프트의 결과물을 되돌리는 게 싼가"** 다.
프로덕션 배포 스크립트의 에러 로그를 던져 원인을 묻는 건 싸지만,
그 답을 그대로 받아 배포 스크립트를 고치는 것은 별개의 판단이다.

### 6. 무상태(stateless)인데 왜 기억하는 것처럼 보이는가

에이전트가 한 세션 안에서 앞 내용을 잘 기억하는 것은 기억력이 아니라,
**매 요청마다 지금까지의 대화를 통째로 다시 보내기 때문**이다.
모델 자체는 요청 사이에 아무것도 들고 있지 않다.

- 컨텍스트 감쇠는 **세션이 끊기거나 초기화될 때** 발생한다.
- 그래서 강의는 "부팅 시점에 최고 품질 맥락을 주입한다"고 표현한다.
  기억을 이어주는 게 아니라 매번 처음부터 다시 채워 넣는 구조다.

### 7. "명세는 상세할수록 좋다"가 틀린 이유

실무적으로는 지시사항 과다로 인한 혼란도 있지만, **1강이 드는 근거는 두 가지다.**

1. **비례성** — 강사는 게으른 프롬프팅을 지지한다.
   5줄짜리 작업에 명세 4분은 손해다. 문제는 혼란이 아니라 **비용 대비 이득**이다.
2. **명세 작성 비용은 사람의 생각 시간** — 강의는 명세 쓰기를
   **"생각(thinking)이 필요한 어려운 일"** 이라고 못 박는다.
   분량은 타이핑으로 늘릴 수 있지만 진짜 비용은 **아직 결정하지 않은 것을 결정하는 일**이다.
   무작정 많이 쓴 명세는 결정이 아니라 빈말을 채운 것에 가깝다.

## 예시

명세 한 줄이 코드 수백 줄을 결정하는 증폭 구조.

```markdown
<!-- spec.md -->
## 기술 스택
- 데이터 저장소: SQLite + Prisma ORM
```

이 한 문장이 스키마 파일, 마이그레이션, 리포지토리 계층, 테스트 픽스처까지 결정한다.
나중에 아래처럼 한 줄만 바꾸면 동일한 하방 증폭(downstream amplification)이 다시 일어난다.

```markdown
- 데이터 저장소: MongoDB
```

같은 판단 기준을 프롬프트에 적용한 대비.

```text
# 게으른 프롬프팅 — 재시도 비용이 쌀 때
[에러 로그 붙여넣기]

# 성실한 프롬프팅 — 되돌리는 비용이 클 때
아래는 Node 20 / Next.js 15 환경에서 npm run build 실행 중 발생한 에러야.
tsconfig는 strict 모드고, 최근에 zod를 3에서 4로 올렸어.
원인을 추정하고 수정안을 제시해줘.
[에러 로그 붙여넣기]
```

## 요약

- SDD는 **에이전트가 아직 모르는 맥락을 마크다운 명세에 담아** 구현하게 하는 워크플로다.
- 3대 이점: **작은 명세 → 큰 코드 제어 / 컨텍스트 감쇠 제거 / 의도 충실도 향상**.
- 명세를 쓸지 말지는 **상용 여부가 아니라 ROI와 내 의견의 유무**로 판단한다.
  재시도 비용이 싸면 게으른 프롬프팅, 되돌리기 비용이 크면 명세.
- 명세는 에이전트와 대화하며 쓰지만 **결정권은 사람**에게 있다. 에이전트는 선택지 제시자이자 서기다.
- 워크플로는 **헌법(constitution) → 기능 개발 루프(계획·구현·검증)** 이며, 기능별 브랜치 격리는 **무상태 에이전트의 컨텍스트를 깨끗하게 유지**하기 위한 장치다.
- 그린필드(greenfield)는 대화로 헌법을 만들고, 브라운필드(brownfield)는 기존 코드에서 헌법을 뽑아낸다.
- **헌법과 명세의 경계**가 SDD 운용의 핵심이다.
  기능이 바뀌어도 안 바뀌는 것(에러 처리 규약, 로깅 형식 등)은 헌법에,
  이 기능에만 해당하는 것은 명세에 쓴다. 전자를 명세에 흩어 놓으면 기능마다 규칙이 어긋난다.
