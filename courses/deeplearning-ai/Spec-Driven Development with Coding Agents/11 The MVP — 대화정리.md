# The MVP — 대화정리

## 개요

11은 **앞의 10개 강의와 정면으로 부딪히는 것처럼 보이는** 편이다. 지금까지 코스가 반복해서 말한 건 "작게 잘라라"였는데, 여기서는 로드맵 나머지 전체를 한 번에 구현한다.

| 강의 | 지침 |
|---|---|
| 07 | 위험 영역은 **태스크 그룹 단위**로 |
| 08 | **관리 가능한 크기**로 검증 |
| 10 | 기능이 크면 **계획 일부만 먼저** 구현 |
| 10 | 큰 변경은 **AI 피로**를 부른다 |

11:

> 표준 기능 명세 프롬프트의 변형으로 **로드맵의 나머지 전체**를 구현하게 하고

이 모순이 풀리는 지점이 강의의 핵심이고, 결론은 하나로 수렴한다. **이 작업의 산출물은 코드가 아니라 명세다.**

## 내용

### 1. 큰 덩어리 구현의 두 조건

> 이렇게 큰 덩어리는 **헌법·명세 품질에 확신이 있을 때만** 실행 — 맥락이 좋을수록 의도와 정렬된 결과에 자신을 가질 수 있고, **리뷰·검증을 감당**할 수 있어야 함.

조건 두 개가 따로 있는 게 아니라, **첫 번째가 두 번째를 가능하게 만든다.**

#### 명세 품질이 리뷰 부담을 줄이는 메커니즘

부담의 **양이 줄어드는 게 아니라 성격이 바뀐다.**

```text
명세가 부실할 때의 리뷰:
  "이거 왜 이렇게 했지?" → 의도 재구성 → 틀린 부분 찾기
    → 고치기 지시 → 다시 리뷰
  ↑ 루프가 돈다.  비용 = 코드량 × 루프 횟수

명세가 좋을 때의 리뷰:
  "명세대로 됐나?" → 확인
  ↑ 루프가 안 돈다. 비용 = 코드량 × 1
```

강의 표현이 이걸 담고 있다.

> 맥락이 좋을수록 **의도와 정렬된** 결과에 자신을 가질 수 있고

코드량은 똑같이 산더미인데 **산더미를 여러 번 안 봐도 되니까** 감당이 된다.

### 2. "잘라라"는 사라지지 않았다 — 적용 지점이 옮겨갔다

명세 품질에 확신이 있어서 큰 덩어리를 돌렸는데도 강의는 이렇게 말한다.

> 명세 검토 — 에이전트가 공백을 메우며 세운 **잘못된 가정**을 자주 발견

확신했는데도 **자주** 틀린다. 그래서 구현 전 명세를 읽는 단계가 그대로 남아 있고, 저장 방식도 명시된다.

> 계획·요구사항·검증을 훑고 **작은 단계·잦은 커밋**으로 저장

```text
명세:  크게 (로드맵 나머지 전체)
커밋:  작게 (10과 동일)
```

10의 원칙이 폐기된 게 아니라 **층위가 분리됐다.**

### 3. 코드 검증 vs 명세 검증 — 이 강의의 심장

> 보통은 코드 결과를 검증하지만 MVP이므로 **에이전트에 명세 검증**을 요청 → 유용하게도 **계획의 구멍(holes)** 을 드러냄

09에서 정리한 명제가 열쇠다.

> 채점하는 주체는 자기 기준의 결함을 못 잡는다

여기서 **채점 기준이 무엇인지**가 전부다.

```text
08 코드 검증
  채점 대상 = 코드
  채점 기준 = 명세        ← 명세는 '자(ruler)'다

11 명세 검증
  채점 대상 = 명세        ← 자였던 게 대상으로 내려온다
  채점 기준 = 로드맵 · 제품계획 · 헌법 · 원래 의도
```

**자로 재는 행위는 자의 눈금이 틀렸는지 절대 알려주지 않는다.** 코드가 명세대로 100% 구현되어도, 명세에 로드맵 항목 3개가 빠져 있으면 코드 검증은 만점을 준다. 그게 만점의 정의다.

기준을 한 층 올려야 아래층의 결함이 보인다.

#### 그래서 "구멍(holes)"이라는 단어가 정확하다

```text
코드 검증 → '있는 것'이 맞는지 본다  → 잘못된 구현을 잡는다
명세 검증 → '없는 것'을 찾는다       → 빠진 계획을 잡는다
```

구멍은 **없는 것**이다. 애초에 아무도 요구하지 않은 기능이 빠진 건 코드에 흔적이 남지 않는다.

### 4. 왜 하필 MVP에서 이걸 하는가

> MVP를 **헌법·완성된 기능 명세의 극한 테스트**로 봄

시험 대상이 코드가 아니라 **명세와 헌법**이다. 시험 대상이 바뀌었으니 채점 대상도 바뀌는 게 당연하다.

로드맵 나머지 전체를 한 번에 돌렸으니 명세의 결함도 한 번에 증폭돼서 드러난다. 그게 "극한 테스트"의 실질적 의미다.

떨어졌을 때의 처방도 명시돼 있다.

> 원한 것과 다르면 에이전트를 벗어나게 한 원인을 제거하는 **재계획**이 필요하다는 신호

```text
MVP가 이상하게 나왔다
        ↓
코드를 고친다?  ✗
명세·헌법을 고친다  ✓   ← 09의 재계획
```

### 5. 진짜 산출물은 명세다

강의의 마지막 흐름이 이상해 보인다.

> 이 평가를 이해관계자와 공유해 MVP 리뷰 → 브랜치 머지 **또는 아카이브**

기능 1·2는 전부 머지했는데, 지금까지 중 가장 큰 작업물인 MVP에는 **버리기** 선택지가 붙는다. 대화에서 도달한 답:

```text
겉보기 산출물:  MVP 코드            → 머지 또는 아카이브 (버려도 됨)
진짜 산출물:    개선된 명세 · 헌법   → 무조건 남는다
```

이해관계자와 공유하는 것이 코드가 아니라 **평가(assessment)** 인 것도 같은 이유다.

그래서 아카이브가 손실이 아니다. 코드를 버려도 "명세에 이게 빠져 있었다"는 발견은 남고, 다음 바퀴에서 회수된다. **10의 "에이전트의 누락은 실패가 아니라 명세 진화"를 로드맵 전체 규모로 한 번에 돌린 것**이 이 강의다.

> 참고 — MVP라는 용어 자체가 원래 "제품 출시"가 아니라 **학습 수단**을 뜻하는 린 스타트업 개념이다. 강의는 이 배경을 설명하지 않지만 결론이 그 원래 뜻과 일치한다. (강의 밖 확장)

### 6. 마지막 줄의 배당금

> SDD 워크플로가 **헌법+두 기능만으로** 유용한 데모를 만듦

사람이 직접 공들여 만든 건 **헌법 하나 + 기능 명세 둘**뿐이다. 그 축적만으로 로드맵 나머지 전체가 한 번에 나왔다.

06~10에서 매번 귀찮게 명세를 고치고 헌법을 갱신한 것에 대한 배당금이 여기서 지급된다.

## 예시

### 전체 흐름

```text
경영진: "MVP 주세요"
        ↓
┌─ 실행 조건 확인 ───────────────────┐
│  □ 헌법·명세 품질에 확신 있나?      │
│  □ 리뷰·검증을 감당할 수 있나?      │
└────────────────┬───────────────────┘
                 ↓
   표준 명세 프롬프트 변형 → 로드맵 나머지 전체
                 ↓  ← 에이전트의 질문·권고에 답 → Submit
        MVP 명세 디스크 기록
                 ↓
        명세 검토  ← 잘못된 가정 자주 발견
                 ↓  ← 작은 단계·잦은 커밋
           대규모 구현
                 ↓
     스크립트로 앱 실행 (DB 샘플 데이터)
                 ↓
     ★ 코드 검증 아님 → 에이전트에 명세 검증
                 ↓
        계획의 구멍(holes) 드러남
                 ↓
   이해관계자와 평가 공유 → MVP 리뷰
                 ↓
        ┌────────┴────────┐
      머지              아카이브
        └────────┬────────┘
                 ↓
      어느 쪽이든 명세·헌법은 남는다
      (틀렸으면 → 09 재계획)
```

### "결과물만 보고 판단하면 된다"의 함정

대화에서 나온 아이디어 — 코드를 다 볼 수 없으니 DB와 화면만 보고 판단하겠다는 안이다. 리뷰를 좁힌다는 방향은 강의와 같지만 **층위가 반대**다.

```text
결과물 확인:  코드 → DB/화면     (층위를 내려서 좁힘)
강의:        코드 → 명세        (층위를 올려서 좁힘)
```

강의에도 결과물 확인 장면은 나온다.

> 스크립트로 앱 실행. 각 섹션이 DB에서 쿼리한 **샘플 데이터**로 풍부해짐

하지만 거기서 끝내지 않고 명세 검증으로 넘어간다. 이유는 10의 "속았는지(fooled)" 문제와 같다.

```text
DB에 데이터 있고 화면에 잘 뜬다
        ↓
≠ 명세에 적힌 게 다 구현됐다
        ↓
앱은 돌면서도 로드맵 항목 3개가 조용히 빠져 있을 수 있다
```

**결과물만 보면 없는 것은 안 보인다.** 3번의 "구멍은 없는 것"과 정확히 같은 함정이다.

### 검증 층위 정리

| | 채점 대상 | 채점 기준 | 잡히는 것 |
|---|---|---|---|
| **08 코드 검증** | 코드 | 명세 | 잘못된 구현 |
| **11 명세 검증** | 명세 | 로드맵·헌법·의도 | 계획의 구멍 |
| **결과물 확인** | 화면·DB | 눈으로 봤을 때 그럴싸함 | 눈에 띄는 오동작 |

## 요약

- 11은 "작게 잘라라"를 뒤집는 것처럼 보이지만, **명세는 크게 / 커밋은 작게**로 층위가 분리된 것이다.
- 큰 덩어리의 조건 둘은 병렬이 아니다. **명세 품질에 대한 확신이 리뷰 감당 가능성을 만든다** — 리뷰의 양이 아니라 루프 횟수가 줄기 때문.
- 그럼에도 **잘못된 가정은 자주 발견된다.** 확신은 명세 검토를 면제해주지 않는다.
- 이 강의의 심장은 **채점 대상을 코드에서 명세로 올린 것**이다. 명세가 자(ruler)인 동안에는 명세의 결함이 원리적으로 안 보인다.
- **구멍(holes)은 없는 것**이라서 코드에도 화면에도 흔적이 없다. 기준을 한 층 올려야 보인다.
- MVP는 **헌법·명세의 극한 테스트**다. 실패의 처방은 코드 수정이 아니라 09의 **재계획**이다.
- MVP의 진짜 산출물은 **개선된 명세와 헌법**이다. 그래서 코드는 아카이브해도 손실이 아니고, 이해관계자에게 공유하는 것도 코드가 아니라 **평가**다.
- 사람이 만든 건 **헌법 + 기능 명세 둘**뿐인데 로드맵 전체가 나왔다 — 06~10의 누적에 대한 배당금.
- 다음은 **브라운필드(기존 코드베이스)** 에 SDD를 도입하는 법.
