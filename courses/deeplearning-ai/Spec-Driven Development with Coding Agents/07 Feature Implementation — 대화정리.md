# Feature Implementation — 대화정리

## 개요

06에서 만든 기능 명세(Hello Hono)로 실제 구현을 수행하는 강의다. 강의를 먼저 읽고 Q&A로 이해도를 확인했다.

- 구현 직전에도 **컨텍스트를 비운다**(`/clear`) — 06의 새 컨텍스트와 같은 패턴.
- 태스크 그룹 쪼개기는 **조건부**다. 기본은 한 번에, 위험 영역만 나눠서.
- 개발자의 역할은 **감독자**이며, 에이전트에게 주는 **계약**은 06의 명세 그 자체다.
- 자체 검증과 사용자 검증은 **보는 대상이 다르다.**

## 내용

### 1. `/clear` — 문서만으로 구현이 되어야 한다

구현 시작 전 `/clear`로 컨텍스트를 비운다. 근거는 "**명세 문서에 필요한 내용이 담겨 있음**"이다.

핵심은 **해당 문서만으로 구현이 되는 것이 중요하다**는 점이다. 06의 새 컨텍스트와 완전히 같은 패턴이고, 이제 두 단계에서 반복된다.

| 단계 | 비우는 행위 | 유일한 출처 |
|---|---|---|
| 06 명세 | 새 컨텍스트(fresh context) | 헌법 |
| 07 구현 | `/clear` | 기능 명세 |

부수 효과도 동일하다 — 명세에 빠진 게 있으면 **구현이 어긋나면서 드러난다.** 대화를 이어갔다면 에이전트가 기억으로 메워버려서 명세가 부실해도 티가 나지 않았을 것이다.

### 2. 태스크 그룹 쪼개기는 조건부다

> 때로는 태스크 그룹을 **하나씩** 처리해 더 작은 단계·커밋으로 진행 — 특히 **보안·데이터베이스 관리**처럼 작은 실수가 나중에 **복리**로 커지는 영역에 유용.

- **조건**: 보안 · 데이터베이스 관리
- **근거 표현**: 복리

#### 왜 복리가 강력한 이유가 되나

복리는 초기 오차가 **시간에 비례**해서가 아니라 **배수로** 커진다는 뜻이다.

- DB 스키마를 잘못 잡으면 → 그 위에 쌓인 코드 전부가 그 형태를 전제하고, 이미 들어간 데이터까지 마이그레이션 대상이 된다
- 인증 로직에 구멍이 있으면 → 이후 모든 기능이 그 구멍 위에서 동작한다

일반 기능은 나중에 고쳐도 그 파일만 고치면 되지만, 이 둘은 **뒤에서 잡는 비용이 앞에서 잡는 비용과 비교가 안 된다.** 그래서 검토 지점을 촘촘히 박는다.

#### 05와 다른 점 — 기본값은 한 번에

**기본값은 모든 태스크 그룹을 한 번에 구현하는 것**이다. 05에서 로드맵을 "작게 쪼개라"고 무조건 지시했던 것과 달리, 여기서는 조건부다. 매번 쪼개면 느려지므로 위험한 영역에만 적용한다.

### 3. 계약(contract) — 새로 만드는 물건이 아니다

> 이 패러다임에서 개발자의 핵심 역할은 **아키텍트·감독자(supervisor)** 로서 에이전트에 **명확한 계약(contract)** 을 제공하는 것.

여기서 말하는 계약은 06에서 만든 산출물 세 개 — **계획 · 요구사항 · 검증** — 그 자체다. 구현 단계에서 새로 작성하는 문서가 아니다.

"계약"이라는 단어를 쓰는 이유는, 계약은 **이행 여부를 판정할 수 있어야** 성립하기 때문이다. 그 판정 조항이 **스코어카드**다. 요구사항만 있고 검증이 없으면 "잘 만들어 주세요" 같은 소망이지 계약이 아니다. 06에서 세 산출물을 동기화하라고 한 이유가 여기서 다시 보인다.

### 4. 감독과 관찰

- Claude 실행 중 콘솔에서 변경을 **실시간 관찰**하고, 이후 커밋 창에서 최종 변경을 확인 → 작업 리뷰를 **조기에** 시작할 수 있다.
- 에이전트는 각 태스크 그룹별 수행 내용의 요약과 세부를 제공한다.

### 5. 실행 확인

- `package.json`에서 앱 실행 → 콘솔에서 서버 시작 → 브라우저에서 결과 확인.
- nano 규모라 화면은 소박하지만 **픽셀 확인**을 한다. 화면이 실제로 어떻게 보이는지는 스코어카드가 대신 봐줄 수 없는 영역이다.

### 6. 검증이 두 번인 이유

에이전트가 **자체 검증**을 수행하고, 다음 레슨에서 **사용자 검증**을 또 한다.

핵심은 **에이전트의 자체 검증은 자기가 만든 것을 자기가 채점하는 것**이라는 데 있다. 에이전트는 스코어카드 **항목대로** 체크한다. 그런데 그 스코어카드가 잘못됐거나 항목이 빠져 있으면 에이전트는 그것을 발견하지 못한다. 06에서 본 실패가 정확히 이것이다 — **없는 기준으로 통과 판정**. 자체 검증은 그 상황에서도 만족스럽게 "전부 통과"를 출력한다.

| | 누가 | 무엇을 확인 |
|---|---|---|
| **자체 검증** | 에이전트 | 코드가 **스코어카드를 만족하나** |
| **사용자 검증** | 사람 | **스코어카드가 옳았나**, 이게 내가 원한 것인가 |

근거는 04강의에 한 줄로 있다.

> **코드에 대한 최종 책임은 나에게** 있다

## 예시

### 구현 단계 흐름

```text
1. 기능 명세 계획 빠르게 재검토
2. /clear  ← 명세 문서만 남긴다
3. "모든 태스크 그룹을 구현하라"
   └ 보안·DB 영역이면 태스크 그룹 하나씩 (복리 위험)
4. 콘솔에서 실시간 관찰 → 커밋 창에서 최종 확인
5. 앱 실행 → 브라우저에서 픽셀 확인
6. 에이전트 자체 검증
   ↓
7. 사용자 검증 (다음 강의)
```

### 스코어카드 복습

06에서 만든 **검증(validation) 산출물**의 이름이다.

- "이 기능이 됐다"고 말하려면 무엇이 참이어야 하는지를 적은 **체크리스트**
- **에이전트가 스스로** 자기 결과를 대조하는 기준 (사람이 채점하는 표가 아님)
- **구현 전에** 만든다 — 나중에 만들면 나온 결과물에 맞춰 기준이 휜다
- Phase 1에서는 "curl로 이 엔드포인트를 치면 이 응답" 수준의 항목

에이전트는 스코어카드 항목대로만 체크하므로, **스코어카드 자체가 틀렸으면 잡아내지 못한다.** 그래서 사람 검증이 한 번 더 필요하다.

## 요약

- 구현 전 `/clear`로 컨텍스트를 비운다. 목적은 **명세 문서만으로 구현이 되게 하는 것**이며, 06의 새 컨텍스트와 같은 패턴이다.
- 명세에 빠진 것이 있으면 구현이 어긋나면서 드러난다 — 컨텍스트를 비우는 행위가 명세를 시험한다.
- 태스크 그룹 쪼개기는 **조건부**다. 기본은 한 번에 전부, **보안·DB**처럼 실수가 **복리**로 커지는 영역만 하나씩.
- **계약 = 06의 명세 세 산출물**. 새로 만드는 게 아니며, 판정 조항(스코어카드)이 있어야 계약으로 성립한다.
- 개발자의 역할은 **아키텍트·감독자**. 실시간 관찰로 리뷰를 조기에 시작한다.
- **자체 검증은 코드가 스코어카드를 만족하는지**, **사용자 검증은 스코어카드가 옳았는지**를 본다. 최종 책임은 사람에게 있다.
