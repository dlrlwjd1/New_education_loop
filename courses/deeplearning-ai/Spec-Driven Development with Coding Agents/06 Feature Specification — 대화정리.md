# Feature Specification — 대화정리

## 개요

로드맵의 Phase 1 단계 하나를 실제 명세로 푸는 강의다. 앞서 이름 붙인 **계획의 아래층**이며, 05에서 만든 헌법이 여기서 처음으로 **쓰이는 쪽**이 된다.

이 대화에서는 스코어카드의 정체, 명세 대화에서 사람이 빠지기 쉬운 함정, 그리고 산출물 세 개의 동기화를 중심으로 다뤘다.

- 스코어카드는 **구현 전에** 만들어 두는 성공 기준이다.
- 선택지 안에서 고르는 것은 검토가 아니다 — **선택지 자체를 의심**할 수 있어야 한다.
- 산출물 세 개(계획·요구사항·검증)는 **함께 움직인다.**

## 내용

### 1. 전체 구조

```text
로드맵 Phase 1 (Hello Hono)
   │
   ├─ 새 컨텍스트 + 기능 브랜치에서 시작
   │
   └─ 명세 대화 → 산출물 3종
        ├── 기능 계획(plan)        ← 접근 방식 · 작업 순서
        ├── 요구사항(requirements)  ← 기술적 필요 · 제약
        └── 검증(validation)        ← 스코어카드
                     ↓
              검토 → 수정 → 커밋
                     ↓
                  구현 (다음 강의)
```

헌법이 세 파일이었듯 기능 명세도 세 산출물로 떨어지고, 05에서 본 문제가 그대로 반복된다 — 하나를 고치면 나머지도 **동기화**해야 한다.

### 2. 스코어카드란 무엇인가

강의가 **검증(validation)** 산출물을 부르는 이름이다. "이 기능이 제대로 됐다"고 말하려면 무엇이 참이어야 하는지를 항목으로 적어둔 체크리스트다.

- **누가 쓰나** — 에이전트가 **스스로** 체크한다. 내가 채점하려고 만드는 표가 아니라, 에이전트가 구현을 끝내고 자기 결과를 대조할 기준이다.
- **언제 만드나** — 구현 **전에**, 명세 단계에서. 강의가 좋은 계획의 요소로 접근 방식·작업 순서와 나란히 **성공 검증 방법**을 꼽는 이유다. 구현 후에 기준을 정하면 나온 결과물에 맞춰 기준이 휘어버린다.
- **뭐가 들어가나** — Phase 1(Hello Hono)에서는 확인 방법으로 **수동 curl**을 골랐다. "curl로 이 엔드포인트를 치면 이런 응답이 온다" 수준의 확인 가능한 항목이 들어간다.

실제 형태와 운용은 `08 Feature Validation.md`에서 다룬다. 이 강의의 범위는 "명세 단계에서 미리 만들어 둔다"까지다.

### 3. 명세 대화의 함정 — 선택지 안에서만 생각하기

> 에이전트가 핵심 결정을 요청 — **잠재적 충돌·문제**에 주의. 제안에 무조건 동의할 필요 없이 **걸리는 부분은 명확히** 질문.

명세 대화 중에 에이전트가 선택지를 들고 온다. 05의 인터뷰 질문과 같은 방식으로, 질문이 뜨고 고르고 **Submit**을 누른다.

여기에 함정이 있다. **선택지가 주어지면 그 안에서만 생각하게 된다.**

```text
Phase 1 범위를 어떻게 잡을까요?

  ( ) A. 서버만 띄우기
  ( ) B. 서버 + 기본 라우팅
  ( ) C. 서버 + 라우팅 + DB 연결

              [ Submit ]
```

버튼이 **Submit 하나뿐**이다. "잠깐, C는 Phase 2 내용 아닌가요?"에 해당하는 버튼은 없고, 그건 직접 타이핑해야 한다.

- A 고르고 Submit → 클릭 두 번, 3초
- "이 선택지가 왜 여기 있죠?" → 직접 문장을 써야 함

구조상 앞쪽이 압도적으로 쉽다. 가만히 두면 계속 고르고 Submit만 누르게 된다.

#### 그래서 뭐가 문제인가

**검토라는 절차는 있는데 실제로 걸러지는 건 없는** 상태가 된다. 매번 화면이 뜨고 매번 승인하니 "나는 검토하고 있다"는 느낌은 드는데, 에이전트 입장에서는 자기 제안이 전부 통과된 것과 똑같다.

03의 아키텍트 비유에서 인간의 역할은 **검토·수락(또는 변경 요청)** 이었다. 검토 후 선택지가 둘인데, 실제로는 **수락**만 하게 되고 **변경 요청**이 사라진다. 그러면 남는 건 수락 도장 찍기뿐이다.

> 선택지 안에서 고르는 게 검토가 아니라, **선택지 자체를 의심할 수 있어야 검토다.**

#### "잠재적 충돌"이 뭘 말하나

에이전트의 제안이 이미 합의된 것 — 즉 헌법 — 과 어긋나는 경우다. 에이전트가 새 컨텍스트에서 헌법을 읽고 오지만 그 해석이 내 의도와 다를 수 있다.

- 로드맵 Phase 1의 **범위**를 슬쩍 넓힌 제안
- 기술 스택에 없던 라이브러리를 자연스럽게 끼워 넣은 제안

둘 다 개별적으로 보면 합리적이다. **헌법과 대조해야** 어긋난 게 보인다.

#### 실제 대응 결과

| 결정 | 성격 |
|---|---|
| Phase 1 범위는 **그대로** | 넓히지 않겠다고 명시적으로 붙잡음 |
| **Hono 버전 고정** | 사람이 추가한 제약 |
| **strict TypeScript 강제** | 사람이 추가한 제약 |
| 확인은 수동 curl | 검증 방법 선택 |

버전 고정과 strict 모드는 에이전트가 알아서 걸어줄 항목이 아니다. 걸리는 부분을 질문하고 제약으로 굳힌 결과다.

#### 왜 하필 이 단계에서 강조하나

> 여기서의 명세 변경은 하방으로 **수백 줄 코드**로 확장

Submit 한 번이 코드 수백 줄이 된다. 명세에서 "이거 좀 이상한데"를 한 문장으로 잡으면 30초지만, 구현 뒤에 잡으면 수백 줄을 되돌려야 한다.

### 4. 왜 새 컨텍스트(fresh context)로 시작하나

근거 표현은 **공식 출처**다.

> 에이전트는 **공식 출처인 헌법**에서 필요한 것을 얻음

한 발 더 들어가면, 새 컨텍스트는 **헌법이 충분한지 시험하는 장치**이기도 하다. 이전 대화를 이어가면 에이전트가 "헌법에 안 적혀 있지만 아까 대화에서 나온 것"을 써버린다. 그러면 헌법이 비어 있어도 티가 안 난다. 컨텍스트를 비우면 헌법에 적힌 것만 남으므로 **빠진 게 있으면 바로 드러난다.**

기능 작업은 **별도 브랜치(feature branch)** 에서 진행한다.

### 5. oversteer — 이름만 바뀐 옛 원칙

> 중요한 기술적 필요·제약을 기재하되 **변수명 같은 사소한 세부는 넣지 않음**. "통제하되 과도하게 조종(oversteer)하지 않기".

이건 03강의의 **적절한 상세 수준(많이 / 적게)** 이 이름을 바꿔 다시 나온 것이다.

- **통제(control)** = 많이 쪽 — 기술적 필요와 제약은 확실히 적는다
- **과잉 조종(oversteer)** = 적게 쪽 위반 — 변수명처럼 에이전트가 알아낼 수 있는 저수준 결정을 적는 것

같은 원칙에 붙은 세 가지 이름:

| 강의 | 표현 |
|---|---|
| 03 | 많이 / 적게, 적절한 상세 수준 |
| 03 | 시공자에게 일하는 법을 지시하지 말라 |
| 06 | 통제하되 과잉 조종하지 말라 |

### 6. 산출물 세 개는 함께 움직인다

검토 중 "플레이스홀더 홈페이지 추가" 변경이 생기면 계획에서 끝나지 않고 셋 다 움직인다.

```text
계획 검토 중 홈페이지 추가 요청
   ↓
요구사항에 반영        ("홈페이지 변경 반영됨")
   ↓
검증도 갱신            ("홈페이지에 맞춰 갱신됨")
```

**하나만 고쳤을 때 뭐가 잘못되는지**가 요점이다. 요구사항만 고치고 검증을 빠뜨리면 — 스코어카드에 홈페이지 항목이 없으니, 에이전트가 홈페이지를 안 만들어도 검증은 **전부 통과**로 나온다. 없는 기준으로 합격 도장이 찍힌다.

05에서 헌법 세 파일을 직접 고치지 말라고 했던 이유가 여기서 그대로 재현된다.

## 예시

### 요구사항에서 무엇을 빼야 하나

```text
- 라우터 핸들러 함수 이름은 handleRoot 로 한다   ← 뺀다
- Hono 버전은 4.6.x 로 고정한다                  ← 남긴다
```

판단 기준은 03에서 세운 것 그대로 — **에이전트가 스스로 알아낼 수 있는가.**

| 항목 | 알아낼 수 있나 | 결론 |
|---|---|---|
| 핸들러 함수 이름 | 가능 | 과잉 조종 → 뺀다 |
| Hono 버전 고정 | 불가 (프로젝트 결정) | 제약 → 남긴다 |

### 명세 단계 흐름

```text
1. 새 컨텍스트 + 기능 브랜치
2. 프롬프트로 대화 시작
   └ 기능 명세 · 작업 계획 · 요구사항 수집 · 검증용 스코어카드
3. 에이전트의 핵심 결정 요청에 응답
   └ 그냥 고르지 말고 헌법과 대조 → 걸리면 질문
4. 산출물 검토
   ├ 계획      — 초기에 바로잡아 궤도 유지
   ├ 요구사항  — 통제하되 과잉 조종 금지
   └ 검증      — 요구사항과 동기화
5. 커밋 → 구현으로
```

## 요약

- 기능 개발은 **새 컨텍스트 + 기능 브랜치**에서 시작한다. 새 컨텍스트를 쓰는 이유는 **헌법을 공식 출처로 강제**하기 위해서이며, 부수적으로 헌법의 빈 곳이 드러난다.
- **스코어카드 = 검증 산출물**. 에이전트가 스스로 대조할 성공 기준이며 **구현 전에** 만든다. 나중에 만들면 결과물에 맞춰 기준이 휜다.
- 명세 대화에서 에이전트의 제안은 **헌법과 대조**해야 어긋난 게 보인다. Submit 버튼만 있고 "이의 있음" 버튼은 없으므로, 변경 요청은 의식적으로 해야 한다.
- **선택지 안에서 고르는 게 검토가 아니다. 선택지 자체를 의심할 수 있어야 검토다.**
- oversteer는 03의 **많이/적게**가 이름만 바꾼 것이다. 통제는 하되 변수명 같은 저수준은 넘기지 않는다.
- 산출물 세 개는 **동기화**되어야 한다. 검증을 빠뜨리면 **없는 기준으로 통과 판정**이 난다.
- 명세 한 줄이 코드 수백 줄로 증폭되므로, 이 단계에 쓰는 시간이 가장 값싸다.
