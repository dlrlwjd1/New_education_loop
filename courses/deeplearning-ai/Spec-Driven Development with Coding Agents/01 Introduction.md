# Introduction

## 개요
- **Spec-Driven Development(SDD, 명세 주도 개발)** 는 에이전트 코딩 도구로 진지한 애플리케이션을 만들 때 **현재 가장 좋은 워크플로**다. (JetBrains 협력, 강사 Paul Everett)
- 코드를 손으로 쓰는 대신, 에이전트가 아직 갖지 못한 **맥락(context)** 을 마크다운 명세(spec)에 적어 주면 에이전트가 그 명세를 구현한다.

## 내용

### SDD의 3가지 이점
1. **작은 명세 변경으로 큰 코드 변경 제어** — "SQLite + Prisma ORM 사용" 한 문장이 수백 줄에 영향. "MongoDB로 바꿔"로 동일한 하방 증폭(downstream amplification). 명세 작성이 코드 작성보다 훨씬 효율적.
2. **컨텍스트 감쇠(context decay) 제거** — 에이전트는 **무상태(stateless)** 라 부팅 시점에 최고 품질 맥락을 주입해 세션 간 비타협 요소(non-negotiable)를 보존.
3. **의도 충실도(intent fidelity) 향상** — 문제·성공 기준·제약을 정의하면 에이전트가 이를 확장해 더 완전한 계획을 세움.

### 명세 작성 방법
- Claude Code·Gemini·ChatGPT Codex 같은 에이전트와 **대화**하며 핵심 아키텍처 선택(트레이드오프)을 하고, 그 결정을 **마크다운 파일로 요약**하게 하는 방식.
- 명세 작성은 **생각(thinking)** 이 필요한 어려운 일 — 어떤 제품·기능·기술 아키텍처를 만들지 결정해야 함. 명세가 없으면 이 중요한 결정이 코딩 에이전트의 변덕에 맡겨져 유지보수성이 떨어지고 이상한 제품이 나옴.

### 워크플로 구조
- **프로젝트 수준의 헌법(constitution)** 을 만들어 불변 표준(immutable standards)을 정의.
- 이후 **기능 개발 루프(feature development loop)** 를 반복 — 각 기능을 자체 브랜치에 격리하고 **계획(plan)·구현(implement)·검증(verify)** 단계로 진행 → 기능 간 깨끗한 상태 유지, 컨텍스트 전환 감소.
- **그린필드(greenfield, 신규)** 와 **브라운필드(brownfield, 기존 코드베이스)** 모두 지원 — 그린필드는 대화로 헌법 작성, 브라운필드는 기존 코드 기반으로 헌법 생성.
- 이 코스에서는 SDD 워크플로를 자동화하는 **에이전트 스킬(agent skills)** 작성법도 다룸.

### 왜 명세인가
- 짧은 프롬프트 하나로 끝나면 좋지만(게으른 프롬프팅 lazy prompting 지지), 복잡도가 있는 프로젝트에는 뛰어난 개발자들이 거의 항상 **상세 명세**를 씀 — 고유한 맥락·의견이 있어 LLM이 무작위로 고르는 것보다 낫기 때문.
- 에이전트가 20~30분(전통 개발 수 시간에 해당) 코드를 짤 것이라면, 3~4분 앉아 **명확한 지시**를 쓰는 편이 낫다.

## 요약
- SDD는 에이전트 코딩의 최선 워크플로로, **명세에 맥락을 담아** 에이전트가 구현하게 한다.
- 3대 이점: **작은 명세→큰 코드 제어, 컨텍스트 감쇠 제거, 의도 충실도 향상**.
- 워크플로는 **헌법 → 기능 개발 루프(계획·구현·검증)** 이며 그린필드·브라운필드 모두 지원한다.
