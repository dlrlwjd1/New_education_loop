# Feature Specification

## 개요
- 로드맵의 **첫 기능(feature)** 을 명세(spec)로 구축한다 — 코딩 전에 명세를 논의하고 모든 세부를 명확히 한다.
- 좋은 계획은 **접근 방식·작업 순서·성공 검증 방법**을 담는다.

## 내용

### 준비
- AgentClinic 로드맵의 **Phase 1 기능: Hello Hono**. 아직 코딩은 이르며 명세부터.
- **새 에이전트 컨텍스트(fresh context)** 로 시작 — 에이전트는 공식 출처인 **헌법**에서 필요한 것을 얻음.
- 이 기능은 **별도 브랜치(feature branch)** 에서 작업(에이전트에게 지시).

### 명세 대화
- 프롬프트로 **기능 명세·작업 계획·요구사항 수집·검증용 스코어카드(scorecard)** 대화를 시작.
- 에이전트가 핵심 결정을 요청 — **잠재적 충돌·문제**에 주의. 제안에 무조건 동의할 필요 없이 **걸리는 부분은 명확히** 질문.
- 예시 결정: Phase 1 범위는 그대로, 요구사항은 **Hono 버전 고정·strict TypeScript 강제**, 확인은 수동 curl → **Submit**.

### 산출물 검토 (휴먼 인 더 루프)
1. **기능 계획(feature plan)** 검토 — 초기에 문서를 바로잡아 에이전트를 궤도에 유지. 문제가 있으면 에이전트에게 수정 요청(요구사항·검증 **동기화** 유지). 예: 예쁜 플레이스홀더 홈페이지 추가를 에이전트 통해 반영.
2. **요구사항(requirements)** — 홈페이지 변경 반영됨. 중요한 기술적 필요·제약을 기재하되 **변수명 같은 사소한 세부는 넣지 않음**. "통제하되 과도하게 조종(oversteer)하지 않기".
3. **검증(validation)** — 에이전트가 제대로 했는지 스스로 체크할 수 있게. 홈페이지에 맞춰 갱신됨.
- 완료 후 IDE에서 **커밋**.

### 요점
- 여기서의 명세 변경은 하방으로 **수백 줄 코드**로 확장 → 이 단계에 시간 쓰는 것은 잘 쓰는 것.

## 요약
- 기능 개발은 **새 컨텍스트 + 기능 브랜치**에서 명세 대화로 시작한다.
- 산출물(**계획·요구사항·검증**)을 검토·동기화하며, 통제와 과잉 조종 사이 균형을 잡는다.
- 명세는 코드로 증폭되므로 초기 투자가 가치 있다. 다음은 **구현(implementation)**.
