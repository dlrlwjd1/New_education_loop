# Creating the Constitution — 대화정리

## 개요

강의를 먼저 훑은 뒤 Q&A로 확인한 내용이다. 헌법을 **어떻게 만드는가**보다, 강의가 그 방식을 택한 **이유**를 짚는 데 초점을 뒀다.

- 헌법 수정을 에이전트에게 맡기는 이유는 **문서 일관성**이다.
- 로드맵을 작게 쪼개는 이유는 기간이 아니라 **검토 지점의 개수**다.
- 로드맵에는 **시간 개념이 없다** — 날짜가 아니라 단계 시퀀스다.

## 내용

### 1. 왜 직접 편집하지 않고 에이전트에게 맡기나

미션에 타깃 청중이 빠진 것을 발견했을 때, 파일을 직접 열어 고치지 않고 에이전트와 대화를 이어 수정한다. 한 줄 추가는 직접 타이핑이 빠른데도 그렇게 한다.

**이유는 관련 문서 일관성이다.** 직접 수정하면 연관 문서 갱신을 놓칠 수 있다.

헌법은 파일 하나가 아니라 `specs/`에 **세 개**로 떨어진다 — `mission.md`, `tech-stack.md`, `roadmap.md`. 이 셋은 서로 얽혀 있다. 타깃 청중을 미션에 추가하면 로드맵의 단계 우선순위도 손봐야 할 수 있다. `mission.md`만 열어 한 줄 고치면 나머지 둘이 조용히 어긋나고, 그 어긋난 문서를 다음 기능 명세가 그대로 물고 간다.

> 한 줄을 고치는 게 일이 아니라, **세 문서를 정합하게 유지하는 게 일**이다.

참고로 헌법을 대화로 쓰는 이유는 따로 하나 더 있다 — 에이전트가 고려하지 못한 아키텍처 패턴, 이미 존재하는 외부 패키지, 속도 vs 데이터 충실도 같은 트레이드오프를 **질문으로 던져준다**. 다만 이건 대화 작성 전반의 이점이고, 위의 일관성 문제와는 별개의 근거다.

### 2. SQLite 사례 — "적게"가 실제로 작동한 장면

사용자가 SQLite를 언급한 적이 없는데 에이전트가 알아서 추천해 기술 스택에 넣었다.

이건 지난 강의 "많이 / 적게" 원칙의 **적게** 쪽 사례다. 그리고 중요한 건 순서다.

- **많이(맥락)를 제대로 줬기 때문에** → **적게(저수준)가 가능해졌다.**
- "빠른 프로토타입"이라는 맥락을 줬더니 → 에이전트가 "그럼 SQLite가 맞겠다"를 스스로 도출.
- 맥락 없이 "DB 골라줘"만 했다면 못 맞혔을 것이다.

판단 기준 — *에이전트가 스스로 알아낼 수 있는가* — 이 실제로 작동한 장면이다.

### 3. 로드맵을 작은 단계로 쪼개는 이유

근거는 강의에 그대로 있다.

> SDD는 **휴먼 인 더 루프(human-in-the-loop)** 로 작은 변경을 검토하는 방식이 최선 → 로드맵을 **작은 단계**로 구성하라 지시.

단계가 크면 결과물도 크게 나오고, 크게 나온 결과물은 사람이 제대로 못 본다. 큰 diff를 받으면 "대충 맞는 것 같다"로 넘어가게 되고, 그 순간 검토는 형식만 남는다.

이건 03강의의 아키텍트 비유와 이어진다. 인간의 역할은 **설계·감독·검토/수락(또는 변경 요청)** 이었다. 그런데 검토와 변경 요청은 **검토 가능한 크기**일 때만 성립하는 역할이다. 작게 쪼개는 것은 관리 편의가 아니라 내 역할이 이름만 남지 않게 하려는 장치다.

같은 원리가 쓰기 권한 확인 요청에도 깔려 있다. 통제 유지가 목적이라서, 일괄 승인은 "보안 트레이드오프가 괜찮으면"이라는 단서를 단다.

### 4. 왜 마크다운 문서 세 개를 굳이 커밋하나

되돌리기(rollback)도 맞는 이야기지만, 강의의 무게중심은 다른 곳에 있다.

**헌법은 계속 바뀌는 문서라서다.** 강의는 커밋을 **살아있는 문서(living document)** 와 묶어 말한다. 되돌리기는 "잘못됐을 때"의 이야기인데, 헌법은 잘못되지 않아도 원래 계속 바뀐다 — 03강의의 재계획 단계에서 기능이 끝날 때마다 헌법을 수정하고 로드맵을 갱신한다.

그러니 커밋의 일차 목적은 비상용 백업이 아니라 **변경 이력 자체를 남기는 것**이다.

여기에 두 가지가 더 붙는다.

- **명세를 코드와 같은 급으로 취급** — 04강의는 "코드 버전 관리를 **밀착 추적**"이 중요하다고 했고, 프로젝트 생성 때부터 "코드·명세 버전 관리를 위해" Git을 켰다. 명세가 코드 옆에 같이 커밋되면 **어느 시점의 헌법이 어느 코드를 낳았는지**가 히스토리에 남는다.
- **인간-인간 합의의 이력** — 03강의에서 헌법은 인간-에이전트뿐 아니라 인간-인간 간 합의를 담는다고 했다. 합의가 문서에만 있고 이력이 없으면 "이거 언제 이렇게 정해졌어?"에 답할 수 없다.

### 5. 로드맵에는 시간 개념이 없다

**질문**: 로드맵이라고 하면 시간 개념이 들어있는 것 같은데, 여기서는 구현 계획을 말하는 건가? 작게 나눴어도 하루에 다 할 수도 있지 않나?

강의의 로드맵 정의 문장에는 **시간 표현이 하나도 없다.**

> **로드맵(roadmap)**: 단계(phase) **시퀀스**를 담은 살아있는 문서 — 각 단계는 자체 기능 명세 프로세스로 구현.

날짜도 기간도 마일스톤도 없고 **순서**만 있다. 일반적인 제품 로드맵(Q3에 뭐, Q4에 뭐)과는 다른 물건이다.

#### 계획은 두 층으로 있다

"구현 계획"이라 부를 때 층위를 구분해두면 좋다.

| | 무엇을 정하나 | 어디서 |
|---|---|---|
| **로드맵** | 무엇을 **어떤 순서로** 만들 것인가 | 헌법 (프로젝트 수준) |
| **계획(plan)** | 이 기능을 **어떻게** 만들 것인가 | 기능 명세 루프의 첫 단계 |

로드맵은 목차에 가깝고, 실제 구현 계획은 각 단계에 진입할 때 기능 명세에서 새로 세운다. 그래서 로드맵 단계에 구현 방법을 미리 다 적을 필요가 없다 — 그건 "적게"에 해당한다.

#### 하루에 다 끝내도 되는 이유

된다. 작게 쪼개는 목적이 **기간을 늘리는 게 아니라 검토 지점을 늘리는 것**이기 때문이다.

- 단계 5개를 하루에 처리 → 검토 체크포인트 **5번**
- 단계 1개로 묶어 하루에 처리 → 검토 체크포인트 **1번**

걸린 시간은 같지만 개입해서 방향을 틀 수 있는 기회는 5배다. 단위는 시간이 아니라 **검토 가능한 변경 덩어리**다.

## 예시

### 헌법 작성 대화 흐름

```text
1. 프로젝트 설명 제공 (+ 이해관계자 의견은 README.md에 있음을 알림)
2. 미션·기술 스택·로드맵을 함께 작성하도록 지시
   └ "로드맵은 작은 단계로"  ← 휴먼 인 더 루프 확보
3. 에이전트의 인터뷰 질문에 답변
   └ 미션 톤 = playful / 백엔드 = TypeScript / 로드맵 세분성 선택
4. 에이전트가 쓰기 권한 요청 → 승인 (통제 유지)
5. specs/ 에 mission.md · tech-stack.md · roadmap.md 생성
6. 검토 → 부족한 부분은 대화로 수정 (직접 편집 X)
7. 커밋
```

### 예제 프로젝트: AgentClinic

- AI 에이전트가 인간에게서 받는 스트레스(환각·컨텍스트 부패·메모리 문제·서브에이전트 조율)를 치료하는 클리닉 — Pet Clinic 패러디.
- 풀스택 웹앱: **Next.js 백엔드 + React 프런트엔드**, 프로토타입용 **SQLite**.
- 관리 대상: 예약(appointments) · 질환(ailments, 예: hallucination) · 치료(treatments, 예: context infusion).

## 요약

- 헌법은 `specs/`의 **세 파일**(mission·tech-stack·roadmap)로 떨어지며 서로 얽혀 있다. 그래서 수정도 **에이전트에게 맡긴다** — 직접 고치면 연관 문서가 어긋난다.
- SQLite 사례는 **맥락을 충분히 주면 저수준은 에이전트가 도출한다**는 "많이/적게" 원칙의 실증이다.
- 로드맵을 작게 쪼개는 이유는 **검토 가능한 크기**를 유지하기 위해서다. 검토와 변경 요청은 그때만 성립하는 역할이다.
- 헌법을 커밋하는 이유는 되돌리기보다 **바뀌는 문서의 이력을 코드와 나란히 남기는 것**이다.
- 로드맵에는 **시간 개념이 없다**. 날짜가 아니라 **단계 시퀀스**이며, 작게 쪼갠다는 건 기간을 늘리는 게 아니라 **검토 지점을 늘리는 것**이다.
- 계획은 두 층 — **로드맵**(무엇을 어떤 순서로) / **기능 명세의 계획**(이 기능을 어떻게).
