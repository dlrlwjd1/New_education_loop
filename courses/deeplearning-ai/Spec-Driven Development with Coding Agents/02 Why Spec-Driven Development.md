# Why Spec-Driven Development

## 개요
- **바이브 코딩(vibe coding)** 과 비교해, SDD는 **엔지니어링을 되살려** 더 나은 결과를 낸다.
- 명세(specification)는 **무엇(what)·왜(why)** 를 **구현(implementation)의 어떻게(how)** 로부터 분리(decouple)하는 패러다임 전환이다.

## 내용

### 바이브 코딩의 한계
- 프롬프트("버튼 만들어줘") → 결과 확인 → 실수 지적 → 재시도 반복. 결국 **저장되지 않는 긴 대화 이력**만 남음.
- 버튼 하나엔 OK지만 **대규모 지속 프로젝트엔 확장 안 됨** — 빠르지만 **일회용 코드·쌓이는 기술 부채(technical debt)**.
- 필요한 것은 엔지니어링, 즉 **영구적 기술 산출물(permanent technical artifact)** 인 잘 유지되는 명세.

### 명세 = 계약(contract)
- 명세는 사람 사이, 그리고 에이전트와의 **계약**. 인간의 주 임무가 **의도를 명확한 명세로 변환**하는 것으로 이동.

### 3대 이점 (재확인)
1. **작은 명세 변경으로 큰 코드 제어** — 앱의 룩앤필 몇 문장이 수백 줄 CSS로 → 초고속 에이전트 작업의 **인지 부담(cognitive overhead) 감소**.
2. **컨텍스트 감쇠 제거** — 멀티턴 세션에서 컨텍스트 윈도가 차면 실수 증가. 명세는 세션·에이전트 간 지속되어 **핵심 맥락에 앵커링**.
3. **의도 충실도 향상** — 코드 생성 전 **문제·성공 기준·제약·사용자 흐름**을 정의하게 강제.

### 비유: 컴파일러
- 컴파일러가 소스코드→기계어로 변환하듯, SDD는 에이전트·프롬프트를 통해 **명세→소스코드**로 변환. 게다가 명세는 **인간 언어**라 이해관계자에게 쉬움.

### 에이전트 vs 챗봇
- **챗봇**: 코드를 이야기할 뿐, 프로젝트 코드·설치된 도구에 접근 못 함.
- **에이전트(agent)**: 프롬프트를 받아 **계획을 세우고 추론하며** 스스로 결과로 나아감. **코드베이스·개발 도구에 접근** 가능.
- SDD에서 에이전트는 **유능한 페어 프로그래머** — 기술 지식·속도 제공. 인간은 **선임 아키텍트**로 청사진 제공.

## 요약
- 바이브 코딩은 빠르지만 일회용·기술 부채를 낳고, SDD는 **명세를 영구 산출물**로 삼아 엔지니어링을 회복한다.
- 명세는 사람·에이전트 간 **계약**이며 3대 이점(제어·컨텍스트·의도)을 제공한다.
- **"에이전트는 근육, 명세는 두뇌"** — 기능성뿐 아니라 장기 목표와 정렬된 소프트웨어를 만든다.
