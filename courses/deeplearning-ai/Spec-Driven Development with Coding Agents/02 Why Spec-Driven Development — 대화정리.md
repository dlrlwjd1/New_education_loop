# Why Spec-Driven Development — 대화정리

## 개요

- 학습일: 2026-07-28
- 원본 강의: `02 Why Spec-Driven Development.md`
- 강의 내용을 먼저 이해한 상태에서 **이해도 점검 문제 5문항**을 풀며 정리한 기록이다.
- 확인한 논점
  1. 챗봇(chatbot)과 에이전트(agent)를 가르는 기준
  2. 바이브 코딩(vibe coding)의 진짜 문제는 품질이 아니다
  3. 명세를 **계약(contract)** 이라 부르는 이유와 그 당사자
  4. 컴파일러 비유에서 명세만의 추가 장점
  5. what/why와 how의 분리(decouple) — 어디까지가 위반인가

## 내용

### 1. 챗봇 vs 에이전트 — 기준은 접근 권한과 자율 실행

> **코드베이스와 개발 도구에 접근해서, 계획을 세우고 추론하며 스스로 결과까지 나아가는가.**

| 사례 | 판정 | 근거 |
| --- | --- | --- |
| 브라우저 ChatGPT에 코드를 붙여넣고 답을 받아 직접 반영 | 챗봇 | 저장소·도구 접근 없음. 사람이 옮겨야 함 |
| Claude Code가 테스트를 돌리고 실패 원인을 찾아 고친 뒤 재실행 | 에이전트 | 도구 실행 + 자율적으로 결과까지 진행 |
| 위키 문서만 참조해 답하는 사내 AI | 챗봇 | 문서 조회는 되지만 저장소를 고치거나 도구를 실행하지 못함 |

세 번째가 함정이다. **문서를 읽는 것은 에이전트의 조건이 아니다.**
강의 표현으로 챗봇은 "코드를 **이야기할** 뿐"이다.

### 2. 바이브 코딩의 문제는 품질이 아니라 "남는 것이 없음"

흔한 오진: "바이브 코딩은 결과물 코드 품질이 떨어져서 나쁘다."

강의는 오히려 바이브 코딩이 **빠르다는 것을 인정한다.** 버튼 하나엔 OK라고까지 말한다.
진짜 문제는 **코드의 원인인 지시사항이 저장되지 않는다**는 것이다.

```text
바이브 코딩 → 저장되지 않는 긴 대화 이력 + 일회용 코드 → 기술 부채(technical debt)
SDD        → 영구적 기술 산출물(permanent technical artifact)로서의 명세
```

"왜 이 코드가 이렇게 됐는지"가 휘발된 대화 속에 있으면 6개월 뒤에는 아무도 모른다.

### 3. 명세는 계약(contract) — 당사자는 둘이 아니라 셋

강의 원문:

> 명세는 **사람 사이**, 그리고 에이전트와의 **계약**.

- 사람 ↔ 에이전트
- **사람 ↔ 사람** ← 놓치기 쉬운 쪽

"설명서"나 "요구사항 목록"이 아니라 **계약**이라고 부른 이유는,
설명서는 일방향이지만 계약은 **양쪽이 구속되고 나중에 근거로 꺼내볼 수 있는 문서**이기 때문이다.

> **주의해야 할 자기 경향** — 1강 점검에서도(헌법이 담는 *인간-인간 간 핵심 결정 합의*),
> 2강 점검에서도 **사람-사람 계약**을 놓쳤다. 두 번 연속 같은 지점이므로 단순 누락이 아니라 관점의 문제다.
> 명세를 "AI에게 주는 입력"으로만 보면 절반을 놓친다.
> 명세의 나머지 절반은 **팀원·이해관계자·6개월 뒤의 나 자신이 합의한 내용을 붙잡아두는 장치**다.

### 4. 컴파일러 비유 — 명세만의 추가 장점은 "인간 언어"

```text
컴파일러:  소스코드  →  기계어
SDD:       명세      →  소스코드
```

컴파일러의 입력인 소스코드는 **개발자만** 읽는다.
반면 명세는 **인간 언어(human language)** 라서 이해관계자(stakeholder)도 읽고 검토할 수 있다.

이것이 3번과 이어진다.

```text
명세가 인간 언어다 → 사람들끼리 읽고 합의할 수 있다 → 사람-사람 계약이 성립한다
```

즉 3번과 4번은 한 논점의 앞뒤다.

### 5. what/why와 how의 분리 — 판정 기준은 "기술 언급 여부"가 아니다

점검 문제로 다룬 다섯 항목의 판정.

| 항목 | 판정 | 이유 |
| --- | --- | --- |
| "예약 목록은 다가오는 순서로 정렬. 사용자가 다음 일정을 먼저 보기 때문" | OK | what + why |
| "`AppointmentList`에서 `.sort()` 대신 `lodash.orderBy`를 쓸 것" | **위반** | how 지시, why 없음 |
| "예약이 없을 때 빈 화면 대신 안내 문구" | OK | what |
| "DB는 SQLite. 프로토타입이라 배포 편의 우선" | OK | 이유 있는 프로젝트 수준 제약 |
| "`useEffect`에서 fetch하지 말고 `useSWR`로 감쌀 것" | **위반** | how 지시, why 없음 |

핵심은 SQLite(4번)와 useSWR(5번)의 차이다. 둘 다 특정 기술을 지목하는데 판정이 갈린다.

| | SQLite | useSWR |
| --- | --- | --- |
| 영향 범위 | 프로젝트 전체 | 컴포넌트 하나 |
| 이유(why) | 있음 — 프로토타입, 배포 편의 | 없음 |
| 사람의 의견 | 있음 (트레이드오프 판단) | 에이전트가 알아서 해도 됨 |
| 하방 증폭 | 큼 | 없음 |

> **기준은 "기술을 언급했느냐"가 아니라,
> 이유가 있는 프로젝트 수준 결정이냐 vs 이 코드 한 줄을 어떻게 쓸지에 대한 참견이냐다.**

1강에서 downstream amplification의 예로 든 것이 정확히 "SQLite + Prisma ORM"이었다.

#### 층위를 바꾸면 판정도 바뀐다

- **4번은 위치가 틀렸다** — 기능 명세가 아니라 `tech-stack.md`(헌법)에 들어가야 한다.
  기능이 바뀌어도 안 바뀌기 때문이다. (1강 점검의 에러 처리 규약과 같은 판정)
- **5번도 헌법에 쓰면 정당해진다** — "이 프로젝트의 모든 데이터 페칭은 useSWR로 통일한다"는
  프로젝트 수준 표준이다.

같은 문장이 **어느 층위에 있느냐**에 따라 마이크로매니징이 되기도, 표준이 되기도 한다.

## 예시

같은 요구를 how 지시에서 what/why 서술로 바꾼 대비.

```markdown
<!-- 위반: how를 지시하고 why가 없다 -->
- `AppointmentList` 컴포넌트에서 `.sort()` 대신 `lodash.orderBy`를 쓸 것.

<!-- 개선: what과 why만 남긴다 -->
- 예약 목록은 다가오는 일정이 먼저 오도록 정렬한다.
  사용자가 화면을 열자마자 다음 일정을 확인하는 것이 주요 사용 흐름이기 때문이다.
```

같은 기술 지정이라도 층위에 따라 두는 곳이 다르다.

```markdown
<!-- specs/tech-stack.md (헌법) — 프로젝트 전체 표준 -->
- 데이터 저장소: SQLite. 프로토타입 단계라 배포 편의를 우선한다.
- 클라이언트 데이터 페칭: useSWR로 통일한다. 캐싱·재검증 정책을 한곳에서 관리하기 위함이다.

<!-- specs/features/appointment-list.md (기능 명세) — 이 기능에만 해당 -->
- 예약이 하나도 없을 때는 빈 화면 대신 안내 문구를 보여준다.
```

## 요약

- 에이전트와 챗봇을 가르는 것은 **코드베이스·도구 접근과 자율 실행**이다. 문서 조회 능력이 아니다.
- 바이브 코딩의 문제는 **품질이 아니라 지시사항이 저장되지 않는다는 것**이다.
  강의는 바이브 코딩이 빠르다는 점을 인정한다.
- 명세는 **계약**이며 당사자는 사람↔에이전트 **그리고 사람↔사람**이다. 후자를 놓치기 쉽다.
- 컴파일러 비유에서 명세만의 장점은 **인간 언어**라는 점이고,
  그 덕분에 이해관계자가 읽을 수 있어 사람-사람 계약이 가능해진다.
- what/why와 how의 분리에서 판정 기준은 **기술 언급 여부가 아니라
  "이유 있는 프로젝트 수준 결정인가"** 다. 같은 문장도 헌법에 있으면 표준, 기능 명세에 있으면 참견이 된다.
- **"에이전트는 근육, 명세는 두뇌"** — 인간은 선임 아키텍트로 청사진을 제공하고,
  에이전트는 유능한 페어 프로그래머로 기술 지식과 속도를 제공한다.
