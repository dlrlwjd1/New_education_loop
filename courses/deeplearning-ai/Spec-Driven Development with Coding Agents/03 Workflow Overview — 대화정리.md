# Workflow Overview — 대화정리

## 개요

이 대화는 강의의 "상세 수준(right level of detail)" 항목에 나오는 **많이 / 적게**가 정확히 무엇을 가리키는지에서 출발했다. 거기서 헌법(Constitution)과 기능 명세(feature spec)의 관계, 그리고 두 문서의 용어 정리까지 이어졌다.

- **많이/적게**는 문서의 분량 규칙이 아니라, 명세 안에서 **내용의 종류를 가르는 축**이다.
- 판단 기준은 중요도가 아니라 **에이전트가 스스로 알아낼 수 있는가**이다.
- SDD의 명세는 두 층이다 — 프로젝트 전체(헌법) / 기능 하나(기능 명세).

## 내용

### 1. "많이"와 "적게"는 무엇에 대한 것인가

**질문**: 강의의 "많이 / 적게"는 해당 내용을 많이 적으라 / 최대한 적게 적으라는 뜻인가?

방향은 맞다. 이건 **명세에 적을 분량**에 대한 이야기다.

| 구분 | 대상 | 지침 |
|---|---|---|
| **많이** | 목표 · 미션 · 타깃 청중 · 제약 (맥락) | 아낌없이 적는다 |
| **적게** | 에이전트가 스스로 알아낼 수 있는 저수준 결정 | 최대한 줄이고 맡긴다 |

### 2. 기준은 "중요도"가 아니라 "알아낼 수 있는가"

저수준 결정을 적게 쓰는 이유는 **덜 중요해서가 아니다.** 에이전트가 코드베이스를 보고 스스로 도출할 수 있기 때문이다.

반대로 맥락은 아무리 유능한 에이전트라도 **코드 안에 없어서 알 수가 없는 정보**다. 내가 주지 않으면 영영 모른다.

강의의 아키텍트 비유가 이 구분을 그대로 설명한다.

> 시공자에게 **일하는 법**을 지시하지 말고, **그들이 모르는 맥락**에 집중.

시공자에게 망치 쥐는 법은 말하지 않는다 — 나보다 잘 안다. 대신 "이 건물은 노인 요양시설이고, 예산은 얼마고, 이 벽은 내력벽이라 못 건드린다"를 말해준다.

### 3. "적게"가 "0"은 아니다

저수준이라도 **에이전트가 알아낼 수 없는 것**은 맥락 쪽으로 넘어온다.

- "날짜는 ISO 8601로" → 알아낼 수 없는 팀 규칙이므로 **적는다**
- "이 함수는 for문으로 짜라" → 알아낼 수 있으므로 **안 적는다**

둘 다 세부 사항이지만 전자는 남고 후자는 빠진다. 그래서 강의는 이걸 분량 규칙이 아니라 **핵심 스킬**, 즉 매번 판단해야 하는 감각이라고 부른다. 판단 기준으로 제시된 것이 "에이전트를 **유능한 페어 프로그래머**로 대하라"이다. 유능한 동료에게 굳이 말 안 할 것은 빼고, 그 동료라도 모를 것은 쓴다.

### 4. 많이/적게는 문서 간 비교가 아니다

"헌법과 기능 명세 중 어느 쪽을 길게 쓰나"는 이 축이 답하는 질문이 아니다. **하나의 명세 안에서** 내용의 종류를 가르는 축이며, 헌법이든 기능 명세든 똑같이 적용된다.

기능 명세 하나를 예로 들면:

| 그 안에서 | 분류 |
|---|---|
| 이 기능이 왜 필요한가, 누가 쓰나, 무엇을 하면 안 되나 | **많이** |
| 어떤 함수로 쪼갤지, 변수명, 루프 구조 | **적게** |

즉 "기능 명세를 많이 쓴다"가 아니라, **기능 명세 안의 목표·맥락 부분을 많이 쓰고 구현 방식은 적게 쓴다**이다.

다만 "많이" 목록(목표·미션·타깃 청중·제약)은 헌법의 구성 요소(미션·기술 스택·로드맵)와 거의 그대로 겹친다. 그래서 "맥락을 아낌없이 쓴다"가 가장 직접적으로 가리키는 것은 헌법 쪽이다.

### 5. 미션이 헌법에 있는데 기능 명세에도 "왜"를 또 쓰나

**질문**: 헌법에 미션이 있는데도 기능 명세에 왜를 적으면 중복 아닌가?

같은 "왜"가 아니라 **고도(altitude)가 다르다.**

- **헌법의 미션**: 프로젝트 전체의 왜 — 비전 · 청중 · 범위
- **기능 명세의 왜**: 이 기능이 그 미션에 어떻게 기여하는가

두 번째를 쓸 때 첫 번째를 다시 적지 않는다. **끌어다 쓰는 것(derive)이지 복사하는 게 아니다.**

그래서 헌법이 두꺼울수록 기능 명세는 오히려 얇아진다. 강의가 미션을 "사전 정의가 진행 중 결정을 안내"한다고 표현한 것이 이 뜻이다. 매번 "우리는 요양시설이고 청중은 고령자고…"를 반복할 필요가 없어진다.

구조적으로도 상하 관계다. 로드맵은 **단계(phase) 시퀀스**이고, 각 단계는 **자체 기능 명세 프로세스**로 구현된다. 같은 층에 놓인 두 문서가 아니라서 중복이 생기는 구조가 아니다.

### 6. 용어 정리 — 명세는 두 층이다

강의 첫 문장이 이 두 층을 그대로 말한다 — "**프로젝트 전체에 대해, 그리고 각 기능(feature)마다**".

| 층 | 이름 | 담는 것 |
|---|---|---|
| 프로젝트 전체 | **헌법(Constitution)** | 미션 · 기술 스택 · 로드맵 |
| 기능 하나 | **기능 명세(feature spec)** | 계획 → 구현 → 검증 루프를 도는 단위 |

헷갈리기 쉬운 지점: 강의는 헌법을 "프로젝트 수준 세부를 형식화하는 **한 방법**"이라고 표현한다. 즉 "프로젝트 전체 명세"라는 자리가 먼저 있고, 그 자리를 채우는 방식 중 하나가 헌법이다. 최상위 `agents.md`도 같은 자리를 채우지만, 헌법 쪽이 **에이전트 비종속적(agent-agnostic)** 이고 더 **구조적**이라는 것이 강의의 주장이다.

### 7. 헌법도 고정된 문서가 아니다

"헌법 위에 기능 명세를 구현한다"는 이해는 맞다. 다만 콘크리트 위에 짓는다기보다 **지어가면서 토대도 같이 다듬는** 쪽에 가깝다.

- **재계획(Replanning)** 단계에서 기능과 기능 사이에 헌법 자체를 수정하고 로드맵을 갱신한다.
- 로드맵이 **살아있는 문서(living document)** 라는 표현이 이것을 뜻한다.

또한 헌법은 인간-에이전트뿐 아니라 **인간-인간 간의 합의**도 담는다. 팀원끼리 "기술 스택 뭐로 가지?"를 매번 다시 논쟁하지 않게 해주는 문서이기도 하다.

## 예시

### 전체 구조

```text
헌법 (프로젝트 전체)
  ├── 미션      ← 왜
  ├── 기술 스택  ← 무엇으로
  └── 로드맵     ← 어떤 순서로 (살아있는 문서)
        │
        ├── 단계 1 → 기능 명세 → 계획·구현·검증
        │                          ↓
        │                      재계획 (헌법 수정 · 로드맵 갱신)
        ├── 단계 2 → 기능 명세 → ...
        └── ...
```

재계획에서 헌법으로 화살표가 되돌아가는 것이 포인트다.

### 많이/적게 판단해보기

| 적을 내용 | 에이전트가 알아낼 수 있나 | 결론 |
|---|---|---|
| 이 서비스의 타깃 청중은 고령자 | 불가 | **쓴다** |
| 배포는 사내 온프레미스로 제한 | 불가 | **쓴다** |
| 날짜 포맷은 ISO 8601 (팀 규칙) | 불가 | **쓴다** |
| 이 반복문을 for로 쓸지 map으로 쓸지 | 가능 | 안 쓴다 |
| 헬퍼 함수 이름 | 가능 | 안 쓴다 |

## 요약

- **많이 = 맥락**(목표·미션·청중·제약), **적게 = 에이전트가 알아낼 수 있는 저수준 결정**.
- 판단 기준은 중요도가 아니라 **에이전트가 스스로 알아낼 수 있는가**. 알아낼 수 없는 세부 사항은 저수준이어도 쓴다.
- 많이/적게는 문서를 비교하는 축이 아니라 **하나의 명세 안에서 내용 종류를 가르는 축**이다.
- 명세는 두 층 — **헌법(프로젝트 전체: 미션·기술 스택·로드맵)** 과 **기능 명세(기능 하나)**.
- 헌법의 미션과 기능 명세의 왜는 중복이 아니라 **고도 차이**. 기능 명세는 헌법을 복사하지 않고 **끌어다 쓴다**. 그래서 헌법이 두꺼울수록 기능 명세는 얇아진다.
- 헌법은 고정이 아니며 **재계획 단계에서 계속 수정**된다. 로드맵은 살아있는 문서다.
- 한 줄 요약: **헌법은 한 번 쓰고 계속 참조되고, 기능 명세는 매번 새로 쓰되 헌법을 전제로 깔고 시작한다.**
