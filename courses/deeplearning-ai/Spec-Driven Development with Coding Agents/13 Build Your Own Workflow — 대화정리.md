# Build Your Own Workflow — 대화정리

## 개요
- 이 강의는 지금까지 손으로 돌린 SDD 워크플로를 **자기 도구로 굳히는** 방법이다 — 스킬·MCP·플러그인·SDD 프레임워크.
- 대화는 자기 점검 형식(5문항 퀴즈)으로 진행했다. 아래 내용은 그 과정에서 확인된 것과 새로 채운 빈칸을 정리한 것이다.

## 내용

### 1. 스킬이 /커맨드보다 나은 점

**이식성(portability)** — 에이전트 스킬(Agent Skills)은 **오픈 표준**이다. 그래서 다른 에이전트에서도 쓸 수 있다. 레슨 14에서 기능 명세 스킬을 **Codex로 복사해도 정상 작동**하는 것으로 실증된다.

**조합 가능성** — /커맨드는 사람이 직접 쳐야만 실행되지만, 스킬은
1. 프롬프트에서 언급하면 호출되고,
2. **다른 스킬이 스킬을 호출**할 수도 있다.

그래서 많은 에이전트가 커스텀 /커맨드에서 **스킬로 이동 중**이다. (`/clear` 같은 내장 /커맨드는 여전히 있다.)

스킬은 에이전트의 **스킬 생성기(skill creator)** 로 함께 작성할 수 있고, **프로젝트별 또는 글로벌**로 설치한다.

### 2. 점진적 공개의 역설 — 왜 스킬을 이름으로 지정하나

오픈 표준상 에이전트는 스킬의 **설명(description)** 을 읽고 호출 시점을 스스로 판단한다. 이것이 **점진적 공개(progressive disclosure)** 다.

그런데도 강의는 원하는 스킬을 **이름으로 직접 지정**하라고 권한다. 이유의 순서가 중요하다.

- **1차 이유(정확성)**: **컨텍스트가 커지면 그 판단이 부정확해진다.** 쓸 스킬을 안 쓰거나 엉뚱한 걸 호출한다.
- **2차 효과(비용)**: 파일 태깅처럼 이름을 박아주면 **사고 토큰이 절약**된다.

토큰 절약은 결과이고, 판단 정확성이 먼저다.

### 3. MCP를 재고하는 흐름 — CLI + 스킬

**MCP(Model Context Protocol)** 는 에이전트에 API·비공개 지식베이스·DB 접근을 주는 보편적 방법이다. 예: **Context7** — 최신 패키지 문서를 컨텍스트에 주입해 React 9.0 대신 9.2+를 인지하게 한다.

그런데 **CLI를 쓰는 스킬**이 같은 목적을 더 우아하게 달성하는 추세다. Context7도 이제 **CLI 호출 스킬**을 제안하고, 설치 시 **MCP 서버 vs CLI+Skills**를 선택하게 한다 (강의는 후자를 사용).

CLI+스킬의 장점 두 가지:

| | 내용 |
|---|---|
| **셋업이 적다** | MCP 서버를 띄우고 붙일 필요가 없다 |
| **컨텍스트가 적다** | 더 적은 컨텍스트로 액션 가능 |

이 두 가지 때문에 업계가 MCP를 재고하는 흐름이다.

### 4. 플러그인 — 무엇을 풀고, 무엇을 못 하나

**주의: "전체 프로젝트에서 쓰고 싶어서"는 플러그인의 이유가 아니다.** 그건 **스킬의 글로벌 설치**로 이미 해결된다 (스킬은 프로젝트별 또는 글로벌).

플러그인이 푸는 문제는 **여러 기기·팀·외부와의 공유**다. 내 노트북 하나가 아니라 동료에게 워크플로를 넘기고 **설치·업데이트**까지 관리하는 배포 단위다. Claude Code의 확장 모음이고 무료 커뮤니티가 성장 중이다.

경고 두 가지:

- **표준 아님** — 플러그인은 **크로스 에이전트 표준이 아직 아니다.** 스킬은 오픈 표준이라 Codex로도 옮겨가는데(위 1번), 그 이식성이 플러그인 층에서는 끊긴다. 대비되는 지점이다.
- **안전** — 플러그인은 **코드를 실행한다.** 그래서 **신뢰한 뒤에** 설치·업데이트한다.

### 5. 리서치 백로그(backlog) — 로드맵과 분리하기

기능 작업 중 아이디어(예: DB 선택)가 떠올랐을 때 선택지는 셋이고, 앞의 둘은 각각 문제가 있다.

| 선택지 | 문제 |
|---|---|
| ① 지금 브랜치 멈추고 처리 | 진행 중인 기능 브랜치의 흐름이 깨진다. SDD는 한 브랜치에서 한 기능에 집중하는 구조다 |
| ② 로드맵에 바로 추가 | 로드맵은 **하기로 결정된 것**의 목록이다. 리서치도 안 한 아이디어를 올리면 로드맵이 오염되고 헌법의 로드맵 신뢰도가 떨어진다 |
| ③ **리서치 백로그** | 에이전트에게 **알려진 위치에 리포트 작성**을 지시해 보관 |

③이 푸는 충돌은 **"브랜치를 멈추고 싶지도 않고, 아이디어를 잃고 싶지도 않다"** 다. 브랜치는 계속 굴러가고 리서치 결과는 파일로 남는다. 나중에 준비되면 **백로그 파일을 링크로 걸어** 로드맵에 예약한다. 리서치가 잦아지면 그 자체를 자동화 **스킬**로 만든다.

핵심은 **결정된 것(로드맵)** 과 **검토 중인 것(백로그)** 을 섞지 않는 것이다.

### 6. SDD 프레임워크 — Spec Kit vs OpenSpec

직접 워크플로를 만들 필요 없는 기성 프레임워크가 있다. 이 코스에서 손으로 한 것을 커맨드로 제공한다.

| | 헌법 | 계획 | 구현 | 재계획 |
|---|---|---|---|---|
| **Spec Kit** (GitHub) | `/constitution` | `/plan` `/tasks` | `/implement` | (소개된 커맨드에 없음) |
| **OpenSpec** (Fission AI) | (대응 단계 없음) | propose · explore | apply | **archive** |

- OpenSpec의 `archive`는 재계획에 대응한다. 이름이 성격을 잘 보여준다 — 레슨 9의 재계획도 **끝난 기능을 정리해 넣고 로드맵을 갱신**하는 일이었고, 완료된 명세를 보관(archive)하는 게 그 절반이다.
- OpenSpec에는 **빠른 기능용 표준 패턴**도 포함된다. 매번 풀 사이클을 돌리지 않아도 되는 작은 변경용 경로다.
- 둘 다 **브랜치 관리·검증 스크립트·명세 문서 포맷**을 제공한다.
- 강의의 결론은 하나를 고르라는 게 아니라 **실험해서 자기 워크플로를 다듬으라**는 것이다. 제목이 Build Your Own Workflow인 이유다.

## 예시

### 어느 프레임워크가 이 코스와 맞는가 (대화에서 논의)

강의 본문의 근거: **Spec Kit을 소개할 때만 "이 코스 워크플로와 유사"** 라고 적혀 있다. OpenSpec에는 그런 표현이 없다.

대화에서 정리한 판단(강의가 명시한 순위가 아니라 추론):

**Spec Kit이 더 맞다.** 이 코스의 중심 산출물이 **헌법**이기 때문이다. 레슨 5에서 헌법으로 시작했고, 레슨 12 레거시 편에서도 가장 먼저 하는 것이 **헌법 역공학**이었다. 헌법이 없으면 이 코스의 SDD는 성립하지 않는다.

두 프레임워크의 결손을 비교하면 무게가 다르다.

| | Spec Kit에 없는 것 | OpenSpec에 없는 것 |
|---|---|---|
| 빠진 단계 | 재계획 | 헌법 |
| 위치 | 사이클 **끝** | 프로젝트 **기반** |
| 대체 난이도 | 대화로 가능 (레슨 9가 실제로 대화 기반) | 매번 손으로 — 기반이라 반복 부담 큼 |

레슨 9의 재계획은 커맨드가 아니라 **에이전트와의 대화**로 진행했으므로 커맨드가 없어도 원래 방식이 통한다. 반면 헌법은 프로젝트마다 처음에 반드시 필요하고 레거시 도입의 관문이다.

**결론: Spec Kit을 기반으로 쓰고, 재계획은 스킬로 만들어 붙인다.** 반복되는 재계획 프롬프트를 스킬로 굳히는 것이 정확히 이 강의 앞부분의 내용이므로, 프레임워크의 빈칸을 스킬로 메우는 그림이 강의 의도와도 맞는다.

## 요약

- 반복 프롬프트는 **스킬**로 자동화한다. 스킬은 **오픈 표준**이라 다른 에이전트로 옮겨가고, 스킬끼리 호출도 된다.
- 원하는 스킬은 **이름으로 지정**한다. 컨텍스트가 커지면 description 기반 판단이 **부정확**해지기 때문이고, 토큰 절약은 부수 효과다.
- **MCP → CLI+스킬** 전환 추세. 이유는 **셋업이 적고 컨텍스트가 적어서**다.
- **플러그인**은 글로벌 설치가 아니라 **기기·팀·외부 공유**를 위한 것이다. **크로스 에이전트 표준이 아니고, 코드를 실행하므로 신뢰 후** 설치한다.
- 아이디어는 **리서치 백로그**로 보관해 **결정된 것(로드맵)과 검토 중인 것**을 분리한다.
- **Spec Kit·OpenSpec**을 실험해 자기 워크플로를 다듬는다. 이 코스와는 헌법 커맨드가 있는 **Spec Kit**이 더 맞고, 재계획은 스킬로 보완할 수 있다.
