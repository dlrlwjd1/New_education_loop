# Project Replanning — 대화정리

## 개요

첫 기능을 머지한 직후, 다음 기능으로 달려가기 전에 멈춰 서는 단계다. 이 강의가 어렵게 느껴지는 이유는 **"재계획(replanning)"이라는 한 단어 아래 성격이 다른 네 가지 작업이 묶여 있어서**다.

- 08 마지막에 남겨둔 숙제(테스트 패키지 미설치)가 여기서 처리된다.
- **한 층만 고치지 않는다** — 재계획의 기본 동작.
- **스킬(skill)** — 재계획의 대상이 프로젝트를 넘어 *일하는 방식 자체*로 확장된다.
- "빨리 가려면 천천히 가라(run slow to run fast)"

## 내용

### 0. 왜 지금 재계획인가

08에서 첫 기능을 머지했다. 보통은 바로 다음 기능으로 간다. 이 강의는 그 사이에 멈추는 단계를 넣는다.

기능 1을 만드는 과정에서 **알게 된 것들**이 생겼는데, 그걸 반영하지 않고 기능 2로 가면 같은 문제를 다섯 번 반복하게 된다.

실제로 08 마지막이 이렇게 끝났다.

> 테스트가 도움이 되지만 에이전트가 테스트 패키지를 설치하지 않았다. 모든 기능에 필요하므로 **다음 레슨**에서 다룬다.

그 "다음 레슨"이 09다. 즉 재계획은 **08에서 발견했지만 그 브랜치에서 처리하기엔 범위가 큰 것들을 처리하는 자리**다.

### 1. 헌법 업데이트 — 테스트 정책

#### 원인은 헌법에 없었던 것

에이전트가 테스트를 안 짰다. 이유는 단순하다. **헌법에 테스트 선호를 안 적어놨으니까.**

> 검증에 테스트가 좋지만 에이전트에 테스트 선호를 다 주지 않았음

에이전트는 안 적힌 건 안 한다. 06의 "명세에 없으면 안 만들어진다"가 헌법 층위에서 반복된 것이다.

#### 왜 재계획 브랜치를 따로 만드나

> 헌법은 **살아있는 문서** — 어떤 버전이 어떤 코드를 만들었는지 추적하려 **별도 브랜치**에서 수정하는 것이 모범 사례

08 마지막의 "어떤 명세가 어떤 코드를 만들었는지 연결하는 건 진화 중인 주제"에 대한 실전 답이다.

```text
브랜치를 섞으면:
  feature/기능2 안에 헌법 수정 + 기능 2 코드가 뒤섞임
  → "이 코드는 어떤 헌법 하에 만들어졌지?" 답이 안 나옴

브랜치를 나누면:
  replan/test-policy  → 헌법 v2
  feature/기능2       → 헌법 v2 하에서 만들어진 코드
  → 커밋 히스토리가 곧 계보(lineage)가 됨
```

08의 기준("작은 변경은 같은 브랜치, 복잡한 헌법 변경은 별도 브랜치")이 그대로 적용됐다.

#### 실행 순서 네 단계

**① 프롬프트로 정책 명시 → 에이전트가 `package.json`에 스크립트 추가**

"(의존성은 아직)"이 포인트다. 스크립트만 추가되고 테스트 라이브러리는 설치되지 않는다. 실제 테스트를 짜는 시점에 필요한 게 정해지기 때문.

**② 이 변경을 기존 기능 명세·구현에도 반영** ← 놓치기 쉬운 곳

헌법만 고치면 이렇게 된다.

```text
헌법:        "테스트를 쓴다" ✓ (새 정책)
기능 1 명세: 테스트 언급 없음  ✗ (옛날 상태)
기능 1 코드: 테스트 없음       ✗ (옛날 상태)
```

**08에서 배운 드리프트(drift)다.** 위층만 바꾸고 아래층을 안 바꾸면 벌어진다. 그래서 헌법 → 기존 명세 → 기존 구현까지 내려가며 전부 동기화한다.

**③ 테스트 작성 요청 → 에디터에서 디버거로 실행**

왜 굳이 디버거인가. `✓ 3 passed`가 떠도 그건 **그 테스트가 진짜 무언가를 검증했다는 증거가 아니다.** 빈 테스트도 통과한다.

디버거로 단계 실행(step)하면 실행 흐름이 실제로 내 코드를 지나가는지 눈으로 본다. 강의가 이걸 **휴먼 인 더 루프(human in the loop)** 라고 부르는 이유 — 08의 사용자 검증이 테스트 층위에서 반복된 것.

**④ 커밋**

### 2. 제품 계획 변경 — 반응형 디자인

#### 입력이 바깥에서 온다

> PM 업데이트: 사용자 40%가 모바일

코드를 아무리 들여다봐도 나오지 않는 정보다. 재계획이 필요한 두 번째 이유가 이것 — **세상이 바뀐다.**

#### 또 세 층 전부

> 에이전트에 반응형을 원하며 **제품 명세·기능 명세·코드**를 모두 수정하라 지시

1번의 헌법 케이스와 완전히 같은 패턴이다.

| | 위층 | 중간층 | 아래층 |
|---|---|---|---|
| 테스트 정책 | 헌법 | 기능 명세 | 구현 |
| 반응형 | 제품 명세 | 기능 명세 | 코드 |

**재계획의 기본 동작은 "한 층만 고치지 않는다"** 로 요약된다.

#### 지금 할 것인가, 로드맵에 미룰 것인가

이 강의에서 실무적으로 가장 중요한 판단 기준이다.

> 개발 초기라 작은 변경이므로 **재계획 중 직접 구현** 타당. 큰 작업이면 재계획에서 처리하지 말고 **로드맵에 별도 기능 단계로 예약** — 판단에 맡김.

```text
변경 요구 도착
   ↓
지금 코드베이스 기준으로 얼마나 큰가?
   ├ 작다  → 재계획 중에 바로 처리
   └ 크다  → 로드맵에 "기능 N: 반응형 대응"으로 예약하고
             재계획은 여기서 끝
```

지금 반응형이 작은 이유는 **개발 초기라 화면이 몇 개 없어서**다. 같은 요구가 화면 40개짜리 프로젝트에 오면 그건 별도 기능 단계다.

강의가 "판단에 맡김"이라고 못 박은 것도 의미가 있다. 규칙이 아니라 사람이 결정할 몫이다.

#### 명세가 존재하는 진짜 이유

> 명세는 코드뿐 아니라 **결정을 포착**해야 하며 둘을 **동기화**해 팀 커뮤니케이션을 도움

반응형 CSS를 코드에만 넣으면 6개월 뒤 누가 보고 이렇게 생각한다. "왜 여기 미디어 쿼리가 있지? 지워도 되나?"

명세에 "사용자 40%가 모바일이라 반응형이 필수"라고 적혀 있으면 **결정의 이유가 남는다.** 코드는 *무엇을* 하는지만 말하고, 명세가 *왜*를 붙든다.

> 작은 단계·잦은 커밋이 리뷰 과부하를 막음

08의 **인지 부채(cognitive debt)** 가 이어진 것. 재계획도 몰아서 하면 리뷰 불가능한 덩어리가 된다.

### 3. 프로젝트 정리 — 로드맵

> 로드맵의 다음 작업이 여전히 타당한지 재검토 → 기능 2·3·4·5가 서로 묶여 있어 **한 단계로 통합**

"05에서는 작게 쪼개라고 했는데?" 싶지만 모순이 아니다. 기준이 **크기가 아니라 응집성**이다.

기능 2·3·4·5가 얽혀 있으면 2만 만들었을 때 3 없이는 동작하지 않는 반쪽이 나온다. 그러면:

- 기능 2를 머지해도 **검증할 게 없다** (08의 사용자 검증이 불가능)
- 3, 4, 5 하면서 2를 계속 뜯어고치게 된다

05의 "작게 쪼개라"는 **독립적으로 검증 가능한 최소 단위**를 만들라는 뜻이지, 무조건 잘게 자르라는 게 아니다.

그리고 이 절이 증명하는 것 — **로드맵도 살아있는 문서다.** 03에서 말만 했던 게 여기서 실제로 고쳐진다.

### 4. 재계획 = 워크플로 개선 + 스킬

#### 대상이 한 단계 확장된다

1~3번은 **이 프로젝트**를 고쳤다. 4번은 **일하는 방식 자체**를 고친다.

> 재계획은 기능·프로젝트뿐 아니라 **조직 전반의 SDD 워크플로 개선**도 포함

#### 체인지로그 예시로 따라가기

```text
문제: 비기술 이해관계자가 진행 상황을 알고 싶다. 커밋 로그를 못 읽는다.
해법: main 머지마다 체인지로그(changelog)를 갱신한다.
문제: 매번 손으로 쓰면 귀찮고 결국 안 하게 된다.
해법: 스킬(skill)로 자동화한다.
```

#### 스킬이란 무엇인가

> **스킬** = 에이전트에 새 능력·전문성을 주는 지시·리소스 묶음

"잘 쓴 프롬프트를 파일로 저장해둔 것"으로 이해해도 크게 틀리지 않는다. 매번 같은 설명을 반복하는 대신 한 번 적어두고 에이전트가 꺼내 쓴다.

#### 어떤 워크플로가 스킬감인가 — 세 조건

> **정의 가능·반복적이며 프로젝트/조직 특유 맥락**이 필요한 워크플로에 적합

셋을 다 만족해야 한다. 하나씩 왜인지 보면:

| 조건 | 없으면 어떻게 되나 |
|---|---|
| **정의 가능(definable)** | 절차를 글로 못 적으면 매번 사람이 판단해야 함 → 스킬로 못 만듦 |
| **반복적(repetitive)** | 한 번만 할 일이면 그때 프롬프트 치면 됨 → 만들 가치 없음 |
| **특유 맥락 필요** | 일반 지식이면 에이전트가 이미 잘함 → 만들 필요 없음 |

체인지로그를 넣어보면 세 칸 다 통과한다.

- 정의 가능 — "머지된 커밋을 모아 사용자 언어로 요약해 CHANGELOG.md 위에 붙인다" ✓
- 반복적 — 머지할 때마다 ✓
- 특유 맥락 — 우리 팀의 체인지로그 형식과 톤 ✓

#### 메타 스킬

> 직접 쓸 수도 있지만 **에이전트가 스킬 작성을 돕는 스킬**도 있음

스킬을 만드는 스킬. "스킬 파일도 손으로 짤 필요 없이 에이전트한테 시킬 수 있다" 정도로 받아들이면 된다.

#### 어디에 두나

> 이 스킬은 **글로벌 스킬 영역**에 생성돼 모든 프로젝트에서 사용 가능(프로젝트 전용 vs 표준화는 스타일 선택)

```text
글로벌   → 모든 프로젝트에서 씀. 조직 표준화에 유리
프로젝트 → 이 저장소에서만 씀. 프로젝트 특성 반영에 유리
```

강의는 "스타일 선택"이라고만 하고 정답을 주지 않는다. 2번의 "판단에 맡김"과 같은 태도다.

#### 자동화해도 검토는 남는다

> Claude Code가 이 스킬로 프로젝트 CHANGELOG 생성 → **수동 검토**

스킬로 자동화해도 **사람이 확인하는 단계는 사라지지 않는다.** 08부터 이어지는 휴먼 인 더 루프가 여기서도 유지된다.

#### 검증 스킬

> 검증 단계(README 갱신·린팅·포매팅·테스트 작성 등)를 **검증 스킬(validation skill)** 로 묶으면 반복 프로세스·수작업 감소

08의 검증 단계에서 매번 손으로 하던 잡일을 하나로 묶는다. 재계획이 워크플로에 주는 실질적 이득이 이것 — **기능 1에서 손으로 했던 걸 기능 2부터는 스킬이 한다.**

## 예시

### 재계획 전체 구조

```text
              [ 첫 기능 머지 완료 ]
                       │
                  ── 재계획 ──
                       │
     ┌─────────┬───────┴────────┬──────────────┐
     │         │                │              │
  ① 헌법    ② 제품 계획      ③ 로드맵      ④ 워크플로
  테스트     반응형           단계 통합      스킬 자동화
  정책       (40% 모바일)                    (체인지로그·검증)
     │         │                │              │
  안에서    바깥에서         계획이         일하는 방식이
  발견한 것  들어온 것       안 맞아짐       비효율적
     │         │                │              │
     └─────────┴───────┬────────┴──────────────┘
                       │
              전부 커밋 → 기능 2로
```

①②③은 **무엇을 만드는가**를 고치고, ④는 **어떻게 만드는가**를 고친다. 이 차이를 잡으면 강의가 정리된다.

### 08 → 09로 이어지는 것들

| 08에서 배운 것 | 09에서 어떻게 쓰이나 |
|---|---|
| 드리프트 | 헌법·명세·코드를 한꺼번에 고치는 이유 |
| 인지 부채 | 작은 단계·잦은 커밋으로 리뷰 과부하 방지 |
| 사용자 검증(휴먼 인 더 루프) | 테스트를 디버거로 단계 실행해 확인 |
| "어떤 명세가 어떤 코드를 만들었나" | 재계획을 별도 브랜치로 분리 |
| 테스트 패키지 미설치 | 1번 헌법 업데이트로 해결 |

### 마지막 문장의 무게

> 이제 개발자 일은 대부분 **계획·검증**이므로 재계획 시간을 확보하라

코스 전체의 주장이 압축돼 있다. 코드 작성은 에이전트가 하니 사람에게 남은 건 앞의 계획과 뒤의 검증이다. 그런데 **재계획은 그 계획을 고치는 일**이므로, 이 시간을 안 내면 사람이 할 일의 절반을 안 하는 셈이 된다.

### 이해도 점검에서 갈렸던 지점들

Q&A로 검증하며 실제로 헷갈렸던 부분만 모았다.

#### "사이즈"는 절대값이 아니라 상대값

큰 변경은 로드맵으로 보낸다 — 여기까지는 쉽다. 함정은 **무엇에 대한** 사이즈냐다.

```text
다크 모드 요구
  ├ 화면 30개 + CSS 40개  → 크다  → 로드맵에 기능 단계로
  └ 화면 2개 (개발 초기)   → 작다  → 재계획 중 직접 처리
```

강의도 "**개발 초기라** 작은 변경이므로"라고 했다. 반응형이 원래 작은 일이라서가 아니라 **지금 프로젝트가 작아서** 작다. 6개월 뒤 같은 요구엔 답이 반대가 된다.

#### 스킬 세 조건은 각각 다른 걸 걸러낸다

"반복적"만 보면 통과해버리는 것들이 있다.

| | 정의 가능 | 반복적 | 특유 맥락 | 판정 |
|---|---|---|---|---|
| 저장소 규칙대로 노트 생성 + README 갱신 | ✓ | ✓ | ✓ | **스킬** |
| 타임아웃 원인 찾기 | **✗** | ✓ | ✓ | 탈락 |
| 파이썬 리스트 정렬 코드 | ✓ | ✓ | **✗** | 탈락 |

- 디버깅은 **반복적이지만 절차를 글로 못 적는다.** 이번엔 커넥션 풀, 다음엔 외부 API — 매번 사람이 판단해야 한다.
- 리스트 정렬은 **정의도 되고 반복도 되지만 에이전트가 이미 잘한다.** 우리 팀만의 맥락이 없으면 만들 이유가 없다.

#### `✓ passed`의 한계 — 08과 같은 뿌리

테스트가 통과했는데 왜 디버거까지 돌리나. **빈 테스트도 통과하기 때문**이다.

```javascript
test('결제가 처리된다', () => {
  expect(true).toBe(true);   // ✓ passed
});
```

`✓ passed`는 "테스트가 실패하지 않았다"이지 "코드가 검증됐다"가 아니다. 08의 구조가 한 층 아래에서 그대로 반복된다.

```text
08:  자체 검증은 [명세]를 기준으로 채점 → [명세]의 결함은 못 잡음  → 사람이 명세를 본다
09:  테스트 실행은 [테스트]를 기준으로 채점 → [테스트]의 결함은 못 잡음 → 사람이 디버거로 본다
```

**채점 기준 자체의 결함은 채점으로 못 잡는다.** 08의 `Home.tsx`에서 스코어카드가 통과했는데도 문제였던 것과 같은 구조다.

#### 이 논리가 재계획의 존재 이유로 이어진다

검증 스킬을 만들어 자동화해도 사람에게 두 가지가 남는다.

1. **스킬의 산출물 검토** — 생성됐다고 내용이 맞는 건 아니다 (강의: CHANGELOG 수동 검토)
2. **스킬 자체(기준)의 점검** — 검증 스킬이 README 갱신을 빠뜨리고 있다면? **스킬은 자기가 뭘 안 하는지 모른다**

②를 언제 하는가. 기능 개발 중엔 못 한다. 그때는 그 스킬을 *쓰는* 중이니까.

```text
기능 개발 중 → 스킬을 사용한다 (기준 안에서 일함)
     ↓
   재계획   → 스킬을 점검한다 (기준 밖으로 나옴)
     ↓
기능 개발 중 → 개선된 스킬을 사용한다
```

**기준 밖으로 나오는 시간을 일정에 명시적으로 박아두지 않으면 영원히 안 나오게 된다.** 일하는 중에는 그 기준이 곧 세계이기 때문이다. 이것이 09가 독립된 단계로 존재하는 이유다.

## 요약

- **재계획**은 첫 기능 머지 후 다음 기능 전에 멈춰 서는 단계다. 08에서 발견했지만 그 브랜치에서 처리하기엔 컸던 것들을 여기서 처리한다.
- 네 가지 대상: **헌법(안에서 발견)·제품 계획(바깥에서 유입)·로드맵(계획이 안 맞아짐)·워크플로(일하는 방식이 비효율적)**.
- 기본 동작은 **한 층만 고치지 않는다** — 헌법/제품 명세를 바꾸면 기능 명세와 코드까지 내려가며 동기화한다. 드리프트 방지.
- 헌법 수정은 **별도 브랜치**로. 어떤 헌법이 어떤 코드를 만들었는지 계보가 커밋 히스토리에 남는다.
- 변경이 **작으면 재계획 중 직접**, **크면 로드맵에 기능 단계로 예약**. 규칙이 아니라 판단이다.
- 로드맵 단계 통합의 기준은 크기가 아니라 **응집성** — 따로 하면 검증 불가능한 반쪽이 나오는 것들은 합친다.
- **스킬**은 정의 가능·반복적·프로젝트 특유 맥락이 필요한 워크플로에 쓴다. 세 조건은 **각각 다른 것을 걸러낸다.**
- **채점 기준 자체의 결함은 채점으로 못 잡는다** — 08(명세 vs 자체 검증)과 09(테스트 vs `✓ passed`)를 관통하는 하나의 논리이자, 재계획이 독립된 단계로 존재하는 이유다.
- 개발자 일이 계획·검증으로 옮겨간 이상, **재계획 시간 확보는 선택이 아니다.**
