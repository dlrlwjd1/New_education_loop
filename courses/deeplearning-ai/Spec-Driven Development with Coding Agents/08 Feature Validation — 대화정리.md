# Feature Validation — 대화정리

## 개요

구현이 끝난 기능을 머지 전에 사람이 검증하는 강의다. 07에서 답하지 못했던 "에이전트 자체 검증이 있는데 왜 사람이 또 하나"의 답이 여기서 나온다.

- 코드의 문제가 **계획의 실수에서 흘러나온 것**일 수 있고, 그럴 땐 명세까지 함께 고친다.
- **드리프트(drift)** — 05·06에서 이름 없이 두 번 만났던 현상이 여기서 용어를 얻는다.
- **인지 부채(cognitive debt)** — 에이전트가 빨라서 생긴 새 문제.
- 리뷰에서도 **저수준은 보지 않는다.**

## 내용

### 1. 뭘 보고 뭘 안 보나 — 원칙이 리뷰 단계로 확장

커밋 뷰로 변경을 훑되 **CSS 클래스 같은 세부**가 아니라 **기능이 동작하고 명세를 반영하는지** 같은 고수준 관심사에 집중한다.

이건 03의 **적절한 상세 수준(많이/적게)**, 06의 **oversteer 금지**와 같은 원칙이 리뷰 단계에 적용된 것이다.

| 단계 | 하지 말 것 |
|---|---|
| 명세 (06) | 변수명 같은 저수준을 **적기** |
| 리뷰 (08) | CSS 클래스 같은 저수준을 **보기** |

들어갈 때와 나올 때 양쪽에 같은 필터가 걸려 있다. 저수준을 안 적어놓고 리뷰에서 그걸 트집 잡으면 앞뒤가 맞지 않는다.

### 2. `Home.tsx` 사례 — 코드 실수가 아니라 계획의 실수

`Home.tsx`가 너무 미니멀한 것을 발견한다. 헤더·메인·푸터 랜드마크가 있는 레이아웃 컴포넌트를 서브컴포넌트로 두고 CSS 파일도 요청한다.

여기서 강의의 규정이 핵심이다.

> 이 코드 실수는 **계획의 실수에서 흘러나온 것** → 에이전트에게 수정을 맡겨 **명세와 구현을 함께** 교정.

#### 이것이 07 질문의 답이다

에이전트는 명세대로 잘 만들었다. 스코어카드도 통과했을 것이다. **명세 자체가 부실했던 것**이고, 명세를 기준으로 채점하는 자체 검증으로는 절대 걸리지 않는다.

```text
자체 검증:   코드 → 명세와 대조   → 통과 ✓
사용자 검증: 명세 → 내 의도와 대조 → 부족함 발견 ✗
```

그래서 코드만 고치면 안 된다. 코드만 고치면 명세는 여전히 부실한 채 남고, **다음 기능이 그 부실한 명세를 물고 간다.**

### 3. 드리프트(drift)

서브컴포넌트 3개가 한 파일에 몰린 것을 발견한다. IDE의 **move 도구**로 직접 분리하고 싶지만 참는다.

**드리프트 = 코드는 바뀌었는데 명세·README 같은 다른 산출물이 그대로 남아 서로 어긋나는 것.**

move 도구로 파일 3개를 분리하면 코드는 깔끔해지지만, 그 파일 구조를 언급한 명세와 README는 옛날 상태로 남는다. 둘이 벌어진다(drift).

에이전트에게 맡기는 이유는 "내가 고려 못 한 걸 봐줘서"가 아니라 **관련 언급을 전부 찾아 함께 고쳐주기** 때문이다. 나중 시간 낭비를 막는다.

#### 세 번째 만나는 현상

| 강의 | 그때 표현 |
|---|---|
| 05 | 헌법 세 파일을 직접 고치면 연관 문서 갱신을 놓친다 |
| 06 | 요구사항만 고치고 검증을 빼면 **없는 기준으로 통과 판정** |
| 08 | **드리프트** ← 이제 이름이 붙음 |

### 4. 인지 부채(cognitive debt)

- **정의**: 코드가 무엇을 하고 어떻게 진화했는지 추적하는 정신적 부담.
- **왜 지금 화두인가**: **에이전트가 빨라서**. 코드가 생산되는 속도는 폭증했는데 사람이 이해하는 속도는 그대로다. 그 격차가 쌓인다.
- **"부채"인 이유**: 지금 안 갚으면 나중에 이자가 붙는다. 그 이자는 버그를 잡거나 기능을 얹으려 할 때 청구된다.
- **대응책**: 프로세스를 빠르고 통제 가능하게 하려면 **변경을 관리 가능한 크기로**.

에이전트는 변경을 만들면서 깨진 것이 없는지도 검증한다.

#### 크기 제한은 이 코스의 반복 축이다

| 강의 | 크기를 제한하는 장치 |
|---|---|
| 05 | 로드맵을 작은 단계로 |
| 07 | 위험 영역은 태스크 그룹 단위로 |
| 08 | 변경을 관리 가능한 크기로 (인지 부채) |

### 5. 테스트와 버전 관리

- 테스트가 도움이 되지만 에이전트가 테스트 패키지를 설치하지 않았다. 모든 기능에 필요하므로 **다음 레슨**에서 다룬다.
- 이 브랜치에서 **헌법의 일부(로드맵 단계 체크오프)** 도 함께 갱신됐다. 03에서 말한 "로드맵은 살아있는 문서"가 실제로 작동하는 장면이다.
- 명세 버전 관리, 그리고 **어떤 명세가 어떤 코드를 만들었는지 연결**하는 것은 커뮤니티에서 **진화 중인 주제**다.
- 브랜치 전략: 로드맵 변경이 작으면 **같은 브랜치**, 헌법 변경이 복잡하면 **별도 브랜치**.
- 작업을 완료로 표시하고 **머지**.

## 예시

### 저수준(low-level)이란 무엇인가

대화 중 정의를 짚고 넘어간 부분이다.

```text
고수준 │ 왜 만드나           ← 미션, 타깃 청중
       │ 무엇을 만드나        ← Phase 범위, 요구사항
       │ 됐다고 판단하는 기준  ← 스코어카드
       ├─────────────────
저수준 │ 어떻게 짜나          ← 함수 쪼개기, 변수명, CSS 클래스
```

**실전 판별법 — 바꿔도 결과가 같은가?**

- `handleRoot` → `rootHandler` : 동작 동일 → **저수준**
- 타깃 청중을 고령자 → 개발자 : 만들 물건이 달라짐 → **고수준**

저수준 결정은 정답이 여러 개고 아무거나 골라도 목적이 달성된다. 그래서 에이전트에게 맡겨도 된다.

#### 주의 — "세부적 = 저수준"이 아니다

06의 예시를 다시 보면 **둘 다 세부적인데** 하나는 빼고 하나는 남긴다.

| | 세부적인가 | 알아낼 수 있나 | 결론 |
|---|---|---|---|
| 함수 이름 `handleRoot` | O | O | 뺀다 |
| Hono 버전 고정 | O | **X** (프로젝트가 정한 것) | 남긴다 |

갈리는 지점은 세부성이 아니라 **에이전트가 스스로 알아낼 수 있는가**다. "저수준"은 실무에서 대개 *알아낼 수 있어서 안 적어도 되는 것*의 줄임말로 쓰이지만, 판단은 항상 03의 기준으로 한다.

#### 08에 적용해보면

CSS 클래스명이 `.home-wrapper`든 `.page-root`든 **기능 동작과 명세 반영 여부는 그대로**다 → 리뷰에서 안 본다.

반면 "헤더·메인·푸터 랜드마크가 없다"는 구조 자체가 명세와 어긋난 것이므로 고수준 문제 → 잡아낸다.

### 검증 단계 흐름

```text
기능 구현 완료 (아직 머지 X)
   ↓
커밋 뷰로 리뷰 — 고수준 관심사만
   ↓
문제 발견
   ├ 코드만의 문제?        → 코드 수정
   └ 계획에서 흘러나온 문제? → 명세 + 구현 함께 교정
   ↓
구조 변경이 필요하면 에이전트에게 (드리프트 방지)
   ↓
로드맵 단계 체크오프
   ↓
머지 → 다음은 재계획
```

## 요약

- 검증은 **커밋 뷰**로 하되 **고수준 관심사(동작·명세 반영)** 만 본다. 저수준 필터가 명세 작성과 리뷰 양쪽에 걸린다.
- 코드 문제가 **계획의 실수에서 흘러나온 것**이면 **명세와 구현을 함께** 고친다. 코드만 고치면 부실한 명세가 다음 기능으로 전달된다.
- 이것이 **자체 검증과 사용자 검증의 차이**다 — 자체 검증은 명세를 기준으로 채점하므로 명세 자체의 결함을 못 잡는다.
- **드리프트** = 코드는 바뀌었는데 명세·README가 그대로 남아 어긋나는 것. 수동 편집이 원인이고, 에이전트가 **관련 언급을 전부 함께** 고쳐준다.
- **인지 부채** = 코드가 뭘 하고 어떻게 진화했는지 추적하는 부담. 원인은 **에이전트의 속도**, 대응은 **관리 가능한 크기**.
- **저수준의 기준은 세부성이 아니라 도출 가능성**이다. 바꿔도 결과가 같으면 저수준.
- 명세와 코드를 연결하는 버전 관리는 **아직 진화 중인 주제**다. 첫 기능을 머지하고 다음은 **재계획**.
