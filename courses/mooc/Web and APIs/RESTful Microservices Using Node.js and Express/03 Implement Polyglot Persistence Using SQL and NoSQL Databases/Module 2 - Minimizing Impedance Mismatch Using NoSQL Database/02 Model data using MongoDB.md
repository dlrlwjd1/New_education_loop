# Model data using MongoDB

## 개요
- 임피던스 불일치의 정의와 세 원인, 해결 방향(데이터 모델링), MongoDB가 불일치를 줄이는 방식, 저장 구조(데이터베이스→컬렉션→문서), BSON vs JSON, 그리고 MongoDB 데이터 모델링 3단계를 다루는 강의

## 내용

### 임피던스 불일치란
- **저장 시스템과 애플리케이션 시스템 사이의 마찰**에서 생기는 결과다. 애플리케이션 데이터와 저장 데이터가 맞지 않을 때 발생한다.

| 원인 | 애플리케이션 쪽 | 저장소 쪽 |
|---|---|---|
| **데이터 형식** | JSON | 테이블·행·열 |
| **데이터 저장 설계** | 객체 하나에 저장 | 여러 테이블에 저장 |
| **데이터 구조** | 같은 엔터티의 데이터가 각각 다르게 구조화됨 | 엄격한 구조 |

### 해결 방향
- 양끝 데이터의 **차이를 최소화**해야 한다.
- 저장소 쪽에서는 **적절한 데이터 모델링 기법**으로 해결한다 — 애플리케이션 쪽 데이터 요구에 맞게 저장소의 데이터를 효율적으로 설계·모델링한다. 애플리케이션 쪽은 차이를 줄이는 로직을 제공한다.
- **데이터 모델링**은 형식적 기법을 적용해 정보 시스템의 데이터 모델을 만드는 과정이다. 전문가가 비즈니스 이해관계자·잠재 사용자와 긴밀히 협력하며, 비즈니스 프로세스를 뒷받침하는 데이터 요구를 정의·분석한다. **개발자가 솔루션 개발 초기에 착수해야 하는 비자명한 작업**이다.

### MongoDB가 불일치를 줄이는 방식
MongoDB는 **문서(document) 데이터베이스**다.

| 원인 | MongoDB의 대응 |
|---|---|
| 형식 | **JSON과 유사한 형식**으로 저장 |
| 저장 설계 | **관련 정보를 하나의 문서 안에 내장(embed)** 가능 |
| 구조 | **스키마리스(schema-less)** 라 유연 |

### 저장 구조
- **데이터베이스**는 하나 이상의 **컬렉션(collection)** 을, 컬렉션은 하나 이상의 **문서(document)** 를 담는다.
- 문서는 **레코드이자 필드-값 쌍으로 이뤄진 데이터 구조**다. 값에는 **다른 문서, 배열, 문서의 배열**이 올 수 있다.
- 문서는 **BSON(Binary JSON)** 으로 저장된다. BSON은 JSON 같은 데이터의 이진 직렬화 프로토콜이다.
- **컬렉션 ≈ 관계형의 테이블, 문서 ≈ 테이블의 행**

### BSON vs JSON
- BSON은 **JSON 타입의 상위 집합(superset)** 이다. MongoDB는 JSON으로 표현되는 모든 것을 그대로 저장하고 JSON으로 쉽게 꺼낼 수 있다.
- BSON은 **JSON 우선(JSON-first)·고성능·범용**인 MongoDB를 만들기 위해 그 간극을 메우려고 발명됐다. **속도·공간·유연성에 최적화된 이진 표현**이다.

| 측면 | JSON | BSON |
|---|---|---|
| 인코딩 | UTF-8 문자열 | 이진(binary) |
| 데이터 타입 | string, boolean, number, array | 위 네 가지 + **date, raw binary** |
| 가독성 | 사람·기계 모두 읽음 | **기계만** 읽음 |

### MongoDB 데이터 모델링 3단계 (인테리어 프로젝트 예)
샘플 데이터는 여러 건물 유형(premise type)의 인테리어 프로젝트다. **premise type, area, budget, ownership** 은 모든 레코드에 있고, **rooms, reception details, changing rooms** 같은 나머지는 건물 유형에 따라 있거나 없다.

1. **데이터셋 정의** — 어떤 데이터를 저장하고 데이터 필드가 서로 어떻게 관계되는지 파악한다.
2. **JSON으로 생각하기** — MongoDB는 JSON 형식으로 저장하므로 행·열 구조의 데이터를 JSON으로 표현해 본다. JSON 문서는 **내장 필드**를 가질 수 있어 관련 데이터와 데이터 목록을 **한 문서 안에** 둘 수 있다.
3. **내장 데이터 후보 식별**
   - **여러 데이터를 필드로 요구하는 필드**가 내장 데이터 후보다. 내장 데이터는 그 자체가 문서일 수 있다. 예: `premise` 필드(`type`과 `details` 하위 필드), `rooms` 필드(kitchen, living room, bedrooms 같은 세부)
   - **여러 항목을 갖는 필드**는 **내장 리스트(배열)** 후보다. 예: `rooms`는 각 항목이 `floor`와 `count` 필드를 가진 문서인 배열
- MongoDB 컬렉션에 저장할 수 있는 문서는 **최대 16MB** 다.

## 예시
```json
// 2단계: 행·열을 JSON으로
{
  "premise": { "type": "hotel", "details": "5-star, downtown" },
  "area": 5000,
  "budget": 250000,
  "ownership": "private",
  "rooms": [
    { "floor": "first",  "count": 15 },
    { "floor": "second", "count": 12 }
  ]
}
```

```text
저장 구조
Database
└─ Collection  (≈ 테이블)
   └─ Document (≈ 행, BSON, ≤ 16MB)
      └─ field: value  (값 = 스칼라 | 문서 | 배열 | 문서의 배열)

3단계 내장 후보
premise  → { type, details }          ← 내장 문서
rooms    → [ {floor, count}, ... ]    ← 내장 리스트(배열)
```

## 요약
- 임피던스 불일치는 형식(JSON vs 테이블)·저장 설계(객체 vs 여러 테이블)·구조(유연 vs 엄격)의 차이에서 오며, 저장소 쪽 데이터 모델링으로 줄인다.
- MongoDB는 JSON 유사 형식, 문서 내 내장, 스키마리스로 세 원인에 각각 대응한다.
- 데이터베이스 → 컬렉션(≈테이블) → 문서(≈행, BSON) 구조이며 BSON은 JSON의 상위 집합으로 date·binary를 추가하고 기계만 읽는다.
- 모델링은 데이터셋 정의 → JSON으로 생각 → 내장 문서·내장 배열 후보 식별 순서로 하며, 문서 크기는 16MB까지다.
