# Explain Monolithic Applications

## 개요
- 모놀리식(monolithic) 애플리케이션의 정의, 변경 시 파급 효과, 8가지 단점을 다루고 마이크로서비스와의 구조적 차이를 비교하는 강의

## 내용

### 정의
- 소프트웨어 공학에서 모놀리식 애플리케이션은 **단일 계층(single-tiered) 소프트웨어 애플리케이션**을 가리킨다.
- **사용자 인터페이스와 데이터 접근 코드가 하나의 플랫폼에서 하나의 프로그램으로 합쳐져** 있다.
- 자기완결적(self-contained)이며 다른 컴퓨팅 애플리케이션과 독립적이다.
- **하나의 모놀리식 애플리케이션으로 배포**된다. Java 웹 애플리케이션이라면 Tomcat 같은 웹 컨테이너에서 실행되는 **WAR 파일 하나**가 된다.

### 차량 공유 앱의 모놀리식 구조
- 현재 서비스 4개: **사용자 인증(user authentication), 승객 관리(passenger management), 요금 정산(billing), 알림(notification)**
- 이 서비스들은 웹 컨테이너 Tomcat을 통해 데이터베이스와 상호작용한다.
- 여기에 **기사 관리(driver management), 운행 관리(trip management)** 등을 더 추가하면 복잡도가 급증한다.
- **실제 문제는 서비스의 개수가 아니라 그 사이의 상호작용(interaction)이다.**

### 변경을 반영할 때의 파급 효과
- **개발·릴리스·배포 관리 주기 전체를 처음부터 다시** 수행해야 한다.
- 변경 영향(change impact)에 관한 심각한 복잡도가 있다. 컴포넌트가 서로 연결되고 의존하므로 **기존 컴포넌트의 작은 변경이 파급 효과(ripple effect)** 를 낳는다.
- 변경을 반영해 서비스에 올리려면 **애플리케이션 전체를 종료하고 오프라인으로 내린 뒤, 변경하고 테스트하고 다시 올려야** 한다.
- **컴포넌트 하나의 버그 수정을 배포하려도 애플리케이션 전체를 재배포**해야 한다.

### 단점 8가지
1. **컴포넌트 간 강한 결합(tight coupling)** — 모놀리식 컴포넌트는 강하게 결합되고 얽힌다. 이 결합이 관리, 확장성, 지속적 배포에 영향을 준다.
2. **웹 컨테이너 과부하** — 애플리케이션이 클수록 시작 시간이 길어진다. 컨테이너 시작을 기다리는 시간 때문에 **개발자 생산성에 큰 타격**을 주고 배포에도 영향을 준다.
3. **거대한 코드베이스** — 개발자와 QA가 코드와 업무 지식을 이해하기 어렵게 만든다.
4. **낮은 확장성** — 개발 조직 확장의 장애물이다. 애플리케이션이 일정 규모가 되면 UI 팀, 회계 팀, 재고 팀처럼 기능 영역별로 팀을 나누는 것이 유용한데, 모놀리식은 **팀들이 독립적으로 일하는 것을 막는다.** 팀들이 개발과 재배포를 서로 조율해야 하므로 한 팀이 변경하고 프로덕션을 갱신하기가 훨씬 어렵다.
5. **지속적 배포(continuous deployment)의 장애물** — 컴포넌트 하나를 갱신하려도 전체를 재배포해야 한다. 이는 **백그라운드 작업을 중단**시킨다(예: Java 애플리케이션의 Quartz 작업). 변경과 무관해도 문제가 생길 수 있고, 갱신되지 않은 컴포넌트가 제대로 시작하지 못할 가능성도 있다. 결과적으로 재배포 위험이 커져 **빈번한 갱신을 억제**한다. 빠르게 반복하고 자주 재배포해야 하는 UI 개발자에게 특히 문제다.
6. **배포·재시작 시간 증가** — 애플리케이션 크기 때문에 느려지고, 사소한 변경도 전체 재배포로 이어져 재시작·재배포 시간이 늘어난다.
7. **새 기술 도입 장벽** — 언어나 프레임워크 변경이 애플리케이션 전체에 영향을 준다. 시간과 비용 모두에서 값비쌀 수 있다.
8. **기술 스택에 대한 장기 종속** — 개발 초기에 고른 기술 스택, 때로는 그 **특정 버전에까지 묶인다.** 점진적으로 새 기술로 옮기기 어렵다. Java를 쓴다면 Groovy·Scala처럼 Java와 잘 연동되는 JVM 언어는 선택지가 되지만, **JVM이 아닌 언어로 쓴 컴포넌트는 들어갈 자리가 없다.** 사용 중인 플랫폼 프레임워크가 뒤에 구식이 되면 더 나은 프레임워크로 점진적 이전이 어려워, 새 프레임워크를 도입하려면 **애플리케이션 전체를 다시 써야 하는 위험한 작업**이 될 수 있다.

### 모놀리식 vs 마이크로서비스의 구조 차이
- **모놀리식**: 모든 기능을 **하나의 프로세스**에 넣는다. 확장은 그 모놀리스를 **여러 서버에 복제(replicate)** 해서 한다.
- **마이크로서비스**: 기능의 각 요소를 **별도 서비스**에 넣는다. 확장은 그 서비스들을 **여러 서버에 분산하고 필요한 것만 복제**해서 한다.
- 이 차이가 마이크로서비스가 갖는 유연성이다.

## 예시
```text
[모놀리식] 확장 = 전체 복제
서버1: [인증|승객|정산|알림]   서버2: [인증|승객|정산|알림]
  → 정산만 부하가 커도 전부 복제해야 한다

[마이크로서비스] 확장 = 필요한 것만 복제
서버1: [인증]  서버2: [정산][정산][정산]  서버3: [승객][알림]
  → 부하가 큰 서비스만 늘린다
```

## 요약
- 모놀리식은 UI와 데이터 접근 코드가 한 프로그램·한 배포 단위(예: WAR 하나)로 합쳐진 구조다.
- 진짜 문제는 서비스 개수가 아니라 컴포넌트 간 상호작용이며, 작은 변경도 전체 종료·재배포·재테스트로 번진다.
- 강한 결합, 컨테이너 시작 지연, 거대한 코드베이스, 팀 독립성 저해, 지속적 배포 방해, 기술 스택 종속이 핵심 단점이다.
- 모놀리식은 전체를 복제해 확장하고, 마이크로서비스는 서비스를 분산해 필요한 것만 복제한다.
