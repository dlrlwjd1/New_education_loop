# Project Brief

## 개요
- 캡스톤 프로젝트 **Meal Drop** 의 요구사항, 구축 단계, 권장 접근법, 제출 규칙을 정리하는 강의

## 내용

### 프로젝트 목표
- 비자명한 과제를 완수하는 법을 익힌다 — **문제 이해 → 설계 → 개발 → 테스트 → 리뷰·리팩터링 → 통합**
- 지난 주차들에서 얻은 지식을 모두 구현해 본다.

### Meal Drop 소개
- **10개 이상 대도시에 수백 개 레스토랑 파트너를 둔 음식 배달 서비스**다.
- 레스토랑은 온라인 포털이나 모바일 앱으로 주문을 받아 준비한다.
- 배달 파트너는 물류(logistics) 애플리케이션으로 픽업과 배달을 처리한다.
- 소비자는 Google Play Store나 App Store에서 앱을 받아 레스토랑을 탐색하고 주문한다.

### 만들어야 할 3개 앱
| 앱 | 사용자 | 역할 |
|---|---|---|
| **Meal Drop app** | 소비자 | 레스토랑 탐색, 메뉴 확인, 주문 |
| **Meal Drop Restaurant Partner app** | 레스토랑 관리자 | 주문 수신·수락 |
| **Meal Drop Delivery Agent app** | 배달 담당자 | 레스토랑에서 픽업해 소비자 주소로 배달 |

- 이 세 앱의 백엔드 API로 **마이크로서비스(microservice) 3개**를 만들고 컨테이너화(containerize)해야 한다.

### 구축 단계
1. **프로젝트 3개 개발** — 마이크로서비스마다 하나씩: `Meal Drop API`, `Meal Drop Restaurant Partner API`, `Meal Drop Delivery Agent API`
2. **마이크로서비스별로 별도 데이터베이스 배포 구성** — MongoDB가 권장이지만 원하는 NoSQL 데이터베이스를 써도 된다.
3. **API 개발** — **JWT(JSON Web Token) 인가(authorization)** 를 구현하고, 제공된 **OpenAPI 명세(specification)** 와 동작이 맞는지 확인한다.
4. **RabbitMQ 메시징으로 세 마이크로서비스 간 주문 데이터 동기화**

### 개발 마일스톤
개발자는 먼저 작업을 계획해 Meal Drop 개발 과정을 마일스톤으로 분해해야 한다:
- 사용자 등록(register)
- 유효한 사용자로 로그인
- 레스토랑·음식 상세 미리보기
- 장바구니(cart)에 음식 추가
- 음식 주문

### 권장 접근법
- **마이크로서비스 아키텍처 기반 설계 작성** — 애플리케이션의 원활한 개발을 가능하게 한다. 애자일 방법론으로 기능을 지원하는 서비스를 개발한다.
- **프로토타입 제작** — 첫 단계로 GUI 도구 **Pencil** 을 사용해 프로토타입을 만든다.
- **데이터 모델(data model) 작성** — 어떤 데이터가 필요하고 어떻게 조직할지에 집중하게 해 준다. 데이터 모델은 로드맵, 건축가의 청사진, 또는 설계 대상에 대한 통찰을 주는 형식적 다이어그램에 비유할 수 있다.
- **마이크로서비스 설계** — 백엔드 애플리케이션 구축의 결정적 단계는 애플리케이션을 여러 서비스로 쪼개는 것이다. 설계에는 **API 게이트웨이를 위한 Discovery Service** 를 사용하고, 서비스 간 통신에 여러 통신 기법을 사용한다.
- **마이크로서비스 통신 설계** — **동기(synchronous)** 방식과 **비동기(asynchronous)** 방식 통신을 모두 사용한다.
- **테스트 코드 개발** — 단위 테스트(unit testing)는 개발자가 이른 단계에서 버그를 찾도록 돕고, 기존 코드를 깨지 않으면서 새 기능을 추가하게 해 준다.
- **설계 구현은 마지막 단계**로 수행한다. 코드 품질은 들여쓰기를 잘 맞추고, 코드를 뒷받침하는 주석을 달고, 사용하지 않는 변수와 import를 제거해 유지한다.

### 지켜야 할 규칙
- **설계 문서는 소스 코드 밖의 별도 폴더**에 저장한다.
- 솔루션은 **NPM 라이브러리**를 사용해 개발한다.
- **REST와 마이크로서비스의 설계 원칙**을 충실히 따른다.
- **SRP(Single Responsibility Principle, 단일 책임 원칙)** 와 **DRY(Don't Repeat Yourself)** 를 설계·개발 시 따른다.
- 테스트 케이스는 **Mocha와 Chai** 라이브러리로 작성하고, 구현에 **기본 훅(default hook)** 을 사용한다.
- 백엔드 지원으로 **MongoDB** 를 사용한다.

### 제출 규칙
- 솔루션 코드를 **zip으로 압축**해 업로드한다.
- zip에서 **`node_modules` 폴더는 제외**한다.
- 솔루션 코드에 **`README.md`** 를 포함해 프로젝트 실행 방법을 적는다. 여기에는 **프로젝트 목표, 사용한 기술 스택(tech stack), 실행 명령 목록**(MongoDB 서버, 애플리케이션, 테스트 케이스)이 들어가야 한다.

## 예시
```text
Meal Drop 아키텍처
┌─ Meal Drop API ────────────┐   소비자 앱
├─ Restaurant Partner API ───┤   레스토랑 관리자 앱
└─ Delivery Agent API ───────┘   배달 담당자 앱
   각 서비스마다 별도 DB 배포 (MongoDB 권장)
   인가: JWT · 명세: OpenAPI
   서비스 간 주문 데이터 동기화: RabbitMQ

마일스톤
사용자 등록 → 로그인 → 레스토랑·음식 미리보기 → 장바구니 추가 → 주문
```

## 요약
- Meal Drop은 소비자·레스토랑·배달 담당자용 3개 앱을 위한 마이크로서비스 3개를 만들고 컨테이너화하는 과제다.
- 서비스별 별도 DB, JWT 인가, OpenAPI 명세 준수, RabbitMQ로 주문 데이터 동기화가 핵심 요구사항이다.
- Pencil 프로토타입 → 데이터 모델 → 마이크로서비스·통신 설계 → 테스트 코드 → 구현 순서로 진행하며 SRP·DRY를 따른다.
- 제출은 `node_modules`를 제외한 zip에 실행 방법을 담은 `README.md`를 포함한다.
