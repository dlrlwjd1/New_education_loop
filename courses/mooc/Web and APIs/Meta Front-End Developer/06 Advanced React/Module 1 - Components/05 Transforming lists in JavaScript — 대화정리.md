# Transforming lists in JavaScript — 대화정리

> 원본 강의: [05 Transforming lists in JavaScript.md](05%20Transforming%20lists%20in%20JavaScript.md)

## 개요
- 자바스크립트 배열의 `map` 메서드로 데이터 목록을 React가 렌더링할 수 있는 형태(JSX 배열)로 변환하는 패턴을 다룬다.
- 이 패턴은 React Native의 `FlatList`가 각 데이터 항목을 컴포넌트로 바꾸는 방식과 사고방식이 같아서, Phase 3의 `FlatList` 학습 전에 반드시 익혀야 한다.

## 내용

### map으로 목록 렌더링하기
```jsx
{desserts.map((dessert) => (
  <Text key={dessert.id}>{dessert.name}</Text>
))}
```
배열의 각 항목을 JSX 엘리먼트로 변환해서 리스트를 그린다.

### key는 왜 필요한가
- React는 리렌더링될 때 이전 렌더링 결과와 새 렌더링 결과를 비교(재조정, reconciliation)해서 바뀐 부분만 실제 DOM에 반영한다.
- `map`으로 만든 리스트처럼 같은 종류의 엘리먼트가 여러 개일 때, React는 "이전 항목과 새 항목이 같은 것인지"를 **key 값으로만** 판단한다. **내용(content)이 같은지는 판단 기준이 아니다.**
  - key가 **이전에 없던 새 값**이면 → 내용과 상관없이 **새 컴포넌트 인스턴스**로 mount한다.
  - key가 **이전 렌더링에도 있던 값**이면 → 내용(props)이 달라져도 **같은 인스턴스로 인식**하고 내용만 갱신한다. 인스턴스가 갖고 있던 내부 state(포커스, 체크 상태 등)도 그대로 유지된다.
- key 없이 `map`을 쓰면 React가 어쩔 수 없이 **배열 인덱스**를 key로 사용한다. 이게 문제가 되는 건 리스트에 **텍스트만 있고 항상 끝에만 추가되는 경우가 아니라, 중간 삽입·삭제·순서 변경 + 항목별 상태(state)**가 섞일 때다.

### 왜 "화면엔 정상으로 보이는데" 실제로는 문제인가
- 단순 텍스트 나열 + 끝에만 추가하는 리스트는 index를 key로 써도 겉보기엔 문제가 없을 수 있다.
- 하지만 각 항목이 자체 state(체크박스, 입력값 등)를 가진 상태에서 **중간 항목을 삭제**하면, index는 "자리"를 가리키므로 삭제 이후 항목들이 한 칸씩 밀리고, React는 index(=key)가 같으니 "같은 인스턴스"로 재사용한다. 그 결과 **인스턴스의 내부 state는 원래 자리에 그대로 남고, 이름표(내용)만 바뀌어 붙는** 현상이 생긴다.
- 그래서 React는 index를 key로 쓸 때 콘솔에 경고를 띄운다 — 지금 당장은 안 터져도 나중에 상호작용(삽입/삭제/재정렬)에서 터질 수 있다는 신호다.

## 예시

**즐겨찾기 체크박스가 있는 디저트 목록** (각 행이 자체 `useState`로 체크 상태를 관리)

초기 상태:
| index(=key) | name | favorited |
|---|---|---|
| 0 | Tiramisu | false |
| 1 | Cheesecake | true (사용자가 체크함) |
| 2 | Brownie | false |

맨 앞의 "Tiramisu"를 삭제하면 데이터는 `[Cheesecake, Brownie]`가 되고 index가 다시 매겨진다:
| index(=key) | name |
|---|---|
| 0 | Cheesecake |
| 1 | Brownie |

React는 key=0, key=1이 이전에도 있던 값이므로 기존 인스턴스를 재사용한다. 하지만 재사용은 위치(index) 기준이라, 원래 favorited: false였던 index=0 인스턴스가 "Cheesecake"라는 이름을 받아 그대로 그려진다.

→ **결과: 사용자가 분명히 체크했던 "Cheesecake"가 화면에서 체크 해제된 것처럼 보인다.** 컴포넌트가 바뀐 게 아니라 이름표만 바뀐 것인데, 사용자 눈에는 데이터가 날아간 버그로 보인다.

새 항목을 리스트 중간(2번째)에 끼워 넣는 경우도 같은 원리로 판단된다:
| key | 이전 위치 | 새 위치 | React의 판단 |
|---|---|---|---|
| 1 (Tiramisu) | 1번째 | 1번째 | 변화 없음 |
| 3 (Brownie, 새 항목) | 없음 | 2번째 | 처음 보는 key → 새로 mount |
| 2 (Cheesecake) | 2번째 | 3번째 | 기존 key → 같은 인스턴스로 인식, 위치만 이동. 내용이 바뀌어 있어도 새로 만들지 않고 갱신만 한다 |

## 요약
- `map`은 배열 데이터를 JSX 리스트로 변환하는 표준 패턴이며, React Native `FlatList`의 항목 렌더링과 같은 사고방식이다.
- React는 리스트 항목의 동일성을 **key 값으로만** 판단하고, 내용(content)은 판단 기준이 아니다.
- key로 배열 index를 쓰면, 텍스트만 있고 끝에만 추가되는 단순한 목록에선 문제가 없어 보일 수 있지만, **중간 삽입/삭제/순서 변경 + 항목별 상태**가 섞이면 상태가 엉뚱한 항목에 눌러붙는 실제 버그로 이어진다.
- Phase 3의 `TextInput` 목록 화면에서 항목을 삭제할 때 정확히 이 문제(값이 밀리는 현상)가 재현된다.
