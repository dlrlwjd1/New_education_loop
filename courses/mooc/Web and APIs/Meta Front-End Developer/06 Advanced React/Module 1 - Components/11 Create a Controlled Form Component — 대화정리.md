# Create a Controlled Form Component — 대화정리

> 원본 강의: [11 Create a Controlled Form Component.md](11%20Create%20a%20Controlled%20Form%20Component.md)

## 개요
- 09~10번에서 다룬 제어 컴포넌트 패턴을 `<input type="range">`(슬라이더)에 적용하는 실습. 사용자가 0~10점으로 피드백 점수를 매기는 슬라이더 + 코멘트 폼을 예시로 쓴다.

## 내용

### 슬라이더도 같은 패턴
- `<input type="range">`의 `value` prop을 state에 연결하고, `onChange`로 변경을 감지해서 state를 갱신하는 건 텍스트 입력과 동일한 제어 컴포넌트 패턴이다.
- 여기에 "사용자 지정 검증(custom validation)"을 추가해 더 나은 사용자 경험을 만든다.

### `event.target.value`는 항상 문자열이다
- HTML `<input>`의 `value` 속성은 `type`이 `range`든 `number`든 `text`든 상관없이 **DOM 스펙 자체가 문자열로 정의**되어 있다. `type="range"`는 슬라이더로 "보여주는 방식"만 다를 뿐, 값을 꺼내는 방식은 다른 입력창과 동일하게 문자열이다.

### 문자열 타입 때문에 실제로 버그가 나는 경우
1. **덧셈 연산** — `value + 1`처럼 `+`를 쓰면 숫자 연산이 아니라 **문자열 이어붙이기**가 된다. `"5" + 1` → `"51"` (숫자 6이 아니다).
2. **엄격한 동등 비교(`===`)** — `value === 5`는 항상 `false`다. `"5" !== 5`이기 때문이다. "만점(10점)인지 확인" 같은 로직에서 `value === 10`이 절대 참이 안 되는 버그로 나타난다.
3. **문자열끼리 비교할 때** — 숫자가 아니라 **사전순(lexicographic)으로 비교**된다. `"9" > "10"`은 실제로 `true`다 (`'9'` 문자가 `'1'` 문자보다 크므로). 이전 값을 문자열로 저장해뒀다가 새 값(문자열)과 비교하면 이 버그를 만난다.
- 반대로 `value >= 5`처럼 **숫자 리터럴과 비교**하는 경우는 문제없다. 자바스크립트는 `>=`, `<=`, `>`, `<` 비교에서 한쪽이 숫자면 다른 쪽 문자열을 자동으로 숫자로 변환해서 비교하기 때문이다 (`"7" >= 5` → `7 >= 5` → `true`).

### 해결책
- `onChange`에서 state에 저장하기 전에 명시적으로 숫자로 변환한다.

```jsx
const handleChange = (event) => {
  setScore(Number(event.target.value)); // 문자열 → 숫자로 변환해서 저장
};
```

이렇게 하면 state 자체가 처음부터 진짜 숫자로 저장되니, 이후의 모든 계산·비교가 안전해진다.

## 예시
- 0~10점 슬라이더 + 코멘트 피드백 폼에서, 슬라이더 값을 `Number()`로 변환하지 않고 state에 그대로 저장하면 "10점 만점인지" 검사(`score === 10`)가 항상 실패하는 등의 버그가 생길 수 있다.

## 요약
- `<input type="range">` 등 어떤 타입의 `<input>`이든 `event.target.value`는 항상 문자열이다.
- 문자열 상태로 덧셈(`+`)하거나 엄격 비교(`===`)하거나 문자열끼리 대소 비교하면 예상과 다른 결과가 나올 수 있다.
- `onChange`에서 `Number()`로 변환한 뒤 state에 저장하는 습관을 들이면 이후 계산·비교가 안전해진다.
