# Using Keys Within List Components — 대화정리

> 원본 강의: [08 Using Keys Within List Components.md](08%20Using%20Keys%20Within%20List%20Components.md)

## 개요
- 07번에서 정리한 key 원칙이 **실제로 눈에 보이는 버그**로 나타나는 걸 데모로 보여주는 강의. 편집 가능한 할 일(todo) 목록 앱 + "순서 뒤집기" 버튼 예제를 쓴다.

## 내용

### 데모 앱 구성
- 각 todo 행은 `id`, `createdAt`(생성일), **편집 가능한 텍스트 입력(TextInput)**으로 구성된 테이블 행이다.
- "순서 뒤집기" 버튼을 누르면 배열 순서가 반대로 바뀐다.

### 순서를 뒤집으면 실제로 벌어지는 일 (index를 key로 쓸 때)
- 배열이 뒤집히면서 각 행에 전달되는 `id`, `createdAt` **prop은 새 값으로 정확히 갱신**된다 (props는 리렌더링마다 갱신되므로).
- 하지만 key가 index라서 React는 "이 위치(index=0)의 인스턴스는 원래 있던 그 인스턴스"라고 판단하고 **입력창 DOM 요소를 재사용**한다.
- 이 입력창은 보통 **제어되지 않는(uncontrolled) 입력**이다 — 사용자가 타이핑한 값이 `defaultValue`로 한 번만 설정되고, 이후로는 그 DOM 요소 안에 값이 그대로 저장된다. props가 바뀐다고 자동으로 다시 채워지지 않는다.
- 결과: **재사용된 DOM 요소 안의 타이핑된 값은 제자리에 그대로 남고, 그 옆에 붙은 id/createdAt 라벨만 새 데이터로 바뀐다.**

### 핵심 원리 (05·07번과 동일한 뿌리)
- **상태(체크 여부든, 타이핑된 텍스트든)는 항상 "위치"에 붙어있지, "데이터"를 따라가지 않는다** — 이게 index-key 문제의 본질이다.
- 05번의 체크박스 예시(삭제 시 체크 상태가 엉뚱한 항목에 남는 것)와 이 강의의 입력창 예시(순서 뒤집기 시 값이 엉뚱한 라벨 옆에 남는 것)는 완전히 같은 원인에서 나온 서로 다른 증상이다.

### 해결책
- 목록에서 어떤 위치에 있든 상관없이 각 항목을 정확히 식별할 수 있는 **고유한 값**(예: todo의 `id`)을 key로 써야 한다.

## 예시
- todo 목록 `[{id: 1, text: "빨래"}, {id: 2, text: "설거지"}]`에서 index를 key로 쓰고 순서를 뒤집으면:
  - id/createdAt 라벨은 뒤집힌 순서대로 정확히 표시된다.
  - 하지만 각 입력창의 실제 타이핑된 텍스트("빨래", "설거지")는 DOM 요소가 재사용되면서 **제자리(원래 위치)에 그대로 남는다.**
  - 화면에는 "설거지" id/생성일 옆에 "빨래"라고 입력했던 텍스트가 붙어있는, 라벨과 값이 서로 안 맞는 상태가 눈에 보인다.

## 요약
- index를 key로 쓰면, 각 항목의 표시용 데이터(props)는 정확히 갱신되지만 각 항목 인스턴스가 갖고 있던 내부 상태(입력값, 체크 상태 등)는 위치에 그대로 붙어있어 데이터와 어긋난다.
- 이 문제를 해결하려면 항목의 위치와 무관하게 항목 자체를 고유하게 식별하는 값(id 등)을 key로 써야 한다.
