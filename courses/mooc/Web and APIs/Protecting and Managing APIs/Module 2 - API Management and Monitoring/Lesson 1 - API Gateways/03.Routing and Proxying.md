# Routing and Proxying (라우팅과 프록시)

## 개요
- 라우팅과 프록시가 API 통신을 원활하고 안전하며 효율적으로 유지하는 방법을 다루는 3분 27초 분량 영상 — Module 2 "Lesson 1: API Gateways"의 세 번째 영상

## 내용

### 라우팅과 프록시가 왜 필요한가
- 올바른 주소를 모른 채 소포를 보내면 배송되지 않을 가능성이 큼 — 디지털 세계의 API도 같은 위험에 처함
- 라우팅과 프록시가 없으면 요청이 유실되거나 잘못된 곳으로 전달될 수 있음
- **라우팅(Routing)**은 요청이 어디로 가야 하는지 결정하고, **프록시(Proxying)**는 그 요청을 안전하게 목적지까지 전달하고 다시 돌려받음

### 라우팅과 프록시의 차이
- **라우팅**은 요청을 올바른 서비스로 전달함 — 예를 들어 로그인 요청은 인증(authentication) 서비스로, 결제 요청은 청구(billing) 서비스로 라우팅됨
- **프록시**는 메신저처럼 동작해 요청을 전달하고 응답을 반환함
- 이 둘이 함께 안전하고 효율적인 통신을 보장함

### 라우팅과 프록시가 해결하는 과제
1. **클라이언트 상호작용 단순화**: 클라이언트가 여러 서비스 엔드포인트 대신 하나의 게이트웨이만 알면 됨
2. **내부 아키텍처 은닉**: 외부 사용자가 서비스에 직접 접근할 수 없도록 숨김
3. **보안 계층 추가**: 인증, SSL 같은 보안 계층을 더함
4. **로드 밸런싱 지원**: 요청을 분산시켜 과부하를 방지함
5. **프로토콜 변환 지원**: 서로 다른 형식을 사용하는 시스템끼리도 통신할 수 있게 함
- 이런 기능들이 없다면 API는 취약하고 비효율적이며 관리하기 어려워짐

### 워크플로
1. 클라이언트가 게이트웨이로 요청을 보냄
2. 라우팅 규칙을 사용해 올바른 서비스를 선택하는 결정이 내려짐
3. 프록시가 해당 서비스로 요청을 전달(forwarding)함
4. 응답이 프록시를 거쳐 클라이언트로 돌아옴
- 이는 온라인으로 음식을 주문하는 것과 비슷함 — 주문을 넣으면 시스템이 올바른 식당을 선택하고, 배달원이 이를 운반해 문 앞에 음식이 도착하는 것과 같음

### 실제 도구
- **Kong**: API 게이트웨이의 라우팅·프록시에 널리 쓰이며 유연성과 확장성을 제공함
- **Apigee(Google)**: 강력한 엔터프라이즈 보안과 분석 기능을 더함
- **Nginx**: 고성능 웹 트래픽 라우팅과 로드 밸런싱으로 잘 알려짐
- 이런 도구들은 우리가 매일 쓰는 앱들 — 영화 스트리밍, 티켓 예매, 결제 처리 — 뒤에서 조용히 작동하며 트래픽이 많을 때도 서비스가 안전하고 확장 가능하며 응답성 있게 유지되도록 보장함

## 요약
- 라우팅은 요청을 올바른 서비스로 보내는 결정이고, 프록시는 이를 안전하게 전달·반환하는 과정임 — 둘이 함께 클라이언트 상호작용 단순화, 내부 아키텍처 은닉, 보안 계층 추가, 로드 밸런싱, 프로토콜 변환을 가능하게 함
- Kong, Apigee, Nginx 같은 실제 도구들이 이 워크플로를 실무에서 구현함
