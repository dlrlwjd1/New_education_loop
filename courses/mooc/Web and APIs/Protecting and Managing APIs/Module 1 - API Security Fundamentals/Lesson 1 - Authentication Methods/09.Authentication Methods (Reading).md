# Reading: Authentication Methods (인증 방법 정리)

## 개요
- Lesson 1에서 다룬 4가지 인증 방법(기본 인증·API 키·OAuth 2.0·JWT)을 특징·예시·비유로 정리하는 10분 분량 읽기자료 — Module 1 "Lesson 1: Authentication Methods"의 아홉 번째 항목
- API는 중요한 데이터와 서비스를 노출하므로 누가 접근하려 하는지 검증하는 것이 필수적 — 인증은 신뢰할 수 있는 사용자·시스템만 들어오게 하며, 각 방법은 보안·단순성·확장성 사이에서 서로 다른 균형을 잡음

## 내용

### 기본 인증(Basic Authentication) — 가장 단순한 접근법
- 클라이언트가 모든 요청과 함께 사용자명·비밀번호를 전송해야 함 — 이 자격증명은 Base64로 인코딩되지만 암호화되지는 않으므로, 전송 중 보호를 위해 HTTPS가 필수임
- **특징**: 최소한의 설정으로 구현이 쉬움 / 거의 모든 프로그래밍 언어·도구에서 지원됨 / 보안이 전적으로 전송 계층 암호화(TLS/HTTPS)에 의존함
- **사용 예**: 개발 중 API를 빠르게 테스트할 때 / 위험과 노출이 낮은 내부 시스템
- **학습 팁**: 기본 인증은 방에 들어갈 때마다 매번 신분증을 건네주는 것과 같음 — 편리하지만 누군가 가로채면 위험함

### API 키(API Keys) — 고유 토큰을 통한 접근
- API 키는 애플리케이션이나 개발자에게 발급되는 고유한 문자열 — 클라이언트를 인증하기 위해 요청에 포함됨. 사용자명·비밀번호와 달리 API 키는 최종 사용자가 아니라 애플리케이션을 식별함
- **특징**: 배포·관리가 간단함 / IP 주소·도메인·사용량 할당량으로 제한 가능 / 사용자 신원이나 세밀한 권한을 담지 않음
- **사용 예**: 서드파티 개발자의 접근을 통제할 때 / 속도 제한(rate limit)을 적용하고 API 사용량을 모니터링할 때
- **학습 팁**: API 키는 방문객 패스와 같음 — 건물 안에는 들어가게 해주지만 당신이 누구인지는 증명하지 않음

### OAuth 2.0 — 위임되고 안전한 인가
- OAuth 2.0은 사용자가 자격증명을 공유하지 않고도 애플리케이션에 제한된 데이터 접근 권한을 부여할 수 있게 하는 인가 프레임워크 — 사용자명·비밀번호를 전송하는 대신, 인가 서버(authorization server)를 통해 접근 토큰을 발급함
- **특징**: 여러 플로우 지원(Authorization Code, Client Credentials, Implicit, Device Code) / 사용자·클라이언트 애플리케이션·리소스 서버의 역할을 분리함 / 소셜 로그인과 엔터프라이즈 통합에서 광범위하게 사용됨
- **사용 예**: 피트니스 앱이 사용자의 Google 비밀번호를 노출하지 않고 Google Calendar에 접근하게 할 때 / 모바일 앱이 로그인된 사용자를 대신해 API를 안전하게 호출하게 할 때
- **학습 팁**: OAuth는 집 열쇠 전체 대신 임시적이고 제한된 용도의 카드키를 건네주는 것과 같음

### JSON 웹 토큰(JWT) — 무상태이고 이동 가능한 인증
- JWT는 사용자나 애플리케이션에 대한 클레임을 담은 압축되고 디지털 서명된 토큰 — 자체 완결적(self-contained)이라 API가 인증 서버에 연락하지 않고도 토큰을 검증할 수 있음
- **특징**: 사용자 신원·역할·권한을 토큰 내부에 인코딩함 / 무상태(stateless) — 서버 측 세션 저장이 필요 없음 / 만료될 때까지 토큰이 유효하므로 도난에 대비해 보호해야 함
- **사용 예**: 세션 관리가 비현실적인 확장 가능한 마이크로서비스 / 여러 애플리케이션에 걸친 싱글 사인온(SSO) 솔루션
- **학습 팁**: JWT는 신원 정보가 안에 적힌 봉인된 봉투와 같음 — 봉인이 온전하다면 내용은 신뢰할 수 있음

## 요약
