# OAuth 2.0 and JWT (OAuth 2.0과 JWT)

## 개요
- OAuth 2.0과 JWT(JSON Web Token)가 각각 무엇이고 어떻게 작동하며 왜 오늘날 애플리케이션에서 널리 쓰이는지 다루는 4분 24초 분량 영상 — Module 1 "Lesson 1: Authentication Methods"의 일곱 번째 항목

## 내용

### 비유 — 손님에게 집 열쇠 전체를 주지 않는 법
- 방문객을 들어오게 하려고 매번 집 열쇠 전체를 건네야 한다면 위험할 것 — 대신 특정 방에만, 제한된 시간 동안만 접근할 수 있는 게스트 패스를 줄 것
- OAuth 2.0과 JWT가 디지털 세계에서 정확히 이 역할을 함 — 사용자와 애플리케이션이 민감한 자격증명을 노출하지 않고도 필요한 리소스에 안전하게 접근하게 해줌

### OAuth 2.0 — 비밀번호 공유 없이 접근 위임하기
- OAuth 2.0은 앱이 비밀번호를 공유하지 않고도 사용자 데이터에 접근할 수 있게 하는 프레임워크 — 임시 게스트 접근을 부여하는 것과 같음
- 실제 자격증명 대신 접근 토큰(access token)을 발급하며, 이 토큰은 무엇에 접근할 수 있는지, 얼마나 오래, 어떤 조건에서 접근할 수 있는지를 정의함
- 이 토큰들은 그랜트 타입(grant type)이라는 여러 형태로 제공되며, 모바일 앱·웹 앱·백엔드 서비스 같은 시나리오에 맞춰져 있음
- 가장 중요한 점은 OAuth가 위임된 접근(delegated access)을 가능하게 한다는 것 — 한 서비스가 사용자의 비밀번호 없이도 사용자를 대신해 행동할 수 있게 함. 이런 유연성과 보안의 균형 덕분에 OAuth 2.0은 거의 모든 현대 애플리케이션에서 사용됨

### OAuth 2.0의 작동 흐름
1. 사용자가 앱에 로그인하고 싶어함
2. 새 계정을 만드는 대신 "Google로 로그인" 또는 "Facebook으로 로그인"을 클릭
3. Google 같은 OAuth 2.0 제공자가 사용자 신원을 검증하고 접근 토큰을 발급
4. 그 토큰이 앱에 전달되어, 사용자의 실제 비밀번호를 노출하지 않고도 이름·이메일 같은 정보에 제한된 접근을 부여
5. 앱은 이 토큰을 사용해 허용된 것만 접근함
- 이 단계별 흐름이 로그인 과정을 매끄러우면서도 안전하게 만듦

### JWT(JSON Web Token) — 자체 완결적인 인증 데이터 전달 형식
- JWT는 인증 데이터를 안전하게 전달하기 위한 자체 완결적(self-contained)이고 압축된 형식
- 헤더(header)·페이로드(payload)·서명(signature) 세 부분으로 구조화됨 — 헤더는 메타데이터를 담고, 페이로드는 사용자 ID 같은 클레임(claim)을 담으며, 서명은 무결성을 보장함
- JWT는 무상태(stateless)이므로 서버 측 세션이 필요 없어 확장성이 매우 높음 — 이런 효율성 때문에 JWT는 API와 현대 인증 시스템에서 흔히 사용됨

### 실생활 적용 사례
- **OAuth**: 서드파티 앱이 제한된 사용자 데이터에 접근함 — 예를 들어 피트니스 앱이 Gmail 비밀번호 없이 Google Fit 데이터를 가져오는 경우
- **JWT**: 싱글 사인온(SSO) 시스템에서 빛을 발함 — 예를 들어 학습 포털에 한 번 로그인하면 JWT 덕분에 다시 로그인하지 않고도 모든 강좌에 매끄럽게 접근할 수 있음
- 두 방법이 함께 작동해 실생활에서 보안과 편의성을 모두 제공하며 매끄러운 디지털 상호작용을 보장함

## 요약
- OAuth 2.0은 접근 토큰을 통해 비밀번호 공유 없이 위임된 접근을 가능하게 하고, JWT는 헤더·페이로드·서명으로 구조화된 무상태 토큰으로 확장성 있는 인증 데이터 전달을 가능하게 함
- 두 기술은 서드파티 데이터 접근과 싱글 사인온 같은 실생활 시나리오에서 함께 사용되어 보안과 편의성을 모두 제공함
