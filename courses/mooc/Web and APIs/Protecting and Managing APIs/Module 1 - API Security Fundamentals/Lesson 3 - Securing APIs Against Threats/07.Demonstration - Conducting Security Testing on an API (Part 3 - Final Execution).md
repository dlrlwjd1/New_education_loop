# Demonstration: Conducting Security Testing on an API — Part 3: Final Execution (API 보안 테스트 실습 데모 3부: 실행 및 검증)

## 개요
- 취약한 서버와 강화된 서버를 실제로 실행해 5가지 공격 테스트(인젝션·경로 순회·인증 우회·속도 제한/DoS·감사)를 수행하고 그 결과를 비교하는 3부작 데모의 마지막 부(7분 3초) — Module 1 "Lesson 3: Securing APIs Against Threats"의 일곱 번째 영상 항목

## 내용

### 취약한 서버 실행 및 테스트

```bash
node server-vulnerable.js
```
- 브라우저에서 `localhost:3000`에 접속하면 5개의 카드(Injection, Path Traversal, Auth Bypass, Rate Limit/DoS, Audit)가 나타남

| 테스트 | 입력 | 취약한 서버의 결과 |
|---|---|---|
| **인젝션** | 이름 "Alina" 입력 후 Run Normal | `Injected: false`, 빈 결과 배열(일치하는 사용자 없음) |
| **인젝션** | Run Injection 클릭 (`OR 1=1` 페이로드) | `Injected: true`, 모든 사용자 반환 — 입력을 쿼리 문자열에 직접 이어붙이기 때문 |
| **경로 순회** | 파일 경로 `package.json`, Read File 클릭 | 상태 200과 함께 파일 내용 반환 — 제한 없이 어떤 경로든 읽기 때문 |
| **인증 우회** | Call `/admin` (파라미터 없음) | 403 Forbidden |
| **인증 우회** | Call `/admin?isAdmin=true` | 비밀 값(secret) 반환 — 쿼리 파라미터를 그대로 신뢰하기 때문 |
| **인증 우회** | Call `/admin` with header token | 여전히 403 — 헤더를 아예 무시하기 때문 |
| **속도 제한/DoS** | 동시 클라이언트 20, 클라이언트당 요청 5회, Run Simulation | 대부분 HTTP 200 — 속도 제한이 전혀 없어 모든 요청을 그대로 수용함 |
| **감사** | Refresh Audit 클릭 | 최근 이벤트(인젝션 시도, 파일 읽기, 인가 결정) 목록 표시, `Hardened: false` |

- 속도 제한(rate limiting)은 고정된 시간 창 안에서 한 사용자나 IP가 만들 수 있는 요청 수를 제한하는 기본적인 보호 장치로, 초과 트래픽을 차단·지연시켜 무차별 대입 로그인이나 DoS 공격을 막는 데 도움을 줌

### 강화된 서버로 전환 및 동일 테스트 재실행

```bash
# 취약한 서버 중지
Ctrl + C

# 강화된 서버 시작
node server_hardened.js
```

| 테스트 | 입력 | 강화된 서버의 결과 |
|---|---|---|
| **인젝션** | 이름 "Alice" 입력 후 Run Normal | `Injected: false`, Alice만 반환 (취약 서버와 동일) |
| **인젝션** | Run Injection 클릭 | **400 에러 "malformed input detected"** — 의심스러운 패턴을 차단해 파라미터화된 쿼리와 같은 보호를 시뮬레이션함 |
| **경로 순회** | 파일 경로 `package.json`, Read File 클릭 | **404 Not Found** — `public` 디렉터리 내부 파일만 허용하고 그 외는 모두 차단하기 때문에 프로젝트 파일을 직접 읽을 수 없음 |
| **인증 우회** | Call `/admin` (파라미터 없음) | 403 Forbidden (토큰 없음) |
| **인증 우회** | Call `/admin?isAdmin=true` | 여전히 **403** — 쿼리 파라미터를 무시하기 때문 |
| **인증 우회** | Call `/admin` with header token | **200**과 함께 비밀 값 반환 — 헤더에 유효한 bearer 토큰이 있을 때만 관리자 접근을 허용함을 확인 |
| **속도 제한/DoS** | 동시 클라이언트 20, 클라이언트당 요청 5회, Run Simulation | **200과 429가 섞여서** 나타남(429 = Too Many Requests) — 로그인 엔드포인트에 분당 IP당 10회라는 단순한 제한을 강제해 과도한 트래픽을 효과적으로 억제함을 보여줌 |

### 종합 정리
- 취약한 서버는 SQL 인젝션, 경로 순회, 접근 제어 결함, 무제한 로그인 시도를 모두 허용했지만, 입력 검증·경로 정규화·헤더 기반 인가·속도 제한 같은 보호 장치가 이런 공격들을 차단하는 것을 확인함
- 이 비교는 안전한 코딩과 계층화된 방어(layered defense)가 흔한 웹 애플리케이션 취약점을 방지하는 데 왜 필수적인지를 강조함

## 요약
- 동일한 5가지 테스트를 취약한 서버와 강화된 서버에서 나란히 실행해, 입력 검증(인젝션 차단), 경로 정규화(순회 차단), 헤더 기반 bearer 토큰 인가(접근 제어 결함 차단), IP당 속도 제한(DoS/무차별 대입 차단)이 실제로 어떻게 공격을 막아내는지 직접 확인함
- 이것으로 3부작 실습 데모가 마무리됨 — 다음 [08.Understanding and Preventing the OWASP Top API Security Threats.md](08.Understanding%20and%20Preventing%20the%20OWASP%20Top%20API%20Security%20Threats.md)에서 OWASP Top API 보안 위협을 다루는 읽기자료로 이어짐
