# Demonstration: Conducting Security Testing on an API — Part 2: Vulnerable and Hardened Server Setup (API 보안 테스트 실습 데모 2부)

## 개요
- 의도적으로 취약하게 만든 `server_vulnerable.js`와 그에 대응하는 안전한 `server_hardened.js`를 작성하는 3부작 데모의 2부(4분 21초) — Module 1 "Lesson 3: Securing APIs Against Threats"의 여섯 번째 영상 항목
- 같은 5가지 공격 표면(SQL 인젝션·경로 순회·인증 우회/DoS·접근 제어 결함)에 대해 취약한 버전과 강화된 버전의 코드를 나란히 비교함

## 내용

### server_vulnerable.js — 의도적으로 안전하지 않은 백엔드
- **설정과 임포트**: `.env`로 환경 변수를 로드하고 `fs`·`path`·`express`를 임포트, JSON·URL 인코딩 바디 파싱을 갖춘 Express 앱을 생성
- **데이터와 감사 로거**: 샘플 사용자 데이터를 담은 작은 `users` 배열과 보안 이벤트를 기록하는 `audit` 배열 — 헬퍼 함수 `addAudit`이 각 이벤트를 타임스탬프와 함께 저장해 나중에 검토할 수 있게 함
- **`/search` 라우트**: SQL과 유사한 검색을 시뮬레이션하며 사용자 입력을 쿼리 문자열에 직접 이어붙임(concatenate) — 입력에 `OR 1=1` 같은 패턴이 포함되면 모든 사용자 레코드가 유출되어 전형적인 SQL 인젝션 결함을 보여줌
- **`/file` 라우트**: 검증 없이 `path.join`을 사용해 사용자가 제공한 경로를 기반으로 파일을 읽음 — `/etc/hosts` 같은 값을 전달하면 공격자가 프로젝트 디렉터리를 벗어나 임의의 시스템 파일을 읽으려 시도할 수 있어 경로 순회(path traversal) 취약점을 보여줌
- **`/login` 라우트**: 속도 제한 없이 무제한 로그인 시도를 허용해 무차별 대입(brute force)이나 서비스 거부 공격에 취약함
- **`/admin` 라우트**: 쿼리 문자열에 `?isAdmin=true`가 포함되면 관리자 접근을 허용함 — 클라이언트가 제공한 파라미터를 신뢰하기 때문에 접근 제어 결함(broken access control)을 보여줌
- **`/audit` 라우트**: 데모 중 수행된 각 작업의 감사 로그를 반환함
- 마지막으로 프로젝트 디렉터리에서 GUI 파일을 서빙하고 `.env`에 정의된 포트(기본값 3000)에서 Express 서버를 시작함
- 이 서버는 의도적으로 안전하지 않게 만들어졌으며 교육 목적으로만 로컬에서 실행해야 함

### server_hardened.js — 더 안전한 백엔드
- **설정과 임포트**: 동일하게 `.env`·`fs`·`path`·`express`를 로드하고 JSON·URL 인코딩 바디를 파싱하는 Express 앱을 초기화
- **데이터와 감사 로거**: 취약 버전과 동일한 샘플 `users` 배열과 `addAudit`을 갖춘 `audit` 배열
- **속도 제한 설정**: 인메모리 rate map, 1분 윈도우, IP당 요청 10회 상한을 도입해 남용적 트래픽을 제한함
- **`/search` 라우트**: 문자열 이어붙이기를 피하고 `OR 1=1` 같은 의심스러운 패턴을 거부해 400 에러를 반환함 — 인젝션된 입력은 차단되지만 정상적인 조회는 그대로 작동함
- **`/file` 라우트**: 읽기를 `./public` 기본 디렉터리로 제한하고 `path.normalize`와 접두사 확인(prefix checking)을 사용함 — `../`로 벗어나려는 시도는 탐지되어 "traversal blocked"와 함께 400을 반환함
- **`/login` 라우트**: IP당 제한을 강제해 임계값을 초과하면 429를 반환하며, 유효한 사용자는 여전히 정상적으로 인증되고 유효하지 않은 사용자는 401을 받음
- **`/admin` 라우트**: 인가 헤더에 bearer 토큰을 요구하며 데모용 admin 토큰만 허용함 — 쿼리 파라미터를 신뢰하는 대신 적절한 인가를 보여줌
- **`/audit` 라우트**: 최근 이벤트를 반환하고 서버를 "hardened"로 표시해 데모 중 차단 결정을 확인할 수 있게 함
- **정적 파일과 서버 시작**: 안전한 `readme.txt`가 담긴 `public` 폴더가 존재하는지 확인하고, 프로젝트 루트에서 GUI를 서빙한 뒤 설정된 포트에서 리스닝을 시작함
- 이 서버도 여전히 교육용 데모이며 프로덕션 등급은 아니지만, 핵심 완화 조치들이 엔드투엔드로 작동하는 모습을 보여줌

## 요약
- 같은 5개 라우트(`/search`, `/file`, `/login`, `/admin`, `/audit`)를 취약 버전과 강화 버전으로 각각 구현해 SQL 인젝션·경로 순회·속도 제한 미비·접근 제어 결함이 실제 코드에서 어떻게 나타나고 어떻게 막히는지 직접 비교함
- 강화된 버전의 핵심 완화 기법: 입력 패턴 거부(인젝션 방지), 경로 정규화+접두사 확인(순회 방지), IP당 속도 제한(무차별 대입/DoS 방지), bearer 토큰 기반 인가(접근 제어 결함 방지)
