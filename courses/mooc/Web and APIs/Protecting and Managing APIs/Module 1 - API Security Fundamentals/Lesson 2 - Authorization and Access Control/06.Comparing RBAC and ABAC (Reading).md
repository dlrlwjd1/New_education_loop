# Reading: Comparing RBAC and ABAC — Choosing the Right Access Control Model for Modern APIs (RBAC와 ABAC 비교)

## 개요
- RBAC와 ABAC의 개념·강점·한계를 비교하고 어떤 상황에 어떤 모델을 선택해야 하는지 다루는 5분 분량 읽기자료 — Module 1 "Lesson 2: Authorization and Access Control"의 여섯 번째이자 마지막 항목
- 인가(authorization)는 API 보안의 핵심 부분이며, RBAC와 ABAC는 누가 무엇에 접근할 수 있는지를 규제한다는 목표는 같지만 유연성·복잡성·실제 사용 사례에서 차이가 있음

## 내용

### RBAC(Role-Based Access Control)
- **개념**: 사용자에게 배정된 역할(role)을 기반으로 접근이 부여됨
- **예시**: "Admin" 역할은 사용자를 관리할 수 있고, "Viewer" 역할은 데이터를 읽기만 할 수 있음
- **강점**: 이해·구현이 쉬움 / 직무가 명확히 정의된 조직에서 잘 작동함
- **한계**: 역할이 많이 필요해지면 경직되고 복잡해질 수 있음 / 동적이고 맥락 인식적인 환경에는 이상적이지 않음

### ABAC(Attribute-Based Access Control)
- **개념**: 사용자·리소스·환경·행동 등의 속성(attribute)을 평가해 접근을 결정함
- **예시**: "HR 부서 사용자가 업무 시간에만 급여 데이터에 접근할 수 있다" 같은 정책
- **강점**: 매우 유연하고 맥락 인식적임 / 세밀한(fine-grained) 정책을 지원함
- **한계**: 설계·관리가 더 복잡함 / 잘못된 설정을 피하기 위해 신중한 정책 거버넌스가 필요함

### 올바른 모델 선택하기
- RBAC는 사내 엔터프라이즈 애플리케이션처럼 역할과 책임이 안정적인 곳에 가장 적합함
- ABAC는 시간·위치·기기·부서 등 맥락이 중요하거나, 클라우드 네이티브 애플리케이션·API 같은 동적인 환경에 가장 적합함
- 많은 현대 시스템은 단순함을 위해 RBAC로 시작한 뒤 세밀한 접근을 위해 ABAC 규칙으로 확장하는 하이브리드 접근법을 채택함

## 요약
- RBAC와 ABAC는 경쟁 모델이 아니라 상호 보완적인 모델임 — RBAC는 단순함과 채택 용이성을, ABAC는 유연성과 정밀함을 제공함
- 현대 API에서는 시스템의 복잡성과 보안 요구에 따라 선택하며, 실무에서는 계층적(layered) 또는 하이브리드 접근법이 관리 용이성과 보안 사이의 최선의 균형을 제공하는 경우가 많음
