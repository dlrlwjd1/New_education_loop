# From Device to Dashboard: Measuring Latency End-to-End (장치에서 대시보드까지: 엔드투엔드 지연시간 측정하기)

## 개요
- 데이터가 장치를 떠나는 순간부터 대시보드에 나타나는 순간까지 지연시간(latency)을 엔드투엔드로 측정하는 방법과, 그 측정이 왜 모든 성능 결정의 토대가 되는지를 다루는 4분 13초 분량 영상 — Module 3 "Optimize for Speed: Measuring Latency in Real-Time Pipelines"의 첫 번째 항목

## 내용

### "실시간"은 무엇과 비교한 것인가
- 사람들이 어떤 시스템이 "실시간"이라고 말할 때, 강사는 항상 "무엇과 비교해서 실시간인가?"라는 후속 질문을 던짐
- GPS 장치가 위치 업데이트를 보내면 몇 초 뒤에 지도 위의 점이 움직임 — 그 지연은 작아 보이지만 실제 시스템에서는 그 몇 초가 의사결정, 신뢰, 때로는 안전(safety)까지 좌우함
- 강사의 경험상 팀들이 저지르는 가장 큰 실수는 지연시간이 있다는 것 자체가 아니라, 그 지연시간이 어디서 오는지 모른다는 것임
- 이 영상은 데이터가 장치를 떠나는 순간부터 대시보드에 나타나는 순간까지 지연시간을 엔드투엔드로 측정하는 방법과, 그 측정이 모든 현명한 성능 결정의 토대가 되는 이유를 다룸
- 영상을 마치면 간단한 타임스탬프(timestamp)로 엔드투엔드 지연시간을 측정하고, 실시간 GPS 파이프라인 내부에서 지연이 어디서 발생하는지 식별하고, 그 지연을 해석해서 무엇을 최적화할 가치가 있는지 판단할 수 있게 됨 — 목표는 완벽함이 아니라 시스템을 신뢰할 수 있을 만큼 잘 이해하는 것임

### 지연시간(Latency)의 정의
- 지연시간은 데이터가 생성된 시점과 사용자가 그것을 보는 시점 사이의 시간임
- 이는 처리량(throughput, 시스템을 통과하는 데이터의 양)이나 지터(jitter, 도착 시간이 얼마나 불규칙한지)와는 다른 개념임
- GPS 타임라인에서 지연시간은 여러 단계에서 나타날 수 있음 — 장치가 데이터를 발행할 때, 메시지가 네트워크를 통해 이동할 때, 브로커가 구독자에게 라우팅할 때, 브라우저가 그것을 처리하고 렌더링할 때
- 누군가 "지도가 느리게 느껴진다"고 말할 때, 그들은 특정 구성 요소 하나가 아니라 엔드투엔드 지연시간에 반응하고 있는 것임 — 이것이 전체 경로를 측정하는 것이 중요한 이유임

### Step — 세 지점에 타임스탬프 추가하기
- 강사가 사용하는 방법은 단순하고 신뢰할 수 있음 — 세 지점에 타임스탬프를 추가함:
  1. **발행 시각(publish time)**: GPS 장치가 메시지를 보낸 시각
  2. **수신 시각(receive time)**: 브라우저가 그것을 받은 시각
  3. **렌더링 시각(render time)**: 마커가 실제로 지도 위에서 움직인 시각
- `Date.now()`처럼 기본적인 로깅만으로도 전송 지연시간(transmission latency), 렌더링 지연시간(render latency), 총 엔드투엔드 지연시간을 계산할 수 있음
- 이는 특별한 도구를 필요로 하지 않음 — 필요한 것은 규율(discipline)과 호기심(curiosity)임. 숫자를 보게 되면 시스템은 더 이상 신비롭게 느껴지지 않음

### 생각해볼 질문
- 자신의 파이프라인에서 가장 큰 지연이 어디서 발생할 것으로 예상하는가, 그리고 왜인가? 이 성찰이 중요한 이유는 증상에 반응하는 것에서 실제로 검증할 수 있는 가설을 세우는 것으로 관점을 바꿔주기 때문임

### 지연시간이 보이면 최적화는 추측이 아니라 추론이 된다
- 지연시간이 눈에 보이게 되면 최적화는 추측(guesswork)이 아니라 추론(reasoning)이 됨
- 팀들이 흔히 실험하는 레버(lever)들: GPS 발행 빈도 스로틀링(throttling), UI가 다시 렌더링하는 빈도 줄이기, MQTT QoS(서비스 품질) 레벨 조정하기, 지도 렌더링 로직 단순화하기
- 모든 변경에는 트레이드오프가 따름 — 지연시간을 낮추면 비용이 늘어날 수 있고, 더 매끄러운 시각 효과는 정밀도를 낮출 수 있음
- 실제 시스템에서는 "충분히 빠른 것(fast enough)"이 "가능한 한 가장 빠른 것(as fast as possible)"보다 나을 때가 많음 — 중요한 것은 자신의 시스템이 왜 그렇게 동작하는지를 아는 것임

### 마무리
- 지연시간은 조용한 지표(quiet metric)이지만 사용자가 경험하는 모든 것을 형성함. 이를 엔드투엔드로 측정하면 무엇이 실제로 느린지, 무엇이 받아들일 만한지, 무엇을 최적화할 가치가 있는지에 대한 명확함을 얻게 됨
- 실시간 시스템은 완벽해서가 아니라 이해되고 있기 때문에 신뢰를 얻음 — 이 관점을 이용해 앞으로 마주치는 어떤 시스템에서든 "실시간"이 진짜로 무엇을 의미하는지 질문하고, 성능을 추측이 아니라 근거에 기반한 판단(evidence-based judgment)으로 다루기

## 요약
- 발행 시각·수신 시각·렌더링 시각이라는 세 타임스탬프로 GPS 파이프라인의 전송 지연시간·렌더링 지연시간·총 엔드투엔드 지연시간을 측정하면, 지연이 어디서 발생하는지 파악해서 발행 빈도 스로틀링, 재렌더링 빈도 조정, MQTT QoS 조정, 렌더링 로직 단순화 같은 최적화를 추측이 아닌 근거에 기반해 선택할 수 있게 됨
