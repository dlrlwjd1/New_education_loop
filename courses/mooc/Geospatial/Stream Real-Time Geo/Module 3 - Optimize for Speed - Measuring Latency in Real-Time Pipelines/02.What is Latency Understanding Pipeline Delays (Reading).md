# What is Latency? Understanding Pipeline Delays (지연시간이란 무엇인가: 파이프라인 지연 이해하기)

## 개요
- 지연시간(latency)이 처리량(throughput)·지터(jitter)와 어떻게 다른지, GPS 스트리밍 파이프라인의 어느 단계에서 지연이 발생하는지, 그리고 타임스탬프 기반으로 어떻게 측정하는지를 다루는 8분 분량 읽기자료(실제로는 5분 51초짜리 내레이션 영상 플레이어로 표시됨) — Module 3 "Optimize for Speed: Measuring Latency in Real-Time Pipelines"의 두 번째 항목

## 내용

### 서론 — 실시간 시스템에서 지연시간이 왜 중요한가
- 실시간 시스템에서 지연시간은 의사결정의 품질을 직접 좌우함 — 5초 늦게 업데이트되는 GPS 대시보드는 장기 계획에는 괜찮을 수 있지만 디스패치(dispatch), 응급 대응, 충돌 회피(collision avoidance)에는 받아들일 수 없음
- 사용자가 "지도가 느리게 느껴진다"고 말할 때, 그 표현을 쓰지 않더라도 그들은 보통 지연시간에 반응하고 있는 것임
- 지연시간은 단일 원인으로 발생하는 경우가 드묾 — 오히려 데이터 생성부터 메시지 전달, 처리, 시각화까지 파이프라인 전반에서 작은 지연들이 누적됨
- 이 읽기자료는 지연시간이 실제로 무엇인지, 관련 개념들과 어떻게 다른지, GPS 스트리밍 파이프라인의 어디에서 나타나는지, 그리고 가벼운 브라우저 기반 기법으로 어떻게 측정할 수 있는지를 설명함
- 목표는 지연시간을 정의하는 것을 넘어, 그것을 추론하고 측정하고 실제 시스템에서 근거 있는 트레이드오프를 만들도록 돕는 것임

### 핵심 개념 — 지연시간, 처리량, 지터
- **지연시간(Latency)**: 단일 데이터 지점이 소스에서 목적지까지 이동하는 데 걸리는 시간. GPS 시스템에서는 보통 위치가 기록된 시점과 지도 위에 나타나는 시점 사이의 시간임
- **처리량(Throughput)**: 속도가 아니라 양(volume)을 나타냄 — 시스템이 초당 처리할 수 있는 메시지 수를 측정함. 시스템이 초당 수천 개의 메시지를 처리할 수 있어도 각 메시지가 나타나는 데 몇 초씩 걸린다면 여전히 느리게 느껴질 수 있음
- **지터(Jitter)**: 지연시간의 변동성(variability)을 가리킴. 평균 지연이 낮아도 지연이 불규칙하면 대시보드가 불안정하게 느껴짐 — 마커가 튀거나, 멈추거나, 불균등하게 도착함. 사람 사용자에게는 원시 지연시간보다 지터가 더 중요한 경우가 많음
- 이 차이를 이해하면 팀이 진짜 문제를 진단하는 데 도움이 됨 — 시스템이 느린가? 과부하 상태인가? 아니면 예측할 수 없는가?

### GPS 스트리밍 파이프라인에서 지연시간이 나타나는 곳
- 실시간 GPS 파이프라인에서 지연시간은 누적됨. 지연은 여러 단계에서 나타날 수 있음:
  - **장치 또는 시뮬레이터 지연**: GPS 데이터를 생성하고 발행하는 데 필요한 시간
  - **발행-구독 지연(MQTT)**: 브로커를 거쳐 구독자에게 메시지를 라우팅하는 데 걸리는 시간
  - **네트워크 지연시간**: 네트워크 상태, 거리, 혼잡으로 인한 지연
  - **클라이언트 처리 지연**: 데이터를 파싱·검증하고 렌더링을 준비하는 데 필요한 시간
  - **시각화 지연**: 브라우저가 마커, 경로, UI 상태를 업데이트하는 데 필요한 시간
- 개별적으로 보면 각 지연은 미미해 보일 수 있지만, 합쳐지면 "실시간" 시스템을 눈에 띄게 뒤처진 것처럼 느껴지게 만들 수 있음

### MQTT 기반 시스템에서의 지연시간 트레이드오프
- MQTT는 오버헤드가 적고 이벤트 기반(event-driven)인 메시징을 위해 설계되어 GPS 스트리밍에 적합함. 하지만 설정 선택은 여전히 지연시간에 영향을 미침
- 핵심 요인들:
  - **서비스 품질(Quality of Service, QoS)**: 더 높은 QoS 레벨은 전달 보장을 높이지만 확인 응답(acknowledgment) 오버헤드를 추가함
  - **메시지 크기**: 더 크거나 복잡한 페이로드는 전송과 파싱에 더 오래 걸림
  - **브로커 부하**: 공유되거나 과부하된 브로커는 큐잉 지연을 유발함
- 실제로 팀은 맥락에 따라 QoS와 페이로드 구조를 선택함 — 예를 들어 차량 추적은 더 빠른 업데이트를 위해 간헐적인 메시지 손실을 감수할 수 있지만, 안전이 중요한 시스템은 속도보다 신뢰성을 우선할 수 있음
- 이는 "맞다 대 틀리다"의 문제가 아니라 트레이드오프임

### 브라우저 기반 지도에서의 지연시간
- 데이터가 빠르게 도착해도 시각화 과정에서 지연이 생길 수 있음
- 흔한 원인: 마커를 업데이트하지 않고 다시 렌더링하기, 들어오는 메시지마다 UI 업데이트를 유발하기, 과도한 애니메이션이나 강제적인 지도 리센터링, 메인 스레드를 막는 긴 JavaScript 실행
- 최신 브라우저 개발자 도구는 이런 문제들을 관찰 가능하게 만들어줌 — 성능(Performance) 패널과 타임라인 뷰는 실시간 업데이트 중 렌더링 시간, 스크립팅 지연, 프레임 드롭을 보여줌. 이런 가시성은 데이터 전달이 빨라도 존재할 수 있는 "UI 지연시간"을 진단하는 데 필수적임

### 타임스탬프로 엔드투엔드 지연시간 측정하기
- 지연시간을 이해하는 가장 신뢰할 수 있는 방법은 명시적으로 측정하는 것임
- 단순하고 효과적인 접근은 타임스탬프를 찍는 것임:
  - GPS 메시지가 발행될 때 타임스탬프를 추가함
  - 클라이언트가 메시지를 수신한 시각을 기록함
  - 지도가 업데이트된 시각을 기록함
- 이 타임스탬프들을 비교하면 다음이 드러남: 지연이 어디서 발생하는지, 어느 단계가 지연시간에 가장 크게 기여하는지, 최적화가 실제로 성능을 개선하는지
- 이는 "대시보드가 느리게 느껴진다" 같은 모호한 불만을 측정 가능하고 실행 가능한 데이터로 바꿔줌

### "적절한(Acceptable)" 지연시간은 왜 맥락에 따라 다른가
- 보편적인 지연시간 목표는 존재하지 않음
- 물류(logistics) 대시보드는 2~5초의 지연을 감수할 수 있음. 승차 공유(ride-share) 앱은 1초 미만의 응답성을 요구할 수 있음. 응급 대응 시스템은 흔히 거의 즉각적인 업데이트를 요구함
- 좋은 시스템 설계는 특정 사용 사례에 대해 "충분히 빠르다(fast enough)"는 것이 무엇을 의미하는지 정의하는 데서 시작하고, 그다음 시스템이 그 기대를 일관되게 충족하는지 검증하는 것으로 이어짐
- 최적화는 모든 지연을 제거하는 것이 아니라, 속도·신뢰성·명확성·비용의 균형을 맞추는 근거 있는 결정을 내리는 것임

### 요약(원문)
- 지연시간은 수집(ingestion), 메시징, 처리, 시각화가 함께 형성하는 시스템 전체의 속성임. 지연이 어디서 시작되고 어떻게 상호작용하는지 이해하면 개발자와 분석가는 병목을 진단하고, 트레이드오프를 평가하고, 실시간 시스템을 의도적으로 개선할 수 있음
- 지연시간을 가정하지 않고 측정하는 것은 사용자가 실제로 신뢰할 수 있는 GPS, IoT, 스트리밍 대시보드를 만들기 위한 기초적인 역량임
