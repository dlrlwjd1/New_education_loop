# Termination Event

## 개요

- **Termination event(종료 이벤트)** — **실행 중인 모든 activity를 종료**시킨다
- 동작: **프로세스와 그 하위 프로세스의 모든 토큰을 소비(consumes)** 한다
- **End event 변형 하나만 존재**한다
- 이 강의는 **"같은 것을 표현하는 여러 방법"** 이라는 중요한 교훈도 함께 준다

## 내용

### 개념

> **이 event는 기본적으로 실행 중인 모든 activity를 종료시킨다. 다시 말해 프로세스와 그 하위 프로세스의 모든 토큰을 소비한다.**

### 비교 사례 — Deluxe에서 고객이 주문을 취소하는 상황

**방법 A — event sub-process를 쓰는 원래 방식**

1. **경리부와 창고가 각자의 일을 하는 동안 고객이 주문을 취소**한다
2. 이것이 **event-based sub-process의 message start event를 촉발**한다
3. 추가로 **송장 처리 하위 프로세스에 부착된 conditional event가 촉발되어 해당 하위 프로세스를 취소**한다
4. → **두 개의 전용 event가 각각 두 토큰의 취소를 담당**한다
5. **두 토큰이 소비되고, 두 하위 프로세스의 원래(표준) 흐름이 종료**된다
6. → **예외 흐름이 촉발**되어 **고객에게 취소 확인이 발송**되고 **CRM 시스템에 케이스가 문서화**된다
7. **케이스 종료**

**방법 B — termination event를 쓰는 방식**

1. **취소를 처리하던 event sub-process를 제거**하고
2. **취소를 처리하는 task들이 뒤따르는 고전적인 부착 interrupting message event로 대체**한다
3. **그 끝에 termination event를 놓는다**
4. > **이 구성에서는 송장 처리 하위 프로세스의 canceling message event도 제거할 수 있다**

**동작 과정**

1. 창고와 경리부에서 평상시대로 업무가 진행된다
2. **고객이 주문을 취소하면 부착된 message event가 촉발**된다
3. > **이 부착 event가 촉발되는 것만으로 이미 하위 프로세스 자체의 토큰이 소비된다.** 그 토큰은 이미 사라졌다
4. 취소는 **세 개의 task로 처리**된다
5. **여기서 취소 흐름에 `close case(케이스 종료)` task를 삽입했다**
6. **이제 termination event가 촉발되어 남은 모든 토큰이 죽는다.** 즉 **이 프로세스 인스턴스가 종료된다**

> **그래서 취소 흐름 안에서 케이스 종료를 처리해야 한다. 그렇지 않으면 표준 흐름 끝에 있는 close case에 결코 도달하지 못하기 때문이다.**

### 매우 중요한 교훈 — 같은 것을 표현하는 방법은 여러 가지다

> **이 흐름이 event sub-process와 부착 event를 조합한 원래 방식보다 더 쉽거나 직관적인지는 논쟁의 여지가 있다.**
>
> **일반적으로 나는 이것이 BPMN에서 때때로 정확히 같은 것을 표현하는 여러 선택지가 있다는 것을 보여주는 완벽한 예라고 말하겠다.**
>
> **이런 경우에는 여러분과 프로세스 독자에게 가장 잘 맞는 것을 시도해 보면 된다.**
>
> **프로세스는 정확하기만 해서는 안 되고, 읽을 수 있고 표현력이 있어야 한다는 것을 기억하라. 프로세스를 보는 사람이 누구든 쉽게 이해할 수 있어야 한다.**
>
> **여러 모델링 선택지를 가질 여유가 있다면, 프로세스 소비자에게 최고의 가독성을 제공한다고 생각하는 것을 선택하겠다.**

### 변형 — End event 하나뿐

> **termination event에는 end event만 있다. 이 event의 발상 자체가 모든 토큰을 소비해 프로세스를 즉시 끝내는 것이기 때문이다.**

## 예시

```text
방법 A — event sub-process 방식

┌─ 경리: 송장 처리 ──┐    ┌─ 창고: 배송 ──────┐
│ [송장 생성]        │    │ [재고 확인]       │
│ [송장 발송]        │    │ [포장·발송]       │
└──────(◇ 부착)─────┘    └───────────────────┘
        ↑ 취소 시 이 하위 프로세스 취소
  ┌─ Event sub-process (취소 처리) ─────┐
  │ (✉ 주문 취소) → [취소 확인 발송]     │
  │              → [CRM 문서화] → (◎)   │
  └─────────────────────────────────────┘
  두 개의 전용 event가 각각 토큰을 취소


방법 B — termination event 방식

┌──────────────────────────────────────────────┐
│  ┌─ 경리 ──┐   ┌─ 창고 ──┐                   │
│  │[송장생성]│   │[재고확인]│                   │
│  │[송장발송]│   │[포장발송]│                   │
│  └─────────┘   └─────────┘                   │
│                                              │
└──────────────(✉ 부착 interrupting)───────────┘
                    ↓ 고객이 주문 취소
             [취소 확인 발송]
                    ↓
             [CRM 문서화]
                    ↓
             [케이스 종료]  ← 여기에 반드시 넣어야 한다
                    ↓
             (⊗ Termination event)
                    ↓
        모든 남은 토큰이 죽는다
        프로세스 인스턴스 즉시 종료

  ※ 송장 처리 하위 프로세스의 canceling event는 제거 가능
  ※ close case를 취소 흐름에 넣지 않으면
     표준 흐름의 close case에 영원히 도달하지 못한다


Termination event 변형 — End 하나뿐

┌─ START ─────────────────────────────────────────┐
│ ✗ 모두 불가                                      │
└─────────────────────────────────────────────────┘
┌─ INTERMEDIATE ──────────────────────────────────┐
│ ✗ 모두 불가                                      │
└─────────────────────────────────────────────────┘
┌─ END ───────────────────────────────────────────┐
│ ✓ End termination event  모든 토큰 소비 후 즉시 종료│
└─────────────────────────────────────────────────┘
```

## 요약

- **Termination event는 프로세스와 하위 프로세스의 모든 토큰을 소비해 즉시 종료**시킨다
- **End event 변형 하나만 존재**한다
- **주의점**: termination이 남은 토큰을 다 죽이므로, **표준 흐름 끝에 있던 마무리 task(케이스 종료 등)를 예외 흐름 안에도 넣어야 한다**
- **가장 중요한 교훈**: **BPMN에서 같은 것을 표현하는 방법은 여러 가지다.** 정확성만이 아니라 **독자의 가독성을 기준으로** 선택한다
