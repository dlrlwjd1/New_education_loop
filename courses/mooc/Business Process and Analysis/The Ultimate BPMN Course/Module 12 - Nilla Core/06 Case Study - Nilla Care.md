# Case Study – Nilla Care

## 개요

- 소형 병원 **Nilla Care**의 **통제 테스트(control testing)** 프로세스
- 배경: 의료 부문에서 **보안이 최우선**이므로 정교한 risk management를 적용한다
- 이번 분기에 **통제 10개를 테스트**하며, **통제마다 다른 결말**을 보여준다
- 핵심 학습: **event sub-process 취소와 attached event 취소의 결정적 차이**

## 내용

### 상황

Nilla Care는 **병원 정전(energy blackout)** 같은 리스크와 실패를 최소화하기 위해 **정교한 통제(controls)** 를 구현했다. 이 통제들은 **제대로 작동하는지 정기적으로 점검·테스트**된다.

**이번 분기에는 총 10개의 통제를 테스트**한다.

### 프로세스 구조

**1. 범위와 파라미터 정의** — 통제 평가의 scope와 parameter를 먼저 정한다

> **작년 통제 보고서를 참고해, 작년에 문제가 있었던 통제가 이번에도 다시 테스트되도록 보장한다.**

**2. Multi-instance sub-process**

> **각 통제의 실제 테스트는 multi-instance sub-process로 표현된다. 여러 통제를 테스트할 것이기 때문이다 — 더 정확히는 이번 분기에 10개를 테스트한다.**

**3. 통제 하나당 두 단계의 테스트**

| 단계 | 확인 내용 | 소화기 비유 |
|---|---|---|
| **Control design 평가** | **통제가 애초에 리스크를 완화하도록 올바르게 설계되었는가** | **소화기 종류가 발생할 수 있는 화재 유형에 맞지 않으면 control design이 불충분한 것** |
| **Operational performance 확인** | 통제가 **실제로 작동하는가** | **소화기가 작동 가능하고, 필요할 때 효과적으로 사용할 수 있는 위치에 놓여 있는가** |

### 통제별 시나리오 — 네 가지 결말

**통제 1~6 — 정상 통과**

두 테스트를 모두 통과 → **passed로 표시** → **해당 sub-process 인스턴스 완료**

**통제 7 — 실패 후 시정 조치 (throwing escalation event)**

1. 설계 테스트와 운영 성능 확인을 수행한다
2. **둘 중 하나가 실패**하면 → **그 통제에 대한 시정 조치(remediation measures)를 정의**해 나중에 고칠 수 있게 한다
3. **throwing escalation event가 시정 조치를 구현하는 event sub-process를 촉발**한다
4. **두 가지가 병렬로 일어난다**
   - **메인 sub-process**: 이 통제에 대한 **전용 통제 테스트 보고서를 작성**
   - **Event sub-process**: **통제의 시정 조치를 실제로 구현**
5. 이후 **시정 조치를 문서화**한다 → 통제 7 테스트 완료

**통제 8 — 마감 기한 초과 (interrupting timer event sub-process)**

1. **통제 설계를 테스트하는데, 설계를 테스트할 수 있는 사람들이 모두 병가나 휴가 중**이라 **task가 심하게 지연**된다
2. **각 통제 테스트에는 마감 기한이 있고, 통제 8에서 그 기한이 막 지났다**
3. → **기한 경과를 처리하는 cancellation event sub-process가 촉발**된다
4. > **이 event sub-process의 촉발 timer event는 실선(solid)이다. 즉 부모 sub-process의 현재 인스턴스를 중단시킨다.** 다시 말해 **설계 테스트 task의 토큰을 죽인다**
5. 팀은 **기한 초과에 대한 사유를 제출**하고
6. **그 통제를 다음 테스트 라운드로 플래그(flag)** 한다 → 통제 8 완료

**통제 9~10 — 시스템 장애 (attached error event)**

1. **통제 설계 테스트는 괜찮아 보인다**
2. **운영 성능 테스트 중 테스트 결과를 문서화하는 IT 시스템이 실패**한다
3. → **부착된 error event가 촉발**된다

> **이것은 테스트 sub-process의 현재 인스턴스(토큰)를 취소할 뿐 아니라, sub-process의 앞으로의 모든 인스턴스도 중단시킨다.**

### 결정적 차이 — Event sub-process 취소 vs Attached event 취소

> **이것이 event sub-process를 통한 취소와의 핵심 차이다.**
>
> - **Event sub-process를 통한 취소** → **현재 인스턴스만 취소**했다 (통제 8의 경우)
> - **Attached event** → **sub-process 전체가 취소**된다 (통제 9~10의 경우)
>
> **이 use case에서는 완벽하게 말이 된다. 시스템 전체가 실패했으므로 이후의 모든 통제도 영향을 받기 때문이다.**

4. → **부모 프로세스의 토큰이 대체 경로로 라우팅**되어 **수동 통제 테스트(manual control testing)를 개시**한다

> **이것은 통제 9와 10에 해당한다. 이제 multi-instance sub-process를 빠져나와 전역 범위(global scope)를 보고 있기 때문이다.**

**마무리 — 전역 보고서**

수동 테스트 후 **중앙 컴플라이언스 팀이 전역 통제 보고서를 작성**한다.

> **여기서도 전체 통제 테스트를 보고 있다. 즉 통제 1번부터 10번까지의 모든 결과가 이 보고서에 반영된다.**

### 왜 sub-process가 유용한가 — 핵심 통찰

> **이것이 sub-process가 왜 그렇게 유용한지 보여주는 아주 좋은 예다. Tofisu의 판매 프로세스와 마찬가지로, 여기서도 10번 실행하는 통제 task가 있고, 그다음에 단 한 번만 실행하는 전역 task가 있다. 이것은 sub-process 인스턴스로 완벽하게 처리된다.**

```text
        ↓

│                                                         │
│  (○) → [control design 평가]                            │
│            ↓                                            │
│        [operational performance 확인]                   │
│            ↓                                            │
│        ◇ 통과했는가?                                     │
│         ├─ yes → [passed 표시] → (◎)      ← 통제 1~6    │
│         │                                               │
│         └─ no  → [시정 조치 정의]                         │
│                      ↓                                  │
│                 (⇗ throwing escalation) ──┐  ← 통제 7    │
│                      ↓                    │             │
│                 [전용 보고서 작성]          │  병렬        │
│                      ↓                    ↓             │
│                    (◎)         ┌─ Event sub-process ─┐  │
│                                │ [시정 조치 구현]      │  │
│                                │ [시정 조치 문서화]    │  │
│                                └─────────────────────┘  │
│                                                         │
│  ┌─ Event sub-process (기한 초과, 실선 = 취소형) ────┐    │
│  │ (⏱ 실선) → [사유 제출] → [다음 라운드로 플래그]   │    │  ← 통제 8

│  └──────────────────────────────────────────────────┘    │
└────────────────────(⚡ 부착 error event)─────────────────┘
                          ↑ IT 시스템 장애            ← 통제 9~10
                          │ sub-process 전체를 취소 ✗✗
                          ↓
                  [수동 통제 테스트]  ← 전역 범위로 복귀
                          ↓
                  [전역 통제 보고서 작성]  ← 통제 1~10 전체 반영 (한 번만)
                          ↓
                       (◎ 완료)


★ 핵심 차이 ★

Event sub-process의 취소형 (실선 start event)
  → 현재 인스턴스 1개만 취소        (통제 8: 그 통제만 중단)

Sub-process에 부착된 event
  → sub-process 전체가 취소         (통제 9~10: 남은 인스턴스 전부 중단)


Sub-process가 유용한 이유

10번 반복하는 task  ─┐
                     ├─ multi-instance sub-process가 분리해 준다
1번만 하는 전역 task ─┘

  범위 정의       → 1번
  통제별 테스트   → 10번  ← sub-process 안
  전역 보고서     → 1번
```

## 요약

- **Multi-instance sub-process가 "N번 반복하는 작업"과 "한 번만 하는 전역 작업"을 깔끔하게 분리**한다
- **Throwing escalation event**로 시정 조치를 **병렬 처리**한다 (본 작업은 계속)
- **Event sub-process의 실선 timer event**는 **현재 인스턴스만 취소**한다
- **Sub-process에 부착된 error event는 남은 인스턴스 전체를 취소**한다 — **이것이 두 취소 방식의 결정적 차이**다
- 시스템 전체 장애처럼 **이후 작업 전부가 영향받는 상황**에서는 **attached event로 전체를 취소**하는 것이 맞다
