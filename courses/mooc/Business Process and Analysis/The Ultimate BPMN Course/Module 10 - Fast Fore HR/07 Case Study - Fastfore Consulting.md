# Case Study – Fastfore Consulting

## 개요

- 실전 case study: 빠르게 성장하는 컨설팅 회사 **Fast Fore**의 **채용(hiring) 프로세스**
- 의뢰인: **HR 총괄 Jessica**
- 핵심 주제: **BPMN 다이어그램이 곧 시스템 요구사항이 된다**

## 내용

### 상황

Fast Fore의 채용 프로세스는 **매우 수동적이고 혼란을 많이 일으킨다.** 빠르게 성장하려는 회사에게는 나쁜 소식이다. 그래서 HR 총괄 **Jessica는 모든 지원서 처리를 지원하는 자동화된 workflow**를 원한다.

> **하지만 무엇을 자동화하기 전에, 비즈니스 요구사항이 실제로 무엇인지 이해해야 한다.**

Jessica는 이미 BPMN 마스터클래스를 수료했으므로 **자신이 구상하는 프로세스를 직접 설계하고 모델링**했다.

### 성공 경로(happy path)

1. **지원서가 접수되면** HR 부서가 먼저 살펴보고 **지원자가 흥미로운지 판단**한다
2. 흥미롭다면 **지원한 부서의 관리자가 살펴보고 면접에 초대**한다
3. 적합하다면 HR 부서가 **면접 일정을 잡고**
4. **초대장을 발송**하고
5. **면접을 진행**하고
6. 마지막으로 **후보자의 면접을 평가하고 결정**을 내린다
7. 긍정적이면 **HR이 지원자에게 오퍼를 보낸다**

### Additional participant의 사용

> **위 세 개 task에서 부서 관리자가 additional participant로 참여한다.**

부서 관리자는 **당연히 면접에 참여**하므로

- **면접 일정 수립** — **자문(consulted)** 을 받는다
- **면접 진행** — **책임을 공유(shared responsibility)** 한다
- **채용 여부 결정** — **책임을 공유**한다

### 거절 경로

모든 지원자를 채용할 수는 없다. 거절은 **세 지점**에서 일어난다.

1. **HR이 이력서와 지원서를 검토한 직후 거절**
2. **두 번째 단계에서 관리자가 지원자에 대해 부정적으로 결정**
3. **면접 후 관리자와 HR이 공동으로 채용하지 않기로 결정**

### 여기서부터가 핵심 — 자동화 엔지니어의 관점

> Jessica가 애초에 BPMN 프로세스를 만든 **바로 그 이유는 자동화하고 싶기 때문**이다. 이제 **여러분이 이 프로세스의 자동화된 workflow를 구현할 책임이 있는 automation engineer**라고 상상해 보자.
>
> **BPMN에서 자동화를 향한 첫 단계는 task type을 적용하는 것이다.**

### Task type을 붙이면 시스템 요구사항이 보인다

**훈련된 눈은 프로세스만 보고도 한눈에 다음을 알아본다.**

**1. Public form 하나가 필요하다** — 지원자가 인터넷으로 지원서를 제출할 수 있도록

**2. User form 세 개가 필요하다** — **세 개의 user task**를 통해 직접 드러난다

> **이 세 개의 user form은 거의 같은 일을 하므로 모두 매우 비슷하게 생길 것이다. 기본적으로 두 개의 필드로 구성된다.**
>
> - **첫 번째 필드**: 지원서와 이력서를 **zip 파일**로 담아, HR 관리자나 부서 관리자가 **다운로드하거나 폼에서 직접 열람**할 수 있게 한다
> - **두 번째 필드**: **버튼 두 개** — **수락(accept)** 과 **거절(reject)**

**3. 폼의 버튼이 곧 다이어그램의 분기다**

> **방금 그린 단순한 폼을 BPMN 다이어그램에, 더 정확히는 이 user task에 직접 연결할 수 있다.**
>
> - **사용자가 reject 버튼을 누르면** 프로세스는 **이쪽 경로**를 따른다
> - **accept를 클릭하면** **저쪽으로** 간다

> **이것이 "task type이 붙은 프로세스 다이어그램은 이미 고수준의 시스템 요구사항을 제공한다"는 말의 의미다. 다시 말해 프로세스 다이어그램에서 최소 기능 사용자 폼(minimal viable user forms)이 어떻게 생겨야 하는지 직접 볼 수 있다.**

### BPMN이 조직의 사일로를 잇는다

> **프로세스가 어떻게 돌아가야 하는지는 알지만 기업 시스템을 설정하고 구성하는 것에 대해서는 전혀 모르는 모든 비즈니스 사용자를 상상해 보라. 그들은 그냥 BPMN 다이어그램을 만들면 되고, 양쪽 모두 서로를 완벽하게 이해할 수 있다.**
>
> **짧게 말해 BPMN으로 조직의 사일로(silos)를 실제로 이을 수 있다.**

**추가로 보이는 것들**

- **자동 발송 이메일이 필요하다** — 그리고 **프로세스의 정확히 어느 지점에서, 누구에게** 보내야 하는지도 보인다
- **면접 일정 수립과 면접 진행은 수동으로 해야 한다**는 것도 workflow 엔지니어에게 바로 보인다

### 한 걸음 더 — 요구사항을 넘어서기

> **평범한 엔지니어라면 Jessica가 설계한 프로세스에 정의된 것을 그대로 하면 된다. 하지만 automation pro가 되어 가는 중이라면 거기서 만족하지 않고, Jessica가 정의한 것을 넘어 진정한 end-to-end 관점에서 본다.**

**개선안**

- **첫 두 user form은 그대로 둔다** — HR과 부서 관리자가 이력서와 지원서를 폼에서 검토하는 것은 이미 완벽하다
- **면접 일정 수립을 service task로 바꾼다**
  - Fast Fore는 **Google을 쓰므로**, service task가 **Google Calendar API로 HR 관리자와 부서 관리자 양쪽의 빈 시간을 조회해 자동으로 면접 일정을 잡는다**
  - 그다음 **부서 관리자와 HR 관리자가 자동 생성된 초대를 수락하거나 거절하는 폼**만 있으면 된다
  - **둘 다 수락하면 면접 일정이 담긴 자동 이메일이 지원자에게 발송**된다
  - > **이것으로 첫 번째 manual task를 제거했다**
- **초대 발송 후에는 event based gateway를 쓴다**
  - **초대를 보낸 뒤 우리 통제 밖의 세 가지 일이 일어날 수 있기 때문**이다
  - 지원자가 제안된 면접 시간을 수락한다고 하면, HR과 부서 관리자가 이전처럼 면접을 진행하고
  - 결과에 따라 **오퍼 이메일** 또는 **자동 거절 이메일**이 발송된다

> **이로써 Jessica의 기대를 초과 달성했고, 바쁜 부서 관리자들의 캘린더를 뒤져 빈 시간을 찾는 일에서 그를 해방시켰다. 사소해 보일 수 있지만, 하루에 다섯 번씩 해야 한다면 자동화되는 작은 단계 하나하나가 반갑다.**

### 마무리 — Task type을 언제 쓸 것인가

> **Task type은 방금 본 것처럼 엔지니어링 요구사항을 정의하는 데 매우 유용하다. 하지만 비기술적 프로세스에는 보통 빈 task(blank task)로 충분하다.**
>
> **비기술적 프로세스에 적용하면 안 된다는 뜻은 아니다. 항상 추가 정보를 더해 주므로 해가 되지는 않는다. 다만 프로세스를 자동화할 때 가장 큰 가치를 발휘한다.**

## 예시

```text
Fast Fore 채용 프로세스 — Jessica의 원안

(✉ 지원서 접수)
      ↓
[이력서 검토] (User task)  ─ 거절 → (◎ 거절 통보)
      ↓ 흥미로움
[관리자 검토] (User task)  ─ 거절 → (◎ 거절 통보)
      ↓ 적합
[면접 일정 수립] (Manual)  ⬭ 부서 관리자 (Consulted)
      ↓
[초대장 발송] (Send task)
      ↓
[면접 진행] (Manual)       ⬭ 부서 관리자 (Responsible 공유)
      ↓
[면접 평가·결정] (User)     ⬭ 부서 관리자 (Responsible 공유)
      ↓ 긍정   └─ 부정 → (◎ 거절 통보)
[오퍼 발송] (Send task)
      ↓
   (◎ 채용)


다이어그램 → 시스템 요구사항 (자동으로 읽힌다)

  Public form 1개    ← 지원서 접수 (외부 제출)
  User form 3개      ← user task 3개
     각 폼 = [zip 파일 열람] + [수락] [거절] 버튼
     버튼 = 다이어그램의 분기
  자동 이메일         ← send task 위치가 곧 발송 시점
  수동 작업 식별      ← manual task = 자동화 후보


개선안 — 자동화 잠재력을 끝까지 활용

[면접 일정 수립] Manual  →  Service task
                            Google Calendar API로
                            양쪽 빈 시간 조회 후 자동 배정
                                 ↓
                            [초대 수락/거절 폼] (User task)
                                 ↓ 둘 다 수락
                            자동 이메일 발송
                                 ↓
                                 ⬡ ← event based gateway
                            (통제 밖의 세 가지 상황)
```

## 요약

- **자동화하기 전에 as-is 프로세스를 먼저 이해해야 한다** — Jessica가 BPMN을 먼저 그린 이유
- **task type을 붙이면 다이어그램이 곧 고수준 시스템 요구사항이 된다**
  - **user task 개수 = 필요한 user form 개수**
  - **폼의 버튼 = 다이어그램의 분기**
  - **send task 위치 = 자동 이메일 발송 시점과 대상**
  - **manual task = 자동화 후보**
- **BPMN이 비즈니스와 IT의 사일로를 잇는다** — 비즈니스 사용자는 다이어그램만 그리면 엔지니어가 이해한다
- **좋은 엔지니어는 주어진 요구사항을 그대로 구현하고, 뛰어난 엔지니어는 end-to-end 관점에서 manual task를 자동화 기회로 본다**
- **Task type의 가치는 자동화 맥락에서 가장 크다.** 비기술적 프로세스에는 빈 task로 충분하다
