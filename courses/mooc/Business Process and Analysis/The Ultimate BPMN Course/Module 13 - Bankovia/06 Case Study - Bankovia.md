# Case Study – Bankovia

## 개요

- 전통적이고 구식인 소매 은행 **Bankovia**의 **모바일 송금 프로세스**
- **네 가지 시나리오**를 모두 따라가며 이 코스에서 배운 event를 총동원한다
- **Transaction의 세 가지 상태**(succeeded · canceled · hazard)가 실제로 어떻게 구현되는지 보여주는 사례

## 내용

### 상황

Bankovia는 **프로세스에 관한 한 종이 전용(paper only) 사고방식**을 가진 은행이다. 하지만 시간이 지나며 **가장 충성스러운 고객들조차 점점 더 디지털 제품을 요구**한다.

경영진은 **고객이 지출을 추적하고 계좌를 관리할 수 있는 앱을 만들기로** 결정한다. 이 앱은 **Bankovia의 내부 거래 관리 시스템(transaction management system)에 크게 의존**하며, 그것이 사실상 **앱의 백엔드 역할**을 한다.

### 프로세스 공통 시작부

1. **사용자가 거래에 필요한 모든 데이터를 입력**한다 — 수취인의 이름, 계좌번호, 금액 등
2. **모든 필수 항목이 채워졌는지 간단히 확인**한다
3. **거래 관리 시스템이 넘겨받아 제공된 IBAN이 유효한지 검증**한다
4. **이후 두 가지가 병렬로 일어난다**
   - **거래 인증을 위해 사용자에게 SMS 번호(TAN) 발송**
   - **사기 확인(fraud check) 하위 프로세스 촉발**

### Fraud check 하위 프로세스 — task type의 실제 적용

| 순서 | Task | Task type | 이유 |
|---|---|---|---|
| 1 | **사용자/고객 메타데이터의 이상 징후 확인** | **Script task** | **모든 데이터가 내부적으로 사용 가능**하므로 script task로 처리 가능 |
| 2 | **수취인 계좌의 신뢰도 확인** | **Service task** | **API 호출이 필요**하다. **수취인 계좌가 Bankovia 인프라 밖에 있을 수 있어 다른 은행에 핑을 보내야** 한다 |
| 3 | **해당 거래를 신고된 모든 사기 사례와 대조** | — | 이상 징후 확인 |

---

### 시나리오 1 — 사기 거래 (escalation event + termination event)

1. **테스트 중 하나 이상이 실패**하면 토큰이 아래로 향하고 **하위 프로세스가 escalation event로 종료**된다
2. 이 **end event가 대응하는 부착 escalation event를 촉발**해 **대체 경로를 활성화**한다
3. **그 사이 사용자도 움직였다.** SMS를 보냈으므로, 사용자는 번호를 받아 앱에 입력했다
4. **TAN이 거래 관리 시스템에서 검증**되고, **위쪽 토큰이 parallel gateway에서 대기**한다
5. **사기 활동으로 인한 에스컬레이션의 경우**
   - **컴플라이언스와 IT 보안 부서에 통보**
   - **보안상의 이유로 고객 계좌를 일시 차단**
   - **고객에게 통보**
6. **이 경로의 끝에는 일반 빈 end event가 아니라 termination event가 있다**

> **이것이 결정적으로 중요하다. parallel gateway에서 여전히 대기 중인 위쪽 토큰을 죽여야 하기 때문이다. 여기에 일반 end event만 두면 그 토큰이 케이스를 영원히 열어 둔 채로 만든다.**

---

### 시나리오 2 — 수취 은행에 연결 불가 (compensation + cancel event) = **canceled 상태**

1. 앞서와 같이 시작 — 데이터 입력 → 검증 → SMS TAN과 fraud check 병렬 처리
2. **이번에는 통과**해서 **두 토큰이 모두 parallel gateway에 도착**한다
3. **거래 프로세스(transaction process)가 촉발**된다
4. **송금액을 발신 계좌에서 차감** — **Script task** (**API 호출 없이 순수 내부 처리**이므로)
5. **수취 계좌로 송금** — **Service task** (**다른 은행에 알리는 정보 서비스 촉발이 필요**하므로)
6. **이제 두 가지가 일어날 수 있다**
   - 다른 은행에서 **확인 알림을 받거나**
   - **24시간이 아무 알림 없이 경과하거나**
7. **수취 은행에 연결할 수 없는 경우이므로 알림이 없다** → **timer event가 촉발**된다
8. 토큰이 아래 경로를 탄다
   - 먼저 **timer event**를 지나고
   - 다음 **throwing compensation event**를 지난다
9. 이것이 **부착된 compensation event를 활성화**해 **차감 취소(undoing of the amount deduction)를 개시**한다
10. → **compensation task가 실행되어 처음 계좌에서 차감했던 금액을 환불**한다
11. **병렬로 끝의 토큰이 cancellation end event를 촉발**하고, 이것이 **부착된 cancel event를 촉발**해 **취소 흐름을 개시**한다
12. → **고객에게 나중에 다시 시도해 달라는 이메일 발송**

> **우리가 방금 살펴본 이 케이스가 거래 프로세스의 canceled 상태를 나타낸다.**

---

### 시나리오 3 — 거래 시스템 장애 (error event) = **hazard 상태**

1. 거래 프로세스에서 시작해 앞서와 동일하게 진행 — **발신 계좌에서 금액 차감** → **수취 계좌로 송금**
2. **그 도중 전체 거래가 시스템 장애의 영향을 받는다**
3. → **부착된 error event가 촉발**된다

> **이것은 현재 실행 중이던 task와 반드시 관련될 필요가 없다. 언제든 발생할 수 있다.**

4. → **오류 조사와 현재 케이스를 해결하기 위한 완화 조치(mitigation actions) 수행**으로 이어진다

> **이것으로 거래 프로세스의 hazard 케이스를 다루었다.**

---

### 시나리오 4 — 성공 경로 (happy path) = **succeeded 상태**

1. 앞서와 같이 **송금할 금액을 발신 계좌에서 차감**
2. 완료되면 **수취 계좌로 송금**
3. **이제 토큰이 event based gateway에서 대기**한다
4. **수취 은행에서 확인이 접수되는 즉시 토큰이 전달되어 거래를 종료**한다
5. **거래가 완료되고 부모 토큰이 프로세스 인스턴스를 종료**한다

## 요약

- **Termination event가 왜 필요한지 보여주는 결정적 사례**다 — **parallel gateway에서 대기 중인 토큰**을 죽이지 않으면 **케이스가 영원히 열려 있다**
- **Transaction의 세 상태가 각각 다른 event로 구현**된다
  - **succeeded** — 확인 수신 후 정상 종료
  - **canceled** — **compensation(환불) + cancel(재시도 안내)** 조합
  - **hazard** — **error event**로 조사·완화
- **Task type이 자동화 관점에서 정확히 구분**된다 — **내부 처리는 script task, 외부 API 호출은 service task**
- **Error event는 현재 실행 중인 task와 무관하게 언제든 발생할 수 있다**
- **Compensation은 이미 완료된 차감을 되돌리고**, **cancel은 transaction 자체의 취소 흐름**을 담당한다 — 둘이 병렬로 동작한다
