# Case Study – Tofisu

## 개요

- Module 11의 종합 case study — **두부 소매업체 Tofisu의 판매 프로세스**
- 사업주 **Leah**, 첫 영업 담당자 **Jen**
- 핵심 구조: **sequential loop가 걸린 expanded sub-process** + **event based gateway** + **non-interrupting event**
- 마지막에 **프로세스 명명(naming) best practice**를 다룬다

## 내용

### 상황

Tofisu는 작지만 빠르게 성장하는 두부 소매업체다. Leah는 트렌드를 일찍 알아채 사업을 확장할 좋은 위치에 있다. **매출을 늘리기 위해 영업 담당자 5명을 새로 채용**했고, 팀을 조직하고 빠르게 궤도에 올리려면 **효율적인 프로세스가 필수**다.

> **Leah는 판매 프로세스를 그려 두어, 자신이 없을 때도 신규 입사자가 일하는 법을 알 수 있게 한다.**

**Jen**이 첫 영업 담당자이고, 이 프로세스 다이어그램으로 업무를 익힌다.

### 프로세스 전체 구조

> **리드(lead)에서 시작해 이상적으로는 충성 고객(loyal customer)으로 끝난다.**

**촉발**: **모든 판매 리드가 자격 검증(qualified)되었을 때**

**1. 리드 점수화** — Jen이 리드를 점수화해 **다음 주에 처리할 주간 리드 목록을 생성**한다. 가용한 리드를 모두 보고 이번 주에 공략할 리드를 정한다

**2. 첫 이메일 발송** — 사전 선별한 모든 리드에게 **사전 정의된 이메일 템플릿**으로 첫 이메일을 보낸다

> **이 두 단계는 sub-process의 sequential loop type과 연결된다. sub-process 안에서 리드 목록을 하나씩 처리해 나가기 때문이다.**

### Sub-process 내부 — 리드 하나의 처리

**Event based gateway** — 이메일 발송 후 **Jen의 통제를 크게 벗어난 세 가지 event**가 발생할 수 있다.

### 리드별 시나리오

**리드 1 — 즉시 성공(quick win)**

1. **긍정적 응답** → **콜드콜(cold call) 진행**
2. 통화 중 **사전 정의된 판매 스크립트**로 **잠재고객의 반응(sentiment)을 평가**한다
3. 반응 평가는 **세 가지 결과**를 가질 수 있다
4. **잠재고객이 바로 구매를 원하는 경우** → **Jen이 주문을 생성하고 배송을 촉발**한다
5. 이후 **고객을 account management 팀에 인계**해 관계를 쌓고 **충성 고객으로 전환**하게 한다

**리드 2 — 샘플 요청 후 실패**

1. **3일 동안 첫 마케팅 이메일에 응답이 없다**
2. → **콜드콜에 사용할 판매 스크립트를 그에 맞게 조정**해야 한다
3. 통화에서 **잠재고객이 주문 전에 샘플을 먼저 원한다**는 것이 드러난다
4. **샘플을 보내고 3일 대기**(샘플 도착 시간) 후 **후속 연락(follow-up)** 을 한다
5. **잠재고객이 만족하지 않으면** → **거래를 lost로 설정**하고, 가능하면 **피드백을 문서화**한다

**리드 3 — 즉시 거절**

1. **부정적 응답** — 제품에 전혀 관심이 없다
2. → 통화 전에 **다시 콜드콜 스크립트를 조정**한다
3. 통화에서도 **잠재고객이 입장을 유지하고 관심을 보이지 않는다**
4. → **Tofisu와 제품에 대한 기본 정보를 담은 안내 이메일을 보내고 거래를 lost로 설정**한다

**리드 4 — 커스텀 제품 요청 (non-interrupting event의 실제 사례)**

1. **처음부터 관심**을 보이고 콜드콜에서도 제안을 마음에 들어 하며 **샘플을 요청**한다
2. **샘플 발송 → 3일 대기 → 후속 연락**
3. **그런데 잠재고객이 Jen에게 전화해 두부 레시피를 자기들에 맞게 조정해 줄 수 있는지 묻는다** — **특별 레시피 요청**

> **이 요청이 non-interrupting conditional event를 촉발한다. event가 점선(dashed)이므로 리드 처리 자체는 중단되지 않고, 커스텀 제품 요청은 병렬로 처리된다.**

4. **Jen의 관리자 Leah가 고객에게 연락해 커스텀 생산의 세부사항을 명확히** 한다
5. **내부적으로 생산팀과 후속 확인해 생산이 가능한지 검증**한다
6. 가능하면 **잠재고객에게 좋은 소식을 전하고 커스텀 계약이나 거래를 진행**한다
7. **그 사이 account management 팀도 인계받을 시간을 확보**한다. Leah는 **커스텀 거래 정보를 반영해 자기 흐름을 그대로 따라가며** 고객을 account management 팀에 인계한다

> **요약하면 non-interrupting event 덕분에 원래 흐름의 activity를 멈추지 않고 들어온 요청을 처리할 수 있다. 리드 처리와 인계를 그대로 유지하면서 고객의 커스텀 요청도 함께 다룬다.**

### 주간 마무리

Jen이 **리드 4개를 처리했고, 이번 주 주간 목록의 모든 리드가 그것으로 끝났다.** 즉 **sequential sub-process의 모든 케이스가 처리되었다.**

→ **sub-process를 촉발했던 부모 프로세스의 토큰이 계속 굴러가 마지막 task를 촉발**한다. Jen은 **주간 기회 보고서(weekly opportunity report)를 작성**하고 주말을 맞는다.

### Best practice — 프로세스 이름 짓기

> 지금까지 프로세스에 명시적으로 이름을 붙이지 않았다. **하지만 프로세스 다이어그램을 많이 만들면 파일명을 정하고 무엇이 무엇인지 파악해야 하므로 이것이 중요해진다.**

**방법 1 — start event와 end event를 잇는다**

> **가장 직관적인 해결책은 이상적인 start event와 end event를 보는 것이다.**

방금 다룬 프로세스는 **`lead generated(리드 생성됨)`** 로 시작해 이상적으로 **`loyal customer(충성 고객)`** 로 끝난다.

→ **start event와 end event를 의역해 `to`로 연결**하면 **`Lead to Loyal Customer`** 라는 좋은 이름이 나온다.

**방법 2 — job to be done으로 간다**

→ 이 경우 **`Process Lead(리드 처리)`** 같은 이름

> 즉 **프로세스에서 해야 할 일을 그대로 서술하거나(`Fulfill the Order`), start event와 end event를 결합한다(`Order to Cash`).**

## 요약

- **Sequential loop가 걸린 expanded sub-process**로 **"리드를 하나씩 처리하되 주간 전체를 관리하는"** 중첩 구조를 만든다
- **Event based gateway**로 **통제 밖의 상황**(긍정 응답 / 무응답 / 부정 응답)을 표현한다
- **Non-interrupting event(점선)** 로 **원래 흐름을 멈추지 않고** 커스텀 요청을 병렬 처리한다
- **모든 리드 처리가 끝나야 부모 토큰이 풀려나** 주간 보고서 task로 넘어간다
- **프로세스 이름은 두 가지 방식**으로 짓는다
  - **start event to end event** — `Lead to Loyal Customer`, `Order to Cash`
  - **job to be done** — `Process Lead`, `Fulfill the Order`
