# Transaction Sub-Process

## 개요

- **Transaction sub-process(트랜잭션 하위 프로세스)** — 여러 activity를 **하나의 트랜잭션으로 묶는다**
- 정의: **집합적으로 성공하거나 실패하는 논리적 작업 단위(logical unit of work)**
- **세 가지 결과**를 가질 수 있다: **succeeded · canceled · hazard**

## 내용

### 개념

여러 activity를 **하나의 트랜잭션으로 그룹화**한다. 기본적으로 **집합적으로 성공하거나 실패하는 논리적 작업 단위**를 나타낸다.

**세 가지 결과(outcomes)**

| 결과 | 의미 |
|---|---|
| **Succeeded(성공)** | 트랜잭션이 성공했다 |
| **Canceled(취소)** | 트랜잭션이 취소되었다 |
| **Hazard(장애)** | 트랜잭션이 비정상적으로 실패했다 |

### 사례 — Leah의 주문 프로세스, 경리부 하위 프로세스

**상황**: 새로 부임한 부서 관리자가 **이 단계들을 이제 현금 수납 시스템(cash collection system)이 실행하도록** 결정한다. 그래서 **하위 프로세스 전체를 하나의 트랜잭션으로 정의**한다.

**적용 결과**: 이제 **sub-process가 아니라 transaction**이 된다.

**세 가지 상태가 실제로 무엇을 의미하는가**

> **송장을 생성하고 발송하는 것은 하나의 논리적 작업 단위다.** 그리고 이것은 세 가지 상태를 가질 수 있다.

| 상태 | 이 사례에서 |
|---|---|
| **Succeeded** | **트랜잭션이 성공**했다 — 송장 생성과 발송이 모두 완료 |
| **Canceled** | **주문이 취소된 경우** |
| **Hazard** | **새로 도입한 현금 수납 시스템이 실패하는 경우** 등 |

> **트랜잭션은 이후 챕터에서 더 자세히 다룬다.**

## 예시

```text
Transaction sub-process — 세 가지 결과

┌═ Transaction: 송장 처리 ═════════════════════┐  (이중 테두리)
║                                              ║
║  (○) → [송장 생성] → [송장 발송] → (◎)        ║
║                                              ║
╚══════════════════════════════════════════════╝
        │            │              │
   Succeeded      Canceled       Hazard
        │            │              │
        ↓            ↓              ↓
   [정상 진행]  [주문 취소     [현금 수납 시스템
                 처리]          장애 처리]


논리적 작업 단위란

  송장 생성 ─┐
             ├─ 둘은 함께 성공하거나 함께 실패해야 한다
  송장 발송 ─┘   송장만 만들고 안 보내면 의미가 없다

  → 하나의 transaction으로 묶는다


일반 sub-process와의 차이

[Sub-process]      완료되면 그냥 다음으로 넘어간다
                   (성공/실패 구분 없음)

[Transaction]      완료 방식이 세 갈래로 나뉜다
                   succeeded / canceled / hazard
                   각각 다른 후속 처리를 붙일 수 있다
```

## 요약

- **Transaction sub-process는 함께 성공하거나 함께 실패해야 하는 activity들을 묶는다**
- **세 가지 결과**: **succeeded**(성공) · **canceled**(취소) · **hazard**(비정상 실패)
- 각 결과에 **서로 다른 후속 처리**를 연결할 수 있는 것이 일반 sub-process와의 차이다
- 전형적 사례: **송장 생성 + 송장 발송** — 둘은 하나의 논리적 단위이며, 시스템 장애(hazard)와 업무상 취소(canceled)를 구분해 처리해야 한다
