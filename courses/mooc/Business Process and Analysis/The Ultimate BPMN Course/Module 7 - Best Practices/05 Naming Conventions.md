# Naming Conventions

> **참고**: MOOC에서 이 강의의 제목은 `Naming Conventions`지만, **실제 영상 내용은 consistent process flow(일관된 프로세스 흐름)와 두 pool의 상호작용**이다. 강좌 자체에 두 영상의 순서가 뒤바뀌어 있다. 명명 규칙 내용은 이전 강의 [04 Consistent Process Flow](04%20Consistent%20Process%20Flow.md)에 있다.

## 개요

- **일관된 프로세스 흐름(consistent process flow)** 을 만드는 법
- 두 개의 pool이 서로 어떻게 상호작용하는가
- 핵심 원칙: **pool 안의 모든 프로세스는 완결되어야 하고 독립적으로 실행 가능해야 한다**

## 내용

### 상황 설정

지금까지 Bookworm 서점 프로세스에서 고객을 **collapsed pool**로 표현했다.

이제 여러분이 그 서점의 **영업 관리자**이고, 상사가 **판매 과정에서 고객 여정(customer journey)을 개선하라**고 지시했다고 하자.

**첫 번째 논리적 단계는?** → **고객의 프로세스를 모델링해 최적화 지점을 평가**한다.

### 흔한 실수 — 불완전한 pool

여기서 문제가 생긴다. 많은 사람이 이 프로세스를 **잘못 모델링한다**.

**왜 틀렸는가**

> **각 pool의 프로세스는 완결(complete)되어야 하기 때문이다.**
>
> 이는 곧 **다른 pool과 독립적으로 실행될 수 있어야 한다**는 뜻이다.
>
> **토큰이 start event에서 end event까지 중단 없이 굴러가야 한다.** 다시 말해 **하나의 pool 안의 sequence flow는 어느 지점에서도 끊어져서는 안 된다.** 시작부터 끝까지 매끄럽게 이어져야 한다.

### 올바른 방법

- **각 pool은 완결된 프로세스를 담아야 한다**
- **각 pool은 다른 pool과 독립적으로 작동하도록 설계되어야 한다**
- 예: **고객의 프로세스는 Bookworm 서점의 프로세스에 의존하지 않고 독자적으로 실행될 수 있어야 하며, 그 반대도 마찬가지다**

### 언제 두 개의 완결된 pool을 쓰는가

> **두 개의 완결된 pool을 쓰기 전에 use case를 점검한다. 다음이 모두 참이어야 한다.**
>
> 1. **두 프로세스가 모두 매우 중요하고 상세한 모델링이 필요하다**
> 2. **목표를 달성하기 위해 외부 당사자의 프로세스와 자신의 프로세스를 모두 완전히 이해해야 한다**

**예시**: 고객 여정을 최적화할 때는 **고객의 프로세스를 상세히 모델링하는 것이 결정적이면서, 동시에 개선점을 찾기 위해 자신의 프로세스도 이해해야 한다.**

### 대부분의 경우 — collapsed pool로 충분하다

> **외부 참여자(고객 등)를 표현하는 데는 대부분 collapsed pool로 충분하다.**
>
> **외부 프로세스의 내부 세부사항을 이해할 필요가 없다면, collapsed pool이 모델을 단순하게 유지하고 복잡성을 줄여준다.**

Bookworm 서점 프로세스의 초기 버전에서 고객의 행동을 **black box**로 표현했던 것이 바로 이 접근이다.

## 예시

```text
✗ 잘못된 모델 — 끊어진 pool

┌─ Pool: 고객 ───────────────────────────────┐
│   [주문한다] ┄┄┄┄> (흐름이 여기서 끊김)      │  ← 독립 실행 불가
└────────────────────────────────────────────┘
┌─ Pool: Bookworm 서점 ──────────────────────┐
│   (○) → [주문 처리] → (◎)                  │
└────────────────────────────────────────────┘


✓ 올바른 모델 — 두 pool 모두 완결

┌─ Pool: 고객 ───────────────────────────────┐
│  (○ 책이 필요함) → [책 검색] → [주문] →     │
│                    [수령] → (◎ 책 확보)     │  ← 독자적으로 완결
└──────────┊──────────────────┊──────────────┘
           ┊ message flow     ┊
┌──────────┸──────────────────┸──────────────┐
│  Pool: Bookworm 서점                        │
│  (✉ 주문 수신) → [처리] → [배송] → (◎)      │  ← 독자적으로 완결
└────────────────────────────────────────────┘


✓ 더 단순한 대안 — collapsed pool

┌─ Pool: Bookworm 서점 ──────────────────────┐
│  (✉ 주문 수신) → [처리] → [배송] → (◎)      │
└──────────┊──────────────────┊──────────────┘
┌──────────┸──────────────────┸──────────────┐
│  Pool: 고객 (collapsed / black box)         │  ← 내부를 모델링하지 않음
└────────────────────────────────────────────┘


판단 기준

  외부 프로세스의 내부를 상세히 알아야 하는가?
        │
   ┌────┴────┐
  예         아니오
   │           │
두 개의     collapsed pool
완결된 pool  (대부분의 경우)
```

## 요약

- **pool 안의 모든 프로세스는 완결되어야 하고 독립적으로 존재할 수 있어야 한다**
- **하나의 pool 안에서 sequence flow가 끊어지면 안 된다.** start부터 end까지 이어져야 한다
- **두 개의 완결된 pool은 꼭 필요할 때만** 사용한다 — 두 프로세스 모두 중요하고 상세 모델링이 필요할 때
- **내부 흐름을 모델링할 필요가 없다면 collapsed pool**로 단순화한다
- 이 원칙을 지키면 프로세스 흐름이 **일관되고, 명확하고, 적절한 범위**를 유지한다
