# Consistent Process Flow

> **참고**: MOOC에서 이 강의의 제목은 `Consistent Process Flow`지만, **실제 영상 내용은 naming convention(명명 규칙)** 이다. 강좌 자체에 두 영상의 순서가 뒤바뀌어 있다. 일관된 프로세스 흐름 내용은 다음 강의 [05 Naming Conventions](05%20Naming%20Conventions.md)에 있다.

## 개요

- **Naming convention(명명 규칙)** — 명확하고 표현력 있는 프로세스 모델을 만드는 핵심 요소
- 이전 강의들이 프로세스의 **레이아웃**을 다뤘다면, 이 강의는 **요소에 레이블을 올바르게 붙이는 것**을 다룬다
- 요소 종류마다 **명명 방식이 다르다**

## 내용

### 1. Pool과 Lane — 사람 이름이 아니라 역할

pool과 lane은 **책임(responsibility)** 을 나타낸다. 담당자 이름(예: `Max`)을 붙이고 싶어질 수 있지만 **올바른 접근이 아니다**.

**왜 안 되는가**

- **Max가 유일한 매장 직원이 아닐 수 있다.** 직원마다 별도의 프로세스를 두면 불필요한 복잡성만 생긴다
- **Max가 퇴사하거나 새 직원이 들어오면 모델을 계속 수정**해야 한다

**올바른 방법**: 항상 **일반적인 역할(general roles)** 로 레이블을 붙인다 — **부서(department)나 직무(job function)**

- 예: `Shop Assistant(매장 직원)`, `Customer Service Team(고객 서비스팀)`
- **역할은 해당 lane의 책임을 제대로 서술해야 한다**

### 2. Task — 능동형, 행동 지향 동사

task 레이블은 **행동 가능한 서술(actionable descriptions)** 에 초점을 둔다.

**비교**

| 나쁨 | 좋음 |
|---|---|
| `Shoe size check` (신발 사이즈 확인) | **`Check if the shoe size is available`** (신발 사이즈가 있는지 확인한다) |

**왜 후자가 나은가**: **능동 동사(active verb)를 사용해 행동이 필요하다는 것을 분명히 나타낸다.**

> `Shoe size check` 같은 **모호하거나 일반적인 서술은 명확성이 부족하고 독자를 혼란스럽게 한다.** 항상 **명확하고 행동 지향적인 동사**를 목표로 한다.

### 3. Event — 수동형, 상태 서술

event는 **정반대 접근**이 필요하다.

> **event는 행동이 아니라 단계(stage)나 상황(situation)을 나타낸다. 따라서 수동형 서술을 사용해야 한다.**

- 예: `Payment reminder has been sent(결제 알림이 발송되었다)`

이렇게 이름 붙이면 **task와 혼동하는 것을 막을 수 있다.**

## 예시

```text
명명 규칙 요약

┌─ Pool / Lane ──────────────────────────────────┐
│  ✗ "Max"           (개인 이름)                  │
│  ✓ "Shop Assistant" (역할·직무)                 │
│  ✓ "Customer Service Team" (부서)              │
└────────────────────────────────────────────────┘

┌─ Task (사각형) ────────────────────────────────┐
│  ✗ "Shoe size check"          (명사형, 모호)    │
│  ✓ "Check if the shoe size is available"       │
│     능동 동사로 시작 → 행동이 필요함이 분명        │
└────────────────────────────────────────────────┘

┌─ Event (원) ───────────────────────────────────┐
│  ✗ "Send payment reminder"    (능동형 = task처럼) │
│  ✓ "Payment reminder has been sent"            │
│     수동형 → 상태·단계임이 분명                   │
└────────────────────────────────────────────────┘


기억법: Task는 "무엇을 하라", Event는 "무엇이 되었다"
```

## 요약

- **Pool·Lane** → 개인 이름이 아니라 **역할·부서**로 명명한다. 사람이 바뀌어도 모델을 고칠 필요가 없다
- **Task** → **능동 동사로 시작하는 행동 지향 서술**. 명사형 축약은 피한다
- **Event** → **수동형 서술**로 상태를 나타낸다. task와의 혼동을 막는다
- 이 규칙만 지켜도 프로세스가 **더 명확하고, 행동 가능하고, 유지보수하기 쉬워진다**
