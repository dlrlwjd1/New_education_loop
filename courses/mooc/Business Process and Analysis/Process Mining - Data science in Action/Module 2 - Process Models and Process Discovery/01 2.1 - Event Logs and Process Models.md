# 2.1: Event Logs and Process Models

## 개요
- 프로세스 발견의 **입력(이벤트 로그)** 과 **출력(프로세스 모델)** 을 정리하는 강의.
- 핵심 통찰: **Case / Activity / Timestamp 매핑은 정답이 하나가 아니라 질문에 따라 달라진다.**
- **XES**(Extensible Event Stream) 표준과 표현 방식(notation)의 두 가지 역할.

## 내용

### 복습 — Play-out / Play-in / Replay

| 관계 | 하는 일 | 대응하는 프로세스 마이닝 유형 |
|---|---|---|
| **Play-out** | 모델에서 행동을 생성 (시뮬레이션, 워크플로 시스템, 관리 게임, 모델 체킹) | — |
| **Play-in** | 행동에서 자동으로 모델 생성 | **발견(discovery)** |
| **Replay** | 모델과 행동을 **대면(confront)** 시킨다 | **적합성 검사**(편차 찾기), **강화**(병목 등) |

> **Replay가 프로세스 마이닝의 가장 중요한 형태**다. 모델과 현실을 맞대면 적합성 검사, 예측, 병목 분석 등 여러 목적에 쓸 수 있다.

### 이벤트 로그의 정의
> 이벤트 로그 = **케이스의 집합**. 각 케이스는 **이벤트의 시퀀스**이고, 이를 **트레이스(trace)** 라고도 부른다.
> 각 이벤트는 **케이스, 활동, 시점(타임스탬프)** 을 가리킨다.

**데이터 출처**: 데이터베이스(병원에서는 환자 데이터 테이블을 쉽게 수백 개 찾을 수 있다), CSV·Excel, 트랜잭션 로그, SAP, 미들웨어, Twitter·Facebook 등.

### 매핑은 질문에 따라 달라진다

**예 — 메일함**. 이메일 하나를 이벤트로 본다면 sender, receiver, to, subject, timestamp, body 중 무엇이 무엇인가?

한 가지 매핑:
| 이메일 필드 | 역할 |
|---|---|
| **subject** | **Case ID** — 같은 제목의 메일을 하나의 트레이스로 묶는다 |
| **timestamp** | 케이스 내 이벤트 정렬 |
| **sender** | **Activity name** (동시에 **resource**로도 해석 가능) |
| 나머지 | 기타 데이터 변수 |

> **다른 매핑도 많이 가능하다.** 예를 들어 **sender를 케이스로, subject를 활동명으로** 볼 수도 있다. **무엇이 최선인지는 맥락과 질문에 달려 있다.**

**예 — 학생 데이터**: student id = case, course = activity, 시험 날짜 = timestamp. 그런데 **course를 케이스로, student를 활동으로** 보는 대안도 가능하다.

### 더 풍부한 이벤트 로그

**트랜잭션 정보** — 지금까지는 이벤트를 **원자적(atomic) 활동**으로 봤다. 그런데 활동에 시간이 걸리는 경우 **명시적인 start와 complete 이벤트**를 볼 수 있다. 많은 이벤트 로그가 이런 정보를 갖고 있고, 있으면 **활동의 지속 시간을 측정**할 수 있다.

**케이스 수준 속성** — 지금까지는 모든 속성을 **이벤트 속성**으로 봤다. 하지만 **케이스 수준에도 속성**이 있을 수 있다 — 그 케이스를 실행하는 동안 **변하지 않는 속성**들이다.

### XES 표준
> **XES = Extensible Event Stream.** **IEEE 프로세스 마이닝 태스크 포스**가 채택한 표준이고, 이 코스에서 쓰는 도구들이 지원한다.

CSV와 달리 **모든 열의 의미를 이미 해석해 둔 형식**이다. ProM이나 Disco에 로드하면 **더 할 일 없이 바로 분석을 시작**할 수 있다.

### 프로세스 모델 — 관점(perspective)

지금까지 본 것은 **제어 흐름(control-flow)** 중심 모델이다(예: Petri net). 하지만 프로세스 모델은 다른 요소도 표현할 수 있다.

- **데이터 요소** — 특정 결정을 이끄는 것
- **시간 정보**
- **자원(resource) 정보**
- **비용, 위험** 등

> 이번 주는 **제어 흐름과 제어 흐름 모델의 발견**에만 집중한다.

### 표현 방식(notation)의 두 가지 역할
표현 방식이 중요한 이유가 **두 가지로 다르다.**

| 역할 | 설명 |
|---|---|
| **탐색을 이끈다** | 프로세스 발견 중에 쓰는 표현이 **탐색 과정 자체를 좌우**한다. 현실을 잘 담는 모델을 찾도록 도와야 한다. 이것은 **발견 기법 내부**의 문제다 |
| **시각화한다** | **최종 사용자가 무엇을 보고 싶어 하는지**를 생각해야 한다 |

> **발견 중에 쓰는 표현과 최종 결과를 제시할 때 쓰는 표현이 다를 수 있다**는 점을 아는 것이 중요하다.

**예 — Disco의 퍼지 모델(fuzzy model)**: 사각형은 활동, 호(arc)는 인과 의존성. 그런데 Petri net과 달리 **AND-join인지 XOR-split인지를 그래픽 표기에서 정확히 명시하지 않는다.** 온갖 혼합을 허용하고 명시적으로 표현하지 않는다.
> 그 결과 **실행 가능한 모델은 아니지만, 훨씬 단순하고 어쩌면 훨씬 직관적인** 모델을 얻는다.

## 요약
- 이벤트 로그 = 케이스(트레이스)의 집합, 각 트레이스 = 이벤트 시퀀스.
- **Case / Activity / Timestamp 매핑에 정답은 없다.** 메일함 하나도 여러 방식으로 매핑할 수 있고, **질문이 매핑을 결정한다.**
- 로그가 더 풍부할 수 있다 — **start/complete 트랜잭션 정보**(활동 소요 시간 측정 가능), **케이스 수준 속성**.
- **XES**는 IEEE 태스크 포스가 채택한 표준 이벤트 로그 형식이다.
- 표현 방식은 **탐색을 이끄는 역할**과 **시각화하는 역할**이 다르며, **둘이 달라도 된다.**
