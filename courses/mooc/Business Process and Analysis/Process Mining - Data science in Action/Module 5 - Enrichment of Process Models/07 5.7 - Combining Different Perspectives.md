# 5.7: Combining Different Perspectives

## 개요
- **코끼리를 만지는 장님들** 비유 — 한 관점만 보면 전체를 오해한다.
- 제어 흐름을 **중추(backbone)** 로 삼아 데이터·시간·자원을 하나의 모델로 결합한다.
- 통합 모델의 활용처: **시뮬레이션**과 **운영 지원**.

## 내용

### 코끼리 비유
> 눈을 가린 사람들이 코끼리의 일부만 만진다. **코를 만진 사람은 뱀이라 생각**하고, **몸통을 만진 사람은 벽이라 생각**하고, **다리를 만진 사람은 나무라 생각**한다.
>
> **프로세스 마이닝에서 한 관점만 고립해서 보면 똑같은 문제**가 생긴다. 프로세스 모델은 제어 흐름만이 아니라 **데이터·시간·자원·비용·위험**이기도 하다.

### 제어 흐름이 중추다
> **프로세스 모델은 여러 관점으로 구성되고, 언제나 중추는 제어 흐름이다.** 다른 것들이 제어 흐름에 붙어서 서로 연결된다.
>
> 제어 흐름의 **활동**이 **특정 자원에 의해 실행**되고, **특정 시간이 걸리고**, **특정 가드**를 가질 수 있다. **제어 흐름이 이 모든 것을 묶는다.**

### 통합 절차
1. **이벤트 로그**에서 시작
2. **프로세스 발견**으로 모델을 만들거나, 손으로 만들거나, 둘을 결합한다
3. 로그의 이벤트를 **제어 흐름 중심으로 모델에 연결**한다 (**정렬**)
4. 연결이 확립되면 **다른 관점들을 마이닝**한다:
   - **역할**을 찾는다
   - **병목**을 찾는다 — 어디서 시간이 흘러가는가
   - **가드**를 식별한다
5. 모든 것을 **통합 모델**로 합친다

**단계별 산출물**:
| 관점 | 붙는 것 |
|---|---|
| **데이터** | 의사결정 지점의 **가드**(+ 변수, 읽기·쓰기 호) |
| **시간** | **병목** 정보를 활동과 자리에 붙이고, **라우팅 확률**도 담는다 |
| **자원** | 자동 학습한 **역할**이 **프로세스 모델의 활동과 개별 작업자를 잇는 연결 고리**가 된다 |

### 한계를 인식하기
> **생성한 모델의 한계를 알아야 한다.** 과적합이거나 과소적합일 수 있다.
>
> **모델은 기술적(descriptive)** 인 경향이 있다 — **일어난 일을 기술하지 일어나야 할 일을 기술하지 않는다.**
>
> 이런 복잡한 모델을 쓸 때는 **자동 생성 모델의 한계를 매우 잘 인식**해야 한다. 대개 **추가 분석의 출발점일 뿐**이고, 후속 단계에서 실제로 쓰려면 **편집과 추가 가정**이 필요하다.

### As-is에서 To-be로
프로세스 마이닝은 흔히 **as-is**(지금 어떤가, 문제가 어디 있는가)에 집중한다. 하지만 **to-be**로 옮겨가고 싶다.

두 가지 방법:
1. **운영 지원(operational support)** — 프로세스를 실행하는 사람에게 **권고와 예측**을 준다 (다음 모듈)
2. **시뮬레이션** — **what-if 질문**에 답한다

### 시뮬레이션
> **시뮬레이션 = 프로세스 모델을 플레이아웃(play-out)하는 것.** 모델대로 프로세스를 여러 번 돌리고 **성능 정보를 수집**한다.

**탐색할 수 있는 대안 설계**:
- 두 활동을 **순차 대신 동시**로 실행하면?
- **자원을 늘리거나 줄이면**?

**필요한 것**: 프로세스 자체의 모델뿐 아니라 **환경의 모델** — **자원의 가용성**, **새 케이스의 도착 과정**. 그리고 **서브런(sub run)의 개수와 길이**, **측정할 성과 지표**.

> **프로세스 마이닝이 바로 이런 시뮬레이션 모델을 만드는 데 필요한 입력을 제공한다.**

### 프로세스 마이닝이 시뮬레이션을 개선하는 지점

전통적 시뮬레이션 프로젝트에는 **10가지 위험**이 있는데, 그중 대표적인 것이 **현실과 맞지 않는 숨은 가정**이다.
> **이벤트 데이터와의 대면이 시뮬레이션 결과의 품질을 높인다.**
>
> **시뮬레이션과 통계 기법은 오용되기 쉽다.** 최종 사용자에게 명시적이지 않은 **파라미터 하나를 조작해 결과를 극적으로 바꿀 수 있다.** 매우 조심해야 한다.

**전통적 시뮬레이션의 세 가지 순진한 가정과 프로세스 마이닝의 개선**:

| 전통적 가정 | 현실 | 프로세스 마이닝의 기여 |
|---|---|---|
| **정상 상태(steady state)** 를 본다 | 현실의 프로세스는 정상 상태가 아닐 때가 많다. **도착 과정이 변하고 자원 가용성도 변한다** | 이벤트 로그에서 정보를 추출해 **더 현실적으로 재생**한다 |
| 자원은 **항상 가용하고, 일하고 싶어 하고, 늘 같은 속도**로 일한다 | 사실이 아니다 | 이런 **더 정교한 현상을 찾아 모델에 추가**한다 |
| **빈 프로세스**에서 시작한다 | 내일이나 다음 주에 무슨 일이 일어날지(**과도 상태, transient behavior**)에 관심이 있다면 | **초기 상태, 즉 현재 상태**를 모델에 반영해야 한다 |

> 또 하나의 흥미로운 점: **시뮬레이션 모델이 생성하는 이벤트 로그는 실제 정보 시스템이 생성하는 이벤트 로그와 매우 유사**하다. 그래서 **현실과 시뮬레이션을 정확히 같은 방식으로 볼 수 있고**, what-if 분석과 대안 시나리오 비교에 큰 도움이 된다.

## 요약
- 한 관점만 보면 **코끼리를 뱀이나 벽으로 오해**한다. **데이터·시간·자원·비용·위험**을 하나의 모델로 합쳐야 한다.
- **제어 흐름이 중추**이고 다른 관점이 거기 붙는다.
- 절차: **로그 → 제어 흐름 발견 → 정렬 → 관점별 마이닝(역할·병목·가드) → 통합 모델**.
- **자동 생성 모델은 기술적이고 한계가 있다.** 후속 분석의 출발점일 뿐이며 편집과 가정 추가가 필요하다.
- 통합 모델의 두 용도: **시뮬레이션**(what-if)과 **운영 지원**.
- 프로세스 마이닝은 시뮬레이션의 세 가지 순진한 가정(**정상 상태 · 항상 가용한 자원 · 빈 시작 상태**)을 현실 데이터로 교정한다.
