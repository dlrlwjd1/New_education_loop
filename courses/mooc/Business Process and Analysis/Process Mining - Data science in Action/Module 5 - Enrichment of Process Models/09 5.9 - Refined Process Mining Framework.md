# 5.9: Refined Process Mining Framework

## 개요
- 발견·적합성·강화 세 가지를 **10개 활동으로 세분화**한 정교화된 프레임워크.
- 두 축이 핵심이다: **사후(post mortem) vs 사전(pre mortem) 데이터**, **de jure vs de facto 모델**.

## 내용

### 프로베넌스(provenance) — 프레임워크의 최상단
> **프로베넌스**란 우리가 수집하는 이벤트 데이터가 **충실(faithful)해야** 한다는 것이다. **실제로 일어난 일을 기술**해야 한다.
>
> 그리고 수집한 이벤트 데이터는 **안전(safe)해야** 한다. **데이터가 그냥 사라지면 안 되고, 특히 선택적으로 사라지면 안 된다.** 우리는 **이벤트 데이터로 항상 이력을 재구성할 수 있어야** 한다.

### 축 1 — 사후 데이터 vs 사전 데이터

| | **사후(post mortem)** | **사전(pre mortem)** |
|---|---|---|
| 대상 | **이미 완전히 끝난** 케이스 | **아직 실행 중이고 살아 있는** 케이스 |
| 영향 | 더 이상 **영향을 줄 수 없다** | **아직 영향을 줄 수 있다** |
| 관심사 | 병목은 어디인가, **지금 돌아가는 케이스가 아니라 프로세스 일반**을 어떻게 개선할까 | **지금 돌아가는, 아직 손댈 수 있는 케이스** |

**예시**:
| 상황 | 사후 질문 | 사전 질문 |
|---|---|---|
| **학생** | 병목과 개선 | **이 학생이 중도 탈락할 것 같다** → 지금 조치할 수 있다. **학생들이 충분히 몰입하지 않는다** → 조치 |
| **병원** | 일반적 개선 | 특정 환자의 **부적합(non-conformance)** 을 발견 → **더 큰 문제가 생기지 않도록 조치** |
| 케이스 지연 | — | **케이스가 늦어지고 있다** → **추가 자원을 투입**해 제때 처리되게 한다 |

### 축 2 — de jure 모델 vs de facto 모델

| | **de facto 모델** | **de jure 모델** |
|---|---|---|
| 성격 | **기술적(descriptive)** | **규범적(normative)** |
| 목적 | **현실을 있는 그대로 기술**한다. 행동에 영향을 주거나 안내하려는 것이 아니다 | **어떻게 해야 하는지**를 명세한다 |
| 어디서 나오나 | **프로세스 발견**의 결과 | 워크플로 시스템이나 BPM 시스템이 쓰는 모델 — **시스템이 사람들을 특정 방식으로 일하게 강제**한다 |
| 종이 위의 모델이라면 | — | 여전히 규범적이지만, **시스템이 강제하지 않으면 사람들이 벗어나기로 선택할 수 있다** |

> 모델은 **여러 관점을 포괄**할 수 있다. 항상 **제어 흐름**은 있고, 그 중추에 **데이터와 규칙, 자원, 시간, 비용** 등이 붙는다.

## 예시 — 10개 활동

### 그룹 1 — 지도로서의 프로세스 모델 (models as maps)

| 활동 | 내용 |
|---|---|
| **discover(발견)** | 제어 흐름이나 다른 관점의 발견. **실제로 일어나는 프로세스의 모델을 학습**한다 |
| **enhance(강화)** | 기존 모델과 이벤트 데이터를 결합해 **모델을 확장하거나 수리**한다 |
| **diagnose(진단)** | 모델 자체로 목적을 수행한다 — 이벤트 데이터와 직접 연결되지 않고도, **예전에 발견한 모델을 훨씬 나중에 진단 목적으로** 쓸 수 있다 |

### 그룹 2 — 감사(auditing) — 모델과 현실의 대면

| 활동 | 데이터 | 내용 |
|---|---|---|
| **detect(탐지)** | **사전** | de jure 모델과 비교해 **편차가 있을 때마다 즉시 경보**를 생성한다. **온라인 환경** |
| **check(검사)** | **사후** | 우리가 계속 논의해 온 **적합성 검사**. **오프라인**으로 과거를 본다 |
| **compare(비교)** | 모델 대 모델 | 발자국 논의에서 본 것처럼 **두 모델을 비교**한다. **de jure와 de facto**를 비교하거나, **같은 프로세스의 다른 변형**을 모델 수준에서 비교 |
| **promote(승격)** | — | **de facto 모델의 요소를 de jure 모델로 옮긴다.** **모델 수리(model repair)** 가 전형적인 예 |

> **detect와 check의 공통점**은 **이벤트 데이터와 모델을 비교**한다는 것이다.

### 그룹 3 — 항해·지원·안내 (프로세스 실행 지원)

| 활동 | 내용 |
|---|---|
| **explore(탐색)** | 이벤트 데이터와 모델을 결합해 **런타임에 프로세스를 탐색**한다. **질의 언어처럼** — 지금 무슨 일이 일어나고 있고 무언가 해야 하는지 이해한다 |
| **predict(예측)** | **이력으로 학습한 모델 + 사전 데이터(실행 중 케이스의 현재 상태)** → **예측** |
| **recommend(권고)** | 예측할 수 있으면 **행동을 권고**할 수 있다. 과거 정보를 써서 **다음 활동을 실행할 특정 활동이나 특정 자원을 추천**한다 |

## 요약
- **프로베넌스**: 이벤트 데이터는 **충실하고 안전**해야 하며, **이력을 항상 재구성**할 수 있어야 한다.
- **사후(끝난 케이스, 프로세스 일반의 개선) vs 사전(진행 중 케이스, 아직 영향 가능)** — 이 구분이 오프라인과 온라인을 가른다.
- **de jure(규범적, 어떻게 해야 하는가) vs de facto(기술적, 실제 어떠한가)** — **역할이 완전히 다르므로** 혼동하면 안 된다.
- **10개 활동**:
  - **지도**: discover · enhance · diagnose
  - **감사**: **detect**(사전·온라인) · **check**(사후·오프라인) · compare(모델 대 모델) · promote(de facto → de jure)
  - **항해**: explore · **predict** · **recommend**
- **프로세스 마이닝의 스펙트럼은 프로세스 발견보다 훨씬 넓다.**
