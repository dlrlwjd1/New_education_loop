# 6.3: Guidelines for Logging

## 개요
- 새 시스템을 설계할 때 **무엇을 어떻게 기록해야** 프로세스 마이닝이 가능한가.
- **12가지 로깅 가이드라인**.
- 요지: **garbage in, garbage out** — 처음부터 잘못 기록하면 의미 있는 분석 결과를 얻기 매우 어렵다.

## 내용

### 용어
> **이벤트(event)** = 일어난 일. **참조(reference)와 속성(attribute)** 으로 기술된다.
> **참조**는 어떤 **객체**를 가리킨다 — 사람, 케이스, 티켓, 방. **실세계에 존재하는 실체**를 가리킨다.
> **속성**은 **이름-값 쌍**이다 — 활동의 이름, 환자의 나이, 특정 시점 등.

## 예시 — 12가지 가이드라인

| # | 가이드라인 | 내용 |
|---|---|---|
| **1** | **의미의 일관성** | 참조와 속성 이름은 **관련된 모든 사람에게 같은 의미**여야 한다. 특정 속성이 이해관계자마다 다른 의미일 수 없다 |
| **2** | **이름의 구조화된 관리** | 정보 시스템을 프로그래밍하는 사람이 **임시로 코드에 기록 구문을 끼워 넣으면 안 된다.** 새 이벤트, 새 참조나 속성 이름은 **관련성과 의미에 합의가 있을 때만** 추가한다 |
| **3** | **참조는 안정적이어야** | **맥락에 의존하면 안 된다.** 기계의 언어 설정을 바꾸거나 시간이 지난다고 바뀌면 안 된다 |
| **4** | **속성 이름은 최대한 정밀하게** | 예: 많은 로그에서 **정확한 타임스탬프를 모르고 날짜만** 안다. 그러면 같은 날 일어난 이벤트를 신뢰성 있게 정렬하기 어렵다. **데이터가 부정밀하면(불가피한 경우도 있다) 그 사실을 명시적으로 표시**해야 한다 |
| **5** | **불확실성을 명시** | 이벤트·참조·속성이 어느 정도 **불확실하면 명시적으로 진술**한다. 시각을 확신하지 못하거나, 어느 자원이 실행했는지 확신하지 못해 **추정한 것이라면 로그에 그렇게 표시**한다. 분석 중에 이 정보를 쓸 수 있다 |
| **6** | **이벤트 데이터는 정렬돼야** | 두 가지 방법 — **타임스탬프**로 정렬하거나, **순서를 명시적으로 저장**한다(리스트, 또는 부분 순서라면 그래프). 날짜만 있으면 순서 재구성이 어렵지만 **그래도 순서를 잡으려는 전용 분석 기법**이 있다 |
| **7** | **트랜잭션 정보를 기록** | **완료만이 아니라 시작과 완료**를 기록하려 노력한다. 중단·일시중지·재개도 마찬가지. **활동의 지속 시간**과 **자원의 가동률(utilization)** 을 계산할 수 있게 해 준다 |
| **8** | **품질 관리는 지속적 프로세스** | 로깅을 **정기적으로 점검**한다. 처음에만 하지 말고 **프로세스와 시스템이 진화하는 동안 반복해서** 로깅이 최신인지 확인한다 |
| **9** | **비교 가능성(comparability)** | **로깅 자체가 시간에 따라 변하거나 맥락에 의존하면 안 된다.** 예: 어느 시점부터 특정 활동 기록을 중단하면 "그 활동이 나중에는 실행되지 않았다"는 **틀린 결론**에 이른다. **두 부서를 비교할 때 로깅 방식이 다르면 실제로 없는 차이를 있다고 결론 내리게 된다** |
| **10** | **집계하지 말 것** | 데이터 웨어하우스와 OLAP 논의에서 봤듯 **이벤트 데이터의 집계를 피해야** 한다. **집계는 분석 중에 해야지 그 전에 하면 안 된다 — 되돌릴 수 없기 때문**이다. **이벤트 데이터는 가능한 한 원시(raw)** 여야 한다 |
| **11** | **일어난 이벤트를 삭제하지 말 것** | 학생 데이터에서 **중도 탈락한 학생을 모두 지우면 매우 오도된 결과**가 나온다. **취소된 콘서트를 지우면 안 되고, 해고된 직원을 지우면 안 된다.** 정보를 제거하는 것이고 **프로베넌스를 위협**한다 |
| **12** | **프라이버시** | **프라이버시 보장과 의미 있는 분석 가능성 사이에 매우 미묘한 균형**이 있다. 케이스가 특정 개인을 가리킨다는 것을 기록할 이유가 없는 경우가 많지만, **같은 사람을 가리키는 이벤트들은 서로 연관시키고 싶다.** → **해싱(hashing)** 이 데이터를 익명화하면서도 결론을 내리고 이벤트를 연결할 수 있게 해 준다. **너무 추상화하면 이 상관관계가 사라져 어떤 분석도 어려워진다** |

## 요약
- 12개 가이드라인의 큰 줄기:
  - **의미와 이름**: 일관된 의미(1), 관리된 이름(2), 안정적 참조(3), 정밀한 속성(4), **불확실성 명시**(5)
  - **구조**: 정렬 가능성(6), **트랜잭션 정보**(7)
  - **운영**: 지속적 품질 점검(8), **비교 가능성**(9)
  - **보존**: **집계 금지**(10), **삭제 금지**(11)
  - **윤리**: **프라이버시 — 해싱으로 익명화하되 상관관계는 보존**(12)
- 특히 중요한 세 가지: **집계하지 말 것 · 삭제하지 말 것 · 로깅 방식을 바꾸지 말 것.** 셋 다 **되돌릴 수 없거나 틀린 결론을 유발**한다.
- **garbage in, garbage out** — 시스템을 설계할 때 무엇을 기록할지가 이후 분석의 상한을 정한다.
