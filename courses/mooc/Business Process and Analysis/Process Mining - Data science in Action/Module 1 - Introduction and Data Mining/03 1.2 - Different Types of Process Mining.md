# 1.2: Different Types of Process Mining

## 개요
- **이 코스에서 가장 중요한 개념 강의.** 프로세스 마이닝의 세 유형을 정의한다.
- **발견(discovery) · 적합성 검사(conformance checking) · 강화(enhancement)**.
- 그 아래 깔린 세 가지 관계: **Play-out · Play-in · Replay**.

## 내용

### 프로세스 마이닝의 위치
프로세스 마이닝은 **고전적 프로세스 모델 분석**과 **데이터 지향 분석(데이터 마이닝·머신러닝)** 사이의 간극을 메운다.

- 고전적 데이터 마이닝 — **프로세스를 보지 않는다**, 특히 엔드투엔드 프로세스를
- 고전적 프로세스 모델 분석 — **데이터를 무시한다**

프로세스 마이닝은 **프로세스에 집중하면서 동시에 실제 데이터를 쓴다.** 목적은 **성능(performance) 관련 질문**과 **컴플라이언스(compliance) 관련 질문**에 답하는 것이다.

### 출발점 — 이벤트 로그
모든 것의 출발점은 **이벤트 데이터**다. 표의 각 행이 하나의 **이벤트**이고, 세 가지 필수 속성이 있다.

| 속성 | 뜻 | 시험 예 | 주문 예 | 병원 예 |
|---|---|---|---|---|
| **Case ID** | 프로세스 인스턴스 식별자 | 학생 | 주문 번호 | 환자 |
| **Activity** | 실행된 활동 | 시험 과목 | 활동명 | 활동명 |
| **Timestamp** | 시각 | 시험 날짜 | 타임스탬프 | 타임스탬프 |

추가로 **Resource**(수행한 사람), 그리고 성적·제품·수량·환자 나이 같은 임의의 속성이 붙을 수 있다.

### 모델과 이벤트 데이터의 세 가지 관계

| 관계 | 방향 | 의미 |
|---|---|---|
| **Play-out** | 모델 → 행동 | 모델에서 행동을 생성한다. **시뮬레이션**이나 모델 기반 정보 시스템이 하는 일 |
| **Play-in** | 이벤트 데이터 → 모델 | 예시 행동들로부터 **자동으로 모델을 추론**한다 = **프로세스 발견** |
| **Replay** | 로그를 모델 위에서 재생 | 현실을 모델 위에 다시 흘려보낸다 = **적합성 검사 + 성능 분석** |

**Play-out 예시** — 출장 신청 처리 BPMN 모델. 항상 a(신청 등록)로 시작하고, 이후 두 경로가 동시에 진행된다. 한쪽은 d(예산 확인), 다른 쪽은 b(지역 관리자 승인)와 c 중 선택. 그 뒤 e에서 **XOR-분기**로 승인/거절/정보 부족(되돌아가기) 셋 중 하나를 고른다. 루프가 있어 **가능한 경로는 무한히 많다.**

**Play-in 예시** — 트레이스들이 모두 a로 시작하면 모델도 a로 시작하게 하고, 모두 g나 h로 끝나면 끝에 g/h 선택을 둔다. **손으로 모델링하지 않는다.** 원시 이벤트 데이터에서 자동으로 추론한다.

### Play-in 실전 사례

**네덜란드 주택 공사** — 각 행이 아파트 ID · 활동 · 타임스탬프. 세입자가 임대를 해지한 시점부터 다른 사람에게 다시 임대될 때까지의 전체 프로세스 모델을 자동 추론한다. 확대해 보면 약 30건이 따라간 순차 경로 같은 조각을 볼 수 있다.

**병원** — 20~30개 병원에서 적용했다. 네덜란드의 한 병원에서 동질적인 환자 집단 **600건**으로 모델을 추론하면 **"스파게티" 다이어그램**이 나온다. 이 환자군의 치료 프로세스가 엄청나게 복잡하다는 뜻이다. (뒤에서 단순화 기법을 배운다.) 활동 대신 **부서(department)** 를 노드로 그리면 일이 부서 사이를 어떻게 흐르는지 보인다.

### Replay — 여기서부터가 핵심
> **모델을 배우는 것으로 끝이 아니다. 핵심은 현실을 모델 위에서 재생하는 것이다.** 그 모델을 손으로 만들었든 자동 발견했든 상관없다.

**정상 경우** — 현실에서 `a c d e g` 순서가 일어났고, 모델 위에서 재생해 보면 문제없이 흘러간다.

**활동 누락** — 현실에서 `a c e g`가 일어났다. a는 가능, c도 가능. 그런데 e(결정)를 하려면 모델상 **d(예산 확인)도 실행돼야 한다.** 재생을 계속하되 **"활동 d(예산 확인)가 빠졌다"는 문제를 기록**한다.

**활동 과잉** — `a c h ...` — 프로세스 중간인데 현실에서 h(거절)가 일어났다. 역시 문제로 기록하고 진단을 제공하며 재생을 이어간다.

**실전 사례** — 네덜란드 지자체의 민원 처리(주택 가치 평가에 이의를 제기해 세금을 덜 내려는 사람들). 전체 **적합도(fitness)는 매우 좋았지만**, 재생해 보니 **집이 23번 재평가된** 경우가 발견됐다 — 모델상 일어나면 안 되는 일이었다.

### Replay는 적합성만이 아니다 — 성능 분석
타임스탬프가 있는 이벤트 로그를 모델 위에서 재생하면서 각 활동의 시각을 기록한다. 그러면 **프로세스의 어느 부분에 시간이 얼마나 쓰였는지** 정확히 안다. 활동 사이의 **지연**도 검은 원으로 표시된다.

수십만~수백만 건에 대해 이렇게 하면:
- 활동이 **얼마나 자주** 실행되는지
- 특정 경로가 **얼마나 자주** 선택되는지
- 활동이 **얼마나 오래** 걸리는지
- 활동 사이 **대기 시간과 동기화 시간**
- 그리고 이것들의 **확률 분포**

실전 사례에서는 **지연이 큰 자리(place)를 보라색으로** 표시해 성능 문제 지점을 보여줬다. 나아가 프로세스의 **임의의 두 지점을 찍으면** 그 사이를 흐른 케이스 수와 소요 시간 통계를 볼 수 있다.

### 전체 그림

```
        현실 세계 (사건 발생)
              ↓
        소프트웨어 시스템 (이벤트 기록)
              ↓
          이벤트 데이터
         ↙     ↓      ↘
    발견    적합성 검사   강화
 (discovery) (conformance) (enhancement)
```

| 세 유형 | 대응하는 관계 | 하는 일 |
|---|---|---|
| **발견(discovery)** | **Play-in** | 모델링 없이 원시 이벤트 데이터에서 프로세스 모델을 자동 학습 |
| **적합성 검사(conformance)** | **Replay** | 이벤트 로그와 프로세스 모델을 비교 |
| **강화(enhancement)** | **Replay** | 편차와 성능 정보로 프로세스 모델을 풍부하게 만든다 (예: 병목) |

**Play-out**은 이벤트 데이터를 쓰지 않는 **고전적 프로세스 모델 사용법**에 해당한다.

## 요약
- 프로세스 마이닝 = **발견 · 적합성 검사 · 강화** 세 유형.
- 그 아래에 **Play-out**(모델→행동), **Play-in**(데이터→모델, = 발견), **Replay**(로그를 모델에서 재생, = 적합성+성능)이 있다.
- 이벤트 로그의 **최소 요건은 Case ID · Activity · Timestamp** 셋뿐이다.
- **Replay가 이 코스의 중심 아이디어**다 — 적합성 문제(누락된 활동, 일어나면 안 될 활동)와 성능 문제(병목, 대기 시간)를 같은 방식으로 잡아낸다.
