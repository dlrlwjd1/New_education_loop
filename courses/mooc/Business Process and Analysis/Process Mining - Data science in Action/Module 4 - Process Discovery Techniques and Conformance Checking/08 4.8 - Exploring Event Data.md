# 4.8: Exploring Event Data

## 개요
- 지금까지는 **출력(모델)** 에 집중했다. 이 강의는 **입력(이벤트 로그)** 을 본다.
- **객체 모델(object model)** — 이벤트·케이스·활동·프로세스의 실제 구조.
- **점 차트(dotted chart)** — 모델을 만들기 전에 데이터를 탐색하는 **헬리콥터 뷰**.

## 내용

### 실제 이벤트 데이터 구조는 더 복잡하다

**기본 관계**:
> 이벤트는 **정확히 하나의 케이스**에 속한다. 케이스는 여러 이벤트로 구성되고 **하나의 프로세스**에 속한다. 프로세스는 여러 케이스를 가질 수 있다.

**이벤트 속성**: 활동을 가리키고, 그 외에 **타임스탬프, 자원, 비용, 트랜잭션 정보** 등.
- **타임스탬프** — 이벤트 정렬과 성능 분석에 매우 중요
- **자원(resource)** — 활동 실행에 필요한 **사람, 조직, 기계**. 분석에 매우 중요하므로 **가능한 모든 방법으로 활용**해야 한다

### 트랜잭션 정보와 활동 인스턴스

**생애주기 모델**의 상태들: 시작(start), 완료(complete), 중단(abort), 일시중지(suspend), 재개(resume) 등.

| 시나리오 | 이벤트 수 | 쓸모 |
|---|---|---|
| **완료 이벤트만** | 활동당 1개 | 가장 단순. 트랜잭션 정보가 없는 로그는 대개 완료로 해석 |
| **시작 + 완료** | 활동당 2개 | **활동의 지속 시간 측정**에 매우 중요 |
| **복잡한 경우** | 여러 개 | 시작 → 일시중지 → 재개 → 중단 등 |

> 이런 경로들이 **활동 인스턴스(activity instance)** 이고, **생애주기 모델을 통과하는 경로**로 생각할 수 있다.

**모호성 문제**: 같은 케이스 안에 **같은 활동의 인스턴스가 여러 개** 있을 수 있다(예: 루프). 그런데 **시작 2개, 완료 2개**가 보이면 **어느 시작이 어느 완료에 대응하는지 불분명**하다.

**해결 방법**:
- 이벤트를 기록할 때 **활동 인스턴스에 대한 명시적 참조**를 넣는다
- 없으면 **재생하면서 계산하거나 휴리스틱으로 만든다**
- (다른 혼란도 가능하다 — 시작 2개에 완료 1개인 경우 등)

### 케이스 수준 속성과 파생 속성

**케이스 수준 속성** — 개별 이벤트가 아니라 **케이스 전체의 성질**이다: 고객 유형, 환자의 생년월일, 케이스의 처리 시간(flow time).

**파생 속성(derived attributes)** — 계산해야 하는 속성.
> 예: 케이스의 처리 시간은 **첫 이벤트와 마지막 이벤트**로 계산한다.
>
> 그런데 **분석 중인 케이스만이 아니라 전체 맥락(context)의 정보**를 쓸 수도 있다:
> - 이벤트가 실행될 때 **프로세스가 얼마나 바빴는가?**
> - **가용 자원은 몇 개였는가?**
> - **대기 중인 케이스는 몇 개였는가?**
> - 개별 자원의 **업무 부하(workload)** 를 이벤트 속성으로 추가

> **왜 결정적인가**: 프로세스의 지연 이유를 이해하려는데 **케이스 하나(고객 한 명)만 고립해서 보면 전체 그림을 볼 수 없다.** **개별 이벤트와 케이스를 전체 맥락과 연결해야** 한다.

### 점 차트(dotted chart)

> **모델을 만들기 전에 이벤트 데이터를 탐색하는 기법**이고, **매우 흥미롭고 인상적인 정보를 드러내는 경우가 많다.**

**구조**: **점 하나 = 이벤트 하나.**
| 축 | 내용 |
|---|---|
| **x축** | **시간** |
| **y축** | 이벤트의 성질 — **소속 케이스 / 실행한 자원 / 실행된 작업** |
| **점 색깔** | 예: 그 이벤트를 실행한 사람, 또는 활동 |

**ProM의 두 플러그인**: **dotted chart** 플러그인과 **XDotted chart** 뷰어. 개념은 유사하지만 **성능 문제 등으로 한쪽을 골라 써야 할 때가 있다.**

## 예시 — 500 케이스, 7,500+ 이벤트

(참고용 프로세스 구조: 귀납적 마이너로 발견한 모델 — 한 활동으로 시작 → **동시적이지만 모두 선택적인(건너뛸 수 있는) 세 활동** → 활동 시퀀스 → 루프 → 마지막에 **승인/거절 결정**)

| 뷰 | x축 | y축 | 색깔 | 보이는 것 |
|---|---|---|---|---|
| 1 | 실제 시간 | **케이스** | 활동 | 한 줄이 한 케이스. **케이스별 이벤트 시퀀스** |
| 2 | 실제 시간 | **활동** | 활동 | **어느 시점에 어떤 활동이 실행됐는지.** 패턴이 드러난다 |
| 3 | 실제 시간 | 활동 | **자원** | **특정 자원 유형과 특정 행(활동) 사이의 뚜렷한 상관** — 특정 자원이 특정 활동 집합을 실행한다 |
| 4 | 실제 시간 | **자원** | 활동 | 뷰 3과 **직교(orthogonal)**. **어느 시점에 어느 자원이 바쁜지** |
| 5 | **상대 시간** | 케이스 | 활동 | 모든 케이스가 **시간 0에서 시작**하고 같은 활동으로 시작(빨간 선). **위쪽은 매우 짧게 끝난 케이스, 아래쪽은 훨씬 오래 걸린 케이스** → **케이스 지속 시간에 대한 통찰** |
| 6 | 상대 시간 | 활동 | — | 같은 아이디어를 활동 기준으로 |
| 7 | **논리적 시간(logical time)** | 케이스 | — | 실제 시간 차이는 무시하고 **케이스의 첫 번째 이벤트, 두 번째 이벤트…** 순번으로 배치 |

## 요약
- 실제 이벤트 데이터 구조는 단순한 표보다 복잡하다 — **이벤트 ↔ 활동 인스턴스 ↔ 활동**의 관계, **케이스 수준 속성**, **파생 속성**.
- **트랜잭션 정보**(시작/완료 등)가 있으면 **활동 지속 시간**을 측정할 수 있지만, **어느 시작이 어느 완료에 대응하는지 모호**할 수 있어 활동 인스턴스 참조나 휴리스틱이 필요하다.
- **맥락 정보**(당시의 업무량, 가용 자원, 대기 케이스 수)를 이벤트에 붙이면 훨씬 정교한 분석이 가능하다. **케이스 하나만 고립해 보면 지연의 이유를 알 수 없다.**
- **점 차트**는 모델을 만들기 전 **데이터 탐색용 헬리콥터 뷰**다. **x축(실제/상대/논리적 시간), y축(케이스/활동/자원), 색깔**의 조합만 바꿔도 완전히 다른 통찰이 나온다.
