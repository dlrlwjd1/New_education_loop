# The MLflow Migration — Role Play

## 개요
- 음성 채팅 기반 AI 롤플레이 활동(15분) — 리드 머신러닝 엔지니어가 되어 엔지니어링 VP에게 GPU 사용과 MLflow 도입을 정당화하는 시뮬레이션. Module 1·2 전체 내용(모델 개발 생애주기, CPU/GPU, MLflow)을 실전처럼 적용해보는 자리.

## 내용

### 시나리오
- 리드 머신러닝 엔지니어로서, 엔지니어링 VP **Sarah**와의 중요한 미팅을 앞두고 있음. Sarah는 실용적인 접근을 중시하며, 명확하고 실질적인 이점이 없으면 새로운 도구 도입에 다소 주저하는 성향.
- 팀은 일관성 없는 실험 추적과 모델 버전에 대한 혼란으로 비효율을 겪어왔음. 머신러닝 운영을 간소화할 명확한 비전을 제시할 기회.
- Sarah는 경청할 준비가 되어 있지만, 제안하는 솔루션이 현재의 문제점을 직접적으로 해결하고 워크플로를 개선한다는 확실한 근거와 명확한 이해를 요구할 것.

### 목표
- **모델 개발 생애주기**를 설명.
- 특정 워크로드에 **GPU** 사용을 정당화.
- **MLflow**가 팀의 실험·버전 관리 프로세스를 어떻게 전문화(professionalize)할지 시연.

### 종합 답변 (강의 개념 기반)
- **모델 개발 생애주기 설명**: 데이터 과학자가 사용 사례에 맞는 모델을 선택 → Jupyter/Colab/SageMaker 등에서 실험 실행 → 정밀도·재현율로 평가 → 하이퍼파라미터 튜닝(그리드 서치, 교차 검증)으로 최적화 → 최종 모델을 버전 관리·배포하는 흐름을 설명.
- **GPU 사용 정당화**: 현재 워크로드가 대용량 데이터셋의 반복적 학습이나 딥러닝 모델을 포함한다면, CPU의 순차 처리보다 GPU의 병렬 처리(수천 개의 코어, 높은 메모리 대역폭)가 학습 시간을 크게 단축시킨다는 점을 근거로 제시. 다만 GPU는 비용이 크고 구하기 어려우므로, 실제로 병렬 연산이 필요한 작업(행렬·벡터 연산 중심)에 한해 요청하는 것이 합리적임을 강조 — 즉 무분별한 GPU 요청이 아니라 워크로드 특성에 근거한 요청임을 보여주는 것이 핵심.
- **MLflow로 전문화 시연**: 현재 팀이 겪는 "일관성 없는 실험 추적"과 "모델 버전 혼란"이라는 두 가지 통증 지점(pain point)을 MLflow의 두 핵심 기능으로 직접 해결:
  - **Tracking**: 모든 실험(하이퍼파라미터, 코드, 데이터, 결과)을 자동 기록해, 어떤 모델이 어떤 설정으로 어떤 성능을 냈는지 한곳에서 비교 가능 — 더 이상 스프레드시트나 개인 메모에 의존할 필요 없음.
  - **Model Registry**: 모델을 버전별로 등록·관리(Docker 레지스트리와 유사한 개념)해, 어느 버전이 프로덕션에 있고 어느 버전이 아카이브되었는지 명확히 파악 가능 — 팀 간 협업과 감사(audit)가 쉬워짐.
- 이 두 가지를 데모(예: 실험 비교 UI, 모델 레지스트리의 버전 태그)로 보여주면 Sarah가 요구하는 "실질적 이점"을 구체적으로 입증할 수 있음.

## 요약
- 이 롤플레이는 "왜 GPU가 필요한가"와 "왜 MLflow가 필요한가"라는 두 가지 실용적 질문에, 워크로드 특성(병렬 연산)과 팀의 실제 통증 지점(추적·버전 혼란)에 근거해 답하는 연습이며, 추상적 이론이 아니라 구체적 문제 해결로 이어지는 논리를 세우는 것이 핵심이다.
