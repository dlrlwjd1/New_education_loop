# Determining the Correct Storage Medium

## 개요
- AWS의 다양한 스토리지 매체(키-값/그래프/SQL 데이터베이스, 데이터 레이크, S3, EFS, EBS)의 특징과 적합한 사용 사례를 비교하는 3분 영상.

## 내용

### 데이터베이스 유형
- **키-값 데이터베이스(DynamoDB)**: 사용자 레코드나 게임 통계처럼 단순 조회에 이상적.
- **그래프 데이터베이스(Neptune)**: 관계(relationship)를 구축하는 데 활용 — 소셜 그래프에서 핵심 인물을 식별하거나 중심성(centrality) 같은 기술 통계를 구하는 데 유용한, 새로운 데이터 과학 워크플로의 중요한 부분이 될 수 있음.
- **SQL(Aurora, RDS)**: 전통적인 트랜잭션 기반 쿼리에 적합.

### 데이터 레이크(Data Lake)
- S3 위에 구축되며, 컴퓨트·스토리지 관점에서 거의 무한대에 가까운 규모로 확장 가능.
- 데이터 레이크는 S3 위에 **메타데이터**를 추가해 내부 콘텐츠를 인덱싱할 수 있게 함 — 예: **AWS Glue**로 S3의 특정 부분을 인덱싱한 뒤 **Athena**로 쿼리.

### S3
- 객체 스토리지의 대표 주자 — 라이프사이클 관리가 필요하거나, 대용량 파일을 저장하거나, 점진적으로 읽고 쓰기보다는 "전체를 한 번에 가져오거나 저장하는(all-or-nothing)" 접근 방식이 괜찮은 경우에 최적.

### EFS(Elastic File System)
- **NFS 방식의 EFS**: 부하나 저장 용량에 따라 디스크 I/O를 점진적으로 확장 가능. 클러스터·마운트 포인트가 생태계 전체에서 균일하게 유지됨. 수십 년간 존재해온 네트워크 마운트 포인트 개념이 클라우드에서 완전관리형으로 제공되는 것이 핵심 장점.
- **FSx for Windows**: 중앙집중식 마운트 포인트가 필요한 워크플로에 유용하며, AWS가 스토리지를 대신 관리.

### EBS(Elastic Block Store)
- **커스텀 디스크 I/O**를 설정할 수 있다는 장점 — 트랜잭션이나 머신러닝 학습처럼 매우 빠른 파일 시스템이 필요한 특정 작업에 맞춰 프로비저닝했다가 작업 후 제거 가능.
- 단, EBS는 **단일 마운트 포인트**로만 사용 가능하다는 제약이 있음.

### 핵심 통찰
- AWS는 거의 모든 유형의 스토리지 매체를 제공하며, 각 매체 아래에도 다양한 하위 범주가 존재. 데이터 과학자·ML 엔지니어·데이터 엔지니어는 주어진 작업에 맞는 올바른 스토리지 매체 조합을 선택해야 하는 책임이 있음.

## 요약
| 스토리지 유형 | 대표 서비스 | 적합한 사용 사례 |
|---|---|---|
| 키-값 DB | DynamoDB | 사용자 레코드, 게임 통계 |
| 그래프 DB | Neptune | 관계 구축, 소셜 그래프 분석 |
| SQL | Aurora, RDS | 트랜잭션 기반 쿼리 |
| 데이터 레이크 | S3 + Glue + Athena | 인덱싱된 대규모 데이터 쿼리 |
| 객체 스토리지 | S3 | 대용량 파일, all-or-nothing 접근 |
| 파일 시스템 | EFS(NFS/FSx) | 다중 마운트 포인트, 점진적 확장 |
| 블록 스토리지 | EBS | 단일 마운트, 커스텀 고성능 I/O |
