# Bridging the Gap (DevOps to MLOps) — Role Play

## 개요
- 음성 채팅 기반 AI 롤플레이 활동(15분) — 신임 MLOps 엔지니어가 되어 숙련된 DevOps 디렉터에게 MLOps의 필요성을 설명하는 시뮬레이션. Module 1 전체 내용(MLOps 생애주기, CI/CD/CT/CM, 아키텍처)을 실전처럼 적용해보는 자리.

## 내용

### 시나리오
- 성장 중인 핀테크 회사의 첫 MLOps 엔지니어로 막 합류. 데이터 과학팀이 ML 모델을 개발해왔지만, 배포 과정에서 어려움을 겪어 프로덕션에서 문제가 자주 발생.
- Platform Engineering 디렉터 **Marcus**(숙련된 DevOps 베테랑)와의 첫 미팅을 앞두고 있음. Marcus는 머신러닝을 그저 또 다른 형태의 소프트웨어로 보고 있어, 왜 특화된 인프라나 프로세스가 필요한지 궁금해함.

### 목표
- **MLOps 생애주기**를 설명하고, 전통적인 CI/CD만으로는 왜 충분하지 않은지 — 특히 **모델 드리프트(model drift)** 때문에 **지속적 학습(CT)**과 **지속적 모니터링(CM)**이 필요한 이유를 정당화.
- 팀의 GitHub 리포지토리를 위한 고수준 MLOps 아키텍처를 제안 — 코드 변경이 소프트웨어 환경과 모델 재학습 양쪽 모두를 위한 자동화된 워크플로를 어떻게 트리거해야 하는지 개괄.

### 종합 답변 (강의 개념 기반)
- **왜 전통적 CI/CD로는 부족한가**: 전통적인 소프트웨어는 코드가 변하지 않는 한 동작이 변하지 않지만, ML 모델은 배포된 이후에도 실제 세계의 데이터 분포가 변화(모델 드리프트)하면서 성능이 저하될 수 있음 — 코드는 그대로인데 모델이 "낡아가는" 현상. 따라서 코드의 통합·배포만 다루는 CI/CD에, 데이터와 모델 성능을 지속적으로 추적하는 **CT/CM**이 추가로 필요.
- **CT(지속적 학습)**: 새 데이터가 들어올 때 자동으로 재학습 파이프라인을 트리거해 모델을 최신 상태로 유지(자동화된 재학습, 데이터 버전 관리, 하이퍼파라미터 튜닝, 배포 전 검증 포함).
- **CM(지속적 모니터링)**: Prometheus/Grafana 같은 도구로 정확도·지연시간 등을 실시간 추적하고, 데이터·모델 드리프트를 탐지해 알림을 보내며, 재학습이 필요한 시점을 판단하는 근거를 제공.
- **제안하는 고수준 아키텍처**: GitHub 리포지토리에 대한 코드 변경(예: 애플리케이션 코드 수정)은 기존처럼 CI/CD 파이프라인(Jenkins/GitLab CI 등)을 트리거해 소프트웨어 환경을 빌드·배포. 이와 별개로, 데이터 소스의 변경이나 스케줄(예: 매일 밤)에 따라 별도의 파이프라인(Airflow/Kubeflow 등)이 트리거되어 데이터 검증 → 모델 재학습 → 모델 평가 → (기준 통과 시) 모델 레지스트리 등록 → 배포까지 자동화. 두 파이프라인 모두 MLflow 같은 도구로 실험·버전을 추적해 재현성을 보장.

## 요약
- 이 롤플레이는 "코드는 안 변해도 모델은 낡아간다(모델 드리프트)"는 MLOps의 핵심 통찰을 DevOps 베테랑에게 설득력 있게 설명하고, 코드 파이프라인과 데이터/모델 파이프라인을 분리하되 각각 자동화된 이중 아키텍처를 제안하는 연습이다.
