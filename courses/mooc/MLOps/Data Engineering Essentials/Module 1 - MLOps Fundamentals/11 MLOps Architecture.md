# MLOps Architecture

## 개요
- 문제 정의부터 프로덕션 배포·모니터링까지 이어지는 MLOps의 고수준 아키텍처를 순서도 형태로 설명하고, 각 단계에서 MLOps 엔지니어의 역할을 명확히 하는 5분 영상.

## 내용

### 전체 흐름

1. **문제 정의(Problem Statement)**: 무엇을 해결하려 하는가로 시작.
2. **데이터 수집(Data Collection)**: 문제 정의에 필요한 데이터를 모음.
3. **데이터 수집/적재(Ingestion)**: 데이터가 구글 시트, 데이터베이스, 공개 데이터 등 어디에 있든 시스템으로 가져옴.
4. **변환·정제(Transform & Clean)**: 모든 데이터가 같은 형식이 아니므로 정제 필요.
5. **데이터 분석(Data Analysis)**: 실제 수치로 문제 정의를 이해.
6. **시각화(Visualization)**: 문제를 더 명확히 분석하는 데 도움.
7. **의사결정 지점 1 — ML이 필요한가?**: 답이 "아니오"면 문제 정의로 돌아가 재정의하거나 프로젝트를 폐기. "예"면 다음 단계로.

### ML 모델링 단계
8. **피처 엔지니어링(Feature Engineering)**: 모델에 필요한 피처를 수집해 **피처 스토어(feature store)**에 저장.
9. **모델 탐색(Model Exploration)**: 이 사용 사례에 어떤 ML 모델이 더 적합한지 실험 → 결과 저장 → 출력 분석(데이터 분석과 유사하게, 학습 데이터에 대한 여러 모델의 출력을 비교).
10. **모델 구축·학습(Model Building & Training)**: 더 큰 데이터로 모델을 구축·학습.
11. **모델 평가(Model Evaluation)**: 올바른 모델을 선택하고, "이 ML 모델이 문제를 해결하는가?"를 다시 질문.

### 의사결정 지점 2 — 왜 이 단계에서 다시 판단하는가
- 문제가 ML로 해결 가능하다고 판단했더라도, 실제로 모델을 구축해 전체 데이터를 통과시켜보면 같은 확신을 갖지 못할 수 있음 — 따라서 배포하지 말고 모델 평가 단계에서 다시 질문해야 함.
- 답이 "애매함(maybe)"이면 학습 데이터가 적절하지 않을 가능성이 있으므로 **피처 엔지니어링 → 모델 탐색 → 모델 구축 → 모델 학습 → 모델 평가** 과정을 반복.
- 답이 "아니오"면 다시 문제 정의로 돌아감.
- 답이 "예"면 다음 단계로.

### 배포와 지속적 순환
12. **프로덕션 배포**: 모델이 실제 사용자 트래픽을 받게 됨.
13. **모니터링·디버깅**: 배포 이후에도 작업은 끝나지 않음 — 지속적으로 모델을 모니터링·디버깅.
14. **재학습 필요 시**: 다시 **데이터 수집** 지점으로 돌아감 — 모델이 프로덕션에 있다는 것은 사용자 입력을 받는다는 뜻이고, 미래에는 더 많고 다양한 입력을 받게 되므로 모델을 업데이트해야 하고, 이를 위해 전체 단계를 처음부터 다시 수행.

### MLOps 엔지니어의 역할
- MLOps 엔지니어의 주요 목표는 **피처 엔지니어링, 모델 탐색, 모델 구축, 모델 학습, 모델 평가** 단계에서 데이터 과학자를 돕는 것 — 이를 위한 구체적인 도구들이 존재하며, 이를 구축·유지하는 것이 MLOps 엔지니어의 역할.
- 다만 여기에 국한되지 않음 — 소규모 조직에서는 MLOps 엔지니어가 **데이터 수집, 데이터 적재, 데이터 변환·정제, 데이터 분석**까지 직접 손을 대야 할 수도 있음.
- 이 외에도 적절한 **CI/CD 시스템, 테스트, 모니터링·디버깅 설정**을 구축하고 ML 모델이 확장 가능하도록 보장하는 것도 역할.

## 요약
- MLOps 아키텍처는 문제 정의 → 데이터 수집·적재·정제·분석·시각화 → (ML 필요 여부 판단) → 피처 엔지니어링 → 모델 탐색·구축·학습·평가 → (모델이 문제를 해결하는지 재판단) → 프로덕션 배포 → 모니터링·디버깅 → (재학습 필요 시 데이터 수집으로 회귀)의 순환 구조를 가지며, 두 번의 핵심 의사결정 지점(ML 필요 여부, 모델의 실제 문제 해결 여부)이 프로세스 전반에 걸쳐 있다.
