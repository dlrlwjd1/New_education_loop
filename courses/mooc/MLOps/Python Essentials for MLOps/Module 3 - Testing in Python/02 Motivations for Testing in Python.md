# Motivations for Testing in Python

## 개요
- 테스트를 왜 해야 하는지에 대한 3가지 흔한 변명(excuse)을 반박하며, 테스트가 소프트웨어 개발에서 왜 필수적인지 설명한다.

## 내용

### 변명 1 — "시간이 너무 많이 든다"
- 맞는 말이다, 테스트는 초반에 시간 투자가 필요하다. 하지만 **투자 대비 돌아오는 이득(ROI)이 결국 더 크다** — 프로젝트가 커질수록 테스트 없이 디버깅하는 데 훨씬 더 많은 시간이 든다.
- 처음부터 과하게 하지 말고, 필요한 만큼 자기 페이스에 맞춰 테스트를 추가해나가면 된다.

### 변명 2 — "너무 어렵다"
- 다른 무엇이든 그렇듯, **좋은 테스트를 작성하는 것도 연습이 필요**하다.
- 좋은 테스트는 보통 빠르고(특히 유닛 테스트), **무엇이 실패했는지, 무엇을 기대했는지를 명확히 알려준다** — 실패 원인을 파악하고 고치는 데 좋은 기반을 제공한다.

### 변명 3 — "내 코드는 완벽해서 버그가 없다"
- **모든 소프트웨어에는 버그가 있다** — 경력이 얼마나 되든 예외는 없다.
- 테스트가 있으면 **배포 전에 버그를 미리 발견**할 수 있고, 패치 후 **수정이 실제로 됐는지 검증**할 수도 있다.
- 버그를 고쳤다고 "생각"하는 것과, 테스트로 실제로 고쳐졌음을 확인하는 것은 다르다 — 자동화하지 않을 이유가 없다.

### "잘못되면 누구를 탓할 것인가?"
- 테스트를 안 하고 배포한다는 것은, 사실상 **누군가 소프트웨어에 문제가 있다고 불평할 때까지 기다리는 것**과 같다.
- 예: 검증해야 할 단계가 30개라면, 사람은 실수로 한 단계를 빼먹거나 오타를 낼 수밖에 없다 — **자동화(테스트)는 견고하고 유지보수 가능한 소프트웨어의 기초**가 된다.

## 예시
> 강사의 핵심 메시지: "테스트가 없다는 것은 사실 테스트를 안 하는 게 아니라, 사용자가 버그를 찾아줄 때까지 기다리는 것이다."

## 요약
- 테스트에 대한 3가지 흔한 변명(시간·난이도·"내 코드는 완벽함") 모두 실제로는 테스트를 하지 않을 이유가 되지 못한다.
- 테스트는 초기 투자 대비 장기적으로 디버깅 시간을 줄여주고, 배포 전 문제를 미리 발견하며, 수정 사항을 검증하는 안전망 역할을 한다.
