# Python API Best Practices

## 개요
- API를 만들 때 지켜야 할 모범 사례 — **적절한 HTTP 상태 코드 사용법**과 **HTTP 메서드(GET/POST/PUT/HEAD)의 의미 구분**, 그리고 **엔드포인트 문서화의 중요성**을 실전 예시와 함께 다룬다.

## 내용

### HTTP 에러 코드를 정확히 쓰는 것의 중요성
- **401 Unauthorized**: 리소스 접근에 인증/인가가 필요한데 클라이언트가 그 권한이 없을 때.
- **400 Bad Request**: 보통 스키마 검증 실패 시 — 예를 들어 정수(integer)를 기대하는데 문자열(string)이 왔을 때.
- **404 Not Found**: 단순히 "리소스가 없음"을 넘어서, **보안 목적으로 리소스의 존재 여부 자체를 숨기고 싶을 때도 사용**한다 — 예: 인증되지 않은 사용자가 특정 사용자명이 존재하는지 캐내려 할 때(피싱 방지), "권한 없음"이라고 알려주는 대신 그냥 404를 반환해 존재 여부 자체를 감춤.

### HTTP 메서드의 의미 구분
| 메서드 | 의미 |
|---|---|
| GET | 읽기 전용(read-only) 요청 — 서버는 아무것도 쓰지 않고 기존 데이터/리소스를 그대로 반환. DB의 읽기 전용 복제본에 매핑하기 좋음 |
| POST | 쓰기(write)/생성 — 새 리소스(예: 신규 사용자)를 만들 때 |
| PUT | 이미 존재하는 리소스의 내용을 갱신(update)할 때 — 예: 기존 사용자의 주소가 바뀐 경우 |
| HEAD | 리소스가 존재하는지만 가볍게 확인하고 싶을 때 — 응답 본문 없이 존재 여부만 확인(클라이언트 부담 최소화) |

### HEAD 메서드 실전 예시
- 실제 코드 예시(다른 프레임워크)에서, `HEAD` 메서드로 정의된 함수는 DB에서 바이너리를 찾아보고 **없으면 404, 있으면 빈 딕셔너리(빈 JSON)를 반환**한다 — "존재는 하지만 본문은 내려주지 않는다"는 HEAD의 취지에 맞음.
- 반면 같은 리소스에 대한 GET은 **완전한 본문을 채워서 반환**한다 — GET과 HEAD의 역할 차이가 명확히 드러남.

### 문서화의 중요성
- 강사는 앞서 만든 Hugging Face 기반 예제 API가 **엔드포인트를 제대로 문서화하지 않았다는 점을 스스로 지적**한다 — `/generate`가 무슨 입력을 기대하는지 알려면 코드(`Body` 정의)를 직접 봐야 했음.
- **프로덕션 코드/애플리케이션을 만들 때는 항상 엔드포인트를 문서화하고 예시를 제공해야 한다** — FastAPI의 `/docs` 같은 자동 문서화 기능을 적극 활용할 것.

## 요약
- 상황에 맞는 정확한 HTTP 상태 코드(401/400/404)와 메서드(GET/POST/PUT/HEAD)를 쓰는 것이 API 설계의 기본이다.
- 404는 단순 "없음"뿐 아니라 보안상 존재 여부를 숨기는 용도로도 쓰이며, HEAD는 본문 없이 존재 여부만 확인하는 가벼운 요청이다.
- 프로덕션 API는 반드시 엔드포인트와 입출력 예시를 문서화해야 한다.
