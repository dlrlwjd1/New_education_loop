# Constructing Realistic Evaluation Data

## 개요
- 프로덕션 로그에서 골드 스탠다드(gold standard) 평가 데이터셋을 구축하는 방법 — 프로덕션 소스, 계층화 샘플링(stratified sampling), 전문가 라벨링, 버전 관리라는 4대 요건과 실전 200개 예시 데이터셋 구축 워크플로를 다루는 8분 영상. "Designing LLM Evaluation Datasets" 레슨의 첫 번째 영상.

## 내용

### 왜 평가 데이터가 중요한가
- 모델 평가는 그것을 테스트하는 데 사용된 데이터보다 좋을 수 없음 — 평가셋이 비현실적이거나, 너무 깨끗하거나, 너무 합성적이거나, 너무 쉬우면 결과는 좋아 보여도 시스템은 프로덕션에서 실패할 수 있음.
- 핵심 아이디어: 프로덕션 로그에서 골드 스탠다드 평가셋으로 어떻게 이동하는지 — 평가 데이터는 실제 사용자 행동, 실제 요청 카테고리, 실제 실패 패턴을 반영해야 함.

### 현실적인 평가 데이터셋의 4가지 핵심 요건
1. **프로덕션 로그에서 소싱**: 합성 예시나 선별된(cherry-picked) 예시가 아니라 실제 사용자 질의를 사용 — 합성 데이터는 실제 사용에서 나타나는 지저분하고, 모호하고, 반복적인 패턴을 놓칠 수 있음.
2. **카테고리별 계층화(Stratification by Category)**: 평가셋이 프로덕션 분포를 반영해야 함(예: 청구 26%, 기술 문제 24% 등) — 분포가 비현실적이면 평가가 더 쉽거나 덜 흔한 케이스로 편향될 수 있음.
3. **80-20 분할**: 데이터셋의 약 80%는 정상적인 프로덕션 질의를, 20%는 엣지 케이스나 적대적(adversarial) 예시를 포함해야 함 — 일반 성능과 견고성(robustness)을 모두 측정하는 데 도움.
4. **골드 라벨(Gold Labels)**: 각 예시는 **2명의 도메인 전문가**가 라벨링하고, 팀은 **Cohen's Kappa 임계값 0.7**로 확인해 라벨이 신뢰할 수 있고 한 사람의 의견에만 의존하지 않도록 해야 함.
5. **데이터셋 크기**: **80% 신뢰도에서 5%의 품질 차이를 탐지하려면 최소 약 200개 예시**가 필요.
- 핵심 요점: 강력한 평가 데이터는 현실적이고, 대표성 있고, 신뢰할 수 있고, 의미 있는 비교를 뒷받침할 만큼 충분히 커야 함.

### 200개 예시 평가셋 구축 워크플로
1. 30일치 프로덕션 로그를 가져와 청구, 기술 등 요청 카테고리의 분포를 계산 — 실제 프로덕션 트래픽에 대한 명확한 그림을 얻음.
2. **비례 샘플(proportional sample)** 생성 — 160개의 대표 예시 + 40개의 엣지/실패 사례(80-20 원칙이 실제로 적용되는 지점).
3. 2명의 전문가가 예시를 **독립적으로** 라벨링 → **Cohen's Kappa**로 합의도 계산 → 0.7 미만이면 라벨러들이 사례를 재논의해 불일치를 해소 — 이 단계가 최종 라벨에 대한 신뢰를 높임.
4. **편향 체크(bias check)**: `value_counts(normalize=True)`로 5% 미만인 카테고리를 플래그 — 평가셋에서 과소 대표될 수 있는 카테고리를 식별하는 데 도움.
5. **데이터셋을 버전 관리·동결**: 예를 들어 `eval_v1.json`을 변경 로그(change log)와 함께 커밋 — 평가가 정의되면 실험 동안 안정적으로 유지되어야 하기 때문에 중요.
- 핵심 요점: 현실적인 평가 데이터셋은 캐주얼하게 수집되는 것이 아니라, 샘플링·라벨링·합의 확인·편향 체크·버전 관리라는 반복 가능한 프로세스를 통해 구축됨.

### 핵심 원칙 4가지
1. **프로덕션 소스 데이터**: 실제 사용자 질의가 합성 샘플보다 더 가치 있음 — 실제 시스템 행동과 실제 사용자 기대를 반영하기 때문.
2. **계층화 샘플링**: 평가셋이 프로덕션 분포와 일치해야 팀이 실수로 잘못된 종류의 케이스에 최적화하지 않게 됨.
3. **전문가 합의(Expert Consensus)**: 최소 2명의 라벨러가 예시를 검토해야 하고, 평가자 간 합의도(inter-rater agreement)가 라벨을 신뢰할 수 있을 만큼 높아야 함.
4. **버전 관리**: 평가 데이터셋은 코드처럼 동결되고 버전 관리되어야 함 — 실험 도중에는 절대 데이터셋을 재샘플링해서는 안 됨(비교가 신뢰할 수 없게 되기 때문).
- 핵심 메시지: 좋은 평가 데이터는 무작위가 아니라, 프로덕션 현실을 반영하면서도 시간이 지나도 안정적이고 신뢰할 수 있도록 신중하게 설계됨.

### 골드셋 SQL 예시
- `goal_set.sql` — 검토된(reviewed) 프로덕션 사례를 가져와 골드셋을 구축하는 쿼리.
- `SELECT prompt, response, label`: 평가에 필요한 핵심 필드를 가져옴.
- `FROM production_reviews`: 검토된 프로덕션 기록에서 데이터가 나옴을 보여줌.
- `WHERE issue_type IS NOT NULL AND resolved = true`: 사례가 분류되고 의미가 있으며, 노이즈가 있거나 불안정한 라벨을 가질 수 있는 미해결 사례를 걸러냄.
- `ORDER BY updated_at DESC`: 가장 최근에 검토된 예시를 우선시함.
- `LIMIT 500`: 팀이 최종 평가셋을 샘플링할 관리 가능한 풀(pool)을 제공.
- 핵심 요점: 평가 데이터는 검토되고, 해결되고, 최근인 프로덕션 예시에서 가져올 때 더 강력해짐 — 골드셋을 더 현실적이고 신뢰할 수 있게 만듦.

### 실전 교훈
1. **검토된 프로덕션 사례로 시작하라**: 실제 사용자 행동을 대체로 대표하기 때문.
2. **미해결 사례를 걸러내라**: 라벨을 노이즈 있고 신뢰할 수 없게 만들 수 있기 때문.
3. **실패 모드를 위해 갱신하라**: 최근 실패가 가치 있음 — 무시하면 어제의 실패 패턴이 내일의 회귀(regression)가 될 수 있기 때문.
- 결과: 골드셋이 이상화된 사용 버전이 아니라 실제 사용을 반영하게 됨.

### 결론
- 평가 데이터는 검토된 프로덕션 예시와 샘플 라벨에서 소싱될 때 더 강력해짐 — 이것이 이 레슨의 핵심 교훈.

## 예시
```sql
-- goal_set.sql (골드셋 구축용)
SELECT prompt, response, label
FROM production_reviews
WHERE issue_type IS NOT NULL
  AND resolved = true
ORDER BY updated_at DESC
LIMIT 500;
```

```text
[200개 예시 평가셋 구축 워크플로]
30일 프로덕션 로그 → 카테고리 분포 계산
        │
        ▼
비례 샘플: 160개 대표 예시 + 40개 엣지/실패 사례 (80-20 원칙)
        │
        ▼
전문가 2명 독립 라벨링 → Cohen's Kappa 계산
        │
        ├─ κ < 0.7 → 재논의로 불일치 해소
        └─ κ ≥ 0.7 → 통과
        │
        ▼
편향 체크: 5% 미만 카테고리 플래그
        │
        ▼
버전 관리·동결: eval_v1.json + 변경 로그
```

## 요약
- 현실적인 LLM 평가 데이터셋은 프로덕션 로그에서 소싱하고, 실제 카테고리 분포를 반영하는 계층화 샘플링(80% 정상 케이스 + 20% 엣지 케이스)을 적용하며, 2명의 전문가가 라벨링하고 Cohen's Kappa 0.7 이상으로 합의를 확인하고, 최소 200개 예시로 5% 품질 차이를 탐지할 수 있게 구성한 뒤, 코드처럼 버전 관리·동결하여 실험 중간에 재샘플링하지 않는 반복 가능한 프로세스를 통해 만들어져야 한다.
