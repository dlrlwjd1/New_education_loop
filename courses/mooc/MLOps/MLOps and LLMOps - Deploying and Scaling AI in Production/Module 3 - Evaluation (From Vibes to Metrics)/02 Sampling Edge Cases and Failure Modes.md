# Sampling Edge Cases & Failure Modes

## 개요
- 평가셋이 일반적인 질의뿐 아니라 **엣지 케이스와 실패 모드**까지 포함해야 하는 이유와, 5가지 엣지 케이스 유형, 그리고 재시도 횟수·판정 점수를 활용한 실전 샘플링 코드를 다루는 7분 영상.

## 내용

### 왜 엣지 케이스가 필요한가
- 시스템이 흔한 케이스에서는 잘 작동해도 중요한 상황에서 심각하게 실패할 수 있음 — 그래서 평가 커버리지는 취약성(brittleness)을 드러내는 어렵고, 희귀하고, 리스크가 가장 큰 케이스를 포함해야 함.
- 이런 케이스들은 무작위 추측이 아니라 **실제 실패, 에스컬레이션, 통계적 이상치, 적대적 시도**에서 나와야 함.

### 5가지 엣지 케이스 유형
1. **실패 기반 엣지 케이스(Failure-driven)**: 로그된 오류, 사용자 에스컬레이션, 퍼징(fuzzing)에서 나옴 — 가장 가치 있는 엣지 케이스는 대체로 시스템이 이미 프로덕션에서 약점을 보인 곳에서 나옴.
2. **프로덕션에서 플래그된 케이스**: 사용자가 이슈를 에스컬레이션했거나 부정적(thumbs-down) 신호를 준 질의 — 프로덕션 시스템 자체가 경험이 어디서 무너졌는지 팀에게 알려줌.
3. **통계적 엣지 케이스**: 응답 길이의 **95번째 또는 99번째 백분위수**에 있는 질의 — 이 이상치들은 정상 입력과 다른 방식으로 시스템에 스트레스를 줄 수 있고 성능·신뢰성 문제를 드러낼 수 있음.
4. **적대적 케이스(Adversarial)**: 프롬프트 인젝션 시도 같은 수작업으로 만든 예시 — 시스템 견고성 테스트를 위해 5~10개 정도 생성 권장.
5. **합성 엣지 케이스(Synthetic)**: LLM이 알려진 실패 사례의 패러프레이즈(paraphrase)를 생성 — 팀이 이미 식별한 실패 패턴 주변의 커버리지를 확장하는 데 도움.
- 핵심 요점: 엣지 케이스는 여러 소스에서 나오지만, 가장 강력한 세트는 대체로 실제 실패와 표적화된 스트레스 테스트의 조합에서 만들어짐.

### 체계적인 수집 파이프라인
- 엣지 케이스 수집은 무작위가 아니라 체계적이어야 함 — 로그 실패, 사용자 에스컬레이션, 카운트다운 피드백(부정 반응), 길거나 특이한 응답, 적대적/합성 테스트 케이스 등 프로덕션의 신호를 마이닝하는 것에서 시작.
- 팀은 큰 사고가 발생하기를 기다렸다가 평가셋을 개선해서는 안 됨 — 파이프라인의 일부로 어려운 케이스를 **지속적으로** 수집해야 함.
- 중요한 이유: 프로덕션 실패 모드는 시간이 지나며 변함 — 특히 프롬프트 업데이트, 검색 변경, 모델 교체 이후 시스템이 한 영역에서는 강해지고 다른 영역에서는 약해질 수 있음. 엣지 케이스 커버리지는 한 번 만들고 잊는 것이 아니라, 시스템과 사용자가 진화함에 따라 계속 갱신되어야 함.

### 핵심 원칙 4가지
1. **실패 기반 샘플링**: 가상의 시나리오가 아니라 **실제 프로덕션 실패**에서 엣지 케이스를 가져올 것.
2. **20% 할당**: 엣지 케이스가 평가셋의 **20%**를 차지해야 함 — 정상 프로덕션 분포를 압도하지 않으면서 다양한 케이스를 충분히 커버.
3. **지속적 갱신**: 프로덕션 실패 모드가 진화함에 따라 **분기별(quarterly)**로 새 엣지 케이스를 추가할 것을 권장.
4. **근거 문서화**: 모든 엣지 케이스에 왜 그것을 테스트하는 것이 중요한지 설명하는 주석을 포함 — 데이터셋을 검토·유지·정당화하기 쉽게 만듦.
- 엣지 케이스 커버리지는 실제 실패에 기반하고, 신중하게 비율이 정해지고, 정기적으로 갱신되고, 명확히 문서화될 때 더 가치 있어짐.

### 코드 예시: `sampler.py`
- 취약한(brittle) 행동을 식별하는 실전 방식:
  1. 프로덕션 케이스를 로드하는 로그를 가져옴.
  2. **재시도 횟수(retry count) > 1**(시스템이 어려움을 겪어 여러 번 시도가 필요했음을 의미) 또는 **판정 점수(judge score) < 0.4**(출력 품질이 나쁘다고 평가됨)인 케이스로 필터링.
  3. **계층화 샘플링(stratified sample)**을 사용해 실패 로그(failure log)별로 샘플링 — 하나의 시끄러운(noisy) 실패 유형이 데이터셋을 지배하지 않도록 하는 것이 중요.
- 핵심 요점: 엣지 케이스 선택은 무작위가 아니라 명확한 취약성 신호(brittleness signal)와 실패 카테고리 전반에 걸친 균형 잡힌 샘플링을 사용해야 함.

### 실전 요약
1. **재시도와 판정 점수를 마이닝하라**: 취약한 시스템 행동의 강력한 신호이기 때문.
2. **샘플을 계층화하라**: 하나의 시끄러운 클래스가 평가셋을 지배하지 않도록.
3. **실제 실패는 여전히 중요하다**: 특히 비즈니스 영향이 클 때.
- 결과: 평가셋이 시스템의 실제 손상 지점(breakpoint)을 커버하기 시작함.

### 결론
- 최종 교훈: 커버리지는 샘플링이 **의도적이고, 희귀하며 비용이 크고 불안정한 케이스**를 겨냥할 때 개선됨.
- 좋은 평가는 단순히 흔한 케이스를 확인하는 것이 아니라, 시스템이 가장 무너지기 쉬운 곳에서 테스트되었는지 확인하는 것.

## 예시
```python
# sampler.py (개념 구조) — 엣지 케이스 중심 평가셋 구축
import pandas as pd

logs = load_production_logs()

brittle_cases = logs[(logs["retry_count"] > 1) | (logs["judge_score"] < 0.4)]

# 실패 유형별로 계층화 샘플링 — 하나의 실패 유형이 지배하지 않도록
edge_case_sample = stratified_sample(brittle_cases, by="failure_type", n=40)
```

```text
[5가지 엣지 케이스 유형]

2. 프로덕션 플래그 — 사용자 에스컬레이션, 부정 피드백
3. 통계적 이상치 — 응답 길이 95th/99th 백분위수

```

## 요약
- 강력한 평가셋은 실패 기반·프로덕션 플래그·통계적 이상치·적대적·합성이라는 5가지 유형의 엣지 케이스를 재시도 횟수와 판정 점수 같은 취약성 신호를 마이닝해 실패 유형별로 계층화 샘플링하는 방식으로 체계적으로 수집해야 하며, 전체 평가셋의 20%를 차지하도록 비율을 맞추고 분기별로 갱신하며 각 케이스에 근거를 문서화해야 시스템이 실제로 무너지기 쉬운 지점에서 테스트되도록 보장할 수 있다.
