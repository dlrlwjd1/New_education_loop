# Evaluation Triggers During Deployment

## 개요
- 프로덕션 LLM 시스템에서 평가가 배포 생애주기의 여러 지점(PR, 메인 브랜치 푸시, 정기 스케줄, 데이터 업데이트)에서 트리거되어야 하는 이유와, 속도·비용·커버리지의 균형을 맞추는 **3단계(tier) 평가 전략**을 다루는 6분 영상. "Integrating Evaluation into CI/CD Pipelines" 레슨의 첫 번째 영상.

## 내용

### 왜 평가가 여러 지점에서 트리거되어야 하는가
- 평가는 한 번만 일어나서는 안 되고, 회귀(regression)·드리프트·데이터 관련 문제를 적절한 시점에 잡아낼 수 있도록 여러 배포 단계에 연결되어야 함.
- 배포 품질은 모델 성능뿐 아니라 평가가 **언제 어디서** 트리거되는지에도 달려 있음 — 트리거 지점은 실패가 사용자에게 도달하기 전에 막는 체크포인트 역할을 함.

### 4가지 핵심 평가 트리거 지점
1. **모든 풀 리퀘스트(Pull Request)마다**: **50개 예시**로 경량 평가 실행 — 빠른 게이트로, 회귀를 조기에 잡아냄.
2. **메인 브랜치 푸시 시(Push to Main)**: **200개 예시**로 전체 평가 실행 — 어떤 아티팩트 등록이든 하기 전에 반드시 통과해야 함.
3. **정기 스케줄(On Schedule)**: 프로덕션 모델에 대해 **주간 전체 평가** 실행 — 실세계 드리프트를 모니터링하는 데 도움.
4. **데이터 업데이트 시(On Data Update)**: 학습 데이터가 바뀔 때마다 평가를 다시 실행해 데이터로 유발된 회귀를 잡아냄.
- **차단 규칙**: 평가가 실패하면 파이프라인은 `sys.exit()`를 사용해 즉시 GitHub Actions 파이프라인을 차단함 — 실패한 평가는 단순 참고사항이 아니라 안전하지 않은 배포를 직접적으로 막음.

### 3단계(3-Tier) 평가 트리거 전략
- 속도, 비용, 커버리지, 깊이의 균형을 맞추기 위해 세 단계의 평가를 사용:
  - **Tier 1 (PR 단계)**: 50개 예시, 5분 타임아웃, **정확성만** 체크, 실행당 **$0.36**.
  - **Tier 2 (메인 푸시 시)**: 200개 예시, 20분 타임아웃, **전체 지표** 포함, 실행당 **$1.44**.
  - **Tier 3 (주간 스케줄)**: 프로덕션 데이터에서 샘플링한 500개 예시, **환각과 드리프트** 체크.
- **주간 비용 추정**: Tier 1에서 주당 20개의 PR, Tier 2에서 5번의 푸시가 있다고 가정하면, 총 평가 비용은 주당 약 **$14.40**.
- 요점: 모든 단계가 동일한 수준의 평가 깊이를 필요로 하지 않음 — 초기 단계는 속도를 우선시하고, 후기 단계는 더 폭넓고 비용이 더 드는 체크를 사용.

### 핵심 원칙 4가지
1. **계층화된 평가(Tiered Evaluation)**: PR에서는 빠르고 가벼운 평가, 병합(merge) 시에는 전체 평가 — 속도와 커버리지의 균형.
2. **빠른 실패 게이트(Fail-fast Gate)**: 평가가 실패하면 파이프라인을 즉시 중단 — 나쁜 코드가 프로덕션으로 이동하지 않도록 보장.
3. **정기 모니터링(Scheduled Monitoring)**: 프로덕션 모델의 주간 평가가 일반적인 CI/CD 체크에서는 나타나지 않을 수 있는 실세계 드리프트를 탐지.
4. **데이터 트리거 평가(Data-triggered Evaluation)**: 학습 데이터가 바뀔 때 평가를 다시 실행해 데이터로 유발된 회귀가 배포 품질에 영향을 미치기 전에 잡아냄.

### 배포 설정 예시: `deployment_checks.yaml`
- 배포 전(pre-deploy) 평가, 배포 후(post-deploy) 평가, 점수 하락 시 롤백을 포함.
- 배포 전 평가는 롤아웃 전 필수. 배포 후 평가 체크도 릴리스 시작 후 필수.
- **롤백 조건**: 점수가 **0.03 하락**하거나 **P95 지연시간이 1,500ms를 초과**하면 시스템이 롤백됨.
- 이를 통해 트리거 시스템이 단순 정보 제공용이 아니라 **실행 가능(actionable)**하게 됨 — 배포 프로세스가 측정 가능한 임계값에 의해 통제됨.

### 실전 요약 (4단계: Contact, Connect, Use, Result)
1. **Contact(접촉)**: 배포 전과 카나리 트래픽 중에도 다시 평가.
2. **Connect(연결)**: 실행 경로(action path)가 없는 트리거는 단지 선언에 불과함.
3. **Use(사용)**: 단순한 임계값이 복잡한 것보다 신뢰하기 쉬움 — 실시간 배포 중 빠른 결정이 필요할 때 중요.
4. **Result(결과)**: 배포가 **게이트가 있는(gated) 프로세스**가 됨.

### 결론
- 품질 트리거는 배포와 롤백 단계에 직접 연결될 때 가장 중요함.
- 프로덕션 AI의 평가는 PR, 메인 푸시, 스케줄, 데이터 업데이트라는 여러 트리거 지점에서 일어나야 하며, 3단계 전략으로 평가 깊이·실행시간·비용의 균형을 맞춰야 함.
- 가장 중요한 점: 트리거는 배포 차단이나 릴리스 롤백 같은 **실제 실행(real actions)**에 연결되어야 함 — 이것이 배포 중 자동화된 품질 게이트를 효과적으로 만듦.

## 예시
```yaml
# deployment_checks.yaml (개념 구조)
pre_deploy_evaluation:
  required: true
  dataset_size: 200

post_deploy_evaluation:
  required: true
  monitor_during: canary_traffic

rollback_conditions:
  score_drop_threshold: 0.03
  p95_latency_ms_max: 1500
```

| 트리거 | 예시 수 | 타임아웃 | 체크 항목 | 실행당 비용 |
|---|---|---|---|---|
| PR (Tier 1) | 50 | 5분 | 정확성만 | $0.36 |
| Push to main (Tier 2) | 200 | 20분 | 전체 지표 | $1.44 |
| 주간 스케줄 (Tier 3) | 500(프로덕션 샘플) | - | 환각+드리프트 | - |

```text
[주간 평가 비용 추정]
PR 20회 × $0.36 + Push 5회 × $1.44 ≈ 주당 $14.40
```

## 요약
- 프로덕션 LLM 평가는 PR·메인 푸시·정기 스케줄·데이터 업데이트라는 4가지 트리거 지점에서 실행되어야 하며, PR(50예시, 정확성만)·메인 푸시(200예시, 전체 지표)·주간(500예시, 환각+드리프트)이라는 3단계 전략으로 속도와 비용, 커버리지의 균형을 맞추고, 평가 실패 시 파이프라인을 즉시 차단하며 점수 하락이나 지연시간 초과 시 자동 롤백하는 실행 가능한 임계값으로 트리거를 실제 배포·롤백 액션에 연결하는 것이 효과적인 자동화된 품질 게이트의 핵심이다.
