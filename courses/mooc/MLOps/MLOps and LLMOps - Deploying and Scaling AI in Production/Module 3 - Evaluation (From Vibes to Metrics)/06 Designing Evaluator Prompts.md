# Designing Evaluator Prompts

## 개요
- **LLM-as-a-Judge** 시스템을 위한 강력한 평가자(evaluator) 프롬프트를 설계하는 4대 원칙(사고 사슬 우선, 명시적 루브릭, temperature 0, 차원 분리)과 지원 봇 정확성 루브릭 실전 예시를 다루는 8분 영상. "LLM-as-a-Judge Methodologies" 레슨의 첫 번째 영상.

## 내용

### 왜 평가자 프롬프트 설계가 중요한가
- LLM이 출력을 신뢰성 있게 평가하도록 하려면 단순히 답변에 점수를 매기라고 요청할 수 없음 — 명확한 구조, 일관된 루브릭, 판단 과정을 안정화하는 규칙으로 안내해야 함.
- 평가자 프롬프트가 모호하면 점수가 일관성 없거나, 설명하기 어렵거나, 사람의 판단과 잘 맞지 않을 수 있음 — 평가자 프롬프트는 자동 평가의 신뢰도에 직접 영향을 미침.

### 평가자 프롬프트 설계 4대 핵심 원칙
1. **사고 사슬 우선(Chain of Thought First)**: 프롬프트는 점수를 매기기 전에 모델이 단계별로 추론하도록 요청해야 함 — 점수 매기기 전 추론은 대체로 사람의 판단과의 정합성을 개선함. 이는 평가자가 곧바로 숫자로 뛰어들지 않고 근거를 따져보도록 강제함.
2. **명시적 루브릭(Explicit Rubric)**: 모든 차원에 대해, 프롬프트는 1부터 5 같은 점수가 구체적인 예시와 함께 실제로 무엇을 의미하는지 정의해야 함 — 모델이 좋음/나쁨의 의미를 추측하도록 방치해서는 안 됨.
3. **Temperature 0**: 평가자 프롬프트는 결정론적 샘플링을 사용해 동일한 입력이 가능한 자주 동일한 판단을 만들어내도록 해야 함 — 실행 간 일관성을 지원.
4. **차원 분리(Separating Dimensions)**: 하나의 큰 종합 점수를 주는 대신, 평가자는 정확성, 관련성, 형식을 **독립적으로** 점수 매겨야 함 — 더 명확한 진단 신호를 제공.
- 핵심 요점: 평가자 프롬프트는 구조화되고, 명시적이고, 결정론적이고, 다차원적이어야 함.

### 정확성 차원 정의 예시 (고객 지원 평가자)
- 루브릭은 특정 비즈니스 맥락에서 서로 다른 점수 수준이 무엇을 의미하는지 명확히 정의해야 함.
- 이 예시에서 평가자는 지원 봇의 답변을 판정하므로, 정확성은 응답이 고객의 질문에 정확하고 안전하게 답했는지와 연결됨.
  - **점수 5**: 완전히 정확함 — 오류 없이 질문을 직접적으로 다룸.
  - **점수 3**: 부분적으로 정확함 — 주요 의도는 다뤄졌지만 일부 세부사항이 누락됨.
  - **점수 1**: 잘못된 정보, 지어낸 내용, 또는 완전히 주제에서 벗어남.
- 이런 설명이 얼마나 구체적인지 주목 — 단순히 "5는 좋음, 1은 나쁨"이라고 말하는 것보다 훨씬 나음. 루브릭이 명확할수록 자동화된 판정이 더 안정적이 됨.
- 이 루브릭은 프롬프트 안에 **채점 가이드(scoring guide) 섹션**으로 추가되어야 함 — 루브릭은 다른 곳에 문서화되는 것이 아니라 평가자 프롬프트 자체 안에 있어야 하기 때문에 중요. 채점 언어가 완전하고, 맥락에 맞으며, 프롬프트에 직접 내장될 때 평가자 프롬프트가 더 잘 작동함.

### 핵심 원칙 재확인
1. **사고 사슬 우선**: 점수 매기기 전 추론이 사람 평가자와의 상관관계를 개선.
2. **명시적 루브릭**: 모든 점수 수준이 명확한 설명과 예시로 정의되어야 함 — 모델이 채점 척도를 이미 이해하고 있다고 절대 가정하지 말 것.
3. **Temperature 0**: 평가가 재현 가능해야 하므로 결정론적 설정이 중요.
4. **차원 분리**: 정확성, 관련성, 형식을 하나의 불명확한 숫자로 합치지 말고 독립적으로 점수 매길 것.

### 실전 판정 프롬프트 예시: `judge_prompt.txt`
- 프롬프트 지시: "답변을 1~5점으로 채점하라. 아래 루브릭에 따라 판정하라. 점수를 반환하라. 근거(rationale)를 반환하라. 인용된 루브릭 조항을 반환하라. **스타일을 정확성보다 우대하지 말라(do not reward style over correctness)**."
- 이 프롬프트가 강력한 이유: 평가자를 명확하게 제약함 — 모델에게 무엇을 반환해야 하는지, 점수를 어떻게 정당화해야 하는지, 무엇을 과대평가하지 말아야 하는지 알려줌.
- "스타일을 정확성보다 우대하지 말라"는 지시가 특히 중요 — 판정 모델은 답변이 완전히 사실적으로 틀렸어도 유능하거나 세련된 언어에 과도하게 감명받을 수 있음. 이 프롬프트는 그런 경향을 명시적으로 차단함.
- 핵심 요점: 평가자 프롬프트는 출력 형식과 판정 경계 모두를 매우 명확하게 정의해야 함.

### 실전 의미
1. **고정(Anchor)**: 평가자 프롬프트가 명확한 기준을 참조할 때 채점이 더 안정적이 됨.
2. **점수와 근거 모두 요구**: 감사(audit)를 더 쉽게 만듦 — 팀이 어떤 점수가 주어졌는지뿐 아니라 왜 주어졌는지도 검토할 수 있게 됨.
3. **스타일 편향 차단**: 판정 모델은 콘텐츠가 약하거나 부정확해도 유능하게 들리는 답변에 과도하게 보상하는 경향이 있음 — 그래서 프롬프트는 스타일보다 정확성을 명시적으로 우선시해야 함.
- 결과: 자동화된 판정이 더 설명 가능(explainable)해짐.

### 결론
- 평가자 프롬프트는 **프로덕션 아티팩트**로 취급되어야 함 — 생성(generation)에 사용되는 프롬프트와 마찬가지로 버전 관리되고, 테스트되고, 실패에 대해 감사되어야 함.
- 핵심 메시지: 루브릭이 명시적이고, 추론이 구조화되고, 설정이 결정론적일 때, 자동화된 판정은 더 신뢰할 수 있고 설명 가능해짐.

## 예시
```text
# judge_prompt.txt (개념 구조)
"다음 답변을 1~5점으로 채점하라.
아래 루브릭에 따라 판정하라:
  5 = 완전히 정확함 — 오류 없이 질문에 직접 답함
  3 = 부분적으로 정확함 — 주요 의도는 다루나 세부사항 누락
  1 = 잘못된 정보, 지어낸 내용, 또는 완전히 주제 이탈

다음을 반환하라:
1) score (점수)
2) rationale (근거)
3) cited_rubric_clause (인용된 루브릭 조항)

스타일을 정확성보다 우대하지 말라."
```

```text
[평가자 프롬프트 4대 원칙]
1. 사고 사슬 우선   — 점수 전에 단계별 추론
2. 명시적 루브릭    — 점수별 구체적 정의+예시
3. Temperature = 0  — 결정론적, 재현 가능한 판정
4. 차원 분리        — 정확성/관련성/형식 독립 채점
```

## 요약
- LLM-as-a-Judge 평가자 프롬프트는 점수 매기기 전 단계별 추론을 요구하고, 모든 점수 수준을 구체적 예시와 함께 명시적으로 정의한 루브릭을 프롬프트 안에 직접 내장하며, temperature 0으로 결정론적 판정을 확보하고, 정확성·관련성·형식을 독립적으로 채점하고, 점수와 근거를 함께 요구하며 스타일이 정확성보다 우대되지 않도록 명시적으로 차단해야 하며, 이런 평가자 프롬프트 자체가 생성용 프롬프트와 마찬가지로 버전 관리·테스트·감사되는 프로덕션 아티팩트로 취급되어야 한다.
