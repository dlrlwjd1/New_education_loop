# Quality Gates & Release Thresholds

## 개요
- 프로덕션 AI 릴리스를 통제하는 **품질 게이트(Quality Gates)** — 절대(absolute) 게이트와 상대(relative) 게이트의 차이, 절대 차단(hard block) 규칙, 그리고 이를 CI/CD 파이프라인에 통합하는 실전 코드를 다루는 7분 영상. "Integrating Evaluation into CI/CD Pipelines" 레슨의 두 번째 영상.

## 내용

### 왜 품질 게이트가 필요한가
- 모델이나 프롬프트는 간단한 테스트에서 멋져 보인다는 이유만으로 배포되어서는 안 됨 — 프로덕션에서는 시스템이 안전하고, 빠르고, 충분히 좋은지 판단하는 명확한 규칙이 필요하며, 이런 규칙을 **품질 게이트**라 부름.
- 팀은 CI/CD 파이프라인에서 자동화된 체크를 사용해 품질이 떨어지거나, 지연시간이 너무 증가하거나, 안전성 문제가 나타날 때 배포를 중단함.

### 품질 게이트의 주요 유형
- 릴리스 결정은 한 종류의 게이트보다 많은 것에 기반해야 함 — 시스템은 "모델이 충분히 정확한가?"뿐 아니라 "충분히 빠른가?", "충분히 안전한가?"도 물어야 함.
- 프로덕션 품질은 다차원적임 — 릴리스가 품질을 약간 개선해도, 지연시간이 너무 높아지거나 환각 리스크가 증가하면 여전히 받아들일 수 없음.
- 품질 게이트의 종류: **정확성(correctness), 형식(format), 환각(hallucination), 상대 품질(relative quality), 지연시간 P95(latency P95)**.
- 품질 게이트는 정책 경계(policy boundary) 역할을 함 — 주관적인 출시 결정을 팀이 자동화하고 설명할 수 있는 명시적 기준으로 전환.

### CI/CD 내 릴리스 게이트 운영 워크플로
- 게이트는 메인 브랜치로의 모든 푸시마다 실행되며, 체크에 실패하면 `sys.exit()`으로 파이프라인을 차단.
- 프로세스: 동결된 평가셋 버전 1.0과 레지스트리의 베이스라인 지표를 로드 → 200개 평가 예시 전체에 모델을 실행해 예시별 지표와 집계 지표를 계산 → **절대 임계값** 체크(어느 절대 게이트든 실패하면 시스템이 차단하고 이유를 기록해 배포를 막음) → 프로덕션 베이스라인 대비 **상대 게이트** 체크(신규 버전이 프로덕션 대비 퇴보하면 배포가 다시 차단됨).
- 핵심 요점: 릴리스 게이팅은 자동적이고, 반복 가능하고, **동결된 벤치마크**에 연결되어야 함 — 이것이 우발적인 회귀가 프로덕션에 도달하는 것을 막음.

### 강력한 릴리스 게이트의 핵심 원칙 4가지
1. **절대 게이트 + 상대 게이트**: 둘 다 통과해야 함 — 절대 게이트는 최소 허용 가능한 품질을 보장하고, 상대 게이트는 신규 버전이 현재 프로덕션 베이스라인 대비 퇴보하지 않도록 보장.
2. **절대 차단(Hard Blocks)**: 형식(format)과 환각(hallucination) 게이트는 **항상 릴리스를 차단**함 — 손상된 출력이나 안전하지 않은 환각은 프로덕션에서 용납될 수 없는 **무관용(zero tolerance)** 체크이기 때문.
3. **상대 품질 보호**: 프로덕션 대비 품질이 **1% 하락**하면 어떤 버전도 승격되어서는 안 됨 — 릴리스가 시간이 지나며 서서히 퇴화하는 것을 방지.
4. **지연시간 SLA**: 게이트는 P95 지연시간을 체크해 성능 회귀가 서비스 수준 기대치(SLA)를 깨뜨릴 때 배포를 차단해야 함.
- 핵심 요점: 좋은 릴리스 게이트는 최소 기준과 회귀 리스크를 모두 보호함.

### 릴리스 게이트 코드 예시
- 코드가 3가지 별도의 릴리스 조건을 체크:
  1. 평가 점수가 **0.82 미만**이면 품질(quality)에서 차단.
  2. **P95 지연시간이 1,200밀리초 초과**하면 지연시간(latency)에서 차단.
  3. **환각률이 0.03 초과**하면 안전성(safety)에서 차단.
- 모든 체크를 통과할 때만 시스템이 릴리스됨.
- 이 예시가 좋은 이유: 로직이 구체적이고 설명하기 쉬움 — 각 규칙이 품질, 성능, 안전성이라는 프로덕션 관심사에 직접 매핑됨. 이것이 좋은 릴리스 게이트가 해야 할 일.
- 핵심 요점: 릴리스는 막판의 의견에 의존해서는 안 되고, 이런 명확한 자동화된 규칙에 의존해야 함.

### 실전 교훈
1. 지연시간이나 안전성이 퇴보한다면 품질만으로는 충분하지 않음.
2. 차단 사유는 리뷰어에게 가시적이어야 함.
3. 게이트를 너무 자주 변경하면 신뢰가 약해짐 — 기준이 불안정하면 팀은 pass/fail의 의미를 신뢰하지 않게 됨.
- 결과: 출시가 비공식적인 논쟁이 아니라 **정책**에 의해 방지됨.

### 결론
- 좋은 릴리스 게이트는 **자동화하기에 충분히 구체적이고, 설명하기에 충분히 단순함**.
- 품질 게이트는 품질·지연시간·안전성에 대한 기대치를 명시적이고 자동화된 규칙으로 전환함으로써 프로덕션 릴리스를 더 안전하게 만듦.

## 예시
```python
# release_gate.py (개념 구조)
def check_release(eval_score, p95_latency_ms, hallucination_rate, production_baseline_score):
    if eval_score < 0.82:
        block("quality")
    if p95_latency_ms > 1200:
        block("latency")
    if hallucination_rate > 0.03:
        block("safety")
    if eval_score < production_baseline_score * 0.99:  # 프로덕션 대비 1% 이상 하락 금지
        block("relative_regression")

    return "RELEASE"  # 모든 체크 통과 시에만 릴리스
```

```text
[품질 게이트 유형]
절대 게이트: 정확성, 형식(항상 차단), 환각(항상 차단), 지연시간 P95
상대 게이트: 프로덕션 베이스라인 대비 1% 이상 하락 시 차단
```

| 체크 | 임계값 | 실패 시 |
|---|---|---|
| 품질(평가 점수) | ≥ 0.82 | 차단 |
| 지연시간(P95) | ≤ 1200ms | 차단 |
| 환각률 | ≤ 0.03 | 차단 (무관용) |
| 상대 품질 | 프로덕션 대비 -1% 이내 | 차단 |

## 요약
- 프로덕션 AI 릴리스는 정확성·형식·환각·지연시간(P95)이라는 절대 게이트와 프로덕션 베이스라인 대비 1% 이상 퇴보를 막는 상대 게이트를 모두 통과해야 하며, 형식과 환각 게이트는 무관용 원칙으로 항상 릴리스를 차단하고, 이런 명확하고 자동화된 임계값 규칙(품질 ≥0.82, P95 ≤1200ms, 환각률 ≤0.03)을 CI/CD에 내장해 동결된 벤치마크에 연결함으로써 막판의 주관적 판단이 아니라 정책에 의해 안전한 릴리스 결정이 이루어지도록 하는 것이 핵심이다.
