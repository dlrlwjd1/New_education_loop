# Tracking Prompt-Response Deltas

## 개요
- 프롬프트가 변경될 때 후보(candidate) 버전과 베이스라인(baseline) 버전을 동일한 평가셋에서 비교해 **델타(delta)**를 측정하고, 자동화된 임계값 게이트로 약한 프롬프트 버전이 프로덕션에 도달하지 못하도록 막는 방법을 다루는 8분 영상.

## 내용

### 왜 델타 추적이 필요한가
- 프롬프트를 바꾸는 것 자체만으로는 충분하지 않음 — 중요한 것은 그 업데이트 이후 모델의 동작이 **무엇이 바뀌었는지** 이해하는 것.
- 프롬프트 버전은 이전 버전과 비교해 차이를 측정할 수 있을 때만 의미가 있음.
- **델타 추적(Delta Tracking)**: 후보 프롬프트를 베이스라인 프롬프트와 **동일한 평가셋**에서 비교해 새 버전이 결과를 개선했는지, 악화시켰는지, 새로운 리스크를 도입했는지 탐지.

### 추적해야 할 델타 유형 (다중 지표)
- 프롬프트는 동시에 여러 가지에 영향을 줄 수 있음 — 새 프롬프트가 답변 품질은 개선해도 응답이 느려지거나 비용이 더 들 수 있음. 그래서 팀은 절대 지표 하나만 봐서는 안 됨.
- 가장 중요한 델타 카테고리:
  1. **정확성/정확도(Correctness/Accuracy)**: 답변이 더 나아졌는가.
  2. **지연시간(Latency)**: 응답이 더 빠른가 느린가.
  3. **비용(Cost)**: 새 프롬프트가 자원을 더 쓰는가 덜 쓰는가.
  4. **형식/행동 변화(Format/Behavior Changes)**: 톤 드리프트, 구조 변화, 출력 불일치 같은 문제 탐지.
- 학습 요점: 프롬프트 평가는 항상 **다중 지표(multi-metric)**여야 함 — 좋은 릴리스는 정확도 향상만이 아니라 효율성과 운영 안정성도 유지해야 함.

### 실전 델타 리포트 예시
- 베이스라인 버전 **v1.3.2** vs 후보 버전 **v1.4.0**을 고정된 200개 샘플 평가 데이터셋으로 비교:
  - 베이스라인: 정확도 0.88, P95 지연시간 1,820ms, 호출당 비용 $0.00712.
  - 후보: 정확도 0.914, P95 지연시간 1,640ms, 호출당 비용 $0.00712(오기 가능성, 비용은 약 2% 감소로 언급됨).
  - 델타: 정확도 **+3.3%**, 지연시간 **-10%**, 비용 **-2%**.
- 모든 델타가 긍정적이며 정의된 임계값을 통과했으므로, 시스템은 **자동 승격(auto-promote)** 결정을 내려 후보를 스테이징으로 이동.
- 이 사례가 중요한 이유: 팀이 단순히 "새 프롬프트가 더 나아 보인다"고 말하는 대신, 정확히 어떻게 개선되었고 왜 승격이 안전한지 보여줄 수 있음.

### 자동화된 비교 워크플로
1. 이전 버전(v1.3.2)의 베이스라인 지표를 로드.
2. 후보 버전(v1.4.0)을 동일한 평가 데이터셋에서 실행.
3. 주요 지표(정확성, 지연시간, 비용, 형식 오류)의 델타를 계산.
4. 임계값을 적용 — 어떤 지표든 임계값을 초과해 변하면 시스템이 승격을 차단하고 팀에 경고.
- 학습 요점: 평가는 체계적이어야 하며 수동적이고 일관성 없어서는 안 됨 — 자동화된 비교 스크립트는 모든 프롬프트 버전이 릴리스 전에 동일한 규칙을 적용받도록 보장. 자동화는 해로운 변경을 초기에 잡아내 리스크를 줄임.

### 신뢰할 수 있는 델타 추적의 핵심 원칙 4가지
1. **고정된 평가 데이터셋 사용**: 베이스라인과 후보 버전은 반드시 동일한 예시로 테스트되어야 공정한 비교가 됨.
2. **다중 지표(Multiple Metrics)**: 정확성, 지연시간, 비용, 형식을 함께 추적할 것 — 지표 하나만으로 승격을 결정하지 말 것.
3. **자동화된 게이트(Automated Gates)**: 임계값이 사람의 검토나 릴리스 전에 자동으로 나쁜 프롬프트 버전을 차단해야 함.
4. **델타 가시성(Delta Visibility)**: 모든 비교가 로깅되어야 팀이 시간이 지나며 프롬프트 동작이 어떻게 변하는지 볼 수 있음.
- 핵심 메시지: 프롬프트 변경은 일관되고, 공정하고, 여러 차원에서 비교할 때만 신뢰할 수 있음.

### 코드 예시: `delta_check.py`
- 이전 실행과 새 실행의 출력을 비교하고, 델타에 기반한 규칙을 적용:
  - 예: 정확도가 2% 하락하면 릴리스를 차단.
  - 예: 톤 변화(tone shift)가 0.15를 초과하면 수동 검토로 전송.
  - 모든 델타는 로깅됨.
- 중요한 점: 모든 변경이 동일하게 처리되지 않음 — 일부 문제는 자동으로 차단할 수 있지만, 톤·스타일·브랜드 보이스처럼 지표가 변화를 나타내도 사람이 수용 가능한지 판단해야 하는 경우도 있음.
- 핵심 요점: 델타 추적은 필요한 경우 자동화된 규칙과 사람의 검토를 결합함.

### 실전 교훈 요약
1. **측정**: 동일한 평가셋에서 이전과 새 동작을 비교해 측정.
2. **차단**: 프로덕션에 도달해서는 안 되는 부정적 변화가 있을 때 릴리스를 차단.
3. **검토**: 톤 드리프트처럼 사람의 판단이 필요한 경우는 검토.
- 결과: 프롬프트 변경이 단순한 버전 번호가 아니라 **행동 변화(behavior shift)**로서 가시화됨.
- 최종 메시지: 버전 변경은 그것이 도입한 행동 델타를 규명(qualify)할 수 있을 때만 의미가 있음 — 새 프롬프트 버전은 팀이 무엇이 바뀌었는지, 시스템을 개선했는지, 승격이 안전한지를 명확히 보여줄 수 있을 때만 가치가 있음.

### 결론
- AI 프로덕션에서 프롬프트 업데이트는 절대 직관만으로 판단되어서는 안 됨 — 업데이트는 명확한 행동 델타로 측정되고, 임계값에 대해 검증되고, 릴리스 전에 신중하게 검토되어야 함.

## 예시
```text
[델타 리포트 예시 — v1.3.2 (베이스라인) vs v1.4.0 (후보)]
평가셋: 고정된 200 샘플

              베이스라인    후보        델타
정확도(Correctness)   0.880       0.914      +3.3%
P95 지연시간          1820ms      1640ms     -10%
비용(호출당)          $0.00712    (약 -2%)

→ 모든 델타가 임계값 통과 → 자동 승격(auto-promote) → 스테이징 이동
```

```python
# delta_check.py (개념 구조)
def check_deltas(baseline_metrics, candidate_metrics):
    accuracy_delta = candidate_metrics["accuracy"] - baseline_metrics["accuracy"]
    tone_shift = compute_tone_shift(baseline_metrics, candidate_metrics)

    if accuracy_delta < -0.02:
        return "BLOCK"  # 정확도 2% 이상 하락 시 자동 차단
    if tone_shift > 0.15:
        return "MANUAL_REVIEW"  # 톤 변화가 크면 사람이 판단

    log_deltas(baseline_metrics, candidate_metrics)
    return "AUTO_PROMOTE"
```

## 요약
- 프롬프트 변경은 그 자체로는 의미가 없으며, 베이스라인과 후보 버전을 동일한 고정 평가셋에서 정확성·지연시간·비용·형식이라는 다중 지표로 비교한 델타를 통해서만 의미를 가지며, 이 비교는 자동화된 임계값 게이트로 나쁜 변경을 조기에 차단하고 톤 드리프트 같은 애매한 경우는 사람의 검토로 넘기는 방식으로 운영되어야 하고, 모든 델타를 로깅해 프롬프트 동작이 시간에 따라 어떻게 변하는지 가시화하는 것이 신뢰할 수 있는 프롬프트 릴리스의 핵심이다.
