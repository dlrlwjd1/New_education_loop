# Model Choices: API vs Local Models

## 개요
- AI 배포에서 가장 중요한 결정 중 하나인 **API 기반 배포 vs 로컬 배포**를 트래픽 규모, 컴플라이언스, 커스터마이징 필요성 관점에서 비교하고, 이커머스 하이브리드 아키텍처 실전 사례(비용 60% 절감, 가동률 99.2%)를 다루는 11분 영상. "Inference Optimization" 레슨의 마지막 영상.

## 내용

### 배포는 기술적 선택만이 아니다
- 많은 학습자가 "가장 좋은 모델이 항상 정답"이라고 가정하지만, 프로덕션에서 더 중요한 질문은 "어떤 배포 방식이 조직의 필요에 가장 잘 맞는가"임.
- 배포 선택을 좌우하는 요인: 요청량(request volume), 컴플라이언스 요구사항, 지연시간 기대치, 규모에 따른 비용, 내부 운영 역량.
- 핵심 마인드셋: **배포는 선호가 아니라, 실제 운영 제약에 가장 잘 맞는 인프라 모델을 선택하는 것**.

### API 배포 vs 로컬 배포 비교
- **API 배포**: 외부 제공업체가 호스팅하는 모델 사용 — 인프라, 확장, 모델 유지보수를 제공업체가 처리하므로 프로토타이핑과 빠른 출시에 매력적. 대체로 **월 1,000만 요청 미만**일 때 강력한 선택 — 이 단계에서는 자체 서빙 스택을 구축하는 것보다 저렴하고 훨씬 간단함.
- **로컬 배포**: 조직이 자체 인프라에 모델을 호스팅 — **월 5,000만 요청 초과**처럼 요청량이 매우 많거나, 엄격한 컴플라이언스·데이터 거주지(data residency)·커스터마이징 요구사항이 있을 때 더 매력적.
- **손익분기점(Break-even point)**: API는 대체로 **월 2,000만 요청**까지는 더 저렴하지만, 그 이후에는 GPU와 운영 비용이 API 지출보다 낮다면 로컬 호스팅이 더 비용 효율적일 수 있음.
- **컴플라이언스**: 헬스케어, 금융 같은 산업에서는 민감한 데이터를 외부 제공업체로 보낼 수 없으므로 비용과 무관하게 로컬 배포가 필요할 수 있음.
- 핵심 요점: API와 로컬 배포 사이의 결정은 모델 선호가 아니라 **규모, 컴플라이언스, 커스터마이징 필요, 운영 성숙도**에 기반해야 함.

### 실전 의사결정 프레임워크
- **API를 사용할 때**: 프로토타이핑 중일 때, 최신 모델을 원할 때, 트래픽이 상대적으로 낮을 때 — 인프라 복잡성을 줄이고 팀이 빠르게 움직이는 데 도움이 되는 최선의 출발점인 경우가 많음.
- **로컬 배포를 사용할 때**: 트래픽이 매우 많을 때, 컴플라이언스가 엄격할 때, 커스텀 파인튜닝이나 더 강한 통제가 필요할 때 — 이 시점에서는 조직이 서빙 환경을 직접 소유하는 것에서 더 많은 가치를 얻을 수 있음.
- 이 프레임워크는 실제로 4가지 질문을 던짐:
  1. 예상 트래픽이 얼마나 되는가?
  2. 데이터가 얼마나 민감한가?
  3. 모델에 대한 커스텀 통제가 필요한가?
  4. 우리가 직접 운영할 스킬이나 인프라를 갖추고 있는가?
- 프로덕션 AI는 결코 단순한 모델 선택이 아니라 **인프라 역량의 선택**이기도 함 — 조직이 로컬 배포를 원해도 GPU 팀이나 운영 준비가 없다면, 단기적으로는 여전히 API가 현실적인 답일 수 있음.
- 학습 통찰: 좋은 배포 결정은 기술적 필요와 조직의 준비 상태 사이의 균형을 맞춤.

### 실전 사례: 이커머스 하이브리드 아키텍처
- 배포 결정은 종종 "API냐 로컬이냐"의 양자택일이 아니라, **하이브리드 아키텍처**가 최선의 답인 경우가 많음.
- 이커머스 기업이 작업 복잡도에 따라 여러 배포 경로를 조합한 사례:
  - **가장 가치 높은 복잡한 상품 추천 작업(전체 트래픽의 5%)**: **GPT-4 API** 사용 — 고가치 요청이며 더 강력한 모델 품질의 혜택을 받음.
  - **더 단순하고 대량인 작업, 예: FAQ 라우팅(전체 트래픽의 80%)**: **로컬 Llama 3 모델** 사용 — 덜 복잡하고 매우 빈번하게 발생하는 작업이라 로컬 서빙이 비용을 상당히 줄일 수 있음.
  - **로컬 모델이 처리할 수 없는 엣지 케이스(전체 트래픽의 15%)**: **GPT-3.5 API로 폴백(fallback)** — 각 요청이 가장 적합한 모델과 서빙 방식에 매칭되는 계층화된 전략을 만듦.
- **결과**: 전체 API 사용 대비 **60% 비용 절감**, 폴백 전략 덕분에 복원력이 향상되어 **99.2% 가동률(uptime)** 달성.
- 학습 통찰: 최고의 프로덕션 아키텍처는 종종 서로 다른 유형의 트래픽을 다르게 라우팅하는 아키텍처 — 고가치·복잡한 작업은 프리미엄 API를 정당화할 수 있고, 단순·대량 작업은 로컬에서 더 잘 서빙될 수 있음.
- 핵심 요점: 하이브리드 배포는 품질, 비용, 규모, 신뢰성의 균형을 맞추므로 종종 가장 실용적인 전략.

### 핵심 원칙 4가지
1. **API로 시작하라(Start with API)**: 대체로 프로덕션으로 가는 가장 빠른 경로.
2. **규모 임계값(Scale Threshold)**: API 비용이 GPU와 운영의 결합 비용을 초과할 때 로컬 배포로 마이그레이션해야 함.
3. **하이브리드 전략**: 항상 하나만 선택할 필요는 없음 — 복잡한 요청에는 API를, 대량·모듈형 작업에는 로컬 서빙을 사용할 수 있음.
4. **컴플라이언스 우선(Compliance First)**: 규제 산업에서는 배포 모델이 비용이 아니라 법률·정책 요건에 의해 결정될 수 있음 — API가 더 저렴하고 쉬워도 로컬 배포가 여전히 필요할 수 있음.
- 핵심 요점: 좋은 배포 결정은 프로덕션까지의 시간, 규모 경제, 워크로드 복잡도, 규제 요건에 의해 인도됨 — 인프라 선택은 습관이나 개인적 선호가 아니라 근거 있고 신중해야 함.

### 배포 설정 예시: `deployment.yaml`
- `mode: api` — 주 서빙 경로가 외부 API 제공업체임을 의미.
- `provider: openai` — 사용 중인 외부 모델 서비스.
- **폴백**: `local vLLM` — 시스템이 단일 경로에만 의존하지 않음을 의미. API가 사용 불가능해지거나 특정 요건을 충족하지 못하면 로컬 모델 서빙 옵션이 백업으로 존재.
- **요구사항**:
  - `p95_latency_target: 1200ms` — 기대되는 사용자 경험을 정의.
  - `data_residency: false` — 데이터에 대한 로컬 통제가 필요한지 여부를 나타냄.
  - `gpu_team: false`(GPU 팀 없음) — 왜 이 단계에서 API 배포가 더 현실적인 주 선택인지를 설명.
- 중요한 프로덕션 교훈: 배포 선택은 설정과 정책에 명시적으로 문서화되어야 함 — 그렇게 해야 근거가 가시적이고 검토 가능해짐. 인프라 결정은 요구사항과 폴백 계획을 통해 명확하게 표현될 때 더 견고해짐.

## 예시
```yaml
# deployment.yaml (개념 구조)
mode: api
provider: openai
fallback: local_vllm

requirements:
  p95_latency_target_ms: 1200
  data_residency: false
  gpu_team: false
```

```text
[이커머스 하이브리드 배포 사례]
복잡한 상품 추천 (트래픽 5%)   → GPT-4 API (고가치, 고품질 필요)
단순 FAQ 라우팅 (트래픽 80%)  → 로컬 Llama 3 (대량, 저복잡도, 비용 절감)
엣지 케이스 (트래픽 15%)      → GPT-3.5 API 폴백

결과: 전체 API 대비 60% 비용 절감, 99.2% 가동률
```

| 배포 방식 | 적합한 경우 |
|---|---|
| API | 프로토타이핑, 최신 모델 필요, 트래픽 낮음(월 1000만 미만) |
| 로컬 | 트래픽 매우 높음(월 5000만 초과), 엄격한 컴플라이언스, 커스텀 통제 필요 |
| 하이브리드 | 작업 복잡도에 따라 라우팅 — 대부분의 실전 프로덕션에서 가장 실용적 |

## 요약
- API 배포와 로컬 배포 사이의 선택은 모델 선호가 아니라 트래픽 규모(월 2000만 요청 근방의 손익분기점), 컴플라이언스 요구, 커스터마이징 필요, 운영 성숙도(GPU 팀 보유 여부)에 따라 결정되어야 하며, 이커머스 하이브리드 사례처럼 고가치·복잡한 작업은 프리미엄 API로, 대량·단순 작업은 로컬 모델로, 엣지 케이스는 폴백 API로 라우팅하는 계층화된 전략이 비용과 신뢰성을 동시에 개선하는 경우가 많고, 이런 결정은 `deployment.yaml` 같은 명시적 설정과 폴백 계획으로 문서화되어야 한다.
