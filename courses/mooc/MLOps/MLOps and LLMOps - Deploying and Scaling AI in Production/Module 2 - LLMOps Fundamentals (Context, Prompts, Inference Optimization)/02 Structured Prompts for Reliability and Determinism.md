# Structured Prompts for Reliability & Determinism

## 개요
- 프롬프트를 5개 섹션(Role, Task, Constraints, Format, Examples)으로 구조화해 출력의 일관성·신뢰성을 높이는 방법과, 실제 정확도 개선 수치(71%→96%)를 다루는 6분 영상.

## 내용

### 구조화된 프롬프트란
- 지시문을 무작위적이고 느슨한 방식으로 작성하지 않고, 명확한 섹션으로 조직화하는 것.
- 프로덕션 AI에서 중요한 이유: 일관성 있고(consistent), 검증하기 쉽고(easy to validate), 파싱하기 쉽고(easy to parse), 애플리케이션에서 사용하기 더 안전한(safer to use) 출력을 원하기 때문.

### 프롬프트 구조의 5개 섹션
1. **Role(역할)**: 모델이 무엇처럼 행동해야 하는지 알려줌.
2. **Task(작업)**: 무엇을 해야 하는지 알려줌.
3. **Constraints(제약)**: 어떤 규칙을 따라야 하는지 알려줌.
4. **Format(형식)**: 답변이 어떻게 보여야 하는지 알려줌.
5. **Examples(예시)**: 샘플 입력-출력 동작을 보여줌.
- 이 섹션들을 사용하면 프롬프트가 더 명확해지고 더 신뢰할 수 있게 됨 — 프롬프트를 섹션으로 나누면 모델이 따르기 더 쉬워짐.

### 구조의 실제 영향(수치 사례)
- 동일한 작업, 동일한 모델에서 구조화된 프롬프트는 **라우팅 정확도를 71%에서 96%로 개선**.
- 이전: "고객 지원 문의를 분류하라"는 단순한 프롬프트 → 파싱 불가능한 출력 유발.
- 이후: Role, Task, Constraints, Format과 2개의 예시를 사용한 프롬프트 → 결과가 훨씬 좋아짐.
  - 파싱 오류(parse errors): **15% → 0.5%**로 감소.
  - 정확도: **71% → 96%**로 향상.
- 교훈: 더 나은 구조는 출력 품질과 신뢰성을 모두 강력하게 개선할 수 있음.

### 퓨샷 예시(Few-shot Examples)
- 프롬프트 안에 2~3개의 입력-출력 쌍(pair)을 추가하는 것을 의미.
- 이런 예시들은 모델이 어떤 종류의 답변이 기대되는지, 어떤 형식을 따라야 하는지, 유사한 입력에 대해 어떻게 동작해야 하는지 이해하는 데 도움 — 혼란을 줄이고 일관성을 향상시킴.
- 예시는 단순히 추가 세부사항이 아니라 모델을 올바른 패턴으로 안내하는 역할 — 모델이 기대되는 스타일과 형식을 모방하도록 돕는 작은 설명.

### 핵심 원칙 4가지
1. **5섹션 구조 사용**: Role, Task, Constraints, Format, Examples.
2. **명시적 제약 작성**: 모델에게 무엇을 하지 말아야 하는지, 무엇만 해야 하는지 알려줄 것.
3. **정확한 출력 형식 정의**: JSON이나 CSV 등.
4. **2~3개의 서로 다른 퓨샷 예시 사용**: 이런 예시들이 일관성을 크게 향상시킴.
- 핵심 아이디어: 좋은 프롬프트는 **계약(contract)**처럼 작동해야 함 — 답변의 내용과 형식을 모두 명확히 정의해야 함.

### 실전 예시: 출력 스키마
- 스키마 구성 요소: `answer`(답변), `evidence`(근거), `confidence`(신뢰도), `follow_up_needed`(후속 조치 필요 여부).
- 이는 출력을 예측 가능하게 만듦 — 무작위 자유 텍스트 대신 구조화된 답변을 얻어 검증·비교가 쉬워짐.
- 실질적 이점:
  - 스키마를 요청하면 응답 변동성과 파싱 실패가 줄어듦.
  - `confidence`와 `follow_up_needed`는 처리를 더 안전하게 만듦.
  - `evidence` 리스트는 근거 없는 주장(unsupported claims)을 억제함.
- 최종 교훈: 좋은 프롬프트 계약은 답변의 내용과 형태(shape)를 모두 정의함 — 스키마를 요청하면 답변이 실제 시스템에서 더 쉽고 안전하게 사용 가능해짐.

## 예시
```text
[구조화된 프롬프트 5개 섹션]
Role        : "당신은 고객 지원 티켓 분류 전문가입니다."
Task        : "다음 고객 문의를 카테고리로 분류하세요."
Constraints : "카테고리 목록 외의 값을 생성하지 마세요. 추측하지 말고 근거가 없으면 'unknown'을 반환하세요."
Format      : "JSON 형식: {answer, evidence, confidence, follow_up_needed}"
Examples    : "입력: '결제가 안 돼요' → 출력: {\"answer\": \"billing\", ...}"
```

```json
// 출력 스키마 예시
{
  "answer": "billing",
  "evidence": ["결제 실패 관련 키워드 포함"],
  "confidence": 0.92,
  "follow_up_needed": false
}
```

| 프롬프트 유형 | 파싱 오류율 | 정확도 |
|---|---|---|
| 단순 프롬프트("분류하라") | 15% | 71% |
| 구조화된 프롬프트(5섹션+예시 2개) | 0.5% | 96% |

## 요약
- 프롬프트를 Role/Task/Constraints/Format/Examples 5개 섹션으로 구조화하고 2~3개의 퓨샷 예시를 포함하면 파싱 오류가 15%에서 0.5%로 줄고 정확도가 71%에서 96%로 오르는 것처럼 출력 품질과 신뢰성이 크게 향상되며, `answer`/`evidence`/`confidence`/`follow_up_needed` 같은 명확한 출력 스키마를 요청하는 것이 좋은 프롬프트를 내용과 형식 모두를 정의하는 하나의 계약(contract)으로 만드는 핵심이다.
