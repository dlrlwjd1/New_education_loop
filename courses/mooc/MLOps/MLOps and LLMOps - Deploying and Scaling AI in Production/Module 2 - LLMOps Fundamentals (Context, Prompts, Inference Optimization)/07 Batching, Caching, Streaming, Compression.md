# Batching, Caching, Streaming, Compression

## 개요
- AI 프로덕션 시스템에서 속도·처리량·비용을 개선하는 3가지 실전 최적화 기법 — **배칭(Batching), 캐싱(Caching), 스트리밍(Streaming)**, 그리고 프롬프트 캐싱 — 을 시맨틱 캐시 사례(캐시 히트 시 30ms vs 신규 생성 1200ms)와 스트리밍 사례(TTFT 280ms)로 설명하는 11분 영상.

## 내용

### 세 기법의 역할 분담
- 최적화는 하나의 트릭이 아니라, 지연이나 비용이 어디서 발생하는지 이해하고 그 부분에 맞는 방법을 적용하는 것.
  - **배칭**: 많은 요청을 처리해야 할 때 **처리량(throughput)**을 개선.
  - **캐싱**: 시스템이 이미 한 작업을 반복하지 않도록 함.
  - **스트리밍**: 응답이 더 빠르게 느껴지도록 해 **사용자 경험**을 개선.
- 세 기법 각각 다른 종류의 문제를 해결하며, 함께 사용할 때 가장 강력함.

### 시맨틱 캐싱(Semantic Caching) 실전 사례
- 캐싱은 정확히 일치하는 것만 저장하는 것이 아니라, **의미(meaning)에 기반한 캐시**도 가능함.
- FAQ 봇 예시: 사용자 질문을 임베딩으로 변환 → Redis 같은 벡터 스토어에서 유사한 질문이 이미 답변된 적 있는지 검색.
- 예: 사용자가 "환불 정책이 뭔가요?"라고 질문 → 시스템이 이를 임베딩 → Redis 벡터 스토어 검색 → 유사도 점수 **0.98**로 이전에 캐시된 환불 정책 답변 발견 → 임계값 **0.95**보다 높으므로 새로 LLM을 호출하는 대신 캐시된 응답 반환.
- **효과**: 캐시된 응답은 **30밀리초**만에 반환 vs 새로 생성 시 **1,200밀리초** — 큰 속도 개선. 불필요한 모델 호출도 피해 자원도 절약.
- **2주 후 68%의 캐시 히트율(cache hit rate)** 달성 — 반복되는 질의에서 **68%의 비용 절감** 효과.
- 핵심 요점: 시맨틱 캐싱은 FAQ, 지원 시스템, 반복되는 정보성 질의처럼 사용자가 조금씩 다른 표현으로 같은 것을 자주 묻는 사용 사례에서 특히 효과적.

### 스트리밍(Streaming) — 체감 속도의 힘
- 핵심 통찰: **체감 속도(perceived speed)가 총 완료 시간보다 더 중요한 경우가 많음**.
- **비-스트리밍 시스템**: 사용자는 전체 응답이 생성될 때까지 아무것도 보지 못하고 기다림 — 예: 답변이 나타나기까지 **3.2초** 대기.
- **스트리밍 시스템**: 응답이 토큰 단위로 거의 즉시 나타나기 시작 — 예: 첫 토큰이 **280밀리초** 만에 도착.
- 전체 응답을 마치는 데 걸리는 총 시간은 비슷해도, 사용자는 진행 상황을 거의 즉시 보게 되어 체감 응답성이 극적으로 달라짐 — **10배 더 빠르게 느껴질 수 있음**.
- **실제 지연시간(actual latency)**은 응답 완료까지의 전체 시간, **체감 지연시간(perceived latency)**은 사용자가 기다린다고 느끼는 시간 — 이 둘을 구분하는 것이 중요.
- 스트리밍은 비용을 반드시 늘리지 않으면서 체감 지연시간을 개선한다는 점에서 강력함 — 채팅 인터페이스, 코파일럿, 어시스턴트처럼 즉각적인 피드백을 기대하는 인터랙티브 AI 경험에서 특히 가치 있음.
- 핵심 요점: 시스템을 반응성 있게 느끼게 하려면, 마지막 토큰까지의 시간을 줄이는 것보다 **첫 토큰까지의 시간(TTFT)을 줄이는 것**이 더 중요한 경우가 많음.

### 핵심 원칙 4가지
1. **적극적으로 캐시하라(Cache Aggressively)**: FAQ와 지원 질의에 시맨틱 캐싱을 특히 강조 — 사용자가 반복적이거나 유사한 질문을 자주 한다면, 매번 모델을 호출하는 대신 이전 답변을 재사용해야 함.
2. **항상 스트리밍하라(Stream Always)**: 스트리밍은 추가 비용 없이 체감 지연시간을 개선하고 시스템을 더 빠르게 느끼게 함 — 인터랙티브 경험에서 가장 쉽고 가치 높은 개선 중 하나.
3. **오프라인 작업은 배칭하라(Batch Offline Tasks)**: 즉각적인 답변이 필요 없는 워크로드(일일 리포트, 요약 작업)는 짧게 지연되어도 괜찮아 배칭의 좋은 후보 — 요청을 그룹화해 처리량을 개선하고 인프라를 더 효율적으로 사용.
4. **프롬프트 캐싱**: 긴 시스템 프롬프트나 반복되는 지시문처럼 입력 프롬프트의 큰 부분이 요청마다 재사용될 때 특히 유용 — **입력 비용의 90% 절감**을 만들어낼 수 있음.
- 핵심 요점: 반복되는 질의는 캐싱의 혜택, 인터랙티브 채팅은 스트리밍의 혜택, 지연 가능한 백그라운드 작업은 배칭의 혜택, 재사용되는 프롬프트 구조는 프롬프트 캐싱의 혜택을 받음 — 최선의 최적화 전략은 시스템이 다루는 요청 유형에 따라 달라짐.

### 실전 설정 예시: `serving-config.yaml`
- **배칭 섹션**: `max_batch = 8` — 시스템이 처리를 위해 최대 8개의 요청을 함께 그룹화할 수 있음. 배칭은 대체로 설정을 통해 제어되고 워크로드 요구에 따라 튜닝됨.
- **캐싱 섹션**: `semantic_cache = true` — 시스템이 의미상 유사한 이전 응답을 찾아 가능하면 재사용하도록 설정됨. 흔한 질의의 반복 비용을 줄이고 속도를 개선.
- **스트리밍 섹션**: `enabled = true`, `first_token_target_ms = 350` — 시스템이 출력을 스트리밍하도록 설계되었고 350밀리초 이하의 첫 토큰 경험을 목표로 함 — 사용자 경험과 관련된 측정 가능한 성능 목표를 가짐.
- 각 최적화가 명시적인 시스템 설정으로 전환됨을 주목 — 프로덕션에서 최적화는 개념적으로만 논의되는 것이 아니라 서비스 설계, 설정, 모니터링, 튜닝 프로세스의 일부가 됨.

### 결론
- 배칭, 캐싱, 스트리밍을 **함께** 사용해야 함 — 각각이 지연시간 곡선의 다른 부분을 해결하기 때문.
- 배칭은 그룹화된 워크로드의 효율성을 개선하고, 캐싱은 불필요한 반복 연산을 제거하며, 스트리밍은 체감 응답 상태를 개선함.
- 프로덕션 AI의 최적화는 다차원적임 — 더 나은 모델을 선택하는 것뿐 아니라, 언제 작업을 재사용할지, 언제 작업을 그룹화할지, 언제 사용자에게 작업을 더 일찍 드러낼지 결정함으로써 시스템을 개선할 수 있음.

## 예시
```yaml
# serving-config.yaml (개념 구조)
batching:
  max_batch: 8

caching:
  semantic_cache: true
  similarity_threshold: 0.95

streaming:
  enabled: true
  first_token_target_ms: 350
```

```text
[시맨틱 캐싱 사례 — FAQ 봇]
질문: "환불 정책이 뭔가요?"
    │
    ▼ 임베딩 → Redis 벡터 스토어 검색
유사 질문 발견 (유사도 0.98 ≥ 임계값 0.95)
    │
    ▼
캐시된 응답 반환: 30ms (vs 신규 생성 1200ms)
2주 후 캐시 히트율 68% → 비용 68% 절감
```

```text
[스트리밍 사례 — 체감 속도]
비-스트리밍: 3.2초 대기 후 전체 답변 표시
스트리밍:   280ms만에 첫 토큰 표시 → 체감 속도 최대 10배 향상
(실제 총 완료 시간은 비슷해도 체감 지연시간은 크게 다름)
```

| 요청 유형 | 최적 기법 |
|---|---|
| 반복되는 FAQ/지원 질의 | 시맨틱 캐싱 |
| 인터랙티브 채팅 | 스트리밍 |
| 지연 가능한 백그라운드 작업(리포트, 요약) | 배칭 |
| 반복되는 긴 시스템 프롬프트 | 프롬프트 캐싱(입력 비용 최대 90% 절감) |

## 요약
- 프로덕션 AI 최적화는 배칭(그룹화된 워크로드의 처리량 개선), 캐싱(시맨틱 캐싱으로 반복 질의의 속도·비용을 30ms/68% 절감 수준까지 개선), 스트리밍(TTFT를 낮춰 체감 속도를 최대 10배 향상), 프롬프트 캐싱(반복되는 프롬프트의 입력 비용 최대 90% 절감)이라는 서로 다른 문제를 해결하는 기법들을 요청 유형에 맞게 조합해야 하며, 이런 최적화는 `serving-config.yaml` 같은 명시적 서비스 설정으로 운영되어야 한다.
