# Promoting Environments Across Dev → Staging → Production

## 개요
- 개발(Dev) → 스테이징(Staging) → 프로덕션(Production)으로 시스템을 단계적으로 승격하는 **환경 승격(Environment Promotion)** 원칙과, 자동화된 스테이징 게이트·승격 매니페스트(promotion manifest)를 다루는 8분 영상. "Environment & Dependency Management" 레슨의 마지막 영상.

## 내용

### 환경 승격이란
- 동일한 시스템을 개발 → 스테이징 → 프로덕션으로 **단계적으로** 이동시키는 것 — 코드를 검증 없이 곧바로 프로덕션에 보내서는 안 되기 때문.
- 각 단계의 목적:
  - **개발(Development)**: 구축과 테스트가 이루어지는 곳.
  - **스테이징(Staging)**: 실제 프로덕션과 유사한 환경에서 시스템을 점검하는 곳.
  - **프로덕션(Production)**: 실제 사용자가 사용하는 라이브 환경.
- 핵심 아이디어는 단순함: 프로덕션이 안전하고 안정적으로 유지되도록 한 단계에서 다음 단계로 신중하게 이동하는 것.
- **아카이브(Archive)**: 과거 감사 기록을 동결된 스냅샷(frozen snapshot) 형태로 보관하는 곳 — 고정된 요구사항(freeze requirements)이나 과거 이력(historical traces)을 아카이브에 저장.

### 승격 전 필요한 체크
- **개발 → 스테이징**: 모든 유닛 테스트와 데이터 체크가 통과해야 함.
- **스테이징 → 프로덕션**: 더 강력한 체크가 필요 — **평가 게이트(evaluation gate), 부하 테스트(load test), 승인/사인오프(sign-off)**.
- 중요한 규칙: **빠른 수정을 위해 단계를 건너뛰지 말 것** — 개발에서 프로덕션으로 곧바로 뛰어넘어서는 안 됨. 모든 단계는 이유가 있고, 모든 단계는 리스크를 줄이는 데 도움이 됨.

### 자동화된 스테이징 게이트
- 모든 환경 승격은 자동 게이트를 트리거함:
  1. 깨진 의존성과 스키마 불일치 확인.
  2. SHA로 고정된 베이스 이미지로 Docker 이미지 빌드.
  3. 헬스 체크(health check) 엔드포인트 실행.
  4. **20개의 실제 프로덕션 샘플**로 통합 테스트를 실행하고, 출력이 예상 스키마와 일치하는지 검증.
  5. 60초 동안 **초당 100 요청**으로 부하 테스트 실행 — **P95 지연시간이 2,000밀리초 미만**으로 유지되는지 확인.
  6. 모든 체크가 통과하면 이미지가 프로덕션 레지스트리로 푸시되고 롤링 배포(rolling deployment)가 시작됨.
- 핵심 교훈: 승격은 수동 확인에만 의존해서는 안 되며 **자동 게이트**의 지원을 받아야 함 — 중요한 체크가 자동으로 일어날 때 승격이 더 안전해짐.

### 환경 승격 4대 핵심 원칙
1. **단계를 절대 건너뛰지 말 것**: 항상 경로(dev → staging → production)를 그대로 따를 것.
2. **자동화된 체크 사용**: 승격을 수동 판단이 아닌 자동 게이트로 뒷받침할 것.
3. **실패 시 중단**: 체크가 실패하면 그 자리에서 승격을 멈출 것.
4. **모든 것을 로깅**: 무엇이 승격되었고 왜 통과했는지 기록할 것.
- 이 규칙들은 승격을 더 안전하고, 추적 가능하고, 관리하기 쉽게 만듦.

### 승격 매니페스트(Promotion Manifest) 예시
- 파일명: `promotion.yaml`.
- 기록하는 내용: 아티팩트 이름, 버전, 이전 단계 → 다음 단계, 체크 결과(평가 점수, 스모크 테스트, 승인 상태) 등.
- 이는 무엇이 승격되었고 왜 다음 단계로 진행이 허용되었는지에 대한 명확한 기록을 만들어 **추적과 감사를 쉽게** 함.

### 실전 교훈 3가지
1. **아티팩트를 재빌드하지 말고 앞으로 승격(promote)하라**.
2. **평가 결과, 스모크 테스트, 승인을 아티팩트와 함께 기록하라**.
3. **단일 매니페스트로 단계 전환(stage transaction)을 추적하라**.
- 결과: 프로덕션이 이전에 이미 검증된 것을 그대로 반영(mirror)함.
- 가장 중요한 메시지: **승격은 불변(immutable) 아티팩트를 앞으로 이동시키는 것이지, 그 과정에서 새로 만드는 것이 아니다.** 일단 테스트되고 승인된 것은, 신선한 버전을 재빌드하는 대신 **정확히 동일한 아티팩트**를 다음 단계로 이동시켜야 함 — 이것이 프로덕션이 이미 검증된 것을 실행하고 있음을 보장하는 방법. 동일한 검증된 아티팩트가 앞으로 이동해야 하며, 승격 과정에서 다시 빌드해서는 안 됨.

### 결론
- 환경 승격은 개발 → 스테이징 → 프로덕션으로 안전하게 이동하는 것을 의미하며, 절대 단계를 건너뛰지 않고, 자동화된 게이트를 사용하고, 항상 검증된 아티팩트를 앞으로 이동시켜야 함 — 이것이 프로덕션을 더 안전하고, 안정적이고, 감사하기 쉽게 만듦.

## 예시
```text
[환경 승격 경로와 체크]
Development (유닛 테스트 + 데이터 체크 통과)
        │
        ▼
Staging (평가 게이트 + 부하 테스트 + 승인/사인오프)
        │
        ▼
Production (자동 게이트 통과 후 롤링 배포)

Archive: 동결된 스냅샷(freeze requirements, historical traces) 보관
```

```text
[자동화된 스테이징 게이트 6단계]
1. 의존성/스키마 불일치 확인
2. SHA 고정 베이스 이미지로 Docker 빌드
3. 헬스 체크 엔드포인트 실행
4. 실제 프로덕션 샘플 20개로 통합 테스트(출력 스키마 검증)
5. 초당 100 요청, 60초 부하 테스트 (P95 < 2000ms)
6. 모두 통과 → 프로덕션 레지스트리 푸시 + 롤링 배포 시작
```

```yaml
# promotion.yaml (개념 구조)
artifact: fraud-detector:2.1.0
from_stage: staging
to_stage: production
checks:
  evaluation_score: 0.91
  smoke_test: passed
  load_test_p95_ms: 1840
approval: signed_off_by: "ml-lead@company.com"
```

## 요약
- 환경 승격은 개발 → 스테이징 → 프로덕션이라는 경로를 절대 건너뛰지 않고, 단계마다 강화되는 자동화된 게이트(유닛 테스트·데이터 체크 → 평가 게이트·부하 테스트·승인)를 통과시키며, `promotion.yaml` 같은 매니페스트로 무엇이 승격되었는지 기록해 추적·감사를 쉽게 만들고, 무엇보다 검증된 아티팩트를 재빌드 없이 그대로 다음 단계로 이동시키는 것이 핵심 원칙이다.
