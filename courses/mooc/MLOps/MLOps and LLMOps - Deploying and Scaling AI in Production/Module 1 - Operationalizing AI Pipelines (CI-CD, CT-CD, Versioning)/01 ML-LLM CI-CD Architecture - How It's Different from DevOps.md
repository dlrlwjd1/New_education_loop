# ML/LLM CI/CD Architecture: How It's Different from DevOps

## 개요
- 전통적인 DevOps의 CI/CD와 ML/LLM 시스템의 CI/CD가 어떻게 다른지, ML/LLM 파이프라인에 필요한 **3가지 추가 게이트(gate)**를 Netflix 추천 시스템 사례와 함께 설명하는 9분 영상. Module 1 "Foundations of CI/CD for ML & LLM Systems" 레슨의 첫 번째 영상.

## 내용

### 왜 ML/LLM 릴리스 프로세스는 더 넓은가
- 소프트웨어 공학에서 CI/CD는 주로 코드를 다루고, 테스트하고, 안전하게 배포하는 것에 관한 것.
- 하지만 ML/LLM 시스템에서는 릴리스 프로세스가 훨씬 넓어짐 — 소스 코드뿐 아니라 **데이터, 모델, 프롬프트, 진화하는 로직(evolution logic), 런타임 동작(runtime behavior)**까지 관리해야 함.

### DevOps 대비 ML/LLM 파이프라인의 핵심 차이 4가지
1. **3가지 추가 게이트 필요**: 전통적 DevOps는 빌드 검증, 유닛 테스트, 통합 테스트, 배포 체크에 의존. ML 시스템에서는 이것만으로 부족 — **데이터 검증(data validation)**, **모델 평가(model evaluation)**, 그리고 LLM 시스템에서는 **응답 품질과 프롬프트 동작 검사**까지 추가로 필요.
2. **침묵의 실패(Silent Failure)**: ML의 프로덕션 실패는 종종 조용히(silently) 발생 — 서비스는 정상 작동 중이어도 모델 품질은 이미 저하되고 있을 수 있음. 즉 배포 상태가 "green"이라고 해서 항상 비즈니스 성공을 의미하지는 않음.
3. **코드 중심 vs 데이터·모델 중심**: DevOps는 대체로 코드 중심(code-centric)이지만, ML/LLM 파이프라인은 데이터와 모델에 의존하는 동작(data and model dependent behavior)까지 추적해야 함.
4. **코드 변경 없이도 망가질 수 있음**: 전통적 소프트웨어와 가장 큰 차이 중 하나 — 모델은 코드 변경 없이도 유입 데이터나 사용자 행동이 바뀌는 것만으로 성능이 저하될 수 있음.

### DevOps vs MLOps vs LLMOps 비교
| 구분 | DevOps | MLOps | LLMOps |
|---|---|---|---|
| 버저닝 대상 | 소스 코드 | 코드 + 데이터셋, 피처 파이프라인, 학습된 모델, 평가 지표 | 코드 + 모델 + 프롬프트, 검색(retrieval) 파이프라인, 모델 설정, 품질 평가 |
| 테스트 | 소프트웨어 정확성 중심(유닛+통합 테스트) | 데이터·모델 검증 게이트 추가 | 환각(hallucination) 검사 등 추가 |
| 배포 아티팩트 | 애플리케이션 패키지/컨테이너 | 코드 + 데이터(피클 파일 등) | 모델 + 프롬프트 + 설정 |
| 핵심 메시지 | 소프트웨어 딜리버리 관리 | 소프트웨어 + 모델 딜리버리 관리 | 소프트웨어 + 모델 + 프롬프트 + 컨텍스트 딜리버리 관리 |

### 표준 DevOps 사고를 ML에 그대로 적용할 때 생기는 문제 (Salient Features)
1. **유닛 테스트는 통과하지만 데이터가 잘못된 경우**: 스키마가 변경되거나, 키 값이 누락되거나, 분포가 이동했을 수 있음 — 코드는 작동하지만 모델 입력을 더 이상 신뢰할 수 없는 상태.
2. **드리프트(Drift)**: 파이프라인이 성공적으로 실행되고 모델이 정상적으로 배포되어도, 실세계 데이터가 충분히 변해 예측이 더 이상 신뢰할 수 없게 됨.
3. **배포 후 품질 저하**: 인프라 상태(health)는 정상으로 보여도, 새 모델이 이전 모델보다 나빠서 비즈니스 성능이 떨어질 수 있음.
- 이 때문에 ML 파이프라인은 일반적인 CI/CD 체크보다 더 많은 계층(데이터 검증, 평가 임계값, 배포 후 모니터링)의 보호가 필요.

### ML CI/CD가 다른 근본 이유
- ML CI/CD는 시스템의 **1급 구성 요소(first-class part)** — 전통적 DevOps에서 애플리케이션 동작은 대체로 코드가 바뀔 때만 변하지만, ML에서는 코드, 데이터, 재학습, 피처 엔지니어링 변경, 모델 버전 업데이트로도 동작이 바뀔 수 있음.
- **비결정성(Non-determinism)**: 동일한 코드로 학습을 다시 실행해도 무작위성, 샘플링, 진화하는 데이터로 인해 정확히 같은 결과가 나오지 않을 수 있음.
- ML/LLM 시스템의 품질 문제는 즉각적인 실패가 아닌 경우가 많고 시간이 지나며 점진적으로 저하될 수 있음 — 따라서 **모니터링과 지속적 평가는 CI/CD와 분리된 것이 아니라 CI/CD의 일부**여야 함.
- 핵심 메시지: ML/LLM CI/CD는 배포뿐 아니라 생애주기 전반에 걸친 **데이터 품질, 모델 품질, 출력 품질**을 통제·검증해야 함.

### 사례: Netflix 추천 시스템 CI/CD
- **DevOps 배포(왼쪽)**: 코드 푸시 → 유닛 테스트 통과 → 배포. 실패 지점: 새 데이터 벤더가 30% 행(row)에 null 값을 추가 → 모델이 손상된 데이터로 조용히 학습됨 → 추천 품질이 12% 하락했으나 **3일 후에야 발견됨**.
- **게이트 2(모델 평가)**: `NDCG@10 ≥ baseline × 0.99`를 만족해야만 통과.
- **게이트 3(프롬프트 품질)**: LLM 설명의 일관성 점수(coherence score)가 **0.85 이상**이어야 함.
- 이런 게이트들이 있었다면 결과는 달랐을 것 — **널 데이터가 게이트 1(데이터 검증)에서 이미 걸러졌을 것이고, 프로덕션 사고는 0건**이었을 것.
- 핵심 교훈: **ML 파이프라인은 DevOps 대비 3개의 추가 게이트가 필요하며, 각 게이트는 특정한 형태의 침묵의 실패(silent failure)를 방지**한다.

## 예시
```text
[ML/LLM CI/CD 3대 추가 게이트]
게이트 1: 데이터 검증(Data Validation) — 스키마·결측치·분포 이동 확인
게이트 2: 모델 평가(Model Evaluation) — 예: NDCG@10 ≥ baseline × 0.99
게이트 3: 프롬프트/응답 품질(LLM 전용) — 예: 일관성 점수(coherence score) ≥ 0.85
```

```text
[Netflix 추천 시스템 사고 시나리오]
새 데이터 벤더 추가 → 30% 행에 null 값 유입
        │
        ▼ (게이트 없이 DevOps만 적용 시)
코드 푸시 → 유닛 테스트 통과 → 배포 → 모델이 손상된 데이터로 조용히 학습
        │
        ▼
추천 품질 12% 하락 → 3일 후 발견 (침묵의 실패)

        │ (3대 게이트 적용 시)
        ▼
게이트 1(데이터 검증)에서 null 값 즉시 차단 → 프로덕션 사고 0건
```

## 요약
- ML/LLM 시스템의 CI/CD는 코드만 다루는 전통적 DevOps와 달리 데이터·모델·프롬프트·런타임 동작까지 관리해야 하며, 코드 변경 없이도 데이터나 사용자 행동 변화만으로 품질이 조용히 저하될 수 있다는 점에서 데이터 검증·모델 평가·프롬프트 품질이라는 3가지 추가 게이트가 필수적이고, 이 게이트들이 Netflix 사례처럼 침묵의 실패를 조기에 차단하는 역할을 한다.
