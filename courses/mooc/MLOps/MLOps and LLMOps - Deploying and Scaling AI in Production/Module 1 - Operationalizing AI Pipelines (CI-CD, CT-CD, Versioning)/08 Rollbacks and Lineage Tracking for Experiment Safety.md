# Rollbacks & Lineage Tracking for Experiment Safety

## 개요
- ML/LLM 릴리스가 잘못되었을 때 안전하게 복구하는 방법 — **롤백 전략**과 **계보(lineage) 추적**을 통해 정확한 릴리스 이력에 기반한 롤백을 수행하는 방법을 다루는 8분 영상.

## 내용

### 왜 ML 롤백은 전통적 소프트웨어보다 복잡한가
- 전통적 소프트웨어에서 롤백은 대체로 이전 애플리케이션 버전을 재배포하는 것.
- ML 시스템에서는 이것만으로 충분하지 않음 — 프로덕션 동작이 그 시점에 함께 있던 **코드 버전, 모델 버전, 프롬프트 버전, 데이터셋 버전의 정확한 조합**에 의존하기 때문.
- 핵심 주제 2가지: (1) 빠르고 신뢰할 수 있는 롤백 전략, (2) 롤백 결정이 추측이 아닌 정확한 릴리스 이력에 기반하도록 하는 **계보 추적(lineage tracking)**.

### 롤백 전략
- ML 시스템의 롤백은 사고가 발생했을 때 즉흥적으로 만드는 것이 아니라 **사전에 계획**되어야 함.
- 좋은 롤백 전략은 "마지막으로 알려진 정상 릴리스(last known good release)"가 무엇인지 명확히 정의하는 것에서 시작 — 이는 단순히 이전 모델 버전이 아니라 **마지막으로 검증된 배포 상태(last validated deployment state)**를 의미해야 함.
- 전략은 또한 다음을 정의해야 함: 어떤 지표가 롤백을 트리거하는지, 누가/무엇이 롤백을 승인할 수 있는지, 이전 버전을 어떻게 복원하는지, 이벤트를 어떻게 기록하는지.
- 핵심 마인드셋: 롤백은 안전한 실험의 정상적인 일부 — 모델을 자주 릴리스한다면, 이를 안전하고 빠르게 되돌릴 수도 있어야 함.

### 긴급 롤백 시나리오 (실제 사고 예시)
- 새벽 2시 47분, 프로덕션 정확도가 0.89에서 0.81로 하락 — 상당한 성능 퇴보(regression)이며 온콜 런북(on-call runbook)을 트리거함.
- 중요한 점: ML 사고는 종종 **인프라 자체는 건강해 보이는 상태**에서 발생 — 서비스는 정상 작동 중이고, 지연시간도 정상이며, 요청도 정상적으로 흐르지만, **비즈니스 지표가 심각하게 저하**된 상태.
- 온콜 대응은 인프라 상태 확인에서 멈출 수 없음 — 런북은 팀을 다음 단계로 안내해야 함: 하락 확인 → 현재 배포된 릴리스 튜플 식별 → 마지막으로 알려진 정상 튜플 위치 파악 → 안전하게 복원 → 정확히 무슨 일이 일어났는지 기록.
- 이때 **롤백 규율과 계보 데이터**가 필수적임.

### 카나리 릴리스(Canary Releases)의 가치
- 모든 트래픽을 새 모델이나 릴리스 설정에 즉시 보내는 대신, 처음에는 **프로덕션 트래픽의 일부**만 노출.
- 이를 통해 품질 지표, 지연시간, 안정성, 예상치 못한 출력 행동을 관찰할 기회를 얻음.
- 카나리가 잘 작동하면 점진적으로 롤아웃을 확대하고, 성능이 저조하면 영향이 광범위해지기 전에 중단하거나 되돌릴 수 있음.
- ML/LLM 딜리버리에서 카나리가 특히 유용한 이유: 일부 실패는 실제 프로덕션 입력에서만 나타남 — 카나리는 스테이징 검증과 완전한 프로덕션 노출 사이의 **안전 버퍼(safety buffer)** 역할.

### 안전한 롤백·계보 추적의 4대 핵심 원칙
1. **결정성(Determinism)**: 롤백은 알려진 정상 상태를 근사(approximately)가 아니라 **정확히(exactly)** 복원해야 함.
2. **추적 가능성(Traceability)**: 무엇이 언제 배포되었고 어떤 업스트림 자산이 관여했는지 항상 알아야 함.
3. **통제된 속도(Speed with Control)**: 사고 상황에서 롤백은 빨라야 하지만, 팀이 상황을 더 악화시키지 않도록 하는 가드레일도 필요함.
4. **감사 가능성(Auditability)**: 모든 롤백 이벤트는 사유, 대상 버전, 타임스탬프와 함께 기록되어야 사고 검토가 사실에 기반할 수 있음.

### 계보 기반 복원(Lineage Restore)
- 롤백은 단순한 릴리스 액션이 아니라 **계보(lineage)에 기반한 복원 액션**.
- 계보는 배포된 버전이 어떻게 만들어졌는지 알려줌 — 어떤 모델이 사용되었는지, 어떤 프롬프트/서빙 설정이 연결되었는지, 어떤 데이터셋/피처 스냅샷이 뒷받침했는지, 그리고 이 자산들이 서로 어떻게 관련되었는지.
- 계보가 제대로 포착되면 롤백은 결정론적(deterministic)이 됨 — 어떤 구성 요소가 함께 속하는지 추측할 필요 없이, 안전하다고 알려진 정확한 검증된 릴리스 조합을 복원할 수 있음. 이것이 압박 속에서도 롤백을 신뢰할 수 있게 만드는 요인.

### 롤백 구현 패턴 (Python 스크립트 개념)
- 스크립트는 "마지막으로 알려진 정상 배포 상태(last good deployment state)"를 **모델 버전, 프롬프트 버전, 데이터셋 버전** 세 요소로 정의하는 것에서 시작.
- 각 부분을 명시적으로 복원: 모델 전환(switch), 프롬프트 고정(pin), 데이터셋 마운트(mount).
- 중요한 설계 선택: **모델만 롤백하지 않고 전체 배포 튜플을 복원**함.
- 이후 롤백 종류, 사유, 대상 버전과 함께 이벤트를 기록 — 운영 복구와 감사 로깅을 결합한 강력한 구현 패턴.

### 실전 예시: 전체 튜플 롤백의 중요성
- 문제가 된 배포: 모델 v2.1.0 + 프롬프트 v1.4.5 + 데이터셋 v5.1.0 조합이 프로덕션에서 드리프트를 일으키기 시작.
- 저장된 마지막 정상(green) 배포: 모델 v2.0.1 + 프롬프트 v1.4.2 + 데이터셋 v5.0.0.
- 모델만 되돌리는 대신, 롤백 스크립트가 **이전 튜플 전체**를 복원 — 실패가 모델 단독이 아니라 모델·프롬프트·데이터셋 사이의 **상호작용**에서 비롯되었을 수 있기 때문에 중요함.
- 최종 결과: 감사 로그에 롤백 사유, 복원된 정확한 버전들, 이벤트 발생 시각이 기록됨.
- 핵심 메시지: ML/LLM 시스템에서 안전한 롤백은 단순히 이전 모델로 돌아가는 것이 아니라, **계보를 사용해 마지막으로 알려진 정상 릴리스 상태를 정확히 복원하는 것**.

## 예시
```python
# rollback.py (개념 구조) — 전체 튜플 복원
LAST_GOOD_DEPLOYMENT = {
    "model_version": "2.0.1",
    "prompt_version": "1.4.2",
    "dataset_version": "5.0.0",
}

def rollback(reason: str):
    switch_model(LAST_GOOD_DEPLOYMENT["model_version"])
    pin_prompt(LAST_GOOD_DEPLOYMENT["prompt_version"])
    mount_dataset(LAST_GOOD_DEPLOYMENT["dataset_version"])

    log_event({
        "event": "rollback",
        "reason": reason,
        "restored_to": LAST_GOOD_DEPLOYMENT,
        "timestamp": get_current_timestamp(),
    })

# 사고 대응 예:
# 배포된(문제) 튜플: model 2.1.0 / prompt 1.4.5 / dataset 5.1.0 → 드리프트 발생
# rollback("production accuracy dropped from 0.89 to 0.81")
# → model 2.0.1 / prompt 1.4.2 / dataset 5.0.0 전체 복원 + 감사 로그 기록
```

```text
[긴급 롤백 대응 흐름]
지표 하락 감지(예: 정확도 0.89→0.81) → 온콜 런북 트리거
→ 현재 배포 튜플 식별 → 마지막 정상 튜플 조회(계보 데이터)
→ 전체 튜플 복원(모델+프롬프트+데이터셋) → 롤백 이벤트 감사 로그 기록
```

## 요약
- ML/LLM 시스템의 안전한 롤백은 모델만 되돌리는 것이 아니라 모델·프롬프트·데이터셋의 전체 튜플을 계보(lineage) 데이터에 기반해 결정론적으로 복원하는 것이며, 카나리 릴리스로 점진적 노출을 통해 리스크를 줄이고, 결정성·추적 가능성·통제된 속도·감사 가능성이라는 4대 원칙 아래 사전에 계획된 롤백 전략과 사고 대응 런북을 갖추는 것이 핵심이다.
