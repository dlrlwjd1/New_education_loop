# Why ML Environments Drift

## 개요
- 데이터 드리프트만큼이나 중요한 **환경 드리프트(Environment Drift)** 문제를 다루는 17분 영상 — 드리프트 유형 분류, "내 컴퓨터에서는 되는데"라는 재현성 역설(reproducibility paradox), 실전 디버깅 시나리오, 그리고 pin/hash/store 원칙을 다룸. "Environment & Dependency Management" 레슨의 첫 번째 영상.

## 내용

### 데이터·모델·코드를 넘어선 네 번째 구성 요소: 환경
- AI/LLM 시스템을 만들 때 보통 데이터, 모델, 코드 세 가지를 생각하지만, 그만큼 중요한 **네 번째 구성 요소가 환경(environment)**.
- 환경에는 Python 버전, 라이브러리 버전, 운영체제, 의존성, GPU 드라이버, CUDA 버전, 컨테이너 이미지 등이 포함됨.
- 모델은 고립되어 실행되지 않고 이 모든 작은 조각들에 의존함 — 하나라도 바뀌면 시스템의 동작이 바뀔 수 있음.
- 예: 한 버전의 NumPy나 PyTorch로 학습된 모델을 패키지가 업그레이드된 다른 환경에 배포하면, 모델 아티팩트는 동일해도 런타임 동작이 바뀔 수 있음 — 실패한 예측, 일관성 없는 출력, 디버깅하기 어려운 프로덕션 문제로 이어질 수 있음.
- 핵심 메시지: **ML 시스템은 데이터 변화뿐 아니라 환경 변화로도 드리프트된다** — 동일한 모델, 동일한 코드라도 환경이 바뀌면 결과가 항상 같지 않음.

### 드리프트 유형 분류
1. **라이브러리 버전 드리프트(Library Version Drift)**: 패키지 버전이 시간이 지나며 변경 — 예: 한 시스템은 NumPy 1.23, 다른 시스템은 NumPy 1.24 사용. 사소한 마이너 업데이트도 수치적 동작, 호환성, 내부 기본값에 영향을 줄 수 있음.
2. **CUDA 버전 드리프트**: GPU 소프트웨어 스택이 변경될 때 발생 — 성능 문제, 런타임 오류, 모델 실행 차이를 유발할 수 있음.
3. **Python 버전 드리프트**: 서로 다른 Python 버전에서 코드가 실행될 때 발생 — 일부 패키지는 인터프리터 버전에 따라 다르게 동작.
4. **시스템 의존성 드리프트(System Dependency Drift)**: 저수준 OS 라이브러리, 빌드 도구, 드라이버, 바이너리를 포함 — Python 패키지보다 눈에 덜 띄지만 여전히 ML 파이프라인에 영향을 줄 수 있음.
- 중요한 교훈: 드리프트는 데이터에서만 발생하지 않고 스택의 어디에서든 발생할 수 있음 — 그래서 증상이 혼란스러울 수 있음. 팀이 모델 문제라고 생각하지만 실제로는 의존성 불일치가 원인일 수 있음.

### 재현성 역설(Reproducibility Paradox): "내 컴퓨터에서는 되는데"
- "works on my machine"이라는 문구는 배포 사고가 발생하기를 기다리는 것과 같음.
- 개발자는 자신의 코드가 정상 작동한다고 정직하게 말할 수 있지만, 다른 팀원, CI 파이프라인, 프로덕션 서버가 동일한 코드를 실행하면 실패하거나 다르게 동작할 수 있음 — 이는 시스템이 진정으로 재현 가능하지 않다는 뜻.
- 근본 문제: 한 머신의 환경이 다른 머신의 환경과 다름 — 패키지 버전, Python 인터프리터, CUDA 런타임, OS 라이브러리, 숨겨진 전이 의존성(transitive dependency) 등이 변했을 수 있음.
- 해법: **결정론적 환경(deterministic environments)** — **모든 것을 고정(pin)하고, 모든 것을 해시(hash)하라**.
  - **핀 everything**: 버전을 열린 범위로 두지 않음 — "최신 NumPy 설치"가 아니라 "정확히 동일한 NumPy 버전 설치"라고 명시. 고정(pinning)은 모호함을 제거.
  - **해시 everything**: 버전 번호만으로는 충분하지 않을 때가 있음 — 해시는 우리가 설치하려는 정확한 아티팩트가 실제로 설치된 것인지 검증하는 방법.
- 진짜 목표: 한 번 실행되는 코드가 아니라, 머신·팀·시간에 걸쳐 신뢰성 있게 동작하는 코드.

### 실전 디버깅 시나리오: 드리프트로 인한 프로덕션 사고
- 상황: 프로덕션에서 모델 정확도가 하락. 처음에는 나쁜 입력 데이터, 손상된 피처 파이프라인, 모델 손상, 서빙 버그를 의심하지만, 실제 원인은 환경.
- **디버깅 흐름 4단계**:
  1. **증상 인식**: 프로덕션 모델 정확도 하락을 발견 — 무언가 바뀌었다는 신호지만 정확히 무엇인지는 아직 모름.
  2. **환경 비교**: 개발 환경과 프로덕션 환경을 비교 — `pip freeze > prod.txt` 같은 명령으로 설치된 의존성을 텍스트 파일로 내보내고, 개발 환경에서도 동일하게 실행해 두 출력을 비교.
  3. **불일치 찾기**: 예를 들어 로컬 환경은 한 버전의 라이브러리를, 프로덕션은 다른 버전을 사용 — 핵심 교훈: 버전의 작은 차이가 중요할 수 있음. 많은 사람이 마이너 업데이트는 안전하다고 가정하지만, ML/LLM/AI 시스템은 민감할 수 있음(전처리, 수치 정밀도, 배열 동작, 다른 라이브러리와의 호환성, 학습/추론 결과에 영향).
  4. **근본 원인 식별**: 불일치를 찾은 후, 그 의존성 차이가 정확도 하락을 설명하는지 테스트.
- **재발 방지**: 근본 원인을 찾은 후, 향후 배포가 조용히 드리프트하지 않도록 환경을 제대로 잠가야(lock) 함.
- 운영상 중요한 습관: ML/LLM 동작이 예기치 않게 바뀌면 **환경을 먼저 비교**해야 함 — 문제가 모델이나 데이터에만 있다고 가정하지 말 것.
- 배운 점: 프로덕션 사고는 의존성 드리프트에서 비롯될 수 있고, `pip freeze`는 간단하지만 유용한 디버깅 도구이며, 근본 원인 분석(RCA)은 환경 비교를 포함해야 함 — 좋은 디버깅은 증거 기반(evidence-based)이어야 함.

### 환경 드리프트 방지를 위한 4대 핵심 원칙
1. **모든 것을 고정(Pin Everything)**: 느슨한 버전 범위 대신 정확한 버전 사용 — 예: `numpy>=1.23` 대신 `numpy==1.23.1`. 느슨한 범위는 의도적인 검토 없이도 환경이 시간이 지나며 변할 수 있게 만듦.
2. **해시 검증(Hash Verification)**: 버전 번호는 원하는 릴리스를 알려주지만, 해시는 정확한 패키지 파일을 검증하는 데 도움 — 우발적인 변형을 방지하고 설치 프로세스에 대한 신뢰를 높임.
3. **재현 가능한 빌드(Reproducible Builds)**: 환경이 일관되게 재생성되어야 함 — 오늘, 다음 주, 또는 다른 머신에서 동일한 프로젝트를 빌드하면 동등한 결과를 얻어야 함. 실험, CI/CD 파이프라인, 배포 롤(rollout), 감사, 디버깅에서 중요.
4. **버전 관리되는 환경(Version Control Environments)**: 환경 정의도 코드처럼 Git에 커밋되어야 함 — 환경이 시스템의 일부이므로 그 변경도 가시적이고 검토 가능하며 추적 가능해야 함.
- 큰 교훈: 환경 관리는 소프트웨어 엔지니어링 규율의 일부이며 선택적인 오버헤드가 아님 — 신뢰할 수 있는 ML 시스템/파이프라인을 만드는 것의 일부.

### 의존성 스냅샷 예시
- `environment-snapshot.yml` 파일이 Python 버전, PyTorch 버전, Transformers 버전, CUDA, 이미지 태그, 로그 파일 해시 같은 세부 정보를 기록 — 환경의 압축된(compact) 기록을 제공.
- **freeze → hash → store → result** 흐름:
  - **Freeze**: 정확한 소프트웨어 버전을 기록해 나중에 추측할 필요 없게 함.
  - **Hash**: 로그 파일 같은 중요한 것에 대한 지문(fingerprint)을 생성 — 두 환경 정의가 정확히 동일한지 검증 가능.
  - **Store**: 환경 메타데이터를 실행(run), 모델 버전, 배포 기록과 함께 보관 — 환경 세부사항이 저장되지 않으면 재현성은 기억력에 의존하게 되어 신뢰할 수 없게 됨.
  - **Result**: 며칠, 몇 주가 지나도 다른 엔지니어가 어떤 환경이 사용되었는지 이해할 수 있는 더 강한 재현성.
- **환경 메타데이터를 모델 지표, 하이퍼파라미터, 데이터셋 버전, 실행 ID, 체크포인트와 나란히 1급 실험 데이터(first-class experiment data)로 취급**해야 함 — 프로덕션급 ML/LLM 시스템에서 환경 메타데이터는 증거 추적(evidence trail)의 일부.

### 결론
- 환경 드리프트란 소프트웨어 스택이 변경되어 코드가 동일해 보여도 모델 동작이 바뀌는 것.
- 신뢰할 수 있는 LLM/AI 기반 시스템을 만들려면 환경을 코드처럼 다뤄야 함 — **정의하고(define), 잠그고(lock), 추적하고(track), 재현하라(reproduce)**.

## 예시
```text
[재현성 역설 해법]
"works on my machine" (경고 신호)
        │
        ▼
결정론적 환경 = Pin Everything + Hash Everything
        │
        ├─ Pin: numpy==1.23.1 (느슨한 numpy>=1.23 금지)
        └─ Hash: 패키지 파일의 정확한 지문 검증
```

```yaml
# environment-snapshot.yml (개념 구조)
python_version: "3.10.12"
pytorch_version: "2.1.0"
transformers_version: "4.35.0"
cuda_version: "12.1"
image_tag: "ml-serving:v2.1.0-cuda12.1"
requirements_hash: "sha256:9f8a3c1e..."
```

```bash
# 드리프트 디버깅 4단계
pip freeze > dev.txt       # 개발 환경 스냅샷
pip freeze > prod.txt      # 프로덕션 환경 스냅샷
diff dev.txt prod.txt      # 불일치 확인
# → 불일치 발견 시 해당 의존성이 정확도 하락의 원인인지 테스트
# → 원인 확인 후 버전 고정(pin)으로 재발 방지
```

## 요약
- ML/LLM 시스템은 데이터 변화뿐 아니라 라이브러리·CUDA·Python·시스템 의존성 버전 변화라는 환경 드리프트로도 성능이 저하될 수 있으며, "내 컴퓨터에서는 되는데"라는 재현성 역설을 해결하려면 모든 버전을 고정(pin)하고 해시로 검증하며, 환경 정의를 코드처럼 버전 관리하고 `environment-snapshot.yml` 같은 형태로 모델 지표와 나란히 1급 실험 데이터로 저장해야 하고, 프로덕션 사고 발생 시 `pip freeze` 비교로 환경 불일치를 근본 원인 분석의 우선 대상으로 삼아야 한다.
