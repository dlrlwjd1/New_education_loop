# Semantic Versioning for Models, Prompts, & Datasets

## 개요
- ML/LLM 시스템에서 **모델·프롬프트·데이터셋**에 시맨틱 버저닝(semantic versioning) 규율을 적용하는 방법과, "항상 트리플(triple)로 배포하라"는 핵심 운영 원칙을 다루는 11분 영상. "Model Versioning & Release Management" 레슨의 첫 번째 영상.

## 내용

### 왜 소스 코드만으로는 부족한가
- 전통적 소프트웨어에서 시맨틱 버저닝은 변경이 breaking인지, additive인지, 단순 수정(fix)인지 팀이 이해하도록 도움.
- ML/LLM 시스템에서는 동일한 명확성이 필요하지만, **코드뿐 아니라 모델, 프롬프트, 데이터셋**에도 적용해야 함 — 애플리케이션 코드가 그대로여도 새 모델, 새 프롬프트 버전, 새 데이터셋만으로 프로덕션 동작이 바뀔 수 있기 때문.

### 버저닝 전략: 3대 핵심 영역
- 버저닝은 소스 코드에서 멈출 수 없음 — **모델, 프롬프트, 데이터셋**이라는 3대 핵심 영역에 걸쳐 일관된 전략이 필요. 각각 독립적으로 진화하며 각기 다른 방식으로 리스크를 유발.
- 시맨틱 버저닝 적용 시 각 버전 자리의 의미:
  - **메이저(Major)**: breaking change.
  - **마이너(Minor)**: 하위 호환 개선(backward compatible improvement).
  - **패치(Patch)**: 전체 내용을 바꾸지 않는 작은 수정.

| 자산 | 메이저 | 마이너 | 패치 |
|---|---|---|---|
| 모델 | 새 아키텍처 | 새 학습 데이터 | 하이퍼파라미터 조정 |
| 프롬프트 | 작업(task) 재설계 | 문구 변경 | 공백/오타 수정 |
| 데이터셋 | 스키마 변경 | 새 레코드 추가 | 중복 제거(deduplication) |

### 핵심 운영 규칙: 항상 트리플로 배포하라
- **모든 서빙 릴리스는 모델 버전 + 프롬프트 버전 + 데이터셋 버전의 정확한 튜플(tuple)로 정의되어야 함** — 예: 모델 v2.1.0, 프롬프트 v1.3.2, 데이터셋 v5.0.0.
- 왜 중요한가: ML/LLM 시스템에서 예측 결과는 코드만으로 결정되지 않고, **런타임에 사용된 자산들의 정확한 조합**에 의해 결정됨.
- 모든 추론(inference)마다 이 튜플을 로깅하면 완전한 재현성(reproducibility)을 얻음 — 나중에 어떤 모델·프롬프트·데이터셋 버전이 특정 결과를 만들었는지 정확히 되짚어볼 수 있음. 이는 디버깅, 감사(audit), 사고 대응, 컴플라이언스에 필수적.

### MLflow 레지스트리를 통한 승격 워크플로 (5단계)
- 학습 실행(training run)이 익명의 아티팩트로 곧바로 프로덕션에 들어가서는 안 됨 — 레지스트리를 통한 통제된 생애주기를 거쳐야 함:
  1. 학습 실행(training run) 완료.
  2. 지표(metrics) 평가.
  3. 모델 아티팩트 등록.
  4. 올바른 시맨틱 버전 할당.
  5. 통제된 검증을 위해 스테이징으로 승격.
- MLflow 레지스트리를 이런 방식으로 사용하면 실험 실행과 배포된 버전 사이의 추적 가능성을 확보하고, 실험(experimentation)과 릴리스 관리(release management)를 분리 — 버저닝이 단순 라벨링이 아니라 릴리스 거버넌스 프로세스의 일부가 됨.

### 버저닝 4대 핵심 원칙
1. **일관성(Consistency)**: 동일한 버저닝 로직이 매번 적용되어야 팀이 버전 번호의 의미를 알 수 있음.
2. **추적 가능성(Traceability)**: 모든 모델·프롬프트·데이터셋 버전이 특정 변경 이력과 릴리스 결정으로 되짚어질 수 있어야 함.
3. **호환성(Compatibility)**: 모든 버전이 서로 안전하게 작동하는 것은 아니므로, 호환성 규칙이 명시적이어야 함.
4. **재현성(Reproducibility)**: 나중에 모델 출력이 문제가 되면, 그것을 만든 정확한 릴리스 상태를 재구성할 수 있어야 함.
- 요점: 버전에 예쁜 이름을 붙이는 것이 목적이 아니라, ML/LLM 릴리스를 **이해 가능하고(understandable), 검토 가능하고(reviewable), 재현 가능하게(repeatable)** 만드는 것이 목적.

### 구현 예시: `release.yaml` 릴리스 매니페스트
- 서빙 패키지를 명시적으로 정의: 모델 `fraud-detector:2.1.0`, 프롬프트 `reviewer-prompt:1.3.2`, 데이터셋 `claims-goal:5.0.0`.
- **호환성 규칙**도 포함: 최소 데이터셋 메이저 버전, 필요한 프롬프트 메이저 버전 — 지원되지 않는 조합이 프로덕션에 도달하는 것을 방지.
- **롤아웃 상태(rollout state)**도 기록(예: staging, approval pending) — 버저닝을 단순 네이밍 표준이 아닌 **운영 통제(operational control)**로 전환. 모든 서빙 단계가 한곳에 기술되어 감사·검토·롤백이 쉬워짐.

### 버전 자리를 언제 올릴지 결정하기
- **메이저 버전**: 호환성을 깨뜨리는 변경 — 새 스키마, 새 모델 패밀리, 다운스트림 소비자에 영향을 주는 프롬프트 계약(contract) 변경.
- **마이너 버전**: 기존 사용을 깨뜨리지 않으면서 능력을 추가 — 새 데이터 슬라이스, 더 안전한 지침(instruction), 개선된 재현율(recall).
- **패치 버전**: 수정만 — 오타 수정, 임계값 튜닝, 중복 제거, 메타데이터 정리.
- 이것이 중요한 이유: 버전 번호는 영향(impact)을 즉시 전달해야 함 — 이해관계자가 버전만 보고 이것이 위험한 변경인지, 개선인지, 단순한 안전 수정인지 알 수 있어야 함.

### 결론
- 모든 서빙 변경마다 **단일한 배포 가능한 릴리스 매니페스트**를 유지해야 함 — 이 매니페스트가 실제로 무엇이 배포되었는지에 대한 진실의 원천(source of truth)이 됨.
- 이점: 모든 예측이 추적 가능해지고, 모든 롤백이 정밀해지며, 모든 조사가 더 빨라짐 — 어떤 자산이 그 시점에 라이브였는지 추측할 필요가 없어짐.
- 최종 메시지: ML/LLM의 시맨틱 버저닝은 단순한 라벨링이 아니라, 모델·프롬프트·데이터셋을 함께 아우르는 신뢰할 수 있는 릴리스 기록(release record)을 만드는 것 — 진정한 힘은 매번 정확한 모델·프롬프트·데이터셋 튜플을 배포하고 로깅하는 데서 나옴.

## 예시
```yaml
# release.yaml (개념 구조)
model:
  name: fraud-detector
  version: 2.1.0
prompt:
  name: reviewer-prompt
  version: 1.3.2
dataset:
  name: claims-goal
  version: 5.0.0

compatibility:
  min_dataset_major_version: 5
  required_prompt_major_version: 1

rollout:
  stage: staging
  status: approval_pending
```

```text
[버전 자리별 예시 — 모델/프롬프트/데이터셋]
메이저(breaking) : 새 아키텍처 / 작업 재설계 / 스키마 변경
마이너(additive) : 새 학습 데이터 / 문구 변경 / 새 레코드 추가
패치(fix)        : 하이퍼파라미터 조정 / 오타 수정 / 중복 제거
```

```text
[MLflow 레지스트리 승격 5단계]
학습 실행 완료 → 지표 평가 → 모델 아티팩트 등록 → 시맨틱 버전 할당 → 스테이징 승격
```

## 요약
- ML/LLM 시스템의 시맨틱 버저닝은 모델·프롬프트·데이터셋 각각에 메이저/마이너/패치 의미를 부여하고, 모든 서빙 릴리스를 이 세 버전의 정확한 튜플로 정의해 매 추론마다 로깅함으로써 완전한 재현성을 확보하며, MLflow 레지스트리를 통한 통제된 승격 워크플로와 `release.yaml` 같은 릴리스 매니페스트로 이를 감사 가능하고 롤백 가능한 운영 통제로 전환하는 것이 핵심이다.
