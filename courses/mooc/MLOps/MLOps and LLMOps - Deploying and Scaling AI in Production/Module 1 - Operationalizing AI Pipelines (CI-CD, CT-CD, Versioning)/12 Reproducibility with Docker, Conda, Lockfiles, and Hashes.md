# Reproducibility with Docker, Conda, Lockfiles, and Hashes

## 개요
- ML/LLM 프로덕션 시스템에서 재현성(Reproducibility)을 달성하기 위한 4가지 핵심 도구·개념 — **Docker, Conda, 로그(lock) 파일, 해시 검증** — 을 실전 5계층 Docker 빌드 예시와 함께 다루는 10분 영상.

## 내용

### 재현성이란
- ML/LLM 프로덕션 시스템에서 재현성은 **동일한 코드, 동일한 의존성, 동일한 입력이 매번 동일한 출력을 만들어내는 것**을 의미.
- 이것이 안 되면 디버깅이 어려워지고, 배포가 위험해지며, 결과를 신뢰하기 어려워짐.

### 재현성을 위한 4가지 핵심 도구
1. **Docker**: 코드와 런타임 의존성을 일관된 컨테이너로 이미지화·패키징 — 특히 데이터 과학 워크플로에서 환경과 패키지 의존성을 관리하는 데 도움.
2. **Conda**: 환경 관리 도구.
3. **로그(lock) 파일**: 정확한 의존성 버전을 기록.
4. **해시 검증(Hash Verification)**: 의도한 정확한 패키지 아티팩트를 설치하고 있는지 보장 — 비슷하지만 다른 버전이 아님을 확인.
- 핵심 아이디어: **재현성은 자동으로 생기지 않음** — 워크플로에 설계되어 들어가야 함. 유동적(floating) 버전, 고정되지 않은 이미지, 고정되지 않은 의존성을 사용하면 빌드가 시간이 지나며 조용히 변할 수 있음.

### Docker 모범 사례
1. **베이스 이미지를 SHA 다이제스트로 고정**: `latest` 같은 유동적 태그 대신 완전히 고정된 이미지 참조를 사용 — 매 빌드가 동일한 바이너리 베이스에서 시작함을 보장.
2. **캐시 효율을 위한 레이어 순서**: 빌드를 시스템 의존성 → Python 의존성 → 로그 파일 → 애플리케이션 코드 순서로 구성 — 캐시 재사용을 높이고 불필요한 재빌드를 줄임.
3. **로그 파일을 소스 코드보다 먼저 복사**: 의존성 설치는 의존성이 실제로 바뀔 때만 반복되어야 함 — 소스 코드는 바뀌어도 로그 파일이 그대로면 Docker가 의존성 레이어를 재사용 가능.
4. **해시 검증**: `pip install --require-hashes -r requirements.log` — 패키지 설치가 재현 가능하면서도 공급망(supply chain) 관점에서 더 안전하도록 보장.
- 핵심 메시지: Docker만으로는 재현성이 보장되지 않으며, 고정된 이미지·올바른 레이어 순서·로그된 의존성과 함께 신중하게 사용되어야 함.

### 5계층 Docker 빌드 (실전 재현성 예시)
- 문제 상황: Dockerfile이 동일해 보여도 NumPy 버전이 로컬에서는 1.3, 프로덕션에서는 1.24 — 의존성이 제대로 고정되지 않아 빌드가 진정으로 결정론적이지 않았기 때문.
- **5계층 구조**:
  1. **SHA로 고정된 이미지 베이스** — 빌드의 시작점이 매번 동일함을 보장.
  2. **시스템 의존성**(libgomp, curl 등) — 레이어가 바뀌지 않는 한 캐시됨.
  3. **`requirements.log` 파일 복사** — 의존성 변경을 애플리케이션 코드 변경과 분리하는 중요한 최적화.
  4. **`pip install --require-hashes`** — 정확한 의존성을 설치하고 해시로 검증.
  5. **소스 코드와 애플리케이션 시작 설정** 포함.
- 이 구조가 주는 2가지 큰 이점: **결정론적 의존성 설치**와 **효율적인 Docker 캐싱**.
- 더 깊은 교훈: 재현성과 성능은 서로를 지원할 수 있음 — 잘 구조화된 Dockerfile은 빌드를 더 빠르고 더 신뢰할 수 있게 만듦. 계층화된 Docker 빌드는 환경의 안정적인 부분과 변화하는 부분을 분리해 재현성과 빌드 효율성을 동시에 개선함.

### Conda 환경 내보내기
- 명령: `conda env export --from-history > environment.yml`.
- 이 명령은 사용자가 명시적으로 설치한 패키지만 포함하는 환경 파일을 생성 — 모든 전이(transitive) 의존성이 아니라, 더 이식성 있고(portable) 읽기 쉬운 파일을 만듦.
- **중요한 한계**: from-history로 내보내면 모든 전이 의존성을 포착하지 못함 — **이식성(portability)**과 **엄격한 재현성(strict reproducibility)**의 차이를 보여줌. 정확히 반복 가능한 빌드가 필요하다면 로그 파일이나 완전히 고정된 의존성 스냅샷이 더 나음.

### 재현 가능한 빌드의 4대 핵심 원칙
1. **모든 것을 고정하라**: 프로덕션 시스템에서 `latest`나 유동적 버전에 절대 의존하지 말 것 — 중요한 모든 의존성은 정확한 버전으로 기록되어야 함.
2. **해시 검증**: 재현성뿐 아니라 공급망 안전성도 보호 — 버전 번호만으로는 정확한 패키지 파일을 검증하기에 충분하지 않음.
3. **레이어 캐싱**: Dockerfile의 명령 순서가 중요함 — 좋은 레이어 순서는 캐시 히트를 극대화하고 의존성 재설치를 피함.
4. **재현 가능한 빌드**: 동일한 입력은 매번 동일한 출력을 만들어야 함 — 이것이 핵심 목표.
- 도구는 팀마다 다를 수 있지만 원칙은 동일함 — **재현성은 변화를 통제하는 것에서 나온다**.

### 재현 가능한 빌드 예시 (Dockerfile)
- Python 3.11 slim에서 시작 → 로그 파일 복사 → 의존성 설치 → 소스 코드 복사 → 작업 디렉토리 설정 → 시작 명령 정의.
- **4가지 실전 시사점**:
  1. 고정된 해시를 사용해 재빌드 중 조용한 의존성 드리프트를 막을 것.
  2. 사전 버전이 지정된 입력에 대해서만 빌드를 신뢰할 것 — 베이스 이미지, 의존성 정의, 애플리케이션 파일 모두 통제되어야 함.
  3. `latest` 같은 유동적 텍스트를 피할 것 — Docker 텍스트 자체는 바뀌지 않았는데 빌드가 바뀌게 되어 재현성을 깨뜨림.
  4. 이를 올바르게 수행한 결과, CI와 프로덕션 전반에서 빌드가 안정적으로 유지됨.
- 결론 문장: **CI(지속적 통합)는 재현성을 지원하지만, 진정한 재현성은 고정된 의존성과 불변(immutable) 이미지를 필요로 한다.**

## 예시
```dockerfile
# Dockerfile (5계층 재현 가능한 빌드 예시)
FROM python@sha256:abcd1234...   # 1. SHA로 고정된 베이스 이미지

RUN apt-get update && apt-get install -y libgomp1 curl  # 2. 시스템 의존성(캐시됨)

COPY requirements.log .          # 3. 로그 파일 먼저 복사
RUN pip install --require-hashes -r requirements.log  # 4. 해시 검증 설치

COPY . /app                      # 5. 소스 코드 + 애플리케이션 설정
WORKDIR /app
CMD ["python", "serve.py"]
```

```bash
# Conda 환경 내보내기 — 이식성 vs 엄격한 재현성
conda env export --from-history > environment.yml
# 장점: 사용자가 명시적으로 설치한 패키지만 포함, 이식성 높음
# 한계: 전이 의존성 미포함 → 정확한 재현이 필요하면 로그 파일/전체 고정 스냅샷 사용
```

## 요약
- ML/LLM 시스템의 재현성은 Docker(SHA 고정 이미지 + 레이어 순서 + 로그 파일 우선 복사 + 해시 검증 설치), Conda(이식성 있는 history 기반 내보내기 vs 엄격한 재현을 위한 전체 고정), 로그 파일, 해시 검증을 결합해 달성되며, 핵심은 도구가 아니라 "모든 것을 고정하고 해시로 검증하며 레이어를 신중히 구성해 동일 입력이 항상 동일 출력을 만들도록 변화를 통제하는" 엔지니어링 원칙이고, CI는 이를 지원할 뿐 진정한 재현성은 불변 이미지와 고정된 의존성에서 나온다.
