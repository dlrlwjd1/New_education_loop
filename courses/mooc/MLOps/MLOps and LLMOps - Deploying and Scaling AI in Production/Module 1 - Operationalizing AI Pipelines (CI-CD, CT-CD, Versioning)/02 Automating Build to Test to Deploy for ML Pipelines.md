# Automating Build → Test → Deploy for ML Pipelines

## 개요
- ML 파이프라인에 CI/CD 규율을 적용하는 방법과, GitHub Actions로 구현한 매일 재학습(daily retrain) 파이프라인 예시(이커머스 이탈(churn) 모델)를 다루는 9분 영상.

## 내용

### 빌드-테스트-배포, ML에서는 무엇이 다른가
- 전통적 소프트웨어에서 빌드·테스트·배포는 익숙한 단계 — ML에서도 동일한 단계가 적용되지만, 파이프라인이 코드 이상의 것을 다뤄야 함: **학습 데이터, 모델 아티팩트, 검증 로직, 재학습 워크플로**.
- 목표는 단순히 "속도를 위한 자동화"가 아니라 **신뢰성을 갖춘 자동화** — 모든 모델 버전이 통제된 방식으로 빌드·테스트·검증·배포되도록 하는 것.

### ML 파이프라인 자동화 4대 원칙
1. **트리거 기반(Trigger-driven)**: 코드 변경, 스케줄, 또는 배포 전에 실행될 수 있어야 함.
2. **중요 단계에 게이트 사용**: 모든 실행을 끝까지 진행시키지 말고, 다음 단계로 넘어가기 전에 데이터와 모델 품질을 검증해야 함.
3. **빠른 실패(Fail Fast)**: 데이터가 손상되었거나 불완전하면 학습에 컴퓨팅을 낭비하지 말고 파이프라인이 즉시 중단되어야 함.
4. **출력을 승격 아티팩트(promotional artifact)로 취급**: 학습된 모델은 필요한 모든 체크를 통과했을 때만 다음 단계로 이동 — 소프트웨어 딜리버리의 프로덕션 준비 빌드와 마찬가지.

### 일상 시나리오: 매일 재학습되는 이탈(Churn) 모델
- 이탈 예측 모델이 신선한 트랜잭션 데이터로 **매일 재학습**되어야 하는 상황 — 사용자 행동이 자주 바뀌는 ML 시스템에서 흔한 사례.
- 충분히 자주 재학습하지 않으면 모델이 낡아져(stale) 예측 품질이 떨어짐.
- 원칙: **설계, 반복(design, repeat)** — 파이프라인은 매일 실행되어 최신 데이터를 가져오고, 모델을 재학습하고, 결과를 평가한 후, 새 모델이 충분히 좋은지 판단하도록 설계됨.
- 이 예시는 ML 파이프라인이 단순한 코드 배포가 아니라 **지속적 학습 워크플로(continuous learning workflow)**임을 보여줌.

### 파이프라인 프로세스 5단계 (이탈 모델 예시)
1. **Cron 트리거**: 매일 오전 3시에 스케줄되어 최근 30일 데이터를 가져옴.
2. **데이터 게이트(Data Gate)**: 데이터 스키마 체크 수행 — 행 개수가 **1,000행 이상**이어야 하는 조건 확인.
3. **학습 및 평가**: 정확도(accuracy)가 `baseline × 0.99` 이상이면 통과.
4. **MLflow 자동 등록**: run ID, 최신 데이터셋 해시(hash), 타임스탬프와 함께 등록.
5. **Slack 웹훅**: 새 모델 버전과 정확도 차이(accuracy difference)를 알림.
- 이후 매일 반복(repeat).

### 신뢰할 수 있는 자동화 파이프라인의 모범 사례
- 파이프라인 단계를 명확히 분리해 어디서 실패가 발생했는지 쉽게 파악 가능하도록 함.
- 모든 단계가 유용한 로그와 지표(metrics)를 생성하도록 함 — 디버깅과 감사(audit)에 가시성이 필수.
- **재현성(Reproducibility)**: 동일한 입력을 반복 사용하면 파이프라인이 동일하게 동작해야 함 — 재실행(rerun)과 실패 복구(failure recovery)에 특히 중요.
- 검증(validation)과 평가(evaluation) 게이트를 통해서만 프로모션이 이루어져야 함 — 성능이 떨어지는 모델이 실수로 안정적인 모델을 대체하는 일이 없도록 보장.

### GitHub Actions로 구현한 스케줄 재학습 파이프라인
- 재학습은 수동일 필요가 없음 — 선택한 시간에 자동으로 실행되는 스케줄 워크플로를 정의할 수 있음.
- 워크플로 내 각 단계가 명시적으로 정의됨: 신선한 데이터 가져오기 → 데이터 검증 → 모델 학습 → 성능 평가 → 결과에 따라 등록 또는 알림.
- GitHub Actions는 스케줄링, 순서 지정(sequencing), 로깅, 실패 처리를 한곳에서 제공해 반복 가능한 ML 재학습 프로세스를 운영하기 쉽게 함.

### 전체 파이프라인 예시: 이커머스 이탈 모델 (GitHub Actions 워크플로)
1. **Cron 트리거**: 매일 오전 3시 실행.
2. **최근 30일 트랜잭션 데이터 가져오기**: 학습 워크플로의 입력을 명시적으로 정의.
3. **데이터 검증(차단 게이트)**: 검증 실패 시 워크플로가 즉시 중단됨.
4. **모델 학습**: **XGBoost**로 이탈 모델 학습.
5. **평가 게이트**: 기준 임계값 — **AUC ≥ 0.82** — 이를 충족해야만 모델이 승격됨.
6. **등록 및 알림**: 모든 것이 통과하면 모델이 MLflow에 등록되고 Slack 알림 전송 — 결과를 추적 가능하고 팀에게 가시적으로 만듦.

### 시나리오별 결과
1. **정상 경로(Happy Path)**: 오전 3시에 파이프라인이 12,400행을 가져옴 → 스키마 통과 → 모델이 AUC 0.84 달성(기준 0.82 상회) → 새 버전이 MLflow에 등록되고 팀에 알림.
2. **검증 게이트 차단 시나리오**: ETL 오류로 필요한 최소치 대신 단 600행만 가져옴 → 파이프라인이 이를 조기에 감지해 학습을 건너뛰고 이전 안정 모델을 그대로 유지 — **빠른 실패 설계**의 목적을 정확히 달성.
3. **평가 게이트 차단 시나리오**: 파이프라인은 실행되지만 모델이 AUC 0.79(기준 미달)만 달성 → 모델이 등록되지 않고 알림이 발생 — 학습 작업이 기술적으로 성공했다는 이유만으로 약한 모델이 승격되는 것을 방지.
4. **멱등성(Idempotency)**: 동일한 30일 입력은 동일한 해시를 가진 동일한 모델을 생성 — 실패 후 재실행이 안전함을 의미하며, 프로덕션급 자동화에서 재시도·복구 시 불확실성을 줄이는 데 매우 중요.

### 결론
- ML 파이프라인 자동화는 단순히 더 빠르게 재학습하는 것이 아니라, **신뢰할 수 있는 모델만 빌드→테스트→배포로 이동하도록 올바른 게이트를 추가하는 것**.

## 예시
```yaml
# GitHub Actions 워크플로 (개념 구조) — 이커머스 이탈 모델 매일 재학습
name: daily-churn-retrain
on:
  schedule:
    - cron: "0 3 * * *"  # 매일 오전 3시

jobs:
  retrain:
    steps:
      - name: Fetch last 30 days transactions
        run: python fetch_data.py --days 30

      - name: Data validation gate
        run: python validate_schema.py --min-rows 1000
        # 실패 시 워크플로 즉시 중단

      - name: Train model (XGBoost)
        run: python train_churn_model.py

      - name: Evaluation gate
        run: python evaluate.py --metric auc --threshold 0.82
        # AUC >= 0.82 미만이면 등록 단계로 진행하지 않음

      - name: Register to MLflow
        run: python register_model.py --run-id $RUN_ID --data-hash $DATA_HASH

      - name: Notify Slack
        run: python notify_slack.py --model-version $VERSION --auc-diff $DIFF
```

| 시나리오 | 결과 |
|---|---|
| 정상 경로 | 12,400행, AUC 0.84 → 등록 + Slack 알림 |
| 데이터 게이트 차단 | 600행(부족) → 학습 스킵, 이전 모델 유지 |
| 평가 게이트 차단 | AUC 0.79(기준 미달) → 등록 거부, 알림만 발생 |

## 요약
- ML 파이프라인 자동화는 트리거 기반 실행, 중요 단계의 게이트, 빠른 실패, 출력의 승격 아티팩트화라는 4대 원칙을 바탕으로 하며, GitHub Actions로 구현한 이커머스 이탈 모델의 매일 재학습 파이프라인(Cron → 데이터 검증 게이트 → XGBoost 학습 → AUC 평가 게이트 → MLflow 등록 → Slack 알림) 예시는 정상 경로뿐 아니라 데이터 부족이나 성능 미달 같은 실패 시나리오를 안전하게 차단하고 멱등성을 보장하는 것이 핵심임을 보여준다.
