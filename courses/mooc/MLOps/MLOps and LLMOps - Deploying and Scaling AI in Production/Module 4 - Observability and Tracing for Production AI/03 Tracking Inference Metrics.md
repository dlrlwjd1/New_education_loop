# Tracking Inference Metrics

## 개요
- 프로덕션 배포 이후 실시간 성능 모니터링이 왜 필수적인지, 추적해야 할 핵심 추론 지표(TTFT/지연시간, 비용, 오류율, 캐시 히트율)와 이를 구체적인 알림·대응으로 연결하는 방법을 다루는 6분 영상. "Experiment Tracking & Telemetry" 레슨의 마지막 영상.

## 내용

### 배포는 끝이 아니다
- AI 시스템이 배포되면 작업이 끝난 것이 아님 — 팀은 사용자가 불만을 제기하기 전에 지연시간 급증, 비용 상승, 실패를 탐지할 수 있도록 프로덕션에서 시스템이 어떻게 동작하는지 계속 지켜봐야 함.

### 추적해야 할 핵심 추론 지표
- 실제 시스템에서는 작은 핵심성과지표(KPI) 세트를 추적하고 **5분 이내에 저하를 탐지**할 수 있도록 알림을 설정해야 함.
- **W&B에 모든 추론을 로깅**: TTFT(밀리초), 비용(달러) 같은 필드 포함.
- **커스텀 대시보드 뷰**: 50분 롤링 P95 지연시간, 1시간 비용 누적.
- **알림 규칙 예시**: P95 TTFT가 연속된 로그에서 1,000ms를 초과하면 Slack 알림 전송.
- **주간 요약 뷰**: 질의당 비용 트렌드, 캐시 히트율, 오류율 포함.
- 핵심 요점: 모니터링은 사용자 경험, 비용, 신뢰성을 명확히 드러내 빠른 의사결정을 지원하는 소수의 신호에 집중해야 함.

### 핵심 원칙 4가지
1. **TTFT와 전체 지연시간 추적(특히 P95, P99)**: 사용자 대면 지연이 불만으로 나타나기 전에 이 임계값들이 잡아냄.
2. **질의당 비용 모니터링**: 일일 예산 알림과 함께 토큰 비용을 추적하면 지출 폭주를 방지하는 데 도움.
3. **오류율 모니터링**: HTTP 오류와 통과 실패(pass failure)가 **0.5%를 초과**하면 즉각적인 조사를 트리거해야 함.
4. **캐시 히트율**: 낮은 캐시 히트율(예: **20% 미만**)은 더 나은 캐싱을 통해 비용과 지연시간을 모두 개선할 기회를 나타낼 수 있음.
- 핵심 요점: 최고의 모니터링 지표는 사용자 경험, 신뢰성, 비용이 무너지기 시작하는 지점을 보여주는 지표.

### 코드 예시: `MetricMonitor.py`
- 최근 5분 창(window)의 지표를 읽고 3가지 문제를 확인: **오류 급증, 지연시간 급증, 높은 폴백(fallback) 사용률**.
- 로직: 오류율이 **0.03 초과** → 오류 급증 알림 전송. P95 지연시간이 **100(ms 또는 관련 단위) 초과** → 지연시간 급증 알림 전송. 폴백률이 **0.10 초과** → 온콜(on-call) 팀 호출(page).
- 핵심 요점: 프로덕션 모니터링은 단순히 숫자를 수집하는 것이 아니라, 숫자를 **구체적인 운영 대응**에 연결해야 함 — 서로 다른 신호는 서로 다른 조치를 필요로 함(일부는 알림만으로 충분하고, 일부는 즉시 온콜 엔지니어를 호출할 정도로 심각함).

### 실전 원칙 3가지
1. **오류율, 지연시간, 폴백 사용률을 지속적으로 관찰하라**: 운영 상태의 강력한 지표.
2. **짧은 롤링 윈도우에서 알림을 설정하라**: 팀이 사용자 불만 전에 사고를 잡아내는 데 도움.
3. **서로 다른 문제 유형을 분리하라**: 지연시간 급증, 정확성 문제, 폴백 증가는 모두 저하처럼 보일 수 있지만 대체로 다른 수정이 필요함.
- 결과: 운영이 모호한 노이즈 대신 명확한 트리거를 얻게 됨.
- 최종 메시지: 먼저 작은 세트의 실행 가능한(action-driven) 지표를 선택하고, 실제로 결정을 바꿀 때만 더 추가할 것.

### 결론
- 실시간 추론 모니터링은 **집중적이고, 실행 가능하고, 직접 알림과 대응에 연결**될 때 가장 잘 작동함.
- 좋은 지표는 단순히 시스템을 묘사하지 않고, 프로덕션 행동이 바뀔 때 팀이 빠르게 행동하도록 돕는 것.

## 예시
```python
# MetricMonitor.py (개념 구조)
def check_window(window_metrics):
    if window_metrics["error_rate"] > 0.03:
        alert("error_spike")
    if window_metrics["p95_latency"] > 100:
        alert("latency_spike")
    if window_metrics["fallback_rate"] > 0.10:
        page_oncall("high_fallback_usage")
```

```text
[핵심 추론 지표와 임계값]
TTFT/전체 지연시간(P95, P99) — 사용자 대면 지연 조기 탐지
질의당 비용             — 일일 예산 알림으로 지출 폭주 방지
오류율                  — 0.5% 초과 시 즉시 조사
캐시 히트율             — 20% 미만이면 캐싱 개선 기회
```

| 신호 | 임계값 | 대응 |
|---|---|---|
| 오류율 | > 0.03 | 알림(오류 급증) |
| P95 지연시간 | > 100 | 알림(지연시간 급증) |
| 폴백률 | > 0.10 | 온콜 엔지니어 호출 |

## 요약
- 프로덕션 AI는 배포 후에도 TTFT·전체 지연시간(P95/P99), 질의당 비용, 오류율(0.5% 임계값), 캐시 히트율(20% 임계값) 같은 소수의 핵심 지표를 짧은 롤링 윈도우에서 지속적으로 모니터링해야 하며, 각 신호를 알림이나 온콜 호출 같은 구체적인 운영 대응에 직접 연결하고 서로 다른 문제 유형(지연시간, 오류, 폴백)을 분리해 처리함으로써 사용자 불만이 발생하기 전에 5분 이내로 저하를 탐지하고 신속하게 대응할 수 있어야 한다.
