# How Chains and Agents Break

## 개요
- 프로덕션 AI에서 체인(chain)과 에이전트(agent)가 실패하는 6가지 방식, "보이지 않는 중간(invisible middle)"이라는 디버깅 문제, 그리고 검증 게이트를 포함한 가드레일 패턴을 지원 봇 사례로 설명하는 7분 영상. "Tracing and Debugging with Arize Phoenix" 레슨의 첫 번째 영상.

## 내용

### 나쁜 답변 = 언어모델 문제라는 오해
- 나쁜 답변을 보면 언어모델 자체가 유일한 문제라고 가정하기 쉬움 — 하지만 실제 시스템에서는 실패가 훨씬 일찍 시작되는 경우가 많음.
- 체인이 망가지는 이유는 잘못된 문서가 검색되었기 때문일 수 있고, 에이전트가 실패하는 이유는 도구 호출이 오류를 반환했기 때문일 수 있음.
- 때로는 이전 단계가 이미 잘못되었는데도 시스템이 계속 진행됨.
- 핵심 아이디어: **프로덕션 실패는 대체로 최종 답변의 실패가 아니라 단계별 실패(step failure)**임.

### 체인·에이전트의 6가지 실패 모드
1. **검색 실패(Retrieval Failure)**: 시스템이 잘못된 문서를 가져오거나 유용한 문서를 전혀 찾지 못할 때 — 이후 단계가 약하거나 놓친 컨텍스트를 받게 됨.
2. **컨텍스트 실패(Context Failure)**: 검색이 무언가를 반환해도, 모델에 전달되는 컨텍스트가 불완전하거나, 관련성이 없거나, 제대로 조합되지 않았을 수 있음.
3. **생성 실패(Generation Failure)**: 도구가 검색된 정보에 그라운딩되지 않은 답변을 생성할 때 — 대체로 환각(hallucination)으로 나타남.
4. **도구 실패(Tool Failure)**: 에이전트 워크플로에서 도구가 API 문제, 타임아웃, 잘못된 입력, 예상치 못한 응답으로 인해 실패할 수 있음.
5. **추론/의사결정 실패(Reasoning/Decision Failure)**: 에이전트가 잘못된 도구를 선택하거나, 동일한 행동을 불필요하게 반복하거나, 잘못된 단계 순서를 따를 때.
6. **연쇄 실패(Cascade Failure)**: 이전 단계의 작은 문제가 확산되어 체인의 이후 단계에서 더 큰 실패를 만들 때.
- 핵심 요점: 체인과 에이전트는 여러 방식으로 실패할 수 있으며, 각 실패 유형은 개별적으로 확인되어야 함.

### 보이지 않는 중간(The Invisible Middle)
- 많은 시스템에서 우리는 사용자 입력과 최종 출력만 봄 — 하지만 가장 중요한 일은 **중간**(검색, 컨텍스트 구성, 도구 사용, 생성)에서 일어남.
- 이 중간 단계들을 볼 수 없으면 실패를 진단하기가 매우 어려워짐 — 답이 틀렸다는 것은 알아도, 검색이 실패했는지, 잘못된 도구가 사용되었는지, 아니면 생성이 그 컨텍스트를 무시했는지 알 수 없음.
- 트레이싱 없이는 시스템이 실제보다 단순해 보임 — **Phoenix** 같은 도구가 이 숨겨진 중간을 드러내고 검색부터 생성까지 모든 스팬(span)을 가시화하는 데 도움.

### 실전 사례: 지원 봇의 실패 추적
- 지원 봇이 유능하게 답하지만 부정확하게 답하는 상황 — 표면적으로는 환각 문제처럼 보임.
- 하지만 단계를 추적해보면: **검색 점수(retrieval score)가 0.43**으로 권장 임계값보다 낮음 → 잘못된 청크가 검색됨 → 이 잘못된 청크가 컨텍스트로 전달됨 → 언어모델이 관련 없는 정보를 받아 잘못된 답변을 생성.
- 해결책: 유사도 임계값을 높이고 랭커(ranker) 단계 추가.
- 핵심 메시지: **환각은 대체로 마지막에 보이는 증상이지, 첫 번째 원인이 아니다.**

### 핵심 원칙 4가지
1. **모든 것을 추적하라(Trace Everything)**: 스팬 수준의 가시성 없이는 체인 실패가 출력 단계까지 보이지 않은 채로 남음.
2. **검색 점수(retrieval score)**: 유사도가 낮으면(대략 0.6 미만) 잘못된 청크가 선택되었을 수 있고 환각 리스크가 높아짐.
3. **도구 오류를 명확히 로깅하라**: 도구 호출 내부의 API 실패는 에이전트 루프(loop)를 유발할 수 있으므로 트레이스는 도구 오류를 명시해야 함.
4. **연쇄 탐지(Cascade Detection)를 주시하라**: 한 단계의 문제가 다음 단계로 복합될 수 있고, 스팬 트레이스가 이 오류 전파를 드러내는 데 도움.
- 핵심 요점: 프로덕션 신뢰성은 각 단계에서의 가시성, 검증, 명확한 실패 신호에 달려 있음.

### 가드레일 패턴 (코드)
- **1단계 검색**: 검색이 문서를 전혀 반환하지 않으면 시스템이 "no_context" 같은 명확한 레이블로 조기에 실패해야 함.
- **2단계 생성**: 생성은 자동으로 신뢰되어서는 안 됨 — 답변을 생성한 후, 시스템은 그 답변이 검색된 문서에 그라운딩되어 있는지 확인해야 함.
- 답변이 그라운딩되지 않았다면, 그것을 그대로 반환하는 대신 시스템은 더 나은 컨텍스트로 재시도하거나 다른 더 안전한 복구 단계를 밟아야 함.
- 핵심 요점: 프로덕션 체인은 맹목적으로 계속 진행해서는 안 되고, 중요한 체크포인트에서 멈추고 검증해야 함.

### 광범위한 의사결정 교훈
1. **작게 실패하라(Fail Small)**: 정보를 다음으로 전달하기 전에 각 단계를 검증할 것.
2. **실패를 명확히 명명하라**.
3. **실패한 단계만 재시도하라**.
- 결과: 체인이 불투명하게 붕괴되는 대신 **우아하게 저하(degrade gracefully)**됨.

## 예시
```python
# 가드레일 패턴 (개념 구조)
def run_chain(query):
    docs = retrieve(query)
    if not docs:
        return {"status": "no_context", "answer": None}  # 조기 실패, 명확한 레이블

    answer = generate(query, docs)

    if not is_grounded(answer, docs):  # 그라운딩 검증
        return retry_with_better_context(query, docs)  # 재시도 또는 안전한 복구

    return {"status": "ok", "answer": answer}
```

| 실패 모드 | 원인 |
|---|---|
| 검색 실패 | 잘못된 문서 검색 또는 결과 없음 |
| 컨텍스트 실패 | 불완전/무관/잘못 조합된 컨텍스트 |
| 생성 실패 | 그라운딩되지 않은 답변(환각) |
| 도구 실패 | API 오류, 타임아웃, 잘못된 입력 |
| 추론/의사결정 실패 | 잘못된 도구 선택, 반복, 순서 오류 |
| 연쇄 실패 | 이전 단계 문제가 확산·복합 |

## 요약
- 프로덕션 체인·에이전트의 실패는 검색·컨텍스트·생성·도구·추론·연쇄라는 6가지 유형으로 나뉘며, 사용자 입력과 최종 출력만 보이는 "보이지 않는 중간" 때문에 진단이 어렵기 때문에 Phoenix 같은 도구로 모든 스팬을 추적해야 하고, 지원 봇 사례처럼 표면적인 환각 증상의 실제 원인은 낮은 검색 점수처럼 훨씬 이전 단계에 있는 경우가 많으므로, 각 단계를 검증하고 그라운딩되지 않은 답변은 재시도하는 가드레일을 두어 체인이 맹목적으로 계속되지 않고 우아하게 저하되도록 설계해야 한다.
