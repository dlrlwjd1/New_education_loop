# Logging Prompts, Responses, and Metadata

## 개요
- 프로덕션 AI 시스템에서 디버깅·성능 측정·모델 행동 추적에 필요한 만큼 로깅하면서도 **PII(개인식별정보)를 노출하지 않는 프라이버시 안전 텔레메트리(privacy-safe telemetry)**를 다루는 7분 영상. "Experiment Tracking & Telemetry (W&B/MLflow)" 레슨의 첫 번째 영상.

## 내용

### 관측 가능성보다 프라이버시가 먼저
- 팀은 이슈를 디버깅하고, 성능을 측정하고, 모델 행동을 추적할 만큼 충분히 로깅해야 하지만, 개인식별정보(PII)를 노출하지 않으면서 그렇게 해야 함.
- 핵심 원칙: **관측 가능성은 중요하지만 프라이버시가 우선되어야 함.**
- 프로덕션 팀은 모델 버전, 프롬프트 버전, 토큰 사용량, 지연시간 같은 유용한 추론 메타데이터는 로깅하되, 원본 사용자 텍스트나 직접적인 식별자를 저장하는 위험한 관행은 피해야 함.

### 프로덕션 추론을 위한 핵심 로깅 규칙
- **핵심 원칙**: 디버깅에 필요한 모든 것을 로깅하되, 불필요하게 민감한 사용자 정보를 저장하지 말 것.
- **사용자 ID를 해시하라**: SHA-256 같은 방식을 사용해 시스템이 실제 신원을 노출하지 않으면서도 여러 요청에 걸쳐 동일 사용자에게 이벤트를 귀속(attribute)시킬 수 있게 함 — 실제 신원을 드러내지 않으면서 추적성을 확보.
- **절대 로깅하지 말아야 할 것**: 원본 질의 텍스트, 사용자명, 이메일, 세션 데이터 — 원본 프롬프트와 응답은 원래 의도하지 않았더라도 쉽게 개인 정보를 포함할 수 있기 때문에 중요.
- 대신 시스템은 질의 길이, 카테고리, `hash_pii_signal` 같은 불리언 값처럼 더 안전한 메타데이터를 로깅해야 함.
- **30일 롤링 보존(암호화된 S3)**: 디버깅 필요성과 프라이버시 준수·데이터 최소화 사이의 균형을 맞춤.
- 핵심 요점: 좋은 텔레메트리는 ID, 버전, 지표를 포착하되 원본 비밀 정보나 직접적인 식별 필드는 포착하지 않음.

### 프로덕션 추론 로그 필드 예시
- `request_id`, `user_id_hash`, `model_version`, `prompt_version`, `tokens_in`, `tokens_out`, `cost`, `format/error_type`, `total_ms`, `TTFT(마이크로초)`.

### 안전한 접근의 핵심 원칙 4가지
1. **항상 PII 해시**: SHA-256으로 사용자 ID를 해시해 실제 신원을 노출하지 않으면서 귀속·분석 가능하도록 함.
2. **원본 텍스트를 절대 로깅하지 말 것**: 질의 텍스트는 PII 리스크로 취급 — 길이나 카테고리 같은 더 안전한 메타데이터를 로깅할 것.
3. **모든 것을 버전 관리하라**: 모델 버전과 프롬프트 버전은 계보(lineage)에 필수 — 문제가 발생하면 팀은 정확히 어떤 모델과 프롬프트가 그 행동을 만들었는지 알아야 함.
4. **30일 보존**: 롤링 암호화 윈도우가 트러블슈팅에 충분한 이력을 제공하면서 불필요한 장기 저장을 피함.
- 핵심 메시지: 프로덕션 AI 시스템의 관측 가능성은 **유용함과 안전함을 동시에** 갖추도록 설계되어야 함.

### 텔레메트리 예시: `telemetry.json`
- 필드: `prompt_id`, `model`, `input_tokens`, `latency_ms`, `pii_detected`, `trace_id`.
- `prompt_id`와 `model`은 계보에 도움, `input_tokens`와 `latency`는 성능·비용 분석에 도움, `pii_detected`는 민감 정보가 이미 안전하게 처리되었음을 나타내고, `trace_id`는 하나의 추론 이벤트를 이후의 다운스트림 분석에 연결하는 데 도움.
- 핵심 교훈: 텔레메트리는 "어떤 프롬프트 버전이 이 결과를 만들었는가", "어떤 모델이 요청을 처리했는가", "얼마나 걸렸는가", "토큰이 몇 개 사용되었는가", "이 이벤트를 시스템 전반에서 추적할 수 있는가" 같은 질문에 답할 수 있어야 함 — 이 정도면 위험한 원본 콘텐츠를 기본적으로 저장하지 않고도 강력한 관측 가능성을 확보하기에 충분함.

### 실전 원칙 3가지
1. **포착(Capture)**: 모든 호출에 대해 프롬프트 ID, 모델, 지연시간, 토큰 사용량 같은 유용한 운영 필드를 포착 — 좋은 관측 가능성의 구성 요소.
2. **보호(Protect)**: 텔레메트리를 전송하기 전에 민감한 필드를 보호 — 개인 사용자 정보를 노출할 수 있는 모든 것을 해시하거나 마스킹(redact).
3. **연결(Link)**: 텔레메트리를 `trace_id`로 연결해 오프라인 분석을 위해 다운스트림 결과와 결합할 수 있도록 함 — 고립된 로그는 시스템 전반에서 연결되는 로그보다 유용성이 떨어지기 때문에 중요.
- 결과: 관측 가능성이 기본적으로 원본 비밀 정보를 저장하지 않고도 유용하게 유지됨.

### 결론
- 최종 원칙: **ID와 지표를 기본으로 사용하고, 정책이 명시적으로 허용할 때만 원본 프롬프트와 응답을 사용하라.**
- 프로덕션 텔레메트리는 프라이버시 리스크를 최소화하면서 디버깅, 추적, 모니터링을 지원하도록 설계되어야 함 — 프롬프트 텔레메트리는 단순한 세부사항이 아니라 **의도적인 프라이버시 인식(privacy-aware by decision)** 설계.

```json
// telemetry.json (개념 구조)

  "request_id": "req_8a3f...",
  "user_id_hash": "sha256:9f2e4c...",
  "model_version": "gpt-4-v2.1",
  "prompt_version": "1.4.0",
  "tokens_in": 320,

  "cost_usd": 0.0041,
  "format_or_error_type": null,
  "total_ms": 1420,
  "ttft_us": 280000,
  "pii_detected": false,
  "trace_id": "trace_7c21..."

```

```text
[프라이버시 안전 텔레메트리 원칙]
로깅해야 할 것: ID(해시), 버전, 토큰 수, 지연시간, trace_id
로깅하지 말아야 할 것: 원본 질의 텍스트, 사용자명, 이메일, 세션 데이터

보존: 30일 롤링, 암호화된 S3
```

## 요약
- 프로덕션 AI의 텔레메트리는 사용자 ID를 SHA-256으로 해시하고, 원본 질의 텍스트·사용자명·이메일 대신 길이·카테고리 같은 안전한 메타데이터를 로깅하며, 모델·프롬프트 버전을 항상 기록하고, 30일 암호화된 롤링 보존 정책을 적용함으로써 디버깅·추적·모니터링에 필요한 관측 가능성을 확보하면서도 PII 노출 리스크를 최소화하는 방식으로 설계되어야 하며, ID와 지표를 기본값으로 삼고 원본 콘텐츠는 정책이 명시적으로 허용할 때만 예외적으로 로깅해야 한다.
