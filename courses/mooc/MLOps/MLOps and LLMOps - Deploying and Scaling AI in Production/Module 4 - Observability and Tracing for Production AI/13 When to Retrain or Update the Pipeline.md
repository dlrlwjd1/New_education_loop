# When to Retrain or Update the Pipeline

## 개요
- 드리프트가 탐지된 후 무엇을 할지 결정하는 방법 — 재학습 vs 파이프라인 업데이트 vs 롤백을 선택하는 의사결정 매트릭스와 5단계 런북(runbook)을 다루는 4분 영상. "Monitoring Drift & System Health" 레슨의 마지막 영상이자 Module 4 마지막 강의 영상.

## 내용

### 드리프트 알림 = 자동 재학습이 아니다
- 드리프트 알림이 항상 모델을 재학습해야 함을 의미하지는 않음 — 어떤 경우에는 파이프라인을 업데이트하거나, 프롬프트를 바꾸거나, 최근 변경을 롤백하는 것이 더 나은 대응일 수 있음.
- 목표는 자동 재학습을 피하고, 대신 **증거에 기반해** 대응을 선택하는 것.

### 의사결정 매트릭스
- **입력 드리프트가 높고 품질이 하락 중이면**: 재학습이 필요함.
- **출력 행동만 변했다면**: 프롬프트나 파이프라인 업데이트로 충분할 수 있음.
- **문제가 최근 릴리스와 연관되어 있다면**: 롤백이 최선의 선택일 수 있음.

### 5단계 런북
1. **알림을 검증**하고 그것이 실제인지 확인.
2. **비즈니스 또는 품질 영향**이 있는지 확인.
3. 프롬프트, 모델, 파이프라인의 **최근 변경 사항을 검토**.
4. **조치를 선택**: 재학습, 업데이트, 롤백, 또는 추가 조사.
5. **결정을 문서화**하고 모니터링을 계속.
- 이 프로세스는 팀이 사고 발생 시 자신 있게 행동하도록 도움 — 의사결정 프레임워크를 실전 운영 절차로 전환.

### 핵심 원칙
- 모든 드리프트 알림이 재학습을 필요로 하는 것은 아님 — 결정은 추측이 아니라 **측정 가능한 증거**에 기반해야 함.
- 표준화된 프로세스가 팀이 더 빠르고 일관되게 대응하도록 도움.
- 전체 메시지: 드리프트 대응은 구조화되고 반복 가능해야 함.

### 코드 예시
- 로직이 드리프트 신호를 확인하고, 품질 영향을 평가한 뒤, 재학습·파이프라인 업데이트·롤백 중 무엇을 권장할지 결정.
- 이 예시가 프레임워크를 이해하기 쉽게 만드는 이유: 의사결정 프로세스가 실제 시스템에서 어떻게 구현될 수 있는지 보여주기 때문.

### 실전 예시
- 파이프라인에서 입력 드리프트, 출력 드리프트, 품질 하락을 추적할 수 있음.
- 고정된 런북을 사용해 엔지니어가 즉흥적으로 판단하지 않도록 함.
- **롤백 조건**을 **재학습 조건**과 별도로 모니터링할 수 있음.
- 결과: 팀이 모호함을 줄이고 재학습, 업데이트, 롤백 중 선택할 수 있게 됨.

## 예시
```python
# drift_response.py (개념 구조)
def decide_action(input_drift, output_drift, quality_dropped, recent_release_flag):
    if recent_release_flag and (output_drift or quality_dropped):
        return "ROLLBACK"
    if input_drift and quality_dropped:
        return "RETRAIN"
    if output_drift and not input_drift:
        return "UPDATE_PIPELINE_OR_PROMPT"
    return "INVESTIGATE"
```

```text
[5단계 런북]
1. 알림 검증 → 2. 비즈니스/품질 영향 확인 → 3. 최근 변경 사항 검토
→ 4. 조치 선택(재학습/업데이트/롤백/추가 조사) → 5. 결정 문서화 + 모니터링 지속
```

| 신호 조합 | 조치 |
|---|---|
| 입력 드리프트 + 품질 하락 | 재학습 |
| 출력 행동만 변화 | 프롬프트/파이프라인 업데이트 |
| 최근 릴리스와 연관된 문제 | 롤백 |

## 요약
- 드리프트가 탐지되면 자동으로 재학습하는 대신, 입력 드리프트·품질 하락·최근 릴리스 여부라는 증거를 바탕으로 재학습·파이프라인 업데이트·롤백 중 하나를 선택하는 의사결정 매트릭스를 적용해야 하며, 알림 검증부터 결정 문서화까지 이어지는 5단계 런북을 표준화함으로써 엔지니어가 즉흥적으로 판단하지 않고 구조화되고 반복 가능한 방식으로 사고에 대응할 수 있다.
