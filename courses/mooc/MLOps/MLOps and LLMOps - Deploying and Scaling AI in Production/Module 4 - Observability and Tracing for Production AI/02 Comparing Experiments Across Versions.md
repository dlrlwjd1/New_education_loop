# Comparing Experiments Across Versions

## 개요
- 여러 실험 실행(run)을 구조적이고 신뢰할 수 있게 비교하는 방법 — 고정된 평가셋, 태깅 전략, 파레토(Pareto) 트레이드오프 분석, 그리고 W&B/MLflow를 이용한 실전 쿼리 예시를 다루는 7분 영상. "Experiment Tracking & Telemetry" 레슨의 두 번째 영상.

## 내용

### 왜 구조적 비교가 필요한가
- 프로덕션 AI에서는 많은 실험을 실행하는 것만으로는 충분하지 않음 — 어떤 버전이 실제로 승격에 가장 적합한지 식별할 수 있는 명확한 비교 방법도 필요함.
- 승격은 하나의 최고 지표가 아니라 **품질, 지연시간, 비용의 균형**에 달려 있어야 함.

### 실험을 올바르게 비교하는 핵심 전략
1. **W&B의 병렬 좌표(Parallel Coordinates)**: 여러 실행에 걸친 모든 지표를 시각화 — 팀이 단일 최고 점수가 아니라 최선의 트레이드오프를 제공하는 실행을 빠르게 발견하는 데 도움.
2. **MLflow Compare Runs**: 태그로 필터링하고, 지표로 정렬하고, 실험을 구조적으로 쿼리할 수 있게 함.
3. **가장 중요한 원칙 — 항상 동일한 평가 데이터셋 사용**: 데이터셋이 바뀌면 실행들이 같은 조건에서 테스트되지 않았으므로 비교가 더 이상 유효하지 않음.
4. **모든 것을 로깅하라**: 일부 필드가 처음에는 중요하지 않아 보여도, 프로덕션에서는 사소한 세부사항이 나중에 근본 원인 분석에 필수적이 되는 경우가 많음.
- 핵심 요점: 신뢰할 수 있는 비교는 일관된 데이터, 완전한 로깅, 트레이드오프를 가시화하는 도구에 달려 있음.

### 태깅으로 실험 조직화
- 예시 태깅 전략: **모델, 프롬프트 버전, 데이터셋 버전, 평가자(evaluator)**.
- 각 태그의 목적:
  - **모델 태그**: 모든 GPT-4o 실행만 보여주는 것처럼 실행을 쉽게 필터링.
  - **프롬프트 버전 태그**: 실험 전반에 걸쳐 프롬프트가 어떻게 변했는지 추적.
  - **데이터셋 버전 태그**: 실행들이 직접 비교 가능한지 팀이 알 수 있도록 보장.
  - **평가자 태그**: 어떤 판정 모델이 그 실행을 채점했는지 기록.
- 핵심 요점: 좋은 태깅은 실험 추적을 검색 가능하고 재현 가능한 것으로 전환함 — 강력한 태그 없이는 실행은 있지만 그들 사이에 무엇이 다른지 이해할 쉬운 방법이 없을 수 있음.

### 실전 쿼리 예시: 최적 후보 찾기
- 2개 모델, 5개의 프롬프트 변형, 2개의 temperature에 걸친 **20개의 실험** 예시.
- MLflow에서 모델이 GPT-4o이고 정확성이 0.9보다 큰 실행으로 필터링 → 합성 점수 내림차순, P95 지연시간 오름차순으로 정렬 → 사람 검토와 비용 분석을 위해 **상위 3개 후보** 선정.
- MLflow Compare는 실행을 데이터프레임으로 내보내 통계 분석에 사용할 수 있음.
- 핵심 요점: 실험 비교는 필터링에서 멈춰서는 안 됨 — 팀은 체계적으로 후보를 좁힌 뒤 승격 전에 가장 강력하고 균형 잡힌 후보들을 검토해야 함.

### 신뢰할 수 있는 프로세스의 핵심 원칙 4가지
1. **동결된 평가셋 사용**: 데이터셋이 바뀌면 지표 비교가 의미를 잃음.
2. **모든 것을 태깅**: 모델, 프롬프트 버전, 데이터셋 버전, 평가자 태그가 실험을 쿼리 가능하고 재현 가능하게 만듦.
3. **파레토 분석(Pareto Analysis) 사용**: W&B 병렬 좌표 같은 시각적 도구가 하나의 지표에만 집중하는 대신 비용·품질·지연시간 사이의 최선의 트레이드오프를 찾는 데 도움.
4. **통계를 위해 내보내기**: MLflow Compare를 데이터프레임으로 내보내면 t-검정과 신뢰구간을 실행할 수 있어 실험 결정에 더 엄격함을 더함.
- 핵심 메시지: 강력한 실험 비교는 구조화된 메타데이터, 유효한 비교, 신중한 트레이드오프 분석을 결합함.

### 코드 예시: `compare_runs.py`
- 프로젝트의 모든 실행을 쿼리 → 최고 F1 점수를 가진 실행을 찾음 → 각 실행의 이름, F1, 지연시간을 출력.
- **승격 조건 2가지** 확인: **F1이 최소 0.84 이상**, **지연시간이 최대 900밀리초 이하**.
- 두 조건이 모두 충족될 때만 실행이 승격됨.
- 핵심 요점: 가장 높은 품질 점수 하나만으로는 충분하지 않음 — 실행은 여전히 승격 가능하다고 간주되기 전에 성능 한계를 충족해야 함. 승격은 가장 시끄럽거나 가장 높은 점수를 받은 실행이 아니라 **가장 균형 잡힌 최고의 실행**에 보상해야 함.

### 실전 메시지 요약
1. 승격 전 품질과 지연시간을 나란히 비교할 것.
2. 실험을 MLflow나 W&B 같은 성장의 소스(source of growth)에 추적할 것.
3. 최고 점수가 지연시간 예산을 깨뜨려도 자동으로 이기지 않도록 승격을 신중히 만들 것.
- 결과: 팀이 단일 최고 점수를 추구하는 대신 **가장 균형 잡힌 실행**을 승격함.
- 최종 메시지: 지표, 파라미터, 아티팩트를 함께 저장해 모든 실험 결정이 재현 가능하도록 할 것.

### 결론
- 실험을 잘 비교하는 것은 단순히 점수를 만드는 것이 아니라, 동일한 데이터셋, 일관된 태그, 균형 잡힌 결정 기준을 사용해 승격 선택이 신뢰할 수 있고 설명 가능하도록 만드는 것.

## 예시
```python
# compare_runs.py (개념 구조)
import mlflow

runs = mlflow.search_runs(
    filter_string="params.model = 'gpt-4o' and metrics.correctness > 0.9"
)
runs = runs.sort_values(["composite_score", "p95_latency_ms"], ascending=[False, True])
top_candidates = runs.head(3)

for _, run in top_candidates.iterrows():
    meets_f1 = run["metrics.f1"] >= 0.84
    meets_latency = run["metrics.p95_latency_ms"] <= 900
    if meets_f1 and meets_latency:
        promote(run)
```

```text
[실험 태깅 전략]
model          — 모델별 필터링 (예: GPT-4o만)
prompt_version — 프롬프트 변화 추적
dataset_version — 실행 간 비교 가능성 보장
evaluator      — 어떤 판정 모델이 채점했는지 기록
```

## 요약
- 여러 버전의 실험을 신뢰할 수 있게 비교하려면 항상 동일한 동결된 평가셋을 사용하고, 모델·프롬프트 버전·데이터셋 버전·평가자로 모든 실행을 태깅해 검색·재현 가능하게 만들며, W&B 병렬 좌표 같은 도구로 단일 지표가 아닌 비용·품질·지연시간의 파레토 트레이드오프를 시각화하고, MLflow Compare를 통계 분석용 데이터프레임으로 내보내야 하며, 최종 승격은 F1과 지연시간 같은 복수 조건을 모두 충족하는 가장 균형 잡힌 실행에 돌아가야 한다.
