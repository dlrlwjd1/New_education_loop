# Introduction to Model Serving

## 개요
- 학습이 끝난 ML 모델(pickle 파일)을 실제 애플리케이션에 통합하는 **모델 배포와 서빙(Model Deployment and Serving)** 개념을 약국 재고 예측 사례로 설명하는 10분 영상. 마이크로서비스 아키텍처 관점에서 MLOps 엔지니어와 DevOps 엔지니어의 역할 유사성을 강조.

## 내용

### 문제 상황: 모델은 준비됐는데, 그다음은?
- 데이터 과학자, 프로덕트 매니저, MLOps 엔지니어가 협업해 모델 개발·실험을 마쳤다면, 다음 질문은 "이 ML 모델을 우리 앱에 어떻게 통합할 것인가?" — 이 통합을 담당하는 것이 **MLOps 엔지니어**의 핵심 역할.

### 예시: 약국 재고 예측
- 약국(pharmacist)이 재고가 필요하면 **재고 관리 앱(inventory application)**에 요청 → 요청은 **창고(warehouse)**의 재고 예측 대시보드로 전달 → 창고가 필요한 재고를 약국에 발송.
- 개선 가능한 영역:
  1. 과거 데이터 기반으로 **제품 수요를 정확히 예측**.
  2. 재고 수준과 창고 운영 **효율 최적화**.
  3. 창고 작업·스케줄링 **자동화**.
- 구체적 흐름: 재고 예측 대시보드에서 지점명(branch name)과 월(month)을 선택 → "Go" 버튼 클릭 → 프론트엔드가 `/predict` API 호출 → 이 API가 ML 모델을 호스팅하며 예측 수행 → 결과 예시: "두바이몰 지점, 2025년 12월 예측 → 특정 의약품 4종과 필요 수량".
- 이 정보로 재고 계획을 세우고 사전에 구매 주문(purchase order)을 낼 수 있어, 실제 주문이 들어왔을 때 즉시 발송 가능 — 효율성뿐 아니라 **비용 절감**(수요 예측을 근거로 공급업체와 유리하게 협상 가능)에도 기여. 이런 재고 예측 모델은 현재 모든 전자상거래 앱에 존재.

### 마이크로서비스로서의 ML 모델
- ML 모델을 API와 통합하려면 **마이크로서비스 아키텍처**로 배포해야 함 — `/predict` 엔드포인트가 ML 모델을 담은 마이크로서비스로 배포됨.
- 마이크로서비스의 속성(모두 기존 DevOps 원칙과 동일):
  - 독립적으로 배포 가능(independently deployable)
  - 확장 가능(scalable)
  - 장애 허용(fault tolerant)
  - 자체 CI/CD 프로세스 보유
  - 다른 마이크로서비스와 느슨한 결합(loose coupling)
  - 단일 책임(single responsibility) — 예: 재고 예측만 담당
  - 우수한 모니터링·로깅

### 팀 간 협업 흐름 (배포 생애주기)
1. **엔지니어링 정렬(Engineering Alignment)**: 어떤 백엔드 서비스가 ML 모델 API를 호출할지 결정 — 이 예시에서는 프론트엔드 엔지니어링 API가 `/predict`를 호출.
2. **API 파라미터 합의**: MLOps 엔지니어와 프론트엔드 엔지니어가 필요한 파라미터(예: 지점명, 날짜)를 합의 — `/predict` 엔드포인트가 이 두 파라미터를 입력받아 예측 수행.
3. **스테이징 배포(Staging Deployment)**: 양 팀 모두 코드 변경이 있으므로 스테이징 환경에서 테스트.
4. **프로덕션 배포(Production Deployment)**: 스테이징 테스트 완료 후 프로덕션 엔드포인트로 이동.
5. **트래픽 점진 전환**: 처음에는 프론트엔드 트래픽의 **10%**만 `/predict` 엔드포인트로 라우팅 → 실시간 예측 동작 확인 → 이후 **100%** 트래픽 전환.
6. **모니터링**: 서비스·인프라 모니터링.
7. **확장성 튜닝(Scalability fine-tuning)**: 두 마이크로서비스(프론트엔드, `/predict`) 모두 수요 급증 시 확장 가능하도록 조정.

### MLOps 엔지니어 vs DevOps 엔지니어
- 마이크로서비스 배포에 적용되는 모든 DevOps 원칙을 MLOps 엔지니어도 동일하게 인지하고 적용해야 함 — 모델을 배포·서빙하는 작업에서 두 역할의 접근 방식은 매우 유사함.

### 다음 단계 예고
- 다음 영상에서는 **온라인 서빙(online serving)**과 **오프라인 서빙(offline serving)**의 차이, 그리고 **모델 드리프트(model drift)**의 개념을 다룰 예정.

## 예시
```text
[프론트엔드 재고 예측 대시보드]
  지점명(branch name) 선택 + 월(month) 선택 → "Go" 클릭
        │
        ▼
[프론트엔드 API] ──POST──▶ [/predict 엔드포인트 (ML 모델 마이크로서비스)]
        파라미터: branch_name, date
        │
        ▼
   예측 결과: "Dubai Mall 지점, 2025년 12월 → 의약품 4종 필요 수량"
        │
        ▼
   재고 계획 수립 + 사전 구매 주문(purchase order)
```

```text
배포 생애주기:
엔지니어링 정렬 → API 파라미터 합의 → 스테이징 배포·테스트
→ 프로덕션 배포 → 트래픽 10% 전환·모니터링 → 트래픽 100% 전환
→ 모니터링 → 확장성 튜닝
```

## 요약
- ML 모델을 pickle 파일 상태에서 실제 서비스로 전환하려면 `/predict` 같은 엔드포인트를 갖춘 **마이크로서비스**로 배포해야 하며, 이 과정은 기존 DevOps의 마이크로서비스 배포 원칙(확장성, 장애 허용, CI/CD, 단일 책임 등)과 동일한 원칙을 따르고, 프론트엔드 팀과의 API 파라미터 합의 → 스테이징 → 점진적 트래픽 전환 → 모니터링이라는 협업 생애주기를 거친다.
