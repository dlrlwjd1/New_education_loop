# Model Drift and Online/Offline Serving

## 개요
- 프로덕션에 배포된 모델이 지속적으로 업데이트되어야 하는 이유인 **모델 드리프트(Model Drift)** 개념과, 이를 다루는 두 가지 서빙 방식인 **온라인 서빙(Online Serving)**과 **오프라인 서빙(Offline Serving)**의 차이를 상세히 비교하는 11분 영상.

## 내용

### 왜 배포 후에도 모델을 계속 업데이트해야 하는가
- 약국 재고 예측 예시로 돌아가서: 약사가 재고 관리 앱으로 **새로운 재고**(예: 기존에 없던 신약, 처방)를 요청 → 이 신규 항목은 모델이 학습한 적 없는 데이터 → 예측 대시보드가 부정확해짐 → 창고가 실제 요청과 예측 사이의 불일치로 혼란을 겪음.
- 이처럼 새로운 정보는 끊임없이 유입되며, 이 현상을 다루는 개념이 **모델 드리프트**.

### 모델 드리프트의 여러 형태
1. **실세계 패턴 변화(Real-world change of patterns)**: 트렌드·계절성·글로벌 이벤트가 데이터 패턴을 계속 바꿈 — 예: 팬데믹 이전 데이터로 학습한 소비자 행동 모델이 COVID-19 기간 동안 정확도를 유지하지 못함.
2. **데이터 드리프트(Data Drift)**: 프로덕션 데이터가 학습 데이터의 패턴에서 벗어남 — 예: 특정 인구통계로 학습된 신용평가 모델이 고객층이 새로운 지역으로 확장되면서 다른 분포의 데이터를 받게 되어 성능이 저하됨.
3. **타깃 변수 드리프트(Target Variable Drift)**: 예측 대상 자체의 정의가 바뀜 — 예: 고객 이탈(churn) 예측 모델에서 비즈니스 정책 변경으로 '이탈'의 정의 자체가 바뀌면 기존 모델이 무의미해짐.
4. **업스트림 데이터 변화(Upstream Data Change)**: 데이터 수집 프로세스 변경이나 파이프라인 오류가 시스템 전체로 전파되는 불일치를 유발 — 예: 센서 보정(calibration) 변경으로 측정값의 스케일이 바뀌면 기존 학습 패턴이 무효화됨.
5. **모델 복잡도 문제**: 파라미터가 매우 많은 과도하게 복잡한 모델은 학습 데이터에서는 높은 정확도를 보이지만 노이즈까지 학습해 견고하지 못한(not robust) 모델이 될 수 있음.
6. **모니터링·재학습 부재**: 가장 위험한 요소 — 견고한 성능 추적 시스템이 없으면 드리프트가 장기간 감지되지 않다가, 비즈니스 지표를 통해 뒤늦게 드러날 때는 이미 조직의 총 수익에 상당한 타격을 준 뒤일 수 있음.

### 모델 드리프트 대응: 온라인 서빙 vs 오프라인 서빙
- 새로운 데이터(feature)가 들어오면 **피처 스토어(feature store)**에 업데이트됨. 이후 두 가지 방식으로 대응 가능:
  - **온라인 서빙(온라인 예측)**: 새 입력을 기반으로 모델이 **지속적으로(continuously)** 재학습됨 — 매시간, 매일, 이틀마다 등 사용 사례에 따라 주기가 다름. 복잡하고 비용이 많이 들지만 많은 조직이 지향하는 이상적 형태("north star").
  - **오프라인 서빙(오프라인 예측)**: 새 피처는 피처 스토어에 저장되지만, 모델 자체는 **배치(batch) 방식**으로 학습됨 — 예측 대시보드 호출 시 최신 모델이 아니라, 일정 주기마다 배치로 업데이트된 모델을 사용.

### 온라인 서빙 vs 오프라인 서빙 상세 비교
| 관점 | 온라인 서빙 | 오프라인 서빙 |
|---|---|---|
| 인프라 투자 | 고성능 컴퓨팅 자원 필요, 실시간 처리 | 표준 컴퓨팅 자원으로 경제적 운영 |
| 대표 사용 사례 | 실시간 추천 시스템, 사기 탐지(fraud detection), 동적 가격 책정 | 고객 세분화 분석, 리스크 모델링, 장기 예측 |
| 지연시간(Latency) | 밀리초 단위 응답 필요(최적화된 배포·요청 처리) | 더 높은 지연 허용 — 예측이 사전 계산됨, 복잡한 모델·배치 처리 가능 |
| 데이터 신선도(Freshness) | 최신 데이터를 지속적으로 반영 | 과거(historical) 데이터셋에 의존 |
| 인프라 요구사항 | 견고하고 확장 가능한 실시간 인프라 필요 | 덜 까다로운 하드웨어로 비용 효율적인 배치 처리 |
| 아키텍처 복잡도 | 실시간 처리로 인해 복잡도 높음(에러 처리, 로드 밸런싱, 모니터링 필요) | 배치 작업 중심의 단순한 아키텍처, 운영·유지보수 용이 |
| 확장성 | 예측 불가능한 트래픽 급증에 대응하는 정교한 오토스케일링 필요 | 예측 가능한 워크로드 → 계획된 자원 확장과 최적화된 배치 파이프라인 가능 |
| 자원 관리 | 일관된 가용성·응답 시간을 위한 지속적 자원 할당 필요 | 사전 정해진 배치 처리 시간에만 컴퓨팅 자원을 활성화해 비용 최적화 |
| 성능 트레이드오프 | 속도 우선 — 모델 최적화·경량 아키텍처로 신속한 응답 | 정확도 우선 — 복잡한 모델과 방대한 연산으로 시간 제약 없이 최대 정확도 추구 |

### 선택 기준
- 온라인 서빙과 오프라인 서빙 중 어느 것을 선택할지는 항상 **비즈니스 사용 사례** 관점에서 결정해야 함 — 해당 사용 사례가 실시간성을 요구하는지, 배치 처리로 충분한지가 핵심 판단 기준.

## 예시
```text
[신규 재고 요청 발생]
        │
        ▼
[피처 스토어(feature store)에 새 피처 업데이트]
        │
        ├── 온라인 서빙: 모델이 지속적으로(매시간/매일 등) 재학습 → 최신 모델로 즉시 예측
        │
        └── 오프라인 서빙: 피처만 저장, 모델은 배치 주기(예: 매주)로만 업데이트
                            → 대시보드 호출 시 "최신"이 아닌 "가장 최근 배치"의 모델 사용
```

## 요약
- 모델 드리프트는 실세계 패턴 변화, 데이터 드리프트, 타깃 변수 드리프트, 업스트림 데이터 변화, 과도한 모델 복잡도, 모니터링·재학습 부재라는 여러 원인으로 프로덕션 모델의 성능을 저하시키며, 이에 대응하는 두 가지 서빙 전략인 온라인 서빙(실시간·고비용·고복잡도)과 오프라인 서빙(배치·경제적·저복잡도) 중 무엇을 선택할지는 실시간성이 요구되는 비즈니스 사용 사례인지에 따라 결정해야 한다.
