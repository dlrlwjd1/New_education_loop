# Computing Runtimes

## 개요
- 지금까지 사용한 "실행되는 코드 줄 수"라는 실행 시간 측정 방식이 왜 부정확한지, 정확한 실제 실행 시간을 구하는 것이 왜 복잡하고 다루기 힘든 문제인지 설명한다.

## 내용
### "코드 줄 수" 측정의 문제
- 지금까지는 실행되는 코드 줄 수(T(n))로 실행 시간을 근사해 왔다.
- 이 방식은 암묵적으로 모든 코드 줄이 서로 비교 가능한(comparable) 하나의 기본 연산이라고 가정한다.
- 피보나치 수 계산 알고리즘(배열 생성 → 초기값 대입 → for 루프에서 합산 → 마지막 원소 반환)을 예로 세부적으로 살펴보면 이 가정이 실제로는 성립하지 않음을 알 수 있다.

### 각 줄에 실제로 필요한 작업
- 배열 생성: 메모리에서 빈 공간을 찾아 포인터를 얻는 것뿐일 수도 있지만, 메모리 관리 시스템에 따라 다른 데이터를 옮기거나 배열 내부를 0으로 초기화해야 할 수도 있어 시간이 상당히 걸릴 수 있다.
- 단순 대입(예: 0번째 원소를 0으로 설정): 실제 기계 수준에서는 배열의 포인터를 불러오고, 포인터 연산을 수행하고, 값을 메모리에 저장하는 등 여러 연산이 필요할 수 있다.
- for 루프: 매 반복마다 i를 증가시키고, n과 비교해 루프를 빠져나갈지 판단하고, 분기(branch)해야 한다.
- 덧셈: 배열에서 두 값을 조회하고 세 번째 값에 쓰는 작업 외에도, 피보나치 수는 매우 커서(machine word 하나에 들어가지 않을 정도) 두 큰 수를 더하는 것 자체가 상당한 시간이 걸리는 비trivial한 연산이다.
- 반환(return): 배열 조회에 더해 프로그램 스택(program stack)을 한 단계 팝(pop)하고 값을 반환하는 작업이 필요하다.
- 결론: 6줄짜리 프로그램이지만 각 줄이 실제로 수행하는 작업량은 서로 매우 다르다.

### 정확한 실행 시간을 구하기 위한 요소들
- 완전히 정확하려면 실제 컴퓨터에서 프로그램을 실행했을 때 걸리는 실제 시간을 알아야 하는데, 이를 위해선 다음과 같은 세부 사항을 모두 알아야 한다.
  - 컴퓨터의 속도(슈퍼컴퓨터 vs. 휴대폰)
  - 시스템 아키텍처(system architecture) — CPU가 지원하는 연산과 상대적 소요 시간
  - 사용하는 컴파일러(compiler) — 고수준 언어(C, Java, Python 등)를 기계어로 바꾸며 다양한 최적화(optimization)를 수행하는데, 어떤 최적화가 적용되는지가 최종 실행 시간에 영향을 준다.
  - 메모리 계층 구조(memory hierarchy) — 계산이 캐시(cache)에 다 들어가면 빠르지만, RAM 조회가 필요하면 느려지고, 디스크(disk)까지 접근해야 하면 밀리초 단위로 훨씬 느려진다.

### 실용적인 문제
- 정확한 실행 시간을 계산하는 것은 너무 복잡해서, 매번 새로운 알고리즘을 분석할 때마다 이 모든 걸 따질 수는 없다.
- 게다가 실제로는 이런 세부 사항을 알 수 없는 경우가 대부분이다 — 프로그램은 남의 컴퓨터에서 실행되며, 그 컴퓨터의 아키텍처를 알 방법이 없고, 여러 사용자가 서로 다른 컴퓨터에서 실행할 것이다.
- 해결책의 실마리: 실제 초 단위 시간이 아니라, 입력 크기(input size)에 따라 실행 시간이 어떻게 스케일(scale)되는지에 주목하는 새로운 측정 방법이 필요하다. 이는 다음 강의(점근 표기법)에서 다룬다.

## 요약
- "코드 줄 수"는 각 줄의 실제 작업량이 다르기 때문에 정확한 실행 시간 측정 방법이 아니다.
- 정확한 실행 시간은 컴퓨터 속도, 시스템 아키텍처, 컴파일러, 메모리 계층 구조 등 알기 어려운 세부 사항에 크게 의존한다.
- 이런 세부 사항 없이도 쓸 수 있는, 입력 크기에 따른 스케일링(scaling)에 주목하는 새로운 실행 시간 측정 방법이 필요하며, 이는 다음 강의의 주제다.
