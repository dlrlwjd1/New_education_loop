# Stress Test - More Testing, Submit and Pass!

## 개요
- 작은 값으로는 버그가 안 보일 수 있으므로 n과 원소 값의 범위를 점점 키워가며 추가 검증을 진행한다.
- 스트레스 테스트 코드를 원래 해답으로 되돌리고, 불필요한 디버그 출력을 제거한 뒤 최종 제출한다.
- 스트레스 테스트의 한계와, 코딩 과제 전반에 적용해야 할 표준 테스트 기법들을 정리한다.

## 내용

### 범위를 늘려가며 추가 검증
- 작은 n, 작은 값으로는 두 해답이 더 이상 다른 결과를 내지 않았지만, 이는 더 큰 n이나 더 큰 값에서도 안전하다는 보장이 아니다.
- Ctrl-C로 실행을 멈춘 뒤 코드로 돌아가 제한을 늘린다: n은 최대 100까지, 원소 값은 문제에서 허용하는 최댓값인 100,000까지.
- 재컴파일 후 다시 실행하면 더 많은 원소와 더 큰 수로 구성된 테스트가 계속 "OK"를 출력하며 실패 테스트가 나타나지 않는다.
- n을 더 키워 테스트할 수도 있다. 다만 느린 해답(main solution)이 이차 시간(quadratic time)으로 동작하므로, n=100,000까지 테스트하면 너무 오래 걸릴 수 있어 n을 최대 1,000 정도까지만 늘려 테스트한다.
- 이 범위에서도 실패 테스트가 나타나지 않으면, 해답이 올바르게 동작한다는 확신을 가질 수 있다.

### 스트레스 테스트 코드 원상 복구
- 스트레스 테스트를 멈추고, `main` 함수에서 스트레스 테스트를 구현한 while 루프를 주석 처리(comment out)해 원래 문제의 해답으로 되돌린다.
- 재컴파일 후 간단한 테스트(예: n=2, 값 3과 5)로 실행해보면, 정답인 15 외에 부가적인 숫자(0이나 1 같은 디버그 출력)가 함께 출력되는 문제를 발견한다.
- 이는 이전에 추가했던 `max_index1`, `max_index2` 디버그 출력이 남아있기 때문이다. 문제 명세에 있는 값만 출력하고 그 외에는 아무것도 출력하지 않아야 하므로, 이 디버그 출력도 주석 처리해서 제거한다.
- 다시 컴파일 후 동일한 테스트를 실행하면 이제 정답인 15만 출력되는 것을 확인한다.

### 제출과 결과
- 수정이 끝난 `stress_test.cpp` 파일을 MOOC에 새 제출(new submission)로 업로드한다.
- 채점 시스템이 채점을 마치면 모든 테스트를 통과(pass)했다는 결과를 받는다.

### 스트레스 테스트에 대한 추가 조언
- **운이 좋았던 경우**: 이 문제에서 두 해답이 달라지는 경우는 "두 최댓값이 같을 때"라는 비교적 드문 경우였는데도 빠르게 실패 테스트를 발견했다. 항상 이렇게 운이 좋은 것은 아니다.
- **코너 케이스(corner case)를 노려라**: 무작위 생성만으로 실패 테스트를 빠르게 찾지 못한다면, 더 특정한 부분공간(subspace)에 집중해 테스트를 생성해야 한다. 예를 들어 그래프 문제라면 비연결 그래프(disconnected graph), 완전 그래프(full graph), 이분 그래프(bipartite graph) 등을 의도적으로 생성한다. 문자열 문제라면 한 글자만 반복되는 문자열이나 두 글자만 섞인 문자열처럼 문자 종류가 적은 경우가 코너 케이스가 되는 경우가 많다.
- **최소 실패 테스트부터 확보하라**: 실패 테스트를 찾았다면 곧바로 디버깅하지 말고, 먼저 가장 작고 단순한 실패 테스트를 찾는 것이 디버깅을 훨씬 쉽게 만든다.
- **스트레스 테스트의 한계**:
  - 속도 문제(주 해답이 너무 느린 경우)는 잘 찾아내지 못한다. 대안 해답이 보통 더 느린 무차별 대입 방식이라 큰 테스트로 비교하기 어렵기 때문이다.
  - 정수 오버플로도 놓치기 쉽다. 큰 수로 무작위 테스트를 생성해도 두 해답 모두 같은 방식으로 오버플로가 나면 차이가 드러나지 않는다.
- **권장 순서**: 수동 테스트(manual test) → 정수 오버플로 테스트 → 최대 크기 테스트(max test) → 스트레스 테스트 순으로 적용하면 대부분의 함정을 찾아낼 수 있다. 이는 실제로 문제 출제자들이 테스트 세트를 만드는 방식(수동 테스트, 오버플로용 큰 수 테스트, 시간 제한용 큰 테스트, 무작위 테스트, 특정 부분공간 테스트)과 유사하다.

### 핵심 교훈
- 프로그램은 허용된 모든 테스트 케이스에서 동작해야 하며, 대부분의 케이스에서만 동작해서는 안 된다.
- 드물게만 드러나는 버그라도 실제 사용자 중 누군가는 반드시 마주치게 되며, 이는 사용자 경험을 크게 해친다.
- 코드에 버그가 있는 줄 모르고 잘못된 결과에 근거해 의사결정을 내리는 경우도 실무에서 자주 발생한다.
- 스트레스 테스트는 특히 해답이 어떤 테스트에서 실패하는지조차 알 수 없을 때(채점 시스템이 테스트를 숨길 때) 유용하다. 실제 현실에서도 프로그램이 실패하는 정확한 조건을 모르는 경우가 많다.

## 요약
- n과 값의 범위를 점진적으로 늘려가며 스트레스 테스트를 반복해 해답의 신뢰도를 높인다.
- 최종 제출 전 스트레스 테스트용 while 루프와 디버그 출력을 모두 제거하고, 문제에서 요구하는 값만 출력하도록 정리해야 한다.
- 스트레스 테스트는 만능이 아니며(속도 문제·오버플로는 놓치기 쉬움), 수동 테스트·오버플로 테스트·최대 크기 테스트와 함께 사용해야 효과적이다.
