# Building a Heap

## 개요
- `BuildHeap` 절차의 실행 시간을 더 정밀하게 분석하여, 앞서 추정한 O(n log n)이 사실은 O(n), 즉 선형 시간(linear time)임을 증명한다.
- 이를 응용해 배열 전체를 정렬하지 않고도 상위 k개의 최댓값을 선형 시간에 찾는 방법을 소개한다.

## 내용

### 왜 O(n log n) 추정이 너무 비관적인가
- `BuildHeap`은 대략 n/2번의 `SiftDown` 호출로 이루어지고, 각 호출을 단순히 O(log n)으로 잡으면 전체는 O(n log n)이 된다.
- 그러나 리프에 가까운 노드에서 `SiftDown`을 호출하면, 그 노드가 내려갈 수 있는 거리(해당 서브트리의 높이)가 훨씬 짧아 실제 비용은 log n보다 훨씬 작다.
- 트리에는 루트에 가까운 노드는 적고(루트 1개, 그다음 레벨 2개, …) 리프에 가까운 노드는 많다(최하위에 가까운 레벨에 대략 n/2개, n/4개, …). 따라서 정확한 합을 구하면 추정치가 크게 줄어든다.

### 더 정밀한 실행 시간 계산
- 각 레벨에서 사용되는 스왑 횟수 상한을 합산하면 다음과 같은 급수가 나온다: n/2개 노드에 대해 비용 1, n/4개 노드에 대해 비용 2, n/8개 노드에 대해 비용 3, … 즉 n × Σ(i / 2^i) (i=1부터 무한대까지).
- 기하급수(geometric series)의 성질을 이용해 Σ(i / 2^i) = 2 임을 기하학적으로(선분들을 겹쳐 쌓는 방식으로) 보일 수 있다.
- 따라서 `BuildHeap`의 실행 시간은 최대 2n, 즉 O(n)이다.

### 이 개선이 힙 정렬(heap sort) 자체에 주는 영향
- `BuildHeap`이 O(n)이라는 사실이 힙 정렬 전체의 점근적 실행 시간을 더 줄여주지는 않는다. 정렬 자체가 비교 기반 알고리즘의 하한인 O(n log n)보다 빨라질 수는 없기 때문이다(BuildHeap 이후에도 `ExtractMax`를 n-1번 호출해야 하므로 여전히 O(n log n)).

### 상위 k개 원소 찾기 문제에의 응용
- 배열 전체를 정렬하지 않고, 정수 k(1 ≤ k ≤ n)가 주어졌을 때 상위 k개의 원소(정렬된 배열의 마지막 k개에 해당)만 찾고 싶은 경우를 생각한다.
- 방법: 배열로 힙을 만든 뒤(`BuildHeap`, O(n)) `ExtractMax`를 k번 호출한다(각 호출 O(log n)).
- 전체 실행 시간은 O(n) + O(k log n). k가 O(n / log n) 이하라면 이 값은 O(n), 즉 선형 시간이 된다.
- 예: n개짜리 배열에서 √n개의 최댓값을 찾고 싶다면, 배열 전체를 O(n log n)에 정렬할 필요 없이 O(n) 만에 구할 수 있다.

## 예시
- Σ(i/2^i) 계산: 1/2 + 2/4 + 3/8 + 4/16 + 5/32 + … = 2. 이를 n배 하면 `BuildHeap`의 상한 2n이 나온다.
- k가 n/log n보다 작을 때: 상위 k개 찾기 실행 시간 = O(n)(BuildHeap) + O(k log n)(k번의 ExtractMax) ≤ O(n).

## 요약
- `BuildHeap`을 리프 근처 노드는 적은 비용, 루트 근처 노드는 많은 비용이 든다는 점을 정확히 합산하면 실행 시간은 O(n log n)이 아니라 O(n)이다.
- 힙 정렬 자체의 점근적 실행 시간은 여전히 O(n log n)이지만(정렬은 비교 기반 하한을 넘을 수 없음), `BuildHeap`이 선형이라는 사실은 "상위 k개 찾기"처럼 정렬이 필요 없는 문제에서 유용하다.
- k ≤ O(n / log n)이면, 배열을 힙으로 만들고 `ExtractMax`를 k번 호출하는 것만으로 상위 k개를 선형 시간에 구할 수 있다.
