# Naive Implementations

## 개요
- 서로소 집합(disjoint sets) 자료구조를 순진하게(naive) 구현하는 두 가지 방법 — 배열 기반과 연결 리스트(linked list) 기반 — 을 살펴보고 각각의 장단점을 분석한다.
- 이를 통해 다음 강의에서 다룰 트리(tree) 기반의 효율적인 구현으로 나아가기 위한 통찰을 얻는다.

## 내용

### 배열 기반 구현 (smallest 배열)
- n개의 원소를 정수 1~n으로 가정하고, 각 집합의 ID로 그 집합에서 가장 작은 원소를 사용한다.
- 각 원소 i에 대해 그 원소가 속한 집합의 ID를 배열 `smallest[i]`에 저장한다.
- `MakeSet(i)`: `smallest[i] = i`. 상수 시간.
- `Find(i)`: `smallest[i]`를 반환. 상수 시간.
- `Union(i, j)`: `Find(i)`, `Find(j)`로 두 ID(`i_id`, `j_id`)를 구한 뒤 같으면 아무 것도 안 하고, 다르면 더 작은 값 `m = min(i_id, j_id)`을 구해 `smallest[k]`가 `i_id` 또는 `j_id`인 모든 k에 대해 `smallest[k] = m`으로 갱신. 이때 n개의 원소를 모두 훑어야 하므로 선형 시간(linear time).
- 병목: `MakeSet`, `Find`는 상수 시간이지만 `Union`이 선형 시간이라는 점.

### 연결 리스트 기반 구현 (linked list)
- 각 집합을 연결 리스트로 표현하고, 리스트의 꼬리(tail)를 그 집합의 ID로 사용한다.
- `Find(x)`: x부터 포인터를 따라가 리스트의 꼬리(ID)에 도달할 때까지 이동. 최악의 경우 리스트 전체를 순회해야 하므로 선형 시간.
- `Union`: 한 리스트를 다른 리스트 뒤에 그냥 이어붙이면(append) 포인터 하나만 바꾸면 되므로 상수 시간이며, 결과 리스트의 ID(꼬리)도 자동으로 일관되게 유지된다.
  - 단, 이 상수 시간 구현을 위해서는 각 리스트의 머리(head)와 꼬리(tail) 위치를 별도로 관리하는 추가 정보가 필요하며, 두 리스트를 합칠 때 이 정보도 갱신해야 한다.
- 장점: `Union`이 상수 시간이고, 병합 후 ID가 자동으로 잘 정의됨.
- 단점: `Find`가 최악의 경우 선형 시간이며, 시간이 지날수록 리스트가 점점 길어져 `Find`가 점점 느려진다.

### 개선의 실마리 — 리스트 대신 트리로
- 두 리스트를 이어붙이는 대신, 한 리스트의 머리를 다른 리스트의 꼬리 노드에 매다는(hang) 방식을 생각해볼 수 있다.
- 이렇게 하면 결과 구조는 더 이상 리스트가 아니라 트리(tree) 형태가 되며, 여전히 상수 시간에 병합할 수 있고 트리의 루트(꼬리였던 노드)를 ID로 그대로 사용할 수 있다.
- 이 아이디어를 발전시키면 각 집합을 트리로 표현하는 효율적인 구현으로 이어지며, 이 경우 모든 연산의 상환(amortized) 실행 시간이 거의 상수에 가까워진다.

## 예시
- 세 집합 {2,3,...}, {5}, {1,...}이 있을 때 `smallest` 배열은 각 원소 위치에 해당 집합의 최소 원소 값을 저장한다(예: 첫 집합의 최소 원소가 2라면, 그 집합에 속한 모든 원소의 `smallest` 값이 2).
- 리스트 기반에서 두 집합 {..., 7}과 {..., 8}(각각 ID가 7, 8)을 `Union`할 때 한 리스트를 다른 리스트에 이어붙이면 병합된 리스트의 ID는 8로 자동 통일된다.

## 요약
- 배열(smallest) 기반: `MakeSet`, `Find` O(1), `Union` O(n) — `Union`이 병목.
- 리스트 기반: `Union` O(1)이지만 `Find`가 최악의 경우 O(n)이며 시간이 지날수록 리스트가 길어져 더 느려진다.
- 리스트 대신 한쪽을 다른 쪽 루트에 매다는 트리 구조를 사용하면, 상수 시간 병합과 잘 정의된 ID를 유지하면서도 리스트의 단점을 피할 수 있는 실마리를 얻는다.
