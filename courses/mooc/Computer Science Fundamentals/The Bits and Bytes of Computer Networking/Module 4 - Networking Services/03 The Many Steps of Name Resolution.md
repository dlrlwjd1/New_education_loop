# The Many Steps of Name Resolution

## 개요

- **이름 해석(name resolution)** = DNS로 도메인 이름을 IP 주소로 바꾸는 과정.
- **5가지 DNS 서버 종류**와 **재귀 조회(recursive resolution)** 의 전체 경로, 그리고 **TTL**을 다룬다.
- 핵심: **루트 → TLD → 권한 네임서버**로 내려가는 **엄격한 계층 구조**가 인터넷의 안정성을 지킨다.

## 내용

### DNS 서버는 반드시 설정해야 하는 네 번째 항목

현대 네트워크에서 호스트가 정상 동작하려면 설정해야 하는 것:

1. **IP 주소**
2. **서브넷 마스크**
3. **게이트웨이**
4. **DNS 서버** ← 네 번째이자 마지막

- MAC 주소는 하드웨어에 하드코딩되어 있어 설정 대상이 아니다.
- **DNS나 DNS 서버 설정 없이도 컴퓨터는 잘 동작한다.** 다만 **그 컴퓨터를 쓰는 사람에게 몹시 불편해질 뿐**이다.

### 5가지 DNS 서버 종류

1. **캐싱 네임서버 (caching name server)**
2. **재귀 네임서버 (recursive name server)**
3. **루트 네임서버 (root name server)**
4. **TLD 네임서버 (TLD name server)**
5. **권한 네임서버 (authoritative name server)**

> **주어진 DNS 서버 하나가 이 역할들을 동시에 여러 개 수행할 수 있다.**

### 캐싱·재귀 네임서버

- 보통 **ISP나 로컬 네트워크가 제공**한다.
- 목적은 **도메인 이름 조회 결과를 일정 시간 저장**하는 것이다.
- 완전한 도메인 해석에는 단계가 많으므로, **새 TCP 연결이 맺힐 때마다 이 과정이 반복되지 않도록** 캐싱 네임서버를 둔다.
- **대부분의 캐싱 네임서버는 재귀 네임서버이기도 하다.** 재귀 네임서버는 **완전한 DNS 해석 요청을 수행**한다.
- 대개 로컬 네임서버가 두 역할을 다 하지만, **둘 중 하나만 하는 것도 가능하다.**

#### 캐싱 동작 예시

1. 나와 친구가 같은 네트워크에 있고 둘 다 facebook.com에 접속하려 한다. **같은 네임서버가 설정**돼 있다.
2. 친구의 컴퓨터가 네임서버에게 `www.facebook.com`의 IP를 묻는다. 네임서버는 **모른다.**
3. 네임서버가 **완전한 재귀 해석**을 수행해 올바른 IP를 알아낸다.
4. 이 IP는 **친구의 컴퓨터에 전달되는 동시에 로컬 캐시에 저장**된다.
5. 몇 분 뒤 내가 같은 주소를 입력한다. 내 컴퓨터가 **같은 로컬 네임서버**에게 묻는다.
6. 방금 조회됐으므로 네임서버는 **저장된 IP를 전체 조회 없이 바로 돌려준다.**

### TTL (Time To Live)

- **전역 DNS 시스템의 모든 도메인 이름에는 TTL이 있다.**
- **도메인 소유자가 설정할 수 있는 초 단위 값**이며, **네임서버가 항목을 캐시해도 되는 시간**을 뜻한다. 그 시간이 지나면 버리고 다시 완전한 해석을 수행해야 한다.
- **몇 년 전에는 TTL이 아주 길어 하루 이상인 경우도 흔했다.** 인터넷에서 쓸 수 있는 대역폭이 훨씬 적었기 때문에, 관리자들은 계속 전체 DNS 조회를 하며 대역폭을 낭비하고 싶어 하지 않았다.
- **인터넷이 커지고 빨라지면서** 대부분 도메인의 TTL은 **몇 분에서 몇 시간** 수준으로 내려왔다. 그래도 **여전히 매우 긴 TTL을 가진 도메인을 만날 수 있다.**

> **DNS 레코드를 변경했을 때 그 변경이 인터넷 전체에 알려지기까지 최대 TTL만큼 걸릴 수 있다.**

### 완전한 재귀 해석의 경로

#### 1. 루트 네임서버

- 첫 단계는 **항상 루트 네임서버에 연락하는 것**이다.
- **총 13개의 루트 네임서버**가 있으며, 질의를 **알맞은 TLD 네임서버로 안내하는 책임**을 진다.
- 과거에는 이 13개가 아주 특정한 지리적 지역에 분산돼 있었지만, **오늘날에는 대부분 애니캐스트(anycast)를 통해 전 세계에 분산**돼 있다.

> **애니캐스트(anycast)** = 위치, 혼잡도, 링크 상태 같은 요인에 따라 트래픽을 **서로 다른 목적지로 라우팅**하는 기법. 특정 IP로 데이터그램을 보내도 **여러 실제 목적지 중 하나로** 라우팅될 수 있다.

- 그래서 **더 이상 물리적으로 13대만 있는 것이 아니다.** **루트 이름 조회를 서비스로 제공하는 13개의 권위체**로 생각하는 편이 낫다.
- 루트 서버는 **어느 TLD 네임서버에 질의해야 하는지**로 응답한다.

#### 2. TLD 네임서버

- **TLD = top-level domain**, 계층적 DNS 이름 해석 체계의 최상단을 나타낸다.
- **도메인 이름의 마지막 부분**이다. `www.facebook.com`에서는 **`.com`** 부분.
- **존재하는 각 TLD마다 TLD 네임서버가 있다.** 루트 서버와 마찬가지로 **물리적으로 한 대라는 뜻은 아니며**, 각 TLD를 담당하는 **애니캐스트로 접근 가능한 서버들의 전 지구적 분산**일 가능성이 높다.
- TLD 네임서버도 리다이렉트로 응답한다. 이번에는 **어느 권한 네임서버에 연락해야 하는지** 알려 준다.

#### 3. 권한 네임서버

- **도메인 이름의 마지막 두 부분**을 책임진다. **하나의 조직이 DNS 조회를 책임질 수 있는 해상도**다.
- `www.weather.com`이면 TLD 네임서버가 **`weather.com`의 권한 서버**를 가리키고, 그 서버는 사이트를 운영하는 **The Weather Channel 조직이 통제**할 가능성이 높다.
- 마침내 이 권한 서버가 **실제 서버의 IP**를 제공한다.

### 왜 이 엄격한 계층이 중요한가

- **인터넷의 안정성에 매우 중요하다.**
- 모든 완전한 DNS 해석이 **엄격하게 규제되고 통제되는 조회 절차**를 거치게 하는 것이, **악의적인 당사자가 트래픽을 리다이렉트하는 것을 막는 최선의 방법**이다.
- **컴퓨터는 알려 준 IP로 아무 의심 없이 트래픽을 보낸다.** 그래서 **신뢰받는 주체들이 통제하는 계층 체계**를 씀으로써 DNS 응답의 정확성을 더 잘 보장할 수 있다.

### 로컬 캐시가 중요한 이유

- 단계가 이렇게 많으므로, **모든 TCP 연결마다 전체 조회 경로가 반복되지 않도록** 로컬 네임서버의 캐싱을 신뢰하는 것이다.
- 실제로 **휴대폰부터 데스크톱까지 로컬 컴퓨터 자체도 자기만의 임시 DNS 캐시**를 갖는다. 그래야 **모든 TCP 연결마다 로컬 네임서버를 귀찮게 하지 않아도** 된다.

## 예시

```
[내 컴퓨터] → [로컬 캐싱/재귀 네임서버]
                     │ (캐시에 없으면)
                     ├→ [루트 네임서버]      → ".com은 저 TLD 서버에 물어봐"
                     ├→ [TLD 네임서버(.com)] → "weather.com은 저 권한 서버에 물어봐"
                     └→ [권한 네임서버]      → "184.29.131.121"
                     │
                (캐시에 저장, TTL 동안 유지)
                     ↓
              [내 컴퓨터] 응답 수신
```

## 요약

- 호스트 설정 4종은 IP, 서브넷 마스크, 게이트웨이, DNS 서버다.
- DNS 서버 종류는 캐싱·재귀·루트·TLD·권한 5가지이며 한 서버가 여러 역할을 겸할 수 있다.
- 재귀 해석은 루트 → TLD → 권한 순으로 리다이렉트를 따라간다.
- 13개 루트 서버는 애니캐스트로 전 세계에 분산된 "13개의 권위체"다.
- TTL은 캐시 유지 시간이며, 레코드 변경이 전파되기까지 최대 TTL만큼 걸린다.
- 엄격한 계층 구조가 트래픽 하이재킹을 막는 안전장치다.
