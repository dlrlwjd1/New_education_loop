# Connection-oriented and Connectionless Protocols

## 개요

- **연결 지향(connection-oriented)** 프로토콜 = 연결을 수립하고 그것으로 **모든 데이터가 제대로 전송됐는지 보장**하는 것. 대표는 **TCP**.
- **비연결(connectionless)** 프로토콜 = 연결도 확인 응답도 없이 그냥 보내는 것. 대표는 **UDP**.
- 핵심 판단 기준: **오버헤드를 감수하고 확실성을 살 것인가.**

## 내용

### 연결 지향 프로토콜

- 전송 계층에서 연결이 있다는 것은 **보낸 모든 데이터 세그먼트가 확인 응답된다**는 뜻이다.
- 그래서 연결의 양쪽 끝은 **어떤 데이터가 확실히 전달됐고 어떤 것이 아닌지 항상 안다.**

### 왜 필요한가 — 무수히 많은 실패 가능성

- 인터넷은 방대하고 붐비는 곳이라 A에서 B로 데이터를 옮기는 동안 잘못될 일이 많다.
- **단 한 비트만 제대로 전송되지 않아도** 수신 측에서 데이터를 알아볼 수 없는 경우가 흔하다. 가장 낮은 수준에서 **비트는 특정 전압 범위의 전기 신호**일 뿐이다.
- 회선 오류 말고도 이유는 많다.
  - **혼잡(congestion)** 때문에 라우터가 더 중요한 트래픽을 위해 내 트래픽을 버릴 수 있다.
  - **공사업체가 두 ISP를 잇는 광케이블을 끊어 버릴** 수도 있다.

### 재전송은 전송 계층의 몫이다

- IP와 이더넷 같은 하위 계층도 **체크섬으로 데이터가 올바른지 확인**한다.
- 그러나 **검사에 실패한 데이터를 재전송하려는 시도는 하지 않는다.**
- **IP나 이더넷 수준에서는 체크섬이 맞지 않으면 그 데이터를 그냥 버린다.**
- **언제 재전송할지 결정하는 것은 전적으로 TCP의 몫**이다.
- TCP는 보내는 모든 데이터에 대해 ACK를 기대하므로, **무엇이 성공적으로 전달됐는지 가장 잘 아는 위치**에 있고 필요하면 세그먼트를 재전송하기로 결정할 수 있다.

### 시퀀스 번호가 다시 중요해지는 이유

- TCP는 대체로 세그먼트를 **순서대로 보내지만, 항상 순서대로 도착하지는 않는다.**
- 하위 계층 오류로 일부가 재전송됐다면 **약간 순서가 어긋나 도착해도 상관없다.**
- **시퀀스 번호 덕분에 모든 데이터를 올바른 순서로 다시 조립**할 수 있기 때문이다.

### 오버헤드

연결 지향 프로토콜에는 오버헤드가 많다.

- 연결을 **수립**해야 하고,
- **끊임없는 확인 응답 스트림**을 보내야 하며,
- 끝에서 연결을 **해제**해야 한다.

→ 전부 추가 트래픽이다. 중요한 트래픽이지만, **데이터가 반드시 목적지에 도달해야만 하는 경우에만 값어치가 있다.**

### 비연결 프로토콜 — UDP

- 가장 흔한 것이 **UDP(User Datagram Protocol)** 다.
- TCP와 달리 **연결에 의존하지 않으며, 확인 응답이라는 개념 자체를 지원하지 않는다.**
- **목적지 포트만 설정하고 패킷을 보내면 끝**이다.
- **아주 중요하지는 않은 메시지**에 유용하다.

## 예시

**스트리밍 비디오**가 UDP의 좋은 예다.

- UDP 데이터그램 하나가 **비디오의 한 프레임**이라고 상상해 보자.
- 최고의 시청 경험을 위해서는 모든 프레임이 도착하길 바라겠지만, **몇 개가 도중에 사라져도 크게 상관없다.** 아주 많은 프레임을 잃지 않는 한 비디오는 여전히 볼 만하다.
- **TCP의 오버헤드를 전부 없앰으로써 오히려 더 높은 품질의 비디오를 보낼 수 있다.** 연결 수립과 확인 응답에 쓰일 대역폭을 **실제 데이터 전송에 더 많이 남겨 두기** 때문이다.

## 요약

- TCP는 연결과 확인 응답으로 전달을 보장하는 연결 지향 프로토콜이다.
- IP·이더넷은 손상 데이터를 버리기만 하고, 재전송 판단은 TCP가 한다.
- 시퀀스 번호 덕분에 순서가 어긋나 도착해도 재조립할 수 있다.
- UDP는 연결도 ACK도 없어 오버헤드가 없으며, 일부 손실이 허용되는 스트리밍 같은 용도에 적합하다.
