# 3.1.5 – UML Deployment Diagram

## 개요

- 배포 다이어그램(deployment diagram)은 소프트웨어를 실제로 실행 가능하게 만드는 데 필요한 파일·실행 파일·환경, 즉 배포 세부 사항을 시각화한다.
- 명세 수준(specification level)과 인스턴스 수준(instance level) 두 가지 유형이 있다.
- 노드(node), 아티팩트(artifact), 통신 경로, 배포·현시(manifestation) 관계 등의 표기법을 비디오 게임 예시로 설명한다.

## 내용

### 배포와 배포 다이어그램

소프트웨어 릴리스는 코드 묶음 그 이상이다. 별도의 라이브러리, 실행 파일(executable), 보통은 설치 프로그램(installer), 설정 파일(configuration file) 등 여러 조각으로 이루어진다. 소프트웨어를 실행 가능하게 만들려면 완전한 배포에 관여하는 모든 파일과 실행 파일, 그리고 그 조각들이 놓이는 환경에 대한 그림이 필요하다. 이런 배포 세부 사항을 시각화하는 것이 UML 배포 다이어그램이다.

배포 환경 또는 배포 대상(deployment target)은 특정 하드웨어 장치까지 명시하는 매우 구체적인 것일 수도 있고, 지원 운영체제 수준의 상당히 일반적인 것일 수도 있으며, 그에 따라 다이어그램의 세부 수준이 달라진다. 예를 들어 Linux나 Mac OS용으로 개발된 비디오 게임은 Windows용과 다소 다르고, 게임 콘솔용과는 더 크게 다르다.

### 아티팩트(artifact)

아티팩트는 개발 프로세스의 **물리적 결과물**을 가리키는 용어다. 비디오 게임의 아티팩트 예로는 게임을 실행하는 실행 파일, 게임을 설치하는 인스톨러, 오디오를 관리하는 오디오 라이브러리, 멀티미디어 에셋 등이 있다. 아티팩트는 시스템 생산의 산출물로 만들어지며, 마지막에 조립되는 최종 조각들이다.

### 두 가지 유형

- **명세 수준 다이어그램(specification level diagram)**: 특정 머신 이름 같은 구체적 세부를 참조하지 않고 아티팩트와 배포 대상의 개요를 제공한다. 배포의 구체적 사항보다 일반적 개요에 집중한다.
- **인스턴스 수준 다이어그램(instance level diagram)**: 훨씬 구체적인 접근으로, 특정 아티팩트를 특정 배포 대상에 매핑할 수 있다. 특히 구체적인 머신과 하드웨어 장치를 식별할 수 있으며, 개발(development)·스테이징(staging)·릴리스(release) 빌드 간 배포 차이를 강조할 때 가장 흔히 사용된다.

### 표기법과 관계

- **노드(node)**: 실행 가능한 아티팩트를 담는 배포 대상으로, 배포 다이어그램의 가장 중요한 요소 중 하나다. **3D 상자** 모양으로 그린다. 하드웨어 장치도 노드와 같은 방식으로 표시하되 `device` 태그로 다른 유형의 노드와 구별한다. 예시의 MacBook Pro 노드는 명세 수준 다이어그램의 일부가 될 수 있다.
- **통신 경로(communication path)**: 배포 대상 사이의 관계로, 두 노드 사이에 통신 경로가 있음을 보여준다. 소프트웨어 실행 환경(execution environment)인 노드들 사이에서는 이 관계가 보통 특정 통신 프로토콜(communication protocol)을 명시한다.
- **배포(deployment)**: 아티팩트가 노드에 배포되면 아티팩트를 노드 상자 안에 그려서 이 의존성을 표현한다. 이는 그 아티팩트가 해당 배포 대상 없이는 기능할 수 없음을 의미하기도 한다.
- **현시(manifestation)**: `manifests` 관계로 표시하며, 아티팩트가 소프트웨어 컴포넌트의 물리적 실현(physical realization)임을 나타낸다. 예: Player.class 파일은 플레이어의 모든 기능을 담은 캡슐화 단위인 Player 컴포넌트를 현시한다. Player.class는 Player 컴포넌트를 위한 Player 자바 파일을 컴파일한 결과다.

### 완전한 다이어그램 작성 요령

- 배포 대상에는 뚜렷한 **계층(hierarchy)** 이 있으며, 직접 그릴 때 이 계층을 완성하는 것이 중요하다. 배포 정보의 최상위 수준(애플리케이션 이름)에서 시작해 장치(device), 운영체제(operating system)까지 내려간다.
- 예시 다이어그램에는 애플리케이션, 장치, 운영체제, 실행 환경이 나열되어 있어, 각 노드를 보면 애플리케이션 실행에 어떤 환경이 필요한지 정확히 알 수 있다.
- 아티팩트는 시스템에서 아주 높은 수준의 것들만 보여준다. 배포 다이어그램에는 많은 컴포넌트가 필요치 않은 경우가 많으므로, 보는 사람이 혼란스럽지 않도록 **가장 중요한 아티팩트들만 선별**한다. 그래서 예시에서는 Player, Level, Score 같은 모든 컴포넌트의 아티팩트 대신 게임 실행 파일 하나만 보여준다. 이 실행 파일이 게임 컴포넌트를 현시(물리적으로 실현)하여 게임의 기능을 구동한다.
- 서드파티 아티팩트는 `library` 태그로 표기한다. 예시에서 오디오 라이브러리가 이렇게 표시된다.

### 유용성

배포 다이어그램은 애플리케이션 실행에 필요한 아티팩트, 라이브러리, 주요 컴포넌트, 머신, 장치를 고수준에서 보여준다. 소프트웨어를 배포·실행하는 데 필요한 파일과 실행 파일을 추적하는 데 쓸 수 있다. 사용하는 배포 머신에 특화된 인스턴스 수준일 수도, 다양한 실행 환경을 아우르는 일반적 수준일 수도 있다. 구현을 마친 뒤 마지막 단계인 배포는 까다로울 수 있는데, 배포에 대한 좋은 계획과 배포의 일관성이 없으면 시스템 장애(system failure)가 나기 쉽다.

## 예시

- **비디오 게임 아티팩트**: 게임 실행 파일, 인스톨러, 오디오 라이브러리, 멀티미디어 에셋.
- **현시 관계**: `Player.class` ──«manifests»──▶ `Player 컴포넌트` (Player.java를 컴파일한 물리적 실현).
- **배포 대상 계층(텍스트로)**:

```text
┌─ 애플리케이션(게임) ────────────────────────┐
│ ┌─ «device» 장치 (예: MacBook Pro) ────────┐ │
│ │ ┌─ 운영체제 ─────────────────────────┐ │ │
│ │ │ ┌─ 실행 환경 ────────────────────┐ │ │ │
│ │ │ │  게임 실행 파일 (아티팩트)      │ │ │ │
│ │ │ │  «library» 오디오 라이브러리    │ │ │ │
│ │ │ └────────────────────────────────┘ │ │ │
│ │ └────────────────────────────────────┘ │ │
│ └──────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

## 요약

- 배포 다이어그램은 소프트웨어 배포에 필요한 아티팩트와 배포 대상, 그 환경을 시각화한다.
- 아티팩트는 개발 프로세스의 물리적 결과물(실행 파일, 인스톨러, 라이브러리, 에셋 등)이다.
- 명세 수준은 일반적 개요, 인스턴스 수준은 특정 머신·장치까지 매핑하며 개발/스테이징/릴리스 빌드 차이를 보여주는 데 흔히 쓰인다.
- 노드는 3D 상자로 그리고 하드웨어는 `device` 태그, 서드파티 아티팩트는 `library` 태그로 표기한다.
- 노드 안에 아티팩트를 그리면 배포 의존성을, `manifests`는 아티팩트가 컴포넌트의 물리적 실현임을 나타낸다.
- 애플리케이션 → 장치 → 운영체제 → 실행 환경의 계층을 완성하고, 아티팩트는 가장 중요한 것만 선별한다.
