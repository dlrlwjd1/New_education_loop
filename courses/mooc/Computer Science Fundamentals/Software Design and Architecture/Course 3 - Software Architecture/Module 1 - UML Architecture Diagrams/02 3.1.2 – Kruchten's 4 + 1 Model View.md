# 3.1.2 – Kruchten's 4 + 1 Model View

## 개요

- 단일 관점만으로는 시스템의 전체 행동을 포착하기 어렵기 때문에 여러 관점(view)이 필요하다.
- Philippe Kruchten의 4+1 뷰 모델(4+1 view model)은 논리 뷰(logical view), 프로세스 뷰(process view), 개발 뷰(development view), 물리 뷰(physical view)에 시나리오(scenarios)를 더해 아키텍처를 이해하는 방법이다.
- 각 뷰는 서로 다른 관심사를 다루며, 필요에 따라 뷰를 생략하거나 합칠 수 있는 유연한 모델이다.

## 내용

### 왜 여러 관점이 필요한가

하나의 관점만으로 시스템의 완전한 행동을 포착하기는 어렵다. 소프트웨어가 목표를 달성하는지 볼 때 코드만 보면 시스템의 물리적 구성요소를 놓칠 수 있고, 물리적 구성요소만 보면 소프트웨어 관리 관점을 놓칠 수 있다. 클라이언트는 소프트웨어의 목적(purpose)을 갖고 있고, 그 목적 외의 구현 방식은 엔지니어가 결정한다. 소프트웨어의 성공을 평가하려면 여러 방식으로 판단할 수 있는 특성들이 필요하다.

### 네 가지 뷰

**논리 뷰(logical view)**
- 시스템의 기능성(functionality)과 시스템 안의 객체(object)에 초점을 둔다. 주로 기능 요구사항(functional requirement) 달성을 다루며, 맥락은 최종 사용자에게 제공되어야 하는 서비스다.
- 실무에서는 시스템의 객체들을 다루며, 이 객체들로부터 UML 클래스 다이어그램(class diagram)을 만들어 논리 뷰를 표현한다.
- 클래스 다이어그램은 문제와 결과 시스템의 어휘(vocabulary)를 확립한다. 모든 클래스와 그 속성(attribute)·행동(behavior)을 정의하면 핵심 추상화와 용어를 이해하기 쉬워진다.
- 데이터베이스 스킴(database scheme)을 명세할 때도 유용하다. 클래스 다이어그램을 펼쳐 놓으면 클래스들이 어떻게 상호작용하는지, 데이터가 데이터베이스에서 어떻게 관계 맺어야 하는지 보기 쉽다.

**프로세스 뷰(process view)**
- 시스템이 갖춰야 할 품질을 명시하는 비기능 요구사항(nonfunctional requirement) 달성에 초점을 둔다. 성능(performance)과 가용성(availability) 같은 품질 속성(quality attribute)이 포함된다.
- 논리 뷰의 객체들에 대응하는 프로세스를 제시한다. 예를 들어 객체들의 실행 순서, 논리 뷰에서 정의된 메서드 호출을 올바른 순서로 보여준다. 프로세스 뷰는 메서드가 올바르게 구현되었다고 가정하고, 어떻게·어떤 순서로 실행할지만 다룬다.
- 비동기(asynchronous)·동시(concurrent) 행동도 기술한다.
- UML 시퀀스 다이어그램(sequence diagram)은 메서드가 어떻게·어떤 순서로 실행되는지 보여주는 데 유용하고, UML 액티비티 다이어그램(activity diagram)은 시스템의 프로세스나 활동을 나타낼 수 있다.

**개발 뷰(development view)**
- 계층적 소프트웨어 구조(hierarchical software structure)를 기술한다.
- 프로그래밍 언어, 라이브러리, 툴셋 같은 요소도 고려한다. 선택한 프로그래밍 언어는 시스템 구조와 개발 제약에 큰 영향을 미친다.
- 본질적으로 소프트웨어 개발의 세부 사항과 이를 지원하기 위해 필요한 것들을 다룬다. 코드 외에도 일정(scheduling), 예산(budget), 작업 배정(work assignment) 같은 관리 세부 사항을 포함하며, 프로젝트 관리(project management)가 개발 뷰의 핵심이다.

**물리 뷰(physical view)**
- 논리·프로세스·개발 뷰의 요소들을 시스템 실행을 위한 여러 노드(node), 즉 하드웨어에 어떻게 매핑할지 다룬다. 예를 들어 데이터베이스는 한 서버에, 웹 클라이언트는 다른 서버들에 호스팅하는 식의 배치 계획이다.
- UML 배포 다이어그램(deployment diagram)으로 시스템 조각들이 하드웨어나 실행 환경(execution environment)에 어떻게 배포되는지 표현할 수 있다.

### +1: 시나리오(scenarios)

네 뷰 모두 공통 목적은 클라이언트가 원하는 능력(capability)이다. 시스템이 사용자를 위해 무엇을 달성해야 하는지 모르면 뷰를 상세화하기 어렵다. 그래서 최종 사용자가 요구하는 유스 케이스(use case)나 태스크인 시나리오가 필요하다.

- 시나리오는 시스템의 유스 케이스·사용자 태스크와 정렬되며, 나머지 네 뷰가 어떻게 함께 작동하는지 보여준다.
- 각 시나리오에는 객체와 프로세스 간 상호작용의 순서를 기술하는 스크립트가 있다.
- 채팅 메시징 예에서는 chat box, chat input 객체가 receive message, send message 프로세스와 상호작용하는 식이다.

논리·프로세스·개발·물리 네 뷰와 시나리오가 합쳐져 Philippe Kruchten이 산업 소프트웨어 프로젝트에서 오랜 경험 끝에 제안한 **4+1 뷰 모델**이 된다.

### 모델의 유연성

- 여러 뷰는 서로 완전히 독립적이지 않으며, 어떤 뷰의 요소는 다른 뷰와 연결된다.
- 모든 소프트웨어 아키텍처를 4+1 뷰 모델로 문서화할 필요는 없다. 쓸모없다고 판단되는 뷰는 생략할 수 있다. 예를 들어 논리 뷰와 개발 뷰가 사실상 같을 만큼 비슷하다면 함께 기술해도 된다.
- 4+1 뷰 모델은 많은 상황에 맞게 변형할 수 있으며, 복잡한 문제를 여러 관점에서 볼 수 있다는 다재다능함이 이 접근의 강점이다.

## 예시

- **채팅 메시징 시나리오**: chat box와 chat input 객체(논리 뷰)가 receive message와 send message 프로세스(프로세스 뷰)와 상호작용하는 스크립트로 시나리오를 기술한다.
- **물리 뷰 배치 예**: 데이터베이스를 호스팅하는 서버 하나와 웹 클라이언트를 호스팅하는 다른 서버들을 두고 이들의 상호작용과 배포를 계획한다.

## 요약

- 단일 관점으로는 시스템 전체를 포착할 수 없어 Kruchten의 4+1 뷰 모델이 제안되었다.
- 논리 뷰는 기능 요구사항과 객체(클래스 다이어그램), 프로세스 뷰는 비기능 요구사항과 실행 순서·동시성(시퀀스/액티비티 다이어그램)을 다룬다.
- 개발 뷰는 계층적 소프트웨어 구조와 언어·라이브러리·프로젝트 관리를, 물리 뷰는 요소들의 하드웨어 매핑(배포 다이어그램)을 다룬다.
- 시나리오(유스 케이스)가 "+1"로서 네 뷰가 함께 작동하는 방식을 보여준다.
- 뷰들은 완전히 독립적이지 않으며, 불필요한 뷰는 생략하거나 합칠 수 있다.
