# 3.1.4 – UML Package Diagram

## 개요

- 패키지(package)는 관련 있는 소프트웨어 요소들을 묶고, 그 요소들을 위한 네임스페이스(namespace)를 정의한다.
- 패키지 다이어그램(package diagram)은 패키지들과 그 사이의 의존성(dependency)을 보여주어 시스템을 고수준에서 조망하게 해준다.
- 요소 표기(중첩·포함 표기·이름 나열), 가시성(public/private), 임포트(import/access), 병합(merge), uses 관계 등을 비디오 게임 예시로 설명한다.

## 내용

### 패키지와 네임스페이스

객체지향 소프트웨어에서는 상호작용하는 클래스들을 정의하는데, 여러 클래스가 어떤 식으로든 관련되어 있을 때가 있다. 예를 들어 비디오 게임에서 플레이어의 이동(movement), 전투(combat), 대화(dialogue)를 처리하는 클래스들은 모두 플레이어와 관련된다.

- 패키지는 데이터, 클래스, 사용자 태스크 등으로 관련된 소프트웨어 요소들을 하나로 묶는다.
- 패키지는 포함하는 요소들의 **네임스페이스**를 정의한다. 즉 패키지는 이름을 가지며, 소프트웨어의 이름 있는 요소들을 별도의 스코프(scope)로 조직할 수 있다.
- 요소는 자신의 이름과 소속 패키지 이름에 기반한 **완전 수식 이름(fully qualified name)** 으로 시스템 안에서 고유하게 식별된다.

패키지 다이어그램은 패키지와 그들 간 의존성을 보여준다. 완성된 시스템을 관련된 패키지화 가능 요소(packageable element) — 데이터, 클래스, 심지어 다른 패키지 — 로 조직하는 데 사용하며, 시스템을 고수준에서 보고 싶을 때 유용하다.

### 패키지 표기법

- 패키지는 **탭 달린 폴더(tabbed folder)** 모양으로 그린다. 보여줄 요소가 없으면 패키지 이름을 폴더 가운데에 쓴다.
- 요소를 보여주는 방법:
  1. 요소를 폴더 안에 **중첩(nest)** — 예: Player 패키지 안에 Movement 인터페이스.
  2. 포함 표기(containment notation)로 패키지가 요소를 포함함을 표시 — 포함된 요소는 폴더 아래에 그린다. 이 관계는 전체 패키지가 요소를 부분으로 갖는 **컴포지션(composition)** 이다.
  3. 포함 요소들의 **이름을 나열** — 이름은 부분 수식(partially qualified)될 수 있지만 패키지 안에서 고유해야 한다.
- 요소 이름 앞의 **더하기(+)/빼기(−) 기호**로 public/private을 표시한다. public 요소는 패키지 밖에서 완전 수식 이름으로 접근할 수 있다. 예시에서는 비디오 게임의 Audio만 밖에서 사용 가능하고 Levels, Accounts, Players는 패키지 밖에서 접근할 수 없다.

### 패키지 간 관계

- **요소 임포트**: 한 패키지가 다른 패키지의 요소를 임포트할 수 있다. 예: Level 패키지가 Player 패키지의 Location을 임포트하면 Location 이름이 Level 네임스페이스로 들어와 Level 안 요소들이 편하게 사용한다. `import` 태그는 **public 임포트**로, 이 이름이 Level을 통해 추가 임포트에도 보인다. 반면 Level이 Player의 Data를 임포트하며 `access` 태그가 붙으면 **private 임포트**로, 그 이름은 Level 네임스페이스 안 요소들에게만 보이고 밖으로는 보이지 않는다.
- **패키지 전체 임포트**: 패키지가 다른 패키지의 전체 내용을 임포트할 수 있다. 예: User Interface 패키지가 Player 패키지를 `import` 태그로 public 임포트(Player의 보이는 요소 이름들을 public으로 임포트)하고, Buttons 패키지를 `access` 태그로 private 임포트(보이는 이름들을 private으로 임포트)한다. User Interface 네임스페이스가 이 이름들을 밖에 더 알릴 필요가 없기 때문이다.
- **병합(merge)**: 두 패키지나 개념을 하나로 합쳐야 할 때 사용한다. 같은 개념의 서로 다른 정의를 제공할 수 있게 하는 일반화(generalization)의 활용이다. 예: 비디오 게임에서 Vendor(상인)와 Quest-giver(퀘스트 제공자)는 모두 아이템을 제공하는 논플레이어 캐릭터이므로, 기능은 비슷하지만 정의가 약간 다른 둘을 Non-player Character 패키지로 병합할 수 있다.

### 전체 예시와 uses 관계

간단한 비디오 게임 시스템의 완전한 패키지 다이어그램에는 Player, Level, Score, 플레이어 습관에 대한 Analytics 패키지가 있다.

- 이 패키지들은 대부분 서로 상호작용하므로 서로를 public 임포트할 수 있다.
- Analytics는 데이터 저장을 위해 온라인 서버와의 통신이 필요하므로 다른 패키지들과 달리 **private 임포트**로 사용된다.
- Bonus Level은 특별히 일반 Level과 **uses 관계**를 갖는다. uses 관계는 Bonus Level의 완전한 구현에 일반 Level이 필요함을 의미한다. Level의 정의가 없으면 Bonus Level의 정의도 있을 수 없다.

### 유용성

- 시스템, 특히 네임스페이스와 이름, "누가 누구를 아는지"를 더 크게 조망할 수 있다.
- 서로 다른 네임스페이스와 그 목적을 훨씬 쉽게 시각화하고, 관련 클래스 그룹들이 어떻게 상호작용하는지 감을 잡을 수 있다.
- 개발의 어느 단계에서든 만들 수 있으며, 소프트웨어 최신 버전에 맞춰 적응하고 변한다.
- 관련 요소 그룹 간 의존성과 관계를 보는 기술 설계자(technical designer)에게 매우 유용하다.
- 시스템을 시각적으로 보여주면 결함(flaw)과 비일관성(inconsistency)을 발견하기 훨씬 쉬워진다.

## 예시

- **비디오 게임 패키지 구성(텍스트로)**:

```text
┌─ Player ──────────┐      ┌─ Level ───────────┐
│  Movement          │      │                   │
│  Combat, Dialogue  │◄─────│ «import» Location │  (public 임포트)
│                    │◄─────│ «access» Data     │  (private 임포트)
└────────────────────┘      └───────────────────┘

User Interface ──«import»──▶ Player    (패키지 전체 public 임포트)
User Interface ──«access»──▶ Buttons   (패키지 전체 private 임포트)

Vendor + Quest-giver ──«merge»──▶ Non-player Character  (병합)

Bonus Level ──«uses»──▶ Level  (Level 정의 없이는 Bonus Level 정의 불가)
```

- **가시성 표기 예**: `+Audio`(패키지 밖에서 접근 가능), `-Levels`, `-Accounts`, `-Players`(패키지 밖에서 접근 불가).

## 요약

- 패키지는 관련 요소를 묶고 네임스페이스를 정의하며, 요소는 완전 수식 이름으로 고유하게 식별된다.
- 패키지는 탭 달린 폴더로 그리고, 요소는 중첩·포함 표기·이름 나열로 보여주며 +/−로 public/private을 표시한다.
- `import` 태그는 public 임포트(이름이 밖으로도 보임), `access` 태그는 private 임포트(해당 네임스페이스 안에서만 보임)다.
- 병합은 비슷하지만 정의가 다른 두 개념을 하나의 패키지로 합치는 일반화의 활용이다.
- uses 관계는 한 패키지의 완전한 구현이 다른 패키지를 필요로 함을 나타낸다.
- 패키지 다이어그램은 네임스페이스 구조와 의존성을 시각화해 결함과 비일관성을 찾는 데 도움을 준다.
