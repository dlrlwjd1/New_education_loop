# 3.2.3 – Databases

## 개요

- 현대 소프트웨어 시스템은 고립되어 동작하는 경우가 드물며, 여러 컴포넌트 간에 정보를 공유해야 한다.
- 데이터 중심 아키텍처(data centric architecture)는 중앙 데이터(central data) 컴포넌트와 데이터 접근자(data accessor) 컴포넌트로 구성되어 데이터 저장과 공유를 해결한다.
- 유지보수성(maintainability), 재사용성(re-usability), 확장성(scalability)을 높이지만 중앙 데이터 컴포넌트에 대한 강한 의존이라는 대가가 있다.

## 내용

### 해결해야 할 문제

- 대기업에서는 부서 간 일상 업무를 위해 서로 다른 시스템이 통신해야 한다. 예: 직원과 관리자는 타임시트 작성·승인 시스템을 쓰고, 급여·회계 부서는 타임시트 처리와 급여 지급에 다른 시스템을 쓴다.
- **문제 1 — 상태의 휘발성**: 컴포넌트의 상태는 실행 중에만 유지된다. 컴포넌트를 멈추면 생성된 객체와 처리된 데이터가 사라진다. 파일로 저장하면 해결되지만 파일은 컴포넌트 간 데이터 전송에 좋지 않다. 파일 형식, 모든 컴포넌트로의 배포를 신경 써야 하고, 컴포넌트가 파일의 모든 데이터를 필요로 하지 않을 수도 있다.
- **문제 2 — 상태 공유**: 여러 컴포넌트 간에 데이터 상태를 전달해야 한다.
- 데이터베이스(database) 같은 공유 데이터 저장 방법을 시스템 설계에 통합하는 데이터 중심 아키텍처가 두 문제를 모두 해결한다.

### 구조: 중앙 데이터와 데이터 접근자

- **중앙 데이터(central data)**: 연결된 모든 컴포넌트에 데이터를 저장하고 제공(serve)하는 컴포넌트.
- **데이터 접근자(data accessor)**: 중앙 데이터 컴포넌트에 연결하여 저장된 정보에 대해 쿼리(query)와 트랜잭션(transaction)을 수행하는 컴포넌트.
- 데이터 접근자들은 서로 분리되어 있고 오직 중앙 데이터 컴포넌트하고만 통신한다. 중앙 데이터는 시스템의 현재 상태에서 원하는 정보를 저장하고 요청에 따라 제공함으로써 데이터 공유를 촉진한다.

### 데이터베이스가 보장하는 품질

- **데이터 무결성(data integrity)**: 데이터가 수명 동안 정확하고 일관되도록 보장한다. 신뢰할 수 있는 데이터를 위해 중요하다.
- **데이터 지속성(data persistence)**: 프로세스가 종료된 뒤에도 데이터가 계속 살아 있도록 보장한다.
- 관계형 데이터베이스(relational database)는 테이블(table)을 사용하는 데이터베이스다. 각 테이블은 하나의 추상화를 표현한다. 예: 직원(employee) 테이블에서 각 열(column)은 직원 속성, 각 행(row)은 개별 직원이다.
- 관계형 데이터베이스는 SQL(Structured Query Language)로 정보를 조회(query)하고 트랜잭션을 수행한다. 이 능력이 데이터 접근자 간 정보 공유를 가능하게 한다.
- 쿼리와 트랜잭션의 관리·최적화는 데이터베이스 관리 시스템(DBMS)이 자동화하므로 데이터베이스 통합이 단순해진다.

### 각 컴포넌트의 역할

- 중앙 데이터는 **수동적(passive)** 이다. 무거운 데이터 처리나 대량의 비즈니스 로직에는 관여하지 않고, 정보 저장과 제공에만 집중한다.
- 데이터 접근자의 특징:
  - 데이터 집합을 공유하면서 독립적으로 동작한다.
  - 쿼리와 트랜잭션으로 데이터베이스와 통신하며, 접근자끼리 직접 상호작용할 필요가 없어 서로를 알 필요가 없다.
  - 계산을 수행하기 위해 데이터베이스에 쿼리하여 공유 시스템 정보를 얻는다.
  - 처리가 끝나면 트랜잭션으로 시스템의 새 상태를 데이터베이스에 저장한다.
- 데이터 접근자는 자기 기능 수행에 필요한 모든 비즈니스 규칙(business rule)을 담는다. 즉 관심사를 특화된 데이터 접근자들로 분리(separation of concerns)할 수 있다.
- 데이터 접근자 사용 권한을 통제하여 최종 사용자가 일상 업무에 필요한 것만 쓰게 할 수 있다.

### 장점

- 데이터베이스를 통한 데이터 무결성, 백업(backup), 복원(restoration)을 지원한다. 대규모 데이터 손실, 손상, 마이그레이션(migration) 문제에 도움이 된다.
- 중앙화된 데이터베이스는 데이터 접근자 간 데이터 전송 오버헤드를 줄인다. 접근자들은 데이터베이스를 통해 간접적으로 통신하므로 서로 대화할 필요가 없다.
- 기능적으로 독립적인 데이터 접근자 덕분에 확장이 쉽다. 접근자끼리 직접 통신하지 않으므로 다른 기능에 영향을 걱정하지 않고 새 기능을 추가·통합할 수 있다.
- 중앙 데이터 컴포넌트는 보통 충분한 디스크 저장 공간을 갖춘 별도 서버에 두며, 중앙 저장소 덕분에 시스템 정보 전체를 관리하기 쉽다.

### 단점

- 시스템이 중앙 데이터 컴포넌트에 크게 의존한다. 데이터 서버가 오프라인이 되거나 사용 불능이 되거나 손상된 데이터를 갖게 되면 전체 시스템이 영향을 받는다. 데이터 중복(redundancy)으로 별도 디스크에 복제하는 안전장치가 있지만, 물리 인프라는 비싸고 시스템 복구도 어렵고 비용이 크다.
- 모든 데이터 접근자가 데이터베이스에 저장된 것에 의존한다. 기존 데이터베이스에 새 접근자를 추가하려면 기존 데이터 스키마(schema)에 맞춰 구축해야 한다. 스키마에 정의된 데이터만 조회·저장할 수 있고, 저장되지 않은 것은 파생(derive)해야 하며, 맞는 테이블·컬럼이 없는 데이터 집합은 저장할 수 없다.
- 기존 데이터 스키마 변경이 어렵다. 특히 저장된 데이터가 방대하면 변경 구현이 힘들고, 스키마 변경은 데이터 접근자에도 영향을 주므로 어떤 접근자를 함께 수정해야 하는지 유의해야 한다.

### 채택 시 고려사항

- 단점에도 불구하고 방대한 데이터를 여러 부서·사무실 간에 공유할 수 있어 많은 기업이 데이터 중심 설계를 사용한다.
- 구현·유지보수가 쉽고 확장성이 높아 매우 인기 있으며, 시장에 다양한 데이터베이스 제품이 있어 필요에 맞게 고를 수 있다.
- 다만 "최종 사용자들이 데이터 집합을 공유해야 하는가?", "사용자 기반이 얼마나 큰가?" 같은 질문을 던져 이 설계가 올바른 선택인지 평가해야 한다. 설계 결정에는 항상 트레이드오프(trade-off)가 있다.

## 예시

- **타임시트 시스템**: 직원·관리자는 타임시트 작성·승인 시스템을, 급여·회계 부서는 타임시트 처리·급여 지급 시스템을 사용하며 두 시스템이 정보를 공유해야 한다.
- **직원 테이블**: 관계형 데이터베이스에서 employee 테이블이 모든 직원이라는 추상화를 표현하고, 열은 직원 속성, 행은 개별 직원을 나타낸다.

## 요약

- 데이터 중심 아키텍처는 대량의 데이터를 중앙 데이터 컴포넌트에 저장·관리하여 시스템의 안정성, 성능, 재사용성, 유지보수성을 높인다.
- 데이터 접근자의 기능을 분리하여 전체 시스템의 유지보수와 확장을 쉽게 한다.
- 데이터베이스 쿼리와 트랜잭션을 통해 데이터 접근자 간 데이터 공유를 촉진한다.
- 중앙 데이터 의존, 스키마 종속, 스키마 변경의 어려움이라는 단점이 있으므로 시스템 요구에 맞는지 평가하고 트레이드오프를 따져야 한다.
