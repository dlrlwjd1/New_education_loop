# 3.2.8 – Event Based

## 개요

- 이벤트 기반(event based) 아키텍처 스타일은 이벤트 주도 프로그래밍 패러다임(event driven programming paradigm)에서 비롯되며, 시스템의 근본 요소는 이벤트(event)다.
- 함수는 이벤트 생성자(event generator)와 이벤트 소비자(event consumer)의 형태를 띠고, 모든 통신은 이벤트 버스(event bus)가 중개하는 암시적 호출(implicit invocation)로 이루어진다.
- 함수 간 느슨한 결합 덕분에 시스템의 진화와 확장이 쉬우며, 대화형(interactive) 애플리케이션에 잘 맞는다.

## 내용

### 이벤트와 암시적 호출

- 이벤트는 신호(signal), 사용자 입력, 메시지, 다른 함수나 프로그램의 데이터일 수 있다. 이벤트는 시스템 변화의 지표이자 함수의 트리거(trigger) 역할을 한다.
- 이벤트 생성자는 이벤트를 보내고 이벤트 소비자는 이벤트를 받아 처리한다. 한 함수가 생성자이면서 동시에 소비자일 수 있다.
- 메인 프로그램과 서브루틴 스타일처럼 함수가 명시적으로 호출되는 것과 달리, 이벤트 기반 스타일에서는 이벤트 생성자가 보낸 이벤트에 따라 이벤트 소비자가 **암시적으로 호출**된다.
- 암시적 호출의 정의적 특징은 함수들이 서로 직접 통신하지 않는다는 것이다. 모든 통신은 이벤트 버스가 중개한다.

### 이벤트 버스

- 이벤트 버스는 시스템의 모든 이벤트 생성자와 소비자를 잇는 커넥터(connector)다.
- 이벤트와 이벤트 소비자는 이벤트 버스를 통해 결합(bind)된다. 각 이벤트 소비자는 특정 이벤트를 통지받도록 이벤트 버스에 등록(register)한다.
- 이벤트 버스가 이벤트를 감지하면 해당하는 모든 이벤트 소비자에게 이벤트를 배포한다. 모든 이벤트가 이벤트 버스를 거치므로 이벤트 버스는 시스템의 핵심 부분이다.
- 이 구조는 전문과정 앞부분의 디자인 패턴에서 배운 **옵서버 패턴(observer pattern)** 과 닮았다. 옵서버 패턴은 실제로 이벤트 기반 아키텍처 스타일을 구현한 것이다.
- 이벤트 버스를 구현하는 한 방법은 이벤트를 계속 수신 대기하는 메인 루프(main loop)를 시스템에 두는 것이다. 이벤트가 감지되면 루프가 그 이벤트에 결합된 모든 함수를 호출한다.
- 이벤트 소비자가 작업 완료를 다른 함수에 알리거나 상태 변화를 전달해야 하는 경우, 그 함수도 이벤트 생성자가 되어야 한다. 완료 후 이벤트를 이벤트 버스로 보내 다른 함수를 암시적으로 호출하고, 대응하는 소비자들이 트리거되어 다음 계산이 진행된다.

### 결합도와 확장성

- 함수 간의 간접 통신은 명시적 함수 호출만큼 효율적이지 않을 수 있으므로 설계 시 고려해야 한다.
- 이벤트 생성자는 누가 자기 이벤트를 소비할지 반드시 알 필요가 없고, 소비자도 누가 이벤트를 생성하는지 반드시 알 필요가 없다.
- 이런 느슨한 결합(loose coupling) 덕분에 시스템의 진화와 확장이 쉽다. 기존 이벤트에 새 기능을 추가하는 일은 이벤트-함수 쌍을 이벤트 버스에 등록하고 새 이벤트 소비자를 추가하는 것만큼 간단하다.

### 공유 데이터와 동시성 문제

- 시스템의 객체가 전역적으로 접근 가능하면 이벤트 소비자가 이벤트를 처리하며 공유 상태(shared state)를 바꿀 수 있다. 그러나 이벤트 소비자는 **비동기(asynchronous)로 호출**될 수 있어 위험하다.
- 비동기 호출에서는 소비자가 다른 소비자의 종료를 기다리지 않고 실행되므로, 두 이벤트 소비자가 같은 공유 데이터 위에서 동시에 실행될 수 있다.
- 비동기 호출은 시스템 효율을 높일 수 있지만 **경쟁 조건(race condition)** 을 일으켜 공유 데이터가 올바르게 갱신되지 않을 수 있다. 함수의 동작이 호출 순서에 의존할 때 시스템에 경쟁 조건이 있다고 말한다.
- 공유 데이터 접근을 조율하는 한 방법이 **세마포어(semaphore)** 다. 단순한 이진 세마포어(binary semaphore)는 사용 가능(available)/사용 중(unavailable) 두 값 사이를 오가는 변수다.
- 세마포어에는 값 확인과 전환을 한 단계로 수행하는 특별한 연산이 있다. 공유 데이터에 접근하려는 함수는 먼저 세마포어 값을 확인해야 한다. 값이 사용 중이면 기다렸다가 나중에 다시 확인하고, 사용 가능이면 즉시 사용 중으로 전환한 뒤 공유 데이터에 접근한다. 접근이 끝나면 값을 사용 가능으로 되돌린다.
- **탈의실 비유**: 옷가게 탈의실 문 손잡이 옆의 초록/빨강 표시등이 사용 가능/사용 중을 알려준다. 초록 방에 들어가 문을 잠그면 표시등이 빨강으로 바뀌고, 빨간 표시의 방은 잠겨 있어 들어갈 수 없다. 나가며 문을 열면 표시등이 다시 초록이 된다.
- 객체가 전역적으로 접근 가능하지 않은데 이벤트 소비자가 그 상태를 바꾼다면, 함수가 끝나기 전에 이를 이벤트 버스에 알려야 한다. 그래야 그 이벤트의 소비자들이 상태 변화를 인지한다.

### 비결정적 제어 흐름

- 이 스타일에서 이벤트와 함수는 예측 가능한 방식으로 발생하지 않는다. 이벤트가 정확히 언제 처리될지, 처리에 얼마나 걸릴지, 생성자가 언제 이벤트를 낼지 보장이 없다.
- 이런 비동기 동작 때문에 제어 흐름은 실행 중 어떤 이벤트가 어떤 순서로 발생했는지에 전적으로 좌우된다. 이벤트 주도 시스템은 비동기 이벤트로 인한 버그를 피하도록 특별히 주의해야 한다.

## 예시

### 코드 에디터의 저장 버튼

- 파일 편집 후 저장 버튼을 클릭하면, 에디터에서 이벤트가 생성되어 프로젝트 재빌드 준비가 되었음을 알리러 이벤트 버스로 전달된다.
- 빌드 도구(build tool)가 이 이벤트에 트리거되어 파일을 처리하고, 빌드 완료 시 이벤트를 생성해 이벤트 버스로 보낸다.
- 이벤트 버스는 이 이벤트를 에디터와 테스트 도구(test tool)에 전달한다. 에디터는 최신 프로젝트 상태를 표시하고, 테스트 도구는 테스트 실행을 시작한다.
- 테스트 도구가 끝나면 테스트 완료 이벤트를 이벤트 버스로 보내고, 에디터가 이를 받아 최신 테스트 상태를 표시한다.
- 이 예에서 빌드 도구, 테스트 도구, 에디터는 모두 이벤트 생성자이자 소비자다.

### Cookie Clicker 게임

- 커서로 쿠키 이미지를 클릭해 쿠키 점수를 최대한 모으는 대화형 게임이다. 단순화한 버전에서 점수는 쿠키를 직접 클릭하거나, 커서 아이콘을 클릭해 일정 시간 간격으로 자동 클릭하는 파란 커서를 구매해 모은다.
- 설계 요구: (1) 쿠키를 직접 클릭할 때마다 총 점수 +1, (2) Buy Clicker 아이콘 클릭 시 5점 차감 후 쿠키 주위에 파란 커서 추가, (3) 5초마다 파란 커서들이 자동 클릭하여 총 점수가 파란 커서 수만큼 증가.
- 이벤트 주도 구현:
  - 시스템은 메인 이벤트 루프로 이벤트를 수신 대기한다. 창 안 클릭 위치에 따라 다른 이벤트 소비자가 관여한다(단순화를 위해 모든 변수는 전역 접근 가능하고 접근이 통제된다고 가정).
  - 쿠키를 클릭하면 이 클릭 이벤트에 등록된 함수가 호출되어 총 점수가 1 증가한다.
  - Buy Clicker 아이콘을 클릭하면 Buy Clicker 함수가 호출되어 먼저 점수를 차감하고, 자동 클리커(automatic clicker) 함수를 시스템에 추가하며 쿠키 주위에 새 파란 커서를 더한다. 파란 커서 하나당 자동 클리커 함수가 하나씩 존재한다.
  - 클리커를 처음 구매할 때 Buy Clicker 함수가 타이머(timer) 함수를 시스템에 추가한다. 타이머 함수는 5초마다 타이머 이벤트를 보내는, 이벤트 버스에 등록된 이벤트 생성자다.
  - 타이머 이벤트가 발생하면 이벤트 버스가 이를 감지해 모든 자동 클리커 함수를 트리거한다. 각 자동 클리커 함수는 쿠키를 한 번 클릭하므로, 5초마다 총 점수가 구매한 자동 클리커 수만큼 자동 증가한다.
  - 그래픽 그리기의 세부는 생략했지만, 그래픽을 만드는 함수들도 시스템에 추가할 수 있다.

## 요약

- 이벤트 기반 스타일에서 이벤트 생성자와 소비자는 서로를 직접 알 필요가 없으며, 모든 통신은 이벤트 버스가 중개한다(암시적 호출).
- 이벤트 소비자는 이벤트 버스에 등록되고, 버스가 이벤트를 감지하면 해당 소비자들에게 배포한다. 옵서버 패턴이 이 스타일의 구현이다.
- 비동기 호출은 효율을 높이지만 경쟁 조건을 일으킬 수 있으며, 세마포어로 공유 데이터 접근을 통제할 수 있다.
- 함수의 이런 디커플링(decoupling)은 진화와 확장이 쉬운 시스템을 만들며, 사용자 입력에 의존하는 GUI 애플리케이션과 다른 프로그램과 상호작용하는 분산 시스템이 이 스타일의 유력한 후보다.
