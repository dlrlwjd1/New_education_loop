# 3.2.5 – Client Server n-Tier

## 개요

- n-티어(n-Tier, Multitier) 아키텍처는 레이어드 아키텍처와 관련된 스타일로, 티어(tier)는 흔히 서로 다른 물리적 머신에 있는 컴포넌트를 가리킨다.
- 두 티어 사이의 관계는 흔히 클라이언트/서버(client/server) 관계이며, 요청-응답(Request-Response) 방식으로 통신한다.
- 확장성(scalability), 기능의 중앙 집중, 관심사의 분리가 큰 장점이며, 관리 자원 증가와 서버의 단일 장애점(central point of failure)이 단점이다.

## 내용

### 티어와 레이어

- 레이어드 아키텍처에서는 설계를 레이어로 나누고, 한 레이어의 컴포넌트는 같은 레이어 또는 바로 위·아래 레이어의 컴포넌트하고만 통신했다.
- 티어는 레이어와 비슷하고 두 용어가 혼용되기도 하지만, **티어는 흔히 서로 다른 물리적 머신 위의 컴포넌트**를 가리킨다.
- 티어 수는 다양하다. 3-티어, 4-티어가 흔하지만 어떤 수든 가능하므로 n-티어 또는 멀티티어(Multitier)라고 부른다.

### 클라이언트-서버 관계와 요청-응답

- 서버 측은 서비스를 제공한다. 데이터베이스에 정보 저장, 계산 작업 수행 등 어떤 서비스든 될 수 있다. 클라이언트 측은 메시지로 이 서비스를 요청한다.
- 이 통신을 요청-응답(Request-Response)이라 한다. 클라이언트가 정보나 동작을 요청하면 서버가 응답한다.
- 하나의 티어가 서버이면서 동시에 클라이언트일 수 있다. 자기 클라이언트의 요청을 처리하면서 자기 서버에 요청을 보낼 수 있다.
- 클라이언트 소프트웨어를 호스팅하는 머신을 클라이언트 호스트(Client-Host), 서버 소프트웨어를 호스팅하는 머신을 서버 호스트(Server-Host)라 부른다.
- 서버는 보통 제공하는 서비스 종류로 지칭한다. 미디어 서버 외에도 웹 서버, 애플리케이션 서버, 파일 서버, 프린트 서버 등이 있다.

### 동기와 비동기 요청-응답

- **동기(synchronous)**: 클라이언트가 요청을 보낸 뒤 서버의 응답을 기다렸다가 실행을 계속한다. UML 2.5에서는 닫힌 화살촉(closed arrowhead)으로 표시한다. 직관적이지만 서버가 항상 빨리 응답하지는 않으므로 클라이언트가 응답 대기 중 멈춰 있을(hang) 수 있다.
- **비동기(asynchronous)**: 클라이언트가 요청을 보내지만 제어가 곧바로 돌아와 다른 필요한 처리를 계속한다. 단, 이 처리는 서버 응답에 의존해서는 안 된다. 서버가 요청을 완료하면 클라이언트에 메시지를 보내고, 클라이언트의 핸들러(handler)가 응답을 처리한다. UML에서는 선 화살촉(line arrowhead)으로 표시한다.
- 서버의 정보를 기다리는 동안에도 클라이언트가 다른 작업에 응답할 수 있도록, 많은 클라이언트 요청이 비동기로 설계된다.

### 2-티어에서 3-티어, n-티어로

- 클라이언트-서버 관계를 요청-응답 메시징 패턴으로 제한하면 클라이언트를 추가하는 방식으로 쉽게 확장 가능한 시스템이 된다. 서버는 아는 메시지를 받기만 하면 응답할 수 있고 메시지의 출처는 중요하지 않으므로, 클라이언트와 서버 모두 확장성(extensibility)이 높다.
- 하나의 서버와 클라이언트 집합으로 이루어진 단순한 관계를 **2-티어 아키텍처**라고도 부른다.
- 비즈니스 사례: 중앙 데이터베이스가 데이터 서버에 있고 여러 기기가 데이터베이스와 클라이언트-서버 관계를 맺는다고 하자. 데이터베이스가 변경되면 모든 컴퓨터의 소프트웨어를 바꿔야 한다. 컴퓨터가 3대면 어렵지 않지만 작은 기업도 컴퓨터가 많을 수 있다.
- **3-티어 아키텍처**: 데이터베이스와 최종 사용자 사이에 티어를 삽입한다. 이 레이어는 중간 레이어(middle layer), 비즈니스 레이어(business layer), 애플리케이션 레이어(application layer) 등 주된 책임에 따라 여러 이름으로 불린다. 이 중간 티어는 데이터베이스의 클라이언트이자 최종 사용자 기기의 클라이언트 애플리케이션 소프트웨어에 대한 서버다.
- 중간 티어의 주요 역할 중 하나는 데이터가 어떻게, 언제, 어떤 방식으로 변경될 수 있는지 결정하는 것이다. 애플리케이션 로직과 데이터 접근 로직을 중간 레이어로 옮기면 클라이언트 소프트웨어가 얇아진다(thinner). 클라이언트는 애플리케이션 티어에 요청하고, 애플리케이션 티어가 데이터 호출을 한다. 클라이언트 소프트웨어는 주로 프레젠테이션(presentation)만 담당하게 되어 유지보수가 쉬워진다.
- 개발자는 관심사의 분리에 기반해 더 많은 추상화 레이어를 추가하기도 한다. 추가 티어의 목적은 시스템마다 매우 구체적이다. 위 데이터베이스 예에서는 애플리케이션 로직을 보안 관심사와 데이터베이스 연산 관심사로 나눌 수 있다.

### 단점

- 클라이언트/서버 관계를 관리하는 데 추가 자원이 필요하다. 티어가 늘수록 관리할 머신·프로세스가 늘어난다.
- 머신 간 통신 프로토콜이 다르면 이질성(heterogeneity)과 복잡성이 커져 시스템 변경·유지보수가 어려워진다.
- 서버가 중앙 장애점(central point of failure)이 된다. 데이터 백업이나 미러(mirror)가 있어도 복구·전환에 시간이 걸리고, 이중화 서버(redundant server)는 가능하지만 복잡성을 더한다.
- 문제가 이 구조에 쉽게 대응되지 않으면 클라이언트/서버 패러다임이나 n-티어 아키텍처를 쓰기 어렵다.

### 장점

- **확장성**: 서버가 받는 요청을 합리적인 시간 안에 처리할 수 있는 한 클라이언트를 계속 추가할 수 있다. 티어를 더하면 확장성은 놀라운 수준이 된다. 월드 와이드 웹(World Wide Web)의 성공이 이 확장성이 어디까지 가는지 보여준다.
- **기능의 중앙 집중**: 여러 클라이언트가 접근해야 하는 데이터베이스는 클라이언트/서버 관계에 자연스럽게 맞는다. 컴퓨팅 파워도 중앙화할 수 있어 투자를 통합한다. 복잡한 현상의 수학적 시뮬레이션을 하는 사람들은 개인 컴퓨터에 충분한 성능이 없는 경우가 많고, 처리 능력을 서비스로 제공하는 회사가 존재하는 것이 더 실용적이고 비용 효율적이다.
- **관심사의 분리**: 중간 레이어가 애플리케이션 로직 관리와 데이터베이스 직접 접근 역할을 맡을 수 있고, 필요에 따라 작업을 더 세분할 수 있다.
- 시스템을 서비스 역할과 요청자 역할로 나눌 수 있다면 언제든 클라이언트/서버 아키텍처를 고려해야 한다. 티어를 추가하면 관심사의 분리, 느슨한 결합(loose coupling), 추상화 수준이 더해져 변경·확장이 쉬운 시스템이 된다.

## 예시

### 홈 미디어 서버(media server)

- 한 컴퓨터가 미디어 서버 프로세스를 호스팅한다. 서버는 영화와 TV 프로그램을 저장하고 요청 시 스트리밍한다. 클라이언트가 영화나 TV 프로그램을 요청하면 서버가 스트리밍으로 응답한다.
- 서버 프로세스는 클라이언트가 몇 개일지 알지 못하며, 필요에 따라 클라이언트를 추가할 수 있다. 새 태블릿을 사면 미디어를 요청하는 클라이언트 앱을 추가하면 된다.
- 서버와 클라이언트 프로세스는 같은 머신에서도 실행될 수 있다. 전용 컴퓨터 대신 데스크톱에 서버를 호스팅하고 같은 데스크톱의 미디어 플레이어나 태블릿으로 시청할 수 있다.
- 이를 2-티어 아키텍처로 볼 수 있다. 클라이언트 호스트들이 클라이언트 티어(Client Tier), 미디어 서버가 데이터 티어(Data Tier)를 이룬다.
- 시퀀스 다이어그램(sequence diagram)으로 보면: 미디어 플레이어가 먼저 서버 라이브러리 목록을 요청하고 서버가 그 정보를 보낸다. 사용자가 선택하면 클라이언트가 해당 영상을 요청하고 서버가 스트리밍을 시작한다.

## 요약

- n-티어 아키텍처에서 티어 간 관계는 흔히 클라이언트/서버 관계이며, 요청-응답 메시징(동기 또는 비동기)으로 통신한다.
- 2-티어(클라이언트-서버)에 중간 티어를 추가한 3-티어에서는 애플리케이션·데이터 접근 로직이 중간 레이어로 이동해 클라이언트가 얇아지고 유지보수가 쉬워진다.
- 장점: 뛰어난 확장성, 데이터·컴퓨팅 파워의 중앙 집중, 티어 추가를 통한 관심사의 분리·느슨한 결합·추상화.
- 단점: 관리 자원 증가, 이질성으로 인한 복잡성, 서버의 중앙 장애점화.
