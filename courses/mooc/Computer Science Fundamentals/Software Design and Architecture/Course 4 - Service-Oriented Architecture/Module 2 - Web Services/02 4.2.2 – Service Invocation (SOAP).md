# 4.2.2 – Service Invocation (SOAP)

## 개요

- 웹 서비스에서 서비스 요청자(service requester)와 서비스 제공자(service provider)가 XML 메시지로 통신하는 방식, 즉 SOAP을 통한 서비스 호출(invocation)을 다룬다.
- SOAP 메시지의 구조(envelope, header, body)와 두 가지 메시징 스타일(document 스타일, RPC 스타일)을 설명한다.
- 네 가지 기본 메시징 패턴(request-response, solicit-response, one-way, notification)과 동기/비동기 상호작용을 정리한다.

## 내용

### SOAP이란

- 웹 서비스에서 서비스 요청자와 서비스 제공자는 XML 메시지 형태로 통신한다. 소프트웨어가 웹 서비스를 사용하려면 요청 메시지를 보내고 응답을 받아야 하며, 이 요청-응답(request-response) 메시징 패턴이 웹 서비스와 그것을 사용하는 소프트웨어 간 모든 상호작용의 기초다.
- 이 메시지들은 SOAP 표준을 따른다. SOAP은 Microsoft에서 개발된 표준으로, 원래 Simple Object Access Protocol의 약자였으나 그 의미는 이후 폐기되었다. 다만 그 이름은 목적 — 서비스 요청자가 서비스를 호출(invoke)할 수 있게 하는 것 — 을 짐작하게 한다.
- SOAP은 서비스 요청자와 제공자(클라이언트와 서버) 간 상호작용에 표준화를 제공한다. 요청과 응답을 XML로 구성하는 방법을 양쪽 모두가 이해하는 표준 방식으로 정의하며, 이 표준화된 통신이 플랫폼과 언어 간 상호운용성(interoperability)을 가능하게 한다.
- SOAP은 또한 메시지가 하위 전송 프로토콜(transport protocol)에 어떻게 바인딩되는지에 대한 지침도 제공한다. 이 강의에서는 HTTP를 사용한다.

### SOAP 메시지의 구조

- 객체지향 언어의 메서드 호출처럼, SOAP 메시지의 목적은 원격 웹 서비스에 연산(operation)을 요청하는 것이다. 예를 들어 두 통화(currency) 간 환율을 알려주는 웹 서비스를 사용한다면, 프로그램은 SOAP 메시지로 이 정보를 요청한다.
- SOAP 메시지는 XML 형식 문서이며 다음 구조를 가진다.
  - **Envelope**: XML 문서를 SOAP 메시지로 식별한다. SOAP에 필수다.
  - **Header**: 필수가 아니다. 클라이언트 정보나 라우팅 정보 같은 맥락(contextual) 정보를 담을 수 있다.
  - **Body**: 필수이며 실제로 전달하려는 메시지를 담는다. 서비스 제공자가 어떤 서비스를 제공할지 판단하는 데 필요한 정보와 서비스의 입력값이 들어간다.

### 두 가지 SOAP 메시징 스타일

- **Document 스타일**: SOAP 메시지가 회사가 발행하는 구매 주문서(purchase order) 같다. 양쪽 모두가 이해할 수 있는 요청을 담은 구조화된 문서다. 환율 서비스 예시에서는 요청의 종류가 문서의 종류로 결정되고, 비교하려는 두 통화가 문서의 필드로 들어간다.
- **RPC(remote procedure call) 스타일**: 겉보기엔 매우 비슷하지만 메시지의 body가 메서드 호출처럼 생겼다. 연산(operation)과 입력 매개변수(parameter)로 구성된다. 환율 예시에서는 body 안에 사실상 메서드 호출이 있고, 비교할 두 통화가 두 입력 매개변수가 된다.
- SOAP은 어떤 스타일을 쓸지 지시하지 않으며 메시지의 구조만 규정한다. 두 상호작용 스타일 모두 흔히 사용된다.

### 전송과 동기/비동기

- SOAP 메시지는 어떤 전송 프로토콜 위에서든 보낼 수 있다. 이메일에 쓰이는 SMTP 같은 다른 프로토콜도 가능하지만, 여기서는 HTTP에 집중한다.
- SOAP 메시지는 HTTP POST로 보낼 수 있다. 요청을 어디로 보낼지는 SOAP 메시지 자체에 직접 포함되지 않으므로 HTTP가 결정한다. HTTP는 POST 요청에 응답해야 하므로, 응답 자체를 돌려주거나 요청이 수신되었다는 확인(acknowledgement)만 돌려줄 수 있다.
- 서비스 요청자가 응답을 기다린 후 계속 진행하면 **동기(synchronous)** 메시징이다. 직관적이지만, 웹 서비스의 가용성이나 응답 시간이 문제가 될 수 있고 응답을 기다리는 동안 프로그램이 아무것도 하지 못한다.
- **비동기(asynchronous)** 상호작용은 코드가 계속 실행되게 하고, 서비스 제공자로부터 응답이 돌아오면 그때 처리한다.

### SOAP 요청의 구현 흐름

- 단순한 SOAP 요청 구현은 다음과 같다. 클라이언트 코드가 로컬로 스텁(stub)을 호출하면, 스텁이 요청을 SOAP 메시지로 변환한다. SOAP 메시지는 HTTP에 패키징되어 서비스 제공자에게 전송된다.
- 도착하면 HTTP 서버가 내용을 SOAP 라우터(SOAP router)에 넘기고, 라우터는 적절한 서버 스텁을 찾아 메시지를 전달한다. 스텁은 SOAP 메시지에 담긴 정보로 적절한 메서드 호출을 수행한다.
- 서비스 코드가 요청을 처리한 뒤에는 이 과정이 역순으로 진행되어 응답을 보낸다.

### 네 가지 메시징 패턴

- **Request-response(요청-응답)**: 서비스 요청자가 먼저 메시지를 보내고 서비스 제공자로부터 회신을 받는다. 동기 방식이며, 본질적으로 동기인 HTTP 위에 구현할 수 있다. 환율 예시가 이 패턴이다.
- **Solicit-response**: 역시 동기 방식으로, 이번에는 서비스 제공자가 서비스 요청자에게 요청을 보낸다. 흔히 확인(confirmation) 용도다. 예를 들어 환율이 요청자에게 전송되면 요청자가 확인을 보내, 제공자는 요청자가 갱신되었음을 알 수 있다.
- **One-way(단방향)**: 서비스 요청자가 제공자에게 요청을 보내지만 응답을 기대하지 않는다. 요청자가 가동 중이라는 단순 알림 등이 될 수 있다. 응답을 기대하지 않으므로 본질적으로 비동기다.
- **Notification(알림)**: 서비스 제공자가 응답을 기대하지 않고 요청자에게 알림을 보낸다. 예를 들어 코드가 항상 최신 환율로 동작하고 서비스가 알릴 때마다 갱신되는 방식이다. 발행자(publisher)와 구독자(subscriber)가 있는 이벤트 기반 시스템(블로그, 날씨 알림 서비스 등)에 잘 맞으며, 역시 비동기다.
- 프로세스 간의 의미 있는 상호작용 대부분은 더 복잡한 메시징 패턴을 요구한다. SOAP 메시지는 무상태(stateless)이므로, 이런 상호작용은 클라이언트나 서버에 상호작용 상태를 저장하거나 WS-Coordination 같은 웹 서비스 확장을 사용하는 등 다른 방법으로 메시지들을 연관시켜 구현한다.

### SOAP의 한계와 의의

- 몇 가지 단점 때문에 SOAP은 많은 애플리케이션에서 RESTful 웹 서비스처럼 HTTP를 더 직접적으로 사용하는 경량 방식으로 대체되었다. XML 인코딩·디코딩은 오버헤드를 더하고 일부 데이터 타입을 쉽게 수용하지 못한다.
- 그럼에도 SOAP과 관련 웹 서비스 인프라는 웹 서비스에 대한 최초의 주요 합의(consensus)의 기반이었다. SOAP의 중립성 덕분에 서로 다른 플랫폼과 언어의 시스템이 상호작용하고 데이터를 주고받을 수 있으며, XML 기반 구조는 웹에 연결된 어떤 기계도 다룰 수 있는 기계 판독 가능한 데이터를 제공한다.

## 요약

- SOAP은 서비스 요청자가 웹 서비스를 호출할 수 있게 하는 XML 기반 메시지 표준으로, 플랫폼·언어 간 상호운용성을 제공한다.
- SOAP 메시지는 envelope(필수), header(선택), body(필수)로 구성된다.
- 메시징 스타일에는 구조화된 문서를 보내는 document 스타일과 메서드 호출 형태의 RPC 스타일이 있으며, SOAP은 구조만 규정하고 스타일은 지시하지 않는다.
- 메시징 패턴은 request-response와 solicit-response(동기), one-way와 notification(비동기)의 네 가지다.
- SOAP 메시지는 무상태이며, XML 처리 오버헤드 등의 단점으로 여러 응용에서 RESTful 방식으로 대체되었지만 최초의 주요 웹 서비스 합의의 기반이 되었다.
