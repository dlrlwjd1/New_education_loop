# 4.2.3 – Service Description (WSDL)

## 개요

- 웹 서비스의 인터페이스를 기술하는 표준 언어인 WSDL(Web Service Description Language)을 다룬다.
- 객체지향의 메서드 시그니처(method signature)에 빗대어 WSDL의 역할과 바인딩(binding) 개념을 설명한다.
- WSDL 2.0 기술서의 구성 요소(types, interfaces, bindings, services)와 모듈성·재사용성을 환율 서비스 예시로 정리한다.

## 내용

### 왜 서비스 기술이 필요한가

- 웹 서비스가 호출되려면 서비스 요청자(service requester)가 서비스 제공자(service provider)가 이해하는 방식으로 요청해야 한다. 즉, 올바른 형식의 SOAP 메시지를 보내야 한다.
- 환율 서비스가 RPC 스타일 상호작용을 따른다고 하면, SOAP XML 문서는 메서드 이름과 매개변수가 있는 메서드 호출과 비슷한 모습이 되고, 비교할 두 통화가 매개변수로 전달된다. 이미 호출 방법을 알고 있다면 어렵지 않다.
- 그런데 환율 서비스를 검색하는 중이거나, 서비스 제공자를 찾았지만 상호작용 방법을 모른다면? 메서드 이름이 무엇인지, 어떤 매개변수가 필요한지 어떻게 알아내는가?

### 메서드 시그니처와의 비유

- 객체지향 프로그래밍에서 특정 메서드를 호출하는 방법을 알아내려면 메서드 시그니처(method signature)를 보면 된다.
- 환율 메서드의 시그니처라면, 반환하는 데이터의 종류(이 경우 BigDecimal 숫자 타입 — boolean, enum, 개발자가 만든 추상 데이터 타입일 수도 있다)와 받는 매개변수(두 통화를 나타내는 두 개의 문자열, 예: 캐나다 달러 CAD, 미국 달러 USD)를 알려준다.
- 웹 서비스에서 WSDL이 메서드 시그니처와 유사한 역할을 한다.

### WSDL의 역할과 바인딩

- WSDL은 Web Service Description Language의 약자로, Microsoft, IBM, Ariba가 이전의 표준화 시도들을 결합해 만들었다. SOAP처럼 WSDL 기술서(description)는 XML로 작성된다.
- WSDL 기술서의 역할은 웹 서비스의 인터페이스를 기술하는 것이다. 예를 들어 요청을 어떻게 구조화할지, 필요한 입력 매개변수, 서비스가 출력할 데이터를 포함하며, 이 모든 것을 기계가 읽을 수 있는(machine-readable) 방식으로 기술한다.
- 기계 판독이 가능하므로 서비스 요청자는 WSDL 기술서를 읽어 서비스 요청 방법을 파악할 수 있고, 필요한 코드를 자동으로 생성할 수도 있다.
- 서비스 제공자와 인터페이스하는 데 필요한 코드를 생성하는 과정을 **바인딩(binding)** 이라 하며, 자동으로 하든 개발자가 직접 하든 마찬가지다. 바인딩 후에야 서비스 요청자는 SOAP 메시지로 서비스를 호출할 수 있다.
- 웹 서비스는 메서드보다 복잡하므로 WSDL 기술서에는 더 많은 정보가 필요하다. 예를 들어 서비스 요청자가 SOAP 메시지를 보낼 위치(location), 전송 프로토콜(transport protocol) 등도 기술해야 한다.

### WSDL 2.0 기술서의 주요 구성 요소

- **Types(타입)**: 사용되는 데이터 타입을 기술한다. 개발자가 XML로 추상 데이터 타입을 정의하는 곳이다. 상호작용이 XML에 이미 있는 기본 데이터 타입만 쓴다면 이 부분은 필요 없다.
- **Interfaces(인터페이스)**: WSDL 1.2에서는 포트 타입(port type)이라 불렸다. 어떤 연산(operation)을 수행할 수 있고 어떤 순서로 수행되는지의 관점에서 서비스의 인터페이스를 기술한다. 연산 순서는 SOAP 강의에서 다룬 메시지 교환 패턴(request-response, solicit-response, one-way, notification) 중 하나로 기술할 수 있다. 인터페이스는 추상적(abstract)이어서, 웹 서비스를 사용하는 데 필요한 구체적 구현에 바인딩되기 전에는 사용할 수 없다.
- **Bindings(바인딩)**: 메시지의 형식을 지정한다. document 스타일과 RPC 스타일 중 무엇을 쓸지, SOAP 메시지를 실어 보낼 전송 프로토콜이 무엇인지 명시하며, 메시지가 XML로 어떻게 변환되는지도 결정한다.
- **Services(서비스)**: 인터페이스와 바인딩을 한데 모아 URI에 위치한 엔드포인트(endpoint) 또는 포트(port)에 할당함으로써 서비스를 구체적으로 정의한다.

### 모듈성과 재사용

- WSDL 기술서는 매우 세밀한 기술 단위로 나뉘어 있다. 이 세밀한 분리 덕분에 개발자는 WSDL 명세의 일부를 다른 방식으로 재사용할 수 있다.
- 예를 들어 같은 서비스를 서로 다른 바인딩과 함께 사용해 서로 다른 통신 프로토콜 위에서 인터페이스를 제공할 수 있다. 잠재적 서비스 요청자 중 일부가 HTTP 대신 SMTP를 쓰는 경우가 그렇다.
- WSDL 문서는 다른 WSDL 문서를 임포트(import)할 수 있어, 임포트한 기술서의 데이터 타입이나 인터페이스에 접근할 수 있다는 점에서도 재사용이 가능하다.

### 환율 서비스 예시로 본 WSDL

- 단순 환율 서비스에서는 기본 데이터 타입으로 충분하므로 새 데이터 타입을 정의할 필요가 없다. 통화 코드는 문자열(string), 두 통화 가치의 비율은 십진수(decimal)다.
- 인터페이스는 하나뿐이며 request-response 스타일 상호작용이다. 상호작용을 구성하는 메시지들 — 이 경우 입력 하나와 출력 하나 — 을 정의한다. 서비스의 관점이므로 입력이 요청이고 출력이 응답이다. 요청과 응답에 어떤 데이터가 필요한지도 여기서 정의한다.
- 바인딩 부분은 SOAP을 사용하며 전송 프로토콜로 HTTP를 명시한다.
- 마지막으로 서비스 섹션이 이 부분들을 모두 모아, 서비스가 특정 URI에 위치한 웹 서비스로 어떻게 노출되는지 정의한다.
- 이 기술서는 세부 사항이 일부 빠져 있지만 웹 서비스의 일반적 형태와 WSDL 2.0으로 기술되는 방식을 보여준다. 이전 버전의 WSDL은 다른 용어와 구조를 썼지만 개념은 대체로 같다. 이런 WSDL 기술서가 있으면 서비스 요청자는 이를 읽고 인터페이스에 바인딩하는 데 필요한 코드를 생성해 서비스에 바인딩할 수 있다.

### WSDL의 의의와 한계

- WSDL은 웹 서비스와 그 인터페이스를 기술하기 위한 XML 기반 표준이다. WSDL 기술서는 잠재적 서비스 요청자가 프로그램적으로 또는 개발자가 직접 읽을 수 있고, 요청자는 서비스 인터페이스에 바인딩한 뒤 WSDL 기술서의 도움으로 구조화한 SOAP 메시지로 서비스를 호출하기 시작할 수 있다.
- WSDL은 모듈식(modular)이다. 서로 다른 구성 요소를 결합해 원하는 인터페이스(또는 여러 인터페이스)를 정의할 수 있고, 다른 WSDL 명세를 임포트해 새 인터페이스 기술로 결합할 수도 있다.
- 이 XML 기반 접근은 웹 서비스의 다른 측면들처럼 인터넷 상에서 서로 다른 플랫폼 간 상호운용성을 제공한다. WSDL은 다른 XML 기반 표준과 함께 쓰이는 경우가 많지만, SOAP에서 본 것처럼 XML 기반이 아닌 서비스도 기술할 수 있다.
- XML의 인코딩과 파싱에는 계산 비용이 든다. 이것이 XML 기반 표준의 주된 단점이다.
- SOAP 기반 상호작용이든 다른 방식이든, 서비스 지향 아키텍처(service-oriented architecture)에서 서비스를 제공·요청할 때 견고하고 모듈식이며 확장 가능한 서비스 기술 언어로 WSDL을 고려할 만하다.

## 요약

- WSDL은 웹 서비스의 인터페이스를 기계 판독 가능한 XML로 기술하는 표준으로, 객체지향의 메서드 시그니처에 해당하는 역할을 한다.
- 바인딩은 WSDL 기술서를 바탕으로 서비스와 인터페이스하는 데 필요한 코드를 생성하는 과정이며, 바인딩 후에야 SOAP으로 호출할 수 있다.
- WSDL 2.0의 주요 구성 요소는 types(데이터 타입), interfaces(추상적 연산 정의), bindings(메시지 형식·전송 프로토콜), services(엔드포인트 URI로 구체화)다.
- 세밀한 구성 요소 분리와 다른 WSDL 문서 임포트 기능 덕분에 모듈성과 재사용성이 높다.
- XML 인코딩·파싱의 계산 비용이 주된 단점이지만, 견고하고 확장 가능한 서비스 기술 언어다.
