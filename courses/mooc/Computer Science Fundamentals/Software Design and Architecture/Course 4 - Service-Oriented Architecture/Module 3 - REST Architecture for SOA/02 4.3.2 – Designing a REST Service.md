# 4.3.2 – Designing a REST Service

## 개요

- 잘 설계된 RESTful API를 만들기 위한 여덟 가지 기본 실천 사항(practices)을 다룬다.
- 학생과 수강 과목 정보를 저장·조회·삭제하는 간단한 REST 서비스를 실제로 만드는 과정을 따라간다.
- Java 라이브러리 Jersey(JAX-RS)로 POST API를 구현하고, 배포 후 CURL로 테스트하는 흐름까지 살펴본다.

## 내용

### 실천 1 — URI에는 명사(noun)만 사용

대학 시스템의 학생과 교수를 다루는 서버라면 URI는 `/students`, `/students/{SID}`, `/teachers`, `/teachers/{TID}`처럼 끝난다. 여기서 학생은 숫자 SID로, 교수는 숫자 TID로 식별된다. `/GETallteachers`처럼 동사(verb) 기반 URI는 자원 기반(resource based)이 아니므로 RESTful하지 않다. 좋은 URI는 클라이언트를 접근할 자원으로 곧장 안내하고, 그 자원에 수행할 동작은 요청의 HTTP 메서드로 전달한다. 예를 들어 학생 목록을 얻으려면 `/students`로 끝나는 URI에 HTTP GET 메서드를 호출한다.

### 실천 2 — GET 메서드는 자원의 상태를 변경하지 않는다

GET은 이름 그대로 자원을 가져오는(get) 일만 해야 한다. 자원을 조작(manipulate)하는 메서드는 PUT, POST, DELETE로 하는 것이 통용되는 관례다. 이 원칙을 따르면 API가 다른 개발자들과 일관되고 이후의 클라이언트 애플리케이션이 따라가기 쉬워진다.

### 실천 3 — URI에 복수형 명사(plural noun) 사용

단순함(simplicity)이 좋은 API의 핵심이다. 전체 학생을 조회할 때는 `/students`, 특정 학생 3번을 조회할 때는 `/students/3`을 사용한다. 단수형 명사를 섞어 쓰면 혼란을 줄 수 있으므로 자원을 가리키는 방식을 하나로 통일해야 개발자가 REST 서비스를 사용하기 쉽다.

### 실천 4 — 자원 간 관계에는 하위 자원(sub-resource) 사용

자원이 다른 자원과 관련되어 있으면 그 연결을 URI에 드러낸다. 예를 들어 첫 번째 API는 학생 3의 모든 과목을 조회하고, 두 번째 API는 학생 3과 연결된 과목 2의 정보를 조회한다. 관계가 URI에 투명하게 드러나므로 API를 쓰고 따라가기 쉬워진다.

### 실천 5 — HTTP 헤더로 입출력 형식 지정

헤더는 다양한 속성을 지정하는 데 쓰인다. 일부 개발자가 모호하게 남겨 두지만 API 사용성에 매우 중요한 두 헤더가 **Content-Type**과 **Accept**다. Content-Type은 메시지의 형식(format)을 정의하고, Accept는 응답으로 받을 수 있는 형식의 목록을 정의한다. 강의 예시에서는 요청이 JSON 형식이고 JSON 또는 text/javascript 형식을 수용하며, 응답 내용은 요청 클라이언트가 수용 가능한 JSON 객체 형식이다.

### 실천 6 — 컬렉션에 필터링(filtering)과 페이징(paging) 제공

대규모 데이터 집합을 훑어야 할 때 좋은 API는 검색을 돕는 필터를 제공한다. 보통 물음표(`?`) 뒤에 매개변수(parameter)를 전달하는 방식으로 구현한다. 예를 들어 전체 과목 중 컴퓨팅 과학(computing science) 학과의 과목만 반환하도록, 물음표 뒤에 학과를 쿼리 매개변수(query parameter)로 전달해 필터링할 수 있다. 또한 offset과 limit을 사용하면 사용자가 큰 데이터 집합을 다루는 데 도움이 된다. 필터링과 페이징을 제공하면 클라이언트 애플리케이션이 대량 데이터를 파싱하는 오버헤드를 덜고, 필요한 정보만 응답에 담아 응답도 빨라진다.

### 실천 7 — API 버전 관리(versioning)

수백만 사용자가 쓰는 웹 서비스에서 API 변경은 이를 호출하는 기존 애플리케이션이나 서비스를 망가뜨릴 수 있다. 미래의 골칫거리를 예방하려면 버전 번호를 붙인다. 강의 예시에서는 `v2`를 추가해 버전 번호를 명시했다.

### 실천 8 — 적절한 HTTP 상태 코드(status code) 제공

응답으로 반환할 수 있는 상태 코드는 매우 다양하다. 가장 흔하고 바람직한 응답은 서버 측에서 모든 것이 정상 동작함을 뜻하는 **200**이다. 그 외에도 **201**은 새 자원이 성공적으로 생성되었음을, **204**는 자원이 성공적으로 삭제되었음을 뜻한다. 올바른 상태 코드를 사용하면 개발자가 API를 더 잘 이해하고 사용할 수 있다. 전체 상태 코드는 보충 자료(supplementary resources)를 참고한다.

### RESTful 서비스 만들기 — 설계

학생과 과목, 그리고 학생이 수강하는 과목 정보를 저장·조회·삭제하는 기본 REST 서비스를 만든다.

1. **제공할 서비스 결정**: 학생, 과목, 학생-과목 관계 정보를 조회하는 GET API들을 먼저 계획한다.
2. **전체 API 표 작성**: 학생(students), 과목(courses), 학생 과목(student courses)을 조회·생성·갱신·삭제하는 API 전체를 계획한다.
3. **자원 표현 클래스 작성**: 학생(Student)의 자원 표현 클래스를 만든다. 이 Java 파일에는 학생 객체의 ID, 전체 이름(full name), 학과(department)에 대한 생성자(constructor)와 접근자 메서드(accessor method)가 있다. 과목(Course) 클래스는 연습으로 남긴다.
4. **HTTP 요청 처리 파일 작성**: RESTful 서비스와 통신하는 클라이언트 라이브러리를 제공하는 여러 기성 Java 라이브러리(Restlet, Spring, Jersey, RESTEasy 등)로 구현할 수 있다. 이 강의에서는 **Jersey**를 사용한다.

### Jersey로 POST API 구현

Jersey는 JAX-RS(Java API for RESTful Web Services)를 지원하며, 자원 클래스를 HTTP 요청으로 접근 가능한 웹 서비스로 매핑해 주는 사전 정의 어노테이션(annotation)을 제공한다. 쉽게 말해 Jersey는 JAX-RS를 단순화·확장해 웹 서비스 생성을 돕는 사용하기 쉬운 메서드들을 제공한다.

학생 생성 POST 서비스를 만드는 과정은 다음과 같다.

- 필요한 Java 라이브러리를 임포트한 뒤, 이 REST 서비스의 경로를 `/studentcourseapi`로 지정한다. 모든 API가 이 경로로 시작하게 된다.
- 어노테이션에 허용 HTTP 메서드를 명시해야 하므로 `@POST`로 POST 메서드임을 지정한다.
- `@Consumes` 어노테이션은 이 API가 받아들일 형식을 정한다. 여기서는 JSON만 받도록 한다(XML, 일반 텍스트 등 다양한 형식도 허용 가능).
- `@Path`로 이 API의 URI를 `/students`로 지정한다. 따라서 이 API는 `/studentcourseAPI/students`에서 접근할 수 있다.
- `@Produces` 필드로 응답의 반환 형식을 지정한다. 여기서는 XML 메시지를 생성한다.
- 어노테이션 다음에는 API가 호출되었을 때 실행될 메서드를 작성한다. 이 API는 새 학생을 생성해야 하므로, 새 학생 객체를 만들고 요청의 POST 매개변수에서 이름과 학과를 얻는다. 요청으로 전송될 입력에 접근하기 위해 `MyJaxBean`을 사용한다. 새 학생 객체를 저장한 뒤, 방금 생성한 학생의 속성을 담은 XML 메시지를 반환한다.

GET, PUT 등 학생·과목의 나머지 API는 연습으로 남긴다.

### 배포와 테스트

모든 API 메서드와 Java 객체·파일이 완성되면 Apache 등 웹 서버 소프트웨어로 배포(deploy)하면 된다. 자신의 머신에 배포한 뒤에는 지정된 URL로 API에 접근할 수 있다.

테스트 방법은 두 가지로, 만든 URI를 특정 내용으로 호출하는 자체 클라이언트 애플리케이션을 만들거나, 커맨드라인에서 HTTP 요청을 직접 보내는 것이다. 둘 다 생성할 학생 정보를 담은 JSON 객체와 함께 HTTP 요청을 만든다는 점에서 동일하게 동작한다.

CURL은 서버로부터 또는 서버로 데이터를 전송하는 도구다. CURL 명령(또는 클라이언트 애플리케이션)은 지정한 URI의 서버로, 컴퓨팅 과학(Computing Science) 학과의 James Dean이라는 학생 한 명의 정보를 담은 JSON 객체와 함께 HTTP 요청을 보낸다. 서버가 이 메시지를 받으면 앞서 만든 메서드를 호출해 JSON 객체로 보낸 속성을 가진 새 학생을 생성하고, 클라이언트에 응답을 돌려보낸다. 응답을 받았다면 자신만의 REST 서비스를 성공적으로 만든 것이다.

## 예시

강의에서 제시된 URI 설계 예시(학생 SID, 교수 TID는 숫자 식별자).

```text
GET /students          # 전체 학생 목록 조회
GET /students/{SID}    # 특정 학생 조회 (예: /students/3)
GET /teachers          # 전체 교수 목록 조회
GET /teachers/{TID}    # 특정 교수 조회
```

하위 자원으로 관계 표현하기.

```text
/students/3/courses    # 학생 3의 모든 과목 조회
/students/3/courses/2  # 학생 3과 연결된 과목 2의 정보 조회
```

필터링(쿼리 매개변수)과 버전 관리.

```text
/courses?department=computing-science  # 컴퓨팅 과학 학과 과목만 필터링
/v2/...                                # URI에 버전 번호(v2) 명시
```

Jersey(JAX-RS) 어노테이션 구조 — 학생 생성 POST API의 골격(강의에서 설명된 어노테이션 기준).

```java
@Path("/studentcourseapi")   // 이 REST 서비스의 모든 API가 시작하는 경로
public class StudentCourseAPI {

    @POST                              // 허용 HTTP 메서드: POST
    @Consumes(MediaType.APPLICATION_JSON)  // 입력 형식: JSON만 허용
    @Path("/students")                 // 접근 URI: /studentcourseAPI/students
    @Produces(MediaType.APPLICATION_XML)   // 응답 형식: XML
    public String createStudent(MyJaxBean input) {
        // 1) 새 Student 객체 생성
        // 2) POST 매개변수(MyJaxBean)에서 이름과 학과를 읽음
        // 3) 새 학생 객체 저장
        // 4) 생성된 학생의 속성을 담은 XML 메시지 반환
    }
}
```

CURL로 테스트: 컴퓨팅 과학 학과의 학생 "James Dean"을 담은 JSON 객체를 서버 URI로 보내 위 POST API를 호출한다.

## 요약

- 좋은 REST API 설계의 여덟 가지 실천 사항:
  1. URI에는 명사만 사용
  2. GET 메서드는 자원의 상태를 변경하지 않음
  3. URI에 복수형 명사 사용
  4. 자원 간 관계에는 하위 자원(sub-resource) 사용
  5. HTTP 헤더(Content-Type, Accept)로 입출력 형식 지정
  6. 컬렉션에 필터링과 페이징 제공
  7. API 버전 관리
  8. 적절한 HTTP 상태 코드 제공(200 정상, 201 생성됨, 204 삭제됨 등)
- REST 서비스 제작 흐름: 제공할 API 계획 → 자원 표현 클래스 작성 → Jersey(JAX-RS) 어노테이션으로 요청 처리 메서드 구현 → 웹 서버로 배포 → 클라이언트 애플리케이션 또는 CURL로 테스트.
- Jersey 외에도 Restlet, Spring, RESTEasy 같은 Java 라이브러리로 RESTful 서비스를 만들 수 있다.
