# 4.3.1 – Introduction to REST

## 개요

- REST(REpresentational State Transfer)는 HTTP로 메시지를 주고받아 분산 애플리케이션의 컴포넌트 간 통신을 수행하는 웹 서비스 아키텍처 스타일이다.
- 기본적으로 요청-응답(request-response) 설계에 기반한 클라이언트-서버(client-server) 아키텍처이며, 통신이 자원 기반(resource based)이라는 점이 특징이다.
- REST를 정의하는 다섯 가지 제약(constraints): 클라이언트-서버, 계층화(layered), 무상태성(stateless), 캐시 가능(cacheable), 균일한 인터페이스(uniform interface).

## 내용

### REST란 무엇인가

REST는 REpresentational State Transfer의 약자로, 분산 애플리케이션에서 HTTP를 사용해 컴포넌트 간 메시지를 주고받는 웹 서비스 아키텍처 스타일이다. 가장 기본적으로는 클라이언트가 요청(request)을 보내고 서버가 응답(response)하는 요청-응답 설계의 클라이언트-서버 아키텍처다.

REST의 고유한 특징은 통신이 자원 기반(resource based)이라는 점이다. 메시지가 자원의 표현(representation)으로 전송된다. 자원(resource)이란 자체적으로 완결된(self-contained) 어떤 정보든 될 수 있으며, 문서(document), 이미지, 객체 표현(object representation) 등이 그 예다.

### 제약 1 — 클라이언트-서버 아키텍처(client-server architecture)

클라이언트-서버 아키텍처는 관심사의 분리(separation of concerns)를 적용해 클라이언트와 서버라는 구체적 책임을 가진 역할들이 서로 상호작용하게 한다. 서버는 데이터 생성·조작 같은 서비스를 제공하고, 클라이언트는 사용자가 이 서비스에 접근할 수 있는 사용자 인터페이스를 제공한다.

이 분리 덕분에 REST 애플리케이션은 높은 확장성(scalability)을 가지며, 클라이언트와 서버의 개발이 서로 독립적으로 진행될 수 있다. 클라이언트는 데이터 저장·조작을 신경 쓰지 않으므로 단순하고 빠른 사용자 인터페이스 제공에 집중해 개선할 수 있고, 서버는 클라이언트 쪽 책임을 구현할 필요가 없으므로 더 큰 데이터 집합을 다룰 수 있도록 확장성을 높일 수 있다.

### 제약 2 — 계층 시스템(layered system)

REST는 클라이언트와 서버가 호출하는 소프트웨어 또는 하드웨어의 여러 아키텍처 계층(layer)으로 구성될 수 있다. 이 계층들은 성능 향상, 메시지 변환(translate), 트래픽 관리 등에 사용할 수 있다. 클라이언트에 필요한 서비스에 따라 계층을 추가·제거할 수 있으므로 REST 웹 서비스의 재사용성(reusability)이 향상된다.

### 제약 3 — 무상태성(stateless)

상호작용은 무상태(stateless)여야 한다. 서버는 클라이언트의 현재 상태나 이전 요청에 대한 정보를 저장하지 않는다. 요청이 들어오는 순간을 제외하면 서버는 클라이언트가 존재한다는 것조차 알 필요가 없다.

또한 각 요청은 서로 독립적이며, 서버가 요청을 이해하고 응답하는 데 필요한 모든 정보를 요청 자체에 담아야 한다. 서버가 요청 처리에 필요로 하는 정보가 있다면, 서버는 이전 요청에서 온 정보에 의존하지 않으므로 클라이언트가 매번 그 정보를 보내야 한다.

이 제약은 서버가 시스템 내 클라이언트들의 현재 상태 정보를 저장할 필요가 없게 하여 웹 서비스 성능을 향상시킨다. 이런 오버헤드가 없으므로 서버는 클라이언트에게 향상된 성능을 제공할 수 있다. 다만 클라이언트-서버 통신 방식에는 상당한 제한이 생긴다. 클라이언트는 요청을 보낼 때마다 자신의 현재 상태 정보를 저장하고 함께 제공해야 한다. 예를 들어 서버가 데이터 접근에 인증(authentication)을 요구한다면, 클라이언트는 모든 요청마다 인증 정보를 보내야 한다.

### 제약 4 — 캐시 가능(cacheable)

클라이언트는 서버 응답의 로컬 복사본을 보관해 이후 요청에 사용할 수 있다. 서버는 클라이언트 요청에 응답할 때마다 해당 응답이 캐시 가능(cacheable)한지 불가능(non-cacheable)한지 표시하는 정보를 응답에 추가한다. 이는 같은 자원에 대한 요청 횟수를 줄여 성능을 개선하기 위한 것이며, 무상태 제약이 가져오는 부정적 영향 일부를 완화할 수도 있다. 어떤 정보를 임시 저장하고 어떤 것을 사용 후 삭제할지는 서버가 클라이언트를 대신해 결정하므로, 클라이언트가 불필요하거나 쓸모없는 데이터를 계속 보관하지 않게 된다.

### 제약 5 — 균일한 인터페이스(uniform interface)

클라이언트와 서버 간 통신에 균일한 인터페이스를 사용한다. 구체적으로는 다음을 뜻한다.

- **정해진 메서드 사용**: REST는 공통 HTTP 메서드인 GET, PUT, POST, DELETE를 사용해 클라이언트가 자원에 수행하려는 서로 다른 동작을 전달한다.
- **URI로 자원 식별**: 요청에서 자원은 특정 URI(Uniform Resource Identifier)로 식별되어야 한다.
- **균일한 자원 표현**: 응답은 캐시 여부 같은 특정 헤더를 가지며, 자원은 XML, JSON, 단순 텍스트(Simple Text)의 세 가지 방식으로 작성된다.

## 예시

강의에서는 온라인 쇼핑 카트에 커피를 추가하는 요청과 그 응답을 예로 들어 제약들을 설명한다.

**요청 예시** — 클라이언트 애플리케이션이 온라인 쇼핑 카트에 커피를 추가하는 요청을 XML 데이터 형태로 보낸다.

- HTTP 메서드 **PUT**을 사용해 서버에서 호출할 메서드를 식별한다. 즉 클라이언트는 서버에게 쇼핑 카트에 새 항목을 추가해 카트를 갱신해 달라고 요청하는 것이다.
- 요청은 URI로 자원을 식별하고, XML은 새 항목을 추가할 특정 쇼핑 카트를 서버에 알려 준다.
- 이 요청은 무상태(stateless)다. `1234`로 식별되는 카트에 커피 항목을 추가하는 데 필요한 정보와 그 카트에 이전에 담겨 있던 항목 정보를 모두 포함하기 때문이다.

**응답 예시** — 웹 서버의 응답은 JSON 객체 형태의 표준 HTTP 응답이다.

- 헤더에는 클라이언트 측 캐시 여부를 결정하는 **cache control** 섹션이 있다. 이 예에서 `max-age=30`은 클라이언트에게 해당 정보를 30초 동안 캐시하라고 지시한다.
- 응답 내용은 5개 항목, 총액 $70.51의 온라인 쇼핑 카트 정보다.

## 요약

- REST(REpresentational State Transfer)는 HTTP 기반의 요청-응답형 클라이언트-서버 아키텍처이며, 메시지는 자원(resource)의 표현으로 전송된다.
- 다섯 가지 제약: 클라이언트-서버 아키텍처, 계층 시스템(layered), 무상태성(stateless), 캐시 가능(cacheable), 균일한 인터페이스(uniform interface).
- 균일한 인터페이스는 HTTP 메서드(GET, PUT, POST, DELETE), URI에 의한 자원 식별, XML·JSON·단순 텍스트로의 균일한 자원 표현을 포함한다.
- 이 제약들 덕분에 REST는 유연하고 고성능인 아키텍처 스타일이 되며, 높은 확장성·재사용성·느슨한 결합(loose coupling)으로 수백만 사용자를 가진 현대 애플리케이션의 요구를 충족한다.
