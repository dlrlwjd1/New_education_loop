# 4.1.1 – Introduction to Service-Oriented Architecture

## 개요

- Software Design and Architecture 전문과정의 네 번째 강좌로, 서비스를 평가하고 조합해 시스템을 만드는 서비스 지향 아키텍처(Service-Oriented Architecture, SOA)를 다룬다.
- 서비스는 요청하는 소프트웨어의 외부에 있으며 종종 원격에 존재한다는 점에서 컴포넌트(component)와 구별된다.
- SOA는 웹(인터넷) 맥락과 대규모 조직 내부 맥락, 두 가지로 나누어 살펴본다.
- SOA도 다른 아키텍처처럼 트레이드오프와 설계 결정을 수반하며, 비기능 요구사항(non-functional requirements)이 특히 중요해진다.

## 내용

### 코스 소개와 구성

이 강좌는 앞선 세 강좌(객체지향 설계, 디자인 패턴, 소프트웨어 아키텍처)를 기반으로 하지만 독립적으로 수강할 수도 있다. 특히 결합도(coupling), 관심사의 분리(separation of concerns), 계층화(layering) 같은 개념과, 서비스 지향 시스템·웹 애플리케이션·웹 서비스의 구조와 동작을 이해하기 위한 다양한 UML 다이어그램을 다시 활용한다.

코스는 4개 모듈로 구성되며 앞의 세 모듈이 영상 중심이다.

- 모듈 1: 시스템 공간과 서비스, 서비스 지향 아키텍처, 주요 웹 표준(web standards)
- 모듈 2: 1세대 웹 서비스(first generation web services)
- 모듈 3: REST 아키텍처와 REST 서비스
- 모듈 4: 캡스톤 프로젝트(REST 서비스 활용) 중심 — 과제는 코스 전반에 걸쳐 진행

### 서비스라는 개념 — 일상에서 소프트웨어로

바쁜 개발자가 빨래는 세탁소(laundromat)에, 식사는 식당이나 밀박스 서비스에, 출퇴근은 차량 호출 서비스에 맡기듯이, 소프트웨어도 외부 서비스를 사용할 수 있다.

- 날씨가 필요하면 직접 기상 관측소와 예측 모델을 만드는 대신 인터넷의 날씨 예보 서비스를 사용한다.
- 파운드-달러 환율이 필요하면 여러 은행의 매수·매도 환율을 직접 조회해 추정하는 대신 이미 존재하는 환율 서비스를 쓴다.

서비스는 컴포넌트와 달리 요청하는 소프트웨어의 **외부**에 있고, 종종 원격(같은 회사의 다른 서버 또는 인터넷 어딘가)에 있다. 서비스를 배포(deploy)한다는 것은 같은 조직의 다른 부서든 인터넷 너머의 소프트웨어든, 다른 소프트웨어가 사용할 수 있는 도구를 제공한다는 뜻이다.

서비스에는 두 가지 역할이 있다.

- **서비스 요청자(service requester)**: 서비스를 요청하는 소프트웨어
- **서비스 제공자(service provider)**: 요청을 수행하는 쪽

이는 유사한 도메인의 클라이언트(client)·서버(server) 역할과 매우 비슷해서 그 용어가 쓰이기도 한다.

### 웹 서비스 맥락 (외부 SOA)

웹 서비스(web services)는 인터넷에서 제공되는 서비스를 말한다. 기능이 풍부한 인터넷 앱을 만드는 한 방법은 기존 외부 웹 서비스로 일부 작업을 처리하는 것이다.

강의의 예시는 여행 예산 웹 애플리케이션 **Backpack Budgeter**다. 고객이 알고 싶은 것들은 대부분 이미 서비스로 존재한다.

- 최저 항공권 가격 → 기존 서비스로 조회
- 환율 변환 → 기존 환율 서비스 사용
- 현지 음식·투어 가격 → 마찬가지로 기존 서비스 사용

핵심은 필요한 서비스 대부분이 이미 웹에 있으므로, 이를 **조합(combine)** 해서 앱을 만들 수 있다는 점이다.

### 조직 내부 맥락 (내부 SOA)

대기업·조직에서는 사내(in-house) 코드를 서비스로 전환해 여러 사업 부서가 사용하거나 서비스들을 조합할 수 있다. 서비스는 처음부터 새로 만들 수도 있고, 기존 소프트웨어에 인터페이스를 추가해 만들 수도 있다.

강의의 예시: IT 부서가 소프트웨어 지원 비용(support cost)을 추적하는데, 다른 부서가 필요할 때마다 이메일로 요청하는 대신 이를 소프트웨어 서비스로 제공하면 어떨까? IT 부서가 인터페이스를 제공하면 경영진은 투자수익률(ROI) 계산에, 회계 부서는 세무 처리에 필요할 때 각자 서비스를 조회하면 된다.

내부 SOA는 조직이 범용적이고 재사용 가능한 소프트웨어 서비스를 만들도록 유도한다. 그 결과,

- 경직된 내부 소프트웨어 시스템 때문에 느리게 움직이는 대신 기회에 빠르게 대응할 수 있다.
- 새 부서나 인수합병(merger) 같은 새로운 사업 단위도 서비스에 쉽게 접근할 수 있다.

### SOA의 트레이드오프

SOA도 아키텍처인 만큼 트레이드오프와 구현상 설계 결정이 따른다.

**웹에서는** 기존 서비스 사용의 편리함과 서비스 품질(개발자가 통제할 수 없는 부분) 사이의 균형이 필요하다. 비기능 요구사항이 매우 중요해진다.

- 응답 시간(response time): 서비스에 의존한다면 얼마나 빨리 제공되는지 알아야 한다.
- 지원 가능성(supportability): 제공자와 서비스를 신뢰할 수 있는가? 앞으로도 계속 제공될 것인가?
- 가용성(availability): 서비스가 항상 실행 중이고 사용 가능한가?

**대규모 조직에서는** 광범위한 SOA가 기존 방식(status quo)과 완전히 다르다는 점이 주요 단점이다. 전면 전환은 비용이 크고 유지가 어려울 수 있어, 서비스는 보통 **점진적으로(bit by bit)** 도입하며 부서 간 활용도가 가장 높은 기능부터 분리한다.

SOA는 쉽지 않다. 아이디어는 단순해 보이지만, 서비스를 효과적으로 만드는 모듈성(modularity)과 플랫폼 독립성(platform independence)은 저절로 얻어지지 않는다. 일단 SOA가 자리 잡으면 모듈성, 확장성(extensibility), 코드 재사용(code reuse)을 제공하기 때문에 매우 강력하다. 애플리케이션은 서비스 조합으로 만들 수 있고, 새 서비스는 기존 서비스 조합, 신규 개발, 또는 기존 코드에 인터페이스 추가로 만들 수 있다.

### 실무자 인터뷰

- 한 실무자는 회사의 거의 모든 비즈니스 로직이 웹 서비스에 캡슐화되어 있다고 말한다. 공유 시스템의 객체 스토리지 관리 같은 유틸리티 서비스부터 전체 비즈니스 플로우를 캡슐화한 고수준 웹 서비스까지, 서비스에 서로 다른 추상화 수준·아키텍처 계층이 존재한다.
- 다른 실무자는 클라이언트가 하는 일을 개념적 덩어리(conceptual chunks)로 캡슐화한 것을 서비스라고 부른다. 예: 엔지니어링 워크플로의 승인(sign-off) 단계 — 설계가 여러 단계를 거쳐 승인되면 해당 부분이 동결(frozen)되고, 변경하려면 워크플로를 다시 시작해야 하는 변경 관리(management of change)를 하나의 개념적 서비스로 캡슐화할 수 있다. UI나 데이터베이스 같은 저수준 구현 서비스도 서비스로 본다(예: 데이터베이스의 인터페이스는 보통 SQL). 무언가를 서비스로 만드는 것은 그 인터페이스를 명확히 표현하는 일이며, API가 정해지면 서비스들을 화이트보드에 놓고 관계를 그리는 것이 아키텍처의 시작이다.
- 조언: 서비스 사용자에게 정보를 최대한 숨기고(정보 은닉), 서비스를 조합할 때 결합을 최대한 단순하게 하라. 서비스 간 관계가 복잡하다면 반드시 문서화하고 팀 전체가 이해하게 하라. 시스템 부분들 사이의 복잡한 상호작용이 바로 실패 위험이 가장 높은 곳이다.

## 요약

- 서비스는 요청 소프트웨어의 외부(종종 원격)에 있으며, 서비스 요청자(requester)와 서비스 제공자(provider) 두 역할로 이야기한다.
- SOA는 서비스를 만들고, 사용하고, 조합해 소프트웨어 목표를 달성하는 방법에 관한 아키텍처다.
- 웹 맥락에서는 기존 웹 서비스를 조합해 앱을 만들 수 있고, 조직 내부에서는 사내 기능을 서비스화해 부서 간 재사용할 수 있다.
- 웹 서비스 사용 시 응답 시간·지원 가능성·가용성 같은 비기능 요구사항이 중요하고, 조직 내부에서는 전환 비용 때문에 점진적 도입이 일반적이다.
- SOA가 갖춰지면 모듈성, 확장성, 코드 재사용이라는 강력한 이점을 제공한다.
