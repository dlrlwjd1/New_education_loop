# 4.1.9 – Object Brokers

## 개요

- 객체 브로커(object broker)는 RPC의 분산 컴퓨팅 측면과 객체지향 설계 원칙을 결합한 미들웨어로, RPC의 자연스러운 진화형이다.
- 가장 일반적인 객체 브로커 아키텍처는 CORBA(Common Object Request Broker Architecture)로, 구현 가이드가 아닌 표준(standards) 집합에 가깝다.
- CORBA는 객체 요청 브로커(Object Request Broker), CORBA 서비스, CORBA 퍼실리티라는 세 주요 컴포넌트로 구성된다.
- 객체 브로커는 현재 대체로 레거시 SOA 시스템으로 간주되지만, SOA의 진화를 이해하는 데 중요하다.

## 내용

### 배경: 객체지향 패러다임과 미들웨어의 진화

프로그래밍 패러다임은 필요에 따라 계속 변하고, 시스템과 표준도 새 패러다임에 맞춰 진화해야 한다. 객체지향 프로그래밍(OOP)이 널리 채택되면서 클래스 상속(inheritance), 일반화(generalization), 추상화(abstraction), 캡슐화(encapsulation) 같은 원칙을 활용하는 새 시스템이 작성되었다. 그러나 시스템을 처음부터 새로 설계·구축하는 것은 비용이 크다. 오래된 시스템은 새 객체지향 언어의 기능을 활용하진 못해도 그 설계는 여전히 유효하므로, 새 패러다임 중심으로 새 아키텍처를 설계하는 대신 **기존 아키텍처를 새 패러다임으로 갱신**할 수 있다.

RPC가 바로 이렇게 진화했다. 레거시로 밀려나는 대신 객체 브로커 기반 미들웨어 아키텍처의 토대가 되었다. 객체 브로커는 OOP를 포함함으로써 분산 시스템이 객체지향 접근을 사용할 수 있게 단순화한다.

### 역사: OOP가 미들웨어에 던진 문제

1970년대 후반 OOP 개념이 등장했다.

- 클래스(class)로 추상 데이터 타입을 정의해 데이터 추상화를 단순화했다. 클래스가 캡슐화한 데이터는 속성(attribute)으로 그 특성을 정의하고, 클래스가 수행할 수 있는 프로시저는 메서드(method)로 그 행동을 기술한다.
- 비정적(non-static) 클래스는 인스턴스화(instantiation)를 통해 객체로 생성된다. 프로그램은 런타임에 새 객체 인스턴스를 동적으로 만들 수 있고, 한 클래스의 고유한 인스턴스가 동시에 여러 개 존재할 수 있다.
- **상속과 다형성(polymorphism)** 은 메서드 식별 방식을 바꿨다. 이전 패러다임에서는 프로그램 내 프로시저의 시그니처(signature)가 유일해서, 특정 시그니처의 전역 프로시저 구현은 하나뿐이었다. OOP에서는 서로 다른 클래스가 같은 메서드 시그니처에 대해 다른 구현을 가질 수 있다.

이것이 미들웨어에 문제가 된다. 미들웨어는 각 객체에 서비스를 제공해야 하고, 상속과 다형성을 고려해 원격 호출을 올바른 서버로 보낼 수 있어야 한다. 그래서 객체 브로커는 RPC의 자연스러운 진화이며, 이 확장은 1990년대에 미들웨어가 OOP를 다루는 문제를 해결하기 위해 시작되었다.

### CORBA란

가장 일반적인 객체 브로커 아키텍처는 **CORBA**다. 이름에 아키텍처가 들어 있지만 실제로는 표준 집합에 가깝다.

- 객체 관리 그룹(Object Management Group, OMG)이 만든 CORBA는 객체 브로커에 무엇이 포함되어야 하는지 개요를 제공할 뿐, 구현 방법 안내서(how-to guide)가 아니다.
- 객체지향 언어가 많으므로 CORBA의 최우선 목표는 객체 브로커가 클라이언트·서버 구현에 쓰인 **프로그래밍 언어에 독립적**이도록 하는 명세를 만드는 것이다.
- 클라이언트 측과 서버 측은 품질 요구사항이 달라 운영체제도 다른 경우가 많으므로, 객체 브로커는 **운영체제에도 독립적**이어야 한다고 명시한다. 분산 컴퓨팅을 위한 미들웨어가 필요할 때 개발자가 미들웨어의 언어·OS 제약에 묶이지 않게 하려는 의도다.
- RPC 기반 아키텍처의 프로시저처럼, 객체는 네트워크의 여러 컴퓨터에 분산되어 서로 다른 물리 주소 공간에 있거나, 같은 컴퓨터의 여러 프로세스에 분산되어 서로 다른 가상 주소 공간에 있을 수 있다.
- 객체 브로커와 CORBA 표준은 미들웨어·분산 컴퓨팅의 진화에서 중요하다. Microsoft .NET 프레임워크와 여러 벤더의 Java 2 Enterprise Edition(J2EE) 프레임워크의 토대가 되었다.

### CORBA의 세 컴포넌트

1. **객체 요청 브로커(Object Request Broker, ORB)**: 클라이언트와 서버에 객체 상호운용성(interoperability)을 제공한다. 객체는 클라이언트나 서버가 브로커를 통해 접근하기 전에 자신의 인터페이스를 선언해야 한다. 브로커는 수신하는 모든 메서드 호출의 마샬링(marshalling)·언마샬링(unmarshalling)도 담당한다. 이 덕분에 클라이언트나 서버를 수정해도 상대편에 영향을 주지 않는다.
2. **CORBA 서비스(CORBA services)**: 미들웨어가 클라이언트·서버가 사용하는 객체들에게 제공하는 서비스. 영속성(persistence)에 필요한 기능부터 객체 보안(security) 관련 기능까지 다양하며, 모두 CORBA 표준화 API로 접근한다.
3. **CORBA 퍼실리티(CORBA facilities)**: CORBA 서비스가 객체 수준 기능이라면, 퍼실리티는 **애플리케이션 수준** 서비스를 제공한다. 문서 관리(document management) 같은 고수준 기능이 보통 여기에 해당한다.

### IDL, 스텁과 스켈레톤

객체 브로커는 RPC 아키텍처의 확장이므로, 시스템 내 통신을 담당할 스텁을 생성하기 위해 인터페이스 정의 언어(IDL)를 사용하는 동일한 설계를 따른다. RPC에서 이미 자세히 봤으므로 여기서는 객체 브로커가 더한 개선점만 본다.

- CORBA의 IDL은 RPC의 IDL과 매우 유사하지만 **상속과 다형성을 지원**한다는 점이 개선이다. 모든 객체 인터페이스는 클라이언트에 제공되기 위해 IDL로 선언되어야 한다.
- 서로 다른 언어로 클라이언트·서버를 개발할 수 있도록, CORBA IDL은 여러 객체지향 언어로의 **표준화된 매핑**을 갖는다. 표준화 덕분에 IDL은 서로 다른 벤더의 브로커 간에도 이식 가능(portable)하다.
- RPC처럼 CORBA IDL 컴파일러가 클라이언트 스텁(stub)과 서버 스켈레톤(skeleton)을 만든다. 기능적으로는 RPC의 대응물과 비슷하지만, 객체를 다루므로 객체를 처리할 수 있게 확장되어야 한다.
- **클라이언트 스텁**은 프록시 객체(proxy object)로 동작한다. 브로커가 서비스하는 분산 객체들을 모두 숨기며, 스텁이 클라이언트 애플리케이션에 링크되어 있으므로 서비스되는 객체에 대한 모든 메서드 호출이 로컬 호출처럼 보인다. 클라이언트가 스텁을 통해 원격 메서드에 접근하므로, 스텁은 브로커들에 분산된 모든 객체의 메서드 선언도 담아야 한다.
- **서버 스켈레톤**은 서버 애플리케이션으로부터 객체 분산을 숨긴다. 원격 객체들이 서버에 함수 호출을 하므로, 스켈레톤이 프록시 객체 역할을 해 호출이 로컬 객체에서 오는 것처럼 보이게 한다.
- 이 설계에서는 클라이언트가 서버의 IDL을 알아야 서로 통신할 수 있다. 이를 모르면 객체 브로커가 서비스하는 메서드에 접근할 수 없다.

### 바인딩: 정적과 동적

상호운용성은 클라이언트가 최소 하나의 브로커에 바인딩해야 달성된다. 바인딩 없이는 객체의 행동에 접근할 수 없다.

- **정적 바인딩(static binding)**: 가장 쉬운 방법으로, 클라이언트 스텁이 생성될 때 일어난다. 브로커에 정적으로 바인딩하는 서비스는 IDL이 처리한다. IDL 컴파일러가 스텁을 생성하면 그 스텁은 컴파일러가 속한 브로커에 정적으로 바인딩된다.
- **동적 바인딩(dynamic binding)**: CORBA에 함께 명시되어 있으며, 클라이언트가 동적으로 새 객체를 검색하고, 인터페이스를 가져오고, 발견한 객체를 인스턴스화할 수 있다는 장점이 있다. 동적 바인딩에서는 IDL 컴파일러가 스텁을 생성할 필요가 없는 대신 두 컴포넌트가 추가로 필요하다.
  - **인터페이스 저장소(interface repository)**: 브로커가 서비스하는 모든 객체의 IDL 정의를 저장한다.
  - **동적 호출 인터페이스(dynamic invocation interface)**: 클라이언트가 인터페이스 저장소를 탐색하고, 발견한 것을 기반으로 메서드를 동적으로 구성하는 데 필요한 모든 연산을 제공한다.
- 동적 호출 인터페이스의 두 서비스가 객체 참조를 제공한다: **네이밍 서비스(naming service)** 는 클라이언트가 필요한 인터페이스의 "이름"으로 객체를 가져오게 하고, **트레이딩 서비스(trading service)** 는 객체 속성 기반으로 객체를 검색하게 한다.

### 동적 호출 인터페이스의 어려움

동적 호출 인터페이스를 만드는 것은 **의미론적으로(semantically) 어렵다**. 컴포넌트 로직 구축에 많은 작업이 들어가는데, 어려운 것은 검색 의미론이다.

- 클라이언트가 저장소에서 서비스를 제대로 검색하려면 각 서비스 속성의 의미를 이해해야 하므로, 클라이언트와 동적 호출 인터페이스가 서로 이해할 수 있는 명명 규칙(naming convention)이 필요하다. 예: get에는 fetch, retrieve, obtain 같은 동의어가 있는데, 양쪽 모두 이 단어들이 같은 의미일 수 있음을 이해해야 한다.
- 클라이언트는 발견한 서비스와 상호작용하는 방법도 알아야 한다. 그렇지 않으면 새로 발견한 서비스의 행동이 무엇인지, 파라미터가 무슨 뜻인지, 원하는 효과를 위해 어떤 순서로 호출해야 하는지 알기 어렵다.
- 동적 호출 인터페이스의 의미 규칙 구현 비용은 일반적으로 이점을 초과한다. 특히 크고 견고한 객체 브로커일수록 발견하고 구현해야 할 의미적 연결이 많아 더욱 그렇다.

### CORBA의 이점

- 브로커가 객체에 대한 참조와 실제 주소를 모두 추적·유지하고, 클라이언트는 객체 참조만 하면 된다. 브로커 안에서 객체의 물리적·가상적 주소가 바뀌어도 클라이언트는 여전히 접근할 수 있다. 즉 객체는 주소로부터 사실상 독립적이어서, 이동해도 계속 참조될 수 있다.
- 프로그래밍 언어·운영체제로부터 기술적으로 독립적이므로 제약 없이 클라이언트와 서버를 개발할 수 있다.
- 데이터 옵션이 다양하다. 데이터를 강타입(strongly typed) 또는 동적 타입(dynamically typed)으로 할 수 있고, 전송 데이터 크기를 줄이기 위해 이진 형태로 마샬링하거나 압축할 수 있다.
- 개발자가 스레드와 네트워크 연결 설정을 관리할 수 있게 하는 최적화 표준도 제공한다.

### CORBA에 대한 비판

- 문제 대부분은 CORBA 표준 자체가 아니라 **표준의 부실한 구현** 때문이다. 표준을 올바르게 구현하지 않은 시스템은 문제를 겪는데, 보통 브로커에서 발생해 지나치게 복잡하고 일관성 없는 API, 사용하기 어려운 객체 브로커, 전반적으로 낮은 성능으로 이어진다.
- 부실 구현의 원인: 개발팀의 경험 부족, 또는 비용 절감 필요(CORBA 표준을 충족하는 시스템 구현은 비싸다).
- 객체가 물리·가상 주소에 묶이지 않는다는 강점은 **위치 투명성(location transparency)** 이라는 문제도 낳는다. 상호작용하는 객체들이 같은 주소 공간에 있어도 메서드 호출을 다른 공간에 있는 것처럼 처리한다. 로컬이어야 할 메서드 호출이 원격 방식으로 이루어지므로, 객체 위치와 무관하게 호출이 항상 가장 복잡한 방식으로 수행된다.

### 마무리

객체 브로커는 현재 대체로 레거시 SOA 시스템으로 간주되지만, 그 진화 과정과 필요했던 이유를 이해하는 것은 중요하다. SOA는 기술과 함께 계속 진화한다. 객체 브로커가 SOA 구현의 인기 있는 수단이었다면, 인터넷의 지배에 대응한 다음 진화 단계는 웹 서비스와 웹 기술이다.

## 요약

- 객체 브로커는 RPC를 객체지향 패러다임으로 확장한 미들웨어로, 상속·다형성 때문에 원격 호출을 올바른 구현으로 보내야 하는 문제를 해결한다.
- CORBA는 OMG가 만든 표준 집합으로, 언어·운영체제 독립적인 객체 브로커의 요건을 명세하며 .NET과 J2EE의 토대가 되었다.
- CORBA는 객체 요청 브로커(상호운용성·마샬링), CORBA 서비스(객체 수준), CORBA 퍼실리티(애플리케이션 수준)로 구성된다.
- IDL이 상속·다형성을 지원하고, 클라이언트 스텁과 서버 스켈레톤이 프록시 객체로서 객체 분산을 숨긴다.
- 바인딩은 스텁 생성 시의 정적 바인딩과, 인터페이스 저장소·동적 호출 인터페이스를 통한 동적 바인딩이 있으나, 동적 방식은 검색 의미론 구현 비용이 이점을 초과하는 경우가 많다.
- 이점(주소 독립적 객체 참조, 기술 독립성, 데이터·최적화 옵션)에도 불구하고, 부실 구현과 위치 투명성(항상 원격처럼 호출) 문제로 비판받았고 현재는 레거시로 간주된다.
