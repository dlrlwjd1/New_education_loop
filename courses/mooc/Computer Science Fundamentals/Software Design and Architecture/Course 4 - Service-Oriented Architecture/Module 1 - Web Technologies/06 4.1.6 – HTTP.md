# 4.1.6 – HTTP

## 개요

- HTTP(Hypertext Transfer Protocol)는 하이퍼텍스트(hypertext)를 포함한 정보가 인터넷을 통해 어떻게 전송되는지를 규정하는 프로토콜이다(이 강의는 HTTP/1.1 기준).
- URI는 리소스를 식별하는 주소이고, URL은 그중 리소스의 위치와 접근 방법까지 알려주는 부분집합이다.
- HTTP는 클라이언트/서버 설계 위에 만들어졌고, TCP 위에서 동작하며, 요청(request)·응답(response) 메시지의 형식과 요청 메서드(GET, POST, PUT 등)를 정의한다.
- HTTP는 무상태(stateless) 프로토콜이며, 상태 추적이 필요하면 쿠키(cookie)를 사용한다.

## 내용

### 하이퍼텍스트와 리소스

하이퍼텍스트는 하이퍼링크(hyperlink)가 삽입된 문서로, 클릭하면 의도된 문서나 리소스(resource)로 이동한다. 원래 하이퍼링크는 주로 HTML 문서를 연결했고, HTTP는 하이퍼텍스트 사용과 HTML로 표현된 문서·리소스의 통신을 지원하도록 설계되었다. 지금은 이미지, 비디오, GIF, 텍스트, 오디오 같은 멀티미디어 리소스와 그 조합을 연결한다.

- 정적(static) 리소스: HTML 문서, 이미지, 비디오 같은 파일
- 동적(dynamic) 리소스: 호출되면 출력을 만들어내는 프로그램

### URI와 URL

- **URI(Universal Resource Identifier)**: 리소스를 식별하는 주소
- **URL(Universal Resource Locator)**: 리소스를 찾는(locate) 데 쓰이는 URI의 부분집합. 리소스 식별에 더해, 프로토콜에게 리소스를 어디서 어떻게 접근할지 알려준다. 즉 프로토콜과 도메인 이름(또는 IP 주소), 그리고 그 머신 안에서의 리소스 위치를 제공한다.
- 요약하면: **모든 URL은 URI이지만, 모든 URI가 URL은 아니다.**

강의의 URI 분해 예시(브라우저에서 열면 선햇 이미지가 보이는 URI):

- 프로토콜: `http`
- 호스트명: `etsy.com`
- 호스트 머신에서 리소스의 위치: `user/favoriteitems/widebrimsunhat`
- 리소스 자체: `sunhat.png`

URI에 IP 주소를 명시할 필요는 없다. 브라우저가 호스트명에 해당하는 IP 주소를 이미 알고 있거나, 모르면 **DNS(Domain Name System) 서버**에 질의해 알아낸다.

### TCP 위의 HTTP

HTTP는 **TCP(Transmission Control Protocol)** 위에 구축되어 있다. TCP는 신뢰성 있고(reliable), 순서가 보장되며(ordered), 연결 지향(connection-oriented) 통신을 제공하기 때문에 HTTP가 TCP 연결에 의존하게 되었다.

- HTTP 메시지는 TCP 포트를 통해 송수신된다.
- 브라우저가 `http`로 시작하는 URI에 접근하면 브라우저와 웹 서버 사이에 TCP **포트 80**(HTTP 기본 포트)으로 연결이 열린다.
- URI에 포트 번호가 포함될 수도 있지만(호스트명 뒤에 붙음), 운영 시스템은 보통 기본 포트를 쓰기 때문에 거의 사용되지 않는다.
- HTTP는 클라이언트/서버 설계 기반이다. 클라이언트가 서버에 요청하면 둘 사이에 통신용 TCP 연결이 열린다. 웹에서는 웹 브라우저와 웹 서버가 이 관계다.

### HTTP 요청의 형식

클라이언트 요청은 **요청 라인(request line) + 헤더(headers) + 빈 줄 + (경우에 따라) 메시지 본문(message body)** 으로 구성된다.

- 요청 라인: 요청 메서드(request method), 요청 URI, 프로토콜을 포함한다. URI는 요청의 파라미터 데이터를 지정하는 쿼리 문자열(query string)로 끝날 수 있으며, 쿼리 문자열은 리소스 경로와 물음표(`?`)로 구분된다.
- 헤더: 선택적 헤더가 많아 수와 종류는 다양하다. 필수 헤더는 요청이 처리될 수 있게 하고, 선택 헤더는 요청에 문맥을 준다.
  - 모든 요청에 반드시 포함되는 두 헤더: 호스트의 도메인 이름 또는 IP 주소를 담는 `Host` 헤더, 클라이언트가 응답으로 수용할 콘텐츠 종류를 서버에 알리는 `Accept` 헤더
  - 메시지 본문이 있으면: 본문 크기(바이트)를 나타내는 `Content-Length` 헤더와 본문 타입을 나타내는 `Content-Type` 헤더가 필수
- 헤더 다음에는 빈 줄이 온다. 본문이 필요 없는 요청이면 여기서 끝나고, 필요하면 그 뒤에 본문이 온다. 본문은 HTML 문서, JSON, 인코딩된 파라미터 등일 수 있다.

### HTTP 응답의 형식

서버 응답은 **상태 라인(status-line) + 헤더 + 빈 줄 + (선택적) 메시지 본문**으로 구성된다.

- 상태 라인: 프로토콜 버전과 HTTP 상태 코드(status code)를 포함한다. 상태 코드는 요청의 처리 상태를 클라이언트에 알린다. 가능한 코드는 많지만, 요청이 성공적으로 처리되면 대개 `200 OK`를 보게 된다.
- 요청과 마찬가지로 본문이 있으면 `Content-Length`와 `Content-Type` 헤더가 필수이고, 그 외 선택 헤더가 있을 수 있다.
- 빈 줄 뒤에 본문이 없으면 응답은 거기서 끝나고, 있으면 본문(HTML 문서, JSON 등)이 바로 이어진다.

### URL 인코딩 (URL-Encoding)

HTTP는 URI, 요청 쿼리, 요청 본문에 쓰이는 문자를 ASCII로 제한한다. 공백이나 유니코드 같은 특수·안전하지 않은(unsafe) 문자는 인코딩해야 한다.

- 보통 안전하지 않은 문자는 퍼센트 기호(`%`) 뒤에 두 자리 16진수 인코딩을 붙여 대체한다.
- 공백은 특수한 경우로 두 가지 인코딩이 있다: `%20` 또는 `+`
- 쿼리 문자열에서는 `=`로 각 파라미터에 값을 할당하고, `&`로 파라미터-값 쌍들을 연결한다.

### 요청 메서드: GET, POST, PUT

요청 메서드는 웹 서버가 요청을 가지고 무엇을 해야 하는지 알려준다. 가장 흔히 보게 되는 것은 GET, POST, PUT이다.

**GET** — 요청 라인의 URI가 가리키는 리소스를 가져온다(retrieve).

- 웹 페이지, 이미지, 또는 리소스로 프로그램이 지정되었다면 그 프로그램의 출력을 가져올 수 있다.
- 쿼리 문자열을 URI에 실어 보낼 수 있다. 쿼리는 항상 `?`로 시작하고 URL 인코딩되어야 한다.
- GET 요청에는 메시지 본문을 보내지 않는다.
- 예시: camping.com에서 예약 번호 17021로 만든 캠핑장 예약을 확인하려면, URL 인코딩된 쿼리 문자열을 `camping.com/reservation`에 보낸다. 응답을 받으면 브라우저가 응답 본문의 HTML 문서를 렌더링해 예약 내용을 화면에서 볼 수 있다.

**POST** — 요청 본문(message body)의 내용에 따라, 요청 URI에 지정된 호스트에서 리소스를 추가하거나 수정한다.

- 본문에는 웹사이트에서 리소스를 생성·갱신하는 데 쓰일 정보가 담긴다.
- HTML 폼(form)은 흔히 POST 요청으로 데이터를 제출한다. 본문 데이터가 HTML 폼에서 온 것이면 GET 쿼리처럼 URL 인코딩된다.
- 예시: 친구 몫의 캠핑장을 새로 예약한다. 웹사이트에 새 예약을 **생성**하므로 POST를 사용한다. 예약 정보 — 이름 Mary Teller, 이메일 mteller@gmail.com, 예약일 01/07/17, 캠핑장 35 — 가 요청 본문에 인코딩된다. 서버가 처리 후 응답을 보내면 브라우저가 본문의 HTML 문서를 렌더링해 예약 확인 화면을 보여준다.

**PUT** — 요청 본문의 정보로, 요청 URI가 지정한 **위치에** 리소스를 생성하거나 갱신한다.

- 즉, 요청의 URI가 동봉된 리소스의 정체성(identity)과 위치를 서버에 지시한다.
- POST와의 차이: POST는 본문의 정보가 **웹 서버가 결정하는** 정체성과 위치로 생성·갱신된다(제공된 URI의 위치라는 보장이 없다). PUT은 URI가 지정한 그 위치다.
- 예시: 기존 예약에 캠핑장 직원용 메모(도끼와 장작 관련)를 추가한다. 예약이 이미 존재하고 예약 번호로 접근 위치를 알고 있으므로, 그 위치로 PUT 요청을 보낸다. 메모는 JSON 객체로 요청 본문에 담기며, 이때 `Content-Type` 헤더가 본문 데이터 타입(JSON)에 맞게 변경된다. 서버가 처리 후 응답 본문에 HTML 문서를 보내고 브라우저가 렌더링한다.

### 무상태성(Statelessness)과 쿠키

HTTP가 무상태(stateless)라는 것은 **요청들 사이의 관계가 보존되지 않는다**는 뜻이다.

- 예: 온라인 쇼핑 사이트에서 상품들을 클릭할 때, HTTP 프로토콜은 이전에 어떤 상품을 클릭했는지 추적하지 않는다. 클릭할 때마다 새 요청이 전송되고, 프로토콜은 같은 클라이언트의 요청인지 알지 못한다.
- 웹사이트는 **HTTP 쿠키**로 방문자의 행동을 추적할 수 있다. 클라이언트가 처음 요청하면 사이트가 브라우징 세션 정보를 저장할 쿠키를 준다. 쿠키는 클라이언트가 저장하고, 클라이언트가 서버에 요청할 때마다 서버가 갱신한다. 이를 통해 서버는 해당 클라이언트와의 상호작용 상태 정보를 저장할 수 있다.

## 예시

공백 인코딩 — "software design and architecture"는 다음 둘 다 유효하다.

```text
software%20design%20and%20architecture
software+design+and+architecture
```

쿼리 문자열 인코딩 — "color는 red, height는 very tall":

```text
?color=red&height=very+tall
```

예약 조회(GET) — 예약 번호 17021을 쿼리 문자열로 전달:

```text
GET /reservation?number=17021 HTTP/1.1
Host: camping.com
Accept: text/html
```

## 요약

- HTTP는 하이퍼텍스트를 비롯한 데이터가 인터넷에서 어떻게 통신·교환되는지 규정하는, 웹의 근간이 되는 프로토콜이다.
- URI는 리소스를 식별하고, URL은 식별에 더해 프로토콜·호스트·위치로 리소스를 찾게 해 준다. 모든 URL은 URI다.
- HTTP는 클라이언트/서버 관계로 요청·응답을 주고받으며, 신뢰성 있는 TCP(기본 포트 80) 위에서 동작한다.
- 요청은 요청 라인·헤더·빈 줄·(선택) 본문으로, 응답은 상태 라인·헤더·빈 줄·(선택) 본문으로 구성된다. `Host`·`Accept`는 요청 필수 헤더이고 본문이 있으면 `Content-Length`·`Content-Type`이 필수다.
- GET은 리소스 조회(본문 없음), POST는 서버가 정하는 위치에 생성·수정, PUT은 URI가 지정한 위치에 생성·갱신이다.
- HTTP는 무상태이므로 요청 간 관계를 보존하지 않으며, 상태 추적에는 쿠키를 사용한다.
