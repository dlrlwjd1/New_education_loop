# 4.1.8 – Remote Procedure Call (RPC)

## 개요

- 이기종 환경(heterogeneous environments)의 클라이언트와 서버가 네트워크로 통신하도록 돕는 미들웨어(middleware) 개념을 소개한다.
- 원격 프로시저 호출(Remote Procedure Call, RPC)은 네트워크 기술을 사용하는 현대 미들웨어의 기반이다.
- RPC는 클라이언트, 서버, 인터페이스 정의 언어(IDL)라는 세 주요 컴포넌트로 구성되며, 스텁(stub)이 네트워킹 세부 사항을 추상화한다.
- RPC 수행은 7단계로 진행되고, 원래 동기(synchronous) 설계였지만 현대 시스템은 비동기(asynchronous) 처리도 요구한다.

## 내용

### 배경: 이기종 클라이언트-서버 환경

인터넷의 급성장과 클라우드 서비스 비용 하락으로 Google Docs, PayPal, Amazon.com 같은 혁신적 웹 서비스가 늘었고, 사내 서비스도 사설 네트워크로 클라이언트-서버 통신을 한다. 많은 경우 클라이언트와 서버는 머신 아키텍처나 운영체제가 다른 **이기종 환경**에서 동작한다.

- 클라이언트 머신은 단일 사용자를 위해 설계되고 뛰어난 사용성(usability)에 집중하므로 OS가 직관적이다.
- 서버는 다수의 동시 사용자에게 컴퓨팅 파워를 제공해야 하고, 주로 시스템 관리자 등 IT 전문가가 사용하므로 UI에 더 많은 전문성이 요구될 수 있다.

컴퓨터 네트워크는 **분산 컴퓨팅(distributed computing)** — 네트워크 상의 컴퓨터들이 메시지를 주고받으며 통신하고 행동을 조율하는 시스템 아키텍처 — 의 성장을 가능하게 했다. 덕분에 계층별로 특정 관심사에 집중하는 티어드 아키텍처(tiered architecture)를 설계할 수 있게 되었고, 클라이언트와 서버가 더 특화되면서 오히려 서로를 이해하지 못해 통신할 수 없는 상황이 생겼다.

### 미들웨어 (Middleware)

이 문제의 해법이 미들웨어다. 미들웨어는 모든 클라이언트와 서버에 **공통 인터페이스(common interface)** 를 제공해 이기종 컴포넌트 간 통신을 관리한다.

- 이 아키텍처는 중재자(mediator) 디자인 패턴과 개념적으로 매우 유사하지만 훨씬 큰 규모다. 미들웨어 컴포넌트가 중재자 역할을 한다.
- 미들웨어는 전체 분산 시스템 사이에 공통 인터페이스를 제공해 대규모 통신을 가능하게 하고, 개발자가 아키텍처에 하위 시스템 티어 전체를 구현하지 않고도 시스템 기능에 접근할 수 있게 한다.
- 시스템이 n-티어(n-tier) 아키텍처로 가면서 미들웨어는 비즈니스 로직, 클라이언트 요청 분배, 인증(authentication)·인가(authorization) 처리까지 더 많은 기능을 캡슐화해야 하며, 따라서 새 미들웨어 아키텍처를 설계하거나 기존 것을 확장할 수 있어야 한다.

### RPC의 개념과 역사

RPC는 네트워크 시스템용 미들웨어 컴포넌트로 설계되었고 유연성과 사용성을 높이도록 확장되어 왔다. 이름 그대로, 클라이언트가 **서버에 구현된 프로시저를 호출**할 수 있게 한다.

- 클라이언트와 서버는 완전히 다른 머신에 있거나, 같은 머신의 서로 다른 가상 인스턴스(virtual instance)에 있다.
- 다른 머신이면 물리 주소 공간이 달라, 클라이언트는 호출하려는 프로시저의 물리 메모리 주소를 알 수 없다.
- 같은 머신의 다른 가상 인스턴스면 가상 주소 공간이 공유되지 않으며, OS가 각 인스턴스를 관리해 올바른 가상 주소를 찾는다.
- 두 경우 모두 클라이언트는 호출 대상 프로시저에 직접 접근할 수 없고, RPC의 주요 기능 중 하나가 이 호출을 성사시키는 것이다.

역사: 1980년대 Birrell과 Nelson이 다른 머신의 프로시저를 **투명하게(transparent)** 호출하는 방법으로 개발·소개했다. 초기 설계의 세 주요 컴포넌트는 다음과 같다.

- **클라이언트(client)**: 호출자(caller). 원격 호출을 만드는 컴포넌트
- **서버(server)**: 피호출자(callee). 호출되는 프로시저를 구현한 컴포넌트
- **인터페이스 정의 언어(Interface Definition Language, IDL)**: 클라이언트와 서버가 통신하는 언어

추가로 RPC는 클라이언트가 여러 서버에 연결할 수 있게 하는 이름·디렉터리 서비스(name and directory services)와 바인딩(binding) 방법을 포함할 수 있다.

RPC가 성공한 이유는 개발자에게 이미 익숙한 **프로시저 개념**을 사용했기 때문이다. 새 언어나 패러다임을 배울 필요가 없어 분산 시스템을 더 효율적으로 설계·구현할 수 있었다. RPC는 처음에는 미들웨어의 초석이 아니라 애플리케이션에 포함시키는 단순한 라이브러리 모음이었지만, 네트워크와 분산 시스템이 중요해지면서 대형 미들웨어 시스템을 지원하도록 확장되었다. 오늘날에는 데이터베이스 시스템의 저장 프로시저 호출(stored procedure call)이나 웹 서비스의 XML 메시지 등 다양한 형태로 쓰인다.

### RPC의 구성 요소: IDL, 스텁, 인터페이스 헤더

**IDL**은 가장 먼저 구현되는 컴포넌트다. 서버의 어떤 프로시저가 클라이언트에 제공되는지, 입력 파라미터와 반환 응답은 무엇인지 정의한다. 즉 IDL은 RPC의 명세(specification)다.

IDL을 컴파일하면 **클라이언트 스텁(client stub)**, **서버 스텁(server stub)**, **인터페이스 헤더(interface headers)** 가 생성되며, 실제 무거운 작업은 이들이 수행한다.

- **클라이언트 스텁**: 프로시저 호출의 프록시(proxy) 역할. 바인딩이라는 과정으로 서버와의 연결을 수립하고, 데이터를 XML 같은 표준화된 메시지 구조로 포맷하고, 원격 프로시저 호출을 전송하고, 서버 스텁의 응답을 수신한다.
- **서버 스텁**: 호출을 받아 원하는 프로시저를 실행한다. 원격 호출을 수신하는 코드를 담고, 메시지를 서버가 인식하는 데이터 형식으로 변환하며, 서버의 응답을 클라이언트 스텁으로 돌려보낸다.
- 각 스텁은 컴파일되어 클라이언트/서버 컴포넌트에 직접 링크된다. 클라이언트 스텁이 같은 주소 공간에 있으므로, 클라이언트가 원격 호출을 해도 애플리케이션에는 **로컬 프로시저 호출처럼** 보인다.
- 복잡한 스텁을 만들면 서버와 다른 환경에서 클라이언트를 개발할 수 있다. 예: Windows에서 동작하는 클라이언트 컴포넌트가 Unix에서 실행되는 서버 컴포넌트와 통신.
- 프로그래밍 언어와 운영 플랫폼이 많으므로 서로 통신 가능한 클라이언트-서버 스텁 쌍을 수동으로 개발하는 것은 비효율적이다. IDL이 구체적 프로그래밍 언어를 스텁의 중간 표현(intermediate representation)으로 매핑하므로 스텁을 생성할 수 있다.
- **인터페이스 헤더**: 컴파일 시점에 어떤 프로시저가 사용 가능한지 정의하는 코드 템플릿과 참조의 모음으로, 클라이언트·서버 컴포넌트 개발에 사용된다.

원격 프로시저 호출을 위한 기본 인터페이스 유형: 서버에서 원격 접근 가능한 프로시저를 클라이언트에 알려주는 **프로시저 등록(procedure registration)**, 실제로 서버에서 호출되는 **프로시저 호출(procedure call)**, 그리고 프로시저 호출과 같지만 브로드캐스트로 호출되는 **브로드캐스트 프로시저 호출(procedure call by broadcast)**.

스텁은 네트워킹 세부 사항을 모두 추상화해 개발자가 신경 쓰지 않게 하지만, 개발자가 클라이언트-서버 연결을 더 세밀하게 제어하고 싶다면 RPC는 연결 설정 구성을 허용한다.

### RPC 수행 7단계

1. **클라이언트의 호출**: 클라이언트 컴포넌트가 프로시저를 호출하고 인수를 클라이언트 스텁에 전달한다. 스텁이 클라이언트에 링크되어 있어 네트워크 연결이 필요 없고, 표준 프로시저 호출과 똑같다.
2. **마샬링(marshalling)**: 클라이언트 스텁이 파라미터를 표준화된 메시지 형식으로 변환해 메시지에 복사한다. 파라미터 데이터가 다른 애플리케이션과의 통신에 적합한 형식으로 변환되며, 사용 형식은 스텁을 컴파일한 IDL이 결정한다.
3. **전송과 바인딩(binding)**: 클라이언트 스텁이 주어진 바인딩 정보로 서버에 메시지를 보낸다. 바인딩은 클라이언트가 서버에 연결하는 과정으로, 정적 또는 동적으로 할 수 있다.
   - **정적 바인딩(static binding)**: 하드코딩된 바인딩 정보(예: 서버 IP 주소와 포트)를 사용. 단순하고 효율적이지만 클라이언트가 서버에 결합(coupled)된다. 서버가 오프라인이 되거나 연결 정보가 바뀌면 연결할 수 없고, 클라이언트가 항상 특정 서버에 연결하므로 서버 이중화(redundancy)도 불가능하다.
   - **동적 바인딩(dynamic binding)**: 더 복잡하며 티어드 아키텍처에 **이름·디렉터리 서버(name and directory server)** 라는 계층을 추가한다. 이 계층은 어떤 서버가 바인딩되었는지 추적하고 서버들 간 부하를 분산하며, 서버가 바뀌면 바인딩 정보를 변경할 수 있다.
   - 어느 방식이든 클라이언트 개발자는 바인딩을 신경 쓸 필요가 없다. 클라이언트 스텁이 정적 바인딩 또는 동적 바인딩 계층과의 통신을 책임진다.
4. **언마샬링(unmarshalling)과 서버 호출**: 메시지가 서버에 도착하면 서버 스텁이 수신한다. 마샬링된 인수를 서버 측 프로시저 호출에 사용 가능한 형식으로 되돌리는 언마샬링을 수행한 뒤, 서버 컴포넌트의 프로시저를 호출하며 인수를 전달한다. 서버 스텁이 서버 컴포넌트에 링크되어 있어 이 호출도 일반 프로시저 호출처럼 보인다.
5. **결과 반환과 마샬링**: 프로시저 실행이 끝나면 서버 컴포넌트가 결과를 서버 스텁에 반환하고, 스텁은 결과를 표준화된 형식으로 마샬링한다. 연결은 클라이언트가 이미 수립했으므로 서버 스텁은 클라이언트에 바인딩할 필요 없이 그 연결로 메시지를 돌려보내기만 하면 된다.
6. **클라이언트 스텁의 언마샬링**: 클라이언트 스텁이 메시지의 결과를 언마샬링해 클라이언트 컴포넌트에 반환한다.
7. **연결 종료**: 클라이언트가 서버와의 연결을 닫을 수 있다.

### 동기 vs 비동기 RPC

RPC는 원래 **동기(synchronous)** 로 설계되었다. 원격 호출 동안 클라이언트 컴포넌트는 응답을 기다리며 실행을 멈춘다. 이를 **블로킹(blocking)** 이라고 한다 — 서버가 결과를 반환할 때까지 클라이언트는 다른 작업을 수행할 수 없다. 구현은 단순하지만 항상 실용적이지는 않으며, 여러 문제를 낳는다.

- 서버가 응답을 영영 반환하지 않으면? 클라이언트는 무한정 기다리게 된다.
- 얼마나 기다려야 하나? 어떤 프로시저는 더 오래 걸리고, 서버가 과부하이면 응답 생성이 더 오래 걸릴 수 있다.
- 재전송해야 하나? 프로시저에 따라 다르다. 예컨대 은행 거래에 대한 원격 호출은 재전송하면 시스템이 그 거래를 여러 번 수행하게 되므로 재전송하면 안 된다.
- 타임아웃, 재전송, 서버 예외 메시지를 클라이언트가 어떻게 처리할지 여러 경우를 검토해야 한다.

현대 시스템은 **비동기(asynchronous)** 원격 호출 처리가 필요하다. 비동기 시스템은 논블로킹(non-blocking)이다 — 클라이언트가 서버 응답을 기다리지 않고 다른 작업으로 넘어갈 수 있다.

- 분산 시스템의 컴포넌트들이 서로 더 독립적으로 동작할 수 있게 하는 중요한 아이디어다.
- 한 작업이 끝나기를 기다리지 않고 다른 작업을 시작할 수 있어 병렬 수행이 가능하다.
- 다만 비동기 동작은 시스템에 복잡성을 더한다. 대기 중인 여러 작업에 시스템 자원을 어떻게 할당할지 관리해야 하고, 비동기 작업으로 시스템을 과부하시키면 전체 성능이 오히려 떨어질 수 있다. 예를 들어 스레드 간 비동기 작업 조율이 부적절하면, 한 스레드의 작업이 다른 스레드의 입력을 필요로 할 때 병목이 생길 수 있다.

## 요약

- 이기종 환경의 클라이언트와 서버는 미들웨어가 제공하는 공통 인터페이스를 통해 통신하며, 이는 중재자 패턴의 대규모 버전과 유사하다.
- RPC는 클라이언트가 서버의 프로시저를 마치 로컬 호출처럼 투명하게 호출하게 하는 미들웨어의 기반 기술로, 클라이언트·서버·IDL로 구성된다.
- IDL 컴파일로 생성되는 클라이언트/서버 스텁이 마샬링·언마샬링, 바인딩, 전송 등 네트워킹 세부 사항을 담당한다.
- 바인딩은 하드코딩된 정적 바인딩과 이름·디렉터리 서버를 통한 동적 바인딩(부하 분산·서버 변경 대응 가능)으로 나뉜다.
- 원래의 동기(블로킹) RPC는 무응답·타임아웃·재전송 문제를 안고 있어, 현대 시스템은 비동기(논블로킹) 처리를 요구하지만 그만큼 자원 관리 복잡성이 커진다.
