# 2.2.5 – Observer Pattern

## 개요

- 옵서버 패턴(Observer Pattern)은 주제(Subject)의 상태 변화가 있을 때 주제가 등록된 옵서버(Observer)들에게 알림(notify)을 보내는 행위 패턴이다.
- 옵서버가 주기적으로 확인(polling)하는 대신, 변화가 생길 때 주제가 먼저 알려주는 구독(subscribe) 구조다.
- 블로그(Subject)와 구독자(Observer) 예시로 UML 클래스 다이어그램, 시퀀스 다이어그램, Java 코드를 살펴본다.

## 내용

### 문제 상황 — 블로그 새 글 확인

- 좋아하는 블로그가 있어 매일 여러 번 방문해 새 글을 확인하다가 이 루틴에 지친다.
- 첫 번째 해결책: 몇 분의 1초마다 블로그를 확인하는 스크립트 작성 → 대부분의 사이트는 이런 요청 폭주를 반기지 않고 IP 주소를 차단할 것이다.
- 두 번째 해결책: 1시간에 한 번 확인하는 스크립트 → 좋아하는 TV 프로그램의 실시간 포스트처럼 라이브로 올라오는 글을 놓치게 된다.
- 더 나은 해결책: 새 글이 추가될 때마다 블로그가 알려주는 것이다. 블로그를 구독(subscribe)하면, 새 글이 게시될 때마다 블로그가 나를 포함한 각 구독자에게 알린다. 어떤 간격으로 정보를 끌어오는(pull) 대신, 새 콘텐츠가 생성될 때 알림을 받는다.

### 주제와 옵서버의 관계

- 예시에서 주제(Subject)인 블로그는 옵서버들의 목록을 유지한다. 이 예에서 옵서버는 블로그의 구독자(subscriber)로 볼 수 있다.
- 옵서버들은 새 글 추가처럼 블로그 상태(state)에 변화가 생기면 블로그가 알려주기를 의존한다.

### 예시 설계

- Subject 상위 클래스는 세 가지 메서드를 정의한다.
  - 새 옵서버의 구독을 허용하는 메서드
  - 기존 옵서버의 구독 해지를 허용하는 메서드
  - 새 블로그 글에 대해 모든 옵서버에게 알리는 메서드
- 이 상위 클래스는 모든 옵서버를 추적하는 속성(attribute)도 가진다.
- Observer 인터페이스에는 옵서버가 스스로 갱신(update)하도록 통지받는 메서드를 둔다.
- Blog 클래스는 Subject 상위 클래스의 하위 클래스가 되고, Subscriber 클래스는 Observer 인터페이스를 구현한다. 이 설계 요소들이 블로그-구독자 같은 주제-옵서버 관계를 형성하는 핵심이다.

### 시퀀스 다이어그램(sequence diagram)

- 옵서버 패턴을 적용한 시퀀스 다이어그램에는 두 주요 역할이 있다: Subject(블로그)와 Observer(구독자).
- 흐름:
  1. 주제-옵서버 관계를 형성하려면 구독자가 블로그를 구독(subscribe)해야 한다.
  2. 블로그는 변화가 발생했음을 구독자들에게 알릴 수 있어야 한다. 모든 구독자를 일관성 있게(consistent) 유지하는 것이 notify 함수의 역할이며, 이 메서드는 구독자가 알아야 할 변화가 준비됐을 때만 호출된다.
  3. 변화가 생기면 블로그가 update 호출로 구독자들에게 알리고, 구독자들은 getState 호출로 블로그의 상태를 가져온다. 구독자들이 최신 정보를 받도록 하는 것은 블로그의 몫이다.
  4. 구독자가 블로그 콘텐츠가 마음에 들지 않으면 구독 해지(unsubscribe)할 방법이 필요하다. 시퀀스 다이어그램의 마지막 호출로, 구독자에게서 시작되어 블로그의 구독자 목록에서 자신을 제거하도록 알린다.
- 이것이 옵서버 디자인 패턴의 핵심 행동이다.

### UML 클래스 다이어그램으로 일반화

- Subject 상위 클래스는 세 메서드를 가진다: registerObserver(옵서버 등록), unregisterObserver(옵서버 해제), notify(알림). 모두 주제가 옵서버들과 관계 맺는 데 필수적이다.
  - Subject의 하위 클래스인 Blog는 이 메서드들을 상속받아 구독·구독 해지·구독자 알림에 사용한다.
- Observer 인터페이스에는 update 메서드 하나만 있다. 옵서버는 항상 스스로 갱신할 방법이 있어야 한다. 갱신하라는 지시를 받을 능력이 없다면 옵서버는 주제의 변화를 알 수 없다.
- Subscriber 클래스는 Observer 인터페이스를 구현해 update 메서드의 본문을 제공하고, 블로그에서 무엇이 바뀌었는지 얻는다.
- 한 주제에는 어느 시점이든 0개 이상의 옵서버가 등록되어 있을 수 있다.

### Java 코드 구조

- Subject 상위 클래스:
  - registerObserver 메서드는 옵서버를 옵서버 목록에 추가한다.
  - unregisterObserver 메서드는 목록에서 옵서버를 제거한다.
  - notify 메서드는 목록의 각 옵서버에 대해 update를 호출한다.
- Blog 클래스는 Subject의 하위 클래스로, registerObserver·unregisterObserver·notify를 상속받고 블로그 관리와 글 게시 같은 나머지 책임을 가진다.
- Observer 인터페이스는 모든 옵서버 객체가 같은 방식으로 행동하도록 보장한다. 옵서버 클래스는 update 메서드 하나만 구현하면 된다. update는 주제가 호출하며, 주제는 변화가 일어나면 모든 옵서버가 스스로 갱신하도록 통지받게 한다.
- Subscriber 클래스는 Observer 인터페이스를 구현하며, 블로그가 변화를 알릴 때 이 update 메서드가 호출된다.

### 패턴의 가치

- 여러 객체가 한 객체의 상태에 의존한다는 것을 안다면 옵서버 패턴의 가치는 더 뚜렷해진다. 옵서버 객체들을 일일이 개별 관리하는 대신, 주제가 그들을 관리하며 필요할 때 옵서버들이 스스로 갱신하도록 한다.
- 시스템 구현 시간을 크게 절약할 수 있으며, 행위 패턴으로서 시스템 전반에 변화 알림을 관리 가능하고 통제된 방식으로 배포하고 처리하기 쉽게 해준다.

## 예시

강의에서 설명한 Subject 상위 클래스, Observer 인터페이스, Blog·Subscriber 클래스 구조를 Java 코드로 옮기면 다음과 같다.

```java
import java.util.ArrayList;
import java.util.List;

public class Subject {
    // 등록된 모든 옵서버를 추적하는 속성
    private final List<Observer> observers = new ArrayList<>();

    // 옵서버를 목록에 추가한다
    public void registerObserver(Observer observer) {
        observers.add(observer);
    }

    // 옵서버를 목록에서 제거한다
    public void unregisterObserver(Observer observer) {
        observers.remove(observer);
    }

    // 목록의 각 옵서버에 대해 update를 호출한다
    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update();
        }
    }
}
```

```java
public interface Observer {
    // 주제가 변화를 알릴 때 호출되는 유일한 메서드
    void update();
}
```

```java
public class Blog extends Subject {
    // registerObserver, unregisterObserver, notifyObservers를 상속받고
    // 블로그 관리와 글 게시 등 나머지 책임을 가진다
    private String state;

    public String getState() {
        return state;
    }

    public void post(String newPost) {
        this.state = newPost;
        notifyObservers();  // 새 글이 게시되면 구독자들에게 알린다
    }
}
```

```java
public class Subscriber implements Observer {
    private final Blog blog;

    public Subscriber(Blog blog) {
        this.blog = blog;
    }

    @Override
    public void update() {
        // 블로그가 변화를 알리면 상태를 가져와 스스로 갱신한다
        String latest = blog.getState();
        System.out.println("New blog post: " + latest);
    }
}
```

Subject가 옵서버 목록 관리와 알림을 담당하므로, Blog는 이를 상속만 하면 되고 Subscriber는 update 구현만 제공하면 된다.

## 요약

- 옵서버 패턴은 옵서버가 주기적으로 확인(polling)하는 대신, 주제(Subject)가 상태 변화 시 등록된 옵서버들에게 알리는(push) 행위 패턴이다.
- Subject 상위 클래스는 옵서버 목록 속성과 registerObserver·unregisterObserver·notify 메서드를 가지며, Observer 인터페이스는 update 메서드 하나만 요구한다.
- 예시에서 Blog는 Subject의 하위 클래스, Subscriber는 Observer 인터페이스의 구현 클래스다.
- 시퀀스: 구독(subscribe) → 변화 발생 시 notify → 각 옵서버에 update 호출 → 옵서버가 getState로 최신 상태 획득 → 원하면 구독 해지(unsubscribe).
- 여러 객체가 한 객체의 상태에 의존할 때, 주제가 옵서버들을 관리하게 하면 개별 관리 없이 일관된 알림 처리가 가능하다.
