# 2.2.4 – Command Pattern

## 개요

- 커맨드 패턴(Command Pattern)은 요청(request)을 그 자체의 객체(command object)로 캡슐화(encapsulate)하는 행위 패턴이다.
- 발신자(sender)와 수신자(receiver) 사이에 커맨드 객체를 두어, 발신자가 수신자와 호출할 메서드를 알 필요가 없게 한다.
- 요청을 객체로 다루면 저장·스케줄링, 실행 취소/재실행(undo/redo), UI 로직 분리 등 단순 메서드 호출로는 불가능한 기능을 구현할 수 있다.

## 내용

### 패턴의 기본 아이디어 — 상사와 메모

- 보통 한 객체가 다른 객체에 작업을 요청할 때는 첫 번째 객체가 두 번째 객체의 메서드를 직접 호출하고, 두 번째 객체가 작업을 완료한다. 이때 발신자 객체는 수신자 객체와 직접 통신해야 한다.
- 커맨드 패턴은 두 객체가 직접 통신하는 대신 발신자와 수신자 사이에 커맨드 객체를 만든다. 이렇게 하면 발신자는 수신자와 호출할 메서드를 알 필요가 없다.
- 강의는 회사의 상사가 메모(memo)로 업무를 처리하는 것에 비유한다. 상사가 한 직원에게는 회의 일정을 잡게 하고 다른 직원에게는 중요한 고객과 이야기하게 해야 할 때, 바쁜 상사는 어떤 직원이 무슨 일을 하는지 기억하거나 직접 찾아가 부탁할 시간이 없다. 대신 할 일을 스티키 노트에 적으면 비서(secretary)가 그것을 처리할 수 있는 직원에게 전달한다. 상사가 명령을 메모로 캡슐화하는 것은 소프트웨어에서 요청을 커맨드 객체로 캡슐화하는 것과 같다.

### 인보커(invoker)

- 앞의 예에서 상사가 메모를 만들면, 그 메모를 실제 수신자에게 전달해 완료되게 하는 비서 같은 존재가 필요하다.
- 소프트웨어에서도 발신자 객체가 커맨드 객체를 만들지만, 커맨드 객체가 할 일을 실제로 수행하게 하고 특정 수신자 객체를 호출해 작업을 완료하게 만드는 것은 무엇인가? 여기서 인보커(invoker)가 등장한다. 커맨드 패턴에는 커맨드 객체를 호출(invoke)해 맡은 작업을 완료시키는 객체, 즉 인보커가 있다.
- 커맨드 매니저(command manager)를 둘 수도 있는데, 이는 커맨드들을 추적하고 조작하고 호출하는 역할을 한다. 인보커는 메모를 추적해 적절한 시점에 실행되도록 하는 비서와 같다.

### 용도 1 — 요청의 저장과 스케줄링

- 객체가 다른 객체의 메서드를 호출하는 방식에서는 메서드 호출 자체에 무언가를 할 수 없다. 요청을 커맨드 객체로 바꾸면 다른 객체를 다루듯 다룰 수 있다.
- 커맨드 객체를 리스트에 저장하거나, 완료되기 전에 조작하거나, 큐(queue)에 넣어 서로 다른 시점에 완료되도록 스케줄링할 수 있다.
- 예: 캘린더 소프트웨어에서 알람을 울리게 할 때, 이벤트가 생성되면 알람을 울리는 커맨드 객체를 만들고 큐에 넣어 이벤트가 실제로 발생할 시점에 나중에 실행되게 한다.

### 용도 2 — 실행 취소/재실행(undo/redo)

- 문서 편집에서 편집을 취소/재실행하듯 커맨드를 취소하거나 재실행할 수 있게 한다.
- 텍스트 편집 소프트웨어 예시: 텍스트 삭제, 글꼴 변경 등 다양한 커맨드가 있다. redo/undo 기능을 위해 두 개의 리스트가 필요하다.
  - history 리스트: 실행된 모든 커맨드를 보관한다.
  - redo 리스트: 취소(undo)된 커맨드를 넣는 데 사용한다.
- 동작 방식:
  - 커맨드가 요청될 때마다 커맨드 객체가 생성되고 실행되며, 완료된 커맨드는 history 리스트로 간다.
  - 사용자가 undo를 원하면, 소프트웨어는 history 리스트에서 가장 최근에 실행된 커맨드를 찾아 그 커맨드에게 스스로 취소(unexecute)하도록 요청한 뒤 redo 리스트에 넣는다.
  - redo가 필요하면 redo 리스트에서 가장 최근에 취소된 커맨드를 가져와 다시 실행하게 하고, 다시 history 리스트로 옮긴다.
  - 새 커맨드가 실행될 때마다 redo 리스트는 비워야 한다. 보통 새 편집이 이루어진 뒤에는 이전 편집을 redo할 수 없기 때문이다.
- 이 undo/redo 기능은 텍스트 편집기에만 국한되지 않고 어떤 종류의 애플리케이션에도 적용할 수 있다.
- 커맨드를 로그(log) 리스트에 저장할 수도 있다. 프로그램이 예기치 않게 충돌(crash)하면 사용자가 최근 커맨드들을 다시 실행(redo)할 수 있게 해준다.

### UML 구조

- Command 상위 클래스가 있고, 모든 커맨드는 이 상위 클래스의 하위 클래스 인스턴스다. 상위 클래스는 커맨드들의 공통 행동을 정의한다.
- 각 커맨드는 세 메서드를 가진다.
  - execute: 커맨드가 해야 할 실제 작업을 수행한다.
  - unexecute: 커맨드를 취소하는 작업을 수행한다.
  - isReversible: 커맨드가 되돌릴 수 있는지(reversible) 판별하며, 취소 가능하면 true를 반환한다.
- 취소할 수 없는 커맨드도 있다. 예를 들어 저장(save)은 취소가 의미 없다 — 이미 저장된 작업을 "저장 취소"할 수는 없다.
- 구체 커맨드 클래스(concrete command class)들은 실제 작업 완료를 위해 특정 수신자(receiver) 클래스를 호출한다.

### 구체 커맨드 예 — PasteCommand

- 텍스트 붙여넣기(paste) 커맨드를 보면 커맨드 객체가 어떠해야 하는지 알 수 있다.
- PasteCommand는 Command 상위 클래스를 상속(extends)한다.
- 텍스트가 삽입될 위치와 삽입될 내용을 추적한다. 이는 커맨드 객체의 매우 중요한 측면이다 — 커맨드가 되돌릴 수 있으려면 문서의 현재 상태에 대한 많은 세부 정보를 추적해야 한다.
- 붙여넣기는 방금 붙여넣은 것을 삭제할 수 있으므로 되돌릴 수 있는 커맨드다. 따라서 isReversible이 호출되면 true를 반환하고, 텍스트가 어디에 붙여넣어졌는지 추적해야 한다.
- execute와 unexecute가 호출되면, 커맨드 객체가 수신자(이 경우 문서 document)를 호출해 실제 작업을 완료한다.

### 인보커의 소스 코드 흐름

- 인보커 코드는 단순한 단계로 이루어진다.
  1. history 리스트와 redo 리스트를 관리하는 객체인 커맨드 매니저(command manager)에 대한 참조를 가진다.
  2. 커맨드 완료에 필요한 정보로 커맨드 객체를 생성한다.
  3. 커맨드 매니저를 호출해 커맨드를 실행한다.

### 커맨드 패턴의 이점

- 메서드 호출로는 할 수 없는 방식으로 커맨드를 객체로서 조작할 수 있다 — 큐에 넣기, undo/redo 기능 추가 등.
- 소프트웨어의 객체들을 분리(decouple)한다. 요청하려는 클래스는 시스템의 다른 객체들을 알 필요가 없다. 커맨드 객체만 만들면, 커맨드 객체가 수신자 객체를 호출해 일을 처리한다. 상사가 어떤 직원이 그 일을 처리할지 몰라도 되는 메모 예시와 같다.
- 사용자 인터페이스(UI)에서 로직을 분리할 수 있다. 보통 요청 처리 코드는 UI의 이벤트 핸들러(event handler)에 들어가지만, 애플리케이션 로직이 UI 클래스에 많이 들어 있는 것은 바람직하지 않다. UI 클래스는 사용자와 정보를 주고받는 UI 문제만 다뤄야 한다.
  - 커맨드 패턴은 커맨드 객체들이 들어가는 새로운 계층(layer)을 만든다. 버튼이 클릭될 때마다 커맨드 객체를 생성하고, 로직은 거기에 둔다.
  - 커맨드 객체는 UI와 독립적이므로 새 버튼 추가 같은 UI 변경이 더 쉽고 빨라진다.
- 시스템의 모든 서비스를 각각 객체로 만들어 훨씬 유연한 기능을 구현할 수 있다. 이 패턴을 적용하면 소프트웨어가 더 다재다능(versatile)해지고 유지보수가 쉬워진다.

## 예시

강의에서 설명한 Command 상위 클래스와 PasteCommand의 구조를 Java 코드로 옮기면 다음과 같다.

```java
public abstract class Command {
    // 커맨드가 해야 할 실제 작업을 수행한다
    public abstract void execute();

    // 커맨드를 취소하는 작업을 수행한다
    public abstract void unexecute();

    // 커맨드를 되돌릴 수 있으면 true를 반환한다
    public abstract boolean isReversible();
}
```

```java
public class PasteCommand extends Command {
    private final Document document;  // 수신자(receiver)
    private final int position;       // 텍스트가 삽입될 위치
    private final String text;        // 삽입될 텍스트

    public PasteCommand(Document document, int position, String text) {
        this.document = document;
        this.position = position;
        this.text = text;
    }

    @Override
    public void execute() {
        // 실제 작업은 수신자인 document가 수행한다
        document.insert(position, text);
    }

    @Override
    public void unexecute() {
        // 방금 붙여넣은 텍스트를 삭제해 되돌린다
        document.delete(position, text.length());
    }

    @Override
    public boolean isReversible() {
        // 붙여넣기는 되돌릴 수 있는 커맨드다
        return true;
    }
}
```

인보커(invoker)는 커맨드 매니저(command manager)에 대한 참조를 갖고, 필요한 정보로 커맨드 객체를 생성한 뒤 커맨드 매니저를 호출해 실행한다. 커맨드 매니저는 history 리스트와 redo 리스트를 관리한다.

## 요약

- 커맨드 패턴은 요청을 커맨드 객체로 캡슐화해 발신자와 수신자 사이에 두는 행위 패턴이다.
- 인보커(invoker)가 커맨드 객체를 호출해 작업을 완료시키고, 커맨드 매니저(command manager)가 커맨드를 추적·조작·호출한다.
- 요청이 객체가 되면 리스트 저장, 실행 전 조작, 큐를 통한 스케줄링이 가능해진다.
- undo/redo는 history 리스트와 redo 리스트, 그리고 각 커맨드의 execute/unexecute/isReversible 메서드로 구현하며, 새 커맨드 실행 시 redo 리스트를 비운다.
- 이 패턴은 객체 간 결합을 줄이고(decoupling), 애플리케이션 로직을 UI 이벤트 핸들러에서 분리된 커맨드 계층으로 옮겨 유지보수를 쉽게 한다.
