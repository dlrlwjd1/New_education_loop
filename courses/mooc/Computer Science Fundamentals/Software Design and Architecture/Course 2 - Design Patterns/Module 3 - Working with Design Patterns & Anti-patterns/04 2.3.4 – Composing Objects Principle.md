# 2.3.4 – Composing Objects Principle

## 개요

- 상속(inheritance)은 코드 재사용에 좋지만 슈퍼클래스와 서브클래스를 강하게 결합(tight coupling)시키는 비용이 따른다.
- 객체 합성 원칙(Composing Objects Principle)은 "클래스는 상속이 아니라 집약(aggregation)을 통해 코드 재사용을 달성해야 한다"고 말한다.
- 합성의 장점(느슨한 결합, 유연성, 런타임 행동 변경)과 단점(모든 행동의 구현을 직접 제공해야 함)을 비교한다.

## 내용

### 배경 — 상속이 만드는 결합

객체지향 시스템에서 디자인 패턴이 다루려는 흔한 문제는 강한 결합을 줄이는 것이다. 모든 디자인 패턴이 사용하는 설계 원칙들은 결합을 관리하는 서로 다른 방법을 정의한다. 결합이 적을수록 시스템은 더 유연해지고, 새 기능 통합 같은 기존 코드베이스 변경을 잘 감당할 수 있다. 우리가 살펴본 디자인 패턴들은 간접화(indirection)의 수단으로 일반화(generalization), 추상화(abstraction), 다형성(polymorphism)을 많이 사용한다.

상속은 높은 코드 재사용을 달성하는 훌륭한 방법이지만, 슈퍼클래스와 서브클래스를 강하게 결합시키는 비용이 따른다. 서브클래스가 슈퍼클래스를 상속하면 접근 제한자(access modifier)가 private이 아닌 한 슈퍼클래스의 모든 속성과 메서드에 대한 지식과 접근 권한을 얻는다. 상속 단계가 여러 층이면, 상속 트리 맨 아래의 서브클래스가 모든 슈퍼클래스의 속성과 행동에 접근할 수 있는 길이 생길 수 있다.

### 원칙의 내용

이를 피하기 위해 **객체 합성 원칙(Composing Objects Principle)** 을 사용하면 상속 없이도 높은 코드 재사용을 얻을 수 있다. 이 원칙은 **클래스가 상속이 아니라 집약(aggregation)을 통해 코드 재사용을 달성해야 한다**고 말한다.

컴포지트 패턴(composite design pattern)과 데코레이터 패턴(decorator design pattern)이 이 원칙을 사용한다. 두 패턴 모두 구체 클래스들을 합성해 더 복잡한 객체를 만들며, 전체 행동은 합성된 개별 객체들의 합에서 나온다. 한 객체는 다른 객체를 재사용·집약해 특정 요청을 그 객체에 위임(delegate)할 수 있다. 구체 클래스가 다른 구체 클래스에 작업을 위임하도록 시스템을 설계하자는 것이며, **위임은 상속보다 느슨한 결합을 제공**한다.

### 장점

1. **느슨한 결합**: 집약과 위임은 상속보다 결합이 적다. 합성된 클래스들은 속성이나 행동 구현을 공유하지 않으므로 서로 더 독립적이다. 서로 팔 길이만큼 떨어진(arms length) 관계여서 변경이 쉽다. 반면 상속에서는 슈퍼클래스의 모든 서브클래스가 그 슈퍼클래스에 강하게 결합된다. 클래스들이 어떻게 합성될지는 설계 단계에서 결정된다. UML 클래스 다이어그램에서 객체는 재귀적·균일하게(recursively and uniformly) 합성되거나, 일관된 타입의 객체들로 합성될 수 있다.
2. **유연성**: 설계 단계에서 클래스들을 분리해 두는 것이 더 쉽고 자연스럽다. 합성은 상속처럼 두 클래스의 공통점을 억지로 찾아 결합할 필요가 없고, 아무것도 공유하지 않으면서 함께 동작하는 클래스를 설계할 수 있다. 시스템 요구사항이 바뀔 때도 도움이 된다. 상속을 썼다면 상속 트리를 재구성해야 할 수도 있다.
3. **런타임 행동 변경**: 객체 합성은 사실상 실행 시간(run time)에 객체의 행동을 동적으로 바꿀 수 있게 한다. 객체들을 합성해 새로운 행동 조합을 만들 수 있다. 상속에서는 클래스의 행동이 컴파일 시간(compile time)에 정의되므로 프로그램 실행 중에는 동작 방식을 바꿀 수 없다.

### 단점

합성의 가장 큰 단점은 **상속으로 코드를 공유하는 이점 없이 모든 행동의 구현을 직접 제공해야 한다**는 것이다. 여러 클래스에 걸쳐 매우 비슷한 구현이 존재할 수 있다. 상속에서는 공유 행동의 구현을 각 서브클래스에 제공할 필요 없이 슈퍼클래스 안의 공통 구현에 접근하면 된다. 모든 클래스에 구현을 제공하려면 시간과 자원이 들고, 같은 행동의 여러 구현을 작성하는 프로그래머가 있다는 것은 다른 기능을 맡을 프로그래머가 한 명 줄어든다는 뜻이다.

### 상속과의 선택

객체 합성 원칙은 코드를 재사용하고 유연하게 행동을 쌓아 올리는 데 상속보다 많은 장점이 있다. 그렇다고 상속을 절대 쓰지 말라는 뜻은 아니다. 합성과 상속은 각자의 자리가 있다. 합성은 재사용성을 유지하면서 더 나은 유연성과 더 적은 결합을 주지만, 항상 상속보다 우선해야 하는 것은 아니다. 어떤 원칙이 적절한지 결정하려면 시스템의 필요를 검토해야 한다.

- 관련 있는 클래스들의 집합인가, 관련 없는 클래스들인가?
- 그들 사이의 공통 행동은 무엇인가?
- 특정 경우를 처리할 특화된(specialized) 클래스가 필요한가, 아니면 같은 행동의 다른 구현만 필요한가?

이런 질문들을 스스로 던지며 설계해야 하고, 각 설계 원칙이 무엇을 권하는지 알면 마주치는 설계 문제에 어떻게 대처할지 이해하게 된다.

## 요약

- 객체 합성 원칙(Composing Objects Principle): 상속 대신 집약(aggregation)과 위임(delegation)으로 코드를 재사용한다.
- 상속의 강한 결합 없이 코드 재사용 수단을 제공하고, 실행 시간에 객체가 동적으로 행동을 추가할 수 있게 하며, 시스템에 더 많은 유연성을 준다. 그만큼 시스템 업데이트에 드는 시간이 줄어든다.
- 단점: 상속의 코드 공유 없이 모든 행동의 구현을 직접 제공해야 하므로 비슷한 구현이 중복되고 시간·자원이 든다.
- 컴포지트 패턴과 데코레이터 패턴이 이 원칙의 대표적 사용 예다.
- 합성과 상속 모두 쓰임새가 있으므로, 시스템의 필요를 검토해 적절한 쪽을 선택해야 한다.
