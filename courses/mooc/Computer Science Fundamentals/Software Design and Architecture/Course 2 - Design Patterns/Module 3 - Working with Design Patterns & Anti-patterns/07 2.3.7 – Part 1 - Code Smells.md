# 2.3.7 – Part 1 - Code Smells

## 개요

- 리팩토링(refactoring)은 코드의 외부 동작은 바꾸지 않으면서 내부 구조를 개선하는 과정이며, 나쁜 코드의 패턴인 안티패턴(anti-pattern), 즉 코드 스멜(code smell)을 찾아내는 것에서 시작한다.
- 코드 스멜이라는 용어는 Martin Fowler의 책 *Refactoring*에서 나왔으며, 이 책은 각 스멜을 개선하는 리팩토링도 제공한다.
- 1부에서는 주석(comments), 중복 코드(duplicated code), 긴 메서드(long method), 거대 클래스(large class), 데이터 클래스(data class), 데이터 뭉치(data clumps), 긴 매개변수 목록(long parameter list)을 다룬다.

## 내용

### 리팩토링(Refactoring)

아무리 잘 설계해도 코드에는 여전히 변경이 필요하다. 처음부터 완벽하게 만드는 것은 어렵거나 불가능하다. 리팩토링은 **코드의 외부 동작(external behavior)은 바꾸지 않으면서 내부 구조(internal structure)를 개선하는 변경 과정**이다. 코드 구조에 작고 점진적인 변경을 가하고, 그 변경이 동작을 바꾸지 않았는지 자주 테스트하며 진행한다.

코드가 완성된 뒤에 리팩토링 대공사를 하는 것은 바람직하지 않다. 시간이 많이 들고 고치는 것보다 더 많은 문제를 만들 수 있다. **기능을 추가할 때 리팩토링을 해야 한다.** 그 시점의 리팩토링은 기능 추가를 더 쉽게 만들고, 나중에 전면 개편이 필요해지는 상황을 막아 준다.

### 안티패턴과 코드 스멜

설계에서 패턴이 나타나듯 나쁜 코드의 패턴도 나타나는데, 이를 **안티패턴(anti-pattern)** 이라 한다. 이런 안티패턴 다수가 Martin Fowler의 책 *Refactoring*에서 식별되었고, 그는 이를 **코드 스멜(code smell)** 이라 불렀다. 이 책은 나쁜 코드의 패턴을 설명할 뿐 아니라 그 냄새를 개선하기 위한 리팩토링도 제공하므로 개발자에게 유용한 자료다. 코드 스멜의 목적은 공항의 마약 탐지견처럼, 코드에 있어서는 안 되는 나쁜 코딩 관행을 냄새로 찾아내는 것이다.

### 주석(Comments)

가장 흔한 나쁜 코드의 예가 주석이다.

- **주석이 없는 코드**: 코드가 무엇을 하는지(해야 하는지) 이해하기 어렵게 만든다. 프로젝트에 새로 합류한 개발자, 코드를 통합해야 하는 팀원, 심지어 자기 코드의 동작을 잊은 자신에게도 문제다.
- **주석이 너무 많은 코드**: 역시 문제다. 코드가 바뀌면서 주석이 코드와 어긋날(out of sync) 수 있다. **주석은 나쁜 냄새 나는 코드의 탈취제(deodorant)** 라고 할 수 있다. 많은 개발자가 코드가 무엇을 하는지 설명하는 주석을 잔뜩 달아 나쁜 설계를 덮으려 한다. 복잡한 설계를 설명하는 주석이 있다면 나쁜 설계를 덮고 있을 가능성이 높다. "이것을 잊지 말 것", "여기를 바꾸면 다른 메서드의 코드도 갱신할 것" 같은 리마인더 주석도 나쁜 코드의 지표다.
- **언어의 한계를 설명하는 주석**: 설계를 설명하는 주석은 프로그래밍 언어가 적절하지 않다는 신호일 수 있다. 언어가 적용하려는 설계 원칙을 지원하지 않거나, 설계에 맞지 않는 언어를 쓰고 있는 것이다. 예로 Java 초기에는 제네릭(generics) 개념이 없어 개발자들이 타입 캐스팅 시 무엇을 하는지 주석으로 설명해야 했다. 결국 제네릭이 Java에 들어왔고, 성숙한 언어가 된 지금은 변명의 여지가 없다. 이는 신생 언어에서 흔한 일이다.
- **주석의 올바른 용도**: 주석을 아예 쓰지 말라는 뜻이 아니다. 주석은 시스템의 API(application programmer interface)를 문서화하거나, 특정 자료구조·알고리즘을 선택한 근거(rationale)를 기록하는 데 매우 유용하며, 다른 사람이 코드를 쉽게 쓸 수 있게 한다. 프로그래밍의 많은 것처럼 효과적인 주석의 균형점을 찾아야 한다.

### 중복 코드(Duplicated Code)

비슷하지만 조금씩 다른 코드 블록이 소프트웨어 여러 곳에 나타나는 것이다. 객체지향 프로그래밍이나 디자인 패턴을 배우기 전의 자기 코드에서 봤을 수 있다.

소셜 네트워킹 웹사이트 예: 사용자는 뉴스 피드, 친구의 담벼락(wall), 그룹에 글(post)을 올릴 수 있다. 먼저 뉴스 피드 게시 기능을 만들고, 친구 담벼락 게시 기능을 만들 때 이미 작성한 게시 코드를 복사해 붙여 넣고, 그룹 게시 기능에서도 같은 일을 한다. 이후 사이트가 확장되어 텍스트뿐 아니라 사진도 게시할 수 있게 하려면 세 곳 모두의 코드를 갱신해야 한다. 게시 가능한 곳이 더 있다면? 갱신할 때 한 곳을 놓친다면?

게시 기능을 접근 가능한 하나의 메서드로 합쳤다면 모든 형태의 게시가 그것을 사용할 수 있었고, 변경할 때 한 곳만 고치면 됐을 것이다. 이는 기능 추가만이 아니라 알고리즘 갱신, 버그 수정에도 적용된다. 한 곳만 갱신하면 되면 변경 구현이 쉬워지고, 갱신이 필요한 코드 블록을 놓칠 위험이 줄어든다. 여기에는 **D.R.Y. 원칙(Don't Repeat Yourself)** 이 적용된다.

### 긴 메서드(Long Method)

이름 그대로다. 긴 메서드는 그 메서드 안에서 필요 이상으로 많은 일이 일어나고 있거나 필요 이상으로 복잡하다는 신호일 수 있다.

그런데 얼마나 길어야 너무 긴 것인가? 상황에 따라 다르다. "x줄이면 너무 길다"는 마법의 규칙은 없다.

- 사용자 인터페이스를 설정하는 메서드는 하나의 작업에 집중해도 자연히 길어지는 경향이 있다(사용하는 툴킷에 따라 다름). 일반적으로 이런 메서드는 길이에 비해 복잡하지 않으므로 괜찮을 수 있다.
- 프로그래밍 언어에 따라서도 다르다. Smalltalk 메서드는 평균 15줄 정도로 짧은 경향이 있으며, 이 언어의 설계는 응집도(cohesion)가 높은 클래스와 메서드를 갖지만 결합(coupling)도 높은 편이다.
- 어떤 개발자들은 메서드 전체가 화면에 한 번에 보이는 것(50줄 이하)을 좋은 가이드라인으로 제안한다. 그러나 프로그래머가 버그를 만들기 시작하기 전까지 수백 줄의 메서드도 다룰 수 있다는 연구들도 있다.
- 메서드가 너무 긴지 판단할 때 코드 줄 수(lines of code)가 과연 코드 복잡도의 괜찮은 척도인지도 별개의 문제다.

### 거대 클래스(Large Class)

큰 메서드처럼 큰 클래스도 문제다. 이런 클래스는 흔히 **갓 클래스(God class), 블롭 클래스(Blob class), 블랙홀 클래스(Black Hole class)** 라 불린다. 계속 커지기만 한다.

보통은 평범한 크기로 시작하지만, 더 많은 책임이 필요해질 때 이 클래스가 놓기 적당한 곳처럼 보인다. 책임이 많아질수록 그 책임들이 더 많은 책임을 끌어들이고, 편의상 결국 또 이 클래스에 넣게 된다. 블랙홀처럼 점점 커지며 책임을 계속 끌어들인다. 결국 클래스 코드 어디에 어떤 기능이 있는지 문서화하는 방대한 주석이 필요해지는데, 앞서 말했듯 주석은 나쁜 설계의 지표일 수 있다.

이를 피하려면 **클래스의 목적을 명시적으로 하고, 클래스가 한 가지 일을 잘하도록 응집력 있게(cohesive) 유지**해야 한다. 어떤 기능이 클래스의 책임에 특정되지 않으면 다른 곳에 두는 것을 고려해야 한다. 거대 클래스는 기하급수적으로 커지는 경향이 있으므로 이 코드 스멜을 일찍 잡는 것이 좋다. 나중에 쪼개려면 어렵고 시간이 많이 든다.

### 데이터 클래스(Data Class)

반대로 클래스가 너무 작은 것도 문제인데, 흔히 데이터 클래스가 그렇다. 데이터 클래스는 **데이터만 담고 실질적 기능이 없는 클래스**다. 게터(getter)·세터(setter) 메서드 외에는 별것이 없다. 예로 x, y 좌표만 담은 2D 포인트 클래스가 있다.

이 데이터 클래스에 담긴 데이터가 무엇에 쓰이는지 생각해 보라. 게터·세터로 조작하는 것 말고, 이 클래스에 둘 수 있는 다른 용도가 있는가? 이 데이터를 조작하는 다른 클래스들을 살펴보라. 그들의 행동 일부를 데이터 클래스에 두는 것이 낫지 않은가? 예를 들어 2D 포인트 클래스에는 점을 이동시키는 다양한 변환(transformation) 함수를 둘 수 있다. 게터·세터만 있는 데이터 클래스는 좋은 추상화(abstraction)가 아니거나 불필요한 클래스일 수 있다.

### 데이터 뭉치(Data Clumps)

관련된 문제로, 클래스의 인스턴스 변수나 메서드의 매개변수에 **함께 몰려다니는 데이터 그룹**이 있다. 정수 변수 x, y, z로 무언가를 하는 메서드가 있다고 하자. 이런 변수들을 반복해서 매개변수로 쓰는 다양한 조작 메서드가 많다면, 변수 대신 객체를 매개변수로 쓰는 편이 낫다. 이 예에서는 x, y, z 값을 담은 3D 포인트 객체를 매개변수로 쓸 수 있다. 세 데이터 값을 매개변수로 쓰는 대신 객체 안에 저장하고, 그 객체를 매개변수로 사용한다.

단, 조심해야 한다. 앞서 말한 데이터 클래스를 그냥 만들어 내는 게 아닌지 확인해야 한다. 이 클래스들이 데이터 저장 이상의 일을 하도록 해야 한다. 원래의 doSomething 메서드(또는 그 유용한 부분)가 Point3D 클래스에 속해야 한다고 결정할 수도 있다. 많은 코드 스멜처럼, **하나의 스멜을 고치는 것이 코드의 다른 곳에 새 스멜을 만들 수 있다.** 데이터 뭉치 스멜을 고치려고 데이터 클래스를 만들었다면, 그 클래스가 게터·세터만이 아닌 실질적 메서드를 갖게 해 데이터 클래스 스멜도 해결해야 한다.

### 긴 매개변수 목록(Long Parameter List)

비슷한 맥락에서 긴 매개변수 목록도 코드 스멜이다. 이 스멜에는 절충(compromise)이 필요하다. 매개변수 목록이 긴 메서드는 쓰기 어려워 나쁘지만, 매개변수를 줄이는 흔한 해법이 전역 변수(global variable)인데 전역 변수는 그 나름의 문제가 있어 일반적으로 피해야 한다.

긴 매개변수 목록은 메서드를 올바르게 쓰기 어렵게 만들고, 뭔가 잘못될 가능성을 높인다. 보통 이런 메서드는 각 매개변수가 무엇을 하고 무엇이어야 하는지 설명하는 방대한 주석이 필요한데, 주석은 대개 나쁜 코드 스멜의 탈취제일 뿐이다. 주석마저 잘 달려 있지 않다면 매개변수가 어떻게 쓰이는지 구현 내부를 들여다봐야 하는데, 이는 캡슐화(encapsulation)를 깨뜨린다.

가장 좋은 해법은 **매개변수 객체(parameter object)를 도입**하는 것이다. 그래픽 라이브러리에서 흔한 방식으로, 그래픽 루틴에 컨텍스트(context)를 주는 객체를 전달하는 툴킷들이 있다. 펜 색, 선 두께, 펜 모양, 불투명도(opacity) 같은 세부 사항을 개별 매개변수로 설정하는 대신 이 컨텍스트를 매개변수 객체로 제공한다. 원 그리기(draw circle) 같은 그리기 메서드를 실행할 때 획(stroke)이 어떻게 보여야 하는지에 대한 모든 정보를 개별 매개변수 값으로 전달할 필요가 없어진다.

## 예시

데이터 뭉치를 매개변수 객체로 바꾸는 강의의 예다. x, y, z를 반복해서 매개변수로 쓰는 대신 Point3D 객체를 쓴다.

```java
// 변경 전: 데이터 뭉치가 매개변수로 반복해서 등장한다
public void doSomething(int x, int y, int z) {
    // ...
}
```

```java
// 데이터 값들을 담는 클래스 — 게터·세터만 있는 데이터 클래스가 되지 않도록
// 유용한 행동(예: 원래 doSomething의 일부)을 함께 두는 것을 고려한다
public class Point3D {
    private int x;
    private int y;
    private int z;

    public Point3D(int x, int y, int z) {
        this.x = x;
        this.y = y;
        this.z = z;
    }
}

// 변경 후: 객체 하나를 매개변수로 사용한다
public void doSomething(Point3D point) {
    // ...
}
```

## 요약

- 리팩토링(refactoring): 외부 동작은 유지한 채 내부 구조를 개선하는 작고 점진적인 변경. 기능을 추가할 때 함께 수행하는 것이 좋다.
- 코드 스멜(code smell)은 Martin Fowler의 *Refactoring*에서 식별된 나쁜 코드의 패턴(안티패턴)이다.
- 주석: 없어도 문제, 너무 많아도 문제. 나쁜 설계의 탈취제가 될 수 있다. API 문서화와 선택 근거 기록에는 유용하다.
- 중복 코드: 한 곳으로 합쳐 D.R.Y. 원칙을 지키면 변경이 쉬워지고 누락 위험이 줄어든다.
- 긴 메서드·거대 클래스(갓 클래스): 너무 많은 책임의 신호. 클래스는 목적을 명시하고 한 가지 일을 잘하게 유지하며, 일찍 잡아야 한다.
- 데이터 클래스: 게터·세터만 있는 클래스는 좋은 추상화가 아닐 수 있다. 관련 행동을 안으로 옮기는 것을 고려한다.
- 데이터 뭉치·긴 매개변수 목록: 매개변수 객체(parameter object)를 도입하되, 새로 만든 클래스가 데이터 클래스 스멜이 되지 않게 한다. 하나의 스멜을 고치면 다른 스멜이 생길 수 있음을 유의한다.
