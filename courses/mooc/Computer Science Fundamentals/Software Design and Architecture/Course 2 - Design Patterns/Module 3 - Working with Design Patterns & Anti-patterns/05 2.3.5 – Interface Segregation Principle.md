# 2.3.5 – Interface Segregation Principle

## 개요

- 인터페이스(interface)에 너무 많은 것이 담기면 구현 클래스가 쓰지 않는 메서드에 의존하게 되는 문제가 생긴다.
- 인터페이스 분리 원칙(Interface Segregation Principle)은 "클래스는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다"고 말한다.
- 식료품점의 사람 계산원(human cashier)과 셀프 계산대(self-serve machine) 예제로 큰 인터페이스를 작은 일반화들로 나누는 방법을 보여준다.

## 내용

### 배경 — 인터페이스와 너무 큰 인터페이스의 문제

우리가 살펴본 많은 디자인 패턴은 구체 클래스의 일반화(generalization)를 사용한다. 이 일반화는 클라이언트 클래스가 구체 클래스의 행동을 간접적으로 호출하는 인터페이스로 제공된다. 그래야 클라이언트 클래스가 구체 클래스에 덜 의존하게 되어 변경이 쉬워진다. 인터페이스는 객체지향 프로그래밍에서 매우 중요해서, 구체 클래스가 아니라 **인터페이스에 대해 프로그래밍(program to interfaces)** 하도록 노력해야 한다. 그러나 인터페이스가 너무 많은 것을 담으면 문제가 생긴다.

### 예제 — 계산원과 셀프 계산대

식료품점의 계산(checkout) 구역을 표현하는 시스템을 만든다고 하자. 북미에서는 고객이 두 가지 방법으로 결제할 수 있다. 계산대(till)를 운영하는 사람 계산원에게 가거나, 자동 셀프 계산대(self-serve machine)를 이용한다. 이 둘의 목적은 인터페이스로 일반화할 수 있다. 둘 다 고객이 구매할 상품을 스캔하고, 어떤 형태의 결제를 받고, 필요하면 거스름돈을 내준다.

그러나 둘이 공유하지 않는 행동도 있다. 자동 셀프 계산대는 무한정 일할 수 있지만, 사람 계산원은 식사하고, 휴식하고, 교대 시간이 끝나면 퇴근해야 한다. 이런 사람의 행동을 그냥 구체 Cashier 클래스에 넣을 수도 있지만, 그러면 문제가 생긴다. 그 행동들이 인터페이스에 없으므로 클라이언트 클래스가 간접화(indirection)로 호출할 수 없고, 클라이언트가 cashier의 메서드를 직접 호출하면 그 구체 클래스에 의존하게 된다. 그렇다면 사람의 행동을 억지로 인터페이스에 넣어야 할까? 아니면 저수준 의존(low level dependency)을 감수하고 변경 때마다 추가 작업을 해야 할까?

### 원칙의 내용

**인터페이스 분리 원칙(Interface Segregation Principle)** 을 사용하면 의존성 문제에 빠지지도, 모든 것을 인터페이스로 일반화하도록 강제되지도 않는다. 이 원칙은 **클래스는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다**고 말한다. 인터페이스를 구현하는 클래스가 인터페이스에 정의된 메서드의 **더미 구현(dummy implementation)** 을 가져서는 안 된다는 뜻이다. 대신 **큰 인터페이스를 더 작은 일반화들로 분리**해야 한다.

### 예제에 원칙 적용하기

ICashier 인터페이스는 사람 계산원 클래스에는 잘 맞는다. 그 행동이 모두 인터페이스에 담기기 때문이다. 하지만 셀프 계산대는 출퇴근을 기록(clock in/out)하거나 휴식을 취할 필요가 없으므로 이 설계는 이상적이지 않다. 기계에 맞지 않는 메서드 구현을 강제로 제공하고 싶지 않다. 그것은 아무 일도 하지 않는 무의미한 구현이 될 것이고, 클라이언트 클래스가 기계에게 기대하거나 요청할 수 있는 행동도 아니다.

인터페이스 분리 원칙을 적용해 ICashier 인터페이스를 두 개의 더 작은 인터페이스로 나눈다.

- **ICashier**: 사람이든 기계든 계산원의 일반적 행동을 기술한다.
- **IHumanWorker**: 직원(employee)의 일반적 행동을 기술한다.

HumanCashier 클래스는 두 인터페이스를 모두 구현하고, SelfServeMachine 클래스는 ICashier 인터페이스만 구현하면 된다. 이렇게 하면 각 구체 클래스는 자신의 기능을 일반화하는 인터페이스에 대해서만 구현을 제공한다. 각 인터페이스는 기대되는 행동을 더 정확하게 기술하게 되고, 구체 클래스가 구현할 인터페이스의 올바른 조합을 골라 쓸 수 있게 된다.

### 인터페이스 설계에 대한 조언

인터페이스는 객체지향 시스템의 필수 요소로, 구체 클래스를 일반화해 결합(coupling)을 줄여 준다. 다만 모든 객체지향 원칙처럼 올바르게 사용해야 한다. 큰 인터페이스 자체가 나쁜 설계 선택은 아니지만, 시스템 맥락에서 검토해 인터페이스 분리 원칙으로 더 작은 일반화들로 나눠야 할지 판단해야 한다.

어떻게 인터페이스를 적절히 분리할지, 또는 인터페이스 분리가 필요해질 미래의 요구사항 변경을 예측할지는 항상 분명하지 않다. 잘 정의된 인터페이스를 가진 시스템은 이런 분리 지점(segregation point)을 더 잘 보이게 해 준다. 인터페이스를 설계할 때는 가능한 한 정밀해지도록 노력해야 한다. 인터페이스는 시스템의 각 부분이 무엇을 할 수 있는지에 대한 기술(description)이며, 기술이 좋을수록 소프트웨어를 만들고 갱신하고 유지보수하기 쉬워진다.

## 예시

강의의 계산원 예제를 코드로 옮기면 다음과 같다.

```java
// 사람이든 기계든 계산원의 일반적 행동
public interface ICashier {
    void scanItem();
    void acceptPayment();
    void dispenseChange();
}

// 사람 직원의 일반적 행동
public interface IHumanWorker {
    void clockIn();
    void clockOut();
    void takeBreak();
}
```

```java
// 사람 계산원은 두 인터페이스를 모두 구현한다
public class HumanCashier implements ICashier, IHumanWorker {
    public void scanItem() { /* ... */ }
    public void acceptPayment() { /* ... */ }
    public void dispenseChange() { /* ... */ }
    public void clockIn() { /* ... */ }
    public void clockOut() { /* ... */ }
    public void takeBreak() { /* ... */ }
}

// 셀프 계산대는 ICashier만 구현하면 되므로
// 사람의 행동에 대한 더미 구현이 필요 없다
public class SelfServeMachine implements ICashier {
    public void scanItem() { /* ... */ }
    public void acceptPayment() { /* ... */ }
    public void dispenseChange() { /* ... */ }
}
```

## 요약

- 인터페이스 분리 원칙(Interface Segregation Principle): 클래스는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다.
- 인터페이스에 너무 많은 것이 담기면 구현 클래스가 아무 일도 하지 않는 더미 구현을 제공해야 하는 문제가 생긴다.
- 해결책은 큰 인터페이스를 시스템의 개별 기능을 제대로 기술하는 더 작은 일반화들로 분리하는 것이다.
- 각 구체 클래스는 자신의 기능에 맞는 인터페이스 조합만 구현하면 된다(예: HumanCashier는 ICashier + IHumanWorker, SelfServeMachine은 ICashier만).
- 인터페이스는 시스템이 할 수 있는 일의 기술이므로 가능한 한 정밀하게 설계해야 한다.
