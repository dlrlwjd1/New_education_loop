# 2.3.7 – Part 2 - Code Smells

## 개요

- 코드를 변경할 때 나타나는 코드 스멜(code smell)들을 다룬다: 발산적 변경(divergent change), 산탄총 수술(shotgun surgery), 기능 욕심(feature envy), 부적절한 친밀(inappropriate intimacy), 메시지 체인(message chains).
- 설계상의 스멜들도 다룬다: 원시 타입 집착(primitive obsession), switch 문(switch statements), 추측성 일반화(speculative generality), 거부된 유증(refused bequest).
- 코드 스멜은 나쁜 코드와 나쁜 설계의 훌륭한 지표이며, 코드를 자주 검토해 재사용 가능·유연·유지보수 가능하게 유지해야 한다.

## 내용

### 발산적 변경(Divergent Change)

하나의 클래스를 **여러 다른 이유로 여러 다른 방식으로** 변경해야 할 때 발생한다. 거대 클래스(large class), 즉 갓 클래스(God class) 스멜과 밀접하다. 큰 클래스는 많은 책임을 가지며, 그 책임들은 다양한 목적을 위해 다양한 방식으로 변경되어야 할 수 있다. **관심사의 분리(separation of concerns)가 제대로 안 된 것**이 발산적 변경의 흔한 원인이다.

클래스가 마땅히 그래야 하듯 하나의 특정 목적만 가진다면, 코드를 변경해야 할 이유의 수가 줄고 구현해야 할 변경의 다양성도 줄어든다. 클래스를 여러 방식으로 바꾸고 있다면, 그 클래스의 책임들을 별도 클래스들로 추출(extract)해야 한다는 좋은 지표다. 원래의 큰 클래스는 추출된 클래스들에 책임을 위임(delegate)한다. 이렇게 하면 관심사의 분리라는 하나의 설계 원칙으로 거대 클래스와 발산적 변경, 두 코드 스멜을 해결한 것이다.

### 산탄총 수술(Shotgun Surgery)

반대로, 하나의 작은 요구사항·하나의 변경을 구현하려는데 그 하나를 위해 설계 곳곳의 수많은 클래스를 건드려야 한다면 좋은 설계가 아니었을 수 있다. 이 스멜은 코드에 산탄총을 쏘고 그 파편(splatter)을 모두 수습해야 한다는 뜻에서 산탄총 수술이라 불린다. (강의자 왈: 폭력적이지만 이름은 우리가 지은 게 아니다.)

흔히 발생하는 스멜로, 한 곳의 변경이 그 결과로 코드의 다른 많은 영역을 고치게 만든다. 기능 추가, 코드 조정, 버그 수정, 알고리즘 변경 때 일어날 수 있다. 이상적으로 변경은 국소화(localized)되어야 한다. 항상 가능하지는 않지만, 한두 클래스만 건드리는 변경이 여러 클래스를 건드리는 변경보다 훨씬 낫다. 코드 곳곳을 바꿔야 한다면 변경을 놓치거나 다른 곳에 문제를 만들 가능성이 높다.

모듈화된 코드가 항상 가능한 것은 아니다. 아무리 잘 설계해도 산탄총 수술이 필요한 변경이 있다. 예로 저작권(copyright) 문구나 라이선스를 갱신하려면 시스템의 모든 파일을 바꿔야 한다.

보통 **메서드를 옮기는 것**으로 이 스멜을 해결할 수 있다. 하나의 변경이 여러 클래스의 여러 메서드 변경을 요구한다면, 그 메서드들을 한두 클래스로 통합하는 편이 나을 수 있다는 지표다. 단, 변경을 한 클래스에서만 하려고 메서드를 몰아넣으라는 뜻은 아니다. 그것은 다시 거대 클래스 스멜이다. 옮기는 것이 타당할 때 옮겨야 한다. 한 곳의 변경이 다른 곳들의 변경으로 이어진다는 사실은 그 메서드들이 어떤 식으로든 관련되어 있음을 보여 주므로 더 나은 조직화 방법이 있을 수 있다. 그러나 그대로 두는 것이 더 타당하다면 그냥 감수해야 할 수도 있다.

### 기능 욕심(Feature Envy)

어떤 메서드가 **자신이 속한 클래스보다 다른 클래스의 세부 사항에 더 관심이 많을 때** 발생한다. 로맨스 영화 같다. 오래전 헤어진 연인이 각자 새 연인이 있음에도 서로를 잊지 못하고, 자기 관계보다 상대의 관계에 더 신경 쓴다. 관객은 "그냥 각자 관계를 정리하고 둘이 만나!"라고 소리친다. 같은 곳에 있기 전까지 그들은 행복해질 수 없다.

이 코드 스멜의 해법도 같다. 두 메서드나 클래스가 항상 서로 대화하고 함께 있어야 할 것 같다면, 아마 그래야 한다. 어떤 클래스의 메서드가 일을 하기 위해 다른 클래스와 많이 대화한다면, 그 메서드는 그 다른 클래스 안에 있는 편이 나을 수 있다.

### 부적절한 친밀(Inappropriate Intimacy)

비슷한 맥락에서, 두 클래스가 **양방향 통신(two way communication)으로 서로에게 너무 의존**하는 문제다. 한 클래스의 메서드가 다른 클래스의 메서드를 호출하고 그 반대도 일어난다. 이렇게 강하게 결합되어야 할까? 아마 아닐 것이다. 이 순환(cycle)을 제거할 방법이 있을 것이다.

순환을 제거하려면 **두 클래스가 모두 사용하는 메서드들을 다른 클래스로 빼내면(factor out)** 된다. 그러면 밀접한 통신이 어느 정도 풀릴 수 있다. 최소한 통신이 한 방향으로만 일어나게 만들 수는 있어야 한다. 단, 순환이 반드시 나쁜 것은 아니다. 스테이트 패턴(state design pattern)에도 순환이 있다. 통신 순환이 필요한 상황도 있다. 그러나 순환을 제거할 방법이 있다면 그것이 설계를 더 단순하고 이해하기 쉽게 만드는 좋은 해법이다.

### 메시지 체인(Message Chains)

앞서 배운 데메테르의 법칙(Law of Demeter), 즉 최소 지식 원칙(principle of least knowledge)은 호출할 수 있는 메서드를 규정한다. private 메서드만이 아니라 public 객체에 대해서도 호출하면 안 되는 경우의 규칙이 있다. 메시지 체인 스멜은 이 법칙을 위반할 소지가 있다.

객체 A에 getB 메서드가 있어 B 객체를 반환하고, 그 B 객체에 getC를 호출해 C 객체를 받고, 마지막으로 그 C 객체에 무언가를 시킨다고 하자. 데메테르의 법칙이 B나 C 객체에 대한 메서드 호출을 금지하는 경우일 수 있다. 호출해서 객체를 받고, 다시 호출해서 또 객체를 받는 긴 메시지 체인은 법칙 위반의 신호이며 나쁜 메시지 체인이다.

나쁜 메시지 체인은 설계에 경직성(rigidity)이나 복잡성을 유발하고, 코드를 독립적으로 테스트하기 어렵게 만든다. 이 예에서 A에서 C까지 가려면 체인과 그 객체들의 의존성을 따라 항해(navigate)해야 한다. 특정 항해 경로를 객체에 박아 넣으면(bake in) 안 된다. 설계를 재작업해 그 의존성을 재구성하면 이 코드는 깨진다. 그것이 취약한(brittle) 설계의 신호다.

다만 호출 체인이 있는 코드 한 줄이 항상 나쁘다는 것은 아니다. 괜찮을 때도 있다. 메시지 체인이 우리가 메서드를 호출할 수 있는 제한된 객체 집합을 반환하는 경우, 즉 그 객체들이 데메테르의 법칙을 따른다면 좋은 것일 수 있다. 모두 상황에 달렸다.

### 원시 타입 집착(Primitive Obsession)

int, long, float, string 같은 내장 타입(built-in type), 즉 원시 타입(primitive)에 **지나치게 의존**하는 스멜이다. 물론 원시 타입은 쓸 수밖에 없지만, 가능하면 코드의 가장 낮은 수준(lowest level)에만 존재해야 한다. 원시 타입 남용은 **추상화(abstraction)를 식별해 적절한 클래스를 정의하지 않을 때** 발생한다.

예컨대 시스템의 모든 것을 문자열로 인코딩해 배열에 넣을 수도 있다. 그러면 코드가 1960년대에 개발된 것처럼 보인다. 그때는 그래야 했지만, 이후 언어들은 더 나은 추상화를 위해 우리만의 타입을 정의할 수 있게 진화했다. 그것을 쓰지 않으면 비객체지향적(non-OO) 사고방식이다.

캐나다의 우편번호(postal code) 예: 지역에 따라 postcode, eircode, PIN code, ZIP code라고도 하며, 우편 분류를 위해 주소에 포함되는 문자·숫자의 나열이다. 캐나다 우편번호는 문자·숫자가 교대로 나오는 6글자(예: T6G 2R3)다. 이를 문자열로 저장해 시스템 전체에서 문자열로 다룰 수도 있지만, 그러면 핵심 추상화가 세부 코드에 묻혀 UML 클래스 다이어그램 같은 시스템 설계에서 잘 드러나지 않는다. 우편번호 문자열과 시스템의 다른 문자열 사이에 명확한 구분이 없어진다. 시스템의 어느 부분이 우편번호가 모두 대문자인지, 공백이 있는지 신경 쓰는가? PostalCode 클래스를 정의하면 문자들을 제대로 저장할 수 있고, 이것이 시스템의 핵심 추상화임이 훨씬 분명해진다. 유효성 검증이나 지역 계산 같은 다양한 메서드도 넣을 수 있다. 높은 수준(high level)에서 원시 타입을 자주 쓰고 있다면 적절한 클래스를 선언하지 않고 있다는 좋은 지표다.

### switch 문(Switch Statements)

switch 문이 왜 나쁜 설계냐고 생각할 수 있다. 때로는 크고 긴 if-else 문이 필요하다. 그러나 switch 문을 더 잘 처리할 수 있는 경우가 있다. **조건문이 타입 코드(type code)나 무언가의 타입을 검사하고 있다면** 더 나은 방법이 있다.

예: say 메서드가 동물의 타입을 검사해, 개(dog)면 "woof"라고 말하게 하는 등 switch 문에 타입별 케이스를 둔다. 이런 조건문은 **다형성(polymorphism)을 사용하는 설계로 줄여야 한다.** 개선된 설계에서는 Dog와 Cat 객체가 자신의 say 메서드가 호출되면 무엇을 말해야 하는지 스스로 안다.

### 추측성 일반화(Speculative Generality)

"언젠가 필요할지도 몰라"라는 생각으로 코드를 작성한 적이 있다면 이 스멜을 범한 것이다. 추측성 일반화는 **지금 필요하지 않은데 언젠가 쓸 것 같아서** 슈퍼클래스, 인터페이스, 코드를 만들 때 발생한다. 언젠가 서브클래스를 만들거나 다른 구현을 제공할 능력을 원하지만 지금 당장은 필요 없는 경우다. 이러면 실제로 코드에 도움이 안 되는 일반성을 도입하는 것이고, 코드를 과잉 설계(over-engineering)하는 것이다.

애자일(agile) 개발에서는 **적시 설계(just in time design)** 를 실천해야 한다. 특정 이터레이션(iteration)의 요구사항을 동작하는 시스템으로 만드는 데 딱 필요한 만큼만 설계한다. 각 이터레이션 시작에 개발할 요구사항 집합을 고르고, 그것만 설계하면 된다. 백로그(backlog)의 다른 요구사항은 무시해도 된다. 실제로는 영영 필요 없을 수 있기 때문이다. 소프트웨어는 자주 바뀌고, 클라이언트는 언제든 마음을 바꿔 백로그에서 요구사항을 뺄 수 있다. 설계는 단순하게 유지해야 한다. 결코 쓰이지 않을 코드를 작성하는 데 시간을 쓰지 마라. **일반화가 필요해지면 그때 일반화하라.** 그 변경은 미리 준비해 둔 경우보다 그 시점에는 더 오래 걸릴 수 있지만, 필요 없는 코드를 작성하지 않음으로써 시스템 전체적으로는 시간을 절약할 것이다. 코드도 군더더기 없고 단순하며 적응하기 쉽게 유지된다.

### 거부된 유증(Refused Bequest)

마지막 스멜로, **서브클래스가 필요 없는 것을 상속받을 때** 발생한다. 갑자기 돌아가신 왕고모 트루디(Trudy)가 유언으로 평생 모은 수백 개의 도자기 피규어 세트를 남겼다고 생각해 보라. 왕고모를 사랑했지만 그 피규어들이 필요하지도, 원하지도, 둘 공간도 없다. 선물로 의도된 것이 짐이 된다.

코드에서도 일어난다. 슈퍼클래스가 모든 서브클래스에 걸친 공통 행동을 선언했는데, 서브클래스들이 쓰지도 필요하지도 않은 것을 상속받고 있다면, 그것들이 이 슈퍼클래스의 서브클래스인 것이 적절한가? 독립(stand alone) 클래스가 더 타당할 수도 있고, 그 원치 않는 행동을 슈퍼클래스에 정의하지 말아야 할 수도 있다. 일부 서브클래스만 쓸 수 있다면, 그 행동을 해당 서브클래스들에만 정의하는 편이 나을 것이다.

### 마무리

코드 스멜은 나쁜 코드와 나쁜 설계의 훌륭한 지표다. 코드가 재사용 가능하고 유연하며 유지보수 가능하게 유지되도록 이런 코드 스멜을 자주 검토하라. 더 알고 싶거나 스멜을 해결하는 방법을 알고 싶다면 Martin Fowler의 책 *Refactoring: Improving the Design of Existing Code*를 참고하라. 한 번의 초고로 좋은 소설을 쓸 수 없듯, 설계 원칙을 따르고 디자인 패턴을 적용하고 코드 스멜을 피하도록 코드를 검토하고 조정하지 않고는 좋은 코드를 쓸 수 없다. 리팩토링은 좋은 설계를 달성하는 매우 중요하지만 때로 간과되는 방법이다. 이제 코드를 탈취(deodorize)하러 가자.

이것으로 이 코스의 모든 내용이 끝났다. 남은 캡스톤 과제에서는 이미 코드 스멜에 대해 분석·비판한 동작하는 소프트웨어 제품을 디자인 패턴을 사용해 더 유연하고 재사용 가능하게 만든다. 이후 코스 전체 내용을 시험하는 기말 퀴즈가 이어진다.

## 예시

타입을 검사하는 switch 문을 다형성으로 대체하는 강의의 예다.

```java

public String say(String animalType) {
    switch (animalType) {
        case "dog":
            return "woof";
        case "cat":
            return "meow";
        default:
            return "";
    }
}
```

// 변경 후: 다형성을 사용한 설계 —
// 각 객체가 say가 호출되면 무엇을 말할지 스스로 안다
public abstract class Animal {

```java
// 우편번호를 시스템 곳곳에서 String으로 다루는 대신
// 핵심 추상화를 드러내는 클래스를 정의한다 (예: "T6G 2R3")
public class PostalCode {
    private String code;

    public PostalCode(String code) {
        this.code = code;
    }

    // 유효성 검증이나 지역 계산 같은 메서드를 포함할 수 있다
    public boolean isValid() {
        // 문자-숫자가 교대로 나오는 6글자인지 검증
        return code.replace(" ", "").matches("[A-Z][0-9][A-Z][0-9][A-Z][0-9]");
    }
}
```

## 요약

- 발산적 변경(divergent change): 한 클래스를 여러 이유로 여러 방식으로 바꿔야 하는 것. 관심사의 분리로 책임을 별도 클래스로 추출해 해결한다.
- 산탄총 수술(shotgun surgery): 하나의 변경이 코드 곳곳의 수정을 요구하는 것. 관련 메서드를 한두 클래스로 통합하되, 거대 클래스를 만들지 않도록 한다.
- 기능 욕심(feature envy): 메서드가 자기 클래스보다 다른 클래스에 더 관심이 많은 것. 그 클래스로 옮기는 것을 고려한다.
- 부적절한 친밀(inappropriate intimacy): 두 클래스의 양방향 통신 순환. 공용 메서드를 빼내거나 통신을 한 방향으로 만든다.
- 메시지 체인(message chains): 긴 호출 체인은 데메테르의 법칙 위반 가능성이 있으며 취약한 설계의 신호다. 상황에 따라 괜찮을 수도 있다.
- 원시 타입 집착(primitive obsession): 원시 타입은 최하위 수준에만 두고, 핵심 추상화는 적절한 클래스(예: PostalCode)로 정의한다.
- switch 문: 타입을 검사하는 조건문은 다형성(polymorphism)을 사용하는 설계로 바꾼다.
- 추측성 일반화(speculative generality): 언젠가 쓸 것 같은 코드를 미리 만들지 말고, 적시 설계(just in time design)로 필요할 때 일반화한다.
- 거부된 유증(refused bequest): 서브클래스가 쓰지 않는 것을 상속받는다면 상속 관계나 슈퍼클래스의 행동 정의를 재검토한다.
- 코드 스멜을 자주 검토하고 리팩토링하는 것이 좋은 설계를 달성하는 중요한 방법이다.
