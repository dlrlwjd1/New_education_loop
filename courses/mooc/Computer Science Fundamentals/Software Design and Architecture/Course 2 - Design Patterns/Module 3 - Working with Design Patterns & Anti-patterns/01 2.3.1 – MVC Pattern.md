# 2.3.1 – MVC Pattern

## 개요

- 사용자 인터페이스(user interface)를 제공하는 시스템의 책임을 모델(Model), 뷰(View), 컨트롤러(Controller) 세 부분으로 나누는 MVC 패턴을 다룬다.
- MVC는 관심사의 분리(separation of concerns) 원칙을 적용한 패턴이며, 모델-뷰 갱신에는 옵저버 패턴(Observer Pattern)을 사용한다.
- 식료품점 계산대(cash system) 예제를 통해 모델·뷰·컨트롤러 각각의 역할과 상호작용 흐름을 살펴본다.

## 내용

### 모듈 소개

이 모듈에서는 앞선 두 모듈에서 배운 생성(creational)·구조(structural)·행동(behavioral) 디자인 패턴 위에 세워지는 MVC(Model-View-Controller) 패턴을 배운다. 또한 재사용 가능하고 유연하며 유지보수 가능한 소프트웨어를 만들기 위해 디자인 패턴의 바탕이 되는 일반 설계 원칙(design principle)들을 배우고, 나쁜 설계를 분석·비판하는 방법을 익힌다. 업계에서 이런 흔한 악습(malpractice)은 안티패턴(anti-pattern) 또는 코드 스멜(Code Smell)이라고 불린다.

### 동기 — 식료품점 예제

동네 식료품점의 계산원(cashier)들은 상품 가격을 일일이 수동 입력해야 하는 구식 계산 시스템에 불만이 있고, 고객들은 계산이 느려 줄을 서서 기다리는 데 지쳐 있다. 필요한 것은 주문을 입력하고 표시하는 시스템, 즉 사용자 인터페이스다. 고객과 계산원은 바코드 스캐너로 입력된 상품과 총 금액을 화면에서 볼 수 있어야 하고, 실수가 있으면 계산원이 쉽게 수정할 수 있어야 한다.

**사용자 인터페이스라는 말이 나오면 MVC 패턴 사용을 고려해야 한다.**

### 모델(Model)

모델은 사용자가 보고 조작하고자 하는 **기저 데이터와 로직**을 담는다. 이 예제에서는 계산원과 고객이 만들고자 하는 식료품 주문이 모델이다. MVC 패턴의 핵심은 **모델이 자기 완결적(self-contained)** 이라는 점이다. 모델은 스스로 존재하는 데 필요한 모든 상태(state), 메서드, 기타 데이터를 가진다. 모델은 백엔드(back end), 즉 기저 소프트웨어에 해당한다.

### 뷰(View)

뷰는 사용자가 모델(또는 그 일부)을 볼 수 있게 해 준다. 식료품점에서는 상품 목록과 가격을 보여주는 화면이다. 뷰는 버튼이나 입력 필드 같은 상호작용 요소를 가질 수도 있다. 뷰는 프런트엔드(front end), 즉 표현 계층(presentation layer)에 가깝다. 하나의 모델에 여러 뷰가 있을 수도 있다.

모델의 값이 바뀌면 뷰가 스스로 갱신하도록 알려야 하는데, 이는 **옵저버 디자인 패턴(Observer Design Pattern)** 으로 구현한다. 옵저버 패턴에서 옵저버는 구독자(subscriber)처럼 동작하며, 여기서는 모든 뷰가 옵저버다. 모델이 변경되면 구독 중인 모든 뷰에 통지(notify)한다.

### 컨트롤러(Controller)

뷰에는 사용자가 기저 모델의 데이터를 바꾸는 수단(예: 항목 삭제, 가격 수정 버튼)이 있을 수 있다. 그러나 MVC 패턴에서 **뷰는 모델에 직접 요청을 보내지 않는다.** 대신 사용자 상호작용 정보가 컨트롤러에 전달되고, 컨트롤러가 그 요청을 해석해 모델을 변경한다. 이렇게 하면 뷰는 시스템의 시각적 표현만, 모델은 정보 관리만 책임진다. 즉 MVC 패턴은 **관심사의 분리(separation of concerns)** 설계 원칙으로 상호작용 시스템의 주요 책임을 나눈다.

일반적으로 모델은 문제 공간 분석에서 도출한 엔티티 객체(entity object), 뷰는 사용자를 상대하는 시스템 경계의 바운더리 객체(boundary object), 컨트롤러는 이벤트를 받아 동작을 조율하는 컨트롤 객체(control object)에 대응한다.

### 가격 변경 흐름 예

1. 계산원이 Change Price 버튼을 누른다.
2. 이 버튼의 이벤트 핸들러가 컨트롤러를 호출한다.
3. 컨트롤러는 뷰의 텍스트 필드에서 새 가격을 읽고, 변경할 항목과 새 가격 두 정보를 이용해 모델의 메서드로 가격 변경을 요청한다. 컨트롤러는 가격 유효성을 검사하고 뷰에 텍스트 박스를 비우라고 요청할 수도 있다.
4. 모델이 항목의 가격을 변경한다.
5. 뷰는 모델의 옵저버이므로 모델이 변경을 통지하고, 뷰가 스스로 갱신되어 계산원의 화면에 새 가격이 표시된다.

### 구현 요점

- **모델**: 뷰나 컨트롤러 없이도 스스로 존재할 수 있어야 한다. 뷰를 옵저버로 만들기 위해 모델을 관찰 가능(observable)하게 만든다. `java.util` 패키지의 `Observable` 클래스를 상속(extend)하면 뷰를 옵저버로 추가할 수 있다. StoreOrder 클래스에는 항목 추가·삭제·가격 변경 메서드가 있으며, 변경이 일어날 때마다 `setChanged` 메서드로 변경을 표시하고 `notifyObservers` 메서드로 뷰들에 통지한다. 모델에는 UI 요소가 전혀 없고, 어떤 뷰도 알지 못한다.
- **뷰**: OrderView 클래스는 `Observer` 인터페이스를 구현(implement)하므로 `update` 메서드를 제공해야 한다. 항목 목록과 가격 목록을 얻으려면 StoreOrder로 다운캐스트(downcast)가 필요한데, 더 타입 안전(type safe)하게 하려면 제네릭(generics)으로 자신만의 옵저버 패턴을 만들 수도 있다. 뷰의 이벤트 처리 코드는 모델의 메서드를 직접 호출하지 않고 컨트롤러의 메서드를 호출한다.
- **컨트롤러**: 자신이 연결하는 뷰와 모델 모두에 대한 참조를 가져야 한다. 결정적으로, 컨트롤러는 모델의 상태를 직접 변경하지 않고 **모델의 메서드를 호출**해 변경한다.

### 컨트롤러가 주는 이점

1. 뷰가 본연의 목적인 사용자 인터페이스 표현에 집중할 수 있다. 사용자 입력 해석과 그에 따른 모델 조작은 컨트롤러가 맡는다. 관심사를 분리하면 코드가 깔끔해지고 수정이 쉬워진다.
2. 컨트롤러가 모델과 뷰 사이에 있으므로 뷰가 모델에 강하게 결합(tightly coupled)되지 않는다. 개발 중 뷰에 넣기 훨씬 전에 모델에 기능을 추가하고 테스트할 수 있다.

### 유연한 적용

다른 디자인 패턴처럼 MVC 패턴을 쓰는 유일한 방법은 없다. MVC의 결정적 특징은 백엔드, 프런트엔드, 그리고 둘 사이의 조율 간 **관심사의 분리**다. 예제는 모델·뷰·컨트롤러 각 하나의 클래스였지만, 실제 소프트웨어 시스템은 보통 여러 개의 모델·뷰·컨트롤러 클래스를 가진다. 사용자 인터페이스가 있는 거의 모든 애플리케이션에서 MVC 패턴을 볼 수 있다.

## 예시

강의에서 설명한 구현 구조를 코드로 옮기면 다음과 같다. 모델은 `java.util.Observable`을 상속하고, 뷰는 `Observer` 인터페이스를 구현한다.

```java
import java.util.Observable;

// 모델: UI 요소가 없고 뷰를 알지 못한다
public class StoreOrder extends Observable {
    // 항목 추가, 항목 삭제, 가격 변경 등의 메서드를 가진다
    public void changePrice(String itemName, float price) {
        // ... 주문 내 항목의 가격을 변경 ...
        setChanged();        // 변경을 표시
        notifyObservers();   // 구독 중인 뷰들에 통지
    }
}
```

```java
import java.util.Observable;
import java.util.Observer;

// 뷰: Observer 인터페이스를 구현하므로 update 메서드를 제공해야 한다
public class OrderView implements Observer {
    @Override
    public void update(Observable o, Object arg) {
        StoreOrder order = (StoreOrder) o; // 다운캐스트가 필요
        // order의 항목 목록·가격 목록을 읽어 화면을 갱신
    }
}
```

```java
// 컨트롤러: 뷰와 모델 모두에 대한 참조를 가지며,
// 모델의 상태를 직접 바꾸지 않고 모델의 메서드를 호출한다
public class OrderController {
    private StoreOrder model;
    private OrderView view;

    public OrderController(StoreOrder model, OrderView view) {
        this.model = model;
        this.view = view;
    }

    public void changePrice(String itemName, float newPrice) {
        // 뷰에서 읽은 입력을 검증한 뒤 모델의 메서드로 변경을 요청
        model.changePrice(itemName, newPrice);
    }
}
```

## 요약

- **모델(Model)**: 사용자가 보고 조작하려는 기저 데이터·상태·로직을 담으며, 자기 완결적이다.
- **뷰(View)**: 모델 정보를 사용자에게 제시하고 상호작용을 허용한다. 하나의 모델에 서로 다른 부분·방식을 보여주는 여러 뷰가 있을 수 있다.
- **컨트롤러(Controller)**: 뷰 요소에 대한 사용자 상호작용을 해석해 모델을 변경한다. 뷰와 모델을 느슨하게 결합(loosely coupled)시키고 뷰가 UI 관심사에 집중하게 한다.
- 이런 기능 분리는 코드를 개발·읽기·유지보수하기 쉽게 만들고, 프로그램을 모듈화(modular)하고 느슨하게 결합시킨다.
- 느슨한 결합(loose coupling)은 대규모 개발 팀에서 특히 중요하다. 한 팀은 프런트엔드(뷰), 다른 팀은 백엔드(모델)를 맡을 수 있고, 혼자 개발하더라도 책임별로 집중할 수 있다. 모델을 유지한 채 다른 UI 툴킷으로 뷰를 교체하기도 쉬워진다.
