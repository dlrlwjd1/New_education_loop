# 2.1.6 – Adapter Pattern

## 개요

- 어댑터 패턴(Adapter pattern)은 서로 호환되지 않는 두 기존 시스템(인터페이스) 사이의 소통을 가능하게 하는 호환 인터페이스를 제공하는 구조 패턴이다.
- 클라이언트(client) — 어댑터(adapter) — 어댑티(adaptee) 구조로, 어댑터가 타깃 인터페이스(target interface)를 구현해 클라이언트의 요청을 어댑티가 이해하는 형태로 번역(translate)한다.
- 제3자 라이브러리(third-party library)나 외부 시스템은 직접 수정할 수 없거나 수정하면 위험하므로, 어댑터로 감싸 재사용한다.

## 내용

### 현실 세계의 어댑터

- 장치는 특정 커넥터를 기대하는데 가진 것은 다른 커넥터를 제공하는 상황 — 불일치(mismatch) 때문에 연결할 수 없고, 다른 커넥터를 장치가 기대하는 것으로 바꿔 줄 어댑터가 필요하다.
- 어댑터가 자주 쓰이는 이유는 벤더마다 장치 커넥터가 다르고 계속 진화하기 때문이다.
- 예: 키보드 같은 주변기기의 흔한 커넥터는 한때 PS2였지만 1990년대 중반부터 컴퓨터가 USB 포트만 지원하기 시작하면서, 구형 PS2 키보드 사용자는 컴퓨터의 USB 포트를 구형 키보드가 꽂을 수 있는 커넥터로 변환하는 어댑터가 필요했다.

### 소프트웨어의 호환성 문제

- 소프트웨어 시스템도 같은 호환성 문제를 겪는다. 물리적 커넥터 대신 **호환되지 않는 소프트웨어 인터페이스**를 가진다. 한 시스템의 출력이 다른 시스템이 기대하는 입력과 맞지 않을 수 있다.
- 기존 시스템이 제3자 라이브러리를 통합해야 하거나 다른 시스템과 연결해야 할 때 반복적으로 나타나는 문제다.
- 어댑터 디자인 패턴은 호환 인터페이스를 제공해 두 기존 시스템 간의 소통을 돕는다.

### 패턴의 구성 요소

- **클라이언트(client) 클래스**: 제3자 라이브러리나 외부 시스템을 사용하려는, 우리 시스템의 일부.
- **어댑티(adaptee)**: 사용하려는 제3자 라이브러리나 외부 시스템 안의 클래스.
- **어댑터(adapter) 클래스**: 클라이언트와 어댑티 사이에 위치한다. 클라이언트가 사용할 인터페이스인 **타깃 인터페이스(target interface)** 를 구현하여 클라이언트가 기대하는 모습에 맞춘다.
- 동작 흐름: 클라이언트가 타깃 인터페이스를 통해 어댑터에 요청을 보낸다 → 어댑터가 요청을 어댑티가 이해할 메시지로 번역한다 → 번역이 끝나면 번역된 요청을 어댑티에 보낸다.

### 구현 예시: WebClient와 WebService

- 기존 `WebClient`로 다른 `WebService`와 통신하려 한다. `WebClient`는 임의의 객체(object)를 요청에 담아 보내려 하지만 서비스는 JSON 객체만 지원한다. 객체 요청을 JSON 객체로 변환할 어댑터가 필요하다.
- **1단계: 타깃 인터페이스 설계** — 어댑터 클래스가 구현하고 클라이언트 클래스가 사용할 타깃 인터페이스를 만든다.
- **2단계: 어댑터 클래스로 타깃 인터페이스 구현** — 어댑터는 클라이언트 클래스의 객체를 받아 JSON 객체로 변환하는 메서드를 제공한다. 클라이언트가 만들 수 있는 어떤 클래스의 인스턴스든 변환해 요청으로 보낼 수 있다는 뜻이다. 어댑터 클래스는 번역된 요청을 어댑티로 전달하는 일도 처리한다. 클라이언트 클래스는 어댑터의 타깃 인터페이스만 알면 된다.
- **3단계: 클라이언트가 타깃 인터페이스로 어댑터에 요청 전송** — `WebClient`는 메시지를 만드는 작업을 담당한다. `WebClient`의 정상 워크플로가 객체를 클라이언트에게 돌려주는 것이므로, 시스템의 다른 부분을 방해할 수 있는 `doWork` 메서드는 수정하지 않는다. 대신 `WebClient`가 평소처럼 동작하게 두고, 어떤 어댑터·WebService·메시지든 전달할 수 있는 sendMessage류 메서드를 추가한다.
- 메인 프로그램에서 `WebAdapter`, `WebService`, `WebClient`를 인스턴스화한다. `WebClient`는 `WebRequester` 인터페이스를 통해 어댑터를 다루며 요청을 보낸다. `WebClient`는 JSON 객체가 필요하다는 것 같은 `WebService`에 대한 정보를 전혀 알 필요가 없다 — 어댑티는 감싸는 어댑터 클래스에 의해 클라이언트로부터 숨겨진다.

### 왜 인터페이스를 직접 바꾸지 않는가

- **어댑티 쪽을 바꾸지 않는 이유**: 예시에서 `WebService`의 구현을 보여주지 않은 것은 그것이 직접 접근할 수 없는 제3자 라이브러리·외부 시스템을 나타내기 때문이다. 접근할 수 있다 해도 벤더의 업데이트가 우리의 변경을 무의미하게 만들 수 있고, 우리의 변경이 그 라이브러리나 시스템을 망가뜨릴 수도 있다.
- **우리 시스템 인터페이스를 바꾸지 않는 이유**: 가능할 수도 있지만, 어떤 서브시스템이 그것을 사용 중이라면? 이런 가정을 바꾸면 시스템의 다른 부분이 의도치 않게 망가질 수 있다.

### 어댑터의 역할 정리

어댑터는 다음을 위한 것이다.

- 어댑티를 감싸고(wrap) 클라이언트에게 타깃 인터페이스를 노출한다.
- 타깃 인터페이스를 구현함으로써 어댑티의 인터페이스를 클라이언트가 기대하는 인터페이스로 **간접적으로** 바꾼다.
- 클라이언트의 요청을 어댑티가 기대하는 요청으로 간접적으로 번역한다.
- 호환되지 않는 인터페이스를 가진 기존 어댑티를 재사용한다.

새 제3자 라이브러리나 외부 시스템과 제대로 인터페이스하기 위해 시스템의 큰 부분을 다시 쓰는 것은 항상 실용적이지 않다. 인터페이스가 우리 시스템의 기대에 맞지 않는다고 해서 우리 시스템이 바뀌어야 하는 것은 아니다.

## 예시

강의에서 단계별로 설명한 WebClient–WebService 예시를 Java로 정리하면 다음과 같다.

```java
// 1단계: 타깃 인터페이스 — 클라이언트가 사용할 인터페이스
public interface WebRequester {
    int request(Object request);
}

// 2단계: 어댑터가 타깃 인터페이스를 구현 — 객체를 JSON으로 변환해 어댑티에 전달
public class WebAdapter implements WebRequester {
    private WebService service; // 어댑티 (제3자 시스템)

    public void connect(WebService currentService) {
        this.service = currentService;
    }

    public int request(Object request) {
        Json result = toJson(request);       // 클라이언트의 객체를 JSON으로 번역
        Json response = service.request(result); // 번역된 요청을 어댑티로 전송
        if (response != null) {
            return 200; // 성공
        }
        return 500; // 실패
    }

    private Json toJson(Object input) { /* 객체 → JSON 변환 */ return null; }
}

// 3단계: 클라이언트는 타깃 인터페이스를 통해서만 어댑터와 상호작용
public class WebClient {
    private WebRequester webRequester;

    public WebClient(WebRequester webRequester) {
        this.webRequester = webRequester;
    }

    private Object doWork() { /* 정상 워크플로 — 수정하지 않음 */ return null; }

    public void sendMessage() {
        Object message = doWork();
        if (message != null) {
            int status = webRequester.request(message);
            if (status == 200) {
                System.out.println("Message sent.");
            } else {
                System.out.println("Message failed.");
            }
        }
    }
}

// 메인 프로그램: WebAdapter, WebService, WebClient를 인스턴스화
public class Program {
    public static void main(String[] args) {
        WebService service = new WebService();
        WebAdapter adapter = new WebAdapter();
        adapter.connect(service);
        WebClient client = new WebClient(adapter);
        client.sendMessage();
    }
}
```

## 요약

- 어댑터 패턴(Adapter pattern)은 호환되지 않는 두 인터페이스 사이의 간극을 잇는 기법이다.
- 구성: 클라이언트 → (타깃 인터페이스를 구현한) 어댑터 → 어댑티. 어댑터가 요청을 번역해 전달하고, 어댑티는 클라이언트로부터 숨겨진다.
- 어댑티(제3자 라이브러리·외부 시스템)는 직접 수정할 수 없거나 수정이 위험하고, 우리 시스템의 인터페이스 변경도 다른 서브시스템을 망가뜨릴 수 있으므로 어댑터를 쓴다.
- 기존 시스템을 계속 사용하면서 외부 소스를 통합할 수 있게 해 준다.
