# 2.1.5 – Facade Pattern

## 개요

- 퍼사드 패턴(Facade pattern)은 복잡한 서브시스템(subsystem)을 감싸는 래퍼 클래스(wrapper class)를 두어, 클라이언트 클래스가 단일한 단순화된 인터페이스로 서브시스템과 상호작용하게 하는 구조 패턴이다.
- 퍼사드는 기능을 추가하지 않으며, 서브시스템으로 들어가는 **진입점(point of entry)** 역할만 한다.
- 은행 서비스(BankService) 예시: 고객이 Checking·Saving·Investment 계좌 클래스를 직접 다루는 대신 BankService 퍼사드를 통해 접근한다.

## 내용

### 왜 퍼사드가 필요한가

- 시스템의 부분들이 커질수록 자연히 복잡해진다. 이는 클라이언트 클래스 입장에서 사용하기 혼란스러울 수 있다.
- 시스템 복잡성이 항상 나쁜 설계의 징후는 아니다. 풀려는 문제의 범위가 커서 복잡한 해법이 필요할 수 있다. 다만 클라이언트 클래스는 더 단순한 상호작용을 원한다.
- 퍼사드 디자인 패턴은 클라이언트 클래스가 서브시스템과 상호작용할 **단일한 단순화된 인터페이스**를 제공한다.

### 현실 세계의 퍼사드

- 소매점에서 쇼핑하거나 식당에서 식사하거나 온라인 주문을 해봤다면 현실의 퍼사드를 경험한 것이다.
- 저녁 먹을 곳을 찾으며 거리를 걸을 때는 건물 정면의 간판(외부로 드러난 표시)을 보고 식사 서비스를 제공하는지 판단한다. 온라인 쇼핑에서도 웹사이트에 가상 매장(virtual storefront)이 있다는 외적 표시를 찾는다.
- 웨이터가 주문을 받아 전달하거나 온라인 판매 플랫폼이 주문을 처리 부서로 보낼 때, 이들은 뒤에서 처리해야 할 모든 추가 작업을 숨기는 퍼사드의 일부로 작동한다. 요청이 어떻게 처리되는지 몰라도 재화와 서비스를 구매할 수 있다.
- 건물 구조, 종업원, 메뉴, 웹사이트 등 수많은 구성 요소가 퍼사드 뒤에 있다.
- 유의: 퍼사드는 기능을 추가하지 않는다. 서브시스템으로의 진입점 역할만 한다.

### 은행 시스템 예시 — 퍼사드 없는 경우

- 퍼사드 클래스가 없으면 `Customer` 클래스가 `Checking`, `Saving`, `Investment` 클래스의 인스턴스를 직접 가진다. 즉, 고객이 이 구성 클래스들을 올바르게 인스턴스화할 책임을 지고, 그들의 서로 다른 속성과 메서드를 모두 알아야 한다.
- 이는 현실에서 금융기관에 맡기지 않고 모든 금융 계좌를 스스로 관리하는 것과 같다 — 계좌가 많으면 복잡해진다.

### 은행 시스템 예시 — 퍼사드 도입

- `BankService` 클래스를 `Checking`·`Saving`·`Investment`의 퍼사드로 도입한다. `Customer`는 더 이상 인스턴스화나 금융 관리의 복잡성을 다룰 필요가 없다.
- 세 계좌 클래스가 모두 `IAccount` 인터페이스를 구현하므로, `BankService`가 계좌 클래스들을 감싸 고객 클라이언트 클래스에게 더 단순한 전면(front)을 제공한다.

### 적용 4단계

1. **인터페이스 설계**: 여러 계좌 클래스가 구현할 Java 인터페이스(`IAccount`)를 만든다. 이 인터페이스는 `Customer` 클래스에게는 알려지지 않는다.
2. **인터페이스 구현**: 인터페이스는 서브타입(subtype)을 만들 수 있게 하므로 `Checking`, `Saving`, `Investment`는 `IAccount`의 서브타입이 되어 계좌답게 동작할 것이 기대된다. 퍼사드로 감쌀 클래스들이 인터페이스를 구현한다. 이 예시는 인터페이스 하나만 숨기지만, 실전에서는 퍼사드 클래스로 서브시스템의 모든 인터페이스와 클래스를 감쌀 수 있다. 무엇을 감쌀지는 설계자의 결정이다.
3. **퍼사드 클래스 생성**: `BankService`가 퍼사드다. public 메서드들은 사용이 단순하고, 그 아래의 인터페이스나 구현 클래스의 흔적을 드러내지 않는다. 각 계좌의 접근 제한자(access modifier)를 private으로 설정한다 — 퍼사드의 목적이 복잡성 은닉이므로, 정보 은닉(information hiding) 원칙으로 클라이언트가 계좌 객체와 그 동작을 보지 못하게 한다.
4. **퍼사드로 서브시스템 접근**: 클라이언트 클래스는 `BankService`의 메서드를 통해 여러 계좌의 기능에 접근한다. `BankService`는 클라이언트가 호출할 수 있는 행동을 알려주고, 해당 동작을 적절한 계좌 객체에 위임(delegate)한다.
- 이제 `Customer`는 자기 계좌를 만들고 관리할 걱정 없이 `BankService`와 그것이 수행할 수 있는 행동 집합만 알면 된다. 계좌 관리의 복잡성이 고객으로부터 효과적으로 숨겨졌다.

### 퍼사드 패턴의 특징 정리

퍼사드는 다른 패턴들처럼 캡슐화(encapsulation)로 시스템 일부의 세부를 숨기므로 혼동하기 쉽다. 퍼사드를 특징짓는 것:

- 서브시스템의 복잡성을 퍼사드 클래스라는 통합 래퍼 뒤에 캡슐화해 숨긴다.
- 클라이언트 클래스가 서브시스템을 스스로 관리할 필요를 없애 서브시스템과 클라이언트 간 **결합도(coupling)를 낮춘다**.
- 인스턴스화와 작업의 방향 지정(redirection)을 처리해 서브시스템 내 적절한 클래스로 넘긴다.
- 클라이언트 클래스에 서브시스템에 대한 단순화된 인터페이스를 제공한다.
- 단지 서브시스템의 진입점으로 작동할 뿐, 서브시스템에 기능을 더하지 않는다.

## 예시

강의에서 단계별로 설명한 은행 예시를 Java로 정리하면 다음과 같다.

```java
// 1단계: 계좌 클래스들이 구현할 인터페이스 (Customer에게는 노출되지 않음)
public interface IAccount {
    void deposit(double amount);
    void withdraw(double amount);
}

// 2단계: 인터페이스를 구현하는 서브타입들 — Checking, Saving, Investment
public class Checking implements IAccount {
    public void deposit(double amount) { /* 입금 처리 */ }
    public void withdraw(double amount) { /* 출금 처리 */ }
}

public class Saving implements IAccount {
    public void deposit(double amount) { /* 입금 처리 */ }
    public void withdraw(double amount) { /* 출금 처리 */ }
}

public class Investment implements IAccount {
    public void deposit(double amount) { /* 입금 처리 */ }
    public void withdraw(double amount) { /* 출금 처리 */ }
}

// 3단계: 퍼사드 클래스 — 계좌 객체는 private으로 숨긴다 (정보 은닉)
public class BankService {
    private IAccount checking = new Checking();
    private IAccount saving = new Saving();
    private IAccount investment = new Investment();

    // 단순한 public 메서드 — 내부 인터페이스와 구현 클래스를 드러내지 않음
    public void depositToChecking(double amount) {
        checking.deposit(amount); // 적절한 계좌 객체로 위임
    }

    public void withdrawFromSaving(double amount) {
        saving.withdraw(amount);
    }
}

// 4단계: 클라이언트는 퍼사드를 통해서만 서브시스템에 접근
public class Customer {
    public static void main(String[] args) {
        BankService bank = new BankService();
        bank.depositToChecking(100.0);
        bank.withdrawFromSaving(50.0);
    }
}
```

## 요약

- 퍼사드 패턴(Facade pattern)은 래퍼(퍼사드) 클래스로 서브시스템을 캡슐화해 복잡성을 숨긴다.
- 클라이언트는 서브시스템 클래스를 직접 인스턴스화·관리하지 않고 퍼사드의 단순한 인터페이스만 사용하므로 결합도가 낮아진다.
- 퍼사드는 인스턴스화를 처리하고 요청을 서브시스템의 적절한 클래스로 위임하는 진입점일 뿐, 새 기능을 추가하지 않는다.
- 적용 순서: 인터페이스 설계 → 클래스로 구현 → 퍼사드 클래스로 감싸기(내부는 private, 정보 은닉) → 클라이언트는 퍼사드로 접근.
