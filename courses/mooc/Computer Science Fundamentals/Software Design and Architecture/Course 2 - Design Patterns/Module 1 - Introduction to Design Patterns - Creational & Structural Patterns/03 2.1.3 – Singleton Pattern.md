# 2.1.3 – Singleton Pattern

## 개요

- 싱글턴 패턴(Singleton pattern)은 클래스의 객체를 **단 하나만** 갖도록 하고, 그 객체에 **전역적으로 접근**할 수 있게 하는 생성 패턴(creational pattern)이다.
- 생성자를 private으로 숨기고, 유일 인스턴스를 참조하는 클래스 변수와 public `getInstance` 메서드로 이를 구현한다.
- 가장 단순한 디자인 패턴 중 하나지만 강력한 기법이며, 지연 생성(lazy creation)이라는 부수 이점도 있다.

## 내용

### 설계 목표: 인스턴스는 하나만

- 이름 그대로 싱글턴은 "단 하나(singular)"에 관한 패턴으로, **한 클래스의 객체를 하나만** 갖는 것을 말한다.
- 예시: 포커 게임 모바일 앱에 사용자 설정을 저장하는 Preferences 클래스가 있다고 하자. 설정에는 플레이 테이블 색상, 카드 뒷면 디자인 같은 시각 요소가 포함된다.
  - 만약 Preferences 인스턴스가 여러 개라면, 사용자가 설정을 바꿀 때 어느 객체가 그 선택을 저장하는가? 게임을 표시할 때는 어느 객체를 참조하는가?
  - 이처럼 Preferences 객체가 하나 더 있는 것은 말이 안 되고, 충돌(conflict)이나 비일관성(inconsistency)으로 이어질 수 있다.
- 싱글턴 패턴의 또 다른 목표는 그 단일 객체가 프로그램 안에서 **전역적으로 접근 가능(globally accessible)** 해야 한다는 것이다.

### 왜 코드로 강제해야 하는가

- 혼자 하는 작은 프로젝트라면 "인스턴스를 하나만 만들자"고 마음속으로 약속하는 비공식적 방법도 가능하지만, 잊고 하나 더 만들면 골칫거리가 된다. 큰 프로젝트나 여러 개발자가 참여하는 프로젝트에서는 통하지 않는 방법이다.
- 해법은 "하나만" 이라는 목표를 **클래스 자체에 내장**해, 싱글턴 클래스의 인스턴스를 하나 더 만드는 것이 단지 지양되는 것이 아니라 **불가능**하도록 만드는 것이다. 이렇게 설계 의도(design intent)를 소프트웨어 안에 명문화한다.

### 구현 방법

- 생성자가 public이면 소프트웨어의 어느 부분에서든 언제라도 객체를 만들 수 있어 막을 방법이 없다. 그래서 **생성자를 private으로** 선언해 클래스 밖에서 호출할 수 없게 한다.
- 그러면 "생성자가 private인데 어떻게 객체를 만드나"라는 모순이 생기는데, 두 가지 핵심 요소로 해결한다.
  1. **클래스 변수 `uniqueInstance`**: 싱글턴 클래스의 유일한 인스턴스를 참조할 변수를 선언한다. 클래스 내부에서만 수정 가능하도록 private으로 선언한다.
  2. **public `getInstance` 메서드**: 인스턴스가 아직 없을 때만 클래스를 인스턴스화하는 공개 메서드를 만든다.
     - `uniqueInstance`가 null이면 클래스를 인스턴스화하고 변수가 그 객체를 참조하게 한다.
     - 이미 객체가 존재하면(변수가 객체를 참조 중이면) 그 객체를 그대로 반환한다.
- `getInstance`는 public이므로 전역에서 호출할 수 있고, 사실상 일반 생성자를 대체한다. 일반 생성자를 숨기고 다른 클래스들이 public `getInstance`를 호출하도록 강제함으로써, 객체가 단 하나만 생성되도록 기본적인 문지기(gatekeeping) 역할을 추가한 것이다. 이미 생성된 경우에는 같은 메서드가 단일 객체를 전역적으로 참조하는 데 쓰인다.

### 지연 생성(Lazy Creation)

- 이 방식의 또 다른 장점은 객체가 **정말 필요해질 때까지 생성되지 않는다**는 것이다. 이를 지연 생성(lazy creation)이라 한다.
- 객체가 클 경우 유용하다. `getInstance`가 호출되기 전에는 만들어지지 않으므로 더 효율적이다.

### 트레이드오프와 변형

- 여러 컴퓨팅 스레드(thread)가 실행 중이라면, 스레드들이 공유 단일 객체에 접근하려 하면서 문제가 생길 수 있다.
- 싱글턴이든 다른 패턴이든 그것이 최적의 설계인지 판단하려면 동작 방식과 잠재적 결과를 잘 알아야 한다.
- 디자인 패턴은 정확한 코드가 아니라 **목적·의도(intent)로 정의**된다. 싱글턴의 구현 방식에는 변형이 있을 수 있지만 목표는 항상 같다 — 인스턴스가 하나로 제한된 클래스에 전역 접근을 제공하는 것. 일반적으로 private 생성자와, 아직 인스턴스화되지 않았을 때만 인스턴스화하는 public 메서드로 달성한다.

### 활용 예

- 하나만 있어야 하는 객체는 많다: 앱의 설정(preferences), 프린터의 인쇄 대기열(print queue), 장치의 소프트웨어 드라이버(driver) 등. 이런 경우 여러 개가 존재하면 혼란스럽거나 심지어 재앙적일 수 있다.
- 싱글턴은 단독으로도, 다른 디자인 패턴과 조합해서도 강력한 기법이 될 수 있다.

## 예시

강의에서 설명한 구현(단계별 서술)을 Java 코드로 옮기면 다음과 같다.

```java
public class Preferences {
    // 유일한 인스턴스를 참조하는 private 클래스 변수
    private static Preferences uniqueInstance = null;

    // private 생성자 — 클래스 밖에서 호출 불가
    private Preferences() {
    }

    // 전역 접근점: 인스턴스가 없을 때만 생성 (지연 생성)
    public static Preferences getInstance() {
        if (uniqueInstance == null) {
            uniqueInstance = new Preferences();
        }
        return uniqueInstance;
    }
}
```

## 요약

- 싱글턴 패턴(Singleton pattern)의 목표: 클래스의 인스턴스를 하나로 제한하고 전역 접근을 제공한다.
- 구현: private 생성자 + private 클래스 변수 `uniqueInstance` + null 검사 후 생성·반환하는 public `getInstance` 메서드.
- 설계 의도를 코드에 내장해 두 번째 인스턴스 생성을 불가능하게 만든다 — 대형·다인원 프로젝트에서 특히 중요하다.
- 부수 이점으로 지연 생성(lazy creation)이 있고, 멀티스레드 환경에서는 공유 객체 접근 문제가 생길 수 있다는 트레이드오프가 있다.
- 패턴은 코드가 아니라 의도로 정의되므로 구현 변형이 존재할 수 있다.
