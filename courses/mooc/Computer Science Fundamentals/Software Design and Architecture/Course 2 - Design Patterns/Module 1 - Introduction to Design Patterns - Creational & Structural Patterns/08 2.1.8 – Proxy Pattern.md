# 2.1.8 – Proxy Pattern

## 개요

- 프록시 패턴(Proxy pattern)은 프록시 클래스(proxy class)가 실제 대상 클래스(real subject class)를 대리(represent)하게 하는 구조 패턴으로, 프록시가 실제 대상을 감싸고(wrap) 요청을 위임(delegate)한다.
- 세 가지 흔한 용도: 가상 프록시(virtual proxy), 보호 프록시(protection proxy), 원격 프록시(remote proxy).
- 프록시와 실제 대상이 공통 대상 인터페이스(subject interface)를 구현해 다형성(polymorphism)을 확보하고, 클라이언트는 프록시와만 상호작용한다.
- 주문 처리(OrderFulfillment) — 창고(Warehouse) 예시로 보호 프록시의 실용적 적용을 보여준다.

## 내용

### 현실 세계의 프록시

- 살다 보면 무언가·누군가를 대신하는 대리물(placeholder)을 쓰는 것이 더 쉽고 안전하고 편리할 때가 있다.
  - 회사를 대표해 컨퍼런스에서 발언하는 개별 대표자
  - 차량 충돌 시험에서 실제 사람 대신 쓰는 충돌 시험 인형(crash test dummy)
  - 현금 대신 지불 수단으로 통용되는 신용카드
- 각 상황에서 어떤 객체가 프록시 객체에 의해 대리된다. 프록시는 원래 객체의 단순화된·경량(lightweight) 버전으로 작동한다. 프록시 객체도 같은 작업을 수행할 수 있지만, 그것을 달성하기 위해 요청을 원래 객체에 위임할 수 있다.

### 프록시 패턴의 목표

- 소프트웨어 시스템에서도 원본 대신 프록시 객체를 쓰는 편이 나은 상황이 있다. 프록시 디자인 패턴은 프록시 클래스가 실제 대상 클래스(real subject class)를 대리하게 한다.
- 프록시 클래스는 실제 대상 클래스를 감싼다 — 즉, 실제 대상 클래스 인스턴스에 대한 참조를 숨긴다.
- 실제 대상 클래스는 예컨대 민감한 정보를 담고 있거나 인스턴스화에 자원이 많이 드는 시스템의 일부일 수 있다.
- 프록시 클래스가 래퍼(wrapper)로 작동하므로 클라이언트 클래스는 실제 대상 클래스 대신 프록시와 상호작용한다.

### 프록시를 쓰는 세 가지 흔한 시나리오

1. **가상 프록시(virtual proxy)**: 인스턴스화에 자원이 많이 드는 실제 대상 클래스 대신 프록시 클래스를 사용한다. 웹 페이지나 그래픽 편집기의 이미지에 흔히 쓰인다 — 고해상도 이미지 하나가 매우 클 수 있어, 모든 이미지를 한꺼번에 로드하면 시스템 자원에 부담이 될 수 있다.
2. **보호 프록시(protection proxy)**: 실제 대상 클래스에 대한 접근을 통제한다. 학습 관리 시스템(learning management system)에서 사용자 자격 증명(credentials)을 확인해, 학생·강사 같은 서로 다른 사용자가 자신의 역할에 허용된 기능에만 접근하게 하는 데 쓸 수 있다.
3. **원격 프록시(remote proxy)**: 프록시 클래스는 로컬에 있고 실제 대상 클래스는 원격에 존재한다. Google 문서 작업을 생각하면 된다 — 웹 브라우저가 필요한 객체를 모두 로컬에 갖고 있지만, 같은 것이 어딘가의 Google 서버에도 존재한다.

### 일반 구조

- 프록시 클래스는 자신에 대한 호출을 감싸서 실제 객체 클래스로 위임하거나 방향을 바꿔(redirect) 전달할 수 있다.
- 모든 호출이 위임되는 것은 아니다. 프록시 클래스는 실제 대상 클래스의 더 가벼운 버전으로 작동해야 하므로 가벼운 책임은 스스로 처리할 수 있고, 더 실질적인(substantive) 요청만 실제 대상 클래스로 전달한다.
- 프록시 클래스는 실제 대상 클래스를 대신해야 하므로 **같은 메서드를 제공해야 한다**. 두 클래스가 공통 대상 인터페이스(subject interface)를 구현하게 하면 이를 보장할 수 있고 다형성도 얻는다.
- 프록시와 실제 대상 클래스가 모두 subject의 서브타입이므로, 클라이언트 클래스는 실제 대상과 동일한 인터페이스를 가진 프록시와 상호작용할 수 있다.

### 실용 예시: 온라인 소매점의 주문 라우팅

- 전 세계에 유통·창고망을 가진 온라인 소매점을 운영한다면, 고객 주문을 처리할 창고를 어떻게 정할까? 재고가 없는 창고로 주문을 보내는 문제가 생길 수 있으므로, 주문을 적절한 창고로 라우팅하는 시스템이 필요하다.
- 프록시 디자인 패턴으로, 창고에 재고가 부족하면 주문을 받지 않도록 프록시가 실제 대상(창고들)을 보호하게 한다.
- **`IOrder` 인터페이스**: 주문 처리 방법을 정의한다. 프록시 클래스와 실제 대상 클래스가 이 인터페이스를 서로 다르게 구현한다. 이 인터페이스가 주문 처리 시스템과 상호작용하는 방법을 선언한다.
- **`OrderFulfillment` 클래스(프록시)**: 모든 창고의 프록시 역할을 한다. 창고가 주문의 일부를 처리할 수 있는지에 따라 고객 주문의 일부를 위임할 수 있는 창고 목록을 가진다.
- **`Warehouse` 클래스(실제 대상)**: 고객 주문의 일부를 실제로 처리(fulfill)하는 책임을 진다. 요청하는 프록시에게 자기 재고(inventory)를 보고한다.
- 일반 구조에서처럼 클라이언트는 인터페이스를 통해 시스템과 상호작용한다.

### 구현 3단계

1. **대상 인터페이스 설계**: 클라이언트 소프트웨어가 시스템과 상호작용할 때 쓸 인터페이스를 만든다. `OrderFulfillment`와 `Warehouse`가 이를 구현한다.
2. **실제 대상 클래스 구현**: `Warehouse`는 주문을 처리하는 법과 품목의 현재 재고를 보고하는 법을 안다. 주문을 처리할 재고가 충분한지 검사할 필요가 없다는 점에 주목 — 처리 가능한 주문만 창고로 보내지기 때문이다.
3. **프록시 클래스 구현**: `OrderFulfillment`는 창고 재고를 확인하고 주문이 성공적으로 완료될 수 있는지 보장하는 모든 작업을 한 뒤에야 창고로 요청을 보낸다. 각 창고에 특정 품목의 재고가 충분한지 묻고, 충분하면 그 품목을 해당 창고로 보낼 새 주문 객체에 추가한다.

### 이 설계가 주는 이점

- 프록시 클래스가 주문 처리 가능 여부를 확인한 뒤에만 창고로 요청을 보내므로, 창고 시스템이 처리할 수 없는 주문을 받지 않도록 보호된다.
- 주문 검증(validation)과 주문 처리(fulfillment)를 두 부분으로 분리한다. 창고가 검증 과정을 신경 쓸 필요가 없어 전체 주문 처리 속도가 개선된다.
- 개별 창고는 주문을 처리할 수 없을 때 재라우팅을 어떻게 할지 걱정할 필요가 없다.
- `OrderFulfillment`는 고객과의 근접성(proximity)에 따라 창고 우선순위를 정해 주문이 최대한 빨리 도착하게 하는 등 다른 기능으로 개선될 수도 있다.

### 프록시 패턴의 핵심 특징

- 프록시 클래스로 실제 대상 클래스를 감싼다.
- 다형적 설계로 클라이언트 클래스가 프록시와 실제 대상에 같은 인터페이스를 기대할 수 있게 한다.
- 자원 집약적인 객체가 실제로 필요해질 때까지 경량 프록시를 대신 사용한다.
- 클라이언트 코드의 요청을 지능적으로 검증(intelligent verification)해 요청을 전달할지, 어떻게, 누구에게 전달할지 결정한다.
- 같은 물리적·가상적 공간에 있지 않은 시스템의 로컬 표현(local representation)을 제공한다.

## 예시

강의에서 단계별로 설명한 주문 처리 예시를 Java로 정리하면 다음과 같다.

```java
import java.util.ArrayList;
import java.util.HashMap;

// 1단계: 대상 인터페이스 — 프록시와 실제 대상이 모두 구현
public interface IOrder {
    void fulfillOrder(Order order);
}

// 2단계: 실제 대상 클래스 — 주문을 실제로 처리하고 재고를 보고
public class Warehouse implements IOrder {
    private HashMap<String, Integer> stock = new HashMap<String, Integer>();

    // 처리 가능한 주문만 도착하므로 재고 충분 여부를 검사할 필요가 없다
    public void fulfillOrder(Order order) {
        for (Item item : order.getItemList()) {
            stock.put(item.getName(), stock.get(item.getName()) - 1);
        }
        /* 주문 처리: 포장, 배송 등 */
    }

    // 프록시가 물어보면 현재 재고를 보고
    public int currentInventory(Item item) {
        if (stock.containsKey(item.getName())) {
            return stock.get(item.getName());
        }
        return 0;
    }
}

// 3단계: 프록시 클래스 — 창고로 보내기 전에 재고를 확인·검증
public class OrderFulfillment implements IOrder {
    private ArrayList<Warehouse> warehouses = new ArrayList<Warehouse>();

    public void fulfillOrder(Order order) {
        // 각 품목에 대해 각 창고의 재고를 확인하고,
        // 재고가 있으면 그 창고로 보낼 새 주문 객체에 품목을 추가
        for (Item item : order.getItemList()) {
            for (Warehouse warehouse : warehouses) {
                if (warehouse.currentInventory(item) > 0) {
                    Order separateOrder = new Order();
                    separateOrder.addItem(item);
                    warehouse.fulfillOrder(separateOrder); // 실질적 요청만 위임
                    break;
                }
            }
        }
    }
}
```

## 요약

- 프록시 패턴(Proxy pattern)은 프록시 클래스가 실제 대상 클래스를 감싸 대리하게 하며, 실질적 요청만 실제 대상에 위임한다.
- 세 가지 흔한 용도: 자원 집약적 객체의 생성을 필요할 때까지 미루는 가상 프록시, 접근을 통제하는 보호 프록시, 원격 시스템의 로컬 표현인 원격 프록시.
- 프록시와 실제 대상이 공통 대상 인터페이스를 구현해, 클라이언트는 같은 인터페이스로 프록시와 상호작용한다.
- 주문 처리 예시에서 프록시(OrderFulfillment)는 검증을, 실제 대상(Warehouse)은 처리를 맡아 관심사를 분리하고 처리 속도를 높인다.
- 프록시는 강력한 간접화(indirection) 수단으로, 더 안전하고 자원을 덜 쓰는 시스템을 만들게 해 준다.
