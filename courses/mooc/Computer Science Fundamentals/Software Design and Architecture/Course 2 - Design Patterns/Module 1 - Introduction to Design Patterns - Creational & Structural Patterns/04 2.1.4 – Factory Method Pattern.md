# 2.1.4 – Factory Method Pattern

## 개요

- 팩토리(factory)는 다른 객체를 만들어 주는 메서드나 객체로, 객체 생성을 분리하면 코드가 읽기 쉽고 유지보수·변경이 쉬워진다.
- 팩토리 객체(factory object)는 별도의 객체에 생성을 위임하는 유용한 기법이지만 Gang of Four 패턴은 아니다.
- 팩토리 메서드 패턴(Factory Method pattern)의 의도는 "객체 생성을 위한 인터페이스를 정의하되, 어떤 클래스를 인스턴스화할지는 **서브클래스가 결정**하게 하는 것"이다.
- 클라이언트 코드는 구체 클래스가 아닌 일반화(generalization)를 다루게 된다 — 구현이 아닌 인터페이스에 맞춰 코딩하기(coding to an interface, not an implementation).

## 내용

### 문제 상황: 온라인 칼 가게

- 온라인 상점 소프트웨어에서 판매할 객체를 만든다고 하자. 칼 가게(knife store)를 예로 들면, 슈퍼클래스 `Knife` 아래 `SteakKnife`, `ChefsKnife` 서브클래스가 있다.
- 칼을 주문하는 `orderKnife` 메서드는 먼저 칼 객체를 만들고, 이후 출고 준비를 한다. 준비 작업은 sharpen(갈기), polish(광내기), package(포장)다.
  - 메서드는 먼저 `Knife` 변수를 선언하고, 조건문(conditional)으로 어떤 `Knife` 서브클래스를 실제로 인스턴스화할지 결정한다.
  - 특정 타입의 객체를 만들기 위해 클래스를 실제로 인스턴스화하는 행위를 **구체적 인스턴스화(concrete instantiation)** 라 하며, Java에서는 보통 `new` 연산자로 수행한다.
  - 그다음 칼 타입과 무관하게 공통 메서드인 sharpen, polish, package를 호출한다. 이 메서드들은 어떤 칼이 만들어졌는지 신경 쓰지 않고, 다룰 칼만 있으면 된다.
- 매출이 늘어 BreadKnife, ParingKnife 등 새 칼 타입이 계속 추가되면 조건문 목록이 계속 늘어난다. 반면 칼을 만든 뒤 하는 일(sharpen, polish, package)은 변하지 않는다. 점점 복잡해진다.

### 팩토리 객체(Factory Object)

- 현실 세계처럼 객체를 "가게"가 아닌 "공장"에서 만들도록 하자. 특정 타입의 제품(product) 객체를 만드는 역할의 **팩토리 객체**를 만든다.
- sharpen·polish·package는 `orderKnife` 메서드에 그대로 두고, 제품 객체 생성 책임은 `KnifeFactory` 객체에 위임한다. 어떤 칼 타입을 만들지 결정하는 코드와 어떤 서브클래스를 인스턴스화할지 결정하는 코드를 팩토리 클래스의 `createKnife` 메서드로 옮긴다.
- `KnifeStore`는 이제 `KnifeFactory`의 클라이언트(client)가 된다. 예시에서는 사용할 `KnifeFactory` 객체를 `KnifeStore` 생성자에 전달한다. `orderKnife`는 이전과 비슷하지만 구체적 인스턴스화를 직접 하지 않고 팩토리 객체에 위임한다.
- 얻는 것:
  - `KnifeStore`의 `orderKnife`만 팩토리의 클라이언트인 것이 아닐 수 있다. 대량 주문(bulk order)이나 품질 테스트 등 다른 클라이언트도 같은 팩토리로 칼을 만들 수 있다.
  - 모든 칼 생성이 팩토리 안에서 일어나므로, 클라이언트 코드를 수정하지 않고 팩토리에 새 칼 타입을 추가할 수 있다.
  - 같은 클래스들을 인스턴스화하려는 클라이언트가 여럿이면 중복 코드를 없애고 수정이 쉬워진다. 흩어진 인스턴스화 코드를 찾아다니는 대신 팩토리에서만 서브클래스를 추가·제거하면 된다.
  - 서브클래스 인스턴스화 방식이 바뀌어도 모든 클라이언트가 아니라 팩토리만 바꾸면 된다.
- `orderKnife` 입장에서는 팩토리로부터 `Knife` 객체만 받으면 책임을 다할 수 있다. 클라이언트 메서드는 구체적인 칼 클래스 이름을 알 필요 없이 `Knife`라는 일반화만 다룬다. 이것이 **구현이 아닌 인터페이스에 맞춘 코딩(coding to an interface, not an implementation)** 이다.
- 현실 비유: 가게는 보통 파는 물건을 직접 만들지 않고 공장에서 받아온다. 공장은 다른 가게에도 납품할 수 있다. 공장이 칼 만드는 방식(칼날 재질, 손잡이 모양 등)을 바꿔도, 올바른 타입의 칼을 받는 한 가게는 신경 쓰지 않는다. 변경은 가게가 아니라 공장에서 일어난다.
- 유용한 기법이지만, 팩토리 객체 자체는 Gang of Four의 23개 패턴에 속하지 않는다.

### 팩토리 메서드 패턴(Factory Method Pattern)

- 팩토리 메서드 패턴은 특정 타입 객체의 생성을 다른 방식으로 접근한다. 별도의 팩토리 객체 대신 **같은 클래스 안의 별도 메서드**가 객체를 생성한다.
- 특화된 제품 객체를 만들 때의 차이:
  - **팩토리 객체 접근**: 팩토리 클래스를 서브클래싱한다. 예: `KnifeFactory`의 서브클래스 `BudgetKnifeFactory`는 `BudgetChefsKnife`·`BudgetSteakKnife`를, `QualityKnifeFactory`는 `QualityChefsKnife`·`QualitySteakKnife`를 만든다.
  - **팩토리 메서드 접근**: 대신 `KnifeStore`의 서브클래스 `BudgetKnifeStore`를 두고, 그 안의 팩토리 메서드가 `BudgetChefsKnife`·`BudgetSteakKnife`를 만든다.
- 설계 의도: **객체 생성을 위한 인터페이스를 정의하되, 어떤 클래스를 인스턴스화할지는 서브클래스가 결정하게 한다.**

### 구조 살펴보기

- `KnifeStore` 슈퍼클래스는 이제 **추상(abstract)** 이다. 직접 인스턴스화할 수 없고 `BudgetKnifeStore`, `QualityKnifeStore` 같은 서브클래스가 필요하다.
- 서브클래스들은 동일한 `orderKnife` 메서드를 상속한다. `orderKnife`는 여전히 팩토리를 사용하지만 이제 그것은 팩토리 메서드인 `createKnife`다.
- `createKnife`는 슈퍼클래스에 선언되지만 **추상이고 비어 있다**. 서브클래스가 정의하길 원하기 때문이다. `KnifeStore` 서브클래스를 정의할 때마다 반드시 `createKnife`를 정의해야 한다.
- 예: `BudgetKnifeStore`를 인스턴스화하면, 이 클래스는 자신만의 `createKnife`로 칼 객체를 만든다. `QualityKnifeStore`는 다른 팩토리 메서드를 가진다. 이 메서드를 제공하지 않으면 새 `KnifeStore` 서브클래스를 정의할 수 없다.
- `BudgetKnifeStore`는 `KnifeStore`의 서브클래스이므로 `orderKnife`를 상속한다. `BudgetKnifeStore`, `QualityKnifeStore`, 어쩌면 `FamilyKnifeStore` 등 모든 서브클래스가 공통 `orderKnife`를 사용하되, 각자 자신의 `createKnife`를 정의해야 한다.

### UML 클래스 다이어그램

- 칼 가게 예시의 UML에서 `Knife`와 `KnifeStore`는 이탤릭체로 표기되어 **추상 클래스**임을 나타낸다. 직접 인스턴스화할 수 없고 서브클래스를 정의해야 한다.
- 다이어그램에는 `Knife` 서브클래스가 하나만 보이지만 `BudgetChefsKnife`, `BudgetParingKnife` 등 더 있을 수 있고, `KnifeStore`도 `QualityKnifeStore`, `FamilyKnifeStore` 등 더 있을 수 있다.
- `createKnife`는 `KnifeStore`에서 추상이므로 모든 서브클래스가 이 메서드를 정의해야 한다 — 이것이 팩토리 메서드 패턴의 핵심이다.

### 일반 구조

팩토리 메서드 패턴은 항상 같은 일반 구조를 따른다.

- **추상 생성자 클래스(abstract Creator)**: 일반화(generalization)에만 작용하는 메서드들을 가진다. 다루고 싶은 제품만 주어지면 만족한다(예시의 제품은 `Knife`). 팩토리 메서드도 추상으로 선언해 각 구체 생성자 클래스가 팩토리 메서드를 제공하도록 강제한다.
- **구체 생성자(Concrete Creator)**: 추상 생성자의 서브클래스로, 구체적 인스턴스화 — 실제 객체 생성 행위 — 를 책임진다. 추상 생성자로부터 메서드를 상속하며, 팩토리 메서드는 구체 생성자 서브클래스에 있다. 개발자가 구체 생성자 서브클래스를 추가할 때마다 알맞은 제품을 만드는 팩토리 메서드를 정의해야 한다. 이렇게 서브클래스가 객체 생성 방식을 결정한다.
- **제품 슈퍼클래스(Product)**: 예시의 `Knife`처럼 구체 제품(concrete product)들을 일반화한다. 생성자 클래스의 메서드는 구체 제품이 아니라 일반 제품에만 작용한다.
- **구체 제품(Concrete Product)**: 구체 생성자가 만든다. 어떤 구체 생성자를 만들었는지에 따라 만들어지는 제품 타입이 결정된다. 예: `BudgetKnifeStore`는 `BudgetChefsKnife`·`BudgetSteakKnife`를, `QualityKnifeStore`는 `QualityChefsKnife`·`QualitySteakKnife`를 만든다.

## 예시

강의에서 단계별로 설명한 코드를 Java로 정리하면 다음과 같다.

팩토리 도입 전 — 조건문이 계속 늘어나는 `orderKnife`:

```java
public class KnifeStore {
    public Knife orderKnife(String knifeType) {
        Knife knife = null;

        // 어떤 Knife 서브클래스를 인스턴스화할지 조건문으로 결정 (concrete instantiation)
        if (knifeType.equals("steak")) {
            knife = new SteakKnife();
        } else if (knifeType.equals("chefs")) {
            knife = new ChefsKnife();
        }
        // 새 칼 타입이 추가될 때마다 조건문이 늘어난다

        // 칼 타입과 무관한 공통 준비 작업
        knife.sharpen();
        knife.polish();
        knife.packageKnife();
        return knife;
    }
}
```

팩토리 객체(factory object) — 생성 코드를 별도 클래스로 이동:

```java
public class KnifeFactory {
    public Knife createKnife(String knifeType) {
        Knife knife = null;
        if (knifeType.equals("steak")) {
            knife = new SteakKnife();
        } else if (knifeType.equals("chefs")) {
            knife = new ChefsKnife();
        }
        return knife;
    }
}

public class KnifeStore {
    private KnifeFactory factory;

    // 사용할 팩토리 객체를 생성자로 전달받는다
    public KnifeStore(KnifeFactory factory) {
        this.factory = factory;
    }

    public Knife orderKnife(String knifeType) {
        // 구체적 인스턴스화를 팩토리 객체에 위임
        Knife knife = factory.createKnife(knifeType);
        knife.sharpen();
        knife.polish();
        knife.packageKnife();
        return knife;
    }
}
```

팩토리 메서드 패턴(Factory Method pattern) — 서브클래스가 생성을 결정:

```java
public abstract class KnifeStore {
    public Knife orderKnife(String knifeType) {
        // 팩토리 메서드 사용
        Knife knife = createKnife(knifeType);
        knife.sharpen();
        knife.polish();
        knife.packageKnife();
        return knife;
    }

    // 팩토리 메서드 — 추상이며 비어 있고, 서브클래스가 반드시 정의한다
    protected abstract Knife createKnife(String knifeType);
}

public class BudgetKnifeStore extends KnifeStore {
    // 자신만의 팩토리 메서드 정의
    protected Knife createKnife(String knifeType) {
        if (knifeType.equals("steak")) {
            return new BudgetSteakKnife();
        } else if (knifeType.equals("chefs")) {
            return new BudgetChefsKnife();
        }
        return null;
    }
}
```

## 요약

- 팩토리는 다른 객체를 만드는 메서드 또는 객체이며, 객체 생성(Java에서 보통 `new`에 의한 구체적 인스턴스화)을 다른 행위로부터 분리한다.
- 팩토리 객체(factory object)는 여러 클라이언트가 같은 객체들을 만들 때 유용하고, 팩토리 클래스를 서브클래싱해 특화된 팩토리를 만들 수도 있다. 단, Gang of Four 패턴은 아니다.
- 팩토리 메서드 패턴(Factory Method pattern)은 별도 객체 대신 같은 클래스의 별도 메서드로 생성을 분리하고, 그 메서드를 사용하는 클래스를 서브클래싱해 특화한다 — 서브클래스가 객체 생성 방식을 결정한다.
- 클라이언트 코드는 일반화에만 의존하므로(coding to an interface, not an implementation) 단순해지고, 생성 세부는 팩토리로 이동해 코드가 더 확장 가능해진다.
- 상속 같은 객체지향 원칙을 활용해 객체 생성을 특화할 수 있다.
