# 2.1.1 – What is a Design Pattern?

## 개요

- 디자인 패턴(design pattern)은 반복적으로 나타나는 설계 문제(recurring design problem)에 대한 실용적이고 검증된 해결책이다.
- 이 코스는 Software Design and Architecture 전문과정의 두 번째 코스로, 총 4개 모듈 중 앞의 3개 모듈에서 디자인 패턴과 설계 원칙, 코드 스멜(code smell)을 다룬다.
- 디자인 패턴은 구체적인 소스 코드가 아니라 설계를 이끄는 개념적 지식이며, 개발자 간 소통을 위한 설계 어휘(design vocabulary)를 제공한다.

## 내용

### 코스 소개

- University of Alberta와 MOOC가 함께 제공하는 Software Design and Architecture 전문과정의 두 번째 코스다. 첫 코스인 객체지향 설계(Object-Oriented Design)를 먼저 듣는 것을 권하지만, 각 코스는 독립적으로 수강할 수 있다.
- 코스는 4개 모듈로 구성되며 처음 3개 모듈이 본 내용이고, 캡스톤 과제는 코스 전반에 걸쳐 수행하되 나머지 작업은 네 번째 모듈에서 진행한다.
- 코스에서 배우는 것: 객체지향 분석·설계 지식을 확장해 설계 문제에 디자인 패턴을 적용하는 법, 확립된 디자인 패턴들의 개관, 소프트웨어를 더 재사용 가능하고 유연하며 유지보수하기 좋게 만드는 설계 원칙, 코드 스멜(code smell) 카탈로그를 참조해 나쁜 설계를 식별하는 법.
- 캡스톤에서는 기존 애플리케이션을 코드 스멜 관점에서 비평하고 재설계해 볼 기회를 가진다. 첫 모듈에서는 생성 패턴(creational pattern)과 구조 패턴(structural pattern)을 배운다.

### 디자인 패턴이란

- 소프트웨어 공학에서는 같은 설계 문제를 여러 번 마주치게 된다. 이런 반복 문제를 다루는 방법은 많지만, 시간이 지나면서 더 유연하거나 재사용 가능하다는 이유로 어떤 해법이 다른 해법보다 선호된다.
- 디자인 패턴은 반복되는 설계 문제에 대한 **실용적이고 검증된 해결책**이다. 매번 기본 객체지향 원칙만으로 어떤 객체를 쓸지, 객체들이 어떻게 관계 맺어야 할지 처음부터 결정하는 대신, 전문가 개발자들이 자주 사용해 온 기존 해법을 활용할 수 있다.
- 이 해법들은 학술적 관심에 그치는 이론적 제안이 아니라 실제 산업 소프트웨어에서 사용되는 해결책이다.
- 요리 레시피(recipe)에 비유할 수 있다. 사람들이 오랫동안 실험하고 반복해서 만들어 온 요리에는 가장 맛있는 결과를 내는 특정 조리법이 선호되듯, 개발자들도 여러 설계 해법을 실험해 왔고 디자인 패턴은 그중 최선의 결과를 내는 해법을 정리한 것이다.
- 유명한 책 『Design Patterns: Elements of Reusable Object-Oriented Software』(저자: Gamma, Helm, Johnson, Vlissides)에 23개의 디자인 패턴이 정리되어 있으며, 이 코스는 그중 일부를 다룬다.

### 패턴 선택은 자동이 아니다 — 체스 비유

- 설계 문제를 보고 자동으로 어떤 패턴을 쓸지 알 수 있는 것은 아니다. 패턴은 많고, 어떤 패턴이 적용 가능해 보여도 실제 문제에 맞지 않을 수 있다.
- 체스에 비유하면, 초보자는 각 말의 기본 움직임만 알지만 전문가는 노출된 킹(exposed king), 고립된 폰(isolated pawn) 같은 확립된 패턴을 판 위에서 찾아 활용한다. 경험을 통해 상황에 맞는 패턴을 판단하는 능력이 길러진다.
- 마찬가지로 초보 개발자는 for 루프, 메서드 작성 같은 언어 문법 요소만 알지만, 연습과 경험이 쌓이면 관용적(idiomatic) 코드를 쓰게 되고, 나아가 특정 설계 문제에 어떤 패턴을 쓸지 아는 설계 전문가가 될 수 있다.

### 패턴은 코드가 아니라 개념이다

- 디자인 패턴은 Java 라이브러리나 프레임워크처럼 외워서 소프트웨어에 그대로 넣는 구체적 소스 코드가 아니다.
- 패턴은 더 개념적인 것으로, 설계 구조를 이끌고 소프트웨어를 더 유연하고 재사용 가능하게 만드는 데 적용하는 **지식**이다.

### 왜 디자인 패턴을 사용하는가

- **전문가처럼 문제 해결**: 모든 것을 처음부터 만드는 대신, 전문가들이 문제를 푸는 방식을 안내하는 가이드가 된다. 재능 있는 초보 운동선수도 경험 많은 코치가 있어야 더 성장하는 것과 같다. 패턴은 이미 전문가들이 검증했으므로 그들이 겪은 시행착오를 건너뛰고 더 잘 작성된 소프트웨어로 직행할 수 있다.
- **설계 어휘(design vocabulary) 형성**: 설계 해법의 세부 내용을 매번 반복 설명하는 대신, 그것을 암시하는 이름 하나로 논의를 단순화할 수 있다.
  - 예: 두 객체가 있고 첫 번째 객체가 두 번째 객체에 의존하며, 두 번째 객체가 바뀌면 첫 번째 객체가 통지받아야 하는 상황은 소프트웨어에서 매우 흔하다. 슈퍼클래스나 인터페이스, 특정 메서드가 얽힌 해법을 길게 설명하는 대신 "여기에 옵저버 패턴(Observer pattern)을 쓰자"라고 말하면 된다.
- **오해의 여지 감소**: 상황과 해법에 대한 설명이 모호하면 구현할 설계를 서로 다르게 이해할 수 있지만, "이건 옵저버 패턴이다"라고 하면 양쪽 모두 정확히 무엇을 논의하는지 알게 된다.

## 요약

- 디자인 패턴(design pattern)은 반복되는 설계 문제에 대한 실용적·검증된 해결책으로, 실제 산업 소프트웨어에서 쓰인다.
- Gang of Four의 책에 23개 패턴이 정리되어 있으며, 어떤 패턴이 적합한지 판단하려면 체스 전문가처럼 경험이 필요하다.
- 패턴은 암기해 붙여 넣는 코드가 아니라 설계를 이끄는 개념적 지식이다.
- 패턴을 쓰면 전문가의 시행착오를 건너뛸 수 있고, 패턴 이름이 설계 어휘가 되어 소통이 명확해지고 오해가 줄어든다.
