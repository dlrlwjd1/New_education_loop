# 2.1.9 – Decorator Pattern

## 개요

- 데코레이터 패턴(Decorator pattern)은 순수 상속(inheritance) 대신 **집약(aggregation)** 을 사용해, 런타임(runtime)에 객체에 추가 행동·책임을 사실상 동적으로 붙일 수 있게 하는 구조 패턴이다.
- 클래스와 상속은 컴파일 타임(compile time)에 고정되므로, 행동 조합마다 새 클래스를 만들면 클래스가 폭발적으로 늘어난다 — 데코레이터가 이 문제를 해결한다.
- 컴포넌트 인터페이스, 구체 컴포넌트(concrete component), 추상 데코레이터(abstract decorator), 구체 데코레이터(concrete decorator)로 구성되며, 객체들을 스택(stack)처럼 쌓아 행동을 조합한다.
- 커피에 재료를 더하는 비유와, 기본 웹 페이지에 권한 부여(authorization)·인증(authentication) 행동을 덧붙이는 예시를 다룬다.

## 내용

### 커피 비유

- 블랙 커피에 우유, 향 크림, 핫초콜릿 같은 재료를 더하면 커피가 달라진다. 여전히 커피 기반 음료지만 블랙 커피와 라떼·에스프레소 같은 더 화려한 버전 사이에는 기대되는 차이가 있다.
- 어떤 커피를 마시든 각 재료의 효과는 변하지 않는다. 커피는 카페인 때문에 항상 각성제(stimulant)로 작용하며, 우유를 넣든 추출 방식을 바꾸든 온도를 바꾸든 그대로다. 커피에 무엇을 넣어도 마찬가지다. 유당불내증인 사람은 우유가 커피에 섞여 있어도 여전히 유제품을 소화할 수 없다 — 우유의 유당은 다른 것과 섞여도 변하지 않는다.
- 각 재료가 자기 특성을 유지하면서도, 조합하면 따로 마실 때보다 더 즐거운 새 음료가 만들어진다.

### 문제: 클래스와 상속은 정적이다

- 소프트웨어에서도 새 음료를 고안하듯 행동의 유연한 조합이 유익하다. 그런데 이를 런타임에 동적으로 하려면 문제가 생긴다.
- 객체의 행동은 클래스가 정의하는데, 클래스라는 개념과 상속 같은 관계는 **정적** — 즉 컴파일 타임에 일어난다. 프로그램 실행 중에 클래스를 바꿀 수 없다.
- 새 행동 조합을 얻으려면 새 클래스를 만들어야 하고, 조합이 많아지면 클래스가 많아진다 — 원치 않는 상황이다.
- 질문: 어떤 행동을 가진 객체에, 사실상 동적으로 추가 행동이나 책임을 붙일 수 있을까? 데코레이터 디자인 패턴이 이를 달성하며, **집약(aggregation)을 사용해 런타임에 행동을 조합**한다.

### 집약 스택(Aggregation Stack)

- 집약은 두 객체 간의 "has a"(약한 포함, weak containment) 관계를 나타낸다. 이 "has a" 관계로 객체들의 스택을 쌓을 수 있는데, 스택의 각 레벨에는 자기 행동을 알면서 자기 아래 객체의 행동을 증강(augment)하는 객체가 있다.
- 스택 구조: 객체 A는 다른 객체를 담지 않는 기반(base) 객체로 자기 행동 집합을 가진다. 객체 B가 객체 A를 집약해 A의 행동을 사실상 증강한다. 객체 C가 객체 B를 집약해 B의 행동을 증강하는 식으로 계속 쌓을 수 있다.
- 데코레이터 패턴에서 집약 관계는 항상 **1대1**이다 — 한 객체가 다른 객체 위에 놓이도록 스택을 쌓기 위해서다.
- 쌓인 객체들의 전체 행동 조합을 얻으려면 맨 위 요소(객체 C)를 호출한다. C가 B를 호출하고, B가 A를 호출한다. A가 자기 행동으로 응답하면, B가 자신의 증분 행동을 더하고, 그다음 C가 자신의 증분 행동을 더한다.
- 실제 구조는 인터페이스와 상속을 모두 활용해 클래스들이 공통 타입을 따르게 하고, 그 인스턴스들이 호환 가능한 방식으로 쌓여 전체적으로 일관된 행동 조합을 만들 수 있게 한다.

### 일반 UML 구조

- **컴포넌트 인터페이스(component interface)**: 모든 클래스의 공통 타입을 정의한다. 클라이언트 클래스는 모든 컴포넌트 클래스에서 같은 인터페이스를 기대한다.
- **구체 컴포넌트(concrete component) 클래스**: 컴포넌트 인터페이스를 구현하고 인스턴스화할 수 있다. 이 클래스의 인스턴스가 스택의 기반 객체가 된다.
- **데코레이터(Decorator)**: 추상 클래스다. 구체 컴포넌트처럼 컴포넌트 인터페이스를 구현하지만, 두 가지가 다르다: (1) 다른 타입의 컴포넌트를 **집약**해 컴포넌트들을 서로 쌓을 수 있게 하고, (2) 증분 행동을 제공할 구체 데코레이터 클래스들의 추상 슈퍼클래스 역할을 한다.
- 스택은 구체 컴포넌트 클래스의 인스턴스로 시작해, 데코레이터 추상 클래스의 서브클래스 인스턴스들로 이어 쌓는다.
- 커피 비유로는 구체 컴포넌트가 블랙 커피이고, 데코레이터는 우유·설탕·핫초콜릿 등 커피에 더할 수 있는 재료다.

### 현실적인 예시: 웹 페이지

- 커피, 피자 등 비유는 많지만 실제 소프트웨어 활용과는 거리가 있다. 더 현실적인 예가 웹 페이지다.
- 기본 웹 페이지는 HTML 마크업, 스타일시트(stylesheet), 그리고 약간의 JavaScript다. 하지만 웹 페이지의 행동은 더 복잡할 수 있다 — 접근하는 사람이 권한이 있는지 확인하고 싶다면? 많은 검색 결과를 여러 페이지로 나누고 싶다면?
- 권한(permission)·페이지네이션(pagination)·캐싱(caching) 행동의 가능한 조합마다 완전히 다른 웹 페이지 타입을 작성하고 싶지는 않다. 대신 데코레이터 패턴으로 행동 타입마다 클래스 하나를 만들고, 원하는 웹 페이지 조합을 런타임에 구성한다.
- UML 구성:
  - 컴포넌트 인터페이스는 `WebPage`. 패턴의 모든 서브클래스를 자신을 표시(display)하는 구현을 가진 웹 페이지 타입으로 정의한다.
  - 구체 컴포넌트는 `BasicWebPage`. HTML, 스타일시트, 스크립트로 구성되며(단순화를 위해 문자열로 표현) 자신의 웹 페이지 요소를 모두 표시할 줄 안다.
  - 기본 웹 페이지를 서브클래싱하는 대신 집약을 사용해 기능을 더하는 데코레이터들이 필요하다. 추상 `WebPageDecorator`의 서브타입들을 사용한다. `WebPageDecorator`는 `WebPage`의 서브타입이므로, 데코레이터의 서브타입 역시 `WebPage` 인터페이스의 서브타입이다.
  - 예시에서는 사용자가 페이지에 접근할 수 있는지 확인하는 권한 부여(authorization)와, 사용자가 주장하는 그 사람인지 확인하는 인증(authentication)으로 기본 웹 페이지를 강화한다.
- 이 방식이 필요한 클래스 수를 줄인다. 기본 웹 페이지의 상속을 썼다면 이 행동들의 모든 조합마다 클래스를 만들어야 한다 — 권한 부여+인증이 결합된 별도 클래스가 필요했을 것이다. 데코레이터 패턴은 구체 데코레이터가 어떤 타입의 컴포넌트든 집약할 수 있게 해 이 문제를 해결한다.

### 구현 4단계

1. **컴포넌트 인터페이스 설계**: 패턴의 나머지 클래스들이 서브타입이 될 인터페이스를 정의한다. 기본 웹 페이지와 데코레이터들이 가질 공통 행동을 정의한다.
2. **기반 구체 컴포넌트 클래스로 인터페이스 구현**: `BasicWebPage`는 표준 HTML 마크업과 CSS로 정의된 페이지 요소 스타일링으로 자신을 표시하는 방법을 구현하고, 기본 JavaScript도 실행한다. 런타임에 모든 웹 페이지 객체의 기반 빌딩 블록이 된다.
3. **추상 데코레이터 클래스로 인터페이스 구현**: 코드는 적지만 중요하다.
   - `WebPageDecorator`는 `WebPage` 인스턴스를 **하나만** 담는다. 이것이 기본 웹 페이지 위에, 그리고 서로의 위에 데코레이터를 쌓을 수 있게 한다.
   - 각 웹 페이지 타입은 자기 행동을 책임지고, 스택의 다음 웹 페이지를 재귀적으로 호출해 그 행동을 실행시킨다.
   - 생성자는 서로 다른 `WebPage` 서브타입들을 스택으로 연결하게 해 준다. 어떤 `WebPage` 서브타입 인스턴스 위에 쌓을지 알려주기만 하면 된다.
   - 생성자가 어떤 서브타입이든 연결할 수 있으므로 **스택을 쌓는 순서가 중요**하다. 핵심은 `BasicWebPage`가 스택의 첫 번째여야 한다는 것이고, 나머지 순서는 시스템 설계와 어떤 증강 행동을 먼저 실행할지에 달렸다.
   - 추상 데코레이터는 표시(display) 행동을 자신이 집약한 `WebPage` 객체에 위임한다. 이것이 스택 아래로 표시 행동을 결합하게 해 준다.
4. **추상 데코레이터를 상속하고 구체 데코레이터 클래스로 인터페이스 구현**: 생성자는 추상 슈퍼클래스의 생성자를 사용한다(데코레이터들을 함께 쌓을 수 있게 하므로). 각 데코레이터는 자기 책임을 적절한 클래스 안에 구현한다.
   - 표시 행동을 재귀적으로 호출하기 위해 구체 데코레이터는 슈퍼클래스의 display 메서드를 호출한다. 추상 데코레이터 슈퍼클래스가 다양한 웹 페이지 타입의 집약을 담당하므로, `super.display()` 호출은 스택의 다음 웹 페이지가 자기 버전의 display를 실행하게 하며, 이것이 기본 웹 페이지까지 이어진다.
   - 재귀 호출은 기본 웹 페이지에서 끝난다 — 구체 컴포넌트는 다른 웹 페이지 타입을 집약하지 않기 때문이다.
   - 아이디어: display 호출을 맨 아래까지 연결(link)하고 실행을 다시 위로 거품처럼 올린다(bubble up). 기본 웹 페이지를 먼저 만들어야 그 위에 행동을 더할 수 있으므로 이치에 맞다.

### 실행 흐름

- 기본 웹 페이지를 먼저 만들고, 권한 부여 행동을 다음에 더하고, 인증 행동을 마지막에 더해 웹 페이지를 완성한다.
- display 메서드가 호출되면 호출이 기본 웹 페이지까지 연결되어 내려간다. 기본 웹 페이지가 자신을 표시한 뒤, display 호출이 연결을 따라 다시 올라오며 권한 부여 행동이 먼저, 인증 행동이 마지막에 실행된다.
- 어떤 데코레이터든 기본 웹 페이지에 더해 서로 다른 결합 행동을 얻을 수 있다. 집약된 스택에 새 객체를 인스턴스화해 추가할 수 있으므로 기본 웹 페이지의 행동을 동적으로 구성할 수 있다.

## 예시

강의에서 단계별로 설명한 웹 페이지 예시를 Java로 정리하면 다음과 같다.

```java
// 1단계: 컴포넌트 인터페이스 — 공통 행동 정의
public interface WebPage {
    void display();
}

// 2단계: 기반 구체 컴포넌트 — 스택의 기반 빌딩 블록
public class BasicWebPage implements WebPage {
    private String html;
    private String styleSheet;
    private String scripts;

    public void display() {
        System.out.println("Basic WEB page");
    }
}

// 3단계: 추상 데코레이터 — WebPage 인스턴스를 하나만 집약
public abstract class WebPageDecorator implements WebPage {
    protected WebPage page; // 1대1 집약 — 스택 쌓기의 핵심

    // 어떤 WebPage 서브타입 위에 쌓을지 생성자로 연결
    public WebPageDecorator(WebPage webPage) {
        this.page = webPage;
    }

    // 표시 행동을 집약한 WebPage 객체에 위임
    public void display() {
        this.page.display();
    }
}

// 4단계: 구체 데코레이터들 — 증분 행동을 더한다
public class AuthorizedWebPage extends WebPageDecorator {
    public AuthorizedWebPage(WebPage webPage) {
        super(webPage);
    }

    public void authorizedContent() {
        System.out.println("Authorized content");
    }

    public void display() {
        super.display();       // 스택의 다음 웹 페이지 display를 재귀 호출
        this.authorizedContent(); // 실행이 위로 올라오며 자기 행동 추가
    }
}

public class AuthenticatedWebPage extends WebPageDecorator {
    public AuthenticatedWebPage(WebPage webPage) {
        super(webPage);
    }

    public void authenticatedContent() {
        System.out.println("Authenticated content");
    }

    public void display() {
        super.display();
        this.authenticatedContent();
    }
}

// 실행: 기본 웹 페이지 → 권한 부여 → 인증 순으로 스택을 쌓는다
public class Program {
    public static void main(String[] args) {
        WebPage myPage = new BasicWebPage();
        myPage = new AuthorizedWebPage(myPage);
        myPage = new AuthenticatedWebPage(myPage);
        myPage.display();
        // 출력: 기본 웹 페이지가 먼저 표시되고,
        // 권한 부여 행동, 인증 행동 순으로 실행이 올라온다
    }
}
```

## 요약

- 데코레이터 패턴(Decorator pattern)은 순수 상속의 대체물로 집약(aggregation)을 사용해, 사실상 임의 개수의 행동을 런타임에 객체에 동적으로 추가한다.
- 단일 인터페이스 구현으로 다형성(polymorphism)을 얻고, 집약으로 객체 스택을 만든다.
- 스택의 각 데코레이터 객체는 자기 아래 객체와 1대1 집약 관계다.
- 집약과 다형성을 결합해 같은 행동을 스택 아래로 재귀 호출하고, 실행은 구체 컴포넌트 객체에서부터 위로 올라온다.
- 객체를 동적으로 수정할 수 있을 뿐 아니라 작성해야 할 클래스 종류도 줄인다 — 코드베이스가 크면 완성에 시간이 더 걸리고 유지보수가 어렵고 시스템 유연성이 떨어진다.
