# 1.3.5 – Inheritance Issues

## 개요

- 일반화(generalization)와 상속(inheritance)은 객체지향에서 익히기 어려운 주제이며, 잘못 쓰면 오히려 문제를 만든다.
- 상속 오용의 신호: (1) 하위 클래스가 특별한 것을 더하지 않고 단지 속성·행동을 공유하려고만 상속하는 경우, (2) 리스코프 치환 원칙(Liskov Substitution Principle)을 깨는 경우.
- 상속이 맞지 않으면 분해(decomposition)가 더 적절한지 고려한다.

## 내용

### 설계 원칙과 판단

- 객체지향 모델링은 문제 공간의 개념을 소프트웨어로 모델링한다. 문제가 복잡할 수 있으므로 추상화(abstraction)·캡슐화(encapsulation)·분해(decomposition)·일반화(generalization)라는 설계 원칙으로 모델을 다듬는다.
- 각 원칙은 시스템에 어떻게 적용할지 판단을 요구한다: 추상화로 어떤 속성과 행동을 모델링할까? 캡슐화로 이들을 어떻게 묶고 접근하게 할까? 분해로 클래스를 더 작은 부분으로 단순화할 수 있을까? 객체들 사이에 일반화할 공통점이 있을까?
- 예를 들어 자동차는 색상·제조사·모델 같은 속성과 가속·조향 같은 행동을 가지며, 엔진·변속기·배터리로 분해할 수 있다. 그런데 이 모든 것이 서로 어떻게 관계 맺는가? 어떤 부분을 일반화할 수 있는가? 이런 결정이 더 어렵다.
- 상속은 깨끗하고 재사용 가능하며 유지보수 가능한 시스템을 만들 수 있는 강력한 설계 도구지만, 오용하면 나쁜 코드가 된다.

### 오용 신호 1 — 특별한 것 없이 공유만을 위한 상속

- "하위 클래스(subclass)에 특별한 것을 더하지 않고 단지 속성이나 행동을 공유하려고 상속을 쓰고 있는가?"라고 물었을 때 답이 '그렇다'라면 상속을 오용하는 것이다.
- 상위 클래스(superclass)만으로 이미 충분하므로 하위 클래스가 존재할 이유가 없다.
- **피자 가게 예시**: 메뉴의 모든 피자 종류를 모델링해야 할 때, 토핑과 이름의 조합이 다양하므로 상속으로 설계하고 싶어질 수 있다. Pizza 클래스는 토핑, 크기, 크러스트 스타일, 조리 시간을 알도록 일반화되어 있다. 그런데 PepperoniPizza 하위 클래스를 보면, 페퍼로니 피자가 더 구체적인 종류이긴 해도 상위 클래스와 실제로 다르지 않다. 생성자가 Pizza의 생성자를 쓰고 Pizza의 메서드로 토핑을 추가할 뿐이다. Pizza 클래스만으로 페퍼로니를 토핑으로 넣은 피자를 만들 수 있으므로 상속을 쓸 이유가 없다.

### 오용 신호 2 — 리스코프 치환 원칙(Liskov Substitution Principle) 위반

- 리스코프 치환 원칙: **하위 클래스가 상위 클래스의 기능(functionality)을 바꾸지 않을 때, 그리고 오직 그럴 때만, 하위 클래스가 상위 클래스를 대체할 수 있다.**
- **고래(Whale) 예시**: 일반화된 Animal 클래스는 먹기(eat), 걷기(walk), 달리기(run)를 안다. 그런데 고래는 달리거나 걸을 줄 모른다 — 달리기와 걷기는 육지 동물의 행동이다. Whale 클래스가 Animal의 run과 walk 기능을 오버라이드(override)해서 수영(swim) 행동으로 대체하면, 고래는 더 이상 상위 클래스에서 기대하는 방식으로 행동하지 않으므로 리스코프 치환 원칙이 위반된다.

### 실제 사례 — Java의 Stack 클래스

- 나쁜 상속의 예를 Java Collections 라이브러리에서 볼 수 있다.
- 스택(stack)은 선입후출(first in, last out) 자료구조로, peek·pop·push라는 소수의 잘 정의된 행동을 가진다.
- 그러나 Java의 Stack 클래스는 Vector 클래스를 상속하기 때문에, 지정한 인덱스의 요소를 반환하고, 요소의 인덱스를 조회하고, 심지어 특정 인덱스에 요소를 삽입할 수 있다.
- 이는 스택에서 기대되는 행동이 아니지만, 잘못된 상속 사용 때문에 Java에서는 허용된다.

### 상속 대신 분해(decomposition) 고려

- 상속이 필요에 맞지 않으면 분해가 더 적절한지 고려한다.
- **스마트폰 예시**: 스마트폰은 전화와 카메라의 특성을 가진다. Phone을 상속받아 하위 클래스 SmartPhone에 카메라 메서드를 추가하는 설계는 말이 되지 않는다.
- 분해를 사용해 카메라 책임을 추출해서 별도의 클래스에 두어야 한다. 스마트폰은 분리된 부품 클래스들을 통해 카메라와 전화의 책임을 간접적으로 제공하며, 이 클래스들이 어떻게 동작하는지 알 필요가 없다.

## 예시

강의의 피자 예시. 하위 클래스가 상위 클래스와 실질적으로 다르지 않아 상속이 불필요한 경우다.

```java
public class Pizza {
    private java.util.List<String> toppings = new java.util.ArrayList<>();
    private String size;
    private String crustStyle;
    private int cookTimeMinutes;

    public Pizza(String size, String crustStyle, int cookTimeMinutes) {
        this.size = size;
        this.crustStyle = crustStyle;
        this.cookTimeMinutes = cookTimeMinutes;
    }

    public void addTopping(String topping) {
        this.toppings.add(topping);
    }
}

// 상속 오용: 특별한 것을 더하지 않고 상위 클래스의 생성자와
// 메서드를 그대로 쓸 뿐이다. Pizza 클래스만으로 충분하다.
public class PepperoniPizza extends Pizza {
    public PepperoniPizza(String size, String crustStyle, int cookTimeMinutes) {
        super(size, crustStyle, cookTimeMinutes);
        this.addTopping("pepperoni");
    }
}
```

리스코프 치환 원칙 위반 예시(고래).

```java
public class Animal {
    public void eat()  { System.out.println("Eating..."); }
    public void walk() { System.out.println("Walking..."); }
    public void run()  { System.out.println("Running..."); }
}

// LSP 위반: 상위 클래스의 walk/run 기능을 수영 행동으로 바꿔버려
// 상위 클래스에서 기대하는 방식으로 행동하지 않는다
public class Whale extends Animal {
    @Override
    public void walk() { System.out.println("Whales can't walk — swimming instead"); }

    @Override
    public void run()  { System.out.println("Whales can't run — swimming instead"); }
}
```

## 요약

- 상속은 공통 속성·행동을 상위 클래스에 정의하면서 시스템에 맞춘 클래스를 만들 수 있는 강력한 기법이지만, 오용하면 나쁜 코드가 된다.
- 하위 클래스가 특별한 것을 더하지 않고 공유만을 위해 존재한다면 상속 오용이다 (피자 예시).
- 하위 클래스가 상위 클래스의 기능을 바꾸면 리스코프 치환 원칙 위반이다 (고래 예시, Java의 Stack이 Vector를 상속한 사례).
- 상속이 맞지 않으면 분해가 더 적절한지 고려한다 (스마트폰 예시).
