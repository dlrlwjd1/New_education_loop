# 1.3.8 – Model Checking

## 개요

- 모델 검사(model checking)는 시스템의 상태 모델(state model)을 가능한 모든 상태에 대해 체계적으로 검사해, 원하는 속성(property) 위반을 찾아내는 검증(verification) 기법이다.
- 전문가 인터뷰를 통해 수기 증명(proof)과 상태 탐색(state exploration)이라는 두 가지 프로그램 추론 접근, 상태 공간 폭발(state space explosion), 작은 세계 가정(small world assumption)을 다룬다.
- 모델 검사는 모델링(modeling) → 실행(running) → 분석(analysis)의 세 단계로 수행한다.

## 내용

### 모델 검사란

- 설계한 시스템이 올바른지 확인하는 방법은 여러 가지가 있다. 예를 들어 테스트를 돌려 실제 행동이 기대와 일치하는지 볼 수 있다.
- 모델 검사는 시스템의 상태 모델을 **가능한 모든 상태**에 대해 체계적으로 검사하는 기법이다. 소프트웨어의 상태와 변수를 바꾸는 여러 이벤트를 시뮬레이션하면서 오류가 있는지 찾아, 상태 모델에 결함이 있는지 확인한다. 이 검사는 모델 검사 소프트웨어(model checker)로 수행한다.

### 전문가 인터뷰 — 시스템에 대한 추론

- **프로그래밍은 복잡한 정신적 추론이다**: 프로그램을 작성할 때 우리는 어떤 프로그래밍 언어의 문장들이 원하는 제품을 만들어낼 것이라는 매우 복잡한 추론을 자동으로 수행한다. for 루프를 처음 보는 학생은 그것이 무엇을 하는지 이해하지 못하지만, 추론 구조를 내면화하고 나면 5년 뒤에는 왜 어렵다고 생각했는지 의아해한다.
- **복잡한 시스템에서는 추론이 불확실해진다**: 다섯 개의 애플리케이션이 여러 웹 서비스와 통신하고, 웹 서비스끼리도 통신하고, 데이터베이스 업데이트가 동시에 일어나는 상황에서는 "데이터가 일관적인가" 같은 단순한 속성조차 성립하는지 분명하지 않다. 우리는 데이터베이스가 트랜잭션 원자성(transaction atomicity)을 보장한다고 믿고 시스템을 만드는데, 데이터베이스 개발자들은 그것을 어떻게 확신했는가?
- **두 가지 상호보완적 접근** (1970년대에 확인된 문제):
  1. **수학적 증명**: 프로그램을 수학적 산물로 보고, 프로그래밍 언어의 의미론(semantics)을 충분히 이해한다는 가정 하에 프로그램의 속성을 증명한다. 다양한 시스템에 성공적으로 쓰였고, 실제 프로덕션 시스템 깊숙한 곳의 프로그램을 이 방법으로 증명한 사례도 있다. 도구 상자의 중요한 일부다.
  2. **특수 사례의 기계적 열거**: 프로그램들이 서로 통신하고 공유 데이터를 갱신하는 동시성(concurrency) 문제에서는 일반화된 대상이 아니라 수많은 특수 사례("네가 이걸 하고 내가 이걸 하고 네가 저걸 하면?")를 다뤄야 하므로, 손으로 쓰는 증명이 통하지 않는다. 문헌에는 프로토콜을 옳다고 증명했는데 그 증명에 미묘한 버그가 있었던 유명한 논문들도 있다. 그래서 특수 사례를 기계적으로 모두 열거하는 접근이 나왔다.
- **상태로 문제 표현하기**: 시스템은 어떤 상태에 있고, 동작하면 한 상태에서 다른 상태로 바뀐다. 시스템의 행동을 상태 변화로 표현하면 "총 차변(debit)과 총 대변(credit)이 맞지 않는 경우는 절대 없다", "같은 티켓을 두 고객에게 파는 경우는 절대 없다"(항공 예약 시스템의 중요한 명세) 같은 속성을 상태에 대한 진술로 표현할 수 있다.
- **모델 검사의 동작**: 모델 검사는 상태 탐색(state exploration)을 수행한다. 현재 상태에서 시작해 미래로 갈 수 있는 모든 경로를 탐색하고, 그 모든 미래 상태가 어떤 모습일지 추론한다. 예: "어느 시점에 티켓 A가 팔렸다면, 그 이후 모든 미래 상태에서 티켓 A의 소유자는 정확히 한 명이다." 모델 검사기는 시스템이 어떻게 진화하는지 살펴본 뒤 답을 준다 — "두 사람이 같은 티켓을 산 경우는 없다"이거나, 아니면 "틀렸다, 여기 반례(counterexample)가 있다"며 고객 1과 2가 같은 티켓을 갖게 되기까지 시스템이 거친 이상한 단계들을 보여준다. 즉, 틀렸다는 사실만이 아니라 **틀린 사례 하나**를 제시한다.
- **상태 공간 폭발(state space explosion)**: 1비트면 2개 상태, 10비트면 2^10개, 100만 비트면 2^1,000,000개 상태가 된다. 2^1,000,000은 탐색할 방법이 없다. (인터뷰 시점 기준) 당시 모델 검사기는 약 2^40개 상태가 탐색 한계였다. 문제를 적은 수의 비트로 기술할 수 없다면 모델 검사기가 도움이 되지 않는다.
- **작은 세계 가정(small world assumption)과 프로그램 추출**: 모델 검사는 코드에서 모델링에 필요한 부분만 추출하는 능력에 의존한다. 예를 들어 구매 시스템에서 구매 주문(purchase order)의 합계 금액은 비트가 너무 많아 모델링할 수 없어도, 주문에 항목이 1~2개 있는 경우만 모델링할 수 있다 — 증명하려는 것이 "이행 시스템(fulfillment system)에 지불 요청을 하면 주문의 모든 항목이 배송(shipping) 상태에 도달해 있다"는 것이라면 그것으로 충분하기 때문이다. 작은 세계 가정이란, 시스템이 잘못된다면 작은 사례에서 잘못되며, 작은 사례들을 살펴보면 큰 사례에서도 잘 동작할 것이라고 합리적인 수준으로 확신할 수 있다는 것이다. 이 프로그램 추출은 여전히 큰 문제이며, 좋은 부분 해법 도구는 많지만 일반 해법은 없다.
- **모델 검사·명세·테스트의 관계**: 시스템이 무엇을 하는지 명세(specify)할 수 있으면 테스트를 쓸 수 있다. 어떤 의미에서 테스트 자체가 명세다. 모델 검사에 성공하면 그 명세에는 테스트 케이스가 필요 없다 — 시스템이 실제로 옳기 때문이다. 반대로 모델 검사에서 반례가 나오면 그것이 새 테스트 케이스가 된다. 테스트 스위트에 넣고 고친 뒤 다시 돌리면 그 테스트가 통과해야 한다. 결국 이들은 수학적 기술만 다른 같은 것이다.
- **적용 범위의 한계**: 작성되는 전체 코드 중 실제로 모델 검사의 혜택을 받을 수 있는 것은 작은 비율이다. 투자할 만큼 중요하지 않거나, 너무 복잡해서 모델 검사가 아직 충분히 강력하지 않기 때문이다.

### 공항 보안 검색대 비유와 데드락

- 모델 검사는 공항 보안 검색과 비슷하다. 보안 요원은 탑승에 필요한 소지품 규칙을 알고 예외를 두지 않는다. 모델 검사도 시스템 상태 모델의 행동을 검사해 규칙 위반을 통지한다.
- 소프트웨어가 만족해야 하는 규칙의 예: **데드락(deadlock)을 만들지 않아야 한다.** 데드락은 두 작업(task)이 같은 자원(resource)을 기다려서 시스템이 진행할 수 없는 상황이다. 모델 검사기는 시스템에서 발생할 수 있는 여러 상태를 시뮬레이션하고, 데드락이 가능하다면 위반의 세부 정보를 제공한다.

### 모델 검사의 수행 방식과 세 단계

- 모델 검사기는 코드에서 상태 모델(state model)을 생성한다. 상태 모델은 여러 상태 중 하나에 있을 수 있는 추상 상태 기계(abstract state machine)다. 그런 다음 상태 모델이 특정 행동 속성(behavioral property)을 만족하는지 검사한다. 예를 들어 가능한 모든 상태를 탐색하며 경쟁 조건(race condition) 같은 결함을 조사할 수 있다.
- **1) 모델링 단계(modeling phase)**: 모델 기술(model description)을 입력한다. 시스템이 사용하는 프로그래밍 언어로 제공한다. 원하는 속성(desired properties)도 기술한다. 이 단계에서 간단한 무결성 검사(sanity check)를 수행할 수 있다 — 명확하고 단순한 논리에서 나오는 빠르고 쉬운 검사로, 스위치를 껐다 켜서 전구가 작동하는지 확인하는 것과 같다. 모델 검사기를 쓰기 전에 이런 단순한 오류를 제거해 두면 더 복잡한 속성 명세에 집중할 수 있다.
- **2) 실행 단계(running phase)**: 모델 검사기를 실행해 모델이 모델링 단계에서 작성한 원하는 속성에 부합하는지 확인한다.
- **3) 분석 단계(analysis phase)**: 모든 원하는 속성이 만족되는지, 위반이 있는지 확인한다. 위반을 **반례(counterexample)** 라고 부른다. 모델 검사기가 위반에 대한 설명을 제공하므로 어떻게 그 상태에 도달했는지 분석할 수 있다. 이 정보로 문제를 고칠 위치를 파악한 뒤 단계를 다시 반복하며, 원하는 속성에 대해 소프트웨어가 옳다고 확신할 수 있을 때까지 반복한다.

### 모델 검사의 위치

- 단위 테스트(unit testing), 베타 테스트(beta testing), 시뮬레이션 등 시스템 행동을 테스트하는 방법은 많지만, 모델 검사는 이런 테스트가 찾지 못하는 오류를 찾도록 도울 수 있다.
- 다양한 언어를 지원하는 무료 모델 검사기가 많이 있다.
- 이 코스에서 배운 설계 기법을 적용한 뒤 모델 검사를 사용하면, 잘 설계되었을 뿐 아니라 원하는 속성과 행동을 만족하며 의도대로 동작하는 소프트웨어를 보장하는 데 도움이 된다.

## 요약

- 모델 검사는 코드에서 생성한 상태 모델의 가능한 모든 상태를 탐색해, 원하는 속성의 위반(반례)을 찾는 체계적 검증 기법이다.
- 수기 증명이 통하지 않는 동시성 문제의 수많은 특수 사례를 기계적으로 열거하는 접근이며, 위반 시 반례를 함께 제시한다.
- 한계는 상태 공간 폭발이며, 코드에서 필요한 부분만 추출하는 작은 세계 가정(작은 사례에서 옳으면 큰 사례에서도 옳을 것이라는 합리적 확신)에 의존한다.
- 세 단계: 모델링(모델·속성 기술, sanity check) → 실행(속성 부합 확인) → 분석(위반 확인 후 수정·반복).
- 모델 검사는 단위 테스트·베타 테스트·시뮬레이션이 찾지 못하는 오류(데드락, 경쟁 조건 등)를 찾을 수 있고, 반례는 새 테스트 케이스가 된다.
