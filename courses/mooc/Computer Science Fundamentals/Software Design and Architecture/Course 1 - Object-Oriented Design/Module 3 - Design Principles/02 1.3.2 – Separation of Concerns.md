# 1.3.2 – Separation of Concerns

## 개요

- 관심사 분리(separation of concerns)는 유연하고 재사용 가능하며 유지보수하기 좋은 시스템을 만들기 위한 설계 원칙이다.
- 관심사(concern)란 문제 해결에 있어 중요한 모든 것을 가리키는 일반적인 개념이다.
- 추상화(abstraction)·캡슐화(encapsulation)·분해(decomposition)·일반화(generalization)를 적용해 각 관심사를 별도의 구획으로 나눈다.

## 내용

### 관심사(concern)란 무엇인가

- 관심사는 문제에 대한 해법을 제공할 때 중요한 모든 것을 가리키는 매우 일반적인 개념이다.
- 슈퍼마켓 비유: "고기를 어떻게 손질하나?", "빵을 어떻게 굽나?", "결제를 어떻게 받나?", "선반을 어떻게 채우나?" 등이 슈퍼마켓의 관심사다.
- 슈퍼마켓은 각 관심사에 집중하는 **별도의 부서(department)** 를 둔다. 각 관심사는 고유한 하위 문제(sub-problem)를 만들고, 각 부서는 자기 관심사를 어떻게 처리할지 안다. 즉, 슈퍼마켓의 조직 자체가 관심사 분리를 적용한 것이다.
- 소프트웨어 시스템도 비슷한 방식으로 문제를 해결한다. 문제는 많은 관심사를 가진 복잡한 것일 수도, 적은 관심사의 단순한 것일 수도 있다. 문제 공간에서 추상화된 개념들이 소프트웨어로 구현되면서 또 다른 관심사(어떤 정보를 표현하는가, 무엇을 조작하는가, 최종적으로 무엇을 보여주는가 등)가 생겨난다.

### 객체지향 설계 전반에 흐르는 관심사 분리

- 관심사 분리는 객체지향 모델링과 프로그래밍 전체에 적용되는 핵심 아이디어다. 추상화, 캡슐화, 분해, 일반화라는 설계 원칙을 적용할 때 중요한 관심사들이 각각 별도로 다뤄진다.
  - 문제 공간의 각 개념은 관련 속성(attribute)과 행동(behavior)을 가진 별도의 추상화로 이어진다.
  - 이 속성과 행동은 클래스(class)라는 별도의 코드 구획으로 캡슐화된다.
  - 클래스에 대한 시스템의 시각(view)과 구현(implementation)이 분리되어, 인터페이스(interface)를 통한 시각은 그대로 두고 구현 세부사항은 바꿀 수 있다.
  - 하나의 클래스는 여러 클래스로 분해될 수 있다.
  - 클래스들 사이의 공통점을 찾아 상위 클래스(superclass)로 일반화할 수 있다.
- 관심사 분리는 설계 과정 전체에 걸친 지속적인 과정이다.

### 개(Dog) 예시 — 먹는 행동과 먹이 주는 행동의 분리

- 개의 기본 행동으로 걷기, 달리기, 짖기, 먹기가 있다. 여기서 "개가 스스로 할 수 있는 행동은 무엇이고, 다른 누군가의 도움이 필요한 행동은 무엇인가?"를 물어야 한다.
- 처음 모델에서는 개(Dog)가 음식(food)을 가지고 있고 먹는 법을 알며, 음식을 주면 먹으라고 시킬 수 있었다. 하지만 실제로 누가 개에게 음식을 주는가? 개는 항상 음식을 가지고 있는가, 아니면 주인이 주는가?
- 현실에서 개는 주인이 먹이를 줘야 한다. 개는 먹는 법은 알지만 주인이 먹이기 전까지는 음식에 대해 아무것도 모른다.
- 따라서 **먹는 행동**과 **음식을 제공하는 행동**이라는 두 관심사를 분리해야 한다. 이를 위해 DogOwner 클래스를 도입한다.
  - 새 설계에서 Dog 클래스는 음식을 먹는 법만 안다.
  - DogOwner 클래스가 개의 음식을 구하고 개에게 주는 법을 안다.
- 이렇게 하면 해당 행동·속성과 관련 있는 클래스에만 그것들을 캡슐화하게 되어, 코드의 많은 부분을 다시 쓰지 않고도 개별 클래스를 쉽게 교체할 수 있는 모듈형(modular) 시스템이 된다.

### 스마트폰 예시 — 카메라와 전화 기능의 분리

- 스마트폰은 사진 촬영, 일정 관리, 이메일, 웹 브라우징, SMS, 전화 등 많은 일을 한다. 여기서는 카메라와 전통적인 전화 기능만 살펴본다.
- 처음 설계에서는 SmartPhone 클래스가 camera와 phone 관련 속성과 행동을 모두 가진다. 이 설계의 문제:
  - 서로 관련 없는 행동들이 한 클래스에 있어 **응집도(cohesion)가 낮다**. 카메라의 행동은 전화의 행동과 함께 캡슐화될 필요가 없다.
  - **모듈성(modularity)이 없다**. 카메라나 전화 중 하나만 필요한 다른 시스템을 만들 때 따로 접근할 수 없고, 이 클래스의 카메라 코드를 통째로 제거하지 않고는 카메라를 다른 것으로 교체할 수 없다.
- SmartPhone 클래스의 관심사는 두 가지다: (1) 전통적인 전화 역할, (2) 내장 카메라로 사진 찍기. 이를 각각 더 응집도 높은 클래스로 분리하고, 각 세부사항을 기능적으로 독립된 클래스에 캡슐화한다.
- 개선 절차:
  1. 카메라와 전화의 속성·행동을 두 개의 **인터페이스(interface)** 로 추출한다 (일반화 적용).
  2. FirstGenCamera 클래스와 TraditionalPhone 클래스가 각 인터페이스를 구현한다 (추상화·캡슐화 적용).
  3. SmartPhone 클래스는 카메라·전화 클래스의 인스턴스를 참조해 두 기능의 **조정자(coordinator)** 역할을 한다 (분해 적용). 각 구성 요소가 어떻게 동작하는지 몰라도 모든 행동에 접근할 수 있다.
  4. SmartPhone 생성자는 camera와 phone을 매개변수로 받는다. 어떤 phone·camera 객체를 생성할지는 별도의 책임으로 남겨두며, SmartPhone은 알 필요가 없다.
  5. SmartPhone의 메서드들은 카메라·전화 사용 책임을 해당 객체들에 **위임(forward)** 한다.
- 결과: 카메라나 전화 클래스를 다른 것으로 교체하고 싶으면 SmartPhone 클래스 코드는 건드리지 않고, 스마트폰과 부품을 생성하는 코드만 바꾸면 된다.
- **트레이드오프**: SmartPhone 클래스는 더 응집도가 높아졌지만, camera·phone 인터페이스를 알아야 하고 다른 클래스들에 간접적으로 의존하므로 시스템의 결합도(coupling)는 증가했다.

### 설계 목표와의 관계

- 관심사 분리는 추상화, 캡슐화, 분해, 일반화를 사용해 더 응집도 높은 클래스를 만든다.
- 각 클래스가 자기 일에 필요한 코드만 담도록 조직되므로 유지보수가 쉬워진다.
- 모듈성이 높아져 개발자가 다른 클래스에 영향을 주지 않고 개별 클래스를 재사용하고 발전시킬 수 있다.
- 스마트폰 예시에서는 클래스 경계가 명확했지만, 실제 문제는 그렇게 분명하지 않을 수 있다. 주어진 문제의 여러 관심사를 어떻게 추상화·캡슐화·분해·일반화할지 결정하는 것이 모듈형 소프트웨어 설계의 핵심이다.

## 예시

강의의 스마트폰 예시를 코드로 정리한 것이다. 카메라와 전화 기능을 인터페이스로 분리하고, SmartPhone이 이를 조합(composition)한다.

```java
// 1. 일반화: 두 개의 인터페이스로 추출
public interface ICamera {
    void takePhoto();
}

public interface IPhone {
    void makePhoneCall();
}

// 2. 추상화·캡슐화: 인터페이스를 구현하는 클래스들
public class FirstGenCamera implements ICamera {
    @Override
    public void takePhoto() {
        System.out.println("Taking a photo with the first-gen camera.");
    }
}

public class TraditionalPhone implements IPhone {
    @Override
    public void makePhoneCall() {
        System.out.println("Making a phone call.");
    }
}

// 3. 분해: SmartPhone은 카메라와 전화의 조정자 역할만 한다
public class SmartPhone {
    private ICamera myCamera;
    private IPhone myPhone;

    // 생성자가 camera와 phone을 매개변수로 받는다.
    // 어떤 구현체를 생성할지는 SmartPhone의 책임이 아니다.
    public SmartPhone(ICamera camera, IPhone phone) {
        this.myCamera = camera;
        this.myPhone = phone;
    }

    // 책임을 부품 객체에 위임(forward)한다
    public void useCamera() {
        this.myCamera.takePhoto();
    }

    public void usePhone() {
        this.myPhone.makePhoneCall();
    }

    public static void main(String[] args) {
        SmartPhone myPhone = new SmartPhone(new FirstGenCamera(), new TraditionalPhone());
        myPhone.useCamera();
        myPhone.usePhone();
    }
}
```

- 카메라와 전화는 서로에 대해 전혀 모르지만 SmartPhone에 의해 합성(compose)된다.
- 카메라를 교체하려면 `new FirstGenCamera()` 부분만 다른 `ICamera` 구현체로 바꾸면 되고, SmartPhone 코드는 그대로다.

## 요약

- 관심사(concern)는 문제 해결에 중요한 모든 것이며, 관심사 분리는 이를 별도의 구획으로 나눠 다루는 원칙이다.
- 추상화·캡슐화·분해·일반화라는 설계 원칙이 모두 관심사 분리를 구현하는 수단이다.
- 해당 행동·속성과 관련 있는 클래스에만 캡슐화하면 클래스 교체가 쉬운 모듈형 시스템이 된다 (개/주인, 스마트폰 예시).
- 응집도가 높아지는 대신 결합도가 증가하는 트레이드오프가 있을 수 있다.
- 어떻게 관심사를 나눌지 결정하는 것이 모듈형 소프트웨어 설계의 핵심이다.
