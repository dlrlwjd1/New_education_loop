# 1.3.1 – Coupling and Cohesion

## 개요

- 설계 복잡도(design complexity)를 평가하는 두 가지 지표인 결합도(coupling)와 응집도(cohesion)를 배운다.
- 결합도는 모듈(module)과 다른 모듈 사이의 복잡도를, 응집도는 모듈 내부의 복잡도를 다룬다.
- 유연하고 재사용 가능하며 유지보수하기 좋은 시스템을 위해 낮은 결합도(low coupling)와 높은 응집도(high cohesion)를 지향한다.

## 내용

### 왜 설계 복잡도를 평가해야 하는가

- 심리학자 George Miller의 논문에 따르면, 평균적인 사람은 단기 기억(short term memory)에 약 7개 정도만 담을 수 있다. 피험자들은 무작위 소리와 이미지가 약 7개에 도달하면 회상에 실패하기 시작했다.
- 프로그래밍에서도 모듈을 단순하게 유지하는 것이 매우 중요하다. 설계 복잡도가 개발자가 정신적으로 감당할 수 있는 수준을 넘어서면 버그가 더 자주 발생한다.
- 설계 복잡도는 클래스(class)와 그 안의 메서드(method) 모두에 적용되므로, 이런 프로그램 단위를 통칭해 **모듈(module)** 이라고 부른다.

### 퍼즐 조각 vs 레고 블록 비유

- 나쁜 설계는 퍼즐 조각과 같다. 퍼즐 조각은 특정한 다른 조각에만 연결할 수 있고 그 외에는 연결할 수 없다.
- 잘 설계된 시스템은 레고(Lego) 블록과 같다. 어떤 두 레고 블록이든 어려움 없이 연결할 수 있고, 모든 블록이 서로 호환된다.
- 시스템을 레고처럼 만들면 모듈을 쉽게 연결하고 재사용할 수 있다.

### 결합도(Coupling)

- 결합도는 한 모듈을 다른 모듈에 연결하는 데 드는 복잡도를 나타낸다.
- 모듈이 다른 모듈에 크게 의존하면 **강한 결합(tight coupling)** — 퍼즐 조각 같은 상태다.
- 다른 모듈과 쉽게 연결되면 **느슨한 결합(loose coupling)** — 레고 같은 상태다. 결합도는 느슨하고 낮은 것이 좋다.
- 결합도를 평가할 때는 세 가지를 고려한다.
  - **정도(degree)**: 모듈과 다른 모듈 간 연결의 개수. 적게 유지해야 한다. 예를 들어 소수의 매개변수나 좁은 인터페이스(narrow interface)로 연결된다면 정도가 작고 결합이 느슨하다.
  - **용이성(ease)**: 모듈 간 연결이 얼마나 명확한가. 다른 모듈의 구현(implementation)을 이해하지 않고도 연결을 쉽게 만들 수 있어야 한다.
  - **유연성(flexibility)**: 다른 모듈을 얼마나 쉽게 교체할 수 있는가. 미래에 더 나은 것으로 쉽게 대체할 수 있어야 한다.

### 응집도(Cohesion)

- 응집도는 모듈이 가진 책임(responsibility)의 명확성을 나타내며, 모듈 내부의 복잡도를 다룬다.
- 모듈이 한 가지 일만 수행하거나 명확한 목적을 가지면 **높은 응집도(high cohesion)** 를 가진다.
- 모듈이 둘 이상의 목적을 담으려 하거나 목적이 불분명하면 **낮은 응집도(low cohesion)** 를 가진다.
- 높은 응집도를 지향해야 하며, 모듈이 둘 이상의 책임을 가진다면 모듈을 분리할 때다.

### 결합도와 응집도의 균형

- 복잡한 시스템에서 복잡도는 모듈 사이(between)에 분산되거나 모듈 내부(within)에 분산될 수 있다.
- 높은 응집도를 위해 모듈을 단순화하면 다른 모듈에 더 의존하게 되어 결합도가 올라갈 수 있다.
- 낮은 결합도를 위해 모듈 간 연결을 단순화하면 모듈이 더 많은 책임을 떠안게 되어 응집도가 낮아질 수 있다.
- 따라서 설계에서 낮은 결합도와 높은 응집도 사이의 균형을 잡아야 한다.

## 예시

강의의 센서(Sensor) 클래스 예시. 습도와 온도라는 두 가지 목적을 하나의 클래스가 가진 나쁜 설계다.

```java
// 나쁜 설계: 목적이 둘이라 응집도가 낮다
public class Sensor {
    // controlFlag: 0이면 습도(humidity), 1이면 온도(temperature)를 반환
    public float get(int controlFlag) {
        switch (controlFlag) {
            case 0:
                return this.humidity;
            case 1:
                return this.temperature;
            default:
                throw new IllegalArgumentException("Unknown flag");
        }
    }
    private float humidity;
    private float temperature;
}
```

- `Sensor` 클래스는 명확한 단일 목적이 없어 응집도가 낮다.
- `get` 메서드는 제어 플래그(control flag)의 의미가 불분명해서, 어떤 값을 넘겨야 하는지 알려면 메서드 내부를 읽어야 한다. 이는 캡슐화(encapsulation)를 존중하지 않는 것이며 용이성(ease)이 부족함을 보여준다. 그 결과 이 메서드를 호출하는 쪽은 강하게 결합된다.

개선된 설계에서는 `Sensor`를 `HumiditySensor`와 `TemperatureSensor` 두 클래스로 대체한다.

```java
// 개선된 설계: 각 클래스가 명확한 단일 목적을 가진다
public class HumiditySensor {
    public float get() {
        return this.humidity; // 습도를 반환한다고 합리적으로 추정 가능
    }
    private float humidity;
}

public class TemperatureSensor {
    public float get() {
        return this.temperature; // 온도를 반환한다고 합리적으로 추정 가능
    }
    private float temperature;
}
```

- 각 클래스가 명확히 정의된 하나의 목적을 가지므로 높은 응집도를 가진다.
- `get` 메서드가 더 이상 정보를 숨기지 않으므로 캡슐화를 깨고 내부를 들여다볼 필요가 없다. 이 클래스들을 사용하는 다른 모듈은 느슨하게 결합된다.

## 요약

- 설계 복잡도가 개발자의 인지 한계를 넘으면 버그가 늘어나므로 평가 지표가 필요하다.
- 결합도(coupling)는 모듈 간 복잡도로, 정도(degree)·용이성(ease)·유연성(flexibility)으로 평가하며 낮을수록 좋다.
- 응집도(cohesion)는 모듈 내 책임의 명확성으로, 높을수록 좋다. 책임이 둘 이상이면 모듈을 분리한다.
- 낮은 결합도와 높은 응집도는 서로 트레이드오프 관계가 있어 균형이 필요하다.
