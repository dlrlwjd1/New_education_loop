# 1.1.6 – Record, Organize, and Refine Components

## 개요

- CRC 카드(Class, Responsibility, Collaborator)는 개념 설계(conceptual design) 단계에서 컴포넌트를 기록(record)·조직(organize)·정제(refine)하는 기법이다.
- 연설 준비에 쓰는 노트 카드처럼, CRC 카드는 컴포넌트를 클래스(class)로 조직하고 책임(responsibility)을 식별하며 서로 어떻게 협력(collaborate)하는지 결정하도록 돕는다.
- 은행 기계(bank machine) 예시로 CRC 카드를 이용한 설계, 프로토타이핑, 시나리오 시뮬레이션을 실습한다.

## 내용

### 노트 카드 비유

연설을 계획할 때 각 말할 요점을 노트 카드에 적고, 논리적으로 한 요점에서 다음 요점으로 흐르도록 카드를 배열한다. 소프트웨어 설계에서도 구조를 논리적으로 배치해 볼 수 있는 비슷한 도구가 있으면 좋은데, 그것이 바로 CRC 카드다.

개념 설계에서는 요구사항으로부터 컴포넌트(component)·연결(connection)·책임(responsibility)을 식별하고, 기술 설계(technical design)에서는 이를 정제해 기술적 세부 사항을 부여한다. 식별까지는 좋은 첫걸음이지만 이를 **표현하는 방법**이 필요하다 — 노트 카드를 재배열하듯 설계를 갖고 놀 수 있어야 한다.

### CRC 카드의 구조

CRC는 **Class, Responsibility, Collaborator**의 약자다. CRC 카드는 세 구역으로 나뉜다.

- **상단**: 클래스 이름(class name)
- **왼쪽**: 그 클래스의 책임(responsibilities)
- **오른쪽**: 협력자(collaborators) — 이 클래스가 책임을 수행하기 위해 상호작용하는 다른 클래스들

개념 설계 중에는 후보 컴포넌트마다 카드 하나를 만들어, 컴포넌트 이름을 클래스 이름 구역에, 책임을 책임 구역에 적는다. 연결은 협력자 구역에 반영된다 — 현재 컴포넌트가 책임을 수행하기 위해 연결되거나 상호작용하는 다른 컴포넌트를 나열한다.

CRC 카드는 세 구역으로 나눈 물리적 색인 카드(index card)면 충분하다. 값싸고, 수정 가능하고, 어디서나 구할 수 있다. **일부러 작게** 만들어져 많이 쓸 수 없는데, 이것이 각 컴포넌트를 더 작은 컴포넌트로, 결국 색인 카드 하나에 개별적으로 기술할 수 있을 만큼 작은 클래스로 계속 분해하도록 강제한다.

### 은행 기계 시스템 설계

시나리오: 은행 카드를 은행 기계에 넣으면, 기계가 PIN 입력을 요구해 접근을 인증(authenticate)한다. 그 후 입금(deposit), 출금(withdraw), 잔액 확인(check balances)을 선택할 수 있다. 이 시나리오가 시스템의 기본 요구사항을 시사한다 — 물론 불완전한 요구사항 집합이지만 좋은 출발점이며, 요구사항은 흔히 불완전하고 클라이언트·최종 사용자와의 추가 상호작용으로 해소된다.

**첫 번째 카드 — Bank Customer(은행 고객)**

- 클래스 이름: Bank Customer
- 책임: 은행 카드 삽입(insert bank card), 작업 선택(choose operation — 입금·출금·잔액 확인)
- 협력자: Bank Machine — 고객의 책임은 모두 은행 기계를 필요로 하기 때문

**두 번째 카드 — Bank Machine(은행 기계)**

- 클래스 이름: Bank Machine
- 책임: 은행 고객 인증(authenticate bank customer), 작업 옵션 표시(display task options), 입금, 출금, 잔액 확인
- 협력자: Bank Customer

### 카드 조직과 시뮬레이션

CRC 카드의 핵심 장점은 설계를 **물리적으로 재조직**할 수 있다는 것이다. 관련 카드를 가까이 옮기거나 관계를 암시하도록 배치할 수 있다. 예: Bank Customer 카드를 왼쪽에, Bank Machine 카드를 오른쪽에 놓는다.

카드가 조직되면 지금까지의 설계로 프로토타입(prototype)을 **시뮬레이션**할 수 있다. 은행 기계가 고객을 인증하는 시나리오를 연기해 보자: 고객의 "카드 삽입" 책임을 실행하면 → 은행 기계와 협력해 "고객 인증" 책임이 촉발되고 → 인증되면 은행 기계가 "작업 옵션 표시" 책임을 실행한다.

### 실험으로 새 컴포넌트 발견

CRC 카드는 값싸고 수정 가능하며 버릴 수 있어(disposable) 대안 설계를 실험하고 갖고 놀도록 장려한다. 위 시뮬레이션에서 "은행 기계는 어떻게 고객을 인증하는가?"라는 질문이 나오는데, 이는 은행 기계가 인증을 위해 통신하는 새 컴포넌트 **Bank(은행)** 의 추가를 시사한다.

다양한 시나리오를 프로토타이핑·시뮬레이션하면서 후보 컴포넌트를 더 찾을 수 있다.

- 은행 기계는 네트워크(network)를 통해 은행과 통신하므로 둘 사이에 **Network** 카드를 추가한다.
- 네트워크 통신이 안전해야 하므로 Network가 새 컴포넌트 **Encryption(암호화)** 과 협력하게 한다. 이 컴포넌트가 은행과의 보안 통신을 지원한다.
- 은행 기계 자체도 여러 컴포넌트를 포함한다: 카드 리더(card reader), 키패드(keypad), 디스플레이(display), 수표 투입구(cheque slot), 현금 배출구(cash dispenser). 각각 프로그래밍 시 개별 클래스가 될 만큼 작아 보이며, 각자의 책임과 협력자를 자기 카드에 기술할 수 있다.

설계 회의에서 모든 카드를 테이블에 올려놓고 클래스들이 어떻게 협력해 책임을 달성하는지 시뮬레이션을 논의할 수 있다. 시뮬레이션은 설계의 결함(shortcomings)을 드러낼 수 있고, 적절한 카드를 도입해 대안을 실험할 수 있다.

### 기법의 한계

CRC 카드는 후보 컴포넌트와 그 책임·연결을 표현하는 기법일 뿐이다. 노트 카드를 쓴다고 훌륭한 연설이 보장되지 않고 요점 배열에는 연설 작성 경험이 필요하듯, CRC 카드를 정의하고 설계를 제대로 구성하려면 다양한 설계 기법에 대한 지식이 필요하다. 이후 전문과정에서 더 효과적으로 설계할 수 있는 다양한 기법을 다룬다.

## 예시

은행 기계 시스템의 CRC 카드 예시:

```text
+--------------------------------------------+
| Bank Customer                              |
+---------------------------+----------------+
| Responsibilities          | Collaborators  |
| - insert bank card        | - Bank Machine |
| - choose operation        |                |
|   (deposit / withdraw /   |                |
|    check balance)         |                |
+---------------------------+----------------+

+--------------------------------------------+
| Bank Machine                               |
+---------------------------+----------------+
| Responsibilities          | Collaborators  |
| - authenticate customer   | - Bank Customer|
| - display task options    |                |
| - deposit                 |                |
| - withdraw                |                |
| - check balances          |                |
+---------------------------+----------------+
```

시뮬레이션으로 확장된 설계:

```text
Bank Customer ── Bank Machine ── Network ── Bank
                                   |
                               Encryption

Bank Machine 내부의 클래스 후보:
  Card Reader, Keypad, Display, Cheque Slot, Cash Dispenser
```

## 요약

- CRC 카드(Class, Responsibility, Collaborator)는 개념 설계에서 컴포넌트를 기록·조직·정제하는 기법이다.
- 카드 구조: 상단 = 클래스 이름, 왼쪽 = 책임, 오른쪽 = 협력자(책임 수행을 위해 상호작용하는 다른 클래스).
- 카드가 일부러 작아서 컴포넌트를 카드 하나에 담길 만큼 작은 클래스로 계속 분해하도록 강제한다.
- 값싸고 수정·폐기 가능하므로 물리적 재배치, 시나리오 시뮬레이션, 대안 설계 실험에 적합하며, 이 과정에서 새 컴포넌트(Bank, Network, Encryption 등)와 요구사항·설계의 결함이 드러난다.
- CRC 카드는 표현 기법일 뿐, 좋은 설계에는 여전히 다양한 설계 기법에 대한 지식이 필요하다.
