# 1.1.4 – Software Requirements, Conceptual and Technical Designs

## 개요

- 소프트웨어 개발은 문제를 받아 소프트웨어 솔루션을 만드는 반복적(iterative) 과정이며, 요구사항(requirements)과 설계(design)를 건너뛰고 바로 코딩하는 것이 프로젝트 실패의 주요 원인이다.
- 요구사항 도출(eliciting requirements)은 클라이언트가 말하지 않은 것까지 드러내는 후속 질문을 던지는 기술이다.
- 설계 활동은 개념 설계(conceptual design) → 기술 설계(technical design) 순서로 진행되며, 각각 개념 목업(conceptual mockup)과 기술 다이어그램(technical diagram)이라는 산출물(artifact)을 만든다.

## 내용

### 요구사항과 설계의 중요성

소프트웨어 개발은 문제를 받아 솔루션을 만드는 과정으로, 보통 각 반복(iteration)마다 일련의 요구사항을 동작하고 테스트된 구현까지 가져가며 점진적으로 완전한 솔루션을 쌓아 올린다.

많은 개발자가 무엇을 프로그래밍해야 할지 충분히 이해하지 못한 채 바로 코딩에 뛰어들고 싶어 한다. 그러나 증거에 따르면 구현으로 바로 뛰어드는 것이 프로젝트 실패의 주요 원인이다. The Standish Group의 설문에서 프로젝트 실패의 가장 흔한 원인은 요구사항과 설계 문제와 관련이 있었고, 예컨대 응답자의 약 **13%**가 불완전한 요구사항(incomplete requirements)이 프로젝트에 지장을 주었다고 답했다. 요구사항이 완벽하지 않더라도, 좋은 소프트웨어를 만드는 데 있어 그 중요성을 간과해서는 안 된다. 일단 코딩을 시작해 특정 가정에 의존하게 되면 그 가정을 바꾸기 어려워진다.

### 요구사항 도출(eliciting requirements): 집 설계 시나리오

설계 단계에서는 건축가처럼 소프트웨어의 구조(structure)와 행동(behavior)을 생각해야 한다. 집을 설계하는 시나리오를 보자. 기초를 놓기 전에 집주인이 원하는 것을 먼저 이해해야 한다.

집주인의 요구: 단층집, 체육관(gym) 1개, 욕실 1개, 침실 3개, 거실 1개.

요구사항 도출은 클라이언트가 말하는 것을 듣는 것뿐 아니라, **말하지 않은 것을 명확히 하는 질문**을 던지는 것이다. 이 집에 주방이 없다는 것이 이상하지 않은가? 자연스러운 후속 질문들:

- 주방이 필요할 것으로 예상하는가?
- 방들은 모두 같은 크기여야 하는가? 아니라면 어느 방이 크거나 작아야 하는가?
- 집은 전체적으로 얼마나 커야 하는가?
- 외부 설계 제약(external design constraints)이 있는가? 예: 지역 사회의 건축 제한
- 수동형 태양 에너지(passive solar energy)나 경치를 위해 집이 특정 방향을 향해야 하는가?
- 어느 방들이 서로 멀어야 하고, 어느 방들이 가까워야 하는가?

요구사항 도출의 기술은 이렇게 드러내는 후속 질문(revealing follow-up questions)을 하는 데 있다. 답을 얻으면 초기 요구사항 집합이 생기고 가능한 설계를 생각할 수 있다.

### 개념 설계(conceptual design)

설계 활동은 요구사항을 받아 솔루션의 윤곽을 잡는 것으로, 개념 설계와 기술 설계를 거쳐 **개념 목업**과 **기술 다이어그램**이라는 두 산출물을 만든다.

개념 목업은 요구사항을 어떻게 만족시킬지에 대한 초기 생각을 제공한다. 이 단계에서는 주요 **컴포넌트(component)**, **연결(connection)**, **책임(responsibility)**을 식별하고 기술적 세부 사항은 미룬다.

집 프로젝트의 컴포넌트: 집이 들어설 부지(lot), 집 자체, 주방, 체육관, 욕실, 침실들, 거실.

- **연결**: 거실이 주방에서 바로 접근 가능하다면 거실은 주방과 연결을 가진다.
- **책임**: 각 컴포넌트가 수행해야 하는 과제. 체육관의 책임은 운동 활동과 장비를 위한 공간과 전력 제공, 주방의 주 책임은 주방 기구·가전·식료품 보관 공간과 조리를 위한 전력·수도 제공이다. 주 컴포넌트인 집은 내부의 모든 필요 컴포넌트에 충분한 전력·수도·지지를 제공할 전체 책임을 가진다.

배선(wiring)이나 배관(plumbing)의 구체 사항은 언급하지 않는다. 이는 개념 목업이 완전히 이해된 후에야 다룰 수 있는 기술적 세부 사항이다. 예를 들어 집의 배전반(electrical distribution panel) 크기는 각 방의 전력 요구량을 합산해야 결정된다. 개념 설계를 끝낸 후 기술 설계로 넘어가는 것이 좋으며, 개념 설계가 명확할수록 기술 설계도 좋아진다.

### 기술 설계(technical design)

개념 목업이 끝나면 솔루션의 기술적 세부 사항을 정의한다. 개념 설계에서 파악한 컴포넌트·연결·책임이 **어떻게 충족되는지 기술하는 것**이 기술 설계의 목표다.

- 각 컴포넌트를 점점 더 작은 컴포넌트로 쪼개어, 상세히 설계할 수 있을 만큼 구체적인 수준까지 내려간다.
- 예: 체육관 컴포넌트에는 바닥(floor) 같은 하위 컴포넌트가 필요하다. 집주인이 올림픽 역도 선수를 목표로 훈련 중이므로 바닥은 큰 무게를 지탱할 책임이 있다. 바닥을 어떻게 보강할지 기술하는 수준까지 내려가면 상세 설계가 가능하고, 기술 다이어그램이 이런 구체적 문제의 해결 방법을 표현한다.

### 타협과 피드백 루프

수용 가능한 솔루션을 만들다 보면 타협(compromise)이 생길 수 있다. 체육관 바닥 보강을 위해 아래 지하실에 기둥이나 보를 넣어야 하는데, 집주인이 지하에 머리 공간이 넉넉한 탁 트인 공간도 원한다면? 이런 충돌이 생기면 집주인과 타협을 이끌어내야 하며, 솔루션이 수용 가능하도록 **지속적인 소통과 피드백**이 핵심이다.

개념 설계의 컴포넌트·연결·책임이 기술 설계에서 달성 불가능하거나 요구사항을 충족하지 못하면 개념 설계로 돌아가 재작업해야 한다. 실현 가능한 설계에 도달하면 개념 목업이 클라이언트가 원하는 것을 담고 있는지 계속 확인해야 한다 — 나중에 실제 벽을 부수는 것보다 종이 위에서 설계를 고치는 편이 낫다. 기술 다이어그램은 의도한 솔루션을 건설하는 기초가 된다.

### 소프트웨어 설계에 적용: 대학 강좌 검색 웹사이트

요구사항: "학습자로서, 나는 검색 페이지를 통해 관련 강좌를 검색하고 싶다.(As a learner, I want to search for relevant courses through a search page.)"

**개념 설계**: 요구사항에서 검색 페이지(Search Page)와 강좌(Course)를 컴포넌트로 인식하고, 검색 페이지는 관련 강좌를 검색할 책임을 가진다. 사용자 인터페이스가 있는 소프트웨어의 개념 목업은 손으로 그린 스케치나 컴퓨터 도구로 만든 그림일 수 있다. UI 목업을 스케치해 보면 빠진 컴포넌트가 많이 보인다 — 검색 키워드는 어떻게 입력하는가? 검색은 어떻게 시작되는가? 검색 결과 목록은 어떻게 표시되는가? 이런 초기 목업의 결함은 클라이언트와의 추가 확인이나 더 많은 개념 설계 작업을 요구한다.

더 완성된 개념 설계에서는 검색 페이지가 입력 필드(Input Field)와 검색 버튼(Search Button)을 포함하고 결과 페이지(Results Page)로 전환되며, Course는 결과를 표시하는 방식이다. 검색 페이지가 검색 책임을 다하려면 입력 필드, 검색 버튼, 결과 페이지가 필요하므로 검색 페이지는 이들과 연결을 가진다.

**기술 설계**: 각 컴포넌트를 상세히 설계할 수 있을 만큼 구체적으로 정제(refine)한다. 사용자가 키워드를 입력했을 때 검색 페이지가 관련 강좌를 찾는 책임을 어떻게 수행하는가? 외부 시스템과 통신해야 하는가? 대학에 이미 강좌 데이터베이스(Course Database) 컴포넌트가 있다면, 검색 페이지는 검색 책임을 위해 이를 필요로 하므로 둘 사이에 연결이 생긴다. 여기서는 내부 소프트웨어 컴포넌트를 설계하는 것이므로 개념적 UI 목업을 쓸 수 없고, 이후 전문과정에서 이런 컴포넌트의 구조와 행동을 기술하는 다양한 기술 다이어그램을 배운다.

컴포넌트는 충분히 정제되면 함수(function), 클래스(class), 또는 다른 컴포넌트의 모음이 되고, 개발자들이 개별적으로 구현할 수 있는 훨씬 단순한 문제가 된다. 시스템이 클수록 컴포넌트·연결·책임이 많아지고 정제 단계도 더 많이 필요하므로 더 긴 설계 시간이 필요하다.

## 예시

집 설계 비유와 강좌 검색 웹사이트에 대응한 개념·기술 설계 흐름:

```text
요구사항(requirement)
  "As a learner, I want to search for relevant courses through a search page."

개념 설계(conceptual design) — 컴포넌트·연결·책임, 기술 세부 사항 없음
  컴포넌트: Search Page, Course
  보완 후: Search Page ── Input Field
           Search Page ── Search Button
           Search Page ── Results Page (Course는 결과 표시 방식)
  책임: Search Page = 관련 강좌 검색

기술 설계(technical design) — 책임을 "어떻게" 충족하는지 정제
  Search Page ── Course Database (기존 대학 시스템과의 연결)
  컴포넌트를 함수·클래스 수준까지 분해 → 개발자가 개별 구현
```

## 요약

- 요구사항·설계를 건너뛰고 코딩부터 시작하는 것은 프로젝트 실패의 주요 원인이다(Standish Group 설문: 약 13%가 불완전한 요구사항으로 지장).
- 요구사항 도출은 클라이언트가 말하지 않은 것(예: 주방 없는 집)을 드러내는 후속 질문의 기술이다.
- 개념 설계는 컴포넌트·연결·책임을 식별하고 기술 세부 사항은 미루며, 산출물은 개념 목업이다.
- 기술 설계는 컴포넌트를 상세 설계 가능한 수준까지 쪼개어 책임을 어떻게 충족할지 기술하며, 산출물은 기술 다이어그램이다.
- 기술 설계에서 달성 불가능하면 개념 설계로 되돌아가고, 클라이언트와의 지속적 소통·피드백으로 타협점을 찾는다.
- 개념 목업은 클라이언트·사용자와의 설계 결정 확인에, 기술 다이어그램은 개발 작업 조율에 쓰인다.
