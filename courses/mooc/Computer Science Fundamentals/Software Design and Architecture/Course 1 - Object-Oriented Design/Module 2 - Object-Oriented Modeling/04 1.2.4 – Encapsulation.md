# 1.2.4 – Encapsulation

## 개요

- 캡슐화(encapsulation)는 데이터와 그 데이터를 조작하는 함수를 하나의 자기 완결적(self-contained) 객체로 묶고, 일부는 노출하고 일부는 접근을 제한하는 설계 원리다.
- 캡슐화는 데이터 무결성(data integrity)을 지키고, 민감한 정보를 보호하며, 인터페이스를 유지한 채 구현을 바꿀 수 있게 한다.
- 블랙박스 사고(Black Box Thinking)와 추상화 장벽(Abstraction Barrier)을 통해 클래스 사용자의 복잡성을 줄이고 재사용성을 높인다.

## 내용

### 캡슐화의 세 가지 아이디어

- 많은 것을 객체로 표현할 수 있다. 예를 들어 대학 과목(course)을 객체로 표현하면, 과목 객체는 수강 인원, 학점(credit value), 선수 과목(prerequisites) 같은 속성 값과 이 값을 다루는 행동을 가진다. 과목 클래스는 모든 과목 객체의 본질적 속성과 행동을 정의한다.
- 캡슐화는 이름 그대로 일종의 캡슐(capsule)을 만드는 것이며 세 가지 아이디어를 포함한다.
  1. **묶기(bundle)**: 속성 값(데이터)과 그 값을 조작하는 행동(함수)을 하나의 자기 완결적 객체로 묶는다.
  2. **노출(expose)**: 그 객체의 특정 데이터와 함수를 다른 객체가 접근할 수 있게 노출한다.
  3. **제한(restrict)**: 특정 데이터와 함수에 대한 접근을 그 객체 내부로만 제한한다.
- 요컨대 캡슐화는 필요한 데이터와 함수를 묶어 자기 완결적 객체를 만들고, 다른 객체가 사용할 수 있는 인터페이스(interface)를 노출하며, 내부 세부 사항에 대한 접근을 제한한다.

### 묶기와 관련 데이터

- 어떤 타입의 객체를 위한 클래스를 정의할 때 자연스럽게 묶기가 일어난다. 추상화가 어떤 맥락에서 개념의 관련 속성·행동을 결정하는 데 도움을 주고, 캡슐화는 그 특성들이 같은 클래스에 함께 묶이도록 보장한다.
- 한 클래스에서 만들어진 서로 다른 객체들은 각자 자신의 속성 데이터 값을 가지며 그에 따른 행동을 보인다. 데이터와 그 데이터를 조작하는 코드가 같은 곳에 있으면 프로그래밍이 더 쉽다.
- 객체의 데이터는 그 객체에 관련된 것만 담아야 한다. 학생 객체는 자신의 학위 과정(degree program)처럼 자신에게 관련된 데이터만 담는다 — 실제 학생이 자기 학위 과정을 알고 있듯이. 과목 객체는 수강생 목록을 알고, 교수 객체는 자신이 가르치는 과목 목록을 안다. 이들 중 어느 것도 개설된 다른 과목 전체 목록을 담지 않는다 — 그들에게 관련 없는 데이터이기 때문이다.

### 인터페이스 노출

- 클래스는 메서드(method)를 통해 행동을 정의한다. 메서드는 객체 안의 속성 값(데이터)을 조작해 실제 행동을 구현한다.
- 특정 메서드를 다른 클래스의 객체가 접근할 수 있게 노출하면 그 클래스를 사용하는 인터페이스가 된다. 예: 과목은 학생이 수강 신청(enroll)하게 하는 메서드를 제공하고, 교수가 가르치는 과목은 그 교수가 수강생 목록을 보게 하는 메서드를 제공할 수 있다.

### 접근 제한과 데이터 무결성

- 캡슐화는 데이터 무결성에 도움이 된다. 클래스의 특정 속성과 메서드를 외부 접근으로부터 제한할 수 있다.
- 실무에서는 보통 모든 속성에 대한 외부 직접 접근을 막고 특정 메서드를 통해서만 접근하게 한다. 그러면 객체의 속성 값이 변수 대입으로 직접 바뀔 수 없다. 그렇지 않으면 객체 내부 데이터에 대한 가정이나 의존 관계가 깨질 수 있다.
- 캡슐화는 민감한 정보도 보호한다. 예: 학생 클래스가 학위 과정과 평점(GPA)을 저장하되, GPA의 실제 값을 드러내지 않고 GPA와 관련된 질의를 지원할 수 있다. 학생이 학위 과정에서 좋은 성적 상태(good standing)인지 알려주는 메서드는 계산에 GPA를 사용하지만 실제 값은 절대 드러내지 않는다.

### 인터페이스 유지와 구현 변경

- 캡슐화는 소프트웨어 변경에도 도움이 된다. 클래스의 접근 가능한 인터페이스는 그대로 두고 속성과 메서드의 구현은 바꿀 수 있다. 클래스를 쓰는 외부에서는 인터페이스 뒤의 구현이 실제로 어떻게 동작하는지 신경 쓸 필요가 없다.
- 대학 예시: 교수가 학생에게 과목 수강 전에 GPA를 계산해 알리라고 요구한다면, 학생이 이 행동을 수행하는 방법은 여러 가지다.
  - 종이 양식을 작성해 행정 직원에게 제출하고, 직원이 종이 파일을 확인해 과목·성적 목록을 적어 주면 그것으로 GPA를 계산한다.
  - 일부 자동화되어, 종이 양식을 제출하면 직원이 컴퓨터 데이터베이스에서 GPA를 확인한다.
  - 학생이 직접 온라인 학생 정보 시스템에서 GPA를 조회한다.
- 어떤 방식이든 최종 목표(교수에게 GPA 보고)는 동일하다. 교수는 학생이 GPA를 어떻게 얻는지 신경 쓸 필요가 없고, 그 방법은 학생만 알면 된다.
- 프로그래밍에도 같은 사고를 적용한다. 학생 클래스에 전공(major)을 반환하는 메서드가 있다면, 전공을 가져오는 실제 단계는 다른 어떤 클래스도 알 필요가 없다.

### 블랙박스 사고와 추상화 장벽

- 이런 사고를 흔히 **블랙박스 사고(Black Box Thinking)** 라 부른다. 클래스를 내부가 보이지 않는 블랙박스로 생각하라 — 속성이 어떻게 표현되는지, 메서드가 결과를 어떻게 계산하는지는 보이지 않고, 메서드를 호출해 입력을 주고 출력을 얻는다. 기대되는 행동만 이루어지면 상자 안에서 무슨 일이 일어나는지는 중요하지 않다.
- 외부 세계가 보는 것과 내부 동작의 이 구분이 중요하다. 캡슐화는 **추상화 장벽(Abstraction Barrier)** 을 달성한다. 내부 동작이 외부 세계와 무관해지므로 클래스 사용자의 복잡성이 효과적으로 줄어든다.
- 이는 재사용성(re-usability)을 높인다. 다른 클래스는 원하는 행동을 얻기 위해 어떤 메서드를 호출할지, 입력으로 어떤 인자를 줄지, 출력이나 효과가 무엇인지만 알면 된다.
- 현실 비유: 내가 탄산음료를 사다 달라고 부탁하면, 자판기에서 사든 다른 도시까지 운전해서 사든 상관없다. 입력과 출력은 같다 — 부탁하고, 음료를 받는다. 어떻게 구했는지의 세부는 알 필요 없다.

## 요약

- 캡슐화 = 묶기(bundle) + 노출(expose) + 제한(restrict).
- 속성은 직접 접근을 막고 메서드를 통해서만 다루게 하여 데이터 무결성을 지킨다.
- GPA 예시처럼 민감한 값을 드러내지 않으면서 관련 질의를 지원할 수 있다.
- 인터페이스가 같으면 구현을 자유롭게 바꿀 수 있다 — 블랙박스 사고, 추상화 장벽.
- 캡슐화는 소프트웨어를 모듈화(modular)하고 관리하기 쉽게 만드는 핵심 설계 원리다.
