# 1.2.1 – Models: Bridging Concepts and Solutions

## 개요

- 복잡한 소프트웨어 문제는 코드로 바로 뛰어들지 않고, 문제 공간(problem space)과 해결 공간(solution space)을 반복적으로 다루는 설계 단계를 거친다.
- 객체 지향 모델링(Object-Oriented Modeling)은 문제 속 개념을 객체(object)로 사고하여 사용자와 개발자가 공통 용어로 소통하게 한다.
- 설계 과정에서 만드는 객체 모델은 UML(Unified Modeling Language)로 표현되며, 설계 문서이자 골격 코드(skeletal source code)의 출발점이 된다.

## 내용

### 이 모듈에서 다룰 것

- 이전 모듈에서는 설계가 소프트웨어 개발 프로세스에 어떻게 들어맞는지, 그리고 CRC 카드로 개념 설계(conceptual design)를 완성하는 법을 배웠다.
- 이번 모듈에서는 객체 지향 모델링을 더 깊이 다룬다. 문제를 모델링하는 방법과 프로그래밍 언어가 객체 지향으로 진화해 온 과정부터 시작한다.
- 이어서 객체 지향 모델링에 쓰이는 네 가지 주요 설계 원리(design principles)를 살펴본다. 이 원리들은 문제 해결을 돕고, 유연하고(flexible) 재사용 가능하며(reusable) 유지보수하기 쉬운(maintainable) 소프트웨어로 이어진다.
- 이 설계 원리들을 UML 클래스 다이어그램(UML Class Diagram)과 Java 코드 양쪽으로 표현하는 방법도 배운다.
- 이 모듈에서 첫 번째 캡스톤(capstone) 과제가 나온다. 캡스톤 프로젝트의 나머지 작업은 각 코스의 네 번째 모듈에서 완료하지만, 필요한 내용을 학습한 뒤에는 앞선 모듈에서도 가끔 캡스톤 과제가 주어진다.

### 왜 설계 단계가 필요한가

- 집을 지을 때 설계 없이 못질부터 시작하지 않듯, 복잡한 소프트웨어 문제도 코드로 바로 해결하려 하지 않는다.
- 그 사이에 문제 공간과 해결 공간을 모두 반복적으로(iteratively) 다루는 설계 단계가 있다.
  - **개념 설계(conceptual design)**: 문제를 관리 가능한 조각으로 계속 쪼개기 위해 필요하다.
  - **기술 설계(technical design)**: 개발자가 동작하는 소프트웨어로 구현할 수 있을 만큼 명확하게 해결책을 기술하고 다듬기 위해 필요하다.

### 설계를 쉽게 하려는 과거의 접근

- 오랜 세월 사람들은 설계 활동을 쉽게 만들려는 여러 접근을 시도했다. 예를 들어 특정 종류의 문제 해결에 적합한 프로그래밍 언어의 설계 전략들이 있다.
- 데이터 처리 문제라면 하향식 프로그래밍(Top Down Programming)을 썼을 수 있다. 이 전략은 문제 속 처리 과정(process)을 호출할 루틴(routine)으로 매핑한다. 처리 요구를 하향식으로 분해하면서 최종 해결책을 위한 루틴 트리를 만들고, 이 루틴들은 서브루틴(subroutine)을 지원하는 언어로 구현했다.

### 객체로 사고하기

- 설계 작업에서 문제 공간의 개념과 해결 공간에서의 처리 방식 사이에 큰 사고의 도약(mental jump)이 없어야 설계가 쉬워진다.
- 개념이 사용자와 개발자 모두에게 이해되는 설계로 기술되면, 두 그룹이 공통 용어로 서로의 이해를 논의할 수 있다.
- 많은 복잡한 문제에서 개념을 객체로 생각하는 것이 자연스럽다. 예를 들어 문제 설명의 모든 명사(noun)는 중요한 객체가 될 수 있다. 문제가 발생하는 현실 세계는 객체로 가득하다. 이것이 객체 지향 언어와 객체 지향 프로그래밍(Object-Oriented Programming)의 인기로 이어졌다.
- 다만 객체 지향에서도 문제에서 코드로 바로 가지 않는다.
  - **객체 지향 분석(object-oriented analysis)**: 문제 속 핵심 객체를 식별하는 개념 설계.
  - **객체 지향 설계(object-oriented design)**: 객체의 속성(attributes)과 행동(behaviors)을 포함해 세부 사항을 다듬는 기술 설계.
- 이 설계 활동들은 반복적이고 지속적으로 일어난다.

### 모델과 UML

- 소프트웨어 설계의 목표는 모든 객체의 모델을 구성하고 다듬는 것이며, 모델은 설계 과정 전반에 걸쳐 유용하다.
- 객체의 종류:
  - **엔티티 객체(entity object)**: 초기에 초점을 두는, 문제 공간에서 온 객체.
  - **컨트롤 객체(control object)**: 해결책이 소프트웨어로 구체화되면서 도입되며, 이벤트를 받아 동작을 조율(coordinate)한다.
  - **바운더리 객체(boundary object)**: 시스템 외부 서비스와 연결한다.
- 모델은 보통 UML(Unified Modeling Language)이라는 시각적 표기법으로 표현한다. 객체 지향 모델링에서는 서로 다른 소프트웨어 이슈에 초점을 맞춘 여러 종류의 모델(UML 다이어그램)이 있다. 예를 들어 구조 모델(structural model)은 객체가 무엇을 하고 어떻게 관계 맺는지 기술한다 — 건물의 축소 모형(scale model)으로 공간 관계를 이해하는 것과 같다.
- 복잡성에 대응하기 위해 설계 원리와 지침을 적용해 객체를 단순화하고, 더 작은 부분으로 나누고, 일관되게 다룰 수 있는 공통점을 찾는다.
- 설계가 원래 문제를 해결하고 품질 목표(재사용성, 유연성, 유지보수성)를 만족하는지 모델을 계속 비판하고 평가해야 한다.
- 모델은 설계 문서(design documentation) 역할도 하며, 특히 Java 같은 객체 지향 언어에서는 골격 소스 코드로 쉽게 매핑되어 개발자에게 좋은 출발점을 준다.

## 요약

- 복잡한 문제는 개념 설계(문제 분해)와 기술 설계(해결책 기술·정제)를 거쳐야 하며, 두 활동은 반복적으로 진행된다.
- 객체 지향은 문제 공간의 개념과 해결 공간 사이의 사고 도약을 줄여 사용자와 개발자가 공통 용어로 소통하게 한다.
- 객체 지향 분석은 핵심 객체를 식별하고, 객체 지향 설계는 속성과 행동 등 세부를 다듬는다.
- 모델은 엔티티·컨트롤·바운더리 객체를 다루며 UML로 표현되고, 설계 문서이자 골격 코드의 기반이 된다.
