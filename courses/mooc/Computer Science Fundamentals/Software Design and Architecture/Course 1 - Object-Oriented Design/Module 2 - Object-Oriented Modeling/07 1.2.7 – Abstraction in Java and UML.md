# 1.2.7 – Abstraction in Java and UML

## 개요

- CRC 카드는 건축가의 스케치처럼 개념 설계·프로토타이핑에 적합하고, UML 클래스 다이어그램(UML Class Diagram)은 청사진(blueprint)처럼 구현을 안내하는 기술 설계에 적합하다.
- 클래스 다이어그램은 클래스 이름·프로퍼티(property)·오퍼레이션(operation)의 3단 박스로 추상화를 표현하며, Java 코드와 매우 가깝게 상호 변환된다.
- 이 강의에서는 개념을 클래스 다이어그램의 클래스로 추상화하고, 다이어그램과 코드를 서로 변환하는 방법을 배운다.

## 내용

### 스케치와 청사진 — CRC 카드 vs 클래스 다이어그램

- 건축가는 다양한 설계를 시각화하고 실험하기 위해 스케치를 그린다. 스케치는 빨리 만들 수 있고 고객에게 설계를 직관적으로 전달하지만, 시공자에게는 세부가 부족하다. 시공자와 소통할 때는 정확한 치수가 담긴 상세한 청사진을 제공한다.
- 소프트웨어에서 개발자는 설계를 표현하기 위해 UML 다이어그램이라는 기술 다이어그램을 사용한다.
- 지금까지는 CRC 카드로 개념 설계(conceptual design)만 해 왔다. CRC 카드는 스케치처럼 상위 수준 설계의 프로토타이핑과 시뮬레이션에만 좋다. 구현을 안내하려면 청사진에 가까운 기법이 필요하다.
- UML 클래스 다이어그램(줄여서 클래스 다이어그램)은 CRC 카드보다 더 상세하게, 그러나 여전히 시각적으로 설계를 표현한다. 구현에 훨씬 가까워 코드의 클래스로 쉽게 변환할 수 있다.
- 추상화(abstraction)는 문제 도메인의 개념을 어떤 맥락 안에서 본질로 단순화하는 아이디어다. 먼저 설계 수준에서 UML 클래스 다이어그램으로 추상화를 적용한 뒤, 설계를 코드로 변환한다.

### 예시: 식료품점 맥락의 음식(food) 추상화

- CRC 카드라면: 식료품 ID(grocery ID), 이름, 제조사(manufacturer), 유통기한(expiry date), 가격을 추적하고, 할인(on sale) 여부를 아는 책임을 가진 food 컴포넌트가 된다.
- 설계의 목표는 컴포넌트가 충분히 정제되면 함수·클래스·다른 컴포넌트의 모음이 되는 것이다. 이 코스에서는 Java를 사용하므로 추상화가 클래스로 형성되며, 클래스에 초점을 둔다.

### 클래스 다이어그램의 구조

- 클래스 다이어그램에서 각 클래스는 박스로 표현되고, 박스는 CRC 카드처럼 세 부분으로 나뉜다.
  - **맨 위 — 클래스 이름(Class Name)**: Java 클래스의 이름과 같다.
  - **중간 — 프로퍼티(Property) 섹션**: Java 클래스의 멤버 변수(member variables)에 해당하며, 추상화의 속성(attributes)을 정의한다.
  - **맨 아래 — 오퍼레이션(Operations) 섹션**: Java 클래스의 메서드(methods)에 해당하며, 추상화의 행동(behaviors)을 정의한다.
- 프로퍼티는 주로 변수 이름과 변수 타입으로 구성된다. 타입은 Java처럼 클래스이거나 원시 타입(primitive type)일 수 있다.
- 오퍼레이션은 주로 오퍼레이션 이름, 매개변수 목록(parameter list), 반환 타입(return type)으로 구성된다.
- 예: food 객체에 할인 여부를 반환하는 `isOnSale` 메서드를 두면, boolean(true/false)을 반환한다. 매개변수가 없으면 매개변수 목록을 쓰지 않는다. `isOnSale`이 날짜(date) 매개변수를 받아 그 날짜에 할인 중이면 true를 반환하도록 바꾸면, 매개변수 목록은 클래스 다이어그램 프로퍼티와 같은 형식(이름: 타입)을 따른다.
- CRC 카드와 비교하면, 카드의 책임(responsibilities) 일부는 프로퍼티가 되고 일부(특히 isOnSale)는 오퍼레이션이 된다. CRC 카드는 프로퍼티와 오퍼레이션의 구분 없이 모두 함께 나열되는 등 모호함이 많아 프로그래머가 코드로 직역하기 어렵다.

### 클래스 다이어그램 ↔ Java 변환

- 다이어그램 → 코드: 클래스 이름은 Java의 클래스로, 프로퍼티는 멤버 변수로, 오퍼레이션은 메서드로 변환된다. (지금은 모든 것을 public으로 가정하며, 접근 제한자(access modifier)는 나중에 배운다.)
- 코드 → 다이어그램도 직관적이다. ClickCounter 코드 예시:
  - 코드에서 클래스 이름이 ClickCounter이므로 그것이 클래스 이름이 된다.
  - 멤버 변수 `count`는 프로퍼티가 되고 타입은 int다.
  - 메서드 `setClickCount`와 `getClickCount`는 오퍼레이션이 된다. `setClickCount`는 매개변수를 받으므로 매개변수 이름과 타입을 명시한 매개변수 목록을 포함하고, `getClickCount`는 반환 값이 있으므로 반환 타입을 명시한다.

### 두 도구의 자리

- 클래스 다이어그램의 추가 세부에도 불구하고, 설계 시뮬레이션·프로토타이핑에서 CRC 카드를 대체하지는 못한다. CRC 카드는 싸고 작아 팀과 물리적으로 다양한 설계를 실험하기 쉽고, 코드와 멀기 때문에 구현이 아니라 문제에 집중하게 한다.
- 클래스 다이어그램은 코드에 훨씬 가까워 개발자에게 기술 설계를 명확히 전달하기 좋지만, 매개변수 목록·반환 값 같은 코드 특유의 사항을 명시해야 하므로 개념 설계에는 과하게 상세하다 — 초기 설계에서는 이런 세부가 방해가 되고 기술하는 데 시간이 든다.
- 이 전문과정의 여러 영역에서 클래스 다이어그램을 계속 사용하며, 이후 강의에서 다른 객체 지향 설계 원리들을 다시 살펴보면서 클래스 다이어그램을 확장한다.

## 예시

Food 클래스의 클래스 다이어그램(텍스트 표현):

```text
+-------------------------------------------+
| Food                                      |
+-------------------------------------------+
| groceryID: String                         |
| name: String                              |
| manufacturer: String                      |
| expiryDate: Date                          |
| price: double                             |
+-------------------------------------------+
| isOnSale( date: Date ): boolean           |
+-------------------------------------------+
```

ClickCounter 코드를 클래스 다이어그램으로 변환하는 예:

```java
public class ClickCounter {
    public int count;

    public void setClickCount(int count) {
        this.count = count;
    }

    public int getClickCount() {
        return count;
    }
}
```

```text
+-------------------------------------------+
| ClickCounter                              |
+-------------------------------------------+
| count: int                                |
+-------------------------------------------+
| setClickCount( count: int )               |
| getClickCount(): int                      |
+-------------------------------------------+
```

## 요약

- CRC 카드는 스케치(개념 설계·프로토타이핑), 클래스 다이어그램은 청사진(기술 설계·구현 안내)에 해당한다.
- 클래스 다이어그램 박스는 클래스 이름 / 프로퍼티(멤버 변수) / 오퍼레이션(메서드)의 3단 구조다.
- 프로퍼티는 이름과 타입, 오퍼레이션은 이름·매개변수 목록·반환 타입으로 기술한다.
- 클래스 다이어그램과 Java 코드는 서로 쉽게 변환되지만, 각 도구는 설계 단계에 따라 쓰임이 다르다.
