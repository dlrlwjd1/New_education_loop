# 1.2.2 – Languages Evolution

## 개요

- 프로그래밍 언어는 자연어처럼 진화해 왔으며, 각 새 언어는 이전 언어가 제대로 해결하지 못한 문제를 풀기 위해 등장했다.
- 개발자 Ted의 여정을 따라 1960년대 명령형(imperative) 언어부터 1980년대 객체 지향(object-oriented) 언어까지 패러다임 전환을 살펴본다.
- 객체 지향이 지배적 패러다임이지만 유일한 도구는 아니며, 문제에 맞지 않으면 비객체지향 접근이 더 효율적일 수 있다.

## 내용

### 언어의 진화라는 관점

- 언어는 생각과 아이디어를 서로 소통하기 위한 시스템이며, 쓰기·읽기·말하기·그림·몸짓 등 다양한 방식으로 쓰인다. 언어는 인류의 필요에 맞게 진화해 왔다(현대 기술과 인터넷 문화로 인한 변화를 생각해 보라).
- 프로그래밍 언어도 비슷하게 진화했다. 새 언어는 기존 언어가 충분히 다루지 못한 문제에 해법을 주기 위해 개발되었고, 이런 아이디어들이 프로그래밍 패러다임(programming paradigm)의 전환을 일으켰다.
- 이 여정은 개발자 Ted를 따라간다. 컴퓨터가 입력 배치(batch)를 출력으로 단순 처리하던 초기부터, 복잡한 작업을 돕는 현대까지다.

### 1960년대 — COBOL·Fortran과 명령형 패러다임

- Ted는 1960년대 은행에 고용되어 계좌 잔고를 추적하는 첫 프로그램을 개발한다. 당시 가장 인기 있던 언어는 COBOL과 Fortran이다.
- 이들은 명령형 패러다임(imperative paradigm)을 따랐고, 큰 프로그램을 서브루틴(subroutine)이라는 작은 프로그램으로 쪼갰다. 서브루틴은 Java의 메서드(method)와 비슷하다.
- 당시에는 컴퓨터 처리 시간이 비쌌기 때문에 처리 성능 극대화가 중요했다. 이를 위해 전역 데이터(global data)를 사용했다 — 프로그램의 메모리 한 곳에 모두 위치하므로 모든 서브루틴이 접근해 계산할 수 있었다.
- 문제점: 전역 데이터는 변경이 프로그램에 이상한 부작용(side effect)을 일으킬 수 있었고, 서브루틴이 전역 데이터가 예상과 다른 상황을 만나기도 했다.

### 1970년대 — Algol 68·Pascal과 지역 변수, 추상 자료형

- 더 나은 데이터 관리의 필요가 명령형 프로그래밍의 변화를 이끌어 1970년대 Algol 68과 Pascal 같은 언어가 부상했다.
- 지역 변수(local variable) 개념이 도입되었다. 서브루틴은 프로시저(procedure)라 불렸고 중첩 프로시저(nested procedure)를 가질 수 있었으며, 각자 자신의 변수를 가질 수 있었다.
- 이 언어들은 추상 자료형(abstract data type)을 지원했다. 추상 자료형은 언어에 내장된 것이 아니라 프로그래머가 정의하는 자료형으로, 관련 정보를 하나의 타입으로 묶어 데이터를 의미 있게 조직하는 방법이다. 개발자는 내장 타입과 비슷한 방식으로 이 타입들을 사용해 소프트웨어를 작성할 수 있었다.
- 서로 다른 스코프(scope)의 변수 덕분에 Ted는 데이터를 프로시저별로 구획화(compartmentalize)할 수 있었다. 어떤 데이터를 지역 스코프에 두면 그 프로시저만 수정할 수 있어, 다른 프로시저가 바꿀 걱정을 하지 않아도 된다.

### 1970년대 중반 — C·Modula-2와 파일 단위 조직화

- 1970년대 중반에는 컴퓨터 처리 시간은 저렴해지고 인간 노동은 비싸졌다. 소프트웨어 개발의 시간 소모 요인은 이제 인간 요소였다.
- 문제가 복잡해지면서 소프트웨어가 거대해졌고, 프로그램을 파일 하나로 유지하기 어려워졌다.
- C와 Modula-2 같은 새 언어는 프로그램을 조직하는 수단과 추상 자료형의 고유한 복사본을 더 쉽게 여러 개 만드는 방법을 제공했다. 프로그램을 별도 파일들로 조직할 수 있게 되었다.
- C에서는 각 파일이 관련 데이터와 그것을 조작하는 함수를 모두 담고, 외부에서 접근 가능한 것은 헤더 파일(Header File)이라는 별도 파일에 선언했다.
- 남은 문제: 이 언어들은 추상 자료형이 다른 추상 자료형을 상속(inherit)하기 어려웠다. 타입을 얼마든지 정의할 수는 있어도, 한 타입이 다른 타입의 확장(extension)이라고 선언할 수 없었다.

### 1980년대 — 객체 지향 설계와 클래스, 상속

- 1980년대에 객체 지향 프로그래밍의 중심이 되는 객체 지향 설계(Object-Oriented Design) 개념이 대중화되었다. 목표는:
  - 추상 자료형을 더 쉽게 작성하게 하고,
  - 클래스(class)라 불리는 추상 자료형을 중심으로 시스템을 구조화하고,
  - 상속(inheritance) 개념을 도입해 한 추상 자료형이 다른 것을 확장할 수 있게 하는 것.
- 객체 지향 패러다임에서 Ted는 전적으로 추상 자료형으로 이루어진 소프트웨어 시스템을 만들 수 있다. 이 시스템은 문제의 구조를 모방(mimic)하므로, 객체 지향 프로그램은 현실 세계의 객체나 아이디어를 더 높은 충실도(fidelity)로 표현할 수 있다.
- 클래스 파일이 C·Modula-2의 일반 파일을 대체했다. 각 클래스는 관련 데이터와 함수(메서드라고도 함)를 가진 타입을 정의한다. 클래스는 공장(factory)처럼 동작해 특정 타입의 개별 객체들을 만들어낸다. 이로써 데이터와 그 조작 방법을 각자의 클래스로 구획화할 수 있다.
- 객체 지향 프로그래밍은 지배적인 패러다임이며, Java·C++·C# 같은 인기 있는 현대 언어들이 객체에 기반한다.

### 왜 이 역사가 중요한가

- 소프트웨어 개발자는 오늘날 업계에 무엇이 있는지 폭넓게 이해해야 한다. 여전히 오래된 언어와 설계 패러다임을 쓰는 시스템이 많다.
- 객체 지향 프로그래밍은 강력한 도구지만 유일한 도구는 아니다. 설계가 문제에 맞지 않을 수 있으므로 객체 지향 설계가 항상 최선은 아니다.
- 비객체지향 접근을 택하더라도 시간을 효율적으로 쓰는 것이 더 중요하다. 컴퓨터 성능이 좋아진 지금, 소프트웨어를 만드는 가장 비싼 비용은 바로 사람(개발자)이다.

## 요약

- 1960년대 COBOL·Fortran: 명령형 패러다임, 서브루틴과 전역 데이터 — 성능은 좋았지만 부작용 문제가 있었다.
- 1970년대 Algol 68·Pascal: 지역 변수, 프로시저, 추상 자료형(abstract data type) 도입으로 데이터 구획화가 가능해졌다.
- 1970년대 중반 C·Modula-2: 파일 단위 조직화와 헤더 파일 — 그러나 타입 간 상속은 여전히 불가능했다.
- 1980년대 객체 지향: 클래스와 상속으로 시스템이 문제 구조를 모방하고 현실을 더 충실히 표현하게 되었다.
- 객체 지향이 항상 정답은 아니며, 개발자의 시간이 가장 비싼 자원이므로 문제에 맞는 접근을 선택해야 한다.
