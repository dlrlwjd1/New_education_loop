# 1.2.11 – Generalization with Interfaces in Java and UML

## 개요

- 인터페이스(interface)는 메서드 시그니처(method signature)만 선언하는 타입으로, 구현 세부 없이 기대되는 행동을 명시하는 계약(contract)이다.
- 상속과 인터페이스 모두 서브타이핑(subtyping)을 달성하지만, 인터페이스는 구현을 상속하지 않으므로 구현 클래스가 직접 메서드 본문을 제공해야 한다.
- 인터페이스는 다형성(polymorphism)을 구현하는 수단이며, 다중 상속(multiple inheritance)의 데이터 모호성(data ambiguity) 문제 없이 한 클래스가 여러 인터페이스를 구현할 수 있게 한다.

## 내용

### 타입과 서브타이핑

- 클래스는 그 객체들의 타입(type)을 나타낸다. 타입은 그 객체들이 public 메서드를 통해 무엇을 할 수 있는지를 뜻한다. 예: dog 클래스의 인스턴스는 dog 타입 객체이고, 개가 하는 일을 한다.
- 문제를 모델링할 때 두 타입 사이의 서브타이핑(subtyping) 관계를 표현하고 싶을 수 있다. 예: dog 타입을 animal 타입의 서브타입(subtype)으로 두면, dog 객체는 dog 타입일 뿐 아니라 animal 타입이기도 하다. 개처럼 행동할 뿐 아니라 동물처럼도 행동해야 한다 — 사실상 개는 동물이다(a dog is an animal).
- Java에서는 `extends` 키워드를 쓰는 클래스 상속이 서브타이핑에 자주 쓰인다. dog 서브클래스가 animal 슈퍼클래스를 extends 하면, dog 객체는 상속받은 animal의 메서드와 속성을 통해 기본적으로 동물처럼도 행동한다. 이때 dog 클래스는 animal 클래스의 **구현 세부(implementation details)를 상속**한다.

### 인터페이스란

- Java 인터페이스도 타입을 나타낸다. 그러나 클래스와 달리 인터페이스는 **메서드 시그니처만 선언**하며, 생성자·속성·메서드 본문(method body)이 없다. 메서드 시그니처로 기대되는 행동을 명시하지만 구현 세부는 제공하지 않는다.
- Java에서 인터페이스도 서브타이핑에 쓰인다. dog 클래스가 IAnimal 인터페이스를 구현(implements)하면, dog 객체는 개처럼 행동할 뿐 아니라 인터페이스에 나열된 메서드 시그니처의 본문을 모두 제공함으로써 동물처럼 행동할 것이 기대된다. 상속과 마찬가지로 개는 동물이다.
- 차이점: dog 클래스가 동물이 된다는 것의 구현 세부를 직접 제공해야 한다. 인터페이스는 구현 클래스가 이행해야 할 **계약(contract)** 과 같다.
- 상속과 인터페이스 모두 dog 타입과 animal 타입 사이의 일관성을 달성하므로, 프로그램에서 animal 타입을 다루는 어느 곳에서든 dog 객체를 사용할 수 있다.
- 상속과 달리 인터페이스는 클래스 집합의 일반화가 아니다. **인터페이스는 클래스가 아니다.** 행동을 기술하는 데 쓰이며, 담고 있는 것은 메서드 시그니처뿐이다.

### Java에서 인터페이스 작성과 구현

- Java에서 인터페이스를 만들 때는 `interface` 키워드를 쓴다. 표준 Java 명명 관례는 이름 앞에 문자 I를 붙여 인터페이스임을 나타낸다.
- 예시 인터페이스는 동물의 세 가지 행동 — 움직이기(move), 말하기(speak), 먹기(eat) — 을 기술한다. 이 행동들이 어떻게 수행되는지는 절대 구현하거나 기술하지 않고, 동물이 이런 행동을 가진다는 것만 보인다.
- 인터페이스는 동물의 속성(attributes)을 캡슐화하지 않는다. 속성은 행동이 아니기 때문이다.
- 인터페이스를 쓰려면 계약을 이행하겠다고 선언해야 한다. Java 키워드는 `implements` 다. dog 클래스가 인터페이스의 행동을 구현하겠다고 선언하면, 인터페이스의 모든 메서드 시그니처를 클래스 안에 명시적으로 선언하고 구현해야 한다 — move, speak, eat 메서드를 모두 가져야 한다.

### UML에서 인터페이스 표기

- 인터페이스는 UML에서 클래스와 비슷하게 그려진다. 인터페이스임은 **기예메(guillemets, 프랑스식 따옴표 « »)** 로 interface라는 단어를 감싸 명시한다.
- 인터페이스와 그것을 구현하는 클래스의 상호작용은 **점선 화살표(dotted arrow)** 로 나타낸다. 클래스가 화살표 꼬리, 인터페이스가 화살표 머리에 닿는다.
- 표준 그리기 방식은 화살표가 위를 향하게 하는 것 — 인터페이스는 항상 위쪽, 구현 클래스는 아래쪽이다.
- Java 코드를 UML로 옮기면, Dog 클래스가 IAnimal 인터페이스에 기술된 행동을 어떻게 구현할지 결정한다는 것을 메서드 시그니처를 반복해 보여 준다.

### 인터페이스의 장점 1 — 다형성(polymorphism)

- 인스턴스화할 수 없는 클래스인 추상 클래스(abstract class)처럼, 인터페이스는 다형성을 구현하는 수단이다.
- 객체 지향 언어에서 다형성은 두 클래스가 같은 행동의 기술(description)을 갖지만 그 행동의 구현은 다를 수 있는 것이다.
- 예: 고양이와 개가 말하는 방식 — 고양이는 야옹(meow), 개는 멍멍(bark). 행동의 기술은 같지만(둘 다 말할 수 있음) 실제 구현은 다르다. 이것이 다형성이다.
- Java에서는 인터페이스로 간단히 달성한다. Cat과 Dog 클래스가 모두 IAnimal 인터페이스를 구현하되 각자 자신만의 speak 행동 버전을 가진다. Doug에게 말하라고 하면 짖을 줄 알지만 Mittens처럼 야옹할 줄은 모른다.

### 인터페이스 상속

- 클래스 상속처럼 인터페이스도 다른 인터페이스를 상속할 수 있다. 그리고 클래스 상속처럼 남용해서는 안 된다 — 단순히 더 큰 인터페이스를 만들려고 인터페이스를 확장하면 안 된다.
- 인터페이스 A는 그 행동들이 인터페이스 B의 완전한 대체(substitution)로 쓰일 수 있을 때만 B를 상속해야 한다.
- 예: 차량의 이동을 x축·y축으로만 제한해 단순화한 IVehicleMovement 인터페이스는 육상·수상 차량의 행동을 기술할 수 있다. 그런데 z축으로도 움직이는 비행기나 잠수함의 이동을 구현해야 한다면? 육상·수상 차량은 z축으로 움직이지 않으므로 기존 인터페이스에 행동을 추가하고 싶지 않다.
- 해법: 첫 번째 인터페이스를 상속하는 두 번째 인터페이스를 만든다. 이제 육상·수상 차량용 인터페이스에 z축 이동을 추가하지 않고도, 3차원 이동을 하는 모든 차량에 IVehicleMovement3D 인터페이스를 쓸 수 있다.

### 인터페이스의 장점 2 — 다중 상속 문제 회피

- 아직 보지 않은 상속 형태로 **다중 상속(multiple inheritance)** 이 있다 — 서브클래스가 둘 이상의 슈퍼클래스를 갖는 것. C++ 같은 다른 객체 지향 언어에서는 가능하지만 Java는 지원하지 않는다.
- 이유는 **데이터 모호성(Data Ambiguity)** 이다. 같은 이름의 속성이나 같은 메서드 시그니처의 행동을 가진 둘 이상의 슈퍼클래스에서 상속받으면, 어느 것을 참조하는지 구분할 수 없다. Java는 이를 판별할 수 없으므로 다중 상속을 허용하지 않는다.
- 인터페이스는 이 문제가 없다. Java에서 클래스는 원하는 만큼 많은 인터페이스를 구현할 수 있다. 인터페이스는 계약일 뿐이고 계약을 완수하는 특정 방식을 강제하지 않으므로, 겹치는 메서드 시그니처가 문제 되지 않는다.
- 겹치는 계약을 가진 여러 인터페이스에 대한 단일 구현이 허용된다. 예: Person 클래스는 speak 메서드의 정의를 하나만 가지며, 그것이 두 인터페이스 모두에 대한 같은 구현이다. 모호성이 없다. 이것이 다중 상속 문제에 대한 Java의 접근이다.

### 인터페이스 사용 시 유의점

- 인터페이스는 행동의 집합을 기술하게 해 주는 강력한 도구다. 클래스는 한 번에 하나 이상의 인터페이스를 구현할 수 있어 여러 타입을 가질 수 있다.
- 인터페이스는 구현 없이 행동을 기술할 수 있게 하여 이 추상화들을 재사용할 수 있게 한다. 재사용 가능하고 유연한 코드를 만드는 데 도움이 된다.
- 다만 모든 행동 계약을 인터페이스로 일반화해서는 안 된다. 인터페이스는 특정한 필요 — 관련 클래스들이 일관되게 작동할 방법을 제공하는 것 — 를 채우기 위한 것이다.

## 예시

IAnimal 인터페이스와 이를 구현하는 Dog·Cat — 다형성 예:

```java
public interface IAnimal {
    void move();
    void speak();
    void eat();
}

public class Dog implements IAnimal {
    public void move() {
        System.out.println("Running on four legs.");
    }

    public void speak() {
        System.out.println("Bark!");
    }

    public void eat() {
        System.out.println("Eating dog food.");
    }
}

public class Cat implements IAnimal {
    public void move() {
        System.out.println("Prowling on four legs.");
    }

    public void speak() {
        System.out.println("Meow!");
    }

    public void eat() {
        System.out.println("Eating cat food.");
    }
}
```

UML 인터페이스 표기(텍스트 표현) — 점선 화살표는 구현 클래스에서 인터페이스로 위를 향한다:

```text
        +-----------------------+
        | «interface»           |
        | IAnimal               |
        +-----------------------+
        | +move()               |
        | +speak()              |
        | +eat()                |
        +-----------------------+
              ^ (점선 화살표)
              ¦
        +-----------------------+
        | Dog                   |
        +-----------------------+
        | +move()               |
        | +speak()              |
        | +eat()                |
        +-----------------------+
```

인터페이스 상속 — 2차원 이동 인터페이스를 3차원 이동 인터페이스가 상속:

```java
public interface IVehicleMovement {
    void moveOnXAxis();
    void moveOnYAxis();
}

public interface IVehicleMovement3D extends IVehicleMovement {
    void moveOnZAxis();
}
```

## 요약

- 인터페이스는 메서드 시그니처만 담는 타입이며, 생성자·속성·메서드 본문이 없는 계약(contract)이다. 관례상 이름 앞에 I를 붙인다.
- 상속(extends)은 구현 세부까지 물려주지만, 인터페이스(implements)는 구현 클래스가 모든 메서드 본문을 직접 제공해야 한다.
- UML에서 인터페이스는 «interface» 기예메로 표시하고, 구현 관계는 점선 화살표(클래스 → 인터페이스, 위 방향)로 그린다.
- 인터페이스는 다형성을 구현한다 — 같은 행동 기술, 다른 구현(고양이는 야옹, 개는 멍멍).
- 인터페이스 상속은 A가 B의 완전한 대체가 될 때만 사용한다(2D/3D 차량 이동 예시).
- Java는 데이터 모호성 때문에 다중 상속을 금지하지만, 클래스는 여러 인터페이스를 구현할 수 있다.
