# Lecture 8 -  Long Preamble Synchronization

> MOOC video · [원본 학습 항목](https://www.mooc.org/learn/iot-communications/lecture/EhxP4/lecture-8-long-preamble-synchronization)

## 개요
- 다른 노드가 깨어 있어서 우리가 이런 쓰기 요청을 계속 보내는 것은 불필요해 보였기 때문에 그렇게 하는 것은 정말 낭비인 것 같았습니다.

## 내용
- 다른 노드가 깨어 있어서 우리가 이런 쓰기 요청을 계속 보내는 것은 불필요해 보였기 때문에 그렇게 하는 것은 정말 낭비인 것 같았습니다.
- A는 다른 노드가 데이터를 전송할 경우에 대비하여 전체 웨이크 타임 동안 깨어 있어야 하지만, 그러다 보면 절전 모드로 전환될 수도 있습니다.
- 매우 안정적으로 유지해야 하는 환경에 배포하고, 매우 엄격하게 구현해야 하는 의료 애플리케이션을 배포하는 경우 프로세스를 점검하는 공식적인 방법을 사용하십시오.프로토콜을 단순하게 유지하려는 경우가 있습니다.
- 그래서 이 프로토콜이 하는 일은 메시지를 주고받는 과정을 추적하는 약간의 추가 단계를 수행하는 것입니다.노드가 다른 노드와 통신할 때를 기억하는 것과 비슷합니다.
- 따라서 노드가 쓰기 승인을 받으면 시간을 기록하고 이를 바탕으로 다른 노드의 일정을 추정할 수 있다는 것이 핵심입니다.
- 그래서 A가 이제 깨어 있을 거고, 이제 깨어 있을 거고, 여기에 T 서브 WI까지 더해서 A가 깨어나는 빈도라는 걸 알 수 있죠.
- 그래서 노드 A가 깨어 있지 않다는 건 알지만, 마지막 쓰기 동작 이후 얼마나 오래 잠을 잤는지 알기 때문에 언제 깨어날지는 압니다.

## 예시
- 예를 들어 어떤 방식으로든 통신을 많이 하게 되는 기지국이라면 이 방식은 훌륭하게 작동합니다.

## 요약
- 그래서 A가 이제 깨어 있을 거고, 이제 깨어 있을 거고, 여기에 T 서브 WI까지 더해서 A가 깨어나는 빈도라는 걸 알 수 있죠. 그래서 노드 A가 깨어 있지 않다는 건 알지만, 마지막 쓰기 동작 이후 얼마나 오래 잠을 잤는지 알기 때문에 언제 깨어날지는 압니다.
