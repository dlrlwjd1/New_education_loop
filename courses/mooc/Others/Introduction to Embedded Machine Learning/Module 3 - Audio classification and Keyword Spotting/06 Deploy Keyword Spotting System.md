# Deploy Keyword Spotting System

## 개요

학습된 키워드 스팟팅 모델을 스마트폰과 Arduino Nano 33 BLE Sense에 실제로 배포한다. 특히 **연속(continuous) 리스닝**을 실시간으로 구현하기 위한 **롤링(슬라이딩) MFCC 버퍼**와 **더블 버퍼링** 구조가 핵심이다.

## 내용

### 스마트폰에서 먼저 확인

- Devices 페이지 → Connect a new device → QR 코드로 폰 연결 → **switch to classification mode** → 브라우저가 프로젝트를 자동으로 빌드·다운로드해 마이크 권한을 요청하고 바로 추론을 시작한다.
- 키워드("Hello", "Stop")를 말하면 해당 라벨의 확신도가 0.5를 넘는지, 다른 말은 `unknown`으로, 무음은 `noise`로 분류되는지 확인.

### Arduino 배포 — Analyze로 예산 확인

- Deployment 페이지 → Arduino library 선택 → **Analyze**: Arm 프로세서(80MHz) 기준 추론 시간 약 **4ms** — 매우 빠름.
- 그러나 MFCC 페이지로 돌아가면, **1초 오디오의 특징 추출(MFCC 계산) 자체가 약 212ms** 걸린다는 것을 알 수 있다. **즉 특징 추출이 추론 자체보다 훨씬 더 무겁다** — 임베디드 오디오 ML에서 자주 간과되는 지점.
- 이 부담을 줄이기 위해, 겹치는 구간의 MFCC를 매번 다시 계산하지 않는 **몇 가지 실전 트릭**을 이어서 다룬다.

### Arduino IDE 설치 (기존과 동일한 절차)

Build → zip 다운로드 → Sketch → Include Library → Add .ZIP Library → File → Examples에서 프로젝트 찾기.

### 예제 1 — 단순 마이크 예제 (비연속)

- 1초 샘플링 → 특징 계산 → 추론을 순서대로 수행하고, 다음 사이클까지 대기한다.
- 흥미로운 데모지만 **실용적이지 않다** — 원하는 건 Alexa/Siri처럼 **계속 듣고 있는** 시스템.

### 예제 2 — 연속(continuous) 마이크 예제 (실전 구조)

가속도계의 연속 예제와 구조는 비슷하지만, 오디오는 **16kHz라는 훨씬 높은 샘플링 레이트** 때문에 더 정교한 처리가 필요하다.

- **PDM(Pulse Density Modulation) 컨트롤러**: Nano BLE Sense 보드가 하드웨어로 오디오 샘플링을 처리해준다. Arduino `PDM` 라이브러리로 이를 설정.
- **더블 버퍼(double buffer)**: 한 버퍼가 채워지는 동안 다른 버퍼가 추론에 쓰이도록 만들어, 샘플링과 추론이 서로 방해하지 않게 한다.
- 한 번에 **5,333개 샘플**(16,000의 1/3 = 약 1/3초 분량)만 모은다.
- **1/3초마다** 그 구간의 MFCC를 계산해 **전체 1초 분량의 MFCC를 담는 더 큰 버퍼**에 추가한다.
- 1/3초마다: **가장 오래된 1/3초 분량의 MFCC를 버리고, 새로 계산한 1/3초 분량을 앞(또는 끝)에 추가**하는 방식으로 **MFCC 버퍼 자체를 슬라이딩 윈도우처럼 굴린다.** 매번 1초 전체를 처음부터 다시 계산하지 않는다는 것이 핵심 최적화.
- 매번 이렇게 갱신된 1초 분량의 MFCC 전체를 모델에 넣어 추론 → 확률 중 최댓값으로 클래스 판정.
- 예: 단어의 앞부분만 들렸을 땐 아직 `unknown`으로 나오다가, 단어가 다 들리고 MFCC 버퍼가 그 전체를 담게 되면 → `Hello`로 정확히 판정.
- 이 과정이 **무한히 반복**되며, 조건은 단 하나 — **오디오 버퍼가 다 차기 전에 MFCC 계산+추론을 끝내야 한다.**

### 타이밍 예산 — 버퍼 오버런 주의

- `loop()`의 `microphone_inference_record()` 함수는 오디오 버퍼가 다 찰 때까지 대기한다. **이미 버퍼가 차 있는 상태로 이 함수에 도달했다면, 다른 코드가 너무 오래 걸려 샘플을 놓쳤다는 뜻** — 이때 콘솔에 **buffer overrun** 메시지가 출력된다.
- 실측: **특징 추출 약 124ms + 추론 약 11ms ≈ 135ms**를 **333ms(1/3초)마다** 소비 — 즉 여유 시간이 그리 많지 않다. 자신의 애플리케이션 코드를 추가할 때 이 예산을 넘기지 않도록 주의해야 한다.

### 특정 키워드에 반응하는 코드 작성

- 라벨이 출력되는 순서 = 시스템에 저장된 순서. 예: 인덱스 2가 `Hello`라면, 그 확률이 **60% 임계값**을 넘을 때만 원하는 동작(예: 시리얼 모니터에 "Hello World" 출력)을 실행하도록 코드를 짤 수 있다.
- 이 확인 로직은 `run_classifier_continuous()` 호출 직후에 넣어, **매 1/3초마다 확실하게 체크**되도록 한다.
- 참고: 통계 출력은 1초에 한 번만 이뤄지므로 3번의 추론 결과 중 2번은 로그에 안 찍힌다는 점도 언급 — 로그와 실제 추론 빈도를 혼동하지 않도록.

## 예시

"Hello"라고 말하면, 1/3초 단위로 갱신되는 MFCC 슬라이딩 윈도우가 결국 그 단어 전체를 담는 순간이 오고, 그 시점의 추론에서 `Hello`의 확률이 60%를 넘으면 시리얼 모니터에 "Hello World"가 출력된다 — 이것이 이 코스가 완성하는 미니 Alexa다.

## 요약

- **특징 추출(MFCC)이 추론보다 더 무거울 수 있다**는 것을 Analyze 단계에서 먼저 확인하는 습관이 중요하다.
- 실전 연속 리스닝은 **더블 버퍼링(샘플링)** + **슬라이딩 MFCC 버퍼(오래된 1/3초를 버리고 새 1/3초를 추가)** 조합으로 구현한다 — 매번 1초 전체를 재계산하지 않는 것이 성능의 핵심.
- 애플리케이션 코드가 특징 추출+추론에 걸리는 시간(예: 135ms)보다 주기(333ms)를 넘기지 않도록 **타이밍 예산을 항상 의식**해야 하며, 넘기면 buffer overrun이 발생한다.
- 특정 키워드 인덱스와 확률 임계값을 비교하는 몇 줄만 추가하면, 이 파이프라인을 실제 트리거 로직(예: "Hello"를 들으면 LED 켜기)으로 바로 확장할 수 있다.
