# Case Study - User Research in the Real World — 대화정리

## 개요
- Meta에서 사용자 조사를 제품 전 과정에 적용하는 방식과 가치를 살펴본다.
- 11~12강에서 배운 사용자 조사·페르소나·공감 지도가 실제 회사에서 어떻게 쓰이는지 보여주는 사례 연구.

## 내용

### 조사 방법과 시점
- A/B 테스트, 설문, 사용 관찰, 페르소나로 **정량·정성** 피드백을 모두 수집한다.
- **아이디어 단계부터 MVP 제작, 출시 후까지** 일찍, 자주 조사한다.

### 직군 간 역할
- 사용자 연구자는 질문과 실험을 수행하고, **디자이너와 PM**은 결과를 제품 변경으로 연결한다.
- **엔지니어도** 예상과 다른 결과를 받아들이고 방향을 수정해야 한다.

### 편향 없는 질문
- 원하는 답을 유도하지 않는 질문으로 솔직한 반응을 얻어야 한다.
- 이는 사용자가 이해하지 못하거나 쓰지 않는 제품을 만드는 위험을 줄인다.

### 사례 분석 — 대화에서 정리
- Meta의 그룹(Groups) 기능은 **MVP 테스트** 후, 사용자가 이름과 개념을 이해하지 못한다는 결과를 받아 기능 방향과 제품 이름까지 변경했다.
- 이 사례는 "편향 없는 질문"보다 "**일찍, 자주 조사한다**" 원칙을 더 잘 보여준다 — MVP 단계(완성 전)에서 테스트했기 때문에, 이름·방향을 바꾸는 비용이 출시 후보다 훨씬 쌌다. 조사가 늦었다면 되돌리는 비용이 훨씬 컸을 것이다.
- "직군 간 역할" 섹션의 "엔지니어도 예상과 다른 결과를 받아들이고 방향을 수정해야 한다"와도 맞닿아 있다 — "사용자가 개념을 이해 못한다"는 기대치 않은 결과를 팀이 실제로 수용하고 변경했다.
- "편향 없는 질문" 원칙 자체는 이 사례의 실제 질문지 내용이 나오지 않아 판단하기 어렵다.

## 예시
Meta의 그룹 기능은 MVP 테스트 후 사용자가 이름과 개념을 이해하지 못한다는 결과를 받아 기능 방향과 제품 이름까지 변경했다.

## 요약
- 사용자 조사는 제품 전 생애주기에서 반복하며, 결과는 기존 가정을 뒤집고 제품 방향을 바꿀 수 있다.
- 편향 없는 질문과 조기 조사가 큰 재작업을 줄인다.
- Meta 그룹 기능 사례는 "조기 조사 → 저비용 방향 전환"과 "예상 밖 결과 수용"을 동시에 보여준다.
