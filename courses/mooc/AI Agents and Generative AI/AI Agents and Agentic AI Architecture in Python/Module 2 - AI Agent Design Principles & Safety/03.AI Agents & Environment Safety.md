# AI 에이전트와 환경 안전성

에이전트가 현실 세계에서 행동을 취할 때는 강력한 안전 메커니즘이 필요하다. 캘린더 일정 조율 예시를 통해 안전한 액션 시스템을 구축하는 패턴을 살펴보자.

---

## 패턴 1: 되돌릴 수 있는 액션 (Reversible Actions)

에이전트가 현실 세계와 상호작용할 때 실수는 발생할 수 있다. 에이전트가 보유한 정보를 바탕으로 올바른 결정을 내렸더라도, 외부 상황이 변해 이미 취한 행동이 바람직하지 않게 될 수 있다. 되돌릴 수 있는 액션은 문제가 발생했을 때 작업을 "취소"할 수 있는 안전망을 제공한다.

액션을 되돌릴 수 있게 만드는 핵심은, 실행 중에 나중에 완전히 되돌릴 수 있을 만큼 충분한 정보를 캡처하는 것이다. 이것이 항상 간단하지는 않다. 예를 들어 캘린더 이벤트 삭제는 이벤트 세부 정보를 저장해두면 되돌리기 쉽지만, 이미 읽힌 이메일을 취소하려면 시스템에서 "취소"가 무엇을 의미하는지 신중하게 생각해야 한다. 때로는 후속 수정 메시지를 보내는 것이 최선일 수도 있다.

액션을 취소할 수 있도록 구조화하는 방법을 살펴보자.

```python
class ReversibleAction:
    def __init__(self, execute_func, reverse_func):
        self.execute = execute_func
        self.reverse = reverse_func
        self.execution_record = None

    def run(self, **args):
        """액션을 실행하고 되돌리는 방법을 기록한다."""
        result = self.execute(**args)
        self.execution_record = {
            "args": args,
            "result": result,
            "timestamp": datetime.now().isoformat()
        }
        return result

    def undo(self):
        """기록된 정보를 사용해 액션을 되돌린다."""
        if not self.execution_record:
            raise ValueError("되돌릴 액션이 없습니다")
        return self.reverse(**self.execution_record)

# 되돌릴 수 있는 액션 사용 예시
create_event = ReversibleAction(
    execute_func=calendar.create_event,
    reverse_func=lambda **record: calendar.delete_event(record["result"]["event_id"])
)

send_invite = ReversibleAction(
    execute_func=calendar.send_invite,
    reverse_func=lambda **record: calendar.cancel_invite(record["result"]["invite_id"])
)
```

에이전트의 액션 로그를 기록해두면 필요할 때 되돌릴 수 있다. 에이전트 자체에도 가장 최근 액션을 취소하거나 특정 상황에서 모든 액션을 되돌리는 "revert" 툴을 제공할 수 있다.

## 패턴 2: 트랜잭션 관리 (Transaction Management)

개별적인 되돌릴 수 있는 액션도 유용하지만, 실제 작업은 여러 조율된 액션을 필요로 할 때가 많다. 예를 들어 회의를 일정으로 잡으려면 가용 시간 확인, 캘린더 이벤트 생성, 알림 발송이 함께 이루어져야 한다. 트랜잭션 관리를 통해 이 관련 액션들을 하나의 단위로 처리할 수 있다. 즉, 완전히 성공하거나 완전히 실패하게 만든다.

트랜잭션 패턴은 되돌릴 수 있는 액션과 결합할 때 특히 강력해진다. 다단계 프로세스에서 어느 단계라도 실패하면, 이전 단계를 자동으로 롤백할 수 있다. 이를 통해 캘린더 이벤트는 생성됐지만 알림이 발송되지 않은 상황, 혹은 알림은 발송됐지만 이벤트가 생성되지 않은 상황 같은 불일치 상태를 방지한다. 마치 전체 작업 시퀀스에 대한 "실행 취소" 버튼을 갖는 것과 같다.

아래는 에이전트 루프 중 실행되는 액션들을 수집했다가 루프 종료 시 전부 커밋하거나 롤백하는 간단한 트랜잭션 관리 시스템이다.

```python
class ActionTransaction:
    def __init__(self):
        self.actions = []
        self.executed = []
        self.committed = False
        self.transaction_id = str(uuid.uuid4())

    def add(self, action: ReversibleAction, **args):
        """액션을 실행 대기열에 추가한다."""
        if self.committed:
            raise ValueError("트랜잭션이 이미 커밋되었습니다")
        self.actions.append((action, args))

    async def execute(self):
        """트랜잭션의 모든 액션을 실행한다."""
        try:
            for action, args in self.actions:
                result = action.run(**args)
                self.executed.append(action)
        except Exception as e:
            # 액션이 실패하면 지금까지 실행된 모든 것을 되돌린다
            await self.rollback()
            raise e

    async def rollback(self):
        """실행된 모든 액션을 역순으로 되돌린다."""
        for action in reversed(self.executed):
            await action.undo()
        self.executed = []

    def commit(self):
        """트랜잭션을 커밋 완료로 표시한다."""
        self.committed = True
```

## 패턴 3: 단계적 실행과 검토 (Staged Execution with Review)

자동 롤백보다 더 많은 제어가 필요할 때도 있다. 단계적 실행을 통해 일련의 액션을 미리 계획하고, 안전성과 정확성을 검토한 후 실행하게 할 수 있다. 일부 액션이 다른 액션보다 되돌리기 어렵거나, 실행 전에 사람 또는 더 유능한 AI 시스템이 계획을 검토하길 원할 때 특히 유용하다.

검토 단계에서는 개별 액션을 볼 때 명확하지 않던 문제를 발견할 수 있다. 예를 들어 대규모 회의를 설정하는 각 단계가 개별적으로는 유효하더라도, 검토자가 전체 액션의 조합이 팀의 일정을 압도하거나 회의 규모에 관한 사내 정책을 위반한다는 것을 알아차릴 수 있다. 이 패턴은 최적화도 가능하게 한다. 검토자가 동일한 목표를 달성하는 더 효율적인 방법을 발견할 수도 있다.

실행 전에 변경 사항을 검토를 위해 단계적으로 처리하는 시스템을 만들어보자.

```python
class StagedActionEnvironment(Environment):
    def __init__(self):
        self.staged_transactions = {}
        self.llm = None  # 검토용 고성능 LLM

    def stage_actions(self, task_id: str) -> ActionTransaction:
        """액션 스테이징을 위한 새 트랜잭션을 생성한다."""
        transaction = ActionTransaction()
        self.staged_transactions[task_id] = transaction
        return transaction

    def review_transaction(self, task_id: str) -> bool:
        """LLM이 스테이징된 액션의 안전성을 검토한다."""
        transaction = self.staged_transactions.get(task_id)
        if not transaction:
            raise ValueError(f"태스크 {task_id}에 대한 트랜잭션을 찾을 수 없습니다")

        # 스테이징된 액션 설명 생성
        staged_actions = [
            f"액션: {action.__class__.__name__}\n인수: {args}"
            for action, args in transaction.actions
        ]
        
        # 가장 안전한 방법은 사람이 직접 검토하는 것이지만,
        # 더 유능한 AI 시스템이 먼저 검토하여 사람의 검토 횟수를 최소화할 수도 있다.
        # 더 유능한 AI가 잠재적으로 문제 있는 액션을 더 일찍 검토하고 거부할 수 있다.
        
        review_prompt = f"""다음 스테이징된 액션들의 안전성을 검토하세요:
        
        태스크 ID: {task_id}
        
        스테이징된 액션:
        {staged_actions}
        
        고려 사항:
        1. 모든 액션이 해당 태스크에 필요한가?
        2. 의도치 않은 결과를 초래할 수 있는 액션이 있는가?
        3. 액션들의 순서가 안전한가?
        4. 동일한 목표를 달성하는 더 안전한 방법이 있는가?
        
        이 액션들을 승인해야 하는가?
        """
        
        response = self.llm.generate(review_prompt)
        
        # 승인되면 사람에게 알리고
        # 진행 여부를 묻는다
        return "approved" in response.lower()

# 사용 예시:
async def schedule_team_meeting(env: StagedActionEnvironment, 
                              attendees: List[str],
                              duration: int):
    """안전 점검을 포함한 팀 회의 일정 조율."""
    task_id = str(uuid.uuid4())
    transaction = env.stage_actions(task_id)
    
    # 가용 시간 확인 (즉시 실행)
    available_slots = calendar.check_availability(attendees, duration)
    if not available_slots:
        return {"error": "가용 시간대가 없습니다"}
    
    best_slot = available_slots[0]
    
    # 이벤트 생성 스테이징
    transaction.add(create_event, 
                   title="팀 회의",
                   time=best_slot,
                   duration=duration)
    
    # 이메일 초안 작성 (즉시 실행)
    email_draft = email.draft_message(
        to=attendees,
        subject="팀 회의",
        body=f"팀 회의가 {best_slot}으로 예약되었습니다"
    )
    
    # 이메일 발송 스테이징
    transaction.add(send_email, 
                   draft_id=email_draft.id)
    
    # 스테이징된 액션 검토...사람 검토로 전송하거나
    # 초기 필터링을 위해 더 유능한 AI에게 전송
    if env.review_transaction(task_id):
        await transaction.execute()
        transaction.commit()
        return {"status": "예약 완료"}
    else:
        return {"status": "거부됨"}
```

## 패턴 4: 단일 안전 툴 vs 다수의 위험한 툴

얼핏 보면 작고 집중된 여러 툴을 갖는 것이 좋은 설계처럼 보인다. 유닉스 철학인 "한 가지를 잘 하라"를 따르는 것이다. 그러나 에이전트 안전성 측면에서 이 접근 방식은 역효과를 낼 수 있다. 작고 집중된 툴은 종종 안전한 결정을 내리기 위한 컨텍스트가 부족하며, 올바른 오케스트레이션에 대한 부담을 에이전트에 전가한다.

반면 단일 포괄적 툴은 작업의 메커니즘뿐만 아니라 올바른 실행을 위한 비즈니스 규칙과 안전 제약도 캡슐화할 수 있다. 에이전트가 회의를 예약하기 전 가용 시간을 확인하고, 초대장을 보내기 전 참석자를 검증하고, 시간대 변환을 올바르게 처리하기를 바라는 대신, 이 모든 안전 점검을 단일 툴에 내장할 수 있다. 이렇게 하면 에이전트가 예상치 못한 방식으로 툴을 사용하려 해도 문제 상황을 만들기가 훨씬 어려워진다.

두 가지 회의 예약 접근 방식을 비교해보자.

```python
# 접근법 1: 느슨하게 제약된 다수의 툴
@register_tool(description="캘린더 이벤트 생성")
def create_calendar_event(action_context: ActionContext,
                         title: str,
                         time: str,
                         attendees: List[str]) -> dict:
    """캘린더 이벤트를 생성한다."""
    return calendar.create_event(title=title,
                               time=time,
                               attendees=attendees)

@register_tool(description="참석자에게 이메일 발송")
def send_email(action_context: ActionContext,
               to: List[str],
               subject: str,
               body: str) -> dict:
    """이메일을 발송한다."""
    return email.send(to=to, subject=subject, body=body)

@register_tool(description="캘린더 이벤트 업데이트")
def update_event(action_context: ActionContext,
                 event_id: str,
                 updates: dict) -> dict:
    """캘린더 이벤트의 모든 속성을 업데이트한다."""
    return calendar.update_event(event_id, updates)

# 접근법 2: 단일 포괄적 안전 툴
@register_tool(description="팀 회의를 안전하게 예약한다")
def schedule_team_meeting(action_context: ActionContext,
                         title: str,
                         description: str,
                         attendees: List[str],
                         duration_minutes: int,
                         timeframe: str = "next_week") -> dict:
    """
    필요한 모든 조율을 포함하여 팀 회의를 안전하게 예약한다.
    
    이 툴은:
    1. 모든 참석자의 유효성을 검증한다
    2. 캘린더 가용 시간을 확인한다
    3. 최적의 가용 시간에 이벤트를 생성한다
    4. 적절한 알림을 발송한다
    5. 모든 오류 케이스를 처리한다
    """
    # 입력 유효성 검사
    if not 15 <= duration_minutes <= 120:
        raise ValueError("회의 시간은 15분에서 120분 사이여야 합니다")
    
    if len(attendees) > 10:
        raise ValueError("10명을 초과하는 회의는 예약할 수 없습니다")
        
    # 참석자 검증
    valid_attendees = validate_attendees(attendees)
    if len(valid_attendees) != len(attendees):
        raise ValueError("일부 참석자가 유효하지 않습니다")
        
    # 가용 시간 찾기
    available_slots = find_available_times(
        attendees=valid_attendees,
        duration=duration_minutes,
        timeframe=timeframe
    )
    
    if not available_slots:
        return {
            "status": "no_availability",
            "message": "적합한 시간대를 찾을 수 없습니다"
        }
    
    # 최적 시간에 이벤트 생성
    event = calendar.create_event(
        title=title,
        description=description,
        time=available_slots[0],
        duration=duration_minutes,
        attendees=valid_attendees
    )
    
    # 알림 발송
    notifications.send_meeting_scheduled(
        event_id=event.id,
        attendees=valid_attendees
    )
    
    return {
        "status": "scheduled",
        "event_id": event.id,
        "scheduled_time": available_slots[0]
    }
```

단일 포괄적 툴이 더 안전한 이유:

- 작업 순서를 강제한다
- 모든 필요한 유효성 검사를 포함한다
- 오류 케이스를 일관되게 처리한다
- 개별 작업의 오용을 방지한다

다수의 툴 접근법에서는 에이전트가 다음과 같은 실수를 할 수 있다:

- 가용 시간 확인 없이 이벤트 생성
- 이벤트 생성 없이 이메일 발송
- 참석자 알림 없이 이벤트 업데이트
- 합리적인 규모 제한 초과

단일 툴은 "안전한" 회의 예약 작업이 무엇인지에 대한 비즈니스 로직을 캡슐화하여, 에이전트가 문제 상황을 만들기 훨씬 어렵게 만든다.
