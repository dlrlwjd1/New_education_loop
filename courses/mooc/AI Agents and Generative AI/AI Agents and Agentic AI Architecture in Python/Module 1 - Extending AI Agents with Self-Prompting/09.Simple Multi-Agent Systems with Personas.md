# 페르소나를 활용한 간단한 멀티 에이전트 시스템

## 핵심 아이디어

페르소나로 할 수 있는 강력한 일 중 하나는 **멀티 에이전트 시스템과 유사한 구조를 만드는 것**이다. 페르소나 프롬프트를 기반으로 도구(tool)를 만들면, 완전한 멀티 에이전트 시스템에 아주 가까운 동작을 구현할 수 있다.

> 엄밀히 말하면 아직 완전한 멀티 에이전트 시스템은 아니지만, 매우 유사하며 많은 경우 충분히 효과적이다.

---

## 구체적 예시: 문서화 에이전트 + 문서화 전문가

### 전체 흐름

```
[에이전트 1: 코드 문서화 에이전트]
    │
    ├── 프로젝트 디렉토리 확인
    ├── 파일 목록 조회
    ├── 파일 내용 읽기
    │
    └── "문서화 전문가에게 README 작성 요청" 도구 호출
                │
         [에이전트 2: 문서화 전문가 (페르소나 기반)]
                │
                └── 친절하고 상세한 README 생성
                        │
    [에이전트 1에게 결과 반환]
                        │
                └── write_file 도구 호출로 파일 저장
```

---

### 에이전트 1: 코드 문서화 에이전트

일반적인 코드 문서화 에이전트다. 프로젝트 디렉토리를 탐색하고, 파일을 읽은 뒤, 다음 도구를 호출한다:

```
ask_documentation_expert_to_write_readme_with_file_content
```

이 도구가 바로 **두 번째 에이전트(페르소나 기반)를 감싸는 래퍼**다.

---

### 에이전트 2: 문서화 전문가 (페르소나 프롬프트)

```
당신은 문서화 전문가입니다.
프로젝트를 위한 매우 상세하고 친절한 README를 작성합니다.
모든 README에는 소개, 설치, 튜토리얼, 결론 섹션이 포함됩니다.
문서화할 파일: print_hello_world.py
```

이 프롬프트를 받은 LLM은 필요한 모든 섹션이 포함된 친절한 README를 생성한다.

---

### 결과

에이전트 2가 생성한 README를 에이전트 1이 받아 `write_file` 도구로 파일에 저장한다. **두 에이전트가 협력해 하나의 문제를 해결**한 것이다.

---

## 왜 에이전트를 분리하는가?

### 추상화 경계(Abstraction Boundary)

페르소나는 **그 자체로 하나의 추상화 단위**다. 페르소나가 바뀌면 그에 따른 지식, 말투, 출력 방식이 모두 달라진다. 서로 다른 페르소나를 하나의 에이전트에 뒤섞으면 문제가 생긴다.

**나쁜 예:**
```
언어치료사 + 문서화 전문가를 하나의 에이전트에 혼합
→ 역할이 충돌하고 출력 품질이 저하됨
```

**좋은 예:**
```
에이전트 1: 언어치료사 페르소나 (평가 담당)
에이전트 2: 문서화 전문가 페르소나 (문서 작성 담당)
→ 각자의 역할에 집중하여 더 높은 품질의 출력 생성
```

---

## 페르소나 기반 멀티 에이전트의 장점

| 장점 | 설명 |
|------|------|
| **모듈성** | 각 페르소나/에이전트가 독립적으로 분리됨 |
| **토큰 효율성** | 각 에이전트의 프롬프트가 자신의 역할에만 집중하여 간결함 |
| **유지보수성** | 특정 에이전트의 페르소나만 수정하면 전체에 영향 없음 |
| **전문화** | 에이전트마다 특화된 도메인 지식과 출력 방식 보유 |
| **구현 단순성** | 완전한 멀티 에이전트 프레임워크 없이도 유사한 효과 구현 |

---

## 핵심 정리

- **페르소나 = 추상화 단위**: 페르소나 하나가 지식, 말투, 출력 방식을 모두 포함
- **도구로 페르소나를 감싸면** 멀티 에이전트 시스템처럼 동작
- **추상화 경계를 존중하라**: 서로 다른 페르소나는 별도 에이전트로 분리
- 결과적으로 **더 모듈화되고, 더 토큰 효율적이며, 더 유지보수하기 쉬운** 에이전트 아키텍처를 구현할 수 있다
