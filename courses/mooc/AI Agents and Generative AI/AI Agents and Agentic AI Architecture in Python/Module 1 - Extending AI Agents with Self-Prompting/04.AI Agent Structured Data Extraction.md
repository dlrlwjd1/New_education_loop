# AI 에이전트 구조화 데이터 추출

## 셀프 프롬프팅 실전 예시

매일 수십 개의 청구서를 처리하는 **미지급금(Accounts Payable) 자동화 에이전트**를 만든다고 상상해보자.

각 공급업체는 서로 다른 형식과 레이아웃의 청구서를 보낸다. PDF도 있고, 텍스트로 변환된 스캔 이미지도 있고, 이메일 본문에 직접 텍스트로 담겨 오는 것도 있다. 에이전트는 각 청구서를 이해하고, 청구서 번호·날짜·금액·항목 등 핵심 정보를 추출해 회사 회계 데이터베이스에 입력해야 한다.

자동화 없이는 누군가 매번 청구서를 읽고 수작업으로 내용을 옮겨야 하는 지루한 일이다.

### LLM이 해결하는 방법

셀프 프롬프팅을 통해 에이전트는 LLM을 **범용 파서(universal parser)** 로 활용할 수 있다. LLM은 형식에 관계없이 청구서의 자연스러운 구조를 이해하고, 사람처럼 청구서를 읽어 맥락과 일반적인 패턴을 기반으로 핵심 정보를 식별한다. 각 공급업체마다 별도 파서를 작성하거나, 특정 정보가 어디에 있는지 찾는 복잡한 규칙을 유지할 필요가 없다.

## 구현: `prompt_llm_for_json` 도구

```python
@register_tool()
def prompt_llm_for_json(action_context: ActionContext, schema: dict, prompt: str):
    """
    LLM에게 프롬프트에 응답하는 JSON을 생성하게 한다.
    구조화된 데이터가 필요할 때 항상 이 도구를 사용한다.
    
    Args:
        schema: 예상 응답 구조를 정의하는 JSON 스키마
        prompt: LLM에게 보낼 프롬프트
        
    Returns:
        제공된 스키마와 일치하는 추출 정보 딕셔너리
    """
    generate_response = action_context.get("llm")
    
    # 유효한 JSON을 얻을 때까지 최대 3회 시도
    for i in range(3):
        try:
            response = generate_response(Prompt(messages=[
                {"role": "system", 
                 "content": f"You MUST produce output that adheres to the following JSON schema:\n\n{json.dumps(schema, indent=4)}. Output your JSON in a ```json markdown block."},
                {"role": "user", "content": prompt}
            ]))

            # 마크다운 코드 블록 안의 JSON 추출
            if "```json" in response:
                start = response.find("```json")
                end = response.rfind("```")
                response = response[start+7:end].strip()

            return json.loads(response)
            
        except Exception as e:
            if i == 2:
                raise e
            print(f"Error generating response: {e}")
            print("Retrying...")
```

> `action_context` 파라미터는 LLM과 기타 유용한 정보를 담은 컨텍스트 객체다. 상세한 설계 이유는 이후 섹션에서 다룬다.

### 이 도구의 핵심 구성 요소

| 요소 | 역할 |
|------|------|
| 시스템 메시지 | LLM이 제공된 JSON 스키마를 반드시 따르도록 지시 |
| 재시도 로직 | 파싱 실패 시 최대 3회까지 재시도 |
| 마크다운 지원 | 직접 JSON 출력과 마크다운 형식 JSON 모두 처리 |
| 명시적 에러 처리 | 유효한 JSON을 얻거나 명시적으로 실패 |

## 활용 예시: 청구서 데이터 추출

```python
invoice_schema = {
    "type": "object",
    "properties": {
        "invoice_number": {"type": "string"},
        "date": {"type": "string"},
        "amount": {"type": "number"},
        "line_items": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "description": {"type": "string"},
                    "quantity": {"type": "number"},
                    "unit_price": {"type": "number"}
                }
            }
        }
    }
}

extracted_data = prompt_llm_for_json(
    action_context=context,
    schema=invoice_schema,
    prompt="Extract invoice details from this text: 'INVOICE #1234...'"
)
```

이 도구로 에이전트가 할 수 있는 일:
- 이메일에서 회의 세부 정보 추출 → 캘린더 형식으로 변환
- 비정형 보고서 데이터 → 구조화된 분석 입력값으로 변환
- 웹 페이지 콘텐츠 → 구조화된 제품/연락처 정보로 변환
- 고객 커뮤니케이션 → 실행 가능한 지원 티켓으로 처리

## 설계 결정: 범용 vs 특화 추출 도구

데이터 추출 도구를 설계할 때 중요한 아키텍처 결정이 필요하다.

### 범용 접근법 (`prompt_llm_for_json` 직접 사용)

**장점**: 최대 유연성. 다양한 문서 유형을 동적으로 처리 가능.

**단점**: 에이전트가 매번 스키마와 프롬프트를 생성해야 하므로 일관성이 떨어질 수 있다.

### 특화 도구 접근법

특정 문서 유형에 고정된 스키마를 가진 전용 도구를 만드는 방법이다.

```python
@register_tool(tags=["document_processing", "invoices"])
def extract_invoice_data(action_context: ActionContext, document_text: str) -> dict:
    """
    청구서 텍스트에서 표준화된 청구서 데이터를 추출한다.
    모든 문서에 걸쳐 일관된 스키마를 강제한다.
    """
    invoice_schema = {
        "type": "object",
        "required": ["invoice_number", "date", "amount"],  # 필수 필드
        "properties": {
            "invoice_number": {"type": "string"},
            "date": {"type": "string", "format": "date"},
            "amount": {
                "type": "object",
                "properties": {
                    "value": {"type": "number"},
                    "currency": {"type": "string"}
                },
                "required": ["value", "currency"]
            },
            "vendor": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "tax_id": {"type": "string"},
                    "address": {"type": "string"}
                },
                "required": ["name"]
            },
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                        "total": {"type": "number"}
                    },
                    "required": ["description", "total"]
                }
            }
        }
    }

    extraction_prompt = f"""
    다음 문서 텍스트에서 청구서 정보를 추출하라.
    주요 식별 항목:
    - 청구서 번호 ('Invoice #', 'Reference' 등으로 표시된 것)
    - 날짜 ('Invoice Date', 'Issue Date' 등)
    - 금액 (통화 포함 총 지불 금액)
    - 공급업체 정보 (회사명, 세금 ID, 주소)
    - 항목별 내역 (개별 청구 항목과 세부 정보)

    문서 텍스트:
    {document_text}
    """
    
    return prompt_llm_for_json(
        action_context=action_context,
        schema=invoice_schema,
        prompt=extraction_prompt
    )
```

**특화 도구의 장점**:

| 장점 | 설명 |
|------|------|
| 데이터 일관성 | 청구서 데이터가 항상 동일한 구조로 저장됨 |
| 필수 필드 강제 | 누락 시 오류 발생으로 중요 정보 보장 |
| 필드 유효성 검사 | 날짜 형식 등 스키마 수준 검증 가능 |
| 집중된 프롬프팅 | 특정 정보를 어디서 찾을지 LLM에게 상세 안내 → 추출 정확도 향상 |

## 언제 어떤 접근법을 선택할 것인가

### 특화 도구를 사용해야 할 때
- 데이터 일관성이 매우 중요할 때
- 처리할 문서 유형이 명확히 정해져 있을 때
- 특정 유효성 검사 규칙이 필요할 때
- 추출 데이터가 엄격한 요구사항을 가진 다른 시스템으로 흘러갈 때

### 범용 도구를 사용해야 할 때
- 매우 다양한 문서 유형을 처리해야 할 때
- 문서 형식과 요구사항이 자주 바뀔 때
- 프로토타입 제작이나 새 유스케이스 탐색 중일 때
- 다운스트림 시스템이 데이터 형식에 유연할 때

### 실전에서의 권장 접근법: 하이브리드

```
일반적이고 중요한 문서 유형 → 특화 도구 (일관성 보장)
엣지 케이스 / 새로운 문서 유형 → 범용 도구 (유연성 활용)
```

가장 필요한 곳에서는 신뢰성을, 그게 중요한 곳에서는 유연성을 확보하는 방식이다.
