# 인보이스 처리 에이전트

## 개요

고정 스키마 기반의 저장 메커니즘과 특화된 추출 기능을 결합한 인보이스 처리 시스템을 구축한다. LLM의 문서 이해 능력을 활용하면서도 고정된 스키마로 데이터 일관성을 보장한다.

---

## 핵심 도구 구현

### 도구 1: 인보이스 데이터 추출 (`extract_invoice_data`)

```python
@register_tool(tags=["document_processing", "invoices"])
def extract_invoice_data(action_context: ActionContext, document_text: str) -> dict:
    """
    문서 텍스트에서 표준화된 인보이스 데이터를 추출한다.

    고정 스키마와 특화된 프롬프팅을 사용해 인보이스 정보를 일관되게 추출한다.
    어떤 형식의 인보이스에서도 인보이스 번호, 날짜, 금액, 품목 등 핵심 필드를 식별한다.

    Args:
        document_text: 처리할 인보이스의 텍스트 내용

    Returns:
        표준화된 형식의 인보이스 데이터 딕셔너리
    """
    invoice_schema = {
        "type": "object",
        "required": ["invoice_number", "date", "total_amount"],
        "properties": {
            "invoice_number": {"type": "string"},
            "date": {"type": "string"},
            "total_amount": {"type": "number"},
            "vendor": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "address": {"type": "string"}
                }
            },
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                        "total": {"type": "number"}
                    }
                }
            }
        }
    }

    # 인보이스 추출에 특화된 프롬프트 생성
    extraction_prompt = f"""
            당신은 인보이스 분석 전문가입니다. 인보이스 정보를 정확하고 빠짐없이 추출하세요.
            특히 다음 항목에 주의하세요:
            - 인보이스 번호 ('Invoice #', 'No.', 'Reference' 등 다양한 표현 확인)
            - 날짜 (인보이스 발행일 또는 발급일 기준)
            - 금액 (총액을 정확하게 캡처)
            - 품목 (모든 개별 항목 캡처)
            
            단계적으로 생각한 뒤 아래 인보이스에서 데이터를 추출하세요:
            
            <invoice>
            {document_text}
            </invoice>
    """

    return prompt_llm_for_json(
        action_context=action_context,
        schema=invoice_schema,
        prompt=extraction_prompt
    )
```

### 도구 2: 인보이스 저장 (`store_invoice`)

```python
@register_tool(tags=["storage", "invoices"])
def store_invoice(action_context: ActionContext, invoice_data: dict) -> dict:
    """
    인보이스를 데이터베이스에 저장한다. 동일한 번호의 인보이스가 있으면 덮어쓴다.
    
    Args:
        invoice_data: 저장할 처리된 인보이스 데이터
        
    Returns:
        저장 결과와 인보이스 번호를 담은 딕셔너리
    """
    storage = action_context.get("invoice_storage", {})
    
    invoice_number = invoice_data.get("invoice_number")
    if not invoice_number:
        raise ValueError("인보이스 데이터에 인보이스 번호가 포함되어야 합니다")
    
    storage[invoice_number] = invoice_data
    
    return {
        "status": "success",
        "message": f"인보이스 {invoice_number} 저장 완료",
        "invoice_number": invoice_number
    }
```

---

## 두 도구의 역할

| 도구 | 역할 |
|------|------|
| `extract_invoice_data` | 원시 문서 텍스트 → 고정 스키마 구조화 데이터 (자기 프롬프팅 활용) |
| `store_invoice` | 구조화된 데이터 → 인보이스 번호 기준 딕셔너리 저장 (메모리와 분리 보관) |

> **주의**: LLM이 환각(hallucination)을 일으킬 수 있으므로 실제 프로덕션 환경에서는 추가적인 검증 기법이 필요하다.

## 에이전트 생성 코드

```python
def create_invoice_agent():
    action_registry = PythonActionRegistry()
    environment = PythonEnvironment()
    
    goals = [
        Goal(
            name="페르소나",
            description="당신은 인보이스 처리 에이전트로, 인보이스 데이터 처리 및 저장을 전담한다."
        ),
        Goal(
            name="인보이스 처리",
            description="""
            인보이스를 처리하는 것이 목표다. 각 인보이스에 대해:
            1. 번호, 날짜, 금액, 품목 등 모든 중요 정보를 추출한다
            2. 추출된 데이터를 인보이스 번호 기준으로 저장한다
            3. 성공적인 처리를 확인한다
            4. 오류가 발생하면 적절히 처리한다
            """
        )
    ]

    return Agent(
        goals=goals,
        agent_language=AgentFunctionCallingActionLanguage(),
        action_registry=action_registry,
        generate_response=generate_response,
        environment=environment
    )
```

---

## 이 설계의 핵심 장점

1. **일관된 데이터 구조**: 고정 스키마로 어떤 형식의 인보이스도 동일한 형태로 처리됨
2. **모듈식 설계**: 각 도구가 단일 책임만 가지며, 에이전트의 핵심 목표와 분리됨
3. **오류 처리**: 필수 필드 검증이 내장되어 있어 불완전한 데이터를 방지
4. **지속적 저장**: 딕셔너리 기반 저장소를 데이터베이스로 교체해도 에이전트 로직은 변경 불필요

## 도구를 통한 에이전트의 수평 확장

### 핵심 개념

에이전트의 핵심 목표(Goals)나 시스템 프롬프트를 계속 늘리는 대신, **잘 정의된 도구에 특정 기능을 캡슐화**함으로써 에이전트를 수평으로 확장할 수 있다.

프롬프트 비대화(prompt bloat)와 지시 충돌 문제를 피하면서 에이전트의 능력을 무한히 확장할 수 있다.

### 도구 캡슐화의 세 가지 원칙

| 원칙 | 설명 |
|------|------|
| **도메인 지식 추상화** | 인보이스 형식, 필드 식별 등의 전문 지식은 도구 안에 숨김. 에이전트는 언제 쓸지만 알면 됨 |
| **관심사 분리** | 추출/저장 등 각 도구가 특정 기능만 담당. 에이전트는 고수준 조율에만 집중 |
| **집중 프롬프팅** | 특화 프롬프트를 도구 내부에 넣어 에이전트의 핵심 목표를 단순하게 유지 |

### 유지보수성과 적응성

- **독립적 개발**: 각 도구를 에이전트 핵심 로직과 별개로 개발·테스트·개선 가능
- **버전 관리**: 에이전트 목표를 건드리지 않고 개별 도구만 업데이트 가능
- **플러그인 방식**: 새 도구를 액션 레지스트리에 등록하는 것만으로 에이전트 능력이 즉시 확장됨

### 실무 구현 시 고려사항

| 항목 | 내용 |
|------|------|
| **도구 탐색성** | 명확한 설명과 태그로 에이전트가 언제 쓸지 이해할 수 있게 |
| **오류 처리** | 도구 내부에 강건한 오류 처리를 내장해 실패가 전파되지 않도록 |
| **계측(Instrumentation)** | 로깅과 모니터링을 추가해 도구 사용 현황과 성능 추적 |
| **컨텍스트 인식** | 도구가 컨텍스트를 유지하고 활용하도록 설계 (예: 수정 이력 추적) |

---

## 결론

도구를 통한 수평 확장은 에이전트 시스템 구축 방식의 **패러다임 전환**이다.

핵심 프롬프트에 모든 기능을 몰아넣는 모놀리식 에이전트 대신, 특화된 도구의 추가로 성장하는 **모듈식·적응형 시스템**을 만들 수 있다.

이는 소프트웨어 공학의 검증된 원칙인 **캡슐화, 모듈성, 관심사 분리**를 LLM 기반 에이전트에 그대로 적용한 것이다. 복잡성을 도구 안에 집중시킴으로써 더 유지보수하기 쉽고, 더 적응력 있고, 궁극적으로 더 강력한 시스템을 만들 수 있다.
