# 멀티 에이전트 시스템 입문

우리가 확인한 것 중 하나는, 에이전트는 **특화된 도구 세트**와 **매우 구체적인 지시사항**을 부여받을 때 가장 잘 작동한다는 점이다. 에이전트가 수행하는 작업에 특화될수록, 일반적으로 성능이 더 좋아지고 동작이 더 일관되고 예측 가능해진다.

그렇다면 여기서 질문이 생긴다. **광범위한 추론 능력**이 필요한 복잡한 과제는 어떻게 처리해야 할까? 단순히 회의 하나를 잡는 것을 넘어, 프로젝트 관리나 복잡한 작업 집합을 다뤄야 하는 경우는? 이런 작업들은 깔끔하게 분리되어 하나의 에이전트에 넣을 수 있는 성질의 것이 아니다.

이때 등장하는 것이 바로 **멀티 에이전트 시스템**이다.

---

## 기본 구조: 코디네이터 에이전트

멀티 에이전트 시스템의 핵심 아이디어는 다음과 같다.

- 전체 흐름을 시작하는 **코디네이터 에이전트**(혹은 프로세스/애플리케이션)가 있다.
- 이 에이전트는 전체 실행 흐름을 유지하는 역할을 한다 — 일종의 **프로젝트 매니저**다.
- 이 에이전트는 작업의 각 단계에서 **다른 에이전트에게 위임**한다.

예를 들어 회의 일정 잡기를 생각해보자:

1. 코디네이터 에이전트가 **스케줄러 에이전트**를 호출한다.
2. 스케줄러 에이전트가 회의 시간과 참석자 목록을 반환한다.
3. 코디네이터 에이전트가 **회의 안건 생성 에이전트**를 호출한다.
4. 안건 에이전트가 회의 안건을 반환한다.
5. 이런 식으로 여러 에이전트를 순차적으로 호출한다.

---

## 왜 분리하는가: 시스템 지시사항 오염 문제

에이전트를 분리하는 핵심 이유는 **시스템 지시사항의 오염**을 방지하기 위해서다.

- 회의 **스케줄링**에서 중요한 판단 기준과 회의 **안건 작성**에서 중요한 기준은 서로 다르다.
- 예를 들어 분기 보고서용 회의 안건은 매우 구체적인 형식과 복잡한 규칙을 필요로 한다.
- 이 모든 규칙을 하나의 큰 시스템 프롬프트에 넣으면, 에이전트는 어떤 규칙을 언제 적용해야 할지 혼란스러워진다.
- 한 맥락에서 맞는 규칙이 다른 맥락을 오염시킬 수 있다.

따라서 **각 에이전트는 자신의 역할에 맞는 깔끔하고 격리된 시스템 지시사항**을 가져야 한다.

## 비교: 단일 에이전트 vs 멀티 에이전트

| 구분 | 단일 에이전트 | 멀티 에이전트 |
|------|--------------|--------------|
| 도구 수 | 4개 (모두 포함) | 에이전트당 1~2개 |
| 시스템 지시사항 | 여러 상황을 모두 기술하는 거대한 하나 | 각 에이전트별로 집중된 하나 |
| 예측 가능성 | 낮음 | 높음 |
| 유지보수성 | 어려움 | 쉬움 |

## 멀티 에이전트의 장점

멀티 에이전트 시스템으로 전환했을 때 얻을 수 있는 이점:

- **집중된 에이전트**: 각 에이전트는 더 작은 도구 세트를 가지고 자신의 작업에만 집중한다.
- **높은 성능**: 모든 도구를 가진 거대한 단일 에이전트보다 일반적으로 더 잘 작동한다.
- **모듈화**: 코드베이스가 모듈화되어 있는 것처럼, 한 에이전트를 변경해도 다른 에이전트에 미치는 영향을 추론하기 쉽다.
- **테스트 용이성**: 개별 에이전트를 독립적으로 테스트할 수 있다.
- **변경 영향 파악**: 거대한 단일 에이전트에서 하나를 바꾸면 전체에 어떤 영향을 미치는지 파악하기 어렵지만, 분리된 에이전트에서는 훨씬 명확하다.
