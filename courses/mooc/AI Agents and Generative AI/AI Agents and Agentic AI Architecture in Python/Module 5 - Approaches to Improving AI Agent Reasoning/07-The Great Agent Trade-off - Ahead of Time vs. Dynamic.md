# 에이전트의 큰 트레이드오프: 사전 계획 vs 동적 실행

## 핵심 질문

에이전트를 설계할 때 중요한 선택지가 있다.

> 에이전트가 **매 단계마다 직접 판단**하게 할 것인가,  
> 아니면 처음에 **워크플로우를 생성**하게 하고 이후에는 고정된 절차를 실행할 것인가?

이 선택은 에이전트 시스템의 속도, 비용, 예측 가능성, 적응력에 큰 영향을 준다.

---

## 실행 스타일 1: 완전 동적 에이전트 실행

가장 기본적인 방식은 에이전트가 매 단계마다 다음 행동을 직접 결정하는 것이다.

```
상황 확인 → 에이전트 호출 → 다음 action 결정 → 실행
       → 결과 확인 → 에이전트 호출 → 다음 action 결정 → 실행
       → ...
```

이 방식에서는 에이전트가 실행의 모든 단계에 깊이 관여한다.
각 단계마다 이전 결과를 보고, 그 결과를 바탕으로 다음에 무엇을 할지 결정한다.

---

## 완전 동적 실행의 장점

### 1. 가장 높은 적응력

에이전트는 매 단계마다 현재 상황을 다시 해석할 수 있다.

- 예상과 다른 결과가 나왔는지 확인
- 계획을 즉석에서 수정
- 새로운 문제를 추론
- 다른 도구나 전략으로 전환

즉, 실행 도중에 상황이 변해도 유연하게 대응할 수 있다.

### 2. 만들기 쉽다

개발자는 에이전트에게 도구 목록을 주고 이렇게 말할 수 있다.

> "이 작업을 해결해라."

처음부터 정교한 워크플로우를 설계하지 않아도 된다.
그래서 프로토타입이나 열린 문제를 다룰 때 유용하다.

---

## 완전 동적 실행의 단점

동적 실행은 유연하지만 비용이 크다.

| 단점 | 이유 |
|---|---|
| 느림 | 매 단계마다 LLM을 호출해야 한다 |
| 비쌈 | 반복 호출로 토큰 사용량이 늘어난다 |
| 예측 불가능 | LLM 호출마다 약간의 확률성과 변동성이 있다 |
| 반복성 낮음 | 같은 입력을 줘도 다음 실행에서 같은 행동이 나오지 않을 수 있다 |
| 오류 가능성 높음 | 매 단계마다 잘못 판단할 기회가 생긴다 |

즉, 완전 동적 실행은 **가장 적응적이지만 가장 불안정한 방식**이다.

---

## 실행 스타일 2: 사전 생성 워크플로우

반대쪽 극단에는 사전 생성 워크플로우 방식이 있다.

이 방식에서는 에이전트가 처음에 전체 실행 계획을 만든다.
그 계획은 코드, 워크플로우 설명, 프로세스 언어 등으로 표현될 수 있다.
그다음에는 에이전트가 개입하지 않고 해당 워크플로우를 실행한다.

```
에이전트 호출 → 전체 워크플로우 생성
              → 워크플로우 실행
              → 결과 반환
```

워크플로우 내부에 수백 개, 수천 개의 단계가 있더라도,
일단 실행이 시작되면 에이전트는 loop 밖에 있다.

---

## 사전 생성 워크플로우의 장점

### 1. 빠르다

워크플로우가 생성된 뒤에는 LLM을 매 단계 호출하지 않는다.
대부분의 실행은 일반 코드나 프로세스처럼 진행된다.

### 2. 비용이 낮다

LLM 호출 횟수가 줄어들기 때문에 토큰 비용이 줄어든다.

### 3. 예측 가능하고 반복 가능하다

한번 생성된 워크플로우는 코드나 프로세스 정의처럼 실행된다.
즉, 매 단계마다 확률적 판단이 개입하지 않는다.

```
같은 워크플로우 + 같은 입력 → 대체로 같은 결과
```

### 4. 저장하고 재사용할 수 있다

잘 작동하는 워크플로우는 저장할 수 있다.
나중에 다시 실행하거나, 테스트 케이스를 만들거나, 운영 프로세스로 발전시킬 수 있다.

이 관점에서 보면 AI 코딩 도구도 비슷하다.
AI가 우리의 아이디어를 코드나 워크플로우로 번역하고,
그 결과물을 사람이 저장하고 반복 실행하는 것이다.

---

## 사전 생성 워크플로우의 단점

### 1. 정적이다

워크플로우가 실행되는 동안 에이전트는 중간 상황을 보지 않는다.
따라서 예상과 다른 일이 생겨도 즉석에서 적응하기 어렵다.

예를 들어 중간에 예외가 발생하면,

```
"잠깐, 상황이 예상과 다르다. 다른 방법으로 해결하자."
```

라고 판단할 에이전트가 없다.

### 2. 지능이 워크플로우 밖에 있다

처음 계획을 만들 때는 AI의 추론이 들어가지만,
실행 중에는 고정된 소프트웨어처럼 동작한다.

### 3. 개발 부담이 생길 수 있다

워크플로우를 안정적으로 만들고 반복 가능하게 다듬는 데 시간이 걸릴 수 있다.

---

## 두 극단의 비교

| 구분 | 완전 동적 실행 | 사전 생성 워크플로우 |
|---|---|---|
| 에이전트 개입 | 매 단계 | 시작 시 1회 |
| 적응력 | 매우 높음 | 낮음 |
| 속도 | 느림 | 빠름 |
| 비용 | 높음 | 낮음 |
| 예측 가능성 | 낮음 | 높음 |
| 반복 가능성 | 낮음 | 높음 |
| 개발 난이도 | 초기 구현 쉬움 | 안정화에 더 많은 작업 필요 |
| 적합한 상황 | 열린 문제, 예외가 많은 문제 | 반복 업무, 안정된 프로세스 |

---

## 실행 스타일 3: 하이브리드 방식

현실에서는 두 극단 중 하나만 선택할 필요가 없다.
사전 생성 워크플로우와 동적 실행을 섞을 수 있다.

예를 들어:

```
1. 에이전트가 긴 워크플로우를 생성한다
2. 워크플로우를 실행한다
3. 결과를 에이전트에게 다시 보여준다
4. 결과가 이상하면 에이전트가 다시 개입한다
```

즉, 먼저 빠르고 예측 가능한 방식으로 실행해보고,
문제가 생기면 에이전트가 다시 들어와 적응적으로 해결하는 구조다.

---

## 하이브리드 방식의 예

에이전트가 코드를 생성하고 실행하는 시스템을 생각해보자.

```
에이전트가 Python 코드 생성
→ 코드 실행
→ 성공하면 결과 반환
→ 예외가 발생하면 에이전트가 코드 수정
→ 다시 실행
```

ChatGPT의 코드 실행 도구나 고급 데이터 분석 도구도 이런 방식에 가깝다.

- 먼저 Python 코드를 생성한다
- 실행한다
- 올바른 CSV, 그래프, 분석 결과가 나오면 종료한다
- 예외가 발생하면 코드를 수정하고 재실행한다

이 방식은 사전 생성 워크플로우의 효율성과 동적 에이전트의 복구 능력을 함께 사용한다.

---

## 하이브리드 방식의 장점

| 장점 | 설명 |
|---|---|
| 효율성 | 워크플로우가 잘 작동하면 빠르고 저렴하게 끝난다 |
| 반복성 | 성공한 워크플로우는 저장하고 재사용할 수 있다 |
| 복구력 | 예외나 이상 결과가 생기면 에이전트가 개입할 수 있다 |
| 유연성 | 필요하면 단계별 문제 해결 모드로 전환할 수 있다 |

하이브리드 방식은 다음과 같은 흐름을 가진다.

```
빠른 실행을 먼저 시도
→ 실패하거나 이상하면 느리지만 적응적인 실행으로 전환
```

이것은 실용적인 에이전트 시스템에서 매우 자주 사용되는 패턴이다.

---

## 실행 스타일 4: AI Shim 방식

또 다른 방식은 **AI Shim**이다.

여기서는 전체 비즈니스 프로세스의 순서는 사람이 고정한다.
에이전트가 다음에 어떤 action을 할지 마음대로 정하지 못한다.
대신 AI는 각 단계 사이에 들어가서 이전 단계의 출력을 다음 단계의 입력에 맞게 변환한다.

```
고정된 action 1 실행
→ AI가 출력 해석 및 변환
→ 고정된 action 2 실행
→ AI가 출력 해석 및 변환
→ 고정된 action 3 실행
```

AI가 프로세스를 새로 만들지는 않는다.
하지만 단계와 단계 사이의 간격을 메우는 adapter 역할을 한다.

---

## 왜 AI Shim이 필요한가

비즈니스 프로세스는 임의로 바뀌면 안 되는 경우가 많다.

인턴을 예로 들어보자.
인턴은 유연하게 생각할 수 있지만, 그렇다고 회사의 업무 프로세스를 마음대로 새로 만들게 하지는 않는다.

대신 이렇게 말한다.

> "우리 회사는 이 순서로 일한다.  
> 너는 각 단계에서 필요한 판단과 변환을 도와라."

AI Shim도 같은 구조다.
프로세스의 순서는 사람이 정하고, AI는 각 단계 사이에서 필요한 해석과 변환을 맡는다.

---

## AI Shim 예시: 회의 일정 잡기

회의 일정을 잡는 업무를 생각해보자.

우리는 매번 다음 세 단계를 실행하고 싶다.

```
1. 사용자의 가능한 시간 조회
2. 모든 사람의 가능 시간을 바탕으로 적절한 시간 선택
3. 답장 이메일 초안 작성
```

이 순서는 고정한다.
에이전트가 갑자기 다른 방식으로 바꾸면 안 된다.

예를 들어 에이전트가 이렇게 결정하면 곤란할 수 있다.

> "그냥 투표 링크를 만들어서 모두에게 보내자."

우리의 비즈니스 프로세스가 그 방식이 아니라면,
에이전트는 그 결정을 하면 안 된다.

---

## AI Shim에서 에이전트가 하는 일

AI Shim 방식에서는 다음 action이 무엇인지는 고정되어 있다.
하지만 이전 action의 결과를 다음 action에 어떻게 넘길지는 AI가 판단한다.

예를 들어:

- 가능한 시간 목록 중 이메일 요청과 관련 있는 시간만 고른다
- 참가자 모두가 가능한 후보 시간을 추론한다
- 다음 단계에 필요한 입력 형식으로 데이터를 정리한다
- 최종 이메일 초안에 들어갈 표현을 만든다

즉, AI는 다음 단계를 선택하지 않는다.
다만 **이전 단계의 출력과 다음 단계의 입력 사이를 연결**한다.

---

## AI Shim의 특징

| 항목 | 설명 |
|---|---|
| action 순서 | 사람이 고정 |
| AI의 역할 | 단계 사이의 데이터 해석, 변환, 연결 |
| 반복성 | 같은 action 순서가 항상 실행되므로 높음 |
| 예측 불가능성 | 데이터 변환 방식에는 일부 남아 있음 |
| 적합한 상황 | 정해진 비즈니스 프로세스, 승인된 업무 절차 |

AI Shim은 완전 동적 에이전트보다 통제 가능하고,
완전 고정 워크플로우보다 유연하다.

---

## 네 가지 실행 방식 비교

| 방식 | 핵심 아이디어 | 장점 | 단점 |
|---|---|---|---|
| 완전 동적 실행 | 매 단계 에이전트가 action 선택 | 가장 유연함 | 느림, 비쌈, 예측 어려움 |
| 사전 생성 워크플로우 | 처음에 계획/코드를 만들고 그대로 실행 | 빠름, 저렴함, 반복 가능 | 실행 중 적응 어려움 |
| 하이브리드 | 먼저 워크플로우 실행, 실패 시 에이전트 개입 | 효율성과 복구력 균형 | 여전히 초기 계획 품질에 의존 |
| AI Shim | action 순서는 고정, 단계 사이 변환만 AI가 담당 | 통제성과 유연성 균형 | 변환 판단에는 변동성 존재 |

---

## 어떤 방식을 선택해야 하는가

| 상황 | 권장 방식 |
|---|---|
| 문제 구조가 불명확하고 예외가 많음 | 완전 동적 실행 |
| 반복 가능하고 절차가 명확한 작업 | 사전 생성 워크플로우 |
| 대부분은 자동화 가능하지만 실패 복구가 필요함 | 하이브리드 |
| 비즈니스 프로세스 순서는 고정해야 하지만 단계 사이 판단이 필요함 | AI Shim |

---

## 핵심 정리

1. 에이전트 실행 방식에는 **적응력과 예측 가능성 사이의 트레이드오프**가 있다.
2. 완전 동적 실행은 가장 유연하지만 느리고 비싸며 반복성이 낮다.
3. 사전 생성 워크플로우는 빠르고 예측 가능하지만 실행 중 적응력이 낮다.
4. 하이브리드 방식은 먼저 빠른 워크플로우를 시도하고, 문제가 생기면 에이전트가 개입한다.
5. AI Shim은 고정된 프로세스 사이에 AI를 넣어 데이터 변환과 판단을 맡기는 방식이다.
6. 좋은 에이전트 설계는 "AI가 모든 것을 결정하게 하는 것"이 아니라, **어디에 AI의 판단을 넣을지 선택하는 것**이다.

> **에이전트 설계의 핵심은 자율성을 최대화하는 것이 아니라, 자율성이 필요한 지점을 정확히 고르는 것이다.**
