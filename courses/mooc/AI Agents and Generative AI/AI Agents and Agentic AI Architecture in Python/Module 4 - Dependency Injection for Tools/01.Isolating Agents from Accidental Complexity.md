# 에이전트를 우발적 복잡성으로부터 격리하기

## 핵심 개념

에이전트가 일을 잘 하려면, **추론(reasoning)** 에 집중할 수 있도록 환경을 최대한 단순하게 만들어줘야 한다.

---

## 에이전트가 하는 일

AI 에이전트는 사용자의 고수준 요청을 **일련의 API 호출**로 변환해 실행한다.

문제는 사용자가 API를 잘 모를 수도 있고, 요청 방식 자체가 AI에게 낯설 수 있다는 것이다.

---

## JSON 변환 비유

> "시험을 보는데, 모든 답을 JSON 형식으로 출력해야 한다면?"

자연어로 답하는 것보다 훨씬 더 어렵다. 에이전트도 마찬가지다.

- 에이전트는 도구를 선택하고, 인자(argument)를 결정하고, 그것을 **JSON으로 변환**까지 해야 한다.
- 이 구조적 출력 부담은 피할 수 없지만, **다른 불필요한 복잡성은 최대한 줄여줘야 한다.**

---

## 우발적 복잡성(Accidental Complexity)이란?

본질적인 문제와 무관하게, **구현 방식 때문에 생겨난 복잡성**을 말한다.

예시: 웹 애플리케이션에서 도구를 호출할 때

1. 요청(request)이 들어온다
2. 세션(session)을 추출한다
3. 세션으로 사용자 데이터를 조회한다
4. 그 데이터를 도구에 전달한다

→ 이 과정 하나하나가 에이전트에게 노출되면 복잡도가 급격히 올라간다.

---

## 도구 설계 원칙

에이전트에게 보이는 도구 인터페이스는 **최대한 깔끔**해야 한다.

에이전트가 실제로 알아야 할 인자만 노출하고, 나머지는 **의존성 주입(Dependency Injection)** 으로 뒤에서 처리한다.

### 에이전트가 필요로 하지만 직접 다루면 안 되는 것들
- 사용자 ID / 세션 ID
- 인증 토큰(credentials)
- 데이터 저장소 접근 정보
- API 엔드포인트 URL (dev/prod 구분 등)

---

## 의존성 주입(Dependency Injection)의 역할

```
[에이전트]
    ↓ (깔끔한 인터페이스만 보임)
[도구 (Tool)]
    ↑ (뒤에서 자동 주입)
[세션 ID / 토큰 / DB 연결 / ...]
```

- 에이전트는 **"회의를 예약해줘"** 라고만 생각하면 된다.
- 그 회의 시스템의 사용자 ID, 토큰, dev URL 같은 것들은 **도구 내부에서 자동으로 처리**된다.

---

## 핵심 요약

| 나쁜 설계 | 좋은 설계 |
|---|---|
| 도구에 파라미터 10개 (세션, 토큰, URL 등 포함) | 도구에 핵심 파라미터만 노출 |
| 에이전트가 의존성을 직접 파악해서 전달 | 의존성은 뒤에서 자동 주입 |
| 추론 + 의존성 관리 동시에 수행 | 추론에만 집중 가능 |

> **목표: 에이전트가 "무엇을 할 것인가"에만 집중하도록, 나머지 복잡성은 시스템이 숨긴다.**
