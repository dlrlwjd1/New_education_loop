# Refining a Skill

## 개요
- 스킬은 처음부터 완벽하게 동작하는 경우가 드물고, **시간이 지나며 계속 유지보수·개선(refine)되어야 한다**는 현실을 다루는 강의.
- RECIPE 프레임워크를 이용해 "문제 유형별로 정확히 어디를 고쳐야 하는지" 판단하는 방법을 알려준다.

## 내용
### 왜 유지보수 전략이 필요한가
- 스킬을 AI로 만들었든 수동으로 만들었든, 운 좋게 한 번에 완벽히 동작하는 경우는 드물다.
- 원하는 것 자체가 시간이 지나며 바뀌기도 한다 ("아, 이것도 시켰어야 했는데" 등).
- 문제는 **아무 데나 무작정 문구를 수정하면, 의도치 않게 다른 부분을 망가뜨릴 수 있다**는 것 — RECIPE 구조가 바로 이런 "격리된 수정"을 가능하게 해준다.

### 문제 유형 1 — 순서/누락된 단계 문제 → Concrete Steps 수정
- 증상: 에이전트가 중요한 단계를 건너뛰거나, 새로운 체크 단계를 추가하고 싶을 때.
- 해결: 해당 요청(request)의 **Concrete Steps**를 찾아 수정한다.
- 요청이 여러 개로 나뉘어 있다면, 문제가 되는 요청만 정확히 찾아가 그 부분만 고치면 됨.

### 문제 유형 2 — 결과물의 형태/품질/추론이 마음에 안 들 때 → Steps를 늘리지 말고 Examples를 추가
- 흔한 실수: 결과물이 원하는 모습이 아닐 때, 사람들은 습관적으로 **Concrete Steps에 설명을 계속 추가**하려 한다 → steps가 점점 복잡해지고 따라가기 어려워짐.
- 더 나은 방법: **"이 입력에 대해 이런 결과가 나왔는데, 사실 이래야 했다"는 예시(example)를 스킬에 추가**하는 것.
- 실전 방법:
  1. 스킬을 쓰다가 잘못된 결과를 목격하면, 그 순간의 입력과 (잘못된) 출력을 캡처한다.
  2. "이 출력이 아니라 이렇게 나왔어야 한다"고 직접 수정한 버전을 만들거나, 잘못된 출력과 올바른 출력을 나란히 보여준다.
  3. 이걸 references(또는 SKILL.md 안)에 예시로 추가한다.
- 슬라이드 덱처럼 복잡한 결과물도 "이 입력에는 이런 슬라이드 덱이 나와야 한다"는 식으로 파일을 예시로 참조시킬 수 있다.
- 즉, **결과물/추론 관련 문제는 지시문을 늘리기보다 예시로 해결하는 것이 낫다.**

### 문제 유형 3 — 전역적인 톤/스타일 변경 → Ideal Result(글로벌 목표) 수정
- 예: "모든 결과물을 좀 더 유머러스하게 써줘", "경비 보고서를 마치 영화 <오피스 스페이스>를 쓴 사람이 감사하듯 해줘" 같은 전체적인 톤/목표 변경.
- 이런 전역적인 변화는 **Ideal Result(전역 목표와 이유)** 레벨에서 수정한다.

### 문제 유형 4 — 기계적(mechanical)이고 계산 중심인 단계들이 계속 틀릴 때 → Script로 전환
- 증상: "이 시스템을 확인하고, 저 시스템을 호출하고, 데이터베이스를 조회하고, 계산해서 합쳐라" 같은 **컴퓨터가 스스로 할 수 있는 기계적인 절차**를 텍스트 지시문으로 계속 설명하다가 계속 실수가 발생하는 경우.
- 해결: 이런 반복적·계산적 단계들을 **스크립트(도구)로 전환**한다.
- 스크립트로 전환하면 얻는 이점:
  - 에이전트 입장에서 작업이 단순해짐
  - 토큰을 덜 쓰므로 비용이 저렴해짐
  - 결과가 더 반복 가능(repeatable)해짐
  - 감사(audit)하기 쉬워짐 — "이 단계에서 이 도구를 호출하면 정확히 이 일이 일어난다"는 게 보장됨 (텍스트 지시문은 매번 다르게 수행될 수 있음).

### 문제 유형 5 — 스킬 파일이 지나치게 비대해짐 → References로 분리
- 증상: "아, 이 엣지 케이스도 말해줬어야 했는데", "이것도 빠뜨렸네" 하며 계속 추가하다 보면 SKILL.md가 점점 커지고, 내용이 섞여 헷갈리기 시작함.
- 해결: **핵심이 아니고, 특정 조건에서만 필요한 지식**을 references로 옮긴다.
- SKILL.md에는 "이런 조건이면 이 참조 파일을 읽어라"는 안내만 남기고, SKILL.md 자체는 **가장 본질적인 핵심 정보**로 슬림하게 유지한다.

## 예시
| 문제 증상 | 고쳐야 할 곳 |
|---|---|
| 순서가 틀리거나 단계가 누락됨 | Concrete Steps |
| 결과물 형태/품질/추론이 이상함 | Examples (틀린 사례 + 올바른 사례를 예시로 추가) |
| 전체 톤/스타일을 바꾸고 싶음 | Ideal Result (전역 목표) |
| 계산/데이터 조회 등 기계적 단계가 자꾸 틀림 | Scripts로 전환 |
| SKILL.md가 너무 비대해짐 | 조건부 지식을 References로 이동 |

## 요약
- 스킬은 계속 진화해야 하며, RECIPE 구조 덕분에 **문제 유형에 따라 정확히 어디를 고쳐야 할지 판단**할 수 있다.
- 결과물의 품질/형태 문제는 지시문을 늘리기보다 **예시(example)를 추가**하는 것이 더 효과적이다.
- 반복적이고 계산적인 절차는 텍스트 지시문 대신 **스크립트**로 전환하면 비용도 낮아지고 결과도 안정적이다.
- 스킬이 비대해지면 조건부 지식을 **references로 분리**해 SKILL.md를 핵심만 남기고 슬림하게 유지한다.
