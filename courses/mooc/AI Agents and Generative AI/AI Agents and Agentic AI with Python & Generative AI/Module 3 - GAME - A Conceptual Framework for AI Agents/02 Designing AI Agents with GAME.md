# Designing AI Agents with GAME — 코드 짜기 전에 설계부터

## 개요
- 에이전트를 만들 때는 코드를 바로 짜기보다, **한 걸음 물러나 아키텍처를 설계하는 것**이 중요하다. [01 GAME 개요](01%20Overview%20of%20the%20GAME%20Framework.md)의 4가지 요소를 활용해 **체계적이고 모듈화된 방식으로 설계**하는 방법을 실제 예시로 보여준다.

## 내용

### GAME 프레임워크 재정리
- **G — Goals / Instructions**: 에이전트가 달성하려는 것과, 그것을 달성하는 방법에 대한 지시.
- **A — Actions**: 목표 달성을 위해 에이전트가 사용할 수 있는 도구들.
- **M — Memory**: 상호작용 간 정보를 어떻게 유지하는지 — Agent Loop의 각 반복에서 어떤 정보를 갖고 있을지를 결정.
- **E — Environment**: 에이전트가 행동을 실행하고 그 결과에 대한 피드백을 받는, 외부 세계와의 인터페이스.

### 왜 Goals와 Instructions가 함께 묶이는가
- **Goals(목표)**는 에이전트가 달성하려는 **"무엇(what)"** — 원하는 결과를 정의하는 상위 목표.
- **Instructions(지시)**는 **"어떻게(how)"** — 목표를 효과적으로 달성하기 위한 구체적 단계/전략/제약을 상세히 기술.
- 둘이 합쳐져야 에이전트가 자신의 목적을 이해하면서도, 그것을 달성하는 **구조화된 접근법**을 따르게 된다.

### Actions와 Environment의 관계 — 인터페이스 vs 구현
- **Actions**는 에이전트가 **무엇을 할 수 있는지**를 정의 — 선택 가능한 것들에 대한 **추상적인 설명**.
- **Environment**는 그 행동들이 **실제로 어떻게 실행되는지** 결정 — 실제 세계 맥락에서 실행되는 구체적 구현.
- 비유: **Actions = "인터페이스"** (가능한 능력을 명시), **Environment = "구현"** (그 능력을 실제로 살아 움직이게 함).
- 예: 에이전트의 행동 `read_file()`은 Actions 레이어에서는 단순한 플레이스홀더일 뿐이고, **Environment가 실제 파일 I/O 로직과 에러 처리를 담당**한다.
- 이 분리 덕분에 **유연성**이 생긴다 — 의사결정 로직은 그대로 두고 구현만 바꿔서, 같은 에이전트를 다른 환경에서 동작하게 만들 수 있다 ([01](01%20Overview%20of%20the%20GAME%20Framework.md)의 Google ↔ Office 365 예시와 동일한 원리).

### 예시 — Proactive Coder 에이전트
- 시나리오: 코드베이스를 스캔해 패턴을 분석하고, 적은 수의 변경으로 구현 가능한 새 기능을 제안하는 에이전트. 사용자가 기능을 승인하면 초기 구현을 만들고 개선안을 제시.

**Goals (무엇을 달성할지)**
- 잠재적인 개선사항을 식별한다
- 그 개선사항이 유용하고 관련성이 있는지 확인한다
- 개선사항이 작고 자기완결적(self-contained)이어서 에이전트가 최소한의 위험으로 구현할 수 있게 한다
- 기존 인터페이스를 깨뜨리지 않도록 보장한다
- 사용자가 동의한 기능만 구현하도록 보장한다

**Instructions (어떻게 달성할지)**
- 코드베이스에서 무작위로 파일 하나를 골라 읽는다
- 원본 파일과 관련된 파일들을 읽는다 (최대 5개 파일까지만)
- 2~3개 함수로 구현 가능하고 기존 코드 수정을 최소화하는 기능 아이디어 3개를 제안한다
- 사용자에게 어떤 기능을 구현할지 선택하게 한다
- 수정이 필요한 파일 목록과 각 파일별 변경 제안을 나열한다
- 파일 하나씩 차례로 변경을 구현해나간다 (모두 수정될 때까지)

**Actions**
- 프로젝트 파일 목록 조회
- 프로젝트 파일 읽기
- 사용자에게 기능 선택 요청
- 프로젝트 파일 수정

**Memory**
- 단순한 대화형 메모리(conversational memory) 사용 — 참조를 위해 파일의 전체 내용을 대화에 저장.

**Environment**
- 로컬에서 실행되는 단순한 Python 구현을 우선 제공하되, 나중에 **GitHub Actions에서 동작하는 구현**으로 바꿀 수 있다.

## 요약
- 에이전트 설계는 코드 작성 전에 **GAME(Goals/Instructions, Actions, Memory, Environment)** 로 구조를 먼저 스케치하는 것에서 시작한다.
- **Actions(인터페이스) vs Environment(구현)**의 분리가 핵심 — 이 덕분에 의사결정 로직을 건드리지 않고 환경만 바꿔 에이전트를 재사용할 수 있다.
- "Proactive Coder" 예시처럼, 실제 코드를 짜기 전에 G/A/M/E 각각을 문서로 정리해보는 것이 설계 단계의 실천적 방법이다.
