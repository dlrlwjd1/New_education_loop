# The Agent Loop (에이전트 루프)

## 개요
- 사람이 수동으로 대화를 이어가던 방식(휴먼 인 더 루프)에서 벗어나, **완전히 자율적으로 동작하는 AI 에이전트**로 넘어가기 위한 핵심 구조가 바로 **에이전트 루프(Agent Loop)**다.
- 이 강좌에서 만들게 될 거의 모든 에이전트의 기반 아키텍처이며, 어떤 에이전트 프레임워크/라이브러리를 쓰든 내부적으로는 이 루프가 돌아간다.

## 내용

### 문제 제기: 사람이 매번 복사-붙여넣기 해야 한다면?
- 에이전트가 컴퓨터 시스템과 상호작용해야 하는 경우, 사람이 매번 "에이전트 말을 듣고 → 컴퓨터에 입력하고 → 결과를 복사해서 다시 에이전트에 붙여넣는" 과정을 반복하는 것은 비효율적이다.
- 목표: 사람(또는 사람이 트리거한 프로세스)이 **작업(task)을 한 번 지시**하면(예: "이 출장 경비를 등록해줘"), 이후 에이전트가 API/함수 등 주어진 자원을 활용해 **스스로 그 작업을 완료**하도록 만드는 것.
- 즉, 사람이 자연어로 표현한 목표를 **연산(computation)으로 번역**하는 것. (Transformer 모델이 애초에 번역 작업에서 검증되었다는 점과 연결 — LLM은 사람 언어를 연산으로 옮기는 데 탁월하다.)

### 왜 "코드를 출력해서 사람이 실행"하는 방식은 부족한가
- 에이전트에게 "이 API를 어떻게 호출해야 하는지 알려줘"라고 시켜서 코드를 받은 뒤, 사람이 그 코드를 복사해서 직접 실행하는 방식도 가능하긴 하다.
- 하지만 이는 여전히 **완전한 휴먼 인 더 루프(human-in-the-loop) 방식**이라서, 진짜 자율적인 AI 에이전트라고 보기 어렵다.
- 우리가 원하는 것은 사람이 작업을 준 이후 **에이전트가 자율적으로 실행**하는 구조.

### 에이전트 루프의 핵심 구조
사람이 작업을 지시한 뒤, 에이전트가 종료(terminate)를 결정할 때까지 다음을 반복한다:

1. **프롬프트 구성(construct the prompt)** — 에이전트 개발의 대부분 노력이 여기에 들어간다. 좋은 프롬프트를 만들고 에이전트를 잘 유도하는 것이 핵심.
2. **LLM에 프롬프트 전송 → 응답 받기**
3. **응답 파싱(parse the response)** — LLM이 원하는 행동(action)을 우리 소프트웨어가 이해할 수 있는 형식으로 뽑아내야 한다. 기존 소프트웨어 인프라는 유연하지 않고 엄격(rigid, brittle)하기 때문에, **파싱 가능한 형식으로 응답하도록 프롬프트를 설계**하는 것이 중요하다.
4. **행동 실행(execute the action)** — 파싱된 행동을 실제 API 호출, 파일 복사 등 실제 컴퓨터 작업으로 실행한다.
5. **결과(피드백) 획득** — API 응답, HTTP 코드, 에러 메시지 등 무엇이든 **문자열(string)로 변환**해 피드백으로 삼는다.
6. **루프 계속 여부 판단 → 다음 프롬프트에 피드백 반영** — 계속 진행한다면, 이전 피드백을 원래 프롬프트에 추가해 다음 프롬프트를 구성한다. 이 과정이 반복되며 프롬프트가 점점 누적/성장한다.

> 이 6단계가 사실상 "대화(conversation)"를 "자율적으로 행동하는 에이전트"로 바꿔주는 핵심 메커니즘이다.

### 설계 포인트
- **루프의 제어권은 우리(개발자)에게 있다.** 각 반복(iteration)에서 "어떤 행동을 할지"는 에이전트(LLM)가 결정하지만, 루프 자체를 계속할지/멈출지는 우리가 관리한다.
- 다음 행동을 명시적으로 "다음엔 뭘 할 거야?"라고 묻지 않아도 되는 경우도 있다 — 누적된 프롬프트/피드백만으로도 에이전트가 알아서 이어간다는 점이 흥미로운 부분.
- 이 기본 루프 구조는 매우 단순하지만 **실무에서 필요한 대부분의 경우를 커버**한다. 복잡한 프레임워크 없이도 이 루프만으로 충분히 강력한 에이전트를 만들 수 있다.

### 예시 시나리오 — 출장 경비 등록 에이전트
1. 작업 지시: "이 출장 경비를 추가해줘 (add this travel expense)."
2. 첫 프롬프트: "경비를 추가하기 위한 첫 번째 행동을 결정해줘. 가능한 옵션은 다음과 같다: ..."
3. 에이전트가 옵션 중 하나를 선택 (예: 스프레드시트의 행(row) 목록을 조회).
4. 우리 코드가 그 행동을 실행하고 결과(행 목록)를 받음.
5. 결과를 다음 프롬프트에 포함시켜 다시 질문: "이 경비가 이미 존재하는가?" → 없다면 → "행을 추가해줘" 라는 다음 행동으로 이어짐.
6. 이 과정을 에이전트가 작업 완료를 선언할 때까지 반복.

## 예시
> **루프 의사코드 (개념적 요약)**
> ```
> while True:
>     prompt = build_prompt(task, feedback_so_far)
>     response = call_llm(prompt)
>     action = parse_action(response)          # 응답 파싱
>     result = execute(action)                  # 실제 API/함수 호출
>     feedback = stringify(result)               # 결과를 문자열로 변환
>     if should_terminate(response, result):
>         break
>     feedback_so_far += feedback                # 다음 프롬프트에 누적 반영
> ```

## 요약
- **에이전트 루프 = 프롬프트 구성 → LLM 호출 → 응답 파싱 → 행동 실행 → 결과(피드백) 획득 → 종료 판단 후 반복**의 6단계 반복 구조.
- 이 루프가 "대화형 상호작용"을 "자율적으로 동작하는 AI 에이전트"로 바꿔주는 핵심 메커니즘이다.
- 개발 노력의 대부분은 **좋은 프롬프트 설계**와 **응답을 안정적으로 파싱하는 방법**에 들어간다.
- 이 단순한 루프 구조만으로도 실무에서 필요한 대부분의 에이전트를 만들 수 있으며, 이후 강의들에서 이 루프를 세부적으로 커스터마이징하는 방법을 다룬다.
