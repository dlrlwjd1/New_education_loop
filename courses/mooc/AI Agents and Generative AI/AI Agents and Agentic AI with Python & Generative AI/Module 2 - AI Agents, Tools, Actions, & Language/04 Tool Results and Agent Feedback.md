# Tool Results and Agent Feedback — 도구 실행 결과를 어떻게 피드백할 것인가

## 개요
- 에이전트는 도구/행동을 실행한 결과를 **직접 관찰할 수 없다** — 반드시 우리가 그 결과를 알려줘야 한다. 이 "피드백"을 어떻게 프롬프트에 반영하는지가 이번 영상의 핵심.

## 내용

### 핵심 아이디어 — "다음 프롬프트 = 이전 행동의 결과"
- 지금까지 반복해서 보여줬지만 명시적으로 말하지 않았던 패턴: **에이전트에게 프롬프트를 주고 → 무엇을 할지 응답받고 → 그 행동을 실제로 수행하고 → 다음 프롬프트로 "그 행동의 결과"를 준다.**
- 사람과의 대화라면 사람이 질문에 답하는 자리에, 에이전트-도구 상호작용에서는 **"행동의 결과"**가 들어간다.
  - 사람과의 대화 흐름: 인간이 질문 → 정보 제공 → 다음 질문 → 정보 제공 → ...
  - 에이전트-도구 흐름: 에이전트가 행동을 지정 → 컴퓨터 시스템이 그 행동을 실행 → 결과를 다음 프롬프트로 제공 → 에이전트가 다음 행동을 결정 → 반복.

### 예시 — 컴퓨터화된 전자레인지(microwave) 시뮬레이션
- 도구를 실제 컴퓨터 시스템의 인터페이스에 가까운 이름으로 정의: `microwave_get_current_time`, `microwave_reset_time`, `microwave_increase_time`, `microwave_stop`, `microwave_start`, `microwave_open_door`, `microwave_close_door`, `insert_food_in_microwave`.
  - 이런 이름은 프로그래머가 실제로 지을 법한 함수명에 가깝다 — **도구/행동 설명을 실제 컴퓨터 시스템의 인터페이스에 가깝게 옮겨가는 것**.
- 프롬프트에 **의존 관계(dependency) 같은 baseline 정보도 포함**해야 한다: "전자레인지를 시작하려면 먼저 시간을 설정해야 한다" — 이런 정보는 에이전트가 추론으로 알아낼 수 없을 수 있으므로 명시적으로 알려줘야 한다.
- "케사디야를 데워달라"는 요청에 대해:
  1. `insert_food_in_microwave` 실행 지시 → 결과 "food in microwave" 전달
  2. `microwave_increase_time` 실행 지시 → **결과로 "5초 증가"라는 정보 전달** — 처음에는 얼마나 증가하는지 명시하지 않았기 때문에, 이 결과 피드백이 있어야 비로소 "1~2분은 부족하다"는 걸 알고 60초까지 반복 증가시키도록 적응한다.
  3. `microwave_start` 실행 지시 → 일부러 **에러를 던짐**: "error door open" → 에이전트가 "문이 열려있는 것 같으니 `microwave_close_door`를 사용하라"고 정확히 대응.
  4. 문 닫힘 결과 전달 → 다시 시작 지시 → 실행 중 결과 전달 → 완료 후 문을 열고 음식을 꺼내라고 지시.

### 왜 결과 피드백이 결정적으로 중요한가
- **행동의 결과를 알려주지 않으면 에이전트는 세상의 상태(state)를 전혀 알 수 없다.** 예: 시간이 얼마나 증가했는지 알려주지 않으면 적절한 조정을 할 수 없다.
- **에러 메시지의 품질이 시스템의 성패를 가른다.**
  - 에러가 발생했을 때는 "무엇이 잘못됐고 왜 안 됐는지"를 명확하고 풍부하게 알려줘야 한다 (예: "문이 열려 있음").
  - 만약 에이전트가 모르는 코드(예: "error 32")를 그대로 전달하면, 에이전트는 **완전히 길을 잃는다(hosed)** — 의미를 알 수 없는 에러 코드는 그 자체로 무용지물.
  - 만약 에이전트가 이미 그 에러 코드의 의미를 알고 있다면(예: 사전 학습이나 문서로), 숫자 코드 그대로 줘도 상관없다.
  - 원칙: **에이전트가 이해하지 못할 에러 코드는, 에이전트가 이해할 수 있는 의미로 번역해서 전달**해야 한다.
- 실무 팁: 에이전트가 같은 실수를 반복하며 루프에 빠져 있다면, **에러 메시지를 더 지능적이고 구체적으로** 만들어보라 — 종종 누락된 정보 하나만 채워주면 문제가 해결된다.

## 예시
> **결과 피드백이 상태 정보를 제공하는 예**
> 에이전트: "microwave_increase_time 사용"
> → 우리(시스템): "result: time increased by 5 seconds" (얼마나 증가했는지는 이 피드백에서 처음 알려짐)
> → 에이전트: "60초가 되도록 microwave_increase_time을 반복 사용해라"

> **좋은 에러 메시지 vs 나쁜 에러 메시지**
> - 나쁨: `error 32` (에이전트가 의미를 모르면 완전히 막힘)
> - 좋음: `error: door open — use microwave_close_door` 같이 원인과 힌트를 포함한 메시지

## 요약
- 에이전트는 행동의 결과를 스스로 관찰할 수 없으므로, **행동 → 실행 → 결과를 다음 프롬프트로 피드백**하는 것이 Agent Loop의 핵심 순환이다 ([Module 1 - 03 The Agent Loop](../Module%201%20-%20Agentic%20AI%20Concepts/03%20The%20Agent%20Loop.md)와 직결).
- 도구 이름을 실제 시스템 인터페이스에 가깝게 짓고, 의존 관계 같은 baseline 정보를 프롬프트에 포함하면 실제 컴퓨터 시스템 연동에 가까워진다.
- **에러 메시지는 에이전트가 이해할 수 있는 형태로 원인을 명확히 설명**해야 한다 — 의미를 모르는 코드/메시지는 에이전트를 완전히 멈추게 만들 수 있다.
