# Two Phase Locking

## 개요
- 동시성 제어(concurrency control) 기법인 2단계 잠금(two-phase locking, 2PL)을 다룬다.
- 잠금 호환성(lock compatibility), 성장 단계(growing phase)와 수축 단계(shrinking phase), 그리고 잠금이 없을 때 발생하는 오류를 살펴본다.
- 수축 단계에서 생기는 문제와 이를 해결하는 엄격한 2단계 잠금(strict two-phase locking)까지 다룬다.

## 내용

### 잠금 호환성(Lock Compatibility)
- 여러 트랜잭션이 같은 값에 읽기 잠금(read lock)을 거는 것은 서로 호환된다. 아무도 값을 바꾸지 않는 한 여러 개의 읽기 잠금은 동시에 존재할 수 있다.
- 트랜잭션 1이 어떤 값에 읽기 잠금을 걸고 있으면, 다른 트랜잭션은 트랜잭션 1이 읽기 잠금을 해제할 때까지 그 값에 쓰기 잠금(write lock)을 걸 수 없다.
- 트랜잭션 1이 쓰기 잠금을 걸고 있으면, 다른 트랜잭션은 읽기 잠금도 쓰기 잠금도 걸 수 없으며 트랜잭션 1이 쓰기 잠금을 해제할 때까지 기다려야 한다.

### 성장 단계와 수축 단계(Growing and Shrinking Phase)
- 정확성을 보장하려면 트랜잭션은 필요한 잠금을 모두 획득할 때까지 잠금을 계속 모아야(accumulate) 한다. 이것이 성장 단계(growing phase)다.
- 필요한 모든 잠금을 확보한 후, 더 이상 필요 없는 자원의 잠금을 천천히 해제하는 것이 수축 단계(shrinking phase)다.
- 두 단계(성장, 수축)로 이루어지기 때문에 2단계 잠금(two-phase locking) 알고리즘이라 부른다.
- 다이어그램에서 위로 올라가는 계단 한 칸은 잠금 획득, 수평선은 처리(processing)를 의미한다. 모든 잠금을 한꺼번에 확보한 뒤에야 잠금을 해제하기 시작할 수 있다.

### 잠금 없이 인터리빙할 때의 오류
- 잘못된 순서로 값이 갱신되면 격리성(isolation)이 깨져 일관되지 않은 결과가 나온다.
- 트랜잭션은 마치 자신이 데이터베이스에 접근하는 유일한 존재인 것처럼 격리되어 동작해야 하며, 다른 트랜잭션이 데이터에 영향을 주어서는 안 된다.

### 수축 단계의 문제와 연쇄 중단(Cascading Abort)
- 수축 단계에서 잠금 관리자(lock manager)가 알기 어려운 것들이 있다: 언제 데이터가 더 이상 필요 없는지, 언제 잠금을 해제해도 되는지, 트랜잭션의 다른 부분에서 그 데이터가 필요 없는지.
- 트랜잭션 1이 값을 잠그고 수정한 뒤 잠금을 해제했지만 아직 작업이 끝나지 않은 상태에서, 트랜잭션 2가 그 값에 잠금을 걸고 트랜잭션 1의 수정에 기반해 또 수정을 한다.
- 이때 트랜잭션 1이 중단(abort)되면 자신의 값을 롤백(rollback)해야 하고, 트랜잭션 2에게도 중단을 알려야 한다. 트랜잭션 2가 가져간 값은 실제 값이 아니었으므로 트랜잭션 2도 롤백해야 한다.
- 이렇게 하나의 중단이 다른 트랜잭션의 중단을 연쇄적으로 유발하는 것을 연쇄 중단(cascading abort)이라 한다.

### 엄격한 2단계 잠금(Strict Two-Phase Locking)
- 위 문제를 단순화하기 위해 엄격한 2단계 잠금(strict two-phase locking) 알고리즘을 사용한다.
- 규칙: 트랜잭션이 커밋(commit)할 때까지 어떤 잠금도 해제하지 않는다.
- 잠금을 천천히 늘려 모두 확보하고, 커밋이 일어날 때까지 하나도 놓지 않다가 커밋 시점에 모두 해제한다.
- 이는 일반 2단계 잠금의 수축 단계에서 유발되는 문제들을 해결하며, 이후 학기 내내 다루게 될 방식이다.

## 예시

### Amazon 기프트 인증서 예시 (2PL이 필요한 이유)
- 상황: Amazon.com이 도서·DVD 기프트 인증서 계좌의 값을 모두 2배로 만든다. 동시에 한 고객이 한 트랜잭션 안에서 기프트 인증서에서 $25, $50을 사용한다.
- 초기값: 도서 인증서 $50, DVD 인증서 $60.

두 개의 올바른 결과(순서에 따라 다름):
- **순서 1** (Amazon 먼저): $50, $60 → 2배 → $100, $120 → 고객이 구매($25 도서, $50 DVD) → **도서 $75, DVD $70**
- **순서 2** (고객 먼저): $50, $60 → 고객이 $25 도서, $50 DVD 구매 → $25, $10 → Amazon이 2배 → **도서 $50, DVD $20**
- 두 결과($75/$70 또는 $50/$20)는 모두 정답이지만, 그 외의 답은 일관되지 않아 오답이다.

트랜잭션 연산:
- 트랜잭션 1 (Amazon): 도서 값 읽기 → 2배 → 쓰기 → DVD 값 읽기 → 2배 → 쓰기 → 커밋
- 트랜잭션 2 (고객): 도서 값 읽기 → $25 빼기 → 쓰기 → DVD 값 읽기 → $50 빼기 → 쓰기 → 커밋

잘못된 인터리빙(잠금을 너무 일찍 해제한 경우):
1. T1: 도서 잠금 → 읽기 → 2배 → 쓰기 → **잠금 해제**
2. T2: 도서 잠금 → 읽기 → $25 빼기 → 쓰기
3. T2: DVD 잠금 → 읽기 → $50 빼기 → 쓰기 → 잠금 해제 → 커밋
4. T1: DVD 잠금 → 읽기 → 2배 → 쓰기 → 잠금 해제 → 커밋
- 결과: 도서 $75, DVD $20 → **오답**. ($75/$70 또는 $50/$20 이어야 함)
- 원인: T1이 도서 값을 수정하고 잠금을 해제한 뒤, 아직 작업이 끝나지 않았는데 T2가 그 잠금을 가져가 수정을 했기 때문.

## 요약
- 읽기 잠금끼리는 호환되지만, 쓰기 잠금은 다른 읽기·쓰기 잠금과 호환되지 않는다.
- 2단계 잠금(2PL)은 성장 단계(잠금 획득)와 수축 단계(잠금 해제)의 두 단계로 구성된다.
- 필요한 모든 잠금을 확보하기 전에 잠금을 해제하면 다른 트랜잭션이 끼어들어 일관성이 깨진다.
- 수축 단계에서는 잠금 해제 시점 판단이 어렵고, 연쇄 중단(cascading abort) 문제가 생긴다.
- 엄격한 2단계 잠금(strict 2PL)은 커밋 전까지 어떤 잠금도 해제하지 않아 이 문제를 해결한다.
