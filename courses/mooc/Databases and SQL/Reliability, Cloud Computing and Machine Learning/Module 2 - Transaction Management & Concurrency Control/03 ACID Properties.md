# ACID Properties

## 개요
- 트랜잭션 데이터베이스 관리 시스템의 네 가지 성질인 ACID — 원자성(Atomicity), 일관성(Consistency), 고립성(Isolation), 지속성(Durability) — 을 다룬다.
- 고립성 위반이 만드는 문제들: 더티 리드(dirty read), 반복 불가능 읽기(non-repeatable/fuzzy read), 팬텀 리드(phantom read), 미커밋 데이터 덮어쓰기(overwriting uncommitted data).
- C·I(일관성·고립성)는 동시성 제어(concurrency control)가, A·D(원자성·지속성)는 회복 관리(recovery management)가 담당한다.

## 내용

### 원자성 (Atomicity)
- 트랜잭션은 연산의 단위(unit of operation)다. 트랜잭션 안의 모든 연산은 전부 완료되거나 전부 완료되지 않는다 — **all or nothing**. 절반만 완료되는 일은 없다.
- 실패가 발생하면 DBMS는 트랜잭션의 일부를 되돌리거나(undo), 나중에 완료해야 한다.
- 실패의 두 종류:
  - **논리적 오류(logical errors)**: 데이터 오류, 교착상태(deadlock), 일관성 문제 등. 보통 트랜잭션이나 DBMS가 스스로 어보트한다.
  - **시스템 크래시(system crashes)**: 미디어 오류, 시스템 크래시, 네트워크 문제 등. 이 경우 크래시 회복(crash recovery)이 필요하다(이후 단원에서 다룸).
- 플러그가 뽑히든, 디스크가 크래시하든, 트랜잭션 중간에 0으로 나누기 오류가 나든, 지금까지 한 것을 모두 제거하거나 나중에 나머지 연산을 완료해야 한다.

### 일관성 (Consistency)
- 일관성은 곧 **정확성(correctness)** 이다. 트랜잭션은 하나의 일관된 데이터베이스 상태를 또 다른 일관된 상태로 매핑해야 한다.
- 연산이 끝났을 때(트랜잭션이 끝났을 때) 데이터베이스가 비일관 상태가 되면 전부 롤백해야 한다.
- **트랜잭션 도중에는 비일관 상태가 있어도 된다.** 시작 시점과 끝 시점에만 일관되면 된다.
- 예: 모든 프로젝트에 최소 한 명이 있어야 한다는 제약이 있을 때, 한 사람을 잠시 빼고 다른 사람을 넣는 동안에는 비일관 상태지만, 트랜잭션의 시작과 끝에는 프로젝트에 사람이 있으므로 일관성이 지켜진다.

### 고립성 (Isolation)
- 가장 이해하기 복잡한 성질이며, 이후 동시성 제어 논의의 상당 부분을 차지한다.
- 각 트랜잭션은 항상 일관된 데이터베이스를 보아야 한다. 다른 사용자가 동시에 작업하고 있어도, 자신의 트랜잭션 실행 중에는 다른 사용자의 효과가 보이면 안 된다.
- 현실적으로 데이터베이스는 효율을 위해 많은 사람이 동시에 작업하게 해야 하므로, 동시 트랜잭션들이 **어떤 선형 순서(linear order)로 실행되는 것처럼 보이도록** 실행해야 한다.

#### 더티 리드 문제 (dirty read, lost update라고도 함)
- T1: 한 계좌에서 다른 계좌로 $100 이체. T2: 각 계좌에 6% 이자 추가.
- 계좌 X = $200, 계좌 Y = $100으로 시작한다고 하자.
  - T1이 전부 먼저 실행: X → $100, Y → $200. 이후 T2가 6% 추가: X = $106, Y = $212. 합계 **$318**. 정상.
  - T2가 전부 먼저 실행: X = $212, Y = $106. 이후 T1이 $100 이체: X = $112, Y = $206. 합계 **$318**. 정상.
  - 어느 쪽을 먼저 실행해도 결과는 동일하게 올바르다.
- 그러나 스케줄러가 연산을 끼워 넣은(interleaved) 경우: T1이 X에서 $100을 빼서 씀(X = $100, Y = $100) → T2가 두 계좌에 6% 추가하고 커밋(각 $106) → T1이 Y에 $100을 다시 더해 씀(Y = $206).
- 결과: X = $106, Y = $206, 합계 **$312**. **$6이 사라졌다.** T1의 write와 T2의 read 사이의 충돌(더티 리드) 때문에 트랜잭션 1이 돈을 잃는다.

#### 반복 불가능 읽기 (non-repeatable / fuzzy read)
- T1: 잔액을 읽고 $100을 인출. 이후 로직에서 잔액이 $50 미만이면 잔액을 다시 읽어 그대로 다시 쓴다.
- T2: 잔액을 읽고 $50을 인출해 쓴다.
- 인터리브: T1이 $100을 읽음 → T2가 아직 $100이 있다고 보고 $50을 빼서 씀 → T1이 잔액을 다시 읽는데 T2가 이미 $50으로 만들어 놓음 → T1이 $50을 쓰고 커밋 → 그런데 T2는 어보트함(인출을 원치 않게 됨).
- T2가 실제로 없었던 셈이므로 T1 실행 후 잔액은 $100이어야 하지만, 반복 불가능 읽기 때문에 $50만 남는다. 트랜잭션 1이 돈을 잃는다.

#### 팬텀 리드 (phantom read)
- read-write 충돌. T1이 값을 읽었는데, T2가 그 값을 바꿔도 T1은 여전히 이전에 읽은 값을 갖고 있다고 생각한다.
- T1이 입금 목록(deposit list)을 읽고 출력한 뒤 다시 읽어 쓰는데, 그 사이 T2가 새 입금을 쓰고 커밋한다.
- T1이 처음 읽어 출력한 것과 나중에 쓴 것이 달라진다. 입금 목록에 잡히지 않은 새 입금이 끼어든다.

#### 미커밋 데이터 덮어쓰기 (overwriting uncommitted data)
- 회사 정책: 같은 직급의 모든 직원은 같은 급여를 받아야 한다.
- T1: x의 급여를 $4,000으로 쓰고, y의 급여를 $4,000으로 쓰고 커밋. T2: x와 y의 급여를 $5,000으로 씀.
- 각 트랜잭션 단독으로는 일관성 규칙을 지키지만, write-write 충돌이 인터리브되면 결과적으로 y = $4,000, x = $5,000이 되어 데이터베이스가 비일관 상태로 남는다.

### 지속성 (Durability)
- 트랜잭션이 한 번 커밋되면 영구적이다. 이후의 모든 장애에도 살아남는다.
- 값을 쓸 때 즉시 디스크에 쓰지 않고 캐시에 먼저 쓰고 나중에 디스크에 쓸 수 있다. 데이터베이스가 커밋됐다고 알렸는데 실제로는 캐시에만 쓰였고 캐시가 크래시해 디스크에 도달하지 못한 경우에도, 지속성은 다음에 그 데이터베이스에 접근할 때 그 데이터가 디스크에 나타나도록 보장한다. (구현 방법은 이후에 다룬다.)

### ACID와 동시성 제어·회복의 관계
- ACID 성질은 동시성 제어와 회복의 기반이다.
- **일관성(C)과 고립성(I)** → 동시성 제어(concurrency control)에서 다룬다.
- **원자성(A)과 지속성(D)** → 회복 관리(recovery management)에서 다룬다.

## 예시
더티 리드 스케줄 (X = $200, Y = $100에서 시작):

```text
T1: R(X)  X-100  W(X)                                R(Y)  Y+100  W(Y)
T2:                    R(X) X*1.06 W(X)  R(Y) Y*1.06 W(Y)  Commit
```

- 직렬 실행 시 어느 순서든 X + Y = $318.
- 위 인터리브 실행 시 X = $106, Y = $206으로 합계 $312 — $6이 사라진다.

## 요약
- **원자성**: 트랜잭션은 all-or-nothing. 실패 시 undo하거나 나중에 완료한다. 실패는 논리적 오류와 시스템 크래시로 나뉜다.
- **일관성**: 일관된 상태에서 일관된 상태로. 트랜잭션 도중의 일시적 비일관성은 허용된다.
- **고립성**: 동시 트랜잭션이 선형 순서로 실행되는 것처럼 보여야 한다. 위반 시 더티 리드, 반복 불가능 읽기, 팬텀 리드, 미커밋 데이터 덮어쓰기가 발생한다.
- **지속성**: 커밋된 트랜잭션은 이후 장애에도 영구적으로 보존된다.
- C·I는 동시성 제어, A·D는 회복 관리가 담당한다.
