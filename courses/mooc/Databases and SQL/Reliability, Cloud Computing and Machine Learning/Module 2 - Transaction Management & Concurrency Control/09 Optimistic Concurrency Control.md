# Optimistic Concurrency Control

## 개요
- 낙관적 동시성 제어(Optimistic Concurrency Control, OCC)를 다룬다.
- 대부분의 동시성 제어 알고리즘은 비관적(pessimistic)으로, 연산 전에 검증(validate)한다.
- OCC는 충돌이 자주 일어나지 않는다고 낙관적으로 가정하고, 읽기·계산을 먼저 한 뒤 쓰기 직전에만 검증한다.
- 세 가지 규칙(Rule 1, 2, 3)으로 두 번째 트랜잭션 T2가 완료(commit)될 수 있는지 판정한다.

## 내용

### 비관적 vs 낙관적
- 비관적(pessimistic) 알고리즘: 값을 읽기·계산·쓰기 전에 연산을 먼저 검증(validate)한다.
- 낙관적(optimistic) 알고리즘(OCC): "이런 문제(충돌 연산)는 자주 오지 않을 것"이라고 판단하고, 먼저 읽고 계산한 뒤 **쓰기 직전에만** 검증한다.
- OCC 알고리즘은 중앙집중식(central) 데이터베이스 시스템에서만 검토되었으며, 실제 상용·프로토타입 데이터베이스 시스템 중 OCC로 구현된 것은 없다.

### 동작 규칙(Rules of Engagement)
- 데이터에 태그(tag)를 붙이지 않는다.
- 대신 각 트랜잭션이 읽은 데이터 목록과 쓸 데이터 목록을 유지한다.
- 세 가지 규칙으로 두 번째 트랜잭션 T2가 완료될 수 있는지 판정한다.
- 전제: 트랜잭션은 인터리빙(interleave)될 수 있지만, 궁극적으로 새로운 트랜잭션은 첫 번째 트랜잭션이 완료된 후에 변경을 가하는 것처럼 보여야 한다. 겹침(overlap)이 있어도 서로 침범하지 않아야 한다.

### Rule 1 — T2의 읽기가 T1의 쓰기 이후에 발생
- T2의 읽기가 T1의 쓰기(write)가 끝난 후에 일어나면 걱정할 것이 없다.
- T2는 원래 T1이 쓴 값을 읽는 것이 맞기 때문이다(T1으로부터 값을 읽는다면).
- 검증 단계를 무난히 통과한다.

### Rule 2 — 부분적 겹침 (T1의 쓰기와 T2의 읽기가 겹치는 시기)
- T1: 읽기(read) → 계산(compute) → 검증(validate) → 변수 집합 X를 쓰기 시작.
- 그 쓰기 도중 T2가 읽기·계산·검증을 시작한다.
- 판정: T1이 쓴 자원(집합 X)이 T2가 읽은 자원(집합 Y)과 전혀 겹치지 않으면 검증이 참이 되어 T2가 완료된다.
- 자원 X와 자원 Y가 하나라도 겹치면 검증되지 않는다.

### Rule 3 — 상당한 겹침 (T1, T2가 크게 겹치는 시기)
- T1: 필요한 값을 읽고 → 계산·검증 → X를 쓴다.
- T2: T1의 읽기 직후에 읽기를 하고 → 계산·검증 → Z를 쓰려 한다.
- 관련 집합:
  - T2가 읽는 자원 집합 = Y
  - T2가 쓰려는 자원 집합 = C
  - T1이 쓰는 자원 집합 = X
- 판정: T1이 쓴 자원(X)이 T2가 읽는 자원(Y) 또는 T2가 쓰려는 자원(C)과 하나라도 겹치면 **T2를 중단(abort)**한다.
- 어느 것도 겹치지 않으면 T2는 자유롭게 검증되고, 검증에 성공하면 값을 쓴다.

### 평가
- OCC는 어떤 시스템에서도 사용되지 않는다.
- 그러나 잠재적으로 충돌 가능한 트랜잭션을 검증하는 유용한 방법이다.
- 겹침이 아무리 많이 일어나더라도, 새로운 트랜잭션의 충돌 연산은 항상 더 이른(earlier) 트랜잭션의 연산보다 뒤에 실행된다는 개념에 기반한다.

## 요약
- OCC는 비관적 방식과 달리 읽기·계산을 먼저 하고 쓰기 직전에만 검증하는 낙관적 방식이다.
- 데이터에 태그를 붙이지 않고, 트랜잭션이 읽은/쓸 데이터 목록을 유지한다.
- Rule 1: T2 읽기가 T1 쓰기 이후면 문제 없음.
- Rule 2: 부분 겹침 시 T1의 쓰기 집합과 T2의 읽기 집합이 겹치지 않으면 통과.
- Rule 3: 큰 겹침 시 T1의 쓰기 집합이 T2의 읽기·쓰기 집합과 하나라도 겹치면 T2 중단.
- 실제 상용 시스템에서는 쓰이지 않지만, 충돌 가능한 트랜잭션 검증의 유용한 개념적 방법이다.
