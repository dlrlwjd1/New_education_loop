# Analysis and Redo Phases

## 개요

- ARIES 알고리즘의 시스템 크래시 복구(recovery)는 세 단계로 이루어진다: 분석 단계(analysis phase), 재실행 단계(redo phase), 취소 단계(undo phase).
- 이 강의는 앞의 두 단계인 분석 단계와 재실행 단계를 다룬다.
- 분석 단계는 크래시 시점의 더티 페이지 테이블(dirty page table)과 트랜잭션 테이블(transaction table)을 로그로부터 재구성하고, 재실행 단계는 커밋 여부와 무관하게 모든 변경을 데이터베이스에 다시 반영한다.

## 내용

### 세 단계 복구 개요

- 로그(log)를 하나의 선으로 볼 때, 위쪽이 오래된 트랜잭션, 아래로 갈수록 최신 트랜잭션이며, 맨 아래 끝이 크래시 지점이다.
- **분석 단계(1단계)**: 어디서부터 redo를 시작할지, 어떤 레코드를 undo할지를 결정한다.
- **재실행 단계(2단계)**: 커밋된 것과 아직 데이터베이스에 반영되지 않은 것을 다시 적용한다.
- **취소 단계(3단계)**: 커밋되지 않은 트랜잭션을 되돌린다.

### 분석 단계 (analysis phase)

- 가장 최근 체크포인트(checkpoint) 레코드를 조사한다.
- 그 체크포인트 시점의 더티 페이지 테이블과 트랜잭션 테이블을 만들어 메모리에 적재한다.
- 재실행을 어디서 시작할지(redo 시작 지점)와 어떤 트랜잭션을 취소할지를 판정한다.
  - redo는 **가장 이른 더티 페이지가 만들어진 지점**부터 로그를 따라 시작한다.
  - undo는 커밋되지 않은 모든 트랜잭션을 대상으로 한다.
- 마지막 체크포인트 레코드부터 로그를 **앞으로(forward) 스캔**하여 두 테이블을 크래시 시점의 상태로 되돌린다.
  - 새로 더티해진 페이지가 있으면 그 LSN과 함께 더티 페이지 테이블에 추가한다.
  - 트랜잭션이 커밋되었으면 트랜잭션 테이블에서 제거한다.
- 즉, 데이터베이스 정상 운영 중 두 테이블을 만들던 과정을 그대로 재현하는 것이며, 이 과정이 끝나면 두 테이블은 크래시 시점과 동일한 상태가 된다.

### 분석 단계 예제

- 설명을 쉽게 하기 위해 마지막 체크포인트가 운영 시작 지점(빈 상태)이라고 가정한다. (실제 체크포인트는 그 시점의 더티 페이지 테이블·트랜잭션 테이블 정보를 담는다.)
- 로그 항목을 순서대로 분석한다.
  1. 페이지 50을 더티하게 만듦 → 더티 페이지 테이블에 페이지 50(이 레코드를 가리키는 LSN) 추가, 트랜잭션 테이블에 T1 추가.
  2. 페이지 60을 T2가 갱신 → 더티 페이지 테이블에 페이지 60, 트랜잭션 테이블에 T2 추가.
  3. T3가 페이지 70을 갱신 → 트랜잭션 테이블에 T3(세 번째 행을 가리킴), 더티 페이지 테이블에 페이지 70 추가.
  4. T2의 update → 트랜잭션 테이블의 T2 포인터를 네 번째 항목으로 변경. 새 더티 페이지가 없으므로 더티 페이지 테이블은 변화 없음.
  5. commit(T3) → 정상 운영 때와 동일하게 T3를 트랜잭션 테이블에서 제거.
  6. T1의 최신 항목 → 트랜잭션 테이블의 T1 포인터를 마지막 행으로 변경, 페이지 55가 처음 더티해졌으므로 더티 페이지 테이블에 새 항목 추가.
- 이 시점에서 두 테이블은 크래시 시점과 동일한 상태가 되어 redo·undo에 필요한 정보를 모두 갖춘다.

### 재실행 단계 (redo phase)

- 커밋·미커밋 트랜잭션을 **모두**, 처음부터 데이터베이스에 다시 적용한다.
- 더티 페이지 테이블의 모든 포인터 중 **가장 이른 LSN을 가리키는 포인터**부터 시작한다. (예제에서는 로그 첫 행이지만, 실제로는 그 앞에 많은 항목이 있을 수 있다.)
- 가장 오래된 LSN부터 각 redo 가능한 로그 레코드를 데이터베이스에 다시 적용한다.
  - 예: 페이지 50, 오프셋 21, 길이 3을 `ABC` → `DEF`로, 페이지 60, 오프셋 41, 길이 3을 `HIJ` → `KLM`로 변경.
  - 모든 로그 항목을 살펴 실제 데이터베이스 페이지를 크래시 직전 값으로 되돌린다.

### redo를 건너뛰는 경우

- 페이지가 더티 페이지 테이블에 있으나, **실제 페이지에 기록된 LSN이 해당 로그 레코드의 LSN보다 큰** 경우, 즉 그 페이지가 이미 이 로그 레코드 이후 값으로 디스크에 기록된(early push) 경우에는 그 로그 레코드를 무시한다.
- 예제에서는 어떤 더티 페이지도 데이터베이스에 기록되지 않았으므로 모든 로그 레코드를 redo한다.
- 변형 예: 만약 페이지 60이 이미 메모리(디스크)에 기록되어 있고 가장 이른 더티 페이지 값이 더 뒤라면, 그 페이지 60 연산은 건너뛰고 페이지 60이 다시 더티해지는 지점부터 재실행한다.

## 예시

분석 단계로 재구성된 크래시 시점 상태(예제):

- 더티 페이지 테이블: 페이지 50 → LSN 1, 페이지 60 → LSN 2, 페이지 70 → LSN 3, 페이지 55 → LSN 6
- 트랜잭션 테이블: T1 → LSN 6, T2 → LSN 4 (T3는 커밋되어 제거)

재실행 단계 연산 예:

- 페이지 50, 오프셋 21, 길이 3: `ABC` → `DEF`
- 페이지 60, 오프셋 41, 길이 3: `HIJ` → `KLM`

## 요약

- ARIES 복구는 분석 → 재실행 → 취소의 세 단계로 진행된다.
- 분석 단계는 가장 최근 체크포인트부터 로그를 앞으로 스캔해 더티 페이지 테이블과 트랜잭션 테이블을 크래시 시점 상태로 재구성한다.
- 재실행 단계는 더티 페이지 테이블의 가장 이른 LSN부터 시작해, 커밋·미커밋 구분 없이 모든 redo 가능한 로그 레코드를 데이터베이스에 다시 적용한다.
- 페이지에 기록된 LSN이 로그 레코드 LSN보다 크면(이미 디스크에 반영됨) 그 redo는 건너뛴다.
- 다음 단계인 취소 단계에서 미커밋 트랜잭션의 효과를 되돌린다.
