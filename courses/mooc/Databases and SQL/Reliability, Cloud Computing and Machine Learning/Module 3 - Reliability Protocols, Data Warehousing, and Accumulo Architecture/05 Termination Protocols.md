# Termination Protocols

## 개요

- 분산 커밋에서 2단계 커밋(2PC, two-phase commit) 프로토콜의 종료 프로토콜(termination protocol)을 다룬다.
- 종료 프로토콜은 두 상황에서 필요하다: (1) 코디네이터(coordinator)나 참여자(participant)가 타임아웃(timeout)할 때, (2) 사이트가 죽었다가 다시 살아날 때.
- 어떤 조치가 필요한지는 2PC 내부의 어느 상태(state)에 있었는지에 따라 달라진다.
- 2PC는 **블로킹 프로토콜(blocking protocol)** 이라 특정 장애 조합에서 참여자가 무한정 멈출 수 있다는 한계를 갖는다.

## 내용

### 2PC 상태 전이 (state transition)

- **코디네이터**:
  - 초기 상태(initial)에서 모든 참여자에게 commit prepare(커밋 준비) 메시지를 보내고 대기 상태(wait)로 이동.
  - 모든 참여자가 commit에 투표하면 참여자들에게 "커밋하라" 메시지를 보내고 commit 상태로 이동.
  - 한 참여자라도 abort에 투표하면 모두에게 abort 메시지를 보내고 abort 상태로 이동.
- **참여자**:
  - 초기 상태에서 prepare 요청을 받음.
  - 커밋할 수 없으면 abort에 투표하고 곧바로 abort 상태로 이동, 코디네이터에게 통보.
  - 커밋할 수 있으면 ready 상태로 이동해 코디네이터에게 통보하고 최종 결정을 기다림.
  - 코디네이터가 commit을 보내면 commit, abort를 보내면(다른 참여자가 abort 투표) abort 상태로 이동.

### 코디네이터 타임아웃

- **wait 상태 타임아웃**: 최소 한 참여자의 투표를 못 받음. 만장일치(unanimous)가 필요하므로 일방적 커밋 불가. 코디네이터는 항상 abort할 능력이 있으므로 **일방적으로 abort**하고 모든 참여자에게 abort 신호를 보낸다.
- **commit 또는 abort 상태 타임아웃**: 참여자들에게 이미 지시는 내렸으나 완료 여부를 모름. 모든 참여자로부터 응답을 받을 때까지 global commit/abort 메시지를 **반복 전송**한다.

### 참여자 타임아웃

- **초기 상태 타임아웃**: prepare 메시지를 기다리다 코디네이터 장애로 가정. 참여자는 **일방적으로 abort**하고 abort 상태로 이동, 코디네이터에게 통보 → 결국 global abort.
- **ready 상태 타임아웃**: 참여자는 이미 commit에 투표했으나 전체 결정을 모른다. 일방적으로 결정할 수 없어 코디네이터를 기다려야 한다. 최악의 경우 **블로킹(block)** 된다.

### ready 상태 블로킹 해소 — 다른 참여자에게 문의

- 코디네이터로부터 응답이 없는 참여자는 다른 참여자들에게 poll(문의)해 상황을 파악할 수 있다.
- 문의 결과에 따른 해석:
  1. 어떤 참여자가 **abort에 투표**(또는 초기 상태여서 아직 투표 안 함) → 결국 전체가 abort되므로 문의한 참여자도 abort.
  2. 어떤 참여자가 이미 **global abort/commit 상태** → 코디네이터의 전체 결정을 알 수 있으므로 그에 맞춰 abort/commit.
  3. 응답한 참여자가 **모두 ready 상태** → 아무도 서로를 도울 수 없고 모두 코디네이터를 기다리며 블로킹.

### 블로킹 상태와 2PC의 한계

- 위 3번(모두 ready)인 경우, 코디네이터가 확실히 장애이므로 참여자들이 **새 코디네이터를 선출(elect)** 하고 커밋 과정을 재시작한다. 모두 commit에 투표한 상태이므로 새 코디네이터가 global commit을 지시할 수 있다.
- 그러나 **코디네이터와 참여자가 동시에 장애**나면, 그 참여자의 결정과 코디네이터의 전체 결정을 아무도 알 수 없다. 이 경우 2PC는 **블로킹**되며, 누군가 시스템 전체를 리셋해야 한다. 이것이 2PC의 근본적 약점이다.
- 원자성(atomicity)을 보장하면서 동시에 독립성(independence)을 갖는 프로토콜은 설계할 수 없는데, 이는 2PC가 블로킹 프로토콜이기 때문이다. 이 문제는 3단계 커밋(3PC)으로 해결한다.

### 사이트 장애 후 복구 — 코디네이터

- **초기 상태에서 장애**: 아직 아무 메시지도 보내지 않았으므로 재시작 시 트랜잭션을 다시 시작.
- **wait 상태에서 장애**: prepare를 모두가 받았는지 모름. 재시작 시 prepare를 재전송하고 다시 투표를 기다림.
- **commit 또는 abort 상태에서 장애**: 이미 결정을 통보함. 모든 참여자가 ack하면 아무 조치도 하지 않음. 일부가 응답하지 않으면 종료 프로토콜을 시작(commit/abort 타임아웃 때와 동일하게 진행).

### 사이트 장애 후 복구 — 참여자

- **초기 상태에서 장애**: 복구 시 트랜잭션을 일방적으로 abort. 코디네이터는 wait 상태에서 이 abort 메시지를 받고 전체를 abort.
- **ready 상태에서 장애**: 이미 commit에 투표한 상태라 문제적. 복구 시 타임아웃처럼 처리해 종료 프로토콜로 넘김. 코디네이터 메시지를 못 받고 다른 참여자도 장애면 블로킹될 수 있음.
- **abort 또는 commit 상태(종료 상태)에서 장애**: 이미 abort 또는 commit을 수행했으므로 특별한 조치 불필요.

## 요약

- 종료 프로토콜은 2PC에서 타임아웃 또는 사이트 장애가 발생했을 때 상태에 따라 취하는 조치를 정의한다.
- 코디네이터는 wait 상태 타임아웃 시 일방적 abort, commit/abort 상태 타임아웃 시 메시지를 반복 전송한다.
- 참여자는 초기 상태 타임아웃 시 일방적 abort하지만, ready 상태에서는 전체 결정을 몰라 블로킹될 수 있다.
- ready 상태 참여자는 다른 참여자에게 문의해 abort 투표나 global 결정을 발견하면 따라가지만, 모두 ready면 새 코디네이터를 선출한다.
- 코디네이터와 참여자가 동시에 장애나면 2PC는 블로킹되며, 이는 블로킹 프로토콜인 2PC의 근본적 한계로 3PC로 해결한다.
