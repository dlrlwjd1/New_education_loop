# Approaches to Cache Management

## 개요

- 데이터베이스 버퍼 관리자(database buffer manager)가 안정 저장소(stable storage)와 데이터베이스 캐시(database cache) 사이의 페이지 이동을 관리하는 구조를 다룬다.
- 캐시 관리의 두 축인 페이지 스틸(steal)과 페이지 강제 기록(force)의 개념과 트레이드오프를 설명한다.
- 실제 시스템은 성능상의 이유로 steal-no-force 방식을 쓰며, 이 때문에 로그(log) 기반의 undo/redo 복구가 필요해진다.

## 내용

### 캐시 관리 구조

- 메인 메모리에는 로컬 복구 관리자(local recovery manager)와 데이터베이스 버퍼 관리자(database buffer manager)가 있다.
- 버퍼 관리자는 보조 저장소(secondary storage)와 데이터베이스 캐시 사이의 데이터 이동을 담당한다.
- 데이터베이스 캐시는 메인 메모리에 있으므로 **휘발성(volatile)** 이다. 시스템 크래시로 언제든 지워질 수 있다.
- 보조 저장소(디스크)는 **안정 데이터베이스(stable database)** 다. 디스크도 가끔 크래시하지만 메인 메모리보다 훨씬 안정적이다.
- 캐시의 목적은 안정 저장소의 페이지를 캐시로 가져와 애플리케이션이 데이터를 빠르게 읽고 수정하게 하여 성능을 크게 높이는 것이다.

### 페이지 스틸 (steal)

- 로컬 복구 관리자가 새 페이지 P'를 요청했는데 캐시가 가득 차 있으면, 캐시의 기존 페이지를 안정 저장소로 내보내야 새 페이지를 넣을 수 있다.
- 이때 내보내는 페이지가 아직 **커밋되지 않은(uncommitted)** 데이터라면, 커밋되지 않은 데이터가 안정 저장소에 기록되는 문제가 생긴다. 시스템이 크래시하면 안정 저장소에 있어서는 안 될 미커밋 데이터가 남는다.
- 이렇게 미커밋 데이터를 휘발성 메모리(캐시)에서 안정 저장소로 옮기는 방식을 **steal 접근법**(페이지 스틸, no-fix 접근법이라고도 함)이라 한다.
- 이상적으로는 안정 저장소에는 커밋된 데이터만, 캐시에는 미커밋 데이터만 두고 싶다.

### 페이지 강제 기록 (force)

- 트랜잭션이 끝나면(커밋하면) 수정한 데이터를 즉시 보조 저장소로 강제 기록(force)하는 방식을 **force 방식**(flush 접근법)이라 한다.

### no-steal / force가 가장 구현하기 쉽다

- **no-steal + force**: 미커밋 데이터는 절대 안정 저장소로 옮기지 않고, 커밋 시에는 즉시 안정 저장소로 플러시한다.
- 이 경우 캐시에는 미커밋 데이터만, 안정 저장소에는 커밋된 데이터만 존재한다. 시스템이 다운되어도 메인 메모리에서 잃는 것은 미커밋 데이터뿐이고, 안정 저장소에는 커밋된 데이터만 있으므로 매우 유용하다.

### 현실의 문제와 steal-no-force

- 그러나 캐시 공간보다 많은 페이지를 가져와야 하는 경우가 많고, 캐시 전체가 미커밋 트랜잭션 데이터로 가득 찰 수 있다. 성능을 위해서는 결국 미커밋 데이터를 안정 저장소로 **steal** 해야 한다.
- 또한 커밋할 때마다 페이지를 디스크로 강제 기록하면 과도한 디스크 I/O가 발생해 시스템 자원을 많이 쓰고 애플리케이션 응답 시간이 느려진다.
- 따라서 실제로 사용되는 복구 알고리즘은 **steal-no-force** 방식이다. 커밋된 트랜잭션 데이터가 휘발성 메모리에 남아 있을 수 있고, 미커밋 트랜잭션 페이지가 안정 저장소에 있을 수 있다.

### 로그와 복구

- 문제는 시스템이 크래시했을 때다. 이를 위해 로그(log)를 사용하며, **로그 항목은 실제 변경이 이루어지기 전에 먼저 기록되어야 한다**. 변경 후 로그를 쓰기 전에 크래시하면 로그 항목이 없는 변경이 생기기 때문이다.
- 로그를 통해 로컬 복구 관리자는 다음을 수행한다.
  - **Undo**: 중단(aborted)되었거나 미완료(incomplete)된 트랜잭션의 동작을 되돌린다. 안정 저장소에 나가 있는 미커밋 데이터를 마지막 커밋된 데이터로 되돌려 제거한다.
  - **Redo**: 커밋되었지만 안정 저장소에 기록되기 전에 휘발성 메모리에만 있던 데이터의 동작을 다시 수행하여, 커밋된 데이터를 재구성해 안정 저장소로 내보낼 수 있게 한다.
- 이것이 로컬 복구 관리(local recovery management) 동작의 기초가 된다.

## 요약

- 데이터베이스 캐시는 휘발성, 보조 저장소는 안정 저장소다. 캐시는 성능을 위해 존재한다.
- **steal**: 미커밋 데이터를 안정 저장소로 내보내는 것. **force**: 커밋 시 즉시 안정 저장소로 강제 기록하는 것.
- no-steal + force가 가장 구현이 쉽지만, 캐시 공간 부족과 과도한 I/O 때문에 현실적이지 않다.
- 실제 복구 알고리즘은 steal-no-force를 사용하며, 로그를 변경보다 먼저 기록(write-ahead)해 크래시 시 미커밋 데이터는 undo, 커밋 데이터는 redo 한다.
