# Example Transaction

## 개요

- 시간에 따라 진행되는 예제 트랜잭션을 통해 로그(log), 더티 페이지 테이블(dirty page table), 트랜잭션 테이블(transaction table)이 어떻게 갱신되는지 단계별로 따라간다.
- 로그 시퀀스 번호(log sequence number, LSN)의 부여 방식과 각 테이블의 포인터 규칙을 설명한다.
- 크래시 후 복구를 빠르게 하기 위한 체크포인트(checkpoint) 개념을 소개한다.

## 내용

### 로그 시퀀스 번호 (LSN)

- 로그 항목마다 LSN이 순차적으로 부여된다. 예제에서는 첫 항목이 10, 다음이 20, 30, … 이다.
- **단조 증가(monotonically increasing)** 하기만 하면 증분은 무엇이든 상관없다(1, 2, 3, … 또는 10, 20, 30, … 등).

### 예제 트랜잭션 시나리오

시간 순서대로 다음 연산이 일어난다.

1. T1이 페이지 50 갱신
2. T2가 페이지 60 갱신
3. T3가 페이지 70 갱신
4. T2가 페이지 50 갱신 (1번에서 T1이 갱신했던 페이지)
5. T3 커밋
6. T1이 페이지 55 갱신
7. **시스템 크래시**

### 테이블 갱신 규칙

- **로그**: 모든 연산마다 항목을 추가한다. 각 항목은 이전 LSN(previous LSN), 트랜잭션 ID, 타입(update/commit), 페이지 ID, 오프셋과 길이, 변경 전 이미지(before image), 변경 후 이미지(after image)를 담는다.
- **더티 페이지 테이블**: 페이지가 처음 더티(dirty)해진 로그 항목을 가리킨다. 항상 **그 페이지를 처음 더티하게 만든 항목**을 가리킨다.
- **트랜잭션 테이블**: 각 트랜잭션의 **마지막 연산**(가장 최근 로그 항목)을 가리킨다. 커밋되지 않은 트랜잭션만 추적하며, 커밋되면 테이블에서 제거한다.

### 단계별 진행

1. **T1이 페이지 50 갱신**: 로그에 첫 항목 생성 — 이전 LSN 없음, T1, update, 페이지 50, 오프셋 21 길이 3, before `ABC` → after `DEF`. 더티 페이지 테이블에 페이지 50 항목(이 로그 항목을 가리킴), 트랜잭션 테이블에 T1 추가.
2. **T2가 페이지 60 갱신**: 이전 LSN 없음, T2, update, 페이지 60, 오프셋 41 길이 3, before `HIJ` → after `KLM`. 더티 페이지 테이블에 페이지 60, 트랜잭션 테이블에 T2 추가.
3. **T3가 페이지 70 갱신**: 이전 LSN 없음, T3, update, 페이지 70, 오프셋 16 길이 5, before `12345` → after `67890`. 더티 페이지 테이블에 페이지 70, 트랜잭션 테이블에 T3 추가.
4. **T2가 페이지 50 갱신**: T2는 이전 로그 항목이 있으므로, 트랜잭션 테이블에서 T2가 가리키던 값(두 번째 행)을 이 로그 항목의 이전 LSN에 넣고, 트랜잭션 테이블의 T2 포인터를 이 새 항목으로 바꾼다. 오프셋 20 길이 3, before `ZDE` → after `QRS`. (첫 항목에서 위치 21~23을 `DEF`로 바꿨으므로 오프셋 20부터는 어떤 문자 뒤에 `DE`가 이어진 상태였다.) 페이지 50은 이미 더티이므로 더티 페이지 테이블은 변경 없음 — 처음 더티해진 지점만 관심 대상이다.
5. **T3 커밋**: 로그에 commit 항목 추가(T3의 이전 LSN은 세 번째 항목). 커밋되었으므로 **T3를 트랜잭션 테이블에서 제거**한다. 새 더티 페이지 없음.
6. **T1이 페이지 55 갱신**: 오프셋 20 길이 3으로 `TUV` → `WXY`. 페이지 55가 처음 더티해졌으므로 더티 페이지 테이블에 새 항목 추가, 트랜잭션 테이블의 T1 포인터를 이 마지막 항목으로 갱신.
7. **시스템 크래시.**

### 크래시 시점의 상태와 복구 방향

- 더티 페이지 테이블과 트랜잭션 테이블은 **메모리**에, 로그는 **안정 저장소(stable storage)** 에 있다. 크래시 후 남는 것은 로그뿐이다.
- 로그로부터 더티 페이지 테이블과 트랜잭션 테이블을 재구성하고, 데이터베이스를 크래시 직전 상태로 되돌려야 한다.
- T1과 T2는 커밋되지 않았으므로 그 변경이 데이터베이스에 반영되지 않은 상태로 만들어야 한다. 트랜잭션을 중간부터 다시 실행할 수는 없으므로, 이 트랜잭션들은 "커밋된 적 없다"고 보고 데이터베이스에서 그 흔적을 모두 지운다. 일부 레코드가 안정 저장소에 나가 있을 수 있으므로 그것도 제거해야 한다.
- 더티 페이지 테이블에서는 가장 이른 더티 페이지 지점부터 redo 단계(redo phase)로 상태를 재구성하고, 트랜잭션 테이블에서는 미커밋 트랜잭션의 변경을 되돌린다.

### 체크포인트 (checkpoint)

- 더티 페이지 테이블과 트랜잭션 테이블은 시간이 지나면 매우 커질 수 있고, 로그는 계속 증가해 거대해진다. 데이터베이스 시작 시점(수년 전)부터 로그를 재생하고 싶지는 않다.
- 그래서 주기적으로 데이터베이스 상태의 스냅숏을 안정 저장소에 저장하는 **체크포인트**를 수행한다.
  - 로그에 begin checkpoint를 기록한다.
  - 더티 페이지 테이블과 트랜잭션 테이블의 이미지를 로그에 덧붙인다.
  - 체크포인트가 완료되면 end checkpoint를 로그에 기록한다.
- 크래시 시 로그 처음부터가 아니라 가장 최근 체크포인트의 테이블 사본에서 시작해, 그 이후의 로그 항목만 재생하여 테이블을 재구성하면 된다.

## 예시

크래시 직전까지의 로그 상태 요약:

| LSN | 이전 LSN | 트랜잭션 | 타입 | 페이지 | 오프셋/길이 | before | after |
|---|---|---|---|---|---|---|---|
| 1 | — | T1 | update | 50 | 21/3 | ABC | DEF |
| 2 | — | T2 | update | 60 | 41/3 | HIJ | KLM |
| 3 | — | T3 | update | 70 | 16/5 | 12345 | 67890 |
| 4 | LSN 2 | T2 | update | 50 | 20/3 | ZDE | QRS |
| 5 | LSN 3 | T3 | commit | — | — | — | — |
| 6 | LSN 1 | T1 | update | 55 | 20/3 | TUV | WXY |

- 크래시 시점의 더티 페이지 테이블: 페이지 50 → LSN 1, 페이지 60 → LSN 2, 페이지 70 → LSN 3, 페이지 55 → LSN 6
- 크래시 시점의 트랜잭션 테이블: T1 → LSN 6, T2 → LSN 4 (T3는 커밋되어 제거됨)

## 요약

- 모든 연산은 로그에 기록되며, 로그 항목은 이전 LSN·트랜잭션 ID·타입·페이지·before/after 이미지를 담는다.
- 더티 페이지 테이블은 페이지가 **처음** 더티해진 로그 항목을, 트랜잭션 테이블은 각 미커밋 트랜잭션의 **마지막** 로그 항목을 가리킨다.
- 트랜잭션이 커밋되면 트랜잭션 테이블에서 제거된다.
- 크래시 후에는 안정 저장소의 로그만 남으므로, 로그로 두 테이블을 재구성한 뒤 커밋 트랜잭션은 redo, 미커밋 트랜잭션은 undo 한다.
- 체크포인트를 주기적으로 기록해 복구 시 로그 처음부터 재생하지 않아도 되게 한다.
