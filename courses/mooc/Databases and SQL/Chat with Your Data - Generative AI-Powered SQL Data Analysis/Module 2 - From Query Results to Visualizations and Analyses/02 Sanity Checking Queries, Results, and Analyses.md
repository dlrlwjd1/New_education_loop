# Sanity Checking Queries, Results, and Analyses

## 개요
- 생성형 AI로 만든 쿼리/분석 결과를 **어떻게 검증(sanity check)할 것인가**를 다루는 강의.
- 핵심 주장: AI를 쓰면 오히려 사람이 직접 할 때보다 **더 엄격한 검증(rigor)**을 실천할 기회가 생긴다.

## 내용
### 문제의식 — 사람도 원래 실수를 많이 한다
- 회의에서 데이터 분석 결과가 발표되면, 사람들은 보통 그것을 그냥 사실로 받아들인다.
- 하지만 사람이 만든 엑셀 수식 오류로 잘못된 의사결정이 내려진 사례가 무수히 많듯, **데이터베이스 쿼리에서도 동일한 실수가 흔하게 일어난다** (데이터 형태를 잘못 이해, 이상치를 놓침 등).
- 생성형 AI를 쓰면 "환각(hallucination)이 걱정된다"는 반응이 나오는데, 저자는 이를 **"오히려 검증 기준을 높이는 계기"**로 본다 — AI에 대한 의심이 사람들로 하여금 더 꼼꼼히 검증하게 만든다는 것.

### "AI가 스스로를 검증한다"는 것이 왜 유효한가
- 반론: "AI가 자기 실수를 자기가 어떻게 잡아내나?"라는 의문이 들 수 있다.
- 답변: **새 대화를 시작하면 그것은 더 이상 "동일한 나"가 아니다** — 다른 컨텍스트, AI 특유의 무작위성(randomness)이 개입되므로, **여러 개의 다른 대화에서 같은 결과가 나온다면 정확할 가능성이 높다.**

### 실습 1 — 데이터에 대한 "새니티 체크 아이디어" 브레인스토밍
- 프롬프트: "이 데이터가 어떤 데이터베이스에서 왔는지 전혀 모른다고 가정해봐. 오류가 있는지 확인할 수 있는 기본적인 새니티 체크에는 어떤 것들이 있을까?"
- 결과: 데이터에 맞춤화된 다양한 체크 아이디어 제시
  - 날짜 값 검증(누락/형식 오류, 미래 날짜 여부, 월별 공백/중복)
  - 장르(genre) 값의 일관성 확인(예: "sci-fi"와 "Sci-Fi" 표기 불일치 등)
  - 연체 건수(late return count)의 음수/이상치/0값 확인
  - 히스토그램, 추세선, 중복 확인, 합계 검산 등

### 브레인스토밍한 체크를 실제로 실행시키기
- 후속 프롬프트: "이 체크들 중 일부를 실제 데이터에 적용해서 문제가 있는지 봐줘."
- 결과: "날짜 누락/형식 오류 없음, 음수/0 연체 건수 없음, 중복 없음, 장르 표기 일관적, 대여월 범위는 2005년 5~8월로 타당함(다만 기간이 좁음)."
- **놀라운 발견**: `new`라는 값이 장르로 등록되어 있음을 발견 — "new는 전통적인 장르는 아니지만, 데이터 소스가 최신 개봉작을 이렇게 분류했을 수도 있다"는 관찰.
  - 저자 스스로도 "new가 장르일 수 있다는 걸 전혀 생각 못 했다"고 인정 — 이 체크를 안 돌렸으면 놓쳤을 발견.

### 코드 검증도 잊지 말 것
- 실행된 코드(예: `isnull()` 체크)를 직접 열어보고 이해할 수 있다면 검토.
- 이해가 어렵다면 **그 코드를 복사해서 다른 대화에 붙여넣고 "이 코드가 정확히 어떤 체크를 하는지 쉬운 말로 설명해줘"**라고 요청할 수 있다.

### 실습 2 — "쿼리 자체"에 대한 새니티 체크 (완전히 새로운 대화에서)
- 이번엔 데이터베이스 컨텍스트 없이, **새 대화에서 쿼리문 자체만** 주고 진행.
- 프롬프트: "이건 방금 실행한 쿼리야(쿼리문 붙여넣기). 이 쿼리와 결과가 맞는지 확인할 수 있는 서로 연관된 일련의 새니티 체크를 생각해줘."
- 결과: 연체 판정 로직 검증, 엣지 케이스(반납일=대여일+대여기간인 경우), 월 추출 정확성, 영화-장르 매핑, 조인 무결성(join integrity), 장르별 연체 분포 교차 검증, 추세 검증, self-join 검증 등 **매우 다양한 교차 검증 아이디어**를 제시.

### 왜 "AI가 새니티 체크 자체를 잘못 만들 수도 있는데 괜찮은가?" — 오히려 안전장치가 된다
- 만약 AI가 만든 새니티 체크 쿼리 자체가 틀렸다면? → **오히려 우리가 더 주의 깊게 데이터를 들여다보게 만드는 신호**가 된다.
- 원래 쿼리와 새니티 체크 쿼리가 서로 다른 방식으로 작성되었는데, 둘 다 우연히 정확히 같은 방식으로 틀릴 확률은 매우 낮다 — 따라서 **불일치가 발견되면 그 자체가 유용한 경고 신호**가 된다.

### 검증을 자동화하기 — Python 스크립트로 전환
- 후속 프롬프트: "이건 MySQL 9.2.0에서 나온 거야. 원래 쿼리를 실행하고 결과를 받아온 뒤, 새니티 체크 쿼리들을 실행해서 결과가 체크를 통과하는지 판단하는 Python 스크립트를 작성해줘."
- 결과: 필요한 파라미터(호스트, 사용자, 비밀번호 등) 안내와 함께 **전체 자동화 스크립트**를 생성.
- 이렇게 만든 스크립트로 **반복적으로 재검증**하거나, 필요시 스크립트를 다시 생성해 정교화할 수 있다.

### 결론 — AI는 검증의 적이 아니라 아군이다
- "AI를 데이터베이스에 쓰면 검증 수준이 낮아질 것"이라는 우려와 반대로, AI는 **통계적 체크, 쿼리 교차 검증, 자동화 스크립트까지 다양한 형태로 검증 도구를 만들어준다.**
- 이해할 수 있는 체크는 직접 수동으로 적용하고, 자동화가 필요하면 스크립트로 전환해 반복 재검증할 수 있다.

## 예시
```
1) 데이터 새니티 체크 아이디어 요청: "Assume you know nothing about the underlying database this came from.
   What are some basic sanity checks we could do on the data to determine if there are any errors?"

2) 체크 실행 요청: "Apply some of these to the data and see if you spot any issues."

3) 쿼리 자체 검증 (새 대화): "Here's the query I just ran to produce some data [쿼리 붙여넣기].
   Think of a series of interrelated sanity checks that I could run to make sure the query and results are correct."

4) 자동화 요청: "This came from MySQL 9.2.0. Write a Python script that runs the original query,
   gets the result, and then runs the sanity checking queries to determine if the results pass the checks."
```

## 요약
- AI로 생성한 쿼리/분석은 **여러 각도(데이터 자체 체크, 쿼리 로직 체크, 새 대화에서의 교차 검증)에서 새니티 체크**를 받아야 하며, AI는 이런 체크 아이디어를 브레인스토밍하고 직접 실행까지 해줄 수 있다.
- 체크 과정에서 예상치 못한 발견(예: "new"라는 이상한 장르값)이 나올 수 있어, 오히려 **분석의 엄격함(rigor)을 사람이 직접 할 때보다 높일 기회**가 된다.
- 새니티 체크 자체가 틀리더라도 위험하지 않다 — 원래 쿼리와 검증 쿼리가 우연히 같은 방식으로 틀릴 확률은 낮으므로, 불일치 자체가 유용한 경고 신호가 된다.
- 검증 과정은 Python 스크립트로 자동화해 반복 재검증할 수 있다.
