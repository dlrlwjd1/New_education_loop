# Interview: Douglas Crockford - JSON

## 개요
- JSON을 세상에 알린 Douglas Crockford를 인터뷰한 보너스 영상. JSON을 "발명"이 아니라 "발견"했다고 표현하는 그의 관점과, JSON이 표준으로 자리잡기까지의 실제 과정을 다룬다 (자막은 기계번역 기반)

## 내용
### "발명이 아니라 발견"
- Crockford는 2001년에 JSON을 알게 되었다고 말하지만, 자신이 이를 발명했다고 주장하지 않는다 — JavaScript 객체 리터럴 표기법은 이미 자연스럽게 존재했고(1996년 Netscape도 유사한 방식으로 데이터 교환에 JavaScript를 사용), NeXT·Apple의 속성 목록(property list) 같은 표현 방식도 사소한 차이를 빼면 JSON과 사실상 같은 표기법이었다. 그는 이 표기법의 가치를 발견하고 이름을 붙이고 그 이점을 세상에 보여준 사람이라고 자신을 설명한다.
- 그는 자바스크립트에서 태어난 아이디어이지만 특정 언어에 종속될 필요가 없다는 것을 깨닫고, 데이터를 구조화하고 전송하는 방법을 최대한 단순화한 명세로 다듬었다.

### State Software와 AJAX 이전의 시대
- 2001년 Crockford는 State Software를 설립해, 오늘날 AJAX라 불리는 방식(웹 브라우저를 통한 애플리케이션 제공)을 시도했다 — 당시에는 급진적인 아이디어로 받아들여졌다.
- 잠재 고객들에게 JSON 방식을 제안하면 "우리는 이미 XML에 전념했다"는 답을 자주 들었다. 그는 XML이 아니라는 이유로 거부당하는 것을 극복하기 위해, JSON을 ECMA-262(JavaScript 표준)의 부분집합으로서 "표준"으로 만들기로 결정했다 — 산업이나 정부를 설득하려 하지 않고, 그저 json.org라는 한 페이지짜리 웹사이트를 만들어 명세를 선언했을 뿐이라고 회고한다.

### XML 대비 JSON의 실질적 이점
- Crockford가 지적하는 XML의 근본적 한계는, 쿼리를 보내고 XML을 받은 뒤 그 XML을 다시 파싱해서 원하는 데이터 구조로 되돌려야 하는 번거로움이었다 — "왜 애초에 내가 바로 쓸 수 있는 형태로 주지 않는가?"라는 문제의식이 JSON의 핵심 동기였다고 설명한다.
- 핵심은 중괄호가 꺾쇠괄호보다 낫다는 것이 아니라, JSON이 나타내는 데이터 구조가 프로그래밍 언어 내부의 데이터 구조와 정확히 동일하다는 점이다.
- AJAX의 "X"는 원래 XML을 의미했지만, 개발자들이 곧 JSON이 XML보다 훨씬 다루기 쉽고 빠르다는 것을 발견해 실제로는 JSON을 사용하기 시작했다 — JSON이 AJAX를 위해 특별히 설계된 사실상 유일한 대안으로 자리잡았다.

### 버전 없는 설계 철학
- JSON 설계에서 가장 과감했던 결정은 버전 번호를 넣지 않은 것이라고 밝힌다 — 즉 JSON을 수정할 공식적인 메커니즘이 없다. 이는 JSON을 사용한 모든 기존 기능이 영원히 계속 작동한다는 것을 보장하는 장점이 있다.
- 순환 참조(cyclic structure)나 그래프처럼 JSON이 표현하지 못하는 구조가 있다는 한계도 언급하며, 필요하다면 JSON을 확장하는 대신 JSON을 완전히 대체하는 새로운 형식을 만드는 편이 낫다는 견해를 밝힌다 — JSON 자체는 절대 변경하지 않는다는 원칙 때문이다.

## 요약
- Crockford는 JSON을 "발명"이 아니라 이미 존재하던 JavaScript 리터럴 표기법의 가치를 "발견"하고 표준화한 것이라고 설명한다.
- JSON의 핵심 동기는 XML처럼 받은 데이터를 다시 파싱할 필요 없이, 프로그래밍 언어의 데이터 구조를 그대로 주고받는 것이었다.
- JSON은 의도적으로 버전이 없는 불변의 명세로 설계되어, 하위 호환성을 영구히 보장하는 대신 확장이 필요하면 대체 형식을 쓰는 방식을 택했다.
