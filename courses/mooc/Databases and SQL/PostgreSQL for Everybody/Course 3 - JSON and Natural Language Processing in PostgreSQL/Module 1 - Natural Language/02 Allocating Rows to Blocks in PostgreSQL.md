# Allocating Rows to Blocks in PostgreSQL

## 개요
- PostgreSQL이 테이블 데이터를 디스크에 저장할 때 사용하는 고정 크기 블록(block) 구조와, 행(row)이 블록 안에 배치·갱신되는 방식을 설명하는 강의

## 내용
### 왜 고정 길이 블록으로 나누는가
- 스키마(각 열의 타입·길이)는 데이터베이스가 데이터를 얼마나 효율적으로 저장할지 결정하는 "계약"이다. 그런데 텍스트 열처럼 실제 길이가 가변적인 데이터가 있으면, 값이 수정될 때마다 레코드 크기가 늘거나 줄 수 있다.
- 매번 데이터가 바뀔 때마다 파일 전체를 다시 쓰는 것은 매우 비효율적이다(기가바이트 단위 파일은 아무리 빨라도 쓰기에 초 단위 시간이 걸림). 그래서 PostgreSQL은 디스크 파일을 고정 길이 블록(기본 8KB, 8192바이트)으로 나누어 관리한다.
- 고정 크기 블록은 오프셋 계산이 쉬워 압축할 필요가 없고, 블록 단위로 메모리에 읽어들일 수 있다. 블록은 잠금(lock)의 단위이자 캐싱(caching)의 단위로도 자주 쓰인다 — 자주 쓰이는 블록은 메모리에 계속 남아있게 된다.

### 블록 내부 구조와 업데이트
- 블록 안에서 행(row)은 뒤에서 앞으로 채워지고, 각 행의 시작 위치를 가리키는 작은 오프셋(offset, 2~3바이트) 배열이 앞쪽에 쌓인다. 가운데 남는 공간이 여유 공간(free space)이다.
- 열 값을 수정(예: 짧은 이메일 → 긴 이메일)하면, 해당 블록 내에서 데이터를 밀어내고 오프셋을 갱신한 뒤 블록 전체를 다시 디스크에 쓴다 — 파일 전체가 아니라 블록 하나만 다시 쓰면 되므로 비용이 훨씬 낮다.
- 블록은 보통 70% 정도 채워진 상태를 유지해, 약간의 여유 공간으로 수정·삽입에 대응한다.

### 블록 크기 선택의 트레이드오프
- 블록이 너무 작으면 한 행이 한 블록에 다 안 들어가거나 여유 공간이 부족해 조각화(fragmentation)가 심해진다. 블록이 너무 크면 필요 이상으로 많은 데이터를 읽고 캐싱해야 해 메모리를 낭비한다.
- 회전식 하드디스크는 회전 지연(rotational delay) 때문에 8KB처럼 큰 블록이 유리하고, SSD는 회전 지연이 없어 더 작은 블록(예: 4KB)도 효율적일 수 있다. PostgreSQL 기본값 8KB는 일반적으로 적절한 절충안으로 간주된다.

### 인덱스로 이어지는 결론
- 특정 행이 디스크의 정확히 어느 바이트에 있는지는 알 수 없지만, 그 행이 "어느 블록"에 있는지는 알고 싶다. 이 "행 → 블록" 매핑을 제공하는 힌트 집합이 바로 인덱스(index)라는 개념으로 이어진다.

## 요약
- PostgreSQL은 테이블 데이터를 고정 크기(기본 8KB) 블록으로 나누어 관리하며, 블록은 잠금·캐싱의 기본 단위다.
- 블록 안에서 행은 뒤에서부터 채워지고, 수정 시 블록 단위로만 다시 쓰기 때문에 파일 전체 재작성을 피할 수 있다.
- 인덱스는 결국 "이 값을 가진 행이 어느 블록에 있는지" 알려주는 힌트 집합이라는 관점으로 다음 강의(인덱스 구현)로 이어진다.
