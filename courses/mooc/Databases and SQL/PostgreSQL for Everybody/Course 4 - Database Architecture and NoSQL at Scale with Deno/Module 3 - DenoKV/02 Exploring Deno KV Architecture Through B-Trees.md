# Exploring Deno KV Architecture Through B-Trees

## 개요
- Deno KV의 데이터 모델(테이블 없는 계층적 논리 키, JSON 문서)과, 이를 분산 B-트리로 시뮬레이션해 최종적 일관성이 실제로 어떻게 수렴하는지 설명하는 강의

## 내용
### Deno KV의 데이터 모델
- 테이블이 없고, 자바스크립트 배열로 표현되는 계층적 논리 키(logical key)만 존재한다. 자동 증가 정수나 자동 생성 GUID 같은 기본 키 개념이 없다 — 키 생성 방식은 전적으로 애플리케이션의 책임이다.
- `set`/`get`으로 정확한 키를 저장·조회하고, `list`로 키 접두사(prefix) 기준 범위를 스캔할 수 있다(SQL의 SELECT와 유사). 유일한 정렬 순서는 논리 키의 순서다 — Python의 튜플처럼 첫 번째 요소, 그다음 두 번째 요소 순으로 비교된다.
- Deno KV를 "항상 키 순으로 정렬된 딕셔너리"라고 생각하면 이해하기 쉽다.

### B-트리는 이 모든 규칙을 만족한다
- B-트리는 논리 키 기반 인덱스이며, 로그(log) 스케일로 성장하는 조회 시간을 제공해 확장에 적합하다 — SQL에서 익숙하게 써온 그 B-트리와 원리가 같다.
- 고정 크기 블록으로 디스크에 저장되며, 루트 블록에서 범위를 좁혀가며 목표 키에 도달한다.

### 분산 B-트리와 최종적 일관성 시뮬레이션
- Deno KV는 전 세계에 분산된 여러 노드에 걸쳐 있는 하나의 거대한 B-트리 변형으로, 노드 간 저지연 네트워크로 조정된다.
- 시뮬레이션: 3개 노드짜리 분산 B-트리에서 루트 노드는 모든 서버에 복제되고, 하위 블록은 특정 서버의 디스크를 가리키는 포인터로 존재한다. 어떤 서버에서 조회를 시작하든 포인터를 따라가면 원하는 레코드에 도달한다.
- 새 레코드를 삽입(`set`)하면, 삽입이 일어난 서버의 블록이 먼저 갱신되고(필요하면 블록 분할도 발생), 이 변경이 다른 서버들에 전파되는 데 약간의 시간(예: 1/3초)이 걸린다. 그 사이 다른 서버에 조회하면 아직 갱신되지 않은(오래된) 결과를 받을 수 있다 — 이것이 최종적 일관성이 실제로 눈에 보이는 순간이다.
- 시간이 지나면 새 루트 노드가 모든 서버에 복제되고, 오래된 인덱스가 정리되어 이후 모든 조회가 최신 결과로 수렴한다.

### 왜 정수 기본 키가 없는가
- 분산 시스템에서는 여러 노드가 조율 없이 "다음 정수"를 순서대로 배정할 방법이 없다. 대신 시간·무작위성·서버명을 조합한 ULID(사전순 정렬 가능한 고유 식별자)처럼, B-트리에 잘 채워지는 방식으로 설계된 식별자가 이런 환경에 적합하다고 언급한다.

## 요약
- Deno KV는 테이블 없이 계층적 배열 키만 존재하며, `set`/`get`(정확한 키)과 `list`(접두사 범위 스캔)로 조작한다.
- 내부적으로는 분산된 B-트리 변형으로 동작하며, 삽입 직후 잠시(예: 1/3초) 서버 간 불일치가 있다가 결국 모든 서버가 같은 값으로 수렴하는 최종적 일관성을 보인다.
- 분산 환경에서는 순차적 정수 기본 키를 만들 수 없으므로, ULID처럼 정렬 가능한 고유 식별자를 사용하는 것이 적합하다.
