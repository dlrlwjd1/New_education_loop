# Lecture: To SQL or to NoSQL?

## 개요
- "SQL이냐 아니냐"보다 "관계형이냐 아니냐", 그리고 진짜 핵심 질문인 "ACID냐 BASE냐"가 SQL과 NoSQL 데이터베이스를 가르는 진짜 기술적 차이임을 설명하는 강의

## 내용
### 잘못된 질문: "SQL이 나쁜가?"
- SQL은 단지 데이터베이스와 소통하는 문법(구문)일 뿐이며, "SQL이 좋은가 나쁜가"는 핵심 질문이 아니다.
- 더 나은 질문은 "관계형(relational)인가 아닌가"다 — 행과 열이 서로 연결된 구조(관계형)인지, 아니면 문서마다 키-값 쌍이 담긴 텍스트 덩어리 구조(비관계형)인지의 차이다.
- 하지만 가장 근본적인 질문은 ACID냐 BASE냐이며, 이것이 Postgres 같은 전통적 데이터베이스와 MongoDB·Cassandra 같은 신흥 데이터베이스의 진짜 기술적 차이다.

### ACID: 즉각적 일관성
- Atomicity(원자성)·Consistency(일관성)·Isolation(격리성)·Durability(지속성)의 약자. 핵심은 어떤 값이 변경되면, 그 순간 이후 모든 독자(reader)가 동시에 새 값을 보게 된다는 것 — 변경 도중의 중간 상태(예: 10→20 변경 중 42→10→20 사이를 어지럽게 오가는 것)를 외부에 노출하지 않는다.
- 여러 작성자(writer)가 동시에 값을 바꾸려 해도, 데이터베이스가 순서를 정하고(하나씩 처리) 그 결과를 모든 독자에게 일관되게 보여준다 — 트랜잭션이 진행되는 동안 일종의 "장벽"을 세워 외부의 혼란스러운 중간 상태 노출을 막는다.

### BASE: 최종적 일관성(Eventual Consistency)
- BASE 시스템은 데이터를 수천 대의 서버에 복제해 분산시키므로 훨씬 뛰어난 확장성을 제공하지만, 그 대가로 어느 한 순간에는 서버마다 다른 값을 보여줄 수 있다(불일치 상태).
- 시간이 충분히 지나면(수 초~수십 초) 모든 복제본이 결국 같은 최신 값으로 수렴한다 — 이것이 "최종적 일관성"이다. 다만 그 수렴 과정 동안에는 같은 값을 물어봐도 서버에 따라 다른 답이 나올 수 있다.
- 이런 특성은 은행 거래처럼 즉각적 정합성이 중요한 도메인에는 부적합하지만, 조회 위주(read-heavy)이고 값의 일시적 불일치를 감내할 수 있는 대규모 시스템에는 훨씬 유리한 확장성을 제공한다.

### BASE 시스템에서의 실무적 절충
- SERIAL 정수 기본 키 대신, 여러 서버가 서로 통신하지 않고도 고유성을 보장할 수 있는 GUID(무작위 값+타임스탬프 조합)를 기본 키로 사용한다.
- 오래된 데이터를 읽지 않도록 트랜잭션에 의존하는 대신, 애플리케이션 레벨에서 재시도 루프(retry loop)를 만들어 대응한다.
- `INSERT ... ON CONFLICT`(UNIQUE 제약 기반 처리)에 해당하는 장치가 BASE 시스템에는 없다 — 어느 서버가 다른 모든 서버와 즉시 통신할 방법이 없으므로, 같은 레코드가 중복 삽입되었을 때 사후에 복구하는 방식으로 처리해야 한다.
- 정교하게 조정된 인덱스 기반 단일 쿼리 대신, "모든 서버에 물어보고 원치 않는 결과는 버린다"는 방식의 검색·삭제 전략이 자주 쓰인다.

## 요약
- SQL 문법이나 관계형/비관계형 여부보다, ACID(즉각적 일관성) vs BASE(최종적 일관성)가 전통적 데이터베이스와 NoSQL의 진짜 기술적 차이다.
- ACID는 트랜잭션으로 일관성을 보장하지만 확장이 어렵고, BASE는 복제를 통해 확장성은 뛰어나지만 일시적 불일치를 감수해야 한다.
- BASE 시스템에서는 GUID 기본 키, 애플리케이션 레벨 재시도, "모두 조회 후 버리기" 같은 실무적 절충 기법이 필요하다.
