# Scaling Relational Databases

## 개요
- 관계형(ACID) 데이터베이스를 확장하는 전통적 기법들 — 수직 확장, 읽기 전용 복제본, 멀티 마스터, 블롭 분리 저장, 멀티테넌트 "가짜 클라우드" — 을 다루는 강의

## 내용
### 수직 확장(Vertical Scaling)의 한계
- 디스크·RAID 어레이·더 많은 CPU와 메모리를 투입해 데이터베이스 성능을 높이는 전통적인 방법이다. 캐시에 더 많은 데이터를 담을 수 있을수록 ACID 데이터베이스 성능이 좋아지지만, 필요량은 계속 늘어나(8GB→16GB→...→128GB) 결국 한계에 부딪힌다.
- 2010~2011년경 가상화가 대중화되면서, 대용량 메모리·다중 프로세서를 가진 대형 서버를 가상화하기 어려워 오히려 하드웨어를 직접 구매·장기 임대해야 하는 상황도 있었다.
- SSD 도입은 회전 지연이 없고 여러 블록을 한 번에 읽는(scatter-gather) 방식이 가능해 한동안 성능 개선에 크게 기여했지만, 이 역시 무한히 확장되지는 않는다.

### 읽기 전용 복제본(Read Replica)
- SQL 문을 분석해 데이터를 변경하는 것(INSERT, UPDATE, 트랜잭션 시작 등)과 그렇지 않은 것(SELECT 등)을 구분한다. 변경 명령은 마스터(master) 데이터베이스로, 읽기 전용 쿼리는 복제본(replica)으로 라우팅한다.
- 마스터의 트랜잭션 로그(transaction log)를 감시하는 여러 복제 서버가 변경 사항을 따라잡아 자체 사본에 반영한다 — 이는 사실상 ACID 데이터베이스에 BASE 스타일의 최종적 일관성을 일부 도입한 하이브리드 구조다. 네트워크·서버 성능에 따라 복제본은 마스터보다 약간(0.25초 이하 수준) 뒤처질 수 있다.
- 이 구조 덕분에 읽기 작업은 복제본을 원하는 만큼 늘려 확장할 수 있지만, 쓰기(트랜잭션 로그)는 여전히 하나의 병목으로 남는다.

### 멀티 마스터(Multi-Master)의 어려움
- 두 개 이상의 마스터를 두는 방식은 마스터 간 조정(coordination) 비용이 매우 크다 — 한 마스터가 트랜잭션을 처리하는 동안 다른 마스터의 관련 잠금까지 조율해야 하기 때문이다. 강사는 대개 멀티 마스터보다 "하나의 더 큰 마스터"가 더 나은 해법이라고 평가한다.

### 블롭(대용량 파일)의 분리 저장
- 프로필 사진, PDF, 동영상 같은 대용량 이진 데이터(blob)는 데이터베이스에 직접 저장하기보다, 공유 파일 시스템에 두고 데이터베이스에는 파일 경로나 해시(예: SHA-1)만 인덱스로 저장하는 것이 일반적이다.
- 이렇게 하면 동일한 물리 파일을 여러 논리적 레코드가 가리키는 단일 인스턴스 저장(single-instance store)도 가능해진다. 파일 시스템과 관계형 데이터베이스는 백업 방식이 다르므로 독립적으로 백업 전략을 세우는 것이 좋다.

### 멀티테넌트 "가짜 클라우드"
- 클라이언트마다 별도의 단일 인스턴스 관계형 데이터베이스를 두고, 동일한 애플리케이션 코드를 재사용하는 아키텍처 — 예를 들어 고등교육 기관용 이메일 서비스에서 각 대학마다 별도 DB(25만 명 이하 규모)를 운영하는 방식이다.
- 겉으로는 "클라우드 서비스"처럼 보이지만 실제로는 각 데이터베이스가 독립적으로 확장 가능한 작은 규모(수십만 단위)에 머무르므로, 진짜 "클라우드 스케일(수백만~수십억 사용자)" 애플리케이션과는 다르다 — 강사는 이를 "가상 클라우드(virtual cloud)"라 부르며 2002년 무렵의 데이터베이스 현황으로 설명한다.

## 요약
- 관계형 데이터베이스는 수직 확장(하드웨어 투입) → 읽기 전용 복제본 → (드물게) 멀티 마스터 순으로 확장 전략을 발전시켜 왔다.
- 읽기 전용 복제본은 ACID 데이터베이스에 BASE 스타일의 최종적 일관성을 일부 도입해 읽기 확장성을 얻는 하이브리드 구조다.
- 대용량 파일은 데이터베이스가 아닌 파일 시스템에 분리 저장하는 것이 실무적으로 유리하며, 멀티테넌트 "가짜 클라우드"는 진짜 클라우드 스케일과는 다른 아키텍처다.
