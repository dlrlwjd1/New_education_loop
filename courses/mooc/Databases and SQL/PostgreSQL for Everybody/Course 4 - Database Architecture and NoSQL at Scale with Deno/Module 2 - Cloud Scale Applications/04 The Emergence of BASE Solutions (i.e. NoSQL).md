# The Emergence of BASE Solutions (i.e. NoSQL)

## 개요
- BASE 스타일 데이터베이스의 기술적 특징(스키마 온 리드, JSON 친화성)과 CouchDB·MongoDB·Cassandra·Elasticsearch 등 주요 NoSQL 제품의 등장 배경, 그리고 실제 도입 실패 사례를 다루는 강의

## 내용
### BASE 데이터베이스의 기술적 특징
- 빠른 네트워크, 광범위한 배포, 중앙 잠금 없음, 메모리는 적지만 CPU와 디스크가 많은 환경을 전제로 설계된다. 데이터는 행-열이 아니라 문서(키-값 쌍) 형태로 저장되고, 인덱스는 "사물의 위치를 찾는" 역할에 집중한다.
- 스키마리스(schema-less)처럼 보이지만 실제로는 "스키마 온 리드(schema-on-read)"에 가깝다 — 데이터를 쓸 때는 자유롭게 키-값을 추가하고, 읽을 때 애플리케이션이 예상되는 키를 찾아 해석한다. ACID 데이터베이스의 "스키마 온 라이트(schema-on-write, 사전에 엄격히 정의)"와 대비된다.
- JSON은 이 시기 부상한 핵심 포맷이다 — 키-값 구조를 표현하기 쉽고, 모든 언어에 빠른 파서가 있으며, 압축·저장 효율 면에서도 유리하다는 점이 강조된다.

### 주요 NoSQL 제품들
- **CouchDB** : 신뢰할 수 없는 상용 하드웨어 클러스터를 전제로 설계.
- **MongoDB** : JSON 저장소 + Node.js(자바스크립트) 생태계와 함께 확산되며 AJAX·마이크로서비스 흐름에 크게 기여.
- **Cassandra** : Facebook 엔지니어들이 Facebook을 만든 노하우를 바탕으로 오픈소스화(Apache Hadoop과 유사한 계보).
- **Elasticsearch** : Google 검색을 재현하려는 시도에서 출발했으며, 강력한 역방향 인덱스 기반 검색 기능으로 유명해지면서 이후 NoSQL 문서 저장소로도 활용됨.
- **DynamoDB(Amazon)**, **BigTable(Google)**, **Azure(Microsoft)** : 클라우드 서비스형 NoSQL. 강사는 DynamoDB/BigTable을 직접 사용해봤지만 성능 특성이 "마법 같아" 분석하기 어려웠다고 개인적 평가를 밝힌다. 자체 인력을 고용해 MongoDB/Cassandra 클러스터를 운영하는 것보다, 관리형 서비스(DynamoDB 등)에 대역폭 비용을 지불하는 편이 경제적으로 더 유리할 수 있다는 점도 짚는다.

### 실제 실패 사례: BareSite
- 표절 검사 서비스(약 100TB 규모)를 만들던 스타트업이 MySQL 개념증명 후 Cassandra로 전환했지만, 규모가 커지자 성능 문제가 발생했고 전문가를 고용해도 해결되지 않았다.
- 결국 Cassandra 인프라를 모두 버리고 Amazon DynamoDB로 전환한 뒤 문제가 해결되었다 — 다만 이는 "마법"이 아니라 DynamoDB의 동작 방식을 이해하고 그에 맞게 설계했기 때문이라고 짚는다. NoSQL이라는 이유만으로 무한히 확장되는 것은 아니라는 교훈을 남긴 사례다.
- 2012년 Gartner Hype Cycle 기준 NoSQL은 "기대의 정점" 단계에 있었고, 2016년경에는 "NoSQL"이라는 용어 자체가 의미를 잃었다고 언급한다 — 대신 "BASE 스타일(최종적 일관성) 데이터베이스"라는 더 정확한 개념으로 자리잡았다.

## 요약
- BASE 데이터베이스는 스키마 온 리드 방식과 JSON 친화적 저장을 특징으로 하며, CouchDB·MongoDB·Cassandra·Elasticsearch 등이 이 시기 등장했다.
- 관리형 NoSQL 서비스(DynamoDB 등)는 자체 클러스터 운영보다 경제적일 수 있지만, "마법"이 아니라 그 동작 방식을 이해해야 제대로 활용할 수 있다.
- NoSQL은 무조건 확장되는 만능 해법이 아니며, 2016년 이후에는 "NoSQL"보다 "BASE 스타일(최종적 일관성)"이라는 더 정확한 개념으로 이해되고 있다.
