# First Generation Cloud Applications 2/2

## 개요
- Google의 검색·컨테이너 인프라·Gmail 복제 전략, 그리고 Amazon Web Services가 상용 하드웨어 위에서 클라우드 경제를 만든 배경("카펫 클러스터")을 다루는 강의

## 내용
### Google 검색: 지연시간보다 병렬성
- 검색 결과가 1/4초 걸려도 "지능적으로 보이는" 체감에는 문제가 없었다 — 이는 최종적 일관성이라기보다는 분산 컴퓨팅의 수집/분산(scatter-gather) 개념에 가깝다. 비용이 들더라도 지연시간을 견딜 수 있다면 이 방식이 문제를 해결하는 유일한 길이었다.
- 각 검색 요청은 리소스의 극히 일부만 짧게 사용하므로, 수천 개의 요청을 동시에 처리할 수 있었다. 웹이 커지면 서버를 늘리기만 하면 되는 뛰어난 확장성을 지녔다.

### Google 컨테이너와 Gmail의 복제 전략
- Google의 데이터센터 컨테이너는 화려한 장식 없이 컴퓨터·디스크·전원공급장치·소형 배터리만 채운 실용적 설계였다 — 에너지 낭비를 최소화하는 방향으로 설계되었다.
- Gmail은 별도의 "백업"이 아니라 데이터를 랙·컨테이너·데이터센터에 걸쳐 7~10곳에 복제하는 방식으로 내구성을 확보했다 — 전체 데이터센터를 잃어도 Gmail 데이터는 잃지 않도록 설계되었다. 디스크 드라이브의 앞부분은 고성능 작업에, 나머지는 백업 사본 저장에 활용하는 방식도 언급된다.
- 메시지 갱신 시 일부 복제본이 몇 초간 최신 상태가 아닐 수 있지만(최종적 일관성), 이는 Gmail의 사용 패턴에서는 감내할 만한 수준이었다.
- Matt Cutts의 설명에서는 PageRank 알고리즘이 애초에 분산 환경에서 수렴(converge)하도록 설계되었다는 점이 강조된다 — 새 페이지가 등장하면 잠시 흔들렸다가 다시 계산되어 안정된다.

### Amazon과 "카펫 클러스터(carpet cluster)"
- Amazon은 책 판매업에서 출발했지만 주문 시스템 확장을 위해 자체 분산 데이터베이스(DynamoDB의 전신)를 구축했고, 이후 AWS(Amazon Web Services)를 통해 상용 하드웨어 위의 가상화 임대 서비스를 제공하기 시작했다.
- 당시 하드웨어 경제성: CPU와 디스크 용량은 저렴했지만 디스크 속도와 메모리는 비쌌다. AWS의 초기 인스턴스들은 이런 저가 요소(CPU, 디스크 용량)를 최대한 활용하도록 설계되었다.
- "카펫 클러스터"는 저렴한 상용 하드웨어를 대량으로 깔아두고, 데이터를 분산·복제하며 광범위하게 질의를 보내는(MapReduce 등) 방식의 은유다 — Teradata 같은 상용 분산 DB나, 내부적으로 다수의 SQLite 인스턴스를 두고 애플리케이션 레이어에서 멀티 리더/라이터처럼 보이게 만드는 샤딩 구조도 이 범주에 속한다.

## 요약
- Google 검색은 지연시간을 감내하는 대신 대규모 병렬(수집/분산)로 문제를 해결했고, Gmail은 여러 곳에 데이터를 복제해 내구성과 최종적 일관성을 확보했다.
- Amazon은 저렴한 상용 하드웨어(CPU·디스크 용량 위주) 위에 가상화를 얹어 AWS라는 클라우드 경제를 만들었다.
- "카펫 클러스터"는 저비용 상용 하드웨어를 대량으로 활용해 분산·복제·병렬 질의로 확장하는 이 시대의 아키텍처를 요약하는 개념이다.
