# Second Generation Cloud Applications

## 개요
- Facebook·Twitter처럼 사용자 간 연결(친구 관계)이 핵심인 2세대 클라우드 애플리케이션이, 1세대(Gmail·Google 검색)보다 훨씬 어려운 이유와 그로 인한 최종적 일관성의 실제 적용 방식을 다루는 강의

## 내용
### 1세대와 2세대의 차이: 독립된 사일로 vs 상호 연결된 그래프
- Gmail은 사용자마다 독립된 "작은 데이터 사일로"였지만, Facebook은 친구 관계·상태 업데이트·좋아요처럼 여러 사용자 데이터가 서로 얽혀 있다 — 로그인 시 자신의 데이터만 보는 것이 아니라 여러 친구의 데이터를 동시에 참조해야 한다.
- 프라이버시 규칙까지 겹치면 복잡도가 크게 증가한다 — 검색도 전체 인덱스 하나가 아니라 "각 사용자 관점에서의 세계"를 반영해야 한다.

### 샤딩과 "가장자리로 데이터 밀어넣기(push to the edge)"
- 사용자를 이름 기준(A-F, G-M 등)으로 여러 서버(샤드)에 배정하는 예시로 문제를 설명한다 — 한 사용자가 친구의 게시물에 "좋아요"를 누르면, 그 친구가 속한 서버로 데이터를 전달해야 하는데, 어떤 친구에게 전달해야 할지·프라이버시 차단 여부까지 고려해야 하는 복잡한 문제가 발생한다.
- 강사가 관여한 엔지니어링 기법으로 "가장자리로 밀어넣기(push to the edge)"를 언급한다 — 각 사용자가 로그인할 때 다른 서버들과 통신할 필요 없이 자신의 타임라인/알림을 바로 볼 수 있도록, 데이터를 미리 관련 서버들로 복제·전달해두는 방식이다. 10개 서버로 미리 전달해두는 비용이, 매번 로그인 시 10개 서버와 통신하는 것보다 저렴하기 때문이다.
- 이 방식은 필연적으로 최종적 일관성을 요구한다 — "좋아요"가 모든 관련자에게 반영되는 데 5~10분이 걸릴 수 있다. 친구 요청의 2단계 승인(요청 → 수락) 같은 패턴도 이런 지연을 감안한 설계다.

### xkcd 만화로 본 엔지니어의 함정
- "20분 걸려도 임의로 조미료를 건네주는 시스템을 만들고 있다"는 xkcd 만화를 인용하며, 엔지니어가 특정 문제(예: Facebook의 친구 목록 문제)를 해결한 뒤 "다른 문제에도 이 해법을 일반화할 수 있지 않을까"라는 생각으로 새로운 유형의 데이터베이스를 만들어내는 패턴을 지적한다 — 이것이 NoSQL 데이터베이스 등장의 한 배경이라고 설명한다.

## 요약
- 2세대 클라우드 애플리케이션(Facebook 등)은 사용자 간 데이터가 서로 얽혀 있어 1세대(독립된 사일로)보다 훨씬 어렵다.
- "가장자리로 밀어넣기" 전략으로 관련 데이터를 미리 여러 서버에 복제해두면 로그인 시 통신 비용을 줄일 수 있지만, 그 대가로 최종적 일관성(수 분의 지연)을 감수해야 한다.
- 특정 회사의 특정 문제 해결책을 일반화하려는 시도가 NoSQL 데이터베이스 붐의 한 배경이 되었다.
