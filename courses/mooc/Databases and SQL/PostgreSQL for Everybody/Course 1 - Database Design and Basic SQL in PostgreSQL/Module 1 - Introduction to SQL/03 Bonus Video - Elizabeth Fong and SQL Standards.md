# Bonus Video: Elizabeth Fong and SQL Standards

## 개요
- SQL 표준화 작업에 실제로 참여했던 Elizabeth Fong을 인터뷰한 보너스 영상으로, 표준화 과정에서 겪은 실무적 이슈들을 다룬다

## 내용
### 표준화가 필요했던 이유
- 당시에는 데이터를 계층형(트리 구조, 예: IBM IMS), 네트워크형, 플랫 파일(flat file) 중 어떤 구조로 저장할지에 대한 논쟁이 있었고, 데이터에 자체 설명 태그(현재의 메타데이터·스키마 개념)를 둘지 여부도 논쟁 대상이었다.
- 데이터베이스 시스템 연구 그룹(Database System Study Group)은 "데이터베이스 관리 시스템이라면 최소한 데이터 저장·검색·수정·구성·삭제가 가능해야 한다"는 참조 모델을 제시했다.
- 이후 ANSI(현재 INCITS) 산하 X3H2 그룹(Don Deutsch, Len Gallagher 등 참여)이 데이터 관리 언어 표준화를 담당했다.

### 표준화의 원칙: "기능이 아니라 언어"를 표준화
- 전구(light bulb)에 비유하면, 색깔(빨간색·흰색)은 표준화할 필요가 없지만 소켓 규격처럼 "서로 대화하기 위한 인터페이스"는 표준화해야 한다.
- 즉 소프트웨어 시스템에서 표준화 대상은 내부 기능 구현이 아니라 통신에 쓰이는 공통 언어(SQL)였다.
- 당시 IBM의 Chris Date가 정규화(normalization)와 플랫 파일(그가 "테이블"이라 부른)을 논의했고, 여기서 "SELECT 컬럼 FROM 테이블" 같은 단순 쿼리 언어의 개념이 나왔다.

### 표준 준수(conformance)와 시장의 요구
- 표준화 이후 중요한 것은 테스트: 제품이 ISO 표준(혹은 JTC 1의 해당 버전)을 준수하는지 검증해야 한다. 그렇지 않으면 학생 성적 관리 시스템 같은 애플리케이션이 Oracle, Sybase, Microsoft SQL 등 서로 다른 벤더 제품 위에서 제대로 동작하지 않을 수 있다.
- 이런 요구는 벤더가 아니라 실제 사용자(구매자) 쪽에서 나왔다 — 조달 과정에서 "SQL 표준 준수"를 요구했고, 이를 검증하는 적합성 테스트 인증서와 NVLAP(공인 시험기관) 인증 제품 목록이 활용되었다.
- 표준화 타이밍의 중요성도 언급된다: 너무 이르면 혁신적인 아이디어를 배제하게 되고, 너무 늦으면 이미 서로 다른 구현이 난립해 기회를 놓친다. SQL은 적절한 타이밍에 표준화된 성공 사례로 꼽힌다.

## 요약
- SQL 표준화는 데이터베이스의 내부 구현이 아니라 "서로 대화하는 방식(언어)"을 통일하기 위한 작업이었다.
- 표준 제정에는 참조 모델 제시 → 언어 설계(ANSI X3H2) → 적합성 테스트/인증이라는 절차가 있었다.
- 표준화 타이밍이 너무 이르면 혁신을 저해하고, 너무 늦으면 파편화를 막지 못한다는 교훈을 준다.
