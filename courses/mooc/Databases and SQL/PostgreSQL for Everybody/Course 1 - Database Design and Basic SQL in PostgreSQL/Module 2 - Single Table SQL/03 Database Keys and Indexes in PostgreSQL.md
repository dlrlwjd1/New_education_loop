# Database Keys and Indexes in PostgreSQL

## 개요
- 테이블 간 관계를 만드는 데 필요한 키(key) 개념과, 대량의 데이터를 빠르게 조회할 수 있게 해주는 인덱스(B-트리, 해시)의 원리를 다루는 강의

## 내용
### 기본 키(Primary Key)와 SERIAL
- 각 행을 효율적으로 참조하려면 행마다 고유한 "손잡이" 역할을 하는 열이 필요하다. PostgreSQL은 `SERIAL` 타입으로 이를 간단히 처리한다 — 삽입할 때마다 자동으로 증가하는 정수 값이 부여되며, 여러 소스에서 동시에 데이터가 들어와도 데이터베이스가 알아서 순서대로 잠금(lock)·증가·삽입을 처리해 중복이 생기지 않는다.
- `PRIMARY KEY`로 지정하면 해당 열에 대한 인덱스가 자동으로 생성된다 — 정수 인덱스는 매우 빠르게 조회할 수 있다. `PRIMARY KEY`라는 선언 자체는 "이 열을 특별하게 취급해 인덱스를 구축해달라"는 신호일 뿐, 구현 방법은 데이터베이스가 알아서 결정한다.

### 고유 제약(UNIQUE)과 논리적 키(logical key)
- `UNIQUE` 제약은 특정 열(예: 이메일)에 같은 값이 두 번 들어가는 것을 막는다. 이런 열을 "논리적 키"라고 부른다.
- UNIQUE 제약도 내부적으로 인덱스를 만들어, 중복 여부 확인과 조회·정렬·접두사 검색 성능을 함께 높여준다.

### 인덱스의 필요성
- 테라바이트 규모 데이터를 매번 순차적으로 전부 스캔하면 아무리 빠른 디스크라도 시간이 오래 걸린다. 인덱스는 데이터 전체를 훑지 않고 정확한 위치로 "지름길"로 이동할 수 있게 해주는 구조다.

### B-트리(B-tree) 인덱스
- B(Balanced/Binary)-트리는 인덱스 블록을 계층적으로 두어, 범위를 좁혀가며 필요한 데이터 블록까지 로그(log) 단위의 접근만으로 도달하게 한다 — 백만 개의 레코드를 스캔하는 대신 로그 스케일(예: 6번 정도)의 블록만 읽으면 된다.
- B-트리는 정확 일치 조회, 정렬(ORDER BY), 범위 검색, 접두사 검색 모두에 유용하다.

### 해시(Hash) 인덱스
- 해시는 문자열/값을 계산(예: 문자를 숫자로 변환해 더한 뒤 나머지 연산)해 위치를 바로 찾아내는 방식으로, B-트리보다도 더 빠르게 동작할 수 있다. MD5, SHA1, SHA256 같은 해시 알고리즘이 이 원리를 정교화한 것이다.
- 단점은 정확히 일치하는 값만 찾을 수 있고, 정렬이나 범위·접두사 검색에는 쓸 수 없다는 것 — 기본 키나 GUID 조회처럼 정확 일치 검색에 특히 유용하다.
- 어떤 인덱스(B-트리 vs 해시)를 사용할지는 대체로 데이터베이스가 열의 제약 조건(PRIMARY KEY, UNIQUE 등)을 보고 자동으로 결정하므로, 사용자가 직접 선택할 필요는 거의 없다.

## 예시
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,       -- 자동 증가 정수 기본 키 (인덱스 자동 생성)
    email VARCHAR(128) UNIQUE,   -- 논리적 키: 중복 이메일 방지 (인덱스 자동 생성)
    name VARCHAR(128)
);
```

## 요약
- `SERIAL` + `PRIMARY KEY`로 자동 증가하는 정수 기본 키를 만들면 데이터베이스가 인덱스를 자동 구성해준다.
- `UNIQUE` 제약은 논리적 키(예: 이메일 중복 방지)를 강제하며 역시 내부적으로 인덱스를 활용한다.
- B-트리 인덱스는 정렬·범위·접두사 검색에 강하고, 해시 인덱스는 정확 일치 검색에서 더 빠르다 — 어떤 인덱스를 쓸지는 대부분 데이터베이스가 자동으로 판단한다.
