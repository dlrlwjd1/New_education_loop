# Relational Database Design Part 2

## 개요
- 음악 라이브러리 예제를 통해 열(column)을 "기존 개체(entity)의 속성"과 "새로운 개체"로 분류해가며 실제로 트랙(track)·앨범(album)·아티스트(artist)·장르(genre) 4개 테이블로 나누는 실습 강의

## 내용
### 첫 번째 개체(entity) 정하기
- 다중 사용자 시스템에서는 보통 "사용자(user)"가 중심 테이블이 되지만, 이 음악 라이브러리는 단일 사용자 앱이므로 다른 기준이 필요하다.
- 앱이 다루는 가장 근본적인 단위가 무엇인지 자문한다 — 이 음악 앱에서는 "트랙(track)"이 그 답이다.

### 열을 속성 vs 새 개체로 분류하기
- 숫자 값(재생 횟수 count, 길이 length, 평점 rating)은 수직 복제 걱정이 없으므로 그대로 트랙 테이블의 속성(column)으로 둔다.
- 문자열 값 중 "앨범"은 한 아티스트가 여러 앨범을 낼 수 있으므로 별도 테이블이 필요하다: 트랙은 앨범에 속하고(belongs to), 앨범은 아티스트가 소유(belongs to)한다.
- "장르(genre)"는 트랙·앨범·아티스트 중 어디에 연결할지가 설계 선택의 문제다 — 트랙에 연결하면 트랙 하나만 바뀌어도 다른 트랙에 영향이 없고, 앨범이나 아티스트에 연결하면 그 앨범/아티스트에 속한 모든 트랙이 한꺼번에 바뀐다. 이 강좌에서는 장르를 트랙에 연결하기로 결정한다.

### 최종 데이터 모델
- 트랙(track) : 제목(title), 길이(length), 개수(count), 평점(rating)을 속성으로 가지며, 앨범과 장르를 각각 가리킨다.
- 트랙은 앨범(album)에 속하고(다대일, many-to-one), 앨범은 아티스트(artist)에 속한다(다대일).
- 이 모델은 완벽한 음악 데이터 모델은 아니며(예: 한 아티스트가 항상 그룹이 아닐 수 있다는 점 등은 단순화되어 있음), 학습을 위한 단순화된 예시임을 강조한다.

## 예시
- 최종 데이터 모델 관계도(개념적):
  - `track` → (다대일) → `album` → (다대일) → `artist`
  - `track` → (다대일) → `genre`
- 각 화살표는 다음 강의에서 실제 외래 키(foreign key) 열로 구현된다.

## 요약
- 숫자 속성은 그대로 테이블 열로 두고, 반복될 수 있는 문자열은 별도 테이블로 분리한다.
- 이 강의의 최종 모델은 track(제목·길이·개수·평점) → album → artist로 이어지는 다대일 관계와, track → genre의 다대일 관계로 구성된다.
- 어떤 속성을 어느 테이블에 연결할지는 "그 값이 바뀔 때 무엇이 함께 바뀌어야 하는가"를 기준으로 판단한다.
