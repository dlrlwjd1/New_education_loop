# Character Sets

## 개요
- ASCII부터 라틴-1, 유니코드, UTF-8까지 문자 인코딩(character encoding)의 역사와 원리를 다루는 강의

## 내용
### ASCII와 초창기 문자 집합
- 초창기 컴퓨터는 메모리가 비쌌기 때문에 문자당 8비트도 아닌 6비트로 대문자만 표현했다. 이후 표준화된 ASCII(128자, 7비트 유효)가 IBM의 EBCDIC보다 더 널리 채택되어 사실상 표준이 되었다.
- ASCII 표에서 각 문자는 고유한 숫자에 매핑된다(예: 대문자 H=72, 소문자 e=101, `*`=42). `chr()`(숫자→문자), `ascii()`(문자→숫자) 같은 함수로 이 매핑을 오갈 수 있다.
- 정렬(sort) 시 ASCII 기준으로 대문자가 소문자보다 사전순으로 앞선다는 점, `>=` 같은 연산자 기호가 ASCII에 없는 문자(예: ≥) 대신 두 글자 조합으로 대체된 이유도 ASCII의 한계에서 비롯되었다고 설명한다.

### 127자를 넘어서는 확장과 파편화 문제
- 8비트(1바이트)로는 최대 256자까지 담을 수 있어, 라틴-1(Latin-1)처럼 128번 이후에 유럽어 특수문자(움라우트 등)를 채운 확장 문자 집합들이 등장했다.
- 문제는 이 128번 이후의 영역이 문자 집합마다 서로 다르게 정의되어(Windows-1252, 키릴 문자 집합 등), 파일 자체에는 "이 파일이 어떤 문자 집합인지" 알려주는 정보가 없어 다른 지역으로 파일을 보내면 문자가 깨지는 문제가 생겼다는 점이다.

### 유니코드(Unicode)의 등장
- 유니코드는 전 세계 모든 문자 집합(약 150개 문자 집합, 13만 자 이상, 역사적 문자 포함)을 하나의 거대한 코드 공간(최대 21비트, 약 20억 이상 표현 가능하지만 UTF-16과의 호환을 위해 21비트로 제한)에 담아 각 문자에 고유 번호를 부여하는 방식이다. 예: 72=H, 231=세딜라가 붙은 문자, 20013=특정 한자.
- 유니코드는 시간이 지나며 계속 버전이 올라가지만(예: 12.1), 기존 문자 할당을 깨지 않는 방식으로 확장된다.

### UTF-8: 유니코드의 압축 전송 형식
- 모든 문자를 32비트로 저장하면 텍스트 용량이 크게 늘어나므로, UTF-8은 문자마다 1~4바이트의 가변 길이로 유니코드를 표현하는 인코딩(encoding)이다.
- 0~127(ASCII 범위)은 그대로 1바이트로 저장되어, 기존 ASCII 파일은 그대로 유효한 UTF-8 파일이 된다는 것이 핵심 장점이다. 이후 바이트에는 "이어지는 바이트"임을 나타내는 비트 패턴이 있어, 이 패턴으로 어떤 파일이 UTF-8인지 아닌지 알고리즘적으로 판별할 수 있다.
- `char_length`, `bit_length`, `octet_length` 함수로 문자 수, 비트 길이, 바이트(옥텟) 길이를 각각 확인할 수 있다 — 한자처럼 3바이트 문자가 섞이면 문자 수와 바이트 수가 달라진다.
- 2004년 약 60%였던 UTF-8 웹페이지 비율이 2012년 이후 90%를 넘어서며, 오늘날에는 사실상 UTF-8이 기본 표준으로 자리잡았다. 레거시 문자 집합으로 남아있는 데이터는 UTF-8로 변환하는 것이 권장된다.

## 예시
```sql
SELECT ascii('H');    -- 72
SELECT chr(72);       -- 'H'
SELECT chr(20013);    -- 한자 문자

SELECT char_length('学ABC'), bit_length('学ABC'), octet_length('学ABC');
```

## 요약
- ASCII(127자, 1바이트) → 확장 문자 집합(라틴-1 등, 파편화 문제) → 유니코드(전 세계 문자를 하나의 코드 공간에 통합)로 발전해왔다.
- UTF-8은 유니코드를 1~4바이트 가변 길이로 압축 인코딩하며, ASCII와 완전히 호환되어 오늘날 사실상의 표준이 되었다.
- `char_length`/`bit_length`/`octet_length`로 문자 수와 실제 저장 바이트 수의 차이를 확인할 수 있다.
