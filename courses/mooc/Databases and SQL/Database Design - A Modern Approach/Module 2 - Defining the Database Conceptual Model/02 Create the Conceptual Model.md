# Create the Conceptual Model (개념 모델 만들기)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 2: Defining the Database Conceptual Model · 토픽 2A

## 개요
- DB를 한 번에 설계하지 않고 **여러 번의 연속적 패스(successive passes)**로 일반 → 구체화하는 접근에서, 가장 일반적인 첫 단계인 **개념 모델(conceptual model)**에 포함할 개념을 선택한다.

## 내용

### 엔티티 식별 (entity identification)
- 개념 모델 = 스키마의 **초안(rough draft)**으로, DB가 표현할 **엔티티 타입**(사람·제품·이벤트·장소 등 = 개념)을 보여준다. 관계형 DB에서 **테이블**로 구현됨.
- **주요(primary) 엔티티**부터 식별(예: 서점 매출 DB의 `Products`, `Sales`). 이후 패스에서 **보조(secondary) 엔티티** 추가(예: `Customers`, `Employees/Personnel`).
- **모든 데이터가 엔티티는 아니다** — 이미 식별한 엔티티의 **속성(attribute)**인지 확인. 예: 거래 날짜는 별도 엔티티가 아니라 `Sales` 테이블의 열.

### 데이터 독립성 (data independence)
- DB는 즉각적 목적(특정 리포트)뿐 아니라 시간이 지나며 진화하는 목적도 지원해야 한다. 출력(리포트)·용도(뷰·폼)는 바뀌기 쉽다.
- 따라서 **원하는 출력(매출 리포트·인보이스)이 아니라, 데이터가 나타내는 개념(거래·고객)을 모델링**하라. 개념은 비교적 안정적이다.
- 특정 용도·출력의 맥락에서 자유로운 성질 = **데이터 독립성**. 이를 달성하면 유지보수가 쉽고, 요구 변화에 덜 취약하며, 새 애플리케이션을 쉽게 지원.

### 개념 모델 작성 가이드라인
- **실제로 다뤄야 할 개념을 찾기** — 나중에 쓸 데이터만 저장(예: 판매 소요 시간이 안 쓰이면 저장 불필요).
- **동작이 아닌 사물(things, not actions)** — `Sale`/`Transaction`은 사물, `Sell`/`Buy`는 동작.
- **열이 아닌 테이블로 생각** — 세부에 매몰되지 말 것. 열 하나면 충분한 것은 테이블이 아닌 열로(예: 거래 시각만 저장하면 `Sales`의 열).
- **데이터 독립성을 위해 설계** — 개념 모델링(출력 아님).
- **테이블이 너무 많을까 걱정 말 것** — 초기엔 오히려 부족하기 쉽다. 예비 **열 목록**에서 논리적 묶음을 찾아 테이블을 식별.
- **아이디어를 문서화** — 보통 ER 다이어그램이나 서술로.

### ER 다이어그램의 엔티티
- 예: 강사 주도 교육 과정 스케줄링 DB — 강사(instructors)·강의실(classrooms)을 특정 과정에 예약, 학생을 배정하되 강의실 좌석 수 초과 금지. 주요 엔티티부터 식별.
- 간단한 ER 다이어그램: 각 엔티티를 **상자(box)**로 그리고, 상단에 엔티티 이름, 아래 빈 영역에 나중에 속성을 기입. 종이·범용 드로잉 도구·DB 모델링 전용 도구 사용 가능.
- 개념 모델의 주 초점은 **포함할 개념을 문서화**하는 것(속성 나열은 필수 아님).

## 예시 — 활동 2-1 (Canal House Books)
서점+커피숍(음료·음식·행사) 매출·재고 추적 DB. 이해관계자 요구:
- 매출 거래 기록(고객, 판매원, 제품 목록, 판매 시점 가격, 판매세, 할인, 총액).
- 각 제품의 현재 재고 추적(판매·반품 시 조정).
- 재고가 제품별 특정 수량에 도달하면 주문 필요 항목의 주간 리포트.

**전형적 해답**: `Personnel`, `Customers`, `Products`, `Purchases` 엔티티. 재고 수량은 `Products`의 속성으로. 재주문을 위해 공급업체 정보가 필요하므로 **`Suppliers` 엔티티**도 유용.
- 처음엔 엔티티 후보처럼 보였으나 제외되는 것들 — 데이터가 전혀 쓰이지 않거나, 값이 하나뿐이라 **속성으로 더 적합**한 경우.

## 요약
- 개념 모델 = 스키마 초안으로, **엔티티 타입(개념)**을 식별(주요 → 보조).
- 원칙: **사물(동작 아님)·테이블 단위·데이터 독립성**(출력이 아닌 개념 모델링)·문서화(ER 다이어그램).
- 모든 데이터가 엔티티는 아님 — 값 하나면 **속성(열)**으로.
