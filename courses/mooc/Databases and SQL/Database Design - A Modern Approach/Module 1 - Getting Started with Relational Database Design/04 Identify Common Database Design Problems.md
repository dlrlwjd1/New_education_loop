# Identify Common Database Design Problems (흔한 데이터베이스 설계 문제 식별)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 1: Getting Started with Relational Database Design · 토픽 1B

## 개요
- 나쁜 설계로 발생하는 **데이터 이상(data anomaly)** 상황을 인식해, 흔한 설계 함정을 피하는 법을 다룬다.

## 내용

### 데이터 이상(data anomaly)이란
- **이상(anomaly)** = 비정상적인 것, 사용자 기대에서 벗어난 것.
- 사용자는 DB가 데이터를 **삽입·갱신·삭제**할 수 있으리라 기대하지만, 설계가 나쁘면 이런 작업 후 적절한 결과를 얻지 못하거나 무결성이 깨진다. 결국 비즈니스에 해를 끼친다.

### 데이터 이상의 세 가지 유형
데이터가 변하는 세 시점(삽입·갱신·삭제)에서 발생:
- **삽입 이상(insertion anomaly)** — 다른 데이터가 없어서 중요한 데이터를 넣을 수 없음. 예: 아직 구매하지 않은 신규 고객 정보를 추가할 수 없음.
- **갱신 이상(update anomaly)** — 같은 테이블에 데이터가 **중복 저장**되어, 값이 바뀔 때 모든 복사본을 갱신했는지 보장하기 어려움.
- **삭제 이상(deletion anomaly)** — 원치 않는 정보를 지울 때 **원하는 정보까지 함께 삭제**됨.

## 예시 — 활동 1-2 (Orders 테이블의 이상)
고객·전화번호·품목번호·설명이 한 `Orders` 테이블에 섞여 여러 이상이 존재:
- **검색 문제** — 회사명 철자가 제각각("General Tool", "General Toll", "General Tool Co.") → 모든 행을 찾기 어려움.
- **연락처 문제** — 같은 회사에 전화번호 2개, 대소문자 다른 이름("Totally Toys" vs "TOTALLY TOYS") → 잘못된 번호가 든 행만 찾을 위험.
- **삭제 이상** — Totally Toys 주문 행을 지우면 그 회사의 연락처도 사라짐. (연락처를 별도 테이블에 두면 주문만 삭제 가능.)
- **삽입 이상** — 주문이 없으면 Consolidated Flange의 전화번호를 저장할 수 없음. (주문 없이도 회사 정보를 저장할 수 있어야 함.)
- **갱신 이상** — 품목 2246 설명을 바꾸려면 그 품목이 나오는 **모든 행**을 갱신해야 함(+ 열이 더 긴 문자열을 받도록 보장 필요).
- **다중 품목 주문** — 한 주문(08622)에 품목 2개(3145, 3967)가 별도 행으로 기록됨. 회사명이 다르게 입력되어 배송 리포트에서 같은 주문으로 묶이지 않을 수 있음.
- → 이 문제들은 **여러 개의 관련 테이블(related tables)**로 나누면 해결된다.

## 요약
- 나쁜 설계는 **삽입·갱신·삭제 이상**을 낳는다.
- 근본 원인은 데이터 중복과 한 테이블에 서로 다른 종류의 정보를 섞는 것 → **관련 테이블로 분리**하는 것이 해법(정규화의 동기).
