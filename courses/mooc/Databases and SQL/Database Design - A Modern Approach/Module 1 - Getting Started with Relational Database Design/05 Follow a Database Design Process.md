# Follow a Database Design Process (데이터베이스 설계 프로세스 따르기)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 1: Getting Started with Relational Database Design · 토픽 1C

## 개요
- 잘 설계된 DB의 **품질(qualities)**과, 그 품질을 설계에 반영하는 **프로세스**를 설명한다. 데이터 모델링, 모델링 용어, 개발 생애주기, 모델링 방법론을 다룬다.

## 내용

### 좋은 설계가 갖는 품질
- **Clear(명확)** — 테이블·열 이름을 업무 개념에 맞게, 자기설명적으로. 가능한 가장 단순한 모델. (예: `name` 대신 `primary_contact_first_name`.)
- **Essential(필수)** — 필요한 데이터만, 중복 없이, 가장 필요한 테이블에 저장. (예: 학생·강사를 따로 두지 말고 `Participants` 하나로.)
- **Cooperative(협력)** — 조직의 다른 DB와 호환되게. 같은 부품번호 체계, 같은 `customer_id`로 동기화.
- **Efficient(효율)** — 단순·일관되게, 용도에 최적화. 자주 쓰는 데이터는 소수 테이블에. 가장 효율적인 데이터 타입 선택.
- **Precise(정밀)** — 업무 규칙을 정확히 모델링·강제. (예: 주문 수량에 음수 입력 못 하게 제약.)
- **Flexible(유연)** — 미래 요구를 고려. (예: 제품 유형별 테이블 대신 범용 `Products` 테이블.)
- **Reusable(재사용)** — 특정 요구에 종속되지 않게 데이터를 조직.
- **Balanced(균형)** — 위 속성들은 충돌하므로 판단으로 절충. **정기 검토**와 동료·이해관계자 리뷰가 필요.

### 데이터 모델링 (data modeling)
- 구현을 너무 일찍 시작하면 변경 비용이 커진다. 설계 단계에서는 **개념/논리 모델**(다이어그램·설명)로 계획 → 종이·도구에서 수정이 훨씬 빠르다.
- 모델링은 **반복적(iterative)** — 문서화 → 검토 → 개선 반복. 모델은 이해관계자와의 **소통 도구** 역할.

### 모델링 용어 (추상 용어 ↔ 물리 용어)
| 추상 용어 | 설명 | 물리 대응 |
|---|---|---|
| **Entity** | 실세계의 고유 객체(책·제품·고객) | — |
| **Entity Type** | 엔티티를 표현하는 템플릿/클래스 (흔히 "entity"로 축약) | — |
| **Relation** | 엔티티 집합의 2차원 표현 | 테이블(table) |
| **Attribute** | 엔티티 타입의 속성 | 열(column) |
| **Tuple** | 개별 엔티티의 데이터 모음 | 행(row) |
| **Relationship** | 둘 이상 엔티티 간의 연결 | 테이블 간 관계(열로 성립) |
- 이 강좌는 이해를 돕기 위해 주로 **물리 용어(테이블·열·행)**를 사용하되, 모델링 도구·문서에서 만날 추상 용어도 알아둔다.

### 데이터베이스 개발 프로세스 (생애주기)
1. DB의 **목적 식별**.
2. **개념 모델(conceptual model)** 정의.
3. **논리 모델(logical model)** 정의.
4. **물리 모델(physical model)** 정의.
5. **테스트·구현**.
6. **유지보수**.
- 설계(2~4단계)가 생애주기의 큰 부분. 각 단계마다 초점이 이동하며, 필요 시 이전 단계로 **반복**해 돌아간다.

### 세 가지 모델의 초점
- **개념 모델** — 업무 개념을 나타내는 **엔티티 타입 이름**과 엔티티 간 **관계** 식별. 특정 기술·DBMS 정보 없음.
- **논리 모델** — 관계의 논리적 성질(예: 출판사는 여러 책, 책은 하나의 출판사), 각 개념의 **속성(→열)**, 속성의 **데이터 타입**(DBMS 무관), 고유 식별용 **키(key)**.
- **물리 모델** — 특정 DBMS·기술에 맞춘 청사진: 명명 규칙에 따른 테이블·열 이름, 구체적 데이터 타입, 뷰·제약·인덱스·보안 역할·프로시저 등. 이후 보안·성능·감사·가용성·확장성 **테스트** 및 수정(프로토타입).

### 모델링 방법론
- 단일 표준은 없고 여러 공식 방법론이 있으며 조합해 사용:
  - **개체-관계 모델링(Entity-Relationship, ER)** — Dr. Peter Chen(1976). **Chen 다이어그램**(단순함이 장점). 이후 crow's foot(까마귀발), Martin, Bachman, Erwin, IE 등 변형. **ER 다이어그램**은 관계가 성립되는 구체적 속성(예: Courses.instructor_id ↔ Instructors.id)에 초점. crow's foot 기호로 카디널리티 표현(예: 강사 1명만 / 강좌 0·1·다수).
  - **의미 모델링(Semantic)** — ORM, BRM, NIAM 등. 구조가 아닌 **정보의 의미**에 초점, 단순 영어 문장으로 관계 표현("An Instructor may deliver a Class"). 비개발자가 이해·검증하기 쉽고, 도구로 자동 DB 구조 생성 가능.
  - **유스케이스 모델링(Use Case)** — 사용자 유형과 각자 필요한 동작(고객이 책 검색, 판매원이 결제, 재고원이 재고 확인)에서 시작. 사용자+동작 조합 = **유스케이스**. 이를 분석해 필요한 데이터·엔티티·접근 권한 결정.

### 설계 프로세스에 영향을 주는/제한하는 요인
- **입력 요인**: 업무 목표·요구사항. 설계는 정답이 하나가 아니며 **경험·판단·창의성**이 작용(어떤 개념을 포함/제외할지, 이름·구성·테이블 분배).
- **제한 요인**: 이해관계자가 주는 재량, 업무 요구 이해도, 제공되는 정보의 질, 시스템의 한계·능력.

### 설계 단계의 중요성
- 성급하게 개발·구현으로 넘어가지 말고, 설계가 좋은지 충분히 검증. 잘 설계된 DB는 프로그래밍 단순화, 앱 개발·유지보수 용이, 재작업 최소화, 새로운 비즈니스 통찰 지원.

## 예시
- **활동 1-2(리뷰)**: 이해관계자에게서 무엇을 알아내야 하나 — 어떤 업무 프로세스를 지원? 현재 다루는 데이터? 샘플 데이터 확보 가능? 필요한 출력(뷰·리포트)? 사용자 유형과 작업?
- **활동 1-3 (Canal House Books)**: 재고 추적·매출 리포트·저자/공연자 일정 관리 DB 설계 프로젝트 착수. 설계는 **반복적**이며 이해관계자와의 리뷰·정보 교환이 핵심(특히 설계자가 업무 전문가가 아닐 때). 상호작용 방식·일정·주요 정보원(누구)을 합의할 것.

## 요약
- 좋은 설계 품질: **Clear·Essential·Cooperative·Efficient·Precise·Flexible·Reusable·Balanced**.
- 개발 생애주기: **목적 → 개념 → 논리 → 물리 → 테스트/구현 → 유지보수** (반복적).
- 세 모델의 초점: 개념(엔티티·관계) → 논리(속성·데이터 타입·키) → 물리(DBMS별 청사진).
- 방법론: **ER(Chen/crow's foot)·의미(ORM)·유스케이스**. 설계는 정답이 하나가 아니며 판단·반복·이해관계자 협업이 중요.
