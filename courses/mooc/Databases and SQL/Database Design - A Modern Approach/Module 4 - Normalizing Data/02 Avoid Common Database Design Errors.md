# Avoid Common Database Design Errors (흔한 설계 오류 피하기 — 정규화 1NF~3NF)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 4: Normalizing Data · 토픽 4A

## 개요
- **데이터 정규화(data normalization)**로 초기 설계를 개선한다. 제1~제3정규형(1NF·2NF·3NF)과 그 위반 사례·해결법을 다룬다.

## 내용

### 데이터 정규화란
- 설계에 적용하는 **논리적 테스트의 집합**으로, 각 테이블이 하나의 개념만 다루고 그 개념을 지원하는 열만 포함하도록 체계적으로 보장.
- 효과: **중복 감소, 유지보수 용이, 미래 기능 변경 시 재설계 최소화, 모범 사례 준수**.
- 특정 DBMS에 종속되지 않음. 점점 엄격한 규칙(=**정규형, normal form**)을 순서대로 적용: **1NF → 2NF → 3NF → BCNF → 4NF → 5NF**.
  - 1NF는 데이터가 열·테이블에 **어떻게 분배**되는지, 2NF·3NF는 **키와 비키 열의 관계**에 관한 것.
  - 대부분 **3NF까지** 하면 삽입·갱신·삭제 이상이 제거된다.
  - 정규화되지 않은 상태 = **비정규형(UNF, unnormalized form)**.

### 제1정규형 (1NF)
- **요구사항**: ① 유사 데이터의 목록은 **여러 행(세로)**으로, 한 행 안에 넣지 않는다. ② 각 행이 다른 모든 행과 **고유**하다.
- **위반 신호**: 한 셀에 콤마로 구분된 목록, `telephone_01`·`telephone_02`처럼 **다중 열 목록**(임의로 개수 제한), **기본 키 없음**.
- **해결**: 목록은 "세로로 가라(go vertical)" — 여러 행 사용. 값이 늘 수 있으면 **별도 테이블**로 분리. **기본 키** 지정.
- 예: 프로젝트·기간을 한 셀 목록이나 가로 다중 열로 넣으면 정렬·필터·데이터 타입 적용이 불가능하고, 프로젝트가 추가될 때마다 열을 늘려야 함 → 세로(행)로 해결.

### 함수 종속 (functional dependency)
- 2NF를 이해하려면 **함수 종속**을 알아야 함: 한 열의 특정 값이 **항상** 다른 열의 특정 값을 결정하면, 후자는 전자에 **함수적으로 종속**된다.
- 예: `Airport → City` — 공항 이름은 고유하고 한 도시에만 있으므로 `City`는 `Airport`에 종속. 역은 성립 안 함(한 도시에 여러 공항). 결정하는 열(`Airport`) = **결정자(determinant)**.
- 표기: `결정자 열 → 함수 종속 열`.

### 제2정규형 (2NF)
- **요구사항**: ① 1NF 충족. ② 모든 **비키 열이 기본 키 전체에 함수적으로 종속**.
- **위반 신호**: 여러 행에 걸쳐 반복되는 데이터 값(한 테이블에 여러 개념을 표현하려는 징후).
- **원칙**: 중복이 허용되는 것은 테이블을 잇는 **키 열뿐**(키 데이터는 거의 안 변함). 자주 변하는 비키 열은 반복하면 안 됨.
- 예: 복합 키(`employee_id`+`project_id`)인데 `last_name`·`first_name`은 `employee_id`에만, `project_title`은 `project_id`에만 종속 → **키의 일부에만** 종속(부분 종속). `project_title` 변경 시 여러 행 수정, 직원 없는 프로젝트 추가 불가(키에 NULL 불가), 프로젝트 삭제 시 직원 정보까지 삭제 위험.
- **해결**: 테이블을 더 작은 테이블로 분해(정규화의 대부분 해법은 **테이블을 더 만드는 것**).

### 제3정규형 (3NF)
- **요구사항**: ① 2NF 충족. ② **이행 종속(transitive dependency)이 없음**.
- **이행 종속**: 비키 열의 값이 **다른 비키 열**에 의해 결정되고, 그 열이 후보 키(candidate key)가 아닌 경우.
- 예: `phone`이 `manager`(비키 열)에 의해 결정되고 `manager`는 후보 키가 아님 → 전화번호는 프로젝트가 아니라 매니저의 속성이라 "이행적"(테이블의 핵심 개념과 간접적으로만 관련).
- **해결**: 이행 종속이 있는 열을 **별도 테이블**로 분리.

## 예시 — 활동들 (프로젝트 추적 DB)
- **4-1(1NF)**: 직원당 프로젝트 3개만 추적하던 설계를 → **personnel 테이블 + 프로젝트별 시간 테이블** 2개로 분해(각각 기본 키·데이터 타입·관계선·crow's foot).
- **4-2(2NF)**: 비키 열의 반복 데이터를 제거 — 어떤 열이 다른 열을 결정하는지 보고 테이블 분리, 필요 시 외래 키/정션 테이블 추가.
- **4-3(3NF)**: 이행 종속을 제거 — 함께 속하는 필드를 새 테이블로, 외래 키로 연결.

## 요약
- 정규화 = 각 테이블이 **하나의 개념**만 다루도록 하는 논리 테스트. 대개 **3NF**까지면 이상이 사라진다.
- **1NF**: 목록은 세로(여러 행)로, 고유 행, 기본 키. **2NF**: 1NF + 비키 열이 **기본 키 전체**에 종속(부분 종속 제거). **3NF**: 2NF + **이행 종속 제거**(비키→비키).
- 대부분의 해결책은 **테이블을 더 나누는 것**. 함수 종속(`결정자→종속 열`)이 분해의 판단 기준.
