# Ensure Referential Integrity (참조 무결성 보장)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 5: Finalizing the Database Design · 토픽 5B

## 개요
- 기본 키·외래 키 값이 일치하도록 유지해 테이블 간 관계를 보존하는 **참조 무결성(referential integrity)** 통제를 다룬다.

## 내용

### 참조 무결성이란
- 진정한 관계형 DB 제품의 정의 중 하나. 원칙: **모든 non-NULL 외래 키 값은 기존 기본 키 값과 일치해야 한다.**
- **non-NULL** = 외래 키에 값이 필수는 아니지만, 값이 있으면 반드시 관련 테이블의 기본 키 값과 일치해야 함. 즉 외래 키 값의 **유효성 보존**.
- 제품마다 참조 무결성을 **명시적으로 활성화**해야 함(관계 정의 또는 조인 방식). 내가 쓰는 제품이 어떻게 강제하는지 알아야 함.
- 예: `Departments`(기본 테이블) ↔ `Employees`(관련 테이블), 1:N. `Employees.dept_id`(외래 키) 값은 NULL이 아닌 한 `Departments.dept_id`(기본 키)와 일치해야 함. 없으면 관계가 무의미해지고 쿼리 결과를 신뢰할 수 없음.

### 캐스케이딩 업데이트·삭제 (cascading updates/deletes)
- 코드 변경·부서 병합 등 참조 무결성을 위반하는 변경을 다루는 방법. 제품마다 규칙·트리거·연산자로 구현.
- **캐스케이딩 업데이트**: `Departments`에서 `AC`→`AG`로 바꾸면 `Employees`의 모든 `AC`가 자동으로 `AG`로 변경(변경이 관련 테이블로 "전파").
- **캐스케이딩 삭제**: `Departments`에서 `SL`(Sales)을 삭제하면 `Employees`의 `SL` 행이 모두 삭제됨. 더 멀리 있는 관련 테이블까지 전파될 수 있어 주의(남는 데이터는 유효).
- 이해하면 **적절한 순서**로 변경 가능. 예(Marketing+Sales 병합): ① `Departments`의 `MK`→`MS`(이름도 변경)로 캐스케이드, ② `Employees`의 `SL`을 모두 `MS`로 변경, ③ 그 뒤 `Departments`의 `SL` 삭제 → 직원 행 삭제 없이 무결성 준수.

### 비즈니스 규칙과 강제 수준
- 참조 무결성은 **DB 수준**(테이블 간)에서 강제. 설계자는 추가로 **열 수준·테이블 수준**에서 데이터 무결성을 강제해 비즈니스 규칙을 반영할 수 있음.

### 참조 무결성 보장 가이드라인
- 각 **규칙과 강제 위치를 문서화**(규칙이 바뀌면 어디를 고칠지 쉽게 찾도록).
- 열/테이블 수준에서 구현할 수 없는 규칙은 **애플리케이션 수준**(쿼리·폼·뷰·리포트·코드)에서 처리.
- 규칙을 구현하면 **테스트**: 충족 시 의도한 결과가 나오는가? 위반 시에는? 좋은 앱 설계는 규칙 위반 시 사용자에게 피드백을 준다.

## 예시 — 활동들
- **5-2**: 부모 테이블의 기본 키 값 변경/삭제가 자식 테이블에 **고아 레코드(orphan records)**를 만들면 참조 무결성 위반(예: Accounting `AC`→`AG` 변경, Sales 부서 삭제). 부모에서 자식을 고아로 만드는 변경은 참조 무결성이 허용하지 않음.
- **5-3**: DBMS가 캐스케이딩을 지원하는지 확인 — 업데이트는 부모의 `type_code`를 바꾼 뒤 자식(`Appearances`) 값이 함께 바뀌는지 확인, 삭제는 부모 행 삭제 시 자식 종속 행 삭제 경고/삭제 여부를 확인.

## 요약
- **참조 무결성** = 모든 non-NULL 외래 키가 기존 기본 키와 일치 → 테이블 간 관계 보존.
- 위반을 만드는 변경은 **고아 레코드**를 낳으므로, **캐스케이딩 업데이트/삭제**로 처리하거나 변경 순서를 조정.
- DB 수준(참조 무결성) + 열/테이블 수준(비즈니스 규칙) + 앱 수준으로 무결성을 강제하고, 규칙은 문서화·테스트한다.
