# Adapt the Physical Model for Different Systems (시스템별 물리 모델 적응)

> 강좌: Database Design: A Modern Approach (Logical Operations, MOOC) · 모듈 5: Finalizing the Database Design · 토픽 5A

## 개요
- 사용할 DBMS의 요구사항에 맞춰 설계를 개정해 **물리 모델(physical model)**을 만든다. 명명 규칙·식별자 규칙·데이터 타입 차이를 다룬다.

## 내용

### DBMS 간 차이
- 좋은 설계는 주요 RDBMS 어디에나 구현 가능하지만, **테이블·열 이름 길이, 문자셋, 데이터 타입** 등에서 차이가 있어 설계에 영향.
- 배포 시스템을 알더라도, 향후 마이그레이션을 위해 **모든(또는 대부분) 시스템에서 통하는 명명 규칙·데이터 타입**을 쓰는 것이 유리.

### 테이블·열 이름(식별자) 짓기
- 좋은 **식별자(identifier)**는 혼란·비효율·실수를 예방. 명명을 좌우하는 요인:
  - **DBMS의 규칙·제한**, **조직의 명명 규칙**, **명확성(clarity)**.

### 식별자 길이
- DBMS별 최대 길이: SQL-92/99(명시 안 됨, 최소 18), **SQL Server 128**, **Oracle 128**(12.2+), **MySQL 64**.
- **짧은 식별자**는 마이그레이션·코딩에 유리하나, 요소를 명확히 식별할 만큼은 길게.

### 특수 문자
- 식별자에 허용되는 문자는 표준·DBMS마다 다름. 대략 **첫 글자는 문자(letter)**, 이후 **문자·숫자·`_`**. 특수문자를 피하면 마이그레이션·코딩이 쉬움.
- 대소문자 구분: SQL-92/99·Oracle·MySQL(Windows)은 비구분, SQL Server는 설정 가능(기본 구분), MySQL(대부분 Linux)은 구분.

### DBMS가 규칙을 두는 이유
- 규칙은 컴퓨터가 코드를 단순·일관되게 해석하기 위함. 예: `SELECT name, address FROM Customers`에서 키워드(SELECT/FROM)와 공백·구두점·식별자 위치가 각 부분의 의미를 파악하게 함.

### 인용 식별자 (quoted identifiers)
- SQL-92는 식별자를 **큰따옴표**로 감싸 특수문자·확장 문자셋(중국어·러시아어 등)을 허용. 시작·끝을 명확히 표시. (= delimited identifier.)
- 복잡성이 커지므로 **꼭 필요한 경우가 아니면 지양**. SQL Server는 대괄호를 쓰며 기본적으로 인용 식별자 미지원(설정 필요).

### 명명 규칙 (convention)
- DBMS가 강제하는 규칙 외에, 개발자가 선택하는 **관례**. 예: **Leszynski Naming Convention(LNC)**, **ISO-11179-4**.
- **LNC**(Hungarian notation 기반): 접두사(scope/status)+태그(객체 유형, `tbl`·`qry`·`frm`·`cur`)+기본 이름(`tblCatalog`). 장점 — 코딩 도구 지원, 객체 유형 즉시 식별. 단점 — **마이그레이션·변경 시 대규모 개명 필요**(예: `tblCatalog`→`qryCatalog`이면 모든 코드 수정), 목록 정렬이 유형별로 묶여 탐색 불편. 주로 MS Access·VB에서 사용.
- **ISO-11179**: ISO의 메타데이터 표준으로 데이터 요소 정의·명명의 일반 규칙 제시.

### 데이터 요소 명명 가이드라인 (호환·작성)
- **호환**: 이름 **18자 이내**, 첫 글자는 문자, 이후 문자·숫자·`_`, `_`로 끝내지 않기, 인용 식별자 지양.
- **작성**:
  - 변할 수 있는 정보의 접두/접미사 지양(LNC의 `tbl`/`cur` 반대 — `Catalog`를 쓰면 테이블→쿼리 전환 시 앱 수정 불필요).
  - **널리 이해되는 약어**만(예: 출판사에선 `ISBN`). 모호한 이름 지양(`ISBN` > `BookCode`).
  - **무엇인지**를 기술(무엇이 아닌지 말고). 다른 요소 정의를 내포한 복잡한 이름 지양.
  - **맥락 안에서 명명**(SalesReps 테이블의 `name`은 굳이 `sales_rep_name` 불필요).
  - **일관성**(같은 `user_id`를 모든 테이블에서 동일하게).
  - **문법 형태가 요소 유형과 일치**: 테이블 = 집합을 나타내는 명사(단수 `Personnel`/복수 `Employees`, 단일 `Employee` 금지), 열 = 단수 명사(`part_number`), 프로시저 = 동사(`Insert`).
  - **대소문자**: 테이블은 대문자로 시작(`Catalog`), 열은 소문자(`product_name`).

## 예시 — 활동 5-1 (물리 모델 만들기)
- 서점 DB를 **Microsoft SQL Server**에 구현하기로 결정 → 논리→물리 전환 시 식별자 길이·특수문자·인용 필요 여부·데이터 타입을 점검.
- 대부분 시스템에서 통하는 명명 규칙을 이미 썼으므로 식별자는 그대로 OK. 단 **데이터 타입은 SQL Server용으로 변경** 필요(모듈 3의 데이터 타입 목록 참조).

## 요약
- 물리 모델은 특정 DBMS에 맞춘 청사진 — **식별자 길이·특수문자·대소문자·데이터 타입** 차이를 반영.
- 이식성을 위해 **18자 이내, 문자로 시작, 문자/숫자/`_`, 인용 식별자·변경 가능한 태그 지양**. 이름은 명확·일관·맥락 기반으로.
- 테이블=대문자 복수/집합 명사, 열=소문자 단수 명사, 프로시저=동사.
