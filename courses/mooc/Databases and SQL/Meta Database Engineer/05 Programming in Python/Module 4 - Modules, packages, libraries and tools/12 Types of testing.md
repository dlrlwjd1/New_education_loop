# Types of testing

## 개요

- 테스트 분류(화이트박스/블랙박스, 기능/비기능/유지보수, 수동/자동)와 4대 테스트 수준: 단위 → 통합 → 시스템 → 인수

## 내용

### 분류 방식

- **화이트박스 vs 블랙박스** — 테스터가 코드 설계·기능을 아는가(화이트) 모르는가(블랙)
- **기능(functional)** — 비즈니스 요구 기반, 기능이 기대에 맞는지 / **비기능(non-functional)** — 전반 성능·품질 같은 복잡한 메트릭 / **유지보수(maintenance)** — 시스템·운영 환경이 수정·확장될 때
- **수동 vs 자동** — 소프트웨어 규모에 따라

### 4대 테스트 수준 (순차적, 서로 위에 쌓임)

1. **단위/컴포넌트 테스트(unit)** — 개별 컴포넌트를 **격리**해 테스트. 코드에 가까운 저수준이라 **코드 작성과 동시에** 쓰고, 작아서 CI 자동화에 적합. Python이면 **pytest** 같은 패키지 사용.
2. **통합 테스트(integration)** — 단위들을 결합해 **컴포넌트 간 데이터 흐름** 테스트. 키워드는 **인터페이스** — DB에서 데이터를 올바로 가져와 웹 페이지로 보내는지 등. 접근법: 톱다운·보텀업·샌드위치. 테스터가 담당.
3. **시스템 테스트(system)** — 전체 소프트웨어를 요구·기대에 대해 검증해 **완전성** 확보. 신뢰성·성능·보안·로드 밸런싱, 플랫폼·OS 등 운영 환경 작동성 측정. **출시 직전의 가장 중요한 단계**, 테스터 팀이 담당.
4. **인수 테스트(acceptance)** — 배포 준비가 된 제품 대상. 이해관계자와 선별된 최종 사용자가 참여하며 **알파·베타·회귀 테스트** 포함. 사전 작성 시나리오를 주고 결과로 개선·누락 버그를 찾는다.

### 핵심 원칙

- **일찍, 자주 테스트하라** — 조기 발견이 시간·노력·비용을 아낀다. 코드가 복잡해질수록 수정이 어렵다.
- 수준들은 반복적으로 접근할 수 있다 — 애자일 모델에서는 몇 주마다 버전을 내며 인수 테스트를 반복한다.

## 요약

- 테스트는 화이트/블랙박스, 기능/비기능/유지보수, 수동/자동으로 분류된다.
- 단위(격리·pytest) → 통합(인터페이스) → 시스템(완전성) → 인수(알파/베타/회귀) 4수준이 순차적으로 쌓인다.
- 일찍·자주 테스트하는 것이 비용을 줄이는 열쇠다.
