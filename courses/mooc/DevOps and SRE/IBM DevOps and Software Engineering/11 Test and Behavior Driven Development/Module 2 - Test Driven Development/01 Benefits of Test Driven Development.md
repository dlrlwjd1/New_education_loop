# Benefits of Test Driven Development

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/test-and-behavior-driven-development-tdd-bdd/lecture/0iNCa/benefits-of-test-driven-development)

## 개요
- API를 만들 때 TDD에서 처음 판매되었습니다.API를 심층적으로 다루고 있었는데 데이터가 필요해서 호출에 파라미터로 추가했습니다.그런 다음 다른 데이터가 필요했고 이를 매개변수로 추가했습니다.그리고 작업을 마쳤을 때 훌륭한 API를 만들었다고 생각했지만 테스트 케이스를 작성하러 갔을 때 호출자로서 코드를 호출하는 데 필요한 데이터의 절반이 없다는 것을 깨달았습니다.정말 끔찍한 API였지만, 제 코드를 소비자 관점에서 보고 호출하기 전까지는 몰랐어요.

## 내용
- API를 만들 때 TDD에서 처음 판매되었습니다.API를 심층적으로 다루고 있었는데 데이터가 필요해서 호출에 파라미터로 추가했습니다.그런 다음 다른 데이터가 필요했고 이를 매개변수로 추가했습니다.그리고 작업을 마쳤을 때 훌륭한 API를 만들었다고 생각했지만 테스트 케이스를 작성하러 갔을 때 호출자로서 코드를 호출하는 데 필요한 데이터의 절반이 없다는 것을 깨달았습니다.정말 끔찍한 API였지만, 제 코드를 소비자 관점에서 보고 호출하기 전까지는 몰랐어요.
- 이것이 바로 테스트 주도 개발에서 원하는 코드의 테스트 케이스를 먼저 작성하는 이유입니다.그런 다음 테스트 케이스를 통과하도록 코드를 작성합니다.TDD는 소비자 API가 무엇을 전달하고 싶어하는지, 어떤 결과를 얻을 것으로 예상하는지 생각해야 하며, 이를 통해 고객 중심을 유지할 수 있습니다.
- 라고 생각할 수도 있습니다.글쎄요, 제가 처음에 TDD에 대한 강의를 들었을 때 교수님이 테스트 케이스를 주시면서 프로그램을 작성해야 한다고 말씀하셨지만 프로그램이 무엇을 하는지는 말씀드리지 않겠습니다.다음은 테스트 케이스입니다.프로그램을 작성한 다음 제출하십시오.나는 이 사람이 미쳤다고 생각했다.그런 다음 테스트 케이스를 읽고 코드에 대해 기대하는 바를 이해하기 시작했습니다.그런 다음 코드를 작성하기 시작했고 이러한 기대에 부응하기 시작했습니다.설계 문서를 따르는 것과 매우 흡사했습니다.그러다가 테스트 중심의 디자인이 떠올랐습니다.이것이 테스트 케이스이고, 우리가 디자인한 것입니다.
- 이 동작을 문서화하는 테스트 케이스를 작성한 다음 해당 동작을 나타내는 코드를 작성하여 테스트 케이스를 통과시킵니다.이는 테스트 기반 개발을 위한 기본 워크플로우입니다.갖고 싶었던 코드에 대해 실패한 테스트 케이스를 작성하세요.이것은 코드를 호출하는 방법과 그 대가로 기대하는 바를 표현합니다.그런 다음 테스트 케이스를 통과할 수 있을 만큼의 코드만 작성합니다.
- 완벽할 필요는 없습니다.예쁘지 않아도 됩니다.테스트 케이스를 통과해야 합니다.이제 코드를 리팩토링하여 품질을 개선할 수 있습니다.처음에는 고정된 값을 반환했는데 이제 실제 값을 계산할 차례일 수 있습니다.마지막으로 이 과정을 반복합니다.이 전체 워크플로를 레드/그린/리팩터링이라고 합니다.많은 테스트 도구가 이 체계를 따릅니다.이러한 도구는 실패한 테스트 사례를 빨간색으로, 합격 테스트 사례는 녹색으로 출력합니다.레드/그린/리팩터라는 이름은 이렇게 붙여졌습니다.그렇다면 TD가 DevOps에 대해 보고하는 이유는 무엇일까요?
- 자신감이 높아지기 때문에 더 빠르게 코딩할 수 있습니다.이제 코드를 리팩터링하면 테스트 케이스가 동작의 변경 사항을 포착하기 때문에 변경 사항이 발생하더라도 문제가 발생할 수 있으므로 걱정할 필요가 없습니다.테스트를 통해 코드가 예상대로 작동하는지 확인합니다.
- 원하는 동작을 정의하기 위해 테스트 케이스를 먼저 작성하면 테스트 케이스가 통과했을 때 해당 동작이 언제 달성되었는지 알 수 있습니다.또한 테스트 케이스는 향후 변경으로 인해 코드가 손상되지 않도록 합니다.테스트 케이스가 실패하면 무언가가 발생하여 코드를 손상시켰음을 즉시 알릴 수 있습니다.마지막으로 가장 중요한 것은 DevOps 파이프라인을 만들려면 버그를 프로덕션에 더 빨리 푸시하려는 경우가 아니라면 모든 테스트를 자동화해야 한다는 것입니다.많은 회사들이 이 점을 이해하지 못하고 있습니다.
