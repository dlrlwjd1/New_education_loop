# Dependencies

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/7H6lP/dependencies)

## 개요
- 소프트웨어 개발에서 **의존성(Dependency)**의 정의와 이점, 사용에 따른 과제와 위험, 검증(vetting) 방법, 그리고 Flask와 `ItsDangerous` 의존성을 이용한 실제 코드 예시를 정리.

## 내용
### 의존성이란
- 소프트웨어나 코드의 한 부분이 기능하기 위해 다른 부분에 의존할 때 필요한 것 — 처음부터 작성하지 않고 소프트웨어에 기능을 추가하는 데 흔히 사용됨.
- 의존성은 코드가 호출하는 라이브러리 패키지나 모듈 안에 있는 재사용 가능한 코드. 패키지 매니저를 사용해 의존성의 다운로드와 설치를 자동화할 수 있음.
- 간단한 예시: 프로그램 A가 기본으로 갖고 있지 않은 함수가 필요한데, 프로그램 B의 코드가 이를 제공할 수 있음 — 프로그램 A는 그 함수를 위해 프로그램 B를 호출하도록 작성되고, 프로그램 B는 요청된 기능을 프로그램 A에 제공해 애플리케이션이 설계대로 작동. 프로그램 A는 의존자(dependent), 프로그램 B는 의존성(dependency)으로 간주됨.

### 의존성 사용의 이점
- 소프트웨어 개발 프로세스가 더 빠르고 효율적이 됨 — 이전 작업 위에 구축해 소프트웨어를 더 빠르게 전달 가능.
- 애플리케이션이 더 많은 기능과 특성을 가질 수 있게 함 — 의존성이 제공하는 기능을 처음부터 작성할 필요가 없어짐.
- 의존성이 제공하는 기능이 자체(native) 구현보다 더 나은 성능을 낼 수도 있음.

### 위험과 과제
- 인터넷에서 코드를 다운로드해 사용하는 것은 위험 — 소프트웨어를 취약점, 버그, 기타 결함에 노출시킬 수 있음.
- 호환되지 않거나, 오래되었거나, 누락된 의존성을 구현한 결과로 프로덕션 위험이 발생할 수 있음:
  - 프로덕션 서버가 영향을 받아 성능 저하나 충돌이 발생할 수 있음.
  - 취약점으로 인해 데이터가 유출될 수 있음 — 고객 데이터가 손상될 수 있음.
  - 회사의 평판도 영향을 받아 사업 손실, 평판 훼손, 심지어 벌금으로 이어질 수 있음.
- **라이선싱 문제** — 사용하는 의존성의 라이선스 요구 사항을 인지해야 함. 프로젝트에 맞는 올바른 유형의 라이선스를 사용하고, 애플리케이션에 무허가(unlicensed) 코드가 없는지 확인해야 함.

### 의존성 검증(Vetting) 방법
- 프로젝트에 의존성을 사용할 계획이라면, 구현 전에 철저히 검증(vet)하는 것이 모범 사례. 다음 항목을 확인:
  - **설계(Design)** — API가 잘 설계되고 잘 문서화되어 있는지 확인.
  - **품질(Quality)** — 원치 않는 동작이나 의미론적(semantic) 문제가 없는지 코드 품질을 확인.
  - **테스트(Testing)** — 기본 코드 기능을 테스트하고 가능한 실패를 찾아봄.
  - **디버깅(Debugging)** — 열려 있는 이슈와 버그 리포트를 확인하기 위해 의존성의 이슈 트래커를 점검.
  - **유지보수(Maintenance)** — 버그 수정과 지속적인 개선을 위한 커밋 히스토리를 검토. 1년 넘게 업데이트되지 않은 의존성은 사용을 피할 것.
  - **사용성(Usage)** — 널리 채택되었는지, 아니면 거의 사용되지 않는지 — 거의 사용되지 않는 의존성은 방치될 수 있음.
  - **보안(Security)** — 소프트웨어 의존성은 공격을 위한 큰 표면(surface)이 될 수 있음 — 악의적인 입력을 허용하는 약점과 취약점을 확인.
  - 다운로드를 관리하고 버전 업데이트를 추적하기 위해 의존성 관리 도구를 사용.

### 간접 의존성(Indirect Dependency)
- 의존성이 다른 의존성에 의존하는 것 자체가 나쁜 것은 아니지만, 몇 가지 과제를 제기함 — 간접 의존성 안에서 발견된 코드 문제가 자신의 코드에 영향을 줄 수 있으므로 모든 간접 의존성을 점검해야 함.
- 모든 코드를 점검하기 위해 직접·간접 의존성 목록을 나열해주는 의존성 관리자를 사용. 의존성을 업그레이드할 때는 프로젝트에 새로 유입될 수 있는 새로운 간접 의존성을 인지해야 함.

### Flask 사례
- Flask는 웹 애플리케이션 구축을 위한 도구, 라이브러리, 기타 기능을 제공하는 Python 웹 프레임워크. LinkedIn과 Pinterest가 Flask를 사용하는 조직의 예.
- Flask 자체의 의존성:
  - **Werkzeug** — WSGI(Web Server Gateway Interface).
  - **Jinja** — 웹 페이지 렌더링을 위한 템플릿 언어.
  - **MarkupSafe** — 신뢰할 수 없는 입력을 위한 보안 의존성.
  - **ItsDangerous** — 안전한 데이터 무결성 의존성.
  - **Click** — 명령줄 애플리케이션 작성을 위한 프레임워크.

### `ItsDangerous`를 이용한 토큰 생성 예시
```python
from itsdangerous import URLSafeSerializer

s = URLSafeSerializer('비밀-키', 'auth')
token = s.dumps({'id': 5, 'name': 'alice'})
# token은 무작위 문자열처럼 보이지만 실제로는 암호화되어 있어
# 비밀 키를 가진 쪽만 복호화 가능

data = s.loads(token)
print(data['name'])  # 'alice'
```
- `URLSafeSerializer`를 자신이 관리하는 비밀 키와 함께 인스턴스화하고, `'auth'`를 지정해 이 토큰을 인가(authorization) 용도로 사용하겠다는 신호를 줌.
- `dump()` 메서드로 직렬화할 데이터(`id`가 5, `name`이 "alice"인 딕셔너리)를 전달해 토큰을 생성 — 이 토큰은 비밀 키로만 복호화 가능하도록 암호화됨.
- 데이터는 이제 키를 가진 다른 서비스로 안전하게 전송되어 복호화될 수 있거나, 나중에 자신에게 다시 전송되었을 때 변조되지 않았음을 알고 복호화할 수 있음.
- `loads()` 메서드로 토큰을 복호화하면 원래 메시지를 반환 — 실제 다른 코드였다면 같은 비밀 키로 `URLSafeSerializer`를 다시 인스턴스화해 토큰을 복호화.

## 요약
- 의존성은 다른 코드가 의존하는 재사용 가능한 코드로, 개발 속도와 기능성을 높여주지만 호환성·라이선싱·보안 측면의 위험을 동반하므로 설계·품질·테스트·디버깅·유지보수·사용성·보안 기준으로 철저히 검증하고 의존성 관리 도구로 직접·간접 의존성을 모두 추적해야 하며, Flask처럼 자체 의존성(Werkzeug, Jinja, MarkupSafe, ItsDangerous, Click)을 가진 프레임워크의 경우 `ItsDangerous`로 비밀 키 기반의 안전한 토큰을 생성·검증할 수 있다.
