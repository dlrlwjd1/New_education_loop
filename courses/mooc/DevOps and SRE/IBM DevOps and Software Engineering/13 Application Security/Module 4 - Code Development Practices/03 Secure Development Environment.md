# Secure Development Environment

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/ED0sp/secure-development-environment)

## 개요
- **안전한 개발 환경(Secure Development Environment)**이 왜 필요한지, 안전하지 않은 개발 환경의 원인, 그리고 개발 환경을 안전하게 만드는 모범 사례를 정리.

## 내용
### 문제 상황
- 개발 중인 애플리케이션이 설계·개발 단계에서 보안을 고려하지 않고 코딩되는 경우가 드물지 않음.
- 흔히 벌어지는 일: 완성된 앱이 Operations에 넘겨져 프로덕션에 배포되고, 앱이 해킹당해 Operations가 서버를 종료해야 하는 상황. Ops의 보안 인풋 없이 개발된 앱은 사이버 공격에 매우 취약.
- 다운타임 비용, 보안 취약점 수정 비용, 데이터 유출 가능성, 조직의 평판을 고려하면 애플리케이션 개발에 보안을 반영하는 것은 마지막 순간의 결정이어서는 안 됨.
- 조직에서 이를 막으려면 소프트웨어 개발 프로세스 초기에 보안 팀을 참여시켜야 함 — 설계 단계 초기부터 보안 담당자와 견고하게 협업.

### 개발 환경도 안전해야 하는 이유
- 처음부터 안전하게 코드를 작성하는 것만으로는 충분하지 않음 — 개발 환경 자체도 안전해야 함.
- 개발 시스템과 플랫폼도 프로덕션 머신과 동일한 유형의 공격에 취약 — 위협 행위자를 막기 위해 환경을 강화(harden)해야 하며, 이를 위해 보안 팀에 의존.
- 실무적인 안전한 개발 기법에 대한 지식과 이해 없이는 코드가 공격을 견뎌내기 어려움. 환경이 안전하지 않으면 그 환경에서 나온 코드가 안전하다고 받아들이기 어려움.
- 보안은 팀의 노력 — DevOps 팀의 모든 구성원이 보안에 책임이 있고, 애플리케이션·서비스·실행 플랫폼에 관여하는 모든 사람과 모든 것이 설계부터 배포, 프로덕션까지 보안에 책임이 있음. DevOps와 보안의 결합된 역량은 방어적 코드 개발과 시스템 위험에 대한 더 깊은 이해를 가져옴.

### 안전한 개발 환경의 정의
- 온프레미스와 클라우드 모두에서 네트워크, 컴퓨팅 자원, 저장 장치를 안전하게 지키는 지속적인 과정.
- 개발 환경을 안전하게 지키면 다음을 시도하는 공격자의 위험을 줄임: 암호화 키·접근 키·지적 재산 같은 민감 정보 탈취, 모르는 사이 프로젝트에 악성 코드 삽입, 빌드·배포 파이프라인이나 네트워크상의 다른 머신에 대한 추가 공격을 시작하는 도구로 시스템 악용.

### 안전한 개발 환경을 위한 실천 사항
- 모든 소프트웨어를 최신 상태로 유지하고, 불필요한 서비스를 제거하거나 비활성화.
- 개발 머신을 물리적으로 안전하게 지키고, 코딩과 업무용으로 별도의 머신을 사용 — 업무 관련 기능에는 가상 머신, Docker 컨테이너, 또는 별도 컴퓨터를 사용하고, 코드는 강화된 시스템에서 개발해 피싱·멀웨어 공격과 기타 사이버 위협을 줄임. (강사 개인은 모든 개발을 Docker 컨테이너에서 수행해 코딩을 시작할 때마다 격리된 알려진 환경을 갖추며, 프로젝트 저장소도 팀원 모두가 동일한 컨테이너화된 환경을 갖도록 구성.)
- 복잡한 비밀번호와 잦은 비밀번호 변경을 사용하고 다중 인증(MFA)을 구현.
- 코드 저장소를 보호하고 빌드·개발 파이프라인을 안전하게 지킴.
- 모니터링, 로깅, 감사 통제에 투자하고 지속적으로 보안을 테스트하며 보안 결함에 대비한 계획을 세움.

### 안전하지 않은 개발 환경의 특징
- 프로덕션 시스템은 안전하지만, 코드가 작성·배포되는 개발 환경이 프로덕션 인프라에 직접 연결된 채 무법지대(free-for-all)인 경우 — 개발 머신이 손상되면 프로덕션 환경도 손상됨.
- 개발 환경에 보호 모니터링, 로깅, 감사가 없으면 공격이 발생했는지, 언제 발생했는지, 다른 취약점이 있는지 판단할 능력이 없음 — 공격자가 조직에 침투해 수개월 이상 탐지되지 않은 채 남아 있을 수 있음.
- 개발 시스템에 최신 백신·안티멀웨어 제품이 설치되어 있지 않으면 개발 머신과 그 위의 코드가 피싱, 멀웨어, 기타 공격에 취약해짐.
- 승인되지 않은 코드 저장소에 대한 무제한 접근과 코드 획득에 대한 거버넌스·정책 부재는 의심스러운 소프트웨어 의존성이 애플리케이션에 유입되도록 허용할 수 있음.

### 개발 환경을 안전하게 지키는 모범 사례
- **인터넷 연결 보안** — 안전하지 않은 네트워크는 네트워크 공격에 매우 취약. 열린 포트를 정기적으로 확인해 불필요한 포트를 닫거나, 허용된 트래픽 외에는 아무것도 통과시키지 않도록 엄격한 인그레스/이그레스 트래픽 정책으로 방화벽을 설정. Docker 컨테이너에서 개발하면 컨테이너가 개발 컴퓨터와 분리된 격리 네트워크에 있고 기본적으로 모든 포트가 외부에 닫혀 있어 특히 유용.
- **다중 인증(MFA) 구현** — 신원 도용을 막기 위해 필요. 비밀번호만으로는 부족하며, 비밀번호만 의존하면 시스템이 공격받을 위험이 매우 높아짐. 비밀번호가 노출되면 전체 코드와 다른 자산까지 위험에 처함. MFA는 공격자가 개발자 권한을 활용하지 못하게 막고, 시크릿도 MFA로 보호해 도난과 손실 위험을 줄임.
- **프로덕션 접근이 필요한 개발자에게 추가 보안 적용** — 개발자 머신에서 프로덕션 시스템에 접근해야 하는 경우 추가 보안 조치를 더함.
- **개발자 환경 모니터링** — 개발자가 하는 모든 일을 감시하는 것을 의미하지는 않음. 개발자 머신은 최대한 잠그되(lock down) 업무 수행에 필요한 자원에는 여전히 접근할 수 있어야 함 — 그렇지 않으면 개발자가 보안 점검을 우회하는 '우회책(workaround)'을 사용하게 되어 머신이 오히려 공격에 취약해짐.
- **일상적인 보안 습관 체득** — 의심스러운 활동을 주시하고, 방문하는 웹사이트가 의심스러운지 안전한지 네트워크 유틸리티로 확인. 문제가 생겼을 때 참조할 수 있도록 개발자가 환경에서 수행한 모든 커밋과 변경 사항을 추적. pre-commit hook을 사용하면 개발자가 자격 증명 같은 민감 데이터를 코드 저장소에 커밋하지 않도록 확인할 수도 있음.

## 요약
- 보안은 흔히 소프트웨어 개발 프로세스에서 빠지거나 마지막 순간에만 다뤄져 공격에 매우 취약한 소프트웨어를 낳으므로, 보안 팀과 개발 팀의 협업이 방어적 코드 개발에 대한 깊은 이해를 길러주고, 앱·개발 환경·실행 플랫폼에 관여하는 모든 사람과 모든 것이 보안에 책임을 져야 하며, 네트워크·개발자 머신·프로덕션 환경을 모니터링해 열린 포트·의심스러운 행동·백신 부재를 확인하고, MFA와 암호화로 비밀번호와 시크릿을 보호하고 공격자가 개발자 권한을 얻지 못하게 막으며, 프로덕션 접근이 필요한 개발자에게 추가 보안 조치를 더하고 모든 커밋과 변경 사항을 추적해야 한다.
