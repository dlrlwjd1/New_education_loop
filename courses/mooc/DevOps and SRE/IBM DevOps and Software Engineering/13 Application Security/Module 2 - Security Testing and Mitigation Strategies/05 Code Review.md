# Code Review

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/LEnxW/code-review)

## 개요
- 보안 테스트의 핵심 부분인 **코드 리뷰**를, 자동화된 리뷰와 수동 리뷰 두 유형으로 나눠 각각의 장단점과 적용 시점을 설명.

## 내용
### 코드 리뷰란
- DevOps 커뮤니티에서 보안이 주요 관심사가 되면서, 개발자들은 보안 테스트 방법론을 SDLC에 추가하고 있음 — 코드 리뷰는 보안 테스트의 중요한 부분.
- 코드 리뷰에서는 자동화된 정적 분석 보안 테스트와 수동 코드 검사를 사용 — 두 유형 모두 노출된 위협이나 보안에 중요한 구성 요소를 담고 있는 소스 코드에 초점을 맞춤. 목적은 기존의 보안 결함이나 취약점을 찾는 것.
- 코드 리뷰는 그중에서도 논리적 결함, 스펙 구현 검토, 스타일 규칙 검증을 찾음. 초기에 수행할 때 가장 효과적 — 그때가 버그를 가장 쉽고 빠르게 해결할 수 있는 시점이기 때문. 하지만 SDLC의 어느 단계에서든 코드 리뷰를 구현할 수 있음.

### 유형 1 — 자동화된 리뷰(Automated Review)
- 파일이 많고 코드가 길다면 자동화된 코드 리뷰가 최선의 선택 — 대규모 코드베이스를 빠르고 효율적으로 평가할 수 있음.
- 코드를 작성하면서 자동화된 코드 리뷰를 사용하면 바로 변경할 수 있음. 지속적 통합 중에는 자동화된 코드 스캐닝을 사용해 Pull Request가 main 브랜치로 병합되기 전에 검증 검사를 수행 가능.
- 코딩하는 동안 실시간으로 취약점을 발견하기 위해 무료 오픈소스나 유료 자동화 도구를 사용할 수 있음. 대부분의 고급 개발팀은 **SAST(Static Analysis Security Testing)** 도구를 사용 — SAST 도구는 추가적인 입력을 제공할 수 있고, 코드를 커밋하기 전에 이런 취약점을 해결할 수 있게 해줌.

### 유형 2 — 수동 리뷰(Manual Review)
- 수동 리뷰는 테스트가 놓치는 문제를 자주 발견 — 코드의 첫 통과(pass)를 개발하는 동안 알아차리지 못했을 수 있는 실수를 찾을 수 있음.
- 수동 리뷰를 완료하려면 전체 프로그램을 검토해야 하는 시니어급이나 더 경험 있는 개발자가 필요 — 애플리케이션의 복잡한 제어와 로직 흐름을 읽고 이해할 수 있는 사람이 필요하기 때문에 매우 시간이 많이 걸릴 수 있음.
- 개발자가 보안 단위 테스트를 작성할 때마다 테스트 케이스가 다를 수 있고, 개발자마다 테스트 케이스가 다를 수 있음 — 이 경우 고려할 정책을 기술해야 할 수 있음. 요즘은 보호해줄 수 있는 라이브러리도 많이 있음.
- 마지막으로 강조하고 싶은 점: 모든 Pull Request마다 코드를 수동으로 리뷰하고 문제에 대해 코멘트해야 함 — Pull Request의 50줄이나 100줄짜리 코드를 리뷰하는 것이, 몇 주 뒤에 수천 줄짜리 코드를 리뷰하는 것보다 훨씬 쉬움.

## 요약
- 안전한 코드 리뷰는 노출된 위협이나 보안에 중요한 구성 요소를 담은 소스 코드에 초점을 맞추며, 자동화된 코드 리뷰는 대규모 코드베이스를 빠르고 효율적으로 평가할 수 있고 SAST 도구를 통해 커밋 전 실시간으로 취약점을 잡아내는 반면, 수동 코드 리뷰는 경험 있는 개발자가 필요하고 시간이 많이 걸리지만 자동화된 테스트가 놓치는 문제를 발견할 수 있으므로, Pull Request마다 코드가 적을 때 즉시 수동 리뷰하는 습관이 나중에 방대한 코드를 리뷰하는 것보다 훨씬 효율적이다.
