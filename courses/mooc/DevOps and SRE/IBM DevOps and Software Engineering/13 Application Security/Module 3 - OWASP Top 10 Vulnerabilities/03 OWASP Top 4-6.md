# OWASP Top 4-6

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/IFFvF/owasp-top-4-6)

## 개요
- OWASP Top 10 중 4~6위인 **Insecure Design(안전하지 않은 설계)**, **Security Misconfiguration(보안 설정 오류)**, **Vulnerable and Outdated Components(취약하고 오래된 구성 요소)**의 정의와 예방 전략을 정리.

## 내용
### 4위 — Insecure Design(안전하지 않은 설계)
- 애플리케이션 설계 단계에서 효과적인 보안 통제가 부족한 것을 의미 — 흔히 공격에 취약한 애플리케이션을 낳음. 방화벽이 구현되지 않았거나 무차별 대입 공격(brute force attack), OTP(One Time Password) 우회, 기타 사이버 위협을 막을 메커니즘이 없는 경우.
- 안전하지 않은 설계는 웹 애플리케이션 설계에 기반한 위험을 강조하며, 존재할 수 있는 모든 아키텍처 결함을 포함. 완벽한 구현이라도 안전하지 않은 설계를 치유할 수 없음 — 공격자는 계속해서 애플리케이션에서 악용할 취약점을 찾음.
- 특정 공격으로부터 보호하기 위한 보안 조치가 필요하며 설계 단계에서부터 고려·구현되어야 함. 방화벽 구현과 다른 보안 조치 설계는 공격 예방에 도움이 됨 — 처음부터 보안을 염두에 두고 설계하면 애플리케이션을 최대한 안전하게 만들 수 있음.
- **오류 메시지(error message) 처리**도 중요한 부분:
  - 오류 메시지는 문제 해결에 도움을 주지만, 안전하게 처리되지 않으면 민감한 정보를 노출해 공격자가 악용할 수 있는 취약점으로 이어질 수 있음.
  - 부적절한 오류 처리는 서버 소프트웨어 버전 정보, 자격 증명이 담긴 설정 파일 위치, 디렉터리 구조, 시스템 구조 등을 노출할 수 있어 데이터 유출·재정적 손실·벌금·평판 훼손 같은 심각한 결과로 이어질 수 있음.
  - 안전한 오류 처리기(secure error-handler)를 사용해 오류의 세부 사항은 로그에 기록하고, 사용자에게는 민감한 데이터를 드러내지 않는 우호적이고 안전한 메시지를 제공.
  - 예: 로그인 시 "비밀번호가 틀렸습니다" 또는 "아이디가 틀렸습니다"처럼 정확히 어느 쪽이 틀렸는지 알려주면, 공격자가 소거법으로 어느 항목이 맞는지 알아낼 수 있어 해로움 — "아이디와 비밀번호가 일치하지 않습니다"처럼 어느 것이 진짜 자격 증명인지 드러내지 않는 것이 나음.
  - 또 다른 예: 오류 메시지에 앱이 사용하는 데이터베이스 테이블 구조 정보가 담기면, 공격자가 SQL 인젝션 공격을 수행하는 데 필요한 모든 것을 제공하게 되어 비밀번호·계좌번호·신용카드 같은 귀중한 데이터가 노출될 수 있음 — 사용자 인터페이스(UI)에는 사용자 친화적인 오류 메시지만 쓰고, 문제 해결에 유용한 상세 오류는 로그에 기록하는 것이 더 나은 처리 방식.

### 5위 — Security Misconfiguration(보안 설정 오류)
- 애플리케이션에 간과된 설정 취약점이 존재하는 상태 — 공격자는 이런 취약점을 악용. 디버그 모드나 QA 기능처럼 라이브 프로덕션 환경에 배포하기 전에 비활성화하지 않으면 위험한 개발자 기능들이 포함됨.
- 공격자는 이런 기능을 악용해 상승된 권한으로 민감한 정보에 무단 접근할 수 있음. 불필요한 기능을 포함한 애플리케이션은 의도치 않게 사용자에게 필요 이상의 권한을 부여할 수 있음 — 사용자는 작업 수행에 필요한 최소한의 권한만 가져야 하며, 항상 **최소 권한 원칙(Principle of Least Privilege, PoLP)**을 따라야 함.
- **예방 방법**:
  - 불필요한 부분·기능·문서가 없는 애플리케이션을 구현하도록 노력.
  - 필요 없는 프레임워크나 기능을 제거하고, 기본 권한을 공개적으로 공유하지 말고 오프라인·비공개로 유지.
  - 설계 단계에서 기본 사용자 이름, 기본 설정과 권한을 확인. 백도어 계정, 평문으로 된 설정 파일, 기타 가능한 취약점도 확인.
  - 보안 설정 오류는 애플리케이션 스택의 어느 부분에서든 발생할 수 있음을 기억 — 플랫폼, 웹 서버, 앱 서버, 데이터베이스, 사용하는 모든 커스텀 코드를 포함해 모든 수준에서 보안을 고려.
  - 보안 설정 오류 예방은 팀 차원의 노력이며, 전략에 시스템 관리자를 포함해야 함 — 개발자와 시스템 관리자의 전문성을 결합해 전체 스택이 올바르게 설정되고 최신 상태로 유지되도록 보장.

### 6위 — Vulnerable and Outdated Components(취약하고 오래된 구성 요소)
- 소프트웨어 애플리케이션, 운영체제, 플랫폼, 하드웨어는 끊임없이 발전 — 버그 수정, 신규 기능 추가, 펌웨어 업데이트, 패치가 계속 출시되어 애플리케이션을 최신 상태로 유지하고 변화하는 기술과의 기능성을 보장.
- 애플리케이션에 사용하는 각 구성 요소와 중첩된 의존성(클라이언트 사이드·서버 사이드 모두)의 버전에 익숙해야 함 — 핵심 플랫폼, 지원 프레임워크, 의존성, 직접 사용하는 구성 요소가 제때 정기적으로 업데이트·업그레이드되지 않으면 오래되어 애플리케이션이 공격에 취약해짐.
- 수정 사항이 존재하더라도 애플리케이션에 반영되지 않으면 패치되기 전까지 며칠에서 몇 달까지 취약한 상태로 남을 수 있음.
- **예방 방법**:
  - 사용하지 않는 의존성과 기능이 없도록 애플리케이션을 유지 — 기능을 추가하지 않으면서 오래되거나 악용될 경우 위험을 초래할 수 있음.
  - 설치된 구성 요소와 중첩된 의존성 목록을 만들고 유지하며, 보안 인지를 위해 업데이트된 구성 요소를 추적.
  - OWASP와 CISA가 발표하는 최신 보안 위험과 취약점 정보를 계속 파악.

## 요약
- 안전하지 않은 설계는 설계 단계의 보안 통제 부재로 발생하며 방화벽·보안 조치를 설계 단계부터 고려하고 안전한 오류 처리기로 민감 정보 노출을 막아 예방하고, 보안 설정 오류는 불필요한 기능 제거·최소 권한 원칙·스택 전 수준의 보안 점검·시스템 관리자와의 협업으로 예방하며, 취약하고 오래된 구성 요소는 사용 중인 구성 요소·의존성 목록을 유지하고 정기적으로 업데이트하며 OWASP·CISA의 최신 정보를 파악해 예방한다.
