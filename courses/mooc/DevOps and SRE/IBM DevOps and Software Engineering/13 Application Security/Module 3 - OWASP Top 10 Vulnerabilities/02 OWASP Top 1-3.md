# OWASP Top 1-3

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/a7z1l/owasp-top-1-3)

## 개요
- OWASP Top 10 중 1~3위인 **Broken Access Control(취약한 접근 제어)**, **Cryptographic Failures(암호화 실패)**, **Injection(인젝션)**의 정의와 각각을 예방하는 구체적인 방법을 정리.

## 내용
### 1위 — Broken Access Control(취약한 접근 제어)
- 접근 제어는 인증된 사용자에게 특정 권한을 부여해 애플리케이션과 리소스에 접근할 수 있게 하는 것 — 부여된 권한 외에는 다른 권한 없이 사용자에게 자신만의 작업 공간을 제공하고, 사용자가 의도된 권한 밖에서 행동하지 못하도록 보안 정책을 강제.
- **취약한 접근 제어**는 공격자가 애플리케이션이나 시스템의 의도된 권한 밖에서 접근·수정·삭제·행동할 수 있는 것 — 접근 제어 취약점을 악용하는 해커는 애플리케이션 보안을 손상시키고, 회사 이미지를 훼손하고, 심지어 재정적 손실을 초래할 수 있음.
- 해커는 URL의 정보를 조작해 악용 가능한 것이 있는지 확인 — 예: 사용자 ID가 URL에 보이면 공격자가 이를 바꿔 무슨 일이 일어나는지 시도. 그런 일이 일어나면 기밀성이 손상되고 애플리케이션 보안이 위험에 처함.
- 취약한 접근 제어는 2022년 OWASP Top 10에서 1위 — 웹 애플리케이션에서 가장 자주 마주치는 취약점 중 하나.
- **예방 방법**:
  - 사용자에게 제한된 권한을 부여해 특권 작업 공간 안에 머물도록 함 — 허용되지 않은 환경에서 몰래 돌아다니거나 무단으로 변경하는 것을 방지.
  - 정기적인 접근 제어 검사 — 관리자가 사용자 수준에 따라 필요한 접근 수준(수평적·수직적)을 항상 인지하도록 보장.
  - 애플리케이션에 대한 공개 정보를 제한적으로 배포 — 너무 많은 정보를 공개하면 공격자가 애플리케이션을 악용할 문을 의도치 않게 열어줄 수 있음. 애플리케이션을 안전하게 지키는 데 필요한 최소한으로 공개 정보를 제한.
  - URL에 파일 경로가 보이는 경우가 있음 — 해커는 이를 웹 서버 디렉터리 목록에 대한 공개 초대로 여김. URL의 디렉터리 목록을 비활성화해 외부 세계가 웹 서버 디렉터리에서 페이지가 어디 있는지 알지 못하게 함.
  - 서버 로그에 기록된 접근 제어 실패가 있으면 먼저 시스템 관리자에게 알려야 함 — 로그에 실패가 기록되도록 하면서 아무 조치도 하지 않으면 안 됨.

### 2위 — Cryptographic Failures(암호화 실패)
- 암호화는 여러 암호화 방법을 사용해 달성됨 — 애플리케이션에서 암호화를 사용할 계획이라면 암호화 실패를 인지해야 함.
- 예: HTTP 요청이 사용자 ID나 신용카드 번호 같은 민감한 정보와 연관된 정보를 담고 있다고 가정. 사용자 ID가 123이고 암호화를 사용해 무작위 문자열로 바꾸면, 의도된 수신자만 복호화해야 읽거나 이해할 수 있음.
- URL에 담겨 전달되는 HTTP 요청이 약하거나 잘 알려진 암호화 방법을 사용하면, 데이터가 암호화 실패를 겪어 민감한 데이터나 정보를 공격자에게 노출·유출할 가능성이 큼. 공격자는 전통적인 암호화 방법을 쉽게 복호화할 수 있음.
- **예방 방법**:
  - 데이터베이스에 저장된 모든 민감한 데이터를 전통적인 암호화 방법 대신 **인증된 암호화(authenticated encryption)**로 암호화하는 것이 최선의 전략.
  - 능동적으로 전송 중이거나 저장 중인 모든 데이터를 암호화.
  - HTTPS는 안전하고 HTTP는 안전하지 않다는 것을 이해하는 것이 중요 — HTTP를 사용하는 웹사이트는 안전하지 않아 공격받을 가능성이 더 높음. HTTPS는 전송 중 정보가 암호화되도록 보장해 데이터를 안전하게 지킴.
  - SMTP, FTP 같은 오래된 프로토콜 사용 피하기 — 중간자 공격에 더 취약함.
  - 암호화 키는 필수적이며 해커의 주요 표적 — 손상된 키는 방대한 개인 정보와 지적 재산에 접근할 수 있게 해줌. 소프트웨어 애플리케이션에 절대 하드코딩하지 말 것. 키는 단일하고 구체적인 목적으로 제한되어야 함. 키 생애주기와 관리 프로세스를 따르고, 안전하게 백업·저장할 것.

### 3위 — Injection(인젝션)
- 신뢰할 수 없는 정보가 명령, 쿼리, 또는 적대적 데이터와 함께 인터프리터로 전달될 때 발생 — 인터프리터를 속여 의도치 않은 명령을 실행하게 함으로써 해커에게 데이터에 대한 무단 접근을 허용하는 방식으로 작동.
- 흔한 인젝션 공격 유형: SQL 인젝션, 운영체제 명령 인젝션, HTTP Host 헤더 인젝션, LDAP 인젝션, 크로스 사이트 스크립팅 코드 인젝션, 코드 인젝션.
- **예방 방법**:
  - 인터프리터 사용을 피하거나 파라미터화된 인터페이스를 제공하는 안전한 API를 사용하는 것이 인젝션 공격을 없애는 최선의 방법.
  - 이스케이프 목록(escape list)을 사용해 키워드나 특수 문자를 차단하는 것이 도움이 됨 — 키워드 목록을 정기적으로 최신 상태로 유지하는 것이 항상 모범 사례.
  - 공격자가 select 문을 활용하고 있는지 확인해 문(statement)을 살균(sanitize).

## 요약
- 취약한 접근 제어는 사용자에게 제한된 권한만 부여하고 정기적인 접근 검사·최소한의 공개 정보 노출·디렉터리 목록 비활성화로 예방하고, 암호화 실패는 전통적 암호화 대신 인증된 암호화와 HTTPS 사용, 오래된 프로토콜 회피, 안전한 키 관리로 예방하며, 인젝션(SQL·OS 명령·LDAP·XSS 등)은 파라미터화된 인터페이스를 제공하는 안전한 API와 이스케이프 목록, 문 살균으로 예방할 수 있다.
