# Security by Design

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/application-security-for-developers-devops/lecture/KtXNW/security-by-design)

## 개요
- Secure SDLC(보안이 통합된 소프트웨어 개발 생애주기)의 개념과 단계를 소개하고, DevOps를 Secure SDLC의 각 단계(요구사항·설계·개발·테스트·배포)에 매핑하는 방법을 설명.

## 내용
### 보안은 나중에 생각할 문제가 아니다
- 프로젝트를 만들 때 보안을 전혀 고려하지 않다가 결국 보안 팀이 모든 서버를 멈추고 코드가 뚫리는 상황을 겪는 경우가 흔함 — 보안이 막판 결정이 되어서는 안 되는 이유.
- 이를 극복하려면 항상 보안 팀을 참여시켜야 함 — 보안 담당자와 초기부터 정기적으로 탄탄하게 협업하는 것이 결정적, 코드를 안전한 방식으로 작성하는 것이 중요하기 때문. DevOps로 안전한 애플리케이션을 개발할 수 있음.

### SDLC(Software Development Lifecycle)란
- 소프트웨어 개발의 각 단계에 관련된 단계를 명시하는 프레임워크 — 프로그램을 개발·배포·유지보수하는 전략을 상세히 기술.
- 완전히 테스트되고 프로덕션에 준비된 고품질 소프트웨어의 신속한 개발로 이어지는 잘 구조화된 단계들의 시퀀스.
- SDLC의 단계들:
  - **요구사항(Requirements)** — 프로젝트 팀이 프로젝트에 대한 고객의 기대를 이해하기 시작하는 단계.
  - **설계(Design)** — 요구사항 단계에서 만든 요구사항 목록에 기반해 결정을 내리는 단계.
  - **개발(Develop)** — 설계를 실행에 옮기는 단계.
  - **테스트(Test)** — 개발자가 코드와 프로그래밍을 테스트해 고객 요구를 충족하는지, 기능이 매끄러운지 확인하는 단계.
  - **배포(Deploy)** — 프로젝트 팀이 테스트한 뒤 각 테스트 단계를 통과한 제품이 실제로 서비스될 준비가 되면 실행하는 단계.

### Secure SDLC란
- 보안이 소프트웨어 개발 생애주기의 여러 단계에 어떻게 들어맞는지 기술 — 기존 개발 모델에 보안 테스트와 그 모범 사례를 통합하는 이 과정은 다음을 포함:
  - 위험 평가(Risk assessment).
  - 위협 모델링과 설계 리뷰(Threat modeling and design review).
  - 정적 분석(Static analysis).
  - 보안 테스트와 코드 리뷰(Security testing and code review).
  - 보안 평가와 보안 설정(Security assessment and security configuration).

### DevOps를 Secure SDLC의 각 단계에 매핑하기
- **요구사항 단계** — 위험 평가를 수행하고 사람들이 코드를 어떻게 공격할 수 있는지 고려. 보안 요구사항과 표준, 다루는 정보의 유형을 확실히 파악. 보호할 정보를 식별하는 보안 요구사항을 정의하고, 위협 모델링 과정 전반에 걸쳐 무슨 일이 일어날 수 있는지 판단하는 공격 프로파일링(attack profiling)을 수행.
- **설계 단계** — 안전한 방식으로 설계하는 것에 관한 것. 위협 모델링 중 "어떤 요소가 아키텍처를 취약하게 만들 수 있는가?"를 질문하고, 이 단계에서 취할 수 있는 예방 조치를 안전하게 설계하는 방법 고민.
  - **배포 파이프라인 보안** — 안전한 설계를 갖췄는지, 모든 테스트를 올바르게 자동화했는지, CI/CD 파이프라인이 취약점을 검색하고 있는지 확인. DevOps에서는 보안 팀원이 개발 팀원에게 흔한 위협 유형을 안내하고 이를 방어하는 단위 테스트를 만들도록 도울 수 있음.
- **개발 단계** — 코드의 보안 취약점을 확인·검사·불안전하다고 알려주는 도구로 **정적 분석**을 수행. 이 단계는 시스템의 정보가 정확하고 유용함을 보장하기 위한 자동화된 데이터 검증도 포함. **보안 태스크와 secure scrum**은 SDLC 전반에 걸쳐 안전한 소프트웨어 개발을 강조하는 스크럼 프레임워크의 변형.
- **테스트 단계** — 취약점 스캔을 통합하고 싶은 단계. 코드에 대해 보안 테스트를 수행하고 출시 전 위험 평가를 실시.
  - **실패를 추구하라(Strive for failure)** — 자신의 애플리케이션을 깰 수 있다면 공격자도 그럴 가능성이 높음.
  - **보안 테스트를 병렬화하라(Parallelize security testing)** — 시간을 절약하기 위해 코드 스캐너를 단위 테스트, 기능 검증 테스트(FVT)와 나란히 병렬로 실행해 테스트 창(test window)을 단축.
- **배포 단계** — 코드가 프로덕션에 있을 때 다양한 방식으로 안전하게 작동하는지 확인:
  - 배포 스크립트의 자동 실행 사용 가능.
  - **배포와 롤백(deploy and rollback)** — 파일 업로드 배포의 경우 롤백은 본질적으로 변경 사항을 되돌림. 이전에 파일이 업로드되었다면 지워지고, 수정이 있었다면 취소되고, 파일이 제거되었다면 다시 복원됨.
  - **프로덕션 보안 테스트** 수행 — 실제 세계의 해킹 방법과 접근을 모방해 장치나 애플리케이션의 숨겨진 결함을 드러냄. 이런 테스트는 진짜 통찰과 실용적인 결과를 제공.

## 요약
- 보안은 SDLC(요구사항·설계·개발·테스트·배포)의 마지막에 덧붙이는 것이 아니라 각 단계에 통합되어야 하며, 요구사항 단계에서는 위험 평가와 공격 프로파일링을, 설계 단계에서는 위협 모델링과 배포 파이프라인 보안을, 개발 단계에서는 정적 분석과 secure scrum을, 테스트 단계에서는 실패를 추구하는 태도와 병렬화된 보안 테스트를, 배포 단계에서는 자동 배포·롤백과 프로덕션 보안 테스트를 적용함으로써 DevOps 프로세스 전체에 Secure SDLC를 매핑할 수 있다.
