# Continuous Integration

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/intro-to-devops/lecture/QAnmv/continuous-integration)

## 개요
- 사람들은 CI/CD라는 약어를 마치 한 가지인 것처럼 사용하지만 지속적 통합과 지속적 전달은 별개의 두 가지 관행입니다.지속적 통합 (CI) 은 일련의 테스트를 통과한 후 모든 개발자 변경 사항을 마스터 브랜치에 지속적으로 구축, 테스트 및 통합하는 프로세스입니다.그 결과 잠재적으로 배포 가능한 코드가 생성됩니다.

## 내용
- 사람들은 CI/CD라는 약어를 마치 한 가지인 것처럼 사용하지만 지속적 통합과 지속적 전달은 별개의 두 가지 관행입니다.지속적 통합 (CI) 은 일련의 테스트를 통과한 후 모든 개발자 변경 사항을 마스터 브랜치에 지속적으로 구축, 테스트 및 통합하는 프로세스입니다.그 결과 잠재적으로 배포 가능한 코드가 생성됩니다.
- 제가 “프로덕션과 비슷하다”고 말한 것을 눈치채셨을 겁니다.프로덕션 환경에 배포할 필요가 없으며 실제로 많은 사람들이 프로덕션 환경에 지속적으로 배포할 때 “지속적 배포”라는 용어를 사용합니다.지속적 전달을 위해서는 프로덕션 환경을 모방한 개발, 테스트, 스테이징 환경과 같은 곳에 배포하기만 하면 됩니다.
- 이는 오랜 기간 동안 변경된 양이 많기 때문에 브랜치가 병합 충돌에 더 취약해지기 때문입니다.빌드는 릴리스 후보 브랜치에서 주기적으로, 때로는 야간에 실행됩니다.개발자들은 계속해서 개발 브랜치에 추가하는데, 이는 마스터 릴리스 브랜치에서 점점 더 멀어지고 있습니다.
- 모든 개발자는 정기적으로 커밋을 수행하면 병합 간에 걸리는 시간이 줄어들어 충돌하는 변경 사항의 수를 줄일 수 있습니다.시간이 지날수록 병합 충돌 위험이 커집니다.일주일 동안 코드를 작업한 다음 한 번에 모두 체크인하면 새 기능이 다른 기능과 충돌할 위험이 커집니다.
- 이렇게 하면 한 명 이상의 사람이 모든 코드를 검토할 수 있으므로 문제가 발생할 위험이 줄어듭니다.모든 변경 사항을 하루에 한 번 이상 또는 기능 빌드당 한 번 커밋하는 것은 일반적으로 지속적 통합의 정의의 일부로 간주됩니다.
- 테스트 결과는 pull 요청에 피드백되어야 하며, 실패한 테스트가 있는 pull 요청을 병합해서는 안 됩니다.지속적 통합을 실천할 때 얻을 수 있는 이점 중 하나는 변화에 대한 대응 시간을 단축하고 더 빠르게 움직일 수 있다는 것입니다.
- 테스트가 자동화되어 있기 때문에 지금까지 수행한 모든 작업이 테스트를 거쳐 제대로 작동하는 것으로 확인되었음을 알 수 있습니다.이러한 테스트를 자동으로 실행하면 테스트에 시간을 낭비하지 않고 기능 구축에 시간을 소비하게 됩니다.

## 예시
- 지속적 전달 (CD) 은 모든 변경 사항을 프로덕션과 유사한 환경에 전달하여 코드를 프로덕션에 빠르고 안전하게 배포할 수 있도록 설계된 일련의 사례입니다.

## 요약
- 테스트 결과는 pull 요청에 피드백되어야 하며, 실패한 테스트가 있는 pull 요청을 병합해서는 안 됩니다.지속적 통합을 실천할 때 얻을 수 있는 이점 중 하나는 변화에 대한 대응 시간을 단축하고 더 빠르게 움직일 수 있다는 것입니다. 테스트가 자동화되어 있기 때문에 지금까지 수행한 모든 작업이 테스트를 거쳐 제대로 작동하는 것으로 확인되었음을 알 수 있습니다.이러한 테스트를 자동으로 실행하면 테스트에 시간을 낭비하지 않고 기능 구축에 시간을 소비하게 됩니다.
