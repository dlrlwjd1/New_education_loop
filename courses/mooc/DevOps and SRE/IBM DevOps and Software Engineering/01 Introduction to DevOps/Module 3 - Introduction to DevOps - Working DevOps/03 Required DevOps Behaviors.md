# Required DevOps Behaviors

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/intro-to-devops/lecture/Vvzc9/required-devops-behaviors)

## 개요
- 기업은 복잡하고 위험도가 높으며 비용이 많이 들고 시간이 많이 걸리는 '새로운 것'으로 간주되는 엔드 투 엔드 프로세스를 중심으로 구축됩니다.그들은 새로운 것을 정해진 예산으로 정해진 시간 내에 완료하는 일회성 프로젝트로 접근하고 사람들을 다음 프로젝트로 옮깁니다.DevOps는 대규모 프로젝트를 세분화하여 관리가 용이한 일련의 작은 변경 사항을 지속적으로 제공함으로써 이러한 문제를 해결하고자 합니다.

## 내용
- 기업은 복잡하고 위험도가 높으며 비용이 많이 들고 시간이 많이 걸리는 '새로운 것'으로 간주되는 엔드 투 엔드 프로세스를 중심으로 구축됩니다.그들은 새로운 것을 정해진 예산으로 정해진 시간 내에 완료하는 일회성 프로젝트로 접근하고 사람들을 다음 프로젝트로 옮깁니다.DevOps는 대규모 프로젝트를 세분화하여 관리가 용이한 일련의 작은 변경 사항을 지속적으로 제공함으로써 이러한 문제를 해결하고자 합니다.
- 문제는 작은 변화로는 기업이 원하는 모든 작업에 가중되는 기존의 오버헤드를 감당할 수 없다는 것입니다.변경 검토 위원회와 같은 프로세스는 작은 변경에 필요한 속도로 이동할 수 없기 때문에 DevOps에서 작동하지 않습니다.
- 언제든지 시스템을 변경할 수 있습니다.배포 기술을 사용하여 필요에 따라 변경 사항을 활성화하거나 비활성화합니다.마지막으로, 기존 Ops의 프로세스는 '한 번 빌드하는 것'에 치우쳐 있습니다.Traditional Ops는 모든 것을 수동으로 빌드하고 영구적으로 또는 적어도 더 이상 필요하지 않을 때까지 (보통 몇 년) 유지 관리합니다.
- 빌드가 문서화되지 않았기 때문입니다.DevOps에서는 대용량의 신속한 변경 처리를 위해 프로세스를 재설계하여 빌드를 반복 가능하게 만들고 Infrastructure as Code를 활용하여 우리가 하는 모든 작업을 다시 구축할 수 있습니다.문화가 충돌하는 것은 이길 수 없는 시나리오입니다.
- 개발자들은 Ops가 이러한 변경 기간 동안 한밤중에 이러한 변경 사항을 전부 또는 전혀 하지 않는다고 생각합니다.그들은 코드로부터 가장 멀리 떨어져 있기 때문에 그것을 이해하지 못합니다.
- 하나하나가 고유하고 이것과 같은 서버를 찾을 수 없는 이러한 수작업으로 만든 눈송이 모양의 서버를 한 번 구축하는 것에서 벗어나 반복 가능하도록 Infrastructure as Code 기술을 사용하여 배포한 임시 인프라를 사용하는 것으로 전환하십시오.
- Docker 컨테이너를 구축할 때마다, 가상 머신을 구축할 때마다 정확히 동일하게 빌드합니다.코드를 변경하지 않은 경우 완전히 동일하게 빌드되고 동일한 결과를 얻을 수 있습니다.수동 주문 처리 (티켓 대기열, 수동으로 작업을 하는 사람) 에서 자동화된 셀프 서비스 활성화로 변경하세요.클라우드를 도입한 후 IT 담당자만 클라우드에서 프로비전할 수 있도록 티켓 대기열을 배치하는 회사를 본 적이 있습니다.이는 셀프 서비스 클라우드의 전체 목적을 무너뜨립니다.셀프 서비스는 빠르게 움직일 수 있는 방법입니다.

## 예시
- 빌드가 문서화되지 않았기 때문입니다.DevOps에서는 대용량의 신속한 변경 처리를 위해 프로세스를 재설계하여 빌드를 반복 가능하게 만들고 Infrastructure as Code를 활용하여 우리가 하는 모든 작업을 다시 구축할 수 있습니다.문화가 충돌하는 것은 이길 수 없는 시나리오입니다.
