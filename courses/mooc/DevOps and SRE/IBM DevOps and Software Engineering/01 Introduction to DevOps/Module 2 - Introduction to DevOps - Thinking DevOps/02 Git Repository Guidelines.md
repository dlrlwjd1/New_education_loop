# Git Repository Guidelines

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/intro-to-devops/lecture/lA0eT/git-repository-guidelines)

## 개요
- 마이크로서비스든 구축 중인 다른 것이든 모든 구성 요소에 대한 리포지토리를 만드세요.한 리포지토리에 여러 마이크로서비스를 넣지 마십시오.

## 내용
- 마이크로서비스든 구축 중인 다른 것이든 모든 구성 요소에 대한 리포지토리를 만드세요.한 리포지토리에 여러 마이크로서비스를 넣지 마십시오.
- 이러한 것들은 모노 리포지토리라고 불리며 눈살을 찌푸리게 합니다.사람들은 종종 데모를 쉽게 하기 위해 여러 마이크로서비스가 포함된 단일 리포지토리인 “모노 리포지토리”를 만들지만 프로덕션 코드에서는 그렇게 해서는 안 됩니다.누군가가 관심 있는 코드를 찾기 위해 신경 쓰지 않는 코드를 많이 확인하지 않아도 되는 것은 아닙니다.
- Git에서는 브랜치가 매우 가볍습니다.마스터 브랜치와 기능 브랜치가 있고 그게 전부입니다.기능 브랜치를 완료하면 삭제됩니다.너무 집착하지 마세요.
- 모든 pull 요청은 코드 검토를 할 수 있는 기회이기 때문에 항상 팀의 다른 사람이 풀 리퀘스트를 병합하도록 하고 싶을 것입니다.
- GitHub 리포지토리부터 시작해 보겠습니다.구성 요소에 대한 새 리포지토리를 만들거나, 다른 사람의 구성 요소에 기여하는 경우 기존 리포지토리를 포크합니다.
- pull 요청을 검토한 후 코드가 완전하고 팀에서 설정한 표준을 충족하면 마스터 브랜치에 다시 병합되어 원래 GitHub 리포지토리의 일부가 됩니다.이 비디오에서는 다음을 배웠습니다.
- 이 비디오에서는 모든 구성 요소에 대한 리포지토리를 만들고, Git Feature Branch 워크플로에 따라, 브랜치를 만들고, pull 요청을 사용하는 것이 좋은 방법이라는 것을 배웠습니다.

## 예시
- 이러한 것들은 모노 리포지토리라고 불리며 눈살을 찌푸리게 합니다.사람들은 종종 데모를 쉽게 하기 위해 여러 마이크로서비스가 포함된 단일 리포지토리인 “모노 리포지토리”를 만들지만 프로덕션 코드에서는 그렇게 해서는 안 됩니다.누군가가 관심 있는 코드를 찾기 위해 신경 쓰지 않는 코드를 많이 확인하지 않아도 되는 것은 아닙니다.

## 요약
- pull 요청을 검토한 후 코드가 완전하고 팀에서 설정한 표준을 충족하면 마스터 브랜치에 다시 병합되어 원래 GitHub 리포지토리의 일부가 됩니다.이 비디오에서는 다음을 배웠습니다. 이 비디오에서는 모든 구성 요소에 대한 리포지토리를 만들고, Git Feature Branch 워크플로에 따라, 브랜치를 만들고, pull 요청을 사용하는 것이 좋은 방법이라는 것을 배웠습니다.
