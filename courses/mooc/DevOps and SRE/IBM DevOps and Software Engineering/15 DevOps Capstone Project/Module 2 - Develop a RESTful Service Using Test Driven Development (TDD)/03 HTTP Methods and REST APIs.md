# HTTP Methods and REST APIs

> MOOC 실습 자료(Ungraded Plugin) · [원본 강의](https://www.mooc.org/learn/devops-capstone-project/ungradedWidget/OgkFh/http-methods-and-rest-apis)

## 개요
- HTTP 메서드와 관련 용어를 정의하고, REST API를 작성하기 위한 가이드라인과 모범 사례를 정리한 참고 자료.

## 내용
### 클라이언트-서버 아키텍처와 REST
- 인터넷은 클라이언트-서버 아키텍처에 의존 — 최종 사용자는 클라이언트와 상호작용하고, 서버는 애플리케이션·비즈니스 로직·데이터를 운영하는 **서비스(service)**를 담고 있음.
- 클라이언트와 서버 사이의 데이터 전송은 **HTTP**(Hypertext Transfer Protocol)를 통해 이뤄지며, 이 통신은 보통 **API**를 통해 일어남.
- 2000년에 클라이언트-서버 아키텍처를 위한 API 작성 가이드라인 모음인 **REST**(REpresentational State Transfer) API가 만들어짐.

### 요청과 응답의 구조
- 서비스는 **리소스(resource)**를 담고 있음. 클라이언트는 서비스 내 **엔드포인트(endpoint)**를 가진 **라우트(route)**를 통해 **요청 객체(request object)**로 리소스에 대한 **요청(request)**을 만듦. 애플리케이션은 그 요청에 답하기 위해 **응답 객체(response object)**를 클라이언트에 돌려보냄.
- **요청 객체**는 세 부분으로 구성: **URL**, **요청 헤더(request header)**, **요청 본문(request body)**. URL은 서비스와 그 안에서 조작되는 엔드포인트를 식별하며, **프로토콜, 호스트명, 경로, 쿼리 문자열**의 네 부분으로 구성됨. 요청 헤더는 user agent, host, content type, content length 등 요청하는 클라이언트의 리소스에 대한 메타데이터를 담음.
- 서버는 **헤더, 본문, 상태 코드**로 구성된 응답 객체로 응답 — 응답 본문에는 보통 클라이언트에 데이터를 제공하기 위한 **JSON payload**가 담김.

### HTTP 메서드
- REST API에서 클라이언트와 서비스 간 상호작용에 사용되는 가장 흔한 메서드: **GET, POST, PUT, DELETE, PATCH**.
- 메서드 이름은 그 메서드가 적용될 때 리소스에 무슨 일이 일어나는지를 설명. **PUT**과 **DELETE**는 같은 API 메서드를 여러 번 호출해도 같은 결과가 되는 **멱등성(idempotent)** 데이터를 만듦.
- 매개변수를 전달하는 3가지 방법: **URL 경로 매개변수(URL path parameter)**, **URL 쿼리 매개변수(URL query parameter)**, **헤더 매개변수(header parameter)**. 경로·쿼리 매개변수는 URL의 일부로 전달되지만, 헤더 매개변수는 브라우저가 서비스로 직접 전달.

### HTTP 상태 코드
| 상태 코드 범위 | 의미 |
|---|---|
| 200-299 | 모든 것이 정상(OK) |
| 300-399 | 리소스가 이동됨 |
| 400-499 | 클라이언트 측 오류 |
| 500-599 | 서버 측 오류 |

### RESTful API의 5가지 필수 요건(+1개 선택 요건)
1. API는 HTTP를 통해 관리·전달되는 리소스로 구성된 클라이언트-서버 아키텍처를 활용해야 함.
2. 클라이언트-서버 간 통신은 **무상태(stateless)**여야 함.
3. 데이터는 클라이언트 측 성능 향상을 위해 **캐시 가능(cacheable)**해야 함.
4. 인터페이스는 표준 형식으로 전송되어, 서버에 저장된 리소스와 클라이언트로 전송되는 표현(representation)이 분리되어야 함 — 전송되는 표현에는 클라이언트가 그 표현을 조작할 수 있을 만큼 충분한 데이터가 담겨야 함.
5. 요청과 응답은 **미들웨어(middleware)** 같은 여러 계층을 통해 통신 — 클라이언트와 서버는 흔히 서로 직접 통신하지 않음.
6. (선택) 리소스는 보통 정적이지만 실행 가능한 코드를 포함할 수도 있음 — 코드는 클라이언트가 요청할 때만 실행되어야 함.
- 무상태성의 의미: 클라이언트가 요청할 때 자신의 상태(state) 정보도 함께 서버에 전달해야 함 — 클라이언트와 서버 간의 모든 통신은 요청을 수행하는 데 필요한 모든 정보를 담아야 하며, 상태는 서비스가 아니라 클라이언트가 유지. 예를 들어 사용자가 데이터베이스 레코드를 보고 있고 그 레코드를 업데이트해야 한다면, 클라이언트는 어떤 레코드를 업데이트해야 하는지도 함께 보내야 함 — 서버는 현재 어떤 레코드가 보이고 있는지 모름.

### Flask의 `@app.route()`
- RESTful 서비스를 정의할 때 `@app.route()` 메서드를 사용 — 서비스로 향하는 URL의 라우트와, POST·GET 같은 선택적 HTTP 메서드 매개변수라는 두 매개변수를 받음. 라우트 매개변수는 `<username>` 같은 변수를 포함할 수 있음. 라우트의 루트는 `/`로 표현 — 예를 들어 `www.mywebsite.com/accounts`가 라우트가 되도록 하려면 `@app.route()` 함수에 `/accounts`만 라우트 매개변수로 지정하면 됨.

### REST API의 특성과 URL 형식 가이드라인
- 리소스 기반(resource-based)이어야 하며, 리소스의 집합을 설명. 동사가 아닌 명사만 포함. 단일 리소스를 가리킬 때는 단수 명사를, 리소스 컬렉션을 가리킬 때는 복수 명사를 사용. 항상 URL로 식별됨.
- 예시 비교:
  | RESTful하지 않은 API | RESTful한 대응 |
  |---|---|
  | `GET http://api.myapp.com/getUser/123` | `GET http://api.myapp.com/users/123` |
  | `POST http://api.myapp.com/addUser` | `POST http://api.myapp.com/users` |
  | `GET http://api.myapp.com/removeUser/123` | `DELETE http://api.myapp.com/users/123` |
- URL 형식 가이드라인: 디렉터리 구조의 계층 관계를 나타낼 때 슬래시(`/`) 사용 / 후행 슬래시(`/resource/`) 사용 지양 / 카멜 케이스가 아닌 하이픈 사용(`/my-resource`, `/myResource` 아님) / 밑줄(`_`) 사용 금지(`/my-resource`, `/my_resource` 아님) / 소문자 사용 / URL에 마침표(`.`) 사용 금지 / URL에 여러 하위 리소스와 ID를 포함할 수 있음(예: `GET /resource/{id}/subordinate/{id}`).

### 핵심 용어 정리
- **Service** — 애플리케이션의 일부를 구성하고 특정 목적을 수행하는 소프트웨어 구성 요소. 보통 클라이언트나 다른 서비스로부터 입력을 받아 출력을 생성.
- **HTTP** — 인터넷상의 클라이언트-서버 아키텍처가 리소스 데이터를 가져오거나 교환하는 데 사용하는 프로토콜.
- **API** — 두 서비스가 서로 통신할 수 있게 하는 정의와 프로토콜의 집합.
- **REST** — 두 구성 요소(보통 클라이언트와 서버) 간 인터페이스(API)를 작성하는 방법을 설명하는 아키텍처 가이드라인 집합. REpresentational State Transfer의 약자. 리소스를 식별하고 조작하는 표준적인 방법을 설명하며, 클라이언트와 서버 사이에 오가는 메시지가 자기 서술적(self-descriptive)이도록 보장.
- **Resource** — RESTful API의 근본 개념. 정의된 타입, 관련 데이터, 다른 리소스와의 관계, 그 리소스에 작동할 수 있는 메서드 집합을 가진 객체 — 보통 JSON 형식으로 정의되지만 XML일 수도 있음.
- **Request** — 클라이언트가 서버의 호스트에게 리소스에 접근하기 위해 만드는 요청. GET, POST, PUT, PATCH, DELETE 외에도 HEAD, CONNECT, OPTIONS, TRACE를 포함.
- **Route** — HTTP 메서드와 경로 루트로부터 리소스까지의 경로의 조합.
- **Endpoint** — REST API로 서버에서 접근되는 리소스의 위치 — 보통 API의 HTTP 메서드 안 URL로 식별됨.
- **Idempotent** — 동일한 요청을 여러 번 만들어도 집합의 원소가 변하지 않는 것을 설명 — PUT과 DELETE 메서드는 같은 API 메서드를 여러 번 호출해도 멱등성 데이터를 만듦.
- **URL Query Parameter** — 보통 JSON 형식의 키-값 쌍을 포함하며 경로와 `?`로 구분됨. 여러 키-값 쌍이 있으면 `&`로 구분 — 작업이 반환하는 결과에 적용할 필터를 전달하는 데 사용될 수 있음.
- **Stateless** — 클라이언트로부터 서버로의 모든 리소스 요청이 서로 독립적으로 일어남. 서버는 클라이언트 측 애플리케이션의 상태를 알지 못하므로, 이 정보는 매 요청마다 함께 전달되어야 함.

### HTTP 메서드별 상세 정의
- **GET** — 리소스의 표현(representation)을 가져오는 요청에 사용. 리소스를 수정해서는 안 되며 요청된 리소스의 표현만 반환해야 함.
- **POST** — 리소스를 생성하기 위해 서버로 데이터를 보내는 HTTP 메서드. `201 CREATED` 상태 코드를 반환해야 함.
- **PUT** — 리소스를 업데이트하거나 기존 리소스를 교체하는 HTTP 메서드. PUT을 연속으로 여러 번 호출해도 부작용이 없다는 점이 POST와 다름. 리소스가 존재하고 업데이트 가능하면 `200 OK`, 리소스가 없으면 `404 NOT_FOUND`를 반환해야 함.
- **DELETE** — 리소스를 삭제하는 HTTP 메서드. 리소스가 존재해 서버가 삭제할 수 있거나, 리소스를 찾을 수 없어(이미 삭제된 것으로 간주) `204 NO_CONTENT`를 반환.
- **PATCH** — 리소스에 부분적인 수정을 적용하는 HTTP 메서드.

## 요약
- REST API는 클라이언트-서버 아키텍처에서 HTTP 메서드(GET·POST·PUT·DELETE·PATCH)로 리소스를 조작하는 표준화된 방법이며, 요청/응답 객체(URL·헤더·본문)의 구조와 상태 코드 범위(2xx~5xx), 무상태·캐시 가능·계층화된 통신 같은 RESTful 필수 요건, 그리고 명사 기반·소문자·하이픈 사용 등의 URL 형식 가이드라인을 따라야 진정한 RESTful API로 인정받을 수 있다.
