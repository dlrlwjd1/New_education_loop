# Infrastructure as Code (IaC)

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/Iur6b/infrastructure-as-code-iac)

## 개요
- 인프라를 텍스트 코드로 기술하고 도구가 이를 읽어 서버·네트워크·스토리지를 구성하는 **Infrastructure as Code(IaC)** 개념, 선언적/명령적 접근 방식의 차이, Ansible을 예시로 한 동작 원리, 그리고 대표적인 IaC 도구들을 정리.

## 내용
### IaC란
- 인프라를 텍스트 형식으로 기술하는 방법 — 워드 프로세서 문서가 아니라, 실제로 시스템을 코드처럼 구성하는 데 사용할 수 있는 텍스트 파일 형식.
- 이 텍스트 코드를 IaC 도구에 건네면, 도구가 코드를 읽어 서버, 네트워크, 스토리지 등 필요한 핵심 인프라 요소를 구축.
- 이런 도구와 텍스트 코드를 사용하면 매번 모두가 **동일한 환경**을 얻게 되어 일관되고 반복 가능함. 텍스트 코드는 보통 **YAML** 형식으로 작성됨.

### 왜 IaC가 필요한가
- 시스템 설정을 수동으로 하는 것은 오류가 발생하기 쉽고 시간도 많이 걸림 — 템플릿이나 명령으로 필요한 스토리지·처리 능력 등에 따라 시스템을 설치·구성하는 방법을 기술 가능.
- DevOps 초기에는 **CMS(Configuration Management System)**가 이를 가능하게 했으며, 최신 IaC 도구보다 앞서 존재했음.
- 반복 가능한 구성 덕분에 같은 플랫폼을 빠르게 몇 번이고 프로비저닝하면서 매번 동일한 상태임을 확신할 수 있음.

### 선언적(Declarative) vs 명령적(Imperative) 접근
- **선언적 접근**: 프로비저닝하려는 인프라 리소스의 **원하는 상태(desired state)**를 명시하면, IaC 도구가 이 상태에 도달하는 방법을 결정 — 의존성을 처리하고 실행 순서를 알아서 올바르게 처리. 도구 예: Terraform, Puppet, SaltStack, CloudFormation, 그리고 어느 정도는 Ansible.
- **명령적 접근**: 원하는 상태에 도달하는 데 필요한 명령의 **구체적인 순서**를 직접 정의해야 함 — 의존성을 올바르게 맞추는 것은 사용자의 몫이며, 도구는 지정한 순서대로 명령을 실행. 도구 예: Chef, 그리고 어느 정도는 Ansible.

### Ansible의 동작 방식 — Inventory File과 Var File
- Chef는 Cookbook/Recipe를, Ansible은 Playbook/Play를 사용 — 본질적으로 같은 개념.
- **Inventory File**: IP 주소나 호스트명 형태의 서버·장치 목록을 담고 있으며, 웹 서버 전체나 DB 서버 전체 같은 서버 그룹핑도 지정 가능 — Ansible이 무엇을 대상으로 작업할지 아는 방법. Ansible 아키텍처의 가장 기본적인 구성 요소이며, Ansible/Playbook 실행 시 반드시 참조해야 함.
- **Var File**: Playbook이 장치나 장치 그룹에서 실행될 때 필요할 수 있는 관련 변수들을 담음 — 변수를 어떻게 정의하는지에 따라 Ansible이 원격 호스트/장치와 상호작용하는 방식을 제어 가능.
- **Playbook**: 여러 개의 **Play**를 담고 있음. Play는 각 서버/장치에서 수행할 지시사항을 담으며, 웹 서버 전체나 DB 서버 전체 같은 특정 그룹을 대상으로 할 수 있음. 즉 Playbook은 Ansible에게 내리는 재사용 가능한 Play(지시사항)들의 모음.
- Ansible은 Playbook을 읽고, Inventory에서 그 Play들에 적합한 서버가 어떤 것인지 판단한 뒤, 각 서버에서 Play를 실행 — 웹 서버·앱 서버·DB 서버를 만들거나, 웹 서버 2개와 앱 서버 3개를 만들거나, 기존 서버 설정을 변경하는 등 필요한 모든 구성 변경과 프로비저닝을 처리.
- 중요한 특징: Ansible은 **멱등적(idempotent)** — 서버가 이미 원하는 상태에 있으면 아무 영향을 주지 않음. 이 덕분에 Playbook을 다시 적용해도 무언가를 두 번 설치할 걱정을 하지 않아도 됨.

### IaC의 이점
- 개발·테스트·프로덕션(및 프로덕션 인프라의 스케일링/해제)을 위한 인프라 프로비저닝 과정을 극적으로 빠르게 함 — 티켓을 열고 누군가 수동으로 처리하기를 기다려야 하는 시간이 오래 걸리는 프로세스로 관리되던 레거시 인프라의 프로비저닝도 자동화 가능.
- 개발자는 샌드박스와 CI/CD 환경을 빠르게 프로비저닝할 수 있고, QA는 완전한 충실도(full-fidelity)의 테스트 환경을 빠르게 제공 가능.
- 프로비저닝 지식이 항상 조직에 남아 있도록 보장 — 과거에는 서버 구성 방법을 조직 내 소수만 알고 있었지만, 이 지식을 IaC로 코드화하면 누구나 필요한 것을 프로비저닝할 수 있고 직원 이직으로 인한 부족 지식(tribal knowledge) 손실에 대한 우려가 사라짐.
- 클라우드 컴퓨팅의 사용량 기반 비용 구조를 최대한 활용할 수 있게 해줌 — 인프라를 프로비저닝하고 확장하는 데 필요한 시간·노력·전문 스킬을 줄이고, 개발자가 배관 작업(plumbing)에 시간을 덜 쓰고 핵심 소프트웨어 솔루션에 더 집중할 수 있게 해줌.

### 주요 IaC 도구
- **Terraform**(HashiCorp, 무료·오픈소스) — 선언적 접근을 사용하며, 예상대로 동작할지 사전 실행 검사(pre-execution check)를 수행. Terraform이 기본 인프라를 프로비저닝하고 Ansible이 그 위에 소프트웨어를 구성하는 조합으로 자주 사용되는 클라우드 프로비저닝의 인기 도구.
- **Ansible**(오픈소스) — 서비스 간 오케스트레이션, 애플리케이션 배포, 클라우드 프로비저닝 등 IT 도구를 자동화. 익숙한 YAML 파일로 원하는 상태를 기술. 클라이언트 측 에이전트나 별도 보안 인프라가 필요 없어 설정이 간단하고 클라이언트에 모듈을 전달하기만 하면 됨 — IoT 장치 구성처럼 메모리가 제한된 환경에 이상적. 모듈은 클라이언트 측에서 실행되고 결과는 Ansible 서버로 다시 전송됨.
- **Chef** — 최종 상태 자체를 기술하기보다 그 상태에 도달하기 위한 필요한 단계를 기술. "Cookbook"을 사용해 시스템을 원하는 상태로 구성하는 다양한 프로세스를 기술. 인기 있고 지원이 많다는 강점이 있지만, Cookbook이 Ruby로 작성되어 팀에 Ruby 스킬이 필요하다는 단점.
- **Puppet** — 기존 플랫폼 어디서든 사용 가능. Chef와의 주된 차이는 Puppet이 선언적이라는 점 — 일부는 이를 선호하는 방식으로 여김.
- **SaltStack** — 유연한 타기팅 시스템으로 여러 머신에서 병렬로 명령을 실행하는 원격 실행 기능. 사용자가 여러 머신에 명시적으로 대상을 지정해 명령을 직접 내릴 수 있도록 설계됨.

## 요약
- IaC는 서버·네트워크·스토리지 같은 인프라를 YAML 등의 텍스트 코드로 기술해 도구가 자동으로 구축하게 함으로써 일관성·반복성·속도를 확보하는 방식이며, 원하는 상태만 명시하면 도구가 순서를 알아서 처리하는 **선언적**(Terraform, Puppet, SaltStack, CloudFormation) 접근과 명령의 순서를 직접 정의해야 하는 **명령적**(Chef) 접근으로 나뉘고, Ansible은 Inventory File(대상 서버)과 Var File(변수), Playbook/Play(지시사항)를 이용해 멱등적으로 인프라를 구성하는 대표적인 도구다.
