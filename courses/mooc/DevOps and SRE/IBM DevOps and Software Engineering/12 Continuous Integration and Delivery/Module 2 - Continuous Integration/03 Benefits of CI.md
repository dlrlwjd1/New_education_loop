# Benefits of CI

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/zqLTF/benefits-of-ci)

## 개요
- CI/CD의 4가지 핵심 이점(빠른 반응 시간, 낮은 통합 위험, 높은 코드 품질, 버전 관리 코드에 대한 신뢰)을 Pull Request 리뷰 과정의 구체적인 예시와 함께 설명.

## 내용
### 이점 1 — 더 빠른 반응 시간
- 코드를 변경해 원격 브랜치에 push할 때마다 코드가 테스트됨 — 테스트 실행을 잊어도 CI 도구가 대신 테스트함. 그다음 변경 사항이 빌드됨 — 빌드가 되는지 확인을 잊어도 CI 도구가 확인함.
- 모든 테스트가 통과했고 빌드가 깨지지 않았음을 알고 있으므로 솔루션을 고객에게 더 빠르게 전달 가능.

### 이점 2 — 낮은 코드 통합 위험
- 점점 더 작은 단위를 통합하기 때문 — 작은 변경은 무언가 잘못될 위험이 적음. 수십만 줄의 코드를 수백만 줄짜리 코드베이스에 통합하던 시절은 끝남.
- 이제는 예를 들어 10, 20, 30, 50줄 정도의 코드만 통합하면 되므로 다뤄야 할 코드가 많지 않음 — 변경이 적을수록 위험도 적음.

### 이점 3 — 더 높은 코드 품질
- 지속적으로 리뷰되고 테스트되기 때문 — 모든 Pull Request가 코드 리뷰의 기회. 코드 리뷰를 별도 작업으로 일정에 잡는 것은 잊어도 됨.
- 모범 사례: 누군가 Pull Request를 만들면 반드시 코드를 살펴봐야 함 — 테스트가 통과하기를 기다리는 동안 다른 사람의 눈으로 변경 사항을 보는 것은 항상 좋은 일.
- Pull Request 리뷰 중 "좋아 보인다"고 승인하거나, 제목은 A를 해야 한다고 되어 있는데 실제 코드는 A와 무관해 보이면 "왜 이걸 바꿨나요?"라고 물어볼 수 있음.
- 테스트가 모두 통과했는지, 코드 커버리지를 확인해야 함 — 예: 팀의 기준이 95% 코드 커버리지인데 91%밖에 안 나왔다면, 누군가 코드는 작성했지만 모든 코드 줄을 실행하는 테스트 케이스는 작성하지 않았을 수 있음.
- 이 경우 Pull Request를 승인하지 않고 "코드 커버리지가 떨어졌으니 아직 승인하지 않겠다"며 더 많은 테스트 케이스 작성을 요청할 수 있음 — 이후 커버리지가 95%를 넘으면 그때 승인.
- 이런 서로에 대한 모니터링이 개발팀에게 기대되는 모습 — 서로 모니터링하고, 돕고, 서로의 코드를 보고, 많은 코드 리뷰를 하기를 원함. 20,000줄보다 20줄짜리 코드 리뷰가 훨씬 쉽기 때문.
- 이것이 Pull Request를 하는 이유 — 코드에 대한 또 다른 시선을 확보해, 아무도 모르는 사이 치명적인 일이 벌어지는 것을 방지.

### 이점 4 — 버전 관리된 코드가 작동한다는 확신
- Continuous Delivery를 어떻게 할 것인가 생각해보면, Git 같은 소스 관리 시스템에 있는 코드에서 배포하게 됨 — Git에 있는 코드가 작동하는지 어떻게 아는가?
- 답은: CI 테스트를 실행했고 모두 통과했기 때문. 모든 변경 사항을 테스트하지 않으면 깨진 코드를 프로덕션에 배포할 수도 있음 — 그래서 master/main 브랜치에 있는 모든 것이 실제로 작동한다는 것을 아는 것이 매우 중요.

## 요약
- CI/CD는 모든 push마다 자동으로 테스트·빌드해 빠르게 반응하고, 작은 단위로만 통합해 위험을 줄이며, Pull Request마다 코드 리뷰와 커버리지 확인이 이뤄져(예: 95% 기준에 미달하면 승인 보류 후 테스트 추가 요청) 코드 품질을 높이고, 이 모든 검증 덕분에 버전 관리된 main 브랜치의 코드가 실제로 작동한다는 확신을 가지고 Continuous Delivery로 넘어갈 수 있게 해준다.
