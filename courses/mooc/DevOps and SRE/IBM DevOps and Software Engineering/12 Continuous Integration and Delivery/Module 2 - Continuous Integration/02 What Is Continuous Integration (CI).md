# What Is Continuous Integration (CI)?

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/VnSly/what-is-continuous-integration-ci)

## 개요
- CI의 정의와 핵심 특징(짧은 생명주기 브랜치, 빈번한 Pull Request, 자동화된 CI 도구)을 설명하고, 전통적인 개발 방식과 CI 기반 개발의 차이를 대비.

## 내용
### CI의 정의
- CI(Continuous Integration)는 이름 그대로 코드 변경 사항을 메인 코드베이스로 지속적으로 통합할 수 있게 해주는 자동화 프로세스.
- 개발자가 정기적으로 자신의 작업을 저장소에 통합해, 변경 사항이 master/main 브랜치에서 너무 멀리 벗어나지 않도록 함.
- 개발자가 소스 코드 저장소에 작업을 push하면, 일련의 테스트를 자동으로 실행해 손상(breakage)을 감지함으로써 소프트웨어가 계속 제대로 작동하도록 보장.
- CI는 팀 전반의 협업 개발을 가능하게 함 — 개발자가 단위 테스트 실행을 잊더라도 CI 프로세스가 대신 테스트를 실행하고 실패를 알려줌. 이는 통합 버그를 더 일찍 식별하는 데 도움.

### 전통적인 개발 방식
- CI를 다루기 전에 전통적인 개발 방식을 먼저 이해해야 함 — 전통적으로 개발자는 큰 기능이나 수정 사항을 자신의 개발 브랜치에서 작업하고 커밋함.
- 이런 브랜치는 오래 존재하고, 범위가 크며, 일반적으로 많은 코드 변경과 편집이 필요함. 개발이 완료된 후에야 테스트되고 메인 브랜치에 병합되어 프로덕션용으로 빌드됨.
- 이 개발 방식은 메인 브랜치와 개발 브랜치 사이의 **드리프트(drift)**를 유발할 수 있음.

### CI의 핵심 특징 1 — 짧은 생명주기 브랜치(Short-lived Branches)
- CI에서 개발자는 코드에 기여하는 작은 기능을 개발하는 **짧은 생명주기의 feature 브랜치**에서 작업 — 목적이 그 작은 기능 개발뿐이므로 메인/master 브랜치에 병합된 후 삭제됨.
- 이점: feature 브랜치와 메인 브랜치 사이에 발생할 수 있는 드리프트를 줄임. 중요하거나 필수적인 수정 사항을 여러 개발자가 각자 다르게 구현하는 상황을 방지 — CI에서는 개발자가 테스트되고 병합될 단일 수정을 빠르게 구현해 병렬적인 변경을 줄임.
- 결과적으로 매번 push될 때마다 변경 사항을 확인해왔기 때문에 대규모 코드 리뷰를 거칠 필요 없이 전체적으로 코드를 더 빠르게 배포 가능.

### CI의 핵심 특징 2 — 빈번한 Pull Request
- master/main 브랜치로 자주 Pull Request를 보내는 것이 모범 사례 — 이 Pull Request는 특정 목적을 수행하는 코드 업데이트를 담고 있어, 코드 변경을 더 깔끔하고 이해하기 쉽게 만듦.
- Pull Request는 저장소 관리자나 소유자의 승인이 있어야 성공적으로 병합됨 — 최소한 자기 자신의 Pull Request는 승인할 수 없어야 함. 모든 변경에 최소 두 사람의 눈이 있어야 함을 보장하기 위함.
- 이 빈번한 Pull Request는 더 큰 퍼즐의 작은 조각 역할을 해, 가장 최신 코드 위에 쉽게 쌓아 올릴 수 있게 함. 이점:
  - 모든 Pull Request가 리뷰되어야 하므로 개발자 간 협업이 증가.
  - 개발자가 빠르게 반응할 수 있게 함 — 필요한 변경을 테스트해 프로덕션에 더 빨리 반영할 수 있어 솔루션이 고객에게 더 빨리 도달.
  - CI의 빈도 덕분에 지금까지 어느 정도의 기능을 구축했는지 정확히 알 수 있어 관리 위험이 줄어들고, 필요한 기능을 제때 전달할지 예측하는 능력이 향상됨.

### CI의 핵심 특징 3 — 자동화된 CI 도구
- CI는 자동화될 수 있음 — 자동화된 CI 도구는 웹훅(webhook)을 이용해 Pull Request나 파일 변경 같은 이벤트를 구독하고, 이것이 워크플로우를 트리거함.
- 그 워크플로우는 애플리케이션을 빌드하는 것 등 무엇이든 될 수 있음. 완료되면 이런 도구들이 빌드 성공/실패 메시지로 결과를 알려줌.
- 이 도구들은 파일 변경이나 Pull Request가 전체 애플리케이션을 망가뜨리지 않도록 확인하는 테스트를 실행 가능 — 이런 자동화 도구를 사용하면 코드를 테스트하고 확인하는 일이 지루하지 않게 개발 프로세스를 간소화할 수 있음.

## 요약
- CI는 짧은 생명주기 feature 브랜치를 활용해 코드를 작은 단위로 자주 통합하는 프로세스이며, 개발자들이 간결한 변경에 대해 자주 Pull Request를 논의하도록 장려해 협업을 촉진하고, 웹훅으로 이벤트를 구독해 빌드·테스트를 자동으로 실행하는 CI 도구들이 개발과 테스트를 간소화해 CI 구현을 쉽게 만들어준다.
