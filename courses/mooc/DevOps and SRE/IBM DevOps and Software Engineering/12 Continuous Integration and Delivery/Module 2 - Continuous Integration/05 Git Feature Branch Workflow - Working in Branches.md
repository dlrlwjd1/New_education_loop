# Git Feature Branch Workflow: Working in Branches

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/BGdIZ/git-feature-branch-workflow-working-in-branches)

## 개요
- Git이 DevOps에 왜 적합한지 설명하고, `git add`/`commit`/`push`/`fetch`/`pull`/`checkout`/`reset` 같은 핵심 명령어의 역할과, Git Feature Branch 워크플로우의 전체 흐름을 정리.

## 내용
### Git이란
- Linus Torvalds가 2005년 Linux 커널 개발을 위해 발명한 **분산형** 소스 코드 관리 도구 — 현재 가장 널리 쓰이는 버전 관리 시스템.
- 코드는 완전히 로컬에 있거나 원격 저장소에 보관되어 협업할 수 있음 — 모든 개발자가 코드의 **전체 사본**을 가짐(작업 중인 부분만 체크아웃하는 다른 버전 관리 시스템과 다른 점).
- 개발자는 매번 중앙 저장소에 연락하지 않고도 로컬에서 작업하고 변경 사항을 추적할 수 있음 — 중앙 저장소에 문제가 생겨도 로컬에 전체 사본이 있어 재구축 가능.
- GitHub, GitLab, BitBucket 등 다양한 저장소 호스트가 있음. GitHub은 오픈소스 프로젝트를 무료로 호스팅해 이전에는 좋은 구현 방법이 없었던 DevOps 방법론을 가능하게 함.
- DevOps가 Git의 덕을 보는 이유: 모든 규모의 프로젝트를 다룰 수 있고, 비선형적(non-linear) 협업을 가능하게 하며, 코드 품질을 보장하기 위한 버전 관리를 추적하기 때문.

### 핵심 Git 명령어
```bash
git add <file>       # 변경 사항을 스테이징 영역으로 이동
git commit            # 스테이징된 변경 사항을 로컬 저장소의 버전 이력에 커밋
git push              # 커밋을 원격 저장소로 푸시(-u <원격 브랜치명>은 최초 1회만 필요)
git fetch             # 원격 저장소의 최신 메타데이터(버전 이력·브랜치 정보)만 가져옴, 코드는 받지 않음
git pull              # 최신 메타데이터와 실제 변경 사항을 모두 가져와 병합
git checkout <branch> # 작업 공간을 다른 브랜치로 전환
git checkout .        # 마지막 커밋 상태로 되돌림
git reset --soft      # 커밋을 취소하되 변경 사항은 스테이징 영역에 유지
git reset --hard      # 특정 커밋까지 로컬에서 만든 모든 변경 사항을 완전히 지움(매우 강력하고 위험하니 주의)
```
- **스테이징 영역(staging area)**은 커밋하고 싶은 변경 사항(전부가 아닐 수도 있음)을 명확히 구분하는 공간 — 마트에 갈 때 쇼핑 목록을 만드는 것과 비슷함: 다음 커밋 때 무엇을 반영하고 싶은지 정리하는 목록.
- `git commit`은 로컬 저장소에만 영향을 주고 다른 사람에게는 영향이 없음. 이후 `git push`로 원격 저장소에 반영하면 모두가 보고 접근 가능해짐.
- `git fetch`는 실제로 최신 코드를 받아오지는 않고 변경 사항이 있는지만 확인할 수 있게 해줌 — 잠재적인 머지 충돌을 피할 수 있게 해줌. 실제 변경 사항을 받아 자신의 작업 공간에 병합하려면 `git pull` 사용.
- `git checkout`은 브랜치 간 전환뿐 아니라 이전 커밋으로 되돌아가는 데도 사용 가능 — 어떤 경로로 갔다가 "이건 나한테 안 맞는다, 마지막으로 커밋한 상태로 돌아가고 싶다"고 결정했을 때 유용.

### Git Feature Branch 워크플로우 — 시각적 흐름
1. 로컬에 없다면 저장소를 클론.
2. 새 브랜치 생성 — 작업하는 모든 새 기능마다 새 브랜치를 만들어야 함.
3. 코드를 작업하며 변경 사항을 커밋 — 커밋은 돌아갈 수 있는 체크포인트를 제공하므로 필요한 만큼 자주 커밋해도 됨.
4. 원격 브랜치로 push — 원격 백업을 갖는 것과 같으므로 필요할 때마다, 최소 하루 한 번은 push할 것을 권장.
5. Pull Request를 염 — 작업이 끝났을 때일 수도, 개발 도중 코드를 보여주고 질문하기 위해서일 수도 있음. 여기서 **논의와 리뷰**가 이뤄짐 — 이것이 소셜 코딩의 일부.
6. 변경 사항이 리뷰되면 테스트 환경에 배포됨.
7. 모든 테스트가 통과하면 메인/master 브랜치로 병합.

### 실제 예시 워크플로우
1. 항상 최신 코드로 시작 — main 브랜치를 체크아웃하고 새 변경 사항을 로컬 작업 공간으로 pull.
2. 새 기능 작업 시 그 기능을 위한 새 브랜치를 생성.
3. 변경을 마치면 `git add <파일명>` 또는 `git add .`로 스테이징하고 설명적인 메시지와 함께 커밋.
   - `git add .`는 주의 필요 — `.gitignore` 파일이 잘 관리되지 않으면 의도치 않은 파일이 커밋될 수 있음. `git status`로 무엇이 커밋될지 항상 확인 가능.
4. 그다음에야 변경 사항을 원격 저장소로 push하고 변경 사항이 있는 브랜치를 추적. `-u <원격 브랜치명>` 옵션은 원격 브랜치를 처음 만들 때만 필요하고, 이후 커밋은 이 옵션 없이 push 가능.
- 전체 과정의 핵심 3요소: 사용 가능한 최신 코드로 작업, 변경 사항을 저장할 새 브랜치 생성, 변경 사항을 push할 원격 브랜치 설정.
- 다음날 추가 작업을 하고 새 변경 사항을 push해야 한다면 같은 과정(스테이징 → 설명적 메시지로 커밋 → 원격 저장소로 push)을 반복.

## 요약
- Git은 모든 개발자가 코드 전체 사본을 갖는 분산형 버전 관리 시스템으로 DevOps에 적합하며, `git add`(스테이징) → `git commit`(로컬 커밋) → `git push`(원격 반영), `git fetch`(메타데이터만 확인) vs `git pull`(실제 병합), `git checkout`(브랜치 전환/되돌리기), `git reset --soft`/`--hard`(커밋 취소) 같은 핵심 명령어를 이용해 Feature Branch 워크플로우(클론 → 브랜치 생성 → 커밋 → push → Pull Request → 리뷰·테스트 → 병합)를 따르는 것이 깨끗하고 간결하며 고품질의 코드를 만드는 표준적인 방법이다.
