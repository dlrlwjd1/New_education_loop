# Continuous Delivery Key Principles

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/5uP3f/continuous-delivery-key-principles)

## 개요
- Continuous Delivery의 5가지 핵심 원칙: 품질 내장, 작은 배치 단위 작업, 반복 작업의 자동화, 지속적 개선, 그리고 시스템 실패에 집중하는 책임 문화.

## 내용
### 원칙 1 — 품질을 내장하라(Build in Quality)
- 모든 단계에 품질이 내장되어 있어야 함 — 품질은 공짜가 아니므로 계획해야 함. 코드를 지속적으로 리뷰함으로써 달성 가능 — 모든 Pull Request가 코드 리뷰와 품질 검사의 기회.
- 파이프라인 전체에 걸쳐 모든 것이 제대로 되어 있는지 확인하는 데 결정적.

### 원칙 2 — 작은 배치 단위로 작업하라(Work in Small Batches)
- 사용자 스토리를 작게 만들어야 하는 이유 — 작은 변경이 더 낫고, 변경이 적을수록 위험도 적음.
- 이런 변경 사항을 기본 코드와 지속적으로 통합해, 다른 모두가 작업하는 기반에서 너무 멀리 벗어나지 않도록 해야 함.

### 원칙 3 — 사람은 반복 작업이 아니라 문제 해결에 뛰어나다
- 사람은 문제를 해결하는 데는 뛰어나지만 반복에는 그다지 능숙하지 않음 — 그래서 사람에게 반복 작업을 시켜서는 안 됨. 실제로 사람은 반복 작업을 형편없이 수행함(쉽게 지루해지고 산만해짐).
- 테스트 주도 개발로 사람의 코드를 계속 끌어와 수동으로 테스트를 돌릴 수도 있지만, 왜 컴퓨터가 애초에 하도록 설계된 이런 반복 작업을 컴퓨터의 힘으로 처리하지 않는가? 컴퓨터는 이런 작업을 사람보다 더 빠르고 효율적으로 수행 가능.
- 예: GitHub Actions 같은 애플리케이션이 그 일을 할 수 있으며, 그러면 코드를 수동으로 pull해서 테스트할 필요가 다시는 없어짐.

### 원칙 4 — 지속적 개선을 가능하게 한다
- 무언가를 더 자주 할수록 그 일에 더 능숙해지고 실패할 가능성이 줄어듦.
- 각 변경 사항을 이미 알려진 정상 작동 환경에 전달함으로써, 항상 자신이 어디에 있는지, 언제 무언가가 깨졌는지 알 수 있어야 함.

### 원칙 5 — 모두가 자신의 몫에 책임을 진다
- 빌드가 깨지면 "누구 잘못이야?"라며 손가락질하는 상황이 아님 — "무엇이 잘못되었는가?"와 "앞으로 이런 일이 발생하지 않게 하려면 어떻게 해야 하는가?"를 물어야 함.
- 고려해야 할 것은 사람의 실패가 아니라 **시스템의 실패** — 시스템이 사람들을 어떻게 실망시켰는가를 봐야지, 그 반대가 아님.

## 요약
- Continuous Delivery의 5대 핵심 원칙은 모든 Pull Request를 코드 리뷰 기회로 삼아 품질을 내장하고, 위험을 줄이기 위해 작은 배치로 작업하며, 사람이 서툰 반복 작업은 GitHub Actions 같은 도구로 자동화하고, 알려진 정상 환경에 자주 전달함으로써 지속적 개선을 이루며, 문제가 생기면 개인을 탓하기보다 "무엇이 잘못됐고 어떻게 재발을 막을지"를 묻는 시스템 중심의 책임 문화를 갖는 것이다.
