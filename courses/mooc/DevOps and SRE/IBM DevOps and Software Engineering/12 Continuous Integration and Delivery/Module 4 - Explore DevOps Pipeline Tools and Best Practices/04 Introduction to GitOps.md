# Introduction to GitOps

> MOOC 영상 · [원본 강의](https://www.mooc.org/learn/continuous-integration-and-continuous-delivery-ci-cd/lecture/LbGoA/introduction-to-gitops)

## 개요
- GitOps의 정의와 핵심 원칙, 이점, 그리고 CI 파이프라인과 별도의 선언적 Config 저장소·GitOps Agent가 함께 작동하는 GitOps 워크플로우 전체를 설명.

## 내용
### GitOps가 필요한 배경
- 전통적인 배포 방식은 업데이트를 위해 개발팀과 운영팀 사이의 수동적인 소통에 의존 — 자동화와 버전 추적이 부족했음. 현대 소프트웨어 시스템에서 개발·운영 작업을 효율적으로 실행하는 배포 프로세스가 필요해짐.

### GitOps란
- "Git 기반 Ops(Git powered Ops)"라고도 불리며, 애플리케이션 개발에 쓰이던 DevOps 모범 사례(협업, 버전 관리, 컴플라이언스 등)를 인프라 자동화에 적용하는 운영 프레임워크.
- 배포 과정을 셸 스크립트로 인코딩하거나 배포된 시스템의 원하는 상태를 YAML 파일로 기술하는 것을 중심으로 함 — 이 파일들은 Git에서 버전 관리되어, 자동화 도구가 시스템 상태에 대한 변경을 눈에 보이고 감사 가능한 방식으로 구현할 수 있게 함.
- GitOps의 핵심은 Git Pull Request를 활용해 인프라와 애플리케이션 설정을 관리하는 실천에 있음 — Git 저장소를 시스템의 전체 상태를 아우르는 **단일 진실 공급원**으로 삼음. 이는 가시성과 감사 가능성을 보장하고 시스템 상태에 가해진 변경에 대한 명확한 기록을 제공.
- 변경 사항의 추적 가능성 자체는 새로운 것이 아니지만, GitOps는 리뷰·Pull Request·태깅 같은 이 원칙들을 인프라와 애플리케이션 설정에도 적용해, 팀이 애플리케이션 소스 코드에 대해 누리는 것과 동일한 보증을 받을 수 있게 함.

### GitOps의 핵심 원칙
- **시스템 정의를 코드로(System Definition as Code)** — 시스템 설정을 코드로 취급해 Git에 저장·버전 관리함으로써 단일 진실 공급원 역할을 하게 함. 이 접근은 시스템 변경의 손쉬운 롤아웃과 롤백을 가능하게 함.
- **원하는 시스템 설정의 버전 관리와 정의** — 시스템의 원하는 설정을 Git에 저장·버전 관리함으로써 변경 사항을 쉽게 관리·추적 가능.
- **Pull Request를 통한 변경 적용** — Git 변경 사항이 Pull Request를 가능하게 하고 이를 자동으로 설정에 적용 — 저장된 설정에 변경이 적용되는 방식을 쉽게 관리하고, 다른 팀원에게 리뷰를 요청하고, CI 테스트를 실행 가능. 게다가 클러스터 자격 증명을 누구와도 공유할 필요가 없음 — 설정을 가져오는 Git 저장소에 대한 접근만 있으면 됨.
- **드리프트 없는 컨트롤러** — 원하는 시스템 상태가 Git에 존재하므로, 현재 시스템 상태가 원하는 시스템 상태와 일치하는지 확인하는 소프트웨어만 있으면 됨 — 이 소프트웨어는 상태가 다르면 스스로 치유(self-heal)하거나 드리프트를 알려줄 수 있어야 함.

### GitOps의 이점
- **지속적 배포(Continuous Deployment)** — 인프라와 애플리케이션 변경을 배포하는 과정을 자동화 가능하게 함. Git 저장소가 단일 진실 공급원이므로, 저장소에 push된 모든 변경이 자동화된 배포 프로세스를 트리거해 시스템에 빠르고 신뢰성 있는 업데이트를 보장.
- **버전 관리와 추적 가능성** — Git의 버전 관리 기능을 활용해 인프라와 애플리케이션 설정에 가해진 변경의 완전한 이력을 제공 — 책임성을 부여하고 개발자가 최소한의 위험으로 이전 버전으로 쉽게 되돌릴 수 있게 함.
- **일관성과 재현성** — 버전 관리되는 설정에 의존함으로써 일관되고 재현 가능한 배포 프로세스를 강제. Kubernetes와 마찬가지로, Git은 시스템의 원하는 상태에 대한 정의를 담고 있고 자동화된 프로세스가 실제 상태가 원하는 상태와 일치하도록 보장 — 설정 드리프트를 줄이고 시스템 신뢰성을 향상.
- **협업과 리뷰** — Pull Request와 코드 리뷰 같은 Git의 협업 기능을 인프라·애플리케이션 설정 변경에도 적용해 협업을 촉진.
- **감사 가능성과 컴플라이언스** — Git 저장소가 시스템에 가해진 모든 변경을 추적해 중앙화되고 감사 가능한 기록을 제공 — 금융이나 의료처럼 특정 정책·규제 준수가 결정적인 규제 산업에서 감사 가능성과 컴플라이언스를 향상.
- **Infrastructure as Code** — 인프라 설정을 Git 저장소에 저장된 코드로 정의·관리하는 Infrastructure as Code 패러다임을 받아들임.

### GitOps 워크플로우
1. 개발자가 애플리케이션 소스 코드를 변경하고 리뷰를 위해 Pull Request로 제출.
2. 승인된 변경이 main 브랜치로 병합되어 **CI 파이프라인**을 트리거.
3. CI 파이프라인이 변경을 감지해 빌드 과정을 시작하고, 아티팩트 저장소에 저장되는 아티팩트를 만듦.
4. **SRE(Site Reliability Engineer)**는 운영 측 환경 설정을 별도의 **선언적 Config 저장소(Declarative Config Repo)**를 통해 관리 — 설정을 변경하고 리뷰를 위한 Pull Request 생성 과정을 따름. 승인되면 이 변경이 선언적 Config 저장소의 main 브랜치로 병합.
5. 목표 환경 아키텍처는 **GitOps Agent** 컴포넌트를 도입해 Git 저장소와 목표 환경 사이의 매끄러운 동기화를 보장 — 이 에이전트는 선언적 Config 저장소의 변경을 지속적으로 모니터링. 변경이 감지되면 GitOps Agent가 저장소에서 최신 설정을 자동으로 가져와 환경에 그 변경을 적용.
6. GitOps 솔루션이 아티팩트 저장소에서 적절한 빌드를 가져와 그 상태 변경을 클라우드 리소스에 적용.
- GitOps 접근의 아름다움은 시스템의 보안과 무결성을 유지하면서 수동 개입의 필요성을 없앤다는 것 — 개발자나 SRE는 IaC 저장소에서 Git 변경을 되돌리기만 하면 그만큼 쉽게 과정을 역전(reverse)시킬 수 있음.

## 요약
- GitOps는 Git Pull Request를 활용해 인프라·애플리케이션 설정을 관리하는 실천으로, 시스템 설정을 코드로 정의해 Git을 단일 진실 공급원으로 삼고 Pull Request를 통한 자동화된 설정 적용, 드리프트를 감지·치유하는 컨트롤러라는 원칙 위에서 지속적 배포·버전 관리·일관성·협업·감사 가능성·Infrastructure as Code라는 이점을 제공하며, 실제 워크플로우에서는 애플리케이션 코드용 CI 파이프라인과 별개로 운영 측 선언적 Config 저장소를 SRE가 관리하고, GitOps Agent가 이 저장소의 변경을 지속적으로 모니터링해 목표 환경에 자동으로 동기화한다.
