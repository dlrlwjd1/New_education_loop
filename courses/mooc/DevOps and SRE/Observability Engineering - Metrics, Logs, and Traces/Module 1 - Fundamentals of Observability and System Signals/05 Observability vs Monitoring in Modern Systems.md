# Observability vs Monitoring in Modern Systems (현대 시스템에서 관찰 가능성 vs 모니터링)

> 강좌: Observability Engineering: Metrics, Logs, and Traces · 모듈 1: Fundamentals of Observability and System Signals

## 개요
- 모니터링이 어떻게 진화했는지, 현대 시스템이 왜 전통적 가정을 무너뜨리는지, 관찰 가능성의 진정한 의미, 그리고 상황별로 어떤 접근을 선택할지 다룬다.

## 내용

### 전통적 시스템의 모니터링
- **안정적·예측 가능한 환경**에서 진화. 서버·애플리케이션이 오래 유지되고 변경이 드물고 통제됨.
- 서버 상태 메트릭(**CPU·메모리·디스크·가동시간**) 중심 — 인프라가 정적이라 이 신호로 전체 상태 대표 가능.
- **고정 배포·정적 인프라** → 토폴로지·자원 식별이 일관되게 유지된다고 안전하게 가정.
- **사전 정의 임계값 + 규칙 기반 경고**로 구동 — 실패 패턴이 과거 경험으로 이미 알려져 있어 잘 작동. → **알려진 장애 조건 탐지** 중심.

### 현대 시스템의 차이
- **동적 스케일링(dynamic scaling)** → 자원이 계속 추가·제거되어 동작 예측 불가.
- **마이크로서비스** → 복잡한 서비스 간 의존성, 장애 영향 추적 어려움.
- **임시 워크로드(temporary workloads)** → 서비스가 짧게만 존재해 고정 메트릭으로 추적 곤란.
- → **규칙 기반 경고가 새롭게 생겨나는 장애**(사전에 예상 못 한 문제)를 탐지하지 못함.

### 관찰 가능성의 전환
- 사전 정의 조건 충족 여부만 확인하는 게 아니라, **텔레메트리로 시스템 동작을 이해**하고 시스템이 무엇을 하는지 **새로운 탐색적 질문**을 던지게 함.
- 핵심: 이미 예상한 장애 탐지가 아니라 **알려지지 않은/예상치 못한 문제 조사** → 실패 방식을 미리 예측할 수 없는 복잡·분산 환경에서 특히 가치.
- **메트릭·로그·트레이스 결합**으로 성능·동작·상호작용에 대한 깊은 맥락 제공 → 전체 실행 경로, 의존성, 미묘한 문제 파악.
- **시스템 설계·텔레메트리 품질에 의존** — 의미 있는 고품질 신호를 노출하도록 의도적으로 계측해야 정확한 통찰 도출.

### 언제 무엇을 쓰나
| 상황 | 접근 |
|------|------|
| 알려진 상태 지표 추적, 예측 가능·반복되는 장애 조건 탐지, 안정성 확인 | **모니터링(Monitoring)** |
| 알려지지 않은·복잡한 문제 조사, 분산·동적·클라우드 네이티브 아키텍처 운영 | **관찰 가능성(Observability)** |
- 실무에서 둘은 **함께 작동**: 모니터링은 안정성 제공, 관찰 가능성은 깊은 이해 가능.

## 요약
- 전통 **모니터링**은 알려진 동작의 **안정적 시스템**용, **관찰 가능성**은 **현대의 복잡·동적 아키텍처**용으로 설계되었다.
- 언제 모니터링을, 언제 관찰 가능성을 쓸지 이해하면 **알려진 문제와 알려지지 않은 문제 모두에 자신 있게 대응**할 수 있다.
