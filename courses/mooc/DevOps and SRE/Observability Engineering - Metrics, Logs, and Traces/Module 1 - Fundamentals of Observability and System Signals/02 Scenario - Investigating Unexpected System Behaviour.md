# Scenario: Investigating Unexpected System Behaviour (예상치 못한 시스템 동작 조사 시나리오)

> 강좌: Observability Engineering: Metrics, Logs, and Traces · 모듈 1: Fundamentals of Observability and System Signals

## 개요
- 프로덕션에서 성능 문제가 어떻게 나타나는지, 그리고 이를 이해·진단·해결하는 데 왜 **관찰 가능성(observability)**이 필수인지 시나리오로 설명한다.

## 내용

### 문제 상황 — 시스템 신호 vs 사용자 경험의 괴리
- 성능 문제는 명백한 장애가 아니라 **서비스·인프라·의존성 간 복잡한 상호작용**에서 발생.
- 피크 시간대에 트래픽 증가로 요청이 느려지고, 일부 사용자는 간헐적 실패·지연 경험.
- 대시보드는 **건강해 보이는 차트**를 보여줌 — 시스템은 기술적으로 정상 작동. 하지만 **왜 성능이 저하되는지 설명하지 못함**.
- → **시스템 신호와 사용자 경험 사이의 간극**이 강한 관찰 가능성 도입 전 가장 흔한 과제.

### 개별 신호의 한계
| 신호 | 제공하는 것 | 한계 |
|------|-------------|------|
| **메트릭(Metrics)** | 지연(latency)·오류율(error rate) 상승 등 이상 지표 확인 | 고수준이라 **어느 서비스·요청 경로·의존성**이 원인인지 실행 세부 정보 부족 |
| **로그(Logs)** | 이벤트·오류·활동의 상세 기록 | 여러 서비스에 흩어지고 형식이 제각각 → 수동 상관에 시간·오류 발생, 실패 지점 놓치기 쉬움 (구조화 부재 시 반응적·비효율적) |
| **트레이스(Traces)** | 요청이 서비스 전반을 어떻게 이동하는지 | **엔드투엔드 가시성·일관된 trace context** 없으면 지연 위치 파악 어려움, 의존성이 예측 불가하게 보임 |

### 관찰 가능성의 본질 — 상관(Correlation)
- **관찰 가능성** = 시스템의 **출력을 분석해 내부 상태를 이해**하는 능력.
- 메트릭·로그·트레이스를 **개별 데이터 소스로 취급하지 않고 서로 상관(correlate)**시키는 데 초점:
  - **메트릭** → 비정상 동작 강조
  - **로그** → 상세 맥락 제공
  - **트레이스** → 요청 흐름 드러냄
- 이 신호들이 연결되면 예상치 못한 장애에도 **정확한 이해** → 빠른 진단, 다운타임 감소, 자신감 있는 운영.

## 요약
- 현대 시스템 장애는 **고립된 신호(isolated signals)**로는 효과적으로 이해할 수 없다.
- 메트릭·로그·트레이스는 각각 가치 있지만, **진정한 이해는 이들을 함께 상관**시킬 때 나온다.
- 관찰 가능성은 흩어진 데이터를 **실행 가능한 지식**으로 바꿔 조기 탐지·효율적 해결을 가능하게 하며, 시스템이 복잡해질수록 **선택이 아닌 기반 역량**이 된다.
