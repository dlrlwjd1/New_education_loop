# Observability Challenges in Kubernetes Environments (쿠버네티스 환경의 관찰 가능성 과제)

> 강좌: Observability Engineering: Metrics, Logs, and Traces · 모듈 3: Distributed Tracing and End-to-End Observability

## 개요
- 쿠버네티스(Kubernetes)가 왜 관찰 가능성을 바꾸는지, 어떤 고유한 과제를 만드는지, 그리고 팀이 가시성을 유지하기 위해 어떻게 관찰 관행을 적응시키는지 설명한다.

## 내용

### 쿠버네티스가 관찰 가능성을 바꾸는 이유
- 컨테이너·파드(pod)·서비스로 인프라를 추상화하고 **동적으로 스케줄링**.
- 워크로드가 고정 서버에 묶이지 않고 수요에 따라 자동 이동·재시작:
  - **동적 워크로드 스케줄링** — 수동 개입 없이 스케일 업/다운.
  - **단명(ephemeral) 리소스** — 파드·컨테이너가 잠깐만 존재.
  - **애플리케이션이 인프라와 분리(decoupled)** — 어디서 어떻게 실행되는지 직접 가시성 감소.
- → **시스템 토폴로지가 끊임없이 변함** → 정적 모니터링이 무력화.

### 고유한 과제
- 파드가 초·분 단위로 생성·소멸 → 런타임 환경이 계속 변함.
- 수요 기반 자동 스케일 → 자원 사용·트래픽 패턴 급변.
- **파드 이름·IP 주소가 계속 변함** → 전통 도구의 고정 호스트 가정 붕괴.
- 잦은 churn 때문에 **실시간·중앙 수집·저장하지 않으면 메트릭·로그가 빠르게 사라짐**.
- → 정적 모니터링 모델은 쿠버네티스에서 고전, **변하는 워크로드를 자동 발견·적응·추적**하는 관찰 시스템이 필수.

### 여러 계층에 걸친 가시성
| 계층 | 역할 |
|------|------|
| **노드(Node)** | 컴퓨트·메모리·네트워킹 자원 제공 |
| **파드/컨테이너(Pod/Container)** | 앱 코드 실행, 노드 간 자주 이동 |
| **서비스/인그레스(Service/Ingress)** | 트래픽 라우팅·외부 접근 관리 |
- 각 계층이 자체 메트릭·로그·트레이스 생성 → **파편화된 가시성** → 신호를 **노드·파드·서비스에 걸쳐 상관(correlate)**해야 하며 이는 운영적으로 복잡.

### 도구별 해결
| 신호 | 도구 | 방식 |
|------|------|------|
| **메트릭** | **Prometheus** | 파드·노드 생성·소멸을 자동 발견(service discovery) → 변하는 워크로드에 매끄럽게 적응 |
| **로그** | **Fluent Bit** | 컨테이너 로그를 중앙 수집 → 파드 생애주기와 로그 분리 → 파드 종료·재시작 후에도 정보 보존 |
| **트레이스** | **Jaeger** | 마이크로서비스 전반 요청 추적, 트레이스 컨텍스트로 각 서비스가 동일 요청 내 역할 이해 |
- 셋이 통합 관찰 시스템으로 작동 → 지속 변화에도 엔드투엔드 가시성.

## 요약
- 쿠버네티스는 유연성·확장성을 주지만 **단명 리소스·변하는 IP·파편화된 계층** 등 큰 관찰 과제를 만든다.
- **쿠버네티스 인식(K8s-aware) 도구**(Prometheus 자동 발견, Fluent Bit 중앙 로그, Jaeger 트레이스)로 가시성을 회복하고 신뢰성 있게 운영·트러블슈팅한다.
