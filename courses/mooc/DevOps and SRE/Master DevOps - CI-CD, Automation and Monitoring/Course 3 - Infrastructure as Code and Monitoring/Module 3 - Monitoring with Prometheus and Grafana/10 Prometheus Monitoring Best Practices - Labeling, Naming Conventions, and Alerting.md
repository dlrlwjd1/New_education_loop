# Prometheus Monitoring Best Practices: Efficient Labeling, Naming Conventions, and Alerting Strategies

## 개요
- Prometheus를 효과적으로 활용하기 위한 레이블링 전략, 지표 이름 규칙, 알림 전략의 베스트 프랙티스를 정리.

## 내용
### 1. 레이블링(Labeling) 전략
- 레이블(Label)은 지표에 차원을 더하는 key-value 쌍으로, 세밀한 필터링과 집계를 가능하게 함.
- **의미 있는 레이블 사용** — `env="production"`, `region="us-east"`, `service="frontend"`처럼 맥락을 제공하는 레이블을 사용해 타겟팅된 쿼리와 대시보드를 만들 수 있음.
- **높은 카디널리티(High Cardinality) 피하기** — 사용자 ID, 세션 ID처럼 고유 값이 매우 많은 레이블은 성능 저하와 저장 공간 증가를 유발.
- **일관성 유지** — 모든 레이블에 걸쳐 일관된 네이밍 스킴 유지(예: `region`, `location`, `geo`를 섞어 쓰지 않고 항상 `region`만 사용) — 지표 집계·쿼리를 효과적으로 만듦.
- **동적으로 변하는 레이블 피하기** — 타임스탬프나 고유 식별자처럼 자주 바뀌는 값은 시계열 수를 폭발적으로 늘릴 수 있어 피해야 함.

### 2. 네이밍 컨벤션(Naming Conventions)
- **소문자와 밑줄 사용** — 지표 이름은 소문자와 언더스코어로 단어를 구분(예: `http_requests_total`).
- **단위를 이름에 포함** — `_seconds`, `_bytes`, `_total` 등으로 무엇을 측정하는지 명확히 함(예: `request_duration_seconds`는 요청 처리 시간을 초 단위로 나타냄).
- **적절한 접두사(Prefix) 사용** — 도메인이나 애플리케이션을 나타내는 한 단어짜리 접두사로 관련 지표를 그룹화(예: `app_cpu_usage_seconds_total`).
- **약어 피하기** — `cpu`처럼 널리 통용되는 경우가 아니면 약어를 피해 명확성을 유지.

### 3. 알림(Alerting) 전략
- 알림은 Prometheus의 핵심 기능으로, 선제적인 문제 감지와 대응을 가능하게 함.
- **명확한 알림 규칙 정의** — 실제 문제를 나타내는 잘 정의된 조건을 기반으로 알림 설정(예: CPU 사용률이 5분간 90%를 초과하면 알림).
- **심각도(Severity) 레이블 사용** — `critical`, `warning` 등 심각도 수준을 부여해 대응 우선순위를 정함.
- **맥락 정보 제공** — 알림에 가능한 원인과 권장 조치를 담은 annotation을 포함해 더 빠른 해결을 지원.
- **알림 피로(Alert Fatigue) 방지** — 알림이 실행 가능한(actionable) 것이어야 하며, 중요하지 않은 이슈에 과도하게 알림을 걸지 않아야 팀이 중요한 알림에 둔감해지지 않음.
- **알림 규칙 정기적으로 테스트** — 알림 규칙이 시스템의 현재 상태를 올바르게 반영하며 적절히 트리거되는지 정기적으로 검증.

## 요약
- Prometheus를 효과적으로 운용하려면 의미 있고 일관되며 카디널리티가 낮은 레이블 전략, 단위를 포함한 명확한 소문자·언더스코어 네이밍 컨벤션, 그리고 심각도와 맥락 정보를 갖추고 알림 피로를 피하는 실행 가능한 알림 전략을 함께 적용해야 한다.
