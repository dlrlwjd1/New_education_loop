# Introduction to Monitoring

## 개요
- 모니터링의 정의와 유형, 중요성, 부재 시 문제점, 그리고 Observability(관측 가능성)와의 차이를 정리.

## 내용
### 모니터링이란
- IT 인프라와 애플리케이션의 성능·상태(health)·가용성을 추적하기 위해 데이터를 수집·분석·시각화하는 프로세스.

### 모니터링의 종류
1. **Infrastructure Monitoring** — 서버, CPU, 메모리, 디스크, 클라우드 리소스 등을 추적.
2. **Application Performance Monitoring(APM)** — 애플리케이션 응답 시간, 오류, 애플리케이션 레벨 지표를 모니터링.
3. **Network Monitoring** — 지연(latency), 패킷 손실, 대역폭 사용량을 추적.
4. **Security Monitoring** — 침입, 로그인, 의심스러운 활동을 점검.
- 예: CloudWatch로 EC2 CPU 사용량 추적, Datadog으로 애플리케이션 응답 시간 모니터링.

### 모니터링의 중요성
1. **시스템 안정성(Reliability)** — 문제를 조기에 발견해 장애나 중단을 예방.
2. **비용과 리소스 효율성** — 리소스 사용을 최적화하고 필요에 따라 스케일 업/다운.
3. **성능 최적화** — 느리거나 성능이 낮은 구성 요소를 찾아 개선.
4. **컴플라이언스와 보안** — 접근 로그를 추적해 규제 요건 충족(예: S3 버킷에 민감한 파일이 퍼블릭으로 노출되면 알림을 받아 보안 위반을 감지).

### 적절한 모니터링이 없을 때 발생하는 문제
1. **다운타임 증가** — 애플리케이션이 다운된 시점을 모르고, 사용자가 영향을 받고 나서야 문제를 인지.
2. **느린 트러블슈팅** — 로그가 어디에도 모니터링되지 않아 팀이 근본 원인을 찾는 데 많은 시간 소요.
3. **매출 손실** — 애플리케이션 불가용성이 판매 손실이나 고객 신뢰 저하로 이어짐.
4. **가시성 부족** — 무엇이 정상 작동하고 무엇이 실패하고 있는지 알 수 없음.
5. **보안 위험** — 침입이나 데이터 유출이 발생해도 알아채지 못함.

### Observability(관측 가능성)란
- 시스템의 로그, 지표(metrics), 트레이스(traces)를 분석해 시스템의 내부 상태를 측정할 수 있는 능력 — 복잡하거나 알려지지 않은 문제에 대한 깊이 있는 디버깅을 가능하게 함.

### Observability의 3대 요소(Three Pillars)
1. **Logs(로그)** — 이벤트 기록 — 언제 무슨 일이 있었는지 알려줌.
2. **Metrics(지표)** — CPU 사용량, 요청 속도(request rate) 같은 수치적 측정값.
3. **Traces(트레이스)** — 여러 서비스를 거치는 요청의 흐름을 보여줌 — 마이크로서비스 환경에서 지연(latency)이나 오류를 디버깅할 때 사용. 마이크로서비스에서는 어느 부분이 실패했는지 알기 어려운데, 트레이스로 특정 API 요청이 어떤 경로를 거쳐 어디서 실패했는지 전체 흐름을 파악 가능.

### 모니터링 vs Observability
| 구분 | 모니터링 | Observability |
|---|---|---|
| 목적 | 이미 알려진 문제(known issues) 감지 | 알려지지 않은/시스템 전반의 문제 탐구 |
| 초점 | 시스템 상태·성능 | 내부 동작과 의존 관계 |
| 접근 방식 | 반응적(Reactive) — 문제 발생 시 알림 | 능동적(Proactive) — 임의 탐색과 심층 디버깅 지원 |
| 대표 도구 | Prometheus, Nagios, Zabbix | Prometheus, Grafana, Jaeger |

## 요약
- 모니터링은 인프라·애플리케이션·네트워크·보안 데이터를 수집해 알려진 문제를 반응적으로 감지하는 반면, Observability는 로그·메트릭·트레이스라는 세 기둥을 통해 시스템 내부 상태를 능동적으로 탐구해 알려지지 않은 문제까지 심층 디버깅할 수 있게 한다.
