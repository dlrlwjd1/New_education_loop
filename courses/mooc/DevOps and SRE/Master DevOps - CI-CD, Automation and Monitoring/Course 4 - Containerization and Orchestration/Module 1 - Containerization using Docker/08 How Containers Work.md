# How Containers Work

## 개요
- 컨테이너의 전체 워크플로우(개발→이미지화→저장→배포→오케스트레이션→모니터링)와 컨테이너 아키텍처(인프라→OS→컨테이너 엔진→컨테이너), 대표 컨테이너 엔진들을 정리.

## 내용
### 컨테이너 워크플로우
1. **애플리케이션 개발·패키징** — 개발팀에서 받은 코드를 빌드해 패키지(RPM, Debian 패키지, Windows exe 등 배포 가능한 단일 아티팩트)로 만듦.
2. **컨테이너 이미지 생성·저장** — 패키지를 바탕으로 Dockerfile을 작성하고 `docker build` 명령으로 이미지를 생성한 뒤, Docker Hub, Nexus, JFrog 같은 컨테이너 레지스트리(중앙 저장소)에 저장.
3. **컨테이너 배포·실행** — 저장된 이미지를 사용해 컨테이너를 배포하고 실행.
4. **오케스트레이션(선택)** — 고가용성을 위해 컨테이너를 여러 개 운영하고(하나가 다운돼도 대응) 싶다면 Kubernetes 같은 오케스트레이션 도구로 고가용성과 장애 허용(Fault Tolerance)을 확보.
5. **모니터링·관리** — 컨테이너의 사용량, 오프라인 여부, 재시작·실패 여부 등을 지속적으로 모니터링하고 장애를 트러블슈팅.

### 컨테이너 아키텍처
1. **인프라(Infra)** — 물리 서버 또는 가상 서버 — CPU, 메모리, NIC(네트워크 인터페이스 카드), 스토리지로 구성.
2. **운영체제(OS)** — 인프라 위에 Linux나 Windows 같은 OS를 설치.
3. **컨테이너 엔진(Container Engine / Runtime, CRE)** — OS 위에 Docker, Podman, CRI-O, containerd 같은 컨테이너 런타임 설치.
4. **컨테이너(Container)** — 컨테이너 엔진 위에서 애플리케이션 A, B, C 등이 각각 자신의 바이너리·라이브러리·의존성과 함께 개별 컨테이너로 실행됨.

### 대표 컨테이너 엔진/런타임
- **Docker** — 가장 널리 알려진 컨테이너 런타임.
- **RKT(Rocket)** — 또 다른 컨테이너 런타임.
- **LXC(Linux Containers)**.
- **CRI-O** — OCI(Open Container Initiative)와 CRI(Container Runtime Interface) 이니셔티브에서 비롯된 컨테이너 런타임.
- **containerd, Podman, nerdctl** 등도 시장에 등장한 컨테이너 도구들.
- 실무에서 가장 널리 쓰이는 것은 **Docker, CRI-O, containerd**.

## 요약
- 컨테이너는 애플리케이션 개발·패키징 → 이미지 생성·레지스트리 저장 → 배포·실행 → (선택적) Kubernetes 오케스트레이션 → 모니터링·관리라는 워크플로우를 따르며, 아키텍처적으로는 인프라(서버) 위에 OS, 그 위에 Docker·containerd 같은 컨테이너 엔진, 그 위에 각 애플리케이션의 컨테이너가 계층적으로 쌓이는 구조를 가진다.
