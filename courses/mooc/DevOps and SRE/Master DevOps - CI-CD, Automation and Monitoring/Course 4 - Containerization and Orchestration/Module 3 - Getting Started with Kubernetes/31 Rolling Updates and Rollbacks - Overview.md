# Rolling Updates and Rollbacks - Overview

## 개요
- Deployment의 핵심 기능인 Rolling Update의 동작 원리를 노드·Pod·컨테이너 단위 다이어그램으로 상세히 설명하고, 일시 정지(Pause)·롤백 가능성을 정리.

## 내용
### Rolling Update란
- Deployment가 제공하는 전략으로, **기존 Pod를 새 Pod로 점진적으로(incrementally) 교체**해 다운타임 없이 애플리케이션을 업데이트.
- 예: Nginx 1.17로 만든 Deployment(ReplicaSet, Replica 3개)를 1.18로 업데이트하려면 YAML 수정이나 `kubectl set image`로 지시 → Deployment가 새로운 ReplicaSet을 만들어 1.18 버전 Pod 3개를 생성하되, **하나씩 순차적으로**(하나 생성 → 하나 종료 → 다음 하나 생성 → 다음 하나 종료 …) 교체.

### Rolling Update의 이점
1. **무중단(Zero Downtime)** — Kubernetes가 Pod를 점진적으로 업그레이드하면서 항상 일부 인스턴스를 가용 상태로 유지.
2. **통제된 롤아웃(Controlled Rollout)** — 단계적으로(phased) 진행 — 새 Pod 하나 온라인 → 기존 Pod 하나 오프라인, 이런 식으로 순서대로 교체.
3. **롤백 가능성(Rollback Capability)** — 언제든 이전 버전으로 되돌릴 수 있으며, 여러 리비전을 거쳤어도(예: 1.17→1.18→1.19→1.20) 원하는 과거 리비전(예: 1.17)으로 직접 롤백 가능.

### 다이어그램으로 본 동작 흐름
- 노드(육각형) 3개, 그 위에 Deployment의 Pod 4개(원형, Replica 4), 각 Pod 안에 컨테이너(사각형)가 있고, Pod마다 고유 IP(예: `10.0.0.5`, `10.0.1.5`, `10.0.2.4`, `10.0.2.5`).
- 업데이트 시작: 첫 번째 Pod가 새 IP(`10.0.0.6`)와 새 이미지(보라색으로 표시된 신버전)로 재생성되고, 기존 Pod는 종료됨.
- 이 단계에서 사용자는 **신·구 버전이 섞인 상태**로 애플리케이션에 접근(일부는 이전 버전, 일부는 새 버전) — 업데이트는 아직 진행 중.
- 다음 Pod들도 순서대로 하나씩 갱신 — Pod가 재생성될 때마다 **IP는 항상 새로 바뀜**.
- 모든 Pod가 새 버전으로 교체되면 업데이트 완료.

### 일시 정지(Pause)와 롤백
- 롤링 업데이트 도중 결과가 마음에 들지 않으면 **업데이트를 일시 정지(Pause)**해 나머지 Pod의 교체를 멈출 수 있음.
- 일시 정지 후에도 마음에 들지 않으면 해당 Pod를 삭제하거나 **롤백**을 수행 — 롤백하면 이전 버전의 Pod가 자동으로 다시 올라옴.

## 요약
- Rolling Update는 Deployment가 새로운 ReplicaSet의 Pod를 하나씩 생성하고 기존 Pod를 하나씩 종료하는 방식으로 진행되어(그 과정에서 IP는 매번 새로 바뀜) 무중단·통제된 업데이트를 제공하며, 업데이트 도중 일시 정지하거나 언제든 원하는 과거 리비전으로 롤백할 수 있다.
