# Dockerfile Instructions

## 개요
- Dockerfile 핵심 지시문 전체 목록과 역할, Build Context·레이어 캐싱 개념, 전형적인 Dockerfile 작성 흐름, 베스트 프랙티스와 흔한 실수를 정리.

## 내용
### Dockerfile이란
- Docker 이미지를 만드는 방법을 정의하는 순수 텍스트 레시피 — 애플리케이션 실행에 필요한 모든 의존성(코드, 라이브러리, 설정 등)을 담은 불변(immutable)·이식 가능한(portable) 패키지를 만듦. 컨테이너 안에서 수동으로 하던 작업을 자동화한 것.

### 핵심 지시문과 역할
| 지시문 | 목적 |
|---|---|
| `FROM` | 각 빌드 단계의 베이스 이미지를 설정 — 이미지의 토대 |
| `WORKDIR` | 작업 디렉터리를 정의해 명확성과 레이어 캐싱 개선 |
| `COPY`/`ADD` | 파일을 이미지에 반영 — 예기치 못한 동작을 피하려면 `ADD`보다 `COPY` 선호 |
| `RUN` | 빌드 중 셸 명령 실행(예: 의존성 설치) |
| `ENV`/`ARG` | 환경 변수 설정(`ARG`는 빌드 타임에만 유효) |
| `EXPOSE` | 의도한 포트를 선언(실제로 게시(publish)하지는 않음) |
| `USER` | 루트가 아닌 사용자를 지정해 위험을 줄이고 베스트 프랙티스 준수 |
| `CMD`/`ENTRYPOINT` | 기본 실행 명령이나 엔트리포인트 지정 |
| `VOLUME` | 퍼시스턴트 또는 공유 스토리지를 위한 마운트 포인트 표시 |

### Build Context와 이미지 레이어
- **Build Context** — 빌드 중 Docker가 사용하는 디렉터리. `.dockerignore`로 불필요한 파일을 제외해 최소한으로 유지해야 이미지가 비대해지지 않음.
- 각 지시문은 이미지의 레이어를 하나씩 만들며, **자주 바뀌는 레이어일수록 뒤쪽에 배치**해야 캐싱 이점을 극대화할 수 있음.

### 전형적인 Dockerfile 작성 흐름
1. **베이스 이미지 선택** — 런타임용으로는 Alpine처럼 최소한의 신뢰할 수 있는 이미지 사용, 빌드 단계에서는 전체 SDK 사용.
2. **`WORKDIR` 설정**.
3. **코드 복사 전에 의존성 먼저 설치** — 패키지 매니페스트(예: `package.json`, `requirements.txt`)를 먼저 복사해 설치 결과를 캐싱.
4. **애플리케이션 코드 복사**.
5. **환경 변수 설정, 포트 노출(`EXPOSE`)**.
6. **비루트(non-root) 사용자 지정**.
7. **`CMD` 또는 `ENTRYPOINT`로 실행 명령 정의**.

### 최적화·베스트 프랙티스
- **레이어 최소화** — 관련된 셸 명령(설치, 정리 등)을 하나의 `RUN`으로 합쳐 레이어 수를 줄임.
- **캐시 활용** — 정적인 의존성 파일을 먼저 복사해 변경되지 않은 패키지를 매번 재설치하지 않도록 함.
- **`.dockerignore` 사용** — 불필요한 컨텍스트 파일이 Docker Daemon에 전송되지 않도록 방지.
- **이미지 버전 고정(Pin)** — `python:3.9-alpine`처럼 태그를 명시해 일관된 빌드와 재현성 확보.
- **루트 사용 회피** — 프로세스를 비루트로 실행해 보안 강화(꼭 필요한 경우에만 루트 유지).
- **빌드 단계 테스트** — `docker build --target=<단계>`로 전체 파이프라인을 거치지 않고 중간 빌드 단계만 테스트.

### 흔한 실수와 회피 방법
- **불필요한 파일 포함** — `.dockerignore`를 놓치면 문서, 테스트, `node_modules` 등이 이미지에 그대로 포함됨.
- **파일 권한 문제** — 비루트 사용자에게 올바른 권한이 없으면 컨테이너 실행이 실패할 수 있음.
- **캐시 미스** — 전체 컨텍스트를 이른 단계에서 복사하면 캐싱이 깨져 빌드가 느려짐.
- **비결정적(Non-deterministic) 빌드** — `latest`나 유동적인 태그를 사용하면 불안정성을 유발 — 재현성을 위해 버전을 고정.

### 고급 고려 사항
- **Build Args vs Env Vars** — 빌드 타임 설정(예: `ARG VERSION=1.0`)에는 `ARG`, 런타임 설정에는 `ENV`나 런타임 주입을 선호.
- **메타데이터용 Label** — `LABEL`로 버전, 관리자, 설명 등을 담아 Registry 검색과 이미지 관리에 활용.
- **Healthcheck** — `HEALTHCHECK`를 추가해 Swarm, Kubernetes 같은 오케스트레이터가 컨테이너 상태를 모니터링할 수 있게 함.
- **보안 스캐닝** — 이미지 스캐너를 통합해 베이스 이미지나 설치된 패키지의 취약점을 조기에 탐지.

### 베스트 프랙티스 체크리스트
- 최소한의 신뢰할 수 있는 베이스 이미지 선택 / `.dockerignore`로 컨텍스트 정리 / 캐시 최적화를 위한 지시문 순서 배치 / 관련 `RUN` 병합 / 불필요한 도구 설치 회피 / 비루트로 프로세스 실행 / 재현 가능한 빌드를 위한 버전 고정 / 필수 메타데이터로 이미지에 Label 부여 / 적절한 경우 `HEALTHCHECK` 사용.

## 요약
- Dockerfile은 `FROM`~`VOLUME`까지 이어지는 지시문들로 이미지를 계층적으로 구성하며, Build Context 최소화(`.dockerignore`)와 레이어 순서(자주 바뀌는 것을 뒤로)로 캐싱을 최적화하고, 비루트 실행·버전 고정·Label·Healthcheck 같은 베스트 프랙티스를 지키면 안전하고 재현 가능하며 효율적인 이미지를 만들 수 있다.
