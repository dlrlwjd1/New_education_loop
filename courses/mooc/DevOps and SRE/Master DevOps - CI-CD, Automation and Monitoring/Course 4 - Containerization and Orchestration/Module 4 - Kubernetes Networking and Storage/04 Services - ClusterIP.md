# Services - ClusterIP

## 개요
- Service가 필요한 이유(Pod IP의 불안정성)와 동작 방식, 그리고 기본 Service 타입인 ClusterIP의 특징을 정리.

## 내용
### Service란
- Pod의 논리적 집합과 그것에 접근하는 정책을 정의하는 추상화 — Pod에서 실행되는 컨테이너 애플리케이션과 통신하기 위한 Kubernetes 리소스.
- 안정적인 엔드포인트를 제공해 Pod 그룹과의 일관된 통신을 클러스터 안팎에서 보장.

### 왜 Service가 필요한가
- Pod는 IP 주소를 가지고 있어 직접 통신할 수 있지만, 이 IP는 **사설(private) IP**라서 클러스터 외부에서 접근 불가능(예: 클러스터가 미국에 있고 인도에서 접근하려는 경우 불가능).
- 클러스터 **내부**에서 Pod와 통신하려 해도, Pod가 죽으면(Deployment가 장애 허용을 위해 재생성) **IP가 바뀌기 때문에** 문제가 생김 — Pod IP는 고정적이지 않고, Pod 이름은 DNS로 해석되지 않음.
- 예: Pod IP가 `10.1.2.3`에서 죽었다가 재생성되면 `10.1.2.4`로 바뀌고, 다시 죽으면 `10.1.2.5`로 바뀌는 식 — 매번 통신 설정을 수동으로 바꿔야 하는 문제가 발생.

### Service가 이 문제를 해결하는 방식
- Pod를 위한 Service를 만들면, 사용자(외부)나 다른 Pod(내부) 모두 **Service를 통해** 통신하며, Service가 실제 Pod로 트래픽을 전달·응답을 반환.
- Pod가 죽고 새 Pod가 생성되어 IP가 바뀌어도, **레이블(Label)이 동일**하기 때문에 Service는 자동으로 새 Pod를 관리 대상으로 인식하고 계속 트래픽을 전달 — 사용자는 IP 변경을 신경 쓸 필요가 없음.

### Service의 3가지 대표 타입
1. **ClusterIP**(기본값) — 타입을 지정하지 않으면 기본으로 이 타입이 적용.
2. **NodePort**.
3. **LoadBalancer**.
(그 외 ExternalName, Headless 타입도 존재 — 후속 강의에서 다룸)

### ClusterIP 상세
- **범위(Scope)**: **클러스터 내부에서만** 사용 가능 — 외부 사용자는 ClusterIP 서비스를 통해 Pod와 통신할 수 없음.
- 클러스터 내의 한 Pod가 같은 클러스터 내의 다른 Pod와 통신하는 것은 가능하지만, 외부 세계에서 ClusterIP로 접근하는 것은 불가능.
- **용도**: 같은 클러스터 안에서 실행되는 애플리케이션의 서로 다른 구성 요소 간 내부 통신에 이상적 — 예: 프론트엔드 Pod, 데이터베이스 Pod, 백엔드 Pod가 서로 통신할 때 ClusterIP Service 사용.

## 요약
- Service는 Pod의 IP가 재생성될 때마다 바뀌어도 동일한 레이블을 통해 자동으로 새 Pod를 찾아 트래픽을 전달함으로써 안정적인 통신 엔드포인트를 제공하며, 그중 기본 타입인 ClusterIP는 클러스터 **내부 전용**으로 프론트엔드·백엔드·데이터베이스 같은 구성 요소 간 내부 통신에 적합하다.
