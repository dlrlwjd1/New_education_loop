# Traditional Integration

## 개요
- 전통적인(수동) 통합 방식의 작동 원리, 워크플로우, 적합한 상황과 한계를 설명.

## 내용
### 전통적 통합의 예시
- 5명의 개발자가 하루 종일 각자 코드를 작성해 공통 저장소(GitHub)에 푸시 → 하루가 끝날 무렵 500줄이 쌓임(1차 통합).
- 밤 11시에 예약된 스크립트가 GitHub에 접속해 500줄을 가져와 빌드 도구로 컴파일·테스트 등을 수행(2차 통합) → 오류가 있으면 개발자에게 보고.

### 전통적 통합이란
- 조직 내 여러 시스템·애플리케이션·프로세스를 결합하는 방법과 관행 — 배치 처리, 미들웨어, 점대점(point-to-point) 연결, 수동 프로세스 등을 포함.
- 통합 간 간격이 크다 — 개발자들이 며칠간 코드를 쌓아두고 한 번에 통합·테스트하기 때문에, 문제가 생기면 며칠치 코드를 뒤져야 해서 수정이 오래 걸린다.
- 버전 호환성 문제(한 개발자의 코드가 다른 개발자의 코드와 호환되지 않음)로 충돌 발생.

### 전통적 통합 워크플로우
1. 개발자가 코드 작성
2. 작성된 모든 코드를 한꺼번에 테스트
3. 버그가 있으면 개발자에게 보고 → 수정 (코드량이 많을수록 시간이 오래 걸림)
4. 서버에 배포·유지보수

### 언제 적합한가
- 단순하고 직관적인 프로젝트, 요구사항 변경이 없는 경우, 개발자 1~2명, 데이터 흐름·프로세스에 대한 더 강한 통제가 필요할 때 → 비용 효율적이고 수동으로도 가능.

### 한계
- 요구사항이 자주 바뀌고, 프로젝트가 복잡한 객체지향 구조이며, 여러 팀원이 참여하는 경우에는 적합하지 않다.
- 잦은 요구사항 변경 반영, 최신 의존성 버전 유지, API 버전 변경 관리, 불일치 시 전체 코드 재작성 등의 문제에 직면한다.

### 해결책
- 수동·시간 소모적·오류가 잦은 이 방식을 **자동화**로 해결.
- 코드를 작은 세그먼트로 나누고, 요구사항을 작은 스토리 단위로 쪼개어 각 조각을 빌드·배포·통합 — 이미 테스트된 부분은 그대로 두고 새로 통합된 부분만 확인하면 되므로 훨씬 관리하기 쉬워진다.
- 이것이 바로 **Continuous Integration**(자동화 도구 기반)으로 이어지는 배경이다.

## 요약
- 전통적 통합은 소규모·단순 프로젝트에는 비용 효율적이지만, 통합 간격이 길어 문제 해결이 느리고 팀 규모·복잡도가 커지면 한계에 부딪히며, 이를 해결하는 방법이 코드를 작은 단위로 나눠 자동화하는 Continuous Integration이다.
