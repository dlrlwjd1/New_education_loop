# Scenario - Emergence of Maven

## 개요
- 팀 회의 시나리오를 통해 Maven 이전에 겪던 문제와 Maven 도입의 필요성을 설명.

## 내용
### 시나리오: Maven 이전의 문제
- 매니저, 시니어 개발자, 주니어 개발자가 Java 프로젝트 지연 원인을 논의.
- **의존성(dependency) 문제**: 인터넷으로 라이브러리를 각자 다운로드해 취약점 위험, 개발자마다 서로 다른 로컬 의존성 보유, 수동 다운로드로 시간 소요.
- **빌드 프로세스 부재**: 서로 다른 버전의 라이브러리를 쓰다 보니 코드 통합 시 빌드 실패 빈발.
- **표준화 부재**: 통일된 프로젝트 구조·의존성 문서·빌드 프로세스가 전혀 없어 각자 로컬에서 코드를 관리.
- 컴파일·테스트에 시간이 오래 걸리고, 여러 개발자가 통합할 때 컴파일 이슈 디버깅에 몇 시간~몇 주가 걸림.

### Maven 이전의 핵심 한계
1. 빌드 프로세스 없음 — 모두가 로컬에서 각자 빌드
2. 의존성 체크·설치 자동화 없음 — 저마다 다른 버전 사용 → 불일치
3. 표준 프로세스 부재

### Maven의 해결책
- 의존성을 하나의 파일(**pom.xml**)에 나열하면 자동으로 다운로드됨.
- 모든 개발자가 동일한 의존성 파일 → 동일한 버전의 의존성을 사용하게 됨.
- 개발자가 코드를 작성하고, 테스트 케이스를 실행하고, 리소스 파일을 관리할 수 있는 구조를 제공.
- Java 프로젝트에서는 Gradle, Ant도 있지만 약 75%는 Maven을 사용.

## 요약
- Maven 도입 전에는 의존성 관리와 빌드 프로세스가 전혀 표준화되지 않아 통합 시마다 문제가 발생했지만, Maven은 `pom.xml` 하나로 의존성을 통일하고 표준화된 빌드 프로세스를 제공해 팀 전체의 협업을 훨씬 쉽게 만든다.
