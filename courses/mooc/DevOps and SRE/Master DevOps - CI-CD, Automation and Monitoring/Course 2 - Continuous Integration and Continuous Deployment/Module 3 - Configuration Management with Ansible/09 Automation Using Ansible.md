# Automation Using Ansible

## 개요
- Ansible 이전(셸 스크립트 기반) 방식의 한계, Ansible의 Idempotency(멱등성), Ad-hoc Command vs Playbook을 설명.

## 내용
### Ansible 이전 — 셸 스크립트 기반 관리
- 운영팀이 각 운영체제별로 셸 스크립트를 작성해 서버에 직접 복사·실행.
- 각 OS마다 다른 스크립트를 유지해야 했고, 스크립팅 실력과 OS 지식이 요구됨.
- 수작업이 많고 사람의 실수 위험이 크며, 일부 서버에서만 스크립트가 동작하는 등 문제가 누적됨.

### Ansible의 해결책
- 단일 스크립트에 OS/워커 노드 설정에 따른 조건을 작성해 여러 서버에서 동일하게 실행 가능 — 일관성 확보.
- **Idempotency(멱등성)** — Ansible 스크립트를 실행할 때마다 서버 상태를 확인해, 원하는 변경이 **이미 적용되어 있으면 아무것도 하지 않고**, 적용되어 있지 않으면 변경을 수행. 항상 스크립트에 명시된 "원하는 상태(desired state)"를 유지한다.
- Ansible 엔진이 호스트 서버 간 차이를 인식해 원하는 상태에 맞게 조정한다.

### 코드 작성 방식 두 가지
1. **Playbook** — 여러 작업을 순서대로 수행하는, 가장 일반적으로 쓰이는 방식.
2. **Ad-hoc Command** — 워커 노드에서 단일 작업을 빠르게 확인·실행할 때 쓰는 한 줄짜리 명령.

## 요약
- Ansible은 OS별로 흩어져 있던 수동 셸 스크립트 관리 방식을 하나의 조건부 스크립트로 통합하고, Idempotency로 항상 원하는 상태를 유지하며, 복잡한 작업은 Playbook으로, 간단한 일회성 작업은 Ad-hoc Command로 실행할 수 있게 한다.
