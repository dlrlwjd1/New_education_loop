# Cherry-Picking in Git

## 개요
- 브랜치 전체를 병합하지 않고 특정 커밋만 선택해 다른 브랜치에 적용하는 Cherry-Picking을 설명.

## 내용
### 개념
- 한 브랜치의 특정 커밋(commit)을 골라 다른 브랜치에 그대로 적용하는 것 — 브랜치 전체가 아니라 필요한 딱 한 조각만 가져온다.
- 과수원에서 바구니 전체가 아니라 잘 익은 사과만 골라 따는 것과 유사.
- 모든 커밋은 고유한 SHA-1 해시(그 변경의 신분증 같은 역할)를 가진다.

### 시나리오
- feature 브랜치에 여러 커밋이 있지만, 그중 긴급한 버그 수정 하나만 master에 즉시 반영하고 싶을 때 cherry-pick으로 그 커밋만 선택해 가져온다.
- 나머지 실험적/미완성 작업은 feature 브랜치에 그대로 남는다.

### 활용 사례
- **실수 수정** — feature 브랜치의 오탈자 수정을 프로덕션에 빠르게 반영
- **팀 간 부분 공유** — Team A의 성능 개선 커밋 하나만 Team B가 관련 없는 나머지 변경 없이 가져옴
- **긴급 패치 배포** — 프로젝트의 나머지 개발은 그대로 진행하면서 단일 수정만 라이브 반영
- **오래된 기능 되살리기** — 몇 달 전 만들었다가 보류한 기능을 전체 브랜치 병합 없이 그 커밋만 되살림

### 단점
- 원본 커밋과 cherry-pick된 커밋이 둘 다 존재하면 커밋 이력이 중복되어 혼란스러울 수 있다.
- 브랜치마다 같은 부분을 다르게 수정했다면 충돌이 발생할 수 있다.
- 크고 복잡한 작업에는 전체 협업 이력을 깔끔하게 보존하는 일반 머지(merge)나 리베이스(rebase)가 더 적합하다.

## 요약
- Cherry-pick은 브랜치 전체가 아니라 특정 커밋 하나만 선택적으로 다른 브랜치에 적용하는 방법으로, 긴급 수정이나 부분 공유에는 유용하지만 이력 중복·충돌 가능성 때문에 대규모 작업에는 merge/rebase가 더 적합하다.
