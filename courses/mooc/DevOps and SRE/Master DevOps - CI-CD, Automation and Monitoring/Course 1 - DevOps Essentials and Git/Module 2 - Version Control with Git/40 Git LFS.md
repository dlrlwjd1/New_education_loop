# Git LFS

## 개요
- 대용량 파일을 효율적으로 관리하는 Git 확장 기능인 Git Large File Storage(LFS)의 개념, 작동 방식, 이점과 트레이드오프를 설명.

## 내용
### Git LFS란
- 비디오, 데이터셋, 디자인 파일 같은 대용량 파일을 저장소 안에 직접 저장하는 대신, 저장소 밖에 저장하고 Git 안에는 **포인터(pointer)** 파일만 남기는 확장 기능.
- 포인터는 파일이 LFS 서버 어디에 저장돼 있고 어떤 버전인지에 대한 정보만 담은 작은 텍스트 파일.
- 저장소를 클론/풀할 때 Git이 모든 대용량 파일을 즉시 다운로드하지 않아도 되어 저장소가 가볍고 빨라진다.

### 작동 방식
1. 로컬에서 개발자가 코드와 대용량 파일(예: `file.psd`)을 함께 추가
2. 커밋·푸시 시 코드는 평소처럼 원격 Git 저장소로, 대용량 파일은 Git이 아니라 **LFS 저장소**로 별도 업로드되고 저장소에는 포인터만 남는다
3. 다른 사람이 클론/풀하면 코드와 포인터를 받고, Git LFS가 포인터를 이용해 실제 파일을 자동으로 LFS 서버에서 가져온다

### 필요한 이유
1. **속도** — 저장소 크기가 작아져 클론·페치·브랜치 전환이 빨라짐
2. **바이너리 파일 문제 회피** — Git이 바이너리 파일을 다룰 때 생기는 이력 비대화, 충돌 문제 방지
3. **팀 워크플로우 개선** — 모두가 대용량 파일을 즉시 필요로 하지 않으므로 필요할 때만 가져옴
4. **대용량 자산의 버전 관리** — Git이 원래 잘 다루지 못하던 무거운 자산에도 제대로 된 버저닝 제공

### 워크플로우
1. Git LFS가 처리할 파일 타입을 추적(track) 지정 (예: `.psd`, `.mp4`, `.zip`)
2. 포인터 파일을 add·commit
3. 푸시하면 실제 대용량 파일은 LFS 저장소로, 저장소 자체는 작고 빠르게 유지
4. 다른 사람이 pull/checkout하면 포인터에 따라 올바른 버전의 대용량 파일이 자동 다운로드

### 이점
- 저장소 크기가 작게 유지됨
- checkout, 브랜치 전환, 협업 속도 향상
- 대용량 파일도 코드처럼 롤백·비교·복원 가능한 완전한 버전 관리

### 트레이드오프
1. 초기 설정·구성이 필요하며 팀 전체가 일관되게 적용해야 함
2. 외부 LFS 서버에 의존 — 서버가 다운되거나 잘못 설정되면 코드는 멀쩡해도 대용량 파일을 받을 수 없음
3. CI/CD 파이프라인에 복잡성 추가 — 모든 환경이 Git LFS를 기본 지원하지는 않음
4. 코드/텍스트 파일만 다루는 프로젝트라면 굳이 필요 없을 수 있음(일반 Git으로 충분)

## 요약
- Git LFS는 대용량 파일을 포인터로 대체해 저장소를 가볍게 유지하면서도 버전 관리를 가능하게 하지만, 외부 서버 의존성과 팀 전체의 일관된 설정이 필요하다는 트레이드오프가 있다.
