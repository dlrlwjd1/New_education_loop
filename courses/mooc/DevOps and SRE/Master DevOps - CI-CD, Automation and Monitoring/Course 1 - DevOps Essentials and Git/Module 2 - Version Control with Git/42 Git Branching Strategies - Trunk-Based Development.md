# Git Branching Strategies - Trunk-Based Development

## 개요
- 지속적 통합·빠른 딜리버리를 중시하는 Trunk-Based Development(TBD) 전략을 GitFlow와 비교해 설명.

## 내용
### Trunk-Based Development란
- 모든 개발자가 trunk(main)에 직접 커밋하거나, 아주 짧게 유지되는 브랜치를 만들어 금방 다시 병합한다.
- 목표는 코드베이스를 **항상 배포 가능한 상태**로 유지하는 것 — CI/CD를 실천하는 팀에 특히 효과적.

### 핵심 관행
- **짧은 수명의 기능 브랜치** — 보통 하루~이틀 이내로 유지해 병합 복잡도를 낮춤
- **지속적 통합** — 하루에도 여러 번 trunk에 통합, 자동 빌드·테스트로 뒷받침
- **Feature Flags(기능 플래그)** — 미완성 기능을 trunk에 병합해두되, 배포와 별개로 활성화 여부를 제어
- **항상 릴리스 가능한 Trunk** — 언제든 main 브랜치의 코드를 프로덕션에 배포할 수 있는 상태 유지

### 이점
- 머지 충돌 감소 (자주 통합하므로)
- 더 빠른 피드백 (자동화된 테스트로 즉시 확인)
- 향상된 협업 (공유 코드베이스에서 작업)
- 가속화된 딜리버리 (항상 릴리스 가능한 trunk)

### Trunk-Based Development vs GitFlow

| 항목 | Trunk-Based Development | GitFlow |
|---|---|---|
| 브랜칭 모델 | 단일 main + 짧은 브랜치 | develop, release 등 여러 장기 브랜치 |
| 통합 방식 | 잦고 지속적인 통합 | 기능 개발 완료 후 통합 |
| 릴리스 전략 | 항상 릴리스 가능한 trunk | 별도 release 브랜치 |
| 복잡도 | 단순, 오버헤드 적음 | 복잡, 대형 프로젝트에 적합 |
| 사용 사례 | Agile, CI/CD 환경 | 정해진 릴리스 일정이 있는 프로젝트 |

### 도전 과제
- 잦은 통합과 높은 코드 품질을 위한 개발자의 규율 필요
- 자동화된 테스트가 견고해야 함
- Feature Flag 관리가 복잡해질 수 있음
- 충돌 방지를 위한 팀 간 커뮤니케이션·조율 필요

### 베스트 프랙티스
- Trunk을 항상 배포 가능한 상태로 유지
- 빌드·테스트·배포를 최대한 자동화
- 코드 리뷰로 품질 유지와 지식 공유
- 빌드 시간, 배포 빈도, 실패율 같은 지표 모니터링

## 요약
- Trunk-Based Development는 잦은 통합과 항상 배포 가능한 trunk를 통해 CI/CD·Agile 환경에 최적화된 전략이며, 여러 장기 브랜치를 쓰는 GitFlow보다 단순하지만 잦은 통합·자동화 테스트·팀 규율을 요구한다.
