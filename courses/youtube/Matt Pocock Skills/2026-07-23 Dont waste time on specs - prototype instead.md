# Don't waste time on specs: /prototype instead

## 개요
- 업로드일: 2026-07-23
- 원본: https://www.youtube.com/watch?v=n0VhIVtviC0
- 채널: Matt Pocock
- 길이: 10분 59초
- 핵심 주제: AI에게 상세 명세(specification)를 바로 넘기기 전에 폐기 가능한 고충실도 프로토타입으로 설계 질문을 확인하고, 그 결과를 프로덕션 구현의 근거로 사용하는 워크플로

## 내용
### 명세 중심 개발의 문제
AI 코딩에서는 먼저 긴 명세와 계획을 작성해야 한다고 생각하기 쉽다. 하지만 아직 제품의 모양과 동작을 모르는 상태에서 상세 명세를 쓰면 확인되지 않은 설계 결정을 텍스트에 고정하게 된다.

명세는 우리가 이미 아는 요구 사항을 전달하는 데는 유용하지만, “어떤 디자인이 더 나은가?”, “실제로 사용하면 어떤 느낌인가?”처럼 아직 답을 모르는 질문에는 대역폭이 낮다. 글로 논의한 뒤 바로 프로덕션 코드로 이동하면 설계와 실제 결과 사이의 간격도 크다.

### 프로토타입은 질문에 답하는 폐기 가능한 코드다
발표자는 프로토타입을 다음과 같이 정의한다.

> 특정 질문에 답하기 위해 만드는 폐기 가능한 코드(throwaway code)

AI가 코드를 빠르게 생성할 수 있게 되면서 프로토타입의 제작 비용이 크게 낮아졌다. 따라서 텍스트로 여러 차례 토론하는 대신 작동하는 여러 안을 만들어 보고 직접 반응하는 편이 더 효율적일 수 있다.

프로토타입은 프로덕션 코드가 아니다. 안정성, 완전한 데이터 연결, 테스트, 접근성, 성능 같은 요구 사항을 모두 해결하기보다 현재 결정해야 하는 질문을 관찰 가능한 형태로 만드는 것이 목적이다.

### 충실도(fidelity)를 질문에 맞추기
충실도는 프로토타입이 최종 제품의 모습과 행동을 얼마나 구체적으로 재현하는지를 뜻한다.

- **낮은 충실도(low fidelity)**: 아이디어의 큰 구조와 방향을 빠르게 비교한다.
- **높은 충실도(high fidelity)**: 실제 화면과 상호작용에 가까운 결과로 세부 행동을 검토한다.

모든 부분을 고충실도로 만들 필요는 없다. 답하려는 질문과 관련된 부분만 정교하게 만들고 나머지는 단순화한다. 예를 들어 검색창의 상호작용을 결정하려면 검색 결과의 실제 백엔드까지 만들 필요는 없지만, 입력·포커스·결과 표시 방식은 작동해야 한다.

### Wayfinder와 `/prototype`
`/prototype` 스킬은 Matt Pocock의 Wayfinder 흐름 안에서 여러 설계안을 빠르게 만든다. 영상에서는 검색창의 모양과 행동이 정해지지 않은 상황에서 서로 다른 선택을 담은 세 가지 프로토타입을 생성한다.

각 안은 단순한 시각 변형이 아니라 몇 가지 설계 결정을 코드로 표현한다. 사용자는 결과를 보며 “이 안의 동작은 좋지만 저 안의 배치는 더 낫다”처럼 구체적으로 반응할 수 있다. 말로 설명하기 어려웠던 선호가 실제 산출물에 대한 피드백으로 드러난다.

### 반복 과정에서 결정 기록하기
프로토타입을 반복 수정할 때는 최종 코드뿐 아니라 채택하거나 거부한 설계 결정을 남겨야 한다. 그렇지 않으면 프로덕션 구현 단계에서 같은 질문을 다시 논의하거나 폐기했던 선택이 되살아날 수 있다.

```text
질문 정의
  → 서로 다른 프로토타입 생성
  → 직접 실행하고 비교
  → 좋은 요소와 문제점 피드백
  → 프로토타입 수정
  → 확정된 설계 결정 기록
  → 프로덕션 구현
```

### 프로토타입에서 프로덕션으로
프로토타입 코드를 그대로 프로덕션에 넣는 것이 목적은 아니다. 프로토타입이 답한 질문과 확정한 설계 결정을 구현 입력으로 사용한다.

발표자는 글과 명세만으로 프로덕션 코드에 도달하는 간격은 크지만, 작동하는 고충실도 프로토타입에서 프로덕션으로 가는 간격은 더 작다고 설명한다. 구현자는 이미 목표 동작을 관찰할 수 있으므로 접근성, 테스트, 실제 데이터, 오류 처리 같은 프로덕션 요구 사항에 집중할 수 있다.

### 프런트엔드 밖에서도 적용하기
프로토타이핑은 UI에만 국한되지 않는다. API 모양, CLI 사용성, 데이터 파이프라인, 시스템 통합처럼 직접 실행해 봐야 판단할 수 있는 설계에도 사용할 수 있다.

핵심은 전체 시스템을 임시로 만드는 것이 아니라 가장 불확실한 가정에 답할 수 있는 최소한의 실행 가능한 실험을 만드는 것이다.

## 예시
### 검색창 설계
요구 사항이 “검색창을 추가한다”뿐이고 모양과 행동이 정해지지 않았다고 가정한다.

```text
프로토타입 A: 페이지 안에 항상 노출되는 검색창
프로토타입 B: 단축키로 여는 명령 팔레트
프로토타입 C: 아이콘을 누르면 확장되는 검색창
```

세 안을 실제로 실행한 뒤 다음과 같은 피드백을 줄 수 있다.

- B의 키보드 흐름을 유지한다.
- C의 간결한 초기 화면을 사용한다.
- 검색 결과는 별도 페이지가 아니라 오버레이로 보여준다.

이 결정들을 기록한 후 프로덕션 구현에서는 실제 검색 API, 로딩·오류 상태, 키보드 접근성, 테스트를 추가한다.

### 백엔드 프로토타입
새 API의 사용성을 확인하려면 임시 인메모리 데이터와 최소 엔드포인트만 만들어 호출 코드를 먼저 작성할 수 있다. 클라이언트가 사용하기 불편한 부분을 확인한 뒤 실제 데이터베이스와 인증을 연결한다.

## 요약
- 아직 모르는 설계 문제를 상세 명세로 먼저 고정하면 확인되지 않은 결정을 문서화하게 된다.
- 프로토타입은 질문에 답하기 위한 폐기 가능한 코드이며, 프로덕션 구현과 목적이 다르다.
- 질문과 관련된 부분의 충실도만 높여 여러 선택을 직접 비교한다.
- 작동하는 결과에 대한 반응은 텍스트 토론에서 드러나지 않던 선호와 요구 사항을 발견하게 한다.
- 확정된 설계 결정을 기록하고, 프로덕션 단계에서는 테스트·접근성·실제 데이터·오류 처리 등을 별도로 완성한다.
