# /wayfinder: Nothing is too big to plan anymore

## 개요
- 업로드일: 2026-07-30
- 영상 링크: https://www.youtube.com/watch?v=F3lL98Pj90o
- 채널: Matt Pocock
- 길이: 15분 8초
- 관련 저장소: https://github.com/mattpocock/skills
- 핵심 주제: `/wayfinder`로 한 세션의 컨텍스트에 담기 어려운 큰 작업을 의사결정 티켓의 지도(map)로 만들고, 조사·프로토타이핑·논의·외부 작업을 여러 세션에 걸쳐 조율하는 방법

## 내용

### 한 세션에 묶인 계획 방식의 한계
Matt Pocock이 기존에 사용하던 `/grill-me`, `/grill-with-docs` 같은 스킬은 AI가 사용자를 인터뷰하며 요구 사항을 구체화하는 중요한 기본 도구다. 다만 한 세션 안에서 계획을 완성해야 한다는 한계가 있다.

큰 작업은 에이전트의 전체 컨텍스트 윈도우뿐 아니라, 높은 품질로 추론할 수 있는 이른바 스마트 존(smart zone)에도 다 들어가지 않는다. 그래서 사용자가 미리 작업을 작은 조각으로 자르거나, 대화 중 토큰 사용량을 계속 신경 쓰게 된다. 그러다 아직 조사하지 않았거나 시제품을 보지 않아 답할 수 없는 질문을 만나면 계획이 막힌다.

이 방식은 만들고 싶은 일을 기준으로 AI를 쓰는 대신 AI의 한계에 맞춰 작업의 야심과 크기를 줄이게 할 수 있다. `/wayfinder`는 계획 자체를 여러 세션으로 나눠 이 제약을 없애려는 스킬이다.

### 목적지·전선·안개로 큰 작업을 표현한다
큰 작업에는 출발점과 목적지(destination)는 있지만, 그 사이 경로가 분명하지 않은 경우가 많다. `/wayfinder`는 이 상태를 다음 요소로 표현한다.

- **목적지(destination)**: 계획이 끝났을 때 얻으려는 결과다. 구현 가능한 명세(specification)일 수도 있고, 실제 작업의 완료일 수도 있다.
- **지도(map)**: 목적지에 도달하기 위해 해결해야 할 의사결정 전체를 나타낸다.
- **티켓(ticket)**: 조사, 프로토타입 제작, 논의처럼 한 번의 독립된 에이전트 세션에서 처리할 의사결정 단위다.
- **전선(frontier)**: 현재 정보만으로 바로 착수할 수 있는 티켓들이다.
- **전쟁의 안개(fog of war)**: 선행 조사나 결정이 끝나지 않아 아직 구체화하거나 해결할 수 없는 영역이다.

처음부터 전체 경로를 정확하게 예측하지 않는다. 현재 가능한 티켓을 해결하면 새로운 결정이 가능해지고, 전선이 이동하면서 안개가 점차 걷힌다. 모든 불확실성을 해소해 목적지에 도달할 때까지 이 과정을 반복한다.

### 지도는 이슈 트래커에 영속적으로 기록한다
영상에서 `/wayfinder` 지도는 GitHub Issue의 부모 이슈로, 개별 의사결정은 하위 이슈로 저장된다. 티켓에서 결정을 내리면 해당 티켓을 닫고, 결정의 짧은 요약도 부모 지도에 다시 기록한다.

이 구조에는 두 가지 이점이 있다.

1. 여러 에이전트 세션이 끝나도 조사 결과, 프로토타입, 논의와 결정이 사라지지 않는다.
2. 지도는 전체 상태를 빠르게 보여주고, 필요할 때는 연결된 티켓에서 결정의 원문과 근거를 다시 확인할 수 있다.

영상에서는 GitHub를 사용하지만 `/wayfinder` 자체는 특정 이슈 트래커에 종속되지 않는다. 초기 설정을 하면 Linear나 Jira 같은 다른 이슈 트래커도 사용할 수 있다고 설명한다.

### 먼저 목적지를 정하고 첫 지도를 만든다
새 `/wayfinder` 세션에서 가장 먼저 정할 것은 목적지다. 영상의 예시는 Course Video Manager 애플리케이션에 다음 기능을 포함한 명령 팔레트(command palette)를 추가하는 큰 작업이다.

- 아이콘 선택기 추가
- 다른 다이어그램 검색
- 다이어그램의 요소를 복사해 저장
- 여러 새 액션 제공

이 사례의 목적지는 바로 구현하는 것이 아니라 **구현 가능한 명세(buildable spec)**를 얻는 것이었다. 사용자가 원하는 바를 설명하자 에이전트가 저장소를 탐색하고 grilling 방식으로 완료 조건과 초기 요구 사항을 질문한 뒤, 부모 지도와 하위 티켓 7개를 만들었다.

7개를 모두 즉시 처리할 수 있었던 것은 아니다. 아이콘 이름의 출처, 컴포넌트 저장 스키마, 팔레트 정보 구조처럼 선행해서 결정할 수 있는 세 티켓만 당시의 전선에 놓였다.

### 지도 작성과 티켓 해결에 모두 `/wayfinder`를 쓴다
실제 진행 방식은 다음과 같다.

1. 큰 목표를 넣어 `/wayfinder`를 실행하고 첫 지도와 티켓을 만든다.
2. 현재 전선에서 처리할 티켓 하나를 고른다.
3. 새 에이전트 세션에서 `/wayfinder`와 해당 티켓 URL을 전달한다.
4. 티켓의 조사·프로토타입·논의 또는 작업을 완료하고 결정을 기록한다.
5. 부모 지도에 반영된 결과를 보고 새로 열린 전선을 확인한다.
6. 다음 티켓을 또 다른 세션에서 진행한다.

Matt는 `/handoff`로 다음 세션용 프롬프트를 만들고 Claude 하위 에이전트를 시작하는 방식을 사용했지만, 핵심은 특정 하위 에이전트 기능이 아니다. 각 티켓을 독립된 세션에서 처리하고 그 결과를 이슈 트래커에 남기는 것이 핵심이다.

### 네 가지 의사결정 티켓 유형

| 유형 | 역할 |
| --- | --- |
| Research | 에이전트가 필요한 정보를 조사해 지도에 가져온다. 영상에서는 하위 에이전트로 조사한 뒤 결과를 보고하는 방식도 보여준다. |
| Prototype | 실제로 작동하는 프로토타입을 만들어 추상적인 계획을 눈으로 보고 피드백할 수 있게 한다. |
| Grilling | 구현 세부 사항이나 계획의 특정 영역을 사용자와 문답하며 결정한다. |
| Task | 사람에게 연락하거나 현장 조사를 의뢰하는 것처럼 현실에서 수행해야 하거나, 다른 작업 뒤에 배치해야 하는 일을 기록한다. |

특히 프로토타입은 `/wayfinder`가 지나치게 많은 사전 계획을 요구하는 폭포수(waterfall) 방식이 되는 것을 막는다. 낮은 충실도의 텍스트 계획만 오래 만드는 대신, 높은 충실도의 작동 결과를 보고 빠르게 피드백하기 때문이다.

### 차단 관계가 결정 순서를 만든다
어떤 결정은 다른 결정이 먼저 끝나야 내릴 수 있다. `/wayfinder`는 티켓 사이의 차단 관계(blocking relationship)를 기록해 현재 착수할 수 있는 티켓과 아직 기다려야 하는 티켓을 구분한다.

영상의 다른 지도는 17개 중 14개 티켓이 끝났지만, 핵심 스킬을 먼저 구현해야 다시 검토할 수 있는 결정들이 남아 있었다. 따라서 단순히 처음 만든 할 일 목록을 순서대로 지우는 것이 아니다.

```text
티켓 해결
  → 결정과 근거 기록
  → 차단 관계 갱신
  → 새로 착수 가능한 티켓 확인
  → 전선 이동
```

작업을 진행하며 새 정보가 생기면 다음에 해결할 수 있는 문제도 달라진다. 지도는 이 변화하는 의사결정 경로를 추적한다.

### 완성된 지도에서 명세와 구현 티켓을 만든다
목적지가 명세인 경우, 완성된 지도를 바로 구현에 쓰기에는 너무 조밀할 수 있다. Matt의 흐름은 다음과 같다.

```text
/wayfinder 지도
  → /to-spec
  → /to-tickets
  → 티켓별 구현
  → 코드 리뷰
```

`/to-spec`은 지도와 모든 의사결정을 하나의 명세로 압축한다. 이어서 `/to-tickets`가 명세를 실제 구현 티켓으로 나눈다.

여기서 `/wayfinder`가 만드는 티켓과 구현 티켓은 역할이 다르다.

- **의사결정 티켓(decision ticket)**: 무엇을 만들고 어떤 선택을 할지 알아내기 위한 티켓
- **구현 티켓(implementation ticket)**: 결정된 내용을 실제 코드나 결과물로 만드는 티켓

명세에는 원래의 의사결정 티켓 링크가 남는다. 에이전트가 요약된 명세만으로 판단하기 어려울 때 조사와 대화가 담긴 1차 출처(primary source)를 열어볼 수 있다. 이는 명세 하나만 진실의 원천(source of truth)으로 삼던 `/grill-with-docs` 흐름보다 결정의 근거를 더 잘 보존한다.

### 명세는 다중 세션 작업의 임시 목적지다
Matt는 이 방식을 전형적인 명세 주도 개발(spec-driven development)과 구분한다. 여기서 명세는 계속 유지·수정하는 영구 문서라기보다 여러 구현 세션이 같은 목적지로 향하게 하는 임시 문서다.

구현이 코드에 반영되면 그는 명세가 담긴 이슈를 닫고 거의 다시 참조하지 않는다. 즉, 명세의 목적은 코드를 대신해 장기간 살아남는 것이 아니라 큰 작업을 여러 세션으로 안전하게 전달하는 것이다.

### 언제 `/wayfinder`를 써야 하는가
한 세션에서 충분히 계획하고 완료할 수 있고 목적지까지의 경로를 이미 안다면 `/wayfinder`를 쓸 필요가 없다. 그 경우에는 단일 세션에서 바로 계획하고 실행하는 편이 낫다.

`/wayfinder`가 유용한 상황은 다음과 같다.

- 작업이 여러 에이전트 세션에 걸릴 만큼 크다.
- 무엇을 원하는지는 대략 알지만 도달 경로는 모호하다.
- 조사, 사용자 문답, 프로토타입과 외부 작업이 서로 의존한다.
- 선행 결정에 따라 다음 작업이 달라진다.
- 세션이 바뀌어도 결정의 근거와 진행 상태를 보존해야 한다.

코딩에만 한정되지 않는다. Matt는 강좌 기획, 엔지니어링 작업뿐 아니라 정원 사무실을 짓기 위한 현장 조사 의뢰, 업체 탐색과 연락처 확인에도 사용했다고 설명한다.

## 예시

### 모호한 기능을 명세로 만드는 지도

```text
목적지
└─ 명령 팔레트의 구현 가능한 명세

현재 전선
├─ [Research] 아이콘 이름의 출처 조사
├─ [Grilling] 컴포넌트 저장 스키마 결정
└─ [Prototype] 팔레트 정보 구조와 키보드 흐름 검증

아직 안개 속에 있는 결정
├─ 검색 결과 표시 방식
├─ 다이어그램 간 복사 형식
└─ 선행 결정에 따라 달라지는 구현 범위
```

현재 전선의 티켓을 각각 새 세션에서 해결한다. 결정이 부모 지도에 반영되면 차단됐던 티켓이 열리고, 모든 의사결정이 끝난 뒤 지도를 명세와 구현 티켓으로 변환한다.

### 도구 선택 기준

| 상황 | 적합한 방식 |
| --- | --- |
| 경로가 분명하고 한 세션 안에 끝낼 수 있음 | 단일 세션에서 계획·실행 |
| 요구 사항을 조금 더 명확히 하면 바로 계획 가능 | `/grill-me` 또는 `/grill-with-docs` |
| 여러 세션과 여러 종류의 의사결정이 필요하고 경로가 불분명함 | `/wayfinder` |

## 요약
- `/wayfinder`는 큰 작업의 계획을 한 컨텍스트에 억지로 넣지 않고 여러 에이전트 세션에 걸쳐 조율한다.
- 목적지까지의 불확실한 경로를 지도, 의사결정 티켓, 현재 전선과 전쟁의 안개로 표현한다.
- 조사·프로토타입·grilling·task 티켓을 각각 독립된 세션에서 처리하고, 결과와 근거를 이슈 트래커에 남긴다.
- 티켓의 차단 관계를 추적하므로 선행 결정을 해결할 때마다 새 전선이 열린다.
- 완성된 지도는 `/to-spec`과 `/to-tickets`를 거쳐 명세와 실제 구현 티켓으로 바뀐다.
- 명세가 요약본이라면 연결된 의사결정 티켓은 조사와 대화가 담긴 1차 출처다.
- 프로토타입으로 실제 결과를 보며 피드백하기 때문에 많은 사전 계획이 폭포수 방식으로 굳어지는 것을 막을 수 있다.
- 한 세션에서 경로와 계획을 충분히 처리할 수 있다면 사용하지 않는다. `/wayfinder`는 여러 세션이 필요한 크고 모호한 작업을 위한 도구다.
