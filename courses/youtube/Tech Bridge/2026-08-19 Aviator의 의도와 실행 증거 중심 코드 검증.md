# Aviator의 의도와 실행 증거 중심 코드 검증

## 개요

- **업로드일:** 2026-08-19
- **채널:** Tech Bridge
- **발표자·출처:** Ankit Jain / Aviator
- **원본:** [YouTube](https://www.youtube.com/watch?v=ymj8Ha0oBtU)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 15:51, 자동 자막 언어 `es-US`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 개발 대화의 의도를 인수 기준으로 바꾸고 반복 결함을 규칙화해, 팀의 합의와 동작 검증을 함께 유지한다.

## 내용

### 리뷰가 수행하던 두 가지 역할 (00:00–04:06)

코드 생성량이 늘면 리뷰 대기가 병목이 된다. AI가 작성하고 AI가 리뷰한 결과를 사람이 형식적으로 승인하는 흐름도 문제다. 발표자는 리뷰의 역할을 **의미적 정확성**과 **팀의 정렬·합의**로 나눈다.

버그·보안·규칙 위반의 탐지뿐 아니라 지식 공유, 멘토링, 아키텍처 논의와 온보딩도 리뷰의 기능이다. 줄 단위 읽기를 줄이더라도 협업 기능을 잃으면 안 된다는 것이 핵심이다.

### 구현 과정에서 생기는 의도를 보존 (04:11–06:17)

사전 명세만 작성하고 구현 중 발견한 내용을 되돌려 반영하지 않으면 일방향 개발이 된다. 실제 의도는 티켓과 PRD뿐 아니라 에이전트에게 주는 질문·수정 요청·선택에도 있다. PR을 만들며 대화 기록을 버리면 중요한 결정 근거가 사라진다.

### 반복 결함을 축적하는 Slop Registry (06:22–08:44)

반복해서 남기는 리뷰 지적을 재사용 가능한 불변 조건과 검사 규칙으로 만든다. 발표자는 이를 AI slop registry라 부른다. 사람의 피드백이 다음 변경을 검증하는 자산으로 누적되는 방식이며, 모델 가중치를 직접 학습한다는 의미는 아니다.

개발 세션에서 추출한 인수 기준과 이 규칙들을 조합해 테스트 계획을 만든다. 미리보기 환경에서 실제로 실행하고 동작 증거를 수집한다.

### 새로운 검토 대상은 기준·아키텍처·증거 (08:48–13:56)

사람은 무엇을 만들기로 했는지, 테스트 계획이 그것을 검증하는지, 실제 결과가 맞는지를 검토한다. 자연어로 된 동작 기준은 PM과 디자이너도 논의할 수 있다.

가능한 검사는 결정적인 방식으로 수행하고, 화면 탐색이나 시각적 판단 등 필요한 부분에는 LLM을 쓴다. 테스트 계획을 구현 코드에서만 역으로 만들면 같은 가정을 반복할 수 있으므로 개발 대화의 의도에서 출발해야 한다.

### 조직에 축적하는 방법 (14:05–15:51)

과거 리뷰 댓글에서 반복 지적을 모아 레지스트리를 만드는 과제를 제안한다. 초기에 정리 비용이 들지만 이후 PR마다 재사용할 수 있다. 발표 당시 Aviator의 Verify를 이러한 검증 흐름을 구현하는 제품으로 소개한다.

## 예시

결제 폼 변경의 검증 예:

1. 개발 대화에서 결제 동작의 인수 기준을 추출한다.
2. 기존 불변 조건과 합쳐 테스트 계획을 검토한다.
3. 에이전트가 미리보기 앱에서 폼을 입력한다.
4. 화면 캡처와 DB 상태를 함께 수집한다.
5. 리뷰어는 의도·아키텍처 선택·실행 증거를 검토한다.

## 요약

- 개발 대화의 결정 사항을 인수 기준으로 남긴다.
- 반복 결함 규칙과 실제 실행 증거로 신뢰를 쌓는다.
