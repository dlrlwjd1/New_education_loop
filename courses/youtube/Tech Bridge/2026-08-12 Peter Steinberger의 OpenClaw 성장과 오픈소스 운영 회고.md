# Peter Steinberger의 OpenClaw 성장과 오픈소스 운영 회고

## 개요

- **업로드일:** 2026-08-12
- **채널:** Tech Bridge
- **발표자·출처:** Peter Steinberger / OpenClaw
- **원본:** [YouTube](https://www.youtube.com/watch?v=zfEGIYQtky8)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 41:40, 자동 자막 언어 `en`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 개인적인 불편에서 시작한 에이전트가 급성장하며 겪은 보안·기능 복잡성·의존성·집중력 문제를 돌아본다.

## 내용

### 부엌에서도 에이전트에 메시지를 보내고 싶었다 (00:00–08:04)

컴퓨터 앞을 떠나면 코딩 에이전트가 사소한 이유로 멈추는 불편에서 WhatsApp 중계 도구를 만들었다. 모델·컨텍스트·세션 관리를 감추고 짧고 능동적인 응답을 주는 경험이 중요했다.

온라인 설명만으로 전달되지 않던 가치를 친구들의 그룹 대화와 공개 Discord 체험에서 보여 주었다. 종료했다고 생각한 프로세스가 자동 재시작된 사건도 회고한다. 사고가 없었다는 경험을 보호 설계의 충분한 증거로 받아들이는 이야기는 아니다.

### 급성장의 관심과 개인적 부담 (08:08–13:21)

이름 변경, 언론 연락, 기여와 이슈의 폭증으로 감당하기 어려운 상황이 되었다고 말한다. 이전 PDF 소프트웨어 사업과 번아웃을 돌아보며 자신이 좋아한 것은 코딩 자체보다 무언가를 만드는 일이었다고 설명한다.

새 회사를 다시 운영하기보다 큰 연구 조직과 일하는 길을 선택한 배경도 이야기한다. 제품은 복제할 수 있어도 개인의 평판과 신뢰는 같은 방식으로 복제되지 않는다고 강조한다.

### 보안과 기능의 사후 비용 (13:27–19:24)

보안 보고에 대응하며 샌드박스·허용 목록·파일 경계·원자적 설정 기록 등을 강화했다. 하지만 변경은 호환성·속도·업데이트 경험에 비용을 만들었다. 검증되지 않은 보고와 과장된 보도에 대한 불만도 밝힌다. 제시한 악성 스킬 비율은 발표자 측 분석 주장이다.

무료 기여자들의 기능을 계속 받아들이고 옵션을 늘리면서 조합을 테스트하기 어려워졌다. 기능 작성 비용보다 이후 유지 책임이 더 크다는 교훈이다.

특정 모델과 구독 조건에 지나치게 최적화한 뒤 공급자의 정책 변경에 빠르게 대응하기 어려웠다고 회고한다. 의존하는 서비스의 사업 모델이 자신의 제품에도 영향을 준다는 점을 강조한다.

### 다시 자신의 제품을 쓰고 집중하기 (19:29–26:58)

모두를 위한 제품을 만들다가 자신이 쓰지 않는 제품이 되었고, 지원·보안·조직 업무가 즐거움을 대체했다고 말한다. 비영리 조직과 기여자·후원사의 도움으로 책임을 분담하면서 만드는 즐거움을 되찾았다고 설명한다.

향후 방향은 여러 모델·기기에서 사용 가능한 오픈소스 에이전트, 음성과 멀티모달 인터페이스, 팀 세션 공유와 작업 조율이다. 자율 실행이 계속 가능하더라도 불필요한 토큰 소모를 줄이는 설계가 남아 있다.

### Q&A — 구현보다 검증과 운영 (27:02–33:31)

세션을 주제 단위로 오래 유지하고, 검토·테스트된 PR이나 직접 눌러 볼 결과물로 주의를 전환하고 싶다고 설명한다. 루프·그래프는 입력과 조건에 따라 일을 수행하는 자동화의 연장이라고 본다.

코드 검토의 깊이는 위험에 따라 다르게 두지만, 실제 사용감은 사람의 직접 확인도 필요하다. 개인 오픈소스 작업과 직장의 검토 기준이 다르다는 점도 명시한다. 초기 사용자는 자신과 친구들로 시작하라고 제안한다.

### Q&A — 경계·비전·실행 자원 (33:36–41:40)

보안에서 보장하는 경계를 먼저 명시했어야 한다고 회고한다. 기능 PR을 거절할 기준을 위해 `vision.md`에 현재 목적과 방향을 쓰는 방법을 소개한다.

여러 세션이 동시에 테스트하면 CPU·스레드가 과도하게 사용되어 실패와 재시도가 생긴다. Mac·Windows 테스트 머신과 로컬 자원이 필요한 작업을 여러 기기에 안정적으로 배분하는 것도 해결되지 않은 불편으로 든다.

대형 세션을 정기 heartbeat마다 다시 보내면 캐시·토큰 비용이 커질 수 있다. 켜진 원격 컴퓨터에 에이전트를 두면 노트북을 닫아도 계속 실행하고 화면 조작 충돌을 피할 수 있다는 개인 설정도 설명한다. 새 제품에서는 자신이 쓰고 싶고 다른 사람이 해결을 고마워할 문제를 찾으라고 말한다.

## 예시

| 겪은 문제 | 발표자가 도출한 교훈 |
|---|---|
| 계속 늘어난 기능과 옵션 | 병합은 장기 유지 책임을 받아들이는 일 |
| 모델 구독 정책 변경 | 공급자의 사업 조건도 의존성 위험 |
| 창작보다 지원 업무에 매몰 | 역할 분담과 자신이 쓰는 제품에 대한 집중 |
| 병렬 테스트의 자원 경쟁 | 실행 머신과 연산 자원 조율도 필요 |
| 추상적인 기능 아이디어 | 직접 써 보고 검토할 결과물로 구체화 |

## 요약

- 개인의 불편을 해결한 경험이 초기 제품의 출발점이었다.
- 급성장 뒤에는 기능·보안·의존성의 유지 비용이 남는다.
- 비전, 책임 분담, 실제 사용과 검증이 지속적인 개발을 돕는다.
- 장기 에이전트에는 토큰과 실행 자원 관리도 중요하다.
