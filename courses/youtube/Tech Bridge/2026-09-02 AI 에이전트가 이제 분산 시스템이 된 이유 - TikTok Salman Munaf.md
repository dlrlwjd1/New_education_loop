- 핵심 주제: 외부 API와 데이터베이스를 호출하고 현실의 상태를 바꾸는 AI 에이전트를 분산 시스템으로 설계하기 위한 안정성 원칙
- 핵심 메시지: 모델은 확률적 코디네이터(probabilistic coordinator)다. 더 똑똑한 모델만으로 네트워크 실패, 중복 요청, 오래된 상태, 과도한 권한을 해결할 수 없으므로 에이전트의 행동을 제한·관찰·복구하는 결정론적 시스템 장치가 필요하다.

## 내용

### 챗봇에서 운영 시스템으로 경계가 이동했다
텍스트를 입력받아 텍스트만 출력하는 챗봇의 잘못은 잘못된 문장에 그쳤다. 에이전트는 도구, 외부 서비스, 데이터베이스, 큐를 호출하며 실제 상태를 바꾼다. 따라서 시스템의 경계는 LLM을 넘어 자격 증명, 외부 의존성, 영속 상태, 수행 가능한 행동 전체로 확장된다.

발표자는 Replit 에이전트의 운영 데이터베이스 삭제 사례와 Air Canada 챗봇의 잘못된 환불 안내를 예로 든다. 견고한 백업, 범위가 제한된 권한, 정책의 권위 있는 원본(authoritative source of truth)이 있었다면 피해를 줄일 수 있었다는 설명이다.

### 에이전트는 확률적 코디네이터다
전통적인 분산 시스템의 워크플로 코디네이터는 미리 정한 상태 전이와 분기를 따른다. AI 에이전트는 계획, 행동, 관찰, 저장, 다음 결정의 루프를 돌지만 선택하는 행동과 순서가 매번 달라질 수 있다.

```text
계획 → 행동 → 관찰 → 상태 저장 → 다음 행동 결정 ↺
```

각 단계는 시스템 경계를 넘는다.

- 계획 중 외부 데이터 소스를 조회한다.
- 행동 중 API나 데이터베이스에 부수 효과를 만든다.
- 관찰 중 부분 결과를 성공으로 오해할 수 있다.
- 저장 중 잘못된 정보를 장기 상태로 굳힐 수 있다.
- 결정 중 실패를 반복 재시도해 장애를 확산할 수 있다.

따라서 각 단계의 입력, 호출, 결과, 상태 변경을 영속적으로 남겨 실패 지점과 복구 경로를 재구성할 수 있어야 한다.

### 타임아웃은 실패가 아니라 상태 불명이다
원격 호출이 타임아웃됐다고 서버 작업이 실패한 것은 아니다. 서버에서 환불을 완료했지만 응답만 유실됐을 수 있다. 에이전트가 단순히 재시도하면 이중 환불이 발생한다.

안전한 도구 계약에는 다음이 필요하다.

- 요청마다 고유한 request ID를 부여한다.
- 같은 의도를 가진 재시도에는 같은 멱등성 키(idempotency key)를 사용한다.
- 서버는 같은 키의 중복 요청에 부수 효과를 다시 만들지 않는다.
- 에이전트가 이전 요청의 실제 상태를 조회할 API를 제공한다.

```text
timeout ≠ failure
timeout = success / failure / processing 중 무엇인지 알 수 없음
```

도구의 응답 스키마도 성공, 명시적 실패, 알 수 없음(unknown)을 구분해야 한다.

### 재시도에는 예산과 백오프가 필요하다
에이전트는 오류를 만나면 반복해서 다시 시도하는 경향이 있다. 여러 에이전트가 동시에 같은 의존성을 호출하면 재시도 폭풍(retry storm)이 생겨 하위 시스템 장애가 전체 시스템으로 번질 수 있다.

다음 제한을 코드와 인프라에서 강제해야 한다.

- 최대 턴 수(max turns)
- 최대 병렬 호출 수(max parallel calls)
- 최대 비용·토큰 예산(max spend)
- 요청 속도 제한(rate limit)
- 지수 백오프(exponential backoff)
- 하위 시스템이 불안정할 때 호출을 막는 서킷 브레이커(circuit breaker)

이 한도는 프롬프트 권고가 아니라 모델이 우회할 수 없는 결정론적 제어여야 한다.

### 행동에 영향을 주는 컨텍스트는 상태다
에이전트의 메모리가 이후 행동을 바꾼다면 단순한 참고 문맥이 아니라 시스템 상태다. 상태는 오래되거나, 권위 있는 데이터와 충돌하거나, 이후 행동을 계속 오염시킬 수 있다.

발표자는 메모리를 두 종류로 구분한다.

- 단기 메모리: 한 실행에 묶인 대화 스레드와 임시 작업 상태
- 장기 메모리: 프로젝트 파일, 시스템 프롬프트, 데이터베이스, 캐시 등 실행을 넘어 남는 정보

메모리는 출처 추적(provenance)과 무효화(invalidation)가 가능한 캐시처럼 다뤄야 한다. 원본 데이터가 바뀌면 관련 기억을 폐기하거나 다시 읽어야 하며, 여러 소스가 충돌할 때 어떤 원본을 우선할지도 미리 정해야 한다.

### 다단계 작업에는 보상 작업이 필요하다
여러 시스템을 넘는 작업은 중간까지만 성공할 수 있다. 예를 들어 내부 티켓을 갱신하고 고객에게 이메일을 보냈지만 CRM 갱신에 실패할 수 있다. 일반 데이터베이스 트랜잭션처럼 전체를 원자적으로 되돌릴 수 없다면 **보상 작업(compensating action)**을 정의해야 한다.

- 잘못된 고객 이메일에는 정정 또는 사과 이메일을 보낸다.
- 일부 시스템에만 반영된 변경은 반대 작업을 수행하거나 사람에게 넘긴다.
- 되돌릴 수 없는 행동은 실행 전 승인과 더 좁은 조건을 요구한다.

에이전트가 실패 후 무엇을 할지는 모델의 즉흥 판단에 맡기지 말고 도구 계약과 워크플로에 명시한다.

### 최소 권한과 행동 단위 승인을 사용한다
에이전트가 작업할 수 있도록 데이터베이스 전체 읽기·쓰기 권한을 주는 방식은 위험하다. 읽기와 쓰기를 분리하고 호출 가능한 도구를 allowlist로 제한해야 한다. 무해한 모델도 강한 자격 증명을 가지면 위험한 시스템이 될 수 있다.

사람의 승인도 포괄적인 허가가 되어서는 안 된다. 승인에는 다음 범위를 묶는다.

- 승인된 구체적 행동
- 대상과 금액 같은 파라미터
- 요청한 행위자와 승인자
- 승인 시각과 만료 시각

30달러 환불 승인이 이후의 300달러 환불까지 허용해서는 안 된다.

### 로그가 아니라 전체 추적이 필요하다
사고가 났을 때 팀은 에이전트가 어떤 정보를 보고 왜 그 결정을 했는지 재구성해야 한다. 일반 애플리케이션 로그만으로는 부족하다.

추적에는 다음이 포함되어야 한다.

- 사용한 모델과 버전
- 시스템·사용자 프롬프트
- 검색한 컨텍스트와 출처
- 모든 도구 호출, 요청, 응답, 오류
- 데이터와 메모리에 쓴 내용
- 받은 사람 승인과 적용 범위
- 실행 비용, 턴 수, 재시도 횟수

이 정보가 있어야 잘못된 모델 판단과 네트워크 오류, 오래된 상태, 권한 문제를 구분할 수 있다.

### 모델 능력과 시스템 안전은 다른 문제다
더 좋은 모델은 실수 확률을 낮추지만 네트워크 지연, 부분 실패, stale data, 적대적 입력을 없애지 못한다. 에이전트 안전성은 “모델이 옳을 것인가?”보다 다음 질문으로 설계해야 한다.

```text
모델이 틀렸을 때 시스템이 무엇을 하도록 허용하는가?
그 행동의 범위를 제한할 수 있는가?
무슨 일이 일어났는지 관찰할 수 있는가?
실패 후 일관된 상태로 복구할 수 있는가?
```

## 예시

### 안전한 환불 도구 계약

```text
refund_customer(
  request_id,
  idempotency_key,
  customer_id,
  order_id,
  amount,
  approval_id
)

보장 조건
- 같은 idempotency_key는 한 번만 환불한다.
- timeout 후에는 status(request_id)로 확인한다.
- approval_id는 고객·주문·금액·만료 시각과 일치해야 한다.
- 에이전트별 환불 한도와 일일 비용 예산을 강제한다.
- 모든 요청·응답·승인을 추적한다.
```

### 에이전트 운영 체크리스트

```text
1. 모든 부수 효과 도구가 멱등성을 지원하는가?
2. timeout을 unknown 상태로 처리하고 조회할 수 있는가?
3. 최대 턴·병렬 호출·비용·재시도 예산이 있는가?
4. 메모리에 출처와 만료·무효화 규칙이 있는가?
5. 다단계 작업마다 보상 또는 사람 에스컬레이션 경로가 있는가?
6. 자격 증명이 최소 권한으로 분리되어 있는가?
7. 승인이 행동과 파라미터, 만료 시각에 묶여 있는가?
8. 사고 당시 모델·프롬프트·컨텍스트·도구 호출을 재구성할 수 있는가?
```

## 요약
- 외부 시스템을 호출해 상태를 바꾸는 순간 AI 에이전트는 분산 시스템의 일부가 된다.
- LLM은 정해진 상태 머신이 아니라 확률적 코디네이터이므로 행동 경계에는 결정론적 제어가 필요하다.
- 원격 호출의 타임아웃은 실패가 아니라 상태 불명이므로 request ID, idempotency key, 상태 조회가 필수다.
- 최대 턴, 병렬성, 비용 예산, 지수 백오프, 서킷 브레이커로 재시도 폭풍과 연쇄 장애를 막는다.
- 행동에 영향을 주는 메모리는 출처 추적과 무효화가 가능한 캐시로 관리한다.
- 여러 시스템을 넘는 작업에는 실패 시 실행할 보상 작업과 복구 경로가 있어야 한다.
- 권한은 최소 범위로 주고 사람 승인은 특정 행동·파라미터·만료 시각에 묶는다.
- 모델 성능 향상은 시스템 안전장치를 대체하지 못하며, 틀린 행동을 제한·관찰·복구할 수 있어야 한다.
