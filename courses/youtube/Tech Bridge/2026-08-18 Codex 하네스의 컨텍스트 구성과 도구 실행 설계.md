# Codex 하네스의 컨텍스트 구성과 도구 실행 설계

## 개요

- **업로드일:** 2026-08-18
- **채널:** Tech Bridge
- **발표자·출처:** Dominik Kundel / OpenAI
- **원본:** [YouTube](https://www.youtube.com/watch?v=1eMDZjsVOh4)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 20:22, 자동 자막 언어 `en`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 메시지 전달부터 컨텍스트 구성, 비동기 도구, 샌드박스, 자동 검토와 장기 실행까지 하네스의 내부 설계를 설명한다.

## 내용

### UI와 추론 사이의 두 프로토콜 (00:00–04:01)

발표 당시 Codex 하네스는 Rust 기반 오픈소스로 소개된다. UI와 하네스 사이에는 App Server 프로토콜을, 하네스와 모델 추론 사이에는 Responses API를 사용한다. 이를 통해 별도 UI가 같은 하네스를 사용하거나 호환 모델 공급자를 연결하는 구조를 설명한다.

발표자는 모델과 API가 빠르게 바뀌므로 이 설명은 발표 시점의 설계라고 전제한다.

### 컨텍스트의 크기·유연성·캐시 (04:06–06:46)

불필요한 정보는 비용을 늘리고 상충하는 지시를 만들 수 있다. 도구를 모두 즉시 넣지 않고 일부를 지연 로딩 대상으로 등록해 필요할 때 검색한다.

스킬 목록은 당시 구현에서 최대 컨텍스트의 2%로 제한하며, 목록이 길어지면 설명을 줄인다고 소개한다. 정적인 모델 지침과 변동하는 도구·스킬 목록을 구분해 캐시 가능성도 고려한다.

### 비동기 작업·브라우저·파일 (06:49–11:43)

하위 에이전트와 백그라운드 터미널은 생성 후 입력을 보내거나 완료를 기다리는 방식으로 관리한다. 주 에이전트는 독립적인 작업을 계속할 수 있다.

브라우저 조작은 지속적인 Node REPL에서 JavaScript를 작성해 탭과 상태를 이어 사용하는 방식으로 설명한다. 파일 수정은 패치 도구, 검색과 탐색은 셸 및 ripgrep을 활용한다. 플랫폼별 샌드박스 구현으로 macOS Seatbelt, Linux Bubblewrap, 별도 Windows 샌드박스를 소개한다.

### 승인 피로를 줄이는 Auto Review (11:46–15:15)

잦은 승인 때문에 전체 접근을 켜면 의도하지 않은 삭제나 외부 업로드 위험이 커질 수 있다. 자동 검토 에이전트는 별도 읽기 전용 맥락에서 사용자 승인 범위, 요청의 영향, 실행할 도구 호출을 판단한다. 같은 삭제라도 사용자가 요청했는지에 따라 판단이 달라진다.

목표는 반복 승인을 줄이면서 권한과 데이터 이동의 경계를 유지하는 것이다. 이 설명은 개념적 요약이며 모든 정책 세부 사항을 다루지는 않는다.

### 빠른 추론 이후의 병목과 긴 실행 (15:19–20:22)

추론이 빨라지면 도구 호출 사이의 네트워크 왕복이 병목이 된다. WebSocket 모드는 지속 연결과 상태를 활용해 전체 기록 대신 새 도구 결과 같은 변경분을 보낸다고 설명한다.

목표 실행은 구체적인 목표를 계속 주입하다가 에이전트가 완료를 표시하면 끝나는 구조다. 그래서 목표는 짧고 검증 가능해야 한다. 컨텍스트가 길어지면 서버 측 압축 결과를 이후 턴에 사용한다. 발표자는 도구 검색·패치·WebSocket·압축 같은 기능을 자체 에이전트에도 활용할 수 있다는 점으로 마무리한다.

## 예시

메시지 한 번이 지나가는 경로:

`UI → App Server → 컨텍스트 구성 → Responses API → 모델의 도구 요청 → 샌드박스·필요한 검토 → 도구 결과 → 다음 추론`

장시간 작업에서는 이 루프에 비동기 작업, 목표 지속, 컨텍스트 압축이 더해진다.

## 요약

- 하네스는 모델 주변의 상태·도구·권한·성능을 관리한다.
- 지연 로딩과 변경분 전송으로 입력 및 통신 비용을 줄인다.
- 긴 자율 실행에는 검증 가능한 목표와 승인·압축 설계가 필요하다.
