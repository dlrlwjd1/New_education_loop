## 내용

### 에이전틱 소프트웨어 스택의 두 루프
발표자는 에이전틱 소프트웨어 스택을 내부 루프와 외부 루프로 구분한다.

- 내부 루프는 코딩 에이전트 하니스(harness)다. 컨텍스트 관리자, 도구와 MCP, 메모리·상태, 스킬 로더가 포함된다.
- 외부 루프는 조직의 워크플로다. 스킬, 서브에이전트, MCP 서버, hooks를 조합해 실제 업무 과정을 실행한다.

두 루프 아래에는 sandbox, MCP gateway, model gateway, 지식 그래프, 스킬 레지스트리, 워크플로 마켓플레이스 같은 공통 기반이 필요하다. 컨텍스트 계층은 프로젝트 지침 파일, MCP 스키마, 대화 기록, 검색한 파일과 코드 등을 작업에 맞춰 공급한다.

### 코딩 워크플로는 전체 가치 흐름의 일부다
명세(specify), 계획(plan), 작업 분해(tasks), 구현(implement)의 네 단계는 코딩 에이전트에서 익숙하지만, 기업의 제품 수명 주기 전체에서 보면 한 번의 제품 증분(product increment)에 불과하다.

실제 흐름에는 더 많은 단계가 있다.

```text
제품 전략과 성공 지표
→ 시장·경쟁 조사와 고객 인터뷰
→ 문제·해결책 발견과 실험
→ 데이터 정제·파이프라인·카탈로그 준비
→ 제품 증분 구현
→ 인프라 프로비저닝과 플랫폼 운영
→ 출시, 성능 최적화, 장애 대응
→ 다음 제품 주기
```

모바일, 사내 플랫폼, 고객 서비스 등 시스템마다 SDLC가 다르므로 하나의 거대 워크플로로 모든 업무를 해결할 수 없다. 조직은 작고 조합 가능한 실행 단위를 여러 워크플로에서 재사용해야 한다.

### 노하우가 축적되는 핵심 단위는 스킬이다
Hooks는 이벤트에 반응해 동작을 실행하고, MCP는 외부 도구에 접근하며, 서브에이전트는 좁은 작업을 별도 컨텍스트에 위임한다. 이 요소만으로 조직이 **어떻게** 일해야 하는지에 관한 노하우가 만들어지지는 않는다.

발표자는 반복 업무의 절차, 판단 기준, 스크립트, 도메인 정책을 담는 스킬을 조직 노하우의 핵심 단위로 본다. 워크플로는 여러 스킬과 도구를 조합해 런타임에서 에이전트 하니스의 행동을 형성하는 blueprint다.

### 마이크로서비스 원칙을 스킬에 적용한다
스킬 확장은 새로운 문제가 아니라 마이크로서비스와 내부 플랫폼에서 이미 다뤄온 설계 문제와 비슷하다.

좋은 스킬의 조건은 다음과 같다.

- 재사용 가능(reusable): 한 작업에서 끝나지 않고 다른 팀과 워크플로에서도 쓴다.
- 모듈화(modular): 하나의 좁고 명확한 책임을 가진다.
- 발견 가능(discoverable): 필요한 사람이 검색하거나 에이전트가 자동으로 찾는다.
- 이식 가능(portable): 공통 표준을 따르는 여러 하니스에서 사용할 수 있다.
- 전문화(specialized): 모든 것을 처리하는 거대 스킬을 피한다.
- 조합 가능(composable): 함께 사용할 때 중복 지침이나 충돌이 없다.
- 일관적이고 결정론적: 같은 정책과 검증 절차를 반복 적용한다.
- 비용 효율적: 필요한 순간에 필요한 지침만 로드한다.

마지막 조건은 점진적 공개(progressive disclosure)와 연결된다. 모든 지침을 항상 컨텍스트에 넣지 않고, 에이전트가 작업에 필요한 스킬만 선택하고 상세 자료는 그때 읽게 하면 토큰 사용을 줄일 수 있다.

### 스킬은 조직 지식을 실행 가능한 단위로 만든다
스킬은 지침 문서만이 아니라 필요할 때 실행할 결정론적 스크립트와 산출물 형식을 함께 가질 수 있다. 따라서 조직의 노하우가 다음 특성을 얻는다.

- 실행 가능(executable)
- 하니스 사이에 이동 가능(portable)
- 반복 적용해도 저렴함(cost-efficient)

발표자는 데이터 보존 정책을 예로 든다. 규제 검토 워크플로가 보존 정책, 공개 기준, GDPR 규칙, 제출 템플릿 같은 여러 스킬을 자동으로 조합하면 웹·모바일 등 서로 다른 제품에서도 같은 기준을 적용하고 결정론적인 감사 보고서를 남길 수 있다.

### 거버넌스가 없으면 새로운 기술 부채가 된다
팀별로 스킬을 자유롭게 만들기만 하면 다음 문제가 발생한다.

| 위험 | 결과 |
| --- | --- |
| 중복 | 여러 팀이 같은 기술과 정책을 위한 스킬을 반복 개발한다. |
| 품질 저하 | 모델과 환경은 바뀌는데 스킬을 테스트·갱신하지 않는다. |
| 발견 실패 | 필요한 스킬이 있어도 존재와 위치를 알 수 없다. |
| 소유권 부재 | 고장이나 정책 변경이 생겨도 책임질 사람이 없다. |
| 조합 충돌 | 서로 다른 스킬의 지침과 스크립트가 충돌한다. |
| 보안 위험 | 외부 스킬에 prompt injection이나 위험한 스크립트가 포함될 수 있다. |
| 권한 누출 | 민감한 업무 로직이나 도구가 불필요한 사용자에게 노출된다. |

모델이 좋아져도 조직 정책에 맞춘 스킬이 자동으로 좋아지는 것은 아니다. 새 모델에서도 호출과 결과가 올바른지 지속해서 평가해야 한다.

### 개인에서 팀, 전사 플랫폼으로 확장한다
스킬 도입은 세 층으로 확장된다.

1. 개인이 정해진 구조에 따라 스킬을 만들고 시험·개선한다.
2. 팀 저장소에서 공유하며 같은 기술과 제품에 맞게 공동 개선한다.
3. 중앙 플랫폼에 검증된 스킬을 게시하고 전 조직이 검색·설치·업데이트한다.

중앙 플랫폼에는 다음 기능이 필요하다.

- 메타데이터가 있는 검색 가능한 카탈로그
- 에이전트가 검색하는 MCP 인터페이스와 사람이 쓰는 CLI
- 스킬 사이의 의존성 관리
- 버전, 출시, 폐기 등 수명 주기 관리
- 역할 기반 접근 제어
- 평가와 사용 현황의 관측 가능성

발표자는 이를 Backstage 같은 내부 개발자 포털(Internal Developer Portal, IDP)의 서비스 카탈로그에 비유한다. 새 작업을 시작할 때 에이전트가 기존 스킬을 발견해 최신 버전을 가져오게 하면 중복을 줄일 수 있다.

### 중앙 배포와 분산 소유를 결합한다
플랫폼만으로 거버넌스가 완성되지는 않는다. 아키텍트, 엔지니어링 리드, 인프라 리드, 보안 리드가 각 도메인의 스킬을 소유하고 변경이 조직 정책에 맞는지 책임져야 한다.

목표는 모든 작성을 중앙팀이 독점하는 것이 아니다. 팀은 스킬을 실행하고 개선해 중앙 플랫폼에 다시 기여한다. 중앙에는 발견·배포·검증의 공통 기반을 두고, 내용의 소유권은 도메인 전문가에게 나누는 구조다.

### 15개 팀 시뮬레이션이 보여준 방향
발표자는 15개 팀이 6개월 동안 스킬을 만들고 사용하는 상황을 시뮬레이션한다. 거버넌스가 없으면 중복이 늘고, 팀별 성숙도 차이 때문에 생산성·품질·보안이 고르지 않으며 토큰 비용도 높아진다.

중앙 레지스트리와 거버넌스를 적용하면 새 스킬을 만들기 전에 기존 스킬을 발견하고 가져올 수 있다. 모든 팀이 완전히 같은 결과를 내지는 않지만 중복을 줄이고 생산성, 품질, 보안, 비용에 공통 기준을 형성할 수 있다.

### 스킬에서 전체 워크플로 거버넌스로
스킬은 외부 루프의 한 요소일 뿐이다. 같은 원칙을 전체 워크플로에도 적용해야 한다. 인프라 프로비저닝 같은 검증된 워크플로를 중앙 카탈로그에서 가져와 필요한 스킬과 함께 실행하고, 개선 사항을 다시 게시하는 흐름이 필요하다.

앞으로 중요해질 영역은 세 가지다.

- 스킬 레지스트리와 내부 개발자 포털 연동
- 구조, 호출 조건, 결과 품질을 확인하는 스킬 평가(evaluation)
- 사용 결과로 스킬을 자동 개선하는 폐쇄 루프

자동 진화는 거버넌스를 대체하지 않는다. 품질 기준과 승인 경계 없이 자동 개선을 먼저 켜면 잘못된 스킬을 더 빠르게 확산시킬 수 있다.

## 예시

### 규제 검토 워크플로의 조합

```text
regulatory-disclosure-review workflow
├─ data-retention-policy skill
├─ disclosure-standard skill
├─ GDPR-rules skill
└─ filing-template skill

출력
├─ 결정론적 감사 보고서
├─ 위반 사항 목록
└─ 수정할 코드·설정 피드백
```

### 중앙 스킬 플랫폼 점검표

```text
1. 스킬의 책임과 호출 조건이 좁고 명확한가?
2. 소유 팀과 유지보수 담당자가 기록되어 있는가?
3. 검색 가능한 메타데이터와 버전이 있는가?
4. 의존 스킬·도구·권한이 선언되어 있는가?
5. prompt injection과 포함 스크립트를 검사하는가?
6. 새 모델에서도 호출과 결과를 평가하는가?
7. 폐기되거나 대체된 버전을 구분할 수 있는가?
8. 개선된 스킬을 중앙 카탈로그에 다시 기여할 수 있는가?
```

## 요약
- 에이전틱 스택은 하니스의 내부 루프와 조직 워크플로의 외부 루프로 구성되며, 스킬은 외부 루프의 핵심 노하우 단위다.
- 명세·계획·구현은 전체 제품 가치 흐름 중 일부이므로 여러 전문 워크플로와 스킬을 조합해야 한다.
- 스킬은 작고 전문화되며 재사용·발견·이식·조합 가능하도록 설계하고 점진적 공개로 컨텍스트 비용을 줄여야 한다.
- 거버넌스 없는 스킬은 중복, 품질 저하, 보안, 권한, 소유권 문제를 가진 새로운 기술 부채가 된다.
- 개인 작성 → 팀 공유 → 중앙 플랫폼 배포의 단계로 확장하고, 카탈로그·버전·의존성·접근 제어·평가를 제공해야 한다.
- 중앙 인프라와 도메인별 분산 소유권을 함께 두어 팀의 개선이 조직 전체에 다시 흐르게 한다.
- 스킬뿐 아니라 전체 워크플로에도 같은 거버넌스 원칙을 적용해야 하며, 자동 진화 전에 품질 기준과 안전장치를 갖춰야 한다.
