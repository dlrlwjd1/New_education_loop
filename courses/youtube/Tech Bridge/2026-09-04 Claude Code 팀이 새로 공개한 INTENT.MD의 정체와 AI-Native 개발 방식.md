# [한영자막] Claude Code 팀이 새로 공개한 INTENT.MD의 정체와 AI-Native 개발 방식

## 개요
- 영상: [Claude Code 팀이 새로 공개한 INTENT.MD의 정체와 AI-Native 개발 방식](https://www.youtube.com/watch?v=rGaSkBWjoHA)
- 채널: Tech Bridge
- 업로드일: 2026-09-04
- 길이: 15:11
- 관련 자료: [Anthropic 공식 AI-Native SDLC 플레이북](https://claude.com/blog/the-ai-native-sdlc-playbook)
- 핵심 주제: 코딩 단계에만 에이전트를 쓰는 것을 넘어 기획, 설계, 구현, 테스트, 배포, 유지보수까지 소프트웨어 개발 수명 주기(Software Development Life Cycle, SDLC) 전체를 AI 네이티브로 재설계하는 방법
- 핵심 메시지: 에이전트가 코드를 빠르게 생성하면서 병목은 구현 자체에서 개발 프로세스로 이동했다. 각 단계의 의사결정을 버전 관리되는 산출물로 남기고, 다음 단계의 독립 에이전트가 이를 입력으로 사용하게 해야 전체 흐름을 자동화할 수 있다.

## 내용

### 코드가 아니라 프로세스가 병목이다
전통적인 SDLC는 기획(plan), 설계(design), 구현(build), 테스트(test), 배포(deploy), 유지보수(maintain) 순으로 진행된다. 과거에는 구현 단계가 가장 오래 걸리고 비용도 컸지만, 코딩 에이전트가 이 시간을 크게 줄였다.

영상은 여기서 한 단계 더 나아가 묻는다. 구현만 두 배 빨라지는 데 그치지 않고, 나머지 단계에도 에이전트를 적용해 전체 리드 타임을 줄이려면 어떻게 해야 하는가?

핵심 해법은 단계마다 대화의 결과를 파일로 확정하는 **산출물 사슬(artifact chain)**이다.

```text
아이디어·버그·운영 신호
        ↓
     intent.md       무엇을, 왜, 어떤 제약 아래 원하는가
        ↓
      spec.md        요구사항과 설계는 무엇인가
        ↓
      plan.md        어떤 파일을 어떤 순서로 바꾸고 어떻게 검증할 것인가
        ↓
 구현 diff + 테스트 결과
        ↓
  PR + 자동 리뷰·승인 게이트
        ↓
 운영 감시 → 이상 발견 시 새로운 intent.md
```

각 산출물은 버전 관리되고, 한 단계에서 승인된 산출물이 다음 단계를 시작시키는 입력이 된다. 에이전트끼리 이전 대화 내용을 공유하지 않아도 문서만으로 작업을 이어받을 수 있다.

### 기획(Plan) — 디스커버리와 `intent.md`
기존 기획에서는 이해관계자 인터뷰, 워크숍, PRD 작성과 여러 차례의 인수인계가 필요했다. AI 네이티브 방식에서는 아이디어 제안자(originator)가 먼저 에이전트와 대화한다.

에이전트는 다음 항목이 구체화될 때까지 반복해서 질문한다.

- 해결하려는 문제와 원하는 결과
- 영향을 받는 사용자와 시스템
- 범위와 제약 조건
- 성공의 기준
- 아직 답하지 못한 질문

이 대화를 에이전트가 사람이 읽을 수 있고 기계가 실행에 활용할 수 있는 `intent.md`로 정리한다. 제안자는 오해나 누락을 바로잡고, 제품 책임자(product owner)가 이를 검토해 다음 단계로 보낼지를 결정한다.

의도는 제품 관리자나 개발자만 만들 수 있는 것이 아니다. 고객의 버그 신고, 개발자의 프로세스 개선 제안, 운영 경보도 모두 `intent.md`의 출발점이 될 수 있다. 여러 의도는 Markdown 목록, Notion, Linear 같은 백로그에서 분류·우선순위화할 수 있으며, 이 분류 작업에도 에이전트를 사용할 수 있다.

### 설계(Design) — `intent.md`에서 `spec.md` 생성
승인된 `intent.md`는 요구사항과 설계를 담은 `spec.md`로 변환된다. 처음에는 사람이 프롬프트로 실행하고, 흐름이 안정되면 `intent.md`가 승인될 때 자동 작업이 실행되도록 만들 수 있다.

명세 생성에는 조직의 정책과 지식을 함께 적용한다.

- 브랜드 및 디자인 가이드
- 보안·컴플라이언스 정책
- UX 표준
- 저장소의 `AGENTS.md`·`CLAUDE.md`
- 팀 고유의 스킬(skills)과 반복 절차

하나의 범용 템플릿이 모든 조직에 맞는 것은 아니다. 기본 plan mode를 쓸 수도 있고, 조직의 명세 형식과 정책을 담은 전용 스킬을 만들 수도 있다. 중요한 것은 모든 산출물이 같은 거버넌스 기준을 따르도록 표준화하는 것이다.

### 구현(Build) — 독립 실행 가능한 `plan.md`
엔지니어는 승인된 `intent.md`와 `spec.md`를 에이전트의 plan mode에 전달한다. 에이전트가 만든 계획은 다음을 포함해야 한다.

- 변경할 파일
- 작업 순서와 독립적으로 병렬화할 수 있는 단위
- 위험과 제약 조건
- 변경으로 깨질 수 있는 기존 동작
- 완료를 증명할 테스트와 성공 기준

좋은 `plan.md`는 이전 대화를 전혀 보지 못한 다른 엔지니어나 에이전트도 그것만 읽고 구현할 수 있어야 한다. 구현이 계획과 달라지면 코드와 함께 `plan.md`도 갱신해 실제 변경과 감사 기록이 어긋나지 않게 한다.

산출물과 Git 기록을 남기면 각 단계에 걸린 시간, 재작업 횟수, 계획과 최종 diff의 일치 여부 같은 선행·후행 지표를 측정할 수 있다. 이를 통해 AI 도입이 실제 전달 성과를 개선하는지도 평가할 수 있다.

### 구현(Build) — 자율 실행과 병렬 작업
계획이 충분히 구체적이면 에이전트가 매번 편집 허가를 기다리지 않고 구현하도록 할 수 있다. 하지만 자동 승인(auto mode)을 안전하게 쓰려면 먼저 허용 범위를 좁혀야 한다.

- 저장소별 명령·파일 접근 권한을 명시한다.
- 허용할 도구, 웹 출처, 패키지를 정한다.
- hooks로 금지된 폴더 변경이나 승인되지 않은 의존성 업그레이드를 차단한다.
- 린트와 테스트처럼 결과가 명확한 검증 장치를 둔다.
- 작업별로 작은 폭발 반경(blast radius)을 유지한다.

서로 다른 파일을 다루는 독립 작업은 Git worktree에 분리해 여러 Claude Code 세션이 병렬로 처리할 수 있다. 한 세션 안에서는 서브에이전트(subagent)가 조사나 검증 같은 범위가 좁은 일을 맡는다. 이 구조에서는 모든 에이전트가 긴 대화 기록을 공유하는 대신 승인된 문서를 통해 작업을 넘겨받는다.

### 테스트(Test) — 검증을 구현 루프 안으로 넣는다
전통적인 방식에서는 개발이 끝난 뒤 QA를 기다리느라 며칠이 지연될 수 있다. AI 네이티브 SDLC에서는 사람의 검토 전에 에이전트가 가능한 한 많은 검증을 수행한다.

- 기능에 필요한 테스트를 작성하고 실행한다.
- 린트와 빌드 오류를 수정한다.
- 기존 동작이 깨지지 않았는지 회귀 테스트한다.
- Playwright 같은 도구로 브라우저 E2E 테스트를 수행한다.
- 화면을 캡처하거나 녹화해 시각적 결과를 증거로 남긴다.

또한 모델, 프롬프트, 스킬 같은 에이전트 설정이 바뀔 때는 **지속적 평가(continuous evals)**를 CI에서 실행한다. 과거 작업 약 20개와 기대 결과를 평가 세트로 만들어 두면, 새 모델이나 스킬이 기존 워크플로의 품질을 떨어뜨리는지 확인할 수 있다. 운영 장애도 재발 방지를 위한 새 평가 사례로 추가한다.

### 배포(Deploy) — 비동기 PR 검토와 승인 게이트
구현과 테스트가 끝나면 에이전트가 작업 브랜치나 worktree의 변경으로 pull request(PR)를 만든다. 별도의 Claude 인스턴스가 다음 기준으로 PR을 비동기 검토할 수 있다.

- 버그와 논리 오류
- 보안 취약점
- `spec.md` 및 `plan.md`와의 일치 여부
- 조직의 설계 원칙과 정책 준수

리뷰 에이전트가 남긴 의견을 또 다른 구현 에이전트가 처리할 수 있다. 보안 검사, CI 미리보기, 린트, 정책 검사도 병렬로 실행한다. 다만 특정 담당자의 승인이나 정해진 출시일처럼 사람이 책임져야 할 조건은 hook과 배포 게이트로 강제한다.

### 유지보수(Maintain) — 운영 신호가 다음 `intent.md`를 만든다
영상에서 가장 미래지향적인 부분은 유지보수 루프다. 전통적인 유지보수는 장애 알림이나 쌓인 티켓에 사람이 반응하면서 시작된다. AI 네이티브 방식에서는 다음과 같은 사건이 에이전트를 자동으로 호출한다.

- 운영 지표가 허용 범위(control band)를 벗어남
- 새 버그 티켓이나 보안 경보가 등록됨
- Slack 등의 채널에 장애 메시지가 올라옴
- 정기 점검 일정이 도래함

에이전트는 로그와 증거를 조사하고, 진단과 제안 결과를 새로운 `intent.md`로 작성한다. 작고 위험이 낮은 수정은 승인된 경로를 따라 PR까지 진행할 수 있고, 더 큰 변경은 사람이 우선순위를 판단한 뒤 기존 산출물 사슬을 다시 탄다.

이렇게 유지보수의 출력이 다시 기획의 입력이 되면서 SDLC가 닫힌 루프(closed loop)가 된다. 목표는 사람을 완전히 제거하는 것이 아니라, 작업을 시작하고 반복 확인하는 시간을 줄이면서 중요한 검토와 책임 지점에는 사람을 남기는 것이다.

### 도구보다 중요한 것은 팀에 맞는 흐름이다
영상은 특정 프레임워크를 그대로 채택하는 것이 목적이 아니라고 강조한다. 이미 Superpowers, BMAD 또는 자체 에이전트 워크플로를 사용하고 있다면 전부 버릴 필요가 없다. 팀의 위험도와 업무 특성에 따라 각 단계에서 사람과 에이전트가 맡을 비율을 정해야 한다.

반드시 유지해야 할 원칙은 다음과 같다.

- 의도와 의사결정을 대화에만 남기지 않고 버전 관리되는 산출물로 확정한다.
- 다음 담당자가 이전 대화 없이도 일을 이어받을 수 있게 한다.
- 자율성은 권한 제한, hooks, 테스트, 평가, 승인 게이트와 함께 높인다.
- 중요한 검토와 고위험 결정에는 사람을 명시적으로 배치한다.
- 팀이 익숙해질 수 있도록 파일 위치와 단계 전환 규칙을 자주 바꾸지 않는다.

## 예시

### 다크 모드 기능의 산출물 사슬

```text
1. 제안자가 에이전트와 다크 모드에서 원하는 동작과 제약을 대화한다.
2. 합의 내용을 intent/dark-mode.md에 저장하고 제품 책임자가 승인한다.
3. 에이전트가 브랜드·UX·보안 스킬을 적용해 spec.md를 작성한다.
4. 엔지니어가 plan mode에서 변경 파일, 작업 순서, 위험,
   단위·E2E 테스트를 포함한 plan.md를 승인한다.
5. 분리된 worktree에서 에이전트가 구현하고 모든 검증을 통과시킨다.
6. PR 리뷰 에이전트가 spec.md·plan.md와 실제 diff를 대조한다.
7. 사람의 최종 승인 뒤 배포하고, 운영 지표 이상은 새 intent.md가 된다.
```

### `intent.md`에 담을 최소 항목

```markdown
# Intent: 다크 모드

## 문제
[해결하려는 문제]

## 원하는 결과
[만들려는 결과와 필요한 동작]

## 영향 대상
- [영향받는 사용자]
- [영향받는 시스템]

## 제약 조건
- [반드시 지켜야 할 조건]

## 성공 기준
- [완료를 판정할 수 있는 기준]

## 열린 질문
- [아직 결정되지 않은 사항]
```

### 계획 검토 질문

```text
1. 이 변경으로 깨질 수 있는 기존 동작은 무엇인가?
2. 가장 위험한 단계는 무엇이며 어떻게 조기에 검증할 것인가?
3. 변경하지 않기로 한 범위는 무엇인가?
4. 이전 대화를 모르는 에이전트도 이 계획만으로 구현할 수 있는가?
5. 성공 여부를 사람의 주관이 아니라 테스트나 증거로 판정할 수 있는가?
6. 어떤 단계에서 반드시 사람의 승인이 필요한가?
```

## 요약
- 코딩 에이전트가 구현 시간을 줄이면서 새로운 병목은 기획, 검토, 인수인계, 승인 같은 프로세스로 이동했다.
- AI 네이티브 SDLC는 `intent.md → spec.md → plan.md → 구현·검증 → PR → 운영 피드백`으로 이어지는 버전 관리된 산출물 사슬을 만든다.
- `intent.md`는 제안자의 의도를 문제, 결과, 사용자, 제약, 성공 기준의 형태로 보존해 이후 단계의 기준점이 된다.
- 에이전트가 이전 대화 없이도 일할 수 있을 만큼 각 산출물을 자족적으로 작성해야 독립 세션과 병렬 작업이 가능하다.
- 자율성은 auto mode만 켜서 얻는 것이 아니다. 좁은 권한, hooks, worktree 격리, 테스트, 지속적 평가, PR 검토와 사람의 승인 게이트가 함께 필요하다.
- 운영 이상이 새로운 `intent.md`를 만들면 유지보수가 다음 개발 주기의 시작점이 되어 SDLC가 닫힌 루프로 이어진다.
- 영상의 제안은 고정된 정답이 아니라 팀별 위험도와 기존 방식에 맞게 조정할 플레이북이다.
