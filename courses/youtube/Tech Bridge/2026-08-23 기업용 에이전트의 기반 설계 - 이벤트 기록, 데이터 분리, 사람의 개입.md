# 기업용 에이전트의 기반 설계 - 이벤트 기록, 데이터 분리, 사람의 개입

## 내용

### 성공한 PoC 다음에 나오는 질문 (00:00~05:09)

의료 행정 업무에서 정확도·속도·비용 목표를 충족해도 운영 준비가 끝난 것은 아니다. 어떤 데이터와 권한을 사용했는지, 민감 정보가 어디로 이동했는지, 언제 누가 결정을 승인하는지, 성능을 계속 어떻게 확인하는지가 남는다. 강연은 의료·규제 산업의 경험에서 네 가지 기반을 설명한다.

### 추가 전용 이벤트 기록 (05:09~08:37)

일반 개발 로그보다 완전한 행동·접근·권한 기록을 목표로 한다. 시각이 있는 불변 이벤트를 원본으로 두고 상태를 재구성하는 이벤트 소싱을 소개한다. 쓰기는 간단해지지만 읽기에는 프로젝션·캐시·스냅샷 등 추가 설계가 필요하다. 기록의 완전성과 접근 통제까지 갖춰야 감사에 쓸 수 있으며 패턴 하나가 규정 준수를 자동 보장하는 것은 아니다.

### 사건과 민감 데이터 분리 (08:37~12:45)

이벤트에는 실제 민감 데이터 대신 스키마가 있는 불변 객체의 참조를 남긴다. 개발자는 데이터 내용을 보지 않고도 흐름과 형태를 조사할 수 있다. 객체를 사용하는 시점에 권한을 확인하고 고객 환경에 데이터를 둘 수도 있다. 관측·조정 정보와 민감한 원문을 분리해 불필요한 전파를 줄이는 접근이다.

### 사람과 모델의 공통 작업 인터페이스 (12:45~14:36)

에이전트가 수행하는 행동을 사람도 같은 작업 모델로 수행할 수 있게 한다. 어느 지점에서든 넘겨받을 수 있고 이후 단계는 실행자가 누구였는지와 무관하게 이어진다. 같은 맥락을 모델에는 프롬프트로, 사람에게는 이해하기 쉬운 UI로 제공한다.

### 평가를 기반 기능으로 만들기 (14:36~18:41)

이벤트와 원본 데이터를 이용해 특정 시점의 입력을 복원하고 프롬프트·모델·코드 변경을 비교한다. 같은 작업에서 사람과 모델의 결과를 비교할 수 있으며 고객 환경 안의 실제 데이터로 평가하는 설계도 가능하다. 비결정성과 데이터 변화 때문에 과거 오프라인 성적만으로 운영 품질을 판단할 수 없다. PoC에 요구를 뒤늦게 붙이기보다 운영 제약에서 기반을 선택하라는 결론이다.

## 예시

| 기반 | 가능해지는 확인 |
|---|---|
| 불변 이벤트 기록 | 누가 언제 어떤 행동을 했는가 |
| 버전이 보존된 객체 참조 | 당시 어떤 자료를 사용했는가 |
| 사람·모델의 공통 작업 | 사람이 같은 단계에서 넘겨받을 수 있는가 |
| 입력 재생 | 변경한 모델·프롬프트가 결과에 어떤 영향을 주는가 |

## 요약

- 운영 요구는 PoC 이후의 부속 기능이 아니라 설계의 출발점이다.
- 사건 기록과 민감 원문을 분리하고 사용 시점에 권한을 확인한다.
- 공통 작업 인터페이스와 기록 재생이 개입·평가를 뒷받침한다.
