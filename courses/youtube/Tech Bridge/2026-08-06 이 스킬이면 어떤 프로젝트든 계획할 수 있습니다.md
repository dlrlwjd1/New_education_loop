## 내용

### 한 세션에 갇힌 계획 방식의 한계
Matt Pocock이 기존에 사용하던 `/grill-me`와 `/grill-with-docs`는 에이전트가 사용자를 인터뷰해 요구 사항을 구체화하는 유용한 도구다. 하지만 이 방식은 기본적으로 한 세션 안에서 계획을 완성해야 한다.

큰 작업은 에이전트의 전체 컨텍스트 윈도우는 물론, 높은 품질로 추론할 수 있는 **스마트 존(smart zone)**에도 들어가지 않는다. 그래서 사용자는 미리 작업을 작은 범위로 제한하고, 세션 중에는 토큰을 얼마나 썼는지 신경 쓰게 된다. 계획 도중 아직 조사하지 않았거나 프로토타입을 보지 않아 답할 수 없는 질문을 만나면 진행도 막힌다.

이 때문에 만들고 싶은 프로젝트를 기준으로 AI를 사용하는 것이 아니라, AI의 한 세션 한계에 맞춰 프로젝트의 크기와 야심을 줄이는 문제가 생긴다. `/wayfinder`는 계획 자체를 여러 세션에 분산해 이 제약을 해결한다.

### Wayfinder의 핵심 모델 — 목적지, 지도, 전선, 안개
큰 프로젝트에는 대략적인 출발점과 도착하고 싶은 목적지는 있지만, 그 사이의 경로가 보이지 않는 경우가 많다. `/wayfinder`는 이 상태를 다음 개념으로 표현한다.

| 개념 | 의미 |
| --- | --- |
| 목적지(destination) | 계획이 끝났을 때 얻으려는 결과. 구현 가능한 명세나 실제 프로젝트 완료가 될 수 있다. |
| 지도(map) | 목적지까지 가기 위해 해결해야 할 의사결정과 작업의 전체 구조 |
| 의사결정 티켓(decision ticket) | 한 번의 독립된 에이전트 세션에서 조사하거나 결정할 작업 단위 |
| 전선(frontier) | 현재 정보만으로 바로 착수할 수 있는 티켓들의 집합 |
| 전쟁의 안개(fog of war) | 선행 조사·프로토타입·대화가 부족해 아직 결정할 수 없는 영역 |

Wayfinder는 처음부터 목적지까지의 모든 단계를 정확하게 예측하려 하지 않는다. 현재 전선의 티켓을 해결하면 새로운 정보와 결정이 생기고, 차단됐던 티켓이 열리면서 전선이 앞으로 이동한다. 이 과정을 반복해 안개를 걷어 내는 것이 Wayfinder의 계획 방식이다.

### 초기 인터뷰에서 첫 지도를 만든다
새 Wayfinder 작업을 시작할 때 가장 먼저 정할 것은 **목적지**다. 원하는 결과를 설명하면 에이전트가 저장소를 탐색하고 grilling skill을 호출해 다음 내용을 묻는다.

- 완료 상태(done)는 무엇인가?
- 최종 결과가 명세인지 실제 구현인지?
- 지금 확정할 수 있는 초기 요구 사항은 무엇인가?

영상의 예시는 Course Video Manager에 아이콘 선택기, 다른 다이어그램 검색, 복사·저장 기능 등을 포함한 명령 팔레트(command palette)를 추가하는 작업이다. 목적지는 바로 코드를 구현하는 것이 아니라 **구현 가능한 명세(buildable spec)**를 얻는 것이었다.

Wayfinder는 첫 인터뷰 후 부모 지도와 하위 티켓 7개를 만들었다. 하지만 아이콘 이름의 출처, 컴포넌트 저장 스키마, 팔레트 정보 구조처럼 선행 결정이 가능한 세 티켓만 당시의 전선에 놓였다. 나머지는 이 결과가 나와야 시작할 수 있는 안개 속 영역이었다.

### 네 가지 의사결정 티켓
Wayfinder 지도에는 네 종류의 티켓이 있다.

| 티켓 | 역할 |
| --- | --- |
| Research | 에이전트가 필요한 정보를 조사하고 결과와 근거를 가져온다. 하위 에이전트로 백그라운드 실행할 수도 있다. |
| Prototype | 실제로 작동하는 시제품을 만들어 추상적인 계획을 눈으로 확인하고 피드백한다. |
| Grilling | 구현 세부 사항이나 제품 방향처럼 사람의 판단이 필요한 내용을 문답으로 결정한다. |
| Task | 사람에게 연락하거나 현장 조사를 의뢰하는 등 현실에서 수행해야 하거나 다른 작업 뒤에 예약해야 하는 일을 기록한다. |

특히 프로토타입은 Wayfinder가 거대한 사전 계획만 만드는 폭포수(waterfall) 방식으로 굳어지는 것을 막는다. 낮은 충실도(low-fidelity)의 텍스트 계획을 오래 작성하는 대신, 높은 충실도의 실제 결과를 보고 방향을 수정할 수 있기 때문이다.

### 이슈 트래커가 세션 사이의 기억을 맡는다
Wayfinder는 지도와 티켓을 GitHub Issues 같은 이슈 트래커에 저장한다. 부모 이슈가 전체 지도이고, 하위 이슈가 개별 의사결정 티켓이다.

티켓을 해결하면 대화·조사·프로토타입 결과가 해당 티켓에 남고, 핵심 결정의 짧은 요약은 부모 지도에도 반영된다. 따라서 새 에이전트 세션에서도 다음 두 수준의 정보를 모두 사용할 수 있다.

- 부모 지도: 전체 진행 상황과 현재 결정 사항을 빠르게 파악
- 하위 티켓: 결정이 필요했던 배경, 원문 대화와 조사 근거를 확인

영상에서는 GitHub를 사용하지만 Wayfinder는 특정 이슈 트래커에 종속되지 않는다. 초기 설정을 거치면 Linear, Jira 등 다른 이슈 트래커와도 사용할 수 있다.

### 지도 작성과 티켓 해결에 모두 Wayfinder를 사용한다
실제 사용 흐름은 다음과 같다.

1. 큰 목표와 목적지를 넣어 `/wayfinder`를 실행한다.
2. 첫 지도와 의사결정 티켓을 만든다.
3. 현재 전선에서 착수 가능한 티켓 하나를 고른다.
4. 새 세션에서 `/wayfinder`와 해당 티켓 URL을 전달한다.
5. 조사·프로토타입·grilling·task를 완료하고 결과를 기록한다.
6. 새로 열린 티켓과 이동한 전선을 확인한다.
7. 모든 안개가 해소될 때까지 반복한다.

즉, `/wayfinder`는 처음 지도를 그릴 때만 쓰는 스킬이 아니다. 개별 티켓을 따라 실제로 지도를 걸어갈 때도 같은 스킬을 사용한다. Matt는 `/handoff`로 다음 프롬프트를 만들고 Claude 하위 에이전트를 시작했지만, 필수적인 것은 특정 에이전트 제품이 아니라 티켓 URL을 새 세션에 넘기는 구조다.

### 차단 관계가 순서와 병렬 처리를 결정한다
어떤 결정은 다른 결정이 끝난 뒤에만 내릴 수 있다. Wayfinder는 티켓 사이의 **차단 관계(blocking relationship)**를 기록해 현재 착수 가능한 티켓과 기다려야 하는 티켓을 구분한다.

```text
티켓 해결
  -> 결정과 근거 기록
  -> 차단 관계 갱신
  -> 새롭게 열린 티켓 확인
  -> 전선 이동
```

서로 의존하지 않는 티켓이 여러 개 전선에 있다면 각각을 별도 세션에서 병렬로 처리할 수 있다. 반대로 핵심 프로토타입이나 선행 결정이 필요한 티켓은 차단 상태로 둔다. 따라서 Wayfinder는 처음 만든 할 일 목록을 순서대로 실행하는 도구가 아니라, 새 정보에 따라 계속 달라지는 의사결정 그래프를 관리하는 도구다.

### 완성된 지도에서 명세와 구현 티켓을 만든다
목적지가 명세인 경우 완성된 Wayfinder 지도는 정보가 너무 많아 그대로 구현 지침으로 쓰기 어렵다. 이때 기존 skills 흐름과 연결한다.

```text
/wayfinder 지도
  -> /to-spec
  -> /to-tickets
  -> 티켓별 구현
  -> code review
```

`/to-spec`은 지도에 축적된 결정을 하나의 구현 명세로 압축하고, `/to-tickets`는 이를 실제 구현 작업으로 나눈다. 여기서 두 종류의 티켓을 구분해야 한다.

- **의사결정 티켓(decision ticket)**: 무엇을 만들고 어떤 선택을 할지 알아내기 위한 Wayfinder 티켓
- **구현 티켓(implementation ticket)**: 이미 결정된 내용을 실제 코드나 결과물로 만드는 티켓

명세에는 원래의 의사결정 티켓 링크가 남는다. 명세는 회의와 조사 결과를 압축한 요약이므로, 에이전트가 모호한 부분을 만나면 연결된 티켓을 열어 대화와 근거가 담긴 **1차 출처(primary source)**를 확인할 수 있다.

### 명세는 영구 문서가 아니라 다중 세션의 목적지다
Matt는 이 접근을 명세 주도 개발(spec-driven development)과 동일하게 보지 않는다. Wayfinder에서 명세는 여러 구현 세션이 같은 목표로 향하게 하는 임시 목적지 문서다.

구현이 모두 코드에 반영되면 그는 명세 이슈를 닫고 거의 다시 참조하지 않는다. 명세를 계속 유지·수정하는 대신, 구현이 완료된 뒤에는 코드가 결과를 담는다. 핵심은 명세를 영구적인 진실의 원천으로 만드는 것이 아니라, 여러 세션에 걸친 작업의 도착점을 잃지 않는 것이다.

### 언제 Wayfinder를 사용해야 하는가
한 세션에서 충분히 계획하고 완료할 수 있고 목적지까지의 경로를 이미 안다면 Wayfinder는 과도한 절차다. 이때는 단일 세션에서 바로 계획하고 실행하는 것이 낫다.

Wayfinder는 다음 상황에 적합하다.

- 작업이 여러 에이전트 세션에 걸릴 만큼 크다.
- 원하는 결과는 대략 알지만 도달 경로는 모호하다.
- 조사, 프로토타입, 사람의 결정과 외부 작업이 서로 의존한다.
- 선행 결정에 따라 다음 작업의 종류나 범위가 달라진다.
- 세션이 바뀌어도 결정의 근거와 진행 상태를 보존해야 한다.

코딩에만 사용할 필요도 없다. Matt는 강좌 기획과 엔지니어링 작업 외에도 정원 사무실을 짓기 위한 현장 조사, 업체 탐색과 연락 같은 현실 프로젝트에 Wayfinder를 사용했다.

## 예시

### 모호한 기능을 구현 가능한 명세로 바꾸기
```text
목적지
└─ 명령 팔레트의 구현 가능한 명세

현재 전선
├─ [Research] 아이콘 이름의 출처 조사
├─ [Grilling] 컴포넌트 저장 스키마 결정
└─ [Prototype] 팔레트 정보 구조와 키보드 탐색 검증

아직 안개 속인 결정
├─ 검색 결과 표시 방식
├─ 다이어그램 간 복사 형식
└─ 선행 결정에 따라 달라지는 구현 범위
```

현재 전선의 티켓을 각각 독립된 세션에서 처리한다. 완료된 결정이 지도에 반영되면 차단됐던 티켓이 열리고, 모든 의사결정이 끝난 뒤 지도를 명세와 구현 티켓으로 변환한다.

### 계획 도구 선택 기준
| 상황 | 적합한 방식 |
| --- | --- |
| 경로가 분명하고 한 세션 안에 계획·완료할 수 있음 | 단일 에이전트 세션 |
| 사용자 인터뷰로 요구 사항을 조금 더 명확히 하면 됨 | `/grill-me` 또는 `/grill-with-docs` |
| 여러 세션이 필요하고 조사·결정·프로토타입의 의존 관계가 복잡함 | `/wayfinder` |

## 요약
- `/wayfinder`는 큰 프로젝트의 계획을 한 컨텍스트에 억지로 넣지 않고 여러 에이전트 세션에 걸쳐 조율한다.
- 목적지까지의 불확실성을 지도, 의사결정 티켓, 현재 전선과 전쟁의 안개로 표현한다.
- Research, Prototype, Grilling, Task 티켓을 독립된 세션에서 처리하고 결과와 근거를 이슈 트래커에 남긴다.
- 티켓의 차단 관계를 추적하므로 선행 결정이 끝날 때마다 새 전선이 열리고, 독립적인 티켓은 병렬로 진행할 수 있다.
- 완성된 지도는 `/to-spec`과 `/to-tickets`를 거쳐 구현 가능한 명세와 실제 구현 티켓으로 바뀐다.
- 연결된 의사결정 티켓은 요약 명세만으로 부족할 때 돌아갈 수 있는 1차 출처다.
- 프로토타입을 반복해 실제 결과를 보며 피드백하므로 많은 사전 계획이 폭포수 방식으로 굳어지는 것을 막는다.
- 한 세션에서 경로를 충분히 알 수 있는 작업에는 사용하지 않는다. Wayfinder는 여러 세션이 필요한 크고 모호한 프로젝트를 위한 도구다.
