# 금융 에이전트 개발의 병목 줄이기 - 작업 격리와 피드백 루프

## 개요

- **업로드일:** 2026-08-07
- **채널:** Tech Bridge
- **발표자·출처:** Auditoria AI 데이터 사이언티스트 발표
- **원본:** [YouTube](https://www.youtube.com/watch?v=J86SNqUsFBs)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 13:18, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 금융 업무용 에이전트를 개선하는 개발 과정에서 반복 수작업을 줄이고, 운영 오류를 개발 도구 개선의 입력으로 삼는다.

## 내용

### 1. 데모 이후에는 개발 과정이 병목이 된다 (0:12~3:02)

새 고객과 처음 보는 데이터가 들어오면 데모에서 드러나지 않은 운영 오류가 발생한다. 더 좋은 모델이나 하드웨어를 기다리는 것과 별개로, 오류를 조사하고 수정·검증·배포하는 속도를 개선해야 한다는 문제의식이다.

발표 중 생산성 배율은 제안의 목표와 기대 효과이며 모든 팀에서 검증된 성과로 받아들이지 않는다.

### 2. 네 가지 구성요소 (3:08~5:05)

- **하위 에이전트:** 독립적인 작업을 나누어 수행한다.
- **Git worktree:** 작업별 코드 변경을 격리해 같은 파일에서 서로 방해하는 일을 줄인다.
- **스킬과 연결 도구:** 조직의 작업 절차를 전달하고 로그·티켓·업무 시스템에 접근한다.
- **통합된 간결한 화면:** 여러 작업의 상태를 사람이 한곳에서 파악한다.

동시에 띄울 수 있는 작업 수는 환경과 작업 특성에 따라 달라진다. 강의의 특정 장비·작업 수는 구성 예시다.

### 3. 버그 수정의 전체 흐름을 대상으로 삼기 (5:20~7:50)

발표자는 QA 티켓 분석, 원인 조사, 로그·트레이스 수집, 격리된 작업 공간의 수정, 테스트, PR, 개발 환경과 스테이징 배포로 이어지는 과정을 설명한다.

코드 작성만 자동화해도 사람이 중간 단계마다 명령과 정보를 옮기면 병목이 남는다. 시작할 목표를 확인하고 결과를 검증하는 역할을 중심으로 사람의 참여를 재배치하자는 제안이다. 통합 화면에는 서비스 상태, 로그, 티켓, PR, 에이전트 세션을 모은다.

### 4. 금융 업무에서 남는 책임 (7:58~9:02)

금융 분야에서는 감사자와 통제 담당자가 검토하고 책임을 확인하는 과정이 중요하다고 설명한다. 운영 오류를 모델이나 클라우드 탓으로 돌리는 것만으로는 책임 문제가 해결되지 않는다.

이 부분은 발표자가 금융 소프트웨어 개발에서 강조한 운영 원칙이다. 특정 규정의 법적 충족 여부를 판정하는 안내는 아니다.

### 5. 수정 작업뿐 아니라 수정 절차도 개선하기 (9:06~10:36)

여러 티켓을 처리한 뒤 에이전트에게 그 과정에서 반복된 병목을 분석하게 한다. 수작업으로 남은 부분을 목록화하고 매일 조금씩 제거하면, 다음 오류를 처리하는 과정 자체가 개선된다.

여기서 자기 개선은 모델이 자동으로 모든 문제를 해결한다는 뜻보다 내부 개발 프레임워크와 업무 절차를 반복 개선하는 의미가 중심이다.

### 6. 목표, 반복 실행, 경험 축적 (10:45~13:18)

보고서와 원천 데이터가 다르다는 목표를 제시하고, 필요한 자료 수집과 수정을 반복하는 예를 든다. 여러 고객 세션에서 반복되는 문제를 모아 이후 개선에 사용할 자료로 정리하는 작업도 소개한다.

마지막 메시지는 사람을 없애는 것이 아니라 제한된 주의를 반복 조작보다 검증에 쓰자는 것이다. 자율 실행의 범위와 결과를 사람이 확인할 수 있어야 한다.

## 예시

강의의 보고서 데이터 불일치 사례를 개발 과정으로 정리하면 다음과 같다.

1. 티켓에서 원천 데이터와 보고서의 차이를 확인한다.
2. 관련 로그와 실행 추적을 모아 원인을 조사한다.
3. 격리된 작업 공간에서 문제를 재현하고 수정한다.
4. 테스트와 검토를 거쳐 검증 환경에서 결과를 확인한다.
5. 처리 과정에서 반복된 수작업을 다음 자동화 개선 대상으로 남긴다.

이 예시는 금융 판단을 자동화하는 방법이 아니라 금융 소프트웨어의 결함을 처리하는 개발 흐름이다.

## 요약

- 데모 이후의 운영 오류에는 조사부터 검증까지 이어지는 개발 속도가 중요하다.
- 작업 격리, 조직 스킬, 시스템 연결, 통합 화면으로 반복 조작을 줄인다.
- 운영 오류와 개발 기록을 다음 개선의 입력으로 삼는다.
- 사람은 책임 있는 검증을 담당하고 중간 단계의 불필요한 전달 작업을 줄인다.
