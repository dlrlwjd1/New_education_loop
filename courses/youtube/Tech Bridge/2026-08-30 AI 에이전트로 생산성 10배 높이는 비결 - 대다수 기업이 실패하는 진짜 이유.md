- 핵심 메시지: 조직의 병목은 코드 작성량이 아니라 소통, 승인, 아이디어, 비전, 취향이다. 에이전트의 큰 생산성 향상을 얻으려면 문제를 아는 사람이 에이전트와 직접 작업하고, 필요한 기능만 갖춘 작은 소프트웨어를 스스로 만들어야 한다.

## 내용

### 대규모 조직의 병목은 구현이 아니다
DHH는 여러 사람이 함께 일하는 순간 구현보다 인간의 대역폭과 의사소통이 병목이 된다고 말한다. 제품 관리자, 디자이너, 여러 관리 계층이 모두 방향 결정과 승인에 참여하면 코드를 빨리 쓰는 능력만으로 전체 전달 속도를 높일 수 없다.

에이전트로 10배, 100배, 드물게는 그 이상의 생산성 향상을 체감하려면 작업자가 에이전트와 직접 상호작용해야 한다는 것이 그의 경험이다. 사람을 한 단계 더 거쳐 요구를 전달하고 여러 승인 계층을 통과하면 에이전트가 줄인 구현 시간은 전체 과정의 작은 부분에 불과해진다.

### 코드 생산량은 좋은 제품을 보장하지 않는다
많은 조직은 구현 역량이 아니라 다음 요소가 부족하다.

- 무엇을 개선해야 하는지 아는 아이디어
- 제품이 향할 방향을 정하는 비전
- 좋은 결과와 나쁜 결과를 구분하는 취향(taste)

수만 명의 개발자를 가진 기업이 항상 뛰어난 소프트웨어를 만든 것은 아니다. 에이전트가 나쁜 아이디어를 더 빨리 구현하게 해도 좋은 제품이 되지 않는다. 생성 속도를 높이기 전에 만들 가치가 있는 문제를 고르는 능력이 필요하다.

또한 강력한 코딩 에이전트가 널리 쓰인 기간은 아직 짧다. 몇 달 안에 모든 기존 소프트웨어가 다시 만들어지지 않았다는 이유로 변화를 과소평가해서는 안 된다고 DHH는 지적한다.

### 기존 기업은 혁신가의 딜레마에 놓인다
대기업의 조직 구조, 관리 계층, 절차는 이전 시대의 높은 구현 비용을 전제로 최적화되어 있다. 이미 성공한 조직은 이런 구조를 빠르게 바꾸기 어렵다. DHH는 이를 혁신가의 딜레마(innovator's dilemma)로 설명한다.

반대로 새 회사, 오픈소스 프로젝트, 개인 개발자는 기존 절차와 호환성 부담이 적다. 문제를 잘 아는 개발자에게 에이전트를 주고 직접 만들게 하면 새로운 방식에 맞춘 제품을 처음부터 설계할 수 있다.

### 40년 만에 다시 열린 컴퓨팅 플랫폼
Linux는 서버와 각종 장치에서 성공했지만 데스크톱에서는 Windows와 macOS의 앱 생태계 때문에 대중화되지 못했다. 영상 편집이나 디자인처럼 필요한 전문 앱이 특정 운영체제에만 있으면 사용자는 플랫폼을 떠나기 어렵다.

코딩 에이전트는 이 진입 장벽을 낮춘다. 기존 대형 앱의 모든 기능을 복제할 필요 없이, 개인이 실제로 사용하는 일부 기능만 구현할 수 있기 때문이다.

```text
기존 전제: 모두가 서로 다른 5%를 쓰므로 거대한 앱 전체가 필요하다.
새 가능성: 각자가 필요한 5%를 자신에게 맞게 만든다.
```

모바일 이후 안경, 이어피스 등 새로운 폼팩터도 등장하면서 오랫동안 고정돼 있던 컴퓨팅 플랫폼 경쟁이 다시 열릴 수 있다는 전망이다.

### 에이전트가 개인을 다언어 개발자로 만든다
DHH는 원래 Ruby를 중심으로 일했고 Bash를 조금 쓰는 정도였지만, 최근에는 에이전트를 이용해 C++와 Qt로 실제 애플리케이션을 만들었다고 말한다.

그는 macOS의 iA Writer를 좋아했지만 Linux에서 사용할 수 없어 Typora를 쓰고 있었다. Typora의 많은 기능 중 자신에게 필요한 것은 일부뿐이었다. 에이전트에게 C++와 Qt로 단순한 Markdown 작성 앱을 만들게 했고 약 20분 만에 첫 버전을 얻었다. 이틀간 다듬은 뒤 기존 앱을 떠나 자신이 만든 Omarchy Write를 일상적으로 사용하게 됐다.

중요한 점은 에이전트가 모든 사용자의 요구를 만족시키는 거대 제품을 한 번에 만든 것이 아니라, 사용자가 문제와 필요한 기능을 정확히 알고 있었고 자신의 5%에 집중했다는 것이다.

### 생산성 향상의 조건

| 조건 | 이유 |
| --- | --- |
| 에이전트와 직접 작업 | 요구 전달과 피드백의 대역폭을 유지한다. |
| 문제를 직접 경험 | 필요한 기능과 불필요한 기능을 구분할 수 있다. |
| 제품 취향과 비전 | 빠르게 생성된 여러 결과 중 좋은 방향을 고른다. |
| 좁은 범위 | 기존 대형 제품 전체가 아니라 핵심 5%를 완성한다. |
| 즉시 사용과 반복 | 실제 작업에서 문제를 발견하고 짧은 루프로 수정한다. |

## 예시

### 개인 맞춤형 도구 만들기

```text
1. 매일 쓰는 앱에서 반복적으로 불편한 점을 기록한다.
2. 전체 기능이 아니라 자신이 쓰는 핵심 5%를 정의한다.
3. 문제를 아는 본인이 에이전트와 직접 첫 버전을 만든다.
4. 곧바로 실제 업무에 사용한다.
5. 불편이 생길 때마다 짧게 수정한다.
6. 기존 앱을 대체할 만큼 안정되면 사용 범위를 넓힌다.
```

### 조직에서 점검할 질문

```text
1. 현재 리드 타임 중 실제 구현이 차지하는 비율은 얼마인가?
2. 요구를 아는 사람이 에이전트와 직접 대화하는가?
3. 승인 계층 때문에 에이전트의 속도가 상쇄되고 있지는 않은가?
4. 아이디어와 제품 판단이 구현 역량보다 부족하지 않은가?
5. 거대 기존 제품을 복제하려 하지 않고 핵심 사용 사례로 좁혔는가?
```

## 요약
- AI가 구현을 빠르게 해도 다계층 조직의 소통과 승인 비용이 그대로라면 전체 생산성은 크게 오르지 않는다.
- 큰 생산성 향상은 문제를 아는 사람이 중간 전달자 없이 에이전트와 직접 작업할 때 나타난다.
- 좋은 제품의 병목은 코드 양보다 아이디어, 비전, 취향이며 AI는 나쁜 아이디어도 빠르게 구현한다.
- 기존 성공 방식에 맞춘 대기업은 구조를 바꾸기 어려워 혁신가의 딜레마에 놓일 수 있다.
- 에이전트는 대형 앱의 모든 기능이 아니라 개인에게 필요한 5%를 새로 만드는 전략을 현실적으로 만든다.
- DHH의 Omarchy Write 사례는 좁은 요구, 직접 사용, 빠른 반복이 개인 맞춤형 소프트웨어로 이어지는 방식을 보여준다.
