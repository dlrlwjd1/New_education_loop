# 코딩 에이전트의 메모리 점검 - 코드, 검증, 명시적 맥락

- **업로드일:** 2026-08-27
- **채널:** Tech Bridge
- **발표자·출처:** Theo / Pi 개발자 대화 인용 및 T3 Code 사례
- **원본:** [YouTube](https://www.youtube.com/watch?v=EAVtSxbzmuM)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 38:02, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 자동 메모리를 쌓기보다 현재 코드와 결정적인 검증을 기반으로 하고 프로젝트의 의도를 명시적으로 공유하자는 주장이다.

## 내용

### 별도 기억이 만드는 동기화 문제 (00:00~06:22)

Theo는 Mario와 Armin의 대화를 인용하며 코드가 변할 때 별도 메모리와 오래된 계획 문서는 쉽게 뒤처진다고 지적한다. 코드 검색 도구와 간결한 안내만으로 필요한 맥락을 찾을 수 있는 상황에서 추가 시스템의 효과는 평가해야 한다는 입장이다. 복잡한 검색 시스템이 언제나 불필요하다는 보편적 검증 결과가 아니라 발표자의 강한 견해다.

### 대화 기억과 코드 지식은 다르다 (06:22~11:55)

일반 대화에서는 과거의 여러 주제를 연결하는 기억이 유용할 수 있다고 인정한다. 반면 코드의 관계는 직접 추적할 수 있다. 인용된 Slack 봇은 대화 전체를 JSONL로 보관하고 jq로 검색한다. Sentry 예시는 필요한 결과 몇 개만 맥락에 넣고 나머지는 파일에 남기는 도구 설계를 보여 준다.

### 자신의 메모리를 감사한 결과 (11:55~20:38)

T3 Code의 여러 저장소 복제본을 조사하자 이미 지침에 있는 중복 규칙, 출시가 끝난 기능 설계, 해결된 일시적 문제, 과거 벤치마크 설정 등이 기억에 남아 있었다. 발표자가 조회한 355개 세션 중 메모리 파일을 연 세션은 19개, 작성·수정한 세션은 80개였다. 이 수치는 개인 환경의 조사 결과이며 전체 제품의 사용률은 아니다. 그는 기존 기억을 보관한 뒤 정리하고 자동 메모리를 끄기로 한다.

### 실수를 줄이는 우선순위 (20:38~30:44)

첫째, 아키텍처와 데이터 구조로 오류 종류 자체를 없앤다. 둘째, 린트·테스트·CI로 잡는다. 셋째, 그 방법으로 해결하기 어려운 절차는 스킬·규칙으로 설명한다. 필요한 경우 사람이 검토한다.

T3 Code의 데이터 전송량 최적화가 되돌아가는 문제에는 실제 스레드를 이용한 CI 검사를 추가했다. 최적화 후 측정값보다 약 30% 높은 한계를 두어 회귀가 발생하면 실패하도록 했다. 공통 TypeScript 데이터 계층이 여러 UI의 불일치를 줄이는 사례와, SwiftUI 전환 시 그 보호가 약해지는 상충 관계도 설명한다.

### AGENTS.md에 무엇을 담는가 (30:44~38:02)

실수 금지 목록만 늘리기보다 제품이 무엇이며 어떤 방향을 지향하는지 설명한다. T3 Code에서는 개방성, 성능, 원격 사용, 여러 화면의 일관성, 공통 용어, 개발 서버와 검증 방법을 적는다. 코드만 읽어서는 알기 어려운 가치와 운영 맥락을 공유해 에이전트가 같은 방향으로 판단하도록 만드는 것이 목표다.
