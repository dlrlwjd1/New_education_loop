## 내용

### 코딩 보조의 네 단계와 프론티어 개발
Clare Liguori는 AI 코딩 보조의 발전을 네 단계로 나눈다.

1. 다음 줄이나 함수를 제안하는 인라인 코드 완성(inline code completion)
2. 코드에 관해 질문하는 채팅(chat)
3. 높은 수준의 요구를 주고 빠르게 구현하는 바이브 코딩(vibe coding)
4. 에이전트가 장시간 자율적으로 일하도록 개발 방식 자체를 바꾸는 프론티어 개발(frontier development)

발표자 개인은 앞선 단계에서 체감한 생산성 향상이 약 10~20%였다고 말한다. 반면 Amazon의 여러 사내 파일럿에서는 생산성이 중앙값 4.5배, 일부 사례에서는 10배 이상 향상됐다. 발표자는 프론티어 개발자를 다음 세 가지 행동으로 정의한다.

| 행동 | 의미 |
| --- | --- |
| 핸즈오프 코딩(hands-off coding) | 산출 코드 중 개발자가 직접 쓰는 비율은 약 1~2%이고 나머지는 에이전트가 작성한다. |
| 낮은 상호작용 빈도 | 에이전트가 사람의 개입 없이 최대 몇 시간씩 실행되게 한다. |
| 유휴 시간 최소화 | 여러 에이전트를 병렬로 돌려 백로그 작업을 동시에 처리한다. |

핵심은 사람이 에이전트의 모든 코드 생성 과정에 계속 붙어 있는 것이 아니라, 에이전트가 스스로 진행하고 검증할 환경을 만드는 데 있다.

### 초기 성공 사례와 그 한계

#### Bedrock Mantle 팀
Amazon Bedrock의 새 추론 데이터 플레인(inference data plane)은 원래 **30명이 18개월** 동안 만들 것으로 추정된 대형 프로젝트였다. 팀은 Kiro를 활용해 **6명이 76일** 만에 구축했고, 커밋 수를 기준으로 약 20배에 이르는 향상을 관찰했다.

그러나 이 팀에는 회사 내 최상위 엔지니어와 저명 엔지니어(distinguished engineer) 두 명이 포함돼 있었다. 분산 시스템과 LLM 아키텍처 전문가들이었기 때문에, 일반 팀에서도 같은 결과가 재현되는지는 알 수 없었다.

#### Prime Video의 10일 스프린트
Prime Video 조직은 엔지니어 6명을 모아 Kiro를 집중적으로 사용하는 10일 실험을 했다. 그 기간의 진척을 바탕으로 프로젝트 예상 기간을 **90주에서 24주**로 줄였다.

이 사례에도 특별한 조건이 있었다.

- 당직(on-call)이 없었다.
- 회의와 방해 요소가 거의 없었다.
- 시니어 엔지니어가 앞선 3주 동안 작고 범위가 명확한 작업과 상세 요구사항을 준비했다.

따라서 성공 가능성을 다시 보여준 실험이지만, 일상적인 팀 환경을 그대로 재현한 것은 아니었다.

### 50개 일반 팀에서 확인한 진짜 차이
Amazon Stores 조직은 신규 프로젝트가 아니라 기존 시스템과 코드베이스를 다루는 **일반적인 50개 팀**을 거의 1년간 관찰했다. 경력 초기·중간·시니어 개발자가 고르게 포함된 팀들이었다.

이 파일럿은 커밋 수 대신 변경 사항이 실제 고객에게 전달되는 속도인 **프로덕션 배포 속도(deployment velocity to production)**를 생산성 지표로 사용했다.

- 절반의 팀은 생산성 향상이 3배 미만이었다.
- 더 높은 성과를 보인 팀들의 중앙값은 4.5배였고, 일부는 10배를 넘었다.
- 팀의 90%가 Kiro를 비롯한 비슷한 내부 도구를 사용했다.

차이는 도구가 아니었다. 고성과 팀은 업무 방식을 의도적으로 바꿨지만, 다른 팀은 기존 방식 위에 AI 도구만 얹었다. 인터뷰를 통해 이런 차이를 만드는 다섯 가지 반복 습관이 도출됐다.

### 습관 1 — 에이전트 컨텍스트에 투자한다
사람의 머릿속에 있던 지식을 에이전트가 읽을 수 있는 형태로 기록해야 한다. 기존에는 이런 지식이 Slack 대화, 온보딩 멘토링, 코드 리뷰, 스탠드업, 스프린트 계획을 통해 사람 사이에서 전달됐다.

에이전트가 실수하거나 팀의 기대와 다르게 행동할 때마다 다음을 묻는 습관이 필요하다.

> 이 에이전트가 필요로 했지만 스킬 파일이나 스티어링 파일에 없었던 정보는 무엇인가?

다만 컨텍스트를 계속 추가하기만 해서는 안 된다. 모델이 발전하면 예전 모델의 특이한 행동을 막기 위해 쓴 `하지 말 것` 규칙이 더는 필요하지 않을 수 있다. 오래된 규칙은 컨텍스트만 부풀리므로, 현재 모델에도 필요한지 정기적으로 확인해 가지치기한다.

### 습관 2 — 더 빨라지기 위해 먼저 속도를 늦춘다
인터뷰한 거의 모든 팀에서 새 방식을 도입한 초기에는 생산성이 오히려 하락했다. 기존 코드베이스, 특히 브라운필드(brownfield) 시스템을 에이전트가 잘 다루게 하려면 먼저 실제 엔지니어링 작업이 필요하기 때문이다.

팀들이 수행한 선행 투자는 다음과 같다.

- 에이전트 컨텍스트 구축
- 실패 원인을 모델이 이해할 수 있도록 기존 도구의 오류 메시지 개선
- 필요한 작업을 수행하게 해 주는 새 도구와 MCP 서버 제작
- 에이전트가 탐색하기 쉬운 형태로 코드베이스 재구성
- 피드백이 더 명확한 언어나 도구 도입

일부 팀은 Python·JavaScript 같은 동적 타입 언어에서 TypeScript로 옮겼고, Amazon 내부에서는 명확한 컴파일러 오류를 제공하는 Rust도 인기를 얻었다. 반드시 언어를 바꿔야 한다는 뜻은 아니며, **에이전트가 빠르고 명확한 피드백을 받을 환경에 투자한 사례**다.

### 습관 3 — 에이전트를 돌보지 말고 먹이를 준다
바이브 코딩처럼 하루 종일 에이전트와 문답을 주고받으면 사람이 계속 루프 안에 남는다. 30초~1분마다 결과를 기다리고 검토해야 하므로 다른 일을 할 수 없고, 여러 에이전트를 병렬로 운영하기도 어렵다.

프론티어 개발에서는 에이전트에 다음 두 가지를 함께 준다.

1. 무엇을 해야 하는가
2. 결과가 올바른지 스스로 검증하는 방법

에이전트는 코드가 실행·컴파일되고 테스트를 통과하며 충분한 커버리지를 갖출 때까지 스스로 수정한다. 품질 기준을 만족한 뒤에만 사람에게 돌아오게 한다. 반복되는 지침은 스티어링 파일에 넣어 매번 프롬프트로 다시 설명하지 않는다.

### 습관 4 — 의도를 명시적으로 문서화한다
모호하고 복잡한 기능을 높은 수준의 한두 문장으로 지시하면 에이전트가 많은 코드를 만든 뒤에야 요구사항이나 기술 설계가 잘못됐음을 발견하기 쉽다. 이 상태에서 여러 파일에 퍼진 코드 변경을 대화로 고치는 것은 비효율적이다.

Amazon에서는 명세 주도 개발(spec-driven development)을 활용해 먼저 요구사항과 기술 설계를 문서로 만든다. 문서 초안은 모델이 작성할 수 있지만, 중요한 점은 **코드를 생성하기 전에 문서를 놓고 의도를 빠르게 합의하는 것**이다. 코드보다 문서 하나를 대상으로 대화하는 편이 수정 범위가 분명하다.

### 습관 5 — 테스트를 왼쪽으로 이동한다
에이전트가 몇 시간씩 자율적으로 일하려면 실수를 즉시 발견하고 스스로 고칠 수 있는 빠른 피드백 루프가 필요하다. 팀들은 다음과 같은 결정론적 검증 수단을 추가했다.

- 린터(linter)
- 단위 테스트(unit test)
- 통합 테스트(integration test)
- 성능 테스트(performance test)
- 보안 테스트(security test)

특히 라이브 클라우드 서비스까지 연결하는 느린 종단 간 테스트 대신, **로컬에서 실행되고 결정론적인 응답을 반환하는 목 서비스(mock service)**를 구축했다. 모든 검증을 노트북에서 빠르게 수행할 수 있으면 에이전트가 같은 시간에 더 많은 수정-검증 루프를 돌 수 있다.

발표자는 이것들이 원래부터 필요했던 좋은 엔지니어링 위생이지만, 에이전트가 반복 실행의 수혜자가 되면서 투자 수익률(ROI)이 훨씬 커졌다고 본다.

### 프론티어 개발의 복병
다섯 습관을 적용한다고 곧바로 이상적인 개발 조직이 되는 것은 아니다. 아직 초기 도입 단계이며 새로운 문제가 나타난다.

#### 번아웃과 인지 부하

- 밤새 실행될 완벽한 프롬프트를 만들려고 늦게까지 일하는 엔지니어가 생긴다.
- 여러 에이전트를 병렬로 돌리면 터미널과 작업 맥락을 계속 전환해야 한다.
- AI가 작성한 코드를 검토하는 일이 직접 작성하는 것보다 어려울 수 있다.
- 코드 리뷰 경험이 적은 초기 경력 엔지니어에게 특히 높은 인지 부하가 걸린다.

#### 조직도 함께 바뀌어야 한다
리더가 AI 도구를 지급한 직후부터 더 빠른 기능 출시를 요구하면, 팀은 코드베이스와 업무 습관을 정비할 시간을 확보하지 못한다. 발표자는 실제로 팀에 **약 두 달의 선행 투자 기간**이 필요할 수 있다고 설명한다.

또한 전 조직에 한 번에 확산하면 각 팀이 모범 사례와 필요한 조직 컨텍스트를 찾지 못한 채 시행착오를 겪는다. Amazon도 선도 팀, 집중 스프린트, 50개 파일럿 순으로 학습했고, 2026년의 과제로 이를 다음 약 2,000개 팀에 확장하는 방법을 탐색하고 있다.

### 코딩이 빨라지면 의사결정이 새 병목이 된다
수동 코딩 시간이 크게 줄어들자 제품 개발 여부를 결정하고 출시를 승인하는 조직 절차가 새로운 병목이 됐다.

과거에는 제품 구현에 9~12개월이 걸렸기 때문에, 개발 결정에 2개월과 출시 승인에 2개월이 걸려도 전체 일정에서 상대적으로 덜 두드러졌다. 이제 코드를 1~2개월 만에 작성할 수 있다면 그 네 달이 가장 긴 구간이 된다.

프론티어 팀은 코드 작성보다 의사결정에 더 많은 시간을 쓸 수 있다. 따라서 특히 되돌리기 쉬운 결정은 더 빠르게 내려야 한다. 에이전트 도입은 개발팀만의 도구 변경이 아니라, 의사결정과 승인 흐름을 포함한 조직 운영의 재설계를 요구한다.

## 예시

### 에이전트를 돌보는 요청과 먹이를 주는 요청

```text
# 돌보기(babysitting)
이 기능을 구현해 줘.
→ 생성 결과를 기다린다.
→ 사람이 오류를 찾아 다시 지시한다.
→ 수정 결과를 기다리고 또 검토한다.

# 먹이 주기(feeding)
이 명세와 기술 설계를 따라 기능을 구현해 줘.
완료 조건은 컴파일 성공, 린트 통과, 단위·통합 테스트 통과,
목 서비스 기반 시나리오 통과다.
실패하면 오류를 분석해 스스로 수정하고, 모든 조건을 만족한 뒤 보고해 줘.
```

### 팀에 적용할 때의 점검 질문

```text
1. 에이전트가 반복한 실수 중 어떤 팀 지식이 문서에 빠져 있었는가?
2. 현재 스티어링 규칙 중 최신 모델에는 불필요한 것은 무엇인가?
3. 오류 메시지와 테스트 결과만 보고도 에이전트가 실패 원인을 알 수 있는가?
4. 요구사항과 기술 설계를 코드 생성 전에 문서로 합의했는가?
5. 에이전트가 사람 없이 로컬에서 실행할 수 있는 검증 루프가 있는가?
6. 초기 생산성 하락을 감수할 선행 투자 시간과 조직적 지원이 있는가?
7. 코딩 이후 의사결정·승인 과정이 새 병목이 되고 있지는 않은가?
```

## 요약
- Amazon 내부 사례에서 큰 성과를 낸 팀은 AI 도구를 추가하는 데 그치지 않고, 에이전트가 장시간 자율 실행할 수 있도록 개발 방식을 바꿨다.
- 프론티어 개발자는 직접 쓰는 코드를 약 1~2%로 줄이고, 여러 에이전트를 병렬 실행하며, 사람의 개입 빈도를 낮춘다.
- 핵심 다섯 습관은 **컨텍스트 투자, 선행 정비, 자가 검증이 가능한 작업 위임, 의도의 문서화, 테스트의 좌측 이동**이다.
- 에이전트 친화적인 코드베이스와 결정론적인 로컬 테스트는 단순한 품질 활동을 넘어 에이전트 생산성을 높이는 기반이다.
- 발표에 제시된 수치는 서로 다른 사례와 지표(커밋 수, 추정 일정, 프로덕션 배포 속도)에서 나온 관찰값이므로 단순 비교나 일반화에는 주의해야 한다.
- AI가 코딩 병목을 줄이면 번아웃, 병렬 작업의 인지 부하, 의사결정과 출시 승인 같은 새로운 병목이 나타난다.
- 최종 메시지는 특정 도구의 도입이 아니라, 개발팀과 조직이 **사람이 계속 루프 안에 있지 않아도 되는 업무 방식**을 의도적으로 만들라는 것이다.
