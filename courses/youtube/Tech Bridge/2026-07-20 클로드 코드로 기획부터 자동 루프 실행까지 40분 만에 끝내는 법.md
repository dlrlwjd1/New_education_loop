# [한영자막] 클로드 코드로 기획부터 자동 루프 실행까지, 40분 만에 끝내는 법 | Thariq Shihipar

## 개요
- 업로드일: 2026-07-20
- 원본: https://www.youtube.com/watch?v=iDLi-WhtLGQ
- 채널: Tech Bridge (해외 기술 강연에 한영자막을 붙여 소개하는 채널)
- 발표자: Thariq Shihipar (Anthropic 클로드 코드 팀) — 진행자 Peter Yang과의 대담(인터뷰) 형식
- 핵심 주제: 에이전트가 "오래, 스스로" 일하게 만드는 세 가지 장치(`/loop`, `/goal`, 워크플로우)와 실전 데모(원샷 프롬프트로 영상 제작), 기획 단계에서 HTML 아티팩트 활용법, 슬랙(Claude Tag)으로 여러 작업 동시 실행, 작업자/검증자 서브에이전트 분리, 시스템 프롬프트 80% 감축 배경, AI 시대에 기술적으로 성장하는 법을 다룬다.

## 내용

### /loop, /goal, 워크플로우 — 클로드를 오래 일하게 만드는 세 가지 장치
- 모델이 똑똑해질수록 필요한 지시, 제약, 예시가 줄어든다는 전제에서 출발한다.
- 세 가지 장치:
  - `/loop`: 에이전트가 피드백을 받으며 오랫동안 조율된 방식으로 일하게 하는 일반적인 개념.
  - `/goal`: 에이전트가 스스로 "종료 조건(exit condition)"을 계속 상기하게 하고, 그 조건이 충족되기 전에는 멈추지 못하게 한다. 복잡한 작업 중간에 스펙과 안 맞는 부분을 만나도 사용자에게 되묻지 않고 알아서 채워 넣으며 계속 밀고 나가게(power through) 만드는 데 유용하다. 사용자가 "탐색은 충분히 했으니 이제 실행만 하라"고 알려주는 신호다.
  - 워크플로우(workflow): 여러 서브에이전트(subagent)를 동시에 띄워 작업을 병렬화하고, 그 결과를 검증까지 하게 만드는 가장 강력한 형태. 비기술적 작업(non-technical work)에서 특히 유용하다 — 비결정적(non-deterministic) 작업을 대략적으로 결정적(deterministic) 작업으로 쪼개는 방법이다.
- 언제 무엇을 쓰는가:
  - 레이턴시처럼 결정적 신호(deterministic signal)가 있으면 `/goal`로 자율 탐색을 시킨다.
  - 디자인 작업처럼 검증 스펙이 명확하면(Figma 파일이 있으면 Figma MCP로 렌더링 결과를 비교) `/goal`이 스크린샷 비교보다 쉽다.
  - 스크린샷처럼 기준이 "말랑말랑(squishy)"하면 루브릭(rubric)과 검증 에이전트를 둔 워크플로우가 적합하다.
- 기획(planning)이 결과 품질을 크게 좌우한다 — "게임 하나 멋지게 만들어줘" 같은 한 줄짜리 지시는 삼천포로 빠지기 쉽다는 점을 진행자가 자신의 경험으로 짚었다.

### 라이브 데모 — 프롬프트 한 번으로 완성된 영상 만들기
- 발표자는 통화 10분 전 스스로 촬영한 짧은 영상을 준비했다 — 자신을 소개하고 손으로 오버레이가 나올 위치를 가리킨 뒤 "fade to black"이라고 말하는 영상.
- 실제 사용한 프롬프트(요지): 이 저장소는 Peter Yang 팟캐스트용이고, "Peter Yang recording"이라는 샘플 영상이 있으니 Whisper로 트랜스크립션한 뒤, Remotion으로 각 단어가 하이라이트되는 자막과 여러 오버레이를 보여주는 UI를 만들라는 것. 그리고 영상이 완전히 렌더링될 때까지 멈추지 말라는 목표(`/goal`)를 덧붙였다.
- 결과: 원샷(one-shot) 실행만으로 Whisper 트랜스크립션 → Remotion 자막/오버레이 생성 → fade to black까지 자동 완료됐다. (이름은 잘못 인식했지만) 캡션과 오버레이가 만들어지는 과정을 실시간으로 확인했다.
- 발표자는 아직 스킬(skill)로 만들지 않았다고 밝혔다 — 스킬화 이전에 먼저 "내가 정말 원하는 게 뭔지", "엣지 케이스가 뭔지"를 충분히 파악하는 게 우선이라는 원칙이다. 예를 들어 손이 가리키는 위치를 잘못 인식하는 문제를 발견했고, 손가락/얼굴 트래킹으로 더 나은 메타데이터를 주는 방향으로 개선할 수 있다고 설명했다.

### 기획(planning)에 HTML 아티팩트를 쓰는 방법
- 기획은 "한 번 계획하고 그대로 실행"하는 원샷이 아니라, 탐색(exploring)·조사(investigating)·모르는 것을 알아가는(finding out what you don't know) 반복적(iterative) 과정으로 봐야 한다는 것이 핵심 주장이다.
- 실제 데모 프롬프트(요지): 오버레이 UI 디자인을 업데이트하고 싶은데 Peter Yang의 블로그 스타일을 참고해서, 오버레이와 캡션의 여러 디자인 변형(design variation)을 탐색할 수 있는 HTML 아티팩트를 만들라는 것.
  - 참조 자료(블로그 URL)를 줌으로써 에이전트가 HTML을 가져와(fetch) 실제 스타일을 반영한 시안을 여러 개 만들게 했다 — 이것도 일종의 기획(탐색)이라는 설명이다.
- 동시에 다른 창에서는 "Whisper가 어떻게 동작하는지", "무엇이 잘못될 수 있는지" 설명을 요청했다. 클로드 코드가 만들어준 설명 문서에는 침묵 구간이 "시청해주셔서 감사합니다"로 오인식되는 문제, 한 단어가 두 조각으로 쪼개지는 문제, 화자 인식(speaker recognition) 기능이 없다는 점 등 Whisper의 엣지 케이스가 정리되어 있었다. 이런 엣지 케이스를 미리 알면 복잡한 워크플로우를 다 만든 뒤에야 문제를 발견하는 상황을 피할 수 있다.
- HTML 아티팩트 생성에는 "프론트엔드 디자인 플러그인(front-end design plugin)"을 사용했다고 언급했다 — 이미지가 포함된 보기 좋은 플랜이 나온 이유다. 다만 발표자는 "플랜의 디자인 자체보다 실제로 읽히는 것이 더 중요하다"고 강조했다 — 사람들이 AI가 만든 장문의 마크다운 플랜/설명 문서를 대충 훑고 넘어가는(glaze over) 실패 패턴을 지적했다.
- 스펙(spec)과 구현(implementation)의 관계: 발표자는 스펙이 처음 한 번에 끝나는 핸드오프(hand-off)가 아니라, "사람의 요청 → 에이전트의 기술적 탐색 → 목업/설명 문서로 되돌아옴 → 다시 다듬음 → 다시 에이전트에게 전달 → 구현 시작"을 오가는 과정이라고 설명했다. 구현 중에도 "구현 노트(implementation notes)"를 남기게 해서 예상치 못했던 부분을 기록하고, 필요하면 다시 스펙을 고친다(respec).
- Anthropic 사내에서는 HTML 아티팩트를 플랜, PR 요약, 상태 보고서(status report), 인시던트 리포트(incident report) 등을 공유하는 표준 방식으로 쓴다고 언급했다. (현재는 Team/Enterprise 플랜 전용이며 Max/Pro로 확장 예정이라고 언급.)
- HTML로 만든 오버레이 디자인은 "프로토타입"이며, 마음에 들면 이후 더 비용이 큰 React 버전(영상 리렌더링, 코드 변경 포함)으로 옮긴다는 단계적 접근을 설명했다.

### 슬랙(Slack)으로 여러 클로드 작업 동시에 돌리기 — Claude Tag
- 발표자의 작업 비중: 병렬로 진행되는 여러 작업(멀티클로딩, multi-clauding)은 대부분 슬랙의 "Claude Tag" 기능으로 처리하고, 로컬에서 꼭 해야 할 이유가 있을 때만 로컬 클로드 코드를 쓴다. Anthropic은 원격(remote) 환경에서도 잘 동작하도록 많은 투자를 했다고 언급했다.
- "멀티클로딩(multi-clauding)"의 정의: 동시에 여러 작업을 돌리는 것. 예를 들어 PR을 머지하려 할 때, 클로드에게 "PR을 봐주면서(babysit) 테스트를 고치고 리뷰어를 태그해라"라고 시키면, 같은 슬랙 채널에 리뷰어가 태그되어 함께 대화할 수 있다.
- 패턴: 초기 탐색·PR·스펙 작성처럼 뭔가를 파악하는 작업은 Claude Tag(슬랙)에서, 정말 집중해서 주고받아야 하는 한 가지 작업은 로컬 클로드 코드 세션 하나로 진행한다. 예전에는 로컬에 클로드 코드 세션 5개를 띄웠다면 지금은 로컬은 활성 세션 1개 + 슬랙의 여러 Claude Tag 세션으로 바뀌었다고 한다.
- 슬랙 대화는 개인 DM(자신만의 "Thariq Claude" 슬랙 채널)과 팀 채널(피드백 채널, 프로젝트별 엔지니어링 채널 등) 양쪽에서 이루어진다.
- 스킬(skill) 사용법: 슬랙(Claude Tag)에서는 슬래시 커맨드 없이 그냥 "이 스킬을 써줘"라고 말로 지시하면 된다.
- 큰 그림 비유: 코딩 앱들은 지금은 "싱글플레이어" 경험(스레드로 에이전트와 1:1 대화)에 가깝다. 클로드 앱 UI도 슬랙처럼 여러 스레드/채널 구조를 닮아 있다. 발표자는 궁극적으로 클로드가 사람을 찾아오는 "능동적인(proactive) 에이전트"가 될 것으로 보고, 지금 Anthropic 사내에서는 슬랙이 그 실험의 장이라고 설명했다. 에이전트를 "정체성(identity)과 기억(memory)을 가진 동료"에 비유할 수도 있지만, 이는 도움이 되는 동시에 제한적인 은유일 수 있다고 조심스럽게 덧붙였다 — 슬랙의 Claude Tag는 채널마다 별도의 메모리를 가진다.

### 작업자(worker)와 검증자(verifier) 서브에이전트를 분리해서 쓰는 법
- 예시 상황: 팟캐스트 영상 클립에서 "5개(혹은 10개)의 쇼츠(shorts)를 만들어라" 같은 작업.
- 워크플로우 동작 방식: 메인 에이전트가 클립에서 어떤 5개 구간이 좋은지 고르고, 워크플로우가 구간마다 서브에이전트를 하나씩 띄워 작업하게 한다. 이때 "좋은 클립이란 무엇인가"에 대한 루브릭(rubric)을 함께 주고, 각 서브에이전트의 결과를 그 루브릭으로 검증한다.
- 워크플로우를 쓰는 두 가지 이유:
  1. 컨텍스트(context) — 서브에이전트를 각각 띄우면 메인 컨텍스트를 깨끗하게 유지할 수 있다.
  2. 게으름(laziness)과 검증 편향 방지 — 작업하는 클로드와 검증하는 클로드를 분리하지 않으면 "자기 참조 편향(self-referential bias)"이 생긴다. 모델이 자기 자신의 결과물을 더 관대하게(lenient) 평가하는 경향이 있다는 것이다. 별도의 검증 에이전트를 두면 이 편향을 줄일 수 있다.
- 구조: 메인(코디네이팅) 에이전트가 작업을 조율 → 각 서브에이전트가 실제 작업 수행 → (별도의) 에이전트가 검증. 서로 다른 컨텍스트를 쓰는 여러 클로드가 관여하면 편향이 줄어들 뿐 아니라, 조기 종료 없이 더 많은 연산(compute)을 투입하고 더 깊이 사고하게 된다.
- 워크플로우 생성 방법: "이러이러한 걸 워크플로우로 만들어줘"라고 말만 하면 된다. 워크플로우는 실제로 JS 파일 하나이며, 이를 스킬(skill) 안에 저장해두면 재사용 가능한 스킬이 된다(워크플로우를 스킬로 패키징).

### 클로드가 병렬로 일하는 동안 집중력을 유지하는 법
- 발표자 본인의 2026년 목표는 "더 생산적이면서도 덜 일하기(more productive but work less)".
- 핵심 습관: 정말로 집중해서 진행하는 프로젝트는 항상 하나만 둔다. 다른 부수적인 일(빌드/머지를 막고 있는 이슈 해결 등)은 병행하더라도, 가장 시간을 많이 잡아먹는 것은 "게으른 프롬프트(lazy prompt)"를 던지고 나중에 그 시간을 낭비했다고 깨닫는 순간이라고 밝혔다. 사람마다 최적의 멀티클로딩 양이 다르지만, 본인은 "제일 집중하는 작업 하나"를 두는 방식을 택했다 — 일종의 자기 자신에 대한 우선순위 지정(prioritization for yourself)이다.
- 레포가 "슬롭(slop)"으로 변해가는 것에 대한 우려에는, Boris가 공개한 `simplify`(레포를 단순화하는 도구)를 언급했다. 다만 용도에 따라 다르다 — 영상 같은 산출물(output) 자체가 목적이면 코드 품질은 덜 중요할 수 있고, 정리·조직화는 에이전트보다 오히려 "내가 이 작업 공간에 대해 기분 좋게 느끼기 위한" 목적이 크다고 설명했다.

### Anthropic이 클로드 코드 시스템 프롬프트를 80% 줄인 이유
- 모델이 똑똑해질수록 필요한 지시, 제약, 예시가 줄어든다는 원칙에 따라 클로드 코드의 시스템 프롬프트를 80% 줄였다고 밝혔다.
- 예전 시스템 프롬프트: "여기 배치 도구(batch tool)가 있다. 사용 예시 5개. 이런 경우엔 절대 하지 마라" 식으로 예시와 금지 규칙이 많았다.
- 이제는 모델이 충분히 정렬(align)되어 있어 예시가 오히려 제약이 된다 — 예시를 주면 "이 예시와 똑같이 해야 하는구나"라고 오히려 자유도를 제한받는다는 것이다. "절대 하지 마라(never)"도 마찬가지 — 실제로는 "대부분의 경우 하지 마라"는 뜻인데, 그 이유(reason)를 설명해주는 편이 단순 금지 규칙보다 더 효과적이다.
- 결론: CLAUDE.md, 스킬(skill), MCP 등 컨텍스트에 넣는 모든 지시문은 지금보다 더 짧게 다듬어야(trim) 한다. CLAUDE.md는 지금 대체로 너무 길고, 스킬도 대체로 너무 길다. MCP는 도구에 따라 다르지만 컨텍스트를 많이 잡아먹을 수 있어 MCP 팀이 도구 검색(tool search) 같은 기능으로 개선 중이라고 언급했다.
- 프롬프트 스타일 예시: 트윗 작성을 시킬 때 "280자 이하로 써라, 이건 하지 마라" 식 제약보다는, "나는 클로드 코드 팀에서 일하고 Anthropic 소속이다, 우리가 따르는 원칙은 이렇다" 같은 맥락(context)을 주는 편이 낫다. 280자 제한처럼 실제로 지켜야 하는 제약은 유지하되, "트윗 스레드가 더 나을 수도 있다"는 여지를 남겨두면 더 나은 결과를 자유롭게 찾을 수 있다.

### AI가 코드를 짜는 시대에 더 기술적으로 성장하는 법
- Boris(Anthropic)가 "코딩은 이제 풀린 문제(solved problem)"라고 말한 것에 대한 논의에서 이어진 질문이다.
- 첫걸음은 스스로 배우려는 동기부여(motivating yourself to learn)다 — 일을 끝내는 데 굳이 필요하지 않으면 배우지 않게 되는 게 인지상정이라고 인정했다.
- 기술적으로 성장하는 목적은 "자신이 모르는 것을 모르는 상태(unknown unknowns)를 아는 것"이다. 문법(syntax)을 아는 것 자체는 별로 도움이 안 되고, 예컨대 "여러 백엔드 서비스의 트레이드오프", "여러 비디오 인코딩 라이브러리의 차이", "로컬 vs 원격 비디오 트랜스크립션 라이브러리의 차이" 같은 시스템의 제약(constraints)을 배우는 것이 중요하다.
- 클로드는 "밀어붙이면(push)" 이런 것들을 브레인스토밍하고 가르쳐줄 수 있지만, 정말로 밀어붙여야만 한다.
- 교육에 대한 일반론: 뭔가를 배우려는 시도 자체는 기분 좋지만, 진짜 배우는 것은 더 많은 노력(work)이 필요하고 실제로 "일처럼 느껴져야" 한다(Karpathy가 자주 하는 말이라며 인용).
- 구체적 조언: 좋은 결과물(예: 좋은 쇼츠)에서 "최고의(highest production quality)" 결과물로 나아가려면, 결국 그 도메인의 기술(영상 제작·편집 등)과 기술적 개념을 더 배우고 스스로를 그 방향으로 밀어붙여야 한다. "더 빨라지는 것"뿐 아니라 "더 나아지는 것"도 함께 추구해야 한다.

## 예시

### 실제 사용된 원샷(one-shot) 영상 제작 프롬프트 (요지)
```
이건 Peter Yang 팟캐스트용 저장소다.
여기 "Peter Yang recording"이라는 샘플 영상이 있다.
Whisper로 트랜스크립션하라.
그다음 Remotion을 써서 각 단어가 하이라이트되는 자막과
여러 오버레이를 보여주는 UI를 만들어라.
(/goal) 영상이 완전히 렌더링될 때까지 멈추지 마라.
```

### 기획용 HTML 아티팩트 프롬프트 (요지)
```
오버레이 UI 디자인을 업데이트하고 싶다.
Peter Yang의 스타일을 쓰고 싶다 — 여기 그의 블로그다.
오버레이와 캡션의 여러 디자인 변형(variation)을 탐색할 수 있는
HTML 아티팩트를 만들어라.
```

### /goal vs 워크플로우 — 언제 무엇을 쓰는가
| 상황 | 적합한 장치 | 이유 |
| --- | --- | --- |
| 레이턴시처럼 결정적 신호가 있는 탐색 | `/goal` | 자율 탐색(autoresearch) 후 스스로 종료 조건 판단 |
| Figma 파일처럼 검증 스펙이 명확한 디자인 작업 | `/goal` + Figma MCP | 렌더링 결과를 스펙과 직접 비교 가능 |
| 스크린샷처럼 기준이 말랑말랑(squishy)한 작업 | 워크플로우(루브릭 + 검증 에이전트) | 비결정적 판단을 루브릭 기반으로 구조화 |
| "쇼츠 5~10개 만들기"처럼 병렬 산출물이 필요한 작업 | 워크플로우(작업자/검증자 서브에이전트 분리) | 컨텍스트 분리 + 자기 참조 편향 방지 |

## 요약
- `/loop`·`/goal`·워크플로우는 모두 "클로드가 오래, 스스로 일하게" 만드는 장치다. `/goal`은 종료 조건을 계속 상기시켜 조기 중단을 막고, 워크플로우는 서브에이전트로 작업을 병렬화·검증까지 하는 가장 강력한 형태다.
- 라이브 데모에서는 자신이 찍은 짧은 영상 하나와 프롬프트 한 번(원샷)만으로 Whisper 트랜스크립션 → Remotion 자막/오버레이 → 렌더링까지 자동 완료되는 과정을 보여줬다.
- 기획(planning)은 한 번에 끝나는 핸드오프가 아니라, 탐색·불확실성 해소를 반복하는 과정이다. HTML 아티팩트로 디자인 시안을 여러 개 뽑아보고, 참조 자료(블로그 등)를 줘서 실제 스타일을 반영하게 하는 것도 기획의 일종이다.
- Whisper 같은 시스템의 엣지 케이스(무음 오인식, 단어 분절, 화자 인식 부재 등)를 미리 파악해두면 나중에 워크플로우를 다 만든 뒤 문제를 발견하는 상황을 피할 수 있다.
- Anthropic 사내에서는 병렬 작업 대부분을 슬랙의 Claude Tag로 처리하고, 정말 집중할 작업 하나만 로컬 클로드 코드에서 진행한다. PR 리뷰어를 같은 슬랙 채널에 태그해 함께 대화하는 식으로 협업한다.
- 작업자와 검증자 서브에이전트를 분리하면 컨텍스트가 깨끗해질 뿐 아니라, 모델이 자기 결과물을 관대하게 평가하는 "자기 참조 편향(self-referential bias)"을 줄일 수 있다.
- 집중력 유지의 핵심은 "가장 집중하는 프로젝트 하나"를 정하는 것이며, 레포가 지저분해지는 것을 막기 위해 `simplify` 같은 도구로 주기적으로 정리한다.
- 모델이 똑똑해질수록 예시와 금지 규칙은 오히려 자유도를 제한하므로, Anthropic은 클로드 코드 시스템 프롬프트를 80% 줄였다 — 규칙 대신 이유(reason)와 맥락(context)을 주는 방향으로 프롬프트 전반(CLAUDE.md, 스킬, MCP)을 다듬어야 한다.
- 기술적으로 성장하려면 문법이 아니라 "시스템의 제약(트레이드오프, 라이브러리 차이 등)"을 배워야 하며, 클로드에게 밀어붙여 브레인스토밍을 시키되 배움 자체는 편함이 아니라 노력이 드는 일이어야 한다.
