## 개요

- **업로드일:** 2026-08-31
- **채널:** Tech Bridge
- **발표자·출처:** Lauren Tan · Roshan Sadhnani / MTS 대담
- **원본:** [YouTube](https://www.youtube.com/watch?v=cVFc9f6M0U0)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 26:37, 자동 자막 언어 `en`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 자체 컴퓨터를 가진 지속 실행 에이전트를 업무에 연결하되, 엔지니어가 코드 기반과 결과의 품질을 책임진다.

## 내용

### 내부 업무에서 출발한 지속 실행 봇 (00:00~06:00)

대담은 잠든 동안 버그를 고치는 내부 봇에서 시작해 운영·마케팅·개발 업무로 확장한 경험을 소개한다. 에이전트는 자체 컴퓨터와 브라우저를 사용하고 다른 에이전트와 협업한다. 여러 봇의 작업을 모아 보고하거나 발표 자료를 만드는 비서 역할도 예로 든다.

### 목표 중심 인터페이스 (06:00~11:42)

영상에서는 Grok 4.6의 성능과 비용을 논의하며, 사용자가 도구별 설정을 모두 조작하기보다 목표를 말하고 에이전트 화면을 확인하는 단순한 인터페이스를 지향한다. 메시지 앱과 비슷한 경험을 설명하지만 구체적인 연동 계획은 확정 기능과 구분해야 한다.

### 버그 보고에서 검토 가능한 PR까지 (11:45~15:10)

지속 실행 봇이 버그 보고를 받아 팀별 기능 에이전트와 클라우드 에이전트에 작업을 넘긴다. 결과에는 코드뿐 아니라 스크린샷과 영상 등 검토 근거가 포함된다. 사람이 변경을 판단할 수 있는 산출물로 연결하는 것이 중요하다.

### 엔지니어의 역할 변화 (15:35~23:16)

엔지니어는 여러 에이전트의 작업을 관리하고 코드 기반을 정돈하는 역할을 더 맡게 된다. PM이나 디자이너도 안전하게 기여할 수 있도록 구조를 개선하고 스타일·규칙을 린트와 CI의 강제 조건으로 옮긴다. 대규모 마이그레이션 역시 에이전트 팀을 활용할 수 있지만, 만들 수 있다는 이유만으로 모든 기능을 만드는 것은 바람직하지 않다.

발표자는 주방을 이끄는 셰프에 비유해 결과물의 품질에 대한 책임이 여전히 사람에게 있음을 강조한다. 베타 제품의 신뢰성 향상도 남은 과제로 이야기한다.

### 벤치마크와 실제 비용 (23:18~26:37)

CursorBench 3.2의 성공률과 작업당 비용을 비교하며 같은 예산으로 더 많은 일을 처리하는 가치를 설명한다. 제시된 수치는 공급자의 특정 평가 환경 결과이므로 모든 저장소와 작업으로 일반화할 수 없다. 핵심 비교 단위는 모델의 단가보다 완료한 작업당 비용이다.

## 예시

영상에서 소개한 개발 흐름:

`버그 보고 → 지속 실행 봇의 분류 → 기능 에이전트에 위임 → 코드 수정·검증 → 스크린샷/영상이 포함된 PR → 사람의 검토`

팀의 스타일 규칙은 매번 프롬프트로 설명하는 데 그치지 않고 린트·CI에서 검사하도록 구성한다.

## 요약

- 지속 실행 에이전트는 업무를 기억하고 여러 실행자를 조정한다.
- 사람은 작업 선택, 코드 기반의 구조, 검토 가능한 품질을 책임진다.
- 성능은 특정 벤치마크와 실제 업무당 비용을 구분해 평가한다.
