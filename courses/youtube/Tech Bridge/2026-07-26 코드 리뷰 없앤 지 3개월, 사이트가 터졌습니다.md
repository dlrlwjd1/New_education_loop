# [한영자막] 코드 리뷰 없앤 지 3개월, 사이트가 터졌습니다

## 개요
- 업로드일: 2026-07-26
- 원본: https://www.youtube.com/watch?v=-c43cv80FiA
- 채널: Tech Bridge (해외 기술 강연에 한영자막을 붙여 소개하는 채널)
- 발표자: Dex Horthy (Human Layer 공동창업자)
- 출처: AI 엔지니어링 컨퍼런스 발표 (영상 내 언급으로 미루어 AI Engineer 계열 컨퍼런스로 추정되나, 정확한 행사명은 자막/영상에서 명시되지 않음)
- 핵심 주제: AI 코딩 에이전트에게 코드 리뷰를 완전히 맡기는 "라이트 오프(lights-off) 소프트웨어 팩토리"가 왜 실패하는지, 그리고 그 원인이 하니스(harness) 설계 문제가 아니라 **코딩 모델의 훈련(RL) 방식 자체의 한계**라는 주장. 문제를 완화하기 위한 실전 대안(사전 계획 기반 워크플로)도 함께 제시한다.

## 내용
### 문제 제기 — 코드 리뷰 없는 소프트웨어 팩토리의 균열
- 모두가 AI 코딩을 프로덕션에 도입 중이며, StrongDM 같은 회사는 아무도 코드를 읽지 않는 "라이트 오프 소프트웨어 팩토리"를 만들었다는 이야기가 돈다. 지배적인 서사는 "토큰을 더 쓰면 된다. 병목은 사람이다"이다.
- 하지만 균열이 보이기 시작했다. 발표자의 친구(AI Engineer Europe에서 만난 Mario)는 코딩 에이전트로 인한 장애가 늘고 있다며 속도를 늦추자고 호소했다.
- Faros AI 리포트(2026년 1~2월경 AI 코딩 툴 본격 도입 이후 기준): PR 코드 리뷰 품질 하락, 코멘트 수·길이 증가, 리뷰 없이 병합되는 PR 급증, 인시던트 및 개발자당 버그 수 증가.
- 흔한 반박은 "잘못 쓰고 있는 것"(you're holding it wrong)이지만, 발표자는 이것이 스킬 문제가 아니라고 주장한다.

### 소프트웨어 팩토리의 진화 (2022 → 에이전틱 → 라이트 오프)
- **2022년 소프트웨어 팩토리**: 사람이 백로그(Jira/Linear 등)에서 작업을 가져가 구현 → PR 생성 → 사람이 리뷰·테스트 → 프로덕션 배포 → 사용자 피드백/버그 리포트 → 다시 백로그로. 팀들은 이미 오래전부터 "구현"과 "리뷰" 단계가 각각 시간·일 단위로 걸린다는 것을 알고, 사전 계획(아키텍처 제안, 스프린트 계획)으로 리워크 확률을 줄여 왔다.
- **에이전틱 소프트웨어 팩토리**: "사람이 만든다" 단계를 에이전트로 교체. 구현 시간은 분·시간 단위로 줄었지만, 리뷰·테스트는 여전히 사람이 해야 해 시간·일 단위로 남아 병목이 된다. 여기에 에이전틱 코드 리뷰·회귀 테스트를 더해 속도를 높인다.
- **라이트 오프 소프트웨어 팩토리** (Dentcho Biero가 이름 붙임): 인시던트와 사용자 피드백까지 곧바로 에이전트 큐에 넣고, 코드 리뷰 자체를 없앤다. 이제 유일한 질문은 "얼마나 많은 일을 큐에 넣고, 얼마나 빨리 리뷰·테스트하는가"가 된다.
- 발표자는 이 마지막 단계가 작동하지 않는다고 주장한다.

### Human Layer의 라이트 오프 실험 (2025년 7월)
- Human Layer는 2025년 7월 실제로 코드 리뷰를 완전히 없애는 "라이트 오프"를 몇 달간 진지하게 시도했다.
- 몇 달이 지나자 에이전트가 (가장 정교한 프롬프팅·리서치·재현을 시도해도) 스스로 해결하지 못하는 이슈가 나타났고, 결국 3개월간 읽지 않은 코드베이스를 사람이 직접 파고들어야 했다. 그 사이 사이트는 다운되고 사용자는 화가 났다.
- 참고: "브라운필드(brownfield)"는 전통적으로 10년 된 Java 시스템 같은 걸 뜻했지만, 발표자는 지금 같은 개발 속도에서는 **3~6개월 된 코드베이스도 에이전트가 다루기 어려워지는 브라운필드**가 된다고 본다.
- 핵심 진단: 모델은 사람의 상당한 개입(steering) 없이는 **코드베이스 품질을 시간에 걸쳐 유지·개선하지 못한다**. 여기서 "유지보수성(maintainability)"은 한 부분을 고치면 다른 부분이 깨지는 문제(Martin Fowler의 "shotgun surgery" 코드 스멜)를 가리킨다.
- 이는 최근 모델이 좋아진 것과는 별개다. 일회성 문제 해결이나 새 마케팅 사이트 바이브 코딩은 2024~2025년 대비 훨씬 좋아졌지만, **코드베이스 품질 유지 능력은 별로 나아지지 않았다**는 것이 발표자의 (증명은 어렵지만) 체감이다.

### 왜 모델은 유지보수성을 못 지키는가 — RL 훈련의 한계
- Claude Code가 급성장(1년 안에 매출 40억→90억 달러 수준)한 이유: 이전에도 Aether, CodeBuff 같은 CLI 에이전트가 있었고 도구(read/write/edit/grep/bash)도 같았다. 차이는 **모델 랩이 자신들이 배포할 하니스에 맞춰 직접 모델을 강화학습(RL)한 첫 사례**였다는 점. 하니스만 만들고 모델 가중치를 갖지 못한 빌더는 항상 불리하다(OpenAI 팀의 2025년 11월 발표 인용).
- RL로 코딩 에이전트를 훈련하는 절차: 문제를 주고 → 여러 시도(trace)를 생성 → 정답 여부(테스트 통과 등)로 점수화 → 나쁜 행동은 덜 나오게, 좋은 행동은 더 나오게 가중치를 업데이트.
- 대표 벤치마크 SWE-bench Multilingual: Redis, JQ, Django 같은 오픈소스 저장소 기반 약 15분 분량 작업. 기준 커밋(base commit)에서 시작 → 에이전트가 패치 생성 → 에이전트가 건드린 테스트 파일은 되돌림(모델이 테스트를 주석 처리해 통과시키는 것을 막기 위해) → 숨겨둔 골든 테스트 패치 적용 → 기존 테스트+신규 테스트가 모두 통과해야 보상.
- 문제: 이 시스템은 **프로그램 설계 품질이나 유지보수성 저하를 벌점 처리할 방법이 없다**. 그래서 불필요한 try/catch 남발, 무리한 타입 캐스팅처럼 "테스트만 통과시키면 그만"인 안티패턴이 생긴다.
- 근본 원인: **코드가 실행되고 테스트가 통과하는지 검증하는 것보다, 코드 품질·유지보수성을 검증하는 것이 훨씬 어렵다.** 나쁜 아키텍처의 비용은 몇 달~몇 년 뒤에야 드러나므로, 그 보상 신호를 훈련 시점까지 되돌려 전파하기가 매우 어렵다.

### 코드 품질을 평가하는 차세대 벤치마크들
- **Sweep Marathon** (Abundant AI): 마이크로소프트 엑셀 전체 기능을 통째로 복제하는 것 같은 400시간 규모의 과제, 정교한 보상 체계.
- **Deep Sweep** (Data Curve): 실제로 만들어진 적 없어 훈련 데이터에 없는 대규모 OSS 저장소 과제.
- **Frontier Code** (Cognition): 여러 PR에 걸친 과제. 모델이 패치 이전 코드에서 실패하지 않는 테스트를 쓰면 벌점을 주는 등 흥미로운 장치. 판정 모델(judge model)이 코드 품질 규칙 준수 여부를 평가.
- 다만 발표자는 "모델이 품질을 판정하는 방식"은 한계가 있다고 본다 — 모델이 좋은 코드가 무엇인지 정말로 안다면애초에 그렇게 짰을 것이기 때문. 리뷰 에이전트를 늘리고 토큰을 더 쓰는 것은 하한선(floor)은 올릴 수 있지만, RL로 가르칠 수 있는 것 자체의 한계에는 여전히 갇혀 있다.

### 실전 대안 — 다시 코드 리뷰를 켜되, 사전 계획으로 부담을 줄인다
- 결론: 지금은 여전히 **코드를 읽어야 하는 단계**이지만, 사전 계획을 통해 훨씬 빠르게 움직일 수 있다. 코드 리뷰를 다시 켜고(라이트 온), 리뷰가 길어지거나 어려워질 확률을 줄이는 사전 정렬(alignment)에 투자한다.
1. **제품 리뷰(product review)** — 어떤 문제를 풀고 있는지, 원하는 동작이 무엇인지, 목업(mock-up)을 함께 검토. (작은 작업은 이 단계 없이 바로 에이전트로.)
2. **아키텍처(system architecture)** — 컴포넌트 계약(component contract), 데이터 모델, 제약 조건 등 시스템이 어떻게 맞물리는지 정리한 문서.
3. **프로그램 설계(program design)** — 아키텍처만 정해지면 나머지는 모델이 알아서 한다는 가정은 과소평가되어 있다. 타입, 메서드 시그니처, 프로그램 구조, 호출 스택 수준까지 미리 들여다본다. (Cloudflare의 Dylan Mulroy도 콜 그래프를 계획 과정에 활용한다고 언급.)
4. **수직 슬라이스(vertical slices)** — 구현 순서, 멀티 레포 조율, 단계별 검증 방법을 정리. (모델의 "수평적 계획" 경향에 대해서는 발표자의 AI Engineer Miami 발표 참고.)
- 요지: 사전 계획·정렬에 30분을 쓰면 리뷰에서 몇 시간을 절약한다. 그러면 모든 줄을 실제로 읽는 것도 충분히 실현 가능해진다.
- PR이 너무 많다고 느껴진다면, 사실은 **나쁜 PR이 너무 많은 것**이다. 좋은 PR은 리뷰가 즐겁다. 20% 정도 재작업이 필요한 PR이라도(바이브 코딩 결과물치고는 양호한 수준) 리뷰어와 제출자 모두에게 감정적·인지적 부담이다.
- 모델 지원 계획·정렬을 쓰면: 정렬은 AI가 정보를 한 번에 모아주므로 더 짧아지고, 코드 리뷰는 사전 정렬 덕분에 더 빨라지고, 코딩 자체는 AI가 하므로 더 빠르다. 결과적으로 훨씬 빨리 움직이면서도 **여전히 모든 코드를 읽고 소유한다.**

### 맺음말
- 다 듣고 나면 조금 실망스러울 수 있다(코드를 영영 안 읽어도 되는 세상이 더 좋아 보이니까). 하지만 우리는 엔지니어이고, 이런 것들은 그저 제약 조건일 뿐이다. 모델이 잘하는 것과 못하는 것을 파악해 그 제약 안에서 문제를 풀면 된다.
- 발표자는 Human Layer(AI IDE 및 협업 플랫폼, Claude Code/Codex 스타일의 협업 워크스페이스를 통해 위 워크플로를 지원)를 소개하며, 소규모 팀에는 무료로 제공된다고 밝혔다.

## 예시
### 소프트웨어 팩토리의 3단계 진화
```
2022 팩토리        : 사람이 구현 (시간~일) → 사람이 리뷰/테스트 (시간~일) → 배포 → 사용자 피드백
에이전틱 팩토리    : 에이전트가 구현 (분~시간) → 사람이 리뷰/테스트 (여전히 시간~일, 병목)
라이트 오프 팩토리 : 인시던트/피드백까지 큐로 직행, 코드 리뷰 자체를 제거 → 3~6개월 뒤 유지보수성 붕괴
```

### SWE-bench류 벤치마크의 보상 판정 절차
```
1. base commit 체크아웃 (이슈 해결 전 상태)
2. 에이전트가 문제 해결 시도 → 패치 생성
3. 에이전트가 건드린 테스트 파일은 원복 (테스트 주석 처리로 편법 통과 방지)
4. 숨겨둔 golden test patch 적용
5. 기존 테스트 + 신규 테스트 모두 통과해야 보상(1) 부여, 아니면 0
   → 이 절차는 "테스트 통과 여부"만 보므로 아키텍처 품질·유지보수성은 애초에 측정 대상이 아님
```

### 사전 계획 4단계 (리뷰 부담을 줄이는 워크플로)
| 단계 | 내용 |
| --- | --- |
| 제품 리뷰 | 문제 정의, 원하는 동작, 목업 검토 |
| 아키텍처 | 컴포넌트 계약, 데이터 모델, 제약 조건 |
| 프로그램 설계 | 타입, 메서드 시그니처, 호출 스택 수준의 설계 |
| 수직 슬라이스 | 구현 순서, 멀티 레포 조율, 단계별 검증 |

## 요약
- "라이트 오프 소프트웨어 팩토리"(코드 리뷰를 완전히 없애고 토큰만 더 쓰면 된다는 접근)는 실패한다. Human Layer가 2025년 7월 직접 겪었다 — 3~6개월 뒤 에이전트가 못 푸는 이슈가 쌓이고 유지보수성이 무너졌다.
- 원인은 하니스 설계 부족이 아니라 **코딩 모델 훈련(RL) 방식의 근본적 한계**다. SWE-bench류 벤치마크는 "테스트 통과"만 이진 보상으로 주기 때문에, 아키텍처 품질·유지보수성 저하는 벌점을 받지 않는다.
- Claude Code가 성공한 이유는 모델 랩이 자사 하니스에 맞춰 직접 RL 훈련을 했기 때문 — 하니스만 만들고 모델을 갖지 못하면 구조적으로 불리하다.
- Sweep Marathon, Deep Sweep, Frontier Code 등 코드 품질을 평가하려는 차세대 벤치마크가 등장하고 있지만, 판정 모델(judge model) 방식에는 한계가 있다.
- 실전 대안은 코드 리뷰를 다시 켜되, **제품 리뷰 → 아키텍처 → 프로그램 설계 → 수직 슬라이스** 순으로 사전 계획·정렬에 투자해 리뷰 부담과 재작업 확률을 줄이는 것. 결과적으로 더 빠르게 움직이면서도 모든 코드를 계속 읽고 소유할 수 있다.
