# GitHub Spec Kit으로 MCP 서버 만들기 - 명세에서 구현과 검증까지

## 개요

- **업로드일:** 2026-08-29
- **채널:** Tech Bridge
- **발표자·출처:** Microsoft Build 세션 / GitHub Copilot·Spec Kit 시연
- **원본:** [YouTube](https://www.youtube.com/watch?v=F_smvU3oqbU)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 21:59, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 일회성 프롬프트 대신 팀이 검토하고 버전 관리하는 명세를 개발의 중심 산출물로 삼는다.

## 내용

### 프롬프트에서 공유 가능한 명세로 (00:00~04:26)

개인의 대화에만 남는 프롬프트는 팀 단위의 검토·재사용에 약하다. Spec Kit 워크플로는 원칙(constitution), 기능 명세(specification), 기술 계획(plan), 작업(tasks), 구현을 연결한다. 기능 명세는 무엇을 만들지 설명하고 기술 스택과 배포 방식은 계획에서 정한다. 생성된 문서는 사람이 읽고 동의한 뒤 다음 단계로 넘어가야 한다.

### 세션 안내 MCP 서버의 원칙과 기능 (04:26~13:51)

데모는 Microsoft Build 세션 데이터를 검색하는 HTTP MCP 서버다. Specify CLI로 기존 프로젝트에 Copilot 통합을 초기화한다. 도구의 기반은 Markdown과 스크립트이므로 생성된 파일을 직접 읽어 동작을 이해할 수 있다.

원칙에는 실제 데이터에 근거하기, 시간 정확성, 안전한 도구 설계, HTTP 안전성, 테스트 가능성, 기본 개인정보 보호를 둔다. 기능 명세에는 세션 검색·상세 조회·현재 진행 중인 세션 등 사용자에게 필요한 동작을 적는다.

### 기술 계획과 작은 작업 (13:51~18:23)

TypeScript·Node.js·HTTP 전송·배포 설정은 기술 계획에서 지정한다. 버전을 생략하면 모델이 원하는 버전과 다른 값을 채울 수 있으므로 명확히 확인한다. 작업 단계는 설정과 기반 구성부터 기능 구현까지 논리적인 순서로 나눈다. 모호함을 해소하고 문서 간 일관성을 분석하는 중간 단계도 권장한다.

### 실행 결과 확인과 작은 도입 (18:23~21:59)

완성된 서버를 실행하고 MCP Inspector에서 연결·도구 목록·검색 결과를 확인한다. 데모의 일부는 미리 준비한 브랜치로 전환해 보여 준다. 발표자는 모든 개발 절차를 한꺼번에 바꾸기보다 작지만 실제 가치가 있는 기능 하나에 적용하라고 제안한다. 원칙은 절대 바뀌지 않는 파일이라기보다 팀의 필수 조건을 담고 학습에 따라 갱신하는 문서다.

## 예시

| 산출물 | 세션 안내 서버에서 담는 내용 |
|---|---|
| 원칙 | 존재하는 세션만 반환하고 시간을 정확히 처리 |
| 기능 명세 | 세션 검색·상세·현재/다음 세션 조회 |
| 기술 계획 | TypeScript, Node.js, HTTP 전송과 배포 설정 |
| 작업 | 기반 설정과 기능별 구현·검증 순서 |
| 검증 | 서버 실행 후 Inspector에서 실제 도구 호출 |

## 요약

- 무엇을 만들지와 어떻게 구현할지를 분리한다.
- 명세와 계획도 코드처럼 검토하고 저장소에서 관리한다.
- 작은 실제 기능으로 시작해 실행 가능한 결과까지 확인한다.
