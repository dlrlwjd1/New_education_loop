# 에이전트와 도구를 연결하는 다섯 가지 인증 패턴

## 개요

- **업로드일:** 2026-08-18
- **채널:** Tech Bridge
- **발표자·출처:** Tech Bridge 소개 영상의 에이전트 보안 아키텍처 해설
- **원본:** [YouTube](https://www.youtube.com/watch?v=CSVg3rUZSQo)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 11:13, 자동 자막 언어 `es-US`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 연결 표준화, 사용자와 에이전트의 신원, 위임 관계, 자격 증명 수명을 나누어 연결 방식을 비교한다.

## 내용

### 직접 연결과 사용자 OAuth (00:00–05:15)

첫 패턴은 에이전트가 서비스 계정이나 API 키로 도구에 직접 접속하는 방식이다. 기존 연결 방식을 재사용하기 쉽지만 도구는 요청한 최종 사용자를 알기 어렵다. 영상은 전체 공개 또는 회사 전체에 허용된 정보로 범위를 제한했던 초기 사례를 든다.

두 번째는 도구의 OAuth 흐름으로 사용자 인증을 거쳐 토큰을 사용하는 방식이다. 사용자 신원은 전달되지만 도구 관점에서 에이전트와 사용자 본인의 행동을 구분하기 어려울 수 있다. 장기간 유효한 자격 증명을 로컬에 보관하는 문제도 설명한다. 실제 토큰 수명은 서비스와 설정에 따라 달라진다.

### MCP를 통한 연결 추상화 (05:22–06:51)

세 번째는 OAuth 연결에 MCP 계층을 더한다. 에이전트마다 도구별 연결 구현을 반복하는 부담을 줄이고 공통 인터페이스를 사용한다. MCP는 연결 방식을 추상화하는 역할이며, 이 단계만으로 사용자·에이전트 신원이나 장기 토큰 문제가 모두 해결되는 것은 아니다.

### On-Behalf-Of와 토큰 교환 (06:57–09:29)

네 번째는 에이전트 자체도 인증하고, 누구를 대신해 어떤 일을 수행하는지 위임 관계를 표현하는 방식이다. 토큰 교환을 통해 사용자와 에이전트 양쪽 신원을 연결해 전달한다고 설명한다.

핵심은 사용자의 토큰을 가진 주체로만 보이는 상태에서 벗어나, 사용자와 대리 실행자의 관계를 관측하고 권한을 판단할 수 있게 하는 것이다. 이것이 OAuth 개념 전체를 없애는 것은 아니며, 영상에서는 도구별 단순 OAuth 연결과 대비해 설명한다.

### Vault와 짧은 자격 증명 (09:35–11:13)

마지막 패턴은 장기 자격 증명을 보안 저장소에 두고 실행 흐름에는 짧게 유효한 자격 증명을 제공하는 방식이다. 탈취 후 재사용할 수 있는 시간을 줄이려는 목적이다. 사용자·에이전트 식별과 위임에 자격 증명 수명 관리까지 더하는 구조로 정리한다.

## 예시

| 패턴 | 추가되는 가치 | 남는 설계 과제 |
|---|---|---|
| 직접 API 연결 | 단순한 구현 | 최종 사용자 식별 |
| 사용자 OAuth | 사용자 신원과 권한 연결 | 대리 실행자 구분·토큰 보관 |
| MCP + OAuth | 연결 인터페이스 표준화 | 신원과 수명 문제는 별도 |
| 위임 + 토큰 교환 | 사용자·에이전트 관계 표현 | 토큰 경로와 권한 검증 |
| Vault + 짧은 자격 증명 | 장기 비밀 격리·노출 시간 축소 | 저장소와 발급 정책 관리 |

## 요약

- 연결 표준과 인증·권한은 구분한다.
- 사용자뿐 아니라 대리 실행하는 에이전트도 식별한다.
- 장기 비밀을 격리하고 실제 실행에는 필요한 범위의 자격 증명을 제공한다.
