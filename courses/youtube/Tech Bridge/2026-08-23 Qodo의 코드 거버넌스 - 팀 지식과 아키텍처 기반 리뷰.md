# Qodo의 코드 거버넌스 - 팀 지식과 아키텍처 기반 리뷰

## 개요

- **업로드일:** 2026-08-23
- **채널:** Tech Bridge
- **발표자·출처:** Itamar Friedman / Qodo
- **원본:** [YouTube](https://www.youtube.com/watch?v=FHewiSeWJhQ)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 17:59, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 코드 리뷰를 자동화하려면 팀 규칙·시스템 계약·실패 경험을 사람과 에이전트가 함께 확인할 맥락으로 만들어야 한다.

## 내용

### 리뷰가 수행하는 두 역할 (00:00~05:05)

코드 리뷰는 안전성·유지보수성·아키텍처를 확인하는 과정이면서 팀의 지식과 의도를 맞추는 과정이다. 줄 단위 리뷰를 줄이려면 두 역할을 다른 방식으로 수행할 수 있어야 한다. 허용 가능한 위험과 빠른 복구를 중시하는 정도에 따라 자동화 경로가 달라진다고 설명한다.

### 모델보다 부족한 조직 맥락 (05:05~12:12)

일반적인 모델은 구체적인 팀 상황 없이 범용 지적을 내놓기 쉽다. 지침 파일·스킬·MCP·여러 실행 환경에 흩어진 규칙을 일관되게 관리하고 사용한 규칙의 링크를 결과에 보여 줘야 한다. 사람에게는 이해하고 통제할 화면을, 에이전트에게는 수정과 재검토에 쓸 구조화된 정보를 제공한다.

자동 리뷰 후 사람이 추가로 발견하는 문제가 줄어드는지 관찰하며 신뢰를 쌓는 방향이다. 일정 개수의 PR을 통과했다고 모든 변경이 안전해진다는 보장은 아니다.

### 시스템 계약과 실패 이력 (12:12~14:33)

중요한 지식은 코딩 스타일만이 아니라 서비스 사이의 계약과 과거 장애의 원인에도 있다. 한 서비스의 변경이 다른 저장소를 깨뜨리는 관계를 그래프로 나타내고 관련 논의·원인 분석을 연결한다. 동시에 진행되는 여러 PR이 서로 영향을 주는지도 봐야 한다.

### 단계적인 승인·차단 자동화 (14:33~17:59)

규칙마다 실제 사용 여부와 효과를 측정하고 받아들여진·거절된 리뷰, 개발자 논의, 운영 장애에서 맥락을 갱신한다. AI의 막연한 판단에 전부 맡기기보다 언제 승인·차단할지 의미가 명확한 규칙을 늘려 간다. 발표자는 이를 경험과 판단을 시스템에 옮기는 과정으로 설명한다. 속도 개선 수치는 목표·주장으로 제시되며 보편적인 실험 결과는 아니다.

## 예시

두 서비스의 API 계약을 바꾸는 PR이라면:

`변경된 계약 확인 → 의존 저장소 탐색 → 관련 장애·리뷰 이력 조회 → 적용 규칙과 근거 제시 → 수정·재검토 → 정해진 조건으로 승인 또는 차단`

개별 diff뿐 아니라 동시에 변경 중인 다른 PR과의 관계도 검토 대상이다.

## 요약

- 자동화는 품질 확인과 팀 학습이라는 리뷰의 두 역할을 보존해야 한다.
- 규칙·계약·장애 이력을 찾을 수 있고 사람이 확인할 수 있어야 한다.
- 승인과 차단은 효과를 관찰하며 단계적으로 자동화한다.
