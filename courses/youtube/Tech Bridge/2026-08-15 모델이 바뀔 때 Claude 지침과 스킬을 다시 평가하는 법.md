# 모델이 바뀔 때 Claude 지침과 스킬을 다시 평가하는 법

## 개요

- **업로드일:** 2026-08-15
- **채널:** Tech Bridge
- **발표자·출처:** Nate / Claude Code 개발자 인터뷰 해설
- **원본:** [YouTube](https://www.youtube.com/watch?v=PFZWAAbQGv0)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 11:40, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 이전 모델의 약점을 보완하던 지시를 재평가하되 업무 맥락과 브랜드 기준은 유지하고 목표·검증을 명확히 한다.

## 내용

### 오래된 지시가 새 모델을 방해할 수 있다 (00:00–03:41)

진행자는 Boris Cherny 인터뷰를 인용해 모델이 바뀔 때 하네스·도구·시스템 프롬프트도 달라진다고 설명한다. 과거의 약점을 보완하던 상세 지시가 새 모델에서는 불필요하거나 더 좋은 해결책을 막을 수 있다는 관점이다.

인터뷰의 스킬·hook·지침 초기화 제안은 모델의 기본 행동을 관찰하는 실험으로 소개된다. 모든 설정을 무조건 삭제해야 한다는 결론으로 받아들이지는 않는다.

### 복제한 저장소에서 비교한 결과 (03:47–07:18)

진행자는 저장소를 복제한 뒤 지침과 스킬을 없애 같은 영상의 자료 가이드를 만들어 보았다. 기존 설정의 결과는 브랜드 이미지·색·링크와 형식이 좋았고, 기본 설정의 결과는 아이디어별 구분과 타임스탬프가 마음에 들었다고 말한다.

따라서 파일 위치, 사업 맥락, 브랜드 자산과 필수 링크는 남기되 내용 전개를 지나치게 고정하는 부분은 줄이는 방향을 택한다. 대규모 코드 개발자의 조언이 자신의 조사·문서 업무에도 그대로 맞는지 결과로 확인해야 한다고 강조한다.

### 목표·제약·성공 기준을 전달 (07:21–10:18)

모델이 이미 할 수 있지만 제품이나 사용 방식 때문에 드러나지 않는 능력을 'product overhang'으로 설명한다. 상세한 순서를 모두 지정하기보다 조금 더 어려운 목표를 주고 허용 범위와 성공 기준을 정의해 보라는 제안이다.

완료를 말로 선언하는 것에서 끝내지 않도록 무엇으로 증명할지도 함께 정한다. 진행자의 감정적인 강조 문구는 개인적인 프롬프트 습관이며 검증된 성능 기법으로 제시하지 않는다.

### 관리하되 이해를 놓치지 않기 (10:21–11:40)

계획·검토·판단·취향을 제공하면서 실행 방법에는 여지를 둔다. 다른 관점의 검토와 자기 검증을 허용하되, 최종 결과를 이해하는 책임까지 넘기지 말라는 결론이다.

## 예시

영상의 자료 가이드 비교에서 도출한 스킬 수정 방향:

| 남길 것 | 다시 시험할 것 |
|---|---|
| 자료 위치와 사업 맥락 | 과거 모델을 위한 지나치게 상세한 순서 |
| 브랜드 색·로고·필수 링크 | 항상 같은 개수와 형식을 강제하는 구성 |
| 결과 품질과 확인 방법 | 모델이 스스로 더 잘할 수 있는 편집 판단 |

## 요약

- 새 모델에서 기존 지침이 여전히 필요한지 비교한다.
- 조직 고유의 맥락과 불필요한 미세 지시를 구분한다.
- 목표와 검증 기준을 주고 결과에 대한 이해는 유지한다.
