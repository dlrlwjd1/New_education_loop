# Harrison Chase의 하네스 커스터마이징과 평가·관측 루프

## 개요

- **업로드일:** 2026-08-15
- **채널:** Tech Bridge
- **발표자·출처:** Harrison Chase / LangChain
- **원본:** [YouTube](https://www.youtube.com/watch?v=H_zE_JwstWU)
- **정리 범위:** 전체 제공 스크립트(마지막 발화 22:50, 자동 자막 언어 `en`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 모델·컨텍스트·하네스를 함께 평가하고 운영 실행 기록으로 조직에 맞는 에이전트를 개선한다.

## 내용

### 에이전트의 세 구성과 하네스의 역할 (00:00–04:38)

에이전트를 모델, 컨텍스트, 이를 조율하는 하네스로 나눈다. 하네스의 핵심은 적절한 시점에 필요한 맥락을 모델에 전달하고 도구 결과를 다음 추론에 연결하는 것이다.

기본 루프는 모델 호출 → 도구 실행 → 관측 결과 반환이다. 호출 전후의 middleware·hook으로 메모리, 하위 에이전트, 샌드박스, 긴 컨텍스트 요약, 큰 도구 출력의 파일 저장을 더할 수 있다.

### 언제 자체 하네스가 필요한가 (04:42–08:05)

범용 하네스로 시작하고 실제로 필요한 영역에 통과 조건과 검사를 추가하라고 권한다. 모델이 학습한 작업에서 멀어지거나 예측 가능성과 통제가 중요해질수록 맞춤 흐름의 가치가 커진다.

전체 작업이 특수하더라도 파일 수정처럼 모델이 익숙한 세부 도구는 유지하는 것이 좋다. Deep Agents의 모델 프로필은 모델에 따라 파일 수정 구현을 바꾸는 예다. 범용 루프·hook 확장·명시적인 단계 구조는 연속적인 선택지다.

### 조직의 기준을 벤치마크로 만들기 (08:08–12:01)

사내 평가는 조직에서 좋은 결과가 무엇인지 정의하고 변경의 회귀를 잡는다. Harbor 작업은 실행 환경, 지시, 검증기와 기준 해답 등으로 구성하고 샌드박스에서 실행한다. 검증에는 코드, 테스트, LLM이나 에이전트 판정을 사용할 수 있다.

모델뿐 아니라 하네스·추론 수준을 바꾸어 비교하며 정확도와 함께 지연 시간·토큰·비용을 본다.

### 실행 기록과 피드백의 순환 (12:05–16:15)

실패는 모델 능력 부족뿐 아니라 필요한 맥락이 전달되지 않아 생길 수 있다. 대화 경로를 읽는 화면과 개별 호출의 입력·출력을 보는 상세 trace가 모두 필요하다.

운영 실행 → trace 수집 → 피드백으로 사례 선별 → 실험 → 개선의 루프를 만든다. 사용자 경험 설계로 자연스러운 피드백을 얻거나 저렴한 평가 모델·코드로 운영 기록을 분류할 수 있다. 개선 대상은 하네스, 모델, 기억·컨텍스트 어느 부분이든 될 수 있다.

### LangSmith Engine 시연과 Q&A (16:20–22:50)

Engine은 trace를 조사해 반복 문제를 이슈로 묶고 근거와 수정안을 제시하는 에이전트로 소개된다. 프롬프트와 하네스 코드 변경을 제안하는 예를 보여 준다.

자체 평가에서는 다른 하네스가 작은 스크립트로 trace를 분석하는 장점을 발견해 가져왔다고 설명한다. 하네스가 하나로 수렴할지는 확답하지 않는다. 공통 코딩 기능은 비슷해져도 도메인과 통제 요구에 따라 달라질 수 있으므로 평가·관측이 필요하다는 결론이다.

## 예시

`운영 trace → 실패 패턴과 근거 사례 → 전용 평가 과제 → 모델·하네스·컨텍스트 변경 실험 → 품질·비용·지연 비교 → 운영 반영`

벤치마크는 순위를 얻는 도구이면서 다른 구현의 좋은 행동을 발견하는 도구다.

## 요약

- 범용 하네스로 시작하고 실제 요구에 맞춰 조정한다.
- 조직의 기준 데이터와 실행 환경으로 변경을 평가한다.
- 관측과 피드백이 모델·컨텍스트·하네스의 개선을 연결한다.
