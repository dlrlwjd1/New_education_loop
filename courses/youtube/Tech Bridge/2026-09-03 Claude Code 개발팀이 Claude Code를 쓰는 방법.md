- 채널: Tech Bridge

- 출연: Thariq Shihipar, Sid Bidasaria, Robert Boyce — Anthropic Claude Code 팀
- 핵심 주제: Claude Code 팀이 개별 도구 호출을 지켜보던 방식에서 목표 기반 위임, 원격 루프, 동적 워크플로, Claude Tag를 이용한 비동기 개발로 이동한 과정
- 핵심 메시지: 모델이 충분히 강해지면 사람은 개별 편집과 도구 호출을 감독하는 대신 목표, 검증 환경, 피드백 연결을 설계해야 한다. 하네스 기능은 영구 자산이 아니라 현재 모델의 한계를 보완하는 임시 발판일 수 있으므로 모델과 작업 범위에 맞춰 계속 바꿔야 한다.

## 내용

### 도구 호출 관찰에서 목표 위임으로
Claude Code 초기에는 사용자가 프롬프트를 주고, 모델의 각 도구 호출을 확인하며, 권한 요청을 승인했다. 현재 팀원들은 복잡한 업무의 상당 부분을 Slack 안의 Claude Tag에 위임한다.

한 팀원은 업무의 70~80%를 Claude Tag에서 처리하고, 세부 조정이 필요하거나 직접 감독하고 싶은 나머지 작업에만 데스크톱이나 터미널 환경을 연다고 설명한다. 작업 단위도 “이 함수를 작성해라”에서 “이 목표를 달성해라”로 바뀌었다.

Slack 기반 에이전트는 팀 대화, 제품 맥락, 과거 결정 같은 주변 정보를 찾을 수 있다. 사용자는 각 도구 호출과 내부 전개보다 최종 목표와 결과를 중심으로 상호작용한다.

### 두 달마다 바뀌는 기반 위에 제품을 만든다
전통적인 제품의 기반 기술은 수년간 유지되지만 AI 모델의 능력은 몇 달 단위로 크게 변한다. Claude Code 팀은 현재 모델 사용자에게 가치를 제공하면서 동시에 다음 모델이 가능하게 할 작업 방식을 미리 준비해야 한다.

초기 모델은 긴 작업에서 다섯 항목 중 세 개만 처리하고 멈추곤 했다. 당시 명시적인 todo list는 장기 작업을 끝까지 수행하게 하는 효과적인 하네스 기능이었다. 모델과 메모리가 좋아지면서 같은 장치는 더 이상 필수적이지 않게 됐다.

이 경험에서 나온 원칙은 자신이 만든 하네스 기능에 집착하지 않는 것이다. 하네스의 많은 기능은 현재 모델의 실패를 보완한다. 모델이 그 문제를 스스로 해결하면 기능을 제거하고, 더 큰 작업에서 새로 나타난 한계를 지원하는 다른 primitive를 만들어야 한다.

### `AskUserQuestion`에서 대화형 아티팩트로
팀은 Claude가 계획 중 필요한 정보를 물어볼 수 있도록 `AskUserQuestion` 도구를 만들었다. 초기에는 모델이 도구를 안정적으로 호출하게 하는 설계가 어려웠지만, 모델 발전과 함께 사용성이 좋아졌다.

최근에는 고정된 질문 도구보다 Claude가 HTML 아티팩트를 만들어 질문, 다이어그램, 목업을 한 화면에 제시하게 하는 방식도 사용한다. 같은 목적을 더 풍부한 인터페이스로 달성할 수 있게 된 것이다.

팀은 권한, 시각화, 메모리, 자동 실행 같은 작은 primitive를 만들고, 모델이 이를 조합해 더 큰 행동을 하도록 한다. 특정 워크플로를 지나치게 고정하기보다 모델 능력에 맞는 기본 재료를 제공하는 접근이다.

### 로컬 세션에서 원격 루프와 루틴으로
로컬 에이전트는 노트북을 닫으면 멈춘다. 팀은 먼저 원격 개발 머신을 사용했고, 이후 Claude Code on the web의 호스팅 컨테이너로 작업을 옮겼다. 초기 환경 구성과 권한 설정은 번거롭지만 한 팀원은 원격 실행 이후 생산성이 약 10배 높아졌다고 말한다.

클라우드에서 에이전트가 계속 실행되면 단일 대화 세션의 경계를 벗어날 수 있다.

- 매일 사용자 피드백을 모아 중요도별로 분류한다.
- 확신이 높은 버그는 자동으로 수정한다.
- 일정에 따라 반복 작업을 실행한다.
- 사람이 오프라인이어도 긴 작업을 계속한다.

이는 프롬프트 한 번의 결과를 기다리는 방식에서, 상위 목표를 받은 루프가 필요한 여러 세션과 행동을 스스로 만드는 방식으로의 전환이다.

### 코드 리뷰는 사람의 주의를 큰 문제로 이동시킨다
전통적인 사람 코드 리뷰에서는 리뷰했다는 신호로 사소한 nit을 몇 개 남기는 일이 생긴다. Claude가 이런 작은 문제를 찾아 자동 수정하면 사람은 API 구조, 서비스 경계, 장기 설계 의도처럼 더 큰 맥락에 집중할 수 있다.

Claude Code 팀의 리뷰 방식은 대규모 fan-out을 활용한다.

1. 여러 에이전트가 서로 다른 관점에서 잠재 버그를 찾는다.
2. 각 후보를 다시 여러 관점에서 적대적으로 검토한다.
3. 실제 문제일 가능성이 낮은 후보를 제거한다.
4. 중요한 문제만 사람에게 요약한다.

추론 시점에 더 많은 계산을 사용해 신뢰도를 높이는 **테스트 타임 컴퓨트(test-time compute)**의 사례다. 같은 패턴은 성능 문제 탐색이나 일반적인 심층 조사에도 사용할 수 있다.

### 동적 워크플로는 fan-out과 축약을 코드로 만든다
Fan-out은 많은 정보를 생성하므로 결과를 사람이 읽을 수 있게 다시 줄여야 한다. 지도-축약(map-reduce)처럼 검색 에이전트를 여러 개 실행하고, 다른 에이전트가 결과를 분류·검증하며, 마지막 에이전트가 핵심만 합치는 구조다.

중요한 점은 Claude가 작업에 맞는 하네스의 형태를 직접 코드로 만든다는 것이다. 몇 개의 에이전트를 어떤 순서로 실행하고, 어느 결과를 다음 단계에 넘길지를 동적으로 구성한다.

```text
문제
  → 여러 조사 에이전트로 fan-out
  → 후보별 반대 관점 검증
  → 중복·낮은 신뢰 후보 제거
  → 사람에게 핵심 결과만 전달
```

에이전트 판단과 결정론적 코드가 섞인 구조도 신뢰를 높인다. 예를 들어 모든 항목을 같은 방식으로 검사하는 부분을 명시적 `for` 루프로 작성하면 모델이 일부 항목을 건너뛸 가능성을 줄일 수 있다.

### Claude Tag로 Claude Tag 자체를 개발한다
팀은 Claude Tag가 자기 자신을 개발할 수 있도록 개발 환경과 검증 루프를 정비한다. 에이전트가 사람이 하는 것처럼 코드를 수정하고 애플리케이션을 실행하며 end-to-end로 동작을 시험할 수 있어야 한다.

Slack에서 보이는 Claude의 메시지는 내부 토큰 스트림 자체가 아니라 메시지 전송 도구를 통해 Claude가 선택한 결과다. 사용자는 필요하면 전체 transcript를 열 수 있지만 기본 인터페이스에서는 Claude가 언제 무엇을 보고할지 스스로 고른다.

처음에는 내부 과정을 전부 보지 못하는 것이 불안했지만, 충분한 검증을 갖춘 뒤에는 세부 도구 호출을 감독하지 않고 결과를 기다리는 방식이 가능해졌다. 모델에게 더 높은 수준의 책임을 주는 동시에 검증 환경을 강화한 것이다.

### 아이디어에서 운영 피드백까지 Slack에서 연결한다
Thariq은 새 도구 아이디어를 Claude Tag와 발전시키는 과정을 설명한다.

- 아이디어에 관심을 가질 이해관계자를 찾는다.
- Slack에서 목업을 만든다.
- 구현하고 사내에 배포한다.
- 이벤트를 추가해 사용자 행동을 관측한다.
- 피드백과 퍼널 지표를 지속해서 감시한다.
- 사람이 제시한 한 가지 수정안보다 “퍼널을 개선하라”는 상위 목표를 준다.

Claude Tag가 다른 사용자의 피드백이 들어올 때 알려주므로 개발자는 휴대폰에서도 대응할 수 있다. 브레인스토밍, 구현, 검증, 코드 리뷰, 모니터링이 하나의 비동기 루프로 이어진다.

### 검증이 자율성의 전제다
에이전트가 만든 PR은 직접 테스트되고, UI 결과에는 스크린샷이나 녹화가 첨부된다. 사람은 처음에는 sanity check를 위해 직접 실행할 수 있지만, 반복해서 증거가 쌓이면 감독 강도를 낮출 수 있다.

영상에서 반복되는 관계는 다음과 같다.

```text
검증 가능성 증가
→ 개별 행동 감독 감소
→ 더 높은 수준의 목표 위임
→ 더 긴 비동기 작업
```

피드백 데이터, 이벤트 저장소, Slack, GitHub issue를 에이전트에 연결하는 것도 중요하다. 결과를 만들게 하는 것만으로는 자기 개선 루프가 닫히지 않는다.

### 엔지니어의 시야가 세부 구현에서 문제 선택으로 이동한다
팀원들은 성능 최적화나 정교한 CSS처럼 직접 깊이 파고들던 작업을 Claude가 더 잘 수행하는 경우가 늘었다고 말한다. 대신 아이디어를 프로토타입과 프로덕션으로 옮기는 속도, 해결할 문제의 선택, 전체 시스템의 방향에 더 많은 시간을 쓴다.

세부 구현의 즐거움이 줄 수는 있지만, 이전에는 기술 부족 때문에 접근하지 못했던 영역도 Claude와 함께 해결할 수 있게 된다. 소프트웨어 엔지니어링은 원래 도구와 추상화가 계속 바뀌는 직업이며, 지금은 변화 속도가 빨라졌을 뿐 핵심은 여전히 문제 해결이라는 결론이다.

## 예시

### 목표 중심 원격 개발 루프

```text
목표: 최근 사용자 피드백에서 영향이 큰 문제를 줄인다.

1. 매일 피드백·이벤트·issue를 수집한다.
2. 중요도와 수정 확신도로 분류한다.
3. 확신이 높은 항목은 원격 컨테이너에서 구현한다.
4. 단위·통합·E2E 테스트를 실행한다.
5. UI 결과에는 스크린샷이나 녹화를 남긴다.
6. 여러 리뷰 에이전트가 fan-out으로 잠재 문제를 찾는다.
7. 반대 관점 검증으로 거짓 양성을 제거한다.
8. 핵심 결과와 PR만 사람에게 Slack으로 보고한다.
```

### 하네스 기능을 평가하는 질문

```text
1. 이 기능은 본질적인 작업 규칙인가, 현재 모델의 약점을 보완하는가?
2. 새 모델에서도 여전히 필요한지 평가했는가?
3. 세부 행동을 강제하기보다 재사용 가능한 primitive로 만들 수 있는가?
4. 사람이 transcript를 보지 않아도 결과를 검증할 증거가 있는가?
5. 반복 작업을 단일 세션 밖의 원격 루프로 옮길 수 있는가?
6. fan-out 결과를 다시 검증·축약해 사람의 인지 부하를 제한하는가?
```

## 요약
- Claude Code 팀은 개별 도구 호출 감독에서 Slack의 Claude Tag에 목표를 위임하는 방식으로 이동했으며, 일부 팀원은 업무의 70~80%를 그곳에서 처리한다.
- 모델이 몇 달마다 크게 변하므로 하네스 기능은 현재 실패 모드를 보완하는 임시 발판으로 보고 필요가 사라지면 제거해야 한다.
- 원격 컨테이너, loop, routine은 노트북과 대화 세션의 경계를 넘어 장시간·반복 작업을 가능하게 한다.
- 코드 리뷰는 여러 에이전트의 fan-out과 적대적 검증으로 후보를 걸러 사람을 사소한 nit이 아닌 큰 설계 문제에 집중시킨다.
- Claude는 작업에 맞는 에이전트 토폴로지와 결정론적 코드를 조합한 동적 워크플로를 직접 만들 수 있다.
- Claude Tag 팀은 Claude Tag 자체를 개발·테스트하고, Slack에서 아이디어·목업·구현·피드백·모니터링을 하나의 비동기 루프로 연결한다.
- 더 큰 자율성은 내부 과정을 덜 보는 데서 나오지 않고, E2E 테스트와 스크린샷·녹화 같은 검증 증거를 강화하는 데서 나온다.
- 엔지니어의 역할은 세부 구현을 직접 수행하는 데서 문제를 고르고 전체 방향을 설계하는 쪽으로 이동한다.
