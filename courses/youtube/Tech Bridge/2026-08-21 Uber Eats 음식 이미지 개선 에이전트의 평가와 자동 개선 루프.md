- **채널:** Tech Bridge
- **발표자·출처:** Uber Eats 엔지니어링 팀

- **정리 범위:** 전체 제공 스크립트(마지막 발화 20:44, 자동 자막 언어 `en`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 음식 사진 개선을 라우팅·편집·게시 검증으로 나누고, 사람의 평가와 실제 서비스 지표로 전체 파이프라인을 개선한다.

## 내용

### 이미지 개선의 목적과 제약 (00:00–06:37)

소규모 음식점은 좋은 사진을 만들 시간과 전문성이 부족하다. 목표는 실제 음식과 음식점의 특성을 보존하면서 사진을 개선하는 것이다. 창의성을 무제한 허용하면 메뉴와 다른 음식이 만들어지고, 고정 규칙만 쓰면 다양한 음식과 지역을 처리하기 어렵다.

파이프라인은 이미지 이해 → 개선 필요 여부 라우팅 → 이미지 편집 → 품질 검사 → 후처리와 최종 게시 검사로 구성한다. 이미 좋은 사진은 그대로 두고, 제한된 재시도 안에 기준을 통과하지 못한 사진도 원본을 유지한다. 초기부터 전체 실행을 JSON으로 기록해 엔지니어와 PM이 개별 사례와 집계를 함께 살핀다.

### 라우터 평가와 사람의 기준 (06:37–12:44)

라우터는 혼동 행렬과 정밀도·재현율로 평가한다. 지역, 음식 종류, 사진 품질을 골고루 포함한 기준 데이터와 명확한 라벨링 지침이 필요하다. 나쁜 사진을 통과시키는 오류뿐 아니라 좋은 사진을 불필요하게 편집해 비용과 변형 위험을 늘리는 오류도 본다.

운영 샘플에 사람의 평가를 붙여 에이전트와 불일치하는 사례를 찾는다. 진단기가 실패한 구성 요소를 식별하고, 최적화기가 **Reflect** 단계에서 반복 문제와 노이즈를 구분한 뒤 **Synthesize** 단계에서 설정을 수정한다. 새 설정은 기준 데이터로 재평가하고 통과했을 때 적용하며 되돌릴 수 있어야 한다. 설정 조정의 자동화에도 사람의 라벨은 평가 기반으로 남는다.

### 편집 재시도와 최종 게시 검사 (12:44–17:57)

사진 설명과 개선 방향으로 편집 프롬프트를 만들고, 음식의 충실도·색상·플레이팅을 검사한다. 실패 사유를 원본 입력과 함께 돌려주어 제한 횟수 내에서 다시 시도한다. 발표에서는 고구마튀김의 양과 접시 표현을 수정하는 예를 든다.

입력과 출력의 쌍을 비교해 더 좋아졌는지, 내용이 온전한지, 자연스러운지를 판단하며 애매하면 게시하지 않는다. 새우 추가, 소스 제거, 접시에 가려진 음식 등이 실패다. 창의적인 실패를 피하려고 모든 음식을 비슷한 그릇에 담는 방식도 실제 개선 없이 평가만 맞추는 문제가 될 수 있다. 마지막 검사층은 앞선 검사에서 빠진 품질·정책 문제를 다시 잡는다.

### 운영 피드백으로 닫는 개선 루프 (17:57–20:44)

모델 판정과 사람 라벨의 차이, 내부 사용자의 의견, 음식점·디자인 팀의 자유 서술 피드백을 모은다. 새 설정은 성공 사례와 실패 사례를 모두 재실행해 회귀를 확인한다. 게시 후에는 장바구니·주문 전환뿐 아니라 지역·기기·음식별 성과와 시장 전체의 영향을 살펴야 한다.

## 예시

영상 사례를 평가 관점으로 정리하면 다음과 같다.

| 사례 | 판단 기준 |
|---|---|
| 이미 좋은 치즈버거 사진 | 편집을 생략해 비용과 품질 저하 위험을 줄인다. |
| 제목은 8개지만 사진에는 6개인 윙 | 제목에 맞춰 음식을 임의로 늘리지 않는다. |
| 편집 후 새우가 추가되거나 소스가 사라짐 | 원본 충실도 실패로 처리한다. |
| 개선 여부가 애매하거나 재시도 한도 도달 | 게시를 강행하지 않고 원본을 유지한다. |

## 요약

- 이미지의 보기 좋은 정도와 실제 음식의 보존을 함께 평가한다.
- 이미지별 편집 재시도와 시스템 설정의 개선 루프를 구분한다.
- 사람의 기준 데이터, 회귀 평가, 실제 서비스 지표를 연결한다.
