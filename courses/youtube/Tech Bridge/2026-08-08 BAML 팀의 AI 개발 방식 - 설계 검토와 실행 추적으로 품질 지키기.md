# BAML 팀의 AI 개발 방식 - 설계 검토와 실행 추적으로 품질 지키기

- **채널:** Tech Bridge
- **발표자·출처:** Vaibhav Gupta (Boundary, BAML)

- **정리 범위:** 전체 제공 스크립트(마지막 발화 20:56, 자동 자막 언어 `de-DE`). 수치·제품 상태·전망은 영상 당시 발표자의 설명을 기준으로 한다.
- **핵심:** 생성된 코드를 모두 읽기 어려운 상황에서 설계 문서, 아키텍처 불변조건, 실행 추적과 언어 도구로 품질을 관리하는 접근을 소개한다.

## 내용

### 1. AI 도구 선택보다 오래 유지할 규칙 (0:00~2:20)

발표자는 팀이 전통적인 코드 리뷰를 하지 않고 병렬 작업과 다양한 AI 도구를 허용한다고 소개한다. 그렇다고 품질 기준이 없는 것은 아니다. 컴파일러의 계층처럼 오래 유지할 아키텍처 원칙을 작고 공통적인 문서로 제공한다. 핵심 계층의 변경에는 다른 사람과 논의하도록 한다.

### 2. 코드보다 설계 의사소통을 엄격하게 (2:23~4:20)

설계 문서의 버전 관리·댓글과 Slack 알림을 갖춘 내부 도구를 만들었다. 그러나 문서를 많이 생산하는 것만으로 품질이 생기지는 않았다. 실제로 다른 사람이 읽고 검토해야 한다는 규칙을 추가했다.

의존성 그래프와 패키지 경계를 시각화하고, 허용하지 않는 의존관계가 들어오면 CLI와 CI에서 발견하도록 한다. 공통 규칙을 단순 권고가 아니라 검사 가능한 조건으로 바꾸는 것이다.

### 3. 프로그램 생성과 실행 기록으로 문제 찾기 (4:25~6:52)

에이전트가 BAML 프로그램을 만들어 실행하게 하고 그 전체 기록을 분석한다. 언어의 오류뿐 아니라 불필요하게 많은 도구 호출을 요구하는 사용성 문제도 찾는다.

에이전트의 문제 제보를 사람이 검토해 실제 결함과 환각을 구분한 뒤 수정한다. 언어 기능의 대안은 A/B 비교로 도구 호출 수·오류·결과의 정확성을 측정한다. 발표자의 핵심은 특정 도구를 복제하라는 것이 아니라, 더 많은 코드를 생산하는 속도에 맞게 검증 체계를 바꾸라는 것이다.

### 4. 사람이 읽는 코드에서 관찰 가능한 시스템으로 (6:57~11:22)

기존 언어에 남아 있는 암묵적 동작과 타입의 한계를 비판하면서 에이전트를 고려한 새 도구의 가능성을 제시한다. 이는 발표자의 언어 설계 관점이다.

시연에서는 코드의 의미적 경계를 시각화하고 필요한 부분에서 실제 코드로 이동한다. 실행 추적은 어떤 부분이 언제 얼마나 수행됐는지 보여준다. 사람과 에이전트 모두 이 정보를 통해 오류와 비효율을 조사할 수 있도록 한다.

### 5. 에이전트가 적은 호출로 이해하는 도구 (11:26~14:40)

문자열 검색만 하는 대신 함수의 설명, 원본, 사용처를 함께 반환하는 도구를 소개한다. 외부 라이브러리 역시 실제 코드에 가까운 정보를 제공하면 탐색 단계가 줄어든다는 주장이다.

함수를 CLI 명령으로 실행하고 독립적인 실행 파일로 묶는 시연도 한다. 에이전트가 함수를 시험하기 위해 매번 별도 실행 코드를 만드는 부담을 낮추고, 타입이 있는 인터페이스를 제공하는 방향이다. 플랫폼과 성능 관련 설명은 영상의 데모 범위로 이해한다.

### 6. 오류를 타입과 컴파일러로 드러내기 (14:45~17:10)

0으로 나누기 오류가 호출 관계를 따라 상위 함수에 전파되는 예를 보여준다. 함수가 발생시킬 수 있는 오류를 추론하고, 처리되지 않은 오류를 컴파일러가 확인하도록 하는 설계다.

모든 오류를 잡아 기본값을 반환하는 시연은 오류 효과를 제거하는 예이며, 그 기본값이 업무상 올바르다는 뜻은 아니다. 컴파일러가 증명할 수 있는 타입·오류 처리 조건과 애플리케이션 전체의 정확성은 구분해야 한다.

### 7. 전체 재작성 대신 다른 언어와 연결하기 (17:16~20:56)

새 언어로 모든 코드를 바꾸라고 요구하면 새로운 문제가 생긴다. BAML 함수를 Python 등 기존 언어에서 호출하고 동기·비동기 인터페이스와 함수 전달을 지원하는 방향을 시연한다.

결론은 코드 리뷰를 무조건 없애라는 일반 규칙이 아니다. 이 팀은 설계 검토, 불변조건 검사, 생성·실행 실험, 추적, 타입 시스템 등 다른 검증 수단을 구축했다. 에이전트 중심으로 작업량이 늘어날 때 조직의 검증 과정과 기반 도구도 함께 발전해야 한다는 제안이다.

## 예시

강의에서 보여준 품질 관리 수단을 연결하면 다음과 같다.

| 확인 대상 | 사용하는 수단 |
| --- | --- |
| 무엇을 만들지 | 사람이 읽고 논의하는 설계 문서 |
| 경계를 지켰는지 | 의존성 그래프와 불변조건 검사 |
| 실제로 동작하는지 | 생성된 프로그램의 실행과 결과 검증 |
| 어디가 비효율적인지 | 도구 호출 기록과 실행 추적 |
| 오류 처리가 누락됐는지 | 오류 타입 추론과 컴파일러 검사 |

각 도구는 서로 다른 질문에 답한다. 하나만 도입한다고 모든 품질 문제가 해결되는 구조는 아니다.

## 요약

- AI 도구는 다양하게 쓰더라도 장기적으로 유지할 아키텍처 규칙은 공유한다.
- 문서 생산량보다 실제 설계 검토와 자동 검사 가능성을 중시한다.
- 실행 추적과 타입·오류 정보로 사람과 에이전트가 시스템을 이해하게 한다.
- 코드 검토 방식의 변경은 대체 검증 체계와 함께 평가해야 한다.
