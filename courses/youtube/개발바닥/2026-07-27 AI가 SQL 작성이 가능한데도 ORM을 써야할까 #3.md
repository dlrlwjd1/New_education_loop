## 내용
### Spring Data JPA, Spring Data JDBC, jOOQ 중 무엇을 선택할까
- Spring Data JPA는 Spring Boot와 함께 널리 사용되지만 학습 곡선(learning curve)이 가파르다. 매핑을 잘못 적용하면 심각한 성능 문제가 생길 수 있다.
- 도구를 충분히 학습하지 않은 채 성능 문제가 생기면 프레임워크를 탓하기 쉽다. 하지만 Spring Data JPA는 이미 오랫동안 사용된 기술이며, 숙련된 개발자는 문제없이 활용할 수 있다.
- Spring Data JPA, Spring Data JDBC, jOOQ 어느 것으로도 같은 종류의 프로젝트를 만들 수 있다. 다만 각 기술의 장단점과 한계가 다르다.
- jOOQ의 `MULTISET`이나 Blaze-Persistence 계열 기능은 JSON 집계를 활용해 카테시안 곱(Cartesian product) 없이 여러 컬렉션을 가져오는 선택지를 제공한다.
- Spring Data JDBC라고 해서 자동으로 성능이 좋아지는 것은 아니다. 컬렉션을 즉시 로딩(eager loading)하면서 의도보다 많은 데이터를 읽을 수 있으며, 실제 생성·실행되는 쿼리를 확인하지 않으면 JPA 때와 같은 문제가 반복된다.
- SQL과 데이터베이스 성능에 숙련된 팀이라면 JDBC나 jOOQ가 좋은 선택이다. 반대로 JPA를 오랫동안 올바르게 사용해 온 팀이라면 단지 유행이 바뀌었다는 이유로 교체할 필요가 없다.
- SQL 지식은 기본 문법만으로 충분하지 않다. 윈도우 함수(window function), 공통 테이블 표현식(CTE), 피벗(pivot), JSON 집계 같은 현대 SQL 기능도 이해해야 한다.
- 자료와 사용 사례가 풍부한 기술일수록 AI도 더 정확하게 도울 가능성이 높다. Spring Data JPA와 jOOQ처럼 오랜 기간 축적된 자료가 많은 기술은 AI가 참고할 맥락도 풍부하다.

### AI가 SQL을 써주는데도 ORM이 필요한 이유
- 예전에는 JDBC 코드와 결과 처리 로직을 모두 사람이 직접 작성해야 했기 때문에 생산성과 편의성을 높이는 추상화가 필요했다. JPA, Hibernate, Spring은 이 문제를 해결해 왔다.
- 현재는 SQL에 익숙한 개발자가 가벼운 구성을 원한다면 **AI와 JDBC의 조합**도 충분히 좋은 선택이 될 수 있다.
- 그러나 Hibernate와 JPA는 단순한 객체-관계 매핑 도구가 아니다. 오랜 기간 검증된 엔터프라이즈 애플리케이션 패턴의 집합으로 볼 수 있다.
- 인터뷰에서 언급한 대표 기능은 다음과 같다.
  - 낙관적 잠금(optimistic locking)
  - 일관된 방식으로 표현하는 비관적 잠금(pessimistic locking)
  - 자동 배치 처리(batching)
  - 데이터베이스 위에 구현하는 상속 매핑(inheritance mapping)
  - 1차 캐시(first-level cache)
  - 카테시안 곱을 피하기 위한 점진적 컬렉션 로딩
- 이런 기능이 필요 없다면 AI의 도움을 받아 순수 JDBC를 사용해도 된다. 반대로 20년 가까이 구현되고 실전 검증된 패턴이 가치 있다고 판단한다면 Spring Data JPA와 리포지터리(repository), 쿼리 메서드(query method)를 계속 사용할 이유가 있다.
- 결론은 “ORM인가 SQL인가”의 절대적인 승부가 아니다. 필요한 추상화와 팀이 안전하게 다룰 수 있는 도구를 선택하는 문제다.

### Vlad Mihalcea의 실제 AI 활용 방식
- 모든 프로젝트에서 AI를 쓰지는 않는다.
  - 핵심 상용 프로젝트인 Hypersistence Optimizer는 세부 구현을 직접 기억하고 통제하기 위해 AI 없이 개발한다.
  - 유지 변경이 많지 않은 오픈 소스 Hypersistence Utils에도 AI를 쓰지 않는다.
  - 발표용 데모 프로젝트는 빠르게 초안을 만들기 위해 AI를 사용하지만, 이후 직접 검토하고 수정하며 내용을 전부 이해한다.
- 개발 외에도 대량의 정보 집계, 계획과 요약 작성, 정보의 빈틈 찾기에 AI를 활용한다.
- 박사 과정 문서를 만들 때는 Claude Code의 CLI 모드로 LaTeX 문법, 참고문헌 추가, PDF 생성 작업을 보조한다.
- 소프트웨어 개발은 본질적으로 지식 노동(knowledge work)이다. 고객이 원하는 것이 무엇인지, 기능을 지금 구현할 가치가 있는지, 어떻게 안전하게 만들지 판단하고 여러 사람과 합의하는 시간이 더 크다.
- 인터뷰에서 구현 자체는 전체 업무의 약 10~15%라는 관점을 제시한다. AI는 이 구간을 최적화하지만 문제 정의와 가치 판단까지 자동으로 대신하지는 않는다.

### AI 시대에도 Java가 유지되는 이유
- JavaScript와 TypeScript 생태계도 크게 발전했다. 과거 JavaScript로 3차원 센서 히트맵과 FFT(Fast Fourier Transform) 기반 확대 기능까지 구현했던 경험을 예로 들며, JavaScript로도 많은 일을 할 수 있다고 설명한다.
- Java의 강점은 문법 자체보다 JVM과 생태계에 있다.
- 엔터프라이즈 분야에는 오랫동안 실전 검증된 프레임워크, JDBC 드라이버, ORM, 의존성 주입, 통합 테스트와 성능 테스트 방식이 축적돼 있다.
- 고빈도 거래(High-Frequency Trading)처럼 마이크로초 단위 성능이 중요한 분야에서도 Java를 사용하는 회사가 있다. 오프힙(off-heap) 처리 등 전문 도구를 이용해 성능을 확보하면서 C/C++의 포인터 관리 부담을 줄일 수 있기 때문이다.
- 기존 엔터프라이즈 시스템을 JavaScript로 전면 교체해도 명확한 비즈니스 이익이 없다면 바꿀 이유가 없다. Java는 계속 진화하고 있으며 엔터프라이즈 시스템에서 여전히 자리가 있다.

### 제품 단계에 따라 달라지는 AI 도입 범위
- 프로토타입 단계에서는 빠른 출시가 중요하고 코드 규모도 작으므로 AI와 에이전트를 더 적극적으로 활용할 수 있다. 필요하면 모듈을 다시 작성하는 비용도 비교적 낮다.
- 은행이나 보험사처럼 수십 년 운영된 시스템은 신규 기능 개발보다 유지보수와 회귀 방지가 중요하다. 이때는 개발 속도보다 충분한 테스트와 검증에 더 큰 비중을 둬야 한다.
- AI가 구현과 테스트를 모두 작성하게 한 뒤, 같은 AI가 자신의 오류를 잡을 것이라고 전적으로 믿기는 어렵다. 다른 모델을 사용해도 놓치는 문제가 있다.
- AI가 코드베이스를 읽더라도 이메일, Slack, Teams, Confluence, 구두 대화에 남은 결정과 선호까지 모두 알지는 못한다. 조직에 존재하는 암묵지(tacit knowledge)가 빠질 수 있다.
- 특히 오래 운영된 프로젝트에서는 사람이 중요한 테스트를 직접 작성하거나, 최소한 어떤 동작을 반드시 보장할지 명확히 정의해야 한다.
- AI 기업의 과장된 생산성 주장도 이해관계를 고려해 받아들여야 한다. AI 도입은 작은 단계로 진행하고 실제 결과를 검증하는 편이 안전하다.
- 생산성보다 먼저 지켜야 할 것은 고객의 신뢰다. 은행·결제처럼 안전이 중요한 서비스에서 검증되지 않은 자동화가 심각한 버그를 만들면 고객은 자금과 개인정보가 안전한지 의심하게 된다.

### 앞으로의 계획과 교육의 가치
- 지난 12년간의 작업을 과학 논문으로 정리하고 박사 과정을 마치는 것이 향후 약 2년의 주요 목표다.
- 사람이 AI의 답을 검증하려면 먼저 옳고 그름을 판단할 지식이 있어야 하므로, 기업 교육과 강좌는 계속 가치가 있다고 본다.
- 미뤄 온 책의 2판도 계획하고 있다. 독자가 비용을 내는 책은 AI가 생성한 문장이 아니라 저자가 직접 책임지고 쓴 내용이어야 한다는 입장이다.
- 한국어로 번역된 강좌가 약 1년 동안 1,500개 가까이 판매된 사례와 학습자 피드백을 언급하며, 한국 개발자 커뮤니티의 학습 의지를 높게 평가한다.
- 모든 학습자가 영어를 익히기를 기다리는 것보다 양질의 콘텐츠를 한국어·일본어·중국어·베트남어 등으로 번역해 제공하는 편이 효과적이라고 본다.

## 요약
- AI가 SQL과 JDBC 코드를 작성해 주므로 순수 JDBC의 생산성 장벽은 낮아졌다. 하지만 이것만으로 ORM의 가치가 사라지지는 않는다.
- Hibernate와 JPA는 매핑뿐 아니라 잠금, 배치, 상속, 캐시 등 오랫동안 검증된 엔터프라이즈 패턴을 제공한다.
- Spring Data JDBC도 잘못 사용하면 과다 조회와 성능 문제가 생긴다. 프레임워크 이름보다 실제 쿼리와 로딩 동작을 확인하는 습관이 중요하다.
- 기술 선택은 유행이 아니라 팀의 SQL 역량, 기존 숙련도, 필요한 기능, 제품의 수명 주기와 위험 수준에 따라 결정해야 한다.
- AI는 데모 작성, 정보 집계, 문서 작업처럼 유용한 영역에서 생산성을 높이지만, 문제 정의·가치 판단·암묵지·최종 검증은 여전히 사람의 몫이다.
- 프로토타입에서는 AI를 적극적으로 쓸 수 있지만, 장기 운영·고위험 시스템에서는 사람이 핵심 테스트와 고객 신뢰를 책임져야 한다.
- AI의 결과를 검증하려면 기본 지식이 필요하므로 SQL, 데이터베이스, Java 생태계에 대한 교육의 가치는 계속 유지된다.
