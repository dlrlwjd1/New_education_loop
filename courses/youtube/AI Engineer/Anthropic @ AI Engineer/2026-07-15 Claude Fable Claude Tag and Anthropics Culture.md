## 내용
### 구현보다 제품 판단으로 이동
코딩 에이전트가 저수준 구현을 더 많이 맡으면서 개발자는 모든 줄을 직접 작성하기보다 문제 선택, 요구 사항, 결과 검토와 제품 감각(product sense)에 더 많은 시간을 쓰게 된다.

구현 비용이 낮아지면 과거의 규칙도 다시 검토할 수 있다. 대규모 재작성은 전통적으로 위험했지만 좋은 테스트가 있고 빠르게 실험할 수 있다면 점진 수정만이 유일한 답은 아니다. 장기 워터폴 계획보다 프로토타입과 피드백의 가치가 커진다.

### 개인 도구에서 팀 에이전트로
Claude Tag는 Slack 같은 협업 공간에서 버그를 관찰하고, PR 초안을 만들고, 팀의 과거 맥락을 유지하는 사전 대응형 에이전트로 소개된다. 발표 시점에는 Anthropic 내부 제품 PR의 65% 이상에 관여하는 사례가 언급된다.

이 흐름은 에이전트를 개인 개발자의 터미널 도구에서 여러 사람이 공유하는 “멀티플레이어” 작업자로 바꾼다. 원격 제어, 팀 메모리, 리뷰 자동화가 중요해지는 이유다.

### 모델이 강해질수록 하니스도 단순해질 수 있다
새 모델에 대한 신뢰는 벤치마크만으로 생기지 않는다. 팀은 실제 업무에 모델을 사용하고 결과를 비교하면서 어떤 감독이 필요한지 학습한다. 더 강한 모델에서는 과거 모델을 위해 작성한 긴 시스템 프롬프트와 예제가 오히려 가능성을 제한할 수 있어 프롬프트를 줄이는 방향도 논의된다.

도구는 모델 행동을 세세하게 규정하기보다 목표를 달성할 수 있는 명확한 기능과 피드백을 제공해야 한다.

### Auto Mode와 안전
장기 실행 에이전트가 파일·네트워크·자격 증명에 접근하면 프롬프트 인젝션과 데이터 유출 위험이 커진다. Auto Mode는 무조건적인 권한 허용이 아니라 평가(evals), 레드팀, 권한 경계에 투자한 실행 방식으로 설명된다.

편리함을 위해 수동 승인만 제거하는 것이 아니라, 에이전트가 처리하는 외부 콘텐츠와 실행 가능한 행동 사이에 보안 설계가 필요하다.

### 더 야심찬 문제 선택
구현 비용이 낮아졌는데도 과거의 인력·시간 가정을 그대로 적용하면 스스로 가능성을 축소하게 된다. 발표자들은 “할 수 없는 이유”를 먼저 협상하기보다 프로토타입을 만들고 실제 한계를 확인하라고 권한다.

## 예시
```text
기존 팀 흐름:
아이디어 → 긴 계획 → 수동 구현 → 늦은 사용자 검증

에이전트 활용 흐름:
아이디어 → 여러 프로토타입 → 테스트·사용자 반응
       → 제품 판단 → 에이전트 구현·수정 → 지속 리뷰
```

## 요약
- 코딩 에이전트는 개발자의 중심 업무를 코드 입력에서 제품 판단과 결과 관리로 이동시킨다.
- 팀 공간에서 능동적으로 일하는 에이전트에는 공유 맥락, 리뷰, 원격 제어가 필요하다.
- 모델이 강해지면 과도한 시스템 프롬프트를 줄이고 도구와 검증에 집중할 수 있다.
- 장기 자율 실행은 평가·레드팀·권한 경계를 갖춘 안전 설계가 전제되어야 한다.
