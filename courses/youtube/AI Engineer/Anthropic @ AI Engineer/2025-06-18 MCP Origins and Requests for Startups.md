# MCP: Origins and Requests for Startups

## 개요
- 업로드일: 2025-06-18
- 원본: https://www.youtube.com/watch?v=x-8pBqWiTzk
- 재생목록: Anthropic @ AI Engineer
- 발표자: Theodora Chu, Anthropic
- 핵심 주제: Model Context Protocol(MCP)이 등장한 배경, 모델의 자율적 도구 사용, 생태계 업데이트와 스타트업 기회

## 내용
### 통합 문제에서 시작한 MCP
AI 애플리케이션이 파일, 데이터베이스, SaaS와 연결될 때마다 서비스별 커넥터를 별도로 만들면 클라이언트와 데이터 소스의 조합만큼 통합이 늘어난다. MCP는 AI 애플리케이션과 외부 기능 사이에 공통 경계를 제공해 이 M×N 연결 문제를 줄이려는 시도다.

발표자는 도구 호출 능력이 좋아지면서 단순히 “모델에 컨텍스트를 넣는 법”을 넘어 **모델 에이전시(model agency)**가 중요해졌다고 설명한다. 어떤 기능을 발견하고, 언제 호출하며, 결과를 이용해 다음 행동을 선택할지까지 프로토콜과 제품이 지원해야 한다.

### 프로토콜과 제품의 역할
MCP는 연결 형식을 표준화하지만 좋은 에이전트 경험을 자동으로 만들지는 않는다.

- 서버는 목적이 분명한 도구와 이해하기 쉬운 설명을 제공해야 한다.
- 클라이언트는 관련 서버와 도구를 발견하고 권한을 관리해야 한다.
- 사용자는 어떤 데이터와 행동을 허용했는지 볼 수 있어야 한다.
- 개발자는 실제 사용자 프롬프트에서 도구 선택이 잘 되는지 평가해야 한다.

발표 시점의 프로젝트 업데이트로 원격 연결, 인증, 레지스트리 API 방향 등이 언급된다. 레지스트리는 사용 가능한 서버를 찾기 쉽게 만들어 도구 생태계의 발견 문제를 줄이는 역할을 한다.

### 무엇을 만들 것인가
스타트업에는 단순히 기존 API를 MCP로 감싸는 것 이상의 기회가 있다.

- 신뢰할 수 있는 MCP 서버 탐색과 배포
- 인증·권한·감사 인프라
- 서버와 도구의 품질 평가
- 조직 내부 데이터에 맞는 관리형 연결
- MCP를 이용해 처음부터 설계한 에이전트 네이티브 업무 제품

중요한 출발점은 “MCP 서버를 만들 수 있는가?”가 아니라 “최종 사용자가 어떤 프롬프트로 어떤 결과를 원하며, 모델이 그 과정에서 어떤 행동을 해야 하는가?”다.

## 예시
```text
사용자 프롬프트:
지난 분기 고객 이탈 원인을 찾아 후속 작업을 만들어 줘.

필요한 제품 설계:
데이터 서버 발견 → 읽기 권한 확인 → 분석 도구 선택
→ 결과 검증 → 작업 생성 전 쓰기 승인 → 감사 기록
```

API를 노출하는 것만으로는 이 전체 경험이 완성되지 않는다.

## 요약
- MCP는 AI 클라이언트와 데이터·도구 사이의 반복 통합을 공통 프로토콜로 줄인다.
- 모델의 도구 선택과 행동이 늘면서 컨텍스트 연결뿐 아니라 에이전시 설계가 중요해졌다.
- 레지스트리, 인증, 권한, 평가와 운영 도구는 별도의 제품 기회를 만든다.
- 서버 기능보다 최종 사용자의 프롬프트와 완료할 업무에서 역으로 설계해야 한다.
