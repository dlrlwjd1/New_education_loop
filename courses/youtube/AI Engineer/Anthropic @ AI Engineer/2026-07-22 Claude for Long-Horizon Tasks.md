# Claude for Long-Horizon Tasks

## 개요
- 업로드일: 2026-07-22
- 원본: https://www.youtube.com/watch?v=9QebvrrY3KY
- 재생목록: Anthropic @ AI Engineer
- 발표자: Lance Martin, Anthropic
- 핵심 주제: 장기 실행 작업을 신뢰성·보안·학습 가능성까지 고려해 수행하는 에이전트 하니스(agent harness) 설계

## 내용
### 장기 작업은 모델 호출보다 시스템 문제다
단일 프롬프트와 응답은 짧은 작업에는 충분하지만, 오랜 시간 여러 행동을 수행하는 에이전트는 실패 복구, 상태 관리, 권한, 결과 검증이 필요하다. 모델 능력만 높이는 것으로는 긴 작업의 누적 오류를 막을 수 없다.

발표는 장기 작업용 하니스를 네 가지 원칙으로 정리한다.

### 두뇌와 손을 분리하기
모델의 추론을 담당하는 **두뇌(brain)**와 실제 시스템에서 행동하는 **손(hands)**을 분리한다. 하니스와 실행 도구는 격리된 샌드박스 또는 컨테이너 안에 놓고, 필요한 자격 증명과 네트워크 접근만 제한적으로 제공한다.

이 분리는 모델을 교체하거나 하니스를 개선하기 쉽게 만들고, 예상하지 못한 명령의 피해 범위를 줄인다. 장기 작업일수록 권한을 한 번에 넓게 주기보다 작업 단계별로 명시해야 한다.

### 별도의 검증 루프
작업을 수행한 빌드 에이전트가 스스로 “완료했다”고 말하는 것으로 끝내지 않는다. 목표나 루브릭(rubric)을 가진 검증자가 산출물을 독립적으로 검사한다.

```text
빌드 에이전트 → 결과 생성
검증 에이전트 → 테스트·루브릭으로 확인
실패 피드백   → 빌드 에이전트가 수정
```

생성과 평가를 분리하면 같은 추론의 맹점을 반복할 가능성을 줄일 수 있다. 가능한 경우 테스트 실행, 파일 확인, 외부 상태 조회처럼 객관적인 증거를 사용한다.

### 경험에서 학습하기
긴 작업의 성공·실패 사례를 버리지 않고 다음 실행에 활용한다. 사람의 기억처럼 특정 사건의 경험과 반복 가능한 절차를 구분해 저장하고, 잘 작동한 전략을 재사용 가능한 지침이나 도구로 승격한다.

중요한 점은 대화 전체를 무작정 누적하는 것이 아니라 다음 작업에 유용한 교훈을 선택해 압축하는 것이다.

### 변하는 하니스를 전제로 설계하기
모델과 도구 능력은 빠르게 바뀐다. 현재 모델의 약점을 보완하려고 만든 복잡한 규칙이 다음 모델에는 불필요한 제약이 될 수 있다. 따라서 모델, 도구, 정책, 메모리, 검증기를 분리해 각각 교체·평가할 수 있어야 한다.

## 예시
대규모 코드 마이그레이션 에이전트라면 다음처럼 구성할 수 있다.

1. 읽기 전용 탐색 단계에서 변경 범위와 테스트를 파악한다.
2. 격리된 작업 공간에서 파일을 수정한다.
3. 별도 검증자가 테스트와 변경 요구 사항을 검사한다.
4. 실패 원인을 작업 에이전트에 돌려보낸다.
5. 반복적으로 유용했던 해결 절차만 재사용 지식으로 저장한다.

## 요약
- 장기 작업의 신뢰성은 모델 하나보다 하니스의 상태·권한·검증 구조에 달려 있다.
- 추론과 실행을 분리하고 손에 해당하는 도구를 샌드박스 안에 둔다.
- 생성 에이전트와 독립된 검증 루프가 완료 주장을 실제 증거로 확인해야 한다.
- 경험을 압축해 재사용하되 모델 변화에 맞춰 하니스 구성 요소를 교체할 수 있어야 한다.
