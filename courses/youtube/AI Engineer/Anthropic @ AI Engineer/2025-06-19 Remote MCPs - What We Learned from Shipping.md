## 내용
### 로컬 연결에서 원격 서비스로
초기 MCP 서버는 로컬 프로세스와 표준 입출력으로 연결하기 쉬웠다. 원격 MCP는 여러 사용자와 조직이 네트워크를 통해 서비스에 접근하므로 인증, 연결 수명, 장애 처리, 확장성 문제가 추가된다.

프로토콜이 도구의 의미와 호출 형식을 표준화해도 원격 운영에 필요한 전송 계층과 보안이 자동으로 해결되는 것은 아니다.

### 공통 전송 표준
발표는 원격 상호운용성을 위해 Streamable HTTP와 OAuth 2.1 같은 표준을 사용하는 방향을 설명한다. 클라이언트와 서버가 자체 전송 방식을 각각 만들면 생태계가 다시 파편화된다.

원격 클라이언트는 다음을 처리해야 한다.

- 서버 기능과 도구 목록 탐색
- 스트리밍 응답과 연결 중단
- 재시도와 타임아웃
- 사용자별 인증과 토큰 갱신
- 오류를 모델과 사용자에게 구분해 전달

### 인증은 사용자와 서버의 관계다
MCP 클라이언트가 모든 외부 서비스의 자격 증명을 대신 보관하는 구조는 확장하기 어렵다. 사용자는 원격 MCP 서버의 인증 흐름을 거쳐 권한을 부여하고, 서버는 자신의 리소스 접근 정책을 적용해야 한다.

어떤 도구를 호출할 수 있다는 프로토콜 수준의 능력과 특정 사용자가 해당 데이터에 접근할 수 있다는 애플리케이션 권한을 구분해야 한다.

### 내부 전송과 공개 표준의 경계
대규모 제품 내부에는 기존 프록시, 서비스 메시, RPC와 관측 인프라가 있다. 공개 MCP 인터페이스를 유지하면서 내부에서는 맞춤 전송 어댑터를 사용할 수 있다. 중요한 것은 외부 서버 작성자가 Anthropic의 내부 구조를 알 필요가 없도록 경계를 유지하는 것이다.

### 서버 개발자 경험
원격 MCP가 확산되려면 샘플, 오류 메시지, 인증 가이드, 테스트 도구가 필요하다. 프로토콜 명세만으로는 운영 가능한 서버를 만들기 어렵기 때문에 실제 배포에서 발견한 실패 모드를 문서와 SDK에 반영해야 한다.

## 예시
```text
Claude 클라이언트
  → 원격 MCP 서버의 인증 시작
  → 사용자가 서버에 권한 부여
  → 제한된 액세스 토큰 발급
  → Streamable HTTP로 도구 호출
  → 서버가 사용자 권한을 확인하고 결과 반환
```

## 요약
- 원격 MCP는 로컬 도구 연결에 인증·네트워크 장애·확장성 문제를 더한다.
- Streamable HTTP와 OAuth 2.1 같은 공통 표준이 클라이언트·서버 파편화를 줄인다.
- 도구 발견과 실제 데이터 접근 권한은 서로 다른 층에서 검증해야 한다.
- 공개 프로토콜 경계와 내부 전송 구현을 분리하면 기존 인프라를 사용하면서 상호운용성을 유지할 수 있다.
