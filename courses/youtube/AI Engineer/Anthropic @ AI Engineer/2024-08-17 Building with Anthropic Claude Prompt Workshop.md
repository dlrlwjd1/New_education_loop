## 개요
- 업로드일: 2024-08-17
- 원본: https://www.youtube.com/watch?v=hkhDdcM5V94
- 재생목록: Anthropic @ AI Engineer

- 형식: 약 1시간 35분의 라이브 프롬프트 개선 워크숍
- 핵심 주제: 실패 사례를 직접 테스트하며 역할·맥락·예시·XML 태그·프리필(prefill)·단계적 추론을 조정하는 프롬프트 개발법

## 내용
### 프롬프트는 예시로 디버깅한다
좋지 않은 프롬프트를 문장만 보고 고치기보다 실패한 구체적 입력과 기대 출력을 함께 준비한다. 워크숍은 실제 프롬프트를 실행하고 결과를 관찰한 뒤 한 요소씩 수정하는 방식으로 진행된다.

```text
프롬프트 초안 → 대표·실패 사례 실행 → 오류 분류
→ 한 가지 변경 → 재실행 → 개선 여부 확인
```

모델이 틀렸다는 사실보다 어떤 요구를 오해했는지, 입력 경계를 놓쳤는지, 출력 형식을 지키지 않았는지를 분리해야 한다.

### 맥락과 지시를 구조화하기
긴 문서와 사용자 입력, 작업 지시가 섞이면 경계가 모호해진다. XML 태그처럼 명시적인 구획을 사용하면 각 텍스트의 역할을 구분할 수 있다.

```xml
<instructions>수행할 작업</instructions>
<document>분석할 원문</document>
<output_format>원하는 결과 구조</output_format>
```

역할 부여는 장식적인 인물이 아니라 판단 기준과 전문 관점을 명확히 할 때 유용하다. 작업의 목적, 독자, 성공 조건을 구체적으로 제공한다.

### 예시와 출력 형식
몇 개의 좋은 입출력 예시는 규칙을 장황하게 설명하는 것보다 원하는 패턴을 명확히 보여줄 수 있다. 다만 예시는 실제 분포와 경계 사례를 대표해야 하며 모델이 예시 내용만 모방하지 않는지 확인해야 한다.

Assistant 응답의 시작을 미리 채우는 프리필은 JSON, 분류 라벨, 특정 형식으로 출력을 유도하는 데 사용된다.

### 생각을 나누고 검증하기
복잡한 문서 분석에서는 모델이 근거를 먼저 찾고 중간 결과를 작성한 뒤 최종 답을 만들게 할 수 있다. 이는 최종 출력 전에 필요한 정보를 빠뜨렸는지 확인하는 가벼운 단계적 추론 구조다.

모든 작업에 긴 사고 단계를 강요하기보다 오류가 발생하는 복잡한 부분에만 적용한다.

### 평가 세트로 전환하기
라이브로 고친 사례는 일회성 데모로 끝내지 않고 회귀 평가 세트에 추가해야 한다. 새 프롬프트가 기존 사례를 고치면서 다른 입력을 망치지 않는지 반복 확인한다.

## 예시
문서 요약 프롬프트가 문서 밖의 정보를 섞는다면 다음처럼 바꿀 수 있다.

```xml
<instructions>
오직 document 안의 근거만 사용하라.
답변 전에 관련 문장을 추출하고, 근거가 없으면 모른다고 답하라.
</instructions>
<document>{{DOCUMENT}}</document>
```

## 요약
- 프롬프트 개선은 구체적인 실패 입력과 기대 출력을 이용한 반복 실험이다.
- XML 태그는 지시, 데이터, 출력 형식의 경계를 분명하게 한다.
- 역할·예시·프리필·단계적 추론은 명확한 실패 원인에 맞춰 선택한다.
- 고친 실패 사례를 평가 세트에 넣어 프롬프트 변경의 회귀를 확인해야 한다.
