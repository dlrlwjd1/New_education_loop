## 내용
### 성능보다 이해 가능한 동시성
실습에서 고루틴을 쓰는 주된 이유는 여러 코어의 성능보다 서로 독립적인 활동을 자연스럽게 표현하기 위해서다. 미세 잠금보다 큰 임계 구역을 하나의 뮤텍스로 보호하는 단순한 설계가 정확성 검증에 유리하다.

### 주요 패턴
- 클로저가 반복 변수나 공유 변수를 캡처할 때 어느 값을 보는지 명확히 한다.
- 공유 상태는 항상 같은 뮤텍스로 보호하고 잠금 규칙을 문서화한다.
- 조건을 기다릴 때는 깨어난 뒤 조건을 다시 검사한다.
- 채널은 이벤트와 소유권 전달에 유용하지만, 버퍼 크기와 송수신자의 종료 관계를 고려한다.
- 타이머와 주기 작업은 오래된 이벤트가 새 상태에 적용되지 않게 세대나 term을 함께 확인한다.
- RPC 응답을 기다리는 동안 상태가 바뀔 수 있으므로, 응답 처리 시 현재 term과 역할을 다시 검증한다.

### Raft 구현에서 흔한 문제
여러 RPC를 병렬로 보내고 나중에 응답을 적용할 때는 응답이 생성된 시점과 현재 상태가 다를 수 있다. 잠금을 잡은 채 RPC를 기다리지 말고, 필요한 인자를 복사한 뒤 잠금을 풀어 전송하고 돌아와 상태를 재검사한다.

### 디버깅
`go test -race`로 데이터 경쟁을 찾고, 무작위 타이밍 때문에 간헐적으로 실패하는 테스트는 반복 실행한다. 로그에는 서버·term·역할·로그 인덱스를 넣어 사건의 인과 순서를 재구성한다. 실패를 고치기 전에 최소 재현 조건을 찾아야 한다.

## 예시
```go
rf.mu.Lock()
term := rf.currentTerm
args := makeArgsLocked()
rf.mu.Unlock()

reply := sendRPC(args)

rf.mu.Lock()
defer rf.mu.Unlock()
if rf.currentTerm != term { return } // 오래된 응답 무시
applyReplyLocked(reply)
```

## 요약
- 동시성 코드는 영리함보다 단순하고 추론 가능한 구조가 중요하다.
- 잠금 밖에서 RPC를 실행하고, 응답을 적용하기 전에 상태가 여전히 유효한지 확인한다.
- 채널·조건 변수·타이머에는 명확한 소유권과 종료 규칙이 필요하다.
- race detector, 반복 테스트, 구조화된 이벤트 로그가 Raft 디버깅의 핵심 도구다.
