## 내용
### 왜 Go를 사용하는가
Go는 고루틴(goroutine), 뮤텍스와 채널, 편리한 RPC 패키지, 타입·메모리 안전성, 가비지 컬렉션을 제공한다. 특히 여러 스레드가 공유 객체를 쓰는 프로그램에서 수명 관리를 자동화해 분산 시스템 실습의 본질에 집중하게 한다.

### 스레드와 공유 상태
스레드는 I/O를 기다리는 동안 다른 작업을 진행하고, 여러 독립 활동을 자연스럽게 표현한다. 그러나 공유 데이터를 동시에 읽고 쓰면 경쟁 상태(race)가 발생한다.

- 뮤텍스(mutex)는 공유 상태의 불변식(invariant)을 보호한다.
- 조건 변수(condition variable)나 채널(channel)은 사건을 기다리고 알리는 데 사용한다.
- 잠금을 잡은 채 오래 걸리는 RPC를 호출하면 병렬성이 떨어지고 교착 상태(deadlock) 위험이 커진다.
- 종료 조건과 고루틴의 생명주기를 명확히 하지 않으면 고루틴 누수(leak)가 생긴다.

### RPC의 환상과 현실
RPC는 원격 함수를 로컬 함수처럼 호출하게 하지만 네트워크에서는 요청이나 응답이 유실될 수 있다. 응답이 없을 때 호출자는 서버가 요청을 실행하지 않았는지, 실행 후 응답만 잃었는지 구분할 수 없다.

재시도만 하면 같은 요청이 두 번 실행될 수 있다. 클라이언트 식별자와 요청 번호를 기록해 중복을 제거하면 적어도 한 번(at-least-once) 실행을 한 번처럼 보이게 만들 수 있지만, 서버 재시작 시 기록을 어떻게 보존할지도 해결해야 한다.

## 예시
```go
mu.Lock()
value := state[key]
mu.Unlock()

// 네트워크 호출은 가능하면 잠금 밖에서 수행한다.
reply := callRemote(value)
```

## 요약
- Go의 고루틴과 가비지 컬렉션은 동시성 중심의 분산 프로그래밍에 적합하다.
- 공유 상태는 명확한 잠금 규칙으로 보호하고, 잠금 범위와 고루틴 종료를 단순하게 유지해야 한다.
- RPC 실패는 함수 실패와 다르다. 응답 부재만으로 실행 여부를 알 수 없다.
- 재시도에는 요청 식별자와 중복 억제 같은 호출 의미 설계가 필요하다.
