# The agent evaluation revolution

## 개요
- 업로드일: 2025-12-03
- 채널: Google Cloud Tech
- 재생목록: AI agent crash course (agent evaluation 시리즈 1편, 총 2편 중 첫 번째)
- AI 에이전트를 평가(evaluate)하는 새 시리즈의 첫 편. 왜 기존 소프트웨어 테스트 방식이 에이전트에는 통하지 않는지, 에이전트 평가가 실제로 무엇을 의미하는지, 그리고 무엇을 측정해야 하는지를 다룬다.

## 내용

### 왜 에이전트 평가는 다른가
- 전통적인 소프트웨어는 결정적(deterministic)이다. 같은 입력이면 거의 항상 같은 출력이 나오기 때문에 단위 테스트(unit test)와 통합 테스트(integration test)가 명확한 통과/실패 규칙과 예측 가능한 동작으로 잘 작동한다.
- 반면 AI 에이전트는 확률적(probabilistic)이고 자율적(autonomous)이다. 계획하고(plan), 적응하고(adapt), 도구를 사용하며, 매 실행마다 다른 유효한 결정을 내릴 수 있다. 같은 프롬프트라도 두 번의 실행이 완전히 다른 경로를 취할 수 있다.
- 에이전트는 여러 방식으로 기대에 미치지 못할 수 있다: 잘못된 도구를 선택하거나, 중요한 맥락을 잃어버리거나, 타임아웃이 나거나 등. 최종 답변이 X와 같은지만 확인하면, 그 사이에 일어난 모든 일을 놓칠 수 있다.
- 따라서 에이전트 평가는 계획이 어떻게 세워졌는지, 도구가 어떻게 쓰였는지, 정보가 어떻게 전달되었는지, 사용자가 실제로 필요한 것을 얻었는지까지 **전체 여정(journey)**을 살펴봐야 한다.

### 에이전트 평가가 실제로 의미하는 것
- 에이전트 평가는 모델 하나만 테스트하는 것이 아니다. LLM 두뇌, 이를 이끄는 프롬프트, 외부 도구·API, 정보를 이어가는 메모리 시스템, 이 모든 것을 묶는 오케스트레이션 로직까지 **전체 스택**을 포함한다.
- 즉 "이 전체 시스템(계획, 도구 사용, 메모리, 추론 포함)이 목표를 신뢰성 있게 달성했는가?"를 묻는 **시스템 레벨 테스트(system-level testing)**이며, 단순히 문자열 하나를 확인하는 것이 아니다.

### 시스템 레벨 테스트를 위한 전체 체크리스트
1. **최종 출력(final output)**: 실제로 작업을 완료했는가? 작업 성공률(task success rate), 단계별 진행(stepwise progress), 출력 품질(일관성·정확성·명료성), 안전성(편향, 프롬프트 인젝션 방어 등)을 확인.
2. **계획과 추론(planning and reasoning)**: 모델이 어떻게 생각했는가? 복잡한 목표를 논리적으로 분해했는가, 각 단계를 합리적으로 정당화했는가, 긴 멀티턴 작업 동안 일관성을 유지했는가.
3. **도구 사용(tool use)**: 도구를 효과적으로 쓸 수 있는가? 올바른 도구를 선택하고 정확한 매개변수를 전달하며 출력을 잘 처리하는가, 불필요한 비용을 피하고 지연 시간·비용을 합리적으로 유지하는가.
4. **메모리와 맥락(memory and context)**: 정말 중요한 것을 기억하는가? 과거 정보를 정확히 회수(retrieve)하고, 장거리 맥락과 충돌을 처리하는가. 예를 들어 RAG(검색 증강 생성)에서는 맥락적 정밀도(precision)와 재현율(recall)을 확인해야 한다.
- 나쁜 답변은 도구 문제, 추론의 공백, 메모리 실패 중 어디서든 비롯될 수 있으므로, 디버깅을 위해 각 계층을 개별적으로 측정하는 것이 매우 중요하다.

### 멀티 에이전트 평가의 예시
- 고객 서비스 시나리오: 에이전트 A(고객 응대 최전선)와 에이전트 B(환불·교환 처리) 두 에이전트.
- 사용자가 "지난주에 산 스마트 지역이 안 켜져서 환불이나 교환을 받고 싶다"고 말하면, 에이전트 A가 사용자를 응대하고 구매 이력을 확인·주문을 확인한 뒤(환불은 직접 처리할 수 없으므로) 세부 정보를 에이전트 B에게 넘긴다. 에이전트 B는 자신의 도구로 환불을 처리한다.
- **함정**: 에이전트 A만 따로 환불 성공 여부로 테스트하면 0% 성공률처럼 보일 수 있다. 하지만 실제로는 에이전트 A의 임무가 정보를 넘기는 것이었지 환불 자체가 아니었으므로 A는 성공한 것이다.
- 반대로, 에이전트 A가 잘못된 주문 ID를 에이전트 B에게 넘기면, 에이전트 B가 환불 자체는 성공적으로 처리하더라도 **전체 시스템은 실패**한다. 원인은 A가 잘못된 정보를 넘긴 데 있다.
- 이것이 멀티 에이전트 평가가 어려운 이유다. 전체 네트워크가 목표를 달성했는지, 공유된 맥락이 안전하게 전달되었는지, 비용·지연 측면에서 시스템 전체가 효율적인지를 함께 봐야 한다.

## 예시
이 영상은 개념·이론 중심으로, 구체적인 코드 데모는 다음 편([How to evaluate agents in practice](2025-12-12%20How%20to%20evaluate%20agents%20in%20practice.md))에서 다룬다. 이번 편의 핵심은 아래 체크리스트를 기억해두는 것이다.

| 평가 계층 | 확인할 것 |
| --- | --- |
| 최종 출력 | 작업 성공률, 진행 상황, 품질, 안전성 |
| 계획·추론 | 목표 분해 논리, 단계별 타당성, 일관성 |
| 도구 사용 | 도구 선택 정확도, 매개변수 정확성, 비용·지연 |
| 메모리·맥락 | 정보 회수 정확도, 장거리 맥락 처리, RAG 정밀도·재현율 |

## 요약
- 전통적 테스트는 결정적 소프트웨어에 맞춰져 있지만, 에이전트는 확률적이고 자율적이어서 최종 답변 하나만 보는 방식으로는 부족하다.
- 에이전트 평가는 LLM·프롬프트·도구·메모리·오케스트레이션을 아우르는 **시스템 레벨** 평가이며, 최종 출력·계획과 추론·도구 사용·메모리와 맥락 네 가지 축으로 나눠 측정해야 한다.
- 멀티 에이전트 시스템에서는 개별 에이전트 단위 성공률만 보면 오해할 수 있으므로, 전체 네트워크가 목표를 달성했는지를 함께 확인해야 한다.
- 다음 편에서는 3단계 테스트 피라미드(three-tier testing pyramid)와 ADK를 이용한 실제 테스트 작성법을 다룬다.
