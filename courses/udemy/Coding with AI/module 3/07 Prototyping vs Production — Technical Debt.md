# Prototyping vs Production — Technical Debt

## 개요
- 프로토타입(노트 앱)은 프로토타입으로선 훌륭하지만 **프로덕션 코드가 아니다**.
- 진지한(시간·돈을 투자할) 프로젝트라면 **바이브 코딩하면 안 된다** (강사의 의견 — 이 코스는 다소 opinionated).
- 바이브 코딩의 실질적 대가는 **기술 부채(technical debt)**.

## 내용

### 왜 진지한 프로젝트는 바이브 코딩 X
- 실속 있는 것은 **너무 크고 복잡**해 몇 개 프롬프트/원샷 플랫폼으로 못 만든다.
- 예: 인증 + 관계형 DB + 여러 리소스 + **신용카드 결제** → 절대 바이브 코딩할 대상 아님.
- ⚠️ 코딩 못 하는 사람에게 "바이브 코딩으로 성공 가능"이라 홍보하는 건 강사가 보기엔 **기만적(disingenuous)**.

### 기술 부채(Technical Debt)란
- 제대로 하지 않고 **빠르고 지저분하게(quick and dirty)** 한 코드를, 나중에 고치거나 재작업하는 **미래 비용**.
- 금융 비유: 지금 지름길로 시간을 빌리지만 **이자까지 붙여 나중에 갚는다**.

### 바이브 코딩이 기술 부채를 빠르게 쌓는 이유
1. **장기 계획을 AI가 모름** — 당면 문제만 풀고, 프로젝트가 어디로 가는지 고려 안 함.
2. **일관성 없는 패턴** — 5개 기능을 5개 세션에 요청하면 5가지 접근이 나올 수 있음.
3. **과잉/과소 엔지니어링** — 불필요한 추상화 남발, 설정 가능해야 할 걸 하드코딩 (프로토타입에서 마크다운을 페이지에 다 넣은 것처럼).
4. **복붙 신드롬(copy-paste syndrome)** — 추상화 대신 약간 변형해 중복. 12곳을 고쳐야 할 때 터짐.
5. **엣지 케이스 누락** — AI는 **해피 패스(happy path)** 에 최적화 → 에러 처리·로딩·빈 상태가 자주 빠짐.
6. **의존성 비대(dependency bloat)** — 4줄이면 될 걸 패키지로 끌어옴 (예: 안 쓰는 recharts가 package.json에).

→ 다시, **아키텍트가 되어라(be the architect)**.

### 바이브 코딩의 환상 (빙산 비유)
- 수면 위(보이는 것): 동작함, 예쁨 (= 노트 앱).
- 수면 아래(숨겨진 것): **기술 부채, 아키텍처 없음, 일관성 없는 패턴** → 확장·유지보수 어려움.

### 프로토타입이 잘하는 것 (가치)
- **컨셉 검증**, 룩앤필 확인, UX 테스트.
- **MVP 기능 목록** 확보 (split 에디터, 마크다운, 라이트/다크 테마, 내보내기 등).
- 💡 메인 프로젝트에선 **대시보드 UI를 프로토타입 → 스크린샷 → 컨텍스트로 활용**해 본격 빌드 시작.
- **이해관계자·잠재 사용자·투자자**에게 말이 아닌 **실물**을 보여줄 수 있음.

### 정리: 언제 쓰고 언제 피하나
- **좋음(바이브 코딩/프로토타입)**: 빠른 프로토타입, 아이디어 테스트, UI 목업, 버릴 코드(throwaway), 가능성 학습, 아주 작은 개인 앱.
- **나쁨(프로덕션)**: 프로덕션 앱, 유지보수할 코드, **사용자 데이터**를 다루는 것, 비즈니스로 런칭할 프로젝트.
  - SaaS를 바이브 코딩했다가 사용자가 몰리면 무너진다.

## 요약
- 프로토타입 ≠ 프로덕션. 진지한 프로젝트는 바이브 코딩 금물.
- 바이브 코딩의 대가 = **기술 부채**(이자까지 붙는 미래 비용), 6가지 원인: 장기계획 무지·일관성 없음·과잉/과소 엔지니어링·복붙·엣지케이스 누락·의존성 비대.
- 프로토타입의 진짜 가치 = **검증·MVP 목록·이해관계자 공유**, 그리고 **스크린샷을 컨텍스트로** 넘겨 본 개발의 출발점.
- 판단 기준: 버릴 것/작은 개인용 → OK, 사용자 데이터/비즈니스 런칭 → 절대 X. 항상 **아키텍트**로.
