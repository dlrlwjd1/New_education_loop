# Planning the Project — Project Spec — 대화정리

## 개요

- 원 강의 핵심: AI 코딩에서는 코드를 거의 직접 안 쓰기 때문에, 그 공백을 계획·문서화·엄격한 워크플로로 메워야 한다. DevStash의 실제 project-spec(8항목 체크리스트)이 그 예시다.
- 이번 대화에서는 이 project-spec을 05강(SDD 코스의 헌법)과 비교해, 두 문서의 관계와 차이를 짚었다.

## 내용

### 1. AI 코딩에서 계획이 더 중요해지는 이유

AI 이전엔 코드를 직접 짜면서 자연히 뭐가 돌아가는지 알게 됐지만, AI 코딩에서는 그 과정이 없다. 이 공백을 계획 + 문서화 + 엄격한 워크플로로 메워야 아키텍트로서 통제와 컨텍스트를 유지하고 기술 부채를 안 쌓는다.

### 2. 프로젝트 계획 체크리스트 (8항목)

1. Problem — 무슨 문제를 푸는가
2. Users — 누구를 위한 것인가
3. Features — MVP에 충분한 만큼
4. Data — 저장할 데이터(테이블/필드까지 구체적으로)
5. Tech stack — 언어·프레임워크·API
6. Monetization — 수익화 모델
7. UI/UX — 룩앤필 + 레퍼런스
8. Documentation — 이 모든 걸 문서로

문서 작성에 AI를 도구로 써도 되지만(아이디어·아웃라인 요청), **결정은 아키텍트인 나**가 내린다.

### 3. 05강 헌법과의 비교 — 같은 점과 다른 점

05강의 헌법은 **미션·기술 스택·로드맵** 세 기둥으로 이뤄진 "전역 고수준 요구사항"이다. 처음엔 project-spec의 8항목 중 Data·Monetization·UI/UX가 헌법에는 없는 이유를 "헌법이 고수준이라 못 담는다"는 식으로 생각했지만, 다시 보니 **두 문서 다 프로젝트 전체를 다루는 전역 문서**라는 점은 같다. "전역이냐 아니냐"는 구분 기준이 아니었다.

실제 차이는 **확정하는 시점과 상세도**에 있다.

- 05강 헌법: 로드맵을 "**작은 단계**"로 구성하라고 지시한다 — 세부 결정은 나중에 기능 하나씩 명세를 쓸 때(이 로드맵의 Phase 3) 정하는 구조.
- 01강 project-spec: 코드를 한 줄도 안 짠 시점에 DB 테이블·컬럼까지 미리 다 확정한다. 강의도 "이제 무엇을 만드는지 알았으니 프로젝트 부트스트랩"으로 끝난다 — 즉 project-spec은 **코드 생성을 시작하기 전에 필요한 모든 구체적 결정**을 담는 문서다.

### 4. Data·Monetization·UI/UX가 upfront로 확정돼야 하는 이유

"중요해서"라는 답은 방향은 맞지만 다른 항목(Features도 중요함)과 구분이 안 된다. 더 정확한 이유는 이 셋이 **다른 모든 기능에 두루 영향을 미치는 기반 인프라**라는 점이다.

- **Data**: `items`, `collections`, `tags`, 조인 테이블처럼 여러 기능이 같은 테이블을 공유. 부트스트랩 시 Prisma 스키마로 확정되므로 나중에 기능마다 따로 정하면 스키마 충돌·재작업이 생긴다.
- **Monetization**: `users` 테이블의 `isPro` 필드 하나가 "이미지 업로드는 Pro 전용", "AI 기능은 Pro 전용"처럼 거의 모든 기능의 게이팅 로직을 좌우한다.
- **UI/UX**: 사이드바+드로어 레이아웃, 다크모드, 색상 코딩 같은 디자인 시스템은 모든 화면이 따라야 할 공통 규칙이다.

즉 하나를 나중에 바꾸면 이미 만든 다른 기능들을 줄줄이 다시 손봐야 하는 기반적 성격 때문에 부트스트랩 전에 확정한다.

### 5. 왜 AI가 아니라 아키텍트가 최종 결정해야 하는가

이런 기반 인프라적 결정은 **되돌리는 데 큰 비용이 들고 돌이키기 어렵다(irreversible)**. AI가 초안을 던지는 건 괜찮지만, 되돌리는 비용이 큰 결정을 AI에게 맡기면, AI는 프로젝트의 사업적 맥락·취향·장기 방향에 대한 진짜 이해나 책임 없이 그럴듯한 답을 내놓을 수 있고, 잘못됐을 때 되돌리는 비용은 고스란히 사람이 진다. 이건 05강의 **휴먼 인 더 루프(human-in-the-loop)** 원칙과 같은 결이다 — 05강에서도 미션에 타깃 청중이 빠지는 실수를 사람이 검토해서 잡아냈듯, 되돌리기 비싼 결정일수록 사람의 최종 확정이 필요하다.

## 예시

```text
DevStash project-spec 핵심
- Problem: 흩어진 개발 자료 → 중앙 허브
- Features: Items(시스템 타입별) + Collections + 검색 + Auth
- Data: users(isPro, Stripe 필드) / items / collections / 조인테이블 / tags
- Tech stack: Next.js+React19+TS, Neon+Prisma, GPT-4o mini, Tailwind/shadcn
- Monetization: Freemium (Free: 아이템 50개·컬렉션 3개 / Pro: 무제한+AI)
- UI/UX: 모던·미니멀, 기본 다크모드, 레퍼런스 Notion/Linear/Raycast
```

## 요약

- AI 코딩에서는 직접 코드를 짜지 않는 공백을 계획·문서화·엄격한 워크플로로 메운다.
- project-spec 8항목(Problem·Users·Features·Data·Tech stack·Monetization·UI/UX·Documentation)은 05강 헌법(미션·기술 스택·로드맵)과 마찬가지로 프로젝트 전체를 다루는 전역 문서지만, 부트스트랩 직전에 필요한 구체적 결정까지 담는다는 점이 다르다.
- Data·Monetization·UI/UX는 다른 모든 기능에 두루 영향을 미치는 기반 인프라라서 upfront로 확정한다.
- 되돌리기 비용이 큰 결정일수록 AI에게 초안은 맡기되 최종 결정은 아키텍트(사람)가 내려야 한다 — 05강의 휴먼 인 더 루프 원칙과 같은 맥락.
