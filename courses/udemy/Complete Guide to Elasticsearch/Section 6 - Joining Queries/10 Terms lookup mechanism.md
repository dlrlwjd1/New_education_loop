# Terms lookup mechanism

## 개요

- `terms` 쿼리에 검색할 값들을 직접 나열하는 대신, 다른 문서의 필드에서 가져오는 terms lookup mechanism을 배운다.
- 원본: [Udemy 강의 100](https://www.udemy.com/course/elasticsearch-complete-guide/learn/lecture/10131964#overview)
- 확인일: 2026-09-06 · Chrome 확장에서 실제 강의 트랜스크립트 확인.

## 내용

### 다른 문서에서 검색 조건 가져오기

검색할 값이 수백 개라면 쿼리에 모두 넣는 방식은 길고 다루기 어렵다. Terms lookup은 값을 가진 문서의 인덱스(`index`), 문서 ID(`id`), 필드 경로(`path`)를 지정해 그 값을 `terms` 검색 조건으로 사용한다. 강의 영상은 문서 타입(`type`)도 지정하는 구버전 문법을 사용한다.

### 팔로우한 사용자의 스토리 조회

강의는 `users`와 `stories` 인덱스를 사용한다. 사용자 문서의 `following`에는 팔로우하는 사용자 ID가 들어 있다. `stories`의 `user` 필드에 대해 terms lookup을 수행하고, `users`에서 ID가 `1`인 문서의 `following` 값을 조회 조건으로 쓴다. 사용자 1이 사용자 2와 3을 팔로우하므로 해당 사용자들의 스토리 두 개가 검색된다. 필드가 중첩된 구조라면 점으로 연결한 경로를 지정할 수 있다.

### 요청 처리와 성능

조정 노드(coordinating node)는 검색 요청을 분석하고, 지정된 문서를 조회해 필드 값을 검색 조건에 적용한다. 애플리케이션이 사용자 문서를 먼저 읽고 그 값을 두 번째 검색 요청에 넣는 것과 개념적으로 비슷하지만, 조회를 클러스터 내부에서 처리한다는 차이가 있다.

애플리케이션과 클러스터 사이의 요청 횟수와 데이터 전송을 줄일 수 있다. 팔로우 대상이 수천 명이거나 ID가 긴 문자열이라면 전송량 차이가 커진다. 실제 이득은 데이터 구조와 양에 따라 달라진다. 검색 조건의 값이 많을수록 메모리·처리 비용도 증가하며, 강의는 약 65,000개 수준의 제한과 인덱스별 설정 가능성을 언급한다.

## 예시

강의의 데이터 흐름:

```text
users 문서 1의 following → [2, 3]
                        ↓ terms lookup
stories의 user 값이 2 또는 3인 문서 검색
```

- 검색 대상 필드: `stories`의 `user`
- 값을 가져올 위치: `users`, 문서 ID `1`, 경로 `following`
- 영상의 타입 지정 문법은 버전에 따라 달라지므로 여기서는 확인된 데이터 흐름을 기록한다.

## 요약

- Terms lookup은 다른 문서에 저장된 값들을 `terms` 쿼리의 조건으로 사용한다.
- 애플리케이션에서 두 번 요청하는 과정을 클러스터 내부 조회로 옮겨 요청과 전송량을 줄일 수 있다.
- 조건 수가 많을 때의 처리 비용과 제한은 여전히 고려해야 한다.
- 이전의 트랜스크립트 미제공 상태를 해소하고 실제 대본에 근거해 보완했다.
