# Product Management Process - Overview — 대화정리

## 개요

- 학습일: 2026-08-04
- 원본 강의: [05 Product Management Process - Overview.md](05%20Product%20Management%20Process%20-%20Overview.md)
- 이 강의의 핵심은 하나다. **제품 관리는 발견(discovery) 트랙과 개발(development) 트랙, 두 개의 트랙이 닫힌 루프로 돌아간다.**
- 엔지니어가 기획을 맡을 때 새로 생기는 업무는 대부분 **발견 트랙** 쪽이다. 개발자는 그동안 개발 트랙 안에서만 일해왔기 때문이다.

## 내용

### 두 트랙의 역할과 산출물

| | 발견 트랙 (discovery) | 개발 트랙 (development) |
|---|---|---|
| 질문 | 어떤 문제를 풀까 / 어떤 해법이 맞을까 / 성공을 어떻게 측정할까 | 검증된 것을 어떻게 잘 만들어 낼까 |
| 활동 | 인터뷰, 프로토타입, 가정 검증 | 설계 → 구현 → 테스트 → 배포 → 운영 |
| 산출물 | **확신(confidence)** — 코드가 아님 | 실제 동작하는 제품 |

발견 트랙을 건너뛰면 개발 트랙은 아주 훌륭하게 — 잘못된 것을 — 만들어 낸다.

### 발견 트랙의 세 가지 질문

1. 어떤 문제를 풀 것인가
2. 어떤 해법이 적합한가
3. **성공을 어떻게 측정할 것인가**

실무에서 가장 자주 누락되는 것이 ③이다. 성공 기준을 출시 **전에** 정해두지 않으면 출시 후에 "잘 된 건가?"를 판단할 수 없다.

### 피드백 루프 — 두 트랙은 단계가 아니다

- 출시 **전**: 인터뷰·프로토타입으로 문제와 해법 가설을 검증한다.
- 출시 **후**: 실제 사용 데이터를 다시 발견 트랙에 되돌려 넣는다.

배포 시점에 일을 끝내버리면 세 가지를 잃는다.

1. **발견 트랙의 입력원이 끊긴다.** 발견 트랙이 없어지는 게 아니라 *근거 없이* 돌아간다. 다음 분기 기획의 재료가 데이터가 아니라 의견·직감·목소리 큰 사람의 주장이 된다.
2. **루프가 파이프라인으로 퇴화한다.** 이것이 워터폴(waterfall)이다. 2주 스프린트를 돌려도 출시 후 데이터가 발견 트랙으로 돌아오지 않으면 구조상 워터폴이다. **스프린트 길이가 아니라 루프의 폐쇄 여부가 차이를 만든다.**
3. **실패 원인을 구분할 수 없다.** "반응이 없다"의 원인은 둘 중 하나다 — 문제를 잘못 골랐거나(①번 실패), 문제는 맞는데 해법이 나빴거나(②번 실패). 전자는 방향을 틀어야 하고 후자는 같은 문제를 다르게 다시 풀어야 한다. 정반대의 대응인데 데이터가 없으면 구분이 안 된다.

### 트랙을 가르는 기준은 "코드를 쓰는가"가 아니다

기준은 **결과물이 무엇인가**다.

| 활동 | 산출물 | 트랙 |
|---|---|---|
| 기술 검증용 스파이크(spike) | 버리는 코드 + **배운 것** | 발견 |
| 코드 리뷰 | 출시 가능한 코드 | 개발 |

스파이크는 코드를 쓰지만 목적이 코드가 아니라 "이 방식이 되는가?"에 대한 확신이고, 그 코드는 보통 버린다. 그래서 발견 트랙이다. 이것이 "발견 트랙의 산출물은 확신"이라는 말의 실체다.

## 예시

### 예시 1 — "경쟁사에 A 있으니 우리도 A 만들자"

상사의 이 요청에서 빠져 있는 것:

- **"A 기능"은 해법(solution)이지 문제가 아니다.** 발견 트랙의 결론을 미리 내려놓고 개발 트랙으로 직행하는 형태다.
- 기획자가 할 일은 요청을 한 칸 위로 되돌리는 것 — "A를 만들면 **누구의 어떤 문제**가 풀리나요?"로 번역한다.
- 그 질문에 답이 안 나오면 문제 해결이 아니라 기능 경쟁(feature parity)이다. 소비자가 원하지도 않는 기능을 쌓게 된다.
- 여기에 "성공을 어떻게 측정할지"까지 정해야 발견 트랙이 완성된다.

### 예시 2 — 활동을 트랙으로 분류하기

| 활동 | 트랙 | 이유 |
|---|---|---|
| 사용자 5명 인터뷰 | 발견 | 문제 가설 검증 |
| 클릭만 되는 목업으로 반응 보기 | 발견 | 해법 가설 검증 |
| 코드 리뷰 | 개발 | 출시 가능한 코드를 만드는 일 |
| 출시 후 전환율 대시보드 확인 | 발견 | 데이터를 발견 과정에 되돌려 넣는 행위 |
| 기술 검증용 스파이크 | 발견 | 산출물이 확신이고 코드는 버린다 |

### 예시 3 — 루프를 물리적으로 닫는 방법

대시보드를 **보는 것**은 발견 트랙이지만, 그 대시보드가 존재하게 만드는 일(이벤트 로깅·계측)은 개발 트랙이다. 여기서 실무 함정이 생긴다.

- 계측을 개발 트랙에서 빼먹으면 발견 트랙이 나중에 볼 데이터가 **아예 없다.** 배포 후에 "지표 좀 보자" 해도 못 본다.
- 따라서 기획자는 기능 요구사항과 함께 **"무엇을 로깅할지"를 같은 티켓에 넣어야 한다.**

## 요약

1. 제품 관리는 **발견 / 개발** 두 트랙이다. 발견의 산출물은 확신, 개발의 산출물은 제품이다.
2. 발견 트랙의 세 질문 — 어떤 문제 / 어떤 해법 / **성공을 어떻게 측정** (③이 가장 자주 누락된다).
3. 두 트랙은 **닫힌 루프**다. 배포에서 끊으면 애자일해 보여도 워터폴이다.
4. 트랙을 가르는 기준은 코드 유무가 아니라 **산출물이 확신인지 제품인지**다.
5. 루프를 닫으려면 요구사항 단계부터 계측(로깅)을 함께 정의해야 한다.
