# AI-Native Software Development Needs Generalists

## 개요
- 원문: [AI-Native Software Development Needs Generalists](https://www.deeplearning.ai/the-batch/ai-native-software-development-needs-generalists/)
- 발행: DeepLearning.AI The Batch / Andrew Ng (2026-04-17)
- 핵심 주제: AI 코딩 에이전트가 소프트웨어 개발 속도를 크게 높이면, 병목은 코드 작성이 아니라 "무엇을 만들지 결정하고, 디자인·마케팅·법무·제품 판단을 조율하는 일"로 이동한다. 따라서 AI 네이티브 소규모 팀에서는 한 가지 전문성만 가진 사람보다 여러 역할을 넘나들 수 있는 제너럴리스트가 더 큰 가치를 만든다.

## 내용

### 1. AI 네이티브 팀의 변화
AI 네이티브 소프트웨어 팀은 코딩 에이전트를 활용해 제품을 훨씬 빠르게 만든다. 이 변화는 단순히 개발 속도만 높이는 것이 아니라, 팀원이 맡는 역할의 폭도 넓힌다.

기존에는 엔지니어가 주로 코드를 작성하고, 제품 방향은 PM이 정하며, 디자인·마케팅·법무 같은 기능은 별도 조직이 담당했다. 하지만 코드 작성 속도가 10배, 100배 빨라지면 나머지 기능이 상대적으로 느린 병목이 된다.

### 2. 제품 관리 병목
개발 속도가 빨라질수록 더 많은 시간이 "어떻게 만들 것인가"보다 "무엇을 만들 것인가"에 쓰인다. 그래서 일부 팀은 엔지니어와 PM의 비율을 기존 8:1 수준에서 1:1까지 낮추기도 한다.

하지만 엔지니어 1명과 PM 1명이 나뉘어 일하는 구조에서도 커뮤니케이션 자체가 병목이 될 수 있다. 더 빠른 방식은 엔지니어가 사용자 문제와 제품 판단을 이해하고, 필요한 결정을 직접 내리며 곧바로 구현하는 것이다.

### 3. 역할 확장의 방향
Andrew Ng은 엔지니어가 제품 관리 역량을 배우고, PM이 소프트웨어를 만들 수 있는 역량을 배우는 것이 모두 유망하다고 본다.

**엔지니어에게 필요한 확장 역량:**
- 사용자 문제를 이해하고 우선순위를 판단하는 제품 감각
- 빠른 프로토타입을 만들고 피드백을 반영하는 실험 역량
- 디자인, 마케팅, 법무 리스크를 초기에 감지하는 주변 기능 이해
- AI 도구를 활용해 낯선 역할의 사고 과정을 보조받는 능력

**PM에게 필요한 확장 역량:**
- 간단한 기능이나 프로토타입을 직접 만들 수 있는 구현력
- AI 코딩 도구를 활용해 제품 아이디어를 빠르게 검증하는 능력
- 엔지니어와 더 낮은 비용으로 소통할 수 있는 기술 문해력

### 4. 코드 이후의 병목
AI가 코딩을 빠르게 만들면, 병목은 다른 영역으로 이동한다.

**대표적인 병목:**
- **디자인 병목**: 기능은 완성됐지만 사용자가 이해하고 사용할 수 있는 흐름이 늦게 정리됨
- **마케팅 병목**: 제품 변화가 빨라져 사용자에게 무엇을 어떻게 알릴지 따라가지 못함
- **법무·컴플라이언스 병목**: 하루 만에 만든 기능을 검토하는 데 일주일이 걸림
- **의사결정 병목**: 빌드는 빠르지만 우선순위와 범위를 정하는 속도가 느림

즉, agentic coding은 개발팀 내부의 워크플로만 바꾸는 것이 아니라 제품을 둘러싼 조직 전체의 작동 방식을 바꾼다.

### 5. 소규모 팀과 제너럴리스트
AI 도구를 잘 쓰는 2~10명 규모의 작은 팀은 과거보다 훨씬 많은 일을 처리할 수 있다. 그러나 작은 팀이 엔지니어링, 제품, 디자인, 마케팅, 법무 등 여러 전문 영역을 모두 다뤄야 한다면, 각 구성원은 단일 전문성 밖의 문제도 어느 정도 판단할 수 있어야 한다.

이는 깊은 전문성이 필요 없다는 뜻이 아니다. 오히려 각자 강한 중심 전문성을 가지되, 프로젝트가 앞으로 나아가는 데 필요한 주변 기능을 이해하고 필요할 때 개입할 수 있어야 한다는 뜻이다.

### 6. 커뮤니케이션 속도
작은 팀이 빠르게 움직이려면 커뮤니케이션 병목도 줄여야 한다. 원문은 같은 공간에서 일하며 즉시 대화할 수 있는 팀이 가장 빠른 속도를 낸다고 본다.

원격 팀도 좋은 성과를 낼 수 있지만, 최고 속도를 목표로 하는 AI 네이티브 소규모 팀에서는 즉각적인 문제 해결과 짧은 피드백 루프가 특히 중요하다.

## 예시

### AI 네이티브 소규모 팀 운영 체크리스트
- [ ] 엔지니어가 사용자 문제와 제품 우선순위를 직접 이해하고 있는가?
- [ ] PM이 AI 도구를 활용해 간단한 프로토타입이나 기능 검증을 직접 수행할 수 있는가?
- [ ] 기능 구현 이후 디자인, 마케팅, 법무 검토가 병목이 되는 지점을 추적하고 있는가?
- [ ] 팀원이 자신의 전문 분야 밖의 문제를 AI 도구와 함께 1차로 탐색할 수 있는가?
- [ ] 2~10명 규모 팀에서 커뮤니케이션 경로가 지나치게 길어지지 않도록 운영하고 있는가?
- [ ] "누가 승인해야 하는가"보다 "지금 판단 가능한 사람이 바로 전진시킬 수 있는가"를 기준으로 일하고 있는가?

### 역할 변화 예시
| 기존 역할 | AI 네이티브 팀에서의 확장 |
| --- | --- |
| 엔지니어 | 코드 작성 + 제품 판단 + 사용자 피드백 해석 + 간단한 디자인·마케팅 고려 |
| PM | 요구사항 정의 + 프로토타입 제작 + AI 도구 기반 실험 + 기술적 제약 이해 |
| 디자이너 | 화면 설계 + 빠른 인터랙션 실험 + 구현 가능성 검토 |
| 마케터 | 출시 커뮤니케이션 + 제품 변화의 빠른 이해 + 사용자 반응 기반 메시지 조정 |

## 요약
- AI 코딩 에이전트는 소프트웨어 구현 속도를 크게 높이지만, 그 결과 제품 결정·디자인·마케팅·법무 같은 주변 기능이 새로운 병목이 된다.
- AI 네이티브 팀에서는 "코드를 잘 쓰는 사람"보다 "무엇을 만들지 판단하고 바로 실행할 수 있는 사람"의 가치가 커진다.
- 엔지니어는 제품 관리 역량을, PM은 구현 역량을 배우면 팀의 커뮤니케이션 비용을 줄일 수 있다.
- 작은 팀이 여러 전문 영역의 일을 처리하려면 구성원이 중심 전문성을 유지하면서도 주변 역할을 넘나드는 제너럴리스트가 되어야 한다.
- AI 도구는 낯선 역할의 사고를 보조해 주기 때문에, 개인과 소규모 팀이 이전보다 훨씬 넓은 범위의 문제를 다룰 수 있게 한다.
- 빠른 AI 네이티브 팀에는 짧은 피드백 루프와 즉각적인 커뮤니케이션이 중요하다.
