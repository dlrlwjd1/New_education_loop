# Research: 영속 저장소 계층 (Persistence Layer)

Technical Context에 미확정 항목(NEEDS CLARIFICATION)이 없었으므로, 이 문서는 구현 방식이 여러 갈래로 갈릴 수 있는 지점에서 내린 결정을 기록한다.

## 1. SQLite 드라이버 선택

- **Decision**: Node.js 24에 내장된 동기 SQLite API `node:sqlite`(`DatabaseSync`, `StatementSync`)를 사용한다. 신규 npm 의존성을 추가하지 않는다.
- **Rationale**: 이 저장소의 `backend/package.json`은 Node 24(`@types/node` 최신)를 이미 전제하고 있고, 실제 실행 환경(`node --version` → v24.20.0)에서 `node:sqlite`를 플래그 없이 바로 `require`할 수 있음을 직접 확인했다(경고 없음). 001의 모든 계약 함수(`parseRoadmaps` 등)가 동기 함수라 API 스타일이 일관되고, 네이티브 addon 빌드(플랫폼별 사전 컴파일 바이너리, `node-gyp` 의존)가 필요 없어 "개인용 로컬 웹앱"이라는 배포 형태와도 맞는다.
- **Alternatives considered**:
  - `better-sqlite3`: 가장 널리 쓰이는 동기 드라이버지만 네이티브 addon이라 Node 버전·플랫폼마다 사전 빌드 바이너리 또는 컴파일 도구가 필요 — 이 프로젝트처럼 의존성을 최소로 유지하려는 001의 방향(순수 JS/TS 의존성만 사용)과 어긋난다.
  - `sql.js`(WASM): 파일 I/O를 직접 하지 않고 메모리 버퍼를 수동으로 저장/로드해야 해서 "파일 하나로 원자적 교체"를 구현하는 데 불필요한 레이어가 추가된다.
  - `node:sqlite`가 아직 없는 Node 버전을 지원해야 한다면 위 대안을 재고해야 하지만, 이 저장소는 이미 Node 24 전제이므로 해당 없음.

## 2. 원자적 교체(atomic replace) 전략

- **Decision**: 재적재 시 새 SQLite 파일을 임시 경로(`<db-path>.tmp-<pid>-<timestamp>`)에 처음부터 완성한 뒤, 완료되면 `fs.renameSync(tmpPath, dbPath)`로 기존 파일을 덮어쓴다. 적재 도중 예외가 나면 임시 파일만 버리고 기존 `dbPath`는 손대지 않는다.
- **Rationale**: 같은 파일시스템 내 `rename`은 POSIX에서 원자적 연산이라, 조회 중인 다른 호출이 "절반만 쓰인 파일"을 볼 수 없다(FR-007). 단일 파일 통째 교체는 SQLite 트랜잭션만으로 구현할 때보다 훨씬 단순하고, "손상되거나 스키마 버전이 오래되면 처음부터 다시 생성"(FR-003)이라는 요구와도 자연스럽게 맞는다 — 매 재적재가 이미 "처음부터 다시 생성"이기 때문이다.
- **Alternatives considered**:
  - 기존 DB 파일을 열어둔 채 `BEGIN`/`COMMIT` 트랜잭션으로 테이블 내용만 갱신: 스키마 버전이 바뀌거나 파일이 손상된 경우를 별도로 다뤄야 해서 복잡도가 커지고, 실행 중 크래시 시 WAL/저널 복구 절차에 의존하게 된다.
  - "activetable_v1 / activetable_v2" 이중 테이블 스와핑: 같은 파일 안에서 스와핑하면 스키마 버전 자체가 오래된 경우(컬럼 구조 변경)에는 대응이 안 된다.

## 3. "파일이 저장소보다 최신이면 우선"(FR-002)의 구현 방식

- **Decision**: 부분 무효화(특정 파일만 다시 파싱)를 구현하지 않는다. 재적재는 항상 001의 `runImport()`를 처음부터 다시 호출해 `study-progress/`·`courses/` 전체를 다시 읽고, 그 결과로 새 SQLite 파일을 통째로 만든다.
- **Rationale**: 매 재적재가 "지금 이 순간의 파일 내용"을 기준으로 전체를 다시 만들기 때문에, "파일이 최신이면 파일이 이긴다"는 규칙이 구조적으로 항상 참이 된다 — 어떤 파일이 바뀌었는지 개별 판단할 필요가 없다. 001의 실제 실행 시간(실저장소 7,865개 자료 포함)이 성능 목표(SC-001: 반복 조회가 최초 적재 시간의 1% 미만)를 위협할 정도로 느리지 않다는 것은 001 `개발결과.md`에 기록된 벤치마크로 뒷받침된다. 부분 무효화는 "어떤 파일이 어떤 로드맵/자료에 영향을 주는지" 추적하는 별도 상태가 필요해, 이 기능의 범위(FR-001~010)를 넘어서는 복잡도를 추가한다.
- **Alternatives considered**:
  - 파일별 mtime을 저장해두고 바뀐 파일만 재파싱: 001 계약(`parseRoadmaps`/`parseMaterials`)이 "특정 파일만" 파싱하는 인터페이스를 제공하지 않아, 이 방식을 쓰려면 001 계약을 확장해야 한다(FR-008 위반 소지 — 001을 다시 해석하지 않는다는 원칙과 충돌).
- **참고(구현 중 확정, 원안에서 수정)**: "적재 실행 기록"(Key Entity)에는 마지막 적재 시각과 그 시점 파일들의 내용 해시를 남긴다. 원안은 이를 `resolveIdentity`의 `previousBatch`로 다음 재적재에 주입해 파일 이동/이름 변경을 식별자 연속성으로 처리하려 했으나, 구현 중 이것이 **현재는 안전하게 연결할 수 없다는 것이 밝혀졌다**:
  1. `RunImportOptions`/`parseRoadmaps`/`parseMaterials`는 `previousBatch`를 받는 매개변수가 없다 — 오직 `resolveIdentity` 단독 함수만 받고, 001의 파이프라인 자신은 항상 그것 없이 호출한다. 이를 열려면 001의 계약(`ingestion-library.md`) 확장이 필요하다(이번 기능 범위 밖).
  2. 더 중요한 문제: `parseMaterials.ts`는 `resolveIdentity`가 `status: "updated"`를 반환할 때마다 새 `MaterialVersion`을 추가하는데, 이 상태는 "내용이 실제로 바뀜"과 "내용이 그대로인 채 재적재됨" 둘 다를 가리킨다(001 자신의 `resolveIdentity.ts` 문서 주석이 인정하는 한계). 즉 지금 상태로 `previousBatch`를 매 재적재마다 먹이면, 바뀐 게 하나도 없어도 자료 7,865개 전부가 재적재할 때마다 "updated"로 잡혀 `material_versions`가 재적재마다 수천 행씩 무의미하게 불어난다 — 001이 매칭된 이전 매핑의 `contentHash`와 실제로 다른지 먼저 비교하도록 고쳐야 안전한, 단순 배선이 아닌 진짜 수정이 필요하다.

  이 기능은 위 두 가지를 이번 범위에서 고치지 않기로 결정했다 — `load_run_file_snapshots`는 현재 "다음 재적재에 쓰일 입력"이 아니라 **쓰기 전용 감사 기록**(마지막 적재가 언제, 몇 개를 처리했는지)으로만 존재한다. FR-006(재적재해도 행 수 안 늘어남)은 이것 없이도 이미 성립한다 — 001이 부여하는 id가 애초에 `sha256(정규화된 경로)`라는, previousBatch 유무와 무관하게 경로 하나당 결정적인 값이기 때문이다(§1 결정과 별개로 성립하는 두 번째 안전장치: 매 재적재가 기존 파일에 upsert하지 않고 완전히 새 파일을 만들기 때문에 애초에 누적 경로가 없다). **알려진 후속 과제**: 파일 이동/이름 변경 연속성과 `material_versions` 실사용은 001의 `previousBatch` 매개변수 추가 + "내용이 실제로 바뀐 경우만 updated로 취급" 수정이 함께 이뤄져야 하며, 그 필요가 실제로 생기면(예: 3단계 화면이 자료 버전 이력을 보여줘야 할 때) 별도 기능/작업으로 다룬다.

## 4. 재적재 트리거 시점

- **Decision**: 이 기능은 "재적재를 실행하는 함수"만 제공하고, 언제 그 함수를 호출할지(서버 시작 시, 수동 명령, 주기 실행 등)는 결정하지 않는다.
- **Rationale**: spec.md Assumptions가 이미 이렇게 범위를 그어 놓았다("재적재를 언제 트리거할지는 화면·운영 기능을 만들 때 정한다"). 이 결정을 이 기능 안에서 내리면 3단계(화면) 요구사항을 앞질러 추측하게 된다.
- **Alternatives considered**: 없음 — 스펙이 이미 확정한 범위 경계이므로 재논의하지 않는다.

## 5. 스키마 버전 관리

- **Decision**: SQLite `PRAGMA user_version`에 정수 스키마 버전을 기록한다. DB 파일을 열 때 이 값이 코드가 기대하는 버전과 다르면(파일이 없거나 손상돼 열기 자체가 실패하는 경우 포함) 오류를 던지지 않고 §2의 재생성 경로로 진행한다.
- **Rationale**: 별도 메타데이터 테이블 없이 SQLite가 기본 제공하는 필드라 스키마 정의(`schema.ts`)와 버전 번호가 한곳에 머무른다. "손상됐거나 예전 스키마 버전"(Edge Cases)을 여는 시점에 동일한 검사 한 번으로 처리할 수 있다.
- **Alternatives considered**: `schema_migrations` 테이블에 적용된 마이그레이션 목록을 기록하는 방식 — 이 기능은 점진적 마이그레이션(기존 데이터 보존)이 아니라 "버전이 다르면 통째로 재생성"이 확정된 정책(FR-003)이라 마이그레이션 이력 추적 자체가 불필요한 복잡도다.
