# Feature Specification: 영속 저장소 계층 (Persistence Layer)

**Feature Branch**: `002-persistence-layer`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "웹전환_기능명세_및_개발가이드.md 5장 3단계(사용자·읽기 화면)의 기반 작업 — 001-content-ingestion-foundation이 정의한 파싱 규칙을 실행해 로드맵·트랙·Phase·학습 항목·자료·매핑을 조회 가능한 영속 저장소(SQLite 파생 캐시)에 적재하고, 파일이 최신이면 파일을 우선하는 동기화 규칙과 향후 화면이 쓸 조회 함수를 제공한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 매번 다시 읽지 않고 즉시 조회 (Priority: P1)

사용자가 로드맵 목록이나 자료를 여러 번 열어도, 매번 `study-progress/`·`courses/` 전체를 다시 파싱하지 않고 즉시 결과를 봐야 한다. 001은 파싱 "규칙"의 정확성만 검증했고, 실제로 반복 조회가 가능한 상태를 만드는 것이 이 기능의 핵심 가치다.

**Why this priority**: 이 저장소가 없으면 화면(3단계의 나머지 부분: 로드맵 탐색, 자료실)이 매 요청마다 7,865개 파일을 다시 순회해야 한다 — 명세서 F09가 이미 금지한 방식이다.

**Independent Test**: 저장소를 한 번 적재한 뒤, 로드맵 목록 조회 함수를 반복 호출해 매번 파일을 다시 순회하지 않고도 같은 결과를 즉시 반환하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 001의 규칙으로 적재를 한 번 완료한 저장소, **When** 로드맵 목록 조회를 100번 반복하면, **Then** 매 호출이 원본 파일을 다시 읽지 않고 완료되며 결과가 매번 동일하다.
2. **Given** 같은 저장소, **When** 특정 자료를 경로로 검색하면, **Then** `courses/` 전체를 순회하지 않고 즉시 그 자료가 반환된다.

---

### User Story 2 - 파일이 원본, 파일을 고치면 반영됨 (Priority: P1)

사용자가 Phase 문서의 체크박스를 직접 고치면(예: 텍스트 에디터로), 다음 재적재 때 그 변경이 조회 결과에 반영돼야 한다. 파일이 저장소보다 최신이면 파일 내용이 항상 우선한다(구현전_결정사항.md 7.1).

**Why this priority**: 이 저장소는 원본의 "파생 캐시"일 뿐이라는 원칙이 깨지면, 사용자가 파일을 직접 고쳐도 웹 화면에는 옛 값이 남는 신뢰 붕괴가 생긴다. US1과 동급으로 중요하다.

**Independent Test**: 적재 후 원본 Phase 파일의 체크박스 하나를 고치고 재적재를 실행해, 조회 결과의 완료 수가 정확히 바뀐 값으로 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 적재된 로드맵, **When** 원본 Phase 파일에서 미완료 항목 하나를 완료로 고치고 재적재하면, **Then** 그 로드맵의 조회 결과 완료 수가 정확히 1 증가한다.
2. **Given** 같은 상황, **When** 재적재 전에 조회하면, **Then** 아직 이전 값을 보여준다(재적재를 실행해야 반영됨 — 실시간 감시는 범위 밖).

---

### User Story 3 - 캐시를 지워도 무손실 재생성 (Priority: P2)

이 저장소 파일 자체는 원본에서 파생되는 캐시이므로, 그 파일을 통째로 지워도 다음 적재 실행에서 원본 파일들로부터 완전히 동일한 결과가 다시 만들어져야 한다.

**Why this priority**: "파생 캐시"라는 설계 원칙(7.1)이 실제로 지켜지는지 확인하는 시나리오다. US1·US2가 먼저 동작해야 이 시나리오를 의미 있게 검증할 수 있다.

**Independent Test**: 정상 적재 후 저장소 파일을 삭제하고 재적재를 실행해, 삭제 전과 로드맵·자료 수·완료/전체 수치가 완전히 동일한지 대조한다.

**Acceptance Scenarios**:

1. **Given** 정상적으로 적재된 저장소, **When** 저장소 파일을 삭제한 뒤 재적재를 실행하면, **Then** 로드맵 8개·자료 수·완료/전체 수치가 삭제 전과 100% 동일하게 재생성된다.
2. **Given** 스키마 버전이 오래된 저장소 파일, **When** 최신 코드로 재적재를 실행하면, **Then** 오류로 멈추지 않고 원본 파일로부터 새로 생성한다.

---

### User Story 4 - 화면이 바로 쓸 수 있는 조회 함수 (Priority: P2)

향후 화면(로드맵 탐색, 자료실)이 001의 파싱 내부 구조(AST, 식별자 해석 로직 등)를 몰라도, 로드맵 목록+진행률, 로드맵 상세, 자료 검색을 바로 호출해서 쓸 수 있는 조회 함수가 있어야 한다.

**Why this priority**: 이 함수가 없으면 다음 단계(로드맵 탐색·자료실 화면)를 만들 때마다 이 기능의 내부 스키마를 직접 다뤄야 해서, 화면 구현이 이 기능의 저장소 구조에 강하게 결합된다. 화면 자체보다는 지원 기능이라 P1보다 한 단계 낮다.

**Independent Test**: 저장소 내부 스키마를 모르는 상태에서, 공개된 조회 함수만으로 로드맵 목록(진행률 포함)·로드맵 상세·자료 검색 결과를 얻을 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 적재된 저장소, **When** "로드맵 목록" 조회 함수를 호출하면, **Then** 각 로드맵의 제목·완료/전체·진행률이 포함된 목록이 반환된다.
2. **Given** 같은 저장소, **When** 제목 일부로 자료를 검색하면, **Then** 일치하는 자료가 경로·분류·연결된 로드맵과 함께 반환된다.

---

### Edge Cases

- 재적재 도중 원본 파일이 또 바뀌면(동시 편집)? → 그 재적재 실행이 시작된 시점의 파일 상태를 기준으로 삼고, 그 사이의 추가 변경은 다음 재적재에서 반영한다. 실시간 파일 감시는 이 기능의 범위 밖이다.
- 001이 보고한 오류(체크박스 해석 불가, 날짜 오류, 식별자 충돌 후보, 깨진 자료 링크)가 있는 항목은 저장소에 어떻게 적재하는가? → 조용히 빠뜨리지 않고 "확인 필요" 상태로 적재해, 화면에서 노출할 수 있게 한다.
- 저장소 파일이 손상됐거나 예전 스키마 버전이면? → 오류로 멈추지 않고 원본 파일로부터 처음부터 다시 생성한다.
- 재적재 실행 중 오류로 중단되면 조회 결과는 어떻게 되는가? → 재적재 시작 전의 마지막으로 성공한 상태를 계속 보여주며, 절반만 반영된 깨진 상태를 노출하지 않는다(원자적 교체).
- 자료(`courses/`)에도 "실제/예시" 구분이 적용되는가? → 아니다. 자료 자체는 공유 참조 데이터이며, "실제/예시" 구분은 로드맵·학습 항목(개인 진도가 있는 대상)에만 적용된다(001 FR-011과 동일한 경계).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 001이 정의한 파싱 규칙(`parseRoadmaps`/`parseMaterials`/`resolveMaterialLinks`/`runImport`)을 실행한 결과를 조회 가능한 영속 저장소에 적재해야 한다.
- **FR-002**: 시스템은 원본 Markdown 파일이 저장소의 마지막 적재 시점보다 최신이면, 파일 내용을 우선해 저장소를 갱신해야 한다(구현전_결정사항.md 7.1).
- **FR-003**: 시스템은 저장소 파일이 없거나 손상됐거나 스키마 버전이 오래된 경우, 원본 파일들로부터 처음부터 다시 생성할 수 있어야 하며, 이 상황을 오류로 취급해 중단하지 않아야 한다.
- **FR-004**: 시스템은 다음 조회 함수를 제공해야 하며, 호출자가 001의 파싱 내부 구조(AST, 식별자 해석 로직)를 알 필요가 없어야 한다: 로드맵 목록(진행률 포함), 로드맵 상세(트랙·Phase·학습 항목), 자료 검색(제목·경로·분류·제공처·강좌).
- **FR-005**: 시스템은 001이 보고한 오류(`checkbox_unrecognized`, `date_invalid`, `id_collision`, `link_broken`)가 있는 항목도 저장소에서 조회 가능해야 하며, "확인 필요" 상태로 구분해 조용히 빠뜨리지 않아야 한다.
- **FR-006**: 시스템은 재적재를 여러 번 실행해도 저장소의 항목 수가 늘지 않아야 한다 — 001이 부여한 안정적 식별자를 저장소의 기본 키로 그대로 사용한다.
- **FR-007**: 시스템은 적재 도중 오류가 발생해도 이전에 성공적으로 적재된 조회 가능한 상태를 훼손하지 않아야 한다(원자적 교체 또는 트랜잭션 — 절반만 반영된 상태를 조회자에게 노출하지 않는다).
- **FR-008**: 시스템은 001의 라이브러리 계약(`contracts/ingestion-library.md`)이 반환하는 타입과 필드를 저장소 스키마의 유일한 근거로 사용해야 하며, 그 데이터를 독자적으로 재해석하거나 001과 다른 규칙으로 다시 계산하지 않아야 한다.
- **FR-009**: 시스템은 `courses/`의 자료 자체를 개인 진도와 무관한 공유 참조 데이터로 취급해야 하며, "실제/예시" 범위 구분은 로드맵과 그 학습 항목에만 적용해야 한다(001 FR-011 상속).
- **FR-010**: 시스템은 이 영속 저장소 파일을 git 커밋 대상에서 제외해야 한다(구현전_결정사항.md 7.1 — 파일에서 파생되는 캐시).

### Key Entities *(include if feature involves data)*

- **로드맵/트랙/Phase/학습 항목/자료/자료 버전**: 001 `data-model.md`에 정의된 엔티티를 그대로 저장소 스키마의 근거로 삼는다(FR-008) — 이 기능이 새로 정의하지 않는다.
- **로드맵 요약(조회 뷰)**: 화면 목록에 필요한 로드맵별 제목·완료/전체·진행률·"확인 필요" 항목 수를 미리 계산해 둔 조회 전용 표현.
- **적재 실행 기록**: 마지막 재적재가 언제 끝났는지, 그때 각 원본 파일의 수정 시각(또는 내용 해시)이 무엇이었는지 담아, 다음 재적재 때 "파일이 저장소보다 최신인지"를 판단하는 근거로 쓴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 저장소를 한 번 적재한 뒤 로드맵 목록 조회를 100회 반복했을 때, 평균 응답 시간이 최초 적재(전체 파싱) 시간의 1% 미만이다.
- **SC-002**: 원본 Phase 파일의 체크박스를 바꾸고 재적재하면, 조회 결과의 완료 수가 실제로 바뀐 값과 100% 일치한다.
- **SC-003**: 저장소 파일을 삭제하고 재생성해도 로드맵·자료 수, 완료/전체 수치가 삭제 전과 100% 동일하다.
- **SC-004**: 재적재를 두 번 실행해도 저장소에 새로 생성되는 중복 항목이 0건이다.
- **SC-005**: 001이 보고한 오류가 있는 항목 100%가 저장소 조회 결과에서 "확인 필요" 상태로 나타나며, 조용히 사라진 항목이 0건이다.

## Assumptions

- 001-content-ingestion-foundation의 라이브러리 계약(`contracts/ingestion-library.md`)이 이 기능의 유일한 데이터 원천이며, 이 기능은 001의 파싱 로직을 다시 구현하지 않는다.
- 저장소 기술은 구현전_결정사항.md 7.1에서 이미 SQLite(파생 캐시)로 확정돼 있으므로 이 스펙에서 다시 논의하지 않는다.
- 단일 사용자 로컬 앱이므로 동시 접근 경쟁은 "재적재 실행 중 조회가 들어오는" 정도로 제한되며, 다중 사용자·다중 프로세스 잠금 전략은 이 기능의 범위 밖이다.
- 실시간 파일 변경 감시(예: 파일 저장 즉시 반영)는 이 기능의 범위 밖이다 — 재적재를 실행해야 반영된다. 재적재를 언제 트리거할지(수동 명령, 서버 시작 시점, 주기적 실행 등)는 화면·운영 기능을 만들 때 정한다.
- 이 기능은 "조회 가능한 상태를 만든다"까지이며, 그 데이터를 실제로 사용자에게 보여주는 화면(로드맵 탐색, 자료실)은 이후 별도 기능으로 이어진다.
