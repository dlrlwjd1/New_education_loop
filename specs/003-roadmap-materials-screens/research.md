# Research: 로드맵 탐색·자료실 화면

Technical Context에 미확정 항목(NEEDS CLARIFICATION)이 남지 않았으므로, 이 문서는 구현 방식이 여러 갈래로 갈릴 수 있었던 지점에서 내린 결정을 기록한다.

## 1. 프론트엔드 아키텍처: 서버 렌더링 단일 앱

- **Decision**: `backend/`(Express) 하나가 요청을 받아 직접 HTML을 렌더링해 응답하는 **서버 렌더링(SSR) 단일 앱**으로 만든다. 별도 `frontend/` 워크스페이스, SPA 프레임워크(React/Svelte 등), 클라이언트 빌드 도구(bundler)를 두지 않는다. 상호작용이 필요한 부분(검색창 디바운스 등)만 번들러 없는 최소 vanilla `<script>`로 얹는다.
- **Rationale**: 이 결정은 이 프로젝트에서 프론트엔드 방향을 처음 정하는 것이고, 이후 모든 화면 기능이 그대로 물려받는 구조적 선택이라 계획 단계에서 사용자에게 직접 확인받았다(AskUserQuestion, "서버 렌더링 단일 앱" 선택). 이 선택은 001/002가 이미 지켜온 "최소 의존성"(001: 순수 JS 파서 라이브러리만, 002: 신규 네이티브 의존성 없이 Node 내장 `node:sqlite`) 원칙과 일관되고, 003이 다루는 화면(목록·상세·검색·본문 열람)이 전부 읽기 전용이라 복잡한 클라이언트 상태 관리가 애초에 필요 없다. `구현전_결정사항.md`가 이미 확정한 "개인용 로컬 웹앱, 다중 사용자 없음"이라는 배포 형태와도 잘 맞는다(별도 정적 호스팅·CDN·API 게이트웨이가 필요 없음).
- **Alternatives considered**:
  - SPA(React/Svelte 등) + REST/JSON API: `design/` 폴더의 기존 Claude Design 캔버스 시안(대화형 학습실 등)과 결이 더 잘 맞고 이후 화면(F04 학습 루프의 채팅형 UI)에는 유리하지만, 지금 이 두 화면(읽기 전용)에는 과한 구조이고 빌드 도구·의존성이 늘어난다.
  - 정적 HTML 목업(`design/learning-loop-preview.html`)을 그대로 확장: 이 파일은 실제 데이터가 전혀 연결되지 않은 디자인 시안일 뿐이라, 002의 실제 조회 함수와 연결하려면 결국 서버가 필요하다.
- **알려진 한계**: F04(질문·답변, 5단계 "학습 핵심 루프") 같은 대화형 화면은 vanilla JS만으로 버거워질 수 있다 — 그 단계에서 이 아키텍처 선택 자체를 재검토할 수 있으며, 지금 이 결정이 그 단계의 선택까지 강제하지는 않는다.

## 2. 서버 프레임워크: Express

- **Decision**: Node 내장 `http` 모듈을 직접 쓰지 않고 `express`를 라우팅·미들웨어 계층으로 채택한다.
- **Rationale**: 경로 매개변수(`:id`) 파싱, 쿼리 문자열 처리, 정적 자산 서빙(`express.static`) 같은 기본기를 직접 구현하면 오히려 버그 표면이 늘어난다. Express는 이런 기본기가 이미 검증돼 있고, 가장 널리 쓰이는 만큼 향후 이어받을 화면 기능(F01, F03~F12)의 라우트도 같은 패턴으로 계속 추가하기 쉽다. SPA 프레임워크가 아니라 얇은 서버 계층일 뿐이라 §1의 "서버 렌더링 단일 앱" 결정과 충돌하지 않는다.
- **Alternatives considered**:
  - Node 내장 `http`/`node:http` 직접 사용: 신규 의존성이 0개라는 장점은 있지만, 라우팅·정적 파일 서빙을 직접 만드는 비용이 이 기능 범위를 벗어난다.
  - Fastify: Express보다 가볍고 빠르지만, 이 앱은 성능이 병목이 될 일이 없는 개인용 로컬 앱이라 그 이점이 의미가 적고, Express가 더 널리 알려져 있어 유지보수 문턱이 낮다.

## 3. HTML 템플릿 방식: 템플릿 엔진 없이 함수 기반

- **Decision**: EJS/Pug 같은 별도 템플릿 엔진 의존성을 추가하지 않는다. 대신 `backend/src/web/html.ts`에 작은 이스케이프 헬퍼(`escapeHtml`, 안전하게 속성/텍스트를 채우는 태그드 템플릿 함수)를 만들고, `views/*.ts`는 그 헬퍼로 조립한 문자열을 반환하는 순수 함수로 작성한다.
- **Rationale**: 이 기능이 그리는 화면(목록, 트리, 검색 결과, 폼 하나)은 조건부 렌더링과 반복이 대부분이라 템플릿 엔진의 표현력이 굳이 필요하지 않다. 로드맵 제목·자료 제목은 파일 시스템에서 온 값이라(파일명에 우연히 `<`, `&` 같은 문자가 있을 수 있음) 신뢰할 수 없는 입력이며, 템플릿 엔진을 쓰더라도 결국 auto-escape 설정에 기대야 하는 것은 마찬가지다 — 작은 자체 헬퍼 하나로 이 요구를 충분히, 더 적은 의존성으로 만족시킨다. "자료 본문"(Markdown에서 온, 훨씬 큰 위험 표면)은 이 헬퍼가 아니라 §4의 별도 sanitize 파이프라인이 전담한다.
- **Alternatives considered**: EJS/Pug/Handlebars — 표현력은 더 크지만 신규 의존성과 별도 문법을 배워야 하는 비용 대비, 이 기능의 화면 복잡도에서 얻는 이득이 작다.

## 4. Markdown → 안전한 HTML 변환 파이프라인

- **Decision**: 001이 이미 쓰는 `unified` + `remark-parse` + `remark-gfm`에 `remark-rehype({ allowDangerousHtml: true })`(Markdown AST → HTML AST) + `rehype-raw`(Markdown에 섞인 원문 raw HTML을 실제 HTML 노드로 파싱) + `rehype-sanitize`(허용 목록 기반 살균) + `rehype-stringify`(HTML 문자열화)를 이어붙인다. 자료 본문을 열람할 때만 이 전체 파이프라인을 한 번 실행한다(FR-009, FR-010, SC-004, SC-005).
- **Rationale**: 001의 파서(`markdownAst.ts`)가 이미 실 데이터(한글·공백·URL 인코딩·중첩 디렉터리·코드 블록·GFM 표)를 상대로 검증됐으므로, 같은 `unified` 생태계를 재사용하면 파싱 결과의 일관성이 보장되고 새 Markdown 파서를 하나 더 신뢰 경계 안에 들이지 않아도 된다. `웹전환_기능명세_및_개발가이드.md` F09가 "Markdown의 raw HTML과 링크를 안전하게 렌더링한다"고 명시하므로, raw HTML을 그냥 이스케이프해 텍스트로 보여주는 것으로는 부족하다 — `remark-rehype`는 기본 설정으로는 Markdown 안에 섞인 raw HTML을 hast 노드로 바꾸지 않으므로, `allowDangerousHtml: true` + `rehype-raw`로 일단 실제 HTML 노드로 만든 뒤, 그 결과를 `rehype-sanitize`(스크립트 태그·인라인 이벤트 핸들러·`javascript:` URL 등을 구조적으로 제거하는 허용 목록 방식)로 살균한다. 이 순서(raw HTML을 파싱한 뒤 살균)여야 사용자가 보는 표·코드 블록·내부 링크·원본 출처 링크·(안전한) raw HTML(FR-009)은 그대로 유지하면서 위험한 요소만 걸러낼 수 있다(SC-005 "스크립트 실행 0건"을 라이브러리 차원에서 보장) — `rehype-raw` 없이 `rehype-sanitize`만 쓰면 raw HTML이 애초에 파싱되지 않아 안전하지만 "렌더링"되지 않은 것이라 F09 요구를 충족하지 못한다.
- **Alternatives considered**:
  - `marked` + `DOMPurify`: 널리 쓰이지만 001과 다른 파서 생태계를 새로 들여오는 것이라, 001이 이미 검증한 파싱 동작(예: 코드 블록 안 체크박스 처리)과의 일관성을 잃을 수 있다.
  - 직접 정규식으로 위험 태그를 걸러내는 자체 sanitizer: OWASP가 명시적으로 경고하는 안티패턴(우회 사례가 계속 발견됨) — 검증된 허용 목록 라이브러리를 쓰는 것이 안전 요구사항(FR-010, SC-005)에 맞다.

## 5. 자료 본문 읽기 경로

- **Decision**: 002는 자료의 메타데이터만 저장하고(002 data-model.md), 본문 자체는 저장하지 않는다(002 spec.md Assumptions에서 이미 이렇게 정함). 003은 `searchMaterials()`가 반환한 `sourcePath`를 001의 `DEFAULT_COURSES_ROOT` 기준으로 `path.join` 한 뒤, 그 결과가 여전히 `DEFAULT_COURSES_ROOT` 하위인지 확인(`path.resolve` 후 접두어 검사)하고 나서만 `fs.readFileSync`로 읽는다.
- **Rationale**: "파일이 원본" 원칙(구현전_결정사항.md 7.1)을 그대로 따르며, 본문을 SQLite에 다시 캐싱하지 않아 002의 책임 경계를 지킨다. 경로 접두어 검사는 `sourcePath`가 이론적으로 `../../etc/passwd` 같은 값을 포함해도(002는 실제로 이런 값을 만들지 않지만, 이 기능의 라우트는 URL 쿼리로 사용자 입력을 받는 새 신뢰 경계이므로 방어적으로 확인한다) `courses/` 밖의 파일을 읽지 않도록 하는 안전장치다(헌법 II "입력 검증은 시스템 경계에서만 수행").
- **Alternatives considered**: 002의 스키마를 확장해 본문(또는 본문 해시)까지 캐싱 — 자료당 최대 수십 KB인 본문을 7,865건 전부 SQLite에 중복 저장하는 것은 002가 이미 결정한 "파생 캐시는 조회에 필요한 메타데이터까지만"이라는 범위를 넘어서고, 파일이 본문의 유일한 원본이라는 원칙과도 어긋난다.

## 6. "이어서 공부" 위치 계산과 확인 필요(null) 항목 처리

- **Decision**: `getRoadmapDetail()`이 반환한 트리를 트랙→Phase→항목 순서(이미 `order_index`로 정렬됨)로 순회해, `completed === false`인 첫 항목을 "이어서 공부" 대상으로 삼는다. `completed === null`(체크박스 해석 불가 등, 002의 "확인 필요" 상태)인 항목은 완료로도, 자동 제안 대상으로도 취급하지 않고 건너뛴다 — 순회 중 그런 항목을 지나치면 그 로드맵에 "확인 필요" 항목이 있다는 사실만 별도로 기록해 화면에 보여준다(FR-004). 순회 결과 `completed === false`인 항목이 하나도 없으면(전부 완료거나 전부 확인 필요) "더 이상 이어서 공부할 항목이 없다"고 안내한다(FR-005 Acceptance Scenario 2를 이 경우까지 확장 적용).
- **Rationale**: spec.md FR-005는 "미완료 항목"이라고만 했지 확인 필요(null) 상태와의 관계를 명시하지 않았다 — 002가 이미 "확인 필요"를 완료(`true`)·미완료(`false`)와 구분된 제3의 상태로 다루고 있으므로(002 data-model.md), 그 경계를 003이 재해석해 null을 미완료로 뭉뚱그리면 사용자가 실제로는 "체크박스 해석이 안 된" 항목을 정상적인 다음 학습 위치로 안내받는 오해가 생긴다. 건너뛰고 별도로 알리는 쪽이 002가 이미 세운 3-상태 구분과 일관된다.
- **Alternatives considered**: null을 미완료와 동일하게 취급 — 구현은 더 단순하지만 "확인 필요"라는 상태를 만든 002의 의도(FR-005, "조용히 빠뜨리지 않는다")를 화면 단에서 무력화하게 된다.

## 7. 검색·목록 결과가 많을 때의 나눠보기 방식

- **Decision**: 서버 렌더링이므로 클라이언트 상태(무한 스크롤 등)를 두지 않고, 쿼리 파라미터 기반 오프셋(`?offset=0&limit=50` 형태)과 "다음 50개 보기" 링크로 나눈다. 링크는 일반 `<a href>`라 새 GET 요청 하나로 다음 페이지를 서버가 다시 렌더링한다.
- **Rationale**: SSR 아키텍처(§1)와 자연스럽게 맞는 가장 단순한 방식이고, 클라이언트 JS나 별도 상태 관리가 전혀 필요 없다. 자료 7,865개 규모에서 "몇 번째 페이지인가"보다 "다음 묶음"만 알면 충분하다(Edge Cases는 정확한 페이지네이션 UI를 요구하지 않는다).
- **Alternatives considered**: 클라이언트 JS로 무한 스크롤 구현 — 상호작용은 매끄럽지만 §1에서 "번들러 없는 최소 vanilla JS"로 정한 범위를 넘어서는 상태 관리가 필요해진다.

## 8. 라우트 테스트 방식: supertest

- **Decision**: Express 앱에 대한 HTTP 통합 테스트에 `supertest`(devDependency 신규 추가)를 쓴다.
- **Rationale**: Express 앱 인스턴스를 직접 넘겨 실제 포트를 열지 않고도 요청/응답을 검증할 수 있어, 001/002가 이미 쓰는 vitest와 자연스럽게 어울리고 테스트가 빠르다. 이 조합은 Express 생태계에서 가장 흔히 쓰이는 표준적인 선택이라 유지보수 부담이 적다.
- **Alternatives considered**: 서버를 실제로 `listen`시키고 Node 내장 `fetch`로 호출 — 신규 의존성은 없지만, 매 테스트마다 포트 충돌 회피·서버 시작/종료를 직접 관리해야 해 테스트 코드가 번거로워진다.
