## 원본 명세와의 관계 *(이 기능에서 바뀐 전제)*

- **F11의 원본 전환 제안을 따르지 않는다.** 웹전환 명세 F11 "개발 시 주의점"은 "최초 이전에서만 파일을 기준으로 상태를 옮기고, 웹 운영 이후에는 DB를 개인 진도의 원본으로 삼는 방식"을 제안한다. 이 제안은 같은 문서 7장·7.1절의 **확정 정책**("진행 기록의 원본은 계속 파일(Markdown)이다. SQLite는 파일에서 파생되는 보조 저장소")으로 대체되었다. 따라서 이 기능에서 "가져오기"는 파일을 한 번 옮겨 담고 파일을 버리는 이전(migration)이 아니라, **원본 파일을 다시 읽어 파생 캐시에 반영하기 전에 그 결과를 점검·확정하는 절차**를 뜻한다. 가져오기 이후에도 파일이 계속 원본이며, 사용자가 파일을 직접 고치면 다음 가져오기에서 파일이 이긴다(002 FR-002).
- **파싱 자체는 새로 만들지 않는다.** Phase 문서 체크박스·자료 색인의 파싱과 식별자 부여는 001, 캐시 적재는 002, 복습큐 파싱·적재는 004가 이미 제공한다. 이 기능은 그 결과를 사용자에게 **보여주고, 비교하고, 확정하게 하는 화면과 절차**, 그리고 **내보내기·백업·복구**를 추가한다.
- **"파생 캐시"와 "파일에서 파생되지 않는 기록"을 구분한다.** 002·004의 공유 캐시는 원본 파일로 언제든 재생성할 수 있다. 반면 005가 만든 브리핑 기록 저장소와 006이 만든 학습 세션 저장소는 파일에서 파생되지 않는 유일한 사실(세션·질문·답변 시도·힌트 기록, 브리핑 스냅샷과 요청 식별자)을 담으므로, 재생성할 수 없고 반드시 백업 대상이다.
- **자동 Git 동기화는 범위 밖이다(7장 확정).** 백업·복구·내보내기 어느 단계에서도 앱이 스스로 커밋·푸시하지 않는다. 버전 관리는 사용자가 CLI·개발 도구에서 직접 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 반영하기 전에 가져오기 결과를 점검하고 확정하기 (Priority: P1) 🎯 MVP

사용자가 설정·데이터 관리 화면에서 "가져오기 시작"을 누르면, 시스템은 `study-progress/`의 로드맵·Phase 문서와 `내학습/`의 복습큐·진행상황·브리핑로그 파일을 다시 읽어, **아직 화면에 반영하지 않은 상태로** 점검 보고서를 보여준다. 보고서에는 새로 생길 항목·바뀔 항목·보류될 항목의 수와 목록, 깨진 링크, 날짜 오류, 중복 후보, 해석할 수 없는 체크박스가 원본 파일 위치와 함께 나오고, 로드맵별 "완료/전체" 수치가 원본 파일에서 직접 센 수치와 나란히 비교된다. 사용자가 가져올 범위(실제 기록 / 예시 데이터)를 확인하고 확정하면 그때 반영된다.

**Why this priority**: 파일이 원본인 구조에서는 사용자가 파일을 직접 고치거나 새 로드맵을 추가할 때마다 다시 가져오기가 일어난다. 이때 무엇이 바뀌는지, 무엇이 조용히 빠지는지를 보여주지 않으면 진도 수치를 신뢰할 수 없다. 001·002가 오류를 수집해 두었지만 사용자가 그것을 볼 수 있는 곳이 아직 없다. 내보내기·백업보다 먼저, 매일 쓰는 수치의 신뢰를 세우는 기능이다.

**Independent Test**: 코드 블록 속 체크박스, `[X]` 표기, 해석 불가 체크박스, 깨진 자료 링크, 잘못된 날짜가 섞인 로드맵 사본으로 가져오기 점검을 실행해, 보고서가 각 오류의 파일·위치를 보여주는지, 원본 직접 집계와 가져오기 결과의 차이가 사유별로 설명되는지, 확정 전에는 화면 수치가 바뀌지 않는지, 같은 원본으로 두 번 확정해도 항목이 늘지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이전에 한 번 가져온 상태에서 사용자가 Phase 문서의 미완료 항목 하나를 완료로 고친 경우, **When** 가져오기 점검을 실행하면, **Then** 보고서는 그 로드맵을 "갱신"으로, 완료 수가 1 증가함을 보여주며, 확정 전에는 로드맵·브리핑 화면의 수치가 이전 값 그대로다.
2. **Given** Markdown 코드 블록 안에 예시 체크박스 3개가 있는 Phase 문서, **When** 점검 보고서를 보면, **Then** 그 3개는 학습 항목 수에 포함되지 않고, 원본 직접 집계와의 차이 사유에 "코드 블록 안 예시 체크박스 3개 제외"로 표시된다.
3. **Given** `[x]`, `[X]`, `[ x ]` 같은 표기가 섞인 Phase 문서, **When** 점검 보고서를 보면, **Then** 모두 완료로 집계되고 오류로 보고되지 않는다.
4. **Given** 해석할 수 없는 체크박스 표기, 깨진 자료 링크, 해석 불가·미래 날짜, 식별자 충돌 후보가 있는 원본, **When** 점검 보고서를 보면, **Then** 각 항목이 종류·원본 파일 경로·줄 위치와 함께 "보류" 또는 "확인 필요"로 나열되고, 그 파일의 나머지 정상 항목은 정상적으로 집계된다(문서 전체가 조용히 빠지지 않는다).
5. **Given** 점검 보고서를 본 사용자가 확정을 누른 경우, **When** 반영이 끝나면, **Then** 화면의 로드맵별 완료/전체 수치가 보고서에 표시됐던 가져오기 결과 수치와 100% 일치하고, 이번 가져오기가 "최근 가져오기" 이력에 날짜·범위·생성/갱신/보류 수와 함께 남는다.
6. **Given** 원본 파일이 전혀 바뀌지 않은 상태, **When** 가져오기를 다시 점검·확정하면, **Then** 보고서의 "생성" 수는 0이고, 확정 후 로드맵·학습 항목·복습 항목의 수가 늘지 않는다.
7. **Given** 점검 보고서를 본 뒤 확정하지 않고 취소한 경우, **When** 다른 화면으로 이동하면, **Then** 캐시·화면 수치·원본 파일 어느 것도 바뀌지 않는다.

### User Story 2 - 학습 기록을 잃지 않도록 백업을 만들고, 복구가 실제로 되는지 검증하기 (Priority: P1)

사용자가 "백업 만들기"를 누르면, 시스템은 개인 학습 기록의 원본 파일(Phase 문서의 체크박스가 담긴 `study-progress/`, `내학습/`의 Markdown 파일)과 파일에서 재생성할 수 없는 기록 저장소(학습 세션, 브리핑 기록), 그리고 재생성 가능한 파생 캐시를 한 개의 백업으로 묶는다. 백업에는 무엇이 들어 있는지와 그 시점의 핵심 수치(로드맵별 완료/전체, 활성·마스터 완료 복습 항목 수, 학습 세션 수, 브리핑 기록 수)가 목록으로 남는다. 사용자는 "복구 검증"을 실행해, 현재 데이터를 건드리지 않은 격리된 공간에 그 백업을 실제로 풀고 캐시를 다시 만든 뒤 수치가 백업 당시와 일치하는지 확인받을 수 있다.

**Why this priority**: 학습 세션 저장소(006)와 브리핑 기록 저장소(005)는 파일에서 파생되지 않고 Git에도 들어가지 않으므로, 디스크 문제나 실수로 지워지면 되살릴 방법이 없다. 이 앱이 쌓는 기록 중 가장 잃기 쉬운 것을 보호하는 기능이라 P1이다. 또한 "백업이 있다"가 아니라 "복구가 된다"를 확인해야 백업이 의미가 있다(F11 7단계).

**Independent Test**: 학습 세션·브리핑 기록이 있는 상태에서 백업을 만들고, 복구 검증을 실행해 격리 공간에서 복구된 수치가 백업 목록의 수치와 모두 일치하는지, 그 과정에서 현재 작업 데이터가 한 바이트도 바뀌지 않는지 확인한다. 이어서 백업 안의 파생 캐시 사본을 지운 백업으로도 복구 검증이 성공하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 학습 세션 기록과 브리핑 기록이 있는 상태, **When** 백업을 만들면, **Then** 백업에는 원본 Markdown 파일들, 학습 세션 저장소, 브리핑 기록 저장소가 반드시 포함되고, 백업 목록 화면에 생성 시각·포함 항목·핵심 수치·전체 크기가 표시된다.
2. **Given** 백업 하나, **When** 복구 검증을 실행하면, **Then** 시스템은 현재 데이터와 분리된 공간에 백업을 풀고 파생 캐시를 원본 파일에서 다시 만든 뒤, 로드맵별 완료/전체·복습 항목 수·학습 세션 수·브리핑 기록 수를 백업 당시 수치와 비교해 항목별 "일치/불일치"를 보여준다.
3. **Given** 복구 검증 도중이나 이후, **When** 현재 작업 데이터를 확인하면, **Then** 원본 파일·기록 저장소·캐시 어느 것도 바뀌지 않았다.
4. **Given** 파생 캐시 사본이 빠져 있거나 손상된 백업, **When** 복구 검증을 실행하면, **Then** 캐시는 백업 안의 원본 파일에서 재생성되어 검증이 성공한다.
5. **Given** 학습 세션 저장소가 빠져 있거나 무결성 확인에 실패한 백업, **When** 복구 검증을 실행하면, **Then** 검증은 "불일치 — 재생성할 수 없는 기록 누락"으로 실패하고 어떤 항목이 문제인지 알려준다.
6. **Given** 백업을 만든 경우, **When** 저장소의 버전 관리 상태를 확인하면, **Then** 앱이 스스로 커밋·푸시를 실행한 흔적이 없고, 백업 파일이 저장소의 버전 관리 대상 파일로 추가되어 있지 않다.

### User Story 3 - 백업으로 학습 기록을 되돌리기, 덮어쓰기 전에 확인받기 (Priority: P2)

사용자가 백업 목록에서 하나를 골라 "이 백업으로 복구"를 누르면, 시스템은 먼저 현재 데이터와 백업 데이터를 비교한 요약(바뀔 로드맵 진도, 사라지거나 되돌아갈 학습 세션·복습 항목·브리핑 기록 수)을 보여주고, 사용자가 명시적으로 확인한 경우에만 복구한다. 복구 직전에 현재 상태를 자동으로 백업해 두어, 잘못 복구해도 다시 되돌릴 수 있다. 복구가 끝나면 복구 후 수치를 백업 당시 수치와 비교한 결과를 보여준다.

**Why this priority**: 복구는 기존 학습 기록을 덮어쓰는 유일한 동작이라 가장 위험하다(F12 "복구 작업이 기존 학습 기록을 덮어쓰지 않도록"). 백업 생성·검증(US2)이 먼저 있어야 의미가 있으므로 P2로 둔다.

**Independent Test**: 백업 이후 새 학습 세션 하나와 체크박스 변경 하나를 만든 뒤 그 백업으로 복구를 시도해, 확인 화면이 "학습 세션 1건이 사라짐, 완료 1건 되돌아감"을 보여주는지, 확인 없이 진행되지 않는지, 복구 후 수치가 백업 당시와 일치하는지, 복구 직전 자동 백업으로 다시 되돌릴 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 백업 이후 새 학습 세션과 진도 변경이 생긴 상태, **When** 그 백업으로 복구를 요청하면, **Then** 시스템은 복구하기 전에 덮어쓰일 내용(로드맵별 완료 수 변화, 사라질 학습 세션·브리핑 기록 수, 복습 항목 수 변화)을 요약해 보여주고 사용자의 명시적 확인을 기다린다.
2. **Given** 복구 확인 화면에서 사용자가 취소한 경우, **When** 현재 데이터를 확인하면, **Then** 아무것도 바뀌지 않았다.
3. **Given** 사용자가 복구를 확인한 경우, **When** 복구가 실행되면, **Then** 시스템은 복구 직전 현재 상태를 자동 백업으로 먼저 남기고, 그 자동 백업이 백업 목록에 "복구 직전 자동 백업"으로 표시된다.
4. **Given** 복구가 끝난 경우, **When** 결과를 보면, **Then** 파생 캐시가 복구된 원본 파일에서 다시 만들어져 있고, 로드맵별 완료/전체·복습 항목 수·학습 세션 수·브리핑 기록 수가 백업 당시 수치와 100% 일치한다는 비교 결과가 표시된다.
5. **Given** 같은 백업으로 복구를 두 번 연속 실행한 경우, **When** 수치를 확인하면, **Then** 학습 세션·복습 항목·브리핑 기록이 중복 생성되지 않고 한 번 복구했을 때와 같다.
6. **Given** 복구 도중 오류가 발생한 경우, **When** 현재 데이터를 확인하면, **Then** 일부만 복구된 상태가 남지 않고 복구 직전 상태 그대로이며, 실패 사유가 안내된다.
7. **Given** 학습 세션이 진행 중(답변 채점 대기 등)인 상태, **When** 복구를 요청하면, **Then** 시스템은 진행 중인 세션이 복구로 사라지거나 되돌아간다는 사실을 확인 화면에 따로 경고한다.

### User Story 4 - 내 로드맵·진도·복습큐·학습 기록을 내보내기 (Priority: P2)

사용자가 내보낼 대상(로드맵, 진도·복습큐, 학습 기록 중 선택)을 고르고 "다운로드"를 누르면, 원문 구조를 그대로 보존한 Markdown 사본과, 안정적인 식별자·원본 경로·내용 해시 매핑을 담은 구조화 데이터가 하나의 파일로 내려받아진다. 내보낸 파일은 사람이 읽을 수 있고, 다시 가져오거나 복구할 때 같은 항목을 중복 생성하지 않도록 식별자 매핑을 담는다.

**Why this priority**: 사용자가 자기 기록을 앱 밖으로 가져가 보관·제출·공유할 수 있게 하는 기능이다. 원본이 이미 사람이 읽을 수 있는 파일이라 급하지는 않지만, 파일에 없는 학습 세션 기록을 읽을 수 있는 형태로 꺼낼 수 있는 유일한 경로이므로 P2다.

**Independent Test**: 로드맵 하나와 진도·복습큐·학습 기록을 내보낸 뒤, 파일을 열어 로드맵 Markdown이 원본과 내용이 같은지, 구조화 데이터의 식별자가 앱 화면의 식별자와 일치하는지, 학습 세션이 사람이 읽을 수 있는 Markdown으로도 들어 있는지, 개발 설정·비밀정보·강의 자료 원문이 들어 있지 않은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 "로드맵 내보내기"로 로드맵 하나를 선택한 경우, **When** 다운로드하면, **Then** 파일 안의 해당 로드맵 Markdown 문서들은 원본 파일과 내용이 한 글자도 다르지 않고(목표·트랙·Phase·항목·체크 상태·완료 날짜·링크 보존), 폴더 구조도 원본과 같다.
2. **Given** 같은 내보내기 파일, **When** 구조화 데이터를 확인하면, **Then** 로드맵·트랙·Phase·학습 항목마다 앱이 쓰는 안정적 식별자, 원본 경로, 내용 해시, 완료 상태가 들어 있고, 앱 화면의 수치(완료/전체)와 일치한다.
3. **Given** 사용자가 "진도·복습큐 내보내기"를 선택한 경우, **When** 다운로드하면, **Then** 복습큐 원본 Markdown과 함께, 활성 항목마다 최초 오답일·반복 단계·다음 복습일이, 마스터 완료 항목마다 마스터 완료일이 구조화 데이터에 들어 있다.
4. **Given** 사용자가 "학습 기록 내보내기"를 선택한 경우, **When** 다운로드하면, **Then** 진행상황·브리핑로그 원본 Markdown과 함께, 학습 세션마다 질문·답변·판정·힌트 횟수가 사람이 읽을 수 있는 Markdown과 구조화 데이터 양쪽으로 들어 있다.
5. **Given** 어떤 범위로든 내보낸 파일, **When** 파일 목록을 확인하면, **Then** 개발 설정(`.claude/`, `.specify/`, `specs/`, 앱 소스), 비밀정보(환경 변수 파일, 인증 정보), 강의 자료 원문(`courses/`)이 포함되어 있지 않다.
6. **Given** 예시(`scope: example`)로 표시된 로드맵이 있는 경우, **When** 기본 설정으로 내보내면, **Then** 예시 로드맵은 개인 기록 내보내기에서 빠지고, 사용자가 명시적으로 포함을 선택했을 때만 "예시"로 구분되어 들어간다.

### User Story 5 - 예시 데이터와 실제 기록을 분리하고, 기록이 없으면 빈 상태로 시작하기 (Priority: P3)

설정·데이터 관리 화면에서 사용자는 지금 보이는 진도가 실제 기록인지 예시 데이터인지 확인할 수 있고, 가져오기 점검 때 범위를 명시적으로 고른다. 개인 학습 기록이 하나도 없는 신규 사용자는 모든 로드맵이 미시작이고 복습큐가 비어 있다는 안내를 보며, 예시 데이터의 완료 체크가 자기 진도로 잡히지 않는다.

**Why this priority**: 001이 이미 예시·실제 분리 규칙을 정했으므로, 이 기능은 그 규칙을 사용자에게 보이고 선택하게 하는 부분만 더한다. 중요하지만 US1의 점검 화면 위에 얹히는 기능이라 P3로 둔다.

**Independent Test**: 예시로 표시된 로드맵과 실제 로드맵이 섞인 저장소에서 "실제 기록만"으로 가져오기를 확정해 예시 항목이 진도에 0건 반영되는지, 개인 기록 파일이 없고 진도가 0인 작업공간에서 미시작·빈 복습큐 안내가 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개인 기록(진행상황·복습큐·학습 세션)이 하나도 없고 실제 범위 로드맵의 완료 항목이 0개인 작업공간, **When** 브리핑·설정 화면을 열면, **Then** 모든 로드맵이 미시작으로, 복습큐는 "아직 쌓인 오답이 없습니다"로 안내되고, 예시 데이터의 완료 체크는 진도에 반영되지 않는다.
2. **Given** 예시로 표시된 로드맵과 실제 로드맵이 섞인 저장소, **When** 가져오기 점검에서 범위를 "실제 기록만"으로 두고 확정하면, **Then** 결과 진도에 포함된 예시 항목 수는 0이다.
3. **Given** 같은 저장소, **When** 사용자가 범위를 "예시 체험"으로 바꾸어 점검하면, **Then** 보고서는 예시 데이터가 실제 기록과 분리된 공간에 반영된다는 것을 표시하고, 실제 기록의 진도 수치는 바뀌지 않는다.
4. **Given** 설정·데이터 관리 화면, **When** 사용자가 현재 상태를 확인하면, **Then** 지금 보이는 진도가 "실제 기록" 범위인지 "예시 체험" 범위인지와 마지막 가져오기 시각이 표시된다.

### Edge Cases

- 원본 파일이 UTF-8로 읽히지 않거나(인코딩 오류) 중간이 잘린 경우 → 그 파일만 "읽을 수 없음"으로 보고서에 위치와 함께 나열하고, 나머지 파일의 처리는 계속한다(T17).
- 점검 보고서를 띄워 둔 사이에 사용자가 원본 파일을 또 고친 경우 → 확정 시 원본이 점검 당시와 달라졌음을 감지해 확정을 막고 다시 점검하도록 안내한다. 점검 때 보지 않은 결과를 조용히 반영하지 않는다.
- 같은 개념·주제의 복습 항목이 복습큐 표에 두 번 적혀 있는 경우 → 보고서에 "중복 후보"로 표시하되 자동으로 합치지 않는다(004 FR-012 유지).
- 복습큐·진행상황·브리핑로그 파일이 아예 없는 경우 → 오류가 아니라 "기록 없음"으로 표시하고 신규 사용자 초기 상태로 취급한다(004 FR-014와 같은 경계).
- 로드맵 폴더가 새로 추가되거나 삭제된 경우 → 보고서에 "생성" 또는 "원본 없음(캐시에서 제거 예정)"으로 표시한다. 삭제된 로드맵에 연결된 학습 세션 기록은 지우지 않고 "원본 로드맵 없음"으로 남긴다.
- 파일 이동·이름 변경만 있고 내용이 같은 경우 → 001의 경로 우선·내용 해시 재확인 규칙으로 같은 항목으로 인식되어, 보고서에 "생성"이 아니라 "이동"으로 표시되고 식별자가 유지된다.
- 백업 저장 공간이 부족하거나 쓰기가 실패한 경우 → 불완전한 백업을 목록에 남기지 않고, 실패 사유를 알린다.
- 백업 파일 안에 허용된 범위 밖의 경로(상위 폴더로 빠져나가는 경로, 절대 경로, 개발 설정 폴더)가 들어 있는 경우 → 그 백업은 복구·검증 대상으로 받아들이지 않고 거부 사유를 보여준다(T19 — 파일을 임의 위치에 쓰지 않는다).
- 이 앱이 만들지 않았거나 형식 버전이 다른 백업·내보내기 파일로 복구하려는 경우 → 무결성·형식 확인에 실패하면 복구하지 않는다. 앱보다 오래된 형식 버전이면 읽을 수 있는 경우에만 복구하고, 그렇지 않으면 이유를 안내한다.
- 학습 세션 저장소나 브리핑 기록 저장소의 스키마 버전이 백업 당시와 현재 앱에서 다른 경우 → 조용히 삭제·재생성하지 않고(005·006 원칙), 복구를 멈추고 버전 불일치를 알린다.
- 백업·복구·가져오기 확정이 서로 동시에 요청되거나, 학습 답변 제출과 겹치는 경우 → 한 번에 하나의 쓰기 작업만 진행하고, 나머지 요청에는 "다른 작업 진행 중"을 안내한다. 이미 저장된 답변은 잃지 않는다.
- 같은 내보내기·백업 요청이 중복 전송된 경우(더블 클릭, 새로고침) → 백업이 두 개 생기지 않고 같은 결과를 돌려준다.
- 원본 Markdown이나 기록 안에 스크립트·지시문이 들어 있는 경우 → 점검 보고서·내보내기 미리보기에서 텍스트로만 보여 주고 실행하지 않는다(T19).

## Requirements *(mandatory)*

### Functional Requirements

**가져오기 점검 (US1, US5)**

- **FR-001**: 시스템은 사용자가 가져오기 점검을 요청하면 `study-progress/`의 로드맵·Phase 문서와 `내학습/`의 복습큐·진행상황·브리핑로그 파일을 다시 읽어, 현재 화면·캐시에 반영하지 않은 상태로 점검 보고서를 만들어야 한다. 파싱은 001·004가 정의한 규칙을 그대로 써야 하며, 이 기능이 별도의 파싱 규칙을 만들지 않아야 한다.
- **FR-002**: 점검 보고서는 로드맵·트랙·Phase·학습 항목·복습 항목 각각을 "생성 / 갱신 / 이동 / 보류 / 원본 없음" 중 하나로 분류해 수와 목록을 보여줘야 한다. 비교 기준은 마지막으로 확정된 가져오기 결과다.
- **FR-003**: 점검 보고서는 깨진 자료 링크, 해석 불가·미래 날짜, 해석 불가 체크박스, 식별자 충돌 후보, 중복 후보, 읽을 수 없는 파일을 종류별로 나열하고, 각 항목에 원본 파일 경로와 줄 위치(알 수 있는 경우)를 함께 표시해야 한다.
- **FR-004**: 점검 보고서는 로드맵별로 "가져오기 결과의 완료/전체"와 "원본 파일에서 체크박스 표기를 직접 센 완료/전체"를 나란히 보여주고, 두 값이 다르면 차이를 사유별(코드 블록 안 예시 체크박스 제외, 해석 불가로 보류, Phase가 아닌 문서의 체크박스 제외 등)로 설명해야 한다. 사유로 설명되지 않는 차이가 있으면 "설명되지 않은 차이"로 따로 표시해야 한다.
- **FR-005**: 시스템은 Markdown 코드 블록 안의 체크박스를 학습 항목으로 세지 않고, `[x]`·`[X]`·괄호 안팎 공백 변형을 완료로 해석하며, 해석할 수 없는 표기는 그 항목만 보류해야 한다. 한 문서에 보류 항목이 있어도 그 문서의 나머지 정상 항목은 집계해야 한다(001 FR-005·FR-006 상속).
- **FR-006**: 시스템은 사용자가 점검 보고서를 확인하고 명시적으로 확정했을 때만 그 결과를 파생 캐시에 반영해야 하며, 반영은 전부 성공하거나 전부 반영되지 않아야 한다(002 FR-007과 같은 원자성).
- **FR-007**: 시스템은 확정 시점의 원본 파일이 점검 당시와 달라졌으면 확정을 거부하고 다시 점검하도록 안내해야 한다.
- **FR-008**: 시스템은 원본 경로와 내용 해시를 기준으로 같은 원본을 식별해(001 FR-003·FR-012), 같은 원본을 다시 가져와 확정해도 로드맵·학습 항목·복습 항목이 중복 생성되지 않아야 한다.
- **FR-009**: 시스템은 확정된 가져오기마다 실행 시각, 범위(실제 기록 / 예시 체험), 생성·갱신·이동·보류 수, 오류 수, 로드맵별 완료/전체를 이력으로 남기고, 사용자가 "최근 가져오기" 목록과 각 이력의 보고서를 다시 볼 수 있게 해야 한다.
- **FR-010**: 가져오기 점검과 확정은 원본 Markdown 파일을 수정하지 않아야 한다.
- **FR-011**: 시스템은 예시(`<!-- scope: example -->` 표시, 001 규약) 데이터와 실제 기록을 기본적으로 분리하고, 사용자가 가져오기 점검 화면에서 범위를 명시적으로 선택하게 해야 한다. "실제 기록" 범위의 결과에는 예시 항목이 하나도 포함되지 않아야 하며, "예시 체험" 범위의 반영은 실제 기록의 진도 수치를 바꾸지 않아야 한다.
- **FR-012**: 시스템은 설정·데이터 관리 화면에 현재 보이는 데이터의 범위(실제 기록 / 예시 체험)와 마지막 가져오기 시각을 표시해야 한다.
- **FR-013**: 시스템은 개인 기록(진행상황·복습큐 파일, 학습 세션)이 하나도 없고 실제 범위 로드맵의 완료 항목이 0개인 상태를 신규 사용자 초기 상태로 인식해, 모든 로드맵을 미시작으로, 복습큐를 빈 상태로 안내해야 한다. 기록 파일이 없는 것을 오류로 다루지 않아야 한다(T01).

**내보내기 (US4)**

- **FR-014**: 사용자는 내보낼 대상을 로드맵(하나 이상 선택), 진도·복습큐, 학습 기록(진행상황·브리핑로그·학습 세션) 중에서 골라 하나의 파일로 내려받을 수 있어야 한다.
- **FR-015**: 내보내기 파일 안의 원본 기반 Markdown(로드맵·Phase 문서, 복습큐, 진행상황, 브리핑로그)은 원본 파일과 내용이 동일해야 하며, 원본의 폴더 구조와 파일 이름을 보존해야 한다.
- **FR-016**: 내보내기 파일은 구조화 데이터를 함께 담아야 한다: 각 로드맵·트랙·Phase·학습 항목·복습 항목의 안정적 식별자, 원본 경로, 내용 해시, 완료 상태·완료 날짜, 복습 항목의 최초 오답일·반복 단계·다음 복습일(또는 마스터 완료일), 그리고 내보내기 시각·형식 버전·항목별 수치 요약.
- **FR-017**: 파일에서 파생되지 않는 학습 세션 기록은 세션마다 질문·답변·판정·힌트 횟수를 사람이 읽을 수 있는 Markdown과 구조화 데이터 양쪽으로 내보내야 한다.
- **FR-018**: 내보내기에 포함된 수치(로드맵별 완료/전체, 복습 항목 수, 학습 세션 수)는 내보내기 시점의 앱 화면 수치와 일치해야 한다.
- **FR-019**: 예시로 표시된 로드맵은 기본 내보내기에서 제외하고, 사용자가 명시적으로 포함을 선택한 경우에만 "예시"로 구분해 포함해야 한다.

**백업·복구 (US2, US3)**

- **FR-020**: 백업은 다음을 반드시 포함해야 한다: `study-progress/` 아래 로드맵·Phase 문서, `내학습/`의 Markdown 기록 파일, 파일에서 파생되지 않는 기록 저장소(학습 세션 저장소, 브리핑 기록 저장소). 파일에서 재생성할 수 있는 파생 캐시(로드맵·자료·복습큐 공유 캐시)는 사본으로 포함하되, 복구가 그 사본에 의존하지 않아야 한다.
- **FR-021**: 백업에는 포함 항목 목록, 파일별 무결성 확인값, 형식 버전, 생성 시각, 백업 당시 핵심 수치(로드맵별 완료/전체, 활성·마스터 완료 복습 항목 수, 학습 세션 수, 브리핑 기록 수)를 담은 목록이 들어 있어야 한다.
- **FR-022**: 사용자는 백업 목록에서 각 백업의 생성 시각·종류(수동 / 복구 직전 자동)·포함 항목·핵심 수치·크기를 확인하고, 백업을 내려받거나 삭제할 수 있어야 한다.
- **FR-023**: 시스템은 "복구 검증"을 제공해야 한다: 현재 작업 데이터와 분리된 공간에 백업을 풀고, 파생 캐시를 백업 안의 원본 파일에서 재생성한 뒤, 복구된 핵심 수치를 백업 목록의 수치와 비교해 항목별 일치 여부를 보여줘야 한다. 복구 검증은 현재 작업 데이터를 바꾸지 않아야 한다.
- **FR-024**: 시스템은 복구를 실행하기 전에 현재 데이터와 백업 데이터의 차이(로드맵별 완료 수 변화, 사라지거나 되돌아갈 학습 세션·브리핑 기록·복습 항목 수, 진행 중 세션 여부)를 요약해 보여주고, 사용자의 명시적 확인을 받은 경우에만 복구해야 한다.
- **FR-025**: 시스템은 복구를 실행하기 직전에 현재 상태 전체를 "복구 직전 자동 백업"으로 남겨야 하며, 이 자동 백업이 만들어지지 않으면 복구를 진행하지 않아야 한다.
- **FR-026**: 복구는 전부 성공하거나 전부 적용되지 않아야 한다. 도중에 실패하면 복구 직전 상태가 그대로 유지되어야 한다.
- **FR-027**: 복구가 끝나면 시스템은 파생 캐시를 복구된 원본 파일에서 재생성하고, 복구 후 핵심 수치와 백업 당시 수치의 비교 결과를 보여줘야 한다(T20 — 원본 수치와 복구 수치 일치).
- **FR-028**: 복구는 백업에 포함된 범위를 백업 내용으로 교체하는 방식이어야 하며, 같은 백업으로 여러 번 복구해도 학습 세션·복습 항목·브리핑 기록이 중복 생성되지 않아야 한다.
- **FR-029**: 시스템은 무결성 확인에 실패하거나, 이 앱의 형식이 아니거나, 허용 범위 밖의 경로(상위 폴더 이탈, 절대 경로, 개발 설정·소스 폴더)를 담은 백업·내보내기 파일을 복구·복구 검증 대상으로 받아들이지 않아야 한다.
- **FR-030**: 시스템은 재생성할 수 없는 기록 저장소(학습 세션·브리핑 기록)의 스키마 버전이 현재 앱과 맞지 않으면 그 저장소를 삭제·재생성하지 않고 복구를 멈춘 뒤 이유를 알려야 한다.

**공통 경계 (전 스토리)**

- **FR-031**: 내보내기·백업·점검 보고서는 저장소 전체를 노출하지 않아야 한다. 대상은 개인 기록(로드맵 진도·복습큐·진행상황·브리핑로그·학습 세션·브리핑 기록)과 그 구조(로드맵 문서)로 한정하고, 개발 설정(`.claude/`, `.specify/`, `specs/`, 앱 소스, 디자인 시안), 비밀정보(환경 변수 파일, 인증 정보), 강의 자료 원문(`courses/`)은 포함하지 않아야 한다.
- **FR-032**: 시스템은 가져오기 확정·백업·복구 어느 단계에서도 Git 커밋·푸시를 실행하지 않아야 하며, 백업 파일을 저장소의 버전 관리 대상 위치에 두지 않아야 한다(7장 확정).
- **FR-033**: 가져오기 확정·백업·복구는 한 번에 하나만 진행되어야 하며, 진행 중에 다른 쓰기 작업(다른 확정·복구, 학습 답변 반영)이 들어오면 기다리게 하거나 "다른 작업 진행 중"을 안내해야 한다. 이미 저장된 학습 답변을 잃지 않아야 한다.
- **FR-034**: 같은 백업·내보내기·확정·복구 요청이 중복 전송되면 한 번만 처리하고 같은 결과를 돌려줘야 한다.
- **FR-035**: 점검 보고서·백업 목록·복구 확인 화면에 표시되는 원본 텍스트(파일 내용, 항목 이름)는 텍스트로만 표시되어야 하며, 그 안의 스크립트나 지시문이 실행되지 않아야 한다(T19).

### Key Entities *(include if feature involves data)*

- **가져오기 점검 보고서**: 한 번의 점검 실행 결과. 범위(실제 기록 / 예시 체험), 점검 당시 원본 파일 목록과 내용 해시, 항목별 분류(생성·갱신·이동·보류·원본 없음), 오류 목록(종류·원본 경로·줄 위치), 로드맵별 "가져오기 결과 vs 원본 직접 집계" 비교와 차이 사유를 담는다. 001의 가져오기 배치·매핑·오류 개념을 사용자에게 보이는 형태로 확장한 것이다.
- **가져오기 이력**: 확정된 점검 보고서의 기록. 확정 시각, 범위, 요약 수치를 담고, 다음 점검의 비교 기준이 된다.
- **백업**: 특정 시점의 개인 기록 묶음. 종류(수동 / 복구 직전 자동), 생성 시각, 형식 버전, 포함 항목 목록과 파일별 무결성 확인값, 백업 당시 핵심 수치를 담는다. 원본 Markdown 파일, 재생성 불가 기록 저장소(학습 세션·브리핑 기록), 재생성 가능한 파생 캐시 사본으로 구성된다.
- **복구 검증 결과**: 한 백업에 대해 격리 공간에서 복구를 시험한 결과. 항목별(로드맵별 완료/전체, 복습 항목 수, 학습 세션 수, 브리핑 기록 수) 백업 당시 값·복구 값·일치 여부를 담는다.
- **복구 실행 기록**: 실제 복구 한 건. 사용한 백업, 복구 직전 자동 백업, 확인 시각, 결과(성공/실패와 사유), 복구 후 수치 비교를 담는다.
- **내보내기 파일**: 사용자가 고른 범위의 원문 보존 Markdown 사본과 구조화 데이터(안정적 식별자·원본 경로·내용 해시·상태·수치 요약·형식 버전)를 담은 하나의 파일.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 코드 블록 속 체크박스·대소문자·공백 변형·해석 불가 표기·깨진 링크·잘못된 날짜가 섞인 점검용 원본에서, 보고된 오류의 100%가 원본 파일 경로와 함께 표시되고, 정상 항목의 집계 누락은 0건이다.
- **SC-002**: 현재 저장소의 모든 로드맵에 대해 점검 보고서의 "가져오기 결과 vs 원본 직접 집계" 차이가 100% 사유로 설명되거나 "설명되지 않은 차이"로 표시되며, 조용히 사라지는 차이는 0건이다.
- **SC-003**: 원본을 바꾸지 않고 가져오기를 두 번 확정했을 때 새로 생기는 로드맵·학습 항목·복습 항목은 0건이다.
- **SC-004**: 가져오기 점검만 하고 확정하지 않은 경우, 화면 수치·캐시·원본 파일의 변화는 0건이다.
- **SC-005**: 백업 후 복구(실제 복구와 복구 검증 모두)를 했을 때 로드맵별 완료/전체, 활성·마스터 완료 복습 항목 수, 학습 세션 수, 브리핑 기록 수가 백업 당시와 100% 일치한다(T20).
- **SC-006**: 파생 캐시 사본이 빠진 백업으로도 복구가 100% 성공하고, 복구 후 수치가 원본과 일치한다.
- **SC-007**: 사용자 확인 없이 기존 학습 기록이 덮어쓰인 사례가 0건이며, 실제 복구 100건 중 100건에서 복구 직전 자동 백업이 먼저 만들어진다.
- **SC-008**: 같은 백업으로 두 번 복구해도 중복 생성되는 학습 세션·복습 항목·브리핑 기록은 0건이다.
- **SC-009**: 내보내기 파일의 원본 기반 Markdown이 원본 파일과 내용이 다른 사례는 0건이고, 구조화 데이터의 수치가 내보내기 시점 화면 수치와 다른 사례는 0건이다.
- **SC-010**: 내보내기·백업 파일에 개발 설정·비밀정보·강의 자료 원문이 포함되는 사례는 0건이다.
- **SC-011**: 가져오기·백업·복구 기능을 사용하는 동안 앱이 Git 커밋·푸시를 실행한 사례는 0건이다.
- **SC-012**: 개인 기록이 없는 신규 작업공간에서 미시작·빈 복습큐가 아닌 다른 진도가 표시되는 사례는 0건이고, "실제 기록" 범위 결과에 포함되는 예시 항목은 0건이다(T01).

## Assumptions

- **원본 정책**: 웹전환 명세 7장·7.1절의 확정 정책(파일이 원본, SQLite는 파생 캐시)이 F11의 "이전 후 DB가 원본" 제안보다 우선한다. 따라서 "가져오기 확정"은 원본 파일을 파생 캐시에 다시 반영하는 것이고, 원본 파일을 버리거나 DB로 원본을 옮기지 않는다.
- **가져오기 대상 위치**: 가져오기 원본은 이 저장소의 등록된 위치(`study-progress/`, `내학습/`)로 한정한다. F11 1단계의 "허용된 업로드"(다른 곳의 Markdown을 올려 가져오기)는 이 기능에서 다루지 않는다. 앱이 만든 백업·내보내기 파일을 올려 복구하는 것만 허용한다.
- **자료(`courses/`)**: 강의 자료는 개인 기록이 아니라 읽기 전용 공유 참조 데이터이므로(002 FR-009) 점검 보고서의 로드맵→자료 링크 확인에는 쓰지만, 내보내기·백업 대상에는 넣지 않는다. 자료는 저장소에서 다시 얻을 수 있고, 내보낸 로드맵은 자료를 식별자와 경로로만 가리킨다.
- **재생성 가능/불가 구분**: 현재 저장소 기준으로 로드맵·자료·복습큐 공유 캐시(002·004)는 원본 파일에서 재생성 가능하고, 학습 세션 저장소(006)와 브리핑 기록 저장소(005)는 재생성할 수 없다. 이후 기능(007~012)이 새로 만드는 저장소도 파일에서 파생되지 않으면 백업 대상에 들어가야 하며, 계획 단계에서 백업 대상 목록을 한곳에서 관리하도록 설계한다.
- **백업 보관 위치와 기간**: 백업은 버전 관리 대상 밖의 로컬 백업 폴더에 저장하고 내려받을 수도 있게 한다. 자동 삭제·개수 제한은 두지 않고, 사용자가 직접 삭제한다(개인 로컬 앱, 7장의 "버전 개수 제한 없음" 방향과 같음). 정기 자동 백업(예약)은 이 기능 범위 밖이며, 복구 직전 자동 백업만 자동으로 만든다.
- **복구 방식**: 복구는 백업에 포함된 범위를 통째로 교체한다. 현재 데이터와 백업 데이터를 항목 단위로 합치는(merge) 복구는 범위 밖이다. 교체 방식이라 중복이 생길 수 없고, 잃을 수 있는 내용은 확인 화면과 복구 직전 자동 백업으로 보호한다.
- **내보내기 파일로 복구**: 내보내기 파일도 형식 버전과 무결성 확인값을 가지므로, 사용자가 원하면 내보내기 파일을 복구 대상으로 쓸 수 있다. 이때는 내보내기에 포함된 범위만 교체된다(F11 완료 확인 "내보낸 기록으로 복구할 수 있다").
- **원본 직접 집계**: 점검 보고서의 "원본 직접 집계"는 Phase 문서 안의 체크박스 표기를 줄 단위로 단순하게 센 값이다(코드 블록 여부를 가리지 않은 기준치). 가져오기 결과와 비교해 코드 블록 제외·보류·비 Phase 문서 제외 같은 차이 사유를 드러내는 용도이며, 기존 `/브리핑` 스킬 집계와 같은 성격의 기준치다.
- **로그 파일 점검 깊이**: 진행상황·브리핑로그 파일은 이 기능에서 줄 수와 날짜 형식 오류만 점검한다. 그 내용의 세부 해석(세션별 이력 구성)은 010(학습 이력·브리핑 이력 상세)의 범위다.
- **예시 범위의 기본값**: 001 규약에 따라 `<!-- scope: example -->` 표시가 없는 로드맵은 실제 기록으로 본다. 사용자가 범위를 한 번도 고르지 않았다면 기본값은 "실제 기록"이다. 현재 저장소에는 이 표시가 붙은 파일이 없으므로 "예시 체험" 범위는 빈 결과가 정상이다(001 Assumptions). `사용과개선.md`의 가상 데이터 고지는 산문 설명일 뿐이라, 사용자가 그 로드맵에 표시를 붙이기 전까지 시스템이 임의로 예시로 분류하지 않는다.
- **AI 호출 원문 로그**: 7장이 정한 AI 요청·응답 원문 로그는 운영 로그로 보고 이 기능의 내보내기·백업 대상에서 기본 제외한다. 운영 로그의 보관·정리는 014(설정·운영·접근성)의 범위다.
- **화면 위치**: 가져오기·내보내기·백업은 설정·데이터 관리 화면(`design/canvas/Settings.dc.html` 시안의 "가져오기", "내보내기 · 백업" 영역)에 둔다. 시간대 등 나머지 설정 항목은 014의 범위다. 화면 경로·문구·파일 형식(압축 방식, 구조화 데이터 형식)은 계획 단계에서 정한다.
- **배포 형태**: 개인용 로컬 단일 사용자 앱이다(7장 확정). 다른 사용자의 내보내기·백업 접근 차단(T18)은 다중 사용자 기능이 없으므로 이 기능에서 다루지 않는다.
- **의존 기능**: 001(파싱·식별자·예시 범위 규약), 002(캐시 적재·원자적 교체), 004(복습큐 파싱), 005(브리핑 기록 저장소), 006(학습 세션 저장소)의 공개 인터페이스를 재사용한다. 이 기능은 그 기능들의 저장 형식을 바꾸지 않는다.
