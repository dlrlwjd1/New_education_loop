# Phase 0 Research: 브리핑

Technical Context에 NEEDS CLARIFICATION은 없다(001~004가 언어·저장소 형태·테스트 도구를 이미 확정했고, `/speckit-clarify`가 이 기능 고유의 두 가지 정책 결정을 이미 확정했다). 이 문서는 그 위에서 구현을 실제로 가능하게 하는 설계 결정 7가지를 다룬다.

## 1. "브리핑 실행" 중복 판정의 자연 키

**Decision**: "브리핑 실행"의 자연 키를 `(기준 날짜, 시간대, 대상 범위)`로 삼는다. 사용자가 GET으로 브리핑 화면을 열 때 그 키에 해당하는 스냅샷이 이미 있으면 그것을 그대로 보여주고(새 기록 생성 없음 — 화면 새로고침·네트워크 재시도가 이 경로를 탄다), 없으면 그 시점에 새로 만든다(그 날 처음 보는 것 = 그 날의 "실행"). 사용자가 명시적으로 "다시 실행"을 누르면(`POST /briefing/rerun`) 이 키가 이미 존재해도 무조건 새 스냅샷을 만든다.

**Rationale**: spec.md Edge Cases가 "화면 새로고침"을 "동일 요청 재전송"의 예로 직접 들었고, User Story 3의 두 번째 시나리오는 "같은 날 의도적으로 다시 실행 → 별개의 새 기록"을 요구한다 — 이 둘을 동시에 만족하려면 자동 조회(같은 키 재사용)와 명시적 재실행(키 무시하고 강제 생성)을 서로 다른 경로로 분리해야 한다. spec.md Assumptions는 "동일 요청과 의도적 재실행을 구분하는 구체적 방식은 계획 단계에서 정한다"고 이미 이 결정을 이 문서로 위임해 뒀다.

**Alternatives considered**: 클라이언트가 생성한 `request_id`를 매 요청에 실어 서버가 그 값으로만 중복을 판정 — 브라우저에서 페이지를 여는 단순 GET에는 자연스러운 request_id가 없어(폼 제출이 아님) 클라이언트 쪽에 상태(예: localStorage)를 추가로 둬야 하는데, 이 앱은 단일 사용자 로컬 앱이라 그 정도 인프라가 실익보다 크다. 매 GET마다 무조건 새 스냅샷 생성 — spec.md Edge Cases가 명시적으로 금지.

## 2. 브리핑 스냅샷 저장 위치: 002 공유 캐시 확장 vs 별도 파일

**Decision**: 002·004의 공유 SQLite 캐시(`backend/.cache/learning-loop.sqlite`)에 얹지 않고, 이 기능 전용 파일 `내학습/briefing-history.sqlite`를 새로 만든다. 이 파일은 자체 스키마 버전 상수를 가지며, 002의 `db.ts`처럼 "버전 불일치 → 삭제 후 전체 재생성"을 하지 않는다 — 버전 불일치는 (지금 스키마가 처음이라 실제로는 발생하지 않지만, 미래를 대비해) 예외로 표면화해 사람이 확인하게 한다.

**Rationale**: 001·002·004가 공유하는 원칙은 "SQLite는 파일에서 파생되는 캐시이므로 언제든 지우고 원본 파일에서 완전히 재생성해도 안전하다"이다(웹전환 명세 7.1). 브리핑 스냅샷은 이 전제를 깬다 — 스냅샷의 존재 이유 자체가 "그 시점 이후 원본(로드맵 진행률·복습 대상)이 바뀌어도 당시 값을 그대로 보존하는 것"(FR-014)이므로, "원본에서 재생성 가능"이 아니라 "원본과 독립적으로 보존해야 하는 사실"이다. 이걸 002의 캐시 파일에 넣으면, 향후 002·004의 스키마가 바뀌어 `SCHEMA_VERSION`이 올라갈 때마다(예: 004가 003 이후 그랬던 것처럼) 그 파일 전체가 재생성되면서 브리핑 이력이 통째로 사라지는 사고가 날 수 있다 — 002·004의 코드를 전혀 손대지 않고도 이 위험을 원천 차단하는 가장 단순한 방법은 물리적으로 다른 파일에 두는 것이다.

**Alternatives considered**: 002의 rebuild 로직을 수정해 브리핑 관련 테이블만 재생성 대상에서 제외 — 002·004가 이미 완료·검증된 코드의 핵심 불변식("재적재는 항상 전체 재생성")을 이 기능 하나를 위해 예외투성이로 만들어야 해서, 헌법의 "역할 간 통합 절차"(계약 변경 시 통보·회귀 확인)에 비해 얻는 것보다 위험이 크다. 웹전환 명세 7.1의 "SQLite 파일 하나" 원칙과는 어긋나지만, 그 원칙이 세워질 때는 "파일에서 파생되는 캐시"만 다뤘고 "그 자체가 유일한 원본인 이력 데이터"는 고려되지 않았던 것으로 판단해 이 기능 하나에 한해 예외를 둔다 — 사용자에게 이 예외를 완료 보고 시 명시한다.

## 3. 평균 진행률(FR-011)의 집계 범위

**Decision**: 평균 진행률은 **현재 화면에 표시 중인 로드맵 집합**(scope='all'이면 전체, scope=특정 로드맵이면 그 하나)을 대상으로 계산한다. 로드맵 하나만 보고 있을 때 "평균"은 그 하나의 진행률과 같아진다.

**Rationale**: User Story 2는 "로드맵을 하나만 지정하면 진행률 표에는 그 하나만 나온다"고 명시한다. 표에 안 보이는 로드맵들의 진행률까지 섞은 "평균"을 그 아래 나란히 보여주면 화면 안에서 근거가 안 보이는 숫자가 되어 오히려 혼란을 준다. FR-011의 "대상 로드맵 수와 계산 방식을 표시한다"는 요구도 "대상 = 화면에 보이는 그 로드맵들"로 읽는 것이 자연스럽다.

**Alternatives considered**: 항상 전체 로드맵 기준 평균(스코프와 무관) — 기존 CLI 스킬의 동작과 더 가깝지만, 그 스킬은애초에 "특정 로드맵만 보기"라는 스코프 개념이 없었다(전체 아니면 로드맵 하나로 범위를 아예 좁히는 방식). 화면에 안 보이는 로드맵의 값을 근거 없이 옆에 붙이는 것은 F01 원안의 "화면 조회와 관계 없는 숫자를 만들지 않는다"는 취지에도 맞지 않아 기각.

## 4. 004(복습 데이터) 조회 실패 시 부분 응답

**Decision**: `briefing/service.ts`는 004의 `getReviewQueueStatus()` 호출을 별도로 try/catch한다. 실패하면 로드맵 진행률 부분은 정상 렌더링하고, 복습 목록 부분만 "복습 데이터를 불러올 수 없음"으로 표시하며, **이 경우 스냅샷을 생성하지 않는다**(불완전한 데이터를 "그 시점의 기록"으로 영구 저장하면 FR-014의 "보존된 값" 자체가 거짓이 되므로) — 사용자가 004 쪽 문제를 해결한 뒤 다시 열면 정상적으로 스냅샷이 생성된다. 002(`listRoadmaps()`)의 실패는 이 기능이 별도로 잡지 않고 003이 이미 만든 서버 레벨 오류 미들웨어(503)로 흘려보낸다 — 로드맵 데이터 자체가 없으면 브리핑이라는 화면 자체가 성립하지 않기 때문이다.

**Rationale**: spec.md Edge Cases가 정확히 이 비대칭(004 실패는 부분 성공, 002 실패는 다르게 취급해도 됨을 암시)을 요구한다. 003이 이미 "캐시가 준비되지 않았을 때 503"이라는 검증된 경로를 갖고 있으므로 002 실패는 그걸 재사용하는 것이 새 코드를 추가하는 것보다 안전하다.

**Alternatives considered**: 004 실패도 스냅샷을 생성하되 복습 항목 수를 0으로 기록 — "아직 쌓인 오답이 없습니다"(정상적인 빈 상태)와 "불러오기 실패"를 혼동시켜 FR-009가 요구하는 구분을 깨뜨리므로 기각.

## 5. 진행률 퍼센트 표시 함수: 003과 별개로 새로 작성

**Decision**: 003의 `routes/roadmaps.ts`에 있는 `toProgressLabel()`(반올림 정수 %, "진행 자료 없음"/"미시작"/"완료 N/M (P%)" 세 갈래)을 재사용하지 않고, `briefing/formatProgress.ts`에 FR-004의 정밀한 규칙(완료 0 → "0% (미시작)", 소수 첫째 자리로도 0.0% → "<0.1% (진행 중)", 반올림 시 100.0%인데 미완료 존재 → "<100%", 그 외 소수 첫째 자리)을 새로 구현한다.

**Rationale**: 003의 함수는 로드맵 탐색 화면에서 "대충 몇 % 인지"를 보여주는 용도로 만들어져 정수 반올림으로 충분했다(F02의 요구 수준). F01은 "2/799가 0%로 뭉개져 진행 여부를 알 수 없었다"는 실제 문제(브리핑 스킬 자체의 존재 이유)를 해결하는 기능이라 정밀도 요구가 다르다 — 두 화면이 같은 로드맵 데이터를 놓고 서로 다른 정밀도의 표시 문자열이 필요하므로, 공유 유틸을 억지로 만들어 한쪽 요구에 맞춰 다른 쪽을 왜곡시키지 않는다.

## 6. 라우트 설계: PRG(Post/Redirect/Get) 패턴

**Decision**: `POST /briefing/rerun`은 새 스냅샷을 만든 뒤 그 스냅샷의 `GET /briefing/history/:id`(또는 `GET /briefing?snapshotId=...`)로 303 리다이렉트한다 — 003이 "이어서 공부"에 이미 쓴 302 리다이렉트 패턴과 동일한 관례다.

**Rationale**: POST 응답을 직접 HTML로 반환하면 사용자가 브라우저에서 새로고침할 때 "다시 실행"이 반복 제출될 위험이 있다 — 이는 이 기능이 막으려는 바로 그 중복 생성 문제를 라우팅 계층에서 재현하는 것이므로, 표준 PRG 패턴으로 원천 차단한다.

## 7. `내학습/브리핑로그.md` 포맷: 기존 3줄 보존 + 신규 섹션 추가

**Decision**: 기존 CLI 시절에 쌓인 3개 행(2026-09-16/18/22, 5열 요약 표: 날짜·밀린 복습 개수·진행 중 로드맵 수·평균 진행률·메모)은 그대로 둔다. 새 스냅샷은 그 표 아래에 `## 상세 기록 (웹)` 섹션을 신설해, 스냅샷 하나당 하위 헤딩(`### YYYY-MM-DD HH:mm — 범위`) + 로드맵별 진행률 표 + 복습 대상 표를 이어 붙이는 방식으로 기록한다.

**Rationale**: 기존 3행의 "평균 진행률" 칸에는 단일 숫자와 "네트워크서비스 2.0%(5/251), 데브옵스 0.6%(5/799)" 같은 로드맵별 텍스트가 섞여 있어(F11이 이미 지적한 문제) 기존 표 형식 그대로는 로드맵별 세부 항목·복습 목록까지 담을 수 없다. 표 스키마를 뜯어고쳐 과거 행에 없는 칸을 억지로 채우기보다, 기존 행은 원문 그대로 보존하고(F11의 "원문 보존, 파싱 가능한 것만 구조화" 원칙 상속) 새 상세 기록을 별도 섹션으로 추가하는 쪽이 과거 기록을 훼손하지 않는다. 이 파일은 §2의 결정에 따라 사람이 읽는 감사 기록일 뿐 앱이 다시 파싱해 SQLite를 복원하는 용도가 아니므로, 새 섹션의 정확한 하위 서식이 파서 친화적일 필요도 없다 — 가독성을 우선한다.

**Alternatives considered**: 기존 5열 표에 칸을 추가(로드맵별 상세·복습 목록을 JSON으로 욱여넣는 등) — 과거 3행과 형식이 달라져 표 자체가 깨지고, git diff에서 과거 행까지 재포맷된 것처럼 보여 "원문 보존" 원칙을 해친다.
