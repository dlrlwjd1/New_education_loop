# Phase 0 Research: 자료 이전 기반 (Content Ingestion Foundation)

## 1. 언어/런타임

**Decision**: Node.js (LTS) + TypeScript.

**Rationale**: 사용자가 백엔드 전체(웹앱의 API·비즈니스 로직)를 Node.js/TypeScript로 통일하기로 선택했다(질문 응답, 2026-09-18). Claude Agent SDK가 TypeScript를 정식 지원하므로 구현전_결정사항.md의 "AI 실행 방식"(Claude Code 헤드리스/Agent SDK) 결정과도 맞는다. 프론트엔드도 결국 JS 생태계를 쓸 것이므로 언어를 하나로 통일해 두는 편이 이후 단계(3~8단계)에서 컨텍스트 전환 비용을 줄인다.

**Alternatives considered**: Python — Agent SDK와 Markdown 파싱 생태계는 강하지만, 프론트엔드는 어차피 별도 언어(JS/TS)가 필요해 언어가 두 개로 쪼개진다. 이번 기능 자체(파싱·검증)에는 두 언어 다 적합하므로, 이후 단계까지 감안한 사용자 선택을 따른다.

## 2. Markdown 파싱 방식

**Decision**: AST 기반 파서(`unified`/`remark` + `remark-gfm`)를 사용해 실제 리스트 구조의 체크박스와 코드 블록(fenced code block) 안의 텍스트를 구조적으로 구분한다. 정규식으로 줄 단위 스캔하는 방식은 채택하지 않는다.

**Rationale**: FR-005(코드 블록 안 예시 체크박스는 집계하지 않음)를 정규식만으로 안전하게 만족시키기 어렵다 — 코드 블록의 시작/끝을 잘못 잡으면 오탐이 생긴다. AST를 순회하면 `code` 노드와 `listItem`(checked 속성이 있는) 노드를 타입 수준에서 구분할 수 있다.

**Alternatives considered**: 정규식 줄 스캔 — 빠르지만 코드 블록 경계 추적이 취약해서 기각. 기존 저장소 스킬(`study` 등)이 이미 정규식 기반으로 동작해왔을 가능성이 있지만, 이번 기능은 "원본과 수치 대조 100% 일치"(SC-001)가 완료 기준이라 더 엄격한 파서가 필요하다.

## 3. 체크박스 표기 변형 처리

**Decision**: AST 파싱 전에 `[ x]`, `[x ]` 같은 공백 변형을 표준 GFM 문법(`[x]`, `[ ]`)으로 정규화하는 전처리 패스를 둔다. remark-gfm은 엄격한 GFM 문법(`[ ]`/`[x]`/`[X]`, 추가 공백 없음)만 체크박스로 인식하므로, 그 전 단계에서 관용적 변형을 정규화해야 FR-006을 만족한다. 정규화·AST 파싱 둘 다로 해석할 수 없는 표기는 오류 목록에 남긴다(FR-006, FR-014).

**Rationale**: F11 기존 근거("`[x]`, `[X]`, 공백 변형은 처리하되 해석할 수 없는 항목은 보류한다")를 그대로 따른다.

**Alternatives considered**: remark-gfm의 커스텀 파서 확장 — 가능하지만 전처리 정규화가 더 단순하고 디버깅하기 쉽다.

## 4. 식별자·매칭 규칙

**Decision**: 구조적 항목(로드맵/트랙/Phase/학습 항목)은 로드맵 루트 기준 상대 경로 세그먼트를 정규화한 결정적(deterministic) 해시를 1차 식별자로 쓴다. 자료(`courses/`) 식별자도 동일하게 경로 기반으로 만들되, 재가져오기 시 경로가 일치하지 않으면 파일 내용의 SHA-256 해시로 재확인한다(스펙 Clarifications 세션의 확정 사항). 경로와 해시가 모두 다르면 신규 항목으로 처리한다.

**Rationale**: 스펙 FR-003·FR-010·FR-012에서 이미 확정된 규칙을 그대로 구현 결정으로 옮긴다.

## 5. 자료 색인 자료구조

**Decision**: 자료 색인은 식별자를 키로 하는 맵(해시맵) 구조와, 제목·분류·경로 접두어별 보조 인덱스(맵 기반)를 함께 만든다. 검색은 이 보조 인덱스를 조회하는 것으로 끝나야 하며, 매 조회마다 전체 목록을 선형 스캔하지 않는다(FR-008).

**Rationale**: 7,865개 규모에서 선형 스캔도 기술적으로는 감당 가능하지만, FR-008이 "매번 전체 목록을 순차 비교해야만 하는 구조로 설계하지 않아야 한다"고 명시했으므로 직접 조회 가능한 구조를 처음부터 강제한다. 3단계에서 이 구조를 그대로 저장소로 옮겨 쓸 것이므로(FR-016) 지금 만드는 자료구조의 키 설계가 이후 스키마에 영향을 준다.

## 6. 테스트 프레임워크

**Decision**: Vitest.

**Rationale**: TypeScript/ESM을 별도 빌드 단계 없이 바로 실행할 수 있고, 실제 저장소의 Markdown 픽스처를 스냅샷으로 검증하기 편하다.

**Alternatives considered**: Node 내장 `node:test` — 의존성이 없다는 장점은 있으나 스냅샷·픽스처 편의 기능이 약해 기각.

## 7. 이번 단계의 출력 형태 (영속 저장소 없음)

**Decision**: 이 기능의 실행 결과는 조회 가능한 DB가 아니라, 한 번의 가져오기 실행에 대한 **가져오기 리포트**(구조화된 결과 객체이자 검증용 JSON 출력물)로 산출한다. 로드맵/트랙/Phase/학습 항목/자료/매핑·오류 목록을 담되, 이 리포트를 실제 서비스가 상시 조회하는 저장소로 쓰지는 않는다.

**Rationale**: 스펙 Clarifications에서 확정한 대로 영속 저장소 구축은 3단계 범위다(FR-016). 이 리포트는 (a) SC-001~006을 검증하는 산출물이자 (b) 3단계 구현자가 "이 기능이 정의한 규칙"을 그대로 재사용할 때 참고할 산출물 계약(contracts/ingestion-library.md)의 실제 출력 형태다.
