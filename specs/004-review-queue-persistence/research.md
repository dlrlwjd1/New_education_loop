# Phase 0 Research: 복습큐 자료 이전·영속화

Technical Context에 NEEDS CLARIFICATION은 없다(001·002가 이미 언어·저장소·테스트 도구를 확정했고, 이 기능은 그 결정을 그대로 물려받는다). 대신 스펙을 실제로 만족시키기 위해 필요한 설계 결정 5가지를 여기서 확정한다.

## 1. Markdown 표 파싱 방식

**Decision**: 001이 이미 도입한 AST 기반 파서(`unified` + `remark-parse` + `remark-gfm`)를 그대로 재사용해 GFM 표(mdast `table` 노드)를 파싱한다. 두 표(활성 큐 / 마스터 완료)는 표 순서만으로 구분하지 않고, 그 표 바로 앞에 있는 헤딩(`# 복습큐`의 본문 vs `## 마스터 완료` 헤딩)을 구조적 앵커로 사용해 식별한다.

**Rationale**: 001의 research.md가 이미 "정규식 줄 단위 스캔은 채택하지 않는다"고 확정했고, 코드 블록 안에 우연히 비슷한 표 텍스트가 있어도 AST는 이를 코드로 정확히 구분한다(001의 `isFromCodeBlock` 원칙과 동일). 헤딩을 앵커로 삼는 이유는, 표가 하나만 있는 파일(마스터 완료 항목이 아직 없는 실제 현재 상태)에서도 "두 번째 표가 마스터 완료"라는 순서 기반 가정이 깨지기 때문이다.

**Alternatives considered**: 표 순서(첫 번째=활성, 두 번째=마스터 완료)만으로 구분 — 마스터 완료 표가 아직 없는 파일(실제 저장소 현재 상태가 이렇다)이나 향후 순서가 바뀌는 경우에 오작동할 수 있어 기각.

## 2. 항목 식별자 생성 방식

**Decision**: 각 행의 id를 `sha256(정규화(항목) + "\u0000" + 정규화(주제) + "\u0000" + 처음 틀린 날)`로 계산한다. 정규화는 001의 `normalizeSourcePath`와 같은 원칙(Unicode NFC, 앞뒤 공백 제거)을 텍스트 필드에 적용한 것이다.

**Rationale**: 001의 `resolveIdentity`는 "이번 실행 자체의 누적 원장을 previousBatch로 주입하지 않는다"는 설계를 확정했다(같은 실행 내 우연한 내용 일치를 이전 항목과 잘못 병합하는 버그를 막기 위해서였다 — 001 개발결과.md에 기록된 실제 버그). 이번 기능도 동일하게 매 재적재를 상태 없는 전체 재계산으로 수행하므로, 내용 기반 결정적 id는 "같은 파일을 다시 적재해도 같은 id"(FR-010)를 별도의 이전 배치 비교 없이 만족시킨다. "처음 틀린 날"을 키에 포함하는 이유는, 같은 개념을 나중에 다시 틀려 새 행이 추가되는 경우(재발)를 서로 다른 항목으로 유지하기 위해서다(spec.md Edge Case: 같은 개념·주제 조합이 중복으로 있어도 자동으로 합치지 않는다).

**Alternatives considered**: 행 위치(순번) 기반 id — 사용자가 표를 손으로 편집해 행 순서가 바뀌면 다른 개념에 이전 이력이 잘못 붙는 위험이 있어 기각. 항목 텍스트만으로 id 계산(주제·날짜 제외) — 서로 다른 로드맵에서 우연히 같은 문구의 복습 항목이 생기면 충돌하므로 기각.

## 3. 날짜 파싱 규칙

**Decision**: 날짜 칸(처음 틀린 날, 다음 복습일, 마스터한 날)은 엄격한 `YYYY-MM-DD`(ISO-8601) 형식만 유효한 값으로 인정한다. 그 외 모든 값(빈 칸, 다른 구분자, 자연어 날짜, 오탈자)은 그 행 전체를 "형식 확인 필요" 오류로 분리한다.

**Rationale**: 실제 `내학습/복습큐.md`를 확인한 결과 모든 날짜가 예외 없이 `YYYY-MM-DD` 형식이다. 관대한 파싱(예: `26-9-14`나 한글 날짜 허용)은 실제로 잘못 적힌 날짜를 조용히 잘못된 값으로 통과시킬 위험이 있어, spec.md의 "형식 확인 필요로 분리하고 조용히 누락하지 않는다"는 원칙과 충돌한다.

**Alternatives considered**: 느슨한 날짜 파싱 라이브러리 도입 — 새 의존성을 추가할 만큼의 실익이 없고(실제 파일에 형식 변형이 없음), 오류를 관대하게 흡수해 사용자가 자신의 오타를 발견할 기회를 줄인다는 점에서 기각.

## 4. 저장 위치: 새 SQLite 파일 vs 기존 파일 확장

**Decision**: 002가 이미 만든 캐시 파일(`backend/.cache/learning-loop.sqlite`) 하나에 테이블 3개(`review_queue_items`, `mastered_items`, `review_import_errors`)를 추가한다. `SCHEMA_VERSION`을 1 → 2로 올려, 002가 이미 구현한 "버전 불일치 시 전체 재생성" 경로(`db.ts`의 `RebuildReason: "version-mismatch"`)를 그대로 태운다.

**Rationale**: 웹전환_기능명세_및_개발가이드.md 7.1절이 "로컬 배포에서 파일과 DB의 관계"를 이미 "SQLite 파일 하나"로 확정했다. 두 번째 캐시 파일을 만들면 002가 만든 원자적 교체·손상 복구 로직을 통째로 복제해야 하는데, 이번 데이터량(행 수십 개)에는 그 비용을 정당화할 이유가 없다.

**Alternatives considered**: 001/002처럼 파싱과 영속화를 별도 파일·별도 기능으로 유지 — 001/002의 분리는 "파싱 책임 vs 저장 책임"의 분리였지 "물리적 파일 분리"가 목적이 아니었다. 004는 이미 spec.md 단계에서 파싱+영속화를 한 기능으로 묶기로 확정했으므로, 저장 위치도 기존 파일을 재사용하는 것이 그 결정과 일관된다.

## 5. `reload()` 오케스트레이션 확장 방식

**Decision**: 002의 `reload()`가 001의 `runImport()` 결과를 적재하는 것과 병렬로, 같은 원자적 재생성 패스 안에서 `reviewQueue.parseReviewQueue()`의 결과도 함께 적재하도록 `persistence/load.ts`를 확장한다. 002가 외부에 공개한 다섯 개 조회 함수(`contracts/persistence-library.md`)의 시그니처는 바꾸지 않는다 — 003이 `getMaterialById`를 추가했을 때와 동일하게, 새 함수를 추가하는 additive 변경이다.

**Rationale**: `reload()`를 두 번(로드맵/자료용 1회, 복습큐용 1회) 따로 호출하게 하면, 두 재적재 사이의 시점 차이 때문에 "어느 쪽이 최신 상태인가"라는 002가 애초에 없애려 했던 문제가 다시 생긴다. 하나의 원자적 교체 안에 묶으면 조회 시점에 항상 두 데이터가 같은 스냅샷을 가리키는 것이 구조적으로 보장된다.

**Alternatives considered**: 완전히 독립된 두 번째 `reload()` 진입점 — 위 이유로 기각. 002 계약 자체를 변경(다섯 함수 시그니처 변경) — 003이 이미 그 계약에 의존하고 있어 불필요한 파급 효과가 생기므로 기각(헌법 "역할 간 통합 절차": 계약 변경 시 통보·재작업 필요).
