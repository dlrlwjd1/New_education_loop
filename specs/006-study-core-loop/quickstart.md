# Quickstart: 학습 핵심 루프 검증

이 문서는 006 구현이 끝난 뒤, 스펙의 User Story 1~5가 실제 브라우저에서 동작하는지 확인하는 절차다. 계약은 [contracts/study-service-library.md](./contracts/study-service-library.md)·[contracts/ai-grading-contract.md](./contracts/ai-grading-contract.md)·[contracts/http-routes.md](./contracts/http-routes.md)를, 상태 기계는 [data-model.md](./data-model.md)를 참고한다.

**전제**: 002·004의 캐시가 최소 한 번 적재돼 있어야 하고(004 quickstart.md 참고), `claude` CLI가 로그인된 상태여야 한다(실제 채점 호출에 필요).

## 사전 준비

```bash
cd backend
npm install
npm run typecheck && npm run lint
npm run web
```

브라우저에서 `http://localhost:3000/study/new` 접속.

## 시나리오 1 — 주제 공부의 핵심 왕복 (User Story 1, SC-001·SC-002)

1. "주제 공부"를 선택하고 임의의 주제명(예: "TCP 3-way handshake")을 입력한다.
2. **기대**: 첫 화면이 "지금 아는 것을 적어 주세요"이며 개발자 도구 네트워크 탭으로 응답 본문에 정답·힌트·자료 요약이 없는지 확인한다(SC-001).
3. 사전 지식을 적어 제출한다. **기대**: 15~20초(research.md §1) 후 인출 질문 하나가 표시된다.
4. 근거를 포함한 정답을 제출한다. **기대**: "맞음"으로 판정되고 정교화 단계 전이 안내가 보인다.
5. 새 세션을 시작해 이번엔 오답을 제출한다. **기대**: "유창하지만 틀림"으로 판정되고 제출한 답의 표현이 인용되며, `내학습/복습큐.md`의 활성 큐 표 끝에 새 행이 추가됐는지 확인한다(SC-002). 004의 `/briefing` 화면을 새로고침해 그 항목이 오늘의 복습에 나타나는지도 확인한다(4번 재적재 없이 즉시 반영되는지가 핵심).
6. 같은 세션에서 같은 질문에 다시 오답을 제출해도 복습큐에 중복 행이 생기지 않는지 확인한다(SC-002).

## 시나리오 2 — 힌트 3회와 설명 전환 (User Story 2, SC-003, SC-005)

1. 같은 인출 질문에 계속 오답을 제출해 힌트가 1→2→3회 늘어나는지 확인한다.
2. 세 번째 힌트로도 오답을 제출한다. **기대**: 힌트 대신 짧은 설명(5분/3~5개념 이하 분량감)이 표시된다.
3. 설명을 확인한 뒤 자기 말로 다시 답한다. **기대**: 설명 문장을 그대로 복사해 제출해도 자동으로 정답 처리되지 않고 다시 채점된다.
4. 힌트를 한 번 받은 상태에서 브라우저를 새로고침한다. **기대**: 힌트 횟수가 유지된 채로 이어진다(SC-005) — 0으로 초기화되지 않는다.
5. (선택) 사전 지식 확인에서 "전혀 모릅니다"처럼 재료가 없다고 판정될 만한 답을 제출해, 힌트 없이 곧바로 설명으로 전환되는지 확인한다(SC-003).

## 시나리오 3 — 채점 실패 시 안전망 (User Story 3, SC-004)

```bash
# claude CLI를 일시적으로 PATH에서 숨기거나, 존재하지 않는 바이너리 경로로 바꿔 채점 호출이 실패하도록 재현한다
```

1. 위 상태에서 답변을 제출한다. **기대**: "채점 대기/재시도 가능"으로 표시되고 오답·모름으로 기록되지 않는다(SC-004).
2. `claude` CLI를 원복한 뒤 "다시 채점" 버튼을 누른다. **기대**: 같은 답변으로 채점이 다시 진행되고 정상적으로 판정이 나온다.

## 시나리오 4 — 자료 기반 학습 시작 (User Story 4)

1. "자료로 공부"를 선택해 003의 자료실에서 실제 자료 하나를 고른다.
2. **기대**: 서버가 그 자료를 읽어 제목과 함께 사전 지식 질문을 보여준다. 등록되지 않은 임의 자료 id로 직접 URL을 조작해 접근하면 오류로 안내되는지 확인한다(FR-003).
3. 존재하지 않는 로드맵/주제로 보일 수 있는 애매한 이름을 입력해, 시스템이 조용히 하나를 고르지 않고 선택지를 보여주는지 확인한다(FR-002).

## 시나리오 5 — 자동 제안 (User Story 5)

1. 오늘 복습 대상이 있는 상태에서 아무것도 정하지 않고 학습을 시작한다. **기대**: 그 복습 대상이 가장 먼저 제안된다.
2. (선택) 복습 대상을 모두 처리한 뒤 다시 시작해, 진행 중 로드맵 → 로드맵 후보 순으로 내려가는지 확인한다.

## 자동화된 검증

```bash
cd backend
npm test
```

- `tests/unit/ai.claudeProcess.test.ts` — 타임아웃·비정상 종료·파싱 실패가 모두 `retry_needed`로 수렴하는지(실제 프로세스를 스폰하되, 아주 짧은 타임아웃과 존재하지 않는 명령으로 실패 경로만 결정적으로 검증 — 실제 채점 성공 경로는 이 파일에서 검증하지 않는다).
- `tests/unit/study.sessionMachine.test.ts` — data-model.md 상태 기계 표의 모든 전이 경로를 결정적으로 검증(AI 호출 없이 순수 함수만).
- `tests/unit/study.store.test.ts` — 답변 시도 append-only(재조회 시 UPDATE 흔적 없음), 힌트 유일성(question_id, hint_number) 검증.
- `tests/integration/study.service.test.ts` — `ai/grader.ts`를 모킹해(research.md §7) 전체 흐름(시작→사전지식→질문→오답→힌트×3→설명→정답)을 결정적으로 검증. 004의 `appendReviewQueueItem`도 임시 캐시로 격리해 검증.
- `tests/integration/web.study.test.ts` — supertest로 라우트 계약(303 리다이렉트, 404, 답변 전 정답 미노출) 검증.
- `tests/integration/persistence.appendReviewQueueItem.test.ts` — 004의 신규 함수가 라이브 캐시에 즉시 반영되고 004의 기존 회귀 테스트를 깨지 않는지 검증.

## 수동 확인이 필요한 것 (헌법 원칙 I/IV, 그리고 이 기능 고유의 것)

- 위 시나리오 1~5를 실제 `claude` CLI로 최소 1회씩 구동 — 자동 테스트는 AI를 모킹하므로, 실제 채점 품질과 지연 시간 체감은 반드시 사람이 확인한다(웹전환 명세 6장 원칙, research.md §7).
- 좁은 뷰포트(모바일)에서 답변 입력창·힌트·설명 패널이 가로로 넘치지 않는지.
- 채점 대기(15~20초) 동안 화면이 멈춘 것처럼 보이지 않고 "채점 중"임을 알 수 있는지.
